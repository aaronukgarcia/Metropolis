## 1. Where do the 100M citizens get born?

**Already ruled (Aaron, 2026-09-04, the Q100137 interview, recorded on FEAT-083):**
- The finish line is a **100,000,000-citizen city with INDIVIDUAL citizens**: the Go engine's Option B, *not* the webconsole aggregate.
- **The cloud engine runs it; the browser views it.** Shadow-first grows into view-first.
- Path A (2026-08-31, FEAT-1972079936): the Go engine is authoritative and the webconsole becomes a thin client.

**So yes: citizens are born only in the Go engine.** Any city with individual citizens is Go-engine-only. The TS sim never gets per-citizen records.

**Recommendation for the TS side:**
- Keep it as the **aggregate** model. It serves offline play, small cities and today's dogfooding.
- Do **not** chase citizen-level parity. `internal/converge` already compares at the aggregate level: finance trajectories, and the population domain's per-tick births/deaths table (landed 5e41f10).
- Parity is "same aggregate story, within tolerance", not "same individuals".

**Still open:**
- **Q100138:** the design doc's ASM-1505 assumes the browser stays authoritative through inc4, while the 100M ruling says the cloud runs it. Aaron should confirm that the cut-over point is per domain, following the converge schedule.
- **Recommendation:** the browser stays authoritative for each domain until that domain passes converge. After that the cloud is authoritative and the browser only views.

## 2. How are household bills and traffic modelled at 100M?

**What ships today:**
- **No per-agent pathfinding anywhere.** `engine.traffic` ships a coarse demand-multiplier layer: destination-keyed trip-demand accumulators plus the Stage 1 network primitives. Its `doc.go` states plainly that it is not the full §19 assignment model, after two rounds rejected fabricated "SUE" claims.
- Citizens carry `Home` and `Workplace` as cold columns. Assigning them from built capacity is FEAT-2326609845, in progress right now (Home half drafted).
- Household money flows (wages, consumption, tax) run in Go's `moneycirc` as **monthly passes over the columns**, not as per-citizen event simulation. BUG-666 removed the quadratic row lookups in those passes.

**Recommendation:** keep it this way. Traffic is a **flow/capacity aggregate per road segment or sector** (FEAT-2326609764's 1000 m sectors), fed by home→work origin/destination counts aggregated per sector pair. Citizens hold only `homeCell` and `workplace`. Per-agent A* at 100M is out of scope for this budget and is not planned.

**Still open:**
- Whether the monthly household pass should be **sliced across ticks** (by shard round-robin) or run as one parallel 256-shard pass. That is an engineering choice to be measured at the 10M/30M rungs, not a ruling.

## 3. Acceptable cold-start wait when waking a 10M–100M city

**Nothing is ruled.**

**What is measured:**
- Snapshots today are **NDJSON + gzip, one JSON record per citizen**, about 350–450 B/citizen raw. That is ~35–45 GB raw at 100M (proving plan §2.3).
- The review's "~2 GB compressed Parquet" assumes a format we do not have.
- Hydration time is **unmeasured** at 10M and 100M.

**Recommendation:**
- **100M is a proving run, not a service** (proving plan §2.4). It wakes once on a Spot box and stays up for the run, so its cold start is a one-off minutes-scale load, not a player-facing wait.
- **10M steady state:** set a target of **≤15 s to playable** behind a "Waking city…" screen. Measure it in inc2.
- If it misses, the lever is a **packed columnar snapshot**: write the SoA columns as they are, at about 75 B/citizen instead of 400 B. Do not trade away scale-to-zero.

**Needs Aaron:** is ~15 s acceptable at 10M, in exchange for £0 idle spend?

## 4. Multiplayer interaction model

**Already ruled (2026-08-31, design §1.9):**
- The cloud host is **multi-tenant single-player**: independent cities co-hosted on shared engine instances, **not** shared-world multiplayer.
- The master plan lists multiplayer/shared worlds as a **future slot, "architecture-ready, shelved"** (MASTER v2.1 §future slots, `future.slots.md`).

**Recommendation if it is ever unshelved:**
- Use **independent cities in a shared regional market**: asynchronous, ledger-settled trade in power, water, freight and commuters. It fits the deterministic, journal-owning, one-replica-per-city engine.
- Multiple mayors editing one grid would break the single-writer journal and determinism model, and would need a different engine shape.

**Needs Aaron:** nothing now. This stays shelved unless he unshelves it.

## 5. The real FinOps ceiling once single-player scales up

**Already ruled:**
- **£20/month** steady-state cap (Q100139, 2026-09-04).
- The cap must be a hard cap enforced in Azure (Q100024).
- The design adds an automation runbook as the true stop, because Azure Budgets only alert.

**What the numbers say** (proving plan §2.4):

| Rung | Fits | Cost |
|---|---|---|
| 1M | Consumption | ≈ £2/mo |
| 10M | Consumption, scaled to zero | ≈ £8–15/mo |
| 30M | last rung that fits Consumption | ≈ £15–25/mo |
| 100M | 32–64 GiB; Consumption impossible | £360–725/mo if continuous: **18–36× the cap** |

**Recommendation (already drafted for Aaron, not yet ruled):**
- Stay inside **Container Apps Consumption** for the always-on city, capped at the 10M rung inside £20.
- Run the **100M finale as a budgeted one-off** on a **Spot VM** (`Standard_E16ds_v5`, uksouth): provision, prove, tear down, at ≈ **£0.80–1.60 per 8-hour run**, ≤ £5 per attempt. Each attempt still needs Aaron's Authorise through the cost gate.

**A third option the review missed: pix.**
- Under GGR94 (2026-11-16), project web services move to **pix**, the always-on home PC. If pix has 64 GB of RAM, a 30M–100M proving run there costs **£0 extra** and needs no Azure orchestration at all.
- pix's RAM and its availability for long CPU-bound runs are **unknown**. That is a question, not a plan.

**Needs Aaron:**
- (a) Accept the "£20 steady state + Spot one-off for 100M" shape?
- (b) Is pix a candidate host for the big proving runs? If so, how much RAM does it have?
