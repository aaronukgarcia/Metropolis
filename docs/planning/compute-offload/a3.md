# A3: Where the compute could be cheaper, and what moving it would take

**Date:** 2026-11-17 · **Author:** Bev · **Follows:** `a1.md`, `a2.md`, the rulings in `A2Bev001.md` v23.

**Price caveat.** Provider prices below are **indicative**, from what I last knew. None was re-checked today except Azure's (`docs/planning/inc1-cost-forecast.md`). Any number that decides a move must be re-priced in a cost-gate forecast first.

---

## 0. What the workload actually needs (from the code)

- **One long-running, stateful Go process per city.** It is a plain container: `Dockerfile`, a static `metroserve` binary, `-persist-dir /data`. It holds the whole city in RAM. It must never run as two writers at once (`a2.md` §1.4).
- **RAM is the cost driver, not CPU.**

  | City | RAM |
  |---|---|
  | 1M | ~0.5 GiB |
  | 10M | 2–4 GiB |
  | 30M | 6–8 GiB with paging |
  | 100M | 32–64 GiB |

- **A WebSocket per player session, and tight latency.** Nothing on the frame path waits on the cloud, but one round trip per tick must fit inside **160 ms** at turbo (design §6).
- **Durable storage:** journal plus snapshots. Today that is a local disk; the plan is chunked object storage (inc2).
- **Idle most of the time.** Scale-to-zero, or "stop when idle", is worth more than a low hourly rate.

**What is already portable:**
- The container.
- The engine. Nothing in Go imports any cloud SDK.
- The `persist.Store` interface.

**What is Azure-specific today:**
- `azure-deploy.yml`: `az` CLI, OIDC, the Container Apps flags and the Azure Files mount.
- The *planned* inc2 Blob backend with its Blob lease (`a2.md` §1.3–1.4). It is not built yet.

**So the exit cost is still low, and it is decided in inc2** (§3).

**The short answer:** the cheapest credible steady-state hosts are **pix (£0)** and **Fly.io or Hetzner (single-digit £/month)**. **Cloudflare is not a compute host for this engine.** It is the best **front door** and a cheap **archive store** for any of them. **China-based hosting is ruled out** by latency and law. The China-based companies' international regions offer nothing a European provider doesn't.

## 2. The best combination

**Cloudflare in front, compute wherever it is cheapest, storage portable:**

1. **Cloudflare Tunnel + Cloudflare Access** in front of the engine, on any host: pix, Fly, Hetzner or Azure.
   - TLS and real identity: email or SSO login, replacing the port-knock (Q100025 / Q100144).
   - **No open inbound ports**, which is what makes pix safe to expose.
   - WebSockets pass through.
   - The Access free tier covers a small number of users, which is the case today.
2. **Snapshots and sealed journal segments on S3-compatible object storage.** Cloudflare R2 charges **no egress fees**, which suits cold restores and the Q100149 cool/archive retention. Hetzner Object Storage, AWS S3, Backblaze B2 and Azure Blob (through an S3 gateway, or a thin adapter) all speak the same API.
3. **Compute, by tier:**
   - **Steady-state 1M–10M play:** pix if it is reliably on. Otherwise Fly.io, which auto-stops when idle. Azure Container Apps stays the **managed fallback** inside the £20 cap.
   - **30M / 100M proving runs:** pix if ≥ 64 GB. Otherwise an hourly box (Hetzner large VM, or Spot on AWS or Azure), torn down after each run and cost-gated per attempt.

### Two technical traps any move must respect

- **Architecture and determinism.**
  - Oracle Free (Ampere), AWS Graviton and Hetzner's ARM servers are **arm64**.
  - The Go compiler **fuses `x*y+z` into a single FMA instruction on arm64** but not on amd64, so float64 results can differ in the last bit.
  - The engine has float paths: traffic flow accounting is canonical-order float64 (FEAT-041, `internal/engine/traffic/doc.go`).
  - A city journaled on amd64 and replayed on arm64 **could diverge**, and determinism is GR#21's P0.
  - **Before any arm64 host:** run the CI `determinism-gate` on arm64 and compare its digests with amd64. Until that passes, pin hosts to **amd64**.
- **Single writer.** The Azure Blob *lease* in `a2.md` §1.4 does not exist on S3-compatible stores. The portable design is the **writer epoch plus conditional writes**: S3 `If-Match` / `If-None-Match` on the manifest PUT, which AWS S3, R2 and most S3-compatible stores now support (to verify per provider), plus the OS file lock on local disk (the BUG-799 primitive). That design works everywhere, including Azure, so nothing is lost by choosing it.

## 3. What it would take

| Work | Effort | Needed for |
|---|---|---|
| Build the inc2 `Store` against the **S3 API** (with epoch + conditional-write fencing), instead of the Azure Blob SDK + Blob lease | ≈ same as the planned Blob store (no extra cost if decided now; ~2–3 days of rework later) | every non-Azure option; Azure still works |
| Generic deploy: keep the `Dockerfile`; add one deploy recipe per host (Fly `fly.toml`, Hetzner compose + systemd, pix compose) next to `azure-deploy.yml` | ~0.5–1 day per host | each host chosen |
| Cloudflare Tunnel + Access in front of the engine (replaces port-knock for anything beyond Aaron) | ~1 day | pix exposure; any multi-user step |
| arm64 determinism gate (CI job on an arm64 runner, digest equality vs amd64) | ~0.5–1 day | Oracle Free, Graviton, ARM Hetzner |
| Per-host cost guard: the in-app active-hours meter (R8) is host-agnostic; budget alerts are per provider (Hetzner/Fly spend caps differ) | ~0.5 day per provider | each paid host |
| Data move between providers: copy the object-store bucket (snapshots + journal segments) and restart the engine at the new host. Replay determinism makes the city identical | ~hours | any migration later |

**A full move of steady-state hosting off Azure to pix or Fly, with Cloudflare in front: about 3–5 working days**, most of it shared with inc2. **The only decision that is expensive to reverse is in inc2's storage API.** Choosing S3-compatible plus epoch fencing now keeps every option open at no extra cost.
