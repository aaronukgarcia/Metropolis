## User stories

- **US-1.** As the player, I need a single whole-economy view of money entering (exports, tourism, out-commuter wages, FDI, grants) and leaving (imports, leakage, interest) the city, so §54's "whole-economy view" is one navigable model, not scattered totals I have to add up myself.
- **US-2.** As `ui.screen.finance` (F2, the master fiscal view — code.json's registered consumer), I need `FiscalAPI` to expose a Sankey topology (nodes = flow categories, edges = amounts) sourced from real ledger data, so the text-Sankey rendering (§54 line 741) shows the actual economy, not a hand-tuned illustration.
- **US-3.** As the player, I need public-sector wages shown gross **and** net of the income-tax clawback those same workers pay back, so §54's "civil-service truth, modelled honestly" is a real, queryable pair of numbers.
- **US-4.** As the player funding planning & administration, I need that funding level to demonstrably move permit speed, build-cost error rate, layout bonuses, and corruption risk, so "municipality quality" is a mechanism, not a dial connected to nothing.
- **US-5.** As the player considering a childcare subsidy, I need to see it as a net line (subsidy spend offset by the income tax it unlocks via higher second-earner participation), so §54's "shown as a net line" claim is literally true on screen.
- **US-6.** As `engine.invariant` (MOD-019, already built), I need `engine.fiscal` to never introduce a second, independently-summed money total, so the whole-economy Sankey view is always consistent with the conservation invariant `engine.finance` already registers — one ledger, one truth, many views of it.

## Scope

The whole-economy Fiscal Circuit: a Sankey-topology query over `engine.finance`'s ledger (money-in nodes, money-out nodes, budget as the central node), civil-service gross/net accounting, municipality-quality functions (permit speed, build-cost error, layout bonus, corruption risk as functions of planning-funding level), childcare subsidy net-line accounting, and benefits/social-housing ledger posting. All monetary computation is a *view* over `engine.finance`/`engine.tax`'s existing ledger — `engine.fiscal` posts new transaction categories (civil-service pay, subsidies, benefits) through `FinanceAPI` but never maintains a parallel total.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `FiscalAPI` exists exposing a Sankey-topology query (nodes with a category tag — source/sink/budget — and edges with a `Money` amount) matching code.json's "Sankey topology provider; every band drill-through to ledger" pattern. Check: `go doc ./internal/engine/fiscal FiscalAPI` shows a topology query method returning a node/edge graph type; a passing test asserts the returned graph is well-formed (every edge references an existing node) (`grep -rn "func Test.*[Ss]ankeyTopology\|func Test.*[Ff]lowGraph" internal/engine/fiscal/*_test.go`).
- **AC-2 (§54 money-in/money-out nodes; honest placeholders for unbuilt producers).** The topology includes distinct nodes for exports, tourism, out-commuter wages, FDI, grants (money-in) and imports, leakage, interest (money-out), each sourced from `engine.finance`'s ledger categories via the registered `engine.fiscal`→`engine.finance` edge. Where a producer module doesn't exist yet this sprint (`engine.export`/`engine.tourism`/`engine.fdi`/`engine.defence` grants — all later sprints), that node is present with a documented zero/placeholder value and a `Provisional` flag, never a fabricated non-zero figure standing in for unbuilt data. Check: `go doc ./internal/engine/fiscal` shows all seven category nodes named; a passing test asserts an unbuilt-producer node is queryable and carries a `Provisional`/equivalent flag rather than an invented amount (`grep -rn "func Test.*[Mm]oneyInOut\|func Test.*[Pp]rovisional" internal/engine/fiscal/*_test.go`).
- **AC-3 (§54 income/sales/corp/rates tax shares).** The budget-inflow side of the topology decomposes tax revenue by type (income, sales, corporation, rates & council tax, duties/levies) by querying `engine.tax`'s per-instrument revenue (the registered `engine.fiscal`→`engine.tax` edge) rather than a single lump "tax revenue" figure. Check: `go doc ./internal/engine/fiscal` shows a per-tax-type revenue breakdown method; a passing test asserts the breakdown's sum equals the total tax revenue queried independently from `engine.tax` (`grep -rn "func Test.*[Tt]axBreakdown" internal/engine/fiscal/*_test.go`).
- **AC-4 (§54 civil-service truth — gross vs net, the "modelled honestly" claim).** Public-employee wage cost is reported as two distinct, simultaneously-visible figures: gross wage bill, and net cost (gross minus the income tax those same employees pay back on that wage, queried from `engine.tax`'s income-tax instrument), never collapsed into a single "staff cost" number. Check: `go doc ./internal/engine/fiscal` shows both a gross and a net accessor for civil-service cost; a passing test asserts `net < gross` for any positive income-tax rate and `net == gross` only at a zero income-tax rate (`grep -rn "func Test.*[Gg]rossNet\|func Test.*[Cc]ivilService" internal/engine/fiscal/*_test.go`). **Lazy implementation this rejects:** a fiscal view that only ever shows one "public sector cost" figure (whichever is more flattering, or an average) would satisfy a check that merely asks "is civil-service cost shown" — this check requires both figures to exist and to differ predictably with the tax rate, proving the clawback is actually modelled rather than narrated.
- **AC-5 (§54 municipality quality — the dial-connected-to-nothing trap).** Planning & administration funding level is a documented input (0-100% of a target level, or equivalent) driving four independently-queryable, monotonic outputs: permit-speed multiplier (higher funding ⇒ faster), build-cost error rate (lower funding ⇒ higher error, matching the spec's "10–20% over" example at underfunding), layout-quality bonus (higher funding ⇒ more likely §52 design-code compounding applies by default), and corruption risk (only rises meaningfully at the low end — "rock-bottom funding"). Check: `go doc ./internal/engine/fiscal` shows all four output accessors taking the funding level as an explicit input or reading it from a documented state field; a passing test sweeps funding level across low/mid/high and asserts each of the four outputs moves in its documented direction, with corruption risk specifically asserted near-zero at mid/high funding and materially non-zero at the lowest tested level (`grep -rn "func Test.*[Mm]unicipalityQuality\|func Test.*[Pp]lanningFunding" internal/engine/fiscal/*_test.go`). **False-pass risk:** a test that only checks "corruption risk is a queryable number" would pass a build where it's a constant — the sweep-and-compare-across-funding-levels shape is required.
- **AC-6 (§54 childcare subsidy — the net-line claim).** The childcare subsidy program exposes: gross subsidy spend, the resulting second-earner-participation uplift's income-tax yield, and the net line (spend minus yield) as three distinct queryable values — not a single number the player has to trust is "mostly self-funding". Check: `go doc ./internal/engine/fiscal` shows a `ChildcareNetLine` (or equivalent) type carrying all three fields; a passing test asserts `net == grossSpend - taxYield` exactly for a synthetic scenario (`grep -rn "func Test.*[Cc]hildcare" internal/engine/fiscal/*_test.go`).
- **AC-7 (§54/§40 benefits & social housing; reuse, not a second ledger).** Unemployment support, housing benefit, and the social-housing build programme post through `FinanceAPI`'s existing transaction/ledger machinery (the registered `engine.fiscal`→`engine.finance` edge) — construction cost for social housing specifically reuses `engine.finance`'s construction-settlement stage (per `engine.finance.md`'s AC-3 chain), not a parallel fiscal-only construction cost model. Check: `grep -n "PostTransaction\|SettleConstruction\|FinanceAPI" internal/engine/fiscal/*.go` shows the reuse; a passing test asserts a social-housing build posts through the same ledger category `engine.finance`'s construction stage uses (`grep -rn "func Test.*[Ss]ocialHousing" internal/engine/fiscal/*_test.go`).
- **AC-8 (UI-SPEC §4 drill-through).** Every Sankey node/edge `FiscalAPI` exposes carries a `Lines()`-equivalent traceability method that resolves to `engine.finance`'s actual ledger lines (reusing `FinanceAPI`'s own `Lines(aggregateID)` per `engine.finance.md` AC-11, not a second drill-through index built inside `engine.fiscal`). Check: `grep -n "finance\.Lines\|FinanceAPI" internal/engine/fiscal/*.go` shows the reuse in the drill-through path; a passing test asserts a Sankey edge's drill-through result matches `engine.finance`'s own line query for the same account/category (`grep -rn "func Test.*[Dd]rillThrough" internal/engine/fiscal/*_test.go`).
- **AC-9 (GR#3; no second money total — the conservation-owner trap).** `engine.fiscal` computes every displayed total (money-in sum, money-out sum, budget balance) at query time from `engine.finance`'s `TotalMoneyInCirculation`/per-category ledger queries — it does not maintain its own persistently-accumulated running total that could drift from the ledger. Check: `grep -n "totalIn\s*+=\|totalOut\s*+=\|budgetBalance\s*=.*+" internal/engine/fiscal/*.go` (excluding `_test.go` and pure query-result aggregation within a single call) finds no independently-persisted running total field; a passing test asserts the Sankey topology's node totals recomputed independently from a synthetic `engine.finance` ledger state always match what `FiscalAPI` reports, across at least two different ledger states in the same test run (proving it's recomputed, not cached-and-stale) (`grep -rn "func Test.*[Nn]oDrift\|func Test.*[Rr]ecompute" internal/engine/fiscal/*_test.go`).

### Error handling

- **AC-10 (GR#7).** Querying an unknown Sankey node/flow category returns a registry-sourced error (new `MET-E`-range code) naming the category, never a zero-value node silently returned as if it were a real, built producer. Check: `grep -n "MET-" internal/engine/fiscal/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownCategory" internal/engine/fiscal/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value node was silently returned as if it were a real producer, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-11 (GR#21).** Sankey topology aggregation over per-district or per-shard sub-ledgers is performed in fixed, sorted order — never unordered Go map iteration. Check: `grep -n "for .* := range" internal/engine/fiscal/*.go` on any map feeding a monetary sum is either absent or followed by sorted-key iteration (`grep -n "sort\." internal/engine/fiscal/*.go`); a passing determinism test asserts identical topology output across repeated runs (`grep -rn "func Test.*[Dd]eterminis" internal/engine/fiscal/*_test.go`).
- **AC-12 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/fiscal/*.go` (excluding `_test.go`) returns no matches — the Fiscal Circuit updates on the simulation's monthly tick, never wall clock.
- **AC-13.** `go test ./internal/engine/fiscal/... -race -count=1` passes with no data race when the topology is queried concurrently with `engine.finance`/`engine.tax` ledger updates. Check: `grep -n "go func()" internal/engine/fiscal/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-14.** `internal/engine/fiscal/doc.go` states the module key `engine.fiscal`, cites §54 and Supp.3, states explicitly that every total is recomputed from `engine.finance`/`engine.tax` and that this package owns no independent money total (GR#3), and documents the `Provisional`-flag convention for unbuilt money-in producer nodes (AC-2). Check: `grep -n "engine.fiscal" internal/engine/fiscal/doc.go` and `grep -n "§54" internal/engine/fiscal/doc.go` and `grep -n "engine.finance\|no.*independent.*total\|GR#3" internal/engine/fiscal/doc.go` all match.

## Out of scope

- The actual export/tourism/FDI/grants revenue models (`engine.export` (not yet a distinct BOW item), `engine.tourism` §44, `engine.fdi` §46, `engine.defence` §55 grants — all later sprints) — AC-2's placeholder-node treatment stands in until those land.
- The full tax instrument panel's own elasticity/incidence mechanics (`engine.tax`, this BA's sibling file) — `engine.fiscal` only queries `engine.tax`'s already-computed per-instrument revenue.
- The Public Service Pie's per-service funding sliders and staffing pools (`engine.services`, MOD-033, already-registered `engine.fiscal`→`engine.services` edge) — this item queries service-funding-quality data from that module; it does not own the per-service slider mechanism itself.
- Central-government grants/mandates content (§55, `engine.defence`) — this item's grants node accepts an inbound-grant transaction type when that module lands (per `engine.finance.md`'s own out-of-scope note).
- The text-Sankey **rendering** itself (block-width bands, layout) — that's `ui.diagrams`' job (§ line 741's "three diagram engines"); this item provides the topology data the renderer consumes.
