# Acceptance criteria — engine.season (MOD-027)

**BOW code:** MOD-027
**Spec refs:** §9 Seasonality (`docs/METROPOLIS-MASTER-v2.1.md` lines 224-226: "Month index drives: power demand (winter peak), water stress (summer), harvest calendar... construction speed (winter slowdown), school year (September intake gates)... leisure mix... minor health wave (winter). All seasonal curves visible in projections."); §17 Resource Consumption Model modifiers (lines 285, 291-292, 322: "before seasonal modifiers (§9)"; electricity "winter +15%"; gas "strongly seasonal: ×2.2 Jan, ×0.2 Jul"; water "+25% summer peak"); §3 Time (lines 115-133: two-layer clock, month = day-night cycle, 30 logistics day-ticks/month); code.json `engine.season` entry (inbound `SeasonAPI`, "pure functions of month index from `seasonal.json`"; consumed by `engine.cafe`, `engine.consumption`, `engine.education`, `engine.farming`, `engine.projections`, and others per code.json's full consumer list).
**Date:** 2026-08-08
**Status:** draft-ahead
**Package under test:** `internal/engine/season/` (path from `node claude-bow.js show MOD-027`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/season/...`.

## User stories

- **US-1.** As `engine.consumption` (a later-sprint consumer), I need a pure function of month index returning the winter power-demand multiplier, summer water-stress multiplier, and gas seasonal curve (×2.2 Jan, ×0.2 Jul per §17.2), so utility demand modifiers are one table-driven lookup, not duplicated seasonal logic in every consuming module.
- **US-2.** As `engine.farming`, I need a harvest-calendar curve so local staples arrive in lumps rather than a smooth flow, forcing a real storage-strategy decision (§9).
- **US-3.** As `engine.build`/the construction system, I need a winter construction-speed slowdown curve, so build queues genuinely take longer in winter months, not just cosmetically.
- **US-4.** As `engine.education`, I need a September school-year intake gate — a specific month index (not "any time") where education-stage transitions occur — so the "twenty-year education fuse" (A5) advances on a realistic calendar, not continuously.
- **US-5.** As `engine.cafe`/leisure-adjacent modules, I need a leisure-mix curve (beach-summer / indoor-winter) so venue demand shifts seasonally, matching §41/§42's café-culture and leisure-time systems.
- **US-6.** As `engine.wellbeing` (a later consumer, via the physical-health driver chain), I need a minor winter health-wave modifier, consistent with §18's physical-health drivers.
- **US-7.** As `engine.projections`, I need every seasonal curve visible/queryable ahead of the current month, so projections (§13, the anti-ambush contract) can show a citizen or the player the seasonal shape of an upcoming shortfall, not just the current month's snapshot.
- **US-8.** As GR#15 ("validators derive from data, never hardcoded constants"), I need every seasonal curve loaded from `data/seasonal.json`, so rebalancing a curve during M2 Batch tuning is a data edit, never a code change.

## Scope

Month-index-driven seasonal curve functions (power, water, gas, harvest, construction speed, school-year gate, leisure mix, health wave) loaded from `data/seasonal.json`, exposed as a pure-function `SeasonAPI` consumed by other engine modules; no state of its own beyond the loaded curve data.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `SeasonAPI` (or equivalent) exists whose functions are pure with respect to month index — same month index in, same curve value out, no hidden mutable state, no side effects — matching code.json's documented pattern "pure functions of month index from seasonal.json". Check: `go doc ./internal/engine/season SeasonAPI` shows functions taking a month index and returning a value/multiplier with no receiver-state mutation; a passing test calls the same function twice with the same month and asserts identical results (`grep -rn "func Test.*[Pp]ure" internal/engine/season/*_test.go`).
- **AC-2 (§17.2 electricity).** A power-demand seasonal multiplier function exists, returning the documented winter +15% peak (relative to baseline) at the appropriate winter month(s), consistent with §17.1's "winter +15%" note. Check: `go doc ./internal/engine/season PowerDemandMultiplier` (or equivalent) exists; a passing test asserts the multiplier at the winter-peak month is ≥1.15× the baseline/summer-month value (`grep -rn "func Test.*[Pp]ower.*[Ss]eason" internal/engine/season/*_test.go`), with the expected 1.15 figure transcribed from §17.1, not invented (GR#15).
- **AC-3 (§17.1/§17.2 water).** A water-stress seasonal multiplier function exists, returning the documented +25% summer peak. Check: `go doc ./internal/engine/season WaterDemandMultiplier` (or equivalent) exists; a passing test asserts the summer-peak multiplier is ≥1.25× baseline (`grep -rn "func Test.*[Ww]ater.*[Ss]eason" internal/engine/season/*_test.go`).
- **AC-4 (§17.1 gas).** A gas-demand seasonal curve function exists returning the documented ×2.2 January and ×0.2 July multipliers (relative to baseline), interpolating smoothly between named months rather than stepping discontinuously mid-curve (unless the design deliberately steps at month boundaries — documented either way). Check: `go doc ./internal/engine/season GasDemandMultiplier` (or equivalent) exists; a passing test asserts the January value is ×2.2 and the July value is ×0.2 (`grep -rn "func Test.*[Gg]as.*[Ss]eason" internal/engine/season/*_test.go`), transcribed from §17.1's literal figures.
- **AC-5 (§9 harvest calendar).** A harvest-calendar function exists returning per-crop-category (or a generic staples category, if per-crop detail belongs to `engine.farming` instead — documented which) lumped arrival timing across the year, distinct from a smooth/continuous supply curve. Check: `go doc ./internal/engine/season HarvestCalendar` (or equivalent) exists; a passing test asserts at least one month has a materially higher harvest-arrival value than the yearly average (a genuine "lump", not a flat curve) (`grep -rn "func Test.*[Hh]arvest" internal/engine/season/*_test.go`).
- **AC-6 (§9 construction slowdown).** A construction-speed seasonal multiplier function exists, returning a documented winter slowdown factor (<1.0×) at winter months and ~1.0× (or the data-defined baseline) at other months. Check: `go doc ./internal/engine/season ConstructionSpeedMultiplier` (or equivalent) exists; a passing test asserts winter months return a multiplier below 1.0 and below the summer-month value (`grep -rn "func Test.*[Cc]onstruction.*[Ss]eason" internal/engine/season/*_test.go`).
- **AC-7 (§9 school year).** A September-intake-gate function exists returning true/the gate event exactly at the September month index (and only then) within each simulated calendar year, consumed by `engine.education`'s stage transitions. Check: `go doc ./internal/engine/season IsSchoolIntakeMonth` (or equivalent) exists; a passing test asserts it returns true for September and false for every other month of a full 12-month cycle (`grep -rn "func Test.*[Ss]choolIntake\|func Test.*[Ss]eptember" internal/engine/season/*_test.go`).
- **AC-8 (§9 leisure mix).** A leisure-mix seasonal function exists returning a distribution/weighting shift between at least an outdoor/beach category (summer-weighted) and an indoor category (winter-weighted), consumed by `engine.cafe` and leisure-venue demand. Check: `go doc ./internal/engine/season LeisureMix` (or equivalent) exists; a passing test asserts the beach/outdoor weight peaks in summer months and the indoor weight peaks in winter (`grep -rn "func Test.*[Ll]eisure.*[Ss]eason" internal/engine/season/*_test.go`).
- **AC-9 (§9/§18 health wave).** A minor winter health-wave modifier function exists, returning a small negative adjustment to physical-health drift concentrated in winter months, consistent with §18's physical-health driver list. Check: `go doc ./internal/engine/season HealthWaveModifier` (or equivalent) exists; a passing test asserts the winter-month value is more negative (or lower) than the summer-month value (`grep -rn "func Test.*[Hh]ealthWave" internal/engine/season/*_test.go`).
- **AC-10.** All curve data is loaded from `data/seasonal.json` at package init/load time — no seasonal multiplier literal is hardcoded in Go source (GR#15). Check: `grep -nE "1\.15|1\.25|2\.2|0\.2" internal/engine/season/*.go` (excluding `_test.go`) finds no bare numeric literals matching the §17 figures outside of doc-comment prose transcribing the spec — the actual values are read from `data/seasonal.json`.
- **AC-11 (US-7; §13 projections).** Every curve function accepts a month index in the future (not just the current sim month) and returns a value for it — the API is queryable ahead of time for `engine.projections`' anti-ambush requirement, not restricted to "the current month only". Check: a passing test calls each curve function with a month index >12 months ahead of a fixed "now" and asserts it still returns a valid, non-error value (`grep -rn "func Test.*[Ff]uture[Mm]onth\|func Test.*[Pp]rojection" internal/engine/season/*_test.go`).

### Error handling

- **AC-12 (GR#7).** A malformed or schema-invalid `data/seasonal.json` (missing a required curve, a curve with fewer than 12 defined month points, an out-of-domain multiplier such as a negative construction-speed factor) produces a registry-sourced error (new `MET-E`-range code) at load time, never a silent default-to-1.0 substitution that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/season/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Mm]alformed\|func Test.*[Ii]nvalidSeasonal" internal/engine/season/*_test.go`).
- **AC-13.** Querying a curve function with an out-of-domain month index (negative, or before the world's epoch) returns a typed error rather than an out-of-bounds panic or a silently-wrapped/aliased value the caller didn't ask for. Check: passing test coverage (`grep -rn "func Test.*[Nn]egativeMonth\|func Test.*[Oo]utOfDomain" internal/engine/season/*_test.go`).

### Determinism & safety

- **AC-14 (GR#21).** Every curve function is a pure, deterministic function of month index and the loaded `data/seasonal.json` content — no randomness, no wall-clock dependency, byte-identical output across repeated calls and across worker counts (trivially true for a stateless pure function, but asserted explicitly since this package sits on the hot consumption/construction/education paths of every later-sprint module). Check: a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/season/*_test.go`).
- **AC-15 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/season/*.go` (excluding `_test.go`) returns no matches — every curve is a function of simulation month index only, never wall clock (consistent with M0-ENG §1.1: "nothing in the engine ever calls wall-clock time for logic").
- **AC-16.** `go test ./internal/engine/season/... -race -count=1` passes with no data race when curve functions are called concurrently from multiple consumer modules/shards (the package's read-only, load-once curve data must be safe for concurrent reads without a lock on the hot path). Check: `grep -n "go func()" internal/engine/season/*_test.go` finds at least one concurrency test; `grep -n "sync.Mutex\|sync.RWMutex" internal/engine/season/*.go` shows the load path is guarded but the read/query path is lock-free or read-lock-only.

### Documentation

- **AC-17.** `internal/engine/season/doc.go` states the module key `engine.season`, cites §9 and §17, and lists all eight documented curves (power, water, gas, harvest, construction, school intake, leisure mix, health wave) with a one-line description each. Check: `grep -n "engine.season" internal/engine/season/doc.go` and `grep -n "§9\|section 9" internal/engine/season/doc.go` both match, and all eight curve names appear.
- **AC-18.** `data/seasonal.json` itself carries a `$comment`/`meta` block citing §9/§17 and documenting the month-index convention (e.g. 1=January vs. 0=January — must be unambiguous and match `§3`'s calendar-month convention exactly, since a fence-post error here silently mis-times every consumer). Check: `grep -n "\$comment\|\"meta\"" data/seasonal.json` matches and states the month-indexing convention explicitly.

## Out of scope

- Any consuming module's actual use of these curves (utility network demand calculation, farming's real harvest logistics, education's actual stage-transition mechanics, the projections engine's rendering) — this item only exposes the curve data and pure lookup functions.
- `data/seasonal.json`'s numeric values beyond the specific figures §17.1/§17.2 state explicitly (winter power +15%, summer water +25%, gas ×2.2/×0.2) — every other curve's exact shape (harvest lump timing, construction slowdown factor, leisure-mix weights, health-wave magnitude) is a balance number pending M2 Batch tuning per the sprint plan's roadmap item 4; this item's job is the mechanism and a plausible v1 default, not the tuned final curve.
- Hot-reload of `data/seasonal.json` during a running dev session — that mechanism belongs to `foundation.data` (`MOD-006`); this item only needs to be safely re-loadable when `foundation.data` triggers a reload.
- Any seasonal effect not named in §9's list (e.g. no seasonal crime-rate curve is specified in §9, even though §28 exists) — this item does not invent seasonal drivers the spec doesn't name.

## Escalations

- **Assumption flagged (per BA instructions §3).** This item depends on `MOD-006` (foundation.data, Sprint 0) for the JSON loader and `MOD-012` (engine.core, Sprint 1) for the sim-month/tick concept its month-index parameter is defined against. If `engine.core`'s month-index representation (absolute month count since world epoch vs. a `(year, month)` pair) differs from what this file assumes, the owning BA must refresh AC-1/AC-7/AC-11's signatures at dispatch.
- **For Bill.** §9's prose names eight seasonal effects but gives exact numbers for only three (power +15%, water +25%, gas ×2.2/×0.2, all actually sourced from §17.1 rather than §9 itself). The other five curves (harvest, construction, school intake's exact September timing relative to the two-layer clock, leisure mix, health wave) have no spec-stated magnitude — AC-5/AC-6/AC-8/AC-9 are written to check curve *shape* (a real seasonal variation exists and points the right direction) rather than a specific number, per GR#15's "validators derive from data" doctrine applied to genuinely untuned balance data. Flagging in case Bill wants provisional target numbers specified now rather than left to the junior's judgment ahead of M2 Batch tuning.
