# Acceptance criteria — data.catalogue (FEAT-010)

**BOW code:** FEAT-010
**Spec refs:** Part IV — Appendix A, Building & Object Catalogue (`docs/METROPOLIS-MASTER-v2.1.md` lines 1004-1276: sections R, E, W, H, ED, F/P, G, PK, L, T, PT, HS, C/I, LM, CM/WF); Catalogue Supplement / Supplement 2 / Supplement 3 (lines 490-528, 587-717: MP mega-projects, security & justice, farming & food, mining, comms & logistics, firms/FDI/rail/destination/fuel-chemicals/roads-v2/policies-v2/tunnels/fiscal/defence additions, business & finance, health splits, civic, married-quarters/cadet); §23 Expansion-Content Mapping (lines 386-397); §17 Resource Consumption Model (lines 283-322: "the catalogue never hard-codes utility numbers — coefficients live in `data/consumption.json`"); GR#15 (validators derive from data, never hardcoded constants); code.json `data.catalogue` entry (consumes `foundation.data` MOD-006's loader).
**Date:** 2026-08-10 (refreshed post-security-sweep; supersedes the 2026-08-08 draft)
**Status:** active — `MOD-006` (foundation.data) is `done`; this item is in the Sprint 2 `ready` queue with no open blocking dependency.
**Deliverable under test:** `data/buildings.json`, loaded via `internal/foundation/data/` (path per `foundation.data`, `MOD-006`) — path for this item from `node claude-bow.js show FEAT-010` is `data/buildings.json`.
**Standard gates:** see `README.md` — SG-1/SG-2/SG-3/SG-6 apply as written; SG-4's package is `./internal/foundation/data/...` (the loader that parses and validates this file, since `data/buildings.json` itself has no Go tests of its own); SG-7 does not apply (no Go source in this item's own path) but the loader's use of `time.Now` (if any, e.g. for hot-reload polling) is covered by `foundation.data`'s own acceptance file, not this one.

## What changed since the 2026-08-08 draft

- **Weakness pattern #1 applies to AC-10's uniqueness claim.** "Every entry has a globally-unique `id`" was stated as a test assertion but not as a structural guarantee against the loader's own public API — AC-10b below closes that: the loader itself must refuse to hand back a loaded catalogue that contains a duplicate ID, not merely have a test that happens to check for one.
- **Weakness pattern #4 applies squarely to this item.** `buildings.json` is exactly the kind of "looks like inert data, isn't" surface the sweep's largest class (`input-validation` ×9) was about: `id` values become foreign keys other files (`unlock_trees.json`, save files) look up by string match, and `consumptionRef` values become lookups into `consumption.json` — both are metadata that becomes an **identifier/lookup key**, the exact shape SEC-001's `ShardMeta.Name` and SEC-008/SEC-012's "identifier -> security decision" findings warn about (not a path-traversal risk here specifically, since these are build-time-fixed data, but the same "state the domain positively, reject don't repair" discipline applies to protect every later module's lookup-by-key logic from an ID collision or malformed key silently resolving to the wrong entry). AC-10b/AC-11b below apply that discipline.

## User stories

- **US-1.** As `engine.build`/`engine.services`/the zoning and unlock-economy modules (Sprint 6+), I need every buildable object from Part IV plus Supplements 1-3 encoded as data, so that adding or rebalancing a building is a table edit, never a code change (§17, §24).
- **US-2.** As the unlock economy (`MOD-032`, milestone ladder + development-point trees), I need every catalogue object's unlock gate (milestone tier, development-point cost, achievement/policy prerequisite where applicable) machine-readable, so the unlock UI and the unlock-check logic both derive from one source of truth.
- **US-3.** As `engine.consumption`/the utility networks (§17), I need every catalogue object that draws or produces a utility to carry a coefficient *reference* (a key into `data/consumption.json`), never a hard-coded number in the catalogue itself, so §17's "the catalogue never hard-codes utility numbers" rule holds structurally.
- **US-4.** As the blight/appeal systems (§21 housing appeal profiles, §32 mining/industry blight), I need the subset of objects with a defined blight class or appeal profile to carry that classification in data, so blight-viewshed and appeal-driven migration logic (later sprints) has a real source to read.
- **US-5.** As §23's Expansion-Content Mapping, I need the 'Blue'-pack-equivalent object groups (waterfront-transport, coastal-shoreline, high-rise, high-street-retail, rail-stations, office-tiers) present and traceable back to their originating catalogue section, so the "all in v1 data" claim in §23's own header is verifiably true, not aspirational.
- **US-6.** As `foundation.data`'s hot-reload feature (debug mode), I need `buildings.json` to be a single well-formed, schema-validated file so an in-session edit-and-reload during balance tuning (M2 Batch) never crashes a running dev build on a malformed entry.

## Scope

`data/buildings.json`: every object from catalogue sections R/E/W/H/ED/F-P/G/PK/L/T/PT/HS/C-I/LM/CM-WF plus Supplements 1-3, each carrying unlock gate, cost, capacity/output, a `consumption.json` coefficient reference where applicable, blight class where the spec assigns one, and appeal profile where the spec assigns one (housing typologies, §21).

## Acceptance criteria

### Functional

- **AC-1.** `data/buildings.json` exists, is valid JSON, and validates against a documented schema (JSON Schema file or a Go struct-tag-derived schema check in `foundation.data`'s loader tests). Check: `go test ./internal/foundation/data/... -race -count=1 -v` includes a test that loads `data/buildings.json` and passes schema validation.
- **AC-2.** Every catalogue section table row from Part IV (R, E, W, H, ED, F/P, G, PK, L, T, PT, HS, C/I, LM, CM/WF — 15 sections, `docs/METROPOLIS-MASTER-v2.1.md` lines 1008-1276) has a corresponding entry in `buildings.json`, identified by a stable `id` and a `catalogueSection` field matching its source section code. Check: a validator script/test counts rows per section from a derived reference list (GR#15: the *expected* count is derived from parsing the spec table or from a checked-in row-count manifest generated from it, never a hardcoded literal in the test) and asserts `buildings.json`'s per-section entry count is >= that derived count (some spec rows describe a family/range rather than one strict SKU — see Escalations).
- **AC-3.** Every entry from Catalogue Supplement (line 490: MP mega-projects, security & justice, farming & food, mining, comms & logistics additions), Supplement 2 (line 587: firms/FDI/rail/destination/fuel & chemicals/roads-v2/policies-v2/tunnels/fiscal/defence), and Supplement 3 (line 707: business & finance, FDI anchors, fuel & chemicals, rail industry, destination, tunnelling, health splits, civic, defence) is present, tagged with a `supplement` field (`"S1"`/`"S2"`/`"S3"`) distinguishing it from a base Part IV entry. Check: `grep -c '"supplement"' data/buildings.json` is greater than zero and a passing loader test asserts at least one entry per named supplement category (mega-projects, security & justice, farming & food, mining, comms & logistics, firms, FDI, rail, destination, fuel & chemicals, roads v2, policies v2, tunnels, fiscal, defence, business & finance, health splits, civic).
- **AC-4.** Every entry carries an `unlock` object encoding at minimum a milestone tier (`M1`-`M13`-class value matching §4's ladder) and, where the spec table shows it, a development-point (`+DP`), achievement (`+ach`), or other named gate (`+univ`, `+£`, `+research`) as a structured flag, not folded unreadably into a free-text string. Check: a passing loader test asserts every entry's `unlock.milestone` parses to a known milestone tier, and entries whose spec source shows `+DP`/`+ach`/etc. carry the corresponding boolean/string flag (`grep -n "unlock" internal/foundation/data/buildings_test.go` shows assertions on this shape).
- **AC-5.** Every entry carries cost and capacity/output fields matching its spec table's columns (e.g. R's `Cost/km`, E's `Cost`+`Output/Cap`, HS's `Density (hh/ha)`), using consistent field names across entries of the same shape (e.g. all linear/per-km objects use the same cost-unit field) rather than one ad hoc field per row. Check: a passing loader test spot-checks representative entries against the spec's literal numbers for at least one row per section (e.g. "Residential street" cost = 250k per §R, "Nuclear station" cap = 1,200 MW per §E) — GR#15: these expected values are transcribed from the spec table into the test, not invented.
- **AC-6 (§17).** No entry contains a raw utility consumption/production number (water L, electricity kWh, gas kWh, waste kg) inline — every utility-relevant entry instead carries a `consumptionRef` (or equivalent) key resolvable against `data/consumption.json`'s class coefficients (§17.2's per-user coefficient table). Check: `grep -n "\"waterL\"\|\"elecKwh\"\|\"gasKwh\"" data/buildings.json` finds no matches (those numbers live only in `consumption.json`); `grep -n "consumptionRef\|consumptionClass" data/buildings.json` finds matches on utility-relevant entries.
- **AC-7.** Entries the spec assigns a blight class to (mining/quarrying, chemicals complex, toxic/hazardous waste processing, heavy industry, defence air bases, dairy/abattoir per Supplement 1) carry a `blightClass` field with a value from a documented enum (e.g. `none`/`low`/`medium`/`high`/`max`), matching the spec's own qualitative language (e.g. toxic waste processing = "max blight class" per line 591). Check: a passing loader test asserts `blightClass == "max"` for the toxic/hazardous waste processing entry and a non-`"none"` value for the chemicals complex and heavy-industry-estate entries.
- **AC-8 (§21).** Every HS — Housing Typology entry carries an `appealProfile` field capturing its "profile sketch" column content (e.g. Detached: `["garden-water-plus","wealth"]`; Beach house: `["premium","shore-only"]`) as structured tags, not just the free-text notes column verbatim. Check: a passing loader test asserts every one of the 17 HS-section entries (line 1206-1225) has a non-empty `appealProfile`.
- **AC-9 (§23).** Every §23 'Blue'-pack-equivalent group (waterfront-transport → port catalogue §PT; coastal-shoreline → beach/waterfront entries; high-rise/high-rise → HS high-rise/penthouse + LM landmark towers; high-street-retail → pedestrianised high street + mixed-use blocks; rail-stations → T station variants; office-tiers → C/I office tiers) is present and each group's entries are tagged with a `sourcePack` (or equivalent) field naming the §23 row it fulfils, so §23's coverage claim is checkable, not asserted by prose alone. Check: a passing loader test asserts at least one `buildings.json` entry per §23 table row (6 rows) carries a matching `sourcePack` tag.
- **AC-10.** Every entry has a globally-unique `id` (stable across data edits — used as the foreign key from `unlock_trees.json`, save files, and future engine modules). Check: a passing loader test asserts zero duplicate `id` values across the whole file.
- **AC-10b (weakness pattern #1 — the loader enforces uniqueness, not just a test).** The loader's public load path itself refuses to return a usable catalogue when a duplicate `id` is present — a duplicate is a load-time failure (AC-11's registry-sourced error), not something only a separate test-suite assertion happens to catch after the fact while the loader itself would have silently returned the last-parsed entry under a shared key (classic last-write-wins duplicate-key JSON-decode behaviour). Check: `go doc ./internal/foundation/data` (buildings-loader section) documents that duplicate-`id` is a load-time rejection; a passing test constructs a fixture with a duplicate `id` and asserts the loader's public entry point returns an error, not a catalogue silently missing one of the two entries (`grep -rn "func Test.*[Dd]uplicateID" internal/foundation/data/*_test.go`).

### Error handling

- **AC-11 (GR#7).** Loading a `buildings.json` that fails schema validation (missing required field, unknown `blightClass` enum value, duplicate `id`, dangling `consumptionRef` to a class absent from `consumption.json`) produces a registry-sourced error (new `MET-`-range code in `data/errors.json`, following `foundation.data`'s own reserved range) identifying the offending entry `id` and field, not a generic parse failure. Check: `grep -n "MET-" internal/foundation/data/*.go` finds a registry code reference used by the buildings-loader path; passing tests cover at least one malformed-entry case per failure class named above (`grep -rn "func Test.*[Bb]uildings.*[Ii]nvalid\|func Test.*[Dd]angling" internal/foundation/data/*_test.go`).
- **AC-12.** A `consumptionRef` that doesn't resolve against a currently-loaded `data/consumption.json` is caught at load time (cross-file validation), not left to fail silently the first time an engine module tries to look up the coefficient at runtime. Check: passing test coverage (`grep -rn "func Test.*[Cc]onsumptionRef" internal/foundation/data/*_test.go`).
- **AC-12b (weakness pattern #4 — id/consumptionRef are lookup keys, name the domain positively).** Both `id` and `consumptionRef` (and `sourcePack`, `blightClass`, `catalogueSection`, `supplement` — every field AC-9/AC-16 name as structured-tag fields other code will switch/match on) have a positively-stated allowed character domain documented at the schema level (e.g. `id`: `^[a-z][a-z0-9_.-]{2,63}$`, no whitespace, no path-separator characters, since a future save-file or `unlock_trees.json` cross-reference will use these strings as map keys and, in `metctl`/debug tooling, potentially as on-disk file/log identifiers) — "a well-formed string" is not sufficient, the exact character class is named. A value outside the domain is a load-time rejection (AC-11), never trimmed/normalised into the nearest legal form. Check: `docs/design/buildings-schema.md` (AC-16) states the positive character-class regex/rule for `id` and `consumptionRef`; a passing loader test asserts an `id` containing a disallowed character (e.g. a path separator or leading digit) is rejected, not silently accepted or normalised (`grep -rn "func Test.*[Ii]dFormat\|func Test.*[Ii]nvalidID" internal/foundation/data/*_test.go`).

### Determinism & safety

- **AC-13 (GR#21).** Loading the same `data/buildings.json` twice produces byte-identical in-memory structures / an identical validation result — no map-iteration-order-dependent behaviour in the loader's validation error ordering (errors, if any, are reported in a stable, sorted order by entry `id`). Check: `grep -n "sort\." internal/foundation/data/buildings.go` (or equivalent) shows sorted error/entry ordering; a passing determinism test exists.
- **AC-14.** `data/buildings.json` itself contains no timestamp, machine-specific path, or other non-reproducible value — it is pure static balance data, consistent with GR#15's "validators derive from data" doctrine requiring the data itself to be a stable source of truth. Check: `grep -n "\"[0-9]\{4\}-[0-9]\{2\}-[0-9]\{2\}T" data/buildings.json` finds no ISO-timestamp values inside entry bodies (a top-level `"generatedAt"`/`"version"` metadata field, if present, is fine and excluded from this check).

### Documentation

- **AC-15.** `data/buildings.json` carries a top-level `$comment`/`meta` block citing Part IV and the three supplements by line-range or section list, mirroring the convention already used in `data/errors.json`'s `ranges` block and `code.json`'s `$comment`. Check: `grep -n "\$comment\|\"meta\"" data/buildings.json` matches and the value mentions "Part IV" or "catalogue".
- **AC-16.** A schema reference document (`docs/design/buildings-schema.md` or `data/buildings.schema.json`) describes every field this item introduces (`unlock`, `blightClass`, `appealProfile`, `consumptionRef`, `sourcePack`, `catalogueSection`, `supplement`), so later data-editors (M2 Batch tuning) have a field reference without reverse-engineering the loader. Check: file exists and lists all seven field names.

## Out of scope

- `data/consumption.json`'s actual coefficient values — this item only references coefficient *classes*; populating/tuning the numbers behind those classes is `engine.consumption`'s (`MOD-021`) concern, itself sourced from §17.1/§17.2's tables.
- `data/unlock_trees.json` (development-point trees, XP costs) — this item's `unlock` field records the gate an object requires; the tree/economy that grants development points is `MOD-032`'s (`engine.unlocks`, Sprint 4) job.
- Any engine-side consumption of this catalogue (zoning placement rules, build-queue logic, blight-viewshed rendering) — those are `engine.build`/`engine.services`/later-sprint modules; this item only produces and validates the data file.
- Hot-reload runtime behaviour itself (file-watch, live diff-apply while a dev build is running) — that is `foundation.data`'s (`MOD-006`) mechanism; this item only needs to produce a file that mechanism can successfully hot-reload without crashing (AC-1's schema validation is the contract that guarantees this).
- Balance correctness of costs/capacities (M2 Batch tuning territory, per the sprint plan's roadmap item 3) — this item transcribes the spec's stated v1 defaults faithfully; it does not invent or tune numbers itself.

## Escalations

- **For Bill (new).** AC-12b invents an illustrative `id` character-class regex (`^[a-z][a-z0-9_.-]{2,63}$`) since neither Part IV nor `foundation.data`'s own acceptance file mandates one. This is a genuine implementer/BA judgment call, logged as **ASM-082** (`node claude-bow.js show ASM-082`) — flagging because the exact regex affects how much of the existing spec's building names ("Nuclear station", etc.) need slugifying into IDs, which is exactly the kind of decision that's cheap to get right now and expensive to change once `unlock_trees.json` and save files start referencing these IDs as foreign keys.
- **For Bill.** Part IV's tables are not uniformly one-row-per-SKU — some rows describe a range or family (e.g. R's "Junction controls: signals / mini-rbt / roundabout / grade-separated" is one table row covering four distinct unlock tiers and a cost range `80k–8M`; Supplement lists (farming & food additions, line 517) are a flat comma-separated list, not a table at all). AC-2/AC-3's "derived expected count" therefore requires a judgment call per section on whether a spec row/list-item becomes one `buildings.json` entry or several. The BA has scoped AC-2/AC-3 to "at least the derived count" rather than an exact count to avoid over-constraining this, but the exact row-to-entry mapping is a real modelling decision the junior (or Bill, at brief time) should make and record — not something a Tester can mechanically verify beat-for-beat, given the spec's own inconsistent table shapes.
- **For Bill.** §17's coefficient-reference rule (AC-6) and §21's appeal-profile structuring (AC-8) require judgment about which catalogue objects are "utility-relevant" or "housing typologies" versus decorative/non-mechanical entries (e.g. Landmarks & Uniques, `LM`, are largely one-off flavour objects with bespoke `Effect` text rather than a capacity/coefficient shape) — flagging so a Sprint 2 review doesn't fail the item over LM/CM-WF entries that structurally don't fit the utility/appeal schema by spec design.
- **Assumption flagged (per BA instructions §3).** This item depends on `MOD-006` (foundation.data, Sprint 0) for the loader/validator and hot-reload mechanism it validates against. If `foundation.data`'s schema-validation approach (JSON Schema library vs. hand-rolled Go validation) isn't settled by Sprint 2 dispatch, AC-1's "validates against a documented schema" check should be read as "the loader's own chosen validation mechanism accepts the file and rejects deliberately broken fixtures" rather than mandating a specific schema technology.
