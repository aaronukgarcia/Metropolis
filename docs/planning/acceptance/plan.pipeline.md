# Acceptance criteria — code.json bidirectional consistency audit (FEAT-062)

**BOW code:** FEAT-062 (P1, open) — "A full both-ways robustness check of code.json against the actual tree, dispatched by Bob to a dedicated agent."
**Spec refs:** GR#3 (Single Source of Truth — no duplication without validation); GR#6 (GUID Documentation — read comments before changing code, update GUID versions and code.json); GR#20 (Contract-First, Stub-Forever — modules consume each other only via registered interfaces); `tools/plan/generate.js` and the plan-pipeline description ("`docs/planning/master-plan-v2.1.json` as SSOT ... mints stable GUIDs ... emits `code.json`"); `.claude/commands/codejson-audit.md` item 4 ("Source coverage... every source directory maps to a code.json entry. Report orphans both ways") — FEAT-062 is that check's full, dedicated, name/type-matching successor, not a duplicate of it; BUG-058 precedent (registry gaps filed as one BOW item per drift **class**, not one per instance); `dev-team-process.md` "An acceptance criterion's CHECK must be able to fail" (v1.9); `metropolis-balance-number-regime` (no fabricated fixed numeric thresholds — not the primary concern for a structural audit, but AC-11 below states explicitly where it could have leaked in and why it doesn't).
**Date:** 2026-08-13
**Status:** active — normal pipeline order (criteria written before dispatch)
**Audit scope:** whole-repo, read-only. Inputs: `code.json` (generated artifact), `docs/planning/master-plan-v2.1.json` (SSOT), the `metro` BOW (`bow_items.status`, queried via `claude-bow.js`/direct read), and the real Go source tree (`cmd/`, `internal/`). No package "under test" in the usual sense — the audit produces a **report**, and this file's checks are checks on that report's correctness and on the agent's own conduct (did it hand-edit anything, did it file findings correctly), not on a compiled artifact.

## User stories

- As **Bill**, I need to know that every `code.json` module entry still points at a real path and a real, name-matching Go contract, so a stale registry entry is never silently trusted as ground truth for a downstream brief (the exact failure class GR#3/GR#20 exist to prevent).
- As **a Jnr developer picking up a module**, I need to know my package isn't an unregistered orphan — an implementation with no `code.json` entry has no GUID, no spec ref, and no BOW item, so it is invisible to the whole planning pipeline (`generate.js`, the BOW import, `/sprint`) even though it exists on disk.
- As **the plan pipeline itself (`tools/plan/generate.js`)**, I need drift reports to route through the SSOT (`master-plan-v2.1.json`) + regenerate, never through a hand-edit of `code.json`, so the generated-artifact invariant this whole pipeline depends on (GR#3) is never quietly broken by an audit that "helpfully" patches the symptom instead of the source.
- As **Bill triaging findings**, I need one BOW item per distinct drift *class* across however many instances it has, not a flood of one-off items, so the registry-gap backlog stays legible (BUG-058 precedent) and each item names a fixable pattern rather than a single symptom.

## Definitions (binding on the audit — read before running it)

- **"Expected to exist" gate (GR#15 — derived from data, not a hardcoded sprint cutoff).** A module is only faulted for a **missing** path, missing exported symbols, or a missing call edge if its BOW item's current `status` (queried live via `claude-bow.js show <mkey>` or an equivalent direct query — never a hardcoded sprint number or a copy of "S0–S2 are closed" typed into the audit's own source) is `done`. A module whose BOW item is `open`/`in_progress`/`blocked` and has no code yet, or partial code, is **not-yet-built** — record it in the report under a separate "not yet built" heading, not as a Direction-A finding. This is the load-bearing distinction that keeps the audit from manufacturing ~60 false findings against modules nobody has started (confirmed at draft time: of 106 `code.json` module entries, roughly 64 have no path on disk yet and nearly all of those correlate with non-`done` BOW status — see AC-1's check for how a passing run must reproduce this split from live data, not from a snapshot number pasted into this file).
- **"Contract" (Direction A, interface/GUID correspondence).** `code.json`'s `inbound`/`outbound` blocks per module: `inbound.name`, `inbound.format`, `inbound.pattern`, `inbound.consumers[].key`/`outboundGuid`, `outbound.calls[]`. "Corresponds to real exported Go symbols" means: the named inbound contract can be matched to an exported Go type/interface/function in the module's package whose identifier is the same string (character-for-character, see AC-5) as `inbound.name`, once the module's BOW status is `done` (per the gate above).
- **"Call edge"** means a `code.json` `outbound.calls[]` entry (or a consumer's matching `outboundGuid` on the far side) asserting module X calls into module Y's contract. "Corresponds to an actual import/call relationship" means: X's Go package actually imports Y's package (or Y's declared interface package, e.g. `internal/protocol`) and the import is used (not a dead/unused import), once both X and Y are `done`.

## Acceptance criteria

### A. Direction A — registry to code

- **AC-1 (path resolution).** For every entry in `code.json`'s `modules[]`, the audit resolves `path` against the real filesystem from repo root and records one of three states: `path-exists-done` (path exists, BOW status `done`), `path-missing-done` (path does **not** exist, BOW status `done` — this is a **finding**, Direction-A Class "missing path"), or `not-yet-built` (BOW status not `done`, regardless of whether the path happens to exist as an empty scaffold directory). Check: the report's per-module table has exactly 106 rows (or the current `moduleCount` at run time — pulled from `code.json` itself, never hardcoded into the audit), the three-state counts sum to the total, and re-running the audit against unchanged repo state reproduces identical counts (determinism — a report that classifies differently on two back-to-back runs against the same commit is itself a defect in the audit, not a repo finding). **False-pass warning:** a report that only lists modules with `path-missing-done` findings, with no visible count of `not-yet-built` or `path-exists-done`, cannot be checked for completeness by a reviewer — the Tester rejects a report that omits the full three-state breakdown even if the findings list itself happens to be correct.
- **AC-2 (contract/GUID correspondence).** For every `done`-status module with an `inbound.name` set (not `null`), the audit greps/parses the module's Go package (per `path`) for an exported declaration whose identifier equals `inbound.name` exactly. A match is `contract-ok`; no match is a **finding** (Direction-A Class "contract name does not resolve to an exported Go symbol"). Every `guid` field on the module, its `inbound`, and its `outbound` block is checked for well-formedness (valid UUID v4 shape, per `generate.js`'s own minting convention) and for **uniqueness across the whole `code.json`** — a duplicate GUID reused across two entries is a finding regardless of `done` status, since a colliding GUID is a data-integrity defect the moment it exists, not something that waits for code to catch up. Check: a report row exists for every `done` module with a non-null `inbound.name`, stating match/no-match and the Go file/line where the match was found (or "not found" plus the files actually searched, so a reviewer can spot-check a no-match finding by opening the named package themselves); a separate GUID-uniqueness table shows zero duplicates or names the colliding entries.
- **AC-3 (call-edge correspondence).** For every `done`-status module X with a non-empty `outbound.calls[]`, and for every consumer entry Y lists against X's `inbound.consumers[]` where Y is also `done`, the audit confirms a real Go import relationship in the stated direction (X's package imports Y's declared package path, or vice versa per which side is asserted) using `go list -deps` or an equivalent static import check (not a text grep for the package name in isolation, which would false-positive on a comment or a string literal mentioning the path). An asserted call edge with no matching import is a **finding** (Direction-A Class "call edge not backed by a real import"). Check: the report's call-edge table lists every checked edge (both endpoints `done`) with a pass/fail per edge; a passing run against the current repo state is re-run twice and produces identical edge lists and verdicts (determinism, same standard as AC-1). **What a lazy implementation looks like:** grepping `strings.Contains(fileContents, "protocol")` to "confirm" an import — this passes on a package that merely mentions the word `protocol` in a comment while never importing `internal/protocol`, and fails to catch a real import written as a dot-import or aliased import; `go list -deps` (or parsing the AST import spec list) is the check that cannot be satisfied by incidental text.

### B. Direction B — code to registry

- **AC-4 (orphan directory detection).** The audit walks `internal/` and `cmd/` and, for every directory that contains at least one `.go` file, checks whether some `code.json` module entry's `path` resolves to that exact directory (or a documented parent/child relationship the audit states explicitly — e.g. a package split across subpackages under one registered module path must be named as such, not silently treated as N orphans). A Go-bearing directory with no corresponding `code.json` entry is a **finding** (Direction-B Class "orphan directory — Go code with no registry entry"). Check: the report lists every directory under `internal/`/`cmd/` containing `.go` files (a count derivable from `find internal cmd -name '*.go'` grouped by directory, restated in the report so a reviewer can cross-check the denominator), each marked registered/orphan; a fixture check — the Tester creates a throwaway directory `internal/_fixture_orphan/x.go` with a trivial package declaration, re-runs the audit, and confirms it appears as a new orphan finding, then deletes the fixture and confirms the finding disappears on the next run (this is the AC's fail-able mutation, per `dev-team-process.md` v1.9 — a check that only ever reads the current, already-clean tree cannot prove it would catch a real orphan).
- **AC-5 not applicable here** — see Direction A/C, name matching is a registry-to-code concern (does the recorded name match the real declaration), not a code-to-registry existence concern; Direction B is existence-only by design (a directory either has a registry entry or it doesn't — there is no "orphan directory's name is wrong" case, since an orphan has no registry name to compare against).

### C. Name/type character-for-character matching

- **AC-6.** Wherever `code.json` records a contract name, a field name, or a type string that is meant to name a real Go declaration (`inbound.name`, `inbound.format` where it names a concrete Go type rather than a prose description, any future `type:` fields introduced by the plan schema), the audit compares it **character-for-character** (case-sensitive, no fuzzy/substring match) against the actual Go source identifier. A near-miss (case difference, pluralization, an extra/missing word) is a **finding**, distinct from AC-2's "does not resolve at all" — this class is "resolves to something similar but not identical," which is the harder-to-notice drift GR#20's contract-first discipline exists to catch before it becomes a real interface mismatch. Check: the report separates "no match" (AC-2) findings from "near-miss, case/spelling drift" (AC-6) findings, each with the recorded string and the actual Go identifier printed side by side; a fixture test — the Tester temporarily renames one already-`done` module's exported contract type by one character in a throwaway git-stash-free local edit (not committed), re-runs the audit, confirms a Class-C finding appears naming exactly that mismatch, then reverts the edit (`git checkout -- <file>`) and confirms the finding disappears. **False-pass warning:** a check using `strings.ToLower(a) === strings.ToLower(b)` or any substring/Levenshtein-threshold comparison would silently swallow real case-sensitivity bugs in Go (exported vs. unexported spelling is semantically load-bearing in Go, not cosmetic) — character-for-character, case-sensitive equality is the only comparison this AC accepts as correct.

### D. Read-only / report-only constraint

- **AC-7.** The audit never modifies `code.json` under any circumstance, including a "helpful" formatting or drift fix. Check: `git status --porcelain code.json` (and `git diff code.json`) show **zero** change immediately before and after the audit runs, for the entire duration of the audit's execution (not merely "reverted before the report was filed" — a mid-run edit that gets reverted still violates the constraint and this check is written to catch it via a file-hash comparison taken before the run and compared after, not merely a final `git status`).
- **AC-8.** The audit never modifies `docs/planning/master-plan-v2.1.json`, any file under `internal/`/`cmd/`, or any BOW row directly (no raw SQL, no `claude-bow.js set`/`comment`/`done` calls made as a side effect of investigation) except the sanctioned finding-filing calls in AC-10. Check: same before/after hash comparison as AC-7, extended to `docs/planning/master-plan-v2.1.json` and a sampled set of Go files the audit read; `node claude-bow.js list --by-seq` diffed before/after shows no row changed except the new finding items themselves.
- **AC-9.** Every finding in the report states its fix route explicitly, using exactly one of two labels, per the constraint in FEAT-062's own description: **(a) "master-plan fix"** — the drift is in `code.json`/the plan (e.g. AC-1's missing-path class where the plan lists a path that was renamed on disk, or a genuine registry typo) and the fix is "edit `docs/planning/master-plan-v2.1.json`, then `node tools/plan/generate.js` to regenerate `code.json`" — never a direct `code.json` edit; or **(b) "code-side defect"** — the drift is in the Go source (e.g. an exported symbol was renamed without updating the plan, or an import was removed but the call edge was never un-registered) and the fix is a code change, filed as its own BOW item. Check: every finding row in the report carries one of these two labels; a report row with neither, or with both, is a FAIL on this AC — ambiguity about which side owns the fix is itself a defect in the report, not a detail a reader can be left to infer.

### E. Findings filing (BUG-058 precedent — class-based, not instance-based)

- **AC-10.** Findings are filed to the BOW as **one item per distinct drift class** (per the class labels used throughout this file: Direction-A missing-path, Direction-A contract-does-not-resolve, Direction-A call-edge-not-backed-by-import, Direction-A duplicate-GUID, Direction-B orphan-directory, Direction-C name/type near-miss), each item's description or an attached comment enumerating every instance of that class found in this run (module keys, paths, line numbers) — mirroring BUG-058's own shape ("registry gaps are a class defect, not one-off"). A class with zero instances in a given run files **no** item (an empty class is not a finding). Check: `node claude-bow.js list --by-seq` after the audit shows at most six new items (one per class actually populated, per this run's findings), not one item per individual instance; `node claude-bow.js show <new-code>` on each shows the full instance enumeration in the body/comment, not merely a count. **What a lazy implementation looks like:** filing one BUG per orphan directory found — if AC-4's fixture check alone would file a new BUG on every Tester re-run, that is the exact anti-pattern BUG-058 was cited to prevent; the check (item count ≤ class count, not ≤ instance count) rejects it directly.
- **AC-11 (no fabricated numeric thresholds).** Where a finding's class could tempt a fabricated tolerance (e.g. "flag only if more than N orphan directories exist," or "ignore GUID collisions below some severity score"), the audit applies none — every instance of every populated class is reported and filed, full stop, matching this project's balance-number-regime instruction against inventing thresholds nobody asked for. This is a structural/correctness audit (a path either exists or it doesn't, a GUID either collides or it doesn't), so the risk surface is small, but the AC exists to name it rather than leave it to an implementer's judgement call under time pressure. Check: reviewed by eye against the report — no threshold, percentage, or "top N" cutoff appears anywhere in the audit's own logic or report framing.

### F. Report completeness and reproducibility

- **AC-12.** The report states, at the top, the exact commit hash (`git rev-parse HEAD`) the audit ran against and the `code.json`/`master-plan-v2.1.json` content hashes at that commit, so a later re-run against a different commit is never confused with this one. Check: present and matches `git rev-parse HEAD` taken independently by the Tester at report-review time (or the commit named, if the Tester reviews after further commits landed).
- **AC-13.** Running the audit twice back-to-back against the same unchanged commit produces byte-identical findings (module lists, orphan lists, GUID tables) modulo only the timestamp/run-id header — no nondeterministic ordering (e.g. unsorted directory-walk order or Go map iteration leaking into the report). Check: two consecutive runs' finding tables diffed show no difference outside the header.

## Out of scope

- Fixing any drift found — this item's agent is report/file-only; a "master-plan fix" finding's actual plan edit + regenerate, and a "code-side defect" finding's actual code fix, are separate BOW items dispatched through the normal Jnr-developer pipeline, not this audit's own commit.
- Auditing `data/errors.json`, `data/modes.json`, or any other registry outside `code.json`/the Go tree — out of FEAT-062's stated scope (registry-vs-code only).
- Re-litigating whether `/codejson-audit`'s existing lighter-weight items 1–3 (plan validity, plan/code.json drift, BOW mirror spot-check) are still adequate — this file's Direction A/B/C criteria supersede only that skill's item 4 ("source coverage"), not items 1–3, which remain that skill's job.
- Performance/scale of the audit itself (how long a full-repo Go AST walk takes) — not a criterion here; if it becomes slow enough to matter, that is a future BOW item, not a blocker on this one's correctness.

## Escalations

- **The "expected to exist" gate (Definitions section) ties findings to live BOW `status`, not to a sprint-number cutoff typed into this file** — a deliberate GR#15 call. If Bill prefers a different gate (e.g. "sprint ≤ current closed sprint" sourced from some other data field), that is a design change to this file, not assumed silently; flagged rather than pre-empted.
- No spec/brief conflict found otherwise. Criteria written before dispatch per normal pipeline order.

## Assumptions logged (process v1.7)

- **ASM — "done" BOW status (not "path exists on disk") is the correct proxy for "this module is expected to be fully registry-consistent."** A module could theoretically have a path and working code while its BOW item is still `open` (mid-build); this file treats such a module as `not-yet-built` for Direction-A purposes even if partially correct, to avoid the audit second-guessing an in-flight pipeline stage. If this produces false "not yet built" suppressions in practice (a module that's actually finished but whose BOW item lags in status), that is a BOW hygiene gap, not an audit defect — logged so it isn't silently assumed away.
