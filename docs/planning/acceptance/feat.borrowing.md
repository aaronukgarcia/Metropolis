# Acceptance criteria — feat.borrowing (FEAT-057)

**BOW code:** FEAT-057 (P1, open) — "Borrowing instruments: IMF/government loans, secured vs unsecured, rate ranges, revenue-share terms, PFI-style facility funding."
**Spec refs:** §7 line 210 ("Loans: facilities unlocked by milestone; interest set by credit rating... Insolvency... = game over") and §7 line 621 (central-bank base-rate environment as a citywide weather system moving "your debt service") are the only master-spec text on borrowing as of this writing. The instrument taxonomy this item adds (IMF-vs-government source split, secured/unsecured, revenue-share, PFI) is **not yet in `docs/METROPOLIS-MASTER-v2.1.md`**; it exists only in FEAT-057's own BOW description, confirmed by Aaron 2026-08-11 (BOW comment: "PFI... is correct"). This file therefore treats the FEAT-057 BOW description as the primary source of truth for scope — Bill's SSOT mapping into the master plan is still outstanding (see Escalations).
**Design (Aaron, 2026-08-11, dictated via Bob):** "the player borrows at DIFFERENT RATES FOR DIFFERENT THINGS." Instrument set: (1) IMF-style lender-of-last-resort and government loans as distinct sources with distinct terms; (2) **secured vs unsecured** borrowing with a range of interest rates — security against land/facilities/revenue streams; (3) **revenue-sharing** terms as an alternative or complement to interest (lender takes a cut of a facility's or the city's income); (4) **PFI-style facility funding** — the classic trade-off (little/no upfront capex vs long-term higher recurring cost and contractual lock-in) the player must judge as a long-bet-in-reverse.
**This file's role:** this is an engine-side extension feature. It sits on `engine.finance` (MOD-022, **done**, committed ecbb8bb) and extends that module's existing loan/credit-rating/insolvency mechanics — it does **not** replace them and does **not** create a new module (ASM-768). It interacts with the permit/facility system (FEAT-053 / `feat.facilitypermits`) and decommission liability (FEAT-054 / `feat.decommission`), since PFI-funded facilities carry contractual obligations on the same balance sheet — both are open and out of scope here beyond the interface shape noted in AC-5. This file owns the instrument taxonomy itself: source split, the secured/unsecured axis, revenue-share recomputation, PFI deferred-capex/unitary-charge/lock-in, and the integration ACs that prove no new instrument bypasses MOD-022's `CreditRating`/`IsInsolvent`.

**Balance-number regime (standing rule, same convention as `engine.finance.md` AC-21 / `feat.maintenance.md` AC-2):** every rate, spread, revenue-share percentage, and PFI unitary-charge multiplier in this file is a **placeholder pending Aaron's balance pass** in a data file (`data/borrowing_instruments.json`), each carrying a disclosure comment naming it pending tuning. A PR that hardcodes "IMF loans are 4.5%–7%" as a literal, undisclosed number is treated the same as ASM-284's tax-rate case: a BA/junior overstepping into player-felt balance territory that is Aaron's alone to set.

## User stories

- **US-1.** As the player under fiscal pressure, I need government loans and IMF-style lender-of-last-resort borrowing to be distinct sources with distinct terms and availability gating, so going to the IMF reads as the desperate, reputationally-costly move it is in reality, not a relabelled copy of an ordinary government loan.
- **US-2.** As the player choosing how to fund a facility, I need to see a real rate difference between pledging collateral (secured) and borrowing on the city's general credit alone (unsecured), so the security/rate trade-off is a legible decision, not flavour text on an identical instrument.
- **US-3.** As the player or a lender modelled by the game, I need a revenue-share facility to actually track the pledged revenue stream month to month (rising and falling with it), so "the lender takes a cut of income" is a real, live-computed obligation rather than a fixed schedule wearing a different label.
- **US-4.** As the player deciding "do you want to build this hospital with PFI funding," I need the PFI trade-off — little/no upfront capex against a long-horizon higher recurring cost and contractual lock-in — to be a real, felt choice on the ledger (compare against a conventionally-financed build of the same facility), so the Slow-Fuse Principle (A5) has a genuine long-bet-in-reverse to render.
- **US-5.** As `engine.invariant`'s insolvency/credit-rating machinery (already built in MOD-022), I need every new instrument this item adds to feed the *same* debt/revenue ratio and the *same* "obligations that must be met" set those mechanics already check, so a new borrowing product can never become a silent side door around the insolvency death condition.

## Scope

A data-driven instrument taxonomy layered on top of MOD-022's existing (and now built) loan/credit-rating/insolvency mechanics: distinct IMF/government loan sources, a secured/unsecured axis with a collateral reference, revenue-share repayment structures computed live against a configurable revenue base, and PFI-style facility funding with a deferred-capex/recurring-unitary-charge shape. All new rate/percentage data is placeholder, disclosed, and data-file-sourced per GR#15 and the balance-number regime above. No instrument type may bypass MOD-022's existing `CreditRating` or `IsInsolvent` mechanics. No crew/supply, no OPEX-ledger placement, no facility-permit or decommission mechanics themselves, and no final rate/percentage values.

## Acceptance criteria

### Functional — instrument taxonomy and sources

- **AC-1 (GR#20; source distinction — IMF vs government).** `data/borrowing_instruments.json` (or equivalent) registers at least two distinct `LoanSource` values — `imf` (lender-of-last-resort) and `government` — each carrying its own rate-range data and its own availability rule, not a shared rate range distinguished only by a label. The IMF source's availability rule reflects "lender of last resort" in a testable, documented way (e.g. gated on credit rating below a data-defined threshold, or on other sources being exhausted/unavailable) rather than being available identically to a government loan at all times. Check: `go doc ./internal/engine/finance LoanSource` (or equivalent) shows at least `imf`/`government` as distinct values; a passing test asserts the two sources' rate-range data differ and that the IMF source's availability function returns `false` for a clean-credit, low-debt synthetic city state where the government source returns `true` (`grep -rn "func Test.*[Ll]oanSource\|func Test.*[Ii][Mm][Ff]" internal/engine/finance/*_test.go`). **What a lazy implementation looks like:** a single `Loan` struct with a cosmetic `Source string` field set to `"IMF"` or `"Government"` that both read the exact same rate table and the exact same availability check — passes a shallow "IMF loans exist" smoke test while delivering nothing FEAT-057 actually asked for. **False-pass warning:** a test that only asserts a loan can be created with `Source: "imf"` (construction succeeds) would pass that lazy implementation; the check must compare the two sources' actual terms/availability, not just that the enum value is settable.
- **AC-2 (secured vs unsecured; collateral reference).** Every loan instrument (regardless of source) carries a `Security` classification of `secured` or `unsecured`; a `secured` instrument carries a non-nil collateral reference (an asset class or specific asset ID — land parcel, facility, or a pledged revenue stream per FEAT-057's own "presumably against land/facilities/revenue streams" wording) while `unsecured` carries none. Secured instruments' data-defined rate range has a strictly lower floor than unsecured instruments' rate range at the same source and same credit rating (directional check only, per the balance-number regime — no specific numbers pinned). Check: `go doc ./internal/engine/finance` shows a `Security`/`Collateral` field set; a passing test constructs a secured and an unsecured instrument from the same source at the same synthetic credit rating and asserts `securedRate.Min < unsecuredRate.Min` (`grep -rn "func Test.*[Ss]ecured\|func Test.*[Cc]ollateral" internal/engine/finance/*_test.go`). What happens to a pledged collateral asset on default is explicitly **out of scope** for this AC — see ASM-413 (Escalations) — this AC only requires the field and the rate-preference direction to exist.
- **AC-3 (GR#15; rate ranges are placeholder data, not Go constants).** Every rate range, spread, and threshold introduced by this item lives in a JSON data file, never a hardcoded Go literal, and carries a non-empty placeholder/pending-tuning disclosure field on each entry (mirroring `data/market.json`'s "pending M2 Batch tuning" convention and `external_world.json`'s AC-16 discipline verbatim). Check: `grep -n "[0-9]\.[0-9]*%\|0\.0[0-9]" internal/engine/finance/*.go` (excluding `_test.go`) for suspicious inline rate literals finds no matches tied to a borrowing-instrument rate; a passing loader test asserts every instrument-taxonomy entry in the data file has a non-empty disclosure/comment field (`grep -rn "func Test.*[Pp]laceholderDisclosure.*[Bb]orrow\|func Test.*[Rr]ateProvenance" internal/engine/finance/*_test.go`). **What a lazy implementation looks like:** a junior "just picking a reasonable IMF rate" (e.g. `const imfRateFloor = 0.045`) to make a test pass quickly — this is the exact ASM-284-class overstep the balance-number regime exists to prevent, and it fails this AC even if every other AC in this file passes.

### Functional — revenue-share terms

- **AC-4 (revenue-share repayment, live-computed).** A `RevenueShareTerms` structure exists carrying a data-driven percentage and a reference to a revenue base — either the city's whole-budget revenue (the existing `CollectTax`/budget-aggregation stage's output, MOD-022 AC-3) or a single facility's own P&L revenue (the `SimpleFirm`/facility revenue figure) — selectable per instrument, not hardwired to one shape (see ASM-414). Each period, the repayment obligation is **recomputed** as `percentage × (that period's actual revenue base)`, not fixed at origination. A period where the revenue base is zero produces a zero repayment obligation for that period (not a negative balance, not debt forgiveness of the principal, not an insolvency-triggering "missed payment" by itself — a zero-revenue-share payment is not a missed obligation under MOD-022 AC-7's "no available credit" definition unless combined with an actual funding shortfall elsewhere). Check: `go doc ./internal/engine/finance RevenueShareTerms` shows the percentage + revenue-base reference; a passing test runs two synthetic months with different revenue-base figures and asserts the repayment amount changes proportionally between them (`repayment = pct × revenue`, recomputed, not memoised from month 1) (`grep -rn "func Test.*[Rr]evenueShare" internal/engine/finance/*_test.go`). **False-pass warning:** a test that only checks month 1's repayment value would pass an implementation that computes the share once at origination and treats it as a fixed schedule thereafter — the check must exercise at least two periods with differing revenue to prove live recomputation, which is the entire point of "revenue-share" as distinct from a normal amortising loan.

### Functional — PFI-style facility funding

- **AC-5 (PFI facility: deferred capex, recurring unitary charge, contractual lock-in).** A `PFIFacility` instrument models the classic PFI trade-off explicitly: at construction, the ledger posts little-to-no upfront capex debit to the city's construction-ledger stage (MOD-022 AC-3's `SettleConstruction`) for a PFI-funded facility, versus the full capex debit for the same facility built conventionally (a comparative test, not a fixed number — GR#15). In exchange, the facility carries a recurring `UnitaryCharge` — a periodic ledger obligation distinct from ordinary debt service, running for a documented `MinimumTermMonths` — that continues for the facility's contracted life. The contract's lock-in is explicit and queryable: either an early-termination penalty function or a documented statement that early termination is not modelled (a real design choice, not a silent gap). Check: `go doc ./internal/engine/finance PFIFacility` shows `UnitaryCharge` and `MinimumTermMonths` (or equivalent); a passing test constructs the same facility both PFI-funded and conventionally-funded and asserts the PFI path's month-of-construction capex debit is materially lower (e.g. below a documented small fraction of the conventional path's debit) while its subsequent monthly `UnitaryCharge` obligation is nonzero for at least `MinimumTermMonths` months (`grep -rn "func Test.*PFI" internal/engine/finance/*_test.go`). **What a lazy implementation looks like:** a `PFIFacility` that is just a `Loan` with a different name and an amortisation schedule stretched over more months — this fails to capture the actual PFI shape (deferred capex + a *service-style* recurring charge, not principal+interest) and would mislead the player about what trade-off they're making. Interaction with FEAT-054's decommissioning liability (also unbuilt) is explicitly out of scope beyond this AC's own `UnitaryCharge`/`MinimumTermMonths` surface — see Escalations.

### Functional — integration with existing credit-rating and insolvency mechanics (the load-bearing requirement)

- **AC-6 (no instrument bypasses insolvency's obligation check — MOD-022 AC-7).** Every instrument this item adds — including a `PFIFacility`'s `UnitaryCharge` and a `RevenueShareTerms` facility's recomputed periodic repayment — is included in the same "obligations that must be met" set MOD-022's `IsInsolvent`/AC-7 already evaluates each month; none is exempt or routed through a bespoke, separate insolvency path. Check: a passing test posts a PFI facility's `UnitaryCharge` as a monthly obligation, then simulates 3 consecutive months where that obligation (and no other) cannot be met and no credit is available, and asserts the *same* game-over signal MOD-022 AC-7 defines fires — reusing that mechanism, not a duplicate one (`grep -rn "func Test.*[Pp][Ff][Ii].*[Ii]nsolven\|func Test.*[Rr]evenueShare.*[Ii]nsolven" internal/engine/finance/*_test.go`). Repeat for a `RevenueShareTerms` facility with a nonzero revenue base that the player nonetheless fails to fund from elsewhere. **False-pass risk (this is the AC an attacker should try hardest to break):** a test that only asserts the new instrument *posts a ledger entry* would pass a build where that entry is silently excluded from the insolvency counter's obligation set (e.g. because `RevenueShareTerms` was implemented as an equity-like "the lender just gets less if revenue is low" concept with no hard obligation floor at all) — such a build would let a player borrow via revenue-share or PFI facilities with **zero insolvency risk**, defeating §12's death condition exactly the way GR#23's "nothing committed un-attacked" rule exists to catch. The check must prove the game-over signal fires through the new instrument, not merely that money moved.
- **AC-7 (credit rating denominator includes all instrument types).** MOD-022 AC-5's `CreditRating` function's debt/revenue ratio input includes the outstanding balance/committed-obligation value of every instrument type this item adds (a PFI facility's remaining committed `UnitaryCharge` stream counts as debt-equivalent exposure; a revenue-share facility's outstanding principal, if any, counts; secured and unsecured instruments both count at their full outstanding value — security affects *rate*, per AC-2, not whether the exposure counts toward the ratio). Check: a passing test computes `CreditRating` for two synthetic city states identical except one carries an additional PFI facility's committed `UnitaryCharge` exposure, and asserts the ratings differ in the documented direction (more committed exposure ⇒ same-or-worse rating, never better) (`grep -rn "func Test.*[Cc]reditRating.*PFI\|func Test.*[Cc]reditRating.*[Ii]nstrument" internal/engine/finance/*_test.go`). **What a lazy implementation looks like:** treating a PFI facility's `UnitaryCharge` as an operating expense line only (since it isn't structured as principal+interest) and never feeding its committed future obligation into the credit-rating ratio at all — technically defensible-sounding ("it's not really debt") but exactly the kind of off-balance-sheet framing PFI is criticised for in reality, and the opposite of what US-5 asks for.

### Error handling

- **AC-8 (GR#7).** A malformed borrowing-instrument entry (missing source, missing security classification on a claimed-secured instrument with no collateral reference, a revenue-share percentage outside `[0, 1]`, a PFI facility with no `MinimumTermMonths`) is rejected at load/construction time with a registry-sourced error (a new `MET-E`-range code, added to `data/errors.json` via the `/new-error` flow), never silently defaulted (e.g. to `unsecured`, to `0%` revenue share, or to a zero-length PFI term). Check: `grep -n "MET-" internal/engine/finance/*.go` finds a registry code reference for the new instrument-validation path, distinct from MOD-022's existing unbalanced-transaction and insolvency codes; passing test coverage for at least the four named malformed cases (`grep -rn "func Test.*[Ii]nstrumentInvalid\|func Test.*[Mm]alformedBorrowing" internal/engine/finance/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100 convention):** each test asserts the returned error's registry code matches its named malformed case AND that no default value (unsecured/0%/zero-length term) was silently substituted and no instrument was partially constructed, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-9 (GR#21; no wall-clock in revenue-share/PFI accrual).** `grep -n "time.Now\|time.Since" internal/engine/finance/*.go` (excluding `_test.go`) continues to return no matches after this item lands — revenue-share recomputation (AC-4) and PFI unitary-charge accrual (AC-5) are both driven by simulation tick/month exactly like MOD-022's existing interest accrual, never wall clock.
- **AC-10 (GR#16; int64 micro-pounds + saturating arithmetic, no float, no overflow).** Every monetary figure introduced by this item — a revenue-share recomputed repayment, a PFI `UnitaryCharge` accrual, an interest amount derived from a credit-rating-adjusted rate, a rate-range midpoint — is an `int64` micro-pounds value (or the documented fixed-point scale MOD-022 AC-2 establishes), and all borrowing arithmetic routes through the project's saturating helpers (`foundation/num`), matching `engine.finance`'s and `engine.build`'s numeric-safety standard (FEAT-086). No `float32`/`float64` field participates in any borrowing money computation; a rate applied to a revenue base cannot overflow or wrap into a negative obligation. Check: `grep -n "float32\|float64" internal/engine/finance/*.go` (excluding `_test.go` and comments) finds no float monetary field on the new instrument types; a passing test applies a pathological (huge or zero) revenue base to a `RevenueShareTerms` facility and asserts the resulting repayment is exactly `0` for a zero base and a saturating (never-wrapped, never-negative) `int64` for a huge base (`grep -rn "func Test.*[Ss]aturat\|func Test.*[Oo]verflow" internal/engine/finance/*_test.go`). **False-pass risk:** a float-based percentage that divides and rounds in the lender's favour would pass a "repayment looks plausible" check while leaking micro-pounds — the check requires the arithmetic to be exact integer and saturation-safe, matching FEAT-086's copy-guard standard.
- **AC-11 (GR#21; deterministic across worker counts + race-free).** Borrowing-instrument resolution — rate selection from a data-defined range given a credit rating, revenue-share recomputation, and PFI unitary-charge accrual — is a deterministic function of prior tick state, loaded data, and injected inputs: repeated runs from an identical snapshot produce byte-identical ledger obligations across worker counts, with any cross-shard summation performed in fixed shard order (never unordered map iteration), per M0-ENG §1.2. Check: a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/finance/*_test.go` — MOD-022 already has `determinism_test.go`; this item extends it to the new instruments); `go test ./internal/engine/finance/... -race -count=1` passes with no data race when instruments are resolved concurrently within a monthly finance phase (`grep -n "go func()" internal/engine/finance/*_test.go`).
