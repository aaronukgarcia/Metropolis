## Why this file exists, and how it differs from its siblings (read first)

Three acceptance files now touch "headless": this one, `harness.headless.md` (MOD-015's CLI/library wrapper — flags, scenario scripts, snapshot output format), and `engine.core.md` (MOD-012's general orchestrator contract — clock, phase order, POOL-SIM sizing). They are not duplicates:

- `engine.core.md` asks "does the orchestrator work at all."
- `harness.headless.md` asks "does the `metropolis -headless` CLI wrap it correctly for CI/batch use."
- **This file** asks the question neither of those two owns: **is `engine.core` itself — the same `NewEngine`/`RunCommandLoop`/`HandleCommand` types a live, UI-attached run would use — provably runnable with zero UI attached, deterministically, with unambiguous termination reporting?** That is the literal wording of MOD-015's own description ("engine without UI") one layer below the CLI, and it is where ASM-001's gap actually lives.

**ASM-001 (Bill, 2026-08-09) is the governing constraint on this file.** It warns that Sprint 1's exit gate does not yet prove `engine.core` participates in the live rendered path — `cmd/metropolis` boots `StubEngine`, and `feat.detgate`'s `RunGate` boots its own fresh, isolated `core.NewEngine` instances that never route through `bootCore`. This file's criteria are written so that satisfying them does NOT let that gap persist under a different name: the headless contract defined here must be **the same code path** a live run would use, not a parallel harness-only implementation that happens to also work. See AC-1 and AC-9.

## User stories

- As **`MOD-036`'s balance/Batch/CI workhorse** (via `harness.headless`'s CLI, which this file's contract underlies), I need `engine.core` to run to completion with no TUI attached and no wall-clock dependency, so unattended sweeps are reproducible from a seed + command log alone.
- As **`feat.detgate`** (GR#21's gate), I need a headless `engine.core` run's termination to be unambiguous — completed cleanly vs. died mid-run — so a red gate is never confused with an infrastructure hang, and so a P0 determinism failure is never masked by a run that silently stopped early and hashed a truncated world.
- As **`harness.replay`'s `EnginePlayer`** (MOD-013), I need `engine.core.RunCommandLoop` to keep consuming exactly the `Commands()`/`SendResult()` shape I already structurally implement, so replaying a fixture into a live engine for regression comparison never needs a second, divergent integration surface.
- As **Bill, reviewing the Sprint 1 exit gate**, I need evidence that "engine.core runs headless" and "engine.core drives the game" are the same claim, not two claims that happen to both be true today by coincidence (ASM-001).

## Scope

`engine.core`'s minimal, stable surface for running a simulation with **no UI, no TUI, no wall-clock pacing, and no interactive input attached**: how a headless run is configured and started (construction options), how ticks are driven and progress is observed (the command path + `PhaseObserver` + `TicksCompleted`), how the run terminates and what a premature termination reports, the determinism guarantees that must hold in a headless configuration specifically, and the contract's interaction with `harness.replay`.

## Acceptance criteria

### Functional — configuration and start

- **AC-1.** A headless run is fully specified by `core.NewEngine`'s existing `Option` surface (`WithWorldSeed`, `WithPoolSize`, `WithPhaseObserver`, `WithSpeedGate`/`WithSpeed8xGate` as applicable) plus a `protocol.Command` log — the **same** construction surface `internal/engine/detgate/gate.go`'s `runOnce` and any future `internal/harness/headless` entry point already use or will use. This file's criteria are satisfied by asserting that surface is sufficient and requires no headless-only constructor, option, or bypass of `NewEngine` — a passing test constructs an `Engine` with only documented `Option`s and drives it to completion with zero references to any UI/TUI package (`internal/ui/...`) anywhere in the import graph (`go list -deps` on the test binary contains no `internal/ui/*` package).
- **AC-2.** Ticks are driven **exclusively** through the real `protocol.Command` envelope (`KindAdvanceTicks` via `HandleCommand`/`RunCommandLoop`), never by a headless-only path that calls `Engine.AdvanceTicks` directly in production code — mirroring `detgate/gate.go`'s own documented rule ("never `Engine.AdvanceTicks` directly"). A passing test/inspection confirms every non-test call site under `internal/engine/detgate`, `internal/harness/replay`, and (once it exists) `internal/harness/headless` reaches ticks only via a `protocol.Command`.
- **AC-3.** Progress during a headless run is observable through the existing, already-exported hooks — `Engine.TicksCompleted()` (lock-free), `Engine.Clock()`, and an installed `PhaseObserver` (`WithPhaseObserver`) — without requiring `mu` or any private field. A passing test installs a `PhaseObserver`, drives several `AdvanceTicks` commands, and asserts the observer saw every phase in the fixed order (`engine.core.md`'s AC-3), interleaved correctly with `TicksCompleted()`'s count at each step.

### Functional — termination and premature-close reporting (the load-bearing section)

- **AC-4 (closes the gap BUG-020/SEC-026 fixed once and MET-H004 fixed a second time — this is the third instance of the same shape, in `engine.core` itself).** `Engine.RunCommandLoop` today (`internal/engine/core/commands.go`) returns **nothing** and cannot distinguish a clean `ctx.Done()` shutdown from a `CommandSource.Commands()` channel closing prematurely out from under it — both branches of its `select` `return` identically, silently. For a headless run (no UI, no operator watching a screen, output judged only by exit code / snapshot file), this is exactly the silent-failure shape GR#1 exists to prevent, and it is strictly more dangerous here than in `harness.stub` (BUG-020) or `harness.replay` (MET-H004) because a headless CI/batch run has no human in the loop to notice a truncated run at all. `RunCommandLoop`'s contract must be changed to distinguish the two and report the premature case: either (a) it returns an error (nil on clean `ctx.Done()`, a distinct registry-sourced error — new code in `engine.core`'s `MET-E0xx` range, next free after `MET-E013` — when `Commands()` closes before `ctx` is done), or (b) an equivalent caller-observable signal is added (e.g. an optional error-sink parameter); Tester confirms whichever the junior implements against this AC's intent, and records which. A passing test closes the `CommandSource`'s `Commands()` channel out from under a running `RunCommandLoop` without cancelling `ctx`, and asserts the distinct error/signal fires — not the same silent return a clean quit produces.
- **AC-5.** The fix reuses `StubEngine.Run`'s already-battle-tested exit contract (`internal/engine/stub/engine.go`'s "Exit contract" doc comment) rather than inventing a third vocabulary: re-check `ctx.Done()` **after** observing `ok == false` on the `Commands()` receive (not before) to tell "ctx was already done, this is the clean path" apart from "something else closed the transport." A passing test proves this ordering specifically: cancel `ctx` and close the channel in the same instant (a WaitGroup-synchronized construction, not a sleep/timing race, per `dev-team-process.md`'s "concurrency tests must be deterministic, not probable" rule) and assert the clean-shutdown branch is taken, matching `StubEngine.Run`'s own documented behaviour for that race.
- **AC-6 (SEC-032's re-check-at-the-alarm pattern, applied here too — weakness pattern #5).** If AC-4's fix is implemented with any wait/notify loop rather than a single `select`, it must re-check its own completion condition **at the point the alarm fires**, not only before arming the wait — exactly the fix `harness.replay`'s `EnginePlayer.Replay` needed after Tester-1 measured a 38.6% false-premature-close rate without it (`player_engine.go`, SEC-032). If AC-4 is instead implemented as the plain two-branch `select` mirroring `StubEngine.Run` directly (the simpler, recommended shape — see AC-5), this AC is satisfied by that shape alone and needs no additional re-check loop; Tester confirms which shape was built and applies the matching check.
- **AC-7.** Whatever headless driver first calls `RunCommandLoop` for a genuinely unattended, long-running batch (i.e. any caller that does not itself immediately and deterministically control both `ctx` cancellation and the transport's `Close()` in the join-then-close order `StubEngine.Run`'s doc comment mandates) **observes** the return/signal from AC-4 and surfaces it — logged and reflected in a non-zero process/command outcome — rather than discarding it the way `cmd/metropolis/boot.go` currently discards `StubEngine.Run`'s return (`BUG-020`'s still-open AC-2, cited here as the pattern to not repeat). `internal/engine/detgate`'s `RunGate` is explicitly exempted from this AC (see "Out of scope") because it already controls shutdown ordering deterministically (`cancel(); transport.Close()`, no join needed since nothing else can close `Commands()` first) — the same reasoning `harness.stub`'s doc names for why the race window is latent, not live, under disciplined ordering.

### Determinism & safety (GR#21)

- **AC-8.** A headless configuration — `StartSubscriptionPump` never called, no `PhaseObserver` installed (or one installed purely for read-only telemetry, per `PhaseObserver`'s own doc comment: "the phase pipeline's own correctness never depends on an observer being set or on anything it does") — produces the **same** `Snapshot` hash, for a given `(seed, command log)`, as any other configuration of the same commands at any `PoolSize` (carrying forward `engine.core.md`'s AC-15 and `feat.detgate`'s own gate, specialised here to assert headlessness itself is not an extra hidden variable). A passing test runs the same `(seed, command log)` twice — once with a `PhaseObserver` installed, once without — and asserts identical `Snapshot` `sha256`.
- **AC-9 (directly answers ASM-001 — the load-bearing criterion of this file).** The construction and driving pattern this file certifies (AC-1/AC-2: `NewEngine` + `Option`s + `RunCommandLoop`/`HandleCommand` over a real `protocol.Command` stream) is **identical in kind** to whatever pattern a live, UI-attached boot path uses once `engine.core` is wired into `cmd/metropolis` for real — not a headless-only shortcut that a live boot path would need to diverge from. Concretely: this AC is satisfied only if no headless-only constructor or driving function is added anywhere in scope (AC-1 already requires this); it explicitly does **not** require `cmd/metropolis` to actually construct `core.NewEngine` today (that remains ASM-001's own open item, outside MOD-015's scope) — but it does require that when that wiring happens, it can reuse this exact contract unchanged. Tester checks this by inspection: no function under `internal/engine/detgate`, `internal/harness/replay`, or `internal/harness/headless` constructs or drives an `Engine` any differently than a hypothetical `bootCore` would have to.
- **AC-10 (GR#21).** `grep -rn "time.Now" internal/engine/core/*.go internal/engine/detgate/*.go internal/harness/replay/*.go` (excluding `_test.go`) returns no matches feeding simulation state, tick advancement, or `Snapshot` content — carrying forward `engine.core.md`'s AC-12 and `harness.replay`'s own doc-stated determinism note, checked here specifically across the three packages a headless run spans.
- **AC-11 (GR#21).** No `range` over a Go map in any code path AC-4's fix adds (error construction, logging) can make two runs of the SAME premature-closure scenario diverge in reported field order — if the new error carries a `map[string]any` context (per this codebase's `errs.New` convention), the fields it names are fixed and documented, not dependent on iteration order, matching every existing `errs.New` call site's practice in this package.

### Documentation

- **AC-12.** `RunCommandLoop`'s doc comment (`internal/engine/core/commands.go`) gains an "Exit contract" section stating explicitly what AC-4/AC-5 implement — mirroring `StubEngine.Run`'s doc comment structure (same heading style, same "the caller-side contract this implies" framing) — so a future reader of `engine.core` finds the same load-bearing statement `harness.stub` already carries, rather than having to independently re-derive it from `StubEngine`'s package by analogy.
- **AC-13.** The package doc (`doc.go`) or a new short section in it states this file's governing relationship to ASM-001 in one sentence: that `engine.core`'s headless contract and its (future) live-boot contract are the same code path by design, not two implementations that happen to agree today.

## Out of scope

- Everything `harness.headless.md` already owns: the `metropolis -headless` CLI flags, scenario-script JSON parsing, per-phase timing *output format*, invariant-report *output format*, and the `-out` snapshot file's exact writing (this file only requires that whatever CLI is built reuses the contract certified here, not that it exists).
- `feat.detgate`'s own 120-month×2-runs×worker-count gate logic and verdict/mismatch reporting (`FEAT-004`) — this file only asserts `detgate`'s existing `RunGate`/`runOnce` pattern is an instance of, not an exception to, the contract in AC-1/AC-2/AC-9.
- `internal/engine/detgate/gate.go`'s `runOnce` observing AC-4's new return value — `RunGate` already controls `cancel()`/`Close()` ordering deterministically with no possible early-close race (see AC-7's explicit exemption); requiring it to additionally handle a signal it structurally cannot receive would be dead code, not defence in depth.
- Resolving ASM-001 itself (wiring `core.NewEngine` into `cmd/metropolis`'s actual boot path) — that is a separate, larger decision for Bill/Aaron; this file only ensures the headless contract does not need to change shape when that wiring happens.
- Any change to `harness.replay`'s `EnginePlayer`/`codeReplayTargetClosedEarly` (MET-H004) — already correctly implemented per its own acceptance file; this file's AC-4/AC-5/AC-6 bring `engine.core` itself up to the same standard `EnginePlayer` and `StubEngine` already meet, it does not touch either of those packages.
