# Acceptance criteria — engine.consumption (MOD-021)

## User stories

- **US-1.** As `data.catalogue`'s `consumptionRef` field (FEAT-010, AC-6 of this BA's own Sprint 2 file), I need every building-class coefficient from §17.2's table resolvable through this module's `DataAPI`-sourced coefficients, so §17's "the catalogue never hard-codes utility numbers" rule is actually true end-to-end, not just structurally true in the catalogue file.
- **US-2.** As the water network, I need demand computed as class coefficients × occupancy/throughput, with an aquifer sustainable-yield ceiling that degrades under over-abstraction, so §17's aquifer note is a real mechanic, not flavour text.
- **US-3.** As the wastewater network, I need output modelled at ≈95% of water drawn (per §17's stated rule) unless a specific building class overrides it, so sewage capacity planning has a real, derivable number rather than a second hand-authored table.
- **US-4.** As the four utility networks (water, wastewater, electricity, gas), I need each modelled as a genuinely separate network with sources, pipes/wires (free within road corridors, costed cross-country per §2.2), storage, and losses, so a player's choice to go all-electric (skip gas entirely) is mechanically viable, not just narratively claimed.
- **US-5.** As `engine.season` (MOD-027, already built in Sprint 3), I need this module to apply the seasonal multiplier curves (winter power +15%, summer water +25%, gas ×2.2 Jan/×0.2 Jul) on top of the coefficient-driven base demand, so §17's "before seasonal modifiers (§9)" qualifier is honoured — base coefficients stay pure, seasonality is a separate multiplicative layer.
- **US-6.** As `engine.wellbeing` (a later Sprint 7 consumer), I need utility shortfalls (a network failing to meet demand) to be queryable per-household/per-district, so unmet water/power/gas needs can feed satisfaction and health drivers per §18.
- **US-7.** As `engine.market` (MOD-020, this BA's own file above), I need this module to source import/local-production costs for grid power, gas, and bulk water through `Market`, not duplicate pricing logic — utility networks consume commodities, they don't reprice them.

## Scope

Coefficient-driven demand computation (§17.1/§17.2, resolving `data/buildings.json`'s `consumptionRef` against `data/consumption.json`), the four separate utility networks (water, wastewater, electricity, gas) with sources/pipes-wires/storage/losses, a conserved daily solve (delivered + shortfall = demand), the aquifer sustainable-yield ceiling, peak-vs-base load, the all-electric-strategy path (no gas network required), and the billed-amount figure `engine.finance`'s household-spend ledger stage needs. Posting the bill to the ledger itself stays `engine.finance`'s job.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `UtilityAPI` exists exposing a daily-tick network-solve entry point and per-cell/per-building demand queries, matching code.json's "network solve per daily tick; coefficients from DataAPI" pattern. Check: `go doc ./internal/engine/consumption UtilityAPI` shows a `SolveDailyTick` (or equivalent) method and demand-query methods.
- **AC-2 (§17.1).** The per-person residential daily baseline is loaded from `data/consumption.json` and matches §17.1's transcribed figures: water 145L/person/day (+25% summer, +20L detached gardens), electricity 3.5kWh/person/day (household base 2kWh + 1.5/person, winter +15%), gas 13kWh/person/day (×2.2 Jan, ×0.2 Jul), food-staples 1.4kg, food-fresh 0.7kg, household waste 1.1kg, wastewater ~138L (95% rule). Check: a passing test loads `data/consumption.json` and asserts each figure matches §17.1 (GR#15: the expected values are transcribed from the spec into the test) (`grep -rn "func Test.*[Bb]aseline" internal/engine/consumption/*_test.go`).
- **AC-3 (§17.2).** Per-user coefficients by building class are loaded and resolvable for every class §17.2 names (school, university, clinic, hospital, elder-care, office, shop, restaurant/café, hotel, light industry, heavy industry, leisure venue, stadium, swimming pool, park, station, airport, water-treatment-works, sewage-works, desalination), each carrying water/elec/gas/waste figures per the table. Check: a passing test asserts at least 5 representative classes (hospital, office, heavy industry, station, desalination) match §17.2's literal figures (`grep -rn "func Test.*[Cc]oefficient" internal/engine/consumption/*_test.go`).
- **AC-4 (US-1; data.catalogue seam).** Given a `data/buildings.json` entry's `consumptionRef` (per this BA's `data.catalogue.md` AC-6), `UtilityAPI` resolves it to a §17.2 coefficient class and computes demand as `coefficient × occupancy/throughput` — the catalogue is never queried for a raw utility number, only for the reference key. Check: a passing integration test loads a `buildings.json` fixture entry with a `consumptionRef`, resolves it through `UtilityAPI`, and asserts the resulting demand equals `coefficient × occupancy` for a known occupancy value (`grep -rn "func Test.*[Cc]onsumptionRef\|func Test.*[Rr]esolve" internal/engine/consumption/*_test.go`).
- **AC-5 (§17 wastewater).** Wastewater output for any building/citizen is computed as 95% of that same entity's water draw by default, with a documented per-class override path for classes whose §17.2 wastewater figure deviates from the flat 95% rule (the table gives wastewater implicitly via the 95% note, not a separate column — confirm no class needs an override before assuming none does; document the finding either way). Check: `go doc ./internal/engine/consumption WastewaterOutput` exists; a passing test asserts residential wastewater = 0.95 × water draw for the §17.1 baseline figures (138/145 ≈ 0.951) (`grep -rn "func Test.*[Ww]astewater" internal/engine/consumption/*_test.go`).
- **AC-6 (§17/§2.2 four networks; sprint-plan S4 exit gate — "utility networks solve").** Water, wastewater, electricity, and gas are modelled as four independently-solvable networks, each with: source nodes (boreholes/reservoir/desalination for water; Sellindge grid tranche/gensets/wind/solar/CCGT/nuclear for power; off-map pipeline/LNG for gas; treatment works for wastewater), edges (pipes/wires), storage nodes, and a loss factor applied over distance/edges. **"Solve" is defined here, binding, since the exit gate names it as its own testable clause and the spec text alone doesn't define what a passing solve looks like:** for any tick, every unit of demand is accounted for as either delivered, stored, or reported as shortfall — `delivered + shortfall = demand` exactly, with losses subtracted from what sources produce before delivery (not invented or dropped silently) — i.e. the solve is a conserved allocation, not merely "some number comes out". Check: `go doc ./internal/engine/consumption Network` (or per-network types `WaterNetwork`, `PowerNetwork`, `GasNetwork`, `WastewaterNetwork`) shows source/edge/storage/loss modelling for each; a passing test asserts a longer pipe run has higher losses than a shorter one for the same network (`grep -rn "func Test.*[Nn]etwork.*[Ll]oss\|func Test.*[Dd]istance" internal/engine/consumption/*_test.go`); a **second, separate** passing test constructs an under-supplied network and asserts `delivered + Shortfall() == demand` holds exactly, not approximately (`grep -rn "func Test.*[Ss]olve.*[Cc]onserv\|func Test.*[Dd]eliveredPlusShortfall" internal/engine/consumption/*_test.go`). False-pass risk: the distance/loss test alone (the 2026-08-09 draft's only check here) would pass a network that "solves" by returning a plausible-looking delivered figure with no accounting discipline at all (e.g. always reporting zero shortfall regardless of actual capacity) — the conservation-equality test is what actually proves a solve, and it is this module's own contribution toward `engine.invariant`'s `GoodsInvariant` (that package's AC-5) ever being registrable against real utility stocks.
- **AC-7 (§2.2 free-in-corridor).** Pipes/wires built within road corridors carry zero additional land/routing cost beyond the utility infrastructure itself, while cross-country runs (off the road network) carry a documented extra cost — matching §2.2's "built in road corridors for free, cross-country at cost". Check: a passing test asserts a corridor-routed edge's cost is lower than an equivalent-length cross-country edge (`grep -rn "func Test.*[Cc]orridor" internal/engine/consumption/*_test.go`).
- **AC-8 (§17 aquifer).** The water network's borehole/aquifer source enforces a sustainable-yield ceiling; abstraction sustained above that ceiling degrades future yield (a documented decay function), rather than the aquifer supplying unlimited water forever. Check: `go doc ./internal/engine/consumption AquiferYield` (or equivalent) exists; a passing test sustains over-abstraction for multiple simulated months and asserts yield degrades (`grep -rn "func Test.*[Aa]quifer" internal/engine/consumption/*_test.go`). False-pass risk: a test that abstracts once, over-ceiling, for a single month and asserts *some* degradation would pass a build that degrades once then flatlines (no real decay curve) — the check requires the multi-month assertion to show *continued*, not one-shot, degradation under sustained over-abstraction.
- **AC-9 (§17.2 peak vs base load).** Electricity (and, where applicable, water) demand distinguishes a peak-load figure from a base-load figure per network, so `engine.build`/service-sizing logic can size generation/storage against peak, not merely average, demand. Check: `go doc ./internal/engine/consumption` shows both `BaseLoad`/`PeakLoad` (or equivalent) query methods for the power network; a passing test asserts peak ≥ base for a synthetic demand profile (`grep -rn "func Test.*[Pp]eak" internal/engine/consumption/*_test.go`).
- **AC-10 (§6 all-electric strategy).** A city can be simulated with zero gas-network infrastructure (all-electric strategy) without any hard error or forced gas dependency — gas demand for heating/cooking simply reroutes to electricity demand (per §17's "electric-heated homes shift this to E" note) when the gas network is entirely absent. Check: a passing test constructs a world with no gas network and asserts total electricity demand for an all-electric building exceeds the same building's electricity demand when a gas network is present (the heating load shifted) (`grep -rn "func Test.*[Aa]llElectric" internal/engine/consumption/*_test.go`).
- **AC-11 (US-5; engine.season integration).** Seasonal multipliers are applied as a layer on top of coefficient-driven base demand, calling `engine.season`'s `SeasonAPI` curve functions (this BA's own MOD-027) — never a locally re-implemented seasonal curve. Check: `grep -n "season\." internal/engine/consumption/*.go` shows calls into the `season` package; a passing test asserts a January gas-demand query returns base-demand × `season.GasDemandMultiplier(January)` exactly (`grep -rn "func Test.*[Ss]eason" internal/engine/consumption/*_test.go`).
- **AC-12 (US-6).** A per-district/per-household shortfall query exists (`Shortfall(network, entityRef) Quantity` or equivalent), returning the gap between demand and delivered supply for the current tick, consumed later by `engine.wellbeing`. Check: `go doc ./internal/engine/consumption Shortfall` (or equivalent) exists; a passing test constructs an under-supplied network and asserts a non-zero shortfall (`grep -rn "func Test.*[Ss]hortfall" internal/engine/consumption/*_test.go`).
- **AC-20 (§7/§54; household utility billing — the exit gate's "spend" step, `engine.finance`'s AC-3 dependency).** For every tick, this module computes the money value of consumed utilities per household/entity as `delivered quantity × engine.market's per-unit price` for each of the four commodities that map to a Market commodity (water, electricity, gas — food/fuel/etc. bill through other consumers, not this module), and exposes this as a queryable per-entity billed-amount, distinct from the raw physical `Quantity` demand/delivered figures AC-1's `SolveDailyTick` already returns. This is the input `engine.finance`'s `PostHouseholdSpend` stage (`engine.finance.md` AC-3) needs — this module does not itself post to the ledger (that stays `engine.finance`'s job), it only computes and exposes the billable amount. Check: `go doc ./internal/engine/consumption BilledAmount` (or equivalent) exists; a passing test asserts the billed amount for a known delivered quantity and a known Market price equals their product exactly, and that raising the Market price (with delivered quantity held fixed) raises the billed amount (`grep -rn "func Test.*[Bb]ill" internal/engine/consumption/*_test.go`). False-pass risk: a method that returns the raw physical quantity relabelled as a "bill" (no price multiplication at all) would pass a check that only confirms the method exists — the check requires varying the Market price independently of quantity and asserting the billed figure moves with it.

### Error handling

- **AC-13 (GR#7).** A `consumptionRef` in `data/buildings.json` that fails to resolve against `data/consumption.json`'s loaded classes produces a registry-sourced error (new `MET-E`-range code) at world-load/reference-resolution time, not a silent zero-demand default. Check: `grep -n "MET-" internal/engine/consumption/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Dd]anglingRef\|func Test.*[Uu]nresolved" internal/engine/consumption/*_test.go`).
- **AC-14.** A network with no source capable of meeting any demand at all (e.g. a water network with zero registered sources) produces a loud, registry-sourced diagnostic each tick it remains unsolvable, rather than silently reporting 100% shortfall indistinguishable from a partial, expected shortfall. Check: passing test coverage (`grep -rn "func Test.*[Nn]oSource" internal/engine/consumption/*_test.go`).

### Determinism & safety

- **AC-15 (GR#21).** The daily network solve is deterministic: the same demand/supply inputs produce byte-identical solved allocations across repeated runs and across worker counts, with any allocation-under-shortfall tie-breaking rule (which consumer gets served first when supply is short) being a documented, deterministic priority order — never map-iteration-dependent. Check: `grep -n "for .* := range" internal/engine/consumption/*.go` on any map feeding allocation order is sorted (`grep -n "sort\." internal/engine/consumption/*.go`); a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/consumption/*_test.go`).
- **AC-16 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/consumption/*.go` (excluding `_test.go`) returns no matches — demand, seasonal multipliers, and network solves are driven entirely by simulation tick/month, never wall clock.
- **AC-17.** `go test ./internal/engine/consumption/... -race -count=1` passes with no data race across the four networks solving concurrently within a single daily tick. Check: `grep -n "go func()" internal/engine/consumption/*_test.go` finds at least one concurrency test.

Check: `grep -n "engine.consumption" internal/engine/consumption/doc.go` and `grep -n "§17\|section 17" internal/engine/consumption/doc.go` and `grep -n "consumptionRef" internal/engine/consumption/doc.go` all match.

## Out of scope

- The actual generation-asset build/upgrade mechanics (building a wind farm, a CCGT plant) — that is `engine.build`/`engine.finance`'s job; this item only models the network's demand/supply/loss arithmetic once sources exist.
- Firm-level power-hungry demand (data centres, chemical plants — §50/§63) — those are later modules' (`engine.chemicals`, `engine.fdi`) specific consumers of this API, not built here.
- Land reclamation / desalination's own build-mechanics — this item only needs desalination as a water-source *option* with its documented coefficient (3.8kWh/m³ per §17.2), not the tier-10 unlock mechanics around it.
- Fuel (petrol/diesel/EV charging, §49) as a utility network — fuel is a `Market` commodity (this BA's `engine.market.md`), not one of the four §17 utility networks.
- Pollution-from-generation modelling feeding land value/wellbeing — that's a later cross-cutting concern (§18/§32); this item exposes generation-source identity/type, not pollution radius computation.
- Posting the household utility bill (AC-20) to the double-entry ledger, collecting the sales tax on it, or settling it against a household's wealth — that is `engine.finance`'s job (its AC-3 `PostHouseholdSpend` stage); this module only computes and exposes the billable amount.
