## User stories

- **US-1.** As the city budget, I need the operating drain decomposed into its five named components — **maintenance, staffing wages, raw materials, services, debt service** — each a first-class, drill-through-able ledger line, so OPEX is a visible, auditable composition and maintenance is *not* hidden inside a single "service opex" number.
- **US-2.** As the player, I need maintenance to be a **MAJOR drain** — its own named component comparable to wages/materials/services/debt — so underfunding it is a felt, visible choice that accrues a queryable backlog and a real efficiency loss, not a cosmetic slider.
- **US-3.** As the player, I need the monthly OPEX settlement to close into the budget exactly like the existing §7 chain, so the composed OPEX total is the budget's real outflow and `BudgetBalance` reflects every component, not just service opex.
- **US-4.** As the player setting maintenance/repair policy, I need **refit/rebuild to be capital events (CAPEX)** and **auto-repair to be operating (OPEX)**, so the CAPEX/OPEX split is a real consequence of my policy choice, not a fixed bucket.
- **US-5.** As `engine.invariant` (MOD-019), I need **OPEX + CAPEX + net == the ledger delta** to hold every tick with the new drains wired in, so the money-conservation invariant stays green and no new drain is a silent money leak.
- **US-6.** As a consuming layer (`ui.screen.finance`/F2 later), I need each OPEX component, the CAPEX total, and the maintenance backlog to drill through to their underlying ledger lines (UI-SPEC §4), so "maintenance" on screen opens real transactions, not a dead end.

## Scope

Fold maintenance, staffing wages, raw materials, services, and debt service into MOD-022's existing double-entry ledger as a composed, drill-through-able OPEX total; a monthly settlement that posts each component (reusing the existing debt-service stage and adding maintenance/material/staff-wage posting paths); a maintenance-backlog + efficiency-loss consequence for underfunding; a policy-driven CAPEX/OPEX classification (refit/rebuild → capital, auto-repair → operating); and the conservation identity `OPEX + CAPEX + net == ledger delta`. All monetary values in int64 micro-pounds; all magnitudes **directional only** (placeholders pending Aaron's balance pass, per GR#15 and the balance-number regime ASM-284 established).

## Acceptance criteria

### Functional — OPEX composition and settlement

- **AC-1 (US-1; OPEX composition is first-class and drill-through-able).** A composed OPEX breakdown exists exposing the five named components — maintenance, staffing wages, raw materials, services, debt service — as distinct, queryable values, with **maintenance** a first-class named component of its own (never folded into the existing `CatOpex` "service opex" category). Check: `go doc ./internal/engine/finance OpexBreakdown` (or equivalently named) shows the five component fields; `grep -rn "func Test.*[Oo]pexBreakdown\|func Test.*[Oo]pexComposition" internal/engine/finance/*_test.go` finds a test asserting each of the five components is independently retrievable and that the maintenance component is not equal to (or subsumed by) the services component for a fixture that posts maintenance separately. **False-pass risk:** a test that only asserts "some maintenance number is summed into a total" would pass a build that keeps a single `CatOpex` bucket and just adds maintenance to it — this AC's check must retrieve the maintenance component *as its own named value*, distinct from services.
- **AC-2 (US-3; composed OPEX = sum of parts, and it is the budget's real outflow).** The composed OPEX total equals the sum of its five components, and `BudgetBalance()` subtracts the composed total (maintenance + staffing wages + raw materials + services + debt service), not just the old service-opex figure — so every component is a real budget drain. Check: `go doc ./internal/engine/finance` shows a composed-Opex aggregate (e.g. `ComposedOpex()` or `OpexBreakdown.Total()`); a passing test posts a known fixture amount for each of the five components and asserts (a) `ComposedOpex() == maintenance + staffingWages + materials + services + debtService` exactly, and (b) `BudgetBalance()` equals `TaxRevenue − ComposedOpex − ConstructionTotal − ImportsTotal` (`grep -rn "func Test.*[Cc]omposedOpex\|func Test.*[Bb]udget.*[Oo]pex" internal/engine/finance/*_test.go`). **False-pass risk:** a test asserting only that "the budget reflects a maintenance posting" would pass a build that posts maintenance but never adds it to the budget's subtraction — the check must recompute `BudgetBalance` against the composed total, proving the drain is *felt* by the budget, not merely recorded.
- **AC-3 (US-1; per-component ledger lines).** Each OPEX component posts via its own ledger category so every component drill-throughs to its lines (AC-11's `LinesByCategory` path), and the components that do not yet have categories (maintenance, raw materials, staffing wages) get their own — services and debt service reuse the existing `CatOpex` and `CatDebtService`/`CatDebtPrincipal`. Check: `grep -n "CatMaintenance\|CatMaterials\|CatStaffWages\|CatStaffing" internal/engine/finance/accounts.go` (or equivalent) finds the new category constants; a passing test posts each component and asserts `LinesByCategory` returns that component's entries and no other component's (`grep -rn "func Test.*[Mm]aintenance.*[Ll]ines\|func Test.*[Cc]omponentLines" internal/engine/finance/*_test.go`). See Escalations on the `CatWages` collision (household-wages stage vs staff wages).
- **AC-4 (US-3; a composable monthly settlement).** The monthly OPEX settlement is a sequence of independently-callable posting stages, mirroring MOD-022 AC-3's composable-stage discipline: a maintenance stage (posting the funded maintenance amount as `CatMaintenance`), a materials stage (`CatMaterials`), a staffing-wages stage, and the existing `SettleOpex` (services) + `ServiceDebt` (debt) — so a caller can run the full settlement or any subset. Check: `go doc ./internal/engine/finance` lists a posting function for each new component (e.g. `PostMaintenance`, `PostMaterials`, `PostStaffWages`, or equivalently named); a passing integration test runs the full five-component settlement for one synthetic month with known inputs and asserts each stage's own posted amount against hand-computed expected values (`grep -rn "func Test.*[Ss]ettle.*[Oo]pex\|func Test.*[Mm]onthly.*[Oo]pex\|func Test.*[Oo]peratingBudget" internal/engine/finance/*_test.go`).

### Functional — maintenance underfunding (the "visible drain" core)

- **AC-5 (US-2; underfunding accrues a visible backlog + efficiency loss).** The maintenance settlement consumes the city's maintenance **demand** (engineer-days/year from `engine.maintenance`/MOD-072, via an interface — GR#20, never hardcoded) and the **funded** amount the player actually allocates, posts the funded amount as `CatMaintenance`, and records the shortfall `demand − funded` (when positive) into a queryable **maintenance backlog** balance. A queryable **efficiency factor** degrades monotonically as the backlog grows, and recovers when the backlog is paid down — underfunding is a felt cost, not cosmetic. Check: `go doc ./internal/engine/finance MaintenanceBacklog` (or equivalent) and a maintenance-efficiency accessor both exist; a passing test runs three synthetic months where funded < demand each month and asserts (a) the backlog grows monotonically each month, (b) the efficiency factor decreases (never increases) as backlog grows, and a second test overfunds in a later month and asserts the backlog shrinks and efficiency recovers (`grep -rn "func Test.*[Bb]acklog\|func Test.*[Mm]aintenance.*[Ee]fficiency" internal/engine/finance/*_test.go`). **False-pass risk:** a test that only asserts "a backlog field exists and is queryable" would pass a build where the backlog never feeds any efficiency consequence — the check must exercise the backlog→efficiency monotonic relationship, which is the entire point of "visible and real".
- **AC-6 (US-2; maintenance is a MAJOR drain — directional magnitude).** The maintenance component is treated as a first-class *major* drain, not a rounding error: for a fixture city state, the maintenance demand figure is a genuine engineering-scaled quantity (engineer-days × a data-sourced cost per engineer-day — GR#15), and a test asserts maintenance is comparable in order-of-magnitude to (not arbitrarily dwarfed by) the other four components under a realistic fixture, via a documented data-file-driven ratio check rather than a hardcoded constant (GR#15). Check: the cost-per-engineer-day and any size/class multipliers live in a data file (`grep -n "engineer.day\|maintenance" data/*.json` or equivalent), never a Go literal; a passing test loads the fixture and asserts the maintenance component is nonzero and at least a documented fraction of the composed total, with the threshold itself data-sourced (`grep -rn "func Test.*[Mm]ajorDrain\|func Test.*[Mm]aintenance.*[Ss]cale" internal/engine/finance/*_test.go`).

### Functional — the CAPEX/OPEX split

- **AC-7 (US-4; refit/rebuild are CAPEX, auto-repair is OPEX).** A maintenance/repair event's financial classification is a function of the player's repair policy: an **auto-repair** event posts as operating expenditure (the `CatMaintenance` OPEX component), while a **refit/rebuild** event posts as a capital event on the capital side (the existing `CatConstruction`/`CatInvestment` path or a new `CatCapex` category) — not as a routine operating drain. Check: `go doc ./internal/engine/finance` shows a classification surface (e.g. `ClassifyMaintenanceSpend(policy, event)` or a `MaintenancePolicy`-aware post); a passing test posts the same underlying maintenance obligation under an auto-repair policy and under a refit/rebuild policy and asserts the auto-repair path lands in the OPEX component while the refit/rebuild path lands in the capital total (`grep -rn "func Test.*[Cc]apexOpex\|func Test.*[Rr]efit.*[Cc]apital\|func Test.*[Aa]utoRepair.*[Oo]pex" internal/engine/finance/*_test.go`). **False-pass risk:** a test asserting only "a refit posts some money somewhere" would pass a build that routes refit/rebuild through the same operating bucket as auto-repair — the check must prove the *destination* differs by policy, which is the entire CAPEX/OPEX distinction.
- **AC-8 (US-4; the policy value drives the split, not the total).** The repair-strategy setting is read from the policy layer (FEAT-091's `engine.policies`, `[auto]`/`[manual]` values) through an interface — GR#20, never a hardcoded switch on a locally-declared enum — and changing the policy changes *which bucket* a maintenance-adjacent obligation lands in (OPEX vs CAPEX) without changing the underlying obligation amount. Check: `grep -n "engine.policies\|policies\." internal/engine/finance/*.go` (excluding `_test.go`) or an interface typed to the policy value shows the seam; a passing test drives the same obligation through two policy values and asserts the total (OPEX + CAPEX) is unchanged while the OPEX/CAPEX proportions differ (`grep -rn "func Test.*[Pp]olicy.*[Ss]plit\|func Test.*[Ss]plit.*[Ii]nvariant" internal/engine/finance/*_test.go`).

### Functional — conservation

- **AC-9 (US-5; OPEX + CAPEX + net == ledger delta).** The conservation identity holds every tick: the composed OPEX total plus the CAPEX total plus the net of all other flows equals the tick's tracked ledger delta exactly (zero residual), and the existing money-conservation machinery (`MoneyStock().TrackedDelta`, `TotalMoneyInCirculation`) stays green with the new drains wired in. Check: `go doc ./internal/engine/finance` exposes the composed-OPEX and CAPEX totals used in the identity; a passing test runs a full monthly settlement (wages → spend → tax → composed OPEX → capex → debt) with known non-overflowing fixture values and asserts `ComposedOpex() + CapexTotal() + NetOther() == MoneyStock().TrackedDelta` exactly, and that `TotalMoneyInCirculation()` closing equals opening + that delta (`grep -rn "func Test.*[Oo]pexCapex.*[Cc]onservation\|func Test.*[Cc]onservation.*[Oo]pex\|func Test.*[Nn]et.*[Dd]elta" internal/engine/finance/*_test.go`). **False-pass risk:** a test that only asserts "conservation is unchanged from before this item" (the existing AC-10 test, untouched) would pass a build where the new maintenance/material/staffing posting paths are never exercised by the conservation check — this AC's check must post the new components *through* the settlement and assert the identity over that same run, catching a new drain that silently creates or destroys money.
- **AC-10 (US-5; a new drain cannot leak money).** A deliberately unbalanced or untracked maintenance/material/staff-wage post (posted via the low-level path, simulating the bug `engine.invariant` exists to catch) is localisable by the existing `FindConservationViolations()` — the new components route through the same tracked-posting path as every existing stage, never a bespoke side-channel. Check: a passing test posts an unbalanced `CatMaintenance` transaction against the low-level entry path and asserts `FindConservationViolations()` reports it with its transaction ID and the accounts it touched (`grep -rn "func Test.*[Mm]aintenance.*[Vv]iolation\|func Test.*[Cc]omponent.*[Cc]onservation" internal/engine/finance/*_test.go`).

### Error handling

- **AC-11 (GR#7).** A negative or malformed settlement input (negative funded amount, negative demand, a refit/rebuild classification for an event with no capital cost declared) is rejected at post time with a registry-sourced error (new `MET-E`-range code), never silently clamped or treated as a zero-funded "skip". Check: `grep -n "MET-" internal/engine/finance/*.go` finds a registry code reference for the new settlement path; passing test coverage for the named malformed cases (`grep -rn "func Test.*[Mm]aintenance.*[Ii]nvalid\|func Test.*[Oo]pex.*[Nn]egative" internal/engine/finance/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100 convention):** each test asserts the returned error's registry code matches its named case AND that no partial post or silently-clamped value was written, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-12 (GR#21).** Any summation over the OPEX components, the maintenance backlog, or the CAPEX total that iterates a collection does so in fixed, sorted order (sorted by a documented stable key — category name, account ID, or event ID), never unordered map iteration. Check: `grep -n "for .* := range" internal/engine/finance/*.go` on any map feeding a component/backlog/capex sum is either absent or followed by sorted-key iteration (`grep -n "sort\." internal/engine/finance/*.go`); a passing determinism test asserts identical composed-OPEX and CAPEX totals across worker counts (`grep -rn "func Test.*[Dd]eterminis.*[Oo]pex\|func Test.*[Oo]pex.*[Ss]hardOrder" internal/engine/finance/*_test.go`).
- **AC-13 (GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/finance/*.go` (excluding `_test.go`) continues to return no matches — maintenance accrual, backlog growth, and the CAPEX/OPEX split are all driven by the simulation month/tick, never wall clock.

This BA includes the full debt-service outflow (interest + principal) in the visible composed OPEX per the design's wording, and flags the accounting nuance: if Aaron wants only *interest* in the OPEX component and principal tracked separately (as a financing outflow, not an operating one), that's a one-line amendment to AC-2's identity, not a rewrite.
- **For Bill — ownership boundary of "backlog + efficiency loss".** The efficiency-decline-with-age model is `engine.maintenance`'s (MOD-072, formerly FEAT-089) domain; the *backlog balance* and its *funding* are FEAT-094's (finance-side). Flagging so the owning junior/Tester confirms the seam: finance records the backlog and exposes the factor; maintenance applies it — not both packages computing a rival efficiency figure (GR#3, single source of truth).
