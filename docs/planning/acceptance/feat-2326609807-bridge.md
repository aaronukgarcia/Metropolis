## One-line definition

The bridge is a programmatic player. A script, a test harness or an AI agent calls bridge verbs; each verb is routed through the **same dispatch-site gate the UI uses**, lands in the **same reducer via `guardedDispatch`**, is **journaled identically**, and is **refused identically**. If the UI cannot do it, the bridge cannot do it. If the UI would ask the player to confirm, the bridge must say so explicitly or be refused.

## User stories

- As **Aaron dogfooding**, I want to reproduce "build 40 houses, a wind turbine, tax 12%, run 500 ticks" as a file I can rerun after every commit, so a balance regression or a money leak is caught by a script and not by me clicking for twenty minutes.
- As **a destructive-round attacker**, I want to drive the real store from a test with the player's verbs (not the bare reducer), so an attack proves what a *player* can break, closing the BUG-652/r3 class where reducer-poking tests passed while the real click path was a silent no-op.
- As **the convergence lane** (northstar waypoint 3), I want the same scripted session run against the TS mock and the live Go engine (via the store's existing protocol path) and the two digests compared, so convergence reports are driven by identical inputs.
- As **a future agent player**, I want `bridge.state()` + `bridge.query.*` for observation and the verb set for action, so an agent can play the city end-to-end without a DOM.
- As **the lead**, I want the bridge absent from a production build, so no player ever finds a console API that mints money.

## Scope (inc1 — this document)

In-page bridge core: verb registry, parity/no-bypass/journal proofs, observation API, awaitable clock, session verbs, JSON-lines script runner, DEV-only exposure on `window`. Increments 2–4 are listed under *Out of scope* with their own gating notes; each gets its own AC document before dispatch.

## Design constraints the builder must honour

- **Pure TS, no React** in `bridge.ts`/`bridgeScript.ts`/`bridgeVerbs.ts` — testable under `node --test` with a real store mount (the `mount.test.tsx` harness pattern) and a fake worker, exactly like `protocolClient.ts`.
- **One dispatch path.** The bridge receives the store's `guardedDispatch` and the store's async session verbs by injection (`createBridge({ dispatch, getState, session, clock })`). It never imports the reducer to call it directly and never touches `SimState` by reference.
- **Gate reuse, not gate re-implementation.** Placement verbs call `placementGate.ts`'s `evaluatePlacementBatch` (which already wraps `data.ts`'s `placementAffordability` and the demand-fix prompt) — the bridge's `confirm` option answers the prompt the UI would have shown. Any new gate logic in the bridge is a FAIL (GR#3).
- **Verb registry is the SSOT** (`bridgeVerbs.ts`): each verb declares `{ name, kind: 'action' | 'session' | 'clock' | 'observe' | 'debug', maps: Action['type'] | sessionVerb, journaled: boolean, devOnly: boolean }`. Tests derive from this table and from `journal.ts`'s `isStateAffecting`, never from a hand-typed list (GR#15).
- **Errors** are claimed through `tools/plan/add-error.js` with owner `ui.webconsole` (see memory: FEAT-/BUG- owners redden the Go scanner) — claim the range in the feature commit, never a standalone reservation commit (guard-refused).
- **No storage or clock reads inside verb execution** beyond what the store already does (memory: BUG-602 class). `Date.now` is banned in `bridge*.ts` outside the script runner's wall-clock timeout, which must be injectable.

## Acceptance criteria

### Functional — verb surface and parity

- **AC-1 (Parity, derived).** A test enumerates every member of `engine.ts`'s `Action` union for which `isStateAffecting(action)` is true, and asserts each has exactly one registry verb whose `maps` equals that action type. The enumeration comes from a fixture of one sample action per union member that is itself checked exhaustive by a TypeScript `satisfies Record<Action['type'], Action>` (so adding an action type reds `tsc` until the fixture and the registry are extended). No `hydrate` verb: `hydrate` is the store's internal hand-off and is explicitly listed as `excluded` with a reason string in the registry.
- **AC-2 (Session verbs).** The registry carries one `session` verb for each of the store's async verbs: `save`, `saveAs(name)`, `load`, `loadNamed(slug)`, `exportCity`, `importCity(bytes)`, `startOver`, `rebuild` (hard-reset + genesis replay, FEAT-1972079897). Each resolves to the same boolean/result the store verb returns; a test spies on the injected session object and asserts one call per bridge verb with identical arguments.
- **AC-3 (UI-only verbs are present but flagged).** `speed`, `tool`, `setClipboard`, the four `dismiss*` verbs and `setConsolidatorSliders` exist as `journaled: false` verbs so a script can drive the UI state a player would set. A test asserts the registry's `journaled` flag equals `isStateAffecting` for every `action`-kind verb (one SSOT, no drift).
- **AC-4 (Placement goes through the gate).** `bridge.build(spec, x, y)`, `bridge.buildMany(spec, tiles)` and `bridge.road(spec, tiles, { bendLegal })` call `evaluatePlacementBatch` with the current state before constructing the action. Proof by mutation: a test stubs the gate to return "blocked" and asserts NO `place`/`placeMany`/`placeRoadPath` action reaches the dispatch spy; the same test with the gate returning "proceed" asserts exactly one action reaches it with the same payload the MapView site would construct.
- **AC-5 (Confirmation is explicit, never implied).** When the gate returns a "needs confirmation" outcome (affordability confirm or demand-fix prompt), the verb refuses with `{ ok: false, code: <MET-… bridge-confirm-required>, prompt: <the same message string the UI would show> }` unless the caller passed `{ confirm: true }`, in which case the gate's `onConfirm` path runs. A test proves both branches and asserts the `prompt` string is byte-identical to the one `AffordabilityConfirm` would render for the same state.
- **AC-6 (Refusal parity).** For each of funds-short, locked spec, out-of-bounds tile and does-not-fit tile, a test builds a state where the UI would refuse and asserts the bridge verb returns `ok: false` with a distinct registry code AND that the state digest (`debugjson` SHA-256) is unchanged after the call. The bridge must not "succeed silently" the way a reducer no-op does.
- **AC-7 (Observation SSOT).** `bridge.state()` returns the same object `debugjson.ts` produces for the Debug tab's export (same function, not a copy). `bridge.query` exposes a fixed set of `data.ts` selectors by name (`attractiveness`, `serviceDemand`, `flows`, `placementAffordability`, `worstDemandFix`, plus whatever the builder needs for AC-13's script) and a test asserts each entry is reference-equal to the `data.ts` export, so no selector is re-derived in the bridge (GR#3).
- **AC-8 (Awaitable clock).** `await bridge.tick(n)` resolves only after `n` ticks have *applied* to the store's state (`state.tick` advanced by `n`), not after `n` tick requests were sent. Proof: with the worker path active and a fake worker that delays replies, the promise is still pending until the delayed `hydrate(source:'tick')` lands; with the worker unavailable (main-thread fallback) it resolves after `n` synchronous ticks. A test also asserts `tick(n)` respects the store's BUG-669/N1 supersede semantics — a bridge action dispatched mid-tick does not lose the tick count (no double count, no lost tick).
- **AC-9 (Timeout is explicit).** `bridge.tick(n, { timeoutMs })` rejects with a registry-coded error if the ticks do not apply within the injected clock's budget; the default budget derives from the store's tick interval and `n`, never a hardcoded wall-clock constant (memory: never wall-clock bounds in CI — the test uses a fake timer).

### Functional — script runner

- **AC-10 (Script format).** `bridge.run(script)` accepts JSON-lines: one `{ "verb": "...", "args": {...}, "expect"?: {...} }` per line, plus `{ "tick": n }` lines. A `README` block at the top of `bridgeScript.ts` documents the grammar; a parser test covers a valid script, a malformed line (registry-coded parse error naming the line number), and an unknown verb (registry-coded, names the verb and the nearest registered name).
- **AC-11 (Fail-closed runner).** The runner stops at the first `ok: false` result unless the line carries `"expect": { "ok": false, "code": "MET-…" }` — an expected refusal that matches continues, an expected refusal that does NOT match (different code, or the verb succeeded) fails the run. The run result is `{ ok, lines: [{ line, verb, result }], digest }` where `digest` is the SHA-256 of `bridge.state()` at the end.
- **AC-12 (Determinism of a scripted session, GR#21).** The same script run three times from the same fresh city (same seed, same build) yields three identical digests. A one-line change to the script (e.g. tax rate) yields a different digest. Both asserted.
- **AC-13 (Replay parity).** After a scripted session, the persisted journal replayed from genesis via the existing `genesisReplay.ts` path reproduces the session's final digest exactly. This is the proof that bridge actions are journaled identically to player actions. A mutation check: a bridge verb wired to bypass `guardedDispatch` (calling the reducer directly) makes this test red.
- **AC-14 (A canonical dogfood script ships).** `webconsole/test/fixtures/bridge/baseline-hamlet.jsonl` builds a small playable hamlet (roads, ~10 houses, one wind turbine, water, a shop, a tax change, 300 ticks) and is run by a test asserting: money moved (treasury changed), citizens arrived (`population > 0`), and the run's digest is pinned in a fixture regenerated ONLY through the runner's `--write` entry (the same discipline as `internal/converge/testdata` — BUG-978/BUG-1089 class). A silent digest change reds the test with a message naming the regeneration command.

### Error handling

- **AC-15 (Every refusal is recorded, GR#1/#7).** Each `ok: false` result carries a code claimed via `add-error.js` and a `correlationId`, and the same refusal is passed through `backend.ts`'s `recordError` so the in-app error surface shows it. A test asserts the `recordError` spy fires once per refusal with the same code and correlation id the result carried. A bridge refusal that returns without recording is a FAIL.
- **AC-16 (Wipe verbs honour GR#27).** `startOver`, `load`, `loadNamed`, `importCity` and `rebuild` route through the store's existing `attemptWipe`/capture-before-wipe path. A test makes the capture throw and asserts the verb returns `ok: false` with the store's existing reset-abort code, the state is intact, and no `reset` action reached the dispatch spy.
- **AC-17 (Argument validation is registry-coded).** Wrong-typed or missing arguments (a string tile coordinate, a negative tax rate, an unknown policy id, an unknown spec key) refuse with a registry code and never construct an action. Coercion uses the existing `safeX()`-style helpers (GR#16); no `as any` in `bridge*.ts` (a grep test).

### Safety and exposure

- **AC-18 (Absent in production).** `window.__metropolis.bridge` is installed only when `import.meta.env.DEV` is true OR the build was made with `VITE_BRIDGE=1`. A test of the install function with `{ DEV: false, VITE_BRIDGE: undefined }` asserts nothing is attached to the window object and `createBridge` is never called. The production `vite build` output is grepped for the install-site string as a belt-and-braces check documented in the AC (same pattern as `debugactions.ts`'s DEV gate).
- **AC-19 (Debug namespace is separate and gated).** `bridge.debug.funds(n)`, `bridge.debug.xp(n)`, `bridge.debug.unlockAll()` and `bridge.debug.reset()` exist ONLY under `bridge.debug`, are built from `debugactions.ts`'s `debugActions(dev)` list (reference-equal payloads for the fixed-amount cheats), and are `undefined` when that list is empty. No player-namespace verb maps to `debugFunds`/`debugXp`/`unlockAll`.
- **AC-20 (Rate discipline).** The bridge does not starve the tick: a script issuing 500 placement verbs without a `tick` line still sees the clock advance under the store's K-consecutive-supersedes escape (BUG-669/N1). A test asserts `state.tick` advanced at least once across the 500 verbs with the worker path active.
- **AC-21 (Play Mode and Administration are honoured, not bypassed).** In a sandbox-declined / administration state where the UI disables building, the bridge's placement verbs refuse with the same predicate the UI uses (reference the exact `data.ts`/`engine.ts` predicate at build time); a test toggles the state and asserts refusal, then `enterPlayMode`/`enterAdministration` via the bridge and asserts the UI predicate flips identically.

### Determinism & safety

- **AC-22.** No `Date.now`, `performance.now`, `Math.random`, `localStorage`, `sessionStorage` or `indexedDB` reference in `webconsole/src/sim/bridge.ts`, `bridgeVerbs.ts`, `bridgeScript.ts` (grep test; the runner's timeout takes an injected `now`/timer).
- **AC-23.** Entry-order test (memory: BUG-1051 import-cycle TDZ class): a test imports `bridge.ts` FIRST, before `engine.ts`/`data.ts`/`consolidator.ts`, and asserts no TDZ throw. Constants the bridge needs from the sim live in leaf modules, not read at bridge top level.

### Documentation

- **AC-24.** `bridge.ts`'s header states the module key `ui.webconsole`, the BOW code, the one-line definition above, the DEV/`VITE_BRIDGE` exposure rule, the "same gate, same dispatch, same journal" invariant with pointers to `placementGate.ts`, `guardedDispatch` and `journal.ts`, and a 10-line quick start (`const b = window.__metropolis.bridge; await b.build('res_house', 12, 8); await b.tick(10); b.state().treasury`).
- **AC-25.** `docs/planning/bridge.md` documents the verb table (generated from `bridgeVerbs.ts` by a small script so it cannot drift — a test compares the generated table to the committed file), the JSON-lines grammar, the canonical hamlet script, and the increment roadmap below.

## Out of scope (later increments — each needs its own AC doc before dispatch)

- **inc2 — out-of-process driver.** A Node driver (`webconsole/scripts/bridge-drive.mjs`) that opens the dev server in a headless browser and forwards a JSON-lines script over the page's bridge, returning the run result and digest; loopback-only, token-gated, never in the production bundle. Enables CI soak runs and agent play without a human. GR#25: still inside `ui.webconsole`; if a persistent WebSocket control channel is chosen instead of a browser driver, register it as an interface item first (INT-005 is the engine transport, not this).
- **inc3 — recorder.** Debug-tab "Export session as bridge script": journal → JSON-lines (each `JournalEntry` maps to one verb line via the registry; `hydrate` entries become a `load` line referencing the savepoint). Every player-found bug then ships with a repro script.
- **inc4 — Go mirror.** `metctl drive <script>` running the same verb set against the Go engine through `int.protocol` commands (`Build`/`Demolish`/`Zone`/`SetSpeed`/`Pause`/`Resume`/`AdvanceTicks`/`SetFunding` exist today in `internal/protocol/commands.go`; verbs with no protocol command yet are listed as gaps for `int.protocol`, not implemented ad hoc). This is the H-HEADLESS scenario scripting the metctl doc already promises, and the input side of convergence A/B.
- **Agent policy / autoplay.** The bridge is the hands, not the brain. No planner, no heuristics, no "auto-build" verb.
- **Multiplayer / remote play.** Loopback and dev only until Aaron rules otherwise.
