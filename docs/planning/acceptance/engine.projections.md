## User stories

- **US-1.** As any engine system with a demand/supply curve, I need to register a curve provider with `engine.projections` (per code.json's "systems register curve providers" pattern), so my system's future values are visible to the player without me building my own projection UI.
- **US-2.** As the player, I need every registered curve to render its history and its projected future on one pane (§13 F7, UI-SPEC §4), so I can see trouble — a deficit, a capacity breach — before it happens, not after.
- **US-3.** As the player queuing a decision (e.g. a school build), I need the projection to show my queued decision's future effect as a step in the curve *before* it lands (UI-SPEC §4's decision-marker idiom), so committing to a plan is visibly rewarded ahead of completion.
- **US-4.** As any decision confirmation flow whose principal effect lands more than 5 game-years out (education funding, planning quality, rehabilitation regime, BDI, debt — A5's named list, non-exhaustive), I need the confirmation UI to be *structurally unable* to proceed without a rendered projected consequence, so the anti-ambush contract cannot be silently skipped by a module that forgets to call it.
- **US-5.** As the player reading a projection, I need to be able to tell a computed consequence (derived from real registered curves within the current forecasting horizon) apart from a guess (an extrapolation beyond what the game has actually modelled), so I never mistake confidence for certainty.
- **US-6.** As `engine.unlocks` (a later/other-sprint system), I need the forecasting horizon N to be a queryable, data-sourced quantity rather than a Go constant, so unlocking "extended forecasting" is a data/config change this module already supports, not a rebuild of it.
- **US-7 (FEAT-068).** As `engine.finance` and `engine.spiral`, the two modules that own this game's death conditions, I need a genuine, trend-derived time-to-death signal I can query and hold my own trigger path against — not merely a UI decoration — so that "the projections engine warned you" (this item's own title) is a provable, causally-connected fact about my own trigger path, not a coincidence of timing.

## Scope

A curve-provider registry (`ProjectionsAPI`) that composes registered systems' curves (seasonally aware via `engine.season`) into history+future series over a horizon N; a decision-marker mechanism so queued-but-unbuilt decisions appear in the projected curve; and the Slow-Fuse gate — a generic, decision-type-agnostic mechanism enforcing that any decision tagged with a >5-game-year fuse cannot be confirmed without an attached projected-consequence payload, together with an explicit confidence/provenance distinction on every projected point. **Added 2026-08-12 (FEAT-068):** `MarginToInsolvency`/`MarginToGhostCity` time-to-death signals, trend-derived from `engine.finance`'s/`engine.spiral`'s own registered curves, plus the `WarningLedger` those two modules' own death-condition gates query to prove they never fire without a prior warning.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `ProjectionsAPI` (or equivalent) exists matching code.json's documented pattern: a registration surface for curve providers (e.g. `RegisterCurveProvider(key, provider)`) and a subscription/query surface for consumers (e.g. `Subscribe`/`Curve(key, fromMonth, toMonth)`), consumed today by `engine.capexport`, `engine.policies`, `ui.alerts`, `ui.screen.proj`. Check: `go doc ./internal/engine/projections ProjectionsAPI` shows both a registration method taking a provider/callback (not a one-off hardcoded switch on system name) and a query method taking a curve key and a month range.
- **AC-2 (§13 F7; horizon is data-sourced, GR#15).** The forecasting horizon N (in months, converted from years — see ASM-239) is read from a config/unlock-tier input at query time, not a hardcoded Go literal, so raising N later (unlocked forecasting, cloud offload per §13 F7) is a data change. Check: `grep -nE "\b60\b|\b72\b" internal/engine/projections/*.go` (excluding `_test.go`) finds no bare month-count literal standing in for the horizon; `grep -n "HorizonMonths\|ForecastHorizon" internal/engine/projections/*.go` shows the horizon read from a passed-in/config value. **False pass warning:** a grep alone cannot tell the difference between "reads from config" and "reads a constant that happens to live in a different file" — the accompanying test (below) is load-bearing, not the grep.
- **AC-3 (§13 F7 seasonally aware; dependency MOD-027).** A curve whose underlying value is seasonally driven (via `engine.season`'s `SeasonAPI`) produces a projected series that varies month-to-month across the horizon, not a linear/flat trend that ignores the seasonal component. Check: a passing test registers a fake curve provider that composes a seasonal multiplier, queries a 12+ month horizon, and asserts the returned series is *not* monotonic/flat where the seasonal input is not (`grep -rn "func Test.*[Ss]easonal.*[Pp]rojection" internal/engine/projections/*_test.go`). **Lazy implementation this rejects:** a projections engine that only ever straight-line-extrapolates the current trend (ignoring registered seasonal composition) would satisfy AC-1's registration/query shape but produce a flat-slope series here — this test specifically catches that.
- **AC-4 (UI-SPEC §4 decision markers; anti-ambush contract).** Enqueuing a future-dated decision (e.g. a build-queue command with a documented completion month) causes the projected curve for the affected capacity metric to show a step at that future month *before* the decision has actually landed in current/actual state, and removing/cancelling the queued decision removes the step. Check: a passing test enqueues a fake future decision, queries the projection before and after enqueue, and asserts the post-enqueue curve differs at the decision's completion month while the *current* (month-0) value is unchanged (`grep -rn "func Test.*[Dd]ecisionMarker\|func Test.*[Qq]ueuedStep" internal/engine/projections/*_test.go`). **Lazy implementation this rejects:** a projection that only reflects state changes once a decision actually executes (i.e. no "queued" concept at all) would pass a naive "the chart updates eventually" reading but fails this before/after-completion-month distinction.
- **AC-5 (A5 Slow-Fuse — the core rule; ASM-238).** A generic, decision-type-agnostic gate exists: any decision submitted through the confirmation path carrying a `FuseYears` (or equivalent) tag greater than 5 must have a non-nil, non-empty projected-consequence payload attached, or the confirmation is rejected — enforced by one shared gate function operating on the tag, not a per-decision-type if/else list. Check: a passing test registers a **fake, previously-unknown decision type** (not one of A5's five named examples) with `FuseYears: 6` and no projection payload, submits it through the gate, and asserts rejection; a second test attaches a projection payload and asserts acceptance. `grep -n "FuseYears\|SlowFuse" internal/engine/projections/*.go` shows the tag consumed by one shared function. **Lazy implementation this rejects, and why it's the load-bearing check:** an implementation that hardcodes the check only for `education`, `planning`, `rehabilitation`, `bdi`, `debt` (A5's five named examples) would pass every test that only exercises those five, and would silently fail to protect the sixth long-fuse decision some future module adds — the fake-decision-type test is specifically designed to be unpassable by a hardcoded list.
- **AC-6 (confidence/provenance — "what a projection promises and does not").** Every projected point carries an explicit confidence/basis marker distinguishing at least: `Computed` (derived from a registered curve provider within the current horizon N) from `Unavailable` or `Extrapolated` (beyond N, or from a provider that itself only supplies a trend continuation rather than a modelled curve). Querying a month beyond the current horizon N never returns a point tagged `Computed`. Check: `go doc ./internal/engine/projections` shows a `Confidence`/`Basis` type with at least two distinct values; a passing test queries within-horizon and asserts `Computed`, then queries beyond-horizon and asserts the result is *not* `Computed` (either an error, or a differently-tagged point) (`grep -rn "func Test.*[Cc]onfidence\|func Test.*[Bb]eyondHorizon" internal/engine/projections/*_test.go`). **Lazy implementation this rejects — this is the Slow-Fuse anti-ambush failure mode named in the brief:** an implementation that keeps extrapolating a flat/trend line past N and tags it identically to a real computed value would satisfy "a curve renders for any month" but is exactly the "guess presented with the same confidence as a computed consequence" failure this AC exists to catch.
- **AC-7 (UI-SPEC §4 history vs projection rendering).** The data payload handed to a UI consumer distinguishes historical points from projected points (e.g. a boolean field or two separate slices), so the UI can render solid-vs-dim per the documented idiom, rather than one undifferentiated series the UI would have to guess about. Check: `go doc ./internal/engine/projections` shows the query result type carrying a historical/projected distinction per point or per segment.
- **AC-8 (UI-SPEC §4 threshold lines).** A curve provider can register a threshold value (e.g. a capacity ceiling) alongside its value series, retrievable independently of the value series itself, so the UI can draw a threshold line without the projections engine hardcoding what "danger" means for each system. Check: `go doc ./internal/engine/projections` shows a threshold-registration/query surface distinct from the value-series surface.

Check: `grep -n "MET-" internal/engine/projections/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregistered\|func Test.*[Nn]egativeMonth" internal/engine/projections/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value curve was silently returned as if valid, not merely that a matching-named test function exists.

Check: `grep -n "MET-" internal/engine/projections/*.go` finds this specific code path; passing test coverage (`grep -rn "func Test.*[Ss]lowFuse.*[Rr]eject" internal/engine/projections/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches the claimed SlowFuse-class code AND that no confirmation was silently accepted without the required projection payload, not merely that a matching-named test function exists.

### Impending-doom warnings (FEAT-068 — added 2026-08-12, BA-S-death-warnings; this module is the "projections must warn" half of the item's own title)

Bill's dispatch note for FEAT-068 states the core requirement in six words: **"firing without prior warning = defect."** The ACs below make that a structural property of `ProjectionsAPI` rather than a UI convention — `engine.finance.md`'s AC-29 and `engine.spiral.md`'s AC-15 are the other half, each requiring their own death-condition trigger path to be provably gated on the warning signal this module computes here. This module's obligation is narrower and load-bearing: compute a genuine, trend-derived margin, never a cosmetic or invented one.

- **AC-17 (FEAT-068; `MarginToInsolvency` — sourced from real `engine.finance` state trending, not invented).** `ProjectionsAPI` exposes a `MarginToInsolvency` query returning a time-to-threshold estimate (months remaining until `engine.finance` AC-7's insolvency condition — 3 consecutive months unable to meet obligations with no available credit — would fire if the current trend continues) plus a confidence/basis marker per AC-6's `Computed`/`Extrapolated` distinction. The estimate is computed by extrapolating a curve `engine.finance` itself registers via the existing `engine.finance`→`engine.projections` outbound edge (confirmed registered: `node -e "require('./code.json').modules.find(m=>m.key==='engine.finance').outbound.calls.some(c=>c.key==='engine.projections')"` exits with a truthy edge) — this module does not reimplement `engine.finance`'s own missed-payment/credit-availability bookkeeping, it only extrapolates the trend `engine.finance` publishes. Check: `go doc ./internal/engine/projections MarginToInsolvency` (or equivalent) exists; a passing test registers a fake `engine.finance`-shaped curve provider at three successively worsening trend states (healthy → one missed payment → two consecutive missed payments) and asserts the returned months-remaining figure **strictly decreases** across the three queries, then re-registers the same provider at a fourth, *recovering* state and asserts the figure increases again (`grep -rn "func Test.*[Mm]arginToInsolven" internal/engine/projections/*_test.go`). **False-pass risk:** a static "you're at risk" boolean, or a number that changes only when a human-authored threshold constant is crossed rather than tracking the actual registered trend continuously, would pass a shallow "a warning value exists" check but fail this monotonic four-point test — the check specifically requires the figure to move with the trend, including recovering when the trend recovers, which a one-way ratchet or a cosmetic flag cannot do.
- **AC-18 (FEAT-068; `MarginToGhostCity` — sourced from real `engine.spiral` state trending — edge landed BUG-118, 2026-08-12; real wiring now required, not the interim fallback; see Corrections).** The same pattern as AC-17 for the population/ghost-city death condition (`engine.spiral.md` AC-7's dual threshold: population below 10% of historic peak, where that peak has exceeded 50,000): a `MarginToGhostCity` query returning months-remaining-until-threshold plus confidence, extrapolated from a curve `engine.spiral` (or `engine.attract`, whichever owns the live population/migration trend — see `engine.spiral.md`'s own ASM-242) registers. **Tripwire (mechanical):** `node -e "const cj=require('./code.json'); const s=cj.modules.find(m=>m.key==='engine.spiral'); const p=cj.modules.find(m=>m.key==='engine.projections'); process.exit((s.outbound.calls.some(c=>c.key==='engine.projections')||p.inbound.consumers.some(c=>c.key==='engine.spiral'))?0:1)"` now exits 0 (re-confirmed 2026-08-12, BUG-118) — the same edge `engine.finance`'s AC-17 already relies on now also covers `engine.spiral`. The interim fallback that used to apply while the tripwire exited 1 (specify `MarginToGhostCity`'s signature and buildable against a fake provider only, mirroring `feat.disasters.md` AC-7's pattern for a still-blocked edge) is retired — the real `engine.spiral` wiring (`engine.spiral.md` AC-15's job) is now buildable and required, not merely specifiable. No code exists yet in `internal/engine/projections/` (the package has not been created), so there is nothing built against the retired interim that needs migrating. The margin is undefined/`Unavailable` (not a false "0 months" alarm) for any city whose historic peak has never exceeded 50,000, matching `engine.spiral.md` AC-7's dual-condition requirement. Check: `go doc ./internal/engine/projections MarginToGhostCity` shows the query and its `Unavailable`-below-50,000-peak case; a passing test against a fake provider mirrors AC-17's three-successively-worsening-state monotonic check, plus a fourth case asserting `Unavailable` when peak has never exceeded 50,000 regardless of current population (`grep -rn "func Test.*[Mm]arginToGhostCity" internal/engine/projections/*_test.go`).
- **AC-19 (FEAT-068; a queryable `WarningLedger` — the record a death-condition trigger can be checked against, independent of any UI rendering).** Every time `MarginToInsolvency` or `MarginToGhostCity` (AC-17/AC-18) crosses a data-sourced warning threshold (AC-20), `ProjectionsAPI` records a timestamped entry — sim month, metric, margin value at time of crossing — in a `WarningLedger` queryable by month range and metric, independent of whether any UI ever rendered it. This ledger is the mechanism `engine.finance.md` AC-29 and `engine.spiral.md` AC-15 query to prove their own death-condition trigger was preceded by a warning; it must exist and be queryable **before** those two files' gates can be built, which is why it is specified here rather than duplicated in each. Check: `go doc ./internal/engine/projections WarningLedger` (or equivalent) shows a query-by-metric/month-range method; a passing test crosses the threshold via a fake provider at a known sim month and asserts a ledger entry appears at that exact month with the correct metric and margin value, and that a query for a month range entirely before the crossing returns no entry (`grep -rn "func Test.*[Ww]arningLedger" internal/engine/projections/*_test.go`). **False-pass risk:** a ledger that records an entry for *every* tick regardless of whether the threshold was actually crossed (i.e., "always warning") would pass a shallow "an entry exists" check while making AC-29/AC-15's lead-time proof meaningless — the check requires the pre-crossing query to come back empty, proving the ledger tracks the crossing event, not a permanent state.
- **AC-20 (GR#15; the warning thresholds are data-sourced placeholders, not Go constants — balance-number regime).** Both the "months-remaining crosses into warning" threshold (AC-19) and the **minimum lead time** a downstream death-condition gate is entitled to expect (the value `engine.finance.md` AC-29 and `engine.spiral.md` AC-15 both compare their measured lead time against) live in a JSON data file (e.g. `data/deathwarnings.json`), never a Go literal, and carry a non-empty placeholder/pending-tuning disclosure field per entry — same convention as `data/market.json`'s "pending M2 Batch tuning" and FEAT-057's balance-number regime (`engine.finance.md` AC-21). Insolvency and ghost-city may carry different values (their dynamics differ — insolvency can move in single-month steps via a missed payment, ghost-city moves on slower demographic timescales) rather than being forced to share one number. Check: `grep -nE "MinWarningLeadMonths|WarningThreshold" internal/engine/projections/*.go` (excluding `_test.go`) shows the values read from a loaded data file, not a bare numeric literal; a passing loader test asserts both entries carry a non-empty disclosure field (`grep -rn "func Test.*[Pp]laceholderDisclosure.*[Ww]arning\|func Test.*[Dd]eathWarningData" internal/engine/projections/*_test.go`). **What a lazy implementation looks like:** a junior picking `MinWarningLeadMonths = 6` directly in Go "because it sounds reasonable" — this is the exact ASM-284/AC-21-class overstep the balance-number regime exists to prevent, and it fails this AC even if AC-17/AC-18/AC-19 all pass.

## Out of scope

- The forecasting-horizon **unlock mechanism itself** (which milestone/dev-point tree unlocks a longer N, cloud-offload extension) — that is `engine.unlocks`'s job; this item only needs to read N from wherever that system publishes it (or a config stand-in until `engine.unlocks` exists).
- Any individual system's actual curve math (what `engine.education`'s attainment curve looks like, what `engine.finance`'s debt-service curve looks like) — this item only provides the registration/composition/rendering-payload/Slow-Fuse-gate mechanism those systems build against.
- The real wiring of education/debt decisions through the Slow-Fuse gate (A5's own named examples) — those modules do not yet exist in this sprint and have no registered `ProjectionsAPI` inbound edge in code.json (see BUG-058 comment, 2026-08-11); this item's ACs are tested against fake/synthetic decision types precisely because the real consumers aren't buildable yet.
- `int.solver`'s cloud-offload path for "deep projections" (§15 Architecture) — registered as an outbound call in code.json but out of scope until the cloud tiers are built.
- A specific tuned value for the base horizon N, threshold magnitudes, or any curve's numeric shape — those are M2 Batch-tuning balance numbers; this item's job is the mechanism and a documented, assumption-logged default.
- The death-condition trigger logic itself (`engine.finance`'s `IsInsolvent`, `engine.spiral`'s ghost-city check) and the gate that makes each provably wait on this module's warning — `engine.finance.md` AC-29 and `engine.spiral.md` AC-15's job respectively; this module only computes and records the warning signal (AC-17/AC-18/AC-19), it does not enforce that anything waits on it.
- The player-facing UI surface for these warnings (which screen, alert style, minimum-lead-time balance figure as shown to the player) — `feat.deathwarnings.md`'s job.

Added as a third instance to the existing BUG-058 (comment logged 2026-08-11) rather than a new item — same class defect (spec-mandated call path, no registered edge).
