## User stories

- **US-1.** As any engine system with a demand/supply curve, I need to register a curve provider with `engine.projections` (per code.json's "systems register curve providers" pattern), so my system's future values are visible to the player without me building my own projection UI.
- **US-2.** As the player, I need every registered curve to render its history and its projected future on one pane (§13 F7, UI-SPEC §4), so I can see trouble — a deficit, a capacity breach — before it happens, not after.
- **US-3.** As the player queuing a decision (e.g. a school build), I need the projection to show my queued decision's future effect as a step in the curve *before* it lands (UI-SPEC §4's decision-marker idiom), so committing to a plan is visibly rewarded ahead of completion.
- **US-4.** As any decision confirmation flow whose principal effect lands more than 5 game-years out (education funding, planning quality, rehabilitation regime, BDI, debt — A5's named list, non-exhaustive), I need the confirmation UI to be *structurally unable* to proceed without a rendered projected consequence, so the anti-ambush contract cannot be silently skipped by a module that forgets to call it.
- **US-5.** As the player reading a projection, I need to be able to tell a computed consequence (derived from real registered curves within the current forecasting horizon) apart from a guess (an extrapolation beyond what the game has actually modelled), so I never mistake confidence for certainty.
- **US-6.** As `engine.unlocks` (a later/other-sprint system), I need the forecasting horizon N to be a queryable, data-sourced quantity rather than a Go constant, so unlocking "extended forecasting" is a data/config change this module already supports, not a rebuild of it.

## Scope

A curve-provider registry (`ProjectionsAPI`) that composes registered systems' curves (seasonally aware via `engine.season`) into history+future series over a horizon N; a decision-marker mechanism so queued-but-unbuilt decisions appear in the projected curve; and the Slow-Fuse gate — a generic, decision-type-agnostic mechanism enforcing that any decision tagged with a >5-game-year fuse cannot be confirmed without an attached projected-consequence payload, together with an explicit confidence/provenance distinction on every projected point.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `ProjectionsAPI` (or equivalent) exists matching code.json's documented pattern: a registration surface for curve providers (e.g. `RegisterCurveProvider(key, provider)`) and a subscription/query surface for consumers (e.g. `Subscribe`/`Curve(key, fromMonth, toMonth)`), consumed today by `engine.capexport`, `engine.policies`, `ui.alerts`, `ui.screen.proj`. Check: `go doc ./internal/engine/projections ProjectionsAPI` shows both a registration method taking a provider/callback (not a one-off hardcoded switch on system name) and a query method taking a curve key and a month range.
- **AC-2 (§13 F7; horizon is data-sourced, GR#15).** The forecasting horizon N (in months, converted from years — see ASM-239) is read from a config/unlock-tier input at query time, not a hardcoded Go literal, so raising N later (unlocked forecasting, cloud offload per §13 F7) is a data change. Check: `grep -nE "\b60\b|\b72\b" internal/engine/projections/*.go` (excluding `_test.go`) finds no bare month-count literal standing in for the horizon; `grep -n "HorizonMonths\|ForecastHorizon" internal/engine/projections/*.go` shows the horizon read from a passed-in/config value. **False pass warning:** a grep alone cannot tell the difference between "reads from config" and "reads a constant that happens to live in a different file" — the accompanying test (below) is load-bearing, not the grep.
- **AC-3 (§13 F7 seasonally aware; dependency MOD-027).** A curve whose underlying value is seasonally driven (via `engine.season`'s `SeasonAPI`) produces a projected series that varies month-to-month across the horizon, not a linear/flat trend that ignores the seasonal component. Check: a passing test registers a fake curve provider that composes a seasonal multiplier, queries a 12+ month horizon, and asserts the returned series is *not* monotonic/flat where the seasonal input is not (`grep -rn "func Test.*[Ss]easonal.*[Pp]rojection" internal/engine/projections/*_test.go`). **Lazy implementation this rejects:** a projections engine that only ever straight-line-extrapolates the current trend (ignoring registered seasonal composition) would satisfy AC-1's registration/query shape but produce a flat-slope series here — this test specifically catches that.
- **AC-4 (UI-SPEC §4 decision markers; anti-ambush contract).** Enqueuing a future-dated decision (e.g. a build-queue command with a documented completion month) causes the projected curve for the affected capacity metric to show a step at that future month *before* the decision has actually landed in current/actual state, and removing/cancelling the queued decision removes the step. Check: a passing test enqueues a fake future decision, queries the projection before and after enqueue, and asserts the post-enqueue curve differs at the decision's completion month while the *current* (month-0) value is unchanged (`grep -rn "func Test.*[Dd]ecisionMarker\|func Test.*[Qq]ueuedStep" internal/engine/projections/*_test.go`). **Lazy implementation this rejects:** a projection that only reflects state changes once a decision actually executes (i.e. no "queued" concept at all) would pass a naive "the chart updates eventually" reading but fails this before/after-completion-month distinction.
- **AC-5 (A5 Slow-Fuse — the core rule; ASM-238).** A generic, decision-type-agnostic gate exists: any decision submitted through the confirmation path carrying a `FuseYears` (or equivalent) tag greater than 5 must have a non-nil, non-empty projected-consequence payload attached, or the confirmation is rejected — enforced by one shared gate function operating on the tag, not a per-decision-type if/else list. Check: a passing test registers a **fake, previously-unknown decision type** (not one of A5's five named examples) with `FuseYears: 6` and no projection payload, submits it through the gate, and asserts rejection; a second test attaches a projection payload and asserts acceptance. `grep -n "FuseYears\|SlowFuse" internal/engine/projections/*.go` shows the tag consumed by one shared function. **Lazy implementation this rejects, and why it's the load-bearing check:** an implementation that hardcodes the check only for `education`, `planning`, `rehabilitation`, `bdi`, `debt` (A5's five named examples) would pass every test that only exercises those five, and would silently fail to protect the sixth long-fuse decision some future module adds — the fake-decision-type test is specifically designed to be unpassable by a hardcoded list.
- **AC-6 (confidence/provenance — "what a projection promises and does not").** Every projected point carries an explicit confidence/basis marker distinguishing at least: `Computed` (derived from a registered curve provider within the current horizon N) from `Unavailable` or `Extrapolated` (beyond N, or from a provider that itself only supplies a trend continuation rather than a modelled curve). Querying a month beyond the current horizon N never returns a point tagged `Computed`. Check: `go doc ./internal/engine/projections` shows a `Confidence`/`Basis` type with at least two distinct values; a passing test queries within-horizon and asserts `Computed`, then queries beyond-horizon and asserts the result is *not* `Computed` (either an error, or a differently-tagged point) (`grep -rn "func Test.*[Cc]onfidence\|func Test.*[Bb]eyondHorizon" internal/engine/projections/*_test.go`). **Lazy implementation this rejects — this is the Slow-Fuse anti-ambush failure mode named in the brief:** an implementation that keeps extrapolating a flat/trend line past N and tags it identically to a real computed value would satisfy "a curve renders for any month" but is exactly the "guess presented with the same confidence as a computed consequence" failure this AC exists to catch.
- **AC-7 (UI-SPEC §4 history vs projection rendering).** The data payload handed to a UI consumer distinguishes historical points from projected points (e.g. a boolean field or two separate slices), so the UI can render solid-vs-dim per the documented idiom, rather than one undifferentiated series the UI would have to guess about. Check: `go doc ./internal/engine/projections` shows the query result type carrying a historical/projected distinction per point or per segment.
- **AC-8 (UI-SPEC §4 threshold lines).** A curve provider can register a threshold value (e.g. a capacity ceiling) alongside its value series, retrievable independently of the value series itself, so the UI can draw a threshold line without the projections engine hardcoding what "danger" means for each system. Check: `go doc ./internal/engine/projections` shows a threshold-registration/query surface distinct from the value-series surface.

### Error handling

- **AC-9 (GR#7).** Querying an unregistered curve key, or a month index before the world's epoch, returns a registry-sourced error (new `MET-E`-range code) naming the key/month, never a zero-value curve silently returned as if valid. Check: `grep -n "MET-" internal/engine/projections/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregistered\|func Test.*[Nn]egativeMonth" internal/engine/projections/*_test.go`).
- **AC-10 (GR#7; AC-5's error path).** A confirmation submitted for a `FuseYears>5` decision with no projection payload attached produces a registry-sourced `SlowFuse`-class error naming the decision and the missing payload, not a generic validation failure or a silent pass-through. Check: `grep -n "MET-" internal/engine/projections/*.go` finds this specific code path; passing test coverage (`grep -rn "func Test.*[Ss]lowFuse.*[Rr]eject" internal/engine/projections/*_test.go`).

### Determinism & safety

- **AC-11 (GR#21).** The same registered-curve state, current sim month, and horizon N produce a byte-identical/hash-identical projected series across repeated calls and across worker/shard counts. Check: a passing test computes the same projection twice (and at two worker counts where feasible) and asserts identical output (`grep -rn "func Test.*[Dd]eterminis" internal/engine/projections/*_test.go`).
- **AC-12 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/projections/*.go` (excluding `_test.go`) returns no matches — projections are a function of simulation month index and registered curve state, never wall clock.
- **AC-13 (relative-regression cost, not a wall-clock bound — see brief).** Projection recomputation contributes phase-timed cost recorded through `harness.synth`'s existing `PerfResult`/`PerfRecord` machinery (`internal/harness/synth/perf.go`, `results.go`) when run under the perf/synthetic harness, so a regression is caught by `CompareToBaseline`'s relative comparison against a CI-recorded baseline (`internal/harness/synth/baseline.go`), never asserted as an absolute wall-clock duration inside this package's own tests. Check: `internal/engine/projections/doc.go` names the phase/hook this package reports its cost under for `harness.synth` to time; `grep -rn "time\.Since|elapsed <|elapsed >|Sleep\(" internal/engine/projections/*_test.go` finds no wall-clock-duration assertions in this package's own test suite. **Explicit caveat this AC's doc.go must state (per the brief):** `BUG-034` is open and no CI-measured real-scale baseline has been recorded yet — this AC verifies the package is *wired* to report through `harness.synth`'s relative-comparison machinery, not that a passing regression comparison currently exists. Citing "no regression against the CI baseline" today would be citing a baseline that does not exist.
- **AC-14.** `go test ./internal/engine/projections/... -race -count=1` passes with no data race when curve providers register/query concurrently from multiple consumer modules/shards. Check: `grep -n "go func()" internal/engine/projections/*_test.go` finds at least one concurrency test.

### Documentation

Check: `grep -n "engine.projections" internal/engine/projections/doc.go` and `grep -n "A5\|Slow-Fuse" internal/engine/projections/doc.go` and `grep -n "ASM-237" internal/engine/projections/doc.go` all match.

Check: `grep -n "BUG-058" internal/engine/projections/doc.go` matches.

## Out of scope

- The forecasting-horizon **unlock mechanism itself** (which milestone/dev-point tree unlocks a longer N, cloud-offload extension) — that is `engine.unlocks`'s job; this item only needs to read N from wherever that system publishes it (or a config stand-in until `engine.unlocks` exists).
- Any individual system's actual curve math (what `engine.education`'s attainment curve looks like, what `engine.finance`'s debt-service curve looks like) — this item only provides the registration/composition/rendering-payload/Slow-Fuse-gate mechanism those systems build against.
- The real wiring of education/debt decisions through the Slow-Fuse gate (A5's own named examples) — those modules do not yet exist in this sprint and have no registered `ProjectionsAPI` inbound edge in code.json (see BUG-058 comment, 2026-08-11); this item's ACs are tested against fake/synthetic decision types precisely because the real consumers aren't buildable yet.
- `int.solver`'s cloud-offload path for "deep projections" (§15 Architecture) — registered as an outbound call in code.json but out of scope until the cloud tiers are built.
- A specific tuned value for the base horizon N, threshold magnitudes, or any curve's numeric shape — those are M2 Batch-tuning balance numbers; this item's job is the mechanism and a documented, assumption-logged default.

## Escalations

- **For Bill/Aaron (ASM-237, P0).** No base/default projection horizon N is stated anywhere in the spec for before any forecasting unlock — only that N "grows with unlocked forecasting". A5's Slow-Fuse Principle requires projecting *any* decision whose effect lands >5 game-years out, at *any* point in the game, with no stated exemption for early/low-unlock play. If the intended base N is shorter than 5-6 years (e.g. deliberately withholding long-range visibility as a progression gate), A5 and F7's unlock-gated-N are in direct, unresolved tension — this is a spec conflict for Aaron, not something a BA or a junior should silently resolve either direction.
- **For Ben (BUG-058, filed this wave).** `code.json`'s `engine.projections` inbound consumer list is `engine.capexport`, `engine.policies`, `ui.alerts`, `ui.screen.proj` only — it does not include `engine.education` or `engine.finance`, even though the S7 exit gate names "Slow-Fuse projections render for education/debt-class decisions" as a required clause. Under GR#20 those two modules have no legal call path to register curve providers or attach a projected consequence at confirmation time. Added as a third instance to the existing BUG-058 (comment logged 2026-08-11) rather than a new item — same class defect (spec-mandated call path, no registered edge). This item's own ACs are written to be testable without that edge (fake decision types), but the S7 gate clause cannot be *fully* satisfied — real education/debt wiring — until BUG-058 is fixed and those modules land.
- **For Ben.** The "300 game-years headless in seconds-minutes" clause of the S7 exit gate is not this module's to own or to make testable — see the brief's finding, repeated here for the record: it is a literal wall-clock claim (forbidden in CI per this project's flakiness rule) and cannot be translated into `harness.synth`'s relative-regression machinery as-is because that harness is keyed to citizen count, not simulated duration — that measurement axis doesn't exist yet. AC-13 above routes *this* module's own cost through `harness.synth`'s existing relative-comparison machinery so a projections-engine regression is at least catchable, but does not solve the axis-mismatch problem for the gate clause as a whole, and `BUG-034`'s CI-measured 1M baseline still does not exist as of this writing.
