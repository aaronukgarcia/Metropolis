# Acceptance criteria — feat.disasters (FEAT-012)

**BOW code:** FEAT-012
**Spec refs:** §10 Service & Feature Inventory (`docs/METROPOLIS-MASTER-v2.1.md` line 230: "...disasters-lite (road closure, storm surge on the shore, aquifer drought) as **event pressure on JIT**"); §W (chalk aquifer / boreholes — line 195: "Aquifer has a sustainable yield ceiling; over-abstraction degrades it. Seasonal stress"); code.json `feat.disasters` entry (inbound: **name/format/pattern all null, zero registered consumers** — a scaffolding gap, see AC-1/Escalations; outbound calls `engine.logistics`, `engine.world`). Owning module for the machinery this feature drives: `engine.logistics.md` (MOD-025) — specifically AC-2 (stock draw/partial fill), AC-3 (lean/fat buffer divergence), AC-4 (junction slot saturation → next-day queue), AC-7 (perishable expiry in queue), AC-9/AC-10 (shortfall is a nonzero typed value reaching a documented downstream hook). **This file does not restate those rules; every AC below is an obligation this feature owes to that machinery, checked by proving the pressure actually reaches it.**
**Date:** 2026-08-11 (BA-S11a, first pass)
**Status:** draft-ahead — `MOD-017` (engine.world) and `MOD-025` (engine.logistics) are both `open`; this item is not in the ready queue until both land.
**Package under test:** `internal/engine/events/` (path from `node claude-bow.js show FEAT-012`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/events/...`.

## User stories

- **US-1.** As `engine.logistics` (the module this feature exists to stress, per its own spec framing "event pressure on JIT"), I need every disaster category to apply pressure through my **real** stock/queue/junction/shortfall mechanisms — not a parallel, disaster-owned simulation that merely looks similar — so a disaster is a genuine JIT stress-test, not a scripted cutscene running alongside the real engine.
- **US-2.** As the player, I need "never random-spam, projected where possible" (§10) to be mechanically true — every event category preceded by a rising, observable precursor — so a disaster reads as foreshadowed pressure, not an unconditioned dice roll, mirroring the identical requirement `engine.crime.md` AC-11 states for the MI5 threat dial.
- **US-3.** As a future Tester, I need "resolved through the same logistics/dispatch machinery" (§10) to mean there is **no second resolution timeline** — recovery from an event is simply the affected module's own state returning to baseline through its own normal tick processing, not a disaster-owned countdown that separately "heals" a duplicated state.
- **US-4.** As `code.json`'s own registered edges, I need this item to be honest that its inbound contract is currently entirely unpopulated (name/format/pattern null, zero consumers) and that `engine.services.md`'s own out-of-scope note explicitly expects this feature to register as a service-adjacent category — a promise the registry cannot currently fulfil (GR#20; BUG-058).

## Scope

Event-pressure generation for the three named categories (road closure, storm surge on shore cells, aquifer drought) applied exclusively through `engine.logistics`'s and `engine.world`'s existing registered mechanisms; the never-random-spam precursor requirement shared in spirit with `engine.crime.md`'s MI5 dial; the no-bespoke-resolution rule that keeps recovery inside the host module's own state machine.

## Acceptance criteria

### Functional — pressure reaches the real machinery, not a parallel one

- **AC-1 (GR#20; code.json inbound contract — currently null, a data-hygiene gap distinct from a missing call edge).** An event-pressure inbound contract is defined and implemented: an `EventsAPI`/`DisasterAPI` exposes queryable active-event state (type, affected cells/junctions, severity, remaining pressure) and command-based event injection for scenario/test use — even though code.json's own `name`/`format`/`pattern` fields for this module are currently null and its consumers list is empty. Check: `go doc ./internal/engine/events` shows both a query surface and an injection command; `internal/engine/events/doc.go` notes explicitly that code.json's inbound fields are null pending registry maintenance (`grep -n "code.json\|inbound contract" internal/engine/events/doc.go`) — this is flagged as a registry-hygiene item for Ben, not a BUG-058 call-edge instance, since nothing currently depends on the inbound contract being populated.
- **AC-2 (§10 road closure — via `engine.logistics.md` AC-4's real junction-slot mechanism, the primary obligation to that file).** A road-closure event reduces a specific junction's real slot capacity (`engine.logistics`'s `JunctionSlotsAvailable`/`SetJunctionCapacity` surface, per `engine.logistics.md` AC-4) to zero or a documented reduced value for its duration — this module does not implement its own "closed road" stock/queue side-channel. Check: `grep -rn "logistics\.(JunctionSlots|SetJunctionCapacity)" internal/engine/events/*.go` (excluding `_test.go`) shows the closure event calling logistics's real capacity-mutation surface; a passing test injects a closure on a junction with pending movements and asserts the resulting behaviour matches `engine.logistics.md` AC-4's own saturation scenario — queued movements appear in the next day's queue, none silently vanish or silently complete anyway (`grep -rn "func Test.*[Rr]oadClosure" internal/engine/events/*_test.go`). **False-pass risk, per the brief's "stresses logistics, not spectacle" framing:** an implementation that logs "road closed" as a ticker event and a cosmetic map overlay without ever touching `engine.logistics`'s slot ledger would satisfy "road closure exists" while producing zero actual JIT stress — the check requires the real queue-saturation behaviour to reproduce, proving the pressure reached logistics's real machinery, not a display-only parallel state.
- **AC-3 (§10/§W storm surge on shore cells — via `engine.world` for cell state, feeding `engine.logistics.md` AC-9's real shortfall surface for the downstream consequence).** A storm-surge event mutates shore-cell state through `engine.world`'s registered command surface (not a disaster-owned duplicate cell-state field); where a surge-affected cell hosts a depot/stock `engine.logistics` draws from, the resulting disruption surfaces as a real shortfall through `engine.logistics.md` AC-9's shortfall mechanism (a nonzero, typed, correctly-magnituded quantity) — this module does not compute its own "surge damage" number for the affected commodity. Check: `grep -rn "world\.(SetCellState|Flood)" internal/engine/events/*.go` (excluding `_test.go`) shows the surge event calling `engine.world`'s command surface; a passing test surges a cell hosting a depot with pending stock draws and asserts a shortfall appears through `LogisticsAPI`'s own AC-9 surface with nonzero magnitude, not a locally-invented figure (`grep -rn "func Test.*[Ss]tormSurge" internal/engine/events/*_test.go`).
- **AC-4 (§W aquifer drought — a sustained pressure exercising `engine.logistics.md` AC-3's lean/fat buffer divergence, not an instantaneous shock).** Aquifer drought reduces water-source replenishment capacity over a sustained window (distinct from AC-2/AC-3's discrete shocks), and the test proves this genuinely exercises `engine.logistics`'s real buffer-policy machinery: a "fat" buffer policy on water measurably outlasts a "lean" one under an identical drought trace, reusing `engine.logistics.md` AC-3's own divergence check rather than a disaster-local resilience calculation. Check: a passing test runs an identical drought trace against a lean-buffered and a fat-buffered water stock (both real `engine.logistics` stock/buffer instances) and asserts the fat-buffered stock's realised stockout rate is lower (`grep -rn "func Test.*[Aa]quiferDrought" internal/engine/events/*_test.go`). **False-pass risk:** a drought implementation that reduces a disaster-owned "water availability" number consulted only by this package's own satisfaction calculation would satisfy "drought exists" while never touching `engine.logistics`'s real buffer/stockout machinery — the check requires the lean/fat divergence to reproduce through logistics's real stock type.

### Functional — never random-spam, and no bespoke resolution path

- **AC-5 (§10 never random-spam — a rising, queryable precursor before every event; mirrors `engine.crime.md` AC-11's identical requirement for the MI5 dial).** Every event category (closure, surge, drought) has a documented, queryable rising-pressure precursor state observable for at least a minimum lead window before the event can fire; no event fires directly from a quiescent/baseline precursor state regardless of elapsed ticks. Check: a passing test asserts, for each of the three categories, that the precursor indicator is nonzero and rising for at least N ticks before any test-triggered event of that category fires in the same run, and that forcing the precursor to remain at baseline suppresses firing indefinitely (`grep -rn "func Test.*[Pp]recursor\|func Test.*[Nn]oRandomSpam" internal/engine/events/*_test.go`). **False-pass risk, identical to the one `engine.crime.md` AC-11 names:** a cosmetic "rising tension" readout uncoupled from the actual trigger draw underneath would pass a bare "precursor exists" check while remaining random-spam under the hood — the check requires the precursor window to be observed in the same run that produces the event, and requires forcing baseline to actually suppress firing.
- **AC-6 (§10 "resolved through the same logistics/dispatch machinery" — the negative check: no bespoke resolution path, the mechanism that keeps this feature honest as pressure rather than spectacle).** No event category maintains its own independent resolution/recovery state machine parallel to `engine.logistics`'s or `engine.world`'s existing state lifecycle — recovery is simply the affected module's own state returning to its pre-event value through that module's normal tick processing, never a disaster-owned countdown that separately "heals" a duplicated state. Check: `grep -rln "type.*Recovery\|type.*Resolution" internal/engine/events/*.go` (excluding `_test.go`) finds no disaster-owned recovery-state type distinct from the affected module's own state; a passing test removes an event's pressure input (returns the precursor/capacity-reduction to baseline) and asserts the affected `engine.logistics`/`engine.world` state recovers via that module's own normal processing with no separate "disaster resolved" flag required to unblock it (`grep -rn "func Test.*[Nn]oBespokeResolution\|func Test.*[Rr]ecoveryViaHost" internal/engine/events/*_test.go`). **This is the check that catches "spectacle" specifically:** a build with its own disaster-resolution timeline (a countdown independent of the host module's real state) would satisfy "event ends eventually" while never actually exercising `engine.logistics`'s/`engine.world`'s real recovery path — indistinguishable from a scripted cutscene bolted onto the simulation rather than pressure applied within it.
- **AC-7 (§10 registrable service-adjacent category — BLOCKED pending BUG-058, this file's obligation to `engine.services.md`'s own out-of-scope note).** Disasters-lite is registrable as one of `engine.services`' §10 service categories — `engine.services.md`'s own out-of-scope note explicitly assigns this feature the role: "disasters-lite is a registrable service-adjacent category the event pressure can act on" — **blocked pending BUG-058:** code.json registers no `feat.disasters`↔`engine.services` edge in either direction, compounding AC-1's null inbound contract, so there is no legal path today for `engine.services` to expose disasters-lite as a fundable/gated category at all. Until unblocked, this AC requires only that event severity/frequency accept a documented, funding-shaped input (e.g. a funding-multiplier parameter on the precursor calculation) without the real cross-module registration. Check: `internal/engine/events/doc.go` states the block explicitly citing BUG-058; `grep -n "FundingMultiplier\|fundingLevel" internal/engine/events/*.go` shows the precursor calculation accepts a funding-shaped input even though nothing calls it yet.

### Error handling

- **AC-8 (GR#7).** Injecting an event against an unregistered junction/cell ID returns a registry-sourced error (new `MET-E`-range code) rather than a silently-created placeholder event. Check: `grep -n "MET-" internal/engine/events/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredTarget" internal/engine/events/*_test.go`).
- **AC-9.** Injecting a second event of the same category on the same target while one is already active is rejected with a typed error (or a documented, deliberate stacking rule), never silently overwriting the first event's remaining duration/severity. Check: passing test coverage (`grep -rn "func Test.*[Dd]uplicateEvent\|func Test.*[Ss]tacking" internal/engine/events/*_test.go`).

### Determinism, safety & scale

- **AC-10 (GR#21).** Event timing and severity draws (including precursor-to-fire transitions) use the counter-based hash stream `hash(worldSeed, id, month, purposeTag)` — no shared/global RNG. Check: `grep -n "rand.New\|math/rand\"" internal/engine/events/*.go` (excluding `_test.go`) finds no shared/global RNG source.
- **AC-11 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/events/*.go` (excluding `_test.go`) returns no matches.
- **AC-12.** `go test ./internal/engine/events/... -race -count=1` passes with no data race.

### Documentation

Check: `grep -n "feat.disasters" internal/engine/events/doc.go` and `grep -n "§10\|section 10" internal/engine/events/doc.go` and `grep -n "BUG-058" internal/engine/events/doc.go` all match.

## Out of scope

- `engine.logistics`'s own stock/buffer/junction-slot/shortfall mechanics — this item only drives them (AC-2/AC-3/AC-4); it does not reimplement or extend `engine.logistics.md`'s own ACs.
- `engine.world`'s own cell-state mechanics — this item only mutates shore-cell state through the registered command surface (AC-3).
- `engine.services`' own service-registration framework — blocked pending BUG-058 (AC-7); this item does not build a parallel registration path.
- Ticker/news presentation of a disaster event — `engine.news`'s job; no `feat.disasters`↔`engine.news` edge is registered (consistent with BA-S8a's broader `engine.news` edge-coverage finding), so this item emits documented event *values* a future consumer can subscribe to, not a direct call outward.
- Specific precursor lead-window lengths and event frequency/severity distributions — balance data pending M2 tuning (see Escalations, ASM-330).
