## User stories

- **US-1.** As the engine, I need every death released from FEAT-087's smoothed death queue to produce exactly one body that enters the death-services pipeline, so "a dead citizen is exactly one body" is a structural identity at the hand-off, not a best-effort assumption.
- **US-2.** As the player, I need a graveyard to consume plots and return them to use only after a documented reuse horizon, so burial is a finite land resource with a recovery curve — land pressure that cremation or woodland can relieve — not an infinite sink.
- **US-3.** As the player, I need cremation to dispose of a body without consuming a plot, at a real per-body cost and a bounded daily throughput, so I can trade money for land pressure, and the trade is never strictly free.
- **US-4.** As the engine, I need a hearse to carry exactly one body per trip, so funeral throughput caps the rate at which bodies are cleared and a death surge (FEAT-087's non-smoothed event) becomes a *backlog that drains*, not an instant wave that vanishes in one tick.
- **US-5.** As the player during a weather-driven major death event, I need emergency dispensation to let bodies move in vans/trucks (more than one per trip) and death services to run 24x7, so the backlog can be cleared faster than the normal hearse cap — at a documented cost/trade-off — and to snap back to normal when the event ends.
- **US-6.** As `engine.invariant` (and as the engine's own conservation identity), I need the body stock conserved — every body handled exactly once, by exactly one terminal method, never lost, never double-counted, never double-disposed.

## Scope

The intake surface that turns FEAT-087's released deaths into bodies; graveyard plot allocation with a data-sourced reuse horizon; cremation as the space-free, costed, throughput-bounded alternative; hearse transport with the one-body-per-trip throughput cap and its backlog consequence; the emergency-dispensation mode (van/truck multi-body transport + 24x7 services) gated on FEAT-087's weather event; and the body-conservation identity (one body, handled exactly once) as a new conserved stock.

## Acceptance criteria

### Functional — intake: death queue → body

- **AC-1 (GR#20; code.json inbound contract; US-1).** A `DeathServicesAPI` (or equivalent) exists exposing a body-intake path driven by FEAT-087's death queue, plus disposal-status queries and disposal/triage commands — mutation only via commands, never a directly-writable exported field on a body/plot/hearse record reached from another package. Check: `go doc ./internal/engine/deathservices DeathServicesAPI` shows an intake entry point keyed off the death queue's release event, a status-query surface, and a command-based disposal/triage surface; `grep -rln "deathservices\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/deathservices` itself and `_test.go`) finds no direct exported-field writes bypassing the interface. **Registration resolved:** `engine.deathservices` is registered in code.json (inbound `DeathServicesAPI`, outbound to `feat.deathwave` — the intake's release-event source), so the GR#20 inbound-contract half is fully buildable. The intake must drain `DeathQueue.Realise(...) []RealisedDeath` (the r2-stable surface) — one released `RealisedDeath` per body, keyed by `CitizenID`.
- **AC-2 (US-1; the intake identity — one death, one body).** Every death released by FEAT-087's queue produces exactly one body record, and no body is produced without a corresponding released death — the intake is a bijection over `(releaseEvent → bodyId)`, never a sampler that might drop or duplicate a death. Check: a passing test feeds a fixed released-death list through intake and asserts the body set is exactly the same cardinality and IDs as the input, with no dropped and no duplicated body (`grep -rn "func Test.*[Ii]ntake\|func Test.*[Oo]neBody" internal/engine/deathservices/*_test.go`). **Lazy implementation this rejects:** an intake that "processes deaths until the backlog cap" and silently discards the excess would satisfy "bodies are produced" on a shallow read while breaking the invariant this whole feature exists to guarantee — the check requires exact cardinality/ID equality, not "some bodies came out".

### Functional — burial (plot allocation + reuse horizon)

- **AC-3 (§Part IV cemetery, line 1075; US-2).** A cemetery is a catalogue structure (registered via `engine.build`'s `buildings.json`-driven catalogue, per `engine.build.md` AC-2/AC-8) with a finite plot capacity, and each burial consumes exactly one plot. The spec-stated capacity (2k plots) is transcribed into `data/deathservices.json` as the seed value — never hardcoded in Go (GR#15). Check: `grep -n "2[ _]000\|2000\|plots" data/deathservices.json` (or the cemetery entry's plot-capacity field) shows the seed capacity sourced from the data file; `go doc ./internal/engine/deathservices Cemetery` (or equivalent) shows plot-capacity and plot-occupancy accessors; a passing test buries one body and asserts occupied-plots advances by exactly one and available-plots decreases by exactly one (`grep -rn "func Test.*[Bb]urial.*[Pp]lot\|func Test.*[Pp]lotConsum" internal/engine/deathservices/*_test.go`).
- **AC-4 (§Part IV cemetery "fills permanently"; US-2; GR#15 reuse-horizon placeholder).** A consumed plot is not allocatable again until a documented reuse horizon has elapsed since its burial; the horizon is a single data-sourced value (`data/deathservices.json`, disclosure comment naming it a placeholder pending Aaron's balance pass), never a hardcoded constant. The AC checks the *mechanism*, not a specific length: plot occupancy is a monotone "occupied-until = burialTick + horizon" function, and a plot is reusable only at/after that tick. Check: a passing test buries a body at tick T, asserts the plot is rejected for reuse at any tick < T+horizon (as loaded from the fixture), and becomes allocatable at T+horizon; a second test loads a *different* horizon from a mutated fixture and asserts the reuse boundary moves with the data, proving the value is data-driven rather than compiled in (`grep -rn "func Test.*[Rr]euseHorizon\|func Test.*[Pp]lot.*[Rr]euse" internal/engine/deathservices/*_test.go`). **Do not invent the horizon length** — the fixture carries a placeholder; the test asserts the boundary follows the fixture, not a literal month count.
- **AC-5 (§Part IV cemetery "fills permanently — land pressure"; US-2).** When every plot in a cemetery is occupied and none has reached its reuse horizon, a burial against that cemetery is rejected (or explicitly routed to cremation/dispensation by a documented triage rule), never silently buried into a nonexistent plot. Check: a passing test fills a cemetery to capacity, attempts one more burial, and asserts (a) the burial does not advance occupancy and (b) either a typed "no-plot" rejection or a documented triage route to cremation occurred (`grep -rn "func Test.*[Ff]ullCemetery\|func Test.*[Ll]andPressure" internal/engine/deathservices/*_test.go`). **Lazy implementation this rejects:** a plot allocator that wraps around or extends capacity on overflow would satisfy "burials keep working" on a shallow read while erasing the land-pressure mechanic the spec's "fills permanently — land pressure" line exists to create.

### Functional — cremation (space-free path + cost)

- **AC-6 (§Part IV crematorium, line 1076; line 543 "£/service"; US-3).** Cremation disposes of a body without consuming any plot (the space-free alternative), at a per-body cost sourced from `data/deathservices.json` (the spec gives only "£/service" — no figure — so the value is a disclosed placeholder), and is bounded by the crematorium's daily throughput (spec-stated 12/d, transcribed into the data file as the seed). Check: `go doc ./internal/engine/deathservices Crematorium` (or equivalent) shows a throughput-capacity accessor and a per-body-cost accessor; a passing test cremates N bodies and asserts (a) zero plots were consumed across the whole run, (b) the recorded cremation cost is > 0 and is charged through the registered funding path (via `engine.services`' funding/quality surface or the documented cost ledger, not a local invented number), and (c) cremating more than the 12/d seed capacity in one day queues the excess rather than silently exceeding it (`grep -rn "func Test.*[Cc]remat\|func Test.*[Ss]paceFree" internal/engine/deathservices/*_test.go`). **Directional-only:** the cost magnitude is a placeholder; the AC checks "cost exists and is charged", never a specific £ figure.

### Functional — hearse throughput (one body per trip)

- **AC-7 (US-4; the throughput cap — a surge becomes a backlog).** A hearse carries exactly one body per trip, and total disposal throughput is therefore bounded by `(hearse fleet size) × (trips per unit time)` — so a death surge released by FEAT-087's non-smoothed event cannot be cleared faster than that cap and instead accumulates as a queryable unhandled-body backlog. Check: `go doc ./internal/engine/deathservices Hearse` (or equivalent) shows a per-trip body-capacity field equal to 1 and a fleet-size accessor; a passing test releases N deaths where N exceeds the hearse throughput in one tick and asserts (a) the unhandled-body backlog grows by exactly `N − cleared`, and (b) no hearse trip in the run ever carries more than one body (`grep -rn "func Test.*[Hh]earse\|func Test.*[Oo]nePerTrip\|func Test.*[Tt]hroughputCap" internal/engine/deathservices/*_test.go`). **Lazy implementation this rejects:** a hearse whose "capacity" field reads 1 but which the scheduler loops over to clear the whole backlog in one tick would satisfy "one at a time" on a field read while destroying the queue-drains-over-time behaviour the design's "funeral throughput gates the death rate" exists to create — the check requires the backlog to persist across ticks at the cap.
- **AC-8 (GR#20 outbound contract; hearse routing owner — RESOLVED to `engine.logistics`).** Hearse movement is expressed through the **registered** `engine.logistics` movement owner's existing machinery (the outbound `engine.deathservices → engine.logistics` edge registered in code.json; hearses-as-scheduled-rounds per the `engine.refuse` precedent, NOT emergency dispatch) rather than a bespoke hearse-only pathfinder, mirroring `engine.refuse.md` AC-4's "same underlying type/method set, not merely a similarly-named one" precedent. Check: `grep -rn "logistics\." internal/engine/deathservices/*.go` (excluding `_test.go`) shows a live call into `engine.logistics`' exported movement/assignment surface, not a locally-duplicated `HearseTrip` type with independent routing logic; a passing test reproduces the owner's own queueing/congestion behaviour on a hearse trip (e.g. a saturated junction delays the hearse exactly as it would any other logistics movement) (`grep -rn "func Test.*[Hh]earse.*[Rr]oute\|func Test.*[Hh]earse.*[Dd]elay" internal/engine/deathservices/*_test.go`). **False-pass risk:** a `HearseTrip` type that merely *looks* like the owner's movement type but is scheduled by independent code would pass a naming grep while never contending for the owner's tracked slots — the check requires reproducing the owner's own queueing behaviour to prove genuine reuse.

### Functional — emergency dispensation (weather-driven major death event)

- **AC-9 (US-5; the trigger is FEAT-087's event, not a second detector).** A dispensation state activates exactly when FEAT-087's weather-driven major death event is active, reading the *same* adverse-weather signal FEAT-087 consumes from `engine.season` (drought/winter) — death services must NOT re-implement weather-event detection (GR#3). Check: `grep -rn "deathwave\.\|feat.deathwave\|DeathQueue\|WeatherEvent" internal/engine/deathservices/*.go` (excluding `_test.go`) shows the dispensation gate reads FEAT-087's event/queue state (or the shared `engine.season` signal through the same registered edge), not a locally-computed weather severity; a passing test activates the weather event and asserts dispensation becomes active in the same tick, then deactivates it and asserts dispensation returns to normal (`grep -rn "func Test.*[Dd]ispensation.*[Tt]rigger\|func Test.*[Dd]ispensation.*[Gg]ate" internal/engine/deathservices/*_test.go`).
- **AC-10 (US-5; vans/trucks + 24x7 lift the cap).** While dispensation is active, bodies may be transported in non-hearse vehicles (vans/trucks) carrying **more than one body per trip**, and death services run 24x7 (no normal-hours idle window), so disposal throughput measurably exceeds the normal one-body-per-trip hearse cap. The multi-body count and the throughput multiple are data-sourced placeholders (`data/deathservices.json`), not hardcoded. Check: `go doc ./internal/engine/deathservices DispensationMode` (or equivalent) exists; a passing test with dispensation active asserts (a) a single trip is permitted to carry more than one body (contra AC-7's normal-mode cap), and (b) total disposal throughput over a fixed window exceeds the normal hearse-only ceiling by more than would be possible under normal mode (`grep -rn "func Test.*[Dd]ispensation.*[Tt]hroughput\|func Test.*[Vv]an.*[Mm]ulti" internal/engine/deathservices/*_test.go`). **Directional-only:** the test asserts the *lift exists and is bounded by data*, not a specific van count or multiple.
- **AC-11 (US-5; dispensation is temporary and reverts).** When FEAT-087's weather event ends, dispensation deactivates: multi-body van/truck transport is no longer permitted, 24x7 operation ceases, and the normal one-body-per-trip hearse cap resumes. Check: a passing test drives dispensation on, clears some bodies via a multi-body trip, then ends the event and asserts (a) a subsequent multi-body trip is rejected with a typed error, and (b) the one-body cap is re-enforced (`grep -rn "func Test.*[Dd]ispensation.*[Rr]evert\|func Test.*[Dd]ispensation.*[Ee]nd" internal/engine/deathservices/*_test.go`). **Lazy implementation this rejects:** a dispensation flag that is set on the event and never cleared (or a van/truck path that remains permitted after the event) would satisfy "dispensation lifts the cap" on a shallow read while leaving the city in a permanent cheat-mode throughput state — the check requires the reversion to be asserted, not merely the activation.

### Functional — conservation invariant (one body, handled exactly once)

- **AC-12 (US-6; body conservation — the strongest available check).** For every accounting period (tick or month, documented which), the following identity holds exactly: `BodiesReleased == BodiesAwaitingHandling + BodiesEnRoute + BodiesBuried(occupying plots) + BodiesCremated + BodiesHandledByDispensation`. Each right-hand term is independently sourced — released from FEAT-087's queue ledger, awaiting from the intake backlog, en-route from the hearse/vehicle assignment ledger, buried from plot occupancy, cremated from the crematorium ledger, dispensation from its own ledger — and the identity is *checked*, never constructed to balance by definition (no term inferred as a remainder). Check: a passing test runs a synthetic surge, independently sums all right-hand terms from their own accessors each period, and asserts the sum equals the independently-tracked `BodiesReleased` exactly (integer bodies) (`grep -rn "func Test.*[Bb]odyConserv\|func Test.*[Bb]ody.*[Ii]dentity" internal/engine/deathservices/*_test.go`). **Lazy implementation this rejects:** computing any term (e.g. `BodiesAwaitingHandling`) as `BodiesReleased − (the other terms)` would make the identity tautologically true and hide a body being dropped or double-counted — exactly analogous to `engine.refuse.md` AC-11's independence requirement.
- **AC-13 (US-6; handled exactly once — terminal exclusivity).** Burial, cremation, and dispensation-handling are mutually exclusive terminal states: a body is disposed of by exactly one method, exactly once, and a handled body is removed from the awaiting/en-route sets and never re-assigned, re-counted, or re-disposed. Check: a passing test disposes a body by burial, then asserts (a) it no longer appears in awaiting or en-route, and (b) a second disposal attempt of that same body is rejected with a typed error; a second test disposes one body by cremation and asserts it never appears in the buried-plot occupancy set (the two methods can never both apply to one body) (`grep -rn "func Test.*[Ee]xactlyOnce\|func Test.*[Dd]oubleDispos\|func Test.*[Tt]erminal" internal/engine/deathservices/*_test.go`).

Check: passing test coverage (`grep -rn "func Test.*[Rr]eject\|func Test.*[Ii]nvalid.*[Dd]ispos" internal/engine/deathservices/*_test.go`).

Check: `grep -n "sort\." internal/engine/deathservices/*.go` shows deterministic ordering on any map feeding assignment; a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/deathservices/*_test.go`).
