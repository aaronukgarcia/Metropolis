## User stories

- **US-1.** As the player choosing to sell spare capacity, I need each service's surplus book (capacity − internal demand) to be independently queryable per service line, so I can see exactly how much slack I actually have before I commit it (§36's opening formula).
- **US-2.** As a signed contract, I need to be a real commitment with a term, £/unit rate and cancellation penalty — not a toggle — so selling slack is genuinely a short position on my own growth, matching §36's closing line verbatim.
- **US-3.** As `engine.projections` (F7, a registered consumer of this item's outbound calls), I need contracted-vs-internal-demand curves registered so the player can see them cross years out — the sprint's own exit-gate wording — before the crossing actually happens in-tick, not only after.
- **US-4.** As the player when a crossing occurs, I need a real choice between paying the cancellation penalty and cutting the service to my own citizens, with both paths having distinct, measurable consequences, so "penalty vs service cut" is a decision, not a foregone conclusion.
- **US-5.** As `engine.finance` (a registered consumer of this item, per `engine.finance.md`'s own consumer list), I need contract revenue and cancellation penalties posted as real ledger transactions tagged for trade/export accounting, so a later balance-of-trade aggregate (F2/F5, not this item's job) can sum them without this item inventing a second money total (GR#3).

## Scope

The per-service surplus book (capacity − internal demand) for the ten service lines this item can legally reach today (all of §36's table except surplus power — see Out of scope/Escalations), contract issuance/cancellation as commands with term/rate/penalty, contract-curve registration with `ProjectionsAPI` so F7 can render the crossing, the penalty-vs-service-cut choice at crossing time, and ledger posting of contract revenue/penalties through `FinanceAPI` tagged for trade accounting. Not in scope: the surplus-power line (blocked, no `engine.consumption` edge), the toxic-waste facility's own accident-event table (that belongs to `engine.services`/a hazard module, this item only carries its contract), and the F2/F5 balance-of-trade aggregate view itself (UI's job, consuming this item's tagged ledger lines).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `CapExportAPI` exists matching code.json's registered pattern — per-service surplus books, contract curves registered with `ProjectionsAPI` — with capacity/demand sourced from `engine.services`' `ServicesAPI` (registered edge) for every applicable service line, never a concrete `services` struct field read directly. Check: `go doc ./internal/engine/capexport CapExportAPI` lists a per-service surplus-book accessor and a contract-issue/cancel command surface; `grep -rn "services\." internal/engine/capexport/*.go` (excluding `_test.go`) shows calls through `ServicesAPI`'s exported methods only; `grep -rln "services\.\(capacityState\|Registry\)\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/services` and `_test.go`) finds no direct exported-field write bypassing the interface. False-pass risk: a grep for `CapExportAPI`'s existence alone would pass a build that reaches into `engine.services` internals directly — the check targets the bypass, not the name.
- **AC-2 (§36 the crossing — made reachable, not just assertable).** A passing scenario test constructs a service line (e.g. hospital beds or prison places) where internal demand is deliberately driven to grow across several simulated months/years while a fixed-capacity contract is held constant, and asserts the contracted-vs-internal-demand curves registered with `ProjectionsAPI` **actually cross within the test's observation window** — i.e. a tick exists where internal demand's queried value exceeds (capacity − contracted commitment), which did not hold at the test's start. The test must also assert the reverse is constructible: a scenario where demand stays flat/declining never crosses. Check: `grep -rn "func Test.*[Cc]apacityCross\|func Test.*[Cc]ontractCross" internal/engine/capexport/*_test.go` finds both a crossing-occurs case and a no-crossing-control case in the same or a paired test. A lazy-but-plausible violation: a model where internal demand is capped below any contracted figure by construction (e.g. demand is a fixed fraction of capacity that can never exceed the uncommitted remainder) makes the crossing structurally unreachable — this passes AC-1's "contract curves exist" check trivially while the crossing itself can never fire. This check rejects that model because it demands a tick where the crossing condition is actually true, read back from the API, not merely that both curves are queryable. (ASM-309: growth rate used to force the crossing is a placeholder figure, not spec-fixed.)
- **AC-3 (§36 the choice — penalty vs service cut, with F7 visibility as a distinct obligation).** At the crossing tick from AC-2, the player-facing command surface offers exactly two real paths — `PayCancellationPenalty` (posts the penalty through `FinanceAPI`, contract is reduced/cancelled) and `CutInternalService` (the service's citizen coverage drops by the shortfall, read back through this item's own `CitizenCoverage` accessor — capacity minus committed — because `ServicesAPI` has no capacity setter for a cut to flow through; the physical capacity still exists, the export contract commits it away) — and a passing test exercises both paths from the same crossing state and asserts each produces the OTHER's absence (paying the penalty leaves citizen coverage unchanged; cutting service leaves the contract intact and no penalty posted). Check: `grep -rn "func Test.*[Pp]enaltyVs[Ss]ervice\|func Test.*[Cc]rossing[Cc]hoice" internal/engine/capexport/*_test.go`. **F7 visibility is `ui.screen.proj`'s (another BA's file) obligation, not this item's to build** — this item's obligation, discharged by AC-2, is that the crossing is a real, queryable event registered with `ProjectionsAPI` before it happens, giving F7 something true to render; if `ui.screen.proj` doesn't yet subscribe to this item's registered curve, that is a gap in that file, not this one, and is flagged in Escalations for Bill to cross-check.
- **AC-4 (§36 contract commitments — term/rate/penalty as real fields, not a toggle).** Every contract carries a term (duration), a per-unit rate, and a documented cancellation-penalty function (not a flat toggle-off), and issuing a contract is a `protocol.Command` producing a durable, queryable record — not a boolean flag on the service. Check: `go doc ./internal/engine/capexport Contract` (or equivalent) shows `Term`, `Rate`, `CancellationPenalty` fields/accessors; a passing test issues a contract and asserts all three are independently retrievable and that cancelling before term-end computes a nonzero penalty while cancelling at/after term-end does not (`grep -rn "func Test.*[Cc]ontractTerm\|func Test.*[Cc]ancellationPenalty" internal/engine/capexport/*_test.go`). False-pass risk: a contract represented as a single boolean "exporting: true/false" would satisfy a naive existence check while having no term/rate/penalty semantics at all — the check requires all three fields to vary independently across test fixtures.
- **AC-5 (§36 catalogue coverage; GR#15 data-driven).** The exportable-service catalogue contains the ten §36 table rows this item can legally reach today (refuse collection & disposal, incineration, toxic/hazardous waste processing, sewage & water treatment, hospital beds, university places, crematorium/cemetery, prison places, port transshipment, fire/ambulance mutual aid), each loaded from data (`data/capexport.json` or equivalent) with its own unit (£/t, £/m³, £/bed-day, £/student-yr, £/service, £/prisoner-yr, £/t, standby retainer) — not hardcoded Go literals, and not silently including surplus power (out of scope, AC blocked — see Escalations). Check: `go doc ./internal/engine/capexport ExportableService` (or equivalent enum) lists exactly these ten cases; `grep -nE "\"£|GBP" internal/engine/capexport/*.go` (excluding `_test.go`) finds no hardcoded rate; a passing test changes a fixture unit/rate and asserts the catalogue reflects it (`grep -rn "func Test.*[Cc]atalogue\|func Test.*[Dd]ataDriven" internal/engine/capexport/*_test.go`).
- **AC-6 (§36/§43 prison overcrowding cross-reference — documented, not silently modelled).** Because `engine.prison`'s own spec text ("Overcrowding... incl. §36 sold places... degrades every regime effect") depends on reading capexport's sold-prison-places figure, and no `engine.prison` consumer edge is registered for this item today, `CapExportAPI` exposes the sold-places-per-service figure as a public, independently queryable accessor (satisfying AC-1's per-service surplus book requirement) so that edge can be wired the moment it's registered, without this item reaching into `engine.prison` itself. Check: `go doc ./internal/engine/capexport` shows a per-service committed-capacity accessor callable for the prison-places line specifically; `grep -rln "\"Metropolis/internal/engine/prison\"" internal/engine/capexport/*.go` (excluding `_test.go`) finds no import (this item never reaches into prison to fake the missing edge — GR#20).
- **AC-7 (§36/GR#3 trade-ledger tagging — feeds a future balance-of-trade aggregate without building a second one).** Every contract-revenue posting and every cancellation-penalty posting goes through `FinanceAPI` (registered edge) tagged with a distinct, documented trade/export account category (not folded into generic service opex/income), so a future consumer (F2/F5, not this item) can sum "money entering via exports" per line 680 of the master spec without re-deriving it. A passing test posts one revenue transaction and one penalty transaction and asserts both are retrievable via `FinanceAPI`'s `Lines`/drill-through accessor filtered by the trade-category tag, and that the two transactions have opposite net effect on the city's balance (revenue credits the city, penalty debits it) — proving this item's own contribution to a future flip is genuinely bidirectional, not export-revenue-only. Check: `grep -rn "func Test.*[Tt]radeLedger\|func Test.*[Ee]xportRevenue.*[Pp]enalty" internal/engine/capexport/*_test.go`. A lazy-but-plausible violation: posting contract revenue through `FinanceAPI` but modelling cancellation penalties as an internal-only counter never posted to the ledger — this check rejects it because it demands both transaction types be retrievable through the same tagged drill-through query, not just that revenue exists.

### Error handling

- **AC-8 (GR#7).** Issuing a contract for more capacity than the service's current surplus book shows available returns a registry-sourced error (new `MET-E`-range code), never a contract that silently oversells and only fails later at the crossing. Check: `grep -n "MET-" internal/engine/capexport/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Oo]versell\|func Test.*[Ii]nsufficientSurplus" internal/engine/capexport/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no contract record was created, not merely that a matching-named test function exists.
- **AC-9 (GR#7).** Cancelling a nonexistent/already-cancelled contract, or a malformed catalogue entry (missing rate/term/unit) at load time, produces a registry-sourced error distinct from AC-8's code, never a silent no-op or a zero-valued contract. Check: `grep -n "MET-" internal/engine/capexport/*.go` finds a second, distinct code; passing test coverage (`grep -rn "func Test.*[Ii]nvalidContract\|func Test.*[Mm]alformedCatalogue" internal/engine/capexport/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code is distinct from AC-8's AND that the contract/catalogue state is unchanged, not merely that a matching-named test function exists.

## Escalations

- **For Ben — the crossing, made reachable-and-checkable (the headline deliverable).** AC-2 is the load-bearing check: it doesn't just assert a crossing-detection method exists, it forces a scenario where internal demand structurally must be able to exceed committed capacity, then reads the crossing back from the API, and pairs it with a no-crossing control so a model where demand is permanently capped below capacity (making the crossing vacuously unfailable) is rejected. AC-3 then requires the resulting choice (penalty vs service cut) to be two real, mutually-exclusive command paths with distinct measured effects, not a single "acknowledge" button. F7 visibility itself is explicitly `ui.screen.proj`'s file, not mine — I've stated that boundary in AC-3 rather than silently assuming the other BA's file covers it; recommend Bill/Ben confirm `ui.screen.proj` actually subscribes to this item's `ProjectionsAPI`-registered curve.
- **For Ben — the balance-of-trade flip, this item's contribution.** No aggregator module owns "balance of trade" as a whole-city figure (checked code.json; only `ui.screen.trade`'s TRD-5 owns a narrower §33 freight-tonnage extension, and `engine.finance.md`'s own Out of scope explicitly punts "firm-level export/import balance-of-trade accounting" to "a later module's addition" — i.e. modules like this one). This item's job is therefore not to compute the citywide flip itself but to guarantee its own contribution is genuinely bidirectional: AC-7 requires contract revenue (inflow) and cancellation penalties (outflow) to both be real, tagged, `FinanceAPI`-posted transactions retrievable through the same drill-through query — a model that only ever posts revenue (penalties tracked as an internal counter never reaching the ledger) passes a naive "exports work" check but fails AC-7 specifically, because AC-7 demands both directions be visible to whatever later module sums the trade tag.
