# Acceptance criteria — feat.policy (FEAT-091)

**BOW code:** FEAT-091 (P1, open) — "Policy system: global + zone policies, [auto]/[manual] values, change history"
**Spec refs:** §52 Policies v2 & Named Districts (`docs/METROPOLIS-MASTER-v2.1.md` lines 668-674: "every policy states its mechanism... and its scope — citywide, **district**, or road-level"; the policy library by category in `policies.json`) — the mechanics baseline this feature's configuration layer sits on; §34 Zoning (line 482: the 8-way zone classes — Dwelling · Shop · Office · Entertainment · Farming · Manufacturing · Heavy Industry · Mining) — the authoritative zone-override key; §13-F8 (line 255: "F8 Districts & Policies (tier 7+)") — the screen that renders this feature's state; §39 Taxation (line 563: "business rates by zone class × land value") — the zone-class × value precedent the tax side already built; `engine.build` (MOD-026, **done**) whose `ZoneType` enum (`internal/engine/build/zone.go`: `dwelling`, `shop`, `office`, `entertainment`, `farming`, `manufacturing`, `heavy_industry`, `mining`) is the authoritative zone vocabulary (ASM-780); `data.taxinstruments.md` (FEAT-056) AC-4/AC-5 — the already-shipped `zoneOverrides` schema (ASM-416, ASM-595) whose zone-key shape this file mirrors; code.json `engine.policies` entry (`PoliciesAPI` inbound, consumer `ui.screen.districts`; outbound `engine.projections`/`engine.tax`/`foundation.data`/`engine.finance`); `engine.policies.md` (MOD-064, this BA's sibling file — this file cross-references its library/mechanism/preview/scope surfaces and does **not** restate them); `feat.activitylog` (FEAT-093, the central "book" history — adjacent, out of scope, see Cross-check).
**Design (Aaron, 2026-08-15, BOW FEAT-091):** Player-set policies are GLOBAL, but zones (business district, industrial, recreational) can override with different policies (e.g. dwelling 'no trucks at weekends'). Every policy has detailed explanation + reader notes + [auto]/[manual] values, with a change history so the player sees every change.
**This file's role:** this feature is the **policy configuration-state layer**. MOD-064 (`engine.policies`) owns what a policy *does* — the coefficient-mutation mechanism, the F7 preview, the scope-resolution service (citywide/district/road), named districts, compounding and conflict warnings. FEAT-091 owns what the player has *set* a policy to — the global value, the per-zone override, whether each value is auto (engine-computed) or manual (player-set), the append-only change history the player reads, and the explanation + reader-notes content attached to each policy. It does **not** re-implement the mechanism: setting a value records configuration and history; the coefficient effect of that value is MOD-064's, applied by the engine. This feature resolves the zone-class scope gap ASM-417 already flagged (see Cross-check and Escalations).
**Date:** 2026-08-16
**Status:** draft-ahead — the feature has **no code.json registration yet**, and the `internal/engine/policies/` package it is assumed to share with MOD-064 does **not exist on disk** (MOD-064 is `open`/unbuilt; `data/policies.json` is a 36-byte `{"version":1,"entries":[]}` stub). Directional/structural checks only, per the balance-number regime below.
**Package under test:** `internal/engine/policies/` (shared with `engine.policies`/MOD-064, by ASM-783's assumption — pending Bill's module-vs-feature ruling; see Escalation ES-1).
**Balance-number regime (standing rule, same convention as `engine.finance.md` AC-21 / `feat.maintenance.md` / `data.taxinstruments.md` AC-9):** every numeric policy figure — valid value ranges, auto-value defaults, any per-zone multiplier — is a **placeholder** in the policy data file (`data/policies.json`, extended per ASM-784), each carrying a disclosure comment naming it pending Aaron's balance pass. No AC may be satisfied by a junior inventing a final value; every AC touching a value requires it to live in data and requires tests to check **direction/structure** (override differs from global; auto value tracks its documented input; a mode switch is recorded), never a specific figure.

## User stories

- **US-1.** As the player, I need a policy to have one GLOBAL setting that applies everywhere by default, so a single decision governs the whole city rather than forcing me to re-set it per area (design: "policies are GLOBAL").
- **US-2.** As the player, I need any zone class to override a policy with a different value — the dwelling 'no trucks at weekends' example — so one policy can mean one thing city-wide and something else inside a specific zone class, and the override never leaks into the global value or another zone (design: "zones can override").
- **US-3.** As the player, I need every policy value to be either [auto] — the game computes it from a documented, deterministic source — or [manual] — I set it and it stays where I left it — so I can either delegate a lever to the engine or pin it by hand (design: "[auto]/[manual] values"; §19.2 signals and §17 waste-routes "auto-optimised or hand-set" precedent).
- **US-4.** As the player, I need a change history that records every change to every policy — global or zone, auto or manual — with the old value, the new value, and when it happened, so I can see exactly how a policy arrived at its current state (design: "change history so the player sees every change").
- **US-5.** As the player browsing a policy, I need its detailed explanation (what it does, what it costs, its consequences) and its reader notes (context, caveats, design intent) surfaced from data, so a policy is explained rather than a bare toggle label (design: "detailed explanation + reader notes").
- **US-6.** As `ui.screen.districts` (FEAT-022), I need the global/zone setting, the auto/manual mode, the history, and the explanation content reachable through one registered engine contract, so the F8 screen renders configuration state without re-deriving it (GR#20).

## Scope

A policy configuration-state layer: a global setting per policy with optional per-ZoneType overrides; effective-value resolution (override else global); a per-setting [auto]/[manual] mode where auto is a deterministic, data-declared engine computation and manual is a persisted player value; an append-only, ordered change-history ledger; and explanation + reader-notes content loaded from data. Does **not** include: the coefficient-mutation mechanism, preview, scope resolution, named districts, compounding or conflict warnings (MOD-064/`engine.policies`); the F8 screen that renders this state (`ui.screen.districts`/FEAT-022); the central activity-log "book" (FEAT-093); or any final rate/value figure (Aaron's balance pass).

## Acceptance criteria

### Functional — global + zone override

- **AC-1 (GR#20; code.json inbound contract — the surface exists, registered, and is not reachable by direct UI import).** A `PolicySettingsAPI` (or equivalent, name per ASM-783) exists exposing at minimum: set/clear a global setting, set/clear a zone override, resolve the effective setting for a zone, set the auto/manual mode, query the change history, and query explanation/reader-notes. The surface lives on the shared `internal/engine/policies/` package and imports **no** `internal/ui/...` package — the F8 screen consumes it through `int.protocol`, never by direct import. Check: `go doc ./internal/engine/policies PolicySettingsAPI` (or the named surface) shows the setting/override/resolve/mode/history/content surfaces; `go list -deps ./internal/engine/policies/...` shows no `internal/ui/...` import; `grep -rn "func Test.*[Ss]ettings\|func Test.*[Oo]verride\|func Test.*[Hh]istory\|func Test.*[Ee]xplanation" internal/engine/policies/*_test.go` finds coverage. **False-pass risk:** a surface that exists but is only reachable by `ui.screen.districts` importing the package directly (rather than via `int.protocol`) would pass a "the functions exist" read while breaking the GR#20 UI/engine split every other module enforces — the check requires the no-UI-import property explicitly.

- **AC-2 (global + zone override — the headline property; a differential single-field test).** Each policy carries exactly one global setting; any of the eight §34 zone classes may additionally carry an override. The effective setting for a zone is the override when one exists, else the global — and setting a zone override mutates **exactly** that (policy, zone) cell, leaving the global value and every other zone's override byte-identical. Check: a passing test sets a global value, then a `dwelling` override, and asserts (a) resolving `dwelling` returns the override while resolving `shop` returns the global, and (b) a field-by-field diff of full settings state before/after the override shows only the `dwelling` cell changed (`grep -rn "func Test.*[Ss]ingleField\|func Test.*[Oo]verride.*[Ii]ndependent\|func Test.*[Gg]lobalVsZone" internal/engine/policies/*_test.go`). **Lazy implementation this rejects:** an override that is implemented as a global rewrite (setting `dwelling` also flips the global) would pass a "dwelling now returns the override" check while silently breaking every other zone — the full-state diff catches the undeclared mutation, exactly the ASM-257 single-field precedent `engine.policies.md` AC-3 already established.

- **AC-3 (zone override key = the §34 `ZoneType` enum, closed and data-derived; ASM-780).** The override key is `engine.build`'s §34 eight-way `ZoneType` (`dwelling`, `shop`, `office`, `entertainment`, `farming`, `manufacturing`, `heavy_industry`, `mining`), sourced from `engine.build`'s own catalogue — **not** a free string, and **not** the BOW description's illustrative naming ("business district / industrial / recreational"). An override for anything outside that closed enum is rejected. Check: `grep -n "ZoneType\|ZoneTypes\|ZoneTypeByID" internal/engine/policies/*.go` shows reuse of `engine.build`'s type (not a locally-redeclared string enum); a passing test sets an override keyed `dwelling` and asserts resolving `dwelling` differs from resolving `shop`, and a second test asserts an override keyed to a non-§34 string is rejected (`grep -rn "func Test.*[Zz]oneKey\|func Test.*[Zz]oneOverride.*[Ee]num" internal/engine/policies/*_test.go`). **False-pass risk:** a `map[string]T` keyed by free string would accept "dwelling" and "dwelling " as two different zones, or accept a typo silently — the closed-enum check is what makes "the dwelling override" a well-defined, single concept rather than a string-matching accident.

### Functional — [auto]/[manual] values

- **AC-4 ([auto]/[manual] per-setting; auto is deterministic engine-derived, manual is persisted; ASM-781).** Each setting (each global value and each zone override) carries a mode: **manual** = the value is exactly what the player set, persisted and stable across ticks until changed; **auto** = the value is computed by a documented, deterministic, per-policy engine function whose source is data-declared. Switching a setting to auto immediately reflects the computed value, and re-running the auto computation on identical engine state is byte-identical (GR#21). (This file reads "values" as *per-setting* mode — each global value and each override carries its own; if Aaron intended a single per-policy mode, this collapses trivially. Flagged inline rather than as a separate ASM.) Check: a passing test (a) sets a manual value and asserts the resolved value equals it exactly across two ticks, (b) switches the same setting to auto and asserts the resolved value equals the engine's computed value, and (c) mutates the input the auto source reads and asserts the auto value changes directionally (never a pinned figure) and deterministically (`grep -rn "func Test.*[Mm]ode\|func Test.*[Aa]utoVsManual\|func Test.*[Aa]uto.*[Dd]eterministic" internal/engine/policies/*_test.go`). **False-pass risk:** an "auto" mode that is really a fixed default constant baked in code (never re-derived from current engine state) would pass a "the mode field flips" grep while the design's delegation promise — the game manages the lever as conditions change — is unmet; the check requires the auto value to track its documented input, not merely to exist.

### Functional — change history

- **AC-5 (change history — append-only, ordered, every change recorded; "the player sees every change").** Every mutation — setting/clearing a global value, setting/clearing a zone override, switching auto/manual mode, repealing a policy — appends one entry to a queryable, append-only history ledger keyed by policy (and scoped where relevant), recording the old value, the new value, the mode, the source (manual/auto), and the simulation month. The ledger is ordered; a later entry never rewrites an earlier one. Check: a passing test performs three mutations on one policy, then queries the history and asserts exactly three entries in mutation order with correct old→new transitions; a second test asserts the history surface exposes no mutation/rewrite of an existing entry (append-only) (`grep -rn "func Test.*[Hh]istory.*[Oo]rder\|func Test.*[Aa]ppendOnly\|func Test.*[Cc]hangeHistory" internal/engine/policies/*_test.go`). **False-pass risk:** a history that recomputes "current value only" (no per-change record) would pass a "history is queryable" grep while the player can never see the *sequence* of changes the design promises — the check requires the ordered list of transitions, not just a present-state read.

- **AC-6 (explanation + reader notes — content from data, never hardcoded prose; ASM-784).** Every policy's detailed explanation and reader notes are loaded from the policy data file (`data/policies.json`, extended per-policy), keyed by policy, and surfaced through the query API. Check: a passing test queries a fixture policy's explanation/reader-notes and asserts the returned text matches the data-file entry; a second test edits the explanation text in the data fixture between two loads and asserts the queried text changes without a code change (`grep -rn "func Test.*[Ee]xplanation.*[Pp]rovenance\|func Test.*[Rr]eaderNotes\|func Test.*[Cc]ontent.*[Dd]ataDriven" internal/engine/policies/*_test.go`). **False-pass risk:** prose baked into `internal/engine/policies/*.go` as string literals would pass a "the field renders" grep while the design's "every policy has detailed explanation + reader notes" becomes code-shipped content that a balance/edit pass can't touch without a rebuild — the check requires the content to trace to data.

### Functional — single source of truth and the boundary to MOD-064

- **AC-7 (effective-value resolution is the single source of truth — GR#3).** The effective setting for a (policy, zone) pair is resolved by one pure function on the settings surface; consumers query it rather than re-deriving override-else-global themselves. The resolution is a pure function of (settings state, policy, zone) — same inputs, same output, no hidden state. Check: a passing test queries the same (policy, zone) twice with identical state and asserts byte-identical results, and asserts a fixture consumer that reads the resolved value (not raw global + raw override + its own `if override != nil` logic) gets the same answer (`grep -rn "func Test.*[Rr]esolve.*[Pp]ure\|func Test.*[Ee]ffective.*[Dd]eterministic" internal/engine/policies/*_test.go`). **Lazy implementation this rejects:** two modules each reimplementing "override if present else global" would drift the moment a third scope kind is added — the single resolution function is what keeps "what is this policy set to here" a one-word answer.

- **AC-8 (boundary — FEAT-091 records configuration, it does not mutate coefficients; that is MOD-064's).** Setting a policy value (global or override) records the configuration and its history and resolves the effective value; it does **not** itself mutate the coefficient(s) the policy targets. The coefficient effect of the resolved value is `engine.policies`' mechanism (`engine.policies.md` AC-2/AC-3), applied by the engine, not a policy-configuration-local mutation. Check: `grep -nE "coefficient|Coefficient" internal/engine/policies/*.go` on the settings surface finds **no** coefficient-mutation code (references to the concept are fine; a mutation is not); a passing test sets a value and asserts the settings/history state changed while no coefficient delta was applied by the settings surface itself (`grep -rn "func Test.*[Bb]oundary\|func Test.*[Nn]oMechanism" internal/engine/policies/*_test.go`). **False-pass risk:** a settings surface that also reaches into the mechanism and applies the coefficient delta would pass every configuration AC while silently duplicating MOD-064's job (a second source of truth for "what this policy does"), the exact GR#3 violation this AC exists to catch.

### Error handling

- **AC-9 (GR#7 — invalid operations).** Setting/clearing a global or override value for an unknown `PolicyID`, an override for a non-§34 zone key (AC-3), a manual value outside the policy's data-declared valid range, or an unknown mode, each returns a registry-sourced error (a new `MET-`-range code claimed at build time) naming the policy/scope/value — never a silent no-op, never a coerced-to-nearest-valid-value false success. Check: `grep -n "MET-" internal/engine/policies/*.go` finds registry-code references on the setting paths; passing test coverage (`grep -rn "func Test.*[Uu]nknownPolicy\|func Test.*[Uu]nknownZone\|func Test.*[Rr]ange" internal/engine/policies/*_test.go`) asserts the returned error's registry code matches **and** that no settings/history state was mutated on failure — not merely that a matching-named test function exists (GR#7 assertion, stated explicitly).

- **AC-10 (GR#7 — malformed data).** A malformed or schema-invalid policy data file (a missing explanation or reader-notes field, an auto-source referencing an unknown input, a valid-range whose lower bound exceeds its upper bound, an explanation/reader-notes field that is not a string) produces a registry-sourced error at load time identifying the offending policy/field — never a silent empty-string default that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/policies/*.go` finds a load-time registry code distinct from AC-9's; passing test coverage (`grep -rn "func Test.*[Mm]alformed.*[Pp]olicy\|func Test.*[Ii]nvalid.*[Pp]olicyContent" internal/engine/policies/*_test.go`) asserts the error's registry code matches **and** that no default-substituted explanation/reader-notes/range was loaded in place of the malformed one.

### Determinism, safety & type-safety

- **AC-11 (GR#21 — deterministic auto computation and deterministic history ordering).** Auto-value computation and history enumeration are deterministic: any iteration over settings/history that feeds output is sorted by a documented stable key (e.g. `PolicyID` then zone, and for history the append sequence — simulation month + sequence number), never dependent on unordered map iteration. Check: `grep -n "sort\." internal/engine/policies/*.go` shows an ordering step wherever a map feeds ordered output; a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/policies/*_test.go`).

- **AC-12 (GR#21/SG-7 — simulation month, never wall clock).** `grep -rn "time.Now\|time.Since" internal/engine/policies/*.go` (excluding `_test.go`) returns no matches — the history's timestamp is the simulation month (plus a monotonic sequence number), and auto-value computation is driven by simulation state, never wall clock. Never assert a wall-clock upper bound on how long a tick takes in CI; assert month/sequence equality only.

- **AC-13 (GR#16 — type-safe storage boundaries).** Values loaded from the policy data file and values resolved at the storage boundary are coerced through the project's safe helpers (`foundation/num` saturating arithmetic, `foundation/data` safe coercion) rather than trusted from the wire; any monetary policy value uses the `int64` micro-pounds convention (matching `engine.tax.md` AC-10), never a `float32`/`float64` monetary field. Check: `grep -n "float32\|float64" internal/engine/policies/*.go` (excluding `_test.go` and comments) finds no matches on monetary fields; the settings surface's load/resolve path routes through the safe helpers.

- **AC-14 (race safety).** `go test ./internal/engine/policies/... -race -count=1` passes with no data race when the settings/history surface is read concurrently with a setting being applied and a mode switched. Check: `grep -n "go func()" internal/engine/policies/*_test.go` finds at least one concurrency test.
