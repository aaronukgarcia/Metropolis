## 1. Why this item exists

Aaron's epic brief (`FEAT-2326609792`, verbatim): "Gridlock, long commutes and slow emergency response ADD TO UNHAPPINESS." inc3 built the routed commute-time distribution and gridlock detector; inc4 (in round) builds emergency coverage and response minutes. All four are currently diagnostic-only exports with no production caller (inc3 AC-8, inc4 AC-7 both explicitly forbid touching wellbeing). This increment is the wiring: three new, bounded, data-sourced, directional terms in the SAME `buildServiceWellbeingParts` list every other service coverage already feeds (`engine.ts:11005`), so the parts-list idiom (§2) renders them with no new UI.

## 2. The design in one paragraph

**(1) COMMUTE.** `congestionFactorOf`'s existing "Traffic/Commute" part (`engine.ts:11003,11026`) stays untouched — it is class-level SUSTAINED SATURATION, already income-coupled elsewhere (`engine.ts:1127`), and answers "is a line class overloaded", not "how long does a real trip take". A NEW "Commute time" part reads `commuteTimeDistributionOf(s).medianMinutes` (inc3, trip-weighted p50 — ASM-1515) through a stress curve anchored at two points sourced from `wellbeing.json.mental` (mirrored per BUG-860, ASM-1519): `(commuteThresholdMinutes, commuteStressAtThreshold)` and `(100, commuteStressAt100Minutes)`, piecewise-linear below the threshold from `(0, 0)`, clamped `[0, commuteStressAt100Minutes]` beyond 100 minutes — mirroring the SAME two-anchor sourcing shape `emergency_response.json`'s `speedDegradation.curve` already uses (inc4 §2 precedent). The stress value converts to a `part()`-shaped coverage via `1 / (1 + stress)` (stress 0 → coverage 1 → best; stress 2.0 at 100 min → coverage 1/3), bounded `[0,1]` by construction. Two class-level and trip-level signals now coexist deliberately (ASM-1516) — not a duplicate.

**(2) GRIDLOCK.** `gridlockedSegmentsOf(s, prevTicks)` (inc3) needs a `prevTicks` carried across ticks; a new `SimState.gridlockTicksBySegment?: Record<string, number>` field is added (`types.ts`, mirroring `congestionTicksBySpec?: Record<string,number>` at `types.ts:885`) and advanced in `advance()` using THIS tick's `segmentDelayOf` snapshot, read back by wellbeing only on the NEXT tick — the EXACT one-tick lag `congestionTicksBySpec` already uses (`engine.ts:7300-7314`, ASM-1517), so there is no same-tick self-reference. The gridlock share is NOT a raw count of gridlocked segments; it is the share of ROUTED PERSON-TRIPS whose assigned path crosses ≥1 gridlocked segment, weighted by `personTrips` (ASM-1520) — `tilePathsOf(s)`/`tileVehicleTripsOf(s)` are additively exported from `trafficAssignment.ts` (the internal `tilePaths`/`tileVehicleTrips` of `assignmentOf`, `:606-607`, already computed, never re-derived — GR#3, BUG-857 precedent). A NEW "Gridlock" part = `part(1 - gridlockShare × gridlockWeightFraction)`, where `gridlockWeightFraction` is a new `wellbeing.json` field (§5), bounded `[0,1]`.

**(3) EMERGENCY.** A NEW "Emergency response" part reads `emergencyCoverageOf(s, 'ambulance')` (inc4 — ambulance chosen for consistency with inc4's own D1 overlay choice, the tightest-target/highest-stakes service). `coverageShare === null` (zero online stations, honest absence) maps to the WORST-case input (as if `coverageShare` were `0`) — ASM-1518, Aaron's "slow response time is to add to unhappiness" reads a station-less city as unserved, not neutral. The part = `part(coverageShare ?? 0)`, i.e. full coverage → best, no stations → worst, scaled through the SAME `part()`/`blend()` idiom every other coverage row uses (`engine.ts:10925`) — no separate weight needed since `coverageShare` is already `[0,1]`.

**No cycle (AC-4).** All three inputs — `commuteTimeDistributionOf`, `gridlockedSegmentsOf`'s ticks-producing snapshot, `emergencyCoverageOf` — are pure functions of buildings/population/segments (`memoOnState(s)`), never of wellbeing, mirroring `congestionFactorOf`'s own argument (`data.ts:3704-3714`) verbatim.

**Rendering.** `buildServiceWellbeingParts` returns `{label, value}[]`; every existing UI consumer (wellbeing panel) iterates that array with no per-label special-casing (verified: no `label === 'Traffic/Commute'`-shaped conditional exists in the render path) — three new `{label, value}` entries render automatically, no new UI (§6).

## 3. Acceptance Criteria

**AC-1 — Commute-time wellbeing part: directional, bounded, zero-effect at the neutral point.**
New `commuteWellbeingPartOf(s): number` (or inlined in `buildServiceWellbeingParts`) computes the stress curve (§2.1) from `commuteTimeDistributionOf(s).medianMinutes` and the mirrored `wellbeing.json` anchors, feeding `part(1/(1+stress))` into the parts list as `{label: 'Commute time', value}`.
**Check:** three fixtures at medianMinutes `{0, thresholdMinutes, 100}` assert the resulting part VALUE is strictly decreasing across the three (0 min → highest, threshold → mid, 100 min → lowest), and the 0-minute fixture's stress is exactly `0` (part value equals `part(1)`, the curve's own zero anchor, not merely "high").
**False-pass note:** a test asserting only "higher commute time gives a lower or equal part value" (non-strict) would pass on a mutant that flattens the curve to a constant — the Tester must assert STRICT monotonicity across at least 3 distinct points, per the verification standard.
**Mutant:** invert the curve (`stress = commuteStressAt100Minutes - stress`) — reds the strict-monotonicity check (0 min now scores worst, 100 min best).

**AC-2 — Gridlock wellbeing part: trip-weighted, not segment-count-weighted; one-tick lag preserved.**
New `gridlockTicksBySegment` state field wired into `advance()` mirroring `congestionTicksBySpec` (`engine.ts:7310-7314`) exactly (same-tick write, next-tick read). New `gridlockWellbeingPartOf(s): number` reads the PREVIOUS tick's `s.gridlockTicksBySegment` (sanitized, same `sanitizeCongestionTicksBySpec`-shaped helper pattern) via `gridlockedSegmentsOf`, then computes `gridlockShare = (Σ tileVehicleTripsOf(s) over tiles whose tilePathsOf(s) path intersects gridlocked) ÷ (Σ tileVehicleTripsOf(s) over all routed tiles)` (`0` when no tiles are routed — honest neutral, never `NaN`).
**Check:** a fixture with 2 routed tiles of EQUAL trip weight, one whose path crosses a forced-gridlocked segment and one whose path does not, asserts `gridlockShare = 0.5` exactly (not `1/segmentCount` or any segment-counting shape); a second fixture with UNEQUAL weights (a heavy tile gridlocked, a light tile clear) asserts `gridlockShare` skews toward the heavy tile's weight, not `0.5`.
**False-pass note:** the equal-weight fixture alone cannot distinguish "trip-weighted" from "tile-counted" (both give `0.5` for 2 equal tiles) — the Tester must run the unequal-weight fixture too, per ASM-1520's exact concern.
**Mutant:** compute `gridlockShare` as `gridlocked.length ÷ segmentCount` (a global segment-count ratio, no trip weighting at all) — reds the unequal-weight fixture (produces a value independent of which tile is heavy).

**AC-3 — Emergency-response wellbeing part: honest-null maps to worst-case, never neutral.**
New `emergencyWellbeingPartOf(s): number` = `part(emergencyCoverageOf(s, 'ambulance').coverageShare ?? 0)`.
**Check:** a fixture forcing `coverageShare = null` (zero online ambulance stations, per inc4 AC-2's own empty-service contract) asserts the part value equals the fixture that forces `coverageShare = 0` exactly (same worst-case treatment, not merely "low"); a fixture at `coverageShare = 1` asserts the best-case value; a monotonicity fixture at `coverageShare ∈ {0, 0.5, 1}` asserts strict ascending part values.
**False-pass note:** a test that only checks `null` gives "some low value" (not the SAME value as `coverageShare: 0`) would pass on a mutant that treats `null` as a smaller-but-nonzero penalty (e.g. `?? 0.5`) — the Tester must assert exact equality between the null-fixture and the explicit-zero-fixture outputs, per ASM-1518.
**Mutant:** default `coverageShare ?? 1` (treat no-station cities as fully covered) — reds the null-vs-zero equality check by producing the BEST value instead of the worst.

**AC-4 — no cycle: the three new inputs depend only on buildings/population/segments, never on wellbeing (mirrors `congestionFactorOf`'s argument).**
A fixture computes `buildWellbeingCoreParts(s)` (`engine.ts:11063`) twice on the SAME state `s`: once normally, once after first calling `wellbeingOf(s)` (forcing any hidden lazy caching to have already run) — the raw INPUTS to the three new parts (`commuteTimeDistributionOf(s)`, `gridlockedSegmentsOf`'s ticks snapshot, `emergencyCoverageOf(s,'ambulance')`) are asserted IDENTICAL (JSON-deep-equal) across both calls, proving none of them read anything wellbeing-derived from `s`.
**Check:** as above; additionally `grep -n "wellbeing\|wbOverall\|approvalOf" webconsole/src/sim/trafficAssignment.ts webconsole/src/sim/emergencyResponse.ts` returns no matches (structural pin, mirrors inc3 AC-8 / inc4 AC-7's own grep shape).
**False-pass note:** a test that only calls `wellbeingOf(s)` once and checks it doesn't throw cannot detect a hidden read of `s.wellbeing`-shaped state — the Tester must assert byte-identical INPUTS across the two-call fixture above, not merely "no crash".
**Mutant:** thread `wbOverall` (or any wellbeing-derived value) into the gridlock-share weight formula as a scaling factor — reds the two-call identity check (the second call's input differs because the first `wellbeingOf(s)` call's result now leaks back in).

**AC-5 — all three parts render via the existing parts-list idiom; no new UI.**
The three new `{label, value}` entries are appended to `buildServiceWellbeingParts`'s returned array (`engine.ts:11005-11027`) in the SAME shape every other row uses; no wellbeing-panel component is edited.
**Check:** a fixture asserts `buildServiceWellbeingParts(s)` includes exactly one entry each labeled `'Commute time'`, `'Gridlock'`, `'Emergency response'` (distinct from the pre-existing `'Traffic/Commute'` label, AC-6), each with `value ∈ [0,100]` (the `part()`/`blend()` output range every other row already satisfies); `grep -rn "'Commute time'\|'Gridlock'\|'Emergency response'"` outside `engine.ts` (i.e. no wellbeing-panel component) returns no matches.
**False-pass note:** a test that checks the parts array LENGTH increased by 3 cannot distinguish "three correctly-labeled new parts" from "three parts with wrong labels/values" — the Tester must assert the LABELS and value BOUNDS explicitly.
**Mutant:** omit one of the three parts from the returned array while still passing its computation through unused — reds the exact-count-of-three-distinct-labels check.

**AC-6 — money and existing terms untouched.**
No file this increment touches writes to `s.budget`/`s.treasury`/any `*Pounds`/`*Revenue`/`*Cost` field; `congestionFactorOf`'s own "Traffic/Commute" part (label, value, position in the array) is byte-identical before/after this increment on a fixture with no new-term inputs at their neutral point (0 commute stress, 0 gridlock share, full emergency coverage).
**Check:** `grep -n "budget\|treasury\|Pounds\|Revenue\|Cost" <new/changed lines in engine.ts>` (scoped diff, not whole file) returns no matches; the neutral-point fixture above diffs `buildServiceWellbeingParts` output before/after and asserts every PRE-EXISTING label's value is unchanged.
**Mutant:** fold the new commute-time stress into `congestionFactorOf`'s OWN computation (in `data.ts`) instead of adding a separate part — reds the neutral-point diff (the pre-existing "Traffic/Commute" value changes even when nothing traffic-related changed for it specifically).

## 4. Decisions for Aaron (recommendation given, not blocking)

**D1 — `congestionFactorOf`'s part stays; commute-time is ADDITIVE, not a replacement.**
**Recommend: keep both.** They measure different things (§2.1) — collapsing them risks losing the class-level saturation signal `congestionFactorOf` already feeds into income (`engine.ts:1127`), a genuinely separate downstream consumer this increment must not disturb.

**D2 — emergency term uses `'ambulance'` only, matching inc4's own D1 overlay choice.**
**Recommend: accept, revisit only if inc10's service selector lands and Aaron wants fire/police wellbeing terms too.** A 3-service average was considered and rejected here: it would mask a city with a great ambulance service but zero fire cover, and the epic's own brief singles out no particular service — ambulance is the tightest/highest-stakes anchor, same rationale inc4 already used.

**D3 — no-station cities take the FULL emergency penalty (ASM-1518), not a grace-period exemption.**
**Recommend: accept as written, but flag for Aaron's balance pass.** A very early city with zero emergency buildings yet is not exempt — this may read as harsh before a player has had time to build; the existing early-game `blend()` factor (`f`, `engine.ts:10913`) already softens EVERY part (including this one) toward the neutral baseline in the opening ticks, which may be sufficient mitigation without a bespoke exemption.
