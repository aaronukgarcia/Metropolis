# Acceptance criteria — engine.roads (MOD-024)

**BOW code:** MOD-024
**Spec refs:** §20 Roads & Auto-Naming (`docs/METROPOLIS-MASTER-v2.1.md` lines 360-370: roads as named edges with identity, class ladder, maintenance state, road inspector; deterministic auto-naming for every object from seed+id, player-renameable); §51 Roads v2 — Types, Upgrades & the Lane Myth (lines 660-664: full class ladder, in-place upgrades, simulated roadworks with phased lane closures, induced-demand pedagogy — the assignment-side mechanics live in `engine.traffic`, this item owns the road-identity/upgrade/roadworks side); code.json `engine.roads` entry (inbound `RoadsAPI`, "Go package API + deltas", pattern "graph mutations via commands; naming registry service for all modules"; outbound calls `engine.world`, `foundation.data`; consumed by `engine.news`, `engine.traffic`).
**Date:** 2026-08-09
**Status:** draft-ahead
**Package under test:** `internal/engine/roads/` (path from `node claude-bow.js show MOD-024`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/roads/...`.

## User stories

- **US-1.** As `engine.traffic`, I need every road to be a named edge with identity — class, lanes, speed limit, start/end nodes, maintenance state — exposed via a stable `RoadsAPI`, so assignment always reads real, addressable link data rather than anonymous graph edges (§20).
- **US-2.** As the player, I need the full 'Blue'-parity class ladder (alley → gravel → residential street → two-lane → one-way pairs → avenue 2+2 → bus-lane variants → tram-track variants → dual carriageway → urban expressway → motorway), each with lane counts, parking presence, and tree/verge options, so road-building has the same depth 'Blue' players expect (§51).
- **US-3.** As the road inspector (consumed by a later F-screen), I need to query, for any road: name, endpoints, daily volume by segment, v/c ratio, top-5 origin→destination flows, and which alternative routes exist, so the game can always explain *why* a road is full — something 'Blue' never could (§20).
- **US-4.** As every object in the game world, I need deterministic auto-naming from seed+id — roads from the Kentish corpus × class-appropriate suffix with continuation rules so one road keeps one name through junctions; civic buildings named for notable deceased citizens or toponym+type; infrastructure functionally numbered; districts named from real local toponyms then generated compounds; transit auto-lettered/coloured — all player-renameable afterward, so the city reads like a real place, not a spreadsheet (§20).
- **US-5.** As the player upgrading a road, I need in-place conversion to any compatible type (cost = delta + rebuild disruption) with simulated roadworks — phased lane closures that genuinely re-route real traffic, warned in projections before I approve, schedulable at night/summer — so upgrades have real, forecastable consequences rather than an instant magic swap (§51).
- **US-6.** As the maintenance budget, I need road condition (potholes) to raise costs and lower speeds when underfunded, so maintenance is a real, felt trade-off rather than cosmetic (§20).
- **US-7.** As `engine.news`/the traffic advisor, I need the roadworks and upgrade machinery to surface real before/after projection numbers (journey-time deltas, mode-share shifts) sourced from `engine.traffic`'s actual re-assignment, not scripted narration text, so §51's induced-demand pedagogy is mechanically grounded.

## Scope

The `RoadsAPI`: road-as-named-edge identity (class, lanes, speed limit, maintenance state, endpoints), the full §51 class ladder with in-place upgrade mechanics, simulated roadworks (phased lane closures, schedulable timing), the road inspector query surface, and the deterministic auto-naming service for roads plus the naming-registry hooks other modules use for civic buildings/infrastructure/districts/transit. Does not include the SUE assignment, junction control, or mode-choice logic that computes the volumes/flows the inspector displays — that is `engine.traffic` (this sprint's sibling item), which `engine.roads` calls into for live numbers.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `RoadsAPI` Go interface exists exposing graph mutations only as commands (never direct field-sets on edge/node structs) plus the naming-registry service consumed by other modules, matching code.json's "graph mutations via commands; naming registry service for all modules" pattern. Check: `go doc ./internal/engine/roads RoadsAPI` shows command-based mutation methods (e.g. `ApplyUpgradeCommand`, `ApplyRoadworksCommand`) and a naming query/registration method (e.g. `NameFor(kind ObjectKind, seed, id uint64) string`); `grep -rn "roads\.\(Edge\|Node\)\.\w\+ = " internal/engine/*/` (excluding the `roads` package itself) finds no direct exported-field writes from other packages.
- **AC-2 (§20; named edges).** Every road is a named edge carrying class, lane count, speed limit (player-settable within class bounds), start/end node references, and maintenance state (a condition value that degrades over time absent upkeep). Check: `go doc ./internal/engine/roads Road` (or `Edge`) lists all these fields; a passing test asserts a fresh road has a maintenance-state value distinct from a synthetically-aged one (`grep -rn "func Test.*[Mm]aintenance" internal/engine/roads/*_test.go`).
- **AC-3 (§51; class ladder).** The full 11-rung ladder is represented: alley, gravel, residential street, two-lane, one-way pairs, avenue 2+2, bus-lane variant, tram-track variant, dual carriageway, urban expressway, motorway — each with distinct lane-count, parking-presence, and tree/verge-option fields. Check: `go doc ./internal/engine/roads RoadClass` lists all 11; a passing test asserts at least two adjacent rungs (e.g. `residential street` vs `two-lane`) have different default lane counts (`grep -rn "func Test.*[Cc]lassLadder\|func Test.*[Rr]oadClass" internal/engine/roads/*_test.go`).
- **AC-4 (§51; in-place upgrade).** Any road can convert in-place to any *compatible* target class (compatibility rules documented — e.g. an alley cannot become a motorway in one step without intermediate rungs, or the rule is explicitly "any-to-any with cost scaling by rung distance," whichever the junior documents), with cost computed as delta cost plus a rebuild-disruption cost. Check: `go doc ./internal/engine/roads ApplyUpgradeCommand` (or equivalent) documents the compatibility rule; a passing test asserts an incompatible upgrade request (per the documented rule) is rejected while a compatible one succeeds (`grep -rn "func Test.*[Uu]pgrade" internal/engine/roads/*_test.go`).
- **AC-5 (§51; widening into buildings).** Widening a road footprint into adjacent built cells requires a purchase/demolition step (compensation cost) before the upgrade can apply — the upgrade command is rejected or blocked pending demolition if the target class's footprint would overlap an occupied cell it does not already own. Check: a passing test asserts an upgrade requiring footprint expansion into an occupied cell fails until a demolition/purchase command clears that cell (`grep -rn "func Test.*[Ww]idening\|func Test.*[Ff]ootprint" internal/engine/roads/*_test.go`).
- **AC-6 (§51; simulated roadworks).** An approved upgrade schedules roadworks as a phased sequence of lane closures over simulated time (not an instant swap), during which `engine.traffic`'s live assignment re-routes real traffic around the reduced capacity — the roadworks phase is schedulable to specific simulated windows (e.g. night hours, summer months) via a documented scheduling command. Check: `go doc ./internal/engine/roads ScheduleRoadworksCommand` (or equivalent) exists with a timing parameter; a passing test asserts a road's usable lane count during an active roadworks phase is lower than its steady-state lane count, and that `engine.traffic`'s link-capacity query for that road reflects the reduction while the phase is active (`grep -rn "func Test.*[Rr]oadworks" internal/engine/roads/*_test.go`).
- **AC-7 (§51; pre-approval projection warning).** Before a roadworks-triggering upgrade is approved (committed), the API exposes a projection query (journey-time delta estimate) that the caller (UI/advisor) can surface to the player prior to commit — the projection is computed from the same `engine.traffic` assignment machinery, not an invented estimate formula unique to this package. Check: `go doc ./internal/engine/roads PreviewUpgradeImpact` (or equivalent) exists and its implementation calls into `engine.traffic`'s query surface (`grep -n "traffic\.\|TrafficAPI" internal/engine/roads/*.go` shows the call site); a passing test asserts the preview and the post-commit actual roadworks-phase reduction reference the same link-capacity delta (`grep -rn "func Test.*[Pp]review" internal/engine/roads/*_test.go`).
- **AC-8 (§20; road inspector).** A query surface returns, for any road: name, endpoints, daily volume by segment, v/c ratio, top-5 origin→destination flows using it, and the set of alternative routes that exist — sourced from `engine.traffic`'s live assignment data, not recomputed independently. Check: `go doc ./internal/engine/roads InspectRoad` (or equivalent) returns a struct with all six fields; a passing test asserts the returned volume/v-c figures match a fixture `engine.traffic` query for the same road (`grep -rn "func Test.*[Ii]nspect" internal/engine/roads/*_test.go`).
- **AC-9 (§20; road auto-naming).** New roads are named deterministically from seed+id using the Kentish corpus (Cheriton, Seabrook, Pent, Risborough, Sandgate, Downs, Alkham, Saltwood, etc., sourced from `data/naming_corpus.json` per §24 — GR#15, not a Go literal list) × a class-appropriate suffix (Lane/Road/Street/Avenue/Way/Drive/Close; motorways get M-/A- numbering), and a continuation rule keeps one name through junctions unless the road's class changes. Check: `go doc ./internal/engine/roads NameRoad` (or equivalent) exists; `grep -n "naming_corpus" internal/engine/roads/*.go` shows the data-sourced corpus is loaded via `foundation.data`, not hardcoded; a passing test asserts naming the same seed+id twice produces the identical name, and a road continuing straight through a same-class junction keeps its name (`grep -rn "func Test.*[Nn]aming\|func Test.*[Cc]ontinuation" internal/engine/roads/*_test.go`).
- **AC-10 (§20; naming-registry service for other object kinds).** The naming service exposed via `RoadsAPI` (or a sibling entry point in the same package, per code.json's "naming registry service for all modules") also supports the other §20 object kinds: civic buildings (named for notable deceased citizens pulled from real records, or toponym+type), infrastructure (functional numbering, e.g. "Pumping Station No. 3"), districts (real local toponyms first, then generated compounds), and transit (auto-lettered/coloured lines, stations named by street/district) — each callable by other modules through the same deterministic seed+id contract. Check: `go doc ./internal/engine/roads` lists a naming function per object kind (or one polymorphic `NameFor(kind ObjectKind, ...)`); a passing test covers at least civic-building and infrastructure naming distinctly from road naming (`grep -rn "func Test.*[Cc]ivic\|func Test.*[Ii]nfrastructure.*[Nn]am" internal/engine/roads/*_test.go`).
- **AC-11 (§20; player-renameable).** Any auto-named object (road or otherwise, via the registry) can be renamed by the player through a documented command, after which the auto-naming service never overwrites the player's chosen name on a later naming pass (e.g. a re-run of the naming service for unrelated new objects). Check: `go doc ./internal/engine/roads RenameCommand` (or equivalent) exists; a passing test asserts a renamed road's name survives a subsequent naming-service invocation for a different object (`grep -rn "func Test.*[Rr]ename" internal/engine/roads/*_test.go`).

### Error handling

- **AC-12 (GR#7).** An upgrade or roadworks-scheduling command targeting a nonexistent road, or an incompatible class transition rejected by AC-4's rule, returns a registry-sourced error (new `MET-E`-range code) rather than a silent no-op or a panic. Check: `grep -n "MET-" internal/engine/roads/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalid.*[Uu]pgrade\|func Test.*[Nn]onexistentRoad" internal/engine/roads/*_test.go`).
- **AC-13.** A naming request for an unrecognised `ObjectKind`, or a corpus/registry load failure (`data/naming_corpus.json` malformed/missing), fails loudly via `foundation.data`'s validated-load path rather than silently returning an empty or placeholder name that could ship visible to the player. Check: passing test coverage (`grep -rn "func Test.*[Uu]nrecognisedKind\|func Test.*[Cc]orpusLoadFail" internal/engine/roads/*_test.go`).

### Determinism & safety

- **AC-14 (GR#21; core requirement).** Naming the same seed+id twice, and re-running an identical sequence of upgrade/roadworks commands against an identical starting graph state, produces byte-identical `RoadsAPI` outputs (names, graph structure, maintenance state) at `POOL-SIM=1` and at `POOL-SIM=14` — a dedicated shard-count-invariance test exists, following `feat.detgate`'s reference structure. Check: `grep -rn "func Test.*[Ss]hardInvariance\|func Test.*POOL_SIM\|func Test.*[Dd]eterminis" internal/engine/roads/*_test.go` finds it; `go test ./internal/engine/roads/... -run TestRoadsDeterminism -race -count=1 -v` (or the actual name) passes.
- **AC-15 (GR#21; no map-range on result-affecting collections).** No `for range` loop over a Go map feeds a value into a naming decision, upgrade-cost computation, or the inspector's top-5 OD flow list without a prior deterministic sort/ordering step. Check: `grep -rn "for .* := range" internal/engine/roads/*.go` — every match iterating a map type is either read-only diagnostics or preceded by a `sort.` call on the iteration keys (`grep -n "sort\." internal/engine/roads/*.go` confirms an ordering step exists for each map-range site that affects output).
- **AC-16 (GR#21; deterministic tie-breaking).** Any point where naming or upgrade logic must break a tie (two equally-eligible corpus names, two candidate deceased citizens with equal tenure for a civic-building name, top-5 OD flows with equal volume) uses a documented deterministic rule (lowest ID, lexicographic ordering, or the counter-RNG from `foundation.det` seeded per the fixed seed) — never Go's undefined map/slice iteration order or a raw unseeded `math/rand` call. Check: `grep -n "math/rand\"" internal/engine/roads/*.go` (excluding `_test.go`) finds no matches; `go doc ./internal/engine/roads` documents each tie-break rule.
- **AC-17 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/roads/*.go` (excluding `_test.go`) returns no matches — maintenance-state decay and roadworks scheduling are functions of simulation tick/month, never wall clock. Any roadworks "night/summer" scheduling window (§51) is expressed as a simulation-calendar predicate (via `engine.season`'s month-index or equivalent), not a real-world date/time check.
- **AC-18.** `go test ./internal/engine/roads/... -race -count=1` passes with no data race under the 256-fixed-shard worker pool pattern. Check: `grep -n "go func()" internal/engine/roads/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-19.** `internal/engine/roads/doc.go` states the module key `engine.roads`, cites §20 and §51, and documents the compatibility rule for in-place upgrades (AC-4) and the tie-break rules (AC-16) explicitly, so a future contributor cannot silently reintroduce nondeterminism or an undocumented upgrade-path restriction. Check: `grep -n "engine.roads" internal/engine/roads/doc.go` and `grep -n "§20\|section 20" internal/engine/roads/doc.go` both match.
- **AC-20.** The route-cache placement question (see `engine.traffic.md`'s AC-22/Escalations) is resolved explicitly in this package's `doc.go` — either "the warm-start route cache lives here" with its contents-independence documented, or "the cache lives in `engine.traffic`, not here." Check: `grep -n "route cache\|warm.start" internal/engine/roads/doc.go` states one or the other unambiguously.

## Out of scope

- SUE assignment, junction control-type modelling, mode-choice logit, and commute-time accounting — that is `engine.traffic` (MOD-023, this sprint's sibling item); `engine.roads` calls into `engine.traffic`'s query surface for live volume/v-c/projection numbers, it does not compute them.
- The road inspector's UI presentation (a later F-screen or `ui.screen.map` overlay) — this item's `InspectRoad` query is the data source, not the rendered panel.
- Civic-building, infrastructure, district, and transit *placement/construction* mechanics — those belong to `engine.build`, `engine.services`, `engine.rail`, etc.; this item only provides the naming-registry service those modules call once they've decided what to build.
- Historical-citizen record lookup for civic-building naming (which deceased citizen is "notable enough") — the eligibility/ranking rule is this item's concern to define deterministically (AC-16), but the underlying citizen mortality/tenure data comes from `engine.citizens`.
- Tunnels/TBM boring mechanics (§53, `MOD-065`, unscheduled future) — an in-place upgrade to a tunnel-requiring class is out of this item's scope until that module lands.

## Escalations

- **For Bill — upgrade compatibility rule is spec-silent on exact adjacency.** §51 says "any road converts to any compatible type" without defining "compatible" precisely (must upgrades step through adjacent class-ladder rungs one at a time, e.g. alley→gravel→residential before reaching two-lane, or can any rung jump to any other rung with cost scaling by rung-distance?). AC-4 requires the junior to pick and document a rule since GR#15 forbids inventing balance numbers without a documented source — flagging because this materially affects early-game player strategy (can a player skip straight to dual carriageway?) and should probably be confirmed against `data/buildings.json`/a roads-specific balance data file rather than left as an implementer's silent choice.
- **For Bill — civic-building naming eligibility ("notable deceased citizens") needs a ranking rule.** §20 says civic buildings are "named for notable deceased citizens (first mayor-era settlers, long-serving teachers...)" but gives no algorithm for selecting *which* deceased citizen is notable enough, or what happens before any citizen has died in a fresh city (early-game civic buildings presumably fall back to toponym+type, per §20's "or toponym + type" alternative) — AC-16's tie-break rule can only cover ties among already-eligible candidates, not the eligibility threshold itself, which reads as a genuine spec gap rather than an implementer detail.
- **Assumption flagged (per BA instructions §3).** This item depends on `MOD-006` (foundation.data, done) and `MOD-017` (engine.world, S3) for terrain/cell footprint queries during widening (AC-5); it has no code.json dependency on `engine.traffic` despite AC-7/AC-8 requiring live calls into `TrafficAPI` for projection/inspector data — code.json's dependency graph shows `engine.roads` as a *provider* to `engine.traffic` (roads → traffic, not traffic → roads) via the outbound-call list, yet AC-7/AC-8 need traffic's query results. This is a real circular-consumption question the owning BA should raise with Bill before Sprint 5 dispatch: does `engine.roads` call `engine.traffic` for read-only queries (a legitimate lateral call within the same sprint, not a package-import cycle if mediated through interfaces) or does the inspector/preview surface actually belong on the `TrafficAPI` side, with `engine.roads` only supplying the road-identity data `engine.traffic` decorates? The BOW dependency list (`engine.traffic` depends on `engine.roads`, not the reverse) suggests the latter is architecturally cleaner — recommend Bill confirm before build, since it changes which package owns AC-7/AC-8.
