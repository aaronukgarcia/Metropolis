## Architecture ruling in force (Bill, MOD-024 comment, 2026-08-09) — corrects the superseded draft

**`engine.roads` must not call `engine.traffic`.** The superseded draft's AC-6/AC-7/AC-8 required exactly that (roadworks capacity reduction "reflected in engine.traffic's query", preview computed "from the same engine.traffic assignment machinery", inspector "sourced from engine.traffic's live assignment data") — every one of those checks would have forced a `roads → traffic` package import, which is the wrong direction per code.json (`engine.traffic` depends on `engine.roads`, not the reverse) and per GR#20. This is not a wording nitpick: a junior building to the old AC-7/AC-8 checks literally cannot pass them without creating the banned import, so the old checks were **unsatisfiable as written without violating GR#20** — a worse failure mode than merely weak. Rewritten below (AC-6, AC-7, AC-8) to test only the half `engine.roads` owns; the joint end-to-end claim (a road inspector showing real live volume/v-c numbers) is deferred to a consuming layer (see ASM-217, logged against `engine.traffic.md`, which this file cross-references).

**Route cache does not live here.** It lives in `engine.traffic` (see `engine.traffic.md` AC-22). Resolved, not an open question (AC-20 below states this as fact).

## User stories

- **US-1.** As `engine.traffic`, I need every road to be a named edge with identity — class, lanes, speed limit, start/end nodes, maintenance state — exposed via a stable `RoadsAPI`, so assignment always reads real, addressable link data rather than anonymous graph edges (§20).
- **US-2.** As the player, I need the full 'Blue'-parity class ladder (alley → gravel → residential street → two-lane → one-way pairs → avenue 2+2 → bus-lane variants → tram-track variants → dual carriageway → urban expressway → motorway), each with lane counts, parking presence, and tree/verge options, so road-building has the same depth 'Blue' players expect (§51).
- **US-3.** As `engine.roads`' own query surface, I need to expose, for any road, its identity data (name, endpoints, class, current lane count including any roadworks-phase reduction) so that a consuming layer can pair it with `engine.traffic`'s live volume/v-c/OD-flow data to build the full road inspector — this package supplies the identity half only (§20).
- **US-4.** As every object in the game world, I need deterministic auto-naming from seed+id — roads from the Kentish corpus × class-appropriate suffix with continuation rules so one road keeps one name through junctions; civic buildings named for notable deceased citizens or toponym+type; infrastructure functionally numbered; districts named from real local toponyms then generated compounds; transit auto-lettered/coloured — all player-renameable afterward, so the city reads like a real place, not a spreadsheet (§20).
- **US-5.** As the player upgrading a road, I need in-place conversion to any compatible type (cost = delta + rebuild disruption) with simulated roadworks — phased lane closures that genuinely reduce this road's own usable lane count for the phase duration, schedulable at night/summer — so upgrades have real, forecastable consequences rather than an instant magic swap. The re-routing of *traffic* around the reduction is `engine.traffic`'s concern, reading the reduced capacity this package exposes on its normal read path (§51).
- **US-6.** As the maintenance budget, I need road condition (potholes) to raise costs and lower speeds when underfunded, so maintenance is a real, felt trade-off rather than cosmetic (§20).
- **US-7.** As a consuming layer (`engine.news`/a future advisor screen), I need this package's capacity-delta data (before/after lane counts for a proposed upgrade) so that layer — composing it with a separate `engine.traffic` call — can show real before/after projection numbers, not scripted narration text. This package computes the capacity delta; it does not compute journey-time deltas itself (§51).

## Scope

The `RoadsAPI`: road-as-named-edge identity (class, lanes, speed limit, maintenance state, endpoints), the full §51 class ladder with in-place upgrade mechanics, simulated roadworks (phased lane closures exposed as a reduced current-lane-count on this package's own read path, schedulable timing), a road-identity query surface (name/endpoints/class/current capacity — not volume/v-c/flows, which are `engine.traffic`'s), and the deterministic auto-naming service for roads plus the naming-registry hooks other modules use for civic buildings/infrastructure/districts/transit. Does not include the SUE assignment, junction control, mode-choice logic, or any live volume/v-c/flow data — that is `engine.traffic` (this sprint's sibling item), which reads this package's identity/capacity data but is never called by it.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `RoadsAPI` Go interface exists exposing graph mutations only as commands (never direct field-sets on edge/node structs) plus the naming-registry service consumed by other modules, matching code.json's "graph mutations via commands; naming registry service for all modules" pattern. Check: `go doc ./internal/engine/roads RoadsAPI` shows command-based mutation methods (e.g. `ApplyUpgradeCommand`, `ApplyRoadworksCommand`) and a naming query/registration method (e.g. `NameFor(kind ObjectKind, seed, id uint64) string`); `grep -rn "roads\.\(Edge\|Node\)\.\w\+ = " internal/engine/*/` (excluding the `roads` package itself) finds no direct exported-field writes from other packages.
- **AC-2 (§20; named edges).** Every road is a named edge carrying class, lane count, speed limit (player-settable within class bounds), start/end node references, and maintenance state (a condition value that degrades over time absent upkeep). Check: `go doc ./internal/engine/roads Road` (or `Edge`) lists all these fields; a passing test asserts a fresh road has a maintenance-state value distinct from a synthetically-aged one (`grep -rn "func Test.*[Mm]aintenance" internal/engine/roads/*_test.go`).
- **AC-3 (§51; class ladder).** The full 11-rung ladder is represented: alley, gravel, residential street, two-lane, one-way pairs, avenue 2+2, bus-lane variant, tram-track variant, dual carriageway, urban expressway, motorway — each with distinct lane-count, parking-presence, and tree/verge-option fields. Check: `go doc ./internal/engine/roads RoadClass` lists all 11; a passing test asserts at least two adjacent rungs (e.g. `residential street` vs `two-lane`) have different default lane counts (`grep -rn "func Test.*[Cc]lassLadder\|func Test.*[Rr]oadClass" internal/engine/roads/*_test.go`).
- **AC-4 (§51; in-place upgrade — compatibility rule RATIFIED by Aaron, ASM-1451).** Any road can convert in-place to any *compatible* target class, with cost computed as delta cost plus a rebuild-disruption cost. The compatibility rule is **any-to-any with rung-distance cost scaling** (RATIFIED, ASM-1451): any rung of the class ladder may convert directly to any other rung — not merely to an adjacent rung — with cost scaled by rung-distance between the source and target class; the step-through-adjacent-rungs alternative was ruled out. The rule must be documented, not silently re-chosen. Check: `go doc ./internal/engine/roads ApplyUpgradeCommand` (or equivalent) documents the compatibility rule it implements (any-to-any with rung-distance cost scaling) and cites the decision it traces to (ASM-1451); a passing test asserts an incompatible upgrade request (per the documented rule) is rejected while a compatible one succeeds (`grep -rn "func Test.*[Uu]pgrade" internal/engine/roads/*_test.go`).
- **AC-5 (§51; widening into buildings).** Widening a road footprint into adjacent built cells requires a purchase/demolition step (compensation cost) before the upgrade can apply — the upgrade command is rejected or blocked pending demolition if the target class's footprint would overlap an occupied cell it does not already own. Check: a passing test asserts an upgrade requiring footprint expansion into an occupied cell fails until a demolition/purchase command clears that cell (`grep -rn "func Test.*[Ww]idening\|func Test.*[Ff]ootprint" internal/engine/roads/*_test.go`).
- **AC-6 (§51; simulated roadworks — rewritten, no longer requires a `roads → traffic` call).** An approved upgrade schedules roadworks as a phased sequence of lane closures over simulated time (not an instant swap), during which this road's `RoadsAPI`-queryable **current lane count** is reduced from its steady-state value for the phase's duration; the roadworks phase is schedulable to specific simulated windows (e.g. night hours, summer months) via a documented scheduling command. `engine.traffic` re-routing around the reduction is proven by `engine.traffic`'s own tests (it reads this package's current-capacity value on its normal per-assignment read path) — **not** by this package calling into `engine.traffic` to check. Check: `go doc ./internal/engine/roads ScheduleRoadworksCommand` (or equivalent) exists with a timing parameter; a passing test asserts a road's `RoadsAPI` current-lane-count query returns a lower value during an active roadworks phase than its steady-state value, entirely within this package (`grep -rn "func Test.*[Rr]oadworks" internal/engine/roads/*_test.go`); `grep -n "traffic\.\|TrafficAPI" internal/engine/roads/*.go` (excluding `_test.go`) finds **no matches** — its presence would indicate the banned import direction.
- **AC-7 (§51; pre-approval projection — rewritten, no longer requires a `roads → traffic` call).** Before a roadworks-triggering upgrade is approved (committed), the API exposes a **capacity-delta projection query** — before/after current-lane-count and any other roads-owned figures (e.g. class change) — that a consuming layer (UI/advisor) can pair with its own separate `engine.traffic` call to build a journey-time-delta estimate for the player. This package computes and exposes the capacity delta only; it does **not** compute a journey-time estimate itself, invented or otherwise. Check: `go doc ./internal/engine/roads PreviewCapacityDelta` (or equivalent, renamed from `PreviewUpgradeImpact` in the superseded draft to make the scope explicit) exists and returns only roads-owned fields (lane-count before/after, class before/after); `grep -n "traffic\.\|TrafficAPI" internal/engine/roads/*.go` (excluding `_test.go`) finds no matches; a passing test asserts the preview's before/after capacity numbers match the actual post-commit roadworks-phase reduction from AC-6 (`grep -rn "func Test.*[Pp]review" internal/engine/roads/*_test.go`).
- **AC-8 (§20; road identity query — rewritten, narrowed from "road inspector" to the identity half this package owns).** A query surface returns, for any road: name, endpoints, class, and current lane count (including any active roadworks reduction) — the identity/capacity fields this package owns. It does **not** return volume, v/c ratio, top-5 OD flows, or alternative-route data — those are `engine.traffic`'s query surface, keyed by the same road/edge ID, composed by a consuming layer into the full §20 "road inspector" view. Check: `go doc ./internal/engine/roads` shows this query returning only identity/capacity fields (no `Volume`, `VCRatio`, `TopFlows`, or `Alternatives` field on the roads-side return type); a passing test asserts the query's fields are all sourced from this package's own edge state, not fetched from another package (`grep -rn "func Test.*[Ii]dentity\|func Test.*[Rr]oadQuery" internal/engine/roads/*_test.go`). **Scope note (see ASM-217, logged on the traffic side):** the full six-field inspector behaviour from §20 is unverifiable by this package alone — that is intentional, not a gap in this AC.
- **AC-9 (§20; road auto-naming).** New roads are named deterministically from seed+id using the Kentish corpus (Cheriton, Seabrook, Pent, Risborough, Sandgate, Downs, Alkham, Saltwood, etc., sourced from `data/naming_corpus.json` per §24 — GR#15, not a Go literal list) × a class-appropriate suffix (Lane/Road/Street/Avenue/Way/Drive/Close; motorways get M-/A- numbering), and a continuation rule keeps one name through junctions unless the road's class changes. Check: `go doc ./internal/engine/roads NameRoad` (or equivalent) exists; `grep -n "naming_corpus" internal/engine/roads/*.go` shows the data-sourced corpus is loaded via `foundation.data`, not hardcoded; a passing test asserts naming the same seed+id twice produces the identical name, and a road continuing straight through a same-class junction keeps its name (`grep -rn "func Test.*[Nn]aming\|func Test.*[Cc]ontinuation" internal/engine/roads/*_test.go`). **Blocking pre-dispatch dependency (ASM-223):** `data/naming_corpus.json` currently has no authored content (`{"version": 1, "categories": {}}`) — this AC cannot be satisfied as written until the corpus is populated; flag alongside `engine.traffic`'s ASM-215 (`modes.json`) as the same class of gap (data.catalogue schema owed before S5 dispatch).
- **AC-10 (§20; naming-registry service for other object kinds).** The naming service exposed via `RoadsAPI` (or a sibling entry point in the same package, per code.json's "naming registry service for all modules") also supports the other §20 object kinds: civic buildings (toponym+type fallback — RATIFIED as the correct shipped rule, ASM-1452; the "notable deceased citizens" eligibility/ranking alternative is future work tracked as FEAT-213, out of scope here), infrastructure (functional numbering, e.g. "Pumping Station No. 3"), districts (real local toponyms first, then generated compounds), and transit (auto-lettered/coloured lines, stations named by street/district) — each callable by other modules through the same deterministic seed+id contract. Check: `go doc ./internal/engine/roads` lists a naming function per object kind (or one polymorphic `NameFor(kind ObjectKind, ...)`); a passing test covers at least civic-building and infrastructure naming distinctly from road naming (`grep -rn "func Test.*[Cc]ivic\|func Test.*[Ii]nfrastructure.*[Nn]am" internal/engine/roads/*_test.go`).
- **AC-11 (§20; player-renameable).** Any auto-named object (road or otherwise, via the registry) can be renamed by the player through a documented command, after which the auto-naming service never overwrites the player's chosen name on a later naming pass (e.g. a re-run of the naming service for unrelated new objects). Check: `go doc ./internal/engine/roads RenameCommand` (or equivalent) exists; a passing test asserts a renamed road's name survives a subsequent naming-service invocation for a different object (`grep -rn "func Test.*[Rr]ename" internal/engine/roads/*_test.go`). **False-pass note:** a test that only renames and immediately re-reads the name proves persistence, not survival-through-a-later-unrelated-naming-pass — the check must specifically invoke the naming service again for a *different* object afterward and re-check the renamed one, or a naive implementation that re-derives all names on every naming-service call (overwriting renames) would still pass.

### Error handling

- **AC-12 (GR#7).** An upgrade or roadworks-scheduling command targeting a nonexistent road, or an incompatible class transition rejected by AC-4's rule, returns a registry-sourced error (new `MET-E`-range code) rather than a silent no-op or a panic. Check: `grep -n "MET-" internal/engine/roads/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalid.*[Uu]pgrade\|func Test.*[Nn]onexistentRoad" internal/engine/roads/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no silent no-op upgrade/roadworks command was applied, not merely that a matching-named test function exists.
- **AC-13.** A naming request for an unrecognised `ObjectKind`, or a corpus/registry load failure (`data/naming_corpus.json` malformed/missing), fails loudly via `foundation.data`'s validated-load path rather than silently returning an empty or placeholder name that could ship visible to the player. Check: passing test coverage (`grep -rn "func Test.*[Uu]nrecognisedKind\|func Test.*[Cc]orpusLoadFail" internal/engine/roads/*_test.go`).

### Determinism & safety

- **AC-14 (GR#21; core requirement — strengthened, same reasoning as `engine.traffic.md` AC-17).** Naming the same seed+id twice, and re-running an identical sequence of upgrade/roadworks commands against an identical starting graph state, produces byte-identical `RoadsAPI` outputs (names, graph structure, maintenance state) at **three or more distinct worker counts** (e.g. `POOL-SIM=1`, `4`, `14`), each repeated at least twice, on a fixture large enough (hundreds+ of roads) that a shard-partition-dependent ordering bug would actually surface in the compared hash rather than coincidentally match. Check: `grep -rn "func Test.*[Ss]hardInvariance\|func Test.*POOL_SIM\|func Test.*[Dd]eterminis" internal/engine/roads/*_test.go` finds it; the test asserts one hash equal across every (worker-count, repeat) pair, not a single pairwise comparison; `go test ./internal/engine/roads/... -run TestRoadsDeterminism -race -count=1 -v` (or the actual name) passes. **False-pass note:** roads' determinism-sensitive outputs (name assignment order, top-tie-break selection) are less numerically fragile than traffic's floating-point sums, but the same two-endpoint-single-run test would still miss an ordering bug that only manifests at a shard count neither 1 nor 14 happens to produce — hence the same three-plus-worker-counts-with-repeats standard applies here too, for consistency across the sprint's determinism gates.
- **AC-15 (GR#21; no map-range on result-affecting collections).** No `for range` loop over a Go map feeds a value into a naming decision, upgrade-cost computation, or the current-capacity query without a prior deterministic sort/ordering step. Check: `grep -rn "for .* := range" internal/engine/roads/*.go` — every match iterating a map type is either read-only diagnostics or preceded by a `sort.` call on the iteration keys (`grep -n "sort\." internal/engine/roads/*.go` confirms an ordering step exists for each map-range site that affects output).
- **AC-16 (GR#21; deterministic tie-breaking).** Any point where naming or upgrade logic must break a tie (two equally-eligible corpus names, two roads with identical adjacency scores, and — once FEAT-213's notable-deceased rule lands — two candidate deceased citizens with equal tenure for a civic-building name; current civic-building naming uses the toponym+type fallback) uses a documented deterministic rule (lowest ID, lexicographic ordering, or the counter-RNG from `foundation.det` seeded per the fixed seed) — never Go's undefined map/slice iteration order or a raw unseeded `math/rand` call. Check: `grep -n "math/rand\"" internal/engine/roads/*.go` (excluding `_test.go`) finds no matches; `go doc ./internal/engine/roads` documents each tie-break rule. **Note:** the top-5-OD-flow tie-break named in the superseded draft is removed here — that data is `engine.traffic`'s, not this package's, per the AC-8 rewrite; any OD-flow tie-break rule belongs in `engine.traffic.md`.
- **AC-17 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/roads/*.go` (excluding `_test.go`) returns no matches — maintenance-state decay and roadworks scheduling are functions of simulation tick/month, never wall clock. Any roadworks "night/summer" scheduling window (§51) is expressed as a simulation-calendar predicate (via `engine.season`'s month-index or equivalent), not a real-world date/time check.
- **AC-18.** `go test ./internal/engine/roads/... -race -count=1` passes with no data race under the 256-fixed-shard worker pool pattern. Check: `grep -n "go func()" internal/engine/roads/*_test.go` finds at least one concurrency test.

## Out of scope

- SUE assignment, junction control-type modelling, mode-choice logit, commute-time accounting, and **all live volume/v-c/OD-flow/journey-time data** — that is `engine.traffic` (MOD-023, this sprint's sibling item); `engine.traffic` reads this package's road-identity/capacity data on its own initiative, `engine.roads` never calls into `engine.traffic`.
- The road inspector's UI presentation, and the composition of this package's identity data with `engine.traffic`'s live data into a single inspector view — that's a consuming layer (a later F-screen or `ui.screen.map` overlay), not this item.
- Civic-building, infrastructure, district, and transit *placement/construction* mechanics — those belong to `engine.build`, `engine.services`, `engine.rail`, etc.; this item only provides the naming-registry service those modules call once they've decided what to build.
- Notable-deceased-citizen naming for civic buildings (which deceased citizen is "notable enough") — RATIFIED (ASM-1452) as future work tracked as **FEAT-213**, out of scope for this item; the shipped civic-building name is the toponym+type fallback. - Tunnels/TBM boring mechanics (§53, `MOD-065`, unscheduled future) — an in-place upgrade to a tunnel-requiring class is out of this item's scope until that module lands.
