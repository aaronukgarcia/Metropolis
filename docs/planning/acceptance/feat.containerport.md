## User stories

- **US-1.** As the player, I need the deep-sea terminal to be a **distinct tier above** `container_terminal` (and `cargo_port_small`), upgrading §9's port milestone to "genuine deep-sea container terminal", so it is a real capacity step — not a renamed `container_terminal` (§8).
- **US-2.** As `engine.freight` (MOD-047), I need the deep-sea terminal's capacity to be expressed as **berths × crane rate × hours** — the same model `engine.freight.md` AC-2 owns — extended to deep-sea scale (40 kt container ships), so the tier reads through `FreightAPI` rather than reimplementing a parallel port model.
- **US-3.** As `engine.rail` (MOD-060), I need the **intermodal rail transfer** (the container crane's sea↔rail↔road handoff) to conserve tonnes across the transfer point, per §47 and §33's invariant, so a container moved from ship to rail to road is counted once, not three times.
- **US-4.** As customs (§28), I need **customs throughput separate** from berth/crane physical throughput, with a **smuggling risk that rises when customs is saturated**, so a deep-sea terminal at capacity is a smuggling exposure, not a free upgrade.
- **US-5.** As the player watching the balance-of-trade screen (F5), I need the **importer→exporter flip** to be a real state transition read off independently-sourced import and export totals, so "the port flips the city" is a verifiable arc, not narration.
- **US-6.** As `feat.facilitypermits`/`feat.decommission` (FEAT-053/FEAT-054), I need the deep-sea terminal to be **permit-gated** and carry a **day-one decommission liability**, inherited through those features rather than reimplemented.

## Scope

The deep-sea container terminal as a tier above `container_terminal`: berths × crane rate × hours capacity expressed through `engine.freight`'s `FreightAPI`; the 40 kt deep-sea ship modal reach; the intermodal rail transfer point conserving tonnes sea↔rail↔road via `engine.rail`; customs throughput separate from physical throughput with saturation-linked smuggling risk (reusing `engine.freight.md` AC-3's customs model); the importer→exporter flip surfaced as an independently-sourced balance-of-trade transition; permit + decommission inheritance via `feat.facilitypermits`/`feat.decommission`. No `engine.freight` port/chain/mass-conservation machinery (extended, not reimplemented), no `engine.rail` intermodal machinery (consumed), no customs/smuggling model (reused), no permit/decommission mechanics (inherited), and no final figure magnitudes (Aaron's balance pass).

## Acceptance criteria

### Functional — the deep-sea tier and its capacity model

- **AC-1 (GR#20; shared-package surface, feature-shape per ASM-675).** A deep-sea-terminal surface exists on the shared `internal/engine/freight` package (a tier/config type set, not a fork), distinct from `engine.freight.md` AC-1's `FreightAPI` port/chain/customs surface, and consuming `FreightAPI` and `RailAPI` via direct calls rather than reimplementing either. Check: `go doc ./internal/engine/freight` shows a deep-sea-terminal accessor distinct from `FreightAPI`'s; `internal/engine/freight/doc.go` (or the tier file's package doc) notes the shared-package, no-separate-inbound-contract arrangement (`grep -n "feat.containerport" internal/engine/freight/doc.go`), mirroring `feat.megafacilities.md` AC-1's convention.
- **AC-2 (§8 "genuine deep-sea terminal tier" — a rung ABOVE `container_terminal`, upgrade not replace).** The deep-sea terminal is a distinct tier that sits **above** `container_terminal` and `cargo_port_small` in the port ladder, and its capacity effect is expressed by extending `engine.freight`'s berths × crane rate × hours model to deep-sea scale (40 kt container ships) — it does not replace or fork the existing port entries. Check: `grep -rn "freight\.\|FreightAPI" internal/engine/freight/containerport*.go` (excluding `_test.go`) shows the tier calling into `engine.freight`'s capacity surface, and `grep -rn "berth\|craneRate\|tonnes" internal/engine/freight/containerport*.go` (excluding `_test.go`) finds no local reimplementation of the port-capacity model; a passing test loads the catalogue and asserts `cargo_port_small`, `container_terminal`, and the deep-sea tier all resolve with the tier sorting strictly above `container_terminal` in milestone/cost (`grep -rn "func Test.*[Pp]ortTier.*[Ll]adder\|func Test.*[Dd]eepSea.*[Tt]ier" internal/engine/freight/*_test.go`). **False-pass risk:** a renamed `container_terminal` entry with the same capacity function would pass a "deep-sea terminal exists" grep while §8's "genuine deep-sea tier" is unmet — the check requires the tier to sort above and to change the capacity model's scale, not just its label.
- **AC-3 (GR#15; berths/crane-rate/hours/deep-sea tonnage are data-driven).** The deep-sea terminal's berth count, crane rate, operating hours, and the 40 kt deep-sea ship modal-reach figure are loaded from `data/containerport.json`, never hardcoded Go literals, and the data file defines the deep-sea tier's figures **distinct from** (and larger than) `container_terminal`'s, so "10× bulk" / "deep-sea" is a real scale ordering. Check: a passing test mutates the deep-sea tier's crane rate in the loaded fixture and asserts the computed capacity for that tier (and only that tier) reflects the change; `grep -nE "[0-9]+" internal/engine/freight/containerport*.go` (excluding `_test.go`) finds no bare capacity-shaped numeric literals. **Balance-regime note:** magnitudes are placeholders (AC-13); this AC checks *data-driven and scale-ordered*, not any magnitude.

### Functional — intermodal rail and customs

- **AC-4 (§47/§33 intermodal tonnes conservation — GR#20 outbound contract to `engine.rail`).** The intermodal container-transfer point conserves tonnes across the sea↔rail↔road handoff by consuming `engine.rail`'s registered intermodal surface (`engine.rail.md` AC-3's tonnes-conservation contract) — total tonnes into the transfer point equal total tonnes out (accounting for any documented, queryable dwell/buffer state), and there is no containerport-local parallel transfer ledger. Check: `grep -rn "rail\.\|RailAPI" internal/engine/freight/containerport*.go` (excluding `_test.go`) shows a real call into `engine.rail`'s intermodal surface; a passing test moves a known tonnage through the transfer point and asserts tonnes-in equals tonnes-out by independently summing both (`grep -rn "func Test.*[Tt]onnesConserv\|func Test.*[Ii]ntermodal" internal/engine/freight/*_test.go`). **False-pass risk:** a transfer point that only *reports* a conservation-OK flag without summing physical tonnage would pass a shallow check while a real sea↔rail↔road leak goes unnoticed — the check requires independently summing in and out (ASM-685). **Dependency note:** `engine.rail` is `open`; its intermodal method name is owned by `engine.rail.md`, not pinned here.
- **AC-5 (§33/§28 customs throughput separate, smuggling risk when saturated — reuse, not reinvention).** The deep-sea terminal's customs throughput is tracked separately from its berth/crane physical throughput, and a smuggling-risk indicator rises as customs saturation (demand ÷ capacity) increases — reusing `engine.freight.md` AC-3's customs model for the deep-sea tier rather than a new smuggling model. The two capacities can saturate independently. Check: `go doc ./internal/engine/freight` shows the deep-sea tier's customs accessor distinct from its physical-capacity accessor; a passing test saturates customs while berths remain under capacity and asserts the smuggling-risk indicator rises while physical throughput is unaffected (`grep -rn "func Test.*[Cc]ustoms.*[Ss]eparate\|func Test.*[Ss]muggling" internal/engine/freight/*_test.go`). **Dependency note:** `engine.freight.md` AC-3 owns the customs/smuggling surface; this AC only extends it to the deep-sea tier (ASM-686).

### Functional — the importer→exporter flip

- **AC-6 (§33 "port flips the city from importer to exporter" — two independently-sourced totals).** The deep-sea terminal's effect on the balance of trade is surfaced as **independently-sourced** import and export totals (import t/day + £/day, export t/day + £/day, each read from its own source — `engine.freight.md` AC-9's `BalanceOfTrade` accessors), so the importer→exporter flip is a real transition read off two independently-tracked numbers, never one computed as the other's complement. Check: a passing test drives export departures above import arrivals and asserts the exports figure rises and crosses the imports figure, with each figure read from its own accessor and neither perturbing the other when held fixed (`grep -rn "func Test.*[Ii]mporterExporter\|func Test.*[Ff]lip" internal/engine/freight/*_test.go`). **False-pass risk:** computing `Exports = Total − Imports` would make the flip trivially readable off any drift in one input — the check requires both terms independently sourced before any net figure (the exact discipline `engine.freight.md` AC-9/AC-10 name).

### Functional — permit & decommission inheritance

- **AC-7 (GR#20; permit-gated via `feat.facilitypermits`, inherited not reimplemented).** Building the deep-sea terminal is permit-gated through `feat.facilitypermits` (FEAT-053), and carries a day-one decommission liability through `feat.decommission` (FEAT-054) — neither obligation is reimplemented as a containerport-local permit check or liability ledger. Check: `grep -n "facilitypermits\|decommission\|permit" internal/engine/freight/containerport*.go` (excluding `_test.go`) shows the build path delegating to those features' surfaces (or the doc.go stating the inheritance), and no local permit-state or liability-provision field is declared. **Dependency note:** both edges are unregistered today (ASM-687/ES-2).

### ASM-1276 — intermodal conservation test exercises a VALID rail-road handoff (amends AC-4)
`TestIntermodalTonnesConservation` was fixed via option 1 (a valid rail-road handoff) rather than option 2 (asserting below-min rejection): option 1 preserves the test's mass-conservation intent — it still asserts in == out + dwell for a VALID transfer — and mirrors `engine.rail`'s own conservation test surface. Option 2 would have kept only rail-road transfers and asserted sea-rail rejection, weakening the end-to-end valid-transfer conservation guard AC-4 exists to protect.
