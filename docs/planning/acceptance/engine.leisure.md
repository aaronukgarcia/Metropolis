## User stories

- **US-1.** As a citizen, I need my weekly discretionary-hours budget computed as `168 − work − sleep − chores − commute`, with commute sourced from `engine.traffic`'s real door-to-door figure (not a flat estimate), so an hour saved on the M20 is genuinely an hour available for leisure (§42's central coupling).
- **US-2.** As a citizen, I need my hours spent across venue categories weighted by my own personality-derived taste distribution (§5.1) and constrained by real access time (evening/weekend network load), so patronage is personality-honest, not a uniform per-capita split.
- **US-3.** As a novelty-seeking citizen, I need venues I've visited repeatedly to lose "freshness" for me specifically, so a city that never opens anything measurably bores its most dynamic residents (§42) — the mechanism `engine.attract`'s emigration path (via `engine.wellbeing`'s leisure-fit driver) ultimately depends on.
- **US-4.** As the player, I need an events calendar (festivals, food fairs, match days, concerts, Christmas market) whose events generate real crowd-transport load on `engine.traffic`, so an event is a logistics exercise, not a satisfaction-only flag flip.
- **US-5.** As `engine.tourism` (registered consumer), I need to query a citywide attraction/venue-mix signal so tourism's portfolio-score draw formula (§44) can include leisure venues as an attraction term.
- **US-6.** As `engine.wellbeing` (via the registered `engine.leisure`→`engine.wellbeing` edge), I need per-citizen leisure-fit (venue mix vs personal taste weights) pushed so the `LeisureFit` mental-health driver (§18) is sourced from a real computation, not invented inside wellbeing itself.
- **US-7.** As the player, I need an F6 "how your city spends Saturday" view backed by queryable hours-by-activity-by-district data, with unmet taste demand surfaced explicitly, so the leisure economy is legible rather than a black box.

## Scope

The per-citizen weekly discretionary-hours budget and its venue-category allocation by personality taste weights and access time; novelty decay per citizen per venue; the openings pipeline (new venues, refurbishments) as a retention mechanic; the events calendar and its crowd-transport/policing/waste-spike side effects; an unmet-taste-demand query surface; the per-citizen leisure-fit push to `engine.wellbeing`; a citywide venue-mix aggregate for `engine.tourism` and (pending BUG-058) `engine.attract`. No venue construction/zoning mechanics (that is `engine.build`/zoning), no policing/waste implementation (that is `engine.services`/`engine.refuse`), no wellbeing scoring itself.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `LeisureAPI` (or equivalent) exists matching code.json's registered pattern "venue patronage personality-weighted; unmet taste demand queryable", consumed by `engine.tourism` and `ui.screen.demo` through this interface alone. Check: `go doc ./internal/engine/leisure LeisureAPI` shows a patronage-query method taking a citizen/personality input and an unmet-demand query method; `grep -rln "leisure\.\w\+State\.\w\+ = " internal/*/ -r --include=*.go` (excluding `internal/engine/leisure` itself and `_test.go`) finds no direct field writes from another package. False-pass risk: a grep for `LeisureAPI`'s mere existence would pass even if `engine.tourism` reaches into leisure's internal venue struct directly — the check targets writes bypassing the interface.
- **AC-2 (§42 discretionary-hours budget).** The weekly budget is computed per citizen as `168 − work − sleep − chores − commute`, where `commute` is read from `engine.traffic`'s door-to-door figure (§19.3, the registered `engine.leisure`→`engine.traffic` edge) rather than a flat constant. Check: `go doc ./internal/engine/leisure` shows a discretionary-hours accessor; a passing test holds work/sleep/chores fixed, varies only the traffic-sourced commute figure between two citizens, and asserts the resulting discretionary-hours figures differ by exactly the commute delta (`grep -rn "func Test.*[Dd]iscretionaryHours\|func Test.*[Cc]ommuteCoupling" internal/engine/leisure/*_test.go`). A lazy-but-plausible violation: `168 - avgWork - avgSleep - avgChores - avgCommute` computed once citywide and applied uniformly — this check rejects it because it demands the commute term actually vary per citizen with `engine.traffic`'s own figure.
- **AC-3 (§5.1/§42 personality-weighted venue allocation).** Hours are allocated across venue categories in proportion to each citizen's own taste-weight distribution (derived from personality × education × age per §5.1), not a population-average split, and the allocation is further reduced by an access-time penalty when a venue is not reachable within available evening/weekend network capacity. Check: a passing test constructs two citizens identical except for one taste-relevant personality axis (e.g. novelty-seeking) and asserts their venue-category hour allocations differ in the direction the taste weight implies (`grep -rn "func Test.*[Tt]asteWeighted[Aa]llocation" internal/engine/leisure/*_test.go`); a second test reduces simulated access-time capacity to a venue and asserts allocated hours to that venue category strictly decrease (`grep -rn "func Test.*[Aa]ccessTime" internal/engine/leisure/*_test.go`). False-pass risk: a single aggregate "leisure hours" number that never decomposes by category would satisfy neither test's assertion shape.
- **AC-4 (§42 novelty decay).** A per-citizen, per-venue "freshness" value decreases with repeated visits, decreasing faster (or only applying) for citizens with a higher novelty-seeking personality trait, and the decayed freshness measurably reduces that citizen's future patronage probability for that venue. Check: `go doc ./internal/engine/leisure` shows a freshness/novelty accessor; a passing test simulates repeated visits by a high-novelty-seeking citizen to the same venue and asserts patronage probability strictly decreases across visits, while an otherwise-identical low-novelty-seeking citizen's probability decreases less or not at all over the same visit sequence (`grep -rn "func Test.*[Nn]oveltyDecay" internal/engine/leisure/*_test.go`). A lazy-but-plausible violation: a citywide venue "popularity" score that decays uniformly regardless of who is visiting — this check rejects it by requiring the personality-conditioned comparison between two citizens.
- **AC-5 (§42 openings pipeline as retention).** Opening a new venue, or refurbishing an existing one, resets or measurably raises the freshness value novelty-decay (AC-4) had reduced, for at least the citizens whose taste weights match the venue's category. Check: a passing test decays a venue's freshness via repeated visits, applies an "opened/refurbished" event, and asserts freshness for matching citizens is measurably higher afterward than immediately before the event (`grep -rn "func Test.*[Oo]peningsPipeline\|func Test.*[Rr]efurbish" internal/engine/leisure/*_test.go`).
- **AC-6 (§42 events calendar — real logistics, not a flag).** A scheduled event (festival, food fair, match day, concert, Christmas market) generates a crowd-transport demand pushed through the registered `engine.leisure`→`engine.traffic` edge — a real trip-generation load, not merely a satisfaction/vitality number computed in isolation. Check: `go doc ./internal/engine/leisure` shows an event-scheduling accessor; a passing test schedules an event and asserts a call into the `engine.traffic` interface (via a fake/stub satisfying the traffic contract) receives a trip-demand figure greater than the no-event baseline for the same district/day (`grep -rn "func Test.*[Ee]ventCrowdTransport\|func Test.*[Ee]ventTripGeneration" internal/engine/leisure/*_test.go`). A lazy-but-plausible violation: an event that only sets `satisfaction += X` with no traffic call — this check rejects it by requiring the traffic-interface call to actually happen and carry a non-zero trip figure.
- **AC-7 (§42/US-7 unmet taste demand).** A queryable unmet-taste-demand signal exists, decomposed at least by taste/venue category (not a single blended shortfall number), so F6 "tells you literally what to build next" per §42's own phrase. Check: `go doc ./internal/engine/leisure` shows an unmet-demand accessor whose return type carries per-category fields; a passing test removes all venues of one category from a fixture city and asserts that category's unmet-demand figure rises while at least one other, unaffected category's figure does not (`grep -rn "func Test.*[Uu]nmetTasteDemand" internal/engine/leisure/*_test.go`). False-pass risk: a grep for the accessor's name alone would pass on a stub returning a constant — the check requires the figure to respond to a real removed-venue scenario.
- **AC-8 (§9/§42 seasonal leisure mix — STILL BLOCKED after c36778b; BUG-100 tripwire applied; see BUG-058 finding #1).** Venue-category demand shifts seasonally (outdoor/beach categories peak in summer months, indoor categories peak in winter) sourced from `engine.season`'s `LeisureMix` curve (`engine.season.md` AC-8) via a live `engine.leisure`→`engine.season` call — never a duplicated August/summer constant inside this package (GR#3/GR#15). **This AC is blocked**: code.json still registers no `engine.leisure`→`engine.season` edge (c36778b registered `engine.build`/`engine.wellbeing`→`engine.season`, not `engine.leisure`). Until the edge lands, this behaviour MUST NOT be implemented via a hardcoded or duplicated seasonal curve — see AC-13. **Tripwire (mechanical — BUG-100):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.leisure'); process.exit(m.outbound.calls.some(c=>c.key==='engine.season')?1:0)"` must exit **0** (edge still absent); a nonzero exit means the edge landed and this AC must be re-armed. Until the tripwire fires: Check (once unblocked): `grep -n "engine/season" internal/engine/leisure/*.go` (excluding `_test.go`) finds a real import; a passing test mutates `data/seasonal.json`'s leisure-mix curve fixture and asserts `engine.leisure`'s seasonal venue-mix output changes accordingly (mirrors `engine.season.md` AC-10's mutation-test method) — a static-value fake would fail this because the mutation would have no effect.
- **AC-9 (§11 citywide leisureFit aggregate for engine.attract).** A citywide (or per-district) leisureFit aggregate — venue mix vs. a configurable would-be-migrant personality distribution, distinct from AC-3's per-resident-citizen allocation — is queryable, matching §11's literal term definition `w₅·leisureFit(venue mix vs would-be migrant personality distribution)`. Per `engine.attract.md` AC-3, this value is currently PUSHED into `AttractAPI.TermInputs` by a caller (no `engine.attract`→`engine.leisure` edge is registered — the already-known BUG-058 gap), so this AC only requires the aggregate be computable and queryable from `LeisureAPI`, not that `engine.attract` calls it directly. Check: `go doc ./internal/engine/leisure` shows a distinct accessor from AC-3's per-citizen allocation, taking a personality-distribution parameter (not a specific citizen ID); a passing test supplies two different migrant personality distributions and asserts the returned leisureFit value differs (`grep -rn "func Test.*[Ll]eisureFit[Aa]ggregate\|func Test.*[Mm]igrantLeisureFit" internal/engine/leisure/*_test.go`).
- **AC-10 (§18/US-6 per-citizen leisure-fit push to wellbeing).** Per-citizen leisure-fit (venue mix vs that citizen's own taste weights) is pushed through the registered `engine.leisure`→`engine.wellbeing` edge, matching the `LeisureFit` driver name `engine.wellbeing.md` AC-1 requires as an independently-queryable, exported field. Check: `grep -n "engine/wellbeing" internal/engine/leisure/*.go` (excluding `_test.go`) finds a real import/call; a passing test asserts a citizen with zero matching venues in range produces a lower pushed leisure-fit value than an otherwise-identical citizen with several matching venues (`grep -rn "func Test.*[Ll]eisureFitPush" internal/engine/leisure/*_test.go`).

### Error handling

- **AC-11 (GR#7).** Querying patronage/unmet-demand/leisureFit for a citizen ID or district that does not exist returns a registry-sourced error (new `MET-E`-range code claimed at build time, per the README's Sprint-1 convention — no `engine.leisure` sub-range pre-exists in `data/errors.json`'s reserved table, correctly left open rather than invented), never a panic or a silently-returned zero value. Check: `grep -n "MET-" internal/engine/leisure/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownCitizen\|func Test.*[Ii]nvalidDistrict" internal/engine/leisure/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value patronage/unmet-demand/leisureFit record was returned, not merely that a matching-named test function exists.
- **AC-12 (GR#7).** Scheduling an event with a malformed or missing date/venue reference produces a registry-sourced error at schedule time, never a silently-dropped event that would leave a satisfaction/tourism payoff promised in the UI but never actually generated. Check: `grep -n "MET-" internal/engine/leisure/*.go` finds a load/schedule-time code distinct from AC-11's query-time code; passing test coverage (`grep -rn "func Test.*[Mm]alformedEvent" internal/engine/leisure/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no event was silently dropped/created with a missing date or venue, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-13 (GR#20 outbound contract discipline — the BUG-058 guard rail).** Until the `engine.leisure`→`engine.season` edge is registered (AC-8), `internal/engine/leisure/*.go` imports no `engine.season` package at all — proving the seasonal-mix gap is not silently closed by an unregistered direct import, which would be a GR#20 violation disguised as a working feature. Check: `grep -rln "\"Metropolis/internal/engine/season\"" internal/engine/leisure/*.go` (excluding `_test.go`) finds **no match** while BUG-058 finding #1 remains open; once the edge lands, this AC is superseded by AC-8's live-call check.
- **AC-14 (GR#21).** All patronage, novelty-decay, and unmet-demand computations are deterministic functions of citizen records, venue state, and the loaded events calendar plus `hash(worldSeed, citizenID, month, purpose)` for any stochastic patronage draw (per §5.2's determinism rule) — never `math/rand` unseeded, never wall-clock. Check: a passing determinism test runs the same fixture twice with the same seed and asserts byte-identical patronage/decay output (`grep -rn "func Test.*[Dd]eterminis" internal/engine/leisure/*_test.go`); `grep -rn "time.Now\|time.Since" internal/engine/leisure/*.go` (excluding `_test.go`) returns no matches.
- **AC-15.** `go test ./internal/engine/leisure/... -race -count=1` passes with no data race when `LeisureAPI` is queried concurrently by `engine.tourism` and `ui.screen.demo` simultaneously. Check: `grep -n "go func()" internal/engine/leisure/*_test.go` finds at least one concurrency test.

## Out of scope

- Venue construction, zoning, and catalogue mechanics (which venue types exist, their build cost/tier) — that is `engine.build`/zoning's job; this item only consumes venue existence/category/capacity as an input.
- Actual policing and waste-collection response to an event's crowd-transport/policing/waste-spike side effects (§42) — this item's job (AC-6) is to generate the demand signal; `engine.services`/`engine.refuse` consuming it is out of scope pending BUG-058 finding #13 (no registered edge exists for either today).
- `engine.wellbeing`'s own scoring of the pushed `LeisureFit` driver into the mental-health composite — that is `engine.wellbeing.md`'s job; this item only computes and pushes the value (AC-10).
- `engine.attract`'s consumption of the leisureFit aggregate (AC-9) — `engine.attract.md` AC-3 already documents the pushed-input workaround; this item only exposes the value.
- Exact venue-capacity, novelty-decay-rate, and event-frequency magnitudes — placeholder v1 defaults pending M2 Batch tuning (ASM-314).

## Escalations

- **BUG-058 finding #1 (blocks AC-8).** No `engine.leisure`→`engine.season` edge is registered in code.json, despite §9's "leisure mix" curve and `engine.season.md`'s own US-5 naming leisure-adjacent modules as intended consumers. Filed as a comment on BUG-058 2026-08-11. Recommend the same resolution Bill already accepted for the `engine.build`→`engine.season` case (BUG-058 comment, 2026-08-11): `engine.season` is already built and delivered (Sprint 3, Tester PASS), `SeasonAPI` is a stateless pure query, so wiring the edge carries no reverse-dependency risk. AC-8 is written to require the LIVE call once wired, not a behavioural-only "summer differs from winter" check, for the same reason BA-S6a gave: a behavioural-only check would pass a duplicated-and-drifted curve just as happily as a correctly-wired one.
- **BUG-058 findings #13 (medium confidence, not blocking).** §42's events calendar names policing and waste-spike effects with no registered `engine.leisure`→`engine.services`/`engine.refuse` edge in either direction; AC-6 only requires the crowd-transport half (which IS registered, via `engine.traffic`) to be real. The policing/waste half is left as a documented gap, not implemented as a fake call.
- **ASM-314/ASM-315 (logged).** Venue-capacity/novelty-decay/event-frequency magnitudes and the unmet-taste-demand query shape are BA judgment calls pending Aaron's balance/UX input — see the assumption records for the specific "what breaks if wrong" statement.
- **For Bill.** AC-9's citywide leisureFit aggregate and AC-3's per-citizen allocation are deliberately two different accessors (city-vs-migrant-distribution vs individual-citizen-vs-own-taste) because §11 and §18 define genuinely different things that happen to share a name ("leisure-fit"). If a future pass wants to collapse them into one query with two call shapes, that is an interface change touching both `engine.wellbeing.md` AC-1's driver name and `engine.attract.md` AC-3's `TermInputs.LeisureFit` field — flagging so it is a deliberate decision, not a drift.
- **ASM-1084 (confirm-and-close).** accessFactor non-finite (NaN/Inf) fallback = 0 (full block), never 1 (free) — a poisoned access-time input never silently grants free access.

- **ASM-1062 (confirm-and-close).** `engine.leisure` consumes the unbuilt `engine.traffic`/`engine.wellbeing` via local contract shapes (`TrafficAPI`/`WellbeingAPI` seams wired by the composition root), mirroring `engine.education`'s unbuilt traffic edge.
- **ASM-1065 (confirm-and-close).** engine.leisure claims ten registry codes **MET-G2100 through MET-G2109** under BUG-234's code-format widening; range added to `data/errors.json` reserved table and codes, verified against `grep MET-G21` and the errs source-scan test.
