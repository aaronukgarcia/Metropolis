# Acceptance criteria — engine.wellbeing (MOD-034)

**BOW code:** MOD-034
**Spec refs:** §18 Wellbeing — Physical & Mental Health (`docs/METROPOLIS-MASTER-v2.1.md` lines 326-332: two 0-100 per-citizen tracks, physical drivers — age curve, healthcare access/quality/queue time, diet/fresh-food share, active travel, pollution exposure, sport×physicality — mental drivers — commute time nonlinear past 45min, job-ambition mismatch, green space within 400m, leisure-fit, crowding, isolation = sociability×community access, noise, financial stress = rent>35%, unemployment duration — "Wellbeing = f(physical, mental, satisfaction) is the headline city stat", downstream effects mortality/productivity/satisfaction/emigration); §42 Leisure Time & Exploration (lines 575-577: leisure-fit vs personal taste weights §5.1, discretionary-hours budget 168−work−sleep−chores−commute, the commute-transport-policy-is-leisure-policy coupling); §5.1 citizen record (personality axes incl. sociability, derived leisure taste weights, satisfaction components: housing/services/environment/leisure-fit/commute — `engine.citizens.md` AC-1); §19.3 commute accounting (door-to-door time "fed to mental health (§18)"); §9 Seasonality (`engine.season.md` US-6: "As `engine.wellbeing`, I need a minor winter health-wave modifier"; `HealthWaveModifier` already built/registered in `engine.season`); code.json `engine.wellbeing` entry — inbound `WellbeingAPI`, pattern **"driver-decomposed scores; every driver drill-through"** (this pattern string is the causal-attribution contract, not incidental wording), outbound calls to `engine.citizens`/`engine.traffic`/`engine.services`/`engine.consumption`/`engine.season`/`engine.shopping`/`engine.world`, inbound consumed by `engine.cafe`/`engine.crime`/`engine.leisure`/`engine.mining`/`engine.refuse`/`engine.shopping`/`engine.social`.

## User stories

- **US-1.** As `engine.crime`, `engine.mining` (blight coupling), and `engine.social`, I need a physical/mental wellbeing score per citizen or district that responds to real, nameable causes, so downstream systems (deprivation-driven crime generation, social-services caseload) can trust the number reflects something real, not a display-only stat.
- **US-2.** As a player debugging a declining district (the Slow-Fuse design — consequences arrive long after their cause), I need to ask "why did wellbeing fall here" and get a named driver back, not just a lower number, because by the time the effect is visible the cause may be years gone and unreconstructable from memory alone.
- **US-3.** As `engine.leisure`, `engine.cafe`, and `engine.shopping`, I need to query a citizen's or district's current wellbeing to gate/weight their own behaviour (venue participation, café-culture vitality inputs, shopping-trip generation), via the registered `WellbeingAPI` inbound edge.
- **US-4.** As `engine.season` (already built, `HealthWaveModifier`), I need `engine.wellbeing` to consume my registered winter health-wave curve rather than reimplement a second seasonal-health effect, per GR#3/GR#15.
- **US-5.** As `engine.citizens` (already built), I need `engine.wellbeing` to source its per-citizen inputs (personality, leisure taste weights, satisfaction components, employment state) through the registered `CitizensAPI` only, never a direct struct reach-in, per GR#20.
- **US-6.** As the 100M-citizen adaptive-fidelity constraint (§5.2/§5.3), I need attribution data to cost nothing extra on the fixed per-citizen byte budget (`engine.citizens.md` AC-1/AC-5: ~250B hot, 60-100B cold, no headroom for 15 driver-delta floats per citizen), so causal attribution is a CPU-time feature, not a memory-budget-breaking one.
- **US-7.** As the mortality/productivity/satisfaction/emigration systems named in §18's last sentence, I need each of those four downstream effects exposed as an independently queryable function of the current tracks.

## Scope

Two per-citizen 0-100 tracks (physical, mental) with driver-decomposed, drill-through-capable causal attribution; the headline `Wellbeing = f(physical, mental, satisfaction)` composite; the four documented downstream effect modifiers (mortality, productivity, satisfaction, emigration); consumption of `engine.season`'s `HealthWaveModifier`, `engine.citizens`' per-citizen inputs, `engine.traffic`'s commute time, and `engine.services`' healthcare access.

## Acceptance criteria

### Functional — causal attribution architecture (the core of this module)

- **AC-1 (GR#20 inbound contract; code.json's "driver-decomposed scores; every driver drill-through" pattern).** `WellbeingAPI` exposes, for both the physical and mental tracks, a queryable attribution result whose EXPORTED type names every documented driver individually — 6 physical (`AgeCurve`, `HealthcareAccess`, `Diet`, `ActiveTravel`, `PollutionExposure`, `SportParticipation`) and 9 mental (`CommuteTime`, `JobAmbitionMismatch`, `GreenSpace400m`, `LeisureFit`, `Crowding`, `Isolation`, `Noise`, `FinancialStress`, `UnemploymentDuration`) — not a single blended score. **Binding:** the driver names must appear as fields/map-keys on the type `go doc` prints for the public attribution result; **illustrative:** the exact type/method names (`PhysicalAttribution`/`Attribute`/etc. are examples). Check: `go doc ./internal/engine/wellbeing` shows an exported attribution type; all 15 driver-name tokens above appear in that type's documented fields or in a driver-name constant/enum it references. **False-pass warning:** a plain `grep` for the 15 tokens alone would pass on internal variable names that never reach the exported API — the check must confirm the tokens are reachable from the type `go doc` prints, not merely present anywhere in the file.
- **AC-2 (additive identity).** For every attribution query, `Total == Baseline + Σ(driver.Delta)` exactly (or to a documented, tested epsilon if floating-point — state which). Check: a passing test sums returned per-driver deltas plus baseline and asserts equality with the returned total (`grep -rn "func Test.*[Aa]ttributionSum\|func Test.*[Dd]ecompositionIdentity" internal/engine/wellbeing/*_test.go`). **Note:** this identity alone is insufficient proof of real causality — any allocation scheme, including a fabricated post-hoc proportional split of a single blended score, can be constructed to sum correctly. AC-3 is the check that actually distinguishes real attribution from a fabricated one; both are required together.
- **AC-3 (isolation — the check that makes causality checkable).** Perturbing exactly ONE driver's input (e.g. raising door-to-door commute time from 30 to 60 minutes) while holding every other driver's inputs fixed changes ONLY that driver's named `Delta` in the returned attribution — every other driver's `Delta` is byte-identical before and after — and `Total`'s change equals exactly the perturbed driver's `Delta` change. Check: a passing test computes attribution twice for the same citizen/context differing in exactly one driver's input, and asserts (a) all non-perturbed drivers' deltas are unchanged, (b) the perturbed driver's delta moved, (c) the total's change equals the perturbed delta's change (`grep -rn "func Test.*[Ii]solat|func Test.*[Ss]ingleDriverPerturb" internal/engine/wellbeing/*_test.go`). **This is the check a lazy-but-plausible implementation fails:** a weighted-blend-with-post-hoc-attribution (compute one total, then split it proportionally across named "driver" labels for display) satisfies AC-1's names and AC-2's sum identity, but changing one input changes the *total*, and a proportional split redistributes that change across every named component — so every driver's reported delta moves, not just the perturbed one, and this AC catches it.

### Functional — driver behaviour

- **AC-4 (§18 nonlinear commute penalty).** `CommuteTime`'s mental-track delta is nonlinear past 45 minutes door-to-door: the marginal |Δdelta| per additional minute above 45 min exceeds the marginal |Δdelta| per minute below 45 min, and for a citizen whose only elevated driver is commute time, `CommuteTime` is the largest-magnitude single mental driver delta at 70 min. Check: a passing test computes deltas at 20/45/70 min and asserts both the steepening and the largest-magnitude claim (`grep -rn "func Test.*[Cc]ommute.*[Nn]onlinear\|func Test.*[Cc]ommute.*[Bb]iggest" internal/engine/wellbeing/*_test.go`).
- **AC-5 (§18 physical driver directions).** `HealthcareAccess`/`ActiveTravel`/`SportParticipation`/`Diet` deltas are non-negative as their respective input (coverage, active-travel mode share, venue-access×physicality, fresh-food share) increases; `PollutionExposure`'s delta is non-positive as exposure increases. Check: a passing test per driver sweeps its input and asserts the documented monotonic direction (`grep -rn "func Test.*(AgeCurve|HealthcareAccess|Diet|ActiveTravel|PollutionExposure|SportParticipation)" internal/engine/wellbeing/*_test.go`).
- **AC-6 (§18 mental driver directions and the financial-stress threshold).** `Crowding` worsens monotonically with persons/room; `UnemploymentDuration` worsens monotonically with duration (not a single employed/unemployed boolean); `FinancialStress` is a **threshold** effect activating once rent burden exceeds 35% (§18), not a smooth penalty starting at £0 of rent. Check: a passing test asserts `FinancialStress`'s delta is ~zero below 35% rent burden and materially nonzero at/above it (`grep -rn "func Test.*[Ff]inancialStress.*35\|func Test.*[Rr]entBurden" internal/engine/wellbeing/*_test.go`); crowding/unemployment-duration monotonicity tests exist (`grep -rn "func Test.*(Crowding|UnemploymentDuration)"`).
- **AC-7 (§18 isolation is a product of two factors, not one).** `Isolation`'s delta responds to BOTH the citizen's sociability personality axis AND community-venue access — neither alone determines it (§18: "isolation (sociability trait × community venue access)"). Check: a passing test holds sociability fixed and varies community access (delta changes), then holds community access fixed and varies sociability (delta also changes) — proving both terms are load-bearing rather than one silently driving a two-factor-named driver (`grep -rn "func Test.*[Ii]solation.*[Ss]ociab" internal/engine/wellbeing/*_test.go`).
- **AC-8 (§18 headline composite).** `Wellbeing = f(physical, mental, satisfaction)` is exposed as its own queryable value, a documented function of the two tracks plus a satisfaction input (`engine.citizens`' satisfaction components), distinct from either sub-track alone. Check: `go doc` shows a headline function taking physical+mental+satisfaction; a passing test asserts the headline changes when either sub-track changes with the others held fixed (`grep -rn "func Test.*[Hh]eadline\|func Test.*[Ww]ellbeingScore" internal/engine/wellbeing/*_test.go`).
- **AC-9 (§18 downstream effects).** Four documented downstream effects — mortality-hazard modifier, productivity modifier, satisfaction modifier, emigration-probability modifier — are each independently queryable as a function of the current tracks, each moving in the spec-consistent direction as its source track worsens (mortality/emigration risk up, productivity/satisfaction down). Check: `go doc` shows four named accessors; passing tests assert each direction (`grep -rn "func Test.*[Mm]ortalityModifier\|func Test.*[Pp]roductivityModifier\|func Test.*[Ee]migrationModifier\|func Test.*[Ss]atisfactionModifier" internal/engine/wellbeing/*_test.go`).

### Error handling

- **AC-13 (GR#7).** Constructing an attribution query with an out-of-domain input (negative commute time, a personality axis outside 0-100, negative rent burden) returns a registry-sourced error (new `MET-E`-range code, claimed against `data/errors.json`'s reserved table at build time — no `engine.wellbeing` sub-range exists yet) rather than a silently clamped value folded into the total. Check: `grep -n "MET-" internal/engine/wellbeing/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalid.*[Dd]river\|func Test.*[Oo]utOfRange" internal/engine/wellbeing/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no clamped out-of-domain value was silently folded into the wellbeing total, not merely that a matching-named test function exists.
- **AC-14.** Missing/unavailable upstream data for one driver (e.g. a district with no `engine.services` coverage record yet) degrades that driver to a documented fallback (neutral delta + a low-confidence flag on the attribution result) rather than propagating `NaN`/a divide-by-zero into `Total`. Check: passing test coverage (`grep -rn "func Test.*[Mm]issingUpstream\|func Test.*[Ll]owConfidence" internal/engine/wellbeing/*_test.go`).

### Determinism, safety & scale

- **AC-15 (GR#21).** Attribution is a deterministic function of `(worldSeed, citizen id, month, driver inputs)` — repeated calls with identical inputs return byte-identical `TrackAttribution` results. Check: `grep -rn "func Test.*[Dd]eterminis" internal/engine/wellbeing/*_test.go`.
- **AC-16 (SG-7; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/wellbeing/*.go` (excluding `_test.go`) returns no matches.
- **AC-17.** `go test ./internal/engine/wellbeing/... -race -count=1` passes; `grep -n "go func()" internal/engine/wellbeing/*_test.go` finds at least one concurrency test.
- **AC-18 (100M-scale memory decision — mandatory, per adaptive fidelity).** Per-driver `TrackAttribution` is NOT a permanently stored field on the citizen hot or cold record — `engine.citizens.md`'s AC-1/AC-5 fix the hot record at ~250B and the cold shard at 60-100B/citizen with no accounted headroom for 15 driver-delta floats per citizen (≈60-120 bytes at float32, per citizen, at 100M citizens ⇒ 6-12GB extra just for attribution if stored durably). Attribution is instead reconstructed **on demand**: live for HOT citizens (full daily driver recompute is already available), and for WARM/COLD citizens via the same deterministic reconstruct-on-inspect pattern `engine.citizens`' life-writing already contracts (`engine.citizens.md` AC-10: `hash(worldSeed, id, month)`-bound reconstruction) — never a durable per-citizen attribution history. Check: `grep -n "DriverContribution\|TrackAttribution" internal/engine/citizens/*.go` (excluding `_test.go`) finds NO occurrence — attribution types live only in `internal/engine/wellbeing/`; a passing test reconstructs a COLD citizen's attribution twice at the same month and asserts identical output with no stored intermediate carried between calls (`grep -rn "func Test.*[Rr]econstructAttribution" internal/engine/wellbeing/*_test.go`).

## Out of scope

- The mortality hazard curve's own Gompertz-Makeham mechanics, healthcare capacity/funding computation, the seasonal curve's own values, the grocery-access score computation, and the pollution overlay computation — this item only *consumes* those via their owning modules' interfaces (or a flagged placeholder per AC-12); it does not build them.
- District-level (cold, distributional) attribution aggregation beyond the per-citizen reconstruction path — if a district-level rollup view is needed for F-series UI, that is a later/separate item.
- Tuned driver weights and the exact functional shape of `f(physical, mental, satisfaction)` beyond "documented, not ad hoc, and each input independently movable" — the specific weighting is a balance number pending M2 tuning (see Escalations).
