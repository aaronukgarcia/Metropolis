# Acceptance criteria — RenderLoop's atomic.Bool ownership gate survives struct copy (BUG-018)

**BOW code:** BUG-018 (P2, open)
**Spec refs:** the SEC-020 class (copyable structs with aliased/independent-but-conflicting state — this is explicitly a **different mechanism** than SEC-020's lock/referent-aliasing shape, per the item's own careful note, so kept as its own fix rather than folded in); Weakness pattern #1.
**Date:** 2026-08-10
**Status:** active
**Package under test:** `internal/ui/core/` (`render.go:60`, `RenderLoop`).
**Standard gates:** see `README.md`, package `./internal/ui/core/...`, `-race` required given the concurrency nature of the defect.

## Acceptance criteria

### Functional

- **AC-1 (Pattern #1 — the invariant "at most one owner" cannot be broken through the public API, including by copying).** `RenderLoop`'s screen-ownership gate uses the same atomic-self-identity pattern already established for `Engine` and `SubscriptionServer` in the SEC-014/SEC-016/SEC-020 fix chain (an `atomic.Pointer` to the owning instance, checked before any ownership-claiming action, per `dev-team-process.md`'s own description of that pattern) rather than a bare `atomic.Bool` a copy trivially gets its own independent instance of. Check: `grep -n "atomic.Pointer\|checkNotCopied\|self" internal/ui/core/render.go` shows the pattern applied to `RenderLoop`, matching the shape already reviewed and accepted for `Engine`/`SubscriptionServer`.
- **AC-2 (the regression test — deterministic, not probable, per the process rule added this same day).** A passing test constructs a `RenderLoop`, takes a **value copy** of it, and asserts that attempting to claim screen ownership on the copy fails with a clear, checkable error (or is otherwise structurally prevented) while the original's ownership is unaffected — **constructed to completion and then asserted**, not raced for timing (per `dev-team-process.md`'s "concurrency tests must be deterministic, not probable" rule, added the same day as this finding). Check: `go test ./internal/ui/core/... -run TestRenderLoop_CopyCannotClaimOwnership -race -count=1 -v` passes, and the test's own structure is a single-goroutine construct-then-assert, not a hammer racing for a window.

### Error handling

- **AC-3.** The rejected copy's attempted ownership claim returns a registry-sourced error carrying a distinct `MET-U`/`MET-E`-range code (the same `errs.New(ErrXCopied, ...)` shape `Engine`'s/`SubscriptionServer`'s own `checkNotCopied` already return — e.g. `ErrEngineCopied = "MET-E012"`) rather than silently no-op'ing or panicking, and no screen-ownership state is mutated as a side effect of the rejected attempt (the copy's own ownership flag/pointer stays exactly as constructed, and — critically — the **original** `RenderLoop`'s ownership is unaffected). Check: `go test ./internal/ui/core/... -run TestRenderLoop_CopyCannotClaimOwnership -race -count=1 -v` — the test asserts `errors.Is(err, &errs.E{Code: ErrRenderLoopCopied})` (not merely `err != nil`) on the copy's claim attempt, and asserts the original's ownership-holding field is still the original's own pointer/state after the copy's rejected attempt, not overwritten or cleared.

### Documentation

- **AC-4.** `RenderLoop`'s doc comment states the copy-safety invariant and cites this fix, in the same style as `Engine`'s own doc comment does for its equivalent guard (Tester compares the two doc comments for consistency of framing, not identical wording).

## Out of scope

- Any change to `RenderLoop`'s actual rendering/diff logic — this item is scoped to the ownership-gate mechanism only.

## Escalations

- None — the fix pattern to follow is explicitly named in the BOW item's own "Definition of done" ("the same atomic self-identity pattern used for Engine and SubscriptionServer is the obvious candidate"), leaving no open design question for a BA to rule on.
