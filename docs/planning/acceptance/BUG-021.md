## Acceptance criteria

### Functional

- **AC-1 (the actual fix — mechanical, not remembered, per GR#17).** `main` has a required-status-checks branch protection rule configured (via `gh api repos/:owner/:repo/branches/main/protection` or the GitHub UI) requiring at least the CI workflow's jobs (the ones that caught `TestSEC003_ConcurrentRegisterDuringAdvanceTicks`'s scheduling dependency and the `staticcheck SA4006` finding) to pass before a PR can merge, and — per the project's current direct-push-to-main workflow, if that has not changed — at minimum a required status check that blocks a push from being considered "landed" without a green run. Check: `gh api repos/aaronukgarcia/Metropolis/branches/main/protection` (or equivalent) returns a policy naming the CI workflow's required checks, run by the Tester/Bill directly against the live repository, not inferred from a config file (branch protection is a GitHub setting, not a repo file — there is nothing to `grep` for).
- **AC-2 (Pattern #1 — this closes BUG-006's open half specifically because a human-remembered check already failed once, per BUG-021's own history).** The criterion is explicitly that the control **cannot be skipped by a human forgetting to look** — "run `gh run list` and eyeball it" is documented as the interim control precisely because it failed (this bug's own root cause). AC-1's branch-protection rule is what makes the invariant "main is never red" enforced by the platform rather than asserted in a process doc. A passing verification: attempt (in a scratch/test scenario, or by inspecting the protection rule's configuration rather than actually breaking `main`) to confirm a failing-CI push would be blocked from merging/being treated as landed.
- **AC-3.** `golangci-lint run ./...` is confirmed present in the standard Tester baseline text in `docs/planning/dev-team-process.md` (already added per the build log — this AC is a **regression check**, not new work: Tester confirms it is still there and has not been quietly dropped) and additionally confirmed to be what CI itself runs as a blocking job (not a weaker or differently-configured local invocation) — check: compare the CI workflow file's golangci-lint invocation (flags, config file) against what the Tester baseline text specifies; they must match, since a mismatch here is exactly how the original gap ("everyone was running a different tool and calling it the same name") could recur in a new form.

### Documentation

- **AC-4.** `docs/planning/checkpoint.md` or `CLAUDE.md`'s hooks/skills reference notes that branch protection is now the enforcement mechanism (not "run `gh run list` after every push," which remains good practice but is no longer the *only* control), so a future session reading the standing orders understands the control has been upgraded from human-remembered to platform-enforced.
