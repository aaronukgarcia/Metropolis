# Acceptance criteria — feat.securehelpers (FEAT-135)

**mkey:** `feat.securehelpers` — the canonical surviving FEAT-135 acceptance file (FEAT-135's BOW `mkey` is NULL; this file's mkey is BA-assigned, see ASM-871). Supersedes `feat.secureprimitives.md` (ASM-924).

**BOW code:** FEAT-135 (P2, open) — "Standardize Secure-by-Default Go Helper Libraries for Input Validation and Encapsulation."
**Spec refs:** the three findings this feature generalises — SEC-066 (live-pointer leak: `ui.screen.menu` returns/stores live keymap/layout profile pointers with no defensive copy), SEC-080 (XP counter wraps int64 negative on large non-negative awards), SEC-093 (`engine.services` silently accepts NaN funding/demand/staffing because the ordered range check is false for NaN); the existing numeric-safety standard `internal/foundation/num` (GR#16 saturating helpers + `ClampInt64FromFloat`/`GuardFinite`); the existing copy-guard pattern `internal/foundation/registry` `checkNotCopied` + `self atomic.Pointer[T]` (SEC-020); `docs/planning/proposals/meta-tooling-reform.md` A1 (the "Tier A, additive, no reversal" framing); Golden Rules #7/#15/#16/#20/#21.
**Design (Bob, 2026-08-16, BOW FEAT-135 / meta-tooling-reform A1):** 95 security findings, 42 open, recur in three families — input-validation (26), concurrency-safety (17), encapsulation-leaks (13). Developers keep writing insecure code and only patching it post-hoc when the Destructive agent catches it. The fix is not more post-hoc patching; it is **secure-by-default primitives** that make the unsafe path the un-written path: (1) a centralized type-safe coercion library (`safeInt64`, bounded/NaN-checked float helpers) that *rejects* — not silently clamps — non-finite/overflowing/out-of-range inputs with a registry-sourced error; (2) a reusable copy-guard + defensive-copy wrapper in `foundation/registry` so `checkNotCopied` and "return a copy, not a live pointer" are not hand-rolled per module; (3) a mandate that every incoming junior brief and acceptance-criteria set require these primitives, so the discipline is structural, not prose.
**This file's role:** cross-cutting foundation feature. It **extends** `foundation.num` (the existing saturating helpers are the *clamp* form; this feature adds the *reject* form they were never meant to be) and **generalises** `foundation.registry` (the existing `checkNotCopied` is hand-rolled per module; this feature makes it a reusable wrapper). It **does not** retrofit the 42 open findings — it gives those findings' fixes a single sanctioned primitive to route through. It **feeds** the `/brief` skill's mandatory block and the BA acceptance-criteria template (part 3). See "Cross-check" and "Escalations" for the code.json seams.
**Date:** 2026-08-16
**Status:** draft-ahead — `foundation.registry` **is** registered in code.json (GUID `d6460761-184d-4bee-aac7-5f1408242a0c`), but `foundation.num` **is not** (verified: no `foundation.num` key exists in code.json), and the reusable copy-guard wrapper does not exist yet (the pattern is still hand-rolled in `engine.core`, `protocol/transport`, `engine/stub`, `engine/debug`, and three `ui.*` modules). Both registration gaps are escalations, not build-blockers.
**North-star vetting (v1.12, FEAT-043):** this item answers **none** of the five-question test — it is not a player-facing feature, mechanic, screen, or lever. It is foundational infrastructure (safety primitives + a process mandate) and is registered as such, per the dev-team process's "an item that answers none may still be necessary infrastructure (register it as such)" clause.
**No balance-number regime applies.** This feature defines *mechanism* (reject vs clamp; guard vs hand-roll), not *values*. There are no rates, lifetimes, or player-felt numbers to place-hold; any bound a coercion helper enforces is caller-supplied (AC-6), never a junior-invented constant. If a junior introduces a numeric bound anywhere in this work, it must be a named constant or a data-file value with a disclosure comment, exactly as the balance-number regime would demand.

## User stories

- **US-1.** As a junior developer writing a module boundary (a command handler, a Setter, a data loader), I need one sanctioned coercion call — `SafeInt64` / a bounded float helper — that **rejects** NaN, ±Inf, overflow, and out-of-range inputs with a registry-sourced error, so I cannot silently accept NaN funding (SEC-093) or wrap a counter negative (SEC-080) even if I forget the check myself.
- **US-2.** As a module author with a mutable, shared state struct, I need a reusable copy-guard wrapper I embed rather than hand-rolling the `self atomic.Pointer[T]` + `checkNotCopied` + `self.Store(x)` boilerplate every module, so the SEC-020 struct-copy attack is guarded once, centrally, and I cannot leave a lock site unguarded by omission.
- **US-3.** As a module author returning internal reference state (a keymap, a layout profile, a settings map), I need a defensive-copy helper so I return a copy, never the live pointer (SEC-066) — a caller mutating what I hand back corrupts nothing.
- **US-4.** As a BA writing junior briefs and acceptance criteria, I need the brief/AC templates to *mandate* these primitives, so "use the safe helper" is a boilerplate requirement every spec carries, not a convention a hurried junior can forget.
- **US-5.** As Bill/Aaron, I need the rule "if an invariant matters, enforce it structurally in the type system / constructor-locked immutability, never prose" recorded as a Golden Rule, so the whole feature's premise — prose-only safety mandates fail — is itself enforced at the process level, not left as a preference.

## Scope

Two additions to existing foundation packages, plus one process mandate. (1) In `foundation.num`: error-returning, registry-sourced coercion helpers — `SafeInt64` (rejects NaN/±Inf/overflow), a bounded-float helper (rejects NaN/±Inf/out-of-[lo,hi]), and `any`-typed safe-coercion variants for the stored-value boundary — coexisting with, and documented against, the existing saturating helpers. (2) In `foundation.registry`: a reusable copy-guard wrapper type (generic, embed-by-value) encapsulating identity capture, the lock-free pre-lock check, and fail-closed rejection, plus a defensive-copy helper for the return-a-copy discipline. (3) The mandate: the `/brief` skill's mandatory block and the BA acceptance-criteria template require these primitives. No retrofit of the 42 open findings, no decommissioning of existing hand-rolled guards, no errors.json re-evaluation (BUG-247), and no numeric values (no balance-number regime).

## Acceptance criteria

### Functional — type-safe coercion (`foundation.num`)

- **AC-1 (GR#20; the coercion helpers are consumed via a registered interface, not a bare import).** The coercion package is a `foundation.*` module registered in code.json with an inbound contract GUID, exactly like `foundation.registry`/`foundation.det`/`foundation.data`. The feature must not land as an unregistered import that GR#20's "modules consume each other ONLY via registered interfaces" tripwire cannot see. Check: `node -e "const m=require('./code.json').modules; process.exit(m.some(x=>x.key==='foundation.num'||x.key==='foundation.coerce')?0:1)"` exits 0; `go doc ./internal/foundation/num` (or the ruled package) shows the exported coercion API. **False-pass risk:** a junior who writes the helpers but never registers the package would pass "the helpers exist" while every GR#20/plan-drift gate stays blind to them — the check requires the code.json entry, not just the Go package. **Open sub-decision:** `foundation.num` (extend the existing package) vs `foundation.coerce` (a sibling) — see ES-3.

- **AC-2 (`SafeInt64` — reject form, GR#7; SEC-080/SEC-093's generalisation).** A `SafeInt64` (or equivalent) converts a `float64` to `int64` and **returns a registry-sourced error** on NaN, +Inf, −Inf, or any value at/outside the int64 range — it never silently clamps (the existing `ClampInt64FromFloat`'s behaviour) and never wraps. This is the boundary-validation path; `ClampInt64FromFloat` remains the saturating path for conserved arithmetic (AC-8). Check: a passing test feeds `math.NaN()`, `math.Inf(1)`, `math.Inf(-1)`, `float64(math.MaxInt64)` (which is 2^63, the wrap-to-negative case SEC-080 lives on), and an in-range value, and asserts the first four return `errors.Is(err, &errs.E{Code: <non-finite or overflow code>})` with `(0, false)`-shaped zero value, and only the in-range input returns `(v, nil)` (`grep -rn "func Test.*SafeInt64\|func Test.*Coerc.*Reject" internal/foundation/num/*_test.go`). **False-pass risk:** reusing `ClampInt64FromFloat` (which clamps NaN→0, +Inf→MaxInt64) would make the test *fail* on the NaN/Inf cases — good — but a junior who returns a bare `fmt.Errorf` would pass a naive "an error was returned" check while violating GR#7; the check requires `errors.Is` against the registry code, not merely a non-nil error.

- **AC-3 (bounded float helper — reject form, GR#7; SEC-093's exact shape).** A bounded-float helper (e.g. `BoundedFloat(v, lo, hi float64)`) rejects NaN and ±Inf **before** the ordered `lo <= v <= hi` check — the ordered check is false for NaN, which is precisely why SEC-093's `level < 0 || level > 1` let NaN through. It returns a registry-sourced error on non-finite and on out-of-range, distinct codes for the two classes. Check: a passing test asserts `BoundedFloat(NaN, 0, 1)`, `BoundedFloat(Inf, 0, 1)`, `BoundedFloat(1.1, 0, 1)`, `BoundedFloat(-0.1, 0, 1)` all error with the expected code, and `BoundedFloat(0.5, 0, 1)` returns `(0.5, nil)` (`grep -rn "func Test.*Bounded\|func Test.*Finite.*Range" internal/foundation/num/*_test.go`). **False-pass risk:** a helper that checks `lo <= v <= hi` first (and returns the out-of-range error for NaN, or worse, accepts NaN because `lo <= NaN` is false but `NaN > hi` is also false) fails SEC-093's own premise; the check requires the non-finite test to fire **first** and to return the *non-finite* code, not the range code.

- **AC-4 (GR#7; distinct registry codes, registered in `data/errors.json`).** Every coercion failure class has its **own** registry-sourced `MET-` code — at minimum a non-finite code and an overflow/out-of-range code — each registered in `data/errors.json` with real `severity`/`module`/`message`/`remedy` fields, under a reserved `foundation.num` sub-range (ASM-873: `F800-F899`, the first free foundation sub-range — current highest F code is `MET-F708`). The helpers construct errors via `errs.New`/`errs.Wrap` only, never a bare `errors.New`/`fmt.Errorf`. Check: `grep -n "MET-F8" internal/foundation/num/*.go` finds the code constants and `grep -n "MET-F8" data/errors.json` finds their registry entries; the `errs` source-scan test (`internal/foundation/errs/source_scan_test.go`) passes, which is what mechanically closes the "code used but never registered" drift class (BUG-008). **False-pass risk:** a code declared as a `const` in the package but absent from `data/errors.json` would `errs.New` into the MET-F003 "unregistered code" fallback at runtime — a grep for `MET-F8` in the `.go` file alone would miss it; the check requires the `data/errors.json` match and the source-scan test green.

- **AC-5 (GR#16; `any`-typed safe coercion for the stored-value boundary).** A variant (e.g. `SafeInt64FromAny(v any)` / `SafeFloat64FromAny(v any)`) coerces an `any`-typed value (a stored field read back from a map/JSON/fixture) and returns a registry-sourced error on a wrong type, non-finite float, or overflow — it never uses a bare `v.(int64)` type assertion that panics or mis-trusts the stored type. Check: a passing test feeds a `string`, a `float64(NaN)`, a `float64(MaxInt64+1)`, and a correct `int64`, asserting the first three error with a registry code and only the correct one succeeds (`grep -rn "func Test.*FromAny\|func Test.*Stored" internal/foundation/num/*_test.go`). **False-pass risk:** a bare two-result type assertion (`v, ok := v.(int64)`) would satisfy "wrong type is detected" for the string case while still panicking on `nil` and silently trusting a `float64` that is NaN — the check requires the non-finite/overflow path to be *coerced through* the safe helper, not a raw assertion.

- **AC-6 (GR#15; bounds are caller-supplied, never hardcoded).** No coercion helper contains a hardcoded numeric bound (a magic `0`/`1`/`1e6` threshold deciding validity) inside its body; any bound is a function parameter (`lo`, `hi`) or, where a default is genuinely required, a named constant or data-file value with a disclosure comment — never a bare literal a future reader cannot trace. Check: `grep -nE "[0-9]+" internal/foundation/num/*.go` (excluding `_test.go`) finds no bare numeric literal outside doc-comment prose and the existing `ClampInt64FromFloat`'s `2^63` boundary commentary; the bounded helper's signature takes `lo`/`hi` as parameters. **False-pass risk:** a junior who hardcodes `lo=0, hi=1` inside the bounded helper (coupling a general primitive to the funding-range case) would pass a "bounded float exists" grep while baking SEC-093's specific `[0,1]` domain into a general library — the check requires the bounds to be parameters, keeping the helper domain-agnostic.

- **AC-7 (GR#21; coercion is a pure, deterministic function).** Every coercion helper is a pure function of its inputs: no `time.Now`/`time.Since`, no `math/rand`, no map iteration, no goroutine, no mutable package state. Identical inputs produce identical outputs (and identical error codes) on every call and across worker counts. Check: `grep -rn "time.Now\|time.Since\|math/rand\|rand\." internal/foundation/num/*.go` (excluding `_test.go`) returns no matches; a determinism test calls each helper twice on the same input and asserts byte-identical results and identical error codes. Never assert a wall-clock upper bound on a helper call in CI; assert output/error equality only.

- **AC-8 (coexistence contract — the reject form is the sanctioned boundary path, the saturating form stays for conserved arithmetic).** The new rejecting helpers are documented as the **boundary-validation** path (module entry points, command handlers, data loaders — where a bad input must be rejected, per SEC-093), while the existing saturating helpers (`SatAdd`/`SatSub`/`SafeMul`/`ClampInt64FromFloat`) remain the **conserved-arithmetic** path (internal accumulation where saturation is the invariant, per `engine.finance`/`engine.build`). Neither is removed; the doc states which is which so a caller cannot pick `ClampInt64FromFloat` for a boundary that must reject. Check: `grep -n "boundary\|saturat\|reject\|clamp" internal/foundation/num/doc.go` matches the distinction; the package doc's one-liner reads "never wrap; never leak +Inf/NaN from a finite input; reject — never silently clamp — at the boundary."

### Functional — copy-guard + defensive-copy wrappers (`foundation.registry`)

- **AC-9 (GR#20; a reusable copy-guard wrapper, not a per-module hand-roll).** A reusable copy-guard wrapper type (e.g. `CopyGuard[T]`) in `foundation/registry` encapsulates the whole SEC-020 pattern a module currently hand-rolls — the `atomic.Pointer[T]`-backed identity field, the one-time identity capture at construction, and the lock-free `Check(correlationID, ctx) error` that rejects a struct copy — so a module embeds it instead of writing its own `self`/`checkNotCopied`/`self.Store(x)` triple. Check: `go doc ./internal/foundation/registry` shows the wrapper type and its `Check`/constructor methods; `grep -n "CopyGuard\|CheckNotCopied\|checkNotCopied" internal/foundation/registry/*.go` (excluding `_test.go`) shows the wrapper is defined once and the `Registry` type's own `checkNotCopied` is either migrated to it or documented as the pre-existing implementation the wrapper generalises. **False-pass risk:** a "wrapper" that is just a renamed `checkNotCopied` still hardcoded to `*Registry` (not generic, not embeddable by a fresh type) would pass a "something named CopyGuard exists" grep while every other module keeps hand-rolling — the check requires the wrapper to be *generic over the guarded type* and embeddable by value.

- **AC-10 (drop-in completeness — a fresh type gets the full guard by embedding, nothing hand-rolled).** The wrapper provides, from a single embed, everything the pattern requires: (a) constructor-time identity capture (a `Bind`/`Init` the constructor calls exactly once at the end, before the value is returned to any caller); (b) a lock-free `Check` (one atomic load) safe to call **before** the embedder's own mutex is ever touched; (c) fail-closed semantics on a struct copy, on the zero value, on `new(T)`, and on a hand-built literal (all rejected, none silently usable); (d) a registry-sourced error (ASM-874: a `MET-F1xx` code in the registry's `F100-F199` range, `F107+` free). Check: a test defines a fresh `type guarded struct { mu sync.Mutex; g registry.CopyGuard[guarded]; n int }`, byte-copies it via `unsafe.Pointer` (mirroring `internal/foundation/registry/sec020_test.go`'s `registryByteCopy`, the sanctioned test-only mechanism), and asserts the copy's `Check` returns `errors.Is(err, &errs.E{Code: <F107+ code>})` and that the zero value/`new`/hand-built-literal forms are all rejected (`grep -rn "func Test.*CopyGuard" internal/foundation/registry/*_test.go`). **False-pass risk:** a wrapper whose `Check` is not lock-free (or that a caller must invoke *after* locking) would pass "the copy is rejected" while reintroducing SEC-016's hang on a copy taken while the lock was held — the check requires the lock-free, pre-lock-ordering guarantee, not just "a copy errors eventually".

- **AC-11 (pre-lock ordering — a copy taken while the lock was held is rejected promptly, not hung; SEC-016 shape).** Because `Check` is lock-free and runs before the embedder's mutex, a struct copy taken while the original's mutex was **held** (Lock'd or RLock'd, whose bytes the copy captures as "currently locked") is rejected promptly rather than parking forever on the copy's own unrecoverable lock. Check: a passing test constructs the attack state directly (lock the original's mutex, byte-copy, unlock the original, then call the copy — building the state, not racing for timing, so it runs under `-race`), and asserts rejection within a per-case 3-second bound via the `runBoundedRejection` helper pattern (ported from `internal/foundation/registry/sec020_test.go`'s `TestSEC020_CopyTakenWhileLockHeld_RejectedNotHung`), for both a write-lock-held and a read-lock-held copy. **False-pass risk:** a synchronous "call the copy, assert an error" test with no time bound would only fail after Go's 10-minute timeout + goroutine dump if the pre-lock guard were stripped — the check requires the bounded-rejection shape, which is itself part of the deliverable's test hygiene.

- **AC-12 (defensive-copy helper — SEC-066's return-a-copy discipline, centralized).** A defensive-copy helper (e.g. `CloneMap[K,V]` / `CloneSlice[V]`, or a thin `DefensiveCopy` wrapper over the stdlib's `maps.Clone`/`slices.Clone`) centralizes the "return a copy, never the live pointer" discipline, so an accessor that hands back internal map/slice state hands back a copy. Check: a test builds an internal map/slice, obtains the copy through the helper, mutates the returned copy, and asserts the internal state is byte-identical (SEC-066's reproduction, inverted — the mutation must NOT be visible on the next read) (`grep -rn "func Test.*Clone\|func Test.*DefensiveCopy" internal/foundation/registry/*_test.go`). **False-pass risk:** an accessor that returns the live map and a test that only checks "the returned map has the right keys" would pass while the SEC-066 corruption path stays open — the check must mutate the returned value and assert the source is unchanged.

- **AC-13 (GR#21; the wrapper and copy helper are race-free and deterministic).** `go test ./internal/foundation/registry/... -race -count=1` passes with the wrapper exercised concurrently (one goroutine `Check`ing / mutating under the embedder's lock while another reads), and neither the wrapper nor the copy helper introduces a wall-clock or RNG dependency. Check: `grep -rn "time.Now\|math/rand" internal/foundation/registry/*.go` (excluding `_test.go`) finds no new matches; `grep -n "go func()" internal/foundation/registry/*_test.go` finds a concurrency test exercising the wrapper.
