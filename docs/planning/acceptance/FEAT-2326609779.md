## 3. The hierarchy tiers

Aaron's stated order, from first-placed to last-placed:

1. **Rail** — smooth curves, realistic junction shapes.
2. **Motorway** — smooth dual or multi-lane, realistic junctions.
3. **Dual carriageway** — A-equivalent dual alignment.
4. **A-road** — single-lane A-road.
5. **Minor road** — residential/village road.
6. **Buildings** — residential, commercial, industrial, service.

**Invariant:** A later-placed tier must never sever an earlier tier (AC-4).

## 4. Scope and non-goals

**In scope for inc3:**
- Hierarchical placement order within a consolidated section.
- Realistic geometry: bend radii, junction shapes, expressed as tile-grid invariants (AC-2/AC-3).
- Free-space disposition: parks or marked growth reserve (AC-7/AC-8).
- Conservation: pay existing consolidator economics, no free infrastructure (AC-9).
- Determinism: same state + same layout seed ⟹ byte-identical tier placement (GR#21, AC-10).
- Audit: the plan stage records the intended tier sequence; the implement stage records actual placement (AC-11).
- Glide interaction: hierarchy holds within a glide day's scope (AC-12).
- Old-save compatibility: load safety when inc3 consolidator data is absent (AC-13).

**Explicitly out of scope (state these as ASSUMPTIONS):**
- Exact bend-radius tile counts are PLACEHOLDER-tier pending Aaron's row-by-row design pass; the ACs state the invariants checkers must verify, not the hardcoded metre/tile magnitudes.
- Multi-tier re-planning (e.g. "demolish a road to make room for a better one") — inc3 places once, preserves all prior tiers.
- Road/rail interior connectivity balancing (cul-de-sacs, dead ends, circuit closure) — handled by the existing `engine.roads` module; consolidator lays raw grid.
- Player-controlled tier preferences (e.g. "I want more motorway, less minor road") — all three-stage audit tiers are automatic.
- Rebalancing existing pre-consolidation road/rail networks — inc3 works on empty-or-sparse sections (or spares a pre-built tier if it survives AC-4's non-severance test).

## 5. Acceptance criteria

### A. Hierarchical placement order

**AC-1 — placement order is absolute within a section, per-tier atomicity.**
When the consolidator enters the implement stage for a section, it applies tier placements in the exact order: rail → motorway → dual → A-road → minor → buildings. Each tier is applied **atomically** — all tiles for that tier are laid, or none are. If any tier fails a validation gate (AC-4, AC-6, economic gates), the whole tier is skipped and recorded in the audit log (AC-11) with reason `'tier failed: <reason>'`. The next tier still proceeds unless the prior tier's failure broke a non-severance invariant (AC-4 outcome). Check: the audit log state (AC-11) records the per-tier attempt order; a test applies a candidate consolidation in multiple cities (different building patterns) and asserts the same tier sequence every time.

**AC-2 — bend radius invariants are tile-grid-expressed, platform-independent.**
The tile grid is 50 m (`TILE_METRES`, `data.ts`). Bend-radius minima per tier are **expressed as a maximum interior angle (not metres)** and checked by tile-level geometry:

- **Rail:** No interior angle smaller than **67.5 degrees** (the tightest curve in a 4-tile straight). Operationally: a single-tile diagonal or perpendicular turn is forbidden; rail segments must arc over at least 2 tiles horizontally or vertically before turning.
- **Motorway:** No interior angle smaller than **90 degrees** (straight-angle turns only, no jogs). Operationally: a motorway cannot enter and exit a single tile perpendicularly — it must span an even-numbered tile width/height for any direction change.
- **Dual carriageway & A-road:** No interior angle smaller than **112.5 degrees** (looser than motorway, tighter than minor). Operationally: a 90-degree corner is allowed, but a reversed U-turn (< 90 degrees) is forbidden.
- **Minor road:** No interior angle smaller than **45 degrees**; allows tight village cul-de-sacs but not hairpin reverses.

**Rationale:** The tile grid does not represent smooth curves; these tile-level invariants are the grid-level approximation Aaron's "realistic" requires. Check: a test builds a test section with candidate rail/motorway/A-road/minor placements of each bend tightness (at the limit and just inside/outside) and asserts the geometry checker's `isValidBend(tier, pathTiles)` result matches the rule.

**AC-3 — junction shapes are derived from tier-pair rules, not hand-modelled.**
A junction is formed when two tier segments meet. The consolidator's junction rules are:

- **Hierarchy rule:** A higher tier (rail) may pass through a lower tier (motorway) unimpeded. A lower tier terminates at or forms a junction with a higher tier; it does not cross it.
- **Angle rule:** At the junction point, the angle between the lower tier's entry and the higher tier's direction must be ≥ 90 degrees (no acute merges). Operationally: a minor road cannot snake into a motorway at a 45-degree angle.
- **Tile-spread rule:** If two tiers meet in the same tile, one must give way; consolidator prefers **not to place both** and records the choice in the audit. A single tile cannot simultaneously carry a motorway and an A-road (they share the road network layer).

Check: a test junction scenario (e.g. a minor road meeting a motorway) asserts the consolidator chooses valid configuration and rejects invalid ones (acute angles, same-tier conflicts).

**AC-4 — a later-placed tier never severs an earlier one; severance is a hard gate.**
After each tier is placed, the consolidator re-evaluates `computeRoadConnectivity` for the section and **all previously-placed tiers** (rail checks rail connectivity, motorway checks motorway + rail, etc.). If any tile of a higher tier is now disconnected from its pre-placement connectivity state, **the entire tier placement is rolled back** and recorded as `'tier failed: severance'` in the audit. This is stricter than AC-19 of `FEAT-2326609761` (which checks player buildings) because the consolidator, not a player, is deciding to demolish tiers.

Check: a test places a rail segment, then attempts a consolidation that would loop a motorway around it, severing the rail's cross-section. The motorway tier is rejected and the rail remains untouched.

### B. Realistic geometry

(See AC-2/AC-3 above for the tile-level definitions. This section adds derived checkers.)

**AC-5 — bend geometry is validated once per tier, not per-tile.**
A helper `isValidBendPath(tier: TierKind, pathTiles: {x,y}[]): boolean` walks the path and checks every three-consecutive-point angle against the tier's minimum from AC-2. The check is O(pathLength), called once per tier placement, hoisted before any mutation (no O(buildings) re-call per candidate). A test asserts the checker catches a single out-of-spec bend in a 20-tile rail path.

**AC-6 — junction conflicts are detected and logged, not silently resolved.**
When the consolidator lays a tier and detects a junction conflict (AC-3: two tiers in the same tile, or an acute angle), it records the conflict in the tier's audit record (`conflictsDetected: [{x, y, reason}]`) and **may choose to skip one of the conflicting placements** at that tile (recorded as `skippedTiles: {x, y, tier, reason}`). The choice is deterministic: prefer the higher tier (rail over motorway, motorway over dual, etc.), and if both are the same tier, prefer the one whose earlier origin-to-tile path was laid first (deterministic via sorted coordinates). Check: a test places overlapping tier grids and asserts the audit records which tiles were skipped and why.

### C. Free-space disposition

**AC-7 — free tiles within the section are classified and allocated.**
After all six tiers are placed, every tile in the section that carries no infrastructure and no buildings is classified:
- **Park candidate** — if its position scores well per AC-13 of `FEAT-2326609761` (amenity: near schools/homes, commute-neutral).
- **Growth reserve** — otherwise, marked for future consolidation (see AC-11).

A `FreeSpaceAllocation` structure is created:
```ts
interface FreeSpaceAllocation {
  tilesByKind: {
    parks: { x: number; y: number }[];
    reserve: { x: number; y: number }[];
  };
  parkCount: number;
  reserveCount: number;
}
```

Parks are placed (or queued for placement during a follow-up game tick if budget allows). Growth-reserve tiles remain empty but are marked on the debug map and in the audit so Aaron can see planned-but-empty zones.

Check: a test consolidates a 4×4 section with buildings only in corners; asserts the centre 8 tiles are allocated to parks or reserve, and the allocation is recorded in the audit.

**AC-8 — growth-reserve tiles are reusable at zero scrap cost.**
A growth-reserve tile carries a `reservedTier: true` flag in the section's audit. If a later consolidation pass revisits this section, a reserved tile may be reused for tier placement (e.g. converting an unused reserve into a motorway segment) at zero scrap cost — no demolition refund is needed because nothing was ever built there. The audit records the reuse.

Check: test a two-pass sequence: first consolidation reserves tiles, second pass re-audits and places a motorway through a reserved tile, cost £0.

### D. Conservation and economics

**AC-9 — no free infrastructure; pay existing consolidator economics.**
Tier placement costs are booked through the normal consolidator economics (`FEAT-2326609761` AC-22):
- **Build cost**: the sum of `placementCost(roadSpec)` for every tile of infrastructure placed. Road tiers inherit the existing `road`/`motorway`/`rail` specs and their costs. **No tier is placed for free.**
- **Scrap**: if a tier placement requires demolishing an existing building or road (rare, gated by AC-4), the scrap recovery follows the normal rule (`CONSOLIDATOR_SCRAP_FRACTION = 0.5`).
- **Booking**: all costs and refunds are booked through the `'Consolidation'` flow lines (matching `FEAT-2326609761` AC-22), so `conservation.funds-vs-flows` continues to hold.

A test asserts conservation over a multi-tier consolidation: funds lost to tier costs + funds recovered from scrap + funds remaining = funds at start + flow inflows.

### E. Determinism

**AC-10 — same section state + same layout seed ⟹ byte-identical tier placement.**
The tier-placement algorithm is a deterministic function of section audit state (buildings, obstacles, existing infrastructure) and a **layout seed** (an integer derived from `sectionKey` and `state.tick`, never from `Math.random`, `Date.now`, or `localStorage`). Repeated runs with identical input produce byte-identical tile placements and junction resolutions.

- No `Math.random`, no `Date.now`, no `performance.now`, no `localStorage` reads anywhere in tier placement (GR#21).
- No `for (const x of someMap) { ... break; }` — every candidate or tile iteration is over an explicitly sorted array (section keys in ascending order, building ids in ascending order, candidate tiles sorted by (x, y)).

Check: `replayIsDeterministic(journal)` passes with a journal containing consolidation passes that include tier placement. A test also drives the same section layout through two independent `advance()` calls with shuffled `buildings` array order and asserts byte-identical tier output.

### F. Audit trail

**AC-11 — three-stage audit: discover, plan, implement.**
The consolidator logs each section's consolidation attempt at three stages:

1. **Discover stage** (existing `FEAT-2326609761` AC-5): `SectionAudit` record of buildings, counts, layout score. No plan yet.
2. **Plan stage** (new, this AC): for each tier in sequence, the consolidator records its **intended** placement:
   ```ts
   interface TierPlan {
     tier: TierKind;
     plannedTiles: {x: number; y: number}[];
     estimatedCost: number;
     estimatedScrap: number;
     validationTests: {
       bendGeometry: boolean;
       severanceTest: boolean;
       junctionRules: boolean;
     };
   }
   ```
3. **Implement stage** (new): as each tier is actually placed, the record is updated:
   ```ts
   interface TierImplementation extends TierPlan {
     actuallyPlaced: boolean;
     failureReason?: string;  // e.g. 'insufficent funds', 'severance detected'
     actualTiles: {x, y}[];
     actualCost: number;
     conflictsResolved: {x, y, reason}[];
   }
   ```

The audit is recorded in `consolidatorLog[0].transactions[i].tierAudit: TierImplementation[]`, visible in the Consolidator tab (AC-25 of `FEAT-2326609761`).

Check: a test triggers a consolidation that places rail, attempts a motorway that would fail severance, succeeds on A-road, and asserts the tierAudit records the plan and the failure reason for motorway.

### G. Glide interaction

**AC-12 — hierarchy ordering is preserved within a glide day's scope.**
The GLIDE consolidator mode (inc2 — BUILT, in destructive round as of 2026-09-04; Aaron's ruling makes glide the DEFAULT mode: one tile-column per day, month-12 whole-map pass) applies changes in column-chunks per game day. Tier placement must not interleave tiers out of order across multiple glide days — within a single day's column, tiers are placed in the full hierarchy order (rail → buildings in one column before the next day). If a column is not completed in one day, the consolidator pauses and resumes the same tier order the next day.

**Rationale:** Interleaving rails and buildings across days would allow buildings to block rail later, violating AC-4.

Check: a test simulates a multi-day glide with a large consolidation section, asserts no building is placed in day 1 before all rail is attempted, and no motorway is placed in day 2 after buildings were placed in day 1 for the same column.

### H. Old-save compatibility

**AC-13 — loads and defaults safely when inc3 tier data is absent.**
Old savepoints (pre-inc3) contain no `tierAudit`, no `freeSpaceAllocation`, no `reservedTile` flags. When loading:
- Existing `consolidatorEnabled` and `consolidatorLog` (from inc1/inc2) are preserved as-is.
- New fields (`tierAudit`, `freeSpaceAllocation`, `reservedTile`) default to `undefined`/`[]`/`false` and are treated as "no inc3 audit data available".
- The consolidator, when enabled on an old save, behaves as inc1/inc2 (building consolidation only, no tier placement) until a **new** consolidation pass is triggered, which then populates the inc3 fields.
- An old savepoint mid-consolidation (with `consolidatorLog` entries) loads safely; the log entries are read-only in the audit display and do not attempt to deserialize tier data.

Check: a test loads a save with `consolidatorEnabled = true` and `consolidatorLog` from 2–3 inc1 passes, verifies no error, and asserts the Consolidator tab displays the old passes as "inc1/inc2 (no tier data)" without crashing.
