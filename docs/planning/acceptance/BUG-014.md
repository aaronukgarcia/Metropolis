# Acceptance criteria — claude-bow.js fresh-database schema matches the live-altered schema (BUG-014)

**BOW code:** BUG-014 (P2, open)
**Spec refs:** GR#3 (single source of truth — the live DB and the code that recreates it must agree); same class as BUG-008 (code-vs-registry drift), explicitly named as such in the item's own description.
**Date:** 2026-08-10
**Status:** active
**Package under test:** `claude-bow.js` (`ensureSchema` / the `CREATE TABLE`/`ALTER TABLE` migration block).
**Standard gates:** no existing Go/Node test harness for this file (see BUG-017's same note) — Tester baseline is the scripted fresh-database bootstrap in AC-3, run against a **throwaway** database, never the live `metro` database.

## Acceptance criteria

### Functional

- **AC-1.** `ensureSchema`'s `CREATE TABLE IF NOT EXISTS` statement for the items table declares the full `item_type` ENUM as it exists on the live database today — `('module','feature','bug','interface','assumption','finding')` (or whatever the live, already-altered set actually is; Tester confirms by inspecting the live schema, not by trusting this file's guess) — not the stale `('module','feature','bug','interface')`. Check: `grep -n "item_type ENUM" claude-bow.js` shows the `CREATE TABLE` and the `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`-style upgrade block (per the existing idiom the item's description points at) declaring the **same** set.
- **AC-2.** `code_path`, `codejson_ref`, and `finding_class` (the columns added for `assumption`/`finding` items) are likewise present in **both** the `CREATE TABLE` statement and the idempotent upgrade block — not only in one, which is exactly this bug's root cause repeated on a second set of columns if left unchecked. Check: `grep -n "code_path\|codejson_ref\|finding_class" claude-bow.js` shows each column name appearing in both the `CREATE TABLE` body and an `ADD COLUMN IF NOT EXISTS` guard.
- **AC-3 (the actual fix — Pattern #1: a fresh bootstrap must be exercised, not assumed).** The BOW item's own diagnosis is that "only the live state was tested" — this criterion requires the untested path be tested: a passing integration test (or a documented, repeatable manual script the Tester runs) creates a **new, empty** database (or drops and recreates all tables in a disposable one), runs `node claude-bow.js init` (or whatever bootstraps a fresh schema) against it, and then successfully inserts one row of **each** item type including `assumption` and `finding` with `code_path`/`codejson_ref`/`finding_class` populated — proving the fresh-bootstrap path actually accepts what the live-altered database already accepts. Check: the test/script runs end-to-end against a throwaway DB (never `metro`) and exits 0; Tester confirms the target database name/connection used was not the live one before running it.

### Error handling

- **AC-4.** If `ensureSchema` is run against a database whose existing schema conflicts irreconcilably with the expected shape (e.g. `item_type` is a different, incompatible type entirely), it fails with a clear error rather than silently proceeding with a half-migrated schema — check via a test that seeds a deliberately-incompatible throwaway schema and asserts a loud failure, not a silent partial success.

## Out of scope

- Migrating any *other* schema drift not named in this bug (the item scopes itself to `item_type` plus the three named columns) — a broader schema audit is a separate BOW item if one is needed.

## Escalations

- **Assumption likely needed at build time:** the exact current live `item_type` ENUM values must be read off the actual `metro` database at implementation time (I cannot verify them from this BA seat without a DB write/read outside my remit) — the junior should log an `ASM-` recording exactly which values were found live and used in the fix, per v1.7, rather than trusting this file's placeholder list above.
