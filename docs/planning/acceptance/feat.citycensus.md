## User stories

- **US-1.** As the determinism-critical sim tick (GR#21), I need the four census threads (stats generator, auditor, consistency checker, regulator) to run OFF my critical path — reading a committed snapshot of my resolved state and writing only to their own output surface — so the census can never change a tick's input or outcome, only report on it.
- **US-2.** As the stats generator, I need to aggregate city statistics (population, age/sex/education-tier distributions, employment, health, crime, income) as a deterministic function of tick state + data, so the player sees one number that is exactly the sum/aggregate of what the owning modules report, not a census-local estimate.
- **US-3.** As the auditor, I need a monotonic, tick-keyed history of the city's progress over time (a time series of the census's own aggregates), so "how has the city changed" is a query against recorded snapshots, not a recomputation from memory.
- **US-4.** As the consistency checker, I need every modelled object (citizen, car, house, chopper) to carry a GUID and a monotonic least-check-in timestamp, and I need to surface any object whose check-in lags, so the sim never silently loses sight of an object it is supposed to be tracking.
- **US-5.** As the regulator/watchdog, I need to flag, as queryable findings (not mutating interventions), when crime is too high, when people are unfed, and when people are uneducated, so the player sees a problem forming before its downstream consequences land (the §12/§27 slow-fuse pattern).
- **US-6.** As the census's bio layer, I need to assemble a cradle-to-grave life-history for EVERY object — citizens (education, job, family, home, workplace, retirement, income-for-tax) and cars/houses/choppers alike — by reading the owning modules' records, so a bio is a faithful view of one object's real state, never a parallel re-derivation.
- **US-7.** As the player watching the education→crime link, I need the census to surface the less-education-to-more-crime correlation and to observe (not implement) the reward/penalise-education policy's effect, so the policy is a real lever whose consequence is visible in the same place its cause lives.
- **US-8.** As the player on the F6 demographics / KPI view, I need a blue/white-collar graph, age/sex/education-tier splines, and the city KPIs (GDP, happiness, land value, homeless, in-hospital, out-of-work, unfilled jobs, job→skill demand) — each drill-in-able to its source, per UI-SPEC §4.

## Scope

Four non-blocking, read-only observation threads (stats generator, auditor, consistency checker, regulator/watchdog) running off the determinism-critical tick path against a committed snapshot; a census/KPI data model aggregated from the seven consumed modules' registered query surfaces; a cradle-to-grave bio assembly for every GUID-tracked object (citizens and non-citizens); the GUID + least-check-in-time liveness invariant and its lost-object surfacing; the education→crime linkage surfaced as a data-derived correlation plus the reward/penalise-education policy observed as an `engine.policies` instrument; and the demographics + KPI data model (blue/white-collar split, three spline series, the city KPI set) with a drill-target resolution surface. It does NOT build: citizen mortality/employment, education stage mechanics, crime generation, wellbeing scoring, service capacity, policy instruments, the finance ledger, or the tcell rendering of F6 (see Out of scope and Escalations).

## Acceptance criteria

### Pillar 1 — the four non-blocking background threads

- **AC-1 (GR#20; code.json inbound contract).** A `CensusAPI` (or equivalent) exists exposing: (a) query surfaces for the stats generator's aggregates, (b) the auditor's tick-keyed history series, (c) the consistency checker's per-object check-in status and its lost-object findings, and (d) the regulator's finding surface — plus the bio and KPI query surfaces AC-9/AC-17/AC-19 require. Check: `go doc ./internal/engine/census CensusAPI` shows the four read surfaces (stats, history, consistency, findings) as query methods, not mutation commands — the census exposes **no** command that mutates another module's state (see AC-2). **False-pass risk:** an API with a catch-all `Query(kind)` returning untyped values would pass a "query surfaces exist" grep while giving no typed contract a consumer (ui.dash / a future ui.screen.demographics) can bind a drill target against — the check requires `go doc` to print named, typed accessors for each surface.

- **AC-2 (GR#21; the load-bearing non-blocking requirement — every thread runs off the critical path and NEVER mutates the tick's input).** The four threads are **observers**: they read a committed snapshot of resolved tick state and write only to the census's own output surface. Running the four threads over a given tick state leaves that tick state **byte-identical** to what it was before the threads ran — the census introduces no write path into any of the seven consumed modules' tick-critical state. Check: a passing test snapshots full tick state, runs all four threads to completion, and asserts the post-run snapshot is byte-identical to the pre-run snapshot (a deep-equal over the consumed modules' exposed state) — not merely that "no obvious mutation happened" (`grep -rn "func Test.*[Oo]bserver.*[Nn]oMutate\|func Test.*[Rr]eadOnly" internal/engine/census/*_test.go`); `grep -rn "func.*(Set|Apply|Add|Remove|Increment|Decrement)" internal/engine/census/*.go` (excluding `_test.go`) finds no exported mutation method against a consumed module's state. **False-pass risk:** a test that only checks the census's *own* aggregates are correct would pass a build where a thread also writes a "cache" back into `engine.citizens`/`engine.finance` state (the cheapest way to keep an aggregate fresh), which would violate GR#21 by making the observer a participant — the check must diff the *consumed modules'* state before/after, not the census's own output.

- **AC-3 (stats generator — deterministic aggregation, not estimation).** The stats generator computes each city statistic as an aggregation over the owning module's query surface (population from `CitizensAPI`, employment from the same, health from `WellbeingAPI`, crime from `CrimeAPI`, income from `FinanceAPI`, education tiers from `EducationAPI`), and the result is a deterministic function of `(tick state, loaded data)` — repeated runs over an identical snapshot produce byte-identical aggregates. Check: `go doc ./internal/engine/census` shows per-statistic aggregate accessors; a passing test runs the generator twice over an identical snapshot and asserts byte-identical output, and independently mutates one module's input (e.g. one citizen's employment state via the owning module's command) and asserts the corresponding aggregate changes by exactly the contribution of that one change (`grep -rn "func Test.*[Ss]tatsGen\|func Test.*[Aa]ggregate" internal/engine/census/*_test.go`). **False-pass risk:** an aggregate computed once at boot and cached forever would pass "aggregates exist" on any early read while silently going stale — the check requires the aggregate to respond to a post-boot input change, proving it is recomputed from live state.

- **AC-4 (auditor — progress over time, monotonic and tick-keyed).** The auditor appends a snapshot of the census's aggregates to a history series keyed by simulation tick/month, monotonic in tick order, and the series is queryable ("give me the value of KPI X at tick T"). Repeated audits of the same tick do not create duplicate or out-of-order entries. Check: `go doc ./internal/engine/census` shows a tick-keyed history accessor (e.g. `HistoryAt(tick)`); a passing test audits ticks 1,2,3 and asserts the series is ordered 1→2→3 with no duplicates when tick 2 is re-audited, and that a query for a tick not yet audited returns a documented not-found result rather than a silent zero (`grep -rn "func Test.*[Aa]uditor\|func Test.*[Hh]istory.*[Oo]rder" internal/engine/census/*_test.go`). **False-pass risk:** a "history" that is just a rolling latest-value (a single overwritten slot) would pass a "value queryable" check while the feature's "progress over time" promise is unmet — the check requires the series to retain multiple ticks in order.

- **AC-5 (consistency checker — the GUID + least-check-in-time invariant).** Every modelled object the census tracks carries a stable GUID (a wrapper over the owning module's existing identity — see ASM-641 in Escalations) and a monotonic least-check-in timestamp: for each tracked object, the census records when it last successfully observed each of the object's tracked facets (for a citizen: job, family, home, workplace, retirement date, income), and the object's **least check-in time** is the *oldest* (least recent) of those per-facet timestamps (the "least" reading, ASM-645). The CC surfaces any object whose least check-in time lags the current tick by more than a data-defined threshold (a placeholder in `data/census.json`, ASM-646). Check: `go doc ./internal/engine/census` shows the per-object check-in record (GUID, per-facet last-seen timestamps, derived least-check-in) and the lag-threshold comparison; a passing test refreshes all of a citizen's facets and asserts the least-check-in equals the current tick, then refreshes all but one facet and asserts the least-check-in equals the stale facet's timestamp (proving "least" is the minimum across facets, not the latest refresh) (`grep -rn "func Test.*[Ll]eastCheckIn\|func Test.*[Cc]heckInFacet" internal/engine/census/*_test.go`). **False-pass risk:** an implementation that records only a single "last seen anything" timestamp (the most recent refresh of any facet) would pass a "check-in time is tracked" grep while a citizen whose *income* facet stopped refreshing (but whose home facet still refreshes) would never surface as stale — the check requires per-facet timestamps and the minimum-derived least-check-in, because the feature's own example enumerates the facets explicitly.

- **AC-6 (consistency checker — the lost-object detection; the remove/forget test).** The CC flags an object the sim has "lost sight of": when an object is removed from, or silently stops refreshing in, its owning module's state (a citizen whose record no longer advances, a car that vanished from the vehicle set, a house whose structure ref no longer resolves), the CC's surface reports that object's GUID as stale/lost once its least-check-in lags beyond the threshold — the object is never silently dropped from the census's own tracked set either. Check: a passing test seeds a citizen with a live check-in, then removes that citizen from the owning module's state (or stops all of its facets from refreshing) and advances past the threshold, and asserts the CC's findings surface names exactly that GUID as lost — and that the census's own tracked-object set still retains the GUID rather than silently forgetting it (`grep -rn "func Test.*[Ll]ostObject\|func Test.*[Ff]orgottenObject" internal/engine/census/*_test.go`). **This is the AC an attacker should try hardest to break (the brief's own hard requirement #2):** a census that drops an object from its tracked set the moment the owning module stops reporting it would pass "no stale objects remain" by the simple expedient of forgetting everything — the check requires the GUID to *persist in the census's tracked set and be flagged*, which is the entire point of "never loses sight of objects."

- **AC-7 (regulator/watchdog — findings, not interventions; thresholds from data).** The regulator evaluates the current aggregates against data-defined thresholds (crime-too-high, unfed, uneducated — each a placeholder threshold in `data/census.json`) and emits **queryable findings** naming the condition and the offending aggregate/scope, without mutating any module's state to "fix" the condition. Check: `go doc ./internal/engine/census` shows a finding type carrying (condition, scope, offending value, threshold); a passing test drives crime above its threshold (via the owning `engine.crime`'s own inputs) and asserts a crime-too-high finding fires with the value and threshold populated, while a state at exactly the threshold boundary does not fire (or fires only per the documented inclusive/exclusive rule) (`grep -rn "func Test.*[Rr]egulator\|func Test.*[Ww]atchdog" internal/engine/census/*_test.go`). **False-pass risk:** a "regulator" that also nudges a module's funding/patrol state toward fixing the problem would pass "a finding fires" while violating AC-2's observer rule — the check requires the finding to be a report, and AC-2's byte-identical-state check already guards against the mutation.

- **AC-8 (thread determinism — snapshot-read, order-independent, no wall clock).** Each thread is a deterministic function of `(committed snapshot, loaded data)`: no thread reads live state mid-computation in an order that depends on goroutine scheduling, no thread's output depends on Go map-iteration order (any map feeding an ordered output is sorted first), and no thread advances any clock other than the simulation tick. Check: `grep -n "time.Now\|time.Since" internal/engine/census/*.go` (excluding `_test.go`) returns no matches; `grep -n "for .* := range" internal/engine/census/*.go` on any map feeding an ordered output is sorted (`grep -n "sort\." internal/engine/census/*.go` corroborates); a passing determinism test runs all four threads repeatedly over an identical snapshot and asserts byte-identical output (`grep -rn "func Test.*[Dd]eterminis" internal/engine/census/*_test.go`). **Never assert a wall-clock upper bound on how long a thread takes in CI** — assert output equality only, per the SG-7 gate pattern.

### Pillar 2 — cradle-to-grave bios for every object

- **AC-9 (citizen bio — complete and sourced from registered interfaces only).** A citizen's bio assembles, through the owning modules' registered query surfaces and never a direct struct reach-in: education history (`EducationAPI`), job/employment and family/home (`CitizensAPI`), workplace (the same employment/sector record), retirement date (derived from the citizen's birth month + the data-file retirement age, ASM-646), and income (sourced from `FinanceAPI`'s tracked income, AC-12). Check: `go doc ./internal/engine/census` shows the bio type naming all these facets; `grep -rn "citizens\.\(Citizen\|ColdShard\)\|education\.\w*Record\|finance\.\w*Ledger" internal/engine/census/*.go` (excluding `_test.go`) finds **no** direct reach into another package's concrete struct — all reads route through the registered API interfaces. **False-pass risk:** a bio that duplicates a citizen's education/employment fields into a census-local store would pass "a bio exists with all fields" while creating a second source of truth (GR#3) that can desync from `engine.citizens` — the check requires the bio to be an *assembled view* over the live interfaces, not a census-local copy.

- **AC-10 (education bio — kindergarten to specialist universities tied to industry).** A citizen's education bio records the full stage trajectory (kindergarten → primary → secondary → fork → specialist university, per §27) including, at the university tier, the industry tie (Pfizer-Sandwich pharma, CERN, SpaceX, Heathrow, mining — the feature's own examples) as a recorded attribute of the citizen's attainment, sourced from `EducationAPI`'s stage/attainment history. Check: `go doc ./internal/engine/census` shows the education-bio facet carrying a stage-history list and an industry-tie attribute; a passing test assembles a bio for a citizen whose `EducationAPI` record ends in a specialist-university stage and asserts the bio's industry tie matches the record (`grep -rn "func Test.*[Ee]ducationBio\|func Test.*[Ss]pecialist.*[Uu]niversity" internal/engine/census/*_test.go`). **Note:** the specialist-university-to-industry taxonomy itself is not yet in the master spec (see Escalations ES-2) — this AC requires the census to *carry* the tie as sourced from `EducationAPI`, and if `EducationAPI` does not yet expose it, that is a cross-module gap, not a census-side invention.

- **AC-11 (non-citizen objects — cars, houses, choppers alike).** The census tracks bios for non-citizen objects too — cars (mileage, a short- or long-lived life-history), houses (a placed-structure life-history from construction onward), choppers (air-unit life-history) — each carrying its own GUID (ASM-641) and its own least-check-in, and each with a documented short-lived vs whole-game life span. Check: `go doc ./internal/engine/census` shows a generic tracked-object/bio surface that is not citizen-specific (a citizen and a car both satisfy the same tracked-object contract); a passing test seeds a car and a citizen and asserts both appear in the tracked-object set with distinct GUIDs and distinct life-history shapes (`grep -rn "func Test.*[Nn]onCitizen\|func Test.*[Cc]arHouseChopper" internal/engine/census/*_test.go`). **Escalation note:** the owning modules for cars/houses/choppers (`engine.traffic`, `engine.build`, `engine.airunits`) are **not** among the seven named consumers — see ES-3; this AC is written against the assumption that those objects expose a stable ID the census can key off, and blocks on that edge if not registered.

- **AC-12 (income tracked for tax — single source of truth, GR#3).** The bio's income figure is sourced from the existing income tracking (`FinanceAPI`'s wage/income ledger or `CitizensAPI`'s employment-derived income), never re-derived by the census from a census-local formula — "an income that is tracked so we can tax them" is already `engine.finance`'s/`engine.citizens`' concern, and the census only surfaces it. Check: `grep -n "income\|Income" internal/engine/census/*.go` (excluding `_test.go`) shows the income facet resolving through a finance/citizens interface call; `grep -rn "TaxRate\|tax" internal/engine/census/*.go` (excluding `_test.go`) finds **no** census-local tax computation — the census reports income, it does not tax.

- **AC-13 (bio determinism + GR#16 storage boundaries).** A bio is a deterministic function of `(object GUID, tick, data)`: assembling the same object's bio twice at the same tick returns byte-identical output, and any field crossing a storage/serialisation boundary (persisted check-in timestamps, persisted bios) is coerced through the project's `safeX()`/`foundation` coercion helpers rather than trusting a stored type blindly. Check: `grep -rn "func Test.*[Bb]io.*[Dd]eterminis\|func Test.*[Rr]econstructBio" internal/engine/census/*_test.go` finds a determinism test; `grep -rn "safe[A-Z]" internal/engine/census/*.go` (excluding `_test.go`) shows the coercion-helper usage on any load/serialise path (or the load path is documented to reject malformed records per AC-22).

### Pillar 3 — the education→crime linkage and the reward/penalise-education policy

- **AC-14 (less education → more crime — direction and structure, never a pinned magnitude).** The census surfaces the education-tier × crime-rate linkage as a data-derived correlation: for the same population scope, a lower aggregate education attainment (lower tier mix, lower attainment score) is associated with a higher crime rate, computed by joining `EducationAPI`'s attainment data against `CrimeAPI`'s generation figures — the census reports the relationship, it does not invent the numbers. Check: a passing test constructs two synthetic populations differing only in aggregate education attainment (via the owning modules' inputs) and asserts the census's linkage report shows the lower-education population with the higher crime figure, while holding every other driver fixed (`grep -rn "func Test.*[Ee]ducationCrime\|func Test.*[Ll]essEducation" internal/engine/census/*_test.go`). **False-pass risk:** a census that hardcodes a "crime = −education × k" line and reports that regardless of the owning modules' actual data would pass a "linkage exists" grep while the feature's "less education → more crime" is meant to *emerge* from the real `engine.crime` drivers (which already consume unemployment/deprivation per `engine.crime.md` AC-1) — the check requires the correlation to be computed from the live modules' data, so mutating one module's input moves the report. **Balance-regime note:** the elasticity/steepness is a placeholder (ASM-646); this AC checks the direction is data-derived, not a specific slope.

- **AC-15 (reward/penalise-education policy — an `engine.policies` instrument, observed not implemented).** The reward/penalise-education lever is an `engine.policies` instrument (data-defined coefficient moves, per `engine.policies.md` AC-2) — the census does NOT build a second policy mechanism; it observes the policy's enacted effect on the education/crime linkage and reports it through its own query surface. Check: `grep -n "policies\." internal/engine/census/*.go` (excluding `_test.go`) shows the census reading the enacted policy state through `PoliciesAPI`, with no census-local policy-enactment surface (`grep -rn "Enact\|Repeal\|SetPolicy" internal/engine/census/*.go` excluding `_test.go` finds no such method); a passing test enacts a reward-education fake policy via `engine.policies` and asserts the census's linkage report reflects the resulting attainment change without the census having enacted anything itself (`grep -rn "func Test.*[Rr]ewardEducation\|func Test.*[Pp]olicyObserved" internal/engine/census/*_test.go`). **Boundary note:** the *policy itself* (its coefficient targets, its cost, its scope) is `engine.policies`' own; this AC only requires the census to observe and report its effect, consistent with AC-2's observer rule.

- **AC-16 (balance-number regime — every bell-curve parameter is a disclosed placeholder).** `data/census.json` carries a `$comment`/`meta` block citing §18/§40/§45/§46 and the design, and documents every bell-curve parameter — lifespan (mean ± spread, e.g. 75±10), retirement age (~68), annual mileage (~10,000), the crime→education elasticity, the blue/white-collar baseline split, and the happiness-weight composition — plus every thread threshold (CC lag, regulator crime/hunger/education alarm levels), each with its unit stated and a non-empty disclosure comment naming the value a placeholder pending Aaron's balance pass. Check: `grep -n "\$comment\|\"meta\"" data/census.json` matches; units are stated for every numeric entry; every bell-curve parameter and threshold carries a disclosure field. **What a lazy implementation looks like (and what this AC rejects):** a junior pinning `lifespanMean = 75` as a bare Go constant to make a test pass quickly — the same ASM-284-class overstep `feat.maintenance.md` AC-16 and `engine.finance.md` AC-21 exist to prevent; no AC in this file may be satisfied by inventing a final figure.

### Pillar 4 — demographics + KPI data model and drill-in

- **AC-17 (blue/white-collar split — emergent, not hardcoded).** The blue/white-collar graph is computed from the population's actual employment/sector data (blue-collar from chains/construction/logistics/services-to-buildings; white-collar from firm overhead/finance/public administration — §45 line 625), never a fixed ratio or a census-local label. Check: `go doc ./internal/engine/census` shows a blue/white-collar split accessor derived from `CitizensAPI`'s employment/sector fields; a passing test moves a cohort of citizens between blue- and white-collar sectors (via the owning module's employment commands) and asserts the split moves by exactly that cohort's contribution, and holds all other drivers fixed (`grep -rn "func Test.*[Bb]lueWhiteCollar\|func Test.*[Ww]hiteCollar" internal/engine/census/*_test.go`). **False-pass risk:** a hardcoded `blue = 60%, white = 40%` split (or a split read from `data/census.json` as a constant) would pass a "split exists" grep while the feature's §45-derived "emergent" premise is unmet — the check requires the split to respond to real employment-state changes.

- **AC-18 (splines — age bands, sex M/F, highest education tier).** The census exposes three spline series over the population — by age band, by sex (M/F), and by highest education tier — each computed from `CitizensAPI`'s per-citizen records (birth month → age, sex, and `EducationAPI`'s attainment), as a deterministic function of tick state + data. Check: `go doc ./internal/engine/census` shows the three series accessors; a passing test seeds a synthetic population with known age/sex/education distributions and asserts each series reproduces the expected distribution, and that the three series are independently computable (changing only the education inputs leaves the age-band series byte-identical) (`grep -rn "func Test.*[Ss]pline\|func Test.*[Aa]geBand\|func Test.*[Ee]ducationTier" internal/engine/census/*_test.go`). **False-pass risk:** three series computed from a single shared bucket-count (or from the same underlying aggregate reshaped three ways) would pass "three series exist" while not being independent observations — the check requires per-citizen-sourced, independently-perturbable series.

- **AC-19 (city KPIs — GDP, happiness, land value, homeless, in-hospital, out-of-work, unfilled jobs, job→skill demand — all aggregated from registered interfaces, data-derived).** Each named KPI is an aggregate over the owning modules' query surfaces, computed by aggregation (not a separately-maintained counter) and never a hardcoded expected value: GDP over `FinanceAPI`'s ledger flows (ASM-648), happiness over `WellbeingAPI`'s headline composite, land value over `FinanceAPI`'s `LandPrice` (or the equivalent), homeless over `CitizensAPI`'s household/home state, in-hospital over `WellbeingAPI`/`ServicesAPI`'s health/waiting-list state, out-of-work over `CitizensAPI`'s employment state, and unfilled jobs + job→skill demand over `ServicesAPI`/`StaffingAPI`'s demand/shortfall surface (the staffing edge — see ES-3). - **AC-20 (drill-in — every KPI/series figure carries a resolvable source, per UI-SPEC §4).** Every aggregate figure the census exposes (each KPI, each spline point, each blue/white-collar datum) carries a drill-target that resolves to the underlying entities/ledger lines that compose it — the census data model exposes a `Source(aggregateID)`-style resolution so a UI surface (ui.dash / a future ui.screen.demographics) can bind `Enter` to a source, exactly as `engine.finance.md` AC-11 does for ledger lines and `ui.dash.md` AC-4/AC-5 require for tiles. ### Error handling

- **AC-21 (GR#7).** Querying a bio/KPI/check-in for an unknown object GUID, or an unknown KPI/statistic key, returns a registry-sourced error (a new `MET-`-range code claimed at build time — no `engine.census` sub-range exists yet), never a silently-constructed zero-value bio or a "0" KPI a caller could mistake for a real empty figure. Check: `grep -n "MET-" internal/engine/census/*.go` finds a registry-code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownGUID\|func Test.*[Uu]nknownKPI" internal/engine/census/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100 convention):** the test asserts the returned error's registry code matches AND that no zero-value bio/KPI was created as a side effect, not merely that a matching-named test function exists.

- **AC-22 (GR#7).** A malformed or schema-invalid `data/census.json` (a bell-curve parameter missing its unit, a threshold outside a sane range, an unrecognised parameter key, a negative lifespan/spread) produces a registry-sourced error at load time, never a silent default substitution that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/census/*.go` finds a load-time registry code distinct from AC-21's; passing test coverage (`grep -rn "func Test.*[Mm]alformedCensus\|func Test.*[Ii]nvalidCensus" internal/engine/census/*_test.go`) asserts the error's registry code matches AND that no default-substituted parameter was loaded in place of the malformed one.

### Determinism & safety

- **AC-23 (GR#21).** The census's aggregation, bio assembly, and CC/regulator evaluation are deterministic functions of prior tick state, loaded data, and the consumed modules' resolved state — repeated runs from an identical snapshot over an identical sequence produce byte-identical census output (aggregates, history, findings, bios), across worker counts. Check: a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/census/*_test.go`); no shared/global RNG source anywhere in the package (`grep -n "rand.New\|math/rand\"" internal/engine/census/*.go` excluding `_test.go` finds none) — any stochastic synthetic seeding routes through the counter-based hash stream `hash(worldSeed, id, month, purposeTag)` per `engine.citizens.md` AC-15's convention.

- **AC-24 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/census/*.go` (excluding `_test.go`) returns no matches — the census advances age/state/check-in by simulation tick/month only, never wall clock. Never assert a wall-clock upper bound on a thread's runtime in CI; assert tick-count/state equality only.

- **AC-25.** `go test ./internal/engine/census/... -race -count=1` passes with no data race when the four threads run concurrently with each other and with a tick resolving the consumed modules' state (the census reads a committed snapshot; the race test proves the snapshot discipline holds). Check: `grep -n "go func()" internal/engine/census/*_test.go` finds at least one concurrency test.
