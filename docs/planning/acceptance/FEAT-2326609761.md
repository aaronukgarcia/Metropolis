## 5. Acceptance criteria

### A. Enable toggle

**AC-1 — the toggle is sim state, set by a journalled action, never localStorage.**
`SimState` gains `consolidatorEnabled: boolean` (default `false`). It is flipped **only** by a new reducer action `{ type: 'toggleConsolidator' }`, classified `true` in `isStateAffecting` (`journal.ts:61`), mirroring the existing `'toggleGridImport'` (`engine.ts:3066`).
**This is a trap the codebase invites and the build MUST NOT fall into:** every existing feature flag (`liveEngineFlag.ts`, `webWorkerFlag.ts`, `debugBuildSpeed.ts`) lives in `localStorage`. A `localStorage` consolidator toggle would make **replay non-deterministic** — the flag would not travel with the journal, so the same journal would rebuild a different city on a different machine or after a cache clear.
*Verification:* a test asserts (a) `isStateAffecting({type:'toggleConsolidator'}) === true`; (b) a journal containing a toggle replays to a state with the same `consolidatorEnabled`; (c) `grep` proves no consolidator code path reads `localStorage`.

**AC-2 — where the toggle lives.**
A checkbox in `components/ConfigMenu.tsx` following the existing `brand-menu-row` pattern (ConfigMenu.tsx:246-256) but **dispatching the action rather than writing storage**, plus a mirrored toggle in the new Consolidator tab (AC-25). Label: *"Consolidator (urban regenerator)"*, title text stating it demolishes and rebuilds automatically and costs money. When off, **zero consolidator work is done** — the pass returns the input state by reference identity (`next === s`), provable in a test, so `memoOnState` WeakMap keys are untouched.

### B. Discovery mode + section audit

**AC-3 — the tile-to-metre conversion is a promoted constant, and the section size is derived from it.**
Export `TILE_METRES = 50` from `data.ts` (with the existing line 122 comment retargeted to reference it), export `CONSOLIDATOR_SECTION_METRES = 200`, and derive `SECTION_TILES = Math.round(CONSOLIDATOR_SECTION_METRES / TILE_METRES)`. **No literal `4` and no literal `200` appears in any logic** (GR#15). A test asserts `SECTION_TILES === 4` **and** that changing `CONSOLIDATOR_SECTION_METRES` to `400` yields `8` with the section grid recomputing accordingly.

**AC-4 — discovery is a single O(buildings) bucketing fold, once per pass, memoised.**
`sectionIndexOf(s: SimState): Map<number, SectionAudit>` is a `memoOnState`-wrapped function that walks `s.buildings` **exactly once**, bucketing each building into `sectionKeyOf(b.x, b.y)` (its origin tile; a building spanning sections is owned by its origin section — see ASM-1493).
**It must never call an O(buildings) helper inside the per-building loop** (BUG-642). Any capacity/online derivation it needs is hoisted once before the loop, exactly as `evaluateBuildingMonitors` hoists `residentsCapacity(s)` and `totalJobs(s)` (`engine.ts:1125-1126`, BUG-467).
Sections with **zero** buildings are absent from the map — the index is O(occupied sections), not O(7,150).

**AC-5 — the section audit output is an explicit, inspectable record.**
```ts
interface SectionAudit {
  key: number;            // sectionKeyOf
  x0: number; y0: number; // section origin tile
  w: number; h: number;   // SECTION_TILES, clipped at the map edge
  buildingIds: number[];              // ascending, deterministic
  countByKind: Partial<Record<ZoneKind, number>>;
  countBySpec: Record<string, number>;
  capacityByFamily: Record<string, number>;  // keyed by familyKeyOf (AC-7)
  tilesUsed: number; tilesFree: number;
  nuisanceCount: number;  // buildings carrying tag 'pollution'
  score: LayoutScore;     // AC-13
}
```
The audit for the pass's candidate sections is surfaced in the debug JSON (`debugjson.ts`) and in the Consolidator tab (AC-25) so Aaron can see what it saw. **The audit itself never mutates state.**

**AC-6 — discovery covers the whole map every pass; the budget is on ACTIONS, not on sections.**
Aaron said "looks at the whole map". A cursor-limited sweep of 7,150 sections at any sane per-pass section budget would take **years of game time** to complete one lap — unwatchable, and a failure by Aaron's own standard. Because AC-4 makes the audit O(buildings) rather than O(sections), the whole map is audited **every pass**, and the budget lives on the number of transactions actually applied (AC-23). A `consolidatorCursor: number` field is still carried in `SimState` but serves only as a **fairness rotation** so the same high-scoring section cannot win every month while others starve (AC-24).

### C. The density ladder

**AC-7 — consolidation families are derived from the catalogue, not hand-listed.**
```ts
type CapacityField = 'residents'|'jobs'|'children'|'served'|'mw'|'wasteCapacity'|'processCapacity'|'tourism'|'capacity';
function capacityFieldOf(sp: Spec): CapacityField | null   // first present, in the order above
function capacityOf(sp: Spec): number                      // capacityAtTier(sp, 0) for tiered specs (data.ts:356)
function tilesOf(sp: Spec): number                         // sp.w * sp.h
function tileDensityOf(sp: Spec): number                   // capacityOf / tilesOf
function familyKeyOf(sp: Spec): string                     // `${sp.kind}|${capacityFieldOf(sp)}|${sp.tag ?? ''}|${sp.stage ?? ''}`
```
The `tag` and `stage` components are **load-bearing, not decoration**: `wat_clean` (tag `clean`) and `wat_waste` (tag `waste`) are both `kind:'water'` with `served`, and are **not interchangeable**; nor are `edu_nursery` (stage `nursery`) and `edu_primary` (stage `primary`).

**AC-8 — the successor rule, stated once, derived from data.**
Spec **B** is a *consolidation successor* of spec **A** iff **all** hold:
1. `familyKeyOf(B) === familyKeyOf(A)`;
2. `canEnterSim(A) && canEnterSim(B)` (neither is a `placeholder`);
3. `capacityOf(B) >= CONSOLIDATOR_MIN_GROUP * capacityOf(A)` — `CONSOLIDATOR_MIN_GROUP = 4` (PLACEHOLDER-balance); a successor must replace a *group*, not a pair;
4. `tileDensityOf(B) >= tileDensityOf(A)` — **never lose density**, which is the whole point of the feature;
5. **B is no more polluting than A**: `!(B.tag === 'pollution' && A.tag !== 'pollution')`;
6. `specUnlocked(state, B)` and `remainingAllowance(state, B) > 0` (AC-27).

The group size is derived, never chosen: `n = Math.ceil(capacityOf(B) / capacityOf(A))` — the number of A-instances whose combined capacity B replaces. A transaction requires **at least `n` instances of A in the section**, so capacity never falls and the player is never gifted free capacity.

**AC-9 — the ladder table is generated, asserted at load, and printed for review; it is never hand-maintained.**
A pure function `consolidationLadder(): Array<{from: string; to: string; groupSize: number}>` derives the whole ladder from `SPECS` by AC-8. A load-time invariant (mirroring `assertResidentialSpecsHaveResidents` / `MET-V852`) asserts every entry satisfies AC-8. A test **snapshots the generated ladder**, so any catalogue edit that silently changes consolidation behaviour fails the build loudly rather than rotting a markdown table.

**AC-10 — capacity-field hygiene is preserved.**
The successor inherits **exactly** the capacity-field family of the group (AC-7 rule 1). The two prior-bug rules stated verbatim in `data.ts` comments are re-asserted as tests: **a non-power spec must never carry `mw`** (it would be summed as grid generation), and **a non-water spec must never carry a water `tag`/`served`** (the waste_depot/estate lesson, `data.ts:1276-1282`, `1345-1355`).

**AC-11 — specs with no capacity field are never consolidated in inc1/inc2.**
`capacityFieldOf(sp) === null` (every `civic` spec, `com_shop`, `com_retail`, `ind_factory`, `farm_*`, most `park`) yields no successor. **`ind_factory` carrying no `jobs` field is a live catalogue gap** — it is Aaron's own "noisy factory" example and cannot be consolidated on capacity today. It is still eligible for **relocation** (inc2, AC-16), which is the part Aaron actually asked for. Raised as ASM-1496.

### D. Multi-level rule and the ceiling

**AC-12 — one rung per section per pass; iteration comes from repeated passes, bounded by four ceilings.**
A section may receive **at most one transaction per pass** (mirroring `evaluateBuildingMonitors`'s one-tier-per-pass, `engine.ts:1149`). Turbines → farm → nuke → XXL therefore happens over **months of game time**, visibly, one rung at a time — not in a single invisible jump. Per-section cooldown `CONSOLIDATOR_SECTION_COOLDOWN_TICKS = 2 * TICKS_PER_MONTH` mirrors `AUTO_SCALE_COOLDOWN_TICKS` (`engine.ts:971`).

The four ceilings that stop the city collapsing into one building:
- **CEIL-1 (locality).** In inc1/inc2 a group must lie wholly inside **one** section. Cross-section grouping is inc3 only, and even then bounded by CEIL-3.
- **CEIL-2 (no net sprawl).** `tilesOf(successor) <= sum(tilesOf(group))`. Guaranteed by AC-8 rule 4 at equal capacity, but asserted independently so a future catalogue edit cannot smuggle sprawl through.
- **CEIL-3 (resilience share) — the real ceiling.** No single building may end a transaction carrying more than `CONSOLIDATOR_MAX_FAMILY_SHARE = 0.5` (PLACEHOLDER-balance) of the city's **online** capacity in its family. This is derived from state, not from a magic list, and it has a game reason: one bulldoze, one road cut, or one outage must never take out most of a service. It is what makes "one XXL nuke for the whole city" refuse itself.
- **CEIL-4 (unique cap).** `remainingAllowance(state, B) > 0` — AC-27.

### E. The adjacency model

**AC-13 — a named, deterministic, state-derived score: `layoutScore`.**
```ts
interface LayoutScore {
  commute: number;   // homes ↔ jobs proximity      (higher is better)
  nuisance: number;  // pollution ↔ homes/schools/health separation (higher is better)
  amenity: number;   // parks ↔ schools/homes proximity (higher is better)
  density: number;   // capacity per used tile
  count: number;     // building-count economy (fewer, bigger — AC-9(b))
  total: number;     // weighted sum, integer
}
function layoutScore(s: SimState, audit: SectionAudit): LayoutScore
```
Terms, all integer arithmetic over state:
- **commute** — for each residential building in the section, the Chebyshev tile distance to the nearest **online** job-bearing building (`kind` in `office | industrial | commercial`), clamped at `COMMUTE_MAX_TILES = 40` (PLACEHOLDER); scored as `(COMMUTE_MAX_TILES - d)`, weighted by that building's residents. *This is Aaron's "offices near where people live" and "we want to reduce commute".*
- **nuisance** — for each building with `tag === 'pollution'`, a penalty per residential/school/health building within `NUISANCE_RADIUS_TILES = 6` (PLACEHOLDER). *Aaron's "no noisy factories where people live".*
- **amenity** — a reward per school and per residential building with a `kind:'park'` building within `AMENITY_RADIUS_TILES = 4` (PLACEHOLDER). *Aaron's "parks near schools and homes".*
- **density** — `sum(capacity) / tilesUsed` for the section.
- **count** — `-buildingIds.length`, weighted by `COUNT_WEIGHT` (PLACEHOLDER). *Aaron's "less dumped down"; BUG-642's "per-tick cost is O(buildings)".*
- **distribution** (implicit in commute + amenity) — because commute and amenity both reward *proximity to the served population*, clustering every school in one place scores badly automatically. *Aaron's "all schools in one location does not make sense"* falls out of the model rather than needing a separate rule.

Weights `LAYOUT_WEIGHT_COMMUTE / _NUISANCE / _AMENITY / _DENSITY / _COUNT` are named exported constants, **PLACEHOLDER-balance, directional only**.

**AC-14 — the score is deterministic: no clock, no randomness, no map-range-with-break.**
- No `Date.now`, no `Math.random`, no `performance.now`, no `localStorage`, no I/O anywhere in the consolidator path (GR#21). A test greps the consolidator module and fails on any of them.
- **No `for (const x of someMap) { ... break; }`** — the recurring GR#21 blind spot: `Map`/`Set` iteration order plus an early exit is a nondeterminism source. Every consolidator iteration is either an **order-independent fold** or a walk over an **explicitly sorted array**. Section keys are visited in ascending numeric order; building ids in ascending numeric order (the `engine.ts:2215` precedent); candidate transactions sorted by `(score delta desc, sectionKey asc, lowest building id asc)` with **no ties possible** at the final key.
- A test asserts the pass's chosen transaction list is byte-identical when the same `SimState` is passed twice, and when `s.buildings` is presented in a shuffled array order.

**AC-15 — the score is reported, not just used.**
Every applied transaction records `score.before` and `score.after` in its log entry (AC-22). A transaction whose `total` does not strictly improve is **never applied** — `after.total > before.total + CONSOLIDATOR_MIN_SCORE_GAIN` (PLACEHOLDER `0`) — so the consolidator can never churn the map for no gain, and a stalled city visibly stops acting.

### F. Relocation and safety

**AC-16 — relocation (R3) is inc2, and is scored, not heuristic.**
A relocation transaction demolishes a building and rebuilds the **same spec** at a different site whose `layoutScore` for both the source and destination sections is strictly better in aggregate. It uses the same atomic transaction machinery as consolidation (AC-17) and the same economics (AC-18) — full build cost paid, scrap recovered, because Aaron ruled it "a real investment decision, never a free gift".

**AC-17 — every transaction is atomic and validated before any mutation.**
Following the `stampRegion` precedent (`engine.ts:4071-4072`): plan the whole transaction (group to demolish, successor spec, target site, connector, net cost), run **every** gate, and only then produce the new state in one step. There is no intermediate `SimState` in which the group is gone and the successor is not yet placed. A rejected transaction returns the input state **by reference identity**.

**AC-18 — capacity never dips.**
By AC-8 the successor's capacity ≥ the group's. Asserted per transaction as a hard gate on the actual instances involved (using `capacityAtTier(sp, b.capacityTier ?? 0)`, `data.ts:356`, so an auto-scaled building's *real* current capacity is counted, not its tier-0 base). A tiered group member's earned tiers are **capacity that must be replaced** — the consolidator must not quietly delete auto-scale progress.

**AC-19 — never strand a building; never break road connectivity.**
Reusing `planRoadReplanCascade`'s existing checks (`engine.ts:2947-3007`):
- Compute `onlineBefore = { b.id | isOnline(s, b) }` over the affected neighbourhood **once**, before the transaction.
- After the candidate transaction, recompute `computeRoadConnectivity` and `isOnline` for the same set. **If any building that was online before is offline after, the transaction is rejected wholesale.**
- The successor is sited so that it is road-adjacent or `autoConnect`-able, and `autoConnect` is run for it exactly as `case 'place'` does (`engine.ts:3288`) — including the `prebuiltBoard` optimisation so the check is not O(buildings) per candidate.
- Note the contrast with plain `bulldoze` (`engine.ts:3849`), which performs **no** stranding check at all. The consolidator must be strictly safer than the player's own bulldozer, because the player did not ask for this particular demolition.

**AC-20 — protected classes the consolidator never touches.**
- Everything in `CONNECT_EXEMPT_KINDS` (`engine.ts:2004`): `road`, `motorway`, `rail`, `station`, `pylon`. Roads are FEAT-1972079928's territory; two autonomous actors on the road graph is a collision hazard.
- `kind: 'landmark'` — one-off set pieces (`land_airport` is 70×70; `land_space`, `land_tunnel`).
- Any building still under construction (`s.tick - (b.builtTick ?? 0) < constructionTicks`) — demolishing a half-built building the player is watching is indefensible.
- Any building carrying a `capacityTier > 0` **cooldown** from `evaluateBuildingMonitors` (`lastAutoScaleTick` within `AUTO_SCALE_COOLDOWN_TICKS`) — do not fight the auto-scaler.
- `placeholder` specs (guaranteed by `canEnterSim`).

**AC-21 — player-placed buildings may be touched, but never invisibly.**
`Building` gains `placedBy?: 'player' | 'auto'`. **Old saves have no field, and `undefined` must be read as `'player'`** — the conservative default (GR#16: never trust stored data to be shaped as the type claims). Under R3 and the FEAT-1972079928 precedent the consolidator **may** demolish and relocate player-placed buildings without confirmation, but:
- every such building appears in the pass log entry with `wasPlayerPlaced: true`;
- the Consolidator tab's pass summary states the count explicitly ("3 buildings, 1 of them yours");
- Undo restores it with its **original id, spec, coordinates, `capacityTier`, `builtTick` and `placedBy`** (AC-24).

### G. Economics

**AC-22 — pay the build cost, recover the scrap, through the normal money path.**
- Build charge: `sum(placementCost(successorSpec))` — using `placementCost` (`data.ts:251`), **never `sp.cost`**, so the zoning-is-free rule is honoured automatically.
- Scrap: `Math.round(placementCost(def) * CONSOLIDATOR_SCRAP_FRACTION)` per demolished building, with `CONSOLIDATOR_SCRAP_FRACTION = 0.5` (**Aaron's placeholder, R2**). **Derived from the spec's own cost — no magic figure appears in logic** (GR#15).
- `netCost = buildCost - scrapRecovered`. `cumulativeCapexSpent += buildCost` (gross, matching `case 'place'` and `stampRegion`, `engine.ts:4093`).
- Booked as **flow lines**, following `'Building Auto-Scale'` (`engine.ts:1285`): outflow `'Consolidation'`, inflow `'Consolidation Scrap'` — so `conservation.funds-vs-flows` (`consistency.ts:423-425`) holds at the tick boundary. A test asserts conservation over 400 ticks with the consolidator active.

> **⚠ FINDING FOR AARON (§12 Q100101).** `placementCost` returns **£0 for every `zones` spec** — residential, commercial, industrial, office, mine, park. So R2's economics has **no effect at all on the zoned half of the city**: consolidating housing is free and scraps nothing. R2 bites only on `services` and `network` — which happens to be exactly Aaron's own examples (turbines, nuke plants, dams), so inc1 is unaffected. It matters from inc3, when residential/office consolidation lands.
>
> **⚠ SECOND FINDING (§12 Q100102).** Aaron's 50% scrap **differs from the player's own bulldozer**, which refunds **25%** (`Math.round(placementCost(def) * 0.25)`, `engine.ts:3869`). As specified, the consolidator gets a better scrap rate than the player doing it by hand. **Recommendation: keep them separate constants and let Aaron rule** — a single `SCRAP_FRACTION` would silently double every hand-demolition refund in the game, which is a balance change nobody asked for.

**AC-23 — a background process can never cause insolvency.**
Before any mutation, the transaction is rejected unless **all** hold:
1. `!state.administrationState` (mirroring `case 'place'`'s hard block, `engine.ts:3243`);
2. `state.funds >= netCost`;
3. `state.funds - netCost >= INSOLVENCY_WARNING_THRESHOLD` (`fiscal.ts:351`) — the consolidator may spend **down to** the warning band but never **through** it. A player may bankrupt themselves; a background process may not do it for them.
4. `insolvencyStateForFunds(state.funds)` (`fiscal.ts:358`) is the healthy band.
When funds are short the transaction is **skipped entirely, never partially applied**, and the reason is recorded honestly in the log — `'insufficient funds'` vs `'action budget'` vs `'no successor'` vs `'would strand'` must be distinguishable. This mirrors `placePlanItem`'s `cappedByUnitLimit` contract (`engine.ts:3187`): **never blame a perf guard on funds.**

**AC-24 — at most ONE ledger row per pass (the BUG-400 trap).**
`LEDGER_CAP = 200` (`engine.ts:104`) and the ledger is the player's finance history. A per-building or per-transaction ledger row from a monthly background process would **evict the player's own rows** — exactly the BUG-400 defect (`Regional Grant` every 30 ticks), which was fixed by removing the recurring row and routing it through flows. The consolidator therefore writes **at most one aggregate row per pass** — `'Consolidation (N sites)'` with the pass's `-netCost` — and only when `netCost !== 0`. The per-building detail lives in `consolidatorLog` (AC-25), which has its own cap and does not share the ledger's ring.

### H. Action log and Undo

**AC-25 — the action log is its own capped structure on `SimState`.**
```ts
interface ConsolidationRecord {
  id: number; spec: string; x: number; y: number;
  capacityTier?: number; builtTick?: number; placedBy?: 'player'|'auto';
}
interface ConsolidationPass {
  id: number; tick: number;
  transactions: Array<{
    sectionKey: number;
    kind: 'consolidate' | 'relocate';
    removed: ConsolidationRecord[];
    added: ConsolidationRecord[];
    buildCost: number; scrapRecovered: number; netCost: number;
    scoreBefore: LayoutScore; scoreAfter: LayoutScore;
  }>;
  skipped: Array<{ sectionKey: number; reason: string }>;
}
```
`SimState.consolidatorLog: ConsolidationPass[]`, newest-first, `.slice(0, CONSOLIDATOR_LOG_CAP)` with `CONSOLIDATOR_LOG_CAP = 20` (PLACEHOLDER). A new **"Consolidator" tab** in `components/left/LeftDock.tsx` (registered alongside the existing `ledger` tab at LeftDock.tsx:66) renders: the enable toggle, the last N passes with their before/after scores and money, the skip reasons, and the **Undo** button. `skipped` is what makes an inactive consolidator explicable rather than mysterious.

**AC-26 — Undo reverses exactly the last pass, and nothing else.**
New action `{ type: 'consolidatorUndo' }`, classified `true` in `isStateAffecting`. It:
- takes `consolidatorLog[0]`, or returns state **by reference identity** if the log is empty (idempotent, never an error);
- removes every `added` building by id;
- restores every `removed` building with its **original `id`, `spec`, `x`, `y`, `capacityTier`, `builtTick`, `placedBy`** — ids are preserved in the record, so `nextId` never moves and `consistency.ts:391 buildings.ids-unique` still passes (asserted by test);
- reverses the money **exactly**: `funds += netCost`, `cumulativeCapexSpent -= buildCost`, booked as the mirror flow lines so conservation still holds;
- pops the entry off `consolidatorLog`;
- **is single-level.** Once a later pass runs, the earlier one is no longer undoable — Aaron said "the last pass". The button is disabled with a title explaining this when `consolidatorLog` is empty.
- Removes any auto-connect road the pass laid **only if** doing so passes the AC-19 stranding check; otherwise the connector stays and the log entry says so (an honest partial-undo note beats a broken road graph).

**AC-27 — Undo and GR#27.**
**A consolidator pass is not a wipe, and neither is Undo.** Neither clears the map, the journal, nor the savepoint history, so `captureBeforeWipe` (`captureBeforeWipe.ts:136`) is **not** invoked by either and GR#27's fail-closed gate does not apply. The corollary is stated explicitly so no one adds a spurious capture: because both the pass (via `tick`) and the Undo (via its own journalled action) are in the journal, **any later genuine wipe's pre-wipe capture already contains the full consolidator history**, and a genesis replay reproduces the pass and its undo in order. A test asserts `captureBeforeWipe` is not called during a pass or an Undo.

### I. The unique-building flag (Five Gorges Dam)

**AC-28 — `maxPerCity` is a data field, not an `if (spec === 'pow_hydro')`.**
`Spec` gains `maxPerCity?: number`. `pow_hydro` (`data.ts:1283`) gains `maxPerCity: 1`. The allowance is **derived from state, never stored** (so it can never desync — GR#3):
```ts
function remainingAllowance(s: SimState, sp: Spec): number
// sp.maxPerCity == null ? Infinity : Math.max(0, sp.maxPerCity - countOfSpec(s, sp.id))
```
`countOfSpec` counts **under-construction buildings too** — otherwise two dams can be started in the same tick. It is `memoOnState`-memoised (BUG-642: it must not be an O(buildings) walk inside a palette render loop over ~150 specs).

**AC-29 — every placement path honours it. All of them.**
- `isPlaceable(s, sp)` (`data.ts:1071`) gains `&& remainingAllowance(s, sp) > 0` — this alone greys the palette via the existing `BottomBar.tsx:88-135` path.
- `case 'place'` (`engine.ts:3229`) mirrors it as defence-in-depth (the file's own stated pattern, `engine.ts:3229` comment), returning `placeNotice: 'One per city — Five Gorges Dam already built'`.
- **`case 'stampRegion'` (`engine.ts:4006`) and `case 'placeMany'` (`engine.ts:3367`) currently gate on `canEnterSim` only — a real hole.** Both must honour the allowance, and `stampRegion` must count *within its own batch* so one stamp cannot place two dams.
- **Auto-build:** `placePlanItem` (`engine.ts:3154`) and `findSpot` (`data.ts:3417`) must honour it — R4 says "unplaceable by auto-build".
- **The consolidator** honours it via AC-8 rule 6 / CEIL-4.
A test drives **each** of these five paths against an at-cap city and asserts refusal with an honest reason.

**AC-30 — palette greying: a third chip, not a reused one.**
`BottomBar.tsx` gains an `atCap` state alongside `isPh` and `locked`, rendering a **"One per city"** chip (visually distinct from the amber `Soon` and the `Lv N` chip) with `disabled` set and a title explaining the cap. `sortPaletteItems` (`data.ts:1087`) is extended so an at-cap real spec sorts **after** available real specs but **before** placeholders — it is built, not unavailable-forever.

**AC-31 — old saves that already contain two.**
**Nothing is demolished and no money is clawed back.** Both dams survive, keep generating, and keep their upkeep. `remainingAllowance` clamps at `0` (never negative), so no third may be built by any path. A **one-time** info alert names the over-cap spec and its count on the first tick after load. This is the honest GR#15/GR#16 answer: silently destroying a £5bn player asset on load — or, worse, silently refunding it — is a far worse outcome than a city that is temporarily over its own cap. Asserted by a test that loads a two-dam savepoint, replays 30 ticks, and proves both survive and a third is refused.

### J. Determinism, save, replay

**AC-32 — the pass needs no new journalled action; the toggle and the Undo do.**
The pass runs inside `advance()` at the monthly boundary, so it replays **from the existing `tick` stream** as a pure function of state. Adding a per-pass journal action would be redundant and would risk the "phantom journal tick" hazard. What **must** be journalled is anything a human does: `toggleConsolidator` (AC-1) and `consolidatorUndo` (AC-26). Both are classified in `isStateAffecting` — and the `const _exhaustive: never` at `journal.ts:169` makes forgetting a compile error.

**AC-33 — byte-identical replay, proved with the existing oracle.**
`replayIsDeterministic(journal)` (`genesisReplay.ts:117`) passes on a fixture journal containing: enable → ≥3 consolidation passes → an Undo → ≥1 further pass → disable. Additionally, `stableStringify` (`genesisReplay.ts:87`) of the state after a full genesis replay equals that of a live run of the same actions.

**AC-34 — persistence and old-save defaults.**
`consolidatorEnabled` (default `false`), `consolidatorLog` (default `[]`), `consolidatorCursor` (default `0`), `Building.placedBy` (default `undefined` → read as `'player'`, AC-21) all serialize through the savepoint (`replay.ts:29`) and the snapshot, and all default safely when absent from an old save. **An old savepoint must load with the consolidator OFF** — loading a save must never silently start demolishing the player's city.

**AC-35 — no in-place mutation.**
The consolidator produces new `SimState`/`buildings` objects and never mutates in place, because every `memoOnState` WeakMap key (`data.ts` `memoOnState`; BUG-642, BUG-602, BUG-622) depends on state identity. A test asserts the input state object and its `buildings` array are `Object.is`-unchanged after a pass that applied transactions.

### K. Performance

**AC-36 — monthly cadence, never a per-tick hot path.**
The pass runs only when `tick % TICKS_PER_MONTH === 0`, in `advance()`, immediately after the existing auto-scale block (`engine.ts:1229-1256`) and before `sweepOrphanConnects`. On all other ticks the consolidator costs **zero** — a test asserts the pass function is not entered on a non-boundary tick.

**AC-37 — one O(buildings) fold per pass; nothing nested.**
Per AC-4 the discovery index is a single memoised walk. Candidate evaluation reads only the pre-built index and the hoisted aggregates. **No consolidator code path may call `isOnline`, `isRoadAdjacent`, `isRoadConnected`, `waterCaps`, `serviceCoverageOf`, `wellbeingOf`, `demandFixPlan`, `residentsCapacity` or `totalJobs` inside a loop over sections or buildings** — every such value is hoisted once per pass, exactly as `evaluateBuildingMonitors` hoists `residentsCapacity`/`totalJobs` (`engine.ts:1125-1126`). This rule is asserted by a call-counting test: on the 13k fixture, each of those helpers is entered at most a fixed small number of times per pass, **independent of building count** — the direct BUG-642 regression guard.

**AC-38 — per-pass action budget.**
`CONSOLIDATOR_MAX_TRANSACTIONS_PER_PASS = 4` (PLACEHOLDER-balance), mirroring `MAX_AUTO_SCALE_UPGRADES_PER_PASS = 25` (`engine.ts:962`). Candidates beyond the budget are **not** silently dropped: they are recorded in `skipped` with reason `'action budget'` (the `cappedByUnitLimit` honesty precedent, `engine.ts:3187`) and the fairness cursor (AC-6) advances so a different section leads next month.

**AC-39 — an explicit per-tick budget, gated in CI.**
`CONSOLIDATOR_TICK_BUDGET_MS = 40` (PLACEHOLDER-balance) — the consolidator's own contribution to a **boundary** tick, expressed as a **median over boundary ticks**, never a wall-clock total (the standing rule at `scale-gate.test.mjs:35/89`).
`webconsole/test/scale-gate.test.mjs` is extended so that, with the consolidator **ENABLED** on the 13,000-building fixture:
- `TICK_MEDIAN_BOUND_MS = 400` still holds across all ticks;
- the median **boundary**-tick duration exceeds the median non-boundary-tick duration by no more than `CONSOLIDATOR_TICK_BUDGET_MS`;
- `RENDER_PATH_BOUND_MS = 250` is unchanged.
**BUG-644's lesson is applied directly:** the scale fixture had ~0 water plants, so the gate could never have caught BUG-642. The fixture used here must therefore be **seeded with a consolidatable population** — at minimum several hundred `pow_wind` in clustered sections — or the new gate will be structurally incapable of catching the defect it exists to catch. This is a required part of AC-39, not an optimisation.

**AC-40 — no new async path, no new storage read.**
The pass runs synchronously inside `advance()`, so it rides the existing Web Worker offload (`simWorkerOffloadController.ts`) with no changes and **must not** introduce its own worker message, promise, or timer (the BUG-592 one-in-flight and round-3 clock-runaway constraints). It performs **zero** `localStorage` reads at any frequency (BUG-602; the rule as stated in-code at `QueueDepthHud.tsx:81`).

### L. Errors

**AC-41 — every consolidator error is registry-sourced (GR#7).**
New `MET-*` codes are claimed via `tools/plan/add-error.js` **before** the build dispatch, with owner **`ui.webconsole`** (a `FEAT-`/`BUG-` reservation owner passes the Node check but reddens the Go scanner). Minimum set: a transaction-rejected code carrying the honest reason, an over-cap-on-load code (AC-31), a ladder-invariant-violation code for the AC-9 load-time assertion, and an undo-integrity code (id collision / log corruption). All are created via `codedError(...)`, never bare `throw new Error`.

## 11. Dependencies and collision risks

- **FEAT-1972079928 road re-planning** already demolishes and reroutes roads autonomously. AC-20 keeps the consolidator entirely off the road graph to avoid two autonomous actors on one structure.
- **FEAT-1972079878 auto-scale ladder** runs at the same monthly boundary. AC-20's cooldown rule prevents the consolidator demolishing a building the auto-scaler just upgraded; ordering is fixed (auto-scale first, then consolidator, then `sweepOrphanConnects`) so the sequence is deterministic.
- **FEAT-autoscale-ladder (up-then-out)**, if it lands first, gives buildings a growing footprint. AC-18 already counts `capacityAtTier(sp, b.capacityTier)` rather than the tier-0 base; if that feature also grows `w`/`h`, `tilesOf` must read the **building's** current footprint, not the spec's. Flagged for the inc1 developer.
- **FEAT-2326609752 debug sink / `debugjson.ts`** — AC-5's audit output goes into the debug JSON; keep it inside `compactDebugForArchive`'s trimming rules (`captureBeforeWipe.ts:57`) so the pre-wipe archive does not blow its byte budget.
