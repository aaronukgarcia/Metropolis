## User stories

- **US-1.** As the player, I need to actually **see** an impending-doom warning somewhere I will encounter it in normal play — not merely have the engine internally "know" a warning fired — so the anti-ambush contract (§1.3) is real for the player, not just true of the engine's internal state.
- **US-2.** As the player who has just been shown an impending-doom warning, I need it to be unmistakably about *this* death condition specifically (insolvency vs. ghost-city), with enough information to act on (which metric, how much runway), so the warning is actionable, not a generic "something is wrong" banner.
- **US-3.** As Aaron, I need the minimum warning lead time to be a placeholder I control, not a number a junior invented while making a test pass, so the eventual balance pass is tuning a real, disclosed value rather than discovering an undisclosed one buried in Go.
- **US-4.** As a Destructive agent (per GR#23, "nothing is committed un-attacked"), I need a single end-to-end test proving BOTH death conditions were preceded by a real, correctly-led warning in the same class of run the engine actually produces — not two isolated unit-level proofs that happen to be true in isolation but were never run together — so a cross-cutting requirement (the item's own title says "both death conditions") is actually verified as a cross-cutting property, not assembled after the fact from unrelated tests.

## Scope

The player-visible surface for the two warning signals `engine.projections.md` computes (`MarginToInsolvency`, `MarginToGhostCity`); the `MinWarningLeadMonths` balance-regime data files those signals and both engine-side gates (`engine.finance.md` AC-29, `engine.spiral.md` AC-15) read from; and one cross-cutting end-to-end scenario proving the "firing without prior warning = defect" requirement holds for both death conditions together, not each in isolation.

## Acceptance criteria

### Functional — the UI surface (where/how the player actually sees it)

- **AC-1 (UI-SPEC §4; the warning must reach a real screen, not just engine state).** An impending-doom warning (either condition) surfaces through `ui.alerts` (a registered `engine.projections` consumer per code.json) as a **proactive** alert — the player does not have to remember to open F7/F2 to discover it — matching §1.3's "the player should almost always be able to see trouble coming" read as an obligation on the alerting system, not merely on the existence of a queryable pane. The alert content names which death condition, the current margin (months remaining, or the `Unavailable`/not-yet-relevant state), and is driven by the **same** `MarginToInsolvency`/`MarginToGhostCity`/`WarningLedger` queries `engine.finance.md` AC-29 and `engine.spiral.md` AC-15 gate on — not a separately-computed, UI-local approximation. Check: `go doc ./internal/ui/alerts` (or the applicable UI package) shows an alert type/handler subscribing to `engine.projections`'s warning signal; a passing test asserts that when `engine.projections`'s `WarningLedger` records a qualifying entry, `ui.alerts` produces a corresponding alert record referencing the same metric and month, without requiring any UI-driven poll/refresh action from the test (`grep -rn "func Test.*[Dd]eathWarning.*[Aa]lert\|func Test.*[Ii]mpendingDoom" internal/ui/alerts/*_test.go` or the applicable package). **What a lazy implementation looks like:** a warning that only appears if the player happens to open the F7 projections pane and notice a threshold line has been crossed — this technically satisfies "the data is visible somewhere" while failing §1.3's "almost always... not from surprises" framing, which this item's own brief treats as the point. **False-pass risk:** a test asserting only that F7's chart *can* render a threshold-crossing (already covered by `engine.projections.md` AC-8) would pass a build with no proactive alert at all — this AC's check specifically requires the alert to be produced without a simulated player action, proving it is push, not pull.
- **AC-2 (the alert is driven by the real gate signal, not a UI-local re-derivation — the cosmetic-warning trap, restated for the UI layer).** `ui.alerts`' warning-producing code path calls `engine.projections`'s `MarginToInsolvency`/`MarginToGhostCity`/`WarningLedger` query surface directly; it does not independently recompute "are we near insolvency" from raw `engine.finance`/`engine.spiral` state using UI-local logic. Check: `grep -n "projections\.(MarginToInsolvency|MarginToGhostCity|WarningLedger)" internal/ui/alerts/*.go` (excluding `_test.go`) shows the call; `grep -rn "func Test.*[Aa]lert.*[Dd]rift" internal/ui/alerts/*_test.go` — a passing drift test (per this project's established weakness-pattern-#2 remedy) mutates `engine.projections`'s reported margin via its own registered fake provider and asserts `ui.alerts`' output tracks it, rather than the UI computing its own independent (and possibly silently diverging) answer. **Why this matters given `engine.finance.md`/`engine.spiral.md`'s AC-29/AC-15 checks GR#20's boundary rule (`internal/ui` → `internal/engine` imports are lint-banned) already forces `ui.alerts` to go through `ProjectionsAPI` rather than reaching into `engine.finance`/`engine.spiral` directly — but a determined implementation could still satisfy the import-boundary rule while recomputing a *parallel* estimate from whatever `engine.finance`/`engine.spiral` data it's otherwise allowed to read, producing a UI warning that silently diverges from the one the engine-side gate actually enforces. This AC's drift test is what catches that specific evasion.**

### Functional — the minimum lead time as balance-regime data

- **AC-3 (GR#15; balance-number regime — restated at the cross-cutting level, both values disclosed together).** `data/deathwarnings.json` (the data file `engine.projections.md` AC-20 specifies) carries both `MinWarningLeadMonths` entries — insolvency and ghost-city — each with a distinct placeholder value, a non-empty disclosure comment naming it pending Aaron's balance pass, and a documented rationale for why the two values may differ (insolvency can move in single-month steps via one missed payment; ghost-city moves on a slower demographic timescale — per `engine.projections.md` AC-20's own note). Check: `grep -n "MinWarningLeadMonths" data/deathwarnings.json` shows two distinct entries; a passing loader test (this file's contribution, distinct from `engine.projections.md` AC-20's package-internal loader test) asserts the file parses, both entries are present, both carry non-empty disclosure fields, and the two values are independently settable (changing one does not require changing the other) (`grep -rn "func Test.*[Dd]eathWarningsData" internal/engine/projections/*_test.go` or wherever the shared loader lives). **What a lazy implementation looks like:** a single shared `MinWarningLeadMonths` constant used for both conditions "because it was simpler" — defensible-sounding, but it silently assumes insolvency and ghost-city warrant the same warning lead, which nothing in the spec establishes and which this AC exists to keep an open, disclosed question rather than an accidental default.

### Cross-cutting — both death conditions, proven together (GR#23-aligned)

- **AC-4 (the item's own title, taken literally — "both death conditions", proven in one cross-cutting scenario, not two isolated ones).** A single documented, headless (`harness.headless`-shaped) test scenario runs two independent scripted sub-scenarios in the same test suite run — one driving toward insolvency, one driving toward ghost-city (reusing `engine.spiral.md` AC-9's canonical scripted-shock fixture, ASM-240, for the population side) — and asserts **both** `engine.finance.md` AC-29's and `engine.spiral.md` AC-15's lead-time inequality hold, using each sub-scenario's own real run timestamps, in the same test-suite invocation. Check: `grep -rn "func Test.*[Bb]othDeathConditions\|func Test.*[Dd]eathWarnings.*[Ee]2[Ee]" internal/engine/projections/*_test.go` (or a cross-package integration test file, given this spans three packages) shows a test exercising both. **Why this is not redundant with `engine.finance.md` AC-29 and `engine.spiral.md` AC-15's own per-file checks:** those two checks can each be individually satisfied while the *item as a whole* is still broken — e.g. a code change that fixes insolvency's gate while regressing ghost-city's (or vice versa) would still show two green per-file test suites if nothing ever runs them together and checks both assertions hold in the same commit's build.
