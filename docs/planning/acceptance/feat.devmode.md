## Why this file exists, and how it relates to `feat.debugmode` (read first)

`internal/engine/debug` (FEAT-008, wired into the real binary by FEAT-035) already provides the single source of truth for "is debug on" (`State.IsOn()`), the sticky `DebugTouched` hygiene guarantee, the entity inspector (`InspectEntity`), the fidelity dial, and simple capability gates including `RequireConsole` (`gates.go`) — a console-reachability gate that already exists and is, today, unconsumed by any UI. FEAT-065 is **not** a second debug-mode system. It is:

1. a UI overlay (DoD #1) that consumes `debug.State` to pause the sim and present a command/inspection surface, gated through `RequireConsole`/`requireOn` exactly as every other debug capability is;
2. a UI-level object-metrics browser (DoD #2) that consumes the **existing** `InspectEntity` — this item adds selection/display, not a second inspection mechanism;
3. a genuinely new capability — in-game feedback reaching the BOW (DoD #3) — that has no existing home in `internal/engine/debug` and is this file's most architecturally significant section.

Every criterion below that touches "is dev mode active" or "was this session dev-touched" routes through `debug.State`, never a parallel flag. A criterion satisfiable by a devconsole-local boolean that does not read `IsOn()` is treated as a defect in this file, not a shortcut — this is the same governing principle FEAT-035 applied to itself after SEC-027, and it applies here for the same reason: a dev-only surface that can silently diverge from the one hygiene-flag source of truth is exactly how a debug-touched session ends up not marked.

## Corrections (ASM-468, 2026-08-12)

**ASM-468.** A Destructive round on FEAT-065 found a genuine contradiction between AC-DM1 and the original AC-DM3: AC-DM1 requires `Console.Open` to call the wired `RequireConsoleFunc` (`debug.State.RequireConsole`) *before* anything else and to reject with `ErrDebugRequired` when `IsOn()==false`; the original AC-DM3 then described a branch where the console is opened "via a path where debug was not already on" and `Open`'s own `Enable` call is what turns debug on. In the real composition (`internal/ui/screens/devmode/console.go`'s `Open`), those two claims cannot both hold: step 1 always calls `RequireConsole` first, which always rejects while `IsOn()==false`, so `Open` can never reach its `Enable` call with debug still off — the "enable on first console open" branch is structurally unreachable. `debug.State.Enable` (`internal/engine/debug/state.go`) is also the *only* place `IsOn()` is ever set true, so by the time `RequireConsole` lets `Open` proceed, `Enable` has necessarily already run once via some other path (flag/config/`:debug on`) and `Header.DebugTouched()` is already `true` before the console's own `Enable` call fires. The only test exercising the original AC-DM3 (`TestOpen_TouchesDebugBeforeOpen`, `internal/ui/screens/devmode/console_test.go`) says as much in its own comment: it wires a permissive stand-in `RequireConsoleFunc` that lets `IsOn()==false` through specifically because the real gate would reject the scenario. The implementation (`gates.go`'s `RequireConsole`, `console.go`'s `Open`) is internally consistent with AC-DM1 — this was an acceptance-doc defect, not a code defect, so **AC-DM3 below is corrected to describe achievable behavior instead of a path that cannot exist in real wiring.** No code changes were made as part of this correction. The alternative resolution — narrowing `RequireConsole` (or adding a bypass) so a debug-off console-open really could be the enable trigger — was considered and rejected here as out of scope for a docs-only pass and because AC-DM1's own wording ("before rendering anything ... with debug off, the request is rejected ... never a silent no-op") reads as intentional, not aspirational; if Bill/Aaron judge otherwise, that is a separate, code-bearing decision to route back through the normal dev-team pipeline, not something this correction attempts.

## User stories

- As **a developer or embedded QA tester**, I need to pause the simulation from anywhere and open a console with object inspection, so I can investigate a bug at the exact tick it manifests rather than reproducing it from a fresh boot.
- As **the save-data hygiene contract** (M0-ENG §3, carried forward from FEAT-008/FEAT-035), I need opening the dev console to be indistinguishable, from `DebugTouched`'s point of view, from any other debug-enable path — a save touched via the console is touched forever, exactly like one touched via `--debug` or `:debug on`.
- As **Bill, reviewing this item**, I need the in-game-feedback-to-BOW path to be a real, testable integration boundary with a named failure mode for every step, not a hand-wave — because "capture feedback into the BOW" is a promise about a compiled Go binary talking to a MariaDB-backed Node CLI it cannot itself invoke, and every FEAT-035-shaped lesson this project has already paid for says an unproven wiring claim ships broken.
- As **a release build**, I need every surface this item adds to be unreachable and inert when debug is off, so dev-mode tooling can never become an accidental gameplay mechanic or an accidental data-exfiltration/BOW-spam path in a shipped build.

## Scope

A pause-anywhere debug console overlay (DoD #1) and object-metrics inspector (DoD #2) built on `internal/engine/debug`'s existing gates and `InspectEntity`; a concrete, testable mechanism carrying free-text in-game feedback into a real `claude-bow.js add` invocation (DoD #3); and an explicit dev-only reachability boundary (DoD #4) proving none of the above is reachable with debug off.

## Architecture decision — how in-game feedback reaches the BOW (read before building DoD #3)

Three shapes were considered:

1. **Direct HTTP call from the running game to a local service fronting `claude-bow.js`.** Rejected. It requires a long-running Node/HTTP service to exist and be listening every time anyone runs the game with dev mode on, adds a network listener (however local) to a compiled game binary's dependency surface, and gives a debug-mode-gated code path a live RPC capability into the BOW/MariaDB stack — a materially larger attack surface than this feature needs, for a capability ("submit some text") that has no latency requirement.
2. **The Go binary shells out to `node claude-bow.js add ...` directly (`exec.Command`).** Rejected. `grep -rn "exec.Command" internal/ cmd/` returns **no matches** anywhere in this codebase today — there is no precedent, and introducing the first one specifically to let a compiled game binary invoke a Node CLI (which itself requires a working Node install and MariaDB connectivity on the machine running the game) couples the shipped binary's runtime environment to this project's own internal tooling stack. It would also mean the exact command-injection concerns `dev-team-process.md`'s weakness pattern #4 catalogues (a value reaching shell syntax) become live the moment free-text player feedback is involved.
3. **File-drop: the game writes a structured JSON record to a well-known inbox directory; a separate, already-Node-side companion script polls the inbox and calls `claude-bow.js add`.** **Chosen.** This matches the project's own established convention — `internal/harness/headless`'s `Run`/`writeBundle` already writes a structured bundle to disk that a separate process (`metctl verify`, a Tester, this project's own tooling) reads back; `int.serializer`'s whole `Header`/bundle model is "write it as data, let something else act on it." The Go binary never needs a DB driver, a Node runtime, or network credentials compiled in. It works fully offline — a submission written to disk survives even if nobody happens to be running the import script at that moment, which an HTTP call or a direct shell-out would simply drop or block on. And it keeps the trust boundary exactly where GR#1/weakness-pattern-#4 want it: free-text feedback is treated as **data** written to a file by the gated-and-audited game process, and is only turned into **instruction** (a `claude-bow.js` invocation) by tooling that already owns that responsibility and already validates its own inputs (BUG-090's `--desc-file` convention exists for exactly this "don't let untrusted text reach a shell-interpreted argument" reason — the import script is required to use it, never inline `--desc`).

## Acceptance criteria

### DoD #1 — pause-anywhere debug console overlay

- **AC-DM1.** Requesting the dev console open (a bound key, e.g. `` ` ``, or a palette command) calls `debug.State.RequireConsole` (the existing `gates.go` gate) before rendering anything — with debug off, the request is rejected with the registry-sourced `ErrDebugRequired` FEAT-008 already defines, never a silent no-op, never a panic, and the overlay never appears. **Check:** a test drives the open-console action with a `debug.State` constructed `IsOn()==false` and asserts (a) the overlay's visible/open state is unchanged, (b) the error returned/logged is `ErrDebugRequired` via `RequireConsole`, not a devconsole-local error code. **What a lazy implementation looks like:** the devconsole package defines its own `isDevMode bool` field, set once at boot from whatever flag happened to be passed, and checks that instead of calling `debug.State.RequireConsole` per open-request — this passes a shallow "console doesn't open without debug" smoke test while silently diverging from `IsOn()` the moment debug is enabled or disabled mid-session (exactly the FEAT-035/SEC-027 shape this file's header warns against). The check above rejects this because it constructs the real `*debug.State`, flips `IsOn()` after construction, and asserts the console's gate re-reads it rather than a boot-time snapshot.
- **AC-DM2.** Opening the console when debug IS on pauses the simulation tick loop (via `engine.core`'s existing pause mechanism — `RequireConsole` gates *reachability*, not pausing itself, so the overlay's open-action must itself issue the pause command) and the pause is visible/queryable through the same clock/state surface any other pause already uses — **Check:** a test opens the console against a running (unpaused) engine/harness fixture and asserts the clock reports paused immediately after, using the existing pause-state read, not a devconsole-local "I think I paused it" flag.
- **AC-DM3 (DebugTouched integration — explicit, not implicit; corrected by ASM-468, see "Corrections" above).** Opening the console **always** calls `debug.State.Enable` (with `EnableSource=SourcePalette` — see the logged assumption below) **before** the console is considered open — unconditionally, regardless of whether debug was already on. This is deliberate defense-in-depth, not an "enable on first open" trigger: AC-DM1's `RequireConsole` gate already requires `IsOn()==true` before `Open` can ever reach its `Enable` call, and `Enable` is the only place `IsOn()` is ever set `true` (`state.go`), so by construction `Open` can never observe `IsOn()==false` at the point it calls `Enable` — every real console-open's `Enable` call is the same harmless, idempotent re-touch AC-DM4 describes. What this AC still guarantees, and why it earns its own line rather than folding into AC-DM4: `Open` must never skip the `Enable` call on the reasoning that "debug must already be on, so what's the point" — it calls it every time, before marking the console open, so `Header.DebugTouched()` is proven `true` immediately after every successful `Open` by the code path itself, not left to depend solely on whatever earlier path enabled debug having behaved correctly. **Check:** a test opens the console against a `debug.State` that is legitimately reachable (pre-enabled via the real `Enable`, matching how the console can ever actually be reached per AC-DM1 — never a permissive stand-in gate that admits `IsOn()==false`) with a `WithHeader` wired, and asserts (a) `Open` calls the wired `EnableFunc` before the console is marked open (the ordering assertion the existing test already proves) and (b) the header's `DebugTouched()` reads `true` immediately after `Open` returns successfully. **False-pass warning:** a test that only asserts the console becomes visible/open, without also reading back the header's `DebugTouched()` bit, would still pass an implementation that opens a devconsole-local UI state without ever calling `Enable` at all — this remains the single most important AC in DoD #1 for that reason, even though the "debug was off, opening the console turned it on" framing is retired per ASM-468.
- **AC-DM4.** If debug is already on when the console opens (enabled earlier via flag/config/`:debug on`), opening the console is a harmless re-touch — `Enable`'s own documented idempotency (state.go) is relied on, not reimplemented — **Check:** open the console twice in one session and assert no error, no double-count side effect, and `DebugTouched` stays `true` (it was already true).

### DoD #2 — object-metrics inspection

- **AC-DM5.** The console overlay exposes a selection/query interface (structural existence — a text command, a keyboard-driven picker, or a click-to-select on whatever entity kinds are already selectable in the UI layer; full UI polish is explicitly out of scope, see "Out of scope" below) that, given a resolved entity reference, calls `debug.State.InspectEntity` — the **existing** FEAT-008 mechanism — and renders its returned JSON, rather than building a second inspection/marshalling path. **Check:** a test selects a known fixture entity through the devconsole's selection interface and asserts the JSON rendered on screen is byte-identical (or a formatted superset, e.g. pretty-printed) to what a direct `InspectEntity` call against the same ref returns — proving the UI is a thin consumer, not a reimplementation. **What a lazy implementation looks like:** a devconsole-specific "dump this citizen's fields via reflection" helper that produces output that *looks* like `InspectEntity`'s but bypasses its gating and its `EntityLookup` seam entirely — this would pass a shallow "selecting a citizen shows fields" smoke test while creating a second, ungated entity-inspection path that AC-DM1's "everything routes through the one gate" guarantee does not cover. The check's byte-identity requirement against the real `InspectEntity` call rejects this.
- **AC-DM6.** Selecting an entity kind/ref the wired `EntityLookup` cannot resolve (a bad ref, or a kind never registered) surfaces the registry-sourced error `InspectEntity` already returns (`ErrEntityLookupFailed`/`ErrEntityLookupNotConfigured`), rendered legibly in the console — never a UI crash, never a blank/silent panel. **Check:** a test selects a deliberately-invalid ref and asserts the console renders an error message derived from the returned `*errs.E`, and the process does not panic.
- **AC-DM7.** With debug off, the selection/query interface is not reachable at all (carries `AC-9`'s "none of the unlocks are reachable" forward) — **Check:** with `IsOn()==false`, attempting the selection action is rejected the same way AC-DM1 requires for opening the console itself (the interface cannot be reached without the console, so this is provable as a consequence of AC-DM1, but a dedicated test is required in case a future change adds a second entry point, e.g. a keybind that bypasses the console).

### DoD #3 — in-game feedback captured into the BOW (the architecturally significant section)

- **AC-DM8 (the game writes a structured feedback record to disk — never a direct BOW/DB/exec call).** With debug on, the console exposes a feedback-submission command (free-text input plus, at minimum, an implicit tick number and correlation ID) that, on submit, writes **one JSON file per submission** to a well-known inbox directory (proposed `data/devfeedback/inbox/`, gitignored — confirm/create the ignore entry as part of this item) — never appended to a shared file (concurrent submissions must not corrupt or interleave), never overwritten, and never transmitted over a network or shelled out. The record's schema (minimum fields, exact names are the implementer's call, logged as an assumption if not already fixed here): a schema version, the submission timestamp (via `debug.State`'s injectable `Clock` — **never** a direct wall-clock call, per this package's existing AC-14/GR#21 discipline, since this is a new write path inside the same package), the tick number at submission, a correlation ID, the free-text feedback body, and the header's `DebugTouched` value at submission time (proving the environment was legitimately dev-touched, not forged after the fact). **Check:** a test submits feedback against a `debug.State` with debug on and a fixed injected clock, and asserts a well-formed JSON file matching the schema appears in the inbox directory with the expected field values — including asserting the timestamp came from the injected clock, not `time.Now()` (mirrors AC-DM"determinism" checks below).
- **AC-DM9 (submitting feedback with debug off is rejected, not silently dropped or silently written).** Attempting the feedback-submission action while `IsOn()==false` returns the same `ErrDebugRequired` gate every other capability in this file returns, and writes **no file** to the inbox — **Check:** a test attempts submission with debug off and asserts (a) the registry-sourced error is returned, (b) the inbox directory's contents are unchanged (byte-for-byte, not just "no new file with today's date" — a mutate-the-data-don't-grep-for-it check per this project's verification standards).
- **AC-DM10 (the companion import script: file → real BOW item, with a named failure mode at every step).** A new root-level Node script (proposed `claude-devfeedback-import.js`, following the existing `claude-*.js` naming/testing convention) scans the inbox directory and, for each well-formed record, calls `claude-bow.js add bug "<derived title>" --desc-file <path-to-a-generated-desc-file-or-the-record-itself> --code-path "<a path identifying where in-game the feedback originated, e.g. the active screen>" --codejson feat.devmode` (type `bug` chosen because `claude-bow.js`'s `TYPES` constant — confirmed at dispatch via `grep -n "const TYPES" claude-bow.js` — has no dedicated `feedback` type; this is logged as an assumption below since a reasonable person could argue for `finding` or a future dedicated type instead), **using `--desc-file`, never inline `--desc`**, per BUG-090's own documented reason (free-text player input containing a backtick, `$(...)`, an embedded quote, or a newline must never reach an inline shell-interpreted argument). On success, the script moves the consumed record to a `data/devfeedback/processed/` subfolder (never deletes — auditability, GR#1); on failure (malformed record, `claude-bow.js` invocation fails/exits non-zero), the record is left in `inbox/` and a `.error` sidecar file is written next to it naming the failure, so a submission is never silently lost and never silently retried into a duplicate BOW item on every script run. **Check:** a test runs the import script against a fixture inbox containing (a) one well-formed record and (b) one deliberately malformed record, and asserts: the well-formed one produces a real `claude-bow.js add bug` invocation (verifiable via a stubbed/mocked `claude-bow.js` call in the test, or by inspecting the actual BOW state change if the test environment has the metro DB available) and is moved to `processed/`; the malformed one stays in `inbox/` with a `.error` sidecar naming the parse failure, and does **not** produce a BOW call. **False-pass warning:** a test that only asserts "the script ran without throwing" is not sufficient — it must assert the BOW-add invocation actually happened (or was actually attempted with the correct arguments) for the well-formed case, since a script that silently no-ops on every record would also "run without throwing."
- **AC-DM11.** Re-running the import script when the inbox is empty, or when it contains only already-`processed/` records, is a no-op — no duplicate BOW items are created — **Check:** run the script twice against the same fixture inbox and assert exactly one `claude-bow.js add` invocation total, not two.

### DoD #4 — dev-only reachability boundary

- **AC-DM12.** None of DoD #1–#3's surfaces are reachable through any path that does not first pass through `debug.State`'s existing gates (`RequireConsole`, `requireOn`, or `IsOn()` directly) — **Check:** a code-level review/grep at Tester time confirms every entry point into the devconsole package's exported API either calls into `internal/engine/debug` for its gate check or is itself gated by a caller that does. A criterion satisfied by "the console just isn't wired into `main` yet" is explicitly insufficient — carrying forward FEAT-035's own lesson, wiring must be proven via an integration test that boots the real construction path (mirroring FEAT-035's AC-M1 shape), not asserted by absence of a call site.
- **AC-DM13.** A release build (default flags/config, no `--debug`, no `:debug on`, no dev-config file present) cannot open the console, cannot reach the object inspector, and cannot submit feedback — **Check:** an integration test boots the real binary entry point with no debug enable path exercised and asserts all three actions are rejected with `ErrDebugRequired`, mirroring AC-E2's "release-default-off" proof in `feat.debugmode.md`'s FEAT-035 section. **What a lazy implementation looks like:** a build-tag-gated devconsole package (`//go:build devmode`) that is simply not compiled into the release binary at all. This looks safe but is a **regression** against this file's own governing principle carried from FEAT-008/FEAT-035: debug support must be a **runtime switch**, present in every build and off by default (see `feat.debugmode.md`'s "Debug is a runtime switch, not a build flavour" section) — a build-tag approach would mean a QA build and a shipped build are different binaries, reopening exactly the "passes locally, fails on CI/in the wild" class of defect `CLAUDE.md`'s Docker/WSL section and this project's own history (BUG-004) already paid to learn to avoid. If DoD #1–#3 are build-tag-gated instead of runtime-gated, that is a deviation from this file and must be escalated to Bill, not silently built.

### Documentation

- **AC-DM14.** The devconsole package's doc comment states its module key (the proposed `feat.devmode`, or whatever Bill confirms), cites this file and `feat.debugmode.md`, and explicitly states that it is a thin consumer of `internal/engine/debug`'s gates/inspector — never a second gating mechanism — so a future contributor does not "helpfully" add a devconsole-local debug flag.
- **AC-DM15.** The companion import script's header comment documents the file-drop architecture decision (this file's "Architecture decision" section, summarized) and the `--desc-file`-only rule, so a future edit does not "simplify" it back to inline `--desc` and reopen BUG-090's class of defect.

### Golden Rules

- **AC-DM16 (GR#21 determinism).** Opening the console, pausing, inspecting an entity, and submitting feedback never retroactively change already-committed simulation history, and none of DoD #1–#3's new code paths call the wall clock directly outside the injected `Clock` seam — **Check:** `grep -rn "time.Now" internal/ui/screens/devconsole/*.go` (excluding `_test.go`) returns no matches; a determinism-style test pauses/inspects/submits feedback mid-run and asserts the resulting tick-stream/state is unaffected by those actions themselves (as distinct from a cheat's own effect, out of scope here — no cheat invocation is part of this file).
- **AC-DM17 (GR#1, error trapping on every new boundary).** Every new failure point this file introduces — a malformed feedback record, an inbox directory that doesn't exist or isn't writable, a `claude-bow.js` invocation that fails — surfaces a registry-sourced `*errs.E` on the Go side (a new error code range for the devconsole package, following the same `data/errors.json`-registered convention `internal/engine/debug/errors.go` documents, exact range TBD at dispatch) and a clearly logged, non-silent failure on the Node side (matching this session's `claude-*.js` house convention of typed, correlation-ID-bearing error output) — never a bare `catch {}` or an unhandled promise rejection swallowing an import failure.

## Out of scope

- Full UI/visual polish of the console, selection picker, or inspector rendering (fonts, layout, scroll, syntax highlighting) — DoD #1/#2 require structural existence and correct gating, not a finished UI. Follow-up polish is a separate item.
- `internal/engine/debug`'s own already-tested internal behaviour (cheats, fidelity dial, `InspectEntity`'s own marshalling correctness) — unchanged, already covered by `feat.debugmode.md`.
- A dedicated `feedback` BOW item type in `claude-bow.js`'s `TYPES` — this file assumes `bug` (see AC-DM10's inline note and the logged assumption below); adding a first-class type is a `tool.bow`-owned change, not this item's.
- Any UI for browsing/triaging submitted feedback from inside the game — the BOW itself (via `/bow` or `claude-bow.js list`) is the triage surface once a submission lands there.
- Multiplayer/networked feedback aggregation, remote telemetry, or any submission path other than the local file-drop — this project has no networked multiplayer surface today and none is assumed here.
