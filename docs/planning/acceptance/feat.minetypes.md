# Acceptance criteria — feat.minetypes (FEAT-103)

**BOW code:** FEAT-103 (P2, open) — "Mine types — extractive facility catalogue."
**Spec refs:** §32 Mining, Extraction & the Blight Model (`docs/METROPOLIS-MASTER-v2.1.md` lines 449-462: the six extraction types table at 453-460 — chalk quarry, sand & gravel pit, brickworks clay pit, ragstone quarry, deep coal mine (headgear + spoil tip + subsidence risk radius + mining-jobs culture), offshore dredger — and the general blight model at 462, which this catalogue feeds); §34 Zoning (line 480-482: the **Mining** zone type, "only on revealed geology, §32" — the siting gate this catalogue's types must satisfy); §17 Resource Consumption Model (line 324: "Farms, quarries, plants: producer coefficients in catalogue (output/day, input demands, land, seasonal profile)" — the per-type producer-coefficient precedent); `docs/planning/resources-design-brief.md` §2 (the subsurface deposit model this catalogue's deposit-backed types consume) and §9 (deep-mine depletion → §32 closure); code.json `engine.mining` entry (inbound `BlightAPI`, pattern "any module registers blighting objects; viewshed computed from WorldAPI elevation"); the parent acceptance files this file cross-references rather than restates: `engine.mining.md` (MOD-046 — AC-2's "six extraction types, geology-gated", AC-1's `BlightAPI`, AC-3's deep-coal subsidence), `feat.resourcedeposits.md` (FEAT-049 — the `Deposit` record and its `DepositType` taxonomy), `feat.extraction.md` (FEAT-051 — the tier ladder that draws down a deposit at a type's output rate).
**Date:** 2026-08-16 (BA, first pass; pipelined ahead per dev-team-process.md)
**Status:** draft-ahead — `MOD-046` (`engine.mining`) is `open` with no code yet, and `FEAT-049` (`feat.resourcedeposits`) is `in_progress`, itself gated on `MOD-046`. This item is not in the ready queue until `engine.mining`'s own siting/`BlightAPI` surface exists (AC-1 below). The feature has **no code.json registration** (`feat.minetypes` is absent from code.json — see Escalations ES-1).
**Package under test:** `internal/engine/mining/` (shared with `engine.mining`/MOD-046, `feat.resourcedeposits`/FEAT-049 and `feat.extraction`/FEAT-051; the mine-type catalogue is a file/type set inside the same package, not a fork — ASM-672).
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/mining/...`.
**Balance-number regime (standing rule, same convention as `engine.mining.md` AC-2/AC-3, `feat.maintenance.md` AC-2):** every per-type figure — footprint (cells), output rate (t/day), blight class, jobs (mining-jobs-culture headcount), and depth band — is a **placeholder** in a data file (`data/minetypes.json`, ASM-670), each carrying a disclosure comment naming it pending Aaron's balance pass. No AC may be satisfied by a junior inventing a final number; every AC touching a per-type figure requires the value to live in the data file and requires tests to check **shape/direction/distinctness** (two types differ; a field is present and typed; data actually loaded), never a specific magnitude.

## The load-bearing rule (this file exists to enforce it)

Each mine **type is a distinct modelled facility** — its own footprint, output, blight class, jobs, and depth band — **never one shared row keyed by a type string**. A single `MineType` struct carrying a `Type string` discriminator with every other field defaulted (or a `map[string]MineType` where all values share one footprint/output/blight/jobs/depth and only the key differs) is the anti-pattern this file's AC-2/AC-4 are written to fail. Two same-category types (e.g. chalk quarry and deep coal mine) must resolve to **two different parameter sets from data**.

## User stories

- **US-1.** As a mine type (chalk quarry, sand & gravel pit, brickworks clay pit, ragstone quarry, deep coal mine, offshore dredger), I need my own footprint, output, blight class, jobs, and depth band — not a generic "mine" row with my name stamped on it — so siting me has type-specific consequences, not one shared consequence with a cosmetic label (load-bearing rule).
- **US-2.** As `engine.mining`'s siting surface (MOD-046 AC-2), I need the six §32 extraction types resolved from a typed catalogue whose availability is gated by `engine.world`'s prospected-geology query, so "mining only where geology permits" reads the same type identities this file authors, not a parallel list.
- **US-3.** As a `feat.resourcedeposits.md` `Deposit` record (FEAT-049), I need each deposit-backed mine type to declare the deposit class and depth band it is compatible with, so a deep coal mine can only ever draw down a coal-class deposit at coal depth — never chalk, never a shallower band (the "uranium doesn't sit in the chalk" discipline extended to extraction).
- **US-4.** As a deep coal mine specifically, I need my spoil-tip footprint and subsidence-risk radius carried as my own parameters (distinct from the noise/viewshed blight every blighting object shares), so `engine.mining.md` AC-3's subsidence check has a real per-type source to read.
- **US-5.** As `engine.mining`'s `BlightAPI` (MOD-046 AC-1), I need each mine type to carry a blight class that registers against the general blight model like any other blighting object, so mine blight is the same mechanism heavy industry/abattoir/landfill use, not a mine-local copy.
- **US-6.** As a balance designer (Aaron, GR#15), I need every per-type figure to live in `data/minetypes.json`, editable without a rebuild, so a future balance pass on "how blighting is a chalk quarry vs a deep coal mine" is a table edit, never a code change.

## Scope

The mine-type catalogue itself: six typed facility entries (the §32 extraction types), each resolving to a distinct parameter set — footprint, output commodity + rate, blight class, jobs headcount, depth band, and a compatibility gate (geology class for bulk types, deposit class for deposit-backed types). Data file `data/minetypes.json`; typed resolver in `internal/engine/mining/`. Does **not** include: `engine.mining.md`'s own `BlightAPI`/noise/viewshed/siting/reclamation machinery (MOD-046); the subsurface `Deposit` model and shuffle (FEAT-049); the extraction tier ladder and depletion draw-down (FEAT-051); `engine.world`'s geology layer (consumed, not authored); the build-catalogue entries for these structures (`data.catalogue`/`data/buildings.json` — see ASM-692).

## Acceptance criteria

### Functional — the typed catalogue surface

- **AC-1 (GR#20; typed resolve surface, no shared row).** A mine-type catalogue exists on `internal/engine/mining` exposing a typed resolve surface (e.g. `MineTypeResolve(typeKey) (MineTypeParams, error)` or equivalent) that returns a **distinct parameter struct** per type — footprint, output, blight class, jobs, and depth band are all named, typed fields on the resolved value, not a `Type string` field whose presence substitutes for the parameters themselves. Check: `go doc ./internal/engine/mining` shows a `MineType`/`MineTypeParams` type with named footprint/output/blight/jobs/depth fields; `grep -rn "Type string\|typeKey.*string" internal/engine/mining/minetype*.go` (excluding `_test.go`) finds no bare type-string discriminator on the parameter struct — the type key is a lookup key, not a field of the parameter set.

- **AC-2 (load-bearing — two types resolve to two different parameter sets from data).** Two same-category types — chalk quarry and deep coal mine — resolve to **two different parameter sets**, and the distinguishing fields are each actually populated AND differ: footprint, output rate, blight class, jobs, and depth band are all pairwise non-equal across the two. A companion isolation assertion proves the difference is data-sourced, not a hardcoded per-type Go literal: mutating one type's footprint in the loaded `data/minetypes.json` fixture changes only that type's resolved footprint (the other type's byte-identical before and after), and the change flows from data, not from a switch/case in code. Check: `grep -rn "func Test.*[Dd]istinct.*[Pp]aram\|func Test.*[Tt]woTypesDiffer\|func Test.*[Cc]halkVsCoal" internal/engine/mining/minetype*_test.go`; `grep -rn "func Test.*[Ii]solat.*[Mm]inetype\|func Test.*[Ss]ingleTypePerturb" internal/engine/mining/minetype*_test.go`. **False-pass risk (the anti-pattern this file exists to kill):** a `map[string]MineTypeParams` where every entry shares one default footprint/output/blight/jobs/depth and only the map key differs would pass a naive "the catalogue has N mine-type entries" grep while violating the "distinct modelled facility" premise — the check requires the resolved *parameters* to differ between two named types, not merely that two keys exist.

- **AC-3 (§32 taxonomy completeness; GR#15 data-derived count).** All six §32 extraction types (chalk quarry, sand & gravel pit, brickworks clay pit, ragstone quarry, deep coal mine, offshore dredger) are present as distinct entries, each resolving to a non-zero output rate. The expected type set is derived from a data/manifest source, never a hardcoded six-element literal in the test (GR#15). Check: `grep -rn "func Test.*[Tt]axonomy\|func Test.*[Ss]ixTypes" internal/engine/mining/minetype*_test.go`; `grep -n "chalk\|sand\|brick\|ragstone\|coal\|offshore\|dredger" data/minetypes.json` matches all six families.

### Functional — per-type parameters

- **AC-4 (GR#15; every figure data-driven, no hardcoded literals).** Every per-type figure (footprint, output rate, blight class ordinal, jobs, depth band) loads from `data/minetypes.json`, none hardcoded as a Go numeric literal, and the data is *actually read* — a test mutates a value in the data file between two runs with the same seed and asserts the resolved parameter reflects the change. Check: `grep -rn "0\.[0-9]\+\|[0-9]\{2,\}" internal/engine/mining/minetype*.go` (excluding `_test.go`, array indices, enum ordinals) shows no bare balance-shaped numeric literals; `grep -rn "func Test.*[Dd]ataDriven.*[Mm]inetype\|func Test.*[Rr]eload.*[Mm]inetype" internal/engine/mining/minetype*_test.go`. **Balance-regime note:** the specific magnitudes are placeholders with disclosure comments (AC-11); this AC checks the values are *data-sourced and consumed*, not any magnitude.

- **AC-5 (per-type depth band + compatibility gate — deposit-backed vs geology-gated bulk).** Each mine type declares (a) a depth band (min/max, matching `feat.resourcedeposits.md` AC-2's realistic-depth discipline) and (b) its sourcing gate: a `geologyClass` requirement (`engine.world`'s chalk/clay/sand-gravel/deep-coal-eastern classification, per `engine.world.md` AC-6) for bulk types, and/or a `depositClass` requirement (a `feat.resourcedeposits.md` `DepositType`) for deposit-backed types. The deep coal mine must declare the coal deposit class and the deep depth band; the chalk quarry declares the chalk geology class and a shallow band. Check: `go doc ./internal/engine/mining` shows a depth-band and compatibility-gate accessor on the resolved params; a passing test asserts deep-coal resolves to the coal `depositClass` + deep band while chalk resolves to the chalk `geologyClass` + shallow band, and that the two compatibility gates are not the same field (`grep -rn "func Test.*[Dd]epthBand\|func Test.*[Cc]ompatibilityGate\|func Test.*[Gg]eologyVsDeposit" internal/engine/mining/minetype*_test.go`). **False-pass risk:** a single "source" field that treats geology and deposits interchangeably would let a deep coal mine silently consume a chalk-geology bulk cell — the check requires the two gate kinds to be distinct, matching `engine.mining.md` AC-2's geology-gated siting and `feat.extraction.md` AC-4's deposit draw-down as *different* mechanisms.

- **AC-6 (deep coal's spoil tip + subsidence radius + jobs culture, as its own parameters).** The deep coal mine entry carries a documented spoil-tip footprint and a subsidence-risk radius (data-sourced magnitude) as parameters **distinct from** the noise/viewshed blight fields every blighting type shares — matching `engine.mining.md` AC-3's requirement that subsidence is a separate risk flag, not part of the viewshed/noise effect. It also carries a jobs headcount materially larger than a bulk quarry's (the "mining-jobs culture" §32 names). Check: `go doc ./internal/engine/mining` shows a subsidence-radius and spoil-tip accessor separate from the blight accessors; a passing test asserts deep-coal's subsidence radius and jobs are nonzero and greater than chalk quarry's, and that the blight-class field is a *separate* field from the subsidence field (`grep -rn "func Test.*[Ss]poilTip\|func Test.*[Ss]ubsidenceRadius\|func Test.*[Dd]eepCoalJobs" internal/engine/mining/minetype*_test.go`). **False-pass risk:** folding subsidence into the generic blight class (a deep coal mine is just "high blight") would pass `engine.mining.md` AC-3's "a distinct risk flag exists somewhere" only by accident — this AC pins the subsidence/spoil-tip/jobs figures to the deep-coal *type entry* specifically.

### Error handling

- **AC-7 (GR#7; unknown type / malformed data — no silent default).** Resolving an unknown mine-type key, or loading a `data/minetypes.json` that fails schema validation (a type missing its footprint or output, a negative jobs count, an unknown blight-class enum value, a dangling deposit/geology class ref, a field of the wrong JSON type — GR#16), produces a registry-sourced error (a new `MET-`-range code claimed at build time) — never a panic, and never a silent default-substituted parameter set that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/mining/minetype*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownMineType\|func Test.*[Mm]alformedMinetypes\|func Test.*[Ww]rongTypeMinetypes" internal/engine/mining/minetype*_test.go`) — **GR#7 assertion, stated explicitly:** the test asserts the returned error's registry code matches the claimed `MET-` code AND that no partially-loaded or default-substituted catalogue was produced as a side effect, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-8 (GR#21).** Loading and resolving the mine-type catalogue is a deterministic function of `(data file, type key)` — loading the same `data/minetypes.json` twice produces byte-identical resolved parameter sets, and resolution never depends on map-iteration order. Check: `grep -rn "func Test.*[Dd]eterminis.*[Mm]inetype" internal/engine/mining/minetype*_test.go`; `grep -rn "time.Now\|time.Since" internal/engine/mining/minetype*.go` (excluding `_test.go`) returns no matches.

- **AC-9 (SG-7 scoped; GR#21).** `go test ./internal/engine/mining/... -race -count=1 -run MineType` passes with no data race (scoped via `-run`, since the shared package also carries `engine.mining.md` AC-14, `feat.resourcedeposits.md` AC-15 and `feat.extraction.md` AC-16 race suites); `grep -n "go func()" internal/engine/mining/minetype*_test.go` finds at least one concurrency test (concurrent resolve of the catalogue across shards).

## Out of scope

No blight/siting/reclamation AC belongs in this file.
- `feat.resourcedeposits.md`'s `Deposit` record, deposit taxonomy, geology co-location, and world-gen shuffle — this item only declares a `depositClass` compatibility gate (AC-5); it does not author the deposit model.
- `feat.extraction.md`'s tier ladder, depletion draw-down, yield variance, and price exposure — this item supplies the output rate a tier multiplies; it does not model extraction economics.
- `engine.world.md`'s geology layer and `CellAt`/prospecting implementation — consumed, not reimplemented.
- `data.catalogue`/`data/buildings.json` build-catalogue entries (unlock/cost/capacity) for the same structures — that catalogue is FEAT-010's; this file's types are the simulation parameters, and the build entry must reference a type key, never duplicate the numbers (ASM-692).
- Exact per-type footprint/output/blight/jobs/depth figures — balance data pending Aaron's balance pass (balance-number regime).
