# Acceptance criteria — cloud.azure (MOD-069)

**BOW code:** MOD-069 (P3, open, `milestone: future`) — "Azure tiers: Blob saves, Batch tuning, solver offload, cloud citizen shards".
**Spec refs:** §15 Architecture (`docs/METROPOLIS-MASTER-v2.1.md` line 267: "Cloud path (designed, unbuilt v1): Blob cloud saves early → Azure Batch headless balance-tuning… → hybrid solver offload slots… → surrogate-model path… Persistent cloud sim server stays shelved"); A9 Cloud thresholds (line 1371: "local CPU covers ≲20–30 M citizens end-to-end; beyond, cold-pass/shard store and (if needed) assignment move to cloud services on the existing seams… the player experience is identical at every tier"); GDD §15 cloud path; `docs/cloud.md` (the DECIDED provider ruling + the secure/resilient contract + the existing-estate reuse ruling); `docs/design/solver-contract.md` (the four offload slots); code.json `cloud.azure` entry (inbound `CloudServices` gRPC+Blob, outbound `int.solver` + `int.serializer`).
**Date:** 2026-08-16
**Status:** draft-ahead — the module is **unbuilt and deferred**. Azure is **confirmed** as the provider (Aaron ruling 2026-08-09, recorded on this BOW item); nothing cloud-shaped is built yet, and none of it is required for v1 to function (cloud is strictly capacity added later on the same seams).
**This file's role:** this is the *cloud* tier of the solver-offload seam plus the *storage* tier of the serializer seam — four backends, all of them **behind interfaces that already exist for local-only reasons** (`int.solver`, `int.serializer`). Per `docs/cloud.md` §1, "cloud backends are additional `registry.Register` calls, not new call sites in the engine." The load-bearing contract, inherited from `int.solver`, is the same as `cloud.gpu`'s: **bit-identical determinism** — a cloud solve or cold-pass MUST return byte-identical results to local CPU, and a cloud save MUST round-trip the exact bytes it was given. The second load-bearing property is **mandatory local fallback**: a cloud outage degrades to local compute/storage (slower, never wrong), never to a broken game (`docs/cloud.md` §3 "Failure mode").
**Balance-number regime (standing rule, same convention as `feat.maintenance.md` AC-2/AC-16):** this module has **no player-felt balance numbers**, but it does carry **operational thresholds** — timeouts, retry budgets, rate limits, queue depths, and the save-size binary-shard threshold. Every one of these is a **placeholder in a data file (`data/cloud.json`)**, each with a disclosure comment naming it pending Aaron's pass. No AC may be satisfied by a junior inventing a final timeout/retry/rate figure; tests check **direction/structure** (fallback preserves correctness; a bigger save selects the binary-shard path; a throttled call retries a bounded number of times) rather than pinning a magnitude. The one class of threshold that is **not** a balance placeholder is the A9 citizen ceiling (20–30 M) and the 4 GB VRAM envelope: those are **spec constants single-sourced in `int.solver`'s `sizing.go`** (`ExceedsLocalCPUCeiling*`, `FitsGPUEnvelope`) and this module **consumes them, never re-hardcodes them** (GR#3; ASM-801). Placeholder home is assumed to be `data/cloud.json` (ASM-804).

## User stories

- **US-1 (Blob saves).** As a player, I need to sync a save to cloud and get back **the exact bytes I put up**, so my save is safely off-machine and restores identically — cloud storage is a byte-preserving mirror, never a re-encoding of my city (§15 "Blob cloud saves early"; A3 "JSON stays the lingua franca").
- **US-2 (Batch tuning).** As the balance engineer, I need to fan thousands of headless parameter runs out to Azure Batch and get **per-seed results that match a local run exactly**, so cloud tuning is a faster version of local tuning, never a different result (H-HEADLESS is "the balance/Batch/CI workhorse", M0-ENG §2).
- **US-3 (Solver offload).** As the engine, I need to route a heavy solve to a stateless Azure solver slot and receive a **bit-identical answer to CPU**, with CPU as the automatic fallback on any cloud failure, so offload is a latency win and never a correctness risk (§15 "hybrid solver offload slots… with local-fallback").
- **US-4 (Citizen shards).** As a very-large city, when my citizen count crosses the A9 line the cold-pass and shard store migrate to a cloud citizen-shard service **without my experience changing at all** — same seam, same results, just a different place the bytes live (A9 "player experience is identical at every tier").
- **US-5 (Secure & resilient).** As the operator, I need every remote call to obey the secure/resilient contract — managed identity (never a committed secret), TLS, bounded retries, mandatory timeouts, correlation IDs — so a failed cloud call is traceable and degrades cleanly, never hangs or leaks (`docs/cloud.md` §3).

## Scope

The four tiers, each as a backend behind an existing seam: a **Blob-backed `StateSerializer`** for save sync (plugs `int.serializer`), an **Azure Batch fan-out** of `harness.headless` runs for M2 balance tuning (consuming `balance.harness`'s sweep surface), a **gRPC cloud `Solver` backend** for solver offload (plugs `int.solver`), and the **cloud citizen-shard service** (cold-pass via the `ColdPassBatch` slot + shard storage via `int.serializer`). Each carries mandatory local fallback; all remote calls obey the secure/resilient contract (consumed from `cloud.netpolicy`, not re-implemented). No persistent shared-world server, no LLM soft layer, no surrogate-model path, no re-implementation of serialization/solving.

## Acceptance criteria

### Functional — the seams

- **AC-1 (GR#20; cloud is backends behind existing seams, never new engine call sites).** `cloud.azure` implements the two already-frozen interfaces — a `Solver` (for solver offload + citizen cold-pass) and a `StateSerializer` (for Blob saves / shard storage) — and registers each into its respective registry (`int.solver`, `int.serializer`). There is **no** new engine call site, and the engine imports neither Azure SDKs nor this module. Check: `grep -rn "Register" cloud/*.go` shows registrations into `internal/foundation/solver` and `internal/foundation/serialize`; `grep -rn "cloud/azure\|cloud/" internal/engine/` returns **no** matches; and a scan of engine packages for Azure/CUDA SDK imports (`grep -rniE "azure|azblob|cuda" internal/engine/`) returns none. **False-pass risk:** a module that adds a side-channel "cloud mode" flag to engine logic would pass a "the backends exist" grep while violating "cloud is a config change, not a code path" — the check requires the seams, not parallel plumbing.

- **AC-2 (GR#20; stub forever).** A `CloudServicesStub` (or per-tier stubs) implements the `CloudServices` inbound interface with typed not-configured/no-op behaviour, so the engine boots and runs headlessly with cloud entirely absent (the v1 reality). Check: `grep -rn "type.*Stub" cloud/*.go` finds it, and a passing test boots the engine with the stub registered and asserts a full tick runs with all-local results (no Azure SDK call attempted).

### Functional — Blob saves (tier a)

- **AC-3 (byte-preserving round-trip; GR#3/GR#21).** The Blob-backed serializer writes a save bundle to Blob and reads it back **byte-identically**, validated against the serializer's **existing** `ShardMeta.SHA256`/`ByteSize` — the module moves the exact bytes `int.serializer` produced; it does **not** re-serialize, re-compress, or re-hash them through a second scheme. Check: a passing round-trip test (against a Blob SDK fake / in-process object-store double) asserts download bytes == upload bytes and the recorded SHA256 matches; `grep -rn "json.Marshal\|gzip\|sha256.New" cloud/` (save tier) shows no re-encoding — the serializer's output is the unit of transfer.

- **AC-4 (own container, never `whatsapp-session`; lead ruling).** The Blob container name is a **single-sourced config value** in `data/cloud.json` defaulting to a dedicated Metropolis container, and the code contains **no reference** to `whatsapp-session` or any Prix Six-owned container. Check: `grep -rni "whatsapp" cloud/` returns no matches; the container name is read from config, not a hardcoded literal (`grep -rn "container" cloud/*.go` shows a config lookup). **Rationale (lead ruling, recorded on this BOW item + `docs/cloud.md` §2):** sharing the container would let Prix Six ops delete Metropolis saves incidentally — different lifecycle, different owner.

- **AC-5 (no committed secrets; GR#11).** No storage-account key, connection string, or SAS token is committed; the module authenticates via **managed identity / short-lived tokens**, and any dev-only credential is read from environment or untracked config, never a committed literal. Check: `grep -rniE "accountkey|account.?key|connection.?string|SharedAccessSignature|sig=" cloud/` finds **no literal secret**; the auth path is an identity provider call, not a static key (and the repo's `claude-secret-guard.js` regex bank stays clean on this directory).

### Functional — Azure Batch tuning (tier b)

- **AC-6 (fan-out keyed by seed; cloud == faster local, not different local).** The Batch runner takes the **same** scenario/seed inputs `harness.headless` takes (`-seed N -months M -out snap.json`), fans them out as independent deterministic jobs, and **collects results keyed by seed** — never by completion order — so a cloud run's result for seed N is byte-comparable to a local run's result for seed N. Check: a passing test runs a 2–3 seed fan-out against a fake Batch job service and asserts (a) results map back to their seeds, and (b) each cloud result's snapshot hash equals the local `harness.headless` output for that seed (determinism).

- **AC-7 (balance.harness is the orchestrator; cloud supplies the pool, not a second harness).** The sweep definition, parameter ranges, and the "achievable-but-hard" comparison logic **stay in `balance.harness` (MOD-036)** / `tools/balance`; `cloud.azure` provides the remote compute pool behind that same surface. Check: the module consumes `balance.harness`'s `SweepRunner` surface (or the `harness.headless` binary) rather than re-declaring a sweep DSL; `grep -rn "sweep\|pacing\|achievable" cloud/` shows **consumption**, and `grep -rn "type.*Sweep\|ParamRange\|scenario" cloud/` finds no parallel sweep-definition type.

### Functional — solver offload (tier c)

- **AC-8 (GR#21; bit-identical cloud solve).** The cloud `Solver` backend returns `Response.Payload` **byte-identical** to `CPUBackend`'s for the same `(Problem, Seed, Payload)`, `Deterministic=true`, on every `ProblemKind` the cloud tier declares. Check: a golden cross-backend test runs the cloud backend over a local gRPC loopback (or mock transport) and asserts `bytes.Equal(cpuPayload, cloudPayload)`. A mismatch is **auto-P0 under GR#21**. **False-pass risk:** a test that only asserts the cloud backend returns *something* would pass a fast-but-wrong backend; the check requires `bytes.Equal` against the CPU result — same invariant as `cloud.gpu` AC-6.

- **AC-9 (mandatory local fallback + mandatory timeouts; cloud is an accelerant, never a dependency).** A cloud failure — timeout, `Unavailable`, throttle, auth error — **degrades to the local CPU/GPU backend** via `int.solver`'s fallback chain: the caller still receives a correct answer, the failure is logged with the propagated **correlation ID**, and **no call can hang** (every outbound RPC carries a deadline). Check: a passing test injects a cloud failure and asserts (a) the result still arrives from a local backend, (b) a failover log/correlation event fires, and (c) `grep -rn "context.WithDeadline\|context.WithTimeout\|Deadline" cloud/` shows a deadline on the RPC path.

### Functional — cloud citizen shards (tier d)

- **AC-10 (A9 threshold single-sourced; GR#3/GR#15).** The migration trigger for citizen-shard offload **consumes `int.solver`'s `ExceedsLocalCPUCeiling` / `ExceedsLocalCPUCeilingHigh` helpers** (the 20 M / 30 M A9 bounds) — the module never re-hardcodes the numbers. Check: `grep -rn "ExceedsLocalCPUCeiling" cloud/` finds the call; `grep -rnE "20000000|30000000|20_000_000|30_000_000|20 ?M|30 ?M" cloud/` finds **no** re-declared threshold literal. **False-pass risk:** a module that copies "20M/30M" as fresh literals would pass a "threshold exists" grep while forking the single source (GR#3) — the check requires the `int.solver` helper, not a re-typed constant.

- **AC-11 (player experience identical at every tier; A9).** The citizen-shard service answers the `ColdPassBatch` problem through the **same `int.solver` seam**, returning **bit-identical cold-pass results** whether the shards live locally or in cloud, and the shard store is **byte-preserving** (the same serializer round-trip as AC-3). Check: a golden test compares a local cold-pass result with a cloud cold-pass result (over a mock) for byte equality; and the engine's citizen code path contains **no branch on "am I in cloud mode"** — `grep -rn "cloud\|remote" internal/engine/citizens/` finds no tier-selection logic (selection lives in the registry, not in simulation).

### Secure & resilient (GR#11 + `docs/cloud.md` §3)

- **AC-12 (cloud.netpolicy consumed, not re-implemented).** Retry/backoff, rate limiting, and timeout policy are applied through **`cloud.netpolicy`'s surface** (or the shared policy package it owns) — not a second hand-rolled copy inside `cloud.azure`. Check: the module imports/calls the policy surface; `grep -rn "time.Sleep\|backoff\|retry" cloud/` shows **no hand-rolled exponential-backoff loop** that duplicates the policy. **Boundary note (ASM-799 / ES-2):** `cloud.netpolicy` (INT-004) is unbuilt with a null inbound contract today; until it lands, the module may sit behind the same policy *interface* with a minimal local implementation — but the AC requires the **seam**, never a parallel re-implementation.

- **AC-13 (GR#7; every cloud failure is a registry-sourced error).** Every cloud failure mode — auth failure, throttle, quota exceeded, blob-not-found, batch-job failure, solver-unavailable — surfaces as a **registry-sourced `MET-`-range error**: the Azure SDK error is mapped to a specific `MET-` code with the correlation ID attached, never a panic, never a silently-swallowed error, never a raw SDK error leaking to the caller. Check: `grep -n "MET-" cloud/*.go` finds the mapping; passing tests assert the returned error's registry code for at least auth-failure and blob-not-found (GR#7 assertion — the code, not merely a matching test name).

### Determinism & safety

- **AC-14 (GR#21; no cloud call changes state except through a bit-identical Payload).** No cloud call can alter simulation state except by returning a bit-identical `Payload` through the seam — `Backend`/`Stats`/latency never leak into world state, and **no wall-clock read influences logic** (age advances by tick only). Check: `grep -rn "time.Now\|time.Since" cloud/*.go` (excluding `_test.go`) returns no matches outside `SolveStats`-population/diagnostic code; source review confirms no feedback loop of diagnostics into `Request.Seed`/`Payload` (the same loop-closing ban `int.solver` AC-15 enforces).

- **AC-15 (GR#21; fan-out/retry order does not affect results).** The batch result collection and the blob upload are **order-independent w.r.t. determinism** — re-running the same fan-out (with job completion order reordered, or with retries) produces the **same per-seed results**. Check: a passing test runs the fan-out twice against a mock that reorders/retries and asserts per-seed snapshot hashes are identical across the two runs.

### Documentation

- **AC-16.** `cloud/` carries a `doc.go` stating the module key `cloud.azure`, citing §15 / A9 / `docs/cloud.md`, and stating explicitly (a) the **four tiers and their seams** (`int.solver` for solve/cold-pass, `int.serializer` for storage), (b) the **operational-number regime** — timeouts/retry budgets/rate limits/queue depths and the save-size binary threshold are placeholders in `data/cloud.json` pending Aaron's pass, (c) the **secure/resilient contract** (managed identity, TLS, bounded retries, mandatory timeouts, correlation IDs), and (d) **local fallback is mandatory** — cloud is strictly an accelerant, never a dependency the game can't run without. Check: `grep -n "cloud.azure" cloud/doc.go` and `grep -n "§15\|A9\|cloud.md" cloud/doc.go` and `grep -n "placeholder\|balance" cloud/doc.go` all match.

## Out of scope

- **Persistent shared-world server** — shelved (Master doc V.1 / §15 "stays shelved unless shared worlds ever appeal"); nothing here costs toward it.
- **LLM soft layer** — optional post-v1 (ticker prose, advisor persona), "never the number cruncher" (§15).
- **Surrogate-model / non-deterministic backend path** — deferred until a subsystem actually outgrows local (§15); this module stays `Deterministic=true` only.
- **The local CPU/GPU backends** — `int.solver` / `cloud.gpu` (MOD-068). This module registers *alongside* them; it does not own them.
- **Re-implementing serialization or solving** — `int.serializer` owns the format; `int.solver` owns the algorithm; `cloud.azure` only *moves/offloads* their bytes (AC-3, AC-8).
- **`cloud.netpolicy`'s own mechanics** (retry/authz/rate-limit internals) — that module owns them; this module consumes them (AC-12).
- **Azure resource provisioning (IaC/Terraform/ARM)** — out of scope for the game module; the module consumes configured endpoints + managed identity from config, it does not provision the estate.

## Cross-check (edges this module sits on / feeds)

- **Sits on `int.solver` (INT-003, done).** Solver offload (tier c) and citizen cold-pass (tier d) are `int.solver` backends; the fallback chain and bit-identical contract are already specified there. AC-8/AC-9/AC-11 inherit from it.
- **Sits on `int.serializer` (INT-002, done).** Blob saves (tier a) and shard storage (tier d) are `int.serializer` backends; the SHA256-verified byte-preserving round-trip (AC-3) inherits from `int.serializer` AC-5/AC-6/AC-13. The binary-shard-at-scale path is `int.serializer`'s own (A3) — this module selects the backend, it does not author the binary format.
- **Depends on `balance.harness` (MOD-036, open — a BOW dependency of MOD-069).** Batch tuning (tier b) is the remote pool for `balance.harness`'s `SweepRunner` (AC-7). MOD-036 has **no committed code**, so AC-6/AC-7 target its contract as a stub-first dependency (see ES-1).
- **Consumes `cloud.netpolicy` (INT-004, open).** The secure/resilient mechanics (AC-12) are that module's; its code.json inbound contract is currently null, so the consumption seam is an assumption (ASM-799 / ES-2).
- **Sibling `cloud.gpu` (MOD-068).** Both register `int.solver` backends; the priority ladder (CPU 0 < GPU ≈50 < cloud ≈100) must not collide, and the bit-identical invariant (AC-8 here, AC-6 there) is the *same* invariant — the two BAs should keep the wording aligned so the determinism gate reads one consistent contract.
