## 1. Why this item exists

Aaron's brief: scale demand tables per population rung with a giant LUT so "runtime computation is interpolation, not simulation" at the 100M scale goal. A scale ladder with 18 rungs (100 → 98M) is the foundation: every numeric field in the traffic tables (mode-share percentages, vehicle-mile rates, station occupancy, etc.) will be pre-tabulated at each rung and interpolated at runtime, guaranteeing O(rungs) + O(fields) cost independent of citizen count. This is the core blocker for hitting 100M deterministically (GR#21); inc1 de-risks it before any consumer is written.

---

## 2. The design in one paragraph

A static data file `data/traffic/scale_ladder.json` declares an ordered array of population rungs (18 entries: 100, 1K, 5K, 10K, 50K, 100K, 250K, 600K, 1M, 1.2M, 2M, 5M, 10M, 20M, 40M, 60M, 80M, 98M), each rung carrying numeric fields to be interpolated. For any query population p, locate the two adjacent rungs i and i+1 where p_i ≤ p < p_{i+1}, compute a logarithmic weight w = (ln p − ln p_i) / (ln p_{i+1} − ln p_i), and interpolate each field linearly in the field (f = f_i + w·(f_{i+1} − f_i)). Exact rung populations return the rung verbatim. Populations below the first rung or above the last rung are errors (no clamping, no extrapolation — Aaron's rule). The loader validates the file structure once at startup; the interpolator is pure, deterministic (GR#21), and cached per state in the webconsole via `memoOnState` convention.

## 3. Acceptance Criteria

### Loader

**AC-1 (GR#7 — registry errors).** File-read and parse errors (missing, unparsable JSON, non-object root) produce typed registry-sourced errors, not panics or silent defaults. Validation errors (rungs unsorted by population, duplicate population values, fewer than 2 rungs, non-finite numbers in numeric fields, population outside [first rung, last rung] in any query) each produce a named registry-sourced error. Check: `grep -n "MET-" internal/engine/traffic/*.go` and `grep -n "MET-" webconsole/src/sim/*.ts` show registry error codes; passing tests cover every condition listed above.

**AC-2 (GR#15 — validators derive from data).** The rung count (18) and exact rung population list (100, 1K, …, 98M) are NOT hardcoded in a validator or test. A test asserting "18 rungs present" must read the count from the loaded data file or from an explicit list the DATA file declares; a test asserting "rungs are sorted" must fail if `data/traffic/scale_ladder.json` is hand-edited to have out-of-order rungs. Check: the loader exposes the rung list it read (e.g. `Rungs() []Rung`), and every test that reasons about rung count or rung populations takes them from that call or from a `meta.rungPopulations` list the DATA file declares (inc0 must declare one); `grep -rn "rungPopulations\|Rungs()" internal/engine/traffic/*_test.go webconsole/src/sim/*.test.ts` finds the derivation. **False-pass note:** a literal `18` in a test file is not itself the defect (line numbers, other counts) — the Tester reads each rung-count assertion and confirms its expected value comes from the data, not a literal. **Mutant:** hand-edit the fixture copy to 17 rungs; the "all rungs present" test must red because the declared list and the array disagree, not because a literal 18 was missed.

**AC-3 (Go: LoadConfig precedent).** The Go loader follows the `internal/engine/traffic/api.go` LoadConfig pattern (§138-163): path construction, `os.ReadFile`, `encoding/json.Unmarshal`, validation function, `invalidInputf` errors, and `checkNotCopied` guard. Check: `internal/engine/traffic/*.go` shows a function named `LoadScaleLadder` or equivalent reusing `invalidInputf` and the same error-return shape.

**AC-4 (TypeScript: static import + validation).** The TypeScript loader imports `data/traffic/scale_ladder.json` using `import x from '...json' with { type: 'json' }` syntax (matching `devcity.ts` precedent), validates at module-load time, and throws an error if validation fails — never a silent partial load. Check: `webconsole/src/sim/data.ts` shows the import statement and a validation block; the module's tests exercise import-time validation failure.

### Interpolator

**AC-5 (interpolation rule, specified precisely).** For population p between rung i and i+1: weight w = (ln p − ln p_i) / (ln p_{i+1} − ln p_i); each numeric field f interpolates as f = f_i + w·(f_{i+1} − f_i) (linear in field, logarithmic in population). Exact rung populations return the rung's values verbatim. Check: passing tests include a golden-vector suite (below, AC-6) that proves the formula.

**AC-6 (golden vectors — cross-language regression test).** A new file `data/traffic/ladder_vectors.json` contains a list of test cases: `{population: number, expectedFields: {...}}` derived from the Go implementation and consumed by BOTH `internal/engine/traffic/*_test.go` and `webconsole/src/sim/*.test.ts`. A test in each language loads the same golden file and asserts its interpolator output matches the expected vector exactly (Go `reflect.DeepEqual`, TypeScript `deepEqual` or JSON stringification). Any divergence between Go and TypeScript implementations is a test failure. Check: both test suites import and run the same `ladder_vectors.json`; a mutant interpolator (e.g. linear in population instead of log-linear) fails the vector test conspicuously.

**AC-7 (integer rounding, identical across languages).** Any integer-valued field (counts of people, vehicles, spaces) is rounded from the interpolated float exactly once at the end using a shared, documented rule (e.g. "floor(x + 0.5) for non-negative quantities"). Go and TypeScript implementations must produce byte-identical rounding. Check: `go doc ./internal/engine/traffic` and `webconsole/src/sim/data.ts` doc comment state the rounding rule explicitly; the golden-vector test includes several integer fields and asserts exact matching.

**AC-8 (determinism — GR#21).** Interpolation is pure: same population input, same rung data, identical output across runs and across Go/TS. No clock reads, no randomness, no maps ranged with early break (GR#21 §18). Check: `grep -rn "time.Now\|Math.random\|for.*range" internal/engine/traffic/*.go webconsole/src/sim/*.ts` (excluding test files) finds no time/random in the interpolation path; passing determinism test runs the interpolator 10 times per population and asserts bit-identical output (Go via `cmp.Equal`, TypeScript via JSON stringification).

**AC-9 (O(rungs) + O(fields) cost, independent of citizen count).** A benchmark on the interpolator alone (isolated from the loader) shows cost does not grow with citizen count — interpolating for population 10M takes the same time whether the city has 1K or 100M citizens. Check (structural, never wall-clock — CI forbids timing bounds): the interpolator's signature takes a population number and the loaded ladder ONLY — no citizen slice, no world state — so it cannot scale with citizens by construction (`go doc` shows the signature; TS export likewise takes `(ladder, population)`); a Go test asserts `testing.AllocsPerRun` for one interpolation is bounded by a constant derived from the field count (allocs, not nanoseconds); `go test -bench=BenchmarkLadderInterpolate` exists for local profiling only and asserts nothing. **Mutant:** an implementation that walks a citizen collection cannot satisfy the signature; an implementation that allocates per rung per field reds the allocs pin.

### Scope & Interface

**AC-10 (no consumer in inc1).** The loader and interpolator are built and tested, but no feature code yet CALLS them — they are exposed only for inc2's use. A grepping for call sites within engine.traffic (excluding the loader/interpolator themselves) should find none until inc2 lands. Check: `grep -rn "ScaleLadder\|Interpolate" internal/engine/traffic/*.go | grep -v "func.*ScaleLadder\|func.*Interpolate"` returns no matches.

**AC-11 (registered API exposure).** The Go interpolator surface (a whole-rung interpolation returning a typed struct, e.g. `func (l *ScaleLadder) At(population int64) (Rung, error)` — NOT a string-keyed per-field lookup, which would move field names into caller strings and defeat the compiler) is documented in `go doc ./internal/engine/traffic`; the TypeScript surface (e.g. `export const scaleLadderOf = memoOnState(s => ...)`) is exported from `webconsole/src/sim/data.ts`. Neither surface changes between inc1 and inc2 dispatch. Check: running `go doc ./internal/engine/traffic` shows the method; grepping `webconsole/src/sim/data.ts` for `export const scaleLadder` finds the export.

## 5. Assumptions

1. **Data file location and format.** Assume the scale-ladder data will be authored in `data/traffic/scale_ladder.json` with a `version`, `meta`, and `rungs` array structure, as described in inc0 brief. If the path or schema differs, the loader's path construction and Unmarshal shape must be adjusted accordingly.

2. **Rung population list is fixed.** The 18 rungs (100, 1K, 5K, 10K, 50K, 100K, 250K, 600K, 1M, 1.2M, 2M, 5M, 10M, 20M, 40M, 60M, 80M, 98M) are the canonical list. Any addition, removal, or reordering of rungs is a breaking change requiring spec review; tests fail if the data file deviates.

3. **No integer overflow at 98M scale.** All intermediate and final numeric fields (occupancies, rates, capacities) remain within float64 and int64 bounds at the 98M rung; no field requires uint128 or arbitrary precision.

4. **Go standard library suffices.** The interpolator uses only Go's `math` and `encoding/json` packages; no external numeric library is required.
