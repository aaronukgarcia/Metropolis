## User stories

- **US-1.** As a placed/employed job (via `engine.staffing`/`engine.citizens`), I need to carry a **TIME pattern** — CoreHours, Shift, or AnyTime — not just a headcount, so staffing coverage is a schedule over the day/week, not a constant (Aaron design).
- **US-2.** As the player, I need a 24x7 role (hospital) to demand multiple shifts of coverage while a 9-5 role (school) demands only core-hours coverage, so under-staffing shows up as a real gap in a specific time window, not a single missing number.
- **US-3.** As `engine.traffic`, I need a schedule-driven commute-demand distribution (workers arriving at shift-start, leaving at shift-end, per hour), so the daily get-to-work rush is a real, time-shaped load on the network, not a flat daily average (§19.3).
- **US-4.** As the player, I need the working week to be a **POLICY** — a varied ~40h default, with a 996 (9-to-9, 6-day) option I can toggle on/off — so labour hours are a lever I pull, with a cost, not a fixed simulation constant (§52).
- **US-5.** As `engine.finance`, I need 996 workers to earn more (a real wage gain), so the policy is a genuine productivity lever with a fiscal footprint.
- **US-6.** As `engine.wellbeing`, I need 996 workers to be less happy (a real wellbeing hit), so overwork is a trade with a cost the player can see in the wellbeing numbers — never free productivity (§18/§42).
- **US-7.** As the determinism gate (GR#21), I need at-work state, commute demand, and coverage to be a pure function of (tick, pattern, policy state, seed) — never wall clock (§5.2).

## Scope

A time-pattern model (CoreHours / Shift / AnyTime, data-driven), the per-tick derivation of who is at work and who commutes (a deterministic function of tick + pattern), a schedule-driven commute-demand-by-hour distribution, the working-week policy consumption (default ~40h vs 996, the toggle effect read from `engine.policies`), and the overwork trade (996 wage gain + wellbeing cost). No traffic assignment (`engine.traffic`), no policy-library/toggle definition (`engine.policies`), no wellbeing-driver arithmetic (`engine.wellbeing`), no staffing labour-pool assignment itself (`engine.staffing`), and no final hour/wage/wellbeing values (Aaron's balance pass).

## Acceptance criteria

### Functional — the time-pattern model (schedule, not headcount)

- **AC-1 (GR#20; code.json inbound contract — `WorkScheduleAPI`).** `WorkScheduleAPI` exposes the five surfaces named in the registered inbound pattern — the pattern vocabulary (core-hours / shift / any-time), an at-work query for (worker, tick), a per-role coverage-requirement query, a commute-demand-by-hour query, and a working-hours query that reflects the active working-week policy. Check: `go doc ./internal/engine/worklife WorkScheduleAPI` shows these five surfaces; `grep -rn "worklife\." internal/engine/*/` (excluding the `worklife` package itself) finds no direct concrete-type import — consumption is interface-only, never a concrete schedule-engine type imported directly by another module. **False-pass note:** the grep only catches one hardcoded name guess — Tester/QA must also confirm by reading `go doc` output that no *other* concrete worklife type (whatever it is actually named) is imported elsewhere.

- **AC-2 (GR#15; patterns data-driven, not hardcoded).** Each time pattern's hours and on-duty profile (start/end/rotation) are loaded from `data/worklife.json`, with the three documented kinds — CoreHours, Shift, AnyTime — carrying distinct profiles, never Go literals for the hours. Check: a passing test mutates one pattern's hours in the loaded data fixture and asserts the at-work profile reflects the change (`grep -rn "func Test.*[Dd]ataDriven\|func Test.*[Pp]attern.*[Rr]eload" internal/engine/worklife/*_test.go`); `grep -nE "[0-9]+" internal/engine/worklife/*.go` (excluding `_test.go`) finds no bare hour-shaped numeric literals outside doc-comment prose.

- **AC-3 (the core claim — schedule, not a constant headcount).** A 24x7 Shift role's required headcount for a given per-hour on-duty demand is strictly greater than a CoreHours role's for the same demand, because shift coverage must span all 24 hours while core-hours spans only the working day. Check: a passing test computes the coverage requirement for the same per-hour demand under Shift vs CoreHours and asserts shift required headcount > core required headcount (`grep -rn "func Test.*[Ss]cheduleNotHeadcount\|func Test.*[Cc]overage" internal/engine/worklife/*_test.go`). **False-pass risk:** a "pattern" field that exists but always resolves to a single constant headcount regardless of pattern would pass a "pattern field exists" grep while the feature's whole premise is unmet — the check requires two patterns to resolve to two *different* headcounts for the same demand.

### Functional — at-work derivation (deterministic function of tick)

- **AC-4 (per-tick at-work).** `AtWork(worker, tick)` is a deterministic function of the worker's pattern and the tick: a CoreHours worker is at-work only during core hours, a Shift worker is at-work on exactly one of the rotations covering 24x7 (so a full roster leaves no hour unstaffed), an AnyTime worker is at-work flexibly within their weekly hours. Check: a passing test walks a tick sequence and asserts the CoreHours worker's at-work profile has the documented on/off boundaries, and that a full Shift roster leaves no hour unstaffed (`grep -rn "func Test.*[Aa]tWork\|func Test.*[Rr]oster" internal/engine/worklife/*_test.go`).

- **AC-5 (deterministic rotation assignment).** Which shift a Shift worker draws (and the AnyTime worker's flexible placement) follows a documented deterministic rule (e.g. derived from worker ID and week index), never map-iteration order. Check: `grep -n "sort\." internal/engine/worklife/*.go` where any map feeds assignment; a determinism test exists (see AC-16).

### Functional — commute (the get-to-work rush)

- **AC-6 (every worker commutes; the rush is time-shaped).** Every employed worker generates a commute trip aligned to their pattern's start (arrive) and end (leave); workers on the same pattern commute at the same tick, so the distribution of commute demand across the day has a peak at core-hours start rather than a flat daily average. Check: a passing test seeds N CoreHours workers and M Shift workers and asserts the per-hour commute-demand distribution has its mode at the core-hours start tick and that shift workers spread their arrivals across the day (`grep -rn "func Test.*[Cc]ommute.*[Rr]ush\|func Test.*[Aa]rrival.*[Dd]istribution" internal/engine/worklife/*_test.go`).

- **AC-7 (commute demand is an output surface feeding `engine.traffic`; worklife does not implement assignment — GR#3).** The commute-demand-by-hour figure is exposed through the worklife surface as the input `engine.traffic` (MOD-023) will consume; worklife contains no traffic-assignment, routing, or travel-time logic. Check: `go doc` shows the demand surface; `grep -rn "route\|assignment\|travelTime\|volume" internal/engine/worklife/*.go` (excluding `_test.go`) finds no assignment machinery. **Deferred dependency (ASM-957):** the end-to-end "rush shapes traffic" claim is MOD-023's and cannot be built until traffic lands; worklife proves its half (the time-shaped demand) alone.

### Functional — the working-week policy (40h default, 996 toggle)

- **AC-8 (working week is a policy lever consumed from `engine.policies`, never owned — GR#3/#20).** The working week's hours, wage, and wellbeing effects are read from the active working-week policy via `engine.policies`' registered inbound edge (the outbound call registered in `code.json`), never a worklife-local "996 mode" branch or a hardcoded hour table. **Tripwire (mechanical):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.worklife'); process.exit(m.outbound.calls.some(c=>c.key==='engine.policies')?0:1)"` must exit 0 (edge confirmed registered); nonzero means the edge was removed and this AC must be re-blocked/re-audited. Check: `grep -rn "policies\.\|PoliciesAPI" internal/engine/worklife/*.go` (excluding `_test.go`) shows the call; `grep -nE "case \"996\"|switch .*[Pp]olicy" internal/engine/worklife/*.go` finds no name-branching dispatch; a passing test enacts the policy via a fake satisfying the real interface and asserts worklife's computed hours/wage/wellbeing inputs change (`grep -rn "func Test.*[Pp]olicyConsum" internal/engine/worklife/*_test.go`).

- **AC-9 (default ~40h, 996 = more hours — data-driven).** The default working week sums to ~40 hours (varied by pattern), and the 996 policy is 9-to-9 across 6 days = 72 hours/week; 996 hours are strictly greater than default hours. Check: a passing directional test asserts default-week hours ≈ 40 and 996 hours > default hours, with both figures read from data (`grep -rn "func Test.*[Ww]orkingWeek\|func Test.*[Hh]ours" internal/engine/worklife/*_test.go`). **Balance-regime note:** the exact figures are placeholders (ASM-953); this AC checks direction and the ~40h default shape, not a pinned total.

- **AC-10 (toggle on/off is reversible and clean).** Toggling the working-week policy off reverts hours/wage/wellbeing inputs to the default-week values, and toggling it back on re-applies 996 — no residue, no partial state. Check: a passing test enacts → asserts 996 effects → repeals → asserts default values restored → re-enacts → asserts 996 effects again (`grep -rn "func Test.*[Tt]oggle\|func Test.*[Rr]evert" internal/engine/worklife/*_test.go`).

### Functional — the overwork trade (earn more, less happy)

- **AC-11 (996 earns more).** A worker under 996 has a strictly higher wage than the same worker under the default week, via the policy's wage coefficient (data-driven). Check: a passing directional test asserts 996 wage > default wage for the same role, both read from the policy effect (`grep -rn "func Test.*[Ww]age.*996\|func Test.*[Ee]arn.*[Mm]ore" internal/engine/worklife/*_test.go`).

- **AC-12 (996 less happy — routes through `engine.wellbeing`, GR#20).** The 996 wellbeing cost is expressed through `engine.wellbeing`'s registered inbound edge (the outbound call registered in `code.json`) — an overwork/work-life input mapping onto §42's discretionary-hours/leisure-fit and/or §18's commute-time driver (ASM-956 decides which) — never a worklife-local happiness number. **Tripwire (mechanical):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.worklife'); process.exit(m.outbound.calls.some(c=>c.key==='engine.wellbeing')?0:1)"` must exit 0 (edge confirmed registered); nonzero means the edge was removed and this AC must be re-blocked/re-audited. Check: `grep -rn "wellbeing\.\|WellbeingAPI" internal/engine/worklife/*.go` (excluding `_test.go`) shows the call; a passing test feeds a 996 worker and a default-week worker (identical otherwise) through the same path and asserts the 996 worker's wellbeing input is strictly lower (`grep -rn "func Test.*[Ll]essHappy\|func Test.*[Ww]ellbeing.*996" internal/engine/worklife/*_test.go`).

- **AC-13 (the trade is genuine — never free productivity).** The wage gain and the wellbeing cost move together from the same policy effect: there is no configuration in which 996 yields the wage gain with zero wellbeing cost. Check: a passing test enacts 996 and asserts BOTH effects fire in the same tick, and that the wellbeing cost is non-zero whenever the wage gain is non-zero (`grep -rn "func Test.*[Tt]rade\|func Test.*[Nn]oFree" internal/engine/worklife/*_test.go`). **False-pass risk:** an implementation that adds a wage bonus and a separate, optional, default-off wellbeing penalty would pass "both effects exist" tests while letting the player harvest the wage gain with the cost disabled — the check requires the two to be inseparable from one policy effect.

### Error handling

- **AC-14 (GR#7).** An unknown pattern kind, an out-of-domain hours input (negative, >24h/day), or an unknown working-week policy reference returns a registry-sourced error (a new `MET-E`-range code claimed at build time — no `engine.worklife` sub-range exists yet), never a panic or a silently-clamped value folded into coverage/hours. Check: `grep -n "MET-" internal/engine/worklife/*.go` finds a registry-code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownPattern\|func Test.*[Oo]utOfRange" internal/engine/worklife/*_test.go`) asserts the returned error's registry code matches **and** that no schedule/hours state was mutated on failure — not merely that a matching-named test function exists (GR#7 assertion, stated explicitly).

- **AC-15 (GR#7; malformed data).** A malformed or schema-invalid `data/worklife.json` (a pattern missing its hours, a negative shift length, an unrecognised kind string) produces a registry-sourced error at load time, never a silent default substitution that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/worklife/*.go` finds a load-time code distinct from AC-14's; passing test coverage (`grep -rn "func Test.*[Mm]alformed.*[Ww]orklife" internal/engine/worklife/*_test.go`) asserts the error's registry code matches **and** that no default-substituted pattern was loaded in place of the malformed one.

### Determinism & safety

- **AC-16 (GR#21; core).** At-work state, commute-demand distribution, coverage requirement, and hours/wage/wellbeing derivation are a deterministic function of (tick, pattern, active policy state, seed) — repeated runs from an identical snapshot over an identical command/policy sequence produce byte-identical results across worker counts. Check: a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/worklife/*_test.go`); and `grep -rn "time.Now\|time.Since" internal/engine/worklife/*.go` (excluding `_test.go`) returns no matches — the "day"/"hour" is a simulation-tick concept, never wall clock. Never assert a wall-clock upper bound in CI; assert state equality only.

- **AC-17 (GR#21; no map-range on result-affecting collections).** No `for range` over a Go map feeds a value into at-work state, coverage, or commute demand without a prior deterministic sort/ordering step. Check: `grep -rn "for .* := range" internal/engine/worklife/*.go` — every match iterating a map type that affects output is preceded by a `sort.` call (`grep -n "sort\." internal/engine/worklife/*.go` shows the ordering step exists for each such site).

- **AC-18 (GR#16; type-safe boundaries).** Hours, wage multipliers, and wellbeing deltas crossing a module boundary (from the policy effect, into wellbeing/staffing/traffic) route through the project's saturating helpers (`foundation/num`) / safe-coercion path, never a raw untrusted numeric read. Check: `grep -rn "num\.\(Add\|Sub\|Mul\|Sat\|Safe\)\|safe[A-Z]" internal/engine/worklife/*.go` shows the coercion on the boundary values (matching FEAT-086's sweep).

- **AC-19 (GR#15; validators derive from data).** Every test that asserts a specific hour total, wage, or wellbeing figure derives that expected value from the loaded data file (or a data fixture), never a hardcoded constant the test invented independently of the data. Check: the direction/structure tests above read their fixtures from `data/worklife.json`; a test that hardcodes "72" as its own expected value without reading it from data fails this AC.

- **AC-20 (race).** `go test ./internal/engine/worklife/... -race -count=1` passes with no data race when the schedule/commute query surface is read concurrently with a tick advancing and a policy toggle. Check: `grep -n "go func()" internal/engine/worklife/*_test.go` finds at least one concurrency test.
