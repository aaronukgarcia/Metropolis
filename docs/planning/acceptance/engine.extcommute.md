# Acceptance criteria — engine.extcommute (MOD-035)

**BOW code:** MOD-035
**Spec refs:** §21 External Commuting & Housing (`docs/METROPOLIS-MASTER-v2.1.md` lines 372-376: off-map jobs London/Ashford/Dover — abstract job pools with wage levels and capacity — reachable via motorway car/coach or, from tier 5, external rail season ticket; city collects income tax without providing the job; dormitory-town strategy, strongest early; commute burden hammers mental health §18; in-commuting fills labour shortage, wages leak out, no residents gained, visible in F6); A6 (Part VI Amendment, line 1352: "R6 — Out-commuter tax farming exploit. ACCEPTED → A6" — off-map job pools get **finite, era-scaled capacity**; external rail/coach capacity and crowding are explicitly the second cap; dormitory districts yield income tax but **no business rates and no corp share**, surfaced in F2 incidence; commute burden→mental health→emigration remains the soft cap; dormitory-city stays a viable *opening*, not an endgame exploit); §19.3 commute accounting (door-to-door time feeds mental health §18); §39 taxation F2 incidence; code.json `engine.extcommute` entry — inbound `ExtCommuteAPI`, pattern **"pools from external_world.json; era scaling"**, outbound calls to `engine.citizens`/`engine.traffic`/`engine.finance`/`foundation.data`, inbound consumed today by `ui.screen.demo`.

## User stories

- **US-1.** As a player, I need a legitimate dormitory-town opening (§21) — housing London/Ashford/Dover commuters for income-tax revenue before local jobs exist — that is genuinely capped, not an infinite money tap, so the strategy stays historically honest rather than becoming R6's tax-farming exploit A6 was written to close.
- **US-2.** As A6's finite-pool amendment, I need off-map job capacity to actually run out under sustained demand, and I need every citizen's employment state to be exactly accounted for (no double-counted or uncounted residents), so the pool's finiteness is a real constraint, not a number that is finite in name only.
- **US-3.** As `engine.wellbeing`, I need out-commuters' door-to-door commute time fed through the same commute-time path as local commuters (§19.3/§18), so the dormitory strategy's mental-health cost is real, not a separate hand-waved penalty.
- **US-4.** As `engine.finance`/F2 taxation incidence, I need dormitory-district revenue to show up as income-tax-only (no rates, no corp share) per citizen, so the "structurally revenue-thin per head" claim (A6c) is a checkable ledger fact, not prose.
- **US-5.** As F6 (the in-commuting leak view), I need in-commuting to fill local labour shortages without creating resident citizens, and the wage leakage to be visibly recorded, so the player sees the leak the spec promises they will.
- **US-6.** As `foundation.data`, I need off-map pool definitions (capacity by era, wage level, transport requirement) loaded from `data/external_world.json`, not hardcoded, so pool capacities are a data-authoring decision (GR#15), not a code change.

## Scope

Off-map job pools (London, Ashford, Dover) with finite era-scaled capacity loaded from `data/external_world.json`; assignment/release of citizens to/from pools subject to two independent caps (pool capacity, transport capacity); the dormitory arithmetic identity across a citizen's employment states; in-commuting's no-resident-gain + wage-leakage accounting; the fiscal-thinness ledger shape (income tax only, no rates/corp share) for off-map-employed citizens.

## Acceptance criteria

### Functional — finite pools and exhaustion

- **AC-1 (GR#20 inbound contract).** `ExtCommuteAPI` matches code.json's registered pattern — pool queries and era-scaled capacity sourced from `data/external_world.json` — consumed by `ui.screen.demo` per the registered edge. Check: `go doc ./internal/engine/extcommute ExtCommuteAPI` (or equivalent) shows pool-query and capacity methods.
- **AC-2 (§21 named pools; era-scaled capacity table).** Three pools — London, Ashford, Dover — are each loaded with a **per-era capacity table** (A6: "London absorbs a bounded and slowly growing share"), not a single static number. Check: `go doc ./internal/engine/extcommute Pool` (or equivalent) shows a capacity function taking an era/tier argument; `grep -n "London\|Ashford\|Dover" data/external_world.json` (or the loader's schema doc) finds all three named.
- **AC-3 (conservation — the exhaustion identity, the check that makes finiteness real).** At every simulated tick and for every pool: `0 ≤ FilledSlots(pool) ≤ Capacity(pool, era)`, enforced as a hard invariant. Check: a passing test drives `FilledSlots` up to `Capacity` via repeated assignment commands, then issues one further assignment, and asserts (a) `FilledSlots` never exceeds `Capacity` at any point in the tick-by-tick trace, and (b) the assignment beyond capacity is **rejected**, not silently accepted (`grep -rn "func Test.*[Pp]oolExhaust\|func Test.*[Cc]apacityInvariant" internal/engine/extcommute/*_test.go`). **This is the check requested against the "never actually exhausted" trap:** a pool whose capacity is advisory-only (logged but not enforced) passes any check that merely asserts a capacity *number exists*; this check instead forces the pool to genuinely fill and proves the next request fails.
- **AC-4 (rejection is typed and non-corrupting).** The `(Capacity+1)`th assignment attempt returns a registry-sourced rejection (new `MET-E`-range code, GR#7) distinct from other rejection causes (AC-9's transport cap, AC-11's double-assignment), and the rejected citizen's employment state is left unchanged — still local-employed/unemployed, never granted a phantom off-map job. Check: a passing test asserts both the specific rejection code and the unchanged post-state (`grep -rn "func Test.*[Pp]oolFull.*[Rr]eject" internal/engine/extcommute/*_test.go`).
- **AC-5 (era scaling shape; GR#15 no hardcoding).** `Capacity(pool, era)` is non-decreasing in era/tier for a given pool, and no capacity number is hardcoded in Go source — every figure traces to `data/external_world.json`. Check: `grep -nE "[0-9]{3,}" internal/engine/extcommute/*.go` (excluding `_test.go`) finds no bare numeric literal plausibly a pool-capacity figure outside doc-comment prose transcribing the spec; a passing test asserts `Capacity(pool, laterEra) ≥ Capacity(pool, earlierEra)` for the same pool (`grep -rn "func Test.*[Ee]raScal" internal/engine/extcommute/*_test.go`).

### Functional — dormitory arithmetic and the second cap

- **AC-6 (the dormitory arithmetic identity — residents in = residents accounted for).** For every citizen of working age, exactly one of `{LocallyEmployed, OffMapEmployed(pool), Unemployed, NotInLaborForce}` holds at any tick — never two, never zero — expressed as an exact per-tick counting identity: `TotalWorkingAgeResidents == Σ LocallyEmployed + Σ_pool OffMapEmployed(pool) + Unemployed + NotInLaborForce`. Check: a passing test sums the four buckets across a synthetic population after a tick and asserts **exact** equality (not an epsilon-tolerant approximation) against the independently-counted working-age total (`grep -rn "func Test.*[Dd]ormitoryArithmetic\|func Test.*[Rr]esidentsAccounted" internal/engine/extcommute/*_test.go`). **Why this is the strongest available check:** it is an identity, not a range check — a citizen double-counted across two pools, or dropped from every bucket on a state transition, breaks it exactly rather than merely producing a plausible-looking total.
- **AC-7 (identity holds across state transitions, not just at rest).** The AC-6 identity holds not only in a static snapshot but immediately after every transition this module drives: assignment, release (job loss, death, emigration, local job found), and pool-full rejection. Check: a passing test drives a sequence of assignment/release commands and re-checks the AC-6 identity after each one, not only at the end (`grep -rn "func Test.*[Dd]ormitoryArithmetic.*[Ss]equence\|func Test.*[Tt]ransitionAccounting" internal/engine/extcommute/*_test.go`).
- **AC-8 (§21/A6b two independent caps — transport).** Assigning a citizen to an off-map job additionally requires available capacity on the reaching transport leg (motorway car/coach subject to `engine.traffic` congestion, or from tier 5 the external-rail season-ticket capacity) — per R6(b): "external rail/coach capacity and crowding already bind — now explicitly listed as the second cap." A citizen cannot be filled into a pool with free slots if the transport leg has none. Check: a passing test sets pool capacity high but saturates transport capacity via `engine.traffic`, and asserts the assignment is rejected despite free pool slots, with a rejection reason distinct from AC-4's pool-full reason (`grep -rn "func Test.*[Tt]ransportCap.*[Rr]eject\|func Test.*[Ss]econdCap" internal/engine/extcommute/*_test.go`).
- **AC-9 (§21 in-commuting — no resident gain).** When in-commuting fills a local labour shortage, the filling worker does NOT create or attach to a resident citizen record — `engine.citizens`' resident/population count is unchanged before and after. Check: a passing test fills a local vacancy via in-commuting and asserts population count is unchanged (`grep -rn "func Test.*[Ii]nCommut.*[Pp]opulation" internal/engine/extcommute/*_test.go`).
- **AC-10 (§21/F6 wage-leakage visibility).** In-commuting records a distinct wage-leakage ledger entry via `engine.finance`, separate from ordinary local wage payment, so F6's "player sees the leak" claim is a queryable ledger fact. Check: a passing test asserts a wage-leakage-category ledger entry exists for an in-commuter-filled vacancy, distinct from the local-wage category (`grep -rn "func Test.*[Ww]ageLeak" internal/engine/extcommute/*_test.go`).
- **AC-11 (double-assignment rejected, not overwritten).** Attempting to assign a citizen already holding an off-map job to a second pool or a second slot is rejected with a typed error, never silently overwriting the first assignment — an overwrite would under-count the pool and corrupt AC-6's identity invisibly. Check: a passing test attempts a double-assignment and asserts rejection plus an unchanged AC-6 identity (`grep -rn "func Test.*[Dd]oubleAssign" internal/engine/extcommute/*_test.go`).

### Functional — fiscal thinness and mental-health coupling

- **AC-12 (§21/A6c/F2 fiscal thinness — an accounting-shape assertion, not "less revenue").** For a citizen holding an off-map job, `engine.finance`'s ledger records nonzero income-tax revenue attributable to that citizen but **exactly zero** business-rates or corporate-share revenue attributable to them (A6c: "dormitory districts yield income tax but no business rates and no corp share"). Check: a passing test sums per-citizen ledger line categories for an off-map-employed citizen and asserts the rates/corp-share category total is exactly zero while the income-tax category is nonzero (`grep -rn "func Test.*[Dd]ormitory.*[Ff]iscal\|func Test.*[Nn]oRates" internal/engine/extcommute/*_test.go`). **False-pass warning:** a test asserting only "off-map citizens generate less total revenue than average" would pass a implementation that still (wrongly) attributes a small nonzero rates share — the check must assert the rates/corp-share category is exactly zero, not merely smaller.
- **AC-13 (§18/§19.3/A6d mental-health commute coupling — no duplicated logic, GR#3).** Out-commuters' door-to-door commute time (the motorway or external-rail leg) flows to `engine.wellbeing`'s `CommuteTime` driver through the same commute-time figure `engine.traffic`/`engine.citizens` already carry (§19.3) — this module does not compute or apply a separate, hand-invented mental-health penalty for dormitory commuters. Check: `grep -n "wellbeing\|mentalHealth\|CommuteTime" internal/engine/extcommute/*.go` (excluding `_test.go`) shows either a pass-through to the shared commute-time field or no direct reference at all (the coupling happens naturally once `engine.wellbeing` reads the citizen's stored commute time) — a duplicated/independent penalty computation in this package fails the check.
- **AC-14 (A6d soft cap only — no invented hard cap).** A citizen may hold an off-map job indefinitely, subject only to the pool cap (AC-3), the transport cap (AC-8), and `engine.wellbeing`'s emigration-probability soft cap (commute burden → mental health → emigration, A6d) — this module imposes no additional artificial hard cap (e.g. a maximum tenure) not named in §21/A6. Check: `grep -rn "maxTenure|forceLocal|yearsLimit" internal/engine/extcommute/*.go` finds no such cap.

### Error handling

- **AC-15 (GR#7).** A malformed or schema-invalid `data/external_world.json` (a pool missing a capacity table, a negative capacity or wage figure, an era not covering the world's current era) produces a registry-sourced error at load time — new `MET-E`-range code — never a silent zero-capacity default (which would make the pool permanently unusable) or unlimited-capacity default (which would defeat AC-3's finiteness). Check: `grep -n "MET-" internal/engine/extcommute/*.go` finds a registry code reference; passing malformed-data test coverage (`grep -rn "func Test.*[Mm]alformed\|func Test.*[Ii]nvalidPool" internal/engine/extcommute/*_test.go`).

### Determinism & safety

- **AC-16 (GR#21).** Pool assignment/selection order is a deterministic function of `(worldSeed, tick, command log)` — no map-iteration-order nondeterminism, no wall-clock dependency. Check: `grep -rn "func Test.*[Dd]eterminis" internal/engine/extcommute/*_test.go`.
- **AC-17 (SG-7; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/extcommute/*.go` (excluding `_test.go`) returns no matches.
- **AC-18.** `go test ./internal/engine/extcommute/... -race -count=1` passes with no data race on concurrent assignment/release, and the AC-3 pool-capacity invariant holds under concurrent access (not just single-threaded). Check: `grep -n "go func()" internal/engine/extcommute/*_test.go` finds at least one concurrency test that also re-checks the capacity invariant.

### Documentation

- **AC-19.** `internal/engine/extcommute/doc.go` states the module key `engine.extcommute`, cites §21 and A6, names the three pools, documents the two-cap model (pool + transport) and the dormitory arithmetic identity in prose, and states the fiscal-thinness accounting shape (income-tax-only, zero rates/corp-share) explicitly. Check: `grep -n "engine.extcommute" internal/engine/extcommute/doc.go` and `grep -n "§21\|A6" internal/engine/extcommute/doc.go` both match; all three pool names appear.

## Out of scope

- `engine.traffic`'s own congestion/crowding computation and `engine.finance`'s ledger mechanics beyond the specific category-zero/wage-leakage assertions — this item consumes those interfaces, it does not build them.
- The actual tuned capacity/wage-level/era-scaling numbers in `data/external_world.json` — currently an empty stub (`{"version":1,"profiles":[]}`); this item's ACs describe schema and mechanism (GR#15: "validators derive from data"), not final balance numbers, pending M2 tuning (same pattern as `engine.season.md`'s untuned curves).
- Housing typology/appeal-profile mechanics (§21's second half) — that is a separate housing-demand system, not this item's off-map-jobs/dormitory-arithmetic scope.
- `engine.citizens`' `employmentState` enum's own definition — this item assumes it as an off-map-job-capable state (see Escalations).
