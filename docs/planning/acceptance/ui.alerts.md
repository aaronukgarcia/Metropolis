## Why this file carries more control-behaviour scrutiny than a typical UI item

This is the one UI item in Sprint 8 whose failure mode is not "looks wrong" but "changes simulation state wrongly" — auto-pause. A dashboard that mis-renders is a visible bug; an alert stack that fails to auto-pause on a real crisis, or that auto-pauses spuriously on a routine P0 alert, is a bug a player may not notice until real damage has already happened in-sim. So alongside the usual functional ACs, this file treats auto-pause as a **control**: what arms it, what disarms it, what happens on repeat triggers, and what happens if a crisis arrives while the game is already paused for an unrelated reason — each gets its own AC rather than being folded into "crisis events auto-pause" as one line.

## User stories

- **US-1.** As **the player**, I need persistent chrome showing date, clock-cycle, speed, money, population, and rating at all times, so I never have to leave a screen to check the city's vital signs (§13).
- **US-2.** As **the player**, I need a bottom alert stack that is genuinely prioritised — the most important thing visible first, regardless of what order things happened to go wrong — so a low-stakes reminder never buries a real emergency (§13).
- **US-3.** As **the player**, I need every alert to jump to its screen on selection, and `!` to jump straight to the top alert, so an alert is an entry point into the game, not a dead notification (§13, UI-SPEC §3).
- **US-4.** As **the player**, I need a genuine crisis to auto-pause and redirect my camera/speed to the relevant queue, so I am never asked to react to a fast-moving emergency at 4× speed while looking at the wrong screen (§3).
- **US-5.** As **the player who is already paused, mid-menu, or already looking at a different crisis**, I need a new crisis to still redirect me to it, and I need auto-pause to never re-fire uselessly on a crisis I've already seen and am already dealing with, so the control earns its keep instead of nagging (§3, this file's own analysis below).

## Scope

The persistent top-bar chrome, the prioritised bottom alert stack (jump-to-source per alert, `!` for top alert), and crisis auto-pause (trigger, camera/speed redirect, re-arm semantics). This item consumes `int.protocol` view subscriptions/events for chrome figures and alert/crisis data, and calls through `ui.core` for navigation and `ui.keys`' global-binding mechanism for `!` — it does not reimplement navigation or key dispatch.

## Acceptance criteria

### Functional

- **AC-1.** The top bar renders date, clock-cycle position (which of the 30 logistics day-ticks within the current month), speed multiplier, money, population, and credit rating, sourced from `int.protocol` view subscriptions/deltas — a passing test asserts each field renders from known injected values and updates when a new delta arrives.
- **AC-2.** The bottom alert stack renders a list of active alerts, each colour-coded by severity/priority tier — a passing test asserts N alerts of mixed tiers render with the correct colour per tier (per this file's ASM-tier scheme, see Escalations).
- **AC-3 (jump-to-source, the drill-through instance).** Selecting an alert and confirming (or `Enter`, matching the drill-through convention `ui.dash.md` establishes) navigates to that alert's registered screen/target via the same `ui.core` navigation call `ui.dash`'s `DrillTarget` mechanism uses (`ui.dash.md` AC-6) — this package does not implement a second, parallel navigation path. Check: `grep -n "core\.\(Focus\|Navigate\|SwitchScreen\)" internal/ui/screens/chrome/*.go` shows the same call shape `ui.dash` uses (cross-reference its AC-6); a passing test asserts selecting a known alert results in exactly its registered target's navigation call. Every alert is constructed with a required, non-optional jump target at creation (mirroring `ui.dash`'s AC-4 "cannot be constructed without a `DrillTarget`" discipline) — a passing test asserts an alert cannot be added to the stack without one (`grep -rn "func Test.*[Nn]ilTarget\|func Test.*[Rr]equireTarget" internal/ui/screens/chrome/*_test.go`). **This is the check that rejects the lazy-but-plausible build**: rendering four example alerts (`Water deficit`, `School capacity`, `Loan payment`, `Junction at 94%`) that each happen to have a target wired by hand is a demo, not a guarantee — the guarantee is that the *construction path* rejects a targetless alert, the same distinction `ui.dash.md` AC-4 draws for tiles.
- **AC-4.** `!` (a global binding per `ui.keys`' registered-action model, not a bespoke key handler in this package) jumps to the current top-of-stack alert — a passing test asserts firing the registered `!` action invokes AC-3's jump mechanism against whichever alert is currently ranked first, not a fixed/first-inserted alert (see AC-5 for what "ranked first" must mean).
- **AC-5 (prioritisation, made adversarial rather than trusted).** The stack's ordering is driven by priority tier, with a documented, deterministic tie-break (e.g. oldest-first within a tier) — **never** insertion order across tiers. Check: a passing test inserts a low-tier alert, then a mid-tier alert, then a **high-tier** alert last, and asserts the stack's top-of-list (and `!`'s target) is the high-tier alert despite arriving last — this is the check that rejects a stack that only ever *looks* prioritised because test fixtures happen to insert alerts in priority order already. A second passing test inserts two same-tier alerts and asserts the documented tie-break (not map-iteration order, not arrival-order-by-accident) determines their relative position, repeatably across runs.
- **AC-6 (crisis trigger — arming).** A crisis is a **distinct, explicitly-tagged** signal on the incoming alert/event data (see Escalations, ASM-276) — not derived implicitly from an alert's priority tier alone. A P0-tier alert that is not tagged crisis (e.g. "Loan payment due" — urgent, but not the kind of emergency §3 means) must not auto-pause; an alert tagged crisis auto-pauses regardless of its display tier. A passing test asserts both: a non-crisis P0 alert arriving does not pause or redirect, and a crisis-tagged alert (of any display tier) does.
- **AC-7 (crisis trigger — the redirect).** A crisis firing (AC-6) pauses (equivalent to `Space`, via `ui.core`'s speed-control call, not a bespoke pause implementation) and redirects the camera/focus to the crisis's relevant queue/screen, via the same jump mechanism as AC-3 — a passing test asserts both effects (speed→pause, navigation→the crisis's target) occur together on a single crisis trigger.
- **AC-8 (edge-triggered, not level-triggered — the spurious-refire guard).** A crisis that is still ongoing across multiple consecutive deltas/ticks (the same crisis identity reported again because the underlying condition persists) triggers AC-7's pause-and-redirect **exactly once** — not once per delta while the condition remains true. A passing test feeds the same crisis ID across ≥3 consecutive deltas and asserts pause/redirect fired on the first occurrence only, with no further `ui.core` navigation/speed calls on the 2nd/3rd. A **second, distinct** crisis ID arriving later (even while the first crisis's alert is still present in the stack) **does** trigger AC-7 again — a passing test asserts a second, different crisis ID does fire a fresh pause-and-redirect, so AC-8's dedupe is keyed on crisis identity, not on "a crisis is currently active at all" (the latter would wrongly suppress a second, unrelated emergency).
- **AC-9 (re-arm across a manual resume — the other half of the spurious-refire guard).** If the player manually resumes (`Space`) after an AC-7 auto-pause while the triggering crisis condition is *still* present in the next delta (the crisis hasn't resolved, it's just no longer the newest information), the still-ongoing same-ID crisis must **not** immediately auto-pause again on the very next tick — AC-8's per-crisis-ID dedupe already covers this (the ID was already seen), but this AC exists to test it specifically at the moment of a manual resume, since that is the point a naive "pause flag" implementation is most likely to get relatched by a stale crisis-still-present check racing the resume. A passing test: crisis fires → auto-pause → player resumes → next delta still reports the same crisis ID → asserts no second pause occurs. A following, genuinely new crisis ID **does** still pause (re-confirms AC-8's second half isn't broken by this AC's resume path).
- **AC-10 (already-paused arrival — the redirect must not silently no-op).** If the player is already paused (manually, or from a prior crisis) when a **new, distinct** crisis arrives, AC-7's camera/screen redirect still fires — pause is idempotent (already paused stays paused, no error, no toggle-to-unpause), but the redirect to the new crisis's queue is **not** skipped just because "we're already paused, nothing to do." A passing test: manually pause → new crisis arrives → asserts the crisis's navigation target still fires (camera moves to the new crisis) even though the speed-control call is a no-op/idempotent-pause rather than a fresh pause transition. **This is the check that rejects the lazy-but-plausible build**: an implementation that guards the whole AC-7 handler behind "if already paused, return early" satisfies AC-7's own single-trigger test (which fires from a running state) and AC-8's dedupe test, but silently drops the redirect for every crisis that arrives while paused — exactly the failure mode US-5 calls out.

### Error handling

- **AC-11 (GR#7).** An alert or crisis-tagged event with a missing/malformed jump target (fails AC-3's/AC-6's required-target construction) is rejected at construction with a registry-sourced error (new `MET-U`-range code, per this sprint's per-module subrange-claiming convention, `README.md` "Conventions ratified during Sprint 1") rather than silently entering the stack targetless or crashing the chrome render loop. A passing test covers this path. — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches the claimed MET-U code AND that no targetless alert/crisis event was silently entered onto the stack, not merely that a passing test exists.
- **AC-12.** A stale alert (its underlying condition has resolved — e.g. the water deficit was fixed) is removed from the stack on the next delta reporting its resolution, not left as a dead entry the player must manually dismiss, unless UI-SPEC's examples imply otherwise (none do) — a passing test asserts a resolved alert's ID disappears from the rendered stack on the delta that reports resolution.

### Determinism & safety

- **AC-13 (GR#20).** `go list -deps ./internal/ui/screens/chrome/...` shows no import of `internal/engine/...` — chrome figures, alerts, and crisis events all arrive via `int.protocol` subscriptions/deltas/events, never a direct engine call (this package's registered outbound edges in code.json are `ui.core` and `engine.projections`; the latter is consumed via `engine.projections`' own documented pattern — "UI subscribes to named projections" — i.e. through the protocol's subscription mechanism, not a Go import; AC-13's grep is what actually proves this rather than the registry entry alone).
- **AC-14 (GR#21).** AC-5's tie-break ordering does not depend on Go map iteration — `grep -rn "for .* := range" internal/ui/screens/chrome/*.go` shows any map range feeding stack order is sorted first (`grep -n "sort\." internal/ui/screens/chrome/*.go` corroborates); a passing determinism test asserts identical ordering across repeated runs with an intentionally map-sourced input.
- **AC-15.** `grep -rn "time.Now" internal/ui/screens/chrome/*.go` (excluding `_test.go`) returns no matches outside a documented, injectable-clock site (if AC-5's tie-break or AC-2's colour-pulse uses elapsed time rather than a sim-tick/sequence number) — matching the pattern already established in `ui.keys`/`foundation.errors`.
- **AC-16.** `go test ./internal/ui/screens/chrome/... -race -count=1` passes with no data race between the delta-consuming goroutine (chrome figures, alert stream) and the render/dispatch path (`grep -n "go func()" internal/ui/screens/chrome/*_test.go` finds a concurrency test).

### Documentation

- **AC-17.** The package doc states module key `ui.alerts`, cites §13 and §3, and documents the crisis-vs-alert distinction from AC-6 explicitly (a crisis is a tagged subset of alerts, not derived from tier) and the edge-triggered/idempotent-redirect semantics from AC-8/AC-9/AC-10, since these are exactly the control behaviours a future maintainer is most likely to "simplify" back into a bug.

## Out of scope

- The engine-side logic that decides *when* a condition becomes crisis-worthy (thresholds, which system's shortfalls qualify) — that is engine-side (`engine.projections` and the owning system modules), not this UI item; this item only consumes the tagged signal once emitted (see Escalations — the tag itself needs a home).
- F1's own overlay/inspect drill-through (`ui.screen.map`'s AC-5/AC-6) and general dashboard tiles (`ui.dash`'s AC-4/AC-5) — this item reuses their shared navigation call (AC-3) but does not own their construction.
- The `` ` `` console, `?` context help, `1/2/3` speed globals — other `ui.keys` global bindings, not this item's concern beyond consuming `Space`'s pause call for AC-7.

## Escalations

- **For Bill/Aaron — the load-bearing finding (protocol carry for the crisis tag).** AC-6 requires a crisis to be a *distinct, explicitly-tagged* signal, not something this package infers from priority tier — but nothing in `int.protocol`'s documented schema (`int.protocol.md`) currently names an "is this a crisis" field on `Event`/`Delta`, nor does `engine.projections`' registered pattern ("systems register curve providers; UI subscribes to named projections") say how a system marks one of its emitted alerts as crisis-grade versus routine. Without that tag living somewhere on the protocol side, `ui.alerts` has no honest way to satisfy AC-6 other than guessing from tier (which AC-6 explicitly forbids, because §3's "Loan payment due" example is P0-worthy but not §3's kind of crisis). This is the same shape of gap as `ui.dash.md`'s `DrillTarget` finding and `BUG-058` — a spec-mandated distinction with no registered carrier — logged as **ASM-276**, but flagging to **both** Bill and Aaron specifically because *what counts as a crisis* (which system conditions get the tag) is a design/balance call, not an engineering one, and belongs to Aaron per this file's own instructions ("Anything a player feels — especially auto-pause triggers — is usually Aaron's call").
- **For Aaron.** The crisis *set* itself is undecided by the spec beyond illustrative colour ("a crisis event" is used but never enumerated) — §3 doesn't say whether "Water deficit in 3 months" (a projection warning, plenty of lead time, exactly what the "squeezed never ambushed" pillar promises) counts as a crisis worth auto-pausing for, versus something acute like a junction gridlock or a service collapse happening *now*. I've written AC-6 so the mechanism is sound regardless of which alerts end up tagged, but the tagging policy itself needs Aaron's call before engine-side systems can implement it consistently — logged as **ASM-277**.
- **Assumptions logged separately (ASM-xxx, see report to Ben).** The concrete priority-tier scheme and its colour mapping (AC-2), the tie-break rule within a tier (AC-5, "oldest-first" chosen as the default), and the specific `MET-U` subrange this item claims (AC-11) are all implementer/BA defaults per the AC-4/AC-9-style precedent already established in `ui.keys.md` and `ui.harness.md`.
- **Balance-number placeholders (folded, A2).** ASM-278: alert priority-tier scheme/colours/tie-break are implementer/BA defaults, not spec-mandated. ASM-532: three-tier scheme (Info/Warning/Critical → TokenSelection/Warning/Danger) BA-chosen.
- **ASM-533 (confirm-and-close).** Tie-break = oldest-first by Alert.Tick, then ascending ID (deterministic).
