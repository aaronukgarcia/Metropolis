## Why this is a dedicated data-authoring item, not an addition to `engine.unlocks.md`

`engine.unlocks.md` (MOD-032) already carries a full, committed acceptance set for the gate-check *mechanism* — the API surface, the milestone ladder, DP spend/prerequisite rules, the Buy path, debug force-unlock, determinism, error handling. Its own AC-6 requires "exactly the 12 named categories... each loaded from `data/unlock_trees.json`," and its own AC-18 requires the file carry a `$comment` citing §22 — but neither AC populates the file's actual node content, because MOD-032's own Escalations section (2026-08-10) flags exactly that gap as "comparable in scope to `data.catalogue`'s buildings.json effort" and recommends splitting it into its own item. FEAT-029 is that split. This file is scoped to `data/unlock_trees.json`'s schema and content only — it does not re-litigate MOD-032's gate-check ACs, load contract, or error-handling requirements, all of which stay as MOD-032 wrote them.

## User stories

- **US-1.** As `engine.unlocks`'s `IsUnlocked`/tree-loading path (MOD-032 AC-6), I need `data/unlock_trees.json` to carry exactly the 12 categories §22 names, each a real progression tree, so two players at the same milestone tier genuinely own different toolkits instead of loading an empty stub that silently gates nothing.
- **US-2.** As the player working through the milestone ladder (§4), I need every tier's §10-named signature content to be represented in the relevant category tree(s), so reaching a population threshold and then opening the DP-tree screen shows the toolkit §10 actually promises, not a handful of nodes concentrated in a few tiers with the rest silently blank.
- **US-3.** As `data.catalogue`'s `unlock` field (FEAT-010) and `engine.unlocks`'s gate-check (MOD-032 AC-10), I need every DP-tree node this file defines to carry a stable `id` catalogue entries can reference, so a building's declared `unlock.dp` gate resolves against a real node, never a dangling string.
- **US-4.** As the Tester/Destructive agent verifying this item, I need every "is this tree complete" check to derive its expected coverage from the file's own declared structure (12 categories × 13 tiers, ASM-482's floor) rather than a hand-picked example count, so the check keeps working correctly as later balance passes add nodes (GR#15).
- **US-5.** As a future contributor reading this file cold, I need every node to state plainly which specific §10 signature-unlock item it represents (or, per ASM-481, that it is a deliberate no-op for a tier/category with no §10 content), so nobody mistakes an authoring gap for a design decision or vice versa.

## Scope

`data/unlock_trees.json` content and schema: 12 category trees (Roads, Electricity, Water & Gas, Health & Deathcare, Education, Fire, Police, Garbage, Parks & Rec, Transport, Communications, Welfare — §22's exact list), each covering all 13 milestone tiers (Wilderness…Centopolis, §4's exact ladder), each tier represented by at least one node — a real signature-unlock node transcribed from §10's inventory, or an explicit documented no-op node where §10 names nothing new for that category at that tier (ASM-481). DP costs and milestone-tier prerequisites are placeholder-and-disclosed (M2 Batch tuning territory, same carve-out `data.catalogue.md`/`data.modes-naming.md` already use) — this item authors the *shape and inventory*, not final balance numbers.

Out of scope: `engine.unlocks`'s gate-check mechanism, API surface, XP accrual, Buy-path, or debug force-unlock (all MOD-032, already committed); `data/buildings.json`'s own `unlock` field content (FEAT-010, already committed); final-tuned DP costs or prerequisite depth (M2 Batch).

## Acceptance criteria

### Schema — structure

- **AC-1 (§22; exactly 12 categories).** `data/unlock_trees.json` is valid JSON, `version: 1`, and its `trees` array contains **exactly** the 12 category names §22 lists verbatim — Roads, Electricity, Water & Gas, Health & Deathcare, Education, Fire, Police, Garbage, Parks & Rec, Transport, Communications, Welfare — each keyed by a stable lowercase-slug `id` matching the project's `buildingIDPattern` convention (`^[a-z][a-z0-9_.-]{2,63}$`, per `data.modes-naming.md` AC-1/AC-13 precedent), since these IDs become the lookup keys `engine.unlocks` AC-6 tests against. Check: a passing loader test asserts the loaded file's category-ID set equals the 12 IDs derived from a checked-in reference list transcribed from §22 (not a hardcoded `len(trees) != 12` literal) (`grep -rn "func Test.*[Tt]welveCategories\|func Test.*[Cc]ategorySet" internal/foundation/data/unlock_trees_test.go`). **What a lazy implementation looks like:** shipping 11 categories because "Water & Gas" gets silently split or merged with another, or a 13th category invented that isn't in §22 — either would pass a bare `len() == 12` check while failing the actual set comparison this AC requires.
- **AC-2 (§4/ASM-481; every category covers all 13 tiers).** Every one of the 12 category trees contains at least one node tagged `tier` for **every** one of the 13 milestone tiers (1=Wilderness…13=Centopolis) — no tier silently skipped. Where §10 genuinely names no new signature content for a category at a given tier, the node for that tier is present but explicitly marked `kind: "none"` with a `note` explaining why (ASM-481) — never simply absent. Check: a passing loader test asserts, for each of the 12 categories, the set of tiers with at least one node equals `{1..13}` exactly (`grep -rn "func Test.*[Aa]llTiersCovered\|func Test.*[Nn]oMissingTier" internal/foundation/data/unlock_trees_test.go`). **What a lazy implementation looks like:** a category tree with real nodes clustered at tiers 4/7/9 (where the big §10 set-pieces land — grid, port, districts) and silently nothing at tiers 1/2/3/5/6/8/10/11/12/13, which is exactly the "toolkit is thin outside a few headline tiers" failure US-2 exists to catch, and which a check for "at least one node total per category" would not detect.
- **AC-3 (ASM-482; the 13-entry-per-category floor).** Every one of the 12 category trees contains **at least 13 nodes** (the 12×13 structure FEAT-029's own title specifies — one node per tier minimum, ASM-482), of which real (non-`none`-kind) nodes number at least as many as the tiers with genuine §10 content for that category. Check: a passing loader test asserts `len(nodes) >= 13` per category, with the `13` read from a named constant documented as tracing to ASM-482 (not a bare magic number) (`grep -rn "func Test.*[Cc]ategoryFloor\|func Test.*[Mm]inNodeCount" internal/foundation/data/unlock_trees_test.go`). **False-pass warning:** a check that only asserts "total nodes across all 12 trees >= 156" would pass an implementation that dumps all 156+ nodes into one or two categories and leaves others at the AC-2 minimum of 13 `none`-kind placeholders — the per-category floor must be checked individually, not as an aggregate sum.
- **AC-4 (node identity and lookup key).** Every node carries a stable lowercase-slug `id`, unique across the *entire* file (not merely unique within its own category tree), matching `buildingIDPattern`, since `data.catalogue`'s `unlock.dp` field (US-3, MOD-032 AC-10) references a node by this ID with no category-scoping in the reference. Check: a passing loader test asserts no two nodes anywhere in the file share an `id` (`grep -rn "func Test.*[Dd]uplicateNodeID\|func Test.*[Gg]lobalUnique" internal/foundation/data/unlock_trees_test.go`).
- **AC-5 (§10; real-node content, spec-traceable).** Every non-`none`-kind node carries a `name`, a `description`, and a `specRef` field naming the specific §10 inventory item it represents (e.g. `"§10: healthcare & deathcare"`, `"§10: public transport (bus)"`) — never a node whose content was invented with no traceable §10 origin. Check: a passing loader test spot-checks at least 6 nodes spanning at least 4 different categories against §10's literal wording for `specRef` traceability (GR#15 transcription, not invention) (`grep -rn "func Test.*[Ss]pecTraceable\|func Test.*[Ss]pecRef" internal/foundation/data/unlock_trees_test.go`).
- **AC-6 (§22/MOD-032 AC-7; DP cost and milestone prerequisite).** Every non-`none`-kind node carries a `dpCost` (non-negative integer, placeholder value) and an optional `prereqTier` (int 1-13, the earliest milestone tier at which the node becomes spendable — matching §4's own tier-gating of signature content) and an optional `prereqNodeIds` (list of other node `id`s that must already be unlocked first, within the same or a different category — DP trees may cross-reference, e.g. a Transport node prerequisiting a Roads node). Check: a passing loader test asserts every real node has a non-negative `dpCost`; where `prereqTier` is present it is in `1..13`; where `prereqNodeIds` is present every referenced ID resolves to a real node in the file (`grep -rn "func Test.*[Dd]pCost\|func Test.*[Pp]rereq" internal/foundation/data/unlock_trees_test.go`).
- **AC-7 (acyclic prerequisite graph).** The `prereqNodeIds` relation across the entire file forms a **directed acyclic graph** — no node, directly or transitively, prerequisites itself. Check: a passing loader test performs a cycle-detection pass over the full node graph and asserts none exists (`grep -rn "func Test.*[Cc]ycle\|func Test.*[Aa]cyclic" internal/foundation/data/unlock_trees_test.go`) — this is the concrete authored-data proof for `engine.unlocks.md` AC-13's "a cyclic tree dependency... fails loudly at load time" requirement; this AC proves the *shipped* file has no such cycle, AC-13's loader-side check (MOD-032, already committed) proves a *future* malformed edit would be caught.
- **AC-8 (§4; tier-node population-threshold consistency).** Where a node carries `prereqTier`, the population threshold implied is consistent with §4's ladder — a node cannot claim `specRef` traceability to a §10 item that §4's table places at tier 7 while declaring `prereqTier: 4`. Check: a passing loader test cross-references each node's `prereqTier` against a checked-in tier→population reference table transcribed from §4, flagging any node whose `specRef` text names a tier-gated item inconsistent with its declared `prereqTier` for the spot-checked sample from AC-5 (`grep -rn "func Test.*[Tt]ierConsistency" internal/foundation/data/unlock_trees_test.go`).
- **AC-9 (kind enum, closed set).** Every node's `kind` field is one of a closed, documented enum: `"unlock"` (real signature content, the default), `"none"` (ASM-481's documented no-op placeholder). Check: a passing loader test asserts no node's `kind` falls outside this two-value enum (`grep -rn "func Test.*[Kk]ind" internal/foundation/data/unlock_trees_test.go`).

### Error handling (GR#7)

- **AC-10.** A malformed or schema-invalid `data/unlock_trees.json` (a category missing entirely, a tier gap within a category, a node with no `dpCost`, a `prereqNodeIds` reference to a nonexistent node, a prerequisite cycle) produces a registry-sourced error (new `MET-E`-range code) at load time, identifying the offending category/tier/node — never a silent default (e.g. treating a missing tier as "no unlocks exist here" indistinguishable from a genuine `kind: "none"` node) or a silently-dropped node. Check: `grep -n "MET-" internal/foundation/data/unlock_trees.go` finds a registry code reference; passing malformed-data test coverage for at least the five named failure classes (`grep -rn "func Test.*[Uu]nlockTreesInvalid\|func Test.*[Mm]alformedTree" internal/foundation/data/unlock_trees_test.go`). **What a lazy implementation looks like:** the loader treating an absent tier the same as a documented `kind: "none"` node — this would defeat AC-2's entire purpose, since a category that silently omits a tier and a category that explicitly documents "nothing here" become indistinguishable to every downstream consumer, exactly the ambiguity ASM-481 exists to remove.

### Determinism & safety

- **AC-11 (GR#21; deterministic load).** Loading the file twice produces byte-identical in-memory structures; any validation-error ordering is stable and sorted (by category ID then node ID), never dependent on Go map iteration order. Check: `grep -n "sort\." internal/foundation/data/unlock_trees.go` shows an ordering step wherever validation errors are aggregated; a passing determinism test exists (mirrors `data.catalogue.md` AC-13 / `data.modes-naming.md` AC-20 precedent).
- **AC-12 (no non-reproducible values).** The file contains no timestamp, machine-specific path, or other non-reproducible value inside a node body (a top-level `version`/`generatedAt` metadata field is fine and excluded). Check: `grep -n "\"[0-9]\{4\}-[0-9]\{2\}-[0-9]\{2\}T" data/unlock_trees.json` finds no ISO-timestamp values inside node bodies.

### GR#15 — validators derive from data, not hardcoded counts

- **AC-13.** No test in `unlock_trees_test.go` hardcodes an expected node count as a bare integer literal compared against a *live* population figure without traceability to this file's own AC-2/AC-3 documented derivation — every "how many" assertion either derives from the loaded file itself, from a checked-in reference list transcribed from §22/§4, or from a named constant documented as tracing to ASM-481/ASM-482 (the sanctioned exceptions, since both are explicitly derived-and-logged, not silently invented). Check: review of `unlock_trees_test.go` for any bare integer literal used as an expected-count assertion with no comment tracing it to a spec table or a named/documented constant.

### Documentation

- **AC-14.** `data/unlock_trees.json` carries a top-level `$comment`/`meta` block citing §22 and §4, listing the 12 category names, and stating the placeholder-DP-cost disclosure (mirroring `data/buildings.json`'s and `data/market.json`'s existing convention, and satisfying `engine.unlocks.md`'s own already-committed AC-18 verbatim). Check: `grep -n "\$comment\|\"meta\"" data/unlock_trees.json` matches, and the value names §22/§4 and the 12 category names.
- **AC-15.** A schema reference document (`docs/design/unlock-trees-schema.md`) describes every field this item introduces (category/tree fields; node `id`/`kind`/`specRef`/`dpCost`/`prereqTier`/`prereqNodeIds` fields; the ASM-481 no-op convention; the ASM-482 floor rule), so a later M2 Batch balance editor or `data.catalogue`-side contributor has a field reference without reverse-engineering the loader. Check: file exists and lists all named field groups.

## Escalations

- **For Bill — the no-op node convention (ASM-481) is a BA judgment call, not spec-mandated.** §10/§22 do not explicitly require every category to have content at every tier, nor do they prescribe how to represent "nothing new here." The `kind: "none"` explicit-placeholder convention is chosen so AC-2's "no missing tier" check is mechanically verifiable (an absent tier and a deliberately-empty tier are otherwise indistinguishable) — consistent with how `data.modes-naming.md` AC-3 handled a comparable degenerate-but-legal schema case (flagged explicitly rather than silently allowed or silently forbidden). If Bill wants a different convention (e.g. tiers may simply be absent, with coverage checked by "every category has a node at at least N tiers" instead of exactly all 13), that changes AC-2/AC-9 materially.
- **For Bill — the 13-entries-per-category floor (ASM-482) sets a minimum, not a target.** §10's inventory is large enough that several categories (notably Transport, given §19/§20's own weight, or Health & Deathcare, given §10's explicit callout) plausibly warrant well more than 13 real nodes if the "full inventory" instruction in FEAT-029's own title is taken literally against §10's complete content. This BA file sets the mechanically-checkable floor (AC-3) but does not attempt to specify an exact per-category node count, since §10 does not itself enumerate a fixed count per category — a fuller inventory is a legitimate over-delivery, not a violation, and a follow-up BOW item may be warranted later if a specific category's tree still reads thin after this pass (same shape as MOD-032's own escalation that led to FEAT-029 existing).
- **Assumptions flagged — ASM-481 (every-category-every-tier coverage with explicit no-op nodes) and ASM-482 (13-entry-per-category floor, deriving the 12×13 multiplier from FEAT-029's own title).** Both logged in the BOW (`node claude-bow.js show ASM-481`, `ASM-482`) per process v1.9; see AC-2/AC-3/AC-9 above for the specific reasoning. Lead ACCEPT/REJECT pending — dispatch should not proceed until these are ruled, since they materially shape AC-2/AC-3/AC-9's pass/fail behaviour.
