## User stories

- **US-1.** As the player, I need **four distinct chopper unit types** — police, fire, ambulance, VIP/commercial — each with a role-specific effect (police = coverage/response, fire = remote/blaze reach, ambulance = hospital-landing time, VIP = commercial/approval), so a chopper is not one generic unit with a cosmetic label (design: "four roles").
- **US-2.** As the city's books, I need a chopper to be **expensive** — a very high purchase cost (CAPEX) AND a high, multi-component running cost (fuel, hangar, insurance, crew — OPEX) — so it is a prestige/capacity asset the player earns, never an early-game unit (design: EXPENSIVE).
- **US-3.** As the air fleet, I need a chopper to fly **only with a trained pilot** assigned from the staffed skill pool, so "no pilot, no flight" is mechanical, not a flavour note (design: SKILLED).
- **US-4.** As the maintenance spine, I need each chopper to carry a **significant** engineer-hour burden with downtime when it goes un-serviced, so air assets are a real upkeep cost, not free power (design: MAINTENANCE-HEAVY).
- **US-5.** As the emergency services, I need choppers to **reach incidents fast and save lives** — the air ambulance lands at hospitals quickly, the fire chopper reaches remote/blaze sites without traffic delay, the police chopper extends coverage — with each role's effect flowing through the unified dispatch outcome path, not a parallel outcome model (design: EFFECTIVE).
- **US-6.** As the population, I need approval to **rise** because a chopper cuts response time / extends coverage (the "not stuck in traffic" dividend), with the weight a data placeholder, so the chopper's popularity is a felt, tunable effect (design: POPULAR).
- **US-7.** As the sim, I need choppers to be **traffic-immune** (road-independent travel) but **weather-limited** (a documented adverse-weather state grounds or degrades them), so gridlock is the problem they solve and weather is the problem they cannot (design: TRAFFIC-IMMUNE).

## Scope

Four distinct rotary-wing unit types (police, fire, ambulance, VIP/commercial) with role-specific effects, data-driven purchase/running costs from `data/helicopters.json`; purchase posting as CAPEX and running cost as OPEX through `engine.finance`; pilot gating through `engine.staffing`'s skill pool; per-chopper maintenance burden through `engine.maintenance`'s demand surface; traffic-immune weather-limited routing; a data-driven population-approval weight; and a fleet-conservation identity. No final cost/salary/hours/delta/weight values (Aaron's balance pass), no pilot-supply modelling (MOD-073), no maintenance-demand authoring (MOD-072), no OPEX-ledger placement (FEAT-094), no dispatch assignment/outcome-curve reimplementation (MOD-040), and no UI screen (ui.screen.*).

## Acceptance criteria

### Functional — four distinct roles and the contract surface

- **AC-1 (four distinct unit types with role-specific effects, not one generic chopper).** The air-unit model defines **four distinct unit types** — police, fire, ambulance, VIP/commercial — each with its own type key and its own effect surface, not a single `Chopper` type carrying a role string. Check: `go doc ./internal/engine/airunits` shows four distinct type constructors/records (or a single registry enumerating four distinct typed entries, each resolving to a distinct effect); a passing test enumerates the type vocabulary and asserts (a) exactly four resolvable types exist, (b) the four type keys are distinct, and (c) each type maps to a distinct effect path (`grep -rn "func Test.*[Ff]ourRoles\|func Test.*[Rr]oleTypes" internal/engine/airunits/*_test.go`). **False-pass risk:** a single `Chopper{role string}` struct with a `switch role` effect dispatch would pass a "roles exist" grep while making the roles cosmetic data on one shared implementation — the check requires four distinct typed surfaces, each with its own effect (the design's "police/fire/ambulance/VIP" are *different units*, not one unit with a mode flag).

- **AC-2 (GR#20; `AirUnitsAPI` contract + registered seams — consume, never reimplement).** An `AirUnitsAPI` (or equivalent) exists with a query surface and command-based mutation, and the feature consumes dispatch, finance, staffing, and maintenance **only** through registered interfaces — never engine internals. Check: `go doc ./internal/engine/airunits AirUnitsAPI` shows query methods (e.g. `Fleet`, `UnitStatus`, `RoleEffect`, `ApprovalWeight`) and command-based mutation (e.g. `Purchase`, `AssignPilot`, `Dispatch`); `grep -rn "dispatch\.\|finance\.\|staffing\.\|maintenance\." internal/engine/airunits/*.go` (excluding `_test.go`) shows live calls into registered surfaces, and `grep -rn "internal/engine/" internal/engine/airunits/*.go` (excluding `_test.go`, excluding the airunits package's own path) finds no raw import of a sibling engine package's internals. See Escalation ES-1 — none of these seams are registered in code.json today. **False-pass risk:** an implementation that imports `engine.dispatch`'s internal unit-assignment map or `engine.finance`'s ledger directly would pass a "choppers dispatch and spend" functional test while violating GR#20's contract-first rule and coupling airunits to unregistered internals — the check requires the seams to be interface-typed, so a registry edge can later be drawn for each call.

### Functional — purchase (CAPEX) and running cost (OPEX)

- **AC-3 (purchase is CAPEX, data-driven and milestone-gated — EXPENSIVE, never early-game).** Each type's purchase cost is loaded from `data/helicopters.json` (with a disclosure comment naming it a placeholder), carries an **unlock milestone** in the same data (so "never an early-game unit" is mechanically enforced, not a hope), and a purchase command posts the cost as a **capital** event through `engine.finance`'s existing settlement surface (`CatConstruction`/`CatInvestment` path, not an operating line). Check: `grep -n "purchase\|cost\|unlock\|milestone\|capex\|capital" data/helicopters.json` shows a per-type purchase figure and a per-type unlock gate with disclosure fields; a passing test mutates a type's purchase cost in the loaded fixture and asserts the purchase command posts the changed figure (`grep -rn "func Test.*[Pp]urchase.*[Dd]ata\|func Test.*[Cc]apex" internal/engine/airunits/*_test.go`); `grep -rn "finance\." internal/engine/airunits/*.go` (excluding `_test.go`) shows the CAPEX post into the finance edge; `grep -nE "[0-9]{4,}" internal/engine/airunits/*.go` (excluding `_test.go`) finds no bare cost literal outside doc prose. **False-pass risk:** a hardcoded per-type cost literal in Go would pass a "purchase costs money" test while freezing a player-felt number a junior was never authorised to invent — the check requires the figure to live in the data file and change with the fixture. **Balance-regime note:** the specific figures are placeholders (see AC-17); this AC checks *purchase is a data-driven, milestone-gated capital event*, not any specific magnitude.

- **AC-4 (running cost is OPEX, composed of named components — EXPENSIVE).** Each type's running cost is a **composed** figure of named components — fuel, hangar, insurance, crew — each loaded from `data/helicopters.json`, and posted through `engine.finance`'s OPEX surface (`SettleOpex`/a `CatOpex`-family path), so the drain is visible and real. A **grounded** chopper still incurs the standing components (hangar, insurance, crew), while **flying** additionally incurs fuel — running a chopper is never free, and flying it is costlier than parking it. Check: `grep -n "fuel\|hangar\|insurance\|crew" data/helicopters.json` shows the named components; a passing test posts a month for (a) a grounded and (b) a flying chopper and asserts both land in finance as distinct OPEX entries and that the flying total exceeds the grounded total by the fuel component (`grep -rn "func Test.*[Rr]unningCost\|func Test.*[Ff]uelComponent\|func Test.*[Gg]rounded.*[Cc]ost" internal/engine/airunits/*_test.go`). **False-pass risk:** a single lumped "operating cost" figure with no components would pass a "running cost posts to OPEX" test while hiding the fuel/hangar/insurance/crew structure the design names explicitly and making the grounded-vs-flying distinction un-checkable — the check requires the components to be named and independently posted. **Balance-regime note:** every component figure is a placeholder (AC-17); this AC checks structure and the flying > grounded direction, never a magnitude.

### Functional — pilot staffing and maintenance burden

- **AC-5 (no pilot, no flight — GR#20 staffing seam).** A chopper may enter a flying/dispatchable state only when a **trained pilot** is assigned to it, and pilot assignment is performed through `engine.staffing`'s skill-pool surface (MOD-073's trained-citizen pool), never a chopper-local headcount. Removing the pilot grounds the chopper; a citizen without the pilot qualification is rejected. Check: `grep -rn "staffing\." internal/engine/airunits/*.go` (excluding `_test.go`) shows the pilot-assignment seam calling the staffing surface; a passing test (a) assigns a qualified pilot and asserts the chopper becomes dispatchable, (b) removes the pilot and asserts it grounds, and (c) attempts an unqualified citizen and asserts rejection with no state change (`grep -rn "func Test.*[Pp]ilot\|func Test.*[Nn]oPilot.*[Nn]oFlight\|func Test.*[Uu]nqualified" internal/engine/airunits/*_test.go`). **False-pass risk:** a chopper that is dispatchable by default and merely *displays* an optional pilot name would pass a "a pilot field exists" grep while "no pilot, no flight" is unmet — the check requires the pilot to gate flight state mechanically. **Boundary note:** the pilot *supply* (how citizens train to be pilots, how many exist) is MOD-073's; this AC only consumes an injected assignment, mirroring `engine.maintenance.md` AC-9's supply-injection pattern (ASM-587).

- **AC-6 (maintenance-heavy — GR#20 maintenance seam).** Each chopper carries a **significant** maintenance burden: flying hours (or cycles) accumulate wear, and un-serviced wear puts the chopper into an out-of-service/downtime state, with the engineer-hour cost surfacing through `engine.maintenance`'s demand surface (MOD-072's MaintenanceView), never a chopper-local maintenance ledger. Check: `grep -rn "maintenance\." internal/engine/airunits/*.go` (excluding `_test.go`) shows the maintenance-demand seam; a passing test flies a chopper for N cycles, asserts its accumulated wear increases monotonically, and that failing to service it (zero maintenance applied) transitions it to out-of-service (`grep -rn "func Test.*[Ww]ear\|func Test.*[Dd]owntime\|func Test.*[Oo]utOfService" internal/engine/airunits/*_test.go`). **False-pass risk:** a chopper that records wear but never has a downtime consequence would pass a "wear field exists" grep while the design's "significant maintenance burden … downtime" promise is unmet — the check requires the out-of-service transition. **Balance-regime note:** the engineer-hours-per-flight-hour rate is a placeholder (AC-17); the monotonic-wear + downtime direction is the invariant, not the rate.

### Functional — effectiveness, roles, approval, traffic-immunity

- **AC-7 (traffic-immune, weather-limited — mirrors `engine.dispatch` AC-7).** Chopper travel is road-independent: a chopper's travel time to an incident is computed by a distinct air path (never the ground blue-light pathfinder), and is unaffected by a congestion state that measurably slows a ground unit on the same origin–destination. A documented adverse-weather state (sourced through the dispatch/weather surface, `engine.world`) **grounds or degrades** air dispatch. Check: `go doc ./internal/engine/airunits` shows a road-independent travel-time computation and a weather-gate check; a passing test asserts (a) chopper travel time is unchanged by a congestion state that slows a ground unit on the same route, and (b) an adverse-weather state grounds/degrades the chopper (`grep -rn "func Test.*[Tt]rafficImmune\|func Test.*[Ww]eatherGate\|func Test.*[Cc]ongestionImmune" internal/engine/airunits/*_test.go`). **False-pass risk:** a "ground unit with a speed multiplier" implementation would satisfy "it's faster" while still being blocked by road congestion under the hood (reusing the ground pathfinder) — the check requires demonstrating congestion-immunity specifically, which a multiplier-only implementation cannot pass (the exact failure mode `engine.dispatch` AC-7 calls out).

- **AC-8 (four role-specific effects — GR#15, data-driven).** The four roles produce **distinct, data-driven** effects: the **ambulance** chopper reduces hospital-landing time / improves medical outcome (via the dispatch outcome path), the **fire** chopper reaches remote/blaze sites without traffic delay (reduces fire spread / block loss), the **police** chopper extends police coverage (deterrence/response radius), and the **VIP/commercial** chopper produces a commercial/approval benefit (not an emergency-response effect). Each role's effect parameters live in `data/helicopters.json` (placeholders). Check: `go doc ./internal/engine/airunits` shows a distinct effect accessor per role; a passing test asserts the four roles resolve to four different effects, and that each effect is sourced from data — mutating a role's effect parameter in the fixture changes only that role's effect (`grep -rn "func Test.*[Rr]oleEffect\|func Test.*[Hh]ospitalLanding\|func Test.*[Rr]emoteFire" internal/engine/airunits/*_test.go`); `grep -nE "[0-9]+\.[0-9]+" internal/engine/airunits/*.go` (excluding `_test.go`) finds no bare effect-parameter literal — values load from `data/helicopters.json`. **False-pass risk:** a single shared "response-time bonus" applied identically to all four roles would pass a "choppers improve response" test while collapsing the design's four distinct effects into one — the check requires the four effects to be distinguishable, and the VIP role to be non-emergency (commercial/approval) specifically (ASM-586). **Boundary note:** the *outcome curves* the ambulance/fire/police effects feed are MOD-040's (dispatch), not airunits' — airunits supplies the role's contribution (e.g. a faster landing time, a coverage radius), dispatch applies it to its existing outcome model.

- **AC-9 (population approval via response-time improvement — POPULAR, data-driven).** The chopper fleet contributes a queryable **approval weight** that rises when a chopper improves response time / extends coverage (the "not stuck in traffic" dividend), and is **reduced or zeroed** when the chopper is weather-grounded or out-of-service. The weight is loaded from `data/helicopters.json` (placeholder) and exposed for the attractiveness model to consume through a registered edge, not hardcoded. Check: `go doc ./internal/engine/airunits` shows an approval-weight accessor; a passing test asserts the approval contribution (a) is positive when a chopper is actively cutting response time, (b) drops to its baseline/zero when the chopper is grounded, and (c) tracks the data file when the fixture weight is mutated (`grep -rn "func Test.*[Aa]pproval\|func Test.*[Nn]otStuckInTraffic\|func Test.*[Gg]roundedApproval" internal/engine/airunits/*_test.go`). **False-pass risk:** a flat "chopper present = +approval" flag would pass a "choppers are popular" test while ignoring the design's mechanism (approval comes from response-time improvement, so a grounded chopper should not earn it) — the check requires the weight to move with the chopper's actual effect. **Boundary note:** which module consumes the weight (`engine.attract`'s satisfaction/attractiveness term) is an unregistered reverse seam — see Cross-check/ES-1.

### Functional — conservation

- **AC-10 (fleet conservation — every chopper accounted for).** For every chopper the identity `TotalChoppers == Available + EnRoute + OnScene + OutOfService` holds exactly at every tick, with each right-hand term independently sourced (available from the fleet free-list, en-route/on-scene from active dispatch assignments, out-of-service from the maintenance/pilot/weather grounding scheduler) — no term computed as the identity's remainder. Check: a passing test constructs a fleet, drives it through a mix of flights, dispatch assignments, pilot removals, and maintenance/weather groundings across several ticks, independently sums all four terms each tick, and asserts the sum equals the fixed `TotalChoppers` at every tick (`grep -rn "func Test.*[Ff]leetConserv\|func Test.*[Cc]hopperConservation" internal/engine/airunits/*_test.go`). **False-pass risk:** deriving `Available` as `TotalChoppers − (en-route + on-scene + out-of-service)` would make the identity tautologically true and hide a chopper double-assigned or never returned to the pool — the check requires each term sourced independently (the exact `engine.dispatch` AC-11 discipline, with the same "resolve and assert the unit ID reappears in the free-list" assertion).

### Determinism & safety

- **AC-13 (GR#21).** Chopper state (flight, wear, out-of-service, dispatch assignment, approval contribution) advances by simulation tick only — `grep -rn "time.Now\|time.Since" internal/engine/airunits/*.go` (excluding `_test.go`) returns no matches — and tick resolution is a deterministic function of `(worldSeed, tick, prior state, commands)` producing byte-identical state across worker counts, with a documented deterministic tie-break for any map-iterated collection. Check: a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/airunits/*_test.go`); any `for ... := range` over a map feeding assignment is followed by sorted-key iteration (`grep -n "sort\." internal/engine/airunits/*.go`). Never assert a wall-clock upper bound in CI; assert tick-count/state equality only.

- **AC-14 (GR#16; type-safe storage + saturating arithmetic).** All air-unit numeric state (purchase/running cost, fuel, wear-hours, engineer-hours) routes through the project's saturating helpers (`foundation/num`, FEAT-086) in integer units — no float money, no int overflow — and stored air-unit state is re-validated on load (coerced through typed constructors), never trusted raw from storage. Check: `grep -rn "foundation/num\|satAdd\|safeMul\|mulDiv" internal/engine/airunits/*.go` shows the saturating helpers on the money/quantity paths; `grep -rn "float64\|float32" internal/engine/airunits/*.go` (excluding `_test.go`) finds no float on a money/quantity path; a passing overflow/round-trip test drives a near-limit quantity through the state and asserts it saturates rather than wraps (`grep -rn "func Test.*[Ss]aturat\|func Test.*[Oo]verflow\|func Test.*[Rr]oundTrip" internal/engine/airunits/*_test.go`).

- **AC-15 (GR#15; data-derived counts + race).** Expected values in tests (fleet size, component totals, approval deltas) are computed from the loaded `data/helicopters.json` fixture or a runtime query, never a hardcoded expected constant; and `go test ./internal/engine/airunits/... -race -count=1` passes with `grep -n "go func()" internal/engine/airunits/*_test.go` finding at least one concurrency test (concurrent dispatch/grounding across the fleet within a tick). Check: a passing test recomputes its expected value from the fixture rather than asserting a literal (`grep -rn "func Test.*[Dd]ataDerived\|func Test.*[Rr]eadBack" internal/engine/airunits/*_test.go`).
