## User stories

- **US-1.** As the player, I need daily traffic assignment to be a capacity-restrained stochastic user equilibrium — flows re-splitting across alternative routes as link times update via volume-delay functions — so that herds never pile onto a single "cheapest" route the way individually-optimal pathing in 'Blue' does (§19 intro point 1).
- **US-2.** As `engine.roads`, I need lanes to be modelled purely as link capacity with turn-movement capacities at junctions, never as routed/choosable path segments, so the "mile-long single-lane queue beside an empty lane" pathology is structurally impossible (§19 intro point 2).
- **US-3.** As the invariant checker (`engine.invariant`), I need vehicle conservation to hold on every tick — nothing despawns or teleports — so gridlock is real, visible, and the player's problem to fix, never masked (§19 intro point 3; §II.5 "nothing despawns").
- **US-4.** As every junction on the road graph, I need a control type (priority / mini-roundabout / roundabout with an entry-capacity formula / signals with cycle time + green splits) plus queue spillback that blocks the upstream junction once a link's queue exceeds its storage, so one failed roundabout can genuinely lock a district and the map view can show it (§19.2).
- **US-5.** As every citizen making a trip, I need my mode choice computed by a per-trip nested logit over generalised cost (time + money + comfort + reliability), personality-weighted (physicality→cycle/walk, patience→transit tolerance, wealth→taxi/car) and using real hill slopes for cycling, so mode share is a genuine behavioural output, not a fixed split (§19.1).
- **US-6.** As `engine.wellbeing` and F6 Demographics, I need a computed door-to-door commute time (access walk + wait + in-vehicle + transfers) written to `engine.citizens`' per-citizen record for every worker/pupil (hot) and rolled up distributionally per district (cold), so mental-health drivers and citywide distributions have a real number to read (§19.3).
- **US-7.** As `engine.logistics`, I need freight trucks to share the same network as commuters, counted as PCUs with junction slot demand, so commuters and JIT genuinely compete for road space (§19.3; §II.5).
- **US-8.** As the traffic advisor / `engine.news`, I need induced demand to emerge naturally from the equilibrium assignment plus a latent-demand pool when capacity is added — never a scripted "trips increase by X%" — so the lane-widening pedagogy (§51) is mechanically true, not narrated fiction.
- **US-9.** As `int.solver`'s CPU v1 backend (A4), I need traffic assignment expressed as a zone-aggregated OD problem (~10³-10⁴ zones, never citizen-pair routing) submitted through the solver contract, so the same assignment logic is backend-interchangeable (CPU today, GPU/cloud later) without `engine.traffic` code changing.
- **US-10.** As GR#21 / the determinism gate, I need SUE assignment to converge via a fixed, deterministic iteration/convergence test — never wall-clock, goroutine-scheduling order, or map-iteration order — so the same seed and command log produce a bit-identical result **at every worker count**, not merely at the two the reference test happens to try.

## Architecture ruling in force (Bill, MOD-023 comment, 2026-08-09)

**`engine.roads` does not call `engine.traffic`.** Roads owns road identity, geometry, class ladder and naming; traffic owns flow, v/c and journey time. Anywhere the spec reads as if the road inspector or the pre-approval projection "call into traffic" (§20, §51), that composition happens at the **consuming layer** (UI/advisor/projection — not yet built this sprint), never as a lateral `roads → traffic` package call. `engine.traffic`'s own registered dependency is `traffic → roads` (traffic reads road identity/capacity from roads), which is the only lateral call this pair is allowed. See `engine.roads.md` for the roads-side ACs this affects; **ASM-217** records that neither package's test suite alone can prove the full "inspector shows real numbers"/"preview shows a real journey-time delta" behavioural claim end-to-end — each proves its own half.

**Route cache lives in `engine.traffic`.** Resolved (was an open escalation in the superseded draft); see AC-22.

## Scope

The `TrafficAPI`: daily capacity-restrained SUE assignment (zone-aggregated OD, submitted via `int.solver`), junction control-type modelling with queue spillback, per-trip nested-logit mode choice over the §19.1 mode table, door-to-door commute-time accounting (hot per-citizen write via `engine.citizens` / cold per-district), freight-as-PCU network sharing, the induced-demand/latent-demand pool mechanism, and the warm-start route cache. Does not include road-graph identity, naming, or class/upgrade mechanics (`engine.roads`, this sprint's sibling item) — this item consumes the road graph `engine.roads` exposes and never calls back into it for anything beyond that read.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `TrafficAPI` Go interface exists exposing at minimum an assignment trigger (daily SUE run) and query surfaces for link volumes, v/c ratios, and per-citizen/per-district commute times, consumed only through the interface (never a concrete assignment-engine type imported directly by other modules). Check: `go doc ./internal/engine/traffic TrafficAPI` shows these surfaces; `grep -rn "traffic\.\(SUE\|Assignment\)Engine\b" internal/engine/*/` (excluding the `traffic` package itself) finds no direct concrete-type imports. **False-pass note:** this grep only catches two hardcoded type-name guesses — Tester/QA must also confirm by reading `go doc` output that no *other* concrete traffic type (whatever it's actually named) is imported elsewhere, not just rely on the grep matching nothing.
- **AC-2 (§19 intro point 1; A4).** Daily assignment is submitted to `int.solver` as a zone-aggregated OD problem (a `ProblemKind` for traffic equilibrium, ~10³-10⁴ zones per A4 — never a per-citizen-pair route request), using volume-delay functions to update link travel times and re-splitting flows across alternatives until AC-3's convergence test passes. Check: `grep -n "solver\.Get\|Registry\.Solve" internal/engine/traffic/*.go` shows contract-mediated calls (per AC-14); `grep -n "ZoneCount\|ODZone" internal/engine/traffic/*.go` shows zone-aggregated sizing consistent with `int.solver`'s `ODZoneCountMin`/`ODZoneCountMax`; a passing test asserts the number of OD entries submitted for a synthetic city with N citizens is O(zones²), not O(N) — i.e. it does not grow when citizen count grows at fixed zone count (`grep -rn "func Test.*[Zz]one[Aa]ggregat" internal/engine/traffic/*_test.go`). **False-pass note:** a `ZoneCount` field existing proves nothing about whether the solver payload actually uses it — the O(zones²)-not-O(N) test is the part that actually catches a disguised per-citizen loop.
- **AC-3 (§19 intro point 1; determinism; convergence — resolved per lead ruling 3).** Convergence is a **fixed, deterministic test**: a maximum-iteration cap AND a numeric tolerance (max link-flow-delta or max link-travel-time-delta between consecutive iterations, whichever the junior documents) are both **balance-data-sourced** (GR#15) from a data file — assumed `data/traffic_balance.json` per **ASM-212**, confirm/adjust at dispatch — with named Go constants in the traffic package used **only** as the fallback default when the data file is absent, never as the live values. The loop terminates the moment the tolerance is met OR the iteration cap is reached, whichever comes first — never "iterate until stable" gated by wall-clock or goroutine order. **If the cap is reached without the tolerance being met, the assignment result is NOT returned as if converged** — see AC-16b. Check: `go doc ./internal/engine/traffic` (or `sue.go`) documents the exact rule and names the data file + fallback constants; `grep -n "traffic_balance\|BalanceData" internal/engine/traffic/*.go` shows the data-file load path; `grep -n "time.Now\|time.Since\|time.After" internal/engine/traffic/*.go` (excluding `_test.go`) finds no matches gating the loop; a passing test asserts that deleting/nulling the balance-data entry falls back to the named Go constant rather than a zero value or a panic (`grep -rn "func Test.*[Bb]alance.*[Ff]allback\|func Test.*[Cc]onverg" internal/engine/traffic/*_test.go`). **False-pass note:** a grep finding `traffic_balance` proves the loader exists, not that the live path actually reads the number it uses to terminate the loop — the fallback test is what closes that gap.
- **AC-3b (§19 intro point 1; warm start defined).** A "warm start" is defined and implemented as: the previous simulated day's converged link-flow (or link-travel-time) state used as the initial iterate for the next day's SUE run, as distinct from a "cold start" (uniform free-flow travel times / zero flow as the initial iterate). Convergence is proven, per AC-17, on a **warm-started synthetic-city-scale fixture** — not a 3-node toy graph — since "converges in a few iterations" is only a meaningful claim at realistic network scale/connectivity. Check: `go doc ./internal/engine/traffic` names both start modes and states which one the daily-tick path uses; a passing test asserts a warm-started run reaches AC-3's tolerance in fewer iterations than a cold-started run against the identical OD matrix on a synthetic-city-scale fixture (`grep -rn "func Test.*[Ww]arm[Ss]tart" internal/engine/traffic/*_test.go`).
- **AC-4 (§19 intro point 2).** Lanes are represented exclusively as link capacity (a numeric field on the road-graph edge, sourced from `engine.roads`'s `RoadsAPI`), never as a routed/selectable path element — no data structure in this package allows a route to "choose a lane" independently of choosing the link. Check: `go doc ./internal/engine/traffic` shows link capacity as a scalar read from `RoadsAPI`; `grep -n "LaneChoice\|ChooseLane" internal/engine/traffic/*.go` finds no matches.
- **AC-5 (§19 intro point 3; §II.5; conservation).** Vehicle conservation holds — no trip is ever despawned, teleported, or silently dropped when a link/junction is saturated; a saturated network manifests as growing queue length and rising travel time, never as vehicles disappearing. Check: a passing test asserts total in-flight trip count (link flow + link queues + junction-held vehicles) is conserved across a tick even when a synthetic bottleneck saturates a link, comparing the sum before and after rather than merely asserting a nonzero queue (`grep -rn "func Test.*[Cc]onserv" internal/engine/traffic/*_test.go`). **False-pass note:** a test that only asserts "queue length > 0" would pass an implementation that drops excess vehicles to relieve pressure — this check must sum total vehicles across links+queues+junctions before and after and assert equality, which a drop-based implementation fails.
- **AC-6 (§19.2).** Every junction node carries one of the four documented control types — priority, mini-roundabout, roundabout (with an entry-capacity formula), or signals (cycle time + green splits, either auto-optimised or hand-set) — each affecting turn-movement capacity distinctly. Check: `go doc ./internal/engine/traffic JunctionControl` (or equivalent) lists all four kinds; a passing test asserts a roundabout junction's entry-capacity formula produces a different admitted flow than a priority junction under identical demand (`grep -rn "func Test.*[Jj]unction" internal/engine/traffic/*_test.go`).
- **AC-7 (§19.2; queue spillback — fixture shape per ASM-218).** Each link stores a queue; when queue length exceeds the link's storage capacity, the upstream junction is blocked (spillback). Fixture shape: a chain of **at least 3 links / 2 junctions**, with the downstream-most link's queue-storage capacity deliberately set below sustained demand. Check: a passing fixture test on this topology asserts BOTH (a) the upstream junction's admitted flow measurably drops once the downstream link's queue exceeds storage, AND (b) total vehicle count across the fixture (AC-5's conservation sum) is unchanged before/after — condition (b) is what stops a drop-based "relieve the queue by discarding vehicles" implementation from passing on (a) alone (`grep -rn "func Test.*[Ss]pillback" internal/engine/traffic/*_test.go`). **False-pass note:** (a) alone is satisfiable by dropping vehicles instead of blocking them — a queue that "clears" because vehicles vanished also shows reduced upstream flow. The conservation check is load-bearing here, not decorative.
- **AC-8 (§19.2).** Level crossings, bus priority, and pedestrian phases are represented as junction-control modifiers (each demonstrably alters turn-movement capacity or cycle timing versus the same junction without the modifier). Check: `go doc ./internal/engine/traffic` documents at least these three modifiers; a passing test asserts at least one modifier changes admitted flow or cycle allocation versus baseline (`grep -rn "func Test.*[Bb]usPriority\|func Test.*[Ll]evelCrossing\|func Test.*[Pp]edestrian" internal/engine/traffic/*_test.go`).
- **AC-9 (§19.1; mode table).** All 11 modes from the §19.1 table are represented (walk, bicycle, motorbike, car, taxi, minibus, bus, tram, metro, heavy rail, ferry, air), each carrying its documented speed/capacity/PCU-load fields, sourced from `data/modes.json` (GR#15 — not Go literals for the balance numbers, though the enum of 11 kinds itself may be a Go type). Bicycle's cost function reads real terrain slope from `engine.world`. Check: `go doc ./internal/engine/traffic Mode` (or `ModeKind`) lists all 11; `grep -n "modes.json\|ModeData" internal/engine/traffic/*.go` shows per-mode speed/capacity/PCU loaded from data, not hardcoded; a passing test asserts a bicycle trip's generalised cost differs between a flat-fixture route and a steep-fixture route using the same `engine.world` slope query (`grep -rn "func Test.*[Bb]icycle.*[Ss]lope\|func Test.*[Hh]ill" internal/engine/traffic/*_test.go`).
- **AC-10 (§19.1; nested logit — coefficient sourcing resolved per lead ruling 3, pending ASM-215).** Per-trip mode choice is computed via a nested logit over generalised cost (time + money + comfort + reliability), personality-weighted per citizen (physicality → cycle/walk propensity, patience → transit tolerance, wealth → taxi/car propensity), reading personality traits from `engine.citizens` and reading the logit utility **coefficients themselves** from `data/modes.json` — no personality-weighting coefficient may be a Go literal. Check: `go doc ./internal/engine/traffic` shows the logit function's signature taking a citizen personality vector; `grep -n "modes.json" internal/engine/traffic/*.go` shows coefficient loading, and `grep -rn "0\.[0-9]+ \* .*\(wealth\|patience\|physicality\)" internal/engine/traffic/*.go` (a heuristic scan for an inline literal multiplying a trait) finds no matches; a passing test asserts two citizens differing only in one personality trait (e.g. wealth) receive different mode-choice probabilities for the identical trip (`grep -rn "func Test.*[Nn]estedLogit\|func Test.*[Pp]ersonality" internal/engine/traffic/*_test.go`). **Blocking pre-dispatch dependency:** `data/modes.json` currently has no authored coefficient schema (ASM-215, P0) — this AC cannot be satisfied as written until that schema is frozen; do not dispatch until resolved.
- **AC-11 (§19.3; commute accounting — interface obligation, see Escalations).** Every worker/pupil citizen gets a computed door-to-door time (access walk + wait + in-vehicle + transfers), written to the citizen's hot record via a `CitizensAPI` command call (never a direct field-set on a citizen struct — GR#20), and an aggregate distributional view is exposed per district for the cold/F6 path. Check: `go doc ./internal/engine/traffic` shows both the `CitizensAPI` write call site (`grep -n "citizens\.\|CitizensAPI" internal/engine/traffic/*.go`) and a per-district distribution query; `grep -n "\.wealth = \|\.commute.* = " internal/engine/traffic/*.go` touching an imported citizens type (excluding `_test.go`) finds no direct field writes; a passing test asserts a citizen's stored commute time equals the sum of its four documented components (`grep -rn "func Test.*[Cc]ommute" internal/engine/traffic/*_test.go`). **Cross-module note:** `engine.citizens`' own acceptance file (`engine.citizens.md`, not owned by this BA) does not currently list a commute-time write command among its `CitizensAPI` surface (its AC-1 lists "commute" only as a satisfaction *component*, not a raw time field/write path) — this is a genuine contract gap between the two modules, flagged in Escalations, not resolved here.
- **AC-12 (§19.3; freight sharing).** Freight trucks (from `engine.logistics`, consumed via the network) are represented as PCUs with junction slot demand identical in kind to passenger-vehicle PCU load — they compete for the same link/junction capacity, not a separate freight-only lane pool. Check: `go doc ./internal/engine/traffic` documents freight-PCU conversion; a passing test asserts adding freight PCU volume to a link measurably raises that link's v/c ratio the same way adding car PCU volume does (`grep -rn "func Test.*[Ff]reight.*PCU" internal/engine/traffic/*_test.go`).
- **AC-13 (§51; induced demand).** Adding link capacity (a fixture road upgrade) causes the equilibrium re-assignment, drawing on a documented latent-demand pool, to increase realised trip volume and shift mode share back toward car on the widened link — with no scripted percentage or hardcoded "refill" event; the effect must emerge purely from re-running the same SUE/logit machinery with the new capacity. Check: `go doc ./internal/engine/traffic LatentDemandPool` (or equivalent) exists; a passing test asserts re-assignment after a capacity increase raises realised volume on the widened link versus before, driven by the same equilibrium call used for every other assignment (`grep -rn "func Test.*[Ii]nducedDemand\|func Test.*[Ll]atentDemand" internal/engine/traffic/*_test.go`); `grep -n "scriptedRefill\|hardcodedIncrease" internal/engine/traffic/*.go` finds no matches. **False-pass note:** the absence-of-literal grep alone is weak (a scripted bump can be named anything) — the comparative before/after test using the *same* equilibrium entry point is what actually distinguishes "emergent" from "scripted", since a scripted implementation would need a second, different code path to apply its bump.
- **AC-14 (A4; solver contract).** The assignment problem payload/response round-trips through `int.solver`'s `Solve` call using a registered `ProblemKind` for traffic equilibrium, with the CPU backend as the only implementation in v1 (per `int.solver`'s AC-5 mandatory fallback) — `engine.traffic` never calls a concrete solver backend type directly. Check: `grep -n "solver\.Get\|Registry\.Solve" internal/engine/traffic/*.go` shows contract-mediated calls; `grep -n "cpu\.CPUBackend" internal/engine/traffic/*.go` finds no direct backend import from this package.

### Error handling

- **AC-15 (GR#7).** A junction whose control type cannot resolve turn-movement capacities (e.g. malformed signal-split data) produces a registry-sourced error (new `MET-E`-range code) naming the junction, rather than defaulting to an arbitrary capacity or panicking. Check: `grep -n "MET-" internal/engine/traffic/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Mm]alformed.*[Jj]unction\|func Test.*[Ii]nvalidSignal" internal/engine/traffic/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no arbitrary default capacity was silently assigned to the junction, not merely that a matching-named test function exists.
- **AC-16 (`Solve` error handling).** A `Solve` call to `int.solver` returning a non-nil error (unsupported problem kind, no backend available) is surfaced as a typed rejection to the caller of the daily assignment trigger — never silently falling back to a stale/previous-tick assignment without a logged, registry-sourced event recording that it happened. Check: passing test coverage asserts the error propagates, and if a stale-assignment fallback exists at all, asserts it emits a `MET-` event recording the fallback (`grep -rn "func Test.*[Ss]olverError\|func Test.*[Ss]olverFail" internal/engine/traffic/*_test.go`).
- **AC-16b (GR#7/#15; non-convergence — new, closes the "silent plausible-looking garbage" gap).** If AC-3's iteration cap is reached without the tolerance being met, the daily assignment trigger returns a **typed non-convergence result** (distinct from a normal converged result — e.g. a `Converged bool` field or a distinct error/status type, not merely a log line) rather than silently handing back the last iterate as if it were a good answer. Callers that ignore the flag get the same numbers a converged run would produce in shape, which is exactly the danger this AC exists to prevent — the check must confirm the signal is structurally impossible to miss, not merely present. Check: `go doc ./internal/engine/traffic` shows the non-convergence signal on the assignment-trigger return type; a passing test forces non-convergence (artificially tiny iteration cap against a fixture that needs more) and asserts the returned result is marked non-converged, distinguishable by type/field from a converged result (`grep -rn "func Test.*[Nn]on[Cc]onverg\|func Test.*[Ff]ailedToConverge" internal/engine/traffic/*_test.go`). **False-pass note:** a test that only checks a log line was emitted is not sufficient — logs are easy to miss downstream; the non-convergence signal must be on the return value itself.

### Determinism & safety

- **AC-17 (GR#21; core requirement — strengthened, was the weakest check in the superseded draft).** Same seed + identical command log produces byte-identical `TrafficAPI` outputs (link volumes, v/c ratios, commute times) **at three or more distinct worker counts** (e.g. `POOL-SIM=1`, `4`, `14` — not merely the two endpoints), each run **repeated at least twice per worker count**, on a **synthetic-city-scale fixture** (per AC-3b, large enough that per-link contributor counts run into the hundreds — a toy fixture is too small for floating-point non-associativity to bite even in a broken implementation, which would make the test pass for the wrong reason). Check: `grep -rn "func Test.*[Ss]hardInvariance\|func Test.*POOL_SIM\|func Test.*[Dd]eterminis" internal/engine/traffic/*_test.go` finds it; the test asserts a single hash equal across every (worker-count, repeat) combination, not pairwise across only the endpoints; `go test ./internal/engine/traffic/... -run TestTrafficDeterminism -race -count=1 -v` (or the actual name) passes. **False-pass note (why the old two-run check was weak):** a test that runs POOL-SIM=1 once and POOL-SIM=14 once and compares can pass by coincidence — either because the fixture is too small for the summation-order difference to surface in the observed bits, or because the specific shard boundaries chosen for 1 vs 14 happen not to split any high-contention link differently that run. Three-plus worker counts with repeats and a realistic-scale fixture make a coincidental pass exponentially less likely and directly targets the failure mode ASM-216 describes (per-shard partial-sum-then-merge, which is reproducible at fixed worker count but not across counts).
- **AC-18 (GR#21; no map-range on result-affecting collections).** No `for range` loop over a Go map feeds a value into the assignment result, mode-choice probability, or commute-time output without a prior deterministic sort/ordering step. Check: `grep -rn "for .* := range" internal/engine/traffic/*.go` — every match iterating a map type is either read-only diagnostics or preceded by a `sort.` call on the iteration keys (`grep -n "sort\." internal/engine/traffic/*.go` shows the ordering step exists for each map-range site that affects output).
- **AC-19 (GR#21; deterministic tie-breaking).** Every point where the assignment or mode-choice logic must break a tie (equal-cost routes, equal-probability mode draws, equal-priority junction turn-movements) uses a documented deterministic rule (e.g. lowest edge ID, lexicographic ordering, or the counter-RNG from `foundation.det` seeded per the fixed seed) — never Go's undefined map/slice iteration order or a raw unseeded `math/rand` call. Check: `grep -n "math/rand\"" internal/engine/traffic/*.go` (excluding `_test.go`) finds no matches (only `foundation.det`'s counter-RNG is used); `go doc ./internal/engine/traffic` documents the tie-break rule explicitly at each decision point named above.
- **AC-20 (GR#21; parallel reduction order — rewritten per ASM-216, this is the AC that actually enforces cross-worker-count determinism, not AC-17 which only tests the outcome).** Any parallel reduction across shards/goroutines that feeds an assignment result (summing PCU load onto a shared link, aggregating district commute distributions) uses a **gather-then-canonical-order** discipline: each shard writes its contributions keyed by a stable, worker-count-independent entity/edge ID into a shared results structure during the parallel phase, with **no cross-shard summation happening inside the parallel phase**; a single-threaded pass afterwards sums each key's contributor list in a fixed order (e.g. ascending contributor ID). A per-shard-partial-sum-then-merge-shards-in-index-order pattern does **not** satisfy this AC even though it is deterministic at a fixed worker count, because the shard partition itself changes with worker count and reshapes the floating-point summation tree. Check: `go doc ./internal/engine/traffic` documents the gather-then-canonical-order rule explicitly and names it as such (not merely "deterministic merge order"); `grep -n "for shardIdx" internal/engine/traffic/*.go` combined with a summation on that loop variable's partial result (rather than on a canonically-sorted contributor list) is the anti-pattern to search for — Tester must read the reduction code, not just grep, since the anti-pattern is a shape, not a string; a passing test runs the reduction at 2+ distinct worker counts on a fixture with a high-contention link (many contributors) and asserts identical output — this is AC-17's test at the unit level, isolated to the reduction function alone so a failure here points directly at the reduction rather than the whole pipeline (`grep -rn "func Test.*[Rr]eductionOrder\|func Test.*[Mm]ergeOrder" internal/engine/traffic/*_test.go`).
- **AC-21 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/traffic/*.go` (excluding `_test.go`) returns no matches anywhere in the assignment/logit/spillback logic — the daily-assignment "day" is a simulation-tick concept, never wall clock.
- **AC-22 (M0-ENG §1.3; route cache — resolved, lives here per lead ruling).** The warm-start route cache (§19 intro point 1, "cached warm starts") lives in `engine.traffic`, not `engine.roads`. It is contents-independent for determinism: a cache-cold run and a cache-warm run of the identical assignment produce identical link volumes/v/c ratios, differing only in solve latency. Check: `grep -rn "func Test.*[Cc]ache.*[Dd]eterminis\|func Test.*[Ww]armStart.*[Dd]eterminis" internal/engine/traffic/*_test.go` finds coverage; `internal/engine/traffic/doc.go` states the placement explicitly (`grep -n "route cache" internal/engine/traffic/doc.go`).
- **AC-23.** `go test ./internal/engine/traffic/... -race -count=1` passes with no data race under the 256-fixed-shard worker pool pattern. Check: `grep -n "go func()" internal/engine/traffic/*_test.go` finds at least one concurrency test.

- Fuel/EV charging systems (`engine.fuel`, a later consumer) — freight/car PCU accounting here does not model fuel consumption or range.
- External rail / off-map commuting mechanics (`engine.rail`, `engine.extcommute`, later consumers) — this item exposes the network those modules query; it does not implement off-map job pools or season-ticket pricing.
