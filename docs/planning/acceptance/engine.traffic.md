## User stories

- **US-1.** As the player, I need daily traffic assignment to be a capacity-restrained stochastic user equilibrium — flows re-splitting across alternative routes as link times update via volume-delay functions — so that herds never pile onto a single "cheapest" route the way individually-optimal pathing in 'Blue' does (§19 intro point 1).
- **US-2.** As `engine.roads`, I need lanes to be modelled purely as link capacity with turn-movement capacities at junctions, never as routed/choosable path segments, so the "mile-long single-lane queue beside an empty lane" pathology is structurally impossible (§19 intro point 2).
- **US-3.** As the invariant checker (`engine.invariant`), I need vehicle conservation to hold on every tick — nothing despawns or teleports — so gridlock is real, visible, and the player's problem to fix, never masked (§19 intro point 3; §II.5 "nothing despawns").
- **US-4.** As every junction on the road graph, I need a control type (priority / mini-roundabout / roundabout with an entry-capacity formula / signals with cycle time + green splits) plus queue spillback that blocks the upstream junction once a link's queue exceeds its storage, so one failed roundabout can genuinely lock a district and the map view can show it (§19.2).
- **US-5.** As every citizen making a trip, I need my mode choice computed by a per-trip nested logit over generalised cost (time + money + comfort + reliability), personality-weighted (physicality→cycle/walk, patience→transit tolerance, wealth→taxi/car) and using real hill slopes for cycling, so mode share is a genuine behavioural output, not a fixed split (§19.1).
- **US-6.** As `engine.wellbeing` and F6 Demographics, I need a computed door-to-door commute time (access walk + wait + in-vehicle + transfers) stored per citizen (hot) and distributional per district (cold) for every worker/pupil, so mental-health drivers and citywide distributions have a real number to read (§19.3).
- **US-7.** As `engine.logistics`, I need freight trucks to share the same network as commuters, counted as PCUs with junction slot demand, so commuters and JIT genuinely compete for road space (§19.3; §II.5).
- **US-8.** As the traffic advisor / `engine.news`, I need induced demand to emerge naturally from the equilibrium assignment plus a latent-demand pool when capacity is added — never a scripted "trips increase by X%" — so the lane-widening pedagogy (§51) is mechanically true, not narrated fiction.
- **US-9.** As `int.solver`'s CPU v1 backend (A4), I need traffic assignment expressed as a zone-aggregated OD problem (~10³-10⁴ zones, never citizen-pair routing) submitted through the solver contract, so the same assignment logic is backend-interchangeable (CPU today, GPU/cloud later) without `engine.traffic` code changing.
- **US-10.** As GR#21 / the determinism gate, I need SUE assignment to converge via a fixed, deterministic iteration/convergence test — never wall-clock, goroutine-scheduling order, or map-iteration order — so the same seed and command log produce a bit-identical result at POOL-SIM=1 and POOL-SIM=14, every time.

## Scope

The `TrafficAPI`: daily capacity-restrained SUE assignment (zone-aggregated OD, submitted via `int.solver`), junction control-type modelling with queue spillback, per-trip nested-logit mode choice over the §19.1 mode table, door-to-door commute-time accounting (hot per-citizen / cold per-district), freight-as-PCU network sharing, and the induced-demand/latent-demand pool mechanism. Does not include road-graph identity, naming, or class/upgrade mechanics (`engine.roads`, this sprint's sibling item) — this item consumes the road graph `engine.roads` exposes.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `TrafficAPI` Go interface exists exposing at minimum an assignment trigger (daily SUE run) and query surfaces for link volumes, v/c ratios, and per-citizen/per-district commute times, consumed only through the interface (never a concrete assignment-engine type imported directly by other modules). Check: `go doc ./internal/engine/traffic TrafficAPI` shows these surfaces; `grep -rn "traffic\.\(SUE\|Assignment\)Engine\b" internal/engine/*/` (excluding the `traffic` package itself) finds no direct concrete-type imports.
- **AC-2 (§19 intro point 1; A4).** Daily assignment is submitted to `int.solver` as a zone-aggregated OD problem (`ProblemKind` for traffic equilibrium, ~10³-10⁴ zones per A4 — never a per-citizen-pair route request), using volume-delay functions to update link travel times and re-splitting flows across alternatives until a defined convergence test passes. Check: `go doc ./internal/engine/traffic` shows a `Solver`-contract call site (`grep -n "solver\.Solve\|SolverContract" internal/engine/traffic/*.go`); `grep -n "ZoneCount\|ODZone" internal/engine/traffic/*.go` shows zone-aggregated sizing consistent with `int.solver`'s A4 tables, not a per-citizen loop.
- **AC-3 (§19 intro point 1; determinism).** Convergence is a **fixed, deterministic test** — either a fixed iteration count or a deterministic numeric-tolerance check evaluated in a fixed, documented order — never "iterate until stable" gated by wall-clock elapsed time or goroutine-completion order. Check: `go doc ./internal/engine/traffic` (or `sue.go`) documents the exact convergence rule (e.g. "N iterations" or "max link-flow delta < ε, ε and max-iterations both named constants"); `grep -n "time.Now\|time.Since\|time.After" internal/engine/traffic/*.go` (excluding `_test.go`) finds no matches gating the convergence loop.
- **AC-4 (§19 intro point 2).** Lanes are represented exclusively as link capacity (a numeric field on the road-graph edge, sourced from `engine.roads`), never as a routed/selectable path element — no data structure in this package allows a route to "choose a lane" independently of choosing the link. Check: `go doc ./internal/engine/traffic` shows link capacity as a scalar on the edge type consumed from `engine.roads`; `grep -n "LaneChoice\|ChooseLane" internal/engine/traffic/*.go` finds no matches.
- **AC-5 (§19 intro point 3; §II.5).** Vehicle conservation holds — no trip is ever despawned, teleported, or silently dropped when a link/junction is saturated; a saturated network manifests as growing queue length and rising travel time, never as vehicles disappearing. Check: a passing test asserts total in-flight trip count is conserved across a tick even when a synthetic bottleneck saturates a link (`grep -rn "func Test.*[Cc]onserv" internal/engine/traffic/*_test.go`).
- **AC-6 (§19.2).** Every junction node carries one of the four documented control types — priority, mini-roundabout, roundabout (with an entry-capacity formula), or signals (cycle time + green splits, either auto-optimised or hand-set) — each affecting turn-movement capacity distinctly. Check: `go doc ./internal/engine/traffic JunctionControl` (or equivalent) lists all four kinds; a passing test asserts a roundabout junction's entry-capacity formula produces a different admitted flow than a priority junction under identical demand (`grep -rn "func Test.*[Jj]unction" internal/engine/traffic/*_test.go`).
- **AC-7 (§19.2; queue spillback).** Each link stores a queue; when queue length exceeds the link's storage capacity, the upstream junction is blocked (spillback) — demonstrable via a fixture where one saturated downstream link measurably reduces throughput at an upstream junction one or more hops away. Check: `go doc ./internal/engine/traffic` shows a queue-length field per link and a spillback propagation function; a passing fixture test asserts upstream-junction admitted flow drops when a downstream link's queue exceeds storage (`grep -rn "func Test.*[Ss]pillback" internal/engine/traffic/*_test.go`).
- **AC-8 (§19.2).** Level crossings, bus priority, and pedestrian phases are represented as junction-control modifiers (each demonstrably alters turn-movement capacity or cycle timing versus the same junction without the modifier). Check: `go doc ./internal/engine/traffic` documents at least these three modifiers; a passing test asserts at least one modifier changes admitted flow or cycle allocation versus baseline (`grep -rn "func Test.*[Bb]usPriority\|func Test.*[Ll]evelCrossing\|func Test.*[Pp]edestrian" internal/engine/traffic/*_test.go`).
- **AC-9 (§19.1; mode table).** All 11 modes from the §19.1 table are represented (walk, bicycle, motorbike, car, taxi, minibus, bus, tram, metro, heavy rail, ferry, air), each carrying its documented speed/capacity/PCU-load fields; bicycle's cost function reads real terrain slope from `engine.world` (real hills matter). Check: `go doc ./internal/engine/traffic Mode` (or `ModeKind`) lists all 11; a passing test asserts a bicycle trip's generalised cost differs between a flat-fixture route and a steep-fixture route using the same `engine.world` slope query (`grep -rn "func Test.*[Bb]icycle.*[Ss]lope\|func Test.*[Hh]ill" internal/engine/traffic/*_test.go`).
- **AC-10 (§19.1; nested logit).** Per-trip mode choice is computed via a nested logit over generalised cost (time + money + comfort + reliability), personality-weighted per citizen (physicality → cycle/walk propensity, patience → transit tolerance, wealth → taxi/car propensity), reading personality traits from `engine.citizens`. Check: `go doc ./internal/engine/traffic` shows the logit function's signature taking a citizen personality vector; a passing test asserts two citizens differing only in one personality trait (e.g. wealth) receive different mode-choice probabilities for the identical trip (`grep -rn "func Test.*[Nn]estedLogit\|func Test.*[Pp]ersonality" internal/engine/traffic/*_test.go`).
- **AC-11 (§19.3; commute accounting).** Every worker/pupil citizen gets a computed door-to-door time (access walk + wait + in-vehicle + transfers) stored on the hot per-citizen record (via `engine.citizens`), and an aggregate distributional view is exposed per district for the cold/F6 path. Check: `go doc ./internal/engine/traffic` shows both a per-citizen commute-time write path and a per-district distribution query; a passing test asserts a citizen's stored commute time equals the sum of its four documented components (`grep -rn "func Test.*[Cc]ommute" internal/engine/traffic/*_test.go`).
- **AC-12 (§19.3; freight sharing).** Freight trucks (from `engine.logistics`, consumed via the network) are represented as PCUs with junction slot demand identical in kind to passenger-vehicle PCU load — they compete for the same link/junction capacity, not a separate freight-only lane pool. Check: `go doc ./internal/engine/traffic` documents freight-PCU conversion; a passing test asserts adding freight PCU volume to a link measurably raises that link's v/c ratio the same way adding car PCU volume does (`grep -rn "func Test.*[Ff]reight.*PCU" internal/engine/traffic/*_test.go`).
- **AC-13 (§51; induced demand).** Adding link capacity (a fixture road upgrade) causes the equilibrium re-assignment, drawing on a documented latent-demand pool, to increase realised trip volume and shift mode share back toward car on the widened link — with no scripted percentage or hardcoded "refill" event; the effect must emerge purely from re-running the same SUE/logit machinery with the new capacity. Check: `go doc ./internal/engine/traffic LatentDemandPool` (or equivalent) exists; a passing test asserts re-assignment after a capacity increase raises realised volume on the widened link versus before, driven by the same equilibrium call used for every other assignment — `grep -rn "func Test.*[Ii]nducedDemand\|func Test.*[Ll]atentDemand" internal/engine/traffic/*_test.go`; `grep -n "scriptedRefill\|hardcodedIncrease" internal/engine/traffic/*.go` finds no matches.
- **AC-14 (A4; solver contract).** The assignment problem payload/response round-trips through `int.solver`'s `Solve` call using a registered `ProblemKind` for traffic equilibrium, with the CPU backend as the only implementation in v1 (per `int.solver`'s AC-4 mandatory fallback) — `engine.traffic` never calls a concrete solver backend type directly. Check: `grep -n "solver\.Get\|Registry\.Solve" internal/engine/traffic/*.go` shows contract-mediated calls, not `grep -n "cpu\.CPUBackend" internal/engine/traffic/*.go` (should find no direct backend import from this package).

### Error handling

- **AC-15 (GR#7).** A junction whose control type cannot resolve turn-movement capacities (e.g. malformed signal-split data) produces a registry-sourced error (new `MET-E`-range code) naming the junction, rather than defaulting to an arbitrary capacity or panicking. Check: `grep -n "MET-" internal/engine/traffic/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Mm]alformed.*[Jj]unction\|func Test.*[Ii]nvalidSignal" internal/engine/traffic/*_test.go`).
- **AC-16.** A `Solve` call to `int.solver` returning a non-nil error (unsupported problem kind, no backend available) is surfaced as a typed rejection to the caller of the daily assignment trigger — never silently falling back to a stale/previous-tick assignment without logging that it happened. Check: passing test coverage asserts the error propagates and a log/event records the fallback-to-stale case if one exists (`grep -rn "func Test.*[Ss]olverError\|func Test.*[Ss]olverFail" internal/engine/traffic/*_test.go`).

### Determinism & safety

- **AC-17 (GR#21; core requirement).** Same seed + identical command log produces byte-identical `TrafficAPI` outputs (link volumes, v/c ratios, commute times) at `POOL-SIM=1` and at `POOL-SIM=14` — a dedicated shard-count-invariance test exists, following `feat.detgate`'s reference structure (fixed seed, two runs, hash-compare). Check: `grep -rn "func Test.*[Ss]hardInvariance\|func Test.*POOL_SIM\|func Test.*[Dd]eterminis" internal/engine/traffic/*_test.go` finds it; `go test ./internal/engine/traffic/... -run TestTrafficDeterminism -race -count=1 -v` (or the actual name) passes.
- **AC-18 (GR#21; no map-range on result-affecting collections).** No `for range` loop over a Go map feeds a value into the assignment result, mode-choice probability, or commute-time output without a prior deterministic sort/ordering step. Check: `grep -rn "for .* := range" internal/engine/traffic/*.go` — every match iterating a map type is either read-only diagnostics or preceded by a `sort.` call on the iteration keys (`grep -n "sort\." internal/engine/traffic/*.go` shows the ordering step exists for each map-range site that affects output).
- **AC-19 (GR#21; deterministic tie-breaking).** Every point where the assignment or mode-choice logic must break a tie (equal-cost routes, equal-probability mode draws, equal-priority junction turn-movements) uses a documented deterministic rule (e.g. lowest edge ID, lexicographic ordering, or the counter-RNG from `foundation.det` seeded per the fixed seed) — never Go's undefined map/slice iteration order or a raw unseeded `math/rand` call. Check: `grep -n "math/rand\"" internal/engine/traffic/*.go` (excluding `_test.go`) finds no matches (only `foundation.det`'s counter-RNG is used); `go doc ./internal/engine/traffic` documents the tie-break rule explicitly at each decision point named above.
- **AC-20 (GR#21; parallel reduction order).** Any parallel reduction across shards/goroutines (e.g. summing PCU load onto a shared link, aggregating district commute distributions) is deterministic regardless of goroutine completion order — implemented via a fixed-order merge (e.g. per-shard partial results combined in shard-index order) rather than an order-dependent accumulator (e.g. a mutex-guarded running sum updated in whatever order goroutines finish). Check: `go doc ./internal/engine/traffic` documents the merge order; a passing test runs the reduction with an artificially randomised goroutine start order (or repeats it many times) and asserts the result is always identical (`grep -rn "func Test.*[Rr]eductionOrder\|func Test.*[Mm]ergeOrder" internal/engine/traffic/*_test.go`).
- **AC-21 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/traffic/*.go` (excluding `_test.go`) returns no matches anywhere in the assignment/logit/spillback logic — the daily-assignment "day" is a simulation-tick concept, never wall clock.
- **AC-22 (M0-ENG §1.3; route cache).** If `engine.traffic` (rather than `engine.roads`) owns the warm-start route cache mentioned in §19 intro point 1 ("cached warm starts"), the cache is contents-independent for determinism: a cache-cold run and a cache-warm run of the identical assignment produce identical link volumes/v/c ratios, differing only in solve latency. Check: `grep -rn "func Test.*[Cc]ache.*[Dd]eterminis\|func Test.*[Ww]armStart" internal/engine/traffic/*_test.go` finds coverage, or `doc.go` states explicitly the cache lives in `engine.roads` and this AC is N/A here.
- **AC-23.** `go test ./internal/engine/traffic/... -race -count=1` passes with no data race under the 256-fixed-shard worker pool pattern. Check: `grep -n "go func()" internal/engine/traffic/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-24.** `internal/engine/traffic/doc.go` states the module key `engine.traffic`, cites §19, §51, A4, and §II.5, and documents the exact SUE convergence rule (iteration count or tolerance) as the canonical reference for AC-3. Check: `grep -n "engine.traffic" internal/engine/traffic/doc.go` and `grep -n "§19\|section 19" internal/engine/traffic/doc.go` both match.
- **AC-25.** The tie-breaking rule (AC-19) and the parallel-reduction merge order (AC-20) are documented in comments next to their implementations, not left implicit, so a future contributor modifying the assignment loop cannot accidentally reintroduce nondeterminism. Check: `grep -n "deterministic tie-break\|merge order" internal/engine/traffic/*.go` finds citations at the relevant functions.

## Out of scope

- Road-graph identity, naming, class ladder, maintenance state, and in-place upgrades — that is `engine.roads` (MOD-024, this sprint's sibling item); `engine.traffic` consumes the road graph `engine.roads` exposes, it does not define edge identity.
- The GPU/cloud solver backend implementations for traffic equilibrium — only the CPU v1 backend via `int.solver`'s mandatory fallback is required (`MOD-068`/`MOD-069`, unscheduled future work).
- Parking mechanics (`engine.parking`, a later consumer) — this item's mode-choice logit references parking cost as a car-mode input but does not implement parking capacity/pricing itself.
- Fuel/EV charging systems (`engine.fuel`, a later consumer) — freight/car PCU accounting here does not model fuel consumption or range.
- External rail / off-map commuting mechanics (`engine.rail`, `engine.extcommute`, later consumers) — this item exposes the network those modules query; it does not implement off-map job pools or season-ticket pricing.
- The road inspector UI (name, endpoints, volume, v/c, top-5 OD flows, alternatives) — that is `ui.screen.map`/a later F-screen consuming this item's query surfaces, not this item's own deliverable.

## Escalations

- **For Bill — SUE convergence definition is spec-silent on exact numbers.** §19 states "converges in a few iterations on cached warm starts" but does not give a fixed iteration count or a numeric tolerance. AC-3 requires the junior to pick and document one (fixed count or ε-tolerance) since GR#21 forbids a wall-clock/order-dependent "until stable" loop — this is an implementer decision within spec intent, not a spec deviation, but flagging since a "few iterations" figure that turns out too low to actually converge on a large synthetic city would be a Sprint-5-exit-gate risk (S5's own exit gate requires "SUE converges in fixed iterations... bit-identical across worker counts" per the sprint plan) worth Bill confirming a starting number for (e.g. is there a target from balance/perf work, or is 20-50 iterations an acceptable placeholder for Sprint 5, tuned later in `balance.harness`, S8)?
- **For Bill — mode-choice personality weighting has no published coefficient table.** §19.1 names the four personality axes qualitatively (physicality, patience, wealth, and implicitly novelty/community-mindedness by analogy with §21's housing appeal profiles) but the master doc does not give numeric weights for the nested-logit utility function. AC-10 requires *a* documented, data-sourced (GR#15) weighting exists and is sensitive to personality — the exact coefficients are properly `data/modes.json` balance content (§24), not something this BA or the junior should invent as Go literals. Recommend confirming `modes.json`'s schema for these coefficients is either already frozen (`foundation.data`/`data.catalogue`, S2) or gets a placeholder-but-real-data-file treatment here, refreshed at Sprint-5 dispatch.
- **Assumption flagged (per BA instructions §3).** This item depends on `MOD-017` (engine.world, S3) for terrain/slope queries and `MOD-018` (engine.citizens, S3) for personality traits and the hot per-citizen commute-time write path, both scheduled to land two sprints ahead of S5 per the sprint plan — by S5 dispatch both should be frozen, but the owning BA should re-verify `WorldAPI`'s slope-query signature and `engine.citizens`' personality-vector shape against their actual landed APIs (not the illustrative names used here) before the junior is briefed, per the same caution `engine.world.md`'s own escalations raise about `engine.core`'s shard-partitioning API.
- **Assumption flagged.** AC-22's route-cache placement (`engine.traffic` vs `engine.roads`) is left ambiguous by code.json (neither entry's description names it explicitly, though §19 intro point 1 says "cached warm starts" in the traffic context). `engine.roads.md`'s own scope note assumes the cache is a `engine.traffic`/`engine.roads` joint concern; whichever module's junior lands first should state the placement in its `doc.go` so the other file's corresponding AC can be marked N/A cleanly rather than both teams building competing caches.
