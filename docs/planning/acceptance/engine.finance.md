## User stories

- **US-1.** As the city, I need household income (wages by sector/skill) to flow through taxes into a city budget that pays service opex, import contracts, debt service, and construction, all as int64 micro-pounds, so §7's money-flow chain is a real, auditable ledger, not a single aggregate number.
- **US-2.** As `ui.screen.finance` (a code.json consumer), I need every figure to drill through to its underlying ledger lines (per UI-SPEC §4's "the drill-through rule (absolute)"), so a cash figure on F2 genuinely opens its transaction history, not a dead end.
- **US-3.** As `engine.invariant` (MOD-019, already built in Sprint 2), I need `engine.finance` to expose a hook/interface the money-conservation invariant can query every tick, so §14's conservation assert has real ledger totals to check against, closing the loop this BA's own Sprint 2 escalation flagged as pending.
- **US-4.** As the player, I need every cell to be continuously priced by `base(terrain) × access(junction, roads) × amenity(services, coast view, pollution⁻¹) × scarcity(city size)`, so land price is a real formula the player can reason about, not a hidden number.
- **US-5.** As the player under financial pressure, I need loan facilities gated by milestone, interest set by a credit-rating function of debt/revenue + payment history + reserve months, and insolvency (3 consecutive months unable to meet obligations with no available credit) to be an actual game-over condition, so §7's and §12's failure mechanics are real and testable, not narrative flavour.
- **US-6.** As `engine.firms` (a later, Sprint 10 consumer, with a simple v1 stand-in here per MOD-022's own description "v1, superseded by engine.firms"), I need a basic firm P&L model (revenue from local demand ± export, costs from wages/inputs/rent, open/close on profitability) so commercial/industrial zones can live or die honestly before the full firms module lands.
- **US-7.** As `engine.projections`, I need investment programmes (capex parked into productivity) to carry a documented multi-year payback curve, so the Slow-Fuse Principle (A5: consequences >5 game-years out render at decision time) has real numbers for investment decisions specifically.

## Scope

Double-entry ledger money flows (wages→spend→tax→budget→opex/imports/debt/construction, per the S4 exit gate's own wording), continuous land pricing, milestone-gated loan facilities with credit-rating-driven interest, the insolvency game-over condition, a v1 simple firm P&L, investment-programme payback modelling, and the localisable conservation-hook data `engine.invariant` needs. All monetary values in int64 micro-pounds.

Check: `go doc ./internal/engine/finance` lists a function/method for each of the five stages above, **including a spend-stage function distinct from the wages and tax stages**; a passing integration test runs the full chain for one synthetic month with known inputs (a fixed wage bill, a fixed utility-consumption quantity at a fixed Market price, a fixed tax rate) and asserts each stage's *own posted amount* against hand-computed expected values (spend = quantity × price; tax = rate × (wages + spend); budget = tax − opex − debt − construction), not merely that the final budget balance is nonzero/plausible (`grep -rn "func Test.*[Mm]onthlyFlow\|func Test.*[Ff]ullChain\|func Test.*[Hh]ouseholdSpend" internal/engine/finance/*_test.go`). False-pass risk: a test asserting only "the budget balance reflects all stages" (the 2026-08-09 draft's original wording) would pass a build that silently folds "spend" into "wages" (e.g. treats wages as already net of consumption, so no distinct spend transaction is ever posted) — the exit gate's own wording requires spend as a separate, visible link in the chain, so the check must assert the spend stage exists and produces its own ledger entries, not just that money eventually reaches the budget by some route. **This stage requires `engine.consumption`'s per-household demand quantities as an input — see ASM-219 below on the code.json wiring gap this surfaces.**

- **AC-5 (§7 loans).** Loan facilities are gated by milestone tier (consuming `engine.unlocks`'s milestone state via its own interface, not a hardcoded tier check), and interest rate is computed as `f(debt/revenue ratio, payment history, reserve months)` — a documented credit-rating function, not a flat rate. - **AC-6 (§7 refinancing spiral).** Missing a loan payment degrades credit rating, which raises the interest rate on new/refinanced debt, which increases future payment burden — a passing test demonstrates this feedback loop compounding over at least two simulated missed-payment months (not just a one-shot rating drop). Check: `go doc ./internal/engine/finance IsInsolvent` (or equivalent) exists; passing tests cover: 3 consecutive failing months → game-over fires; 2 failing months then 1 successful month → counter resets, no game-over at month 4's second failure (`grep -rn "func Test.*[Ii]nsolven" internal/engine/finance/*_test.go`).

## Acceptance criteria

### Functional — instrument taxonomy and sources

- **AC-19 (source distinction — IMF vs government).** `data/borrowing_instruments.json` (or equivalent) registers at least two distinct `LoanSource` values — `imf` (lender-of-last-resort) and `government` — each carrying its own rate-range data and its own availability rule, not a shared rate range distinguished only by a label. The IMF source's availability rule reflects "lender of last resort" in a testable, documented way (e.g. gated on credit rating below a data-defined threshold, or on other sources being exhausted/unavailable) rather than being available identically to a government loan at all times. Check: `go doc ./internal/engine/finance LoanSource` (or equivalent) shows at least `imf`/`government` as distinct values; a passing test asserts the two sources' rate-range data differ and that the IMF source's availability function returns `false` for a clean-credit, low-debt synthetic city state where the government source returns `true` (`grep -rn "func Test.*[Ll]oanSource\|func Test.*[Ii][Mm][Ff]" internal/engine/finance/*_test.go`). **What a lazy implementation looks like:** a single `Loan` struct with a cosmetic `Source string` field set to `"IMF"` or `"Government"` that both read the exact same rate table and the exact same availability check — passes a shallow "IMF loans exist" smoke test while delivering nothing FEAT-057 actually asked for. **False-pass warning:** a test that only asserts a loan can be created with `Source: "imf"` (construction succeeds) would pass that lazy implementation; the check must compare the two sources' actual terms/availability, not just that the enum value is settable.
- **AC-20 (secured vs unsecured; collateral reference).** Every loan instrument (regardless of source) carries a `Security` classification of `secured` or `unsecured`; a `secured` instrument carries a non-nil collateral reference (an asset class or specific asset ID — land parcel, facility, or a pledged revenue stream per FEAT-057's own "presumably against land/facilities/revenue streams" wording) while `unsecured` carries none. Secured instruments' data-defined rate range has a strictly lower floor than unsecured instruments' rate range at the same source and same credit rating (directional check only, per the balance-number regime — no specific numbers pinned). Check: `go doc ./internal/engine/finance` shows a `Security`/`Collateral` field set; a passing test constructs a secured and an unsecured instrument from the same source at the same synthetic credit rating and asserts `securedRate.Min < unsecuredRate.Min` (`grep -rn "func Test.*[Ss]ecured\|func Test.*[Cc]ollateral" internal/engine/finance/*_test.go`). What happens to a pledged collateral asset on default is explicitly **out of scope** for this AC — see ASM-413 (Escalations) — this AC only requires the field and the rate-preference direction to exist.
- **AC-21 (GR#15; rate ranges are placeholder data, not Go constants).** Every rate range, spread, and threshold introduced by this item lives in a JSON data file, never a hardcoded Go literal, and carries a non-empty placeholder/pending-tuning disclosure field on each entry (mirroring `data/market.json`'s "pending M2 Batch tuning" convention and `external_world.json`'s AC-16 discipline verbatim). Check: `grep -n "[0-9]\.[0-9]*%\|0\.0[0-9]" internal/engine/finance/*.go` (excluding `_test.go`) for suspicious inline rate literals finds no matches tied to a borrowing-instrument rate; a passing loader test asserts every instrument-taxonomy entry in the data file has a non-empty disclosure/comment field (`grep -rn "func Test.*[Pp]laceholderDisclosure.*[Bb]orrow\|func Test.*[Rr]ateProvenance" internal/engine/finance/*_test.go`). **What a lazy implementation looks like:** a junior "just picking a reasonable IMF rate" (e.g. `const imfRateFloor = 0.045`) to make a test pass quickly — this is the exact ASM-284-class overstep the balance-number regime exists to prevent, and it fails this AC even if every other AC in this section passes.

### Functional — revenue-share terms

- **AC-22 (revenue-share repayment, live-computed).** A `RevenueShareTerms` structure exists carrying a data-driven percentage and a reference to a revenue base — either the city's whole-budget revenue (the existing `CollectTax`/budget-aggregation stage's output, MOD-022 AC-3) or a single facility's own P&L revenue (the `SimpleFirm`/facility revenue figure) — selectable per instrument, not hardwired to one shape (see ASM-414). Each period, the repayment obligation is **recomputed** as `percentage × (that period's actual revenue base)`, not fixed at origination. A period where the revenue base is zero produces a zero repayment obligation for that period (not a negative balance, not debt forgiveness of the principal, not an insolvency-triggering "missed payment" by itself — a zero-revenue-share payment is not a missed obligation under MOD-022 AC-7's "no available credit" definition unless combined with an actual funding shortfall elsewhere). Check: `go doc ./internal/engine/finance RevenueShareTerms` shows the percentage + revenue-base reference; a passing test runs two synthetic months with different revenue-base figures and asserts the repayment amount changes proportionally between them (`repayment = pct × revenue`, recomputed, not memoised from month 1) (`grep -rn "func Test.*[Rr]evenueShare" internal/engine/finance/*_test.go`). **False-pass warning:** a test that only checks month 1's repayment value would pass an implementation that computes the share once at origination and treats it as a fixed schedule thereafter — the check must exercise at least two periods with differing revenue to prove live recomputation, which is the entire point of "revenue-share" as distinct from a normal amortising loan.

### Functional — PFI-style facility funding

- **AC-23 (PFI facility: deferred capex, recurring unitary charge, contractual lock-in).** A `PFIFacility` instrument models the classic PFI trade-off explicitly: at construction, the ledger posts little-to-no upfront capex debit to the city's construction-ledger stage (MOD-022 AC-3's `SettleConstruction`) for a PFI-funded facility, versus the full capex debit for the same facility built conventionally (a comparative test, not a fixed number — GR#15). In exchange, the facility carries a recurring `UnitaryCharge` — a periodic ledger obligation distinct from ordinary debt service, running for a documented `MinimumTermMonths` — that continues for the facility's contracted life. The contract's lock-in is explicit and queryable: either an early-termination penalty function or a documented statement that early termination is not modelled (a real design choice, not a silent gap). Check: `go doc ./internal/engine/finance PFIFacility` shows `UnitaryCharge` and `MinimumTermMonths` (or equivalent); a passing test constructs the same facility both PFI-funded and conventionally-funded and asserts the PFI path's month-of-construction capex debit is materially lower (e.g. below a documented small fraction of the conventional path's debit) while its subsequent monthly `UnitaryCharge` obligation is nonzero for at least `MinimumTermMonths` months (`grep -rn "func Test.*PFI" internal/engine/finance/*_test.go`). **What a lazy implementation looks like:** a `PFIFacility` that is just a `Loan` with a different name and an amortisation schedule stretched over more months — this fails to capture the actual PFI shape (deferred capex + a *service-style* recurring charge, not principal+interest) and would mislead the player about what trade-off they're making. Interaction with FEAT-054's decommissioning liability (also unbuilt) is explicitly out of scope beyond this AC's own `UnitaryCharge`/`MinimumTermMonths` surface — see Escalations.

### Functional — integration with existing credit-rating and insolvency mechanics (the load-bearing requirement)

- **AC-24 (no instrument bypasses insolvency's obligation check — MOD-022 AC-7).** Every instrument this item adds — including a `PFIFacility`'s `UnitaryCharge` and a `RevenueShareTerms` facility's recomputed periodic repayment — is included in the same "obligations that must be met" set MOD-022's `IsInsolvent`/AC-7 already evaluates each month; none is exempt or routed through a bespoke, separate insolvency path. Check: a passing test posts a PFI facility's `UnitaryCharge` as a monthly obligation, then simulates 3 consecutive months where that obligation (and no other) cannot be met and no credit is available, and asserts the *same* game-over signal MOD-022 AC-7 defines fires — reusing that mechanism, not a duplicate one (`grep -rn "func Test.*[Pp][Ff][Ii].*[Ii]nsolven\|func Test.*[Rr]evenueShare.*[Ii]nsolven" internal/engine/finance/*_test.go`). Repeat for a `RevenueShareTerms` facility with a nonzero revenue base that the player nonetheless fails to fund from elsewhere. **False-pass risk (this is the AC an attacker should try hardest to break):** a test that only asserts the new instrument *posts a ledger entry* would pass a build where that entry is silently excluded from the insolvency counter's obligation set (e.g. because `RevenueShareTerms` was implemented as an equity-like "the lender just gets less if revenue is low" concept with no hard obligation floor at all) — such a build would let a player borrow via revenue-share or PFI facilities with **zero insolvency risk**, defeating §12's death condition exactly the way GR#23's "nothing committed un-attacked" rule exists to catch. The check must prove the game-over signal fires through the new instrument, not merely that money moved.
- **AC-25 (credit rating denominator includes all instrument types).** MOD-022 AC-5's `CreditRating` function's debt/revenue ratio input includes the outstanding balance/committed-obligation value of every instrument type this item adds (a PFI facility's remaining committed `UnitaryCharge` stream counts as debt-equivalent exposure; a revenue-share facility's outstanding principal, if any, counts; secured and unsecured instruments both count at their full outstanding value — security affects *rate*, per AC-20, not whether the exposure counts toward the ratio). Check: a passing test computes `CreditRating` for two synthetic city states identical except one carries an additional PFI facility's committed `UnitaryCharge` exposure, and asserts the ratings differ in the documented direction (more committed exposure ⇒ same-or-worse rating, never better) (`grep -rn "func Test.*[Cc]reditRating.*PFI\|func Test.*[Cc]reditRating.*[Ii]nstrument" internal/engine/finance/*_test.go`). **What a lazy implementation looks like:** treating a PFI facility's `UnitaryCharge` as an operating expense line only (since it isn't structured as principal+interest) and never feeding its committed future obligation into the credit-rating ratio at all — technically defensible-sounding ("it's not really debt") but exactly the kind of off-balance-sheet framing PFI is criticised for in reality, and the opposite of what US-12 asks for.

### Error handling

- **AC-26 (GR#7).** A malformed borrowing-instrument entry (missing source, missing security classification on a claimed-secured instrument with no collateral reference, a revenue-share percentage outside `[0, 1]`, a PFI facility with no `MinimumTermMonths`) is rejected at load/construction time with a registry-sourced error (new `MET-E`-range code), never silently defaulted (e.g. to `unsecured`, to `0%` revenue share, or to a zero-length PFI term). Check: `grep -n "MET-" internal/engine/finance/*.go` finds a registry code reference for the new instrument-validation path; passing test coverage for at least the four named malformed cases (`grep -rn "func Test.*[Ii]nstrumentInvalid\|func Test.*[Mm]alformedBorrowing" internal/engine/finance/*_test.go`).

Check: `grep -n "FEAT-057\|borrowing instrument" internal/engine/finance/doc.go` and `grep -n "placeholder\|pending.*tun" internal/engine/finance/*.go` (on the new instrument data/loader file specifically) both match.

# FEAT-068 — Impending-doom warnings: the insolvency half

**BOW code:** FEAT-068 (P1, open) — "projections must warn before insolvency or ghost-city can ever fire." Bill's dispatch note: "firing without prior warning = defect" is the core requirement.
**Spec refs:** §7/§12 (insolvency, this file's AC-7); A5 the Slow-Fuse Principle (`engine.projections.md`'s AC-5) and §1.3's "the player should almost always be able to see trouble coming" — the same anti-ambush contract A5 states for decisions now extended to a death condition itself.
**Depends on:** `engine.projections.md` AC-17 (`MarginToInsolvency`) and AC-19 (`WarningLedger`) — both specified in that file as part of this same item; the `engine.finance`→`engine.projections` edge is already registered in code.json (confirmed 2026-08-12), so unlike the spiral half of this item, nothing here is blocked on a missing edge.
**Balance-number regime:** the minimum warning lead time this section's AC compares against is a placeholder pending Aaron's balance pass — see `engine.projections.md` AC-20 and `feat.deathwarnings.md`. No AC below may be satisfied by a junior inventing a final month count.

## User stories

- **US-13 (FEAT-068).** As the player about to lose the game to insolvency, I need to have had a real, measurable chance to see it coming through `engine.finance`'s own connection to `engine.projections`, so insolvency reads as a consequence of choices I could have corrected, not a number that silently crossed a line I was never shown.
- **US-14 (FEAT-068).** As a Destructive agent auditing this module, I need the insolvency trigger's dependency on a prior warning to be a structural property of the trigger path itself — not a correlation a lazy implementation could satisfy by coincidence — so "warn before insolvency" cannot be gamed by a build that computes a warning nobody's trigger logic actually consults.

## Acceptance criteria

### Functional — the causal gate (the load-bearing requirement)

- **AC-29 (FEAT-068; insolvency cannot fire without a prior, sufficiently-led `engine.projections` warning — the core "firing without prior warning = defect" requirement).** `IsInsolvent`'s (AC-7) transition to the game-over signal is gated on `engine.projections`'s `WarningLedger` (that file's AC-19) already carrying a `MarginToInsolvency` warning entry for this save, recorded at least `MinWarningLeadMonths` (a data-sourced placeholder, `engine.projections.md` AC-20) before the month the insolvency signal fires. This is a **structural gate**, not a logged correlation: the code path that flips insolvency to true queries the ledger itself and the transition cannot occur if no qualifying entry exists — it is not merely "usually preceded by" a warning that some other code path happens to compute independently.
  **Check, part (a) — real-run lead time, not an invented one.** A passing test constructs a synthetic city trending toward insolvency via the module's own normal monthly processing (missed payments accumulating through the real posting/credit-rating machinery, not test-forced state), runs it to the point insolvency actually fires, and reads back **from that same run** (i) the sim month `engine.projections`'s `WarningLedger` recorded the qualifying warning entry and (ii) the sim month `IsInsolvent` actually transitioned to true. The test asserts `warning_month + MinWarningLeadMonths <= trigger_month`, using the run's own real timestamps on both sides — never a hand-computed "expected" trigger month, which would let a lazy implementation's actual (late or absent) warning slip past unnoticed. (`grep -rn "func Test.*[Ii]nsolven.*[Ww]arn\|func Test.*[Ww]arn.*[Ii]nsolven" internal/engine/finance/*_test.go`)
  **Check, part (b) — the anti-cosmetic bypass test (this is the check that catches a warning system that exists but isn't wired to the real trigger path).** A second passing test drives the ledger toward insolvency through a path that **bypasses** the normal monthly recompute that feeds `engine.projections`'s curve provider (e.g. posting the missed-payment/no-credit state directly against the low-level ledger/credit-rating internals, skipping the hook that registers the trend with `engine.projections`) and asserts the insolvency trigger **cannot fire** — it must return a typed rejection/error (a "no qualifying warning on record" condition, registry-sourced per GR#7) rather than silently proceeding to declare game over with no warning on record. (`grep -rn "func Test.*[Bb]ypass.*[Ww]arn\|func Test.*[Nn]oWarning.*[Rr]eject" internal/engine/finance/*_test.go`)
  **False-pass risk, stated explicitly.** A test that only checks "a `MarginToInsolvency` warning object exists somewhere in the logs by the time insolvency fires" — temporal correlation with no structural dependency — would pass a build with a cosmetic warning panel that happens to render around the same time as the death condition, or one that fires the warning and the trigger on the *same* tick (zero real lead time). Part (a)'s enforced minimum lead (measured from the same run, both timestamps real) rules out the simultaneous-firing case; part (b)'s bypass test rules out the "computed somewhere, never actually consulted" case — an implementation must pass both, and a build passing only (a) because it got lucky on timing while never actually gating on the ledger is exactly what (b) exists to catch.
- **AC-30 (FEAT-068; the warning tracks the real trajectory, including recovery — no "cry wolf" and no "silent all-clear").** If a city trending toward insolvency (a qualifying warning recorded per AC-29) subsequently recovers (missed-payment streak breaks, credit becomes available again — the same reset condition AC-7 already defines) before the insolvency threshold is reached, the `WarningLedger` reflects the recovery (a documented "warning cleared"/superseded entry, or an equivalent query returning "no active warning" once recovered) rather than leaving a stale warning standing that no longer reflects real state. Check: a passing test drives a synthetic city into a qualifying warning state, then recovers it (per AC-7's reset semantics) before insolvency fires, and asserts a subsequent `WarningLedger`/status query no longer reports an active insolvency warning (`grep -rn "func Test.*[Ww]arning.*[Rr]ecover\|func Test.*[Ww]arning.*[Cc]lear" internal/engine/finance/*_test.go`). **Why this matters for AC-29's gate specifically:** without this, a build could satisfy AC-29 by latching a warning permanently on the first sign of trouble and never clearing it — which would make AC-29's lead-time check trivially satisfiable (there's *always* an old warning on file) while providing the player no real signal about their *current* trajectory. This AC is what stops AC-29's gate from being satisfied by a warning system that has degraded into "always warn once, forever" — which is functionally the same failure as never warning at all.

### Error handling

- **AC-31 (GR#7; AC-29's rejection path).** The AC-29(b) rejection — insolvency threshold reached with no qualifying warning on record — produces a registry-sourced error (new `MET-E`-range code) naming the missing-warning condition explicitly, distinct from AC-12's unbalanced-transaction error and AC-7's ordinary game-over signal, so a Tester/Destructive agent can tell "insolvency correctly triggered" apart from "insolvency was about to trigger with no warning on record, and the gate caught it" in test output and in any production log. Check: `grep -n "MET-" internal/engine/finance/*.go` finds this specific code path, distinct from AC-12's code; passing test coverage asserts the returned error's registry code matches AND that no game-over signal was emitted alongside it (`grep -rn "func Test.*[Nn]oWarning.*[Ee]rror" internal/engine/finance/*_test.go`).

### Documentation

- **AC-32 (FEAT-068).** `internal/engine/finance/doc.go` states that `IsInsolvent` is gated on `engine.projections`'s `WarningLedger` per AC-29, names the `MinWarningLeadMonths` placeholder and where it lives (`engine.projections.md` AC-20's data file), and cross-references FEAT-068 explicitly. Check: `grep -n "FEAT-068" internal/engine/finance/doc.go` and `grep -n "WarningLedger" internal/engine/finance/doc.go` both match.
