# Acceptance criteria — engine.freight (MOD-047)

**BOW code:** MOD-047
**Spec refs:** §33 The Freight Harbour — Tonnes & Chains (`docs/METROPOLIS-MASTER-v2.1.md` lines 462-476: all freight accounted in tonnes/day end-to-end; port capacity = berths × crane rate (t/hr) × hours, customs throughput separate (smuggling risk when saturated, §28); modal reach — road 25t/truck (junction slots §8), rail freight 1,000t/train (tier-8 yard), sea 3kt coaster→40kt container ship; storage: quayside stacks, silos (grain), tank farm (fuel), cold store (fresh/fish); five production chain families (construction, steel & machinery, food, consumer goods, energy), each stage a firm with input t/day → output t/day, jobs, power/water draw, blight class; exports earn, balance-of-trade screen (F5 extension) shows t/day and £/day by commodity and by artery, port flipping the city importer→exporter is a mid-game arc); §8 Logistics & Just-in-Time, artery #2 framing (lines 213-222: freight shares the road/junction-slot mechanism with commuter traffic); code.json `engine.freight` entry (inbound `FreightAPI`, pattern "chains from data; stages register as firms; tonnes conserved (invariant)", consumers: `engine.chemicals`, `engine.rail`, `ui.screen.trade`; outbound calls: `engine.logistics`, `engine.market`, `engine.firms`).
**Date:** 2026-08-11 (BA-S10a, first pass)
**Status:** draft-ahead — `MOD-020` (engine.market) and `MOD-025` (engine.logistics) are both `open`; this item is not in the ready queue until both land. Content written now, ahead of both.
**Package under test:** `internal/engine/freight/` (path from `node claude-bow.js show MOD-047`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/freight/...`.

## User stories

- **US-1.** As the port, I need capacity to be a real function of berths × crane rate × hours, with customs throughput tracked separately, so port saturation is a computed bottleneck, not a flat unconditional import ceiling.
- **US-2.** As a production-chain stage (e.g. steel mill, bakery), I need to be registered as a genuine firm through `engine.firms` (the registered outbound edge, per code.json's "stages register as firms" pattern), so a chain stage's staffing/premises/credit constraints are the same real mechanism `engine.firms` gives any other firm — not a bespoke chain-only entity.
- **US-3.** As `engine.logistics` (the registered outbound edge, MOD-025), I need every freight movement — port→estate, estate→estate along a chain, estate→port for export — to be an ordinary logistics movement consuming real junction slots, so freight genuinely competes with commuter traffic for road space (§II.5's "the whole game").
- **US-4.** As `engine.market` (the registered outbound edge, MOD-020), I need chain-stage input/output commodities priced and availability-bounded through `MarketAPI`, so a chain's economics are consistent with the same commodity prices every other consumer sees.
- **US-5.** As `engine.chemicals` and `engine.rail` (registered inbound consumers), and `ui.screen.trade` (F5), I need tonnage figures, chain-stage state, and the balance-of-trade breakdown queryable through `FreightAPI`, so downstream modules and the trade screen read real engine state, not a UI-side recomputation.
- **US-6.** As the auditor of this module's own registered pattern ("tonnes conserved (invariant)"), I need a mass-conservation identity that actually holds and is checked — not merely asserted in the pattern string — for every commodity flowing through the freight system, so a silent tonnage leak or duplication is structurally impossible to miss.
- **US-7.** As the player watching the balance-of-trade screen (F5 extension), I need import tonnage/value and export tonnage/value to be independently sourced totals, so "the port flips the city from importer to exporter" is a real state transition read off two independently-tracked numbers, not a single signed figure that could be wrong in either direction undetected.

## Scope

Port capacity accounting (berths × crane rate × hours, customs throughput separate); the five production-chain families (construction, steel & machinery, food, consumer goods, energy), each stage registered as a firm via `engine.firms`; storage-site tracking (quayside stacks, silos, tank farm, cold store); modal-reach tonnage caps (road 25t, rail 1,000t, sea 3-40kt) expressed as `engine.logistics` movements; the balance-of-trade breakdown (t/day and £/day by commodity and artery); the mass-conservation identity for freight tonnage. No production-chain stage business logic beyond the input→output t/day relationship itself (each stage's internal firm mechanics belong to `engine.firms`), no commodity pricing (`engine.market`'s job, only consumed), no junction-slot/movement-scheduling mechanics (`engine.logistics`'s job, only consumed).

## Acceptance criteria

### Functional — port capacity and customs

- **AC-1 (GR#20; code.json inbound contract).** A `FreightAPI` exists exposing port-capacity, chain-stage, storage-site, and balance-of-trade queries plus movement/customs commands, matching code.json's documented pattern "chains from data; stages register as firms; tonnes conserved (invariant)", consumed by `engine.chemicals`/`engine.rail`/`ui.screen.trade` through this interface alone. Check: `go doc ./internal/engine/freight FreightAPI` shows both a query surface and a command surface; `grep -rln "freight\.\(portState\|chainStage\)\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/freight` itself and `_test.go`) finds no direct exported-field writes bypassing the interface.
- **AC-2 (§33 port capacity formula).** Port throughput capacity is computed as `berths × craneRate(t/hr) × hours`, not a flat daily-tonnage constant — changing any one of the three factors (holding the other two fixed) changes the computed capacity. Check: `go doc ./internal/engine/freight PortCapacity` (or equivalent) shows the three-factor accessor; a passing test asserts capacity scales with each factor independently (`grep -rn "func Test.*[Pp]ortCapacity" internal/engine/freight/*_test.go`). **Lazy implementation this rejects:** a single "port throughput = N tonnes/day" constant satisfies "port has capacity" on a shallow read but fails the per-factor scaling test, which is exactly what §33's explicit multiplicative formula requires.
- **AC-3 (§33/§28 customs throughput, separate and saturation-linked smuggling risk).** Customs throughput is tracked as its own capacity figure, independent of berth/crane physical throughput, and a smuggling-risk indicator rises as customs saturation (customs demand ÷ customs capacity) increases — the two capacities can be saturated independently (e.g. physical berths free but customs backed up, or vice versa). Check: `go doc ./internal/engine/freight` shows a distinct `CustomsCapacity`/`CustomsSaturation` accessor separate from `PortCapacity`; a passing test saturates customs while berths remain under capacity and asserts the smuggling-risk indicator rises while port physical throughput is unaffected (`grep -rn "func Test.*[Cc]ustoms.*[Ss]eparate\|func Test.*[Ss]muggling" internal/engine/freight/*_test.go`).

### Functional — chain stages as firms

- **AC-4 (§33 five chain families; GR#20 outbound contract).** All five documented production-chain families — construction (chalk→cement→concrete; clay→bricks; timber→joinery), steel & machinery (coal+ore→steel→fabrication→machinery/vehicles), food (grain→mill→bakery; milk→dairy; livestock→abattoir→processing; fish→processing; fruit→packhouse/winery), consumer goods (plastics+fabrication→light goods), energy (coal→power; fuel import→distribution) — are modelled as ordered stage sequences loaded from data, and EVERY stage registers itself as a real firm through `engine.firms`'s registered outbound edge (a firm with staff, premises, credit — code.json's "stages register as firms" pattern), not a freight-owned pseudo-firm struct with its own parallel staffing/growth logic. Check: `grep -rn "firms\.\(RegisterFirm\|FirmAt\)" internal/engine/freight/*.go` (excluding `_test.go`) shows a real call into `engine.firms`'s package per stage; a passing test asserts a chain stage's firm is queryable through `FirmsAPI` itself (not merely a freight-internal mirror) and has a real staff roster (`grep -rn "func Test.*[Cc]hainStage.*[Ff]irm\|func Test.*[Ss]tageIsFirm" internal/engine/freight/*_test.go`). **Lazy implementation this rejects:** a `ChainStage` type that merely looks firm-shaped (similar field names: staff count, output) but is entirely freight-owned and never reaches `FirmsAPI` would pass a naming grep while violating the registered "stages register as firms" contract and duplicating `engine.firms`'s lifecycle mechanics (GR#3).
- **AC-5 (§33 per-stage input→output).** Each chain stage exposes documented input commodity t/day and output commodity t/day (per the chain table), plus jobs, power/water draw (consumed via §17-consumption-coefficient inputs), and a blight class — with output t/day bounded by input t/day availability (per `MarketAPI`'s capacity-bounded availability, AC-8 below), not an unconditional output regardless of input supply. Check: `go doc ./internal/engine/freight ChainStage` shows input/output/jobs/power-water/blight fields; a passing test constrains a stage's input commodity below its documented consumption rate and asserts output falls proportionally rather than continuing unconstrained (`grep -rn "func Test.*[Ii]nputBound.*[Oo]utput\|func Test.*[Ss]tageThroughput" internal/engine/freight/*_test.go`).
- **AC-6 (§33 storage sites).** The four documented storage-site types — quayside stacks (general), silos (grain), tank farm (fuel), cold store (fresh/fish) — each carry a distinct, documented capacity and are the queryable holding point for a chain stage's output pending onward movement/export, matching commodity type to storage type (grain cannot silently occupy tank-farm capacity). Check: `go doc ./internal/engine/freight StorageSite` shows the four typed variants; a passing test asserts routing grain to a tank farm (or fuel to a silo) is rejected or requires an explicit type override, not silently accepted (`grep -rn "func Test.*[Ss]torageType\|func Test.*[Mm]ismatchedStorage" internal/engine/freight/*_test.go`).

### Functional — freight as logistics movements

- **AC-7 (§33/§II.5; US-3; GR#20 outbound contract).** Freight movements — port↔estate, estate↔estate along a chain, estate→port export — are literally `engine.logistics` movements consuming real per-junction daily slots (reusing `LogisticsAPI`'s movement machinery per `engine.logistics.md` AC-4's "same underlying type/method set, not merely a similarly-named one" precedent), not a freight-owned parallel truck/rail model. Modal caps are enforced as documented per-movement bulk limits: road 25t/truck, rail 1,000t/train, sea 3kt (small coaster) to 40kt (container ship). Check: `grep -rn "logistics\.(Movement|Draw|Stock)" internal/engine/freight/*.go` (excluding `_test.go`) shows freight movements constructed through `engine.logistics`'s exported movement type; a passing test asserts a saturated junction on a freight route produces the same next-day-queue behaviour `engine.logistics.md` AC-4 defines, and that a single road movement never exceeds 25t (`grep -rn "func Test.*[Ff]reightMovement\|func Test.*[Mm]odalCap" internal/engine/freight/*_test.go`). **False-pass risk:** a `FreightTruck` type resembling `engine.logistics`'s movement in field names but scheduled independently would pass a naming grep while never contending for the junction slots `engine.logistics` tracks — the check requires the saturation scenario to reproduce `engine.logistics`'s own queueing behaviour.
- **AC-8 (§33/§45; US-4; MarketAPI pricing).** A chain stage's input/output commodities are priced and availability-bounded through `MarketAPI.Price`/`Availability` (the registered outbound edge), and export revenue is computed from `MarketAPI`'s (or the balance-of-trade path's own) export price, never a freight-owned hardcoded commodity price. Check: `grep -rn "market\.\(Price\|Availability\)" internal/engine/freight/*.go` (excluding `_test.go`) shows a real call; `grep -nE "[0-9]+\.[0-9]+" internal/engine/freight/*.go` (excluding `_test.go`) finds no bare price-shaped numeric literals outside doc-comment prose transcribing the spec.

### Functional — balance of trade

- **AC-9 (§33 balance-of-trade screen; F5 extension).** The balance-of-trade breakdown exposes, per commodity and per artery (port/rail/road), an independently-sourced import t/day+£/day figure (from `MarketAPI`-priced import movements) and an independently-sourced export t/day+£/day figure (from the port/rail departure ledger's own tracked departures) — never one computed as the other's signed complement. Check: `go doc ./internal/engine/freight BalanceOfTrade` (or equivalent) shows separate `Imports`/`Exports` accessors, each independently populated; a passing test asserts changing only export departures (holding imports fixed) changes the exports figure without perturbing the independently-queried imports figure, and vice versa (`grep -rn "func Test.*[Bb]alanceOfTrade\|func Test.*[Ii]mportExportIndep" internal/engine/freight/*_test.go`). **Lazy implementation this rejects:** computing `Exports = SomeTotal - Imports` (or the reverse) would make "the city flipped to exporter" trivially, tautologically readable off any single input drifting, regardless of whether exports actually moved — the check requires both terms independently sourced before any net figure is derived, the same discipline AC-10's identity applies to conservation.
- **AC-10 (mass conservation — the strongest available check, per the brief; the "chains conserve tonnes" clause).** For every accounting period (tick or month, documented which) and every commodity tracked by the freight system, the following identity holds exactly: `TonnesProduced == TonnesConsumedDownstream + TonnesExported + TonnesInStorage(delta from prior period, per storage-site's own stock accessor) + TonnesInTransit(en-route in an engine.logistics movement, per AC-7)`. **Every term is independently sourced, never inferred as a remainder:** `TonnesProduced` from each chain stage's own output accessor (AC-5), `TonnesConsumedDownstream` from the NEXT stage's own `engine.logistics.Draw` ledger (per `engine.logistics.md` AC-2's stock-draw mechanism — not freight's own bookkeeping of what it "sent"), `TonnesExported` from the port/rail departure ledger's own tracked departures (AC-9's export accessor, itself independently sourced), `TonnesInStorage` delta from each storage site's own stock accessor (AC-6), and `TonnesInTransit` from `engine.logistics`'s own movement ledger (AC-7) — five genuinely independent sources, only combined at the moment of the check. Check: a passing test runs a synthetic chain (at least two stages plus one export path) for several ticks with a mix of full and constrained throughput, independently sums each of the four right-hand terms from its own source accessor, and asserts the sum equals the independently-tracked `TonnesProduced` figure to an exact (integer-tonnage) or documented epsilon (`grep -rn "func Test.*[Mm]assConserv\|func Test.*[Tt]onnage.*[Ii]dentity" internal/engine/freight/*_test.go`). **Lazy implementation this rejects, stated per the brief's explicit warning:** computing `TonnesConsumedDownstream` (or any single term) as `TonnesProduced − (the other three)` rather than reading it from the downstream stage's own `engine.logistics.Draw` ledger would make the identity trivially, tautologically true regardless of a real bug in that term's accounting — a leak or double-count anywhere else would silently balance around the derived term, indistinguishable from correct until a downstream consumer (a chemicals-chain stage, `engine.rail`) reads a wrong tonnage. This is the exact failure mode `engine.refuse.md` AC-11 names and the brief explicitly warns has already happened in this wave; this identity is written to structurally exclude it by requiring all four terms to resolve through genuinely different code paths (three different modules' own ledgers, one local storage accessor) before summation.
- **AC-11 (US-6; registration with `engine.invariant` — STILL BLOCKED after c36778b; BUG-100 tripwire applied; the module's own pattern string names this).** Freight tonnage (per AC-10's identity) is registered as a conserved stock with `engine.invariant`'s (MOD-019) registry, per code.json's OWN `engine.freight` inbound pattern text, "tonnes conserved (invariant)" — this is not an inference from spec prose, it is the module's registered self-description. **Blocked pending BUG-058:** code.json still shows (a) no `engine.freight`→`engine.invariant` outbound call edge (c36778b registered `engine.citizens`/`engine.finance`/`engine.traffic`→`engine.invariant`, not `engine.freight`), and (b) `engine.invariant`'s own inbound `consumers` list is `engine.citizens`/`engine.finance`/`engine.traffic` only, `engine.freight` absent. The package must still pass AC-10's local identity test (which needs no cross-module edge) as the interim proof of correctness — this remains a SHARPER instance than most of BUG-058's existing entries, because here the registry's own pattern text promises the exact thing the registry's own edge list still fails to wire. **Tripwire (mechanical, not a prose label — BUG-100):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.freight'); process.exit(m.outbound.calls.some(c=>c.key==='engine.invariant')?1:0)"` must exit **0** (edge still absent). A nonzero exit means the edge has landed and this AC is stale, unarmed prose that MUST be rewritten to a real check before the next commit touching `internal/engine/freight/`; Tester/CI treat a nonzero exit here as a hard FAIL, not a silent pass. Until the tripwire fires: `grep -n "invariant\.Register" internal/engine/freight/*.go` shows a registration call at package init/boot; until then, `internal/engine/freight/doc.go` states the block explicitly, citing BUG-058 and quoting the module's own "tonnes conserved (invariant)" pattern text as the specific promise left unfulfilled.

### Error handling

- **AC-12 (GR#7).** Routing a movement against an unregistered chain stage, storage-site ID, or commodity, or querying port capacity before any berths are configured, returns a registry-sourced error (new `MET-E`-range code, claimed against `data/errors.json`'s reserved table at build time — no `engine.freight` sub-range exists yet) rather than a silently-created zero-value stage/site entry. Check: `grep -n "MET-" internal/engine/freight/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredStage\|func Test.*[Uu]nknownStorage" internal/engine/freight/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value stage/site entry was created, not merely that a matching-named test function exists.
- **AC-13.** A movement command whose declared tonnage exceeds its mode's documented cap (>25t declared for a road movement, >1,000t for rail, >40kt for sea), or a negative tonnage/price input, is rejected with a typed error, never silently clamped to the cap or silently ignored. Check: passing test coverage (`grep -rn "func Test.*[Oo]verCap\|func Test.*[Nn]egativeTonnage" internal/engine/freight/*_test.go`).

- **AC-15 (SG-7; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/freight/*.go` (excluding `_test.go`) returns no matches.

## Out of scope

- `engine.firms`'s own firm lifecycle mechanics (founding, growth, credit, failure) — this item only registers chain stages AS firms (AC-4); it does not reimplement firm behaviour.
- `engine.logistics`'s own movement-scheduling/queueing/junction-slot mechanics — this item only *drives* that machinery for freight-typed movements (AC-7).
- `engine.market`'s own commodity pricing mechanics — this item only queries it (AC-8).
- `engine.invariant`'s own registry/hard-assert/release-error mechanics — this item only registers against it once the edge exists (AC-11); it does not build a second invariant framework.
- The specific per-chain input/output t/day figures, storage-site capacities, and port berth/crane-rate/customs-throughput starting values — balance data pending M2 tuning (see Escalations).
- `engine.chemicals`'s own petrochemical/pipeline network (§50, a separate registered consumer downstream of this module) — out of scope beyond exposing the tonnage this module produces.
