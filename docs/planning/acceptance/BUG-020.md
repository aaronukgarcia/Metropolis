# Acceptance criteria — StubEngine.Run must not exit silently on premature channel close (BUG-020)

**BOW code:** BUG-020 (P2, open) — **LATENT, not live under current wiring** per the finding's own note (`boot.go`'s `shutdown()` ordering closes the window today); this fix is preventative.
**Spec refs:** GR#1 (aggressive error trapping — a distinguishable failure, not a silent one); the finding's own framing as "the same family as SEC-020/ASM-058: a failure invisible to the immediate caller control flow."
**Date:** 2026-08-10
**Status:** active
**Package under test:** `internal/engine/stub/` (`engine.go:103`, `StubEngine.Run`) plus `cmd/metropolis/boot.go`'s call site.
**Standard gates:** see `README.md`, package `./internal/engine/stub/...` and `./cmd/metropolis/...`.

## Acceptance criteria

### Functional

- **AC-1.** `StubEngine.Run` distinguishes a premature `Commands()` channel closure (`ok == false` on the receive) from a legitimate `ctx.Err() != nil` cancellation, and returns a distinct, registry-sourced error for the former rather than `nil`. Check: `grep -n "func.*Run" internal/engine/stub/engine.go` shows the two paths returning different values, and a passing test closes the `Commands()` channel out from under a running `Run` (without cancelling `ctx`) and asserts a non-nil, specific error is returned — not the same `nil` a clean quit would produce.
- **AC-2.** `cmd/metropolis/boot.go` observes `engine.Run(ctx)`'s return value instead of discarding it (`_ = engine.Run(ctx)` becomes `if err := engine.Run(ctx); err != nil { ... }`), and on the new premature-closure error, surfaces it (log + non-zero-exit-relevant signal, matching however `boot.go` already surfaces other startup/shutdown failures — Tester confirms consistency with the existing pattern rather than a bespoke new one). Check: `grep -n "engine.Run(ctx)" cmd/metropolis/boot.go` shows the return value used, not discarded.

### Determinism & safety

- **AC-3 (Pattern #1 — deterministic, not probable, per the process rule).** The regression test drives the premature-closure scenario to completion deterministically (close the channel, then wait on `Run`'s return via a channel/WaitGroup — not a timing-based race for who closes first), consistent with `dev-team-process.md`'s "concurrency tests must be deterministic, not probable" rule.
- **AC-4.** The fix does not change behaviour for the two paths that currently work correctly: a clean `ctx` cancellation still returns cleanly (whatever `Run` currently returns for that case, unchanged), and the send methods' existing "already guarded, keep returning false without panicking" behaviour (per the finding's own note) is unaffected — a passing regression test for the clean-cancellation path continues to pass unchanged.

## Out of scope

- Any change to what currently makes the race window unreachable in `boot.go`'s `shutdown()` ordering — this fix is defence-in-depth against a *future* wiring change (a copied transport, an early `Close()`) reopening it, not a claim that today's ordering is itself wrong.

## Escalations

- None — the finding's own "Definition of done" maps directly onto AC-1/AC-2/AC-3.
