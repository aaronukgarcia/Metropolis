## 1. Why this item exists, and what it does NOT touch

Aaron's brief: "provide congestion-reduction options modelled on Gibraltar... and Singapore." `policy_levers.json` (inc0) already documents five levers with sourced elasticity ranges; this increment is the FIRST to wire any of them to a measured effect through the tables, per the epic's own inc8 description. **Scoping decision (see §5 for Aaron):** `data/policies.json` is a *different, already-designed* engine-side surface — `engine.policies`'s multiplicative-combination library keyed by `citywide/district/road` scope with conflict resolution (`errors.json:4402-4451`) — that module does not exist in the webconsole yet and building it is out of proportion for one increment. The brief's own line ("hooks into the existing webconsole policies surface... extend, never duplicate") points at the SIMPLER surface that already ships: `PolicyId`/`POLICIES`/`SimState.policies`, the same boolean-toggle idiom `transitSubsidy`/`austerity` already use. inc8 extends THAT surface. `data/policies.json` is not read or written this increment.

Four of the five `policy_levers.json` entries carry a number this increment can apply without inventing a new demand model or a new zone concept: `coe_ownership_quota` and `erp_road_pricing` give citywide mode-share elasticities; `integrated_transit_singapore_style` gives a transit mode-share gain; `bus_priority_lanes` gives a journey-time figure the brief itself redirects to a CAPACITY effect ("never a second demand model"). `park_and_ride`'s `centreBoundCarTripReductionPercent` is explicitly a CENTRE-BOUND (zonal) effect and the webconsole has no "city centre" concept yet — shipping it as a citywide effect would misrepresent the data's own scope note, so it is OUT OF SCOPE this increment (§5, §6). `gibraltar_land_constraint_analogue` is explicitly structural (parking scarcity + a periodic closure event, not a tunable rate) — its own `expectedEffect` says so — and belongs with inc6's parking work, not a boolean policy lever (§6).

## 2. The design in one paragraph

**One adjustment point, before inc2's aggregation (GR#3).** A new memoised export, `policyModeShareAdjustmentOf(s): Record<string, number>` in `trafficDemand.ts`, starts from `modeShareOf(ladderPointOf(s))` (inc2's existing per-rung split, untouched) and applies each ACTIVE policy's effect as one multiplicative or additive move on specific mode keys, using the **midpoint** of `policy_levers.json`'s `expectedEffect` range (a range is a data-sourced confidence interval; the midpoint is the single deterministic number GR#21 needs — never re-rolled, never the range's own two endpoints averaged with anything else). Order is fixed and documented (ownershipQuota, then roadPricing, then integratedTicketing) so composing two active policies is deterministic, not order-of-toggle dependent. After every move the result is renormalised so the mode-share vector sums to exactly 1 (conservation of trips — a policy shifts WHERE people go, never how many trips exist). `forecastLineUsage` (inc2) is the ONE call site changed: it reads `policyModeShareAdjustmentOf(s)` in place of the raw `shares` object; `demandForecastOf`'s per-tile trip generation is untouched (mode split is a city-wide overlay on top of trip generation, per inc2's own D1 boundary). **`busPriority` is a capacity effect, not a demand-share effect (§1):** `forecastLineUsage`'s road branch reads a data-sourced per-tile capacity delta — `link_capacity.json`'s `avenue_2_plus_2` minus `bus_lane_variant` `capacityPcuPerLanePerHour` — multiplied by the count of currently-online `avenue_2_plus_2`-tier road tiles (spec-counted from `s.buildings`, never hand-typed), moved OUT of `totalDrivableCap` (road capacity) and INTO a new `bus` capacity figure `forecastLineUsage` already tracks as a line class. **Money (GR#15, absolute conservation):** `roadPricing` books ONE new inflow line inside `computeFlows` — `taxation.json`'s `peakGbpPerCrossing` (converted to micro-pounds, the existing convention) times the POST-adjustment car person-trips for the tick (the trips that still cross, having already been reduced by the demand-share move — charging a suppressed trip twice would double-count the policy's own effect). `ownershipQuota` books a second inflow — `certificateOfEntitlement.illustrativePriceGBP` times a data-sourced new-registration proxy, `population * quotaGrowthRatePerYear / 365` (ASM-flagged tick-to-day mapping, §4). `busPriority` and `integratedTicketing` are fiscally neutral this increment (capacity reallocation and mode-share redistribution move trips, not money — matches `transitSubsidy`'s own precedent of a SEPARATE, later-landed fiscal effect).

## 3. Acceptance Criteria

**AC-1 — surface extension: 4 new `PolicyId`s, `POLICIES` entries, `SimState.policies` keys, old-save default false.**
`types.ts:242` gains `'ownershipQuota' | 'roadPricing' | 'busPriority' | 'integratedTicketing'`. `data.ts` `POLICIES` gains four `PolicyDef` entries (label/description mirroring the existing four's plain-language style, description states the DIRECTIONAL effect only, no bare formula per the `transitSubsidy` precedent at `data.ts:6859-6866`). `engine.ts:716`'s default policies object and the save/load sanitizer both gain the four keys defaulting `false`.
**Check:** load a serialised save captured BEFORE this increment (missing the four keys) through the existing sanitize path; assert all four read `false`, never `undefined`.
**False-pass note:** a fixture that constructs `SimState` fresh (never round-tripping an old save) cannot catch a missing-key path — the Tester must load an actual pre-inc8-shaped JSON blob.
**Mutant:** default a missing key to `true` instead of `false` — reds the old-save fixture (a save made before ERP existed silently starts charging ERP).

**AC-2 — `policyModeShareAdjustmentOf(s)`: fixed-order composition, renormalised to exactly 1.**
Order: ownershipQuota (car share **−10 percentage points**, the `[5,15]` midpoint, moved onto `bus`+`heavy_rail`+`hs_rail` proportional to their pre-move share) → roadPricing (car share **×(1−0.15)**, the `[10,20]` midpoint, same proportional redistribution) → integratedTicketing (**+15 percentage points**, the `[10,20]` midpoint, taken proportionally from `car`+`motorbike`+`taxi`). After all active moves, divide every mode's share by the vector's own sum.
**Check:** a fixture with `car=0.5, bus=0.2, heavy_rail=0.2, hs_rail=0.1` and only `roadPricing` on: car becomes `0.5*0.85=0.425` before renormalisation, the sum is already 1 (mass was redistributed not removed) — assert the exact post-adjustment vector to 1e-9, AND assert `Object.values(v).reduce(sum) === 1` to 1e-9 with all four policies on in combination (order matters — assert the SAME fixture with policies toggled on in reverse dispatch order still yields the identical vector, proving composition order is fixed, not toggle-order dependent).
**False-pass note:** a test that only checks "car share decreased" cannot catch a renormalisation bug that also silently shrinks the total (fewer total trips) — must assert the sum.
**Mutant:** skip the final renormalisation divide — reds the sum-equals-1 assertion (floating additive/multiplicative moves alone do not guarantee it once more than one policy is active).

**AC-3 — `forecastLineUsage` reads the adjusted shares; `demandForecastOf` is untouched.**
`trafficDemand.ts`'s `forecastLineUsage` body replaces its `const shares = modeShareOf(point)` line with `policyModeShareAdjustmentOf(s)`. No other line in the function changes.
**Check:** with every policy off, `policyModeShareAdjustmentOf(s)` returns byte-identical values to `modeShareOf(ladderPointOf(s))` (the identity case) — `forecastLineUsage`'s output is UNCHANGED from its pre-inc8 committed values on the existing inc2 golden fixture.
**False-pass note:** a fixture that only exercises the "policy on" path cannot prove the off-path is a true no-op regression guard against the golden fixture from inc2's own committed tests.
**Mutant:** apply the ownershipQuota/roadPricing/integratedTicketing moves unconditionally (ignore the policy boolean) — reds the golden-fixture no-op check (every existing inc2 test with policies off now sees a shifted mode split).

**AC-4 — `busPriority` capacity reallocation, sourced from existing `link_capacity.json` rows, never a demand-share move.**
When `s.policies.busPriority`, `forecastLineUsage`'s road branch computes `delta = (avenueCapPerLane - busLaneCapPerLane) * onlineAvenueTileCount` and subtracts it from `totalDrivableCap`, adding it to the `bus` line class's capacity figure (both read via the existing `linkCapacityRow`-style lookup, never a hand-typed number).
**Check:** a fixture with 10 online `avenue_2_plus_2` tiles and `busPriority` on: assert `totalDrivableCap` equals the off-fixture's value minus exactly `10 * (avenueCap - busLaneCap)`, and `bus` capacity gains exactly that amount (money and mode SHARE both untouched — only the capacity split moves).
**False-pass note:** checking only that `bus` capacity increased cannot catch a double-count where road capacity was NOT correspondingly reduced (a free capacity increase, breaking the "reallocation" framing) — assert both sides of the transfer.
**Mutant:** add the delta to `bus` without subtracting it from `totalDrivableCap` — reds the road-side assertion (free capacity created from nothing).

**AC-5 — `roadPricing` books an inflow in `computeFlows`, sized off post-adjustment trips, never pre-adjustment.**
New `computeFlows` line, gated `s.policies.roadPricing`: `inflow = peakGbpPerCrossing_microPounds * carPersonTripsAfterAdjustment` where `carPersonTripsAfterAdjustment` reads `policyModeShareAdjustmentOf(s)['car'] * totalPersonTrips` from `demandForecastOf`'s own tile sum (the SAME total `forecastLineUsage` already computes — read, not re-derived, GR#3).
**Check:** a fixture with a known `totalPersonTrips` and `roadPricing` on: assert the new inflow's `.value` equals `peakGbpPerCrossing * adjustedCarShare * totalPersonTrips` to the micro-pound, and that toggling `roadPricing` off removes exactly that line from `outflows`/`inflows` with every OTHER flow item byte-identical (conservation — the policy adds one line, touches nothing else).
**False-pass note:** sizing the check off the file's own PRE-adjustment car share would pass even if the code double-charges (charges the trips the policy itself already suppressed) — must use the adjusted figure in the assertion, not the raw ladder share.
**Mutant:** compute the inflow from the PRE-adjustment `modeShareOf(point)['car']` instead of the post-adjustment figure — reds the exact-value check (over-charges by the suppressed fraction).

**AC-6 — `ownershipQuota` books a second, independent inflow; money conservation holds with both policies on.**
`inflow = illustrativePriceGBP_microPounds * round(s.population * quotaGrowthRatePerYear / 365)` (ASM-flagged day-tick mapping, §4), gated `s.policies.ownershipQuota`, added inside `computeFlows` alongside AC-5's line (both may be active simultaneously — two independent lines, not a combined one).
**Check:** with BOTH `roadPricing` and `ownershipQuota` on, assert `inflows` contains exactly two NEW lines versus the all-off baseline, each matching its own formula, and every pre-existing flow item unchanged.
**False-pass note:** a fixture that enables only one policy at a time cannot catch the two lines being accidentally merged/summed into one label, which would silently break per-policy toggling off later.
**Mutant:** place the `ownershipQuota` inflow computation outside `computeFlows` (e.g. added directly to `s.funds` in the reducer's `advance` step) — reds a test asserting the inflow appears in `lastFlows.inflows` (the existing UI/audit trail reads flows from THAT array only, `financeTabs.tsx` income sum).

**AC-7 — `parkAndRide` is NOT shipped this increment; toggling an unknown `PolicyId` is unreachable, not silently ignored.**
No `parkAndRide` entry is added to `PolicyId`/`POLICIES`/`policies` this increment (§1, §5). `POLICIES.map` in `financeTabs.tsx` is unchanged as a component — it renders whatever `POLICIES` contains, so shipping fewer than five is a data-only decision with zero UI risk.
**Check:** `PolicyId` type-checks (`tsc`) to exactly the 8-member union (4 existing + 4 new); a fixture attempting `dispatch({type:'policy', id:'parkAndRide'})` fails to compile (type-level proof, not a runtime test) — grep confirms zero references to `parkAndRide` as a `PolicyId` anywhere under `webconsole/src`.
**False-pass note:** a runtime-only test suite would pass even if `parkAndRide` were accidentally half-wired (e.g. present in `policy_levers.json` reads but missing from the type) — the type-level check is the one that catches drift.
**Mutant:** add `'parkAndRide'` to the `PolicyId` union without any effect code — reds nothing at compile time (this is why the check above also greps for a wired effect site, not just the type).

## 4. Assumptions (log via `claude-bow.js add assumption`)

- **ASM-A** "Policy lever elasticity applied at the range midpoint, not either bound" — `policy_levers.json` gives ranges (e.g. `[5,15]`); this doc picks the midpoint as the single deterministic figure. Aaron's balance pass may prefer a different point in the range.
- **ASM-B** "Ownership-quota new-registration proxy is `population * quotaGrowthRatePerYear / 365`, not a real fleet model" — the webconsole has no vehicle-registration or fleet-size state; this is a population-scaled proxy standing in until one exists, and assumes one tick ≈ one day (unverified against the sim's actual tick-to-calendar-day ratio — flag to Aaron, §5).
- **ASM-C** "`busPriority`'s capacity delta is charged once per online `avenue_2_plus_2` tile, not scoped to a chosen corridor" — the real-world mechanism (a specific road repainted with bus lanes) is corridor-scoped; this increment applies it CITY-WIDE across every avenue tile as a first approximation, matching the boolean (not per-road) policy shape the existing `PolicyId` surface offers.
- **ASM-D** "`park_and_ride` and `gibraltar_land_constraint_analogue` are out of scope this increment because both need a spatial concept (a 'centre' zone; a runway-crossing closure event) the webconsole does not have yet" — not a data gap, a missing zone/event primitive.

## 5. Decisions for Aaron

1. **Ship all 4 or stage 2 first?** This doc specs `ownershipQuota`, `roadPricing`, `busPriority`, `integratedTicketing` together (they share one mechanism — AC-2/AC-4 — so the marginal cost of the extra two is small). If Aaron prefers the narrower rollout named in the brief, **recommend `roadPricing` + `busPriority` first** (cleanest, least-composed data: one relative elasticity, one already-existing capacity number) with `ownershipQuota`/`integratedTicketing` following once AC-2's composition order has a round verdict.
2. **Is ERP zoned or city-wide this increment?** Recommend **city-wide flat**, matching AC-5 — Singapore's real ERP is gantry/zone-specific, but the webconsole has no zone concept (same gap as `park_and_ride`, ASM-D); zoning is a later increment once a "district" concept exists (which would also unlock `park_and_ride`).
3. **Tick-to-day mapping for `ownershipQuota` (ASM-B):** confirm whether one sim tick should be treated as one day for the `/365` figure, or whether a different existing tick-rate constant should be read instead.
4. **`busPriority` scope (ASM-C):** confirm a city-wide per-avenue-tile capacity charge is acceptable as a first approximation, or whether it should wait for a per-road policy mechanism (closer to the actual `data/policies.json` `road` scope kind already designed for the OTHER surface, §1) — that would argue for building THAT surface sooner than currently planned.
