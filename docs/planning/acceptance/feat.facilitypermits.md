## North-star vetting (dev-team-process.md v1.12 BA mandate)

This item is an **economy/gate feature** and it sharpens the north-star directly — it is not necessary infrastructure answering none of the questions (unlike `feat.resourcedeposits.md`'s shuffle, which explicitly is):

- **Q1 (conflicting demand, sharpened directly).** A permit is a claim on a finite currency — XP/Development Points, milestone-allowance, or money — that could have gone to housing, transit, wellbeing, or the next district. Every "large" facility now competes for a shared, scarce gate currency, which is exactly §7's "land allocation scales with facility size" made into a felt trade-off rather than a free placement.
- **Q2 (felt no, directly).** Choosing to permit an airport by spending Development Points is choosing NOT to spend those points in a progression tree; choosing the purchase route is money not spent elsewhere on the pie. Each of the three routes has a felt no, and the player selects which currency to pay.
- **Q3 (consequence sticks, directly).** The permit is a persistent record, not a transient check (AC-8) — land allocated under it is committed, and the same record is what FEAT-054 hangs the day-one "put back to nature" liability off, so a permit is a long-lived obligation, not a consumed-and-forgotten token.
- **Q4 (snowball, directly).** "All facilities can grow and expand" (§7) re-engages the gate at each size threshold (AC-9) — a facility that was cheap to permit at small scale costs again at the next size tier, so growth compounds the permit bill exactly as §7's "increasing run costs" intends.
- **Q5 (long bet, partially).** The purchase route lets a player stretch for a large facility's permit early, before the XP/milestone route would naturally open it — buying the permit now against land they expect to be scarce later. The long bet is real but weaker than the extraction ladder's; this file states that honestly rather than overclaiming.

## User stories

- **US-1.** As the player placing a facility, I need a size threshold below which building is permit-free and above which a permit is required, so "land allocation scales with facility size" (§7) is a real, data-sourced cut line, not an arbitrary or hidden rule.
- **US-2.** As the player deciding how to pay for a large facility's permit, I need experience points, milestones, and purchase to be three alternative routes to the SAME gate, so I can spend whichever of progression / achievement / money I have the most of — "all currencies for the same gate" (§7).
- **US-3.** As the milestone/unlock economy (`engine.unlocks`, MOD-032), I need the permit gate's experience-points and milestone routes to read MY XP/Development-Point balance and MY milestone tier, not a second, permit-owned copy of the same state, so there is one source of truth for "how many points / what tier" (§22, GR#3).
- **US-4.** As `engine.finance` (MOD-022), I need the purchase route to post a real money movement through MY double-entry ledger, not a permit-owned money store, so a purchased permit is on the books and auditable like every other spend (§7, US-3).
- **US-5.** As the decommissioning feature (FEAT-054, later), I need a permit to be a persistent, queryable record attached to a facility — not a one-shot boolean that evaporates after the check — so I can hang the "every PERMITTED facility carries a put-back-to-nature liability" obligation off something that actually persists (§7).
- **US-6.** As the player expanding a facility, I need growth past the next size threshold to re-engage the permit gate, so expansion is not a one-time permit that a growing facility then outgrows for free (§7, "all facilities can grow and expand").
- **US-7.** As `engine.build`'s command-acceptance path (MOD-026), I need a permit-gate check I can call at zone/build-command time for a facility whose size exceeds the threshold, so a large facility cannot be placed without a permit exactly the way an unowned cell cannot be zoned (engine.build.md AC-3's enforcement-point pattern).

## Scope

The permit gate itself: a data-sourced "large facility" size threshold; a `RequiresPermit`/`HasPermit` check layered on top of (not merged into) the existing `data/buildings.json` `unlock` gate; three acquisition routes (experience points via `engine.unlocks`, milestone via `engine.unlocks`, purchase via `engine.finance`) all resolving the same gate; a persistent, queryable permit record (the FEAT-054 seam); and expansion re-engaging the gate at data-sourced size thresholds. Does **not** include: the decommissioning liability itself (FEAT-054 — this file only produces the permit record it hangs off); the building-type unlock gate (`data.catalogue`/`engine.unlocks` — this file only checks it, never mutates or redefines it); the land-price formula or purchase transaction mechanics (`engine.finance` AC-4/AC-3); the build queue/zone mechanics (`engine.build`); the §8 expert-workforce gate for mega-facilities (a separate "cannot buy this with money alone" gate, later sprint — the permit is only the land-allocation half of §8's "permit-gated, expert-workforce-gated").

## Acceptance criteria

### Functional — the permit gate and its place in the build/unlock stack

- **AC-1 (GR#20; shared-package registered call surface — inbound contract currently unpopulated).** A permit-gate surface exists on the shared `internal/engine/build` package (e.g. `RequiresPermit(facilityClass, size) bool` and `HasPermit(facilityID) (Permit, bool, error)`, or equivalent), distinct from `engine.build.md` AC-1's `BuildAPI` zone/queue surface and consuming `BuildAPI` and `FinanceAPI` via direct calls rather than reimplementing either. code.json's `feat.facilitypermits` entry has no registered inbound contract of its own (`consumers: []`) because it shares `engine.build`'s package, mirroring `feat.resourcedeposits.md` AC-1's convention. Check: `go doc ./internal/engine/build` shows a permit-query function distinct from `BuildAPI`'s command surface; `internal/engine/build/doc.go` (or `permit.go`'s package doc) notes the shared-package, no-separate-inbound-contract arrangement explicitly (`grep -n "feat.facilitypermits" internal/engine/build/doc.go`).
- **AC-2 (permit gate ≠ unlock gate — the BOW-mandated reconciliation with `data/buildings.json`).** The permit gate is a **size/land-allocation gate**, layered on top of the existing `data/buildings.json` `unlock`/`UnlockGate` gate (that field's `milestone`/`developmentPoint`/`funds`/`achievement`/`university`/`research`/`policy`/`conditional` per `docs/design/buildings-schema.md`), not a replacement for it and not a new boolean added to that field. The distinction is enforced, not merely documented: a "large" facility must be **both** unlocked (type gate — `engine.unlocks`/`data.catalogue`) **and** permitted (size gate — this feature) before it can be built at that size; a facility that is permitted but whose type is still unlock-gated, or unlocked but size-unpermitted, is rejected at build-command acceptance. This file does not restate the unlock field's own semantics and does not mutate `data/buildings.json`. Check: `grep -n "unlock\|UnlockGate" internal/engine/build/permit*.go` (excluding `_test.go`) shows the permit code READING the existing gate fields as an input, never writing them; a passing test constructs a fixture facility that is size-permitted but type-locked and asserts build-command acceptance is rejected, and the converse (type-unlocked but size-unpermitted) also rejected (`grep -rn "func Test.*[Pp]ermitVsUnlock\|func Test.*[Bb]othGates" internal/engine/build/*_test.go`). **False-pass risk:** a build that folds the permit into the unlock field (e.g. a new `unlock.permit` boolean) would pass a shallow "there is a permit check" read while erasing the size dimension §7 is about — the check requires the two gates to be independently evaluable, not one merged flag.
- **AC-3 (§7 "land allocation scales with facility size" — the size threshold, data-sourced).** A facility requires a permit if and only if its size (land footprint, capacity tier, or equivalent documented size model) exceeds a per-facility-class threshold sourced from the GR#15 data file (AC-10); a facility at or below its class threshold builds with no permit check at all. The threshold itself is never a hardcoded Go literal. Check: `go doc ./internal/engine/build` shows a size model (e.g. a `FacilitySize`/`SizeTier` type or a documented footprint field) and `RequiresPermit`'s answer is derived from the loaded data file; a passing test loads two otherwise-identical facilities differing only in size (one below, one above the data-file threshold for their class) and asserts the below-threshold one needs no permit while the above-threshold one does (`grep -rn "func Test.*[Tt]hreshold\|func Test.*[Rr]equiresPermit" internal/engine/build/*_test.go`). **False-pass risk:** a gate keyed only on facility CLASS (all airports need a permit, no size dimension) would pass a shallow "permits exist" check while failing §7's explicit "scales with facility size" — the check requires the size variable, not just the class, to flip the gate.
- **AC-4 (§7 "three routes, so progression, achievement, and money are all currencies for the same gate").** The permit gate resolves true if and only if at least one of the three routes — experience points, milestone, or purchase — is satisfied, and the three routes are alternative currencies for the SAME gate, each independently evaluable via its own documented condition. There is no fourth hidden route and no route is silently required in combination with another. Check: `go doc ./internal/engine/build` shows the gate's three-route structure (e.g. a `PermitRoute` enum with three cases, or three documented predicate functions); a passing test asserts the gate is true under each route satisfied in isolation and false under all three unsatisfied, covering all four states explicitly (`grep -rn "func Test.*[Tt]hreeRoutes\|func Test.*[Pp]ermitRoute" internal/engine/build/*_test.go`). **False-pass risk:** a gate that returns true whenever ANY currency above zero is present without actually distinguishing the routes would pass a "permits can be granted" check while silently allowing a facility to be permitted via a route the player never consciously chose — the check requires each route's condition to be asserted independently, not just "some currency exists".
- **AC-5 (§7 purchase route → `engine.finance`; the registered edge).** The purchase route debits money through `FinanceAPI`'s double-entry ledger (the registered `feat.facilitypermits → engine.finance` edge, `engine.finance.md` AC-1/AC-3's posting surface) — there is no permit-owned money store or parallel balance. Granting a permit by purchase with sufficient funds posts a real ledger debit and produces the permit record (AC-8); with insufficient funds it is rejected (AC-11) and no money moves. Check: `grep -n "finance\.\|FinanceAPI" internal/engine/build/permit*.go` (excluding `_test.go`) finds the purchase route calling the registered finance edge; a passing test grants a purchased permit and asserts a balanced ledger entry exists for the purchase amount, and a second assertion drives an insufficient-funds purchase and asserts the ledger balance is unchanged (`grep -rn "func Test.*[Pp]urchasePermit\|func Test.*[Ii]nsufficientFunds" internal/engine/build/*_test.go`).
- **AC-6 (§22 experience-points route → `engine.unlocks`; OPEN DEPENDENCY — the edge is NOT registered in code.json).** The experience-points route reads the XP / Development-Point balance from `engine.unlocks` (MOD-032) via that module's gate/balance query surface, and does NOT create a fourth, permit-owned points currency. **This AC is blocked on a code.json gap:** `feat.facilitypermits`'s outbound `calls` list contains only `engine.build` and `engine.finance` — there is no registered `feat.facilitypermits → engine.unlocks` edge, and `engine.unlocks`'s inbound `consumers` list (`ui.screen.build` only) does not carry this feature's outbound GUID. Until that edge is registered (master-plan amendment → regenerate code.json), the experience-points route cannot be built against a real contract, and this AC must be treated as an open dependency, not an immediately-buildable check. Check (once the edge exists): `node -e "const m=require('./code.json').modules.find(x=>x.key==='feat.facilitypermits'); process.exit(m.outbound.calls.some(c=>c.key==='engine.unlocks')?0:1)"` exits 0; `grep -n "unlocks\.\|UnlocksAPI" internal/engine/build/permit*.go` shows the route consuming the unlock economy rather than a permit-local points map; a passing test grants a permit via the points route and asserts the XP/DP balance read is the SAME state `engine.unlocks` owns (not a shadow copy) (`grep -rn "func Test.*[Xx]pRoute\|func Test.*[Dd]pPermit" internal/engine/build/*_test.go`).
- **AC-7 (§4/§22 milestone route → `engine.unlocks`; same OPEN DEPENDENCY as AC-6).** The milestone route is satisfied by the milestone-tier / expansion-permit-allowance state `engine.unlocks` (MOD-032) owns — §4's "each milestone grants an expansion-permit allowance" generalised by §7 to "permits for any large facility" — and is read from `engine.unlocks`, not a permit-local copy of the tier. It shares AC-6's code.json edge gap and is subject to the same open-dependency treatment. Check (once the edge exists): `grep -n "unlocks\.\|UnlocksAPI" internal/engine/build/permit*.go` shows the milestone route reading the shared milestone state; a passing test drives a synthetic city below and above the data-file milestone threshold for a permit and asserts the route flips accordingly (`grep -rn "func Test.*[Mm]ilestoneRoute\|func Test.*[Mm]ilestonePermit" internal/engine/build/*_test.go`).
- **AC-8 (§7/§8 persistent permit record — the FEAT-054 seam).** Granting a permit produces a persistent, queryable `Permit` record attached to the facility (facility ID, facility class, size tier, route used, grant tick/month), not a transient boolean evaluated and discarded. The record survives a save/load round-trip and is retrievable by facility ID; this is the record FEAT-054 hangs its "every PERMITTED facility carries a put-back-to-nature liability" obligation off. Check: `go doc ./internal/engine/build Permit` (or equivalent) shows a record type with the fields above; a passing test grants a permit, round-trips the package state through `int.serializer` (or the package's own save/restore path), and asserts the permit is still queryable by facility ID afterward (`grep -rn "func Test.*[Pp]ermitPersist\|func Test.*[Pp]ermitRecord" internal/engine/build/*_test.go`). **False-pass risk:** a build that returns `true` from `HasPermit` by re-checking live route state each call (no stored record) would pass a "can I query permit status" check while giving FEAT-054 nothing to attach liability to — the check requires the stored record to round-trip, not just the check to re-derive.
- **AC-9 (§7 "all facilities can grow and expand" — expansion re-engages the gate).** Expanding a facility past its next size threshold re-engages the permit gate: the expansion is a new gate evaluation at the new size, and growth into a size tier the facility has no permit for is rejected at expansion-command acceptance. The expansion thresholds are the SAME data-sourced size thresholds as AC-3, not a separate hardcoded scale. Check: a passing test permits a facility at its current size, then submits an expansion command that crosses the next size threshold, and asserts the expansion requires (and, absent a permit for the new size, is rejected with) the gate re-evaluated at the new size — a second assertion confirms an expansion that stays within the already-permitted size tier succeeds without a new permit (`grep -rn "func Test.*[Ee]xpand.*[Pp]ermit\|func Test.*[Rr]eengageGate" internal/engine/build/*_test.go`). **False-pass risk:** a build that checks the permit once at initial build and never again on expansion would pass a shallow "facilities are permit-gated" read while letting a facility grow to arbitrary size for free — the check requires the re-evaluation on the expansion path specifically.

### Functional — GR#15 balance data

- **AC-10 (GR#15 — every permit parameter lives in a data file, not code constants).** Per-facility-class size thresholds (AC-3), the route conditions and any per-route numeric costs (experience/Development-Point amount, milestone tier required, purchase price) (AC-4/AC-5/AC-6/AC-7), and the expansion thresholds (AC-9) are ALL sourced from a data file (e.g. `data/facility_permits.json`, following the `data/*.json` convention already used by `deposits.json`/`extraction.json` proposals and `errors.json`/`modes.json`), none hardcoded as Go numeric literals, and each numeric entry carries a non-empty placeholder/pending-tuning disclosure field per the balance-number regime (`data/market.json`'s "pending M2 Batch tuning" convention, `feat.resourcedeposits.md` AC-6's and `feat.extraction.md` AC-12's precedent). Check: `grep -rn "0\.[0-9]\+\|[0-9]\{2,\}" internal/engine/build/permit*.go` (excluding `_test.go` and array indices/enum ordinals) shows no bare balance-shaped numeric literals; `go doc ./internal/engine/build` or `internal/engine/build/doc.go` names the data file path explicitly; a passing test edits the data file's threshold for one facility class between two test runs with identical inputs and asserts `RequiresPermit`'s answer for that class changes (proving the parameter is actually read, not merely present in an unloaded file) (`grep -rn "func Test.*[Dd]ataDriven.*[Pp]ermit\|func Test.*[Pp]ermitParams" internal/engine/build/*_test.go`).

### Error handling

- **AC-11 (GR#7 — rejection is loud and side-effect-free).** A permit check or grant against an unknown facility class, an invalid/out-of-taxonomy route, insufficient route currency (funds for the purchase route, points for the experience route), or a build/expansion command that requires a permit the facility lacks, produces a registry-sourced error (new `MET-E`-range code) and produces **no** partial state: no permit record created, no land allocated, no currency debited, no expansion applied. Check: `grep -n "MET-" internal/engine/build/permit*.go` finds a registry code reference on each rejection path; passing test coverage asserts the returned error's registry code matches AND that the affected facility/ledger/points state is byte-identical before and after each rejected attempt, not merely that a matching-named test function exists (`grep -rn "func Test.*[Pp]ermit.*[Ee]rror\|func Test.*[Pp]ermitReject" internal/engine/build/*_test.go`). **False-pass risk:** a rejection that returns an error but still writes the permit record (or debits money) as a side effect would pass a naive "returns an error" grep while leaving the gate bypassable in practice — the check requires the negative-state-change assertion, the same shape `engine.build.md` AC-3 already mandates for its ownership gate.

Check: `grep -rn "time.Now\|time.Since" internal/engine/build/permit*.go` (excluding `_test.go`) returns no matches.
- **AC-13.** `go test ./internal/engine/build/... -race -count=1 -run Permit` passes with no data race (scoped to the permit test subset via `-run`, since the shared package also carries `engine.build.md`'s own AC-14 race suite).
