## Why this file exists, and what it is NOT (read first)

FEAT-082 is the **composition concern**, distinct from the orchestrator mechanism it wires against. `engine.core.md` (MOD-012) defines *how* a phase pipeline runs and what `RegisterPhaseHook`/`PhaseHook` guarantee; this file defines *which* real modules register, in *what order*, driven *headlessly*, and the *flip* of `cmd/metropolis` off `StubEngine`. `engine.headless.md` AC-9 (ASM-001) already anticipated this: it required that the headless contract and the live-boot contract be the same code path — this item is where that finally becomes true. **This file does not rewrite the phase-pipeline or RegisterPhaseHook contract**; it consumes it. The developer wires against the real, landed API (`internal/engine/core/phase.go`, `engine.go`), the same way `engine.invariant` already does.

The built-surface audit behind this item found the gap precisely: every runnable path (`cmd/metropolis` interactive, `-headless`, `harness/replay`, `harness/synth`) performs ZERO `RegisterPhaseHook` calls; the only production caller is `engine.invariant.Wire`, which nothing invokes; `cmd/metropolis` renders `harness.stub.StubEngine` end to end (its own `main.go` says so); and `harness/synth` + `harness/replay` carry CI-enforced tests ASSERTING no `RegisterPhaseHook` exists in their paths. The bricks are real (world/citizens/market/invariant all have real logic); the car is not assembled. This item is the assembly.

## Package path (design reasoning — open question for the lead)

**Proposed: `internal/engine/compose/` — new.**

Reasoning:

1. **It is a composition root, the one place allowed to know all concrete modules.** By definition it imports `engine.core` *and* every module it wires (world, citizens, market, invariant, and the four baseline-one stubs). Nothing imports *it* except the two runnable tops: `cmd/metropolis` (interactive boot) and the headless driver. Placing it under `internal/engine/` puts it at the top of the engine dependency DAG where its imports are legal and its "knows everyone" privilege is visible, rather than in `cmd/` (a process shell) or `internal/harness/` (a harness concern).
2. **ASM-001 demands ONE wiring path shared by live and headless.** If the wiring lived in `cmd/metropolis`, `internal/harness/headless` could not reuse it without an awkward `cmd` → harness → cmd inversion, and the headless driver would need its own parallel copy — exactly the two-implants-that-happen-to-agree failure `engine.headless.md` AC-9 forbids. A shared `internal/engine/compose/` is importable by both.
3. **Not `internal/engine/wire`.** `engine.invariant` already owns a `Wire` symbol with a narrower meaning ("wire the invariant hook"). Naming a package `wire` would invite confusion with it; `compose` states the concern plainly.
4. **Reuse-first (GR#3 / dev-team-process v1.8 rule 1):** it does NOT reimplement the phase pipeline, the invariant hook, or the registry — it composes the existing `core.Engine`, the existing `invariant.WireDaily`, the existing `world.WorldAPI`/`citizens.NewCitizensAPI`/`market.MarketAPI`, and four new STUB hooks. The only genuinely new mechanism is the ordering/registration discipline and the missing-module failure path.

**Open question for the lead:** whether the headless driver (`internal/harness/headless.Run`) calls `compose.Wire` directly (making every headless/perfci/synth run a real simulation — the recommended reading, since a `-headless` run with zero hooks is exactly the "walking-skeleton overhead wearing a simulation label" BUG-034 was raised to stop), or whether `compose.Wire` is invoked only by `cmd/metropolis` and the headless library gains a narrow "wire these hooks" seam. Either is acceptable **provided the registration lives in exactly one function** and both runnable paths call it; the developer records the chosen placement. Logged as ASM-885.

## Registration order (the composition contract)

The composition root registers the baseline-one module set in this fixed order, invariant last and on the daily tick:

```
world  ->  citizens  ->  market + consumption  ->  finance  ->  build  ->  attract   (monthly/phase hooks, in this registration order)
invariant                                                                    (PhaseDailyTick, every tick)
```

Each module registers against the **fixed** `core.PhaseKind`s `engine.core` already defines (`PhaseProduction`, `PhaseLogisticsSettlement`, `PhaseConsumptionShortfall`, `PhasePopulation`, `PhaseLandValueDecay`, `PhaseFinance`, `PhaseDailyTick`) — this file does NOT add, remove, or reorder phases. The registration order above is what determines intra-phase hook order where two modules share a phase, and the build-up order (world state before citizens before market, etc.). The proposed phase-kind mapping, flagged where genuinely ambiguous:

| Module | BOW | Baseline-one depth | Proposed phase(s) | Flag |
|---|---|---|---|---|
| world | MOD-017 (done) | real | production | — |
| citizens | MOD-018 | real | population | — |
| market | MOD-020 (done) | real | consumption-shortfall | — |
| consumption | MOD-021 | **stub** | consumption-shortfall (after market) | — |
| finance | MOD-022 | **stub** | finance | — |
| build | MOD-026 | **stub** | land-value-decay | **ambiguous — see Escalations** |
| attract | MOD-029 | **stub** | population (after citizens) | **ambiguous — see Escalations** |
| invariant | MOD-019 (done) | real | daily-tick (every tick) via `WireDaily` | — |

The exact phase-kind assignment for **build** and **attract** is a scheduling decision the spec does not pin (the same class of call `engine.invariant.md` AC-7 flagged as ASM-080); the developer picks and documents, the ACs below bind only the *registration order*, not those two mappings.

## User stories

- As **the player (via `cmd/metropolis`)**, I need the interactive binary to boot a real `core.Engine` wired with the real modules rather than `StubEngine`, so what I watch is the simulation, not a canned fixture.
- As **`harness.headless`/`perfci`/CI**, I need a headless run to actually drive real phase hooks, so a `-headless -months 12` run is a real simulation whose population and money move and whose invariants are checked, not a walking-skeleton timing exercise (BUG-034's whole complaint).
- As **FEAT-083 (BASELINE ONE)**, I need the must-have spine (world → citizens → market/consumption → finance → build → attract) tick-wired once, in one place, so the loop runs watchable for N months and the remaining modules go real one at a time without re-architecting the composition.
- As **the invariant checker (MOD-019)**, I need my `WireDaily` actually invoked at boot by the composition root, so "hard assert every tick" (§14) is live, not latent.
- As **a future module author**, I need the composition root to fail loudly when a required module is missing or double-registered, so a silent partial wiring (the exact SEC-003-shaped "hooks claim boot-only but nothing enforces it" habit) is structurally impossible at the assembly layer.

## Scope

One composition root that registers the real must-have modules plus four stub phase-hooks into a `core.Engine` in a fixed, deterministic order (invariant checking every tick), drives it headlessly for N simulated months producing a city whose population and money actually change with conservation invariants holding every tick, and flips `cmd/metropolis`'s interactive path from `StubEngine` to the real engine. Plus the two blocker-clearing changes: rescope the `harness/synth`+`harness/replay` "no RegisterPhaseHook" CI assertions to the stub/replay fixtures only, and flip the perf-gate exit-3 warn→hard-fail.

## Acceptance criteria

### Functional — composition root and registration order

- **AC-1 (the single wiring path — answers ASM-001).** `internal/engine/compose/` exposes exactly one entry point that registers the full baseline-one hook set against a `*core.Engine` (e.g. `compose.Wire(e *core.Engine, deps ...Deps) error`, exact signature the developer's call). Every runnable path — `cmd/metropolis` interactive boot AND the headless driver — reaches real hooks only through this one function. Check: `go doc ./internal/engine/compose` shows the entry point; `grep -rn "RegisterPhaseHook" cmd/ internal/harness/ internal/engine/ --include=*.go` (excluding `_test.go`) shows the composition root as the only caller for the real modules — `internal/engine/core` (the interface itself), `internal/engine/invariant/wire.go` (invoked BY compose, not directly by any runnable path), and `internal/engine/compose/**` are the only allowed references; a reference in `cmd/metropolis` or `internal/harness/headless` that calls `RegisterPhaseHook` directly (bypassing compose) is a FAIL — that is the "two implants that happen to agree" divergence this AC exists to kill.
- **AC-2 (deterministic registration order).** The baseline-one modules are registered in the documented order — world, citizens, market, consumption, finance, build, attract, then invariant on `PhaseDailyTick` — and that order is held in a fixed, ordered structure (a slice/sequence, never a Go map range), so registration is deterministic run-over-run (GR#21). Check: a passing test wires an engine via the composition root, then asserts the registered hook order (via an instrumented `PhaseObserver` capturing phase-entry, or by inspecting `core.Engine`'s hook slices in registration order) matches the documented order; `grep -n "range " internal/engine/compose/*.go` (excluding `_test.go`) finds no map-range over a registration map. A lazy implementation that registers the modules but in a scrambled order (e.g. iterating a `map[string]hook`) must FAIL this test.
- **AC-3 (no double-register — weakness pattern #1).** Registering the same module's hook twice is impossible-or-loud through the composition root's public API: either the composition root is idempotent by construction (each module registered exactly once, no second call path exists) or a second `Wire` call on an already-wired engine returns a registry-sourced "already composed" error rather than silently appending a duplicate hook. Check: `go doc ./internal/engine/compose` documents the behaviour; a passing test calls the composition twice (or registers a module's hook twice via the exposed surface) and asserts either a defined error or an unchanged hook count — never a silent duplicate (`grep -rn "func Test.*[Dd]oubleRegister\|func Test.*[Aa]lreadyComposed\|func Test.*[Ii]dempoten" internal/engine/compose/*_test.go`).
- **AC-4 (a missing module fails loudly, never silently — GR#1/#7).** If any required module's construction or wiring fails (e.g. `market.LoadDefault` cannot load, a stub constructor returns an error), the composition root returns a registry-sourced error naming the failed module, and does NOT leave a partially-wired engine that still "succeeds". Additionally, the composition root carries a declared required-module list and a test proves a module silently absent from the set is detectable (registering N-1 of N required modules is a distinct failure, not a quiet success). Check: a passing test injects a failing module dependency and asserts the returned error's registry code names that module AND that no `AdvanceTicks` was run against the partial engine (`grep -rn "func Test.*[Mm]issing\|func Test.*[Ff]ail.*[Mm]odule\|func Test.*[Pp]artial" internal/engine/compose/*_test.go`); `grep -n "MET-" internal/engine/compose/*.go` finds registry-code references. A lazy implementation that `err := module.Wire(); _ = err` (swallow) must FAIL this test.
- **AC-5 (invariant wired every tick).** The composition root calls `invariant.WireDaily` (or the equivalent `invariant.Wire(e, core.PhaseDailyTick, ...)`) so the conservation suite runs once per daily tick — not once per month, not never. Check: a passing test wires an engine, drives at least one `AdvanceTicks`, and asserts the invariant hook fires once per tick (e.g. a `PhaseObserver` records `PhaseDailyTick` visited every tick with the invariant registered against it); `grep -n "WireDaily\|invariant.Wire" internal/engine/compose/*.go` matches.
- **AC-6 (sealing discipline).** The composition root wires hooks before the first `AdvanceTicks`; if it is invoked after the engine has sealed, it surfaces `core.ErrEngineSealed` (wrapped with a composition-root correlation ID and the module name, mirroring `invariant.Wire`'s `ErrWiringAfterSeal` pattern), never a silent no-op that leaves the simulation running hook-less. Check: a passing test seals an engine, then calls the composition root, and asserts the caller receives an error unwrapping to `core.ErrEngineSealed` (`grep -rn "func Test.*[Ss]ealed" internal/engine/compose/*_test.go`).

### Functional — headless drive (N months, a living city)

- **AC-7 (a headless run exercises real phase hooks).** A `metropolis -headless -seed N -months M -out <dir>` run (and the `internal/harness/headless` library it wraps) drives an engine that has the real baseline-one hooks registered — the hook count is greater than zero and includes the real must-have modules, not the walking-skeleton zero. Check: the headless run's engine construction reaches the composition root (per AC-1), and a passing test/inspection confirms the registered hook count is non-zero after wiring (`grep -rn "compose\." internal/harness/headless/*.go cmd/metropolis/*.go` finds the wiring call); a run that constructs `core.NewEngine` and advances ticks with zero registered hooks is a FAIL — that is the exact "walking-skeleton wearing a simulation label" state BUG-034 exists to forbid.
- **AC-8 (population actually changes — directional, able to fail).** After N=12 simulated months, total population (all fidelity tiers) is strictly greater than population at tick 0, given a non-zero seed population the composition root establishes. Check: a passing integration test runs `-headless -months 12` (or drives the composed engine 12 months directly), reads population at tick 0 and at month 12, and asserts `pop(month12) > pop(tick0)`. A lazy implementation whose citizens/citizen-stub hook never spawns, migrates, or births anyone must FAIL this — "the loop ran" with a flat population is precisely the failure this AC catches. No hardcoded target number; the assertion is directional over the run's own initial population.
- **AC-9 (money actually changes — directional, able to fail).** Over the same 12-month run, the tracked money figure actually moves: the money-conservation stock's cumulative tracked inflows/outflows over the run are non-zero (wages paid, tax collected, or a budget that closes — whatever the composed finance stub emits), while the total remains conserved. Check: a passing test reads the money stock's tracked movement at month 12 and asserts it is non-zero (and, per AC-10, that no conservation delta accumulated). A lazy implementation whose finance stub is a no-op emitting zero flows must FAIL this. No hardcoded pound figure; the assertion is "money moved" not "money equals £X".
- **AC-10 (conservation invariants hold every tick — the load-bearing correctness AC).** The invariant suite reports zero violations across every tick of the 12-month run — people, money, goods, and vehicle conservation all balance to zero unexplained change on every single tick, not merely "no violation at the end". Check: a passing integration test drives 12 months and asserts the tracked invariant delta is zero at every tick (the invariant hook's `ApplyEffect`/`RunSuite` records zero detected violations for all 360 daily ticks); the test fails if ANY tick reports a detected violation, including the first. A lazy implementation that runs the invariants only once at month 12 (or that silently skips the daily check) must FAIL this.
- **AC-11 (determinism carried through the composition — GR#21).** Same seed + same months + same composition produces a byte-identical `-out` snapshot across two runs, and (per `engine.core.md` AC-15) across two pool sizes. Check: a passing test runs the composed headless path twice (and, if cheap, at two `WithPoolSize` values) and asserts identical snapshot `sha256` — carrying forward `engine.core`'s guarantee, specialised to prove the composition itself introduces no nondeterminism (no map-range, no wall clock, no goroutine-scheduling dependence in any stub hook).

### Functional — the flip (cmd/metropolis interactive off StubEngine)

- **AC-12 (no StubEngine in the interactive path).** `cmd/metropolis`'s interactive boot constructs and drives a real `core.Engine` wired via the composition root, not `harness.stub.StubEngine`. Check: `grep -rn "stub\." cmd/metropolis/*.go` (excluding `_test.go`) finds no `stub.NewStubEngine`/`stub.StubEngine` construction in the live boot path (`boot.go`/`run.go`), and `grep -rn "compose\." cmd/metropolis/*.go` finds the wiring call. A build that still boots `StubEngine` behind the map is a FAIL — this is the literal "flip" this item exists to make. (`harness.stub`'s own package and its tests remain; this AC is about `cmd/metropolis`'s boot, not deleting the stub.)
- **AC-13 (interactive and headless share the SAME composition — ASM-001, the load-bearing flip AC).** The interactive boot and the headless driver reach the real simulation through the identical `compose.Wire` function and the identical `core.Engine` surface (construction via `Option`s, ticking via `RunCommandLoop`/`HandleCommand` over `protocol.Command`) — no interactive-only or headless-only wiring divergence. Check: by inspection, `cmd/metropolis`'s boot and `internal/harness/headless.Run` both call the same composition entry point and neither re-implements hook registration locally (the AC-1 grep already forbids direct `RegisterPhaseHook` outside compose). This is the criterion `engine.headless.md` AC-9 deferred; it closes that gap rather than papering over it.

### Functional — blocker clearing

- **AC-14 (blocker (a) — rescope the "no RegisterPhaseHook" CI assertions to the stub/replay fixtures, not the real composition path).** The `harness/synth` `TestPhaseHookCountAssertionStillTrue` scan and the `harness/replay` assertion no longer treat a `RegisterPhaseHook` reference in the real composition path (`internal/engine/compose/**`, and the `internal/harness/headless`/`cmd/metropolis` call sites that reach compose) as a failure. Concretely: the scan's allow-list is extended to cover the composition root and its legitimate callers, so the real wiring this item lands does NOT redden CI, while the scan continues to assert hook-freedom for the **stub/replay fixtures only** (`internal/harness/replay`'s `EnginePlayer` must still never register hooks — `harness.replay.md` AC-3b). AND `PhaseHookCountInHeadlessPath()` (`internal/harness/synth/phasehooks.go`) must no longer hand-assert a stale `0` in the same change — either (a) it is replaced by a runtime accessor read from the engine (the `core.Engine.HookCount()` / `headless.Result.PhaseHookCount` fix its own doc comment already recommends as the only thing that can close the gap for real), or (b) its value is updated to reflect reality with a recorded reason; a hardcoded `0` left lying is a FAIL because it is exactly the "stale constant wearing a live label" the file's own doc comment warns about. Check: `go test ./internal/harness/synth/... ./internal/harness/replay/... -race -count=1` stays green WITH the composition root present in the tree; `grep -n "PhaseHookCountInHeadlessPath" internal/harness/synth/*.go` shows the updated mechanism, not a bare `return 0` with no accessor or reason.
- **AC-15 (blocker (b) — flip the perf-gate exit-3 warn→hard-fail).** `.github/workflows/ci.yml`'s `perf-1m-probe` job (the real 1M merge-blocking gate) changes its exit-3 handling from "pass with a `::warning::`" to "FAIL the job": `perfci` exiting 3 (could-not-evaluate) now exits non-zero and blocks the merge, per BUG-034/ASM-352's recorded "mandatory condition of MOD-018's first real tick work landing" — real phase hooks now exist, so a gate that cannot evaluate a real cost is a hard failure, not a warning. Check: in `ci.yml`, the `perf-1m-probe` step's `if ($p.ExitCode -eq 3) { ... exit 0 }` branch is replaced so exit 3 propagates as a non-zero job outcome (e.g. `exit 3` or falling through to `exit $p.ExitCode`); the `::warning::` message, if retained, is kept only as a diagnostic on the way to the non-zero exit, never as the terminal `exit 0`. (The `perf-smoke` job's exit-3 warning is OUT of scope — it is the deliberate small-scale smoke override, not the real gate; see Out of scope.)

### Error handling

- **AC-16 (GR#7 — every composition error is registry-sourced).** Every error the composition root itself constructs (missing module, double-register, seal-after-wire, a failed dependency wrap) is raised via `errs.New`/`errs.Wrap` with a `MET-` code claimed in `data/errors.json` (the developer claims the next free `MET-E` sub-range following `README.md`'s per-module-range convention and records it in `doc.go`), never a bare `fmt.Errorf` or a swallowed `_ =`. Check: `grep -n "fmt.Errorf" internal/engine/compose/*.go` (excluding `_test.go`) returns no matches; `grep -n "MET-" internal/engine/compose/*.go` finds the claimed codes; `data/errors.json` gains the range entry in the same change (SG-5 permits it).

### Determinism & safety

- **AC-17 (GR#21 — no wall clock).** `grep -rn "time.Now\|time.Since" internal/engine/compose/*.go` (excluding `_test.go`) returns no matches, and the same holds for every stub hook the composition root wires — simulation logic is tick/phase-driven only. Check: the grep is clean across `internal/engine/compose/**` and the stub-hook files.
- **AC-18 (GR#21 — no map-range on the tick path).** No `range` over a Go map in the composition root or any stub hook's `RunShard`/`ApplyEffect` can affect committed state — stub hooks follow `engine.core`'s AC-13 discipline. Check: `grep -n "range " internal/engine/compose/*.go` (excluding `_test.go`) on tick-path files shows no map-range whose iteration order reaches simulation state; a passing determinism test (AC-11) is the falsifying backstop.
- **AC-19 (PhaseHook contract conformance for the stubs — determinism & shard-safety).** Each of the four baseline-one stubs (consumption, finance, build, attract) implements `core.PhaseHook` per the contract in `phase.go`: `RunShard` touches only shard-local scratch (no shared mutable state across shards), `ApplyEffect` runs single-goroutine at the barrier, and both are deterministic for a given shard+state. Check: each stub's package/`_test.go` carries a determinism or shard-count test (`grep -rn "func Test.*[Dd]eterminis\|func Test.*[Ss]hard" internal/engine/compose/*_test.go` finds coverage per stub), and `go test ./internal/engine/compose/... -race -count=1` passes.

## Escalations

- **For Bill — phase-kind mapping for build and attract (and, secondarily, consumption's placement).** The fixed phase set is `engine.core`'s contract; which of those phases `build` and `attract` register against is a scheduling decision the spec does not pin (the exact class `engine.invariant.md` flagged as ASM-080). The BA's proposed mapping is in the table above; the developer may pick a different fixed phase and document it in `doc.go` per AC-20, provided the registration ORDER across modules is preserved per AC-2. Flagging so the lead rules once rather than the developer guessing.
- **For Bill — the `PhaseHookCountInHeadlessPath` fix genuinely needs `internal/engine/core` (or `harness.headless`).** The synth doc comment's own "Verdict" is unambiguous: no source-level scan can prove the real hook count; the honest fix is a runtime accessor (`core.Engine.HookCount()` or `headless.Result.PhaseHookCount`). That touches `engine.core`/`harness.headless`, which are not FEAT-082's natural file ownership but are reachable in this item's scope (it already flips `harness.headless` and `cmd/metropolis`). Recommend landing the accessor in this item rather than leaving a re-scoped-but-still-stale constant; if Bill prefers, the re-scope-without-accessor is an acceptable interim and the accessor is filed as a follow-up. Logged as ASM-886.
- **For Bill — the "money actually changes" metric when finance is a stub.** AC-9 asserts "money moved" directionally, but the concrete money figure (citizen wealth + treasury + firm balances, per `engine.invariant.md` AC-4) depends on what the coarse finance stub emits. If the stub emits only a budget-closing transfer, "money moved" is real but tiny. Flagging so the Tester's integration test binds to the *actual* money flow the stub produces, not a figure the BA would have to invent. The BA has deliberately not hardcoded a pound value (GR#15 / "no invented balance numbers").
