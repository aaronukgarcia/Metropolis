## User stories

- **US-1.** As `engine.traffic`'s nested-logit mode-choice function (AC-10), I need `data/modes.json` to carry a schema-valid coefficient set for every mode's utility function and every personality-weighting term, so the coefficient is never a Go literal and mode choice is a genuine data-driven behavioural output (§19.1).
- **US-2.** As `engine.roads`' auto-naming service (AC-9/AC-10), I need `data/naming_corpus.json` to carry a Kentish place-name corpus and a class-appropriate suffix table large enough that deterministic seed+id naming does not visibly repeat across a city-scale road network, so "the city reads like a place, not a spreadsheet" (§20) is actually true, not merely asserted.
- **US-3.** As `engine.extcommute`'s off-map pool loader (AC-2/AC-5), I need `data/external_world.json` to carry a schema-valid v1 dataset for the three named pools (London, Ashford, Dover) with era-scaled capacity and wage data, so AC-2/AC-5's data-driven checks are Tester-measurable instead of blocked on an empty stub.
- **US-4.** As GR#15 and every future data editor, I need every coefficient/number in these three files to be either transcribed verbatim from the spec (traceable) or explicitly marked as a sourced-from-literature estimate or a placeholder pending balance tuning — never a bare number with no traceable origin — so a future contributor can tell the difference between "the spec said this" and "someone guessed this" at a glance.
- **US-5.** As the Tester and Destructive agent verifying this item, I need every validator to derive its expected counts/coverage from the loaded file itself (GR#15) — never a hardcoded "must have exactly N entries" — so the check keeps working correctly as the corpus/coefficient set grows in later balance passes.

## Scope

Three data files, each schema-authored (structure + plausible/placeholder initial values) but **not** final-tuned (M2 Batch territory, same carve-out `data.catalogue.md` and `engine.season.md` already use):

1. `data/modes.json` — the 12-mode §19.1 table (speed/capacity/PCU-load, spec-transcribed) plus a nested-logit schema: nest structure, per-mode generalised-cost utility coefficients, and personality-weighting coefficients, each coefficient **set** citation-tagged.
2. `data/naming_corpus.json` — the Kentish road-name place-name corpus and the class-appropriate suffix table per §20, sized to actually avoid visible repetition at city scale, consumed by `engine.roads` AC-9 (road naming) and read by AC-10's naming-registry service for the object kinds that reuse toponyms (districts).
3. `data/external_world.json` — the three off-map pools (London, Ashford, Dover) with era-scaled capacity tables, wage levels, and transport-requirement tags, consumed by `engine.extcommute` AC-2/AC-5.

## Acceptance criteria

### Schema — `data/modes.json` (engine.traffic AC-9/AC-10)

- **AC-1 (§19.1; the 12-mode table, spec-transcribed).** `data/modes.json` is valid JSON, `version: 1`, and carries exactly the 12 modes named in §19.1's table — walk, bicycle, motorbike, car, taxi, minibus, bus, tram, metro, heavy rail, ferry, air — each keyed by a stable lowercase-slug `id` (matching `engine.roads`'s `buildingIDPattern` convention: `^[a-z][a-z0-9_.-]{2,63}$`, since this ID becomes a lookup key from `engine.traffic`'s `Mode`/`ModeKind` type, weakness pattern #4). Check: a passing loader test asserts the loaded file's mode-ID set equals the 12 IDs derived from a checked-in reference list transcribed from the spec table (not a hardcoded `len(modes) != 12` literal standing in for a live count — GR#15) (`grep -rn "func Test.*[Mm]odeCount\|func Test.*[Ee]levenModes" internal/foundation/data/modes_test.go`). **What a lazy implementation looks like:** shipping 9 or 12 modes because the author miscounted the table, or naming one mode differently than `engine.traffic`'s eventual `ModeKind` enum expects, silently breaking AC-10's lookup at build time instead of at data-load time. **False-pass warning:** a test that only asserts `len(entries) == 12` passes an implementation with the wrong 12 modes (e.g. missing "ferry", duplicating "car"); the check must compare the actual ID *set*, not just its cardinality.
- **AC-2 (§19.1; per-mode base fields, spec-transcribed, not placeholder).** Every mode entry carries `speedUrbanKmh`, `capacityPerUnit` (nullable where the spec shows "—", e.g. walk/bicycle/air), `pcuLoad` (nullable where not applicable, e.g. walk/tram/metro/heavy rail/ferry/air use track/none instead of a PCU figure), and `notes`, with values matching the spec table's literal figures (e.g. car `speedUrbanKmh` range "15–48 by congestion" represented as a documented min/max pair, not a single number; bus `capacityPerUnit: 80`, `pcuLoad: 2.0`). Check: a passing loader test spot-checks at least 4 representative entries against the spec's literal numbers (car speed range, bus capacity 80, metro capacity "1,200/train, 30k/h/dir", motorbike PCU 0.4) — GR#15: these are transcribed from the spec table into the test, not invented (`grep -rn "func Test.*[Bb]aseFields\|func Test.*[Ss]pecTranscri" internal/foundation/data/modes_test.go`). **What a lazy implementation looks like:** rounding car's speed range to a single "30" or dropping metro's dual capacity figures (per-train + per-hour-per-direction) down to one number, silently discarding information `engine.traffic`'s eventual capacity model needs.
- **AC-3 (§19.1; nested-logit nest structure — schema only, see ASM-391/Escalations).** `data/modes.json` carries a `nestedLogit.nests` array: each nest has a stable `id`, a `members` list of mode IDs (every one of the 12 modes belongs to **exactly one** nest — no mode omitted, none duplicated across nests), and a `nestingParameter` (the logit dissimilarity/inclusive-value coefficient, a float strictly within `(0, 1]` per standard nested-logit constraints — `1.0` degenerates to a flat multinomial logit, which is a legal but explicitly-flagged special case). Check: a passing loader test asserts every one of the 12 mode IDs appears in exactly one nest's `members` (a partition, not merely a covering) and every `nestingParameter` is in `(0, 1]` (`grep -rn "func Test.*[Nn]estPartition\|func Test.*[Nn]estingParam" internal/foundation/data/modes_test.go`). **What a lazy implementation looks like:** putting every mode in one giant nest with `nestingParameter: 1.0` — technically schema-valid but degenerates the "nested" logit into a flat multinomial choice, silently defeating the point of AC-3 existing at all; the check cannot mechanically reject this (a single valid nest is not itself malformed), so the loader's doc comment must name this explicitly as a documented, deliberate choice if a junior makes it, not a silent default (per this file's own provenance discipline, AC-6). **False-pass warning:** the partition check alone cannot detect a *bad* (as opposed to malformed) nest tree — nest membership quality is a judgment call the Tester cannot mechanically verify; this AC only guarantees the schema is internally consistent, not that the nest tree is behaviourally sound.
- **AC-4 (§19.1; per-mode utility coefficients — generalised cost).** Every mode carries a `utility` object with `alternativeSpecificConstant`, `betaTime` (cost-of-time coefficient), `betaCost` (money coefficient), `betaComfort`, and `betaReliability` — the four generalised-cost components §19.1 names explicitly ("time + money + comfort + reliability"). Check: `go doc ./internal/foundation/data` (modes section) lists all five fields; a passing loader test asserts every one of the 12 modes has a non-null value for all five (`grep -rn "func Test.*[Uu]tilityFields\|func Test.*[Gg]eneralisedCost" internal/foundation/data/modes_test.go`). **What a lazy implementation looks like:** leaving `betaComfort`/`betaReliability` as `0.0` for every mode because they're harder to source than time/cost — a technically-present-but-inert field that makes AC-4's check pass while leaving two of the four generalised-cost components behaviourally dead; the check must additionally assert at least one mode has a nonzero comfort or reliability coefficient, not merely that the field exists.
- **AC-5 (§19.1; personality-weighting coefficients — the three named traits).** `data/modes.json` carries a `personalityWeights` block with, at minimum, a `physicality` weight applied to walk/bicycle mode utility, a `patience` weight applied to transit-mode (bus/tram/metro/heavy rail) utility, and a `wealth` weight applied to taxi/car utility — the exact three trait→mode-group mappings §19.1 names ("physicality→cycle/walk, patience→transit tolerance, wealth→taxi/car"). Check: `go doc ./internal/foundation/data` documents the three mappings; a passing loader test asserts each named trait has a nonzero weight on at least the modes §19.1 names for it (`grep -rn "func Test.*[Pp]ersonalityWeight" internal/foundation/data/modes_test.go`). **What a lazy implementation looks like:** a single flat `personalityMultiplier` applied uniformly to all modes regardless of trait or mode group — schema-different from what AC-5 requires but easy to mistake for "close enough"; the check must confirm the weight is keyed by (trait, mode-or-modegroup) pair, not a single scalar.
- **AC-6 (GR#15/FEAT-047; provenance — the coefficient-citation requirement, this item's own text).** Every coefficient **set** introduced by AC-3/AC-4/AC-5 (i.e., the nest tree as a whole, and each mode's utility block, and each personality-weight entry) carries a structured `provenance` object: `{"source": "<citation string, e.g. author/report/year>", "sourceType": "literature" | "derived-placeholder", "note": "<why this source, or why placeholder>"}` — a bare number with no `provenance` sibling is a schema violation. `sourceType: "literature"` values must name a real, checkable transport-modelling source (e.g. a discrete-choice/mode-choice modelling text or a national transport-appraisal guidance document); `sourceType: "derived-placeholder"` is legitimate only when explicitly flagged as such (matching `data/market.json`'s existing "Plausible v1 static price, pending M2 Batch tuning" convention) — never silently substituted for a real citation. Check: a passing loader test asserts every coefficient block has a non-empty `provenance.source` and a `sourceType` from the closed enum (`grep -rn "func Test.*[Pp]rovenance\|func Test.*[Cc]itation" internal/foundation/data/modes_test.go`); the loader's public `Load` path rejects a coefficient block with an empty or missing `provenance` (see AC-13). **What a lazy implementation looks like:** a `provenance.source` field that says `"transport modelling literature"` with no author, report, or year — technically non-empty, satisfying a naive non-empty-string check, but exactly the "bare numbers with no traceable origin" this AC exists to prevent. **False-pass warning:** a check that only asserts `provenance.source != ""` would pass that lazy value; the Tester must additionally spot-check that at least a sample of `source` strings look like real citations (author/report/year shape) rather than a placeholder sentence, and the Destructive agent should specifically try this exact bypass.

### Schema — `data/naming_corpus.json` (engine.roads AC-9/AC-10)

- **AC-7 (§20; corpus structure).** `data/naming_corpus.json` is valid JSON, `version: 1`, and carries a `categories.roadPlaceNames` array of distinct Kentish toponym strings and a `categories.roadSuffixes` map keyed by road class (matching `engine.roads`' 11-rung class ladder minus the two numbered classes — see AC-9 below) to a list of class-appropriate suffix words. Check: `go doc ./internal/foundation/data` (naming-corpus section) documents both top-level keys; a passing loader test asserts both are present and non-empty (`grep -rn "func Test.*[Cc]orpusStructure" internal/foundation/data/naming_corpus_test.go`).
- **AC-8 (§20; spec-cited place names present verbatim).** All 8 place names §20 names explicitly by example (Cheriton, Seabrook, Pent, Risborough, Sandgate, Downs, Alkham, Saltwood) are present in `roadPlaceNames`, spelled exactly as the spec spells them. Check: a passing loader test asserts all 8 strings are present in the loaded corpus (`grep -rn "func Test.*[Ss]pecExamples\|func Test.*[Cc]iteroPlaceNames" internal/foundation/data/naming_corpus_test.go`). **What a lazy implementation looks like:** shipping fewer than the 8 spec-named examples, or misspelling one, which would silently fail every future consumer that expects "the spec's own worked examples" to resolve.
- **AC-9 (§20; coverage floor — derived, logged as ASM-392).** `roadPlaceNames` contains **at least 40 distinct entries** (5× the 8 spec-cited examples — the multiplier is a BA judgment call, logged as **ASM-392**, chosen so the check can fail an implementation that ships only the spec's literal worked examples and calls it done, per §20's own "reads like a place, not a spreadsheet" standard, which an 8-name corpus visibly violates the moment a city has more than a handful of roads). Check: a passing loader test asserts `len(roadPlaceNames) >= 40`, with the expected floor read from a named Go constant documented as tracing to ASM-392 (not a bare magic number in the test body) (`grep -rn "func Test.*[Cc]orpusFloor\|func Test.*[Mm]inCorpusSize" internal/foundation/data/naming_corpus_test.go`). **What a lazy implementation looks like:** exactly 8 entries (the spec's own examples, nothing more) — passes AC-8, fails AC-9, and is precisely the corner-cutting shape this AC exists to catch. **False-pass warning:** a check that only asserts "at least 1 entry beyond the 8 examples" would technically satisfy "more than the spec's literal list" while still producing visible repetition at city scale; the numeric floor is load-bearing here, not decorative.
- **AC-10 (§20; suffix coverage per non-numbered road class).** Every one of `engine.roads`' 9 non-numbered class-ladder rungs (alley, gravel, residential street, two-lane, one-way pairs, avenue 2+2, bus-lane variant, tram-track variant, dual carriageway — i.e. all 11 rungs from `engine.roads.md` AC-3 except urban expressway and motorway, which use §20's M-/A- numbering scheme instead of a place-name+suffix pair) has at least one class-appropriate suffix entry in `roadSuffixes`, drawn from §20's named suffix set (Lane/Road/Street/Avenue/Way/Drive/Close) or a documented class-appropriate extension. Check: a passing loader test asserts all 9 non-numbered classes have a non-empty suffix list (`grep -rn "func Test.*[Ss]uffixCoverage" internal/foundation/data/naming_corpus_test.go`). **What a lazy implementation looks like:** one universal suffix list applied to every class regardless of appropriateness (e.g. "Motorway Close") — technically non-empty per class, but not "class-appropriate" as §20 requires; the check must confirm at least residential-tier classes and arterial-tier classes get visibly different suffix sets (e.g. "Close"/"Lane" only appear on lower-tier classes, "Avenue"/"Way" appear on higher-tier classes), not an identical list copy-pasted 9 times.
- **AC-11 (uniqueness).** No duplicate string appears in `roadPlaceNames`; within any single road class's suffix list, no duplicate suffix appears. Check: a passing loader test asserts both (`grep -rn "func Test.*[Dd]uplicate.*[Pp]laceName\|func Test.*[Dd]uplicate.*[Ss]uffix" internal/foundation/data/naming_corpus_test.go`).
- **AC-12 (§20; the numbered-scheme classes are explicitly out of the place-name+suffix shape).** `naming_corpus.json`'s schema (or its loader doc) states explicitly that urban expressway and motorway classes use the M-/A- numbering scheme (out of this file's place-name-corpus scope) rather than silently omitting them with no explanation, so a future reader does not mistake the omission for a gap. Check: `go doc ./internal/foundation/data` (or the file's own `$comment`) states this explicitly (`grep -n "numbering scheme\|M-\|A-" data/naming_corpus.json` or the loader doc).

### Schema — `data/external_world.json` (engine.extcommute AC-2/AC-5)

- **AC-13 (§21/A6; the three named pools, schema-valid v1 dataset).** `data/external_world.json` is valid JSON, `version: 1`, and carries a `profiles` array with **exactly 3** entries — `london`, `ashford`, `dover` (stable lowercase-slug IDs, matching `engine.roads`' `buildingIDPattern` convention for the same lookup-key reason) — closing the empty-stub gap ASM-274 names. Check: a passing loader test asserts the loaded file's pool-ID set equals `{london, ashford, dover}` (`grep -rn "func Test.*[Tt]hreePools\|func Test.*[Pp]oolNames" internal/foundation/data/external_world_test.go`).
- **AC-14 (§21/A6; era-scaled capacity table, non-decreasing).** Each pool carries a `capacityByEra` array of `{era: int, capacity: int}` pairs covering every era/tier the game defines up to at least tier 5 (the tier §21 names as when external-rail season tickets unlock, the point at which the second transport channel becomes available), with `capacity` **non-decreasing** as `era` increases for the same pool (A6: "London absorbs a bounded and slowly growing share"). Check: a passing loader test asserts, for every pool, capacity at each successive era is `>=` the previous era's capacity (`grep -rn "func Test.*[Ee]raScal\|func Test.*[Nn]onDecreasing" internal/foundation/data/external_world_test.go`). **What a lazy implementation looks like:** a single flat capacity number reused across every era — schema-valid (satisfies non-decreasing trivially, since it's constant) but fails the *spirit* of "slowly growing"; the check as written cannot mechanically distinguish flat-but-legal from genuinely-growing, so the loader's doc comment must state whether flat-per-era is a deliberate v1 simplification (documented) or an oversight — same discipline as AC-3's degenerate-nest case.
- **AC-15 (§21; wage level and transport requirement).** Each pool carries `wageMicropounds` (int64 micro-pounds, M0-ENG §1.2 — never a float, matching `data/market.json`'s existing money-representation convention) and a `transportRequirement` field naming which channel(s) reach it (`"motorway"` always available; `"externalRail"` gated to tier 5+, per §21's "from tier 5, the external rail station"). Check: a passing loader test asserts every pool has a positive `wageMicropounds` and a `transportRequirement` value from the documented closed set (`grep -rn "func Test.*[Ww]ageField\|func Test.*[Tt]ransportReq" internal/foundation/data/external_world_test.go`).
- **AC-16 (balance-number placeholder discipline — logged as ASM-393, distinct from modes.json's literature-citation bar).** Unlike `modes.json`'s AC-6, `external_world.json`'s `capacityByEra`/`wageMicropounds` figures are player-felt balance numbers with no spec-given magnitude (A6 states mechanism only). Per Aaron's standing balance-number regime, each pool carries a `comment` field explicitly disclosing the figures are a placeholder pending M2 Batch tuning (matching `data/market.json`'s "Plausible v1 static price, pending M2 Batch tuning" convention verbatim in spirit) — a bare number with **no** disclosure comment is still a schema violation, but the disclosure is "this is a placeholder," not a literature citation. Check: a passing loader test asserts every pool's `comment` field is non-empty and contains a placeholder/pending-tuning disclosure (`grep -rn "func Test.*[Pp]laceholderDisclosure" internal/foundation/data/external_world_test.go`). **What a lazy implementation looks like:** copying modes.json's `provenance.source` structured-citation shape onto external_world.json's balance numbers, inventing a fake "literature source" for a number that is actually just a guess — worse than an honest placeholder disclosure, because it manufactures false traceability; the Destructive agent should specifically check that no `external_world.json` comment cites a source that doesn't actually justify a specific magnitude.

### Error handling (GR#7 — all three files)

- **AC-17.** A malformed or schema-invalid `data/modes.json` (missing a mode, a coefficient block with no `provenance`, a nest tree that doesn't partition all 12 modes, a `nestingParameter` outside `(0, 1]`) produces a registry-sourced error (new `MET-E`-range code) at load time, identifying the offending mode/field — never a silent default coefficient (e.g. `0.0`) or a silently-dropped mode. Check: `grep -n "MET-" internal/foundation/data/modes.go` finds a registry code reference; passing malformed-data test coverage for at least the four named failure classes (`grep -rn "func Test.*[Mm]odesInvalid\|func Test.*[Mm]alformedModes" internal/foundation/data/modes_test.go`).
- **AC-18.** A malformed or schema-invalid `data/naming_corpus.json` (a road class with no suffix, a corpus below AC-9's floor, a duplicate place name) produces a registry-sourced error at load time identifying the offending field — never a silent fallback to a hardcoded default corpus, which would defeat GR#15 by resurrecting exactly the Go-literal pattern this file exists to remove. Check: `grep -n "MET-" internal/foundation/data/naming_corpus.go` finds a registry code reference; passing malformed-data test coverage (`grep -rn "func Test.*[Cc]orpusInvalid\|func Test.*[Mm]alformedCorpus" internal/foundation/data/naming_corpus_test.go`). **What a lazy implementation looks like:** the loader silently falling back to an in-Go hardcoded 8-name emergency list "just in case" — this exact pattern is `engine.roads.md` AC-13's own named failure mode ("fails loudly... rather than silently returning an empty or placeholder name that could ship visible to the player") and must not exist here either.
- **AC-19.** A malformed or schema-invalid `data/external_world.json` (a pool missing a capacity table, a negative capacity or wage figure, a capacity table not covering the current era, a `capacityByEra` that decreases) produces a registry-sourced error at load time — never a silent zero-capacity default (permanently unusable pool) or unlimited-capacity default (defeats `engine.extcommute` AC-3's finiteness invariant), matching `engine.extcommute.md` AC-15's own wording exactly. Check: `grep -n "MET-" internal/foundation/data/external_world.go` finds a registry code reference; passing malformed-data test coverage for all four named failure classes (`grep -rn "func Test.*[Ee]xtWorldInvalid\|func Test.*[Mm]alformedPool" internal/foundation/data/external_world_test.go`).

### Determinism & safety

- **AC-20 (GR#21; deterministic load).** Loading each of the three files twice produces byte-identical in-memory structures; any validation-error ordering is stable and sorted (by mode ID / place name / pool ID respectively), never dependent on Go map iteration order. Check: `grep -n "sort\." internal/foundation/data/modes.go internal/foundation/data/naming_corpus.go internal/foundation/data/external_world.go` shows an ordering step wherever validation errors are aggregated; a passing determinism test exists per file (mirrors `data.catalogue.md` AC-13 exactly).
- **AC-21 (no non-reproducible values).** None of the three files contains a timestamp, machine-specific path, or other non-reproducible value inside an entry body (a top-level `version`/`generatedAt` metadata field is fine and excluded). Check: `grep -n "\"[0-9]\{4\}-[0-9]\{2\}-[0-9]\{2\}T" data/modes.json data/naming_corpus.json data/external_world.json` finds no ISO-timestamp values inside entry bodies.

### GR#15 — validators derive from data, not hardcoded counts

- **AC-22.** No test in `modes_test.go`, `naming_corpus_test.go`, or `external_world_test.go` hardcodes an expected count (mode count, place-name count, pool count) as a bare integer literal compared against a *live* population figure without traceability to this file's own AC-9/AC-1/AC-13 documented derivation — every "how many" assertion either derives from the loaded file itself, from a checked-in reference list transcribed from the spec, or from a named constant documented as tracing to a specific ASM/AC (AC-9's 40-entry floor is the sanctioned exception, since it is explicitly derived-and-logged, not silently invented). Check: review of the three test files for any bare integer literal used as an expected-count assertion with no comment tracing it to a spec table, a reference list, or a named/documented constant.

### Documentation

- **AC-23.** Each of the three JSON files carries a top-level `$comment`/`meta` block citing its governing spec section(s) (§19.1 / §20 / §21+A6 respectively) and, for `modes.json` and `external_world.json`, restating in one line which numbers are literature-cited versus placeholder — mirroring `data/buildings.json`'s and `data/market.json`'s existing `$comment`/`meta` convention. Check: `grep -n "\$comment\|\"meta\"" data/modes.json data/naming_corpus.json data/external_world.json` matches in all three, and the value names the relevant spec section.
- **AC-24.** A schema reference document (`docs/design/modes-naming-external-schema.md`) describes every field this item introduces across all three files (mode utility/nest/personality-weight fields and their provenance shape; naming-corpus place-name/suffix fields and the coverage-floor rule; external-world pool/era/wage/transport fields and the placeholder-disclosure rule), so a later M2 Batch balance editor has a field reference without reverse-engineering three loaders at once. Check: file exists and lists all named field groups.

## Out of scope

- Final-tuned balance numbers for any of the three files — `modes.json`'s literature-cited coefficients are a defensible v1 estimate, not a claim of measured accuracy for this specific city model; `external_world.json`'s capacity/wage figures are explicitly placeholder (AC-16); `naming_corpus.json`'s exact 40+ place-name list beyond the 8 spec-cited examples is a reasonable authoring pass, not an exhaustive gazetteer. M2 Batch tuning territory in all three cases, same carve-out `data.catalogue.md` and `engine.season.md` already use.
- `engine.traffic`'s, `engine.roads`', and `engine.extcommute`'s own consumption of these files (the actual nested-logit computation, the actual naming-continuation algorithm, the actual pool-assignment/exhaustion logic) — those are the three consuming modules' own acceptance files (`engine.traffic.md` AC-10, `engine.roads.md` AC-9/AC-10, `engine.extcommute.md` AC-2/AC-5), unaffected except that their blocking pre-dispatch dependency (ASM-215/ASM-223/ASM-274) closes once this item lands.
- Civic-building, infrastructure, district, and transit naming's *non-corpus* mechanics (deceased-citizen eligibility, functional numbering, auto-lettering) — `naming_corpus.json` supplies the shared toponym pool districts may draw on (per §20 "real local toponyms first"), but the district-naming algorithm itself, and the wholly-separate civic-building/infrastructure/transit naming rules, belong to `engine.roads` AC-10's own scope, not this data file.
