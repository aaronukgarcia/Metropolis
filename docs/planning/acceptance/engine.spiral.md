# Acceptance criteria — engine.spiral (MOD-030)

**BOW code:** MOD-030
**Spec refs:** §12 "Failure — the Detroit Spiral" (`docs/METROPOLIS-MASTER-v2.1.md` line 240: "No scripted loss. The spiral: shock (major employer closes, service collapse, sustained shortage) → emigration → tax base ↓ → forced service cuts or debt → attractiveness ↓ → more emigration → abandoned buildings (decay state: drag neighbouring land value, small ongoing hazard/fire/crime pressure, cost money to demolish) → district blight spreads cell-by-cell. Recovery is possible but expensive (demolition, targeted investment, tax relief districts). Death conditions: insolvency (§7), or population falls below 10% of historic peak after the city has ever exceeded 50,000 — the ghost-city ending, with an epilogue screen generated from the city's history log."); §II.7 Government (line 64, budgets/loans/credit rating as the fiscal side of the same mechanics); §11 Attractiveness & Migration (line 236, the reputation-momentum "Detroit trap" asymmetry the spiral rides on); §13 F9 Ticker & History (line 254, the searchable history log that is the epilogue's data source); code.json `engine.spiral` entry (inbound `DecayAPI`, "decay states on cells/buildings; spiral metrics subscribable", consumer `engine.crime`; outbound calls `engine.attract`, `engine.build`, `engine.world`).
**Date:** 2026-08-11 (initial BA pass)
**Status:** draft-ahead — both dependencies (`MOD-026` engine.build, `MOD-029` engine.attract) are `open`; this item is not in the ready queue until they land. Content written now, ahead of both.
**Package under test:** `internal/engine/spiral/` (path from `node claude-bow.js show MOD-030`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/spiral/...`.

## User stories

- **US-1.** As the simulation, I need the Detroit-spiral chain (shock → emigration → tax base decline → cuts/debt → attractiveness decline → more emigration → abandonment → blight spread) to emerge from real, live system values (attractiveness score, tax receipts, migration rate) rather than a scripted cutscene sequence, so "no scripted loss" (§12) is actually true and the spiral can be *escaped* by changing those real values, not just watched.
- **US-2.** As `engine.crime` (a registered consumer of `DecayAPI`), I need decay-state metrics per cell/building, so crime pressure can respond to real blight rather than a proxy.
- **US-3.** As the player, I need abandonment to carry three distinct, independently visible costs (neighbour land-value drag, hazard/fire/crime pressure, demolition cost) so the decision to intervene (or not) is a real tradeoff, not a single opaque penalty number.
- **US-4.** As the player who let a district blight, I need genuine, if expensive, recovery paths (demolition, targeted investment, tax relief districts) so the spiral is a hole you can climb out of, matching §12's "recovery is possible but expensive".
- **US-5.** As a BA/Tester/QA verifying the S7 exit gate's "Detroit spiral reproducible from a scripted shock scenario" clause, I need a documented, seeded, scripted shock scenario whose outcome — full stage-transition sequence, not just a final number — is byte-identical across repeated runs and across worker counts (GR#21), so "reproducible" is a property that can fail an implementation that is merely *usually* the same.
- **US-6.** As the player who has driven the city to ruin, I need the ghost-city ending's epilogue to be generated from what actually happened in *this* save's history log, so the ending reads as the story of my city, not a template.

## Scope

Decay-state modelling for abandoned buildings (per-cell/building state: severity, neighbour land-value drag, hazard/fire/crime pressure, demolition cost), cell-by-cell blight spread, recovery mechanics (demolition, targeted investment, tax relief districts), the two death conditions (insolvency, sub-10%-of-historic-peak population) and the ghost-city epilogue generated from the history log. The spiral's *causal chain* is emergent from `engine.attract`'s attractiveness score and `engine.finance`'s fiscal state (edge registered c36778b, BUG-058 resolved for this pair) — this module does not reimplement those systems, it consumes and reacts to them.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `DecayAPI` (or equivalent) exists matching code.json's documented pattern: per-cell/building decay-state queries plus subscribable spiral metrics, consumed by `engine.crime` today. Check: `go doc ./internal/engine/spiral DecayAPI` shows a cell/building decay-state query method and a metrics-subscription surface.
- **AC-2 (§12; no scripted loss).** Each stage of the spiral (emigration onset, tax-base decline, service cuts/debt, attractiveness decline, abandonment onset, blight-spread onset) is triggered by a documented threshold or derivative on a real, externally-owned value (`engine.attract`'s attractiveness score / migration rate; the fiscal signal per AC-6 below), not by an internal counter or a hardcoded stage-advance sequence. Check: `grep -n "stage++\|Stage =\|case StageEmigration" internal/engine/spiral/*.go` finds no bare sequential-advance switch with no real-value input; each transition function's signature takes a real external value (attractiveness score, tax delta, etc.) as an argument, verifiable via `go doc`. **Lazy implementation this rejects:** a "spiral" that is actually a scripted timer counting down stages once a shock event fires would satisfy "the spiral happens" but is exactly the scripted loss §12 forbids — reversing the driving value (e.g. attractiveness recovering) must be able to halt or reverse the stage progression, which a timer-driven implementation cannot do; see AC-5 for the explicit reversibility test.
- **AC-3 (§12 abandonment decay state).** Abandoned-building decay state exposes at least three independently queryable, independently testable effects: neighbour land-value drag (a measurable reduction to adjacent cells' land value), hazard/fire/crime pressure (a measurable increase to a hazard metric consumed by `engine.crime`/later fire-safety systems), and demolition cost (a real money figure, growing with severity/age). Check: `go doc ./internal/engine/spiral` shows all three as distinct fields/queries on the decay-state type; three passing tests each show raising decay severity moves exactly the effect under test in the documented direction, independent of the other two (`grep -rn "func Test.*[Ll]andValueDrag\|func Test.*[Hh]azardPressure\|func Test.*[Dd]emolitionCost" internal/engine/spiral/*_test.go`). **Lazy implementation this rejects:** a single scalar "blight penalty" applied uniformly to nearby systems would satisfy a vague "abandonment has consequences" reading but fails the independence tests — this AC specifically requires three separable, separately-verifiable effects, per §12's own three-item list.
- **AC-4 (§12 blight spread, cell-by-cell + GR#4 crown rule).** Blight spreads cell-by-cell via a documented, deterministic frontier-selection order over eligible neighbour cells (e.g. coordinate-sorted, shard-ordered — anything except Go map iteration order), never all-at-once across a district. Check: `go doc ./internal/engine/spiral` or `doc.go` documents the frontier-selection order explicitly; a passing test constructs a decayed source cell with **multiple equally-eligible neighbour cells** (a forced tie) and asserts the same neighbour is chosen first across repeated runs (`grep -rn "func Test.*[Bb]lightOrder\|func Test.*[Ff]rontierTie" internal/engine/spiral/*_test.go`); `grep -n "for .* := range .*map\[" internal/engine/spiral/*.go` in the spread path finds no bare map-range driving spread order. **Lazy implementation this rejects:** iterating a Go `map[CellID]*Cell` to pick the next cell to blight is idiomatic-looking and "spreads cell-by-cell" in casual testing, but Go map iteration order is randomised per-run — the forced-tie test is specifically constructed to expose this, since a hash-ordered pick would choose differently across repeated runs of the identical scenario.
- **AC-5 (§12 recovery, reversibility).** Recovery actions — demolition, targeted investment, a tax-relief-district designation — each exist as a distinct command, each carrying a documented cost, and each measurably reduces the decay/blight state of its target cell/district (not merely halts further spread; existing decay actually improves). Check: `go doc ./internal/engine/spiral` shows three distinct command types; three passing tests each apply one recovery command to a decayed fixture cell/district and assert its decay severity (or the AC-3 effects) strictly decreases afterward, at a cost strictly greater than zero (`grep -rn "func Test.*[Rr]ecovery.*[Dd]emolition\|func Test.*[Rr]ecovery.*[Ii]nvestment\|func Test.*[Tt]axRelief" internal/engine/spiral/*_test.go`).
- **AC-6 (§7/§12 insolvency death condition — RE-ARMED 2026-08-11, BUG-100: the `engine.spiral`→`engine.finance` edge landed in c36778b).** A death-condition evaluator consumes a real insolvency/money-stock signal exposed by `engine.finance` (per §7) and triggers the insolvency death path when that signal indicates insolvency — this module does not reimplement insolvency math itself. The edge is confirmed registered: `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.spiral'); process.exit(m.outbound.calls.some(c=>c.key==='engine.finance')?0:1)"` exits 0, so the fake/injected-signal interim is retired — this AC now requires the real integration. Check: `go doc ./internal/engine/spiral` shows the insolvency check taking a real call into `engine.finance`'s exposed money-stock signal (not a build-local balance-sheet computation, and no longer merely an externally-supplied interface satisfied only by a test fake); `grep -n "finance\." internal/engine/spiral/*.go` (excluding `_test.go`) shows the live call; a passing test drives `engine.finance` (directly or via a fake satisfying its real interface) to an insolvent state and asserts the death path triggers, and to a solvent state and asserts it does not (`grep -rn "func Test.*[Ii]nsolven" internal/engine/spiral/*_test.go`); `internal/engine/spiral/doc.go` no longer cites BUG-058 as a live block for AC-6.
- **AC-7 (§12 population death condition — both clauses independently required).** The ghost-city trigger requires **both** named conditions: current population below 10% of the city's all-time historic peak, **and** that historic peak having exceeded 50,000 at some point in the save's history. Check: `go doc ./internal/engine/spiral` shows the death check taking both a current-population and a historic-peak-population input; three passing tests: (a) peak never exceeded 50,000, current population near zero → no trigger; (b) peak exceeded 50,000, current population at exactly 10%+1 of peak → no trigger; (c) peak exceeded 50,000, current population below 10% of peak → trigger (`grep -rn "func Test.*[Gg]hostCity\|func Test.*[Hh]istoricPeak" internal/engine/spiral/*_test.go`). **Lazy implementation this rejects:** a check using only "population < 5,000" (10% of the *threshold*, not of the actual *peak*) would coincidentally pass a city that peaked at exactly 50,000 but silently misfire (or fail to fire) for any city with a different peak — test (b)/(c) with a peak other than 50,000 is the part that catches this.
- **AC-8 (§13 F9 epilogue).** The ghost-city ending produces an epilogue generated from the actual logged history of *this* save (referencing real logged events — the shock date, key stage-transition dates, the historic peak value and date) rather than a static templated string with no per-run data. Check: `go doc ./internal/engine/spiral` shows the epilogue generator taking the history log as an input; a passing test runs two different scripted scenarios (different shock timing/type) and asserts the two generated epilogues differ in their referenced dates/events, not just cosmetic wording (`grep -rn "func Test.*[Ee]pilogue" internal/engine/spiral/*_test.go`). **Lazy implementation this rejects:** an epilogue built from a fixed Lorem-Ipsum-style template with the final population number substituted in would satisfy "an epilogue screen exists" but fail this two-scenario differentiation test, which requires the *events*, not just one number, to flow through.

### Reproducibility (the load-bearing GR#21 clause)

- **AC-9 (S7 exit gate — "Detroit spiral reproducible from a scripted shock scenario"; GR#21; ASM-240).** A documented, versioned scripted shock scenario — fixed seed, a fixed `harness.synth`-generated starting city, a specific shock command (major-employer-closure, at a fixed month — see ASM-240) — run headless to completion (either a death condition triggers, or a fixed month cap is reached with no death) produces a **byte-identical/hash-identical outcome** across (a) repeated runs at the same worker/shard count, and (b) runs at at least two different worker/shard counts. "Outcome" is defined as the ordered sequence of stage-transition events (shock recorded → emigration onset → tax-base decline recorded → cuts/debt recorded → attractiveness-decline recorded → abandonment onset → blight-spread events in frontier order → death-condition verdict or non-death verdict at the month cap) **plus** the final simulation state hash — not a single scalar (e.g. final population) standing in for the whole run. Check: a passing test runs the scripted scenario twice at the same worker count and asserts identical event-sequence + state hash; a second passing test runs it at two different worker/shard counts (e.g. 1 vs. `NumCPU-2` per M0-ENG §1.2) and asserts the same (`grep -rn "func Test.*[Ss]piralReproduc\|func Test.*[Ss]criptedShock" internal/engine/spiral/*_test.go`). **This is the check the brief specifically requires be unable to pass a "usually the same" implementation:** a build that gets the same *final population* every run (because the headline economic math is deterministic) but a different *blight-spread order* or a different *stage-transition timing* every run (because a map-iteration or goroutine-ordering bug lives somewhere in the chain) would still fail this AC, because the hash and the ordered event log — not the population scalar — are what's compared. A test asserting only "final population matches within X%" would be exactly the "vacuously passes on 'usually'" shape this AC is written to prevent.
- **AC-10.** `go test ./internal/engine/spiral/... -race -count=1` passes with no data race in stage-transition or blight-spread code that uses the shard worker pool. Check: `grep -n "go func()" internal/engine/spiral/*_test.go` finds at least one concurrency test.

### Error handling

Check: `grep -n "MET-" internal/engine/spiral/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalidShock\|func Test.*[Uu]nknownTarget" internal/engine/spiral/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no silently-ignored or silently-substituted shock was applied, not merely that a matching-named test function exists.
- **AC-12.** A recovery command (AC-5) issued against a cell/district with no decay state (nothing to recover) returns a typed rejection via `CommandResult`/`ErrorRef` (per `docs/design/protocol.md`), never a silent no-op success that would let the player "recover" a healthy district for free. Check: passing test coverage (`grep -rn "func Test.*[Nn]oDecay.*[Rr]eject\|func Test.*[Rr]ecovery.*[Nn]oOp" internal/engine/spiral/*_test.go`).
