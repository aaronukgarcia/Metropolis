# Acceptance criteria — tool.destructiveguard (FEAT-040)

**BOW code:** FEAT-040
**Spec refs:** GR#23 (Nothing Is Committed Un-Attacked, `CLAUDE.md` line 54, added 2026-08-10); GR#15 (Validators Derive From Data); GR#12 (Dependency & Completeness Check); `docs/planning/dev-team-process.md` §"The Destructive agent (v1.8)" (what a verdict is, weakness-class ledger, weakness pattern #5 "a guard must not damage what it protects", weakness pattern #6 "a guard must be judged on cost-to-reach"); §"An acceptance criterion's CHECK must be able to fail (v1.9)"; `node claude-bow.js show FEAT-040`'s description (the lead's required behaviour, quoted throughout below).
**Date:** 2026-08-10
**Status:** active — normal pipeline order (criteria written before junior dispatch)
**Package under test:** `claude-destructive-guard.js` (new, repo root) **and** `claude-bow.js` (extended — new verdict-recording surface; this item deliberately spans both files, see Scope).
**Standard gates:** see `README.md` for the general convention; both files are **Node.js, not Go** — SG-1/SG-2/SG-4/SG-7 do not apply. This item's own gates are `node --check` on each changed/added `.js` file, SG-5 (forbidden-touch: only `claude-destructive-guard.js`, `claude-bow.js`, `.claude/settings.json`, and this item's own test file(s) may be touched), and SG-6 (no Co-Authored-By).

## User stories

- As **Bill**, I need no code-bearing commit to reach history without a recorded Destructive verdict on its BOW item(s), mechanically enforced, so GR#23 does not depend on a busy morning the way the v1.8 process note already failed to survive twice (BUG-034, BUG-035).
- As **a Destructive agent**, I need a first-class, queryable place to record accept/reject/attacker/date/weakness-classes-filed, so the gate derives its answer from data (GR#15) instead of a human or a hook grepping prose out of a free-text BOW comment.
- As **a developer whose commit is denied**, I need the denial to name exactly which BOW item(s) lack a verdict, so the fix is "get it attacked" not "guess what the gate wants."
- As **an operator facing a genuinely broken gate**, I need a documented, harness-environment-only escape hatch, so a defect in this guard can never brick every commit including its own fix (weakness pattern #5 — a guard must not damage what it protects).
- As **the commit that introduces this very guard**, I need a way to satisfy GR#23 for FEAT-040 itself without circularity, so the bootstrap case is a designed path, not a hand-wave.

## Scope

Two deliverables under one BOW item, because the second cannot be built or tested without the first (GR#12):

1. **`claude-bow.js` — verdict storage and surface.** A new table, `bow_destructive_verdicts` (append-only history, one row per Destructive round: `guid`, `item_guid` FK, `verdict` — `accept`|`reject`, `attacker`, `weakness_classes` — validated against the existing `FINDING_CLASSES` constant, `findings` — optional list of `SEC-` codes this round filed, `note`, `created_at`). Two new CLI subcommands:
   - `destructive <code|mkey> --verdict accept|reject --attacker "<name>" [--class <c1>[,<c2>,...]] [--findings <SEC-001>[,<SEC-002>,...]] [--note "..."]` — records a new verdict row.
   - `verdict <code|mkey> [--json]` — reports the **latest** (by `created_at`) verdict row for the item, human-readable by default, machine-readable with `--json`.
   Two new exported functions, mirroring how `findItemByRef` is already reused by `claude-bow-ref-check.js` rather than re-queried: `recordDestructiveVerdict(db, ref, {verdict, attacker, classes, findings, note})` and `latestDestructiveVerdict(db, ref)`.
2. **`claude-destructive-guard.js` — the gate.** A `PreToolUse` hook on `Bash`/`PowerShell` `git commit` that: detects whether the commit is code-bearing (staged files under `cmd/`, `internal/`, `data/`, `tools/`, or a root-level script wired into `.claude/settings.json`'s hooks — see AC-6 on why that boundary is data-derived, not name-pattern-derived); extracts every `[mkey]`/`[CODE]` tag from the commit message (reusing `claude-bow-ref-check.js`'s extraction shape); for each tag that resolves to a live BOW item, calls `latestDestructiveVerdict` and denies naming any item whose latest verdict is missing or `reject`; denies a code-bearing commit that carries **no** recognisable tag at all (the bypass trap); and fails closed on any internal error. Wired into `.claude/settings.json` immediately after `claude-author-guard.js`.

## Acceptance criteria

### A. `claude-bow.js` verdict storage (GR#15: data, not prose)

- **AC-1.** `bow_destructive_verdicts` is created by `init` (auto-run on every command, matching every other table). Check: on a scratch/test database, run `node claude-bow.js list` (which triggers `init`) then query `SHOW TABLES LIKE 'bow_destructive_verdicts'` — one row. **What a lazy implementation looks like:** storing the verdict as a formatted string inside `bow_comments.body` and calling that "recorded." Check rejects it: AC-4/AC-5 query a dedicated table's columns directly, which a comment-string implementation cannot produce (there is no `verdict`/`attacker` column on `bow_comments` to select).
- **AC-2.** `destructive <code>` requires `--verdict` (one of exactly `accept`/`reject`, case-insensitive, else a clear error naming the allowed values) and `--attacker` (non-empty; a bare `--attacker` with no value, or an empty string, is rejected — an unnamed attacker is not an audit trail). Check: a passing test asserts `--verdict maybe` errors without writing a row; a passing test asserts a missing/empty `--attacker` errors without writing a row (verified by counting rows before/after — see the false-pass note below).
- **AC-3.** `--class` values, when given, are each validated against the existing `FINDING_CLASSES` constant already defined in `claude-bow.js` for `add finding` — **not** a second, independently-typed list. Check: `grep -n "FINDING_CLASSES" claude-bow.js` shows exactly one array literal definition, referenced (not redefined) at the `destructive` command's validation site; a passing test asserts `--class not-a-real-class` errors, and `--class concurrency-safety` (a real class already in the constant) succeeds. **False-pass warning:** a grep for `FINDING_CLASSES` alone would also pass an implementation that defines a *second*, textually-similar constant under a different name and validates against that — the binding part of this check is "referenced, not redefined," which the grep's line-count (`exactly one array literal`) is written to catch; a reviewer must confirm by eye that the `destructive` command's validation calls into the same identifier, not a copy.
- **AC-4.** `--findings`, when given, is a comma-separated list of existing BOW codes, each resolved via `findItemByRef` (reused, not re-queried) before the verdict row is written; an unresolvable code in the list aborts the whole write with no partial row (all-or-nothing). Check: a passing test asserts `--findings SEC-999-does-not-exist` (or any fixture code guaranteed absent) errors and leaves `bow_destructive_verdicts` row count unchanged for that item.
- **AC-5.** `destructive <code>` on an unknown `<code>`/`mkey` (does not resolve via `findItemByRef`) errors without writing a row, matching every other subcommand's existing "unknown ref" behaviour. Check: a passing test asserts this and checks no row was inserted.
- **AC-6.** Recording is **append-only**: a second `destructive <code>` call for the same item does not overwrite or delete the first row — both persist, and `latestDestructiveVerdict`/`verdict <code>` report the one with the greatest `created_at`. Check: a passing test records `reject` then `accept` for the same item, asserts two rows exist for that `item_guid`, and asserts `verdict <code>` reports `accept` (the more recent one) — this is the re-verdict-after-fix loop (Destructive REJECT → same junior fixes → Tester → Destructive again) and it must be representable without ever mutating history. **What a lazy implementation looks like:** a single mutable `latest_verdict` column on `bow_items`, overwritten each call. Check rejects it: it demands two rows recoverable afterward, which a single-column implementation cannot produce even if `verdict <code>` happens to report the right answer on the surface — a query against `bow_destructive_verdicts` for `COUNT(*) WHERE item_guid = ?` is the binding part, not just the final reported verdict.
- **AC-7.** `verdict <code>` with no verdict ever recorded for that item reports "no verdict recorded" (not an error, not a false `reject`) — the three-way distinction (accept / reject / never-attacked) must survive to the caller, because the gate (AC-15) needs to tell a developer "get this attacked" apart from "it was attacked and failed." Check: a passing test on a freshly-created fixture item with zero verdict rows asserts `verdict <code>`'s output is distinguishable from both `accept` and `reject` (e.g. `null`/`"none"` in `--json` output), and a passing test on `--json` output specifically asserts the field is not simply absent (an absent field is indistinguishable from a bug that failed to populate it — the check requires an explicit "no verdict" value).
- **AC-8.** `recordDestructiveVerdict`/`latestDestructiveVerdict` are exported from `claude-bow.js`'s `module.exports`, alongside the existing `findItemByRef` export, so `claude-destructive-guard.js` can `require('./claude-bow.js')` them directly rather than shelling out or re-implementing the query — mirroring exactly how `claude-bow-ref-check.js` already reuses `findItemByRef` (line 55 of that file) instead of writing a second lookup. Check: `grep -n "module.exports" claude-bow.js` includes both new names, and `grep -n "require('./claude-bow.js')" claude-destructive-guard.js` shows the guard importing them (not `execSync('node claude-bow.js ...')` for this specific lookup — see AC-16 for why a subprocess-per-check design would itself be a finding under weakness pattern #6, "what does the approach to the guard cost").

### B. `claude-destructive-guard.js` — code-bearing detection

- **AC-9.** The hook intercepts only `git commit` commands (same shell-boundary-anchored regex family as `claude-bow-ref-check.js`/`claude-version-guard.js`) — non-commit Bash/PowerShell commands exit 0 immediately with no stdout. Check: a test harness feeds `{"tool":"Bash","tool_input":{"command":"git status"}}` and asserts exit 0, empty stdout.
- **AC-10.** Code-bearing detection is by **staged file paths** (`git diff --cached --name-only`), never by the command string — matching `claude-bow-ref-check.js`'s AC-3 precedent and for the identical reason (a command string tells you nothing about what's actually staged). Check: `grep -n "diff --cached --name-only" claude-destructive-guard.js` matches; a passing test stages a file under `internal/` and asserts the gate activates (requires a tag+verdict), and a passing test stages only a `docs/`-only change and asserts the gate is silently exempt.
- **AC-11.** The enforced-path set is `cmd/`, `internal/`, `data/`, `tools/` (prefix match on the staged path) **plus** any root-level file that is, at commit time, wired as a hook `command` inside `.claude/settings.json` — **derived by reading and parsing that file at runtime, not by a hardcoded filename list or a `claude-*guard*.js` name pattern** (GR#15: the set of "root guard scripts" is data that already exists — the hooks array — not a second, independently-maintained list that can silently drift from it). Check: `grep -n "require.*settings.json\|readFileSync.*settings.json" claude-destructive-guard.js` shows the guard reading `.claude/settings.json` itself; a passing test stages a fixture root `.js` file that is present in a fixture `settings.json`'s hooks array and asserts the gate activates for it, and a passing test stages a root `.js` file that is **not** in that array (e.g. a scratch script) and asserts the gate does **not** activate for it purely on the basis of its filename looking guard-like. **False-pass warning for a name-pattern implementation:** `grep -n "claude-.*guard" claude-destructive-guard.js` would pass an implementation using a hardcoded regex like `/^claude-.*guard.*\.js$/` — that satisfies "some scripts are covered" but fails the second half of this test (a hooks-array-derived implementation excludes an unwired scratch file with "guard" in its name; a name-pattern implementation wrongly includes it, and separately would miss a real hook that happens not to have "guard" in its name, e.g. `claude-bow-ref-check.js`, which the fixture test also covers).
- **AC-12.** A commit touching only paths outside the enforced set (e.g. `docs/`, `.claude/settings.json` on its own with no `.js` change, `README.md`) is exempt — silent allow, no output. Check: a passing test stages only `docs/foo.md` and asserts exit 0, empty stdout.
- **AC-12a (BUG-722, FEAT-077 tier extension).** The FEAT-077 test-only exemption's file-shape allowlist also covers `.test.mjs`/`.test.tsx`/`.test.ts`/`.test.jsx` — the webconsole's own test naming, missed when the original three shapes (`.md`/`.test.js`/`_test.go`) were chosen — but ONLY under a `test/`/`__tests__/` directory segment or at the repo root; a same-named file under `src/` stays code-bearing (rename-visibility class, BUG-340 r1 F3). Check: `isExemptFile('webconsole/test/foo.test.mjs')` is `true`; `isExemptFile('webconsole/src/sim/foo.test.mjs')` is `false`.

### C. Verdict lookup and denial

- **AC-13.** The commit message's `[mkey]`/`[CODE]` tags are extracted using the same tag shape `claude-bow-ref-check.js` already uses (`TAG_RE = /\[([^\[\]\n]+)\]/g` over the parsed `-m`/`--message` body) — reused or duplicated verbatim with a comment pointing at the original, not reinvented with different edge-case behaviour. Check: a passing test asserts a message with `[tool.destructiveguard]` and a message with `[FEAT-040]` both extract correctly, including a multi-tag message.
- **AC-14.** For every extracted tag that resolves to a live BOW item (`findItemByRef`), the gate calls `latestDestructiveVerdict` for that item. An item whose latest verdict is `accept` passes; an item with no verdict row, or whose latest verdict is `reject`, is collected as a **missing-verdict** item. Check: a passing test with a fixture item carrying an `accept` verdict asserts the commit is allowed; a passing test with a fixture item carrying only a `reject` verdict (no later `accept`) asserts the commit is denied — proving the check reads the *latest* row, not merely "a verdict exists at all" (a check that only asked "does any row exist" would wrongly allow a still-rejected item, which is exactly the shape GR#23 exists to prevent).
- **AC-15.** A denial for missing-verdict item(s) names every one of them individually (code + title), not an aggregate "some items lack verdicts" message — mirroring `claude-bow-ref-check.js`'s AC-6/AC-12 per-tag enumeration. Check: a passing test stages two enforced-path files referencing two different BOW items, one with an `accept` verdict and one with none, and asserts the deny message names the second item specifically and does not falsely also name the first.
- **AC-16 (the bypass trap).** A code-bearing commit (per AC-10/AC-11) whose message contains **zero** recognisable tags is **denied**, with a message explaining the requirement — this is the explicit non-goal from the BOW description: "it must not become trivially bypassable by omitting the BOW code from the message." Check: a passing test stages a file under `internal/` with a commit message containing no `[...]` tag at all and asserts denial. **What a lazy implementation looks like, and why the check rejects it:** an implementation that only checks "for each tag found, does it have a verdict" — and silently allows when the tag list is empty, because its loop over zero tags finds zero problems — satisfies every other AC in this file (every *present* tag it ever sees does get checked) while being the exact bypass GR#23's own description calls out by name. This AC's check does not merely assert "the loop ran"; it asserts the **outcome is deny** on a real zero-tag fixture, which a "loop found nothing to complain about" implementation fails by construction.
- **AC-17.** A code-bearing commit's message contains an unresolvable tag (does not match any live BOW item) — this is denied too (treated the same as missing-verdict, named individually), not silently skipped as "not our problem" — an unresolvable tag cannot have a verdict on file by definition. Check: a passing test stages an enforced-path file with a message tag that resolves to nothing and asserts denial naming that tag as unresolvable.

### D. Escape hatch and self-application (weakness pattern #5, bootstrap)

- **AC-18.** A documented, operator-only escape hatch: `CLAUDE_DISABLE_DESTRUCTIVE_GUARD=1`, read from `process.env` in the guard's own process — **never** from inline `VAR=value` text inside the proposed `git commit` command string. The header must state, in the same terms as `claude-secret-guard.js`'s and `claude-author-guard.js`'s headers, *why* an inline setting can never reach this process: `PreToolUse` hooks run in the harness process to decide whether to allow a proposed command, before that command's own child shell exists, so an env var an agent writes into the command it is asking permission for is never visible to the hook evaluating that same request. Check: `grep -n "CLAUDE_DISABLE_DESTRUCTIVE_GUARD" claude-destructive-guard.js` shows it read via `process.env.CLAUDE_DISABLE_DESTRUCTIVE_GUARD`, never via any parsing of `tool_input.command`; a passing test sets the var in the test process's own env (not in a simulated command string) and asserts allow; a passing test puts `CLAUDE_DISABLE_DESTRUCTIVE_GUARD=1` as literal text inside the simulated `command` string (with the real process env unset) and asserts the commit is **still denied** — proving the escape hatch cannot be self-granted by an agent from within the very command it is submitting. **This is the check that gives the "operator-only" claim teeth**; without the second half (inline text must NOT work), the AC only proves the honest path works and says nothing about the bypass it exists to rule out.
- **AC-19.** The header explicitly documents the escape hatch's purpose (genuine false positive / gate-is-itself-broken emergency only) and the cost asymmetry that justifies fail-closed-by-default: a false block costs a human seconds to diagnose and bypass deliberately; a code-bearing commit that skipped adversarial review, on a public repo, is not something a later commit can retroactively undo. Check: header comment present with both points, matching the register of `claude-codename-guard.js`'s and `claude-author-guard.js`'s equivalent paragraphs (reviewed by eye, not grepped — prose quality is not a grep-checkable property, and this AC says so rather than pretending a keyword match proves it).
- **AC-20 (bootstrap).** The criteria file itself states, and the guard's header must restate, how FEAT-040's own commit satisfies GR#23 without circularity: verdict recording is a **BOW/database write**, independent of git — a Destructive round against `claude-destructive-guard.js` and `claude-bow.js`'s new surface runs, and `node claude-bow.js destructive FEAT-040 --verdict accept ...` is executed **before** the commit is attempted. By the time `git commit` (carrying `[tool.destructiveguard]` or `[FEAT-040]` and, in the same commit, the guard's own wiring into `.claude/settings.json`) is proposed, the accept verdict already exists as data the gate can query — the gate does not need to have executed even once beforehand for this to be true, so there is no "the guard must approve its own installation before it exists" loop. Check: this is a documentation/process AC, not a code AC — verified by the lead's own commit sequence: `node claude-bow.js verdict FEAT-040` must report `accept` **before** the commit containing `claude-destructive-guard.js` is run, confirmable after the fact via `node claude-bow.js show FEAT-040`'s comment/verdict history and the commit's timestamp both being checkable post-hoc (verdict `created_at` < commit `author date`). **What a lazy non-implementation of this AC looks like:** skipping the Destructive round for FEAT-040 "because the guard isn't live yet to enforce it on itself" — the check rejects that reasoning specifically because the pipeline (BA → junior → Tester → Destructive → Docs → Bill) applies to every item regardless of whether the item's own gate is wired yet; FEAT-040 is not exempt from the same process it mechanises.

### E. Error handling — fail-closed (unlike `tool.bow`'s fail-open posture)

- **AC-21.** Unlike `claude-bow-ref-check.js` (fail-open hygiene gate), this guard is **fail-closed**, matching the BOW description's explicit requirement #5 ("fails closed on its own internal errors, like the codename and author guards") and GR#23's status as a security rule, not a traceability-hygiene rule. The header must say so explicitly, contrasting with `tool.bow`'s posture by name so a future reader does not assume this hook copies that one's fail-open behaviour. Check: header comment names the contrast explicitly (reviewed by eye).
- **AC-22.** A metro DB unreachable at gate time, for a code-bearing commit, **denies** (cannot verify a verdict exists → cannot allow) — the inverse of `claude-bow-ref-check.js`'s AC-10. Check: a passing test mocks/forces the DB connection to fail and asserts a code-bearing commit is denied with the underlying error surfaced in the deny reason.
- **AC-23.** An unparseable commit message (no `-m`/`--message` extractable — `-F`, heredoc, editor flow) on a code-bearing commit **denies**, rather than the fail-open "cannot verify, allow with a warning" behaviour `claude-bow-ref-check.js` uses for the same situation — this is a deliberate, named divergence (see AC-21). Check: a passing test simulates a code-bearing commit whose command string carries no parseable message and asserts denial (not a warn-allow).
- **AC-24.** Unparseable stdin JSON is handled the same way `claude-secret-guard.js` handles it (not the same way `claude-bow-ref-check.js` handles it): fail-closed is scoped to *commit-shaped* input — a raw-substring fallback checks whether the unparsed text looks like a `git commit`; if it plainly does not, allow immediately (so a hook-input hiccup never bricks `git status`/`npm install`); if it does look like a commit, deny (cannot verify, and the input is commit-shaped). Check: `grep -n "git commit" claude-destructive-guard.js` shows this fallback substring check in the parse-failure path; a passing test feeds non-JSON stdin with no `git commit` substring and asserts allow; a passing test feeds non-JSON stdin containing the substring `git commit` and asserts deny.
- **AC-25.** Any other internal error (git invocation failure, `.claude/settings.json` unreadable/malformed when deriving the root-script set per AC-11, an unexpected exception anywhere in the evaluation path) results in DENY for anything that could be a `git commit`, via a top-level try/catch mirroring `claude-author-guard.js`'s `main()` wrapper. Check: a passing test forces `git diff --cached --name-only` to throw and asserts denial (not a silent allow) — this is the inverse case from AC-10's normal-operation path, isolating "can't tell what's staged" (deny, fail-closed) from `claude-bow-ref-check.js`'s equivalent case (allow, fail-open) as the single clearest illustration of why these are different guards with different postures despite similar code shape.
- **AC-26.** Deny output uses the exact `hookSpecificOutput` JSON convention (`permissionDecision: "deny"`, `permissionDecisionReason`), `process.exit(0)` — matching the sibling guards' convention. Check: `grep -n "hookSpecificOutput\|permissionDecision" claude-destructive-guard.js` matches the shape used by `claude-author-guard.js`'s `deny()` helper.

### F. Determinism & safety

- **AC-27.** Evaluating the same staged commit + BOW state twice produces identical verdicts (no randomness, no wall-clock-dependent logic beyond reading `created_at` ordering, which is itself deterministic given fixed data). Check: a passing test runs the evaluation function twice against the same fixture and asserts identical output.
- **AC-28.** The guard is read-only with respect to the git working tree, index, and the BOW (it queries `latestDestructiveVerdict`; it never calls `recordDestructiveVerdict` itself — a gate that could grant its own passing verdict would defeat the entire point). Check: `grep -n "recordDestructiveVerdict" claude-destructive-guard.js` finds **no** match (only `latestDestructiveVerdict`/`findItemByRef` calls) — a passing test snapshots `bow_destructive_verdicts` row count and `git status --porcelain` before and after invoking the guard against a fixture and asserts no change either way.

### G. Documentation

- **AC-29.** `claude-destructive-guard.js` carries a header in the same style as the three sibling guards: BOW mkey (`tool.destructiveguard`), spec refs (GR#23, GR#15, GR#12), a behaviour summary, the fail-closed posture and its explicit contrast with `tool.bow`'s fail-open posture, the root-guard-script derivation rule (AC-11) and why it's data-derived rather than name-pattern, and the escape-hatch env var name with the operator-only reasoning (AC-18/AC-19).
- **AC-30.** `claude-bow.js`'s header comment block (the `Commands:` list) is updated to list `destructive` and `verdict` alongside the existing subcommands, in the same one-line style as the rest of that list.

## Out of scope

- Auto-dispatching a Destructive agent, or any pipeline orchestration — this item is the **gate**, not the workflow that produces the verdict it checks for. The Destructive agent role itself is already specified in `docs/planning/dev-team-process.md`.
- `git merge`, `git cherry-pick`, `git revert`, and any other porcelain command that can create a new commit without going through `git commit` — the BOW description says "a PreToolUse hook on git commit" specifically, matching `claude-author-guard.js`'s identical scope decision for `git rebase`. Logged as an assumption (ASM, see report) rather than silently narrowed.
- Retroactively backfilling verdicts for commits already on `main` before this gate existed (BUG-034, BUG-035, and everything before them) — a separate, one-time reconciliation task if Bill wants the BOW's verdict history to be complete for historical items, not a behaviour of the gate itself.
- A UI/report surface beyond `verdict <code>` and `node claude-bow.js weakness` (already shipped) — e.g. a dashboard of verdict coverage across all open items is future work, not this item.
- `CLAUDE.md`'s hooks table being updated to list the new hook — that belongs to the Documentation role's pass, not this item's junior.

## Escalations

- **The root-guard-script boundary (AC-11) is a judgement call, not something the BOW description or CLAUDE.md fully specifies** — the description says "root guard scripts" in prose; this file resolves it as "whatever is currently wired into `.claude/settings.json`'s hooks," which is GR#15-clean (derived from data) but is a real scope decision (it would, for example, exclude `claude-sync.js` and `claude-bow.js` themselves from *this specific path-triggering rule*, even though `claude-bow.js` is being extended by this very item — its own commit is covered because `internal`/`cmd`/`data`/`tools` isn't where it lives, but because `.js` changes to it are still governed by whatever OTHER commit-time rules already apply; this item does not additionally sweep it in by name). Flagged for Bill's confirmation, not held back — logged as an assumption (see report) since the alternative (a hardcoded name list) is worse under GR#15 and under weakness pattern #6 (a name-pattern list is a second, driftable source of truth).
- No spec/brief conflict found otherwise. Criteria written before dispatch per normal pipeline order.
