# Acceptance criteria — engine.defence (MOD-067)

**BOW code:** MOD-067
**Spec refs:** §55 Defence & Central Government (`docs/METROPOLIS-MASTER-v2.1.md` lines 688-703: central government interacts two ways — **grants** (optional competitive pots: transport/regeneration/culture, bid with match funding, "§54 planning quality raises win rate") and formula support at low tax capacity; **mandates** at population thresholds — "at 100k you will host a naval facility; at 500k an army garrison; at 1M contribute to air defence" — each offering "a choice within compliance (which facility, where) plus compensation grants; refusal is possible but costs grant access and reputation (a legitimate libertarian-city strategy with a price tag)"; facilities table (army/navy/air/defence-research/reserve-cadet, each "service + civilian jobs, stable payroll (recession-proof anchor — the anti-cyclical employer), land take, resources, and character"); "Defence integrates, not decorates: bases consume §17 utilities and §33 goods, personnel are citizens (housing! schools for forces families!), procurement flows to your shipyard/rail works/aerospace anchors (**§46** — the Airbus campus bidding for defence contracts), and closure events (national policy) are **§32-scale** local shocks"); Catalogue Supplement 3 (line 716: "Defence: per §55 table + married-quarters housing typology · cadet centre"); code.json `engine.defence` entry (inbound `DefenceAPI`, "mandate events from external_world.json era script", consumers: none registered; outbound calls `engine.build`, `engine.finance`, `engine.citizens`).
**Date:** 2026-08-11 (BA-S11a, first pass)
**Status:** draft-ahead — `MOD-022` (engine.finance) and `MOD-026` (engine.build/zoning) are both `open`; this item is not in the ready queue until both land.
**Package under test:** `internal/engine/defence/` (path from `node claude-bow.js show MOD-067`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/defence/...`.

## User stories

- **US-1.** As the mandate-event script (`external_world.json`, per code.json's own registered pattern text), I need mandate timing to be data-driven from that script rather than a hardcoded per-tier `if` chain, so a future era change is a data edit, not a rebuild.
- **US-2.** As the player at each of the three named population thresholds, I need the exact mandate to fire at the exact spec-literal figure (100k → naval, 500k → army, 1M → air defence), so the thresholds are a genuine, checkable gate rather than an approximate "somewhere around here."
- **US-3.** As the player considering refusal, I need refusal to be a legal, real command that actually prevents the build while still costing grant access and reputation — a real "libertarian-city strategy with a price tag" — not either a forced build in disguise or a free pass with no consequence.
- **US-4.** As `engine.finance` and `engine.citizens` (registered outbound dependencies), I need every built facility's payroll to be a genuine, floor-protected budget line reaching real citizen records for personnel (housing/school demand), so "defence integrates, not decorates" is mechanically true.
- **US-5.** As `engine.fdi`'s (MOD-046) anchor employers, I need defence procurement to be a real contract-value output this module produces, so the spec's explicit §46 cross-reference ("procurement flows to your shipyard/rail works/aerospace anchors") is buildable once the registry catches up — flagged as blocked, not silently skipped (GR#20; BUG-058).
- **US-6.** As `engine.spiral`'s shock/blight mechanism, I need a facility closure to be routed through the same §32-scale shock machinery every other one-industry-district closure uses, so defence closures aren't a second, parallel blight model.

## Scope

Competitive grant bids (match-funded, planning-quality-weighted win rate) and formula support at low tax capacity; population-threshold mandates (100k/500k/1M) with choice-within-compliance and a genuinely-priced refusal path; facility integration (anti-cyclical payroll, personnel as citizens with housing/school draw, procurement-value output for a future `engine.fdi` consumer, closure-as-blight-shock).

## Acceptance criteria

### Functional — grants

- **AC-1 (GR#20; code.json inbound contract).** A `DefenceAPI` exists matching code.json's registered pattern "mandate events from external_world.json era script": mandate-event generation is sourced from that data file (not hardcoded per-tier logic), plus grant-bid commands and facility-siting/mandate-response commands. Check: `go doc ./internal/engine/defence DefenceAPI` shows a mandate-event accessor and `BidForGrant`/`RespondToMandate` commands; `grep -n "external_world" internal/engine/defence/*.go` (excluding `_test.go`) confirms the mandate-timing source is the data file, not a hardcoded population `if`/`switch` ladder (`grep -n "if.*population.*>=.*100000\|switch.*population" internal/engine/defence/*.go` should NOT match outside test fixtures).
- **AC-2 (§55 grant win-rate driven by match-funding AND planning quality — BLOCKED pending BUG-058 for the real edge).** Grant win probability for a bid strictly increases with (a) match-funding amount and, independently, (b) a planning-quality input — the spec's explicit "§54 planning quality raises win rate" — **blocked pending BUG-058:** no `engine.defence`→`engine.fiscal` edge is registered (engine.fiscal is the module `engine.services.md`'s own out-of-scope note assigns "municipality/planning quality" to), so this AC requires win-rate to accept planning quality via a documented pushed-input surface (mirroring `engine.attract.md` AC-3's `TermInputs` pattern) rather than a live call, pending that edge. Check: a passing test holds match-funding fixed and varies the pushed planning-quality input, asserting win probability moves in the documented direction; a second test holds planning-quality fixed and varies match-funding, asserting the same (`grep -rn "func Test.*[Gg]rantWinRate\|func Test.*[Pp]lanningQualityInput" internal/engine/defence/*_test.go`). **False-pass risk:** a win-rate function driven only by match-funding (with a planning-quality parameter accepted but never actually used in the probability calculation) would pass a test that only varies match-funding — the check requires the second, planning-quality-only variation to independently move the result, proving the input isn't decorative.
- **AC-3 (§55 formula support at low tax capacity — distinct from competitive bidding).** Below a documented tax-capacity threshold, formula support (unconditional, non-competitive funding) is available without a grant bid, distinct from AC-2's competitive pots. Check: a passing test asserts a low-tax-capacity city receives formula support with no bid submitted, and a high-tax-capacity city above the threshold receives none (`grep -rn "func Test.*[Ff]ormulaSupport" internal/engine/defence/*_test.go`).

### Functional — mandates

- **AC-4 (§55 population-threshold mandates — exact spec figures, anchored per `engine.services.md` AC-7's precedent against off-by-one).** Mandates fire at the spec-literal thresholds — 100k → naval facility, 500k → army garrison, 1M → air defence — anchored to these exact figures and facility types, not a generic "some threshold, some mandate" fixture. Check: three independent tests, each holding population just below its named threshold (asserting no mandate fires) and just at/above it (asserting the correct, named mandate fires) (`grep -rn "func Test.*[Mm]andate100k\|func Test.*[Mm]andate500k\|func Test.*[Mm]andate1M" internal/engine/defence/*_test.go`). **False-pass risk:** a test using arbitrary population figures that happen to straddle *some* boundary would pass a build whose thresholds are off by a factor, or that pairs the wrong facility with the wrong threshold — anchoring to the three literal spec figures and their named facilities closes both gaps at once.
- **AC-5 (§55 choice-within-compliance — a real, recorded player decision).** Each mandate offers at least two distinct compliant facility/siting choices plus a documented compensation-grant amount attached to compliance, and the player's choice is recorded and drives the actual `engine.build`/`engine.finance` calls (siting the chosen option, crediting the chosen compensation) rather than the engine auto-selecting. Check: a passing test presents a mandate, submits two different valid choices in two separate scenario runs, and asserts the resulting built facility's location/type differs between runs while both runs receive the documented compensation figure (`grep -rn "func Test.*[Cc]hoiceWithinCompliance" internal/engine/defence/*_test.go`).
- **AC-6 (§55 refusal path — genuinely priced, genuinely legal, the sharpest check in this section).** Refusing a mandate is a legal command that succeeds (the facility is **not** force-built), and produces documented, queryable costs: subsequent grant bids are rejected specifically because a refusal is in effect (not a generic funding-shortage rejection), and a queryable reputation penalty becomes nonzero. Check: a passing test refuses a mandate and asserts (a) the facility is not built, (b) a subsequent grant-bid attempt is rejected with a refusal-specific reason distinct from AC-2's ordinary rejection paths, and (c) a reputation-penalty accessor becomes nonzero (`grep -rn "func Test.*[Rr]efuseMandate\|func Test.*[Rr]efusalCost" internal/engine/defence/*_test.go`). **Lazy implementation this rejects:** a build that silently force-builds the facility regardless of a refusal command (treating "refusal" as flavour text with no mechanical effect) would satisfy "mandate eventually gets built" while contradicting §55's explicit "refusal is possible... a legitimate libertarian-city strategy with a price tag" — the check requires refusal to actually block the build while remaining priced, not merely be rejected outright as an illegal command.

### Functional — facility integration ("integrates, not decorates")

- **AC-7 (§55 anti-cyclical payroll — mechanical, not descriptive).** A built facility's payroll is floor-protected: under a synthetic recession scenario (broad wage-bill contraction across ordinary firms), the facility's payroll stays at or above its pre-recession baseline while a comparable ordinary employer's payroll contracts. Check: a passing test runs a recession fixture and asserts the defence facility's payroll is unchanged or floor-protected while an ordinary-employer comparator's payroll measurably contracts in the same run (`grep -rn "func Test.*[Aa]ntiCyclicalPayroll" internal/engine/defence/*_test.go`). **False-pass risk:** a facility with a documented "stable payroll" comment but no actual recession-response logic (payroll simply never wired to the recession fixture at all, on either side) would pass a test that only checks the facility's payroll is unchanged without also checking that an ordinary employer's payroll *did* contract in the same run — the check requires both halves in one scenario.
- **AC-8 (§55 personnel as citizens — real housing/schools draw, not an abstract headcount).** Facility personnel are represented as real `CitizensAPI` records requiring married-quarters housing and generating school-place demand for forces families. Check: a passing test builds a facility with a documented personnel count and asserts `CitizensAPI`'s household/housing-demand figures increase by a corresponding amount, and that forces-families' children appear in education-demand figures a downstream consumer would read (`grep -rn "func Test.*[Pp]ersonnelAsCitizens\|func Test.*[Ff]orcesFamilies" internal/engine/defence/*_test.go`). **False-pass risk:** a facility that adds "jobs: 500" as a bare aggregate number without creating actual citizen records would pass a naive "jobs exist" check while leaving housing/schools untouched, directly contradicting §55's explicit "personnel are citizens (housing! schools for forces families!)".
- **AC-9 (§55 procurement to anchor employers — BLOCKED pending BUG-058, the sharpest finding in this file).** Defence procurement contracts flow to the player's own shipyard/rail-works/aerospace anchor employers when one exists in the city — **blocked pending BUG-058:** `engine.fdi` currently has **zero** registered consumers in code.json, and no `engine.defence`→`engine.fdi` edge exists in either direction, despite §55's explicit named cross-reference ("procurement flows to your shipyard/rail works/aerospace anchors — §46 — the Airbus campus bidding for defence contracts"). Until unblocked, this AC requires a documented, queryable procurement-contract-value output on `DefenceAPI` a future `engine.fdi` consumer can subscribe to — mirroring `engine.refuse.md` AC-10's interim pattern for a blocked edge — not yet the real cross-module contract award. Check: `go doc ./internal/engine/defence` shows a procurement-contract-value accessor; `internal/engine/defence/doc.go` states the block explicitly citing BUG-058 (`grep -n "BUG-058" internal/engine/defence/doc.go`).
- **AC-10 (§55/§32 closure events reuse the shared blight-shock mechanism, not a local reimplementation).** A national-policy-driven facility closure is routed through the same shock/blight mechanism §32 defines for a one-industry-district closure (reusing the mechanic per §55's explicit "closure events... are §32-scale local shocks" cross-reference), via `engine.spiral`'s registered edge, rather than a defence-owned duplicate blight formula. Check: `grep -rn "spiral\." internal/engine/defence/*.go` (excluding `_test.go`) shows a call into the shared shock/blight mechanism; a passing test closes a facility and asserts the same class of blight/land-value/unemployment shock `engine.spiral`'s own tests expect from an equivalent-scale event (`grep -rn "func Test.*[Cc]losureShock" internal/engine/defence/*_test.go`). **False-pass risk:** a `defence.ClosureBlight()` function that produces a plausible-looking land-value hit independently of `engine.spiral` would pass a shallow "closure has consequences" check while duplicating a system GR#3 assigns to `engine.spiral` alone — the check requires the call to cross the registered interface, not merely produce a similar-shaped number.

### Error handling

- **AC-11 (GR#7).** A grant bid against an undeclared pot, or a facility-siting command against an ineligible cell, returns a registry-sourced error (new `MET-E`-range code) rather than a silently-accepted no-op. Check: `grep -n "MET-" internal/engine/defence/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]ndeclaredPot\|func Test.*[Ii]neligibleSite" internal/engine/defence/*_test.go`).
- **AC-12.** A mandate-response command (accept / choose-option / refuse) issued a second time for a mandate already responded to is rejected with a typed error, never silently overwriting the first response. Check: passing test coverage (`grep -rn "func Test.*[Dd]oubleMandateResponse" internal/engine/defence/*_test.go`).

Check: `grep -n "rand.New\|math/rand\"" internal/engine/defence/*.go` (excluding `_test.go`) finds no shared/global RNG source.
