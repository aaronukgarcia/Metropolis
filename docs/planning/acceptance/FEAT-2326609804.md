## 1. Why this item exists

FEAT-2326609802 inc9's r3 verdict (BUG-938, row 7630): the webconsole's `modeShareBalance` component was routed as `shannonModeBalanceOf(modeShareOf(ladderPointOf(s)))` — a pure function of population, never of what the player builds. Every built city, regardless of transit infrastructure, scored identically lower than a bare map at the same population, a HIDDEN POPULATION BONUS dressed up as "integrated transport reward." The honest fix is twofold: (1) inc9 reverted the score to population-keyed and marked the full `integratedTransportScoreOf` diagnostic-only (no wellbeing part, no attract multiplier), and (2) filed inc4 as the REAL prerequisite — a per-tile mode-split model in inc2's demand code that makes each tile's modal split depend on WHAT infrastructure the player has built around it (local access to rail/bus/tram within a walk radius, which is a direct player decision), not merely population. Once per-tile splits exist, inc9's integration coupling can be re-enabled: each demand tile's mode split depends on its own access, tiles are aggregated by demand weight, and the result is realisedCityWideModeShareOf(s) — a city-wide vector that genuinely reflects the aggregate transport infrastructure the player has built, not just city size. Then `modeShareBalance` becomes `shannonModeBalanceOf(realisedCityWideModeShareOf(s))`, a build-sensitive score that rewards integration.

## 2. The design in one paragraph

Each demand-generating tile (every online building with `residents` or `jobs`, as computed by inc2's `demandForecastOf`) gains a LOCAL mode-share vector keyed on TWO signals: (1) its land-use density band (residential tier from `SPECS` — the five distinct tiers residential/commercial/industrial/civic/industrial present at the game's current scale, each mapped to a density band from `mode_split_local.json`: a small `res_hut` is rural~small_town, a large `res_tower_sgp` is metro_core, etc.) and (2) its local access to transit infrastructure within a walk radius (sourced from `mode_split_local.json`'s configurable `walkAccessRadiusM`, e.g. 400 m, reused from inc9's own ASM-1528 note on interchange scope; access is discovered by walking from the tile outward via `lineSegmentIndexOf(s).tileToSegment` to find the NEAREST online rail/bus/tram segment — GR#21 sorted determinism, no repeated-traversal cost — and clamping the result to the `[0, 1]` interval via the walk-radius bound, so "has a bus station 100 m away" and "has a metro within 200 m" both contribute to a local access band key: `local_access_high`/`local_access_medium`/`local_access_low`/`local_access_none`). The per-tile vector is looked up in `mode_split_local.json` using a composite key like `{landUseDensityTier: 'res_tower_nyc', localAccessBand: 'local_access_high'}` — entries not present in the table fall back to the city-level split from inc2 to ensure no tile ever reads `undefined` (honest fallback, not a silent absence). All four outputs from inc2 (person-trips split by mode, freight tonnes, freight vehicle-trips, demand aggregated into line classes) are recomputed using per-tile vectors instead of the city-level split — the city-total person-trips count is unchanged (conservation: Σ per-tile person-trips = Σ city-level person-trips by construction, because fallback = city row), but the MODE COMPOSITION of those trips is now spatially varied. A new export `realisedCityWideModeShareOf(s)` computes the trip-WEIGHTED sum of every per-tile vector to produce a CITY-WIDE mode split that reflects the aggregate access the player has built — this is the basis `modeShareBalance` should use (rewrite as `shannonModeBalanceOf(realisedCityWideModeShareOf(s))` in a follow-up inc9 coupling increment). `forecastLineUsage`'s total demand per line class (person-trips summed over all modes and tiles for one class) stays exactly conserved — each class's demand is the same whether computed city-wide or per-tile-then-aggregated, never a divergence introduced.

## 3. Acceptance Criteria

### Per-tile land-use density band mapping

**AC-1 — each building's land-use density tier maps deterministically to a density band in `mode_split_local.json`.**
The five SPECS resident/commercial/industrial/civic categories (civic is a placeholder for police/fire/health/school/etc.) each span multiple tiers with different populations. A `res_hut` (tier 0, 8 residents) is rural~small_town band; a `res_tower_sgp` (tier 4, 20,000 residents) is metro_core or megacity band. The mapping is deterministic and sourced from `mode_split_local.json`'s own `landUseDensityMapping` section (never hand-typed in TS), using the TIER (not the raw `capacityRaw` field) as the lookup key because tier already encodes the building's SCALE class. Every SPECS id that appears in any online building must be present in the mapping at load time; a missing entry is fail-closed via a registry error (GR#7).
**Check:** a fixture with one `res_hut` (tier 0) and one `res_tower_sgp` (tier 4) asserts each building maps to the EXACT SAME `densityBand` value that is sourced from `mode_split_local.json`'s own mapping table, never a hand-computed interpolation.
**False-pass note:** a test that hard-codes the expected band string will pass even if the mapping is read from the WRONG data file (e.g. the old inc0 `mode_share_by_density.json` instead of the new `mode_split_local.json`) — the check above guards against that; a value-match alone is not sufficient.
**Mutant:** replace the `mode_split_local.json` mapping read with a hand-computed tier→band formula (e.g. tier < 2 → rural, tier >= 3 → metro_core) — reds the exact-source check the moment the mapping changes in the data file and the hard-coded formula does not follow.

### Per-tile local-access band discovery

**AC-2 — discover local access to rail/bus/tram infrastructure via a bounded walk from each tile, deterministic and efficient.**
For each demand-generating tile at grid position `(tx, ty)`: walk outward via Manhattan distance up to the configured walk radius (e.g. 400 m = ~8 tiles at 50 m/cell, sourced from `mode_split_local.json`'s `walkAccessRadiusMetres`, not a hand-typed literal — GR#15). At each distance, check EVERY online rail-carrying segment (class ∈ `['heavy_rail', 'hs_rail', 'metro', 'tram']`) and EVERY online bus segment (class = `'bus_lane_variant'` or `'bus_priority'` or `'bus_mixed_traffic'`, the three bus classes defined in `roads.json`) reachable via `lineSegmentIndexOf(s).tileToSegment`: for each segment's tile, if the segment's tile is within the walk radius of `(tx, ty)`, record that segment's class and nearest-access distance. Aggregate: if ANY rail segment is found within radius, set `hasRailAccess = true`; if ANY bus segment is found, set `hasBusAccess = true`. Map to a local-access band: both rail AND bus ⇒ `local_access_high`; rail XOR bus ⇒ `local_access_medium`; neither rail nor bus, but within walk radius of an online station (via `stationLinks(s)` — binary adjacency only, not a separate catchment) ⇒ `local_access_low`; no transit anywhere ⇒ `local_access_none`. GR#21: sorted iteration (a tile is always checked in a consistent order, and ties are broken by sorted segment ids, never by map-range order or discovery order).
**Check:** two residential demand-generating tiles, one adjacent to both a `heavy_rail` and a `bus_priority` segment, one surrounded by only commercial buildings (no transit nearby), assert they map to `local_access_high` and `local_access_none` respectively.
**False-pass note:** a test that only measures distance (e.g., "is there a segment within 400 m") without checking whether that segment IS actually rail/bus will pass even if the class classifier is broken — the check must verify the ACTUAL class assignment, not merely the radius logic.
**Mutant:** return `local_access_high` unconditionally (no class distinction) — reds any fixture where only one class is present (e.g. all commercial neighborhoods with bus but no rail must fall to `local_access_medium` or `local_access_low` depending on the band rules above, not `high`).

### Per-tile local mode-share vector lookup and fallback

**AC-3 — per-tile mode split reads a composite (land-use, local access) key from `mode_split_local.json`; no second mode model, fallback to city row.**
Each tile's lookup key is `{landUseDensityBand: (from AC-1), localAccessBand: (from AC-2)}`. `mode_split_local.json` contains a table of entries, keyed by `landUseDensityBand + '_' + localAccessBand` (e.g. `"res_hut_rural~small_town_local_access_none"`, `"res_tower_sgp_metro_core_local_access_high"`), with mode-share vectors matching inc2's own `modeShare` shape (11 keys: walk/bicycle/car/motorbike/taxi/bus/tram/metro/heavy_rail/hs_rail/ferry, each a fraction summing to 1.0 across the mode set). If a composite key is not found in the table, fall back to the CITY-WIDE row from `modeShareOf(ladderPointOf(s))` (the same ladder point inc2 already uses) — never invent a default, never read the old inc0 `mode_share_by_density.json` table per-tile (that would be a SECOND density model, violating GR#3 as inc2 AC-2 forbids). A lookup failure on the city fallback is a registry error (GR#7).
**Check:** a fixture with tiles in 5 different (densityBand, localAccessBand) combinations asserts each tile's `perTileLocalModeShareOf` vector matches the EXACT entry from `mode_split_local.json` sourced (not the city row, and not a hand-computed fallback); a tile whose composite key is NOT in the table asserts it returns the city-level vector exactly (byte-identical to `modeShareOf(ladderPointOf(s))`).
**False-pass note:** a composite key that "happens to match" the city row by coincidence will pass a value-equality check even though the tile is incorrectly falling back — the check must assert WHICH SOURCE was used (composite vs city), not merely the number. Add a comment note or a debug-only field to the vector naming its source (dropped in production).
**Mutant:** always return the city row, ignoring the composite key entirely — reds any fixture where a specific composite key's vector DIFFERS from the city row (all tiles must produce the same split, breaking AC-2's local-access differentiation).

### Aggregation into realised city-wide mode share (trip-weighted)

**AC-4 — `realisedCityWideModeShareOf(s): Record<string, number>` — trip-weighted sum of every per-tile vector into a CITY-WIDE vector.**
For each demand-generating tile in `demandForecastOf(s)`, multiply that tile's `perTileLocalModeShareOf` vector by the tile's PERSON-TRIP count (residents + workers, from inc2's own occupancy-fraction calculation, AC-1 of the inc2 doc) to weight the vector. Sum across all tiles, then RENORMALIZE the result to sum exactly to 1.0 (a correction for floating-point drift; the sum should already be very close to 1.0 because each tile's vector sums to 1.0 by construction, so renormalization is tiny and GR#15 — no hand-typed divisor). The result is a CITY-WIDE mode split that reflects the aggregate access the player has built. No tile is double-counted; every tile's trips are weighted exactly once.
**Check:** a fixture with 2 residential demand tiles, tile A at `modeShare {car: 0.5, bus: 0.5}` with 100 person-trips, and tile B at `modeShare {car: 0.3, bus: 0.7}` with 200 person-trips, asserts the city-wide result is exactly `{car: (0.5*100 + 0.3*200) / 300, bus: (0.5*100 + 0.7*200) / 300}` = `{car: 0.3667, bus: 0.6333}` (computed by hand, matched to floating-point precision `1e-12`).
**False-pass note:** a plain arithmetic average (ignoring trip weights) will pass on a fixture where all tiles have equal trip counts — the Tester must use UNEQUAL weights, per the check above.
**Mutant:** drop the renormalization (leave the sum close to but not exactly 1.0) — on a fixture where floating-point drift accumulates (many tiles, diverse vectors), this will produce a vector summing to 0.9999 or 1.0001, breaking the conservation invariant and any downstream clamp-to-[0,1] logic that relies on the sum.

### Demand conservation (no divergence introduced by per-tile split)

**AC-5 — demand conservation: TOTAL person-trips are conserved; per-class totals legitimately diverge from the city-wide computation.** (Lead amendment 2026-09-11 after the round-2 verdict, BUG-1001: the original wording - per-line-class totals identical between the per-tile and city-wide computations - is self-contradicting with AC-2/AC-4, because per-tile differentiation IS the feature: on the mixed fixture the per-class divergence is car 1.1656 / heavy_rail 0.5264 person-trips while the grand total matches 37.6 vs 37.6 exactly.)
For the same tile set compute the total person-trips in TWO ways: (1) the city-wide method (inc2's `modeShareOf(ladderPointOf(s))` applied to every tile, summed over all classes), and (2) the per-tile method (`perTileLocalModeShareOf` applied to each tile, summed over all classes). Assert the two GRAND TOTALS are identical to 1e-9, and assert that on a fixture with differentiated tiles at least one PER-CLASS total differs by more than 1e-6 (the divergence must be real, or the per-tile split is not being applied).
**Check:** three fixtures (single-class, mixed land use, a rail city) assert grand-total conservation to 1e-9 and a non-trivial per-class divergence on the differentiated ones; every per-tile vector sums to 1 within the loader tolerance (1e-9).
**False-pass note:** a test that asserts only the grand total cannot distinguish "per-tile applied" from "city-wide applied everywhere" - the per-class divergence assertion is what proves the split is live; a fixture with identical vectors on every tile is vacuous for that half.
**Mutant:** drop the per-tile renormalisation (a vector no longer summing to 1) - grand-total conservation reds; apply the city-wide vector at the tile level - the divergence assertion reds.

### Determinism and cost (GR#21, AC-9 shape)

**AC-6 — `perTileLocalModeShareOf` and `realisedCityWideModeShareOf` are `memoOnState`, pure functions of `s`, byte-identical across repeated calls and a StrictMode double-mount.**
No `Date.now`, no `Math.random`, no `localStorage`; GR#21 sorted iteration in the walk-radius BFS and in the trip-weighting loop (no map-range order). Cost is O(tiles × walk-radius-bounded-segments + modes), independent of citizen count — the walk is bounded by `mode_split_local.json`'s `walkAccessRadiusMetres` (a constant, e.g. 400 m = ~8 tiles), never by the city's own diameter or occupied area. Per-tile trip counts are reused from inc2's already-computed `demandForecastOf` (no recalculation, no `s.citizens` array walk).
**Check:** `grep -n "Date.now\|Math.random\|localStorage" webconsole/src/sim/trafficDemand.ts` (excluding tests) returns no matches in the new per-tile code; a 10-rerun determinism test (JSON-identical); a 5,000-building fixture timing smoke test (local profiling only, no wall-clock assertion in CI — mirrors inc2 AC-9).
**Mutant:** implement the walk-radius search as a full-map scan instead of bounded BFS — the cost becomes O(tiles × MAP_W × MAP_H), red on a large-map timing test.

### Build health / no literal modes or bands

**AC-7 — data-sourced, registry errors on missing tables, no hand-typed magnitude.**
Every mode id in `perTileLocalModeShareOf` and `realisedCityWideModeShareOf` output is sourced from `mode_split_local.json`'s own modeIds array or the fallback `modeShareOf(ladderPointOf(s))`'s own keys, never a literal string in TS (`'car'`, `'bus'`, etc.). Every composite lookup key is built from the data-sourced density band and access band names, never a hand-typed string. Walk-radius in metres is read from `mode_split_local.json`'s `walkAccessRadiusMetres`, not a hand-typed `400` or `800` constant. A missing composite key in the lookup table is NOT a silent fallback — the log/retry logic records a registry error (GR#7) when a key is missing the SECOND time it is encountered (one-shot, same pattern as inc2's freight-sector-gap logging, BUG-851 model — the first encounter on a hot path is silently demoted to fallback, the second and beyond log the gap).
**Check:** `grep -n "^\s*['\"](walk|car|bus|tram|metro|rail|hs_|local_access|rural|small_town|urban|density)\b" webconsole/src/sim/trafficDemand.ts` (excluding test data) returns no hand-typed mode/band literals; a malformed `mode_split_local.json` (missing `walkAccessRadiusMetres`, or modeIds absent) fixture asserts the registry error throws at module-load time, fail-loud (mirrors inc2 AC-8's shape).
**Mutant:** hard-type a walk radius (e.g. `const WALK_RADIUS_TILES = 8`) instead of reading from the config — caught when `mode_split_local.json`'s actual radius is edited in the fixture copy and the hard-typed value does not follow.

## 4. Decisions for Aaron (recommendation given, not blocking)

**D1 — `mode_split_local.json` structure: flat composite-key table, or nested [landUseDensityBand][localAccessBand] object?**
**Recommend: flat composite-key table** (e.g. `{ "res_hut_rural~small_town_local_access_none": { "walk": 0.2, "car": 0.6, ... }, ... }`) for consistency with inc0's own flat design. A nested object is more readable (`json.res_hut.rural['local_access_none']`) but the flat design is already established as the pattern; keep it. The table can be GENERATED from a higher-level spec (a matrix of rows × columns) at build time if readability is a concern.

**D2 — fallback for a missing composite key: log-once per GAME SESSION, or fail-closed at load time?**
**Recommend: log-once per game session per the BUG-851 model** — a missing entry in `mode_split_local.json` is a data-build issue, not a runtime error. The first encounter silently demotes to the city row (cheap, no user impact); the second encounter (different tile, same missing key) logs a registry error so the developer sees the gap in the session's logs. If a table LOADS with a missing entry, fail-closed at module-load time (GR#7 — all tables are validated on import, never silently partial-loaded).

**D3 — transit mode class distinction: should "has a bus stop" and "has only a bus stop, no rail" map to DIFFERENT access bands?**
**Recommend: yes, as stated in AC-2** — `local_access_high = rail AND bus`, `local_access_medium = rail XOR bus`, `local_access_low = station-only`. Aaron may want a different banding (e.g., `high = anything`, `medium = only bus`, `low = none`); that is a `mode_split_local.json` data edit and a tweaked AC-2 comment, not a code change.

**D4 — walk-radius units: metres (e.g. 400 m) or tiles (e.g. 8 cells)? Should `mode_split_local.json` carry both for clarity?**
**Recommend: metres in `mode_split_local.json` (with a comment noting the conversion to cells at 50 m/cell), matching the traffic-data convention** — `traffic.json` already uses metres for other bounds (ASM-1526 on traffic.json fields, if any exist), and a metre-based number is more portable than a grid-specific tile count. The TS code converts metres to tiles at load time: `radiusTiles = Math.ceil(radiusMetres / METRES_PER_TILE)`.

## 5. New data fields

A new JSON file `data/traffic/mode_split_local.json` (or an extension of the existing `mode_share_by_density.json`, Aaron's choice at build time) contains:
- **`walkAccessRadiusMetres`** (number, e.g. 400) — the walk-radius bound for the access-band discovery (AC-2), sourced (not hand-typed).
- **`landUseDensityMapping`** (object, map of `specId` → `densityBand` string) — every buildable SPECS id mapped to its density band from `mode_share_by_density.json` or a new band set (e.g. `{ "res_hut": "rural~small_town", "res_tower_sgp": "metro_core", "off_tower": "dense_urban", ... }`).
- **Mode-share table** (object, map of composite key `"densityBand_accessBand"` → mode-share vector) — e.g. `{ "res_hut_rural~small_town_local_access_none": { "walk": 0.2, "bicycle": 0.05, ..., "ferry": 0 }, "res_tower_sgp_metro_core_local_access_high": { ... }, ... }`. Every vector sums to 1.0 exactly. Every missing composite key falls back to the city-level split; the table need not be exhaustive (e.g. a fully-comprehensive table would be 5 landUseDensityTiers × 4 accessBands × 11 density bands = 220 entries, but most combinations are not distinct and can be omitted, relying on fallback for the rest).
- **Provenance and source notes** (as per inc0's own convention) — every numeric entry includes a data-backed `source` (e.g. "derived from mode_split_by_density.json for metro_core band, adjusted for local bus access penalty per HITS 2023 transit-frequency effect").

Error codes (pre-assigned, GR#7): **MET-V955** (PerTileModeSplitLocalAccessBandMissing), **MET-V956** (PerTileModeSplitTableMalformed), **MET-V957** (PerTileModeSplitLandUseMappingMissing), **MET-V958** (PerTileModeSplitWalkRadiusMissing), **MET-V959** (PerTileModeSplitModeVectorInvalid).

## 6. Assumptions

- **ASM-1530** — per-tile land-use density band is determined by TIER (the building's scale class), not by its current occupancy or the surrounding neighborhood density. **What breaks if wrong:** two identical buildings placed in a sparse rural area vs a dense urban center would map to the SAME density band (tier-based) rather than different bands (location-based), so the local access (via walk-radius discovery) becomes the ONLY differentiator. A future increment could introduce a "surrounding density" lookup (what density band is most common within N cells of this tile?) to refine the mapping, but for inc4, tier is the canonical signal. This is acceptable because TIER encodes the building's own footprint/capacity class, and larger buildings (towers) are inherently more likely to attract transit investment relative to small sheds (huts).
- **ASM-1531** — local access is BINARY per mode class (rail: yes/no; bus: yes/no), not a continuous distance-decay function. **What breaks if wrong:** a station 5 m away and a station 395 m away (just inside the 400 m walk radius) both contribute equally to `hasRailAccess = true`. A future increment could introduce distance-decay weights, but inc4 keeps it simple: within radius = true, outside = false. This is acceptable because the walk radius is already chosen empirically (400 m is a typical "15-minute walk" threshold in planning literature).
- **ASM-1532** — `stationLinks(s)`'s binary adjacency check is sufficient for the `local_access_low` case. **What breaks if wrong:** a station that is adjacent (by road connection) to ANY online building might be counted as "accessible" even if it is surrounded by cliffs or water. `stationLinks` already filters for road-connected stations (the "binary" part), so this is satisfied by inc2's own design (AC-2 of inc2 references `stationLinks`'s definition at `data.ts:3020`). If a future update makes stationLinks ambiguous, this assumption must be re-examined.
- **ASM-1533** — bus-lane and tram-track mode classes are NOT reached via the walk-radius discovery today because `roadClassIdOfSegment` (data.ts:225) only produces 5 road classes (tiers 1–5: `residential_street`/`avenue_2_plus_2`/`two_lane`/`dual_carriageway`/`motorway`), never `bus_lane_variant` or `tram_track_variant` (both are real `roads.json` classes, but no spec builds them yet). **What breaks if wrong:** the `local_access_high` band cannot be reached by any tile today, only `_medium` and `_low` — this is honest, documented in the out-of-scope section below. No test asserts that `local_access_high` is reachable; the AC checks only verify the LOGIC, not the reachability.
- **ASM-1534** — trip-weighting the per-tile mode vectors converges to the city-wide split in the limit (all tiles have the same vector, or all tiles have identical trip counts). **What breaks if wrong:** a city with one massive tower and nine huts would weight the tower's local mode split much higher than the huts' in the city-wide aggregate — this is CORRECT and INTENDED (a downtown tower is more influential than an outlying shed). If Aaron wants a geographic-area-weighted average instead (each grid cell = 1 unit weight, regardless of occupancy), that is a different model (dec D1/D2, not a bug fix).

## 7. Out of scope

- **Bus-lane and tram-track placeable specs** — `bus_lane_variant` and `tram_track_variant` road classes exist in `roads.json` but are unreachable via `roadClassIdOfSegment` because `ROAD_CLASS_ID_OF_TIER` (data.ts:2000-ish) only maps tiers 1–5 to the five listed road classes. Making these two classes reachable requires a new placeable spec in `SPECS` with a proper `tier` and kind, or an edit to the tier→class mapping. That work is out of scope for inc4 — a **later increment will add the placeable specs and the mapping update** (noted in FEAT-2326609792's inc5 sub-brief). Until then, `local_access_high` (rail AND bus) is not reachable, and the mode-split local table will not use it. AC-2 and AC-3 are STILL CORRECT: the logic is sound, the test is honest about the structural gap (ASM-1533 above).
- **Distance-decay mode choice** — per-tile access is binary (within radius = true; outside = false), not a continuous falloff with distance. A future increment might weight a 50 m walk higher than a 350 m walk; inc4 keeps it simple.
- **Per-building occupancy variance** — per-tile actual occupancy is still a UNIFORM city-wide fraction (inc2's ASM-1495), not per-building. A sparse new-build residential block would use the same occupancy-fraction scaling as a full old-stock block, even though they are spatially different. Refining this requires a future per-building occupancy field (beyond the scope of the traffic epic).
- **Purpose-based mode split** — every mode-share vector is all-purpose (commute + shopping + leisure + business combined), never broken down by trip purpose. A future update to `mode_split_local.json` could add purpose fields, but inc4 uses the all-purpose rows from inc0.
- **Interchange-adjacency coupling into `perTileLocalModeShareOf`** — inc9's AC-4 defines `interchangeAdjacency` as the share of online, road-connected stations also adjacent to `bus_lane_variant`/`tram_track_variant` segments. A future enhancement might reward a tile's mode split if it is near an interchange (e.g., `local_access_interchange = true` at a station-to-bus-lane tile). inc4 addresses only general rail/bus/tram access, not interchange-specific logic. The follow-up is FEAT-2326609804's own AC-8 note (the coupling path once FEAT-2326609809 or a similar increment adds interchange specs).
