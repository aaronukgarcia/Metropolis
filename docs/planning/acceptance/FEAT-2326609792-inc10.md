## 1. Why this item exists

Aaron's epic brief (verbatim): "demand/mode-share/congestion/response-time overlays and a Transport screen." The Lines overlay already exists (inc3, inc4) for network capacity saturation and emergency response tint; this increment extends it with read-outs for six additional traffic metrics on the map (demand, mode-share split, congestion, parking/fuel shortfalls, wear condition), and creates a single Transport screen panel that consolidates every traffic statistic — commute times, gridlock, emergency coverage, parking/fuel/EV shortfalls, road wear and repair status, the four policy effects, and the safe-road score — into one read-only summary, so the player can see the full consequences of their transport choices without bouncing between six tabs and a map overlay.

## 2. The design in one paragraph

**Map overlays (AC-1).** Five new tints, rendered like the existing Lines response-time tint (§2, inc4): demand tiles per `demandForecastOf` as a per-tile count/intensity (pale at 10 trips, saturated at 200+, no hand-typed bounds — data-driven from fixture-observed ranges), mode-share as the dominant mode's share (car/transit/walk, one of three band colours per mode at tiles over 50 persons), congestion via `segmentDelayOf`'s v/c read-out on every segment (red if over 0.8, yellow 0.5–0.8, green under 0.5 — matching the threshold semantics `congestion.json` sets), response-time **ambulance** (same inc4 tint as inc4, reused not repainted), parking shortfall per `parkingShortfallOf` (red where demand > supply), fuel/EV shortfall per `fuelAndEVDemandOf` (red where demand > capacity), road wear condition per `roadWearBySegment`'s cumulative ESAL (condition `1.0` fresh → `0.0` failed, green→red band). Every overlay **toggles independently** on a per-service/per-metric toggle set (not one monolithic "Traffic" button) — the new toggles are added AFTER the existing "Lines" group in the button panel (AC-6). A tile with no data for an overlay (zero demand, unreachable ambulance, no segment) renders with NO tint, never a fabricated worst-case value (honest-absence contract, mirroring inc3/inc4). **Transport screen (AC-2).** A read-only panel (same idiom as WellbeingTab, AC-2 references) with section headers and metric rows: (a) commute p50/p90 and gridlock share; (b) emergency coverage (ambulance/fire/police, separate rows); (c) parking and fuel/EV shortfalls; (d) road condition summary and repair deferred count; (e) the four policy effects (ownership quota, road pricing, bus priority, integrated ticketing — all quantified effects from `busPriorityCapacityInfoOf`, or the policy state itself); (f) safe-road score and integration score (both from the snapshot, no live derivation). Every number is pulled from `s.trafficSnapshot` (cadence-refreshed, never live derivation — BUG-935/BUG-936 class, perf bound AC-7) or memoOnState exports with zero structural additions to SimState.

## 3. Acceptance Criteria

### Map Overlays

**AC-1 — Five new overlay tints, folded into the existing "Lines" toggle group, toggled independently, data-driven bounds, honest absence.**

New overlay tints render ONLY when `showLines === true` (exact same conditional as inc4's response-time tint, lines 641–707 `MapView.tsx`). Each overlay tint reads from memoised exports or the snapshot — no new state, no engine change, no per-tick overhead beyond the assignment's existing op count (AC-7 structural pin). Five toggles are added to the left panel's button group AFTER the existing Water/Power/Lines/Refs buttons (exact UI location: post-dispatch time determination, not specified here; AC-6 placeholder).

1. **Demand overlay** — per-tile trip count from `demandForecastOf(s)`. Bound: [10 trips (pale, 25% alpha) … 200+ trips (saturated, 85% alpha)]; a tile with 0 trips is absent (no tint). **Check:** a fixture with 9 tiles at 10/30/50/100/150/200/250/300/400 trips asserts each tile's alpha is non-decreasing and the 400-trip tile's alpha equals the 200-trip tile's (saturation-capped at 85%). **False-pass note:** a fixture with ONLY the 200-trip and 400-trip cases would pass even if the bound were `[10…100]` (both clamp to 85%, indistinguishable) — test the full range. **Mutant:** hand-type the bounds `[50…150]` — reds the 10-trip underflow and 200-trip overflow checks.

2. **Mode-share overlay** — per-tile dominant mode (the mode with the largest share from `demandForecastOf[tile].modeShareEstimate`, a field confirmed live on HEAD via grep). Three colours (e.g. car = red, transit = blue, walk = green); alpha scaled by dominance share so a pure car tile is 85%, a split 50/50 is 42.5%. A tile with <50 person-trips is absent (insufficient to colour meaningfully). **Check:** a fixture where two adjacent tiles have identical trip counts but opposite mode dominance (tile A 70% car, tile B 70% transit) asserts DIFFERENT fill styles; a tile with 40 person-trips is absent (no tint). **False-pass note:** a test that only checks "the colour is different" does not prove the alpha scaled — must assert the specific alpha value is half the pure-dominance value. **Mutant:** use `mean(modeShare)` instead of `max(modeShare)` — reds the opposite-dominance fixture (the two tiles read identically in alpha even though colours differ).

3. **Congestion overlay** — per-segment v/c ratio from `segmentDelayOf(s)`, three-band: red if v/c > 0.8 (alpha 85%), yellow if 0.5–0.8 (alpha 50%), green if < 0.5 (alpha 25%), or absent if segment has no entry in `segmentDelayOf` (zero flow, honest absence per inc3 AC-4). **Check:** a fixture with three identical segments (same road class, same length) but different flow levels (forced v/c to 0.3/0.65/0.95) asserts three distinct colours and alphas matching the exact bands above. **False-pass note:** a fixture where every segment passes `v/c < 0.8` cannot distinguish "three-band logic" from "two-band (green everywhere)"  — must include a band-boundary segment (v/c ~0.8). **Mutant:** use a continuous-gradient alpha (alpha = v/c) instead of the three-band logic — reds the boundary check (the 0.65 segment's alpha changes from 50% to 65%).

4. **Parking shortfall overlay** — per-tile shortfall from `parkingShortfallOf(s)`, red (85% alpha) where demand > supply, absent (no tint) where supply >= demand. **Check:** a fixture with two demand tiles at identical predicted occupancy, one with excess parking and one at capacity-only, asserts the first is absent, the second is tinted red; a neutral-change city (no shortfall change) asserts the tint draw count unchanged. **False-pass note:** a test checking "`shortfall !== 0`" without asserting `.shortfall > 0` would pass on a mutant that showed green for negative shortfall (capacity excess) — must assert exactly red, not any non-zero colour. **Mutant:** render green where shortfall < 0 (capacity abundance) instead of absent — reds the neutral-change fixture (tint draw count increases even though shortfall didn't change).

5. **Fuel/EV shortfall overlay** — per-tile shortfall from `fuelAndEVDemandOf(s)`, red (85% alpha) where total demand (fuel litre-km + EV charge-point km) exceeds capacity (available fuel stations + EV charge points), absent where capacity >= demand. **Check:** a fixture with a bare-roads city (zero fuel/EV infrastructure) asserts every demand tile is tinted red; a city with one fuel station and 10,000 vehicle-km demand asserts red (unless `fuelLitresCapacity >= 10,000km × litreDemandFactor`, a literal drawn from `fuelAndEVDemandOf`'s own return contract). **False-pass note:** a test that only checks "the tint is present or absent" cannot distinguish "fuel shortage" from "EV shortage" — must assert that BOTH fuels contribute to the aggregated shortfall (test a city with zero EV but high fuel demand, and vice versa). **Mutant:** hard-code fuel shortfall check only (ignore EV) — reds the EV-only test.

6. **Road wear overlay** — per-segment condition from `roadWearBySegment`, mapped to a 1.0 (fresh, green, 25% alpha) → 0.0 (failed, red, 85% alpha) band; segment absent from the wear map (zero wear to date, or freshly built) renders absent (no tint, same as fresh green). **Check:** a fixture with a segment worn to 0.5 condition asserts the intermediate tan/orange tint and alpha matching the linear interpolation between green 25% and red 85% (e.g. 55% alpha). **False-pass note:** a fixture that only checks "the colour changes" without asserting the CONDITION VALUE is actually read would pass on a mutant that uses `tick / MAX_TICKS` (wall-clock, GR#21 violation) instead of the condition field — must assert the colour stays CONSTANT across multiple ticks while the condition value is held. **Mutant:** use condition^2 (non-linear warping) — reds the 0.5-condition check (computed alpha differs from the linear interpolation).

### Transport Screen

**AC-2 — New Transport screen panel, same idiom as WellbeingTab (populationTabs.tsx:30-76), read-only, every number from `trafficSnapshot` or a memoOnState export.**

New `transportTab.tsx` export a `TransportTab()` component following the exact structure: (1) a "tiles" div with key summary metrics (commute p50, gridlock share, ambulance coverage); (2) section headers (h4); (3) list divs with rows, each row bearing a label, a bar/indicator, and a value. NO new `SimState` fields added (every metric read from snapshot or memoOnState). NO per-tick computation (all numbers refresh on the traffic assignment cadence like wellbeing parts do, AC-7).

**AC-3 — Commute section (p50, p90, gridlock).**
Pulls from `trafficSnapshot.medianCommuteMinutes` (p50) and `trafficSnapshot.gridlockShare`. Renders "Commute p50", "Commute p90" (rows), and "Gridlock share" (row with a green→red bar identical to wellbeing's own bar style). A city with no commute (zero commuters) reports `0` for times and `0%` for gridlock, never `NaN`/`undefined`. A city where `trafficSnapshot` is absent (legacy save, or pre-traffic-tick) renders "Not yet available" placeholders, never crashes.
**Check:** a fixture where commute times are forced to 15/25 minutes and gridlock to 0.3 asserts the exact values render, and two fixtures with identical times but different gridlock share visibly different bar fills; a `trafficSnapshot`-absent city asserts the Transport tab still renders with placeholder text. **False-pass note:** a test that only checks "the panel renders" without verifying the ACTUAL VALUES would pass on a mutant that hard-codes 0 for all metrics — must assert exact values are read from the snapshot. **Mutant:** read commute times from `demandForecastOf(s).length / 1000` (a fabricated proxy) instead of the snapshot — reds a fixture where snapshot and proxy disagree (easily forced by varying commute routes vs demand count).

**AC-4 — Emergency coverage section (three service rows).**
Pulls from `emergencyCoverageOf(s, service)` for ambulance, fire, and police. Each row: label (e.g. "Ambulance coverage"), bar (green if `coverageShare >= targetMinutesUrban/Rural`, red else), value (as percentage, e.g. "87%"). Services are listed in the order ambulance, fire, police (mkey the order into AC if Aaron wants a different sequence). A city with zero online stations of a service reports `0%` coverage. A city with unreachable demand reports three coverage values, one per service (not a single blended "emergency coverage" — each service's own metric).
**Check:** a fixture with two services at 70%/90% coverage asserts both render with their exact percentages and the bars are distinctly different colours/alphas. **False-pass note:** a test that renders three identical-green bars would pass on a mutant that used the SAME service (ambulance three times) — must grep the rendered labels (or the function call) to assert all three services are present. **Mutant:** hard-code all three to the ambulance coverage value — reds a fixture where services differ (any difference in fire vs police coverage would be hidden).

**AC-5 — Parking and fuel/EV section (two rows).**
Pulls from `parkingShortfallOf(s)` and `fuelAndEVDemandOf(s)`. Row 1: "Parking shortfall", value = sum of all tiles' shortfall (vehicles lacking a parking space, clamped to >= 0). Row 2: "Fuel/EV shortfall", value = max(fuel-km demand - fuel-km capacity, EV-charge-point-km demand - capacity, 0) — a combined metric showing the bottleneck across both fuels. Each row includes a bar: green if shortfall = 0, red if > 0, alpha scaled by shortfall as a fraction of (total parking spaces OR total fuel/EV capacity) so a city at 5% shortfall is pale and 95% shortfall is vivid red. A city with zero infrastructure (no parking buildings, no fuel stations) reports 100% shortfall on both (red, vivid).
**Check:** a fixture with identical parking shortfall counts (e.g. 1000 vehicles) but different population bases (5000 vs 50000 citizens) asserts the same shortfall LOOKS different (different alpha, since the bar scales relative to capacity) — the percentage-of-capacity framing is key. **False-pass note:** a test that only checks "shortfall > 0 → red" does not verify the SCALING — must test two fixtures with the same shortfall value but different capacities and verify the alpha is proportionally different. **Mutant:** use absolute shortfall as alpha (no capacity scaling) — reds the equal-shortfall-different-capacity fixture (both alphas become identical even though capacities differ).

**AC-6 — Road wear section (condition and repair status).**
Pulls from `roadWearBySegment` and `roadRepairDeferredSegmentIds`. Row 1: "Road condition", value = average of all segments' condition values (Σ condition / segment count), rendered as `${(value * 100).toFixed(0)}%` (e.g. 75% = good, 10% = failing). Row 2: "Repairs deferred", value = count of segments in `roadRepairDeferredSegmentIds` (a list maintained by engine.ts's `advanceRoadWear`). Each row has a bar: for condition, green if >= 0.7, yellow 0.3–0.7, red < 0.3; for deferred repairs, green if 0, red if > 0 (no yellow band for a binary state). A city with zero segments reports condition = 1.0 (no wear, all fresh).
**Check:** a fixture with 2 segments, one at 0.8 condition and one at 0.2, asserts the average is 0.5 (yellow band, 50%) exactly. A fixture with one deferred repair asserts the count = 1 and the bar is red. **False-pass note:** a non-strict inequality check (e.g. `>=` instead of `>`) on the band boundary (condition = 0.3) could pass both green and yellow tests — must use a 0.3-exactly fixture to verify the boundary is exclusive. **Mutant:** sort the condition values and report the median instead of the mean — reds an asymmetric wear distribution (e.g. 90% good, 10% failed: mean 50% vs median 90%).

**AC-7 — Policy effects and safe-road score section (five rows).**
Pulls from `busPriorityCapacityInfoOf(s)` (the four policy effects), `s.policies` (the policy states themselves), `trafficSnapshot.safeRoadScore`, and `trafficSnapshot.integratedTransportScore`. Row 1–4: one row per policy (ownership quota, road pricing, bus priority, integrated ticketing). Each row label includes the policy name and its current setting (e.g. "Ownership quota: 0.8" or "Road pricing: £5"), and the value is the measured effect (a percentage or multiplier, e.g. "−5% traffic" or "−£2M annual"). Row 5: "Safe-road score", value from snapshot (0–100, rendered as percentage); bar green if >= 70, yellow 50–70, red < 50. Row 6: "Integration score", value from snapshot (0–1 or 0–100, depending on snapshot representation — **CHECK snapshot field on HEAD before AC-6 implementation**), no bar (diagnostic only, per inc9 ruling).
**Check:** a fixture where bus priority is ON vs OFF asserts the row's effect value changes (or becomes "inactive"). A fixture with forced safe-road score to 0.5 asserts the yellow band, 50 or 50% rendering, and bar colour. **False-pass note:** a test that only checks "a policy row exists" would pass even if the effect values were all `0` or hard-coded — must assert the effect actually CHANGES across policy configurations (e.g. toggle a policy ON/OFF and verify the effect value changes). **Mutant:** report the policy NAME only, without the effect value — caught the moment a second row is added and the value field vanishes.

**AC-8 — Perf bound: overlay paint cost does NOT add a traffic assignment; snapshot or memoOnState only; determinism (GR#21).**
No new assignment runs during the overlay render pass (MapView's draw effect). All overlay tints derive from `segmentDelayOf`/`assignedFlowOf`/other memoOnState exports (cached if state unchanged) or the snapshot (zero derivation cost). **AC-9 — Non-finite snapshot values are guarded; Transport screen stays finite always.**

## 4. Decisions for Aaron (recommendation given, not blocking)

**D1 — Six independent overlay tints in the Lines group, not a merged "all traffic" view.**
**Recommend: independent toggles.** A player wanting to diagnose a traffic jam needs to isolate congestion (v/c overlay) from demand (per-tile count) from shortfalls (parking/fuel) — different diagnostic lenses. A single "all six at once" view would paint six overlapping tints per tile (illegible). Independent toggles let the player paint demand alone, then add congestion on top, etc.

**D2 — Transport screen is a new panel tab, not an in-map HUD.**
**Recommend: new tab.** The Transport screen aggregates eight sections (commute, coverage, parking, wear, policies, scores) — too much content for an in-map HUD without breaking the map's viewport. A new left-panel tab (like Demographics/Employment) keeps it always available, never obscures the map, and leverages the existing panel layout code.

**D3 — Ambulance response-time tint stays in the Lines group, not replicated in inc10.**
**Recommend: reuse inc4's tint.** inc4 already wired the ambulance overlay into showLines; inc10 does not repaint it — the showLines block now runs the inc4 ambulance tint AND the five new inc10 tints all inside the same conditional (line 641 `MapView.tsx`).

## 5. Assumptions

- **ASM-1529** — every overlay metric's data source (demand count, segment v/c, parking shortfall, fuel/EV shortfall, road condition) is read-only on the current tick; no per-render re-derivation happens. **What breaks if wrong:** if an overlay tint were to trigger a new assignment or condition-recomputation per frame, the overlay cost would immediately violate AC-8's structural bound and every traffic metric would race between the live derivation and the cadence snapshot (incohesive player view).

- **ASM-1530** — the road condition metric (AC-6) is an average over all segments, not a per-segment worst-case. **What breaks if wrong:** reporting the worst-condition segment (the bottleneck) instead of the mean would hide widespread minor wear under one dramatic failure, and would over-incentivise "just fix the worst road" over city-wide maintenance.

- **ASM-1531** — the Transport screen's policy effects rows (AC-7) pull from `busPriorityCapacityInfoOf`, which is a MEASURED effect (e.g. "this policy reduced traffic by 5%"), not a STATED effect (e.g. "the player set this to 'strict'"). **What breaks if wrong:** a city could have a policy ON but zero measured effect (e.g. a bus-priority lane on an empty road) — conflating the on/off switch with the effect would mislead the player into thinking the policy doesn't work.

- **ASM-1532** — the "fuel/EV shortfall" metric is a COMBINED shortfall (max of the two), not a separate pair. **What breaks if wrong:** a city could have abundant fuel but zero EV charge points (or vice versa) — a separate "fuel shortfall" and "EV shortfall" metric would make two rows where one "bottleneck" combined metric is clearer for the player's immediate action (build more infrastructure or it doesn't matter which type).
