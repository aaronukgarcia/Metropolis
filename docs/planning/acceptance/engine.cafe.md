# Acceptance criteria — engine.cafe (MOD-054)

## User stories

- **US-1.** As the player, I need a per-centre vitality index computed as the literal §41 product `footfall × venue density × dwell quality × safety(§28) × weather-adjusted outdoor capacity`, visible as an F1 overlay, so vitality is a real composite the player can read and act on, not a single opaque satisfaction number.
- **US-2.** As `engine.wellbeing` (registered edge), I need cafés/third-places to reduce isolation for sociability-matched citizens near access, so §18's "third places directly counter isolation" is a real driver input, not a cafe-side-only stat.
- **US-3.** As the outdoor-seating/pavement-licensing mechanic, I need capacity to genuinely respond to season and weather ("a Mediterranean July pavement is dead in January gales"), sourced from `engine.season`'s live curve (the registered edge), never a duplicated cafe-side calendar.
- **US-4.** As the player exercising pavement-licensing/street-performance-licensing policy, I need those instruments delivered via `PoliciesAPI` as code.json's own registered pattern text promises — blocked pending BUG-058 finding #9 (the registry contradicts its own claim: no `engine.cafe`→`engine.policies` edge exists).
- **US-5.** As the vitality formula's own safety term, I need `safety(§28)` sourced from `engine.crime`'s real deprivation/policing signal — blocked pending BUG-058 finding #8 (no `engine.cafe`→`engine.crime` edge).
- **US-6.** As `engine.tourism`, I need to read cafe's vitality index as an attraction-portfolio term (§44) — this item exposes the value; `engine.tourism.md` AC-9 documents the consuming side as blocked pending the same missing edge (BUG-058 finding #2).
- **US-7.** As adjacent retail/land-value systems (§35's "anti-e-commerce force"), I need vitality to be a queryable positive input to retail survival, so the small-money, high-leverage claim is testable as a real effect, not marketing copy.

## Scope

The per-centre vitality index and its five named terms (footfall, venue density, dwell quality, safety, weather-adjusted outdoor capacity); the isolation-reduction push to `engine.wellbeing`; seasonal/weather-driven outdoor-capacity sourced live from `engine.season`; the F1-overlay-shaped output. No pavement-licensing policy mechanics themselves (blocked, `engine.policies`), no crime/deprivation computation (blocked, `engine.crime`), no retail-survival/land-value computation (`engine.shopping`/`engine.finance`'s job — this item only exposes vitality as an input).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `VitalityAPI` exists matching code.json's registered pattern "vitality as F1 overlay; policy instruments via PoliciesAPI" — a per-centre vitality-index query shaped for direct F1-overlay rendering (per-cell/per-centre value, not a single citywide scalar). Check: `go doc ./internal/engine/cafe VitalityAPI` shows a per-centre query returning a spatially-addressable result; `grep -rln "cafe\.\w\+State\.\w\+ = " internal/*/ -r --include=*.go` (excluding `internal/engine/cafe` and `_test.go`) finds no bypassing writes.
- **AC-2 (§41 the five-term formula, independently decomposed).** The vitality index is computed as the product of five independently-queryable terms — footfall, venue density, dwell quality, safety, weather-adjusted outdoor capacity — matching the spec's literal formula, not a single blended score. Check: `go doc ./internal/engine/cafe` shows five distinct term accessors plus the composite; a passing test changes one term's input and asserts only that term's accessor and the composite change (`grep -rn "func Test.*[Tt]ermDrillThrough\|func Test.*[Vv]italityIsolation" internal/engine/cafe/*_test.go`). A lazy-but-plausible violation: one opaque `Vitality()` float — rejected because the check demands five independently-inspectable accessors.
- **AC-3 (§41 footfall/venue-density/dwell-quality — real sourcing).** Footfall is sourced from realised pedestrian/venue-patronage activity (via `engine.wellbeing`'s or the citizen-movement path, not an invented flat rate), venue density is a real per-centre venue count normalised by area, and dwell quality reflects venue-quality/outdoor-seating provision. Check: a passing test adds venues to a centre (holding footfall/safety/weather fixed) and asserts venue-density term rises; a second test removes all venues from a centre and asserts venue-density falls to its floor value, not merely "some lower number" (`grep -rn "func Test.*[Vv]enueDensity" internal/engine/cafe/*_test.go`).
- **AC-4 (§41 weather-adjusted outdoor capacity — live season call, the January-gales test).** Outdoor-seating capacity is scaled by a live `engine.season` query (the registered `engine.cafe`→`engine.season` edge), peaking in summer months and reduced in winter months — the "Mediterranean July pavement is dead in January gales" case must be literally reproducible: a July query and a January query against the same fixture centre must differ. Check: `grep -n "engine/season" internal/engine/cafe/*.go` (excluding `_test.go`) finds a real import; a passing test queries outdoor capacity for July and January on an identical fixture centre and asserts July's value is strictly greater (`grep -rn "func Test.*[Ww]eatherAdjustedCapacity\|func Test.*[Jj]anuaryGales" internal/engine/cafe/*_test.go`); a second test mutates `data/seasonal.json`'s relevant curve fixture and asserts the July/January values move accordingly (GR#3/GR#15 mutation-test proof, mirroring `engine.season.md` AC-10). A lazy-but-plausible violation: a cafe-local `if month == 7 { capacity *= 3 }` constant — the mutation test rejects it because changing the data file would have no effect on a hardcoded conditional.
- **AC-5 (§41/§28 safety term — BLOCKED, see BUG-058 finding #8).** The safety term is sourced from `engine.crime`'s deprivation/policing signal via a registered edge, matching the formula's explicit `safety(§28)` citation. **This AC is blocked**: no `engine.cafe`→`engine.crime` edge is registered today, and `engine.crime`'s inbound consumers list is `engine.prison` only (BUG-058 finding #8). Until unblocked, the safety term MUST be an explicitly marked placeholder input (documented as such, never a silently hardcoded constant that would satisfy AC-2's "five independently-queryable terms" prose while violating GR#15). Check (once unblocked): `grep -n "engine/crime" internal/engine/cafe/*.go` (excluding `_test.go`) finds a real import; a passing test lowers `engine.crime`'s safety/deprivation signal (via a fake) and asserts the vitality composite falls (`grep -rn "func Test.*[Ss]afetyTerm" internal/engine/cafe/*_test.go`). Until then: `grep -n "TODO\|STUB\|PLACEHOLDER" internal/engine/cafe/*.go` referencing the safety term finds an explicit marker.
- **AC-6 (§18 isolation reduction — the third-places mechanism).** Cafe/third-place access reduces isolation for citizens weighted by their sociability trait, pushed through the registered `engine.cafe`→`engine.wellbeing` edge, matching §18's "isolation (sociability trait × community venue access)" driver. Check: `grep -n "engine/wellbeing" internal/engine/cafe/*.go` (excluding `_test.go`) finds a real import/call; a passing test compares two citizens identical except sociability trait, both within access range of a café centre, and asserts the higher-sociability citizen's pushed isolation-reduction figure is greater (`grep -rn "func Test.*[Ii]solationReduction\|func Test.*[Tt]hirdPlaces" internal/engine/cafe/*_test.go`). A lazy-but-plausible violation: a flat isolation-reduction figure applied to all nearby citizens regardless of sociability — rejected because the check demands the sociability-weighted comparison.
- **AC-7 (§41 pedestrianisation/market-days/street-performance instruments — structural existence).** At minimum the instrument SURFACE exists (a settable configuration for pedestrianised-street status, market-day scheduling, street-performance licensing) even where the policy-application channel itself is blocked (AC-9); each instrument measurably affects at least one vitality term when set directly via `CoastalAPI`-equivalent test fixtures. Check: `go doc ./internal/engine/cafe` shows configuration accessors for pedestrianisation/market-days/street-performance; a passing test sets pedestrianised-street status on a fixture centre and asserts footfall or dwell-quality term rises (`grep -rn "func Test.*[Pp]edestrianisation\|func Test.*[Mm]arketDay" internal/engine/cafe/*_test.go`).
- **AC-8 (§41 "small-money, high-leverage" — a real leverage ratio is queryable).** A cost-to-vitality-delta figure is queryable for at least the pedestrianisation/licensing instrument (AC-7), so the "small-money, high-leverage" claim is a checkable ratio, not narrative. Check: a passing test applies a documented-cost pedestrianisation change and asserts both the cost figure and the resulting vitality delta are queryable from the same call/response pair (`grep -rn "func Test.*[Ll]everageRatio\|func Test.*[Cc]ostVitalityDelta" internal/engine/cafe/*_test.go`).
- **AC-9 (§41 policy instruments via PoliciesAPI — BLOCKED, see BUG-058 finding #9).** Pavement-licensing and street-performance-licensing policy changes are applied through the registered `engine.cafe`→`engine.policies` edge, matching code.json's own documented inbound pattern text "policy instruments via PoliciesAPI" verbatim. **This AC is blocked**: no such edge is registered today — code.json's `engine.cafe` outbound calls are `engine.wellbeing`/`engine.build`/`engine.season` only, and `engine.policies`' own outbound/consumer lists do not include cafe either (BUG-058 finding #9 — the registry contradicts its own claim, same defect class BA-S9a found for `engine.social`). Check (once unblocked): `grep -n "engine/policies" internal/engine/cafe/*.go` (excluding `_test.go`) finds a real import; a passing test sets a pavement-licensing policy via `PoliciesAPI` (a fake satisfying the interface) and asserts AC-7's configuration state changes accordingly, proving the policy channel — not a parallel cafe-owned settings API — is the real path (`grep -rn "func Test.*[Pp]oliciesAPIChannel" internal/engine/cafe/*_test.go`).

Check: `grep -n "go func()" internal/engine/cafe/*_test.go` finds at least one concurrency test.

## Escalations

- **BUG-058 finding #8 (blocks AC-5).** The vitality formula's own spec text explicitly cites `safety(§28)` as a multiplicative term, but no `engine.cafe`→`engine.crime` edge is registered, and `engine.crime`'s consumers are `engine.prison` only. Filed as a comment on BUG-058, 2026-08-11.
- **BUG-058 finding #9 (blocks AC-9) — the registry contradicts itself.** code.json's own `engine.cafe` inbound pattern text says "policy instruments via PoliciesAPI", but no `engine.cafe`↔`engine.policies` edge exists in either direction. This is not a case of the spec implying an edge nobody registered — it is code.json's own documented contract for this exact module being unfulfillable as written. Same defect class as BA-S9a's `engine.social` finding (registry inbound pattern claims a channel that has no supporting edge). Filed as a comment on BUG-058, 2026-08-11; recommend this instance be prioritised over the purely-inferred findings since it is self-contradictory rather than merely incomplete.
- **ASM-325 (logged).** The five formula terms' relative weights are data-driven placeholders pending M2 balance pass — see the assumption record.
- **For Bill.** AC-4's July-vs-January test is deliberately named for the spec's own example ("a Mediterranean July pavement is dead in January gales") because that sentence is the single most concrete, checkable claim in §41 — treating it as a literal test case rather than illustrative colour is a judgment call worth confirming is the intended reading.
