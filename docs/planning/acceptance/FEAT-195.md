# Acceptance criteria — supermarket archetypes & society shopping profile (FEAT-195)

**BOW code:** FEAT-195

**Package under test:** `internal/engine/shopping/` — this feature extends the owning module `engine.shopping` (MOD-050), which the proposal names as this design's "target end-state".

## User stories

- **US-1.** As a household choosing where to shop, I need six genuinely distinct supermarket archetypes — Discounter, Value big-box, Mainstream, Quality mid, Premium, Convenience — each carrying its own data-driven price level, range breadth, fresh-food quality, footprint/format, catchment draw, demographic affinity, delivery capability, and restock intensity, so "which store is near me" is a real trade-off, not one undifferentiated "supermarket" type.
- **US-2.** As the settlement tier (village → small town → large town → city → mega city), I need a data-driven retail-mix template stating what mix "should" exist per capita at each tier, so demand signals — and, later, FEAT-171 auto-provision — have a real target to read rather than a hardcoded ladder.
- **US-3.** As a household choosing a store, I need my store choice to be a deterministic function of price-sensitivity × access × quality preference (the proposal's "deterministic choice model"), so an affluent household and a price-sensitive household genuinely weight different archetypes — demographic affinity is a mechanism, not a label.
- **US-4.** As `engine.citizens` (the now-registered outbound `CitizensAPI` edge), I need the demand-side input for US-3 (household price-sensitivity/demographics/affluence) to arrive through that registered interface — read from a live citizen/household, not a shopping-owned placeholder.

## Scope

The six archetypes as data-driven entities (GR#15) with the full attribute set (price, range, freshness, footprint/format, catchment, demographic affinity, delivery capability, restock intensity); the per-tier society shopping profile template as a queryable, data-driven table; the deterministic household store-choice model (price-sensitivity × access × quality). The household demand-source wiring now consumes the registered `engine.shopping`→`engine.citizens` edge (`CitizensAPI`, AC-5): the choice model's demand profile (price-sensitivity, affluence, home location) is read from live citizen state, not an injected seam. Remaining unregistered edges (`engine.households`, `engine.comms`, `engine.freight`) stay out of this feature's scope (Escalations). Auto-provision (FEAT-171) consumption of the template is out of scope (AC-6, Escalations).

## Acceptance criteria

### Functional — six archetypes, data-driven

- **AC-1 (GR#15; six archetypes from data, not Go literals).** All six archetypes — Discounter, Value big-box, Mainstream, Quality mid, Premium, Convenience — exist as entries in `data/shopping.json`, each carrying price level, range breadth, fresh-food quality, footprint/format, catchment draw, demographic affinity, delivery capability, and restock intensity; the Go code loads those values from the data file and defines NO per-archetype balance literal. Check: `grep -rn "discounter\|valueBigBox\|mainstream\|qualityMid\|premium\|convenience" internal/engine/shopping/*.go` (excluding `_test.go`) shows the archetype keys referenced only as data-file lookup keys, never as inline balance values; a passing test loads `data/shopping.json` and asserts all six keys exist AND that at least the price-level and fresh-quality attributes differ pairwise across archetypes, so a six-way copy of one archetype fails (`grep -rn "func Test.*[Aa]rchetype.*[Ll]oad\|func Test.*[Ss]ixArchetype" internal/engine/shopping/*_test.go`). **Lazy violation this rejects:** a Go `switch` with six cases each hardcoding a price/quality constant would satisfy "six archetypes exist" while violating GR#15 — the check requires the values to come from the data file and to actually differ.

- **AC-2 (GR#3/GR#22; generic keys, no real brand names in code/data).** Archetypes are keyed by generic identifiers only; no real UK chain name (or its abbreviation) appears in code or data — the real-world models are recorded in the proposal, not in the build. Check: `grep -rniE "aldi|lidl|asda|tesco|sainsbury|waitrose|marks &? spencer|\\bM&S\\b|\\bspar\\b|co-?op" internal/engine/shopping/*.go data/shopping.json` returns no matches.

- **AC-3 (GR#15; demographic affinity is data-driven and load-bearing, not decorative).** Each archetype's demographic affinity is a data field that genuinely moves store choice. Check: a passing test constructs two households differing only in price-sensitivity/demographic profile and asserts they are assigned (or strongly weighted toward) different archetypes for identical access/quality inputs; a second sub-test nulls the affinity field in the loaded data and asserts the choice degenerates toward access/price-only weighting, proving the field is actually read (`grep -rn "func Test.*[Aa]rchetype.*[Aa]ffinity\|func Test.*[Dd]emographic" internal/engine/shopping/*_test.go`). **False-pass risk:** a build that stores affinity in the data but never reads it into the choice model would pass "the field exists" on a shallow read — the null-out sub-test is what catches it.

### Functional — society shopping profile by tier

- **AC-4 (GR#15; per-tier retail-mix template).** A queryable per-tier retail-mix template maps each settlement tier to the archetype mix that "should" exist per capita, sourced from `data/shopping.json`. Check: `go doc ./internal/engine/shopping` shows a tier-template accessor (e.g. `SocietyShoppingProfile(tier)`); a passing test asserts the village template contains Convenience and does NOT contain a hypermarket/mega-format entry, while the mega-city template contains all six archetypes plus hypermarket and dark-store entries (`grep -rn "func Test.*[Tt]ierTemplate\|func Test.*[Ss]ocietyProfile" internal/engine/shopping/*_test.go`). A build returning an identical mix for every tier fails.

- **AC-5 (GR#20/GR#25 — demographic/price-sensitivity demand source via the registered `engine.shopping`→`engine.citizens` edge; BUG-100 tripwire resolved, edge landed).** US-3/US-4's demand-side inputs — the household's price-sensitivity/affluence, quality preference, and access location — are sourced from `engine.citizens` through the registered outbound `CitizensAPI` edge (code.json `engine.shopping.outbound.calls` now includes `engine.citizens` → inbound `CitizensAPI`, guid `35078084-e4a5-4c34-b9ee-6b0352b76fe3`; this edge was absent when this file was first written and has since landed), never a shopping-owned demographic/price table and never the pre-edge injected seam. Check: `grep -rn "CitizensAPI\\|citizens\\." internal/engine/shopping/*.go` (excluding `_test.go`) shows the store-choice model reading the demand profile across the registered interface (`CitizenAt`/`HouseholdOf` query surface, per `engine.citizens.md` AC-1b), not from an internal stub; a passing test seeds two citizens identical in `homeCell`, store access and quality inputs but differing only in a `CitizensAPI`-visible affluence field (`wealth`, per `engine.citizens.md` AC-1), runs the choice model, and asserts the two are weighted toward different archetypes (low-`wealth` toward Discounter/Value, high-`wealth` toward Premium/Quality), AND that zeroing the CitizensAPI-sourced profile collapses the choice to access-only weighting with no archetype preference (`grep -rn "func Test.*[Dd]emandSource\\|func Test.*[Cc]itizensEdge\\|func Test.*[Aa]ffluence" internal/engine/shopping/*_test.go`). **Lazy violation this rejects:** keeping the pre-edge injected `DemandProfile` seam, or standing up a shopping-owned `data/shopping.json` per-household demographic table, would satisfy "the choice model uses demographics" on a shallow read while leaving the now-registered edge unconsumed and duplicating citizen state (GR#3) — the check requires the profile to be READ from `CitizensAPI`. **GR#15:** the affluence→archetype mapping weights and the demographic-affinity field stay in `data/shopping.json` (AC-1/AC-3 own those field-level checks); this AC owns only the SOURCE of the profile. **GR#21:** the CitizensAPI read is a pure query (no RNG); any choice/dispersal draw still routes through `det.NewStream` (AC-9), and the two-citizen comparison is reproducible from `(worldSeed, citizenId, tick)`. The same landed edge is what FEAT-196's per-household shopping-cycle identity (AC-1/AC-2) keys off — that half is re-armed in FEAT-196.md, not duplicated here.

- **AC-6 (GR#25 — auto-provision boundary, out of scope for this feature).** The per-tier template (AC-4) is exposed as a queryable value ONLY; it does not call any auto-provision consumer. FEAT-171 ("Planning-Dept auto-provision") is not a registered module/consumer in code.json, so this feature must not invent a call to it. Check: `grep -rn "provision\\|AutoProvision" internal/engine/shopping/*.go` (excluding `_test.go`) finds no outward auto-provision call — the template is data + a query surface, consumed later by whoever FEAT-171 registers.

### Error handling

- **AC-7 (GR#7).** Loading `data/shopping.json` with an unknown archetype key, a missing attribute, or an out-of-domain value (e.g. negative price level, affinity outside [0,1]) returns a registry-sourced error (new `MET-E`-range code, claimed against `data/errors.json` at build time) rather than silently substituting a zero archetype. Check: `grep -n "MET-" internal/engine/shopping/*.go` finds a registry code reference; passing test coverage asserts the returned error's registry code matches AND that no default archetype was silently substituted (`grep -rn "func Test.*[Uu]nknownArchetype\\|func Test.*[Mm]alformedShopping" internal/engine/shopping/*_test.go`).

- **AC-8.** Querying the society profile for an unregistered settlement tier is rejected with a typed error, never silently clamped to the nearest tier. Check: `grep -rn "func Test.*[Uu]nknownTier" internal/engine/shopping/*_test.go`.

### Determinism & safety

- **AC-9 (GR#21).** Store-choice draws (any tie-breaking or weighted selection across archetypes) use `foundation.det`'s counter-based stream `det.NewStream(worldSeed, householdID, tick, purposeTag)` — no shared/global RNG, no `math/rand`, no map-iteration order feeding the choice. Check: `grep -n "rand.New\\|math/rand\\"" internal/engine/shopping/*.go` (excluding `_test.go`) finds no shared/global RNG source; `grep -rn "func Test.*[Dd]eterminis" internal/engine/shopping/*_test.go` finds a determinism test asserting byte-identical archetype assignments across repeated runs from identical state.

- **AC-10 (SG-7; GR#21).** `grep -rn "time.Now\\|time.Since" internal/engine/shopping/*.go` (excluding `_test.go`) returns no matches.

- **AC-11.** `go test ./internal/engine/shopping/... -race -count=1` passes; `grep -n "go func()" internal/engine/shopping/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-12.** `internal/engine/shopping/doc.go` states the six archetypes and their generic-key rule (AC-2), cites §37 and the retail proposal §3-4, states the demographic-affinity choice model (AC-3), states that the demand profile is sourced from the registered `engine.shopping`→`engine.citizens` `CitizensAPI` edge (AC-5), and states the one remaining GR#25 block (auto-provision AC-6) explicitly so a future reader does not assume that wiring already happened. Check: `grep -n "engine.shopping" internal/engine/shopping/doc.go` and `grep -n "archetype\\|§37\\|section 37" internal/engine/shopping/doc.go` and `grep -n "BUG-058\\|blocked\\|CitizensAPI\\|citizens" internal/engine/shopping/doc.go` all match.

## Out of scope

- Household demand-source mechanics beyond what `CitizensAPI` already exposes (e.g. a richer household-level income/typology input per §21, if ever wanted) — this feature consumes the citizen-level affluence/demographic profile the registered `engine.shopping`→`engine.citizens` edge provides (AC-5); it does not own or duplicate citizen demographic state.
- FEAT-171 auto-provision — consumes the template later; this feature only exposes the template (AC-6).
- The exact archetype attribute magnitudes, the demographic-affinity weighting, and the per-tier mix thresholds — balance data in `data/shopping.json`, pending M2 tuning (GR#15; balance-number regime).
