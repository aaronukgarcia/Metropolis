## User stories

- **US-1.** As the engine, I need every citizen to be a persistent individual record forever — no shared birthdays, no culls, only simulation *fidelity* varying — so that "every citizen is a persistent individual record" (§5) is a structural guarantee, not a best-effort approximation that quietly breaks at scale.
- **US-2.** As the HOT/WARM/COLD fidelity dial (§5.2), I need HOT citizens (viewport + followed + rotating deterministic sample) to path to work, queue in traffic, attend venues, get sick, and shop daily, while COLD citizens advance only at the monthly tick via a vectorised batch pass, so the game affords 100M citizens without simulating 100M citizens in full daily detail.
- **US-3.** As A1's cold citizen store, I need columnar struct-of-arrays storage with field-level compression (bucketed enums, delta-coded ages, bit-packed states) targeting 60-100B/citizen, so 100M citizens cost 6-10GB, not the naive 25GB that motivated this amendment.
- **US-4.** As A2's amortised cold pass, I need a fixed rolling schedule that processes 1/30 of shards per daily tick rather than one monthly spike, so cold-pass I/O is smooth and every citizen still advances exactly once per calendar month, deterministically.
- **US-5.** As A7's sampling firewall, I need cold-pass batch parameters (mortality hazard inputs, education-stage transition rates, job-matching statistics, satisfaction drift) estimated ONLY from the stratified rotating sample (stratified by district × age band × income), never from viewport-hot citizens whose elevation is display fidelity only, so a player who parks the camera over one district can never skew citywide cold-pass statistics.
- **US-6.** As a player who inspects any cold citizen, I need the engine to deterministically reconstruct their recent detail via life-writing (record + district statistics + `hash(seed, id, month)`) and have that reconstruction be *binding* — it is what happened, already accounted for in aggregates — so inspection never reveals a contradiction with the citywide numbers.
- **US-7.** As the mortality model, I need per-person monthly Gompertz-Makeham hazard draws (keyed by age, health band, healthcare access) via the counter-based hash-stream determinism rule, so death is a real per-individual probabilistic event, not a scripted cull, and is bit-reproducible from `(worldSeed, id, month)`.
- **US-8.** As the Sprint 3 exit gate, I need 10M synthetic citizens to advance a full simulated month inside the reference-hardware budget (i7 8C/16T, 20GB RAM envelope, M0-ENG §1.3's 8GB citizen-shard region), with camera-invariance (A7) and shard-count invariance both green in CI, so the scale risk this item exists to retire is actually retired, not merely built.

## Scope

The citizen record (hot AoS ~250B + cold columnar SoA 60-100B/citizen), the HOT/WARM/COLD adaptive-fidelity dial and its promotion/demotion rules, the amortised 1/30-shards-per-day cold batch pass, the A7 sampling firewall (stratified rotating sample, camera-invariance), deterministic per-citizen monthly mortality hazards (Gompertz-Makeham), and binding deterministic life-writing on inspection.

## Acceptance criteria

### Functional

- **AC-1 (§5.1).** A hot citizen record exists matching the documented ~250B field set: `id` (uint64), `birthMonth` (int32), `sex`, `householdId`, `partnerId`, `childIds`, `homeCell`, `workplaceRef | schoolRef`, an 8-axis personality vector (sociability, ambition, conscientiousness, novelty-seeking, physicality, community-mindedness, patience, aesthetic drive — 0-100 each), an education record (stage history + quality-weighted attainment score), derived leisure taste weights, `healthBand`, `wealth`, `employmentState` + sector, and satisfaction components (housing, services, environment, leisure-fit, commute). Check: `go doc ./internal/engine/citizens Citizen` (or `HotRecord`) lists all these fields; `grep -n "unsafe.Sizeof" internal/engine/citizens/*_test.go` (or a documented size comment) confirms the struct is in the ~250B range.
- **AC-1b (GR#20; code.json inbound contract).** A `CitizensAPI` (or equivalent) exists matching code.json's registered inbound contract — read/query methods over hot, warm and cold citizen state (record lookup, fidelity-tier queries, household membership) plus mutation paths expressed only as commands (never a direct exported field-set on `Citizen`/`ColdShard`), consumed by all 16 registered consumers (`engine.attract`, `engine.coastal`, `engine.crime`, `engine.defence`, `engine.education`, `engine.extcommute`, `engine.firms`, `engine.households`, `engine.leisure`, `engine.services`, `engine.social`, `engine.staffing`, `engine.traffic`, `engine.wellbeing`, `ui.screen.demo`, `ui.screen.map`) through this interface alone, never a concrete `citizens.Citizen`/`citizens.ColdShard` reached directly from another package's non-test code. Check: `go doc ./internal/engine/citizens CitizensAPI` shows query methods (e.g. `CitizenAt`, `HouseholdOf`, `FidelityOf`) and a command-based mutation path (e.g. `ApplyLifeEventCommand`); `grep -rln "citizens\.\(Citizen\|ColdShard\)\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/citizens` itself and `_test.go` files, the sanctioned H-STUB fixture exception per README's "Conventions ratified during Sprint 1") finds no direct exported-field writes from another package.
- **AC-2 (§5.1).** Age is always derived from `birthMonth`, never stored as a separate mutable field — "no shared birthdays, no culls: stored to the month" is enforced structurally by having no `Age` field to desync. Check: `grep -n "func.*Age()" internal/engine/citizens/*.go` shows age computed from `birthMonth` + current sim month, and `grep -n "Age  *int\|Age int" internal/engine/citizens/citizen.go` (the struct definition) finds no stored age field.
- **AC-3 (§5.1).** Personality vector P is initialised at birth from a parental blend plus deterministic noise (via the counter-based hash stream, AC-13), and education modifies P over time (widening or narrowing ambition/novelty-seeking/taste range per schooling quality) rather than P being fixed at birth forever. Check: `go doc ./internal/engine/citizens InitPersonality` and a `driftPersonality`/`ApplyEducationEffect` (or equivalent) both exist; passing tests cover birth-initialisation and an education-driven drift (`grep -rn "func Test.*[Pp]ersonality" internal/engine/citizens/*_test.go`).
- **AC-4 (§5.2 HOT/WARM/COLD dial).** Three fidelity tiers are modelled with documented promotion/demotion rules: HOT = viewport region + followed/inspected + rotating deterministic sample (~0.1-1% citywide); WARM = recently-hot, simplified daily update, cheap re-promotion; COLD = everyone else, advanced only at the monthly tick. Check: `go doc ./internal/engine/citizens Fidelity` (or equivalent enum) shows the three tiers; passing tests cover promotion (COLD→WARM→HOT on viewport entry) and demotion (`grep -rn "func Test.*[Pp]romot\|func Test.*[Dd]emot" internal/engine/citizens/*_test.go`).
- **AC-5 (§5.2, A1).** Cold citizens are stored in columnar struct-of-arrays layout per shard, with field-level compression: bucketed enums (e.g. `healthBand`, `employmentState` as small integer codes, not strings), delta-coded ages (relative to a shard epoch, not absolute `birthMonth` repeated per field), and bit-packed boolean/small-range states. Check: `go doc ./internal/engine/citizens ColdShard` (or equivalent) documents the columnar layout; a passing test measures actual per-citizen byte cost of a populated cold shard and asserts it falls within 60-100B (`grep -rn "func Test.*[Cc]old.*[Ss]ize\|func Benchmark.*Cold" internal/engine/citizens/*_test.go`).
- **AC-6 (A2).** The cold batch pass is amortised on a fixed rolling schedule: exactly 1/30 of cold shards are processed per simulated daily tick (30 logistics day-ticks per calendar month, per §3's two-layer clock), and the schedule is deterministic (which shards process on which day-tick is a fixed, seed-independent or seed-derived-but-reproducible function of the day index), not random jitter. Check: `go doc ./internal/engine/citizens ColdPassSchedule` (or equivalent) exists; a passing test asserts exactly 1/30 of total cold shards are scheduled per day-tick across a 30-day-tick month and every shard appears exactly once (`grep -rn "func Test.*[Aa]mortis\|func Test.*[Ss]chedule" internal/engine/citizens/*_test.go`).
- **AC-7 (A2).** Despite the amortised schedule, every cold citizen advances (ages, has mortality/health/education/employment/satisfaction updated) exactly once per calendar month — the amortisation changes *when within the month* a citizen's shard processes, never *how many times*. Check: a passing test runs a full 30-day-tick month and asserts every cold citizen's monthly-update counter is exactly 1 (`grep -rn "func Test.*[Oo]ncePerMonth" internal/engine/citizens/*_test.go`).
- **AC-8 (§5.2).** Cold-pass batch parameters (mortality/health-drift/education-transition/job-matching rates) are "measured from the hot sample, not invented" — the cold pass consumes parameters computed from the rotating sample (AC-9), never hardcoded constants, consistent with GR#15. Check: `grep -n "hardcod\|// TODO.*hardcode" internal/engine/citizens/coldpass.go` (or equivalent) finds none on the parameter-consumption path; a passing test asserts changing the sample's composition changes the derived cold-pass parameters (`grep -rn "func Test.*[Dd]erivedParam" internal/engine/citizens/*_test.go`).
- **AC-9 (A7 sampling firewall).** A stratified rotating sample exists, stratified by district × age band × income, coverage-guaranteed (every district/age-band/income stratum has at least a minimum sample count), and this sample — never viewport-hot citizens — is the sole source for cold-pass parameter estimation. Check: `go doc ./internal/engine/citizens StratifiedSample` (or equivalent) exists; a passing test asserts a citizen entering HOT tier via camera/viewport is excluded from the parameter-estimation input set unless independently selected by the stratified sampler (`grep -rn "func Test.*[Ss]tratif\|func Test.*[Ss]amplingFirewall" internal/engine/citizens/*_test.go`).
- **AC-10 (§5.2 life-writing).** Inspecting a cold citizen triggers deterministic life-writing: the engine reconstructs their recent detail from `(record, district statistics, hash(seed, id, month))`, and the result is binding — re-inspecting the same citizen at the same month returns identical reconstructed detail, and the reconstruction is consistent with (already accounted for in) the district-level aggregates. Check: `go doc ./internal/engine/citizens LifeWrite` (or equivalent) exists; a passing test inspects the same cold citizen twice at the same month and asserts identical output (`grep -rn "func Test.*[Ll]ifeWrit" internal/engine/citizens/*_test.go`).
- **AC-11 (§5.1 mortality).** Per-person monthly mortality hazard is drawn from a Gompertz-Makeham curve parameterised by age, health band, and healthcare access, via the counter-based hash stream `hash(worldSeed, id, month, "mortality")` (or equivalent purpose tag). Check: `go doc ./internal/engine/citizens MortalityHazard` (or equivalent) exists and documents the Gompertz-Makeham formula; a passing test asserts hazard increases with age for fixed health/access (`grep -rn "func Test.*[Mm]ortality\|func Test.*[Gg]ompertz" internal/engine/citizens/*_test.go`).
- **AC-12 (§5.4).** Households are real entities formed by partnering events among hot/sampled citizens (statistically among cold, calibrated to the sample per §5.2's "measured from the hot sample" rule), with overcrowding and rent-burden derivable from household composition and dwelling size. Check: `go doc ./internal/engine/citizens Household` exists with `partnerId`/`childIds`-consistent membership; a passing test asserts a partnering event creates a shared `householdId` for both partners (`grep -rn "func Test.*[Hh]ousehold\|func Test.*[Pp]artner" internal/engine/citizens/*_test.go`).

### Error handling

- **AC-13 (GR#7).** Constructing a citizen record with an invalid state (negative `birthMonth` relative to world start, personality axis outside 0-100, a `householdId` referencing a nonexistent household) returns a registry-sourced error (new `MET-E`-range code) rather than a silently-clamped or corrupted record. Check: `grep -n "MET-" internal/engine/citizens/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalid.*[Cc]itizen\|func Test.*[Oo]utOfRange" internal/engine/citizens/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no clamped or corrupted citizen record was created/persisted, not merely that a matching-named test function exists.
- **AC-14.** A cold-pass batch encountering a shard whose stratified-sample coverage guarantee is violated (e.g. a district with zero sampled citizens) degrades to a documented fallback (borrow from the nearest comparable stratum, or flag the district's cold-pass estimate as low-confidence) rather than dividing by zero or silently using an empty parameter set. Check: passing test coverage (`grep -rn "func Test.*[Zz]eroSample\|func Test.*[Cc]overageGap" internal/engine/citizens/*_test.go`).

### Determinism & safety

- **AC-15 (GR#21).** Every stochastic draw for citizen `i` at month `m` uses an independent counter-based hash stream `hash(worldSeed, i, m, purposeTag)` — no shared RNG object anywhere in the package (M0-ENG §1.2's "crown rule"). Check: `grep -n "rand.New\|math/rand\"" internal/engine/citizens/*.go` (excluding `_test.go`) finds no shared/global RNG source; all randomness routes through the documented counter-based hash function (`grep -n "hash(worldSeed" internal/engine/citizens/*.go` or its actual function name).
- **AC-16 (A7; sprint plan S3 exit gate).** Cold-pass parameter estimates are camera-invariant — a CI test asserts that moving the viewport/camera over different districts between otherwise-identical runs produces byte-identical cold-pass parameter estimates and byte-identical resulting world state.
