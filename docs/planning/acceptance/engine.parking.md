# Acceptance criteria — engine.parking (MOD-051)

**BOW code:** MOD-051
**Spec refs:** §38 Parking (`docs/METROPOLIS-MASTER-v2.1.md` lines 552-554, in full: "Parking is land wearing a disguise." On-street (capacity per road type, permits by district), surface car parks, multi-storey (exists), park & ride (exists), workplace parking; charges are a player instrument (per district, per hour, permit prices) — revenue AND the strongest mode-choice lever in the toolkit, expensive parking + good transit shifts commuters off the network; insufficient parking near destinations creates cruising traffic (search circulation added to local load — "the invisible congestion 'Blue' never modelled") and overspill into residential streets (satisfaction ↓, permit politics); every non-walking car trip must terminate in a real space; F1 parking overlay shows occupancy heat; late-era autonomy (M12 tree) shrinks demand — car parks become redevelopment land, "a lovely endgame dividend"); §39 Taxation (line 562: "parking charges (§38)" listed among the behavioural/levies instrument panel, each with a revenue line + incidence display + elasticity curve per §39's own contract); Catalogue Supplement 2 (line 592: "Surface car park / on-street schemes / residents-permit zone | M4/M3/M6 | §38"); code.json `engine.parking` entry (inbound `ParkingAPI`, pattern "space accounting per destination; charge instruments via PoliciesAPI", consumers: `engine.destination`; outbound calls: `engine.traffic`, `engine.world`).
**Date:** 2026-08-11 (BA-S10a, first pass)
**Status:** draft-ahead — `MOD-017` (engine.world) and `MOD-023` (engine.traffic) are both `open`; this item is not in the ready queue until both land. Content written now, ahead of both.

## User stories

- **US-1.** As every non-walking car trip, I need to terminate in a real parking space that occupies real land tracked by `engine.world`, so "land wearing a disguise" is a literal accounting fact, not a description that a build can satisfy with a bare occupancy counter.
- **US-2.** As `engine.world` (the registered outbound edge, MOD-017), I need a parking space's land footprint to be a real query/mutation against my cell zoning and land-value fields (per `engine.world.md` AC-4's documented per-cell field set), so a surface car park genuinely consumes buildable land the same way any other zoned use does.
- **US-3.** As `engine.traffic` (the registered outbound edge, MOD-023), I need insufficient parking near a destination to generate real cruising-traffic load — additional circulation trips searching for a space — added to the local network, so "the invisible congestion 'Blue' never modelled" is a real load term, not a satisfaction penalty with no traffic consequence.
- **US-4.** As `engine.destination` (a registered inbound consumer), I need per-destination parking-space accounting (capacity, occupancy, type) queryable through `ParkingAPI`, so a destination's parking sufficiency is a live read of real engine state.
- **US-5.** As the player, I need parking charges to be a real per-district/per-hour/per-permit instrument that measurably shifts mode choice, so "the strongest mode-choice lever in the toolkit" is a real elasticity, not a revenue-only slider with no behavioural effect.
- **US-6.** As late-era autonomy (M12 unlock tree), I need a car park whose demand has shrunk below a documented threshold to become eligible for conversion to redevelopment land through the SAME land-accounting mechanism that tracked it as parking, so the endgame dividend is a real land-use transition, not a scripted event.
- **US-7.** As a resident on a street near an under-provisioned destination, I need overspill parking demand to be trackable to residential on-street capacity specifically (not folded into the destination's own count), so residential permit politics (§38) has a real, separately-accounted state to react to.

## Scope

Space accounting per destination across the five documented instrument types (on-street, surface, multi-storey, park & ride, workplace); land-footprint accounting per space type through `engine.world`; charge instruments (per-district/hour/permit) and their mode-choice elasticity effect via `engine.traffic`; cruising-traffic generation from parking insufficiency; residential overspill accounting distinct from destination-side accounting; late-era demand-driven car-park-to-redevelopment-land conversion. No traffic assignment itself (`engine.traffic`'s job, only consumed here), no cell/zoning mechanics beyond the land-footprint query/mutation (`engine.world`'s job, only consumed here), no tax-instrument-panel mechanics beyond exposing the charge figure a §39 tax consumer would read (blocked pending BUG-058, see Escalations).

## Acceptance criteria

### Functional — land accounting (the load-bearing clause: "land wearing a disguise")

- **AC-1 (GR#20; code.json inbound contract).** A `ParkingAPI` exists exposing per-destination space-accounting queries (capacity, occupancy, type) and charge-instrument commands, matching code.json's documented pattern "space accounting per destination; charge instruments via PoliciesAPI", consumed by `engine.destination` through this interface alone. Check: `go doc ./internal/engine/parking ParkingAPI` shows both a space-accounting query surface and a charge-instrument command surface.
- **AC-2 (§38 five instrument types, each with a distinct land-footprint model).** The five documented parking instrument types — on-street, surface, multi-storey, park & ride, workplace — each carry a DISTINCT, documented land-footprint-per-space figure, and multi-storey's footprint-per-space is materially SMALLER than surface's (the whole point of building up rather than out), while on-street consumes linear road-adjacent frontage rather than cell-interior zoned area (a structurally different accounting than the other four). Check: `go doc ./internal/engine/parking InstrumentType` lists all five with distinct footprint fields; a passing test asserts `FootprintPerSpace(MultiStorey) < FootprintPerSpace(Surface)` for the same space count, and that on-street's footprint is expressed in linear-frontage units distinct from the area units the other four use (`grep -rn "func Test.*[Ff]ootprint\|func Test.*[Ii]nstrumentType" internal/engine/parking/*_test.go`). **Lazy implementation this rejects:** a single `SpacesPerLot` constant applied uniformly to all five types would satisfy "five instrument types exist" while failing to make multi-storey's real advantage (less land per space) checkable — the check requires the footprint figures to actually differ.
- **AC-3 (§38 land-accounting identity — the check that rejects a parking model consuming no land, per the brief).** For every registered parking facility (surface or multi-storey; on-street and workplace accounted separately per AC-2's frontage/allocation distinction below), the following identity holds: `TotalLandFootprint(facility) == SpaceCount(facility) × FootprintPerSpace(InstrumentType)`, and this figure is INDEPENDENTLY reconciled against `engine.world`'s own cell zoning/area accounting (the registered outbound edge) — the sum of cell area zoned/tagged as parking use within the facility's footprint, queried through `WorldAPI`, must equal `TotalLandFootprint` to a documented tolerance. Both sides are independently sourced: `TotalLandFootprint` from `ParkingAPI`'s own space inventory (AC-2), the zoned-area figure from `WorldAPI`'s own cell records (`engine.world.md` AC-4's `zoning`/`ownership` fields) — never one computed as a function of the other declared to trivially match. Check: `grep -rn "world\.\(CellAt\|ZoningAt\)" internal/engine/parking/*.go` (excluding `_test.go`) shows a real call into `engine.world`'s package to read zoned area, independent of the local space-inventory sum; a passing test constructs a facility with a known space count, independently sums both sides, and asserts they match (`grep -rn "func Test.*[Ll]andFootprint.*[Rr]econcil\|func Test.*[Zz]onedAreaMatch" internal/engine/parking/*_test.go`). **This is the check the brief specifically asks for and the lazy implementation it rejects:** a `ParkingCapacity int` field with no corresponding call into `WorldAPI` at all would satisfy every functional description of "parking exists" — occupancy overlay, charges, mode-choice effect — while never actually consuming a single square metre of tracked land; the reconciliation check fails such a build immediately, because there is no independently-sourced zoned-area figure for it to match against (the call into `engine.world` simply doesn't exist), which is exactly the "consumes no land" failure mode the brief names.
- **AC-4 (§38 workplace parking is a building-attached allocation, not a standalone facility).** Workplace parking's land footprint is accounted as an allocation WITHIN an existing zoned building's footprint (via `engine.world`'s cell record for that building's site) rather than a separate parking-only facility — i.e. workplace parking never independently claims new zoned land the way surface/multi-storey do; it consumes a documented fraction of the workplace site's own footprint. Check: `go doc ./internal/engine/parking WorkplaceAllocation` (or equivalent) references a building/site cell reference rather than owning an independent `Facility` record; a passing test asserts creating workplace parking does not increase the count of cells independently zoned "Parking" in `WorldAPI` (`grep -rn "func Test.*[Ww]orkplaceAllocation\|func Test.*[Nn]oNewZoning" internal/engine/parking/*_test.go`).

### Functional — charges, mode choice, and cruising traffic

- **AC-5 (§38 charges as a per-district/hour/permit instrument).** Parking charges are configurable per district, per hour, and per permit type (three independent axes, not a single citywide flat rate), and the resulting charge is queryable per space/destination. Check: `go doc ./internal/engine/parking` shows a charge-setting command taking district/hour/permit-type parameters; a passing test asserts two districts with different configured rates return different effective charges for the same hour/permit type (`grep -rn "func Test.*[Cc]hargeByDistrict\|func Test.*[Cc]hargeAxes" internal/engine/parking/*_test.go`).
- **AC-6 (§38 the strongest mode-choice lever — real elasticity, not revenue-only).** Raising a destination's effective parking charge (holding transit quality fixed) measurably reduces car-mode trip share for trips terminating at that destination, via `engine.traffic`'s mode logit (the registered outbound edge) — a build where charges only produce revenue with no traffic-side mode-share effect fails this AC. Check: `grep -rn "traffic\.\(ModeShare\|ModeLogit\)" internal/engine/parking/*.go` (excluding `_test.go`) shows a real call feeding the charge into `engine.traffic`'s mode-choice input; a passing test raises a destination's charge and asserts, via a constructed `engine.traffic` scenario, that car-mode share for that destination falls (`grep -rn "func Test.*[Cc]hargeElasticity\|func Test.*[Mm]odeShift" internal/engine/parking/*_test.go`). **Lazy implementation this rejects:** a `Revenue = Charge * OccupiedSpaces` calculation with no call into `engine.traffic`'s mode-choice path would satisfy "charges generate revenue" while leaving §38's explicit "AND the strongest mode-choice lever" clause entirely unimplemented — the check requires the traffic-side effect, not merely the fiscal one.
- **AC-7 (§38 cruising traffic from insufficiency — US-3).** When a destination's parking demand (arriving car trips) exceeds its documented space capacity, the excess generates a queryable cruising-traffic load (additional circulation trips, not merely a "some drivers couldn't park" flag) fed into `engine.traffic`'s local network load via the registered outbound edge, distinct from the trips that successfully parked. Check: `go doc ./internal/engine/parking` shows a cruising-load accessor separate from successful-parking count; a passing test drives demand above capacity and asserts (a) a nonzero cruising-load figure results and (b) that figure is delivered into `engine.traffic`'s load input, verifiable by a measurable local-network load increase in a constructed scenario (`grep -rn "func Test.*[Cc]ruisingTraffic\|func Test.*[Ss]earchCirculation" internal/engine/parking/*_test.go`). **Lazy implementation this rejects:** a destination that simply turns away excess arrivals (a rejected-trip counter) without ever adding load to the network satisfies "insufficient parking has a consequence" on a shallow read while failing to model the specific consequence §38 names — the check requires the excess to become real, measured circulation load, not a vanished trip.
- **AC-8 (§38 residential overspill — US-7).** Overspill demand from an under-provisioned destination onto nearby RESIDENTIAL on-street capacity is tracked as its OWN accounted quantity, distinct from the destination's own occupancy figure, keyed to the residential street/district it lands on (so permit-politics satisfaction effects can be attributed to the correct residents, not folded into the originating destination's stats). Check: `go doc ./internal/engine/parking` shows a residential-overspill accessor keyed by residential district/street, separate from destination occupancy; a passing test drives a destination's demand into overspill and asserts the overspill is attributed to the correct nearby residential on-street accounting, not silently absorbed into the destination's own figures (`grep -rn "func Test.*[Rr]esidentialOverspill" internal/engine/parking/*_test.go`).

### Functional — late-era conversion

- **AC-9 (§38 autonomy-driven demand shrinkage and redevelopment conversion — US-6).** Late-era autonomy (an M12-tree-gated input) reduces modelled parking demand at a documented rate, and a facility whose OCCUPANCY falls below a documented threshold for a documented sustained period becomes eligible for a `ConvertToRedevelopment` command that releases its land back to `engine.world` as unzoned/redevelopment-eligible (through the SAME `WorldAPI` land-accounting path AC-3 uses to claim it, run in reverse) — not a scripted "car park becomes park" flavour event bypassing the land ledger. Check: `go doc ./internal/engine/parking ConvertToRedevelopment` exists and calls into `WorldAPI` to release the zoned area; a passing test drives a facility's occupancy below threshold for the documented duration, converts it, and asserts (a) `WorldAPI`'s zoned-parking-area figure for those cells falls by the reconciled amount from AC-3 and (b) attempting to convert a still-busy facility is rejected (`grep -rn "func Test.*[Cc]onvertRedevelopment\|func Test.*[Aa]utonomyShrink" internal/engine/parking/*_test.go`).

### Error handling

- **AC-10 (GR#7).** Querying space accounting for an unregistered destination ID, or setting a charge for an unregistered district/permit type, returns a registry-sourced error (new `MET-E`-range code, claimed against `data/errors.json`'s reserved table at build time — no `engine.parking` sub-range exists yet) rather than a silently-created zero-value facility. Check: `grep -n "MET-" internal/engine/parking/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredDestination\|func Test.*[Uu]nknownDistrict" internal/engine/parking/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value facility record was created, not merely that a matching-named test function exists.
- **AC-11.** A negative space count, negative/over-documented-ceiling charge, or a `ConvertToRedevelopment` command against a facility still above the occupancy threshold, is rejected with a typed error, never silently clamped or silently ignored. Check: passing test coverage (`grep -rn "func Test.*[Ii]nvalidSpaceCount\|func Test.*[Cc]onvertRejected" internal/engine/parking/*_test.go`).

### Determinism, safety & scale

- **AC-12 (GR#21).** Space accounting, charge-driven mode-share effect, cruising-traffic generation, and the redevelopment-conversion decision are deterministic functions of `(worldSeed, tick, prior state, commands)` — repeated runs from identical starting state and command sequence produce byte-identical occupancy, cruising-load, and conversion-eligibility state, across worker counts. Check: `grep -rn "func Test.*[Dd]etermnis\|func Test.*[Dd]eterminis" internal/engine/parking/*_test.go`.
- **AC-13 (SG-7; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/parking/*.go` (excluding `_test.go`) returns no matches.
- **AC-14.** `go test ./internal/engine/parking/... -race -count=1` passes; `grep -n "go func()" internal/engine/parking/*_test.go` finds at least one concurrency test.
