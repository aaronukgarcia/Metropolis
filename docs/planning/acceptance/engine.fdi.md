## User stories

- **US-1.** As the player at M7+, I need prospects to appear as named archetypes (from the §46 table) each carrying a requirement sheet, so bidding for an anchor is a real evaluation against my city's actual capabilities, not a blind lottery.
- **US-2.** As the player bidding, I need my incentive package to be composed of real, costed commitments (land, infrastructure build orders with penalties, whatever tax/training levers are legally reachable today) so winning genuinely costs something before any benefit arrives.
- **US-3.** As `engine.firms` (a registered consumer of this item, and this item's own registered edge), I need a winning anchor to register as a real firm through `FirmsAPI`'s lifecycle, so anchor-closure risk (§46's "§32-coal-mine-scale shock") is a real, reachable event through the same firm-closure mechanism every other firm uses — not a scripted separate one, mirroring `engine.attract`'s AC-1's "same mechanism, not a scripted separate one" precedent.
- **US-4.** As `engine.build` (a registered consumer of this item), I need infrastructure commitments to be real `BuildAPI` orders carrying penalties for missed dates, so "road/rail/power/water to site by date" is an enforceable contract, not flavour text.
- **US-5.** As the S10 exit gate's "balance-of-trade flips" clause, I need this item's incentive costs (outflow) to be genuinely capable of exceeding the anchor's benefit (inflow) in the short run — a losing or over-generous bid is a real possible outcome, not a foregone win — so the flip has a real losing case behind it, not just a winning one.

## Scope

Prospect generation from data (the eight §46 archetypes, each with a requirement sheet), the competitive bid mechanic against an off-map region, the incentive-package composition using the two legally-reachable levers today (land/infrastructure via `BuildAPI`; consumption/utility demand via `UtilityAPI`), anchor registration as a real firm via `FirmsAPI` on a win (including the closure event that produces the coal-mine-scale shock), and win/loss cost accounting. Tax-holiday and training-partnership incentive levers are named by §46 but have no registered call edge — scoped out, blocked-pending-fix (see Escalations).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** An `FdiAPI` exists matching code.json's registered pattern — prospect archetypes from data, commitments become tracked build orders — consuming `FirmsAPI`, `BuildAPI`, `UtilityAPI` through their registered interfaces only. Check: `go doc ./internal/engine/fdi FdiAPI` shows a prospect-query surface and a bid-submission command; `grep -rln "firms\.\(firmState\|Registry\)\.\w\+ = \|build\.\(queueState\)\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/fdi`, `internal/engine/firms`, `internal/engine/build`, and `_test.go`) finds no direct exported-field write bypassing either interface.
- **AC-2 (§46 archetype coverage; GR#15 data-driven).** The prospect catalogue contains exactly the eight §46 archetypes (pharma R&D campus, semiconductor fab, PC/logistics assembler, chemicals complex, steel process plant, EV gigafactory, rail engineering works, aerospace campus), each carrying its own requirement sheet (the needs column: e.g. semiconductor fab's "colossal: 40 MW, 20k m³/day ultra-pure water, vibration-free land, port access") loaded from data, not hardcoded per-archetype Go branches. Check: `go doc ./internal/engine/fdi Archetype` (or equivalent) lists exactly these eight cases; a passing test asserts the requirement sheet differs meaningfully between at least two archetypes (semiconductor fab's utility figures vs. rail works' rail-connection requirement) so a build that ships one generic requirement template for all eight fails (`grep -rn "func Test.*[Aa]rchetype.*[Rr]equirement\|func Test.*[Ee]ightArchetypes" internal/engine/fdi/*_test.go`). False-pass risk: a count-only test (`len(archetypes) == 8`) would pass eight near-identical stubs — the check requires the requirement-sheet content to actually differ.
- **AC-3 (§46 competitive bid — win and lose both reachable).** Bidding is resolved against a modelled off-map competing region such that both outcomes (win, lose) are reachable from different bid qualities in otherwise-identical scenarios — a passing test submits a strong bid and a deliberately weak bid (same archetype, same city state) and asserts the strong bid wins and the weak bid loses. Check: `grep -rn "func Test.*[Bb]idWin\|func Test.*[Bb]idLose\|func Test.*[Cc]ompetingRegion" internal/engine/fdi/*_test.go`. A lazy-but-plausible violation: a bid resolver that always wins once the player submits any package (since there's no real off-map competitor model, just a rubber stamp) — this check rejects it by requiring a losing bid to actually lose in the same test run. (ASM-310: arrival cadence and the bid-quality-to-win-probability curve are placeholder, data-driven figures.)
- **AC-4 (§46 incentive package — real costed commitments, legally-reachable levers only).** A submitted bid's land/infrastructure incentive commitments are issued as real `BuildAPI` orders (registered edge) carrying penalty terms for missed delivery dates, and land discount/free-land grants are posted as a real cost through the same `BuildAPI` land-purchase path (not a bespoke parallel land-pricing calculation — GR#3), each independently retrievable after bid submission. Check: `go doc ./internal/engine/fdi` shows the incentive package composed of `BuildAPI` order references, not opaque cost floats; a passing test submits a bid with an infrastructure commitment and asserts a corresponding `BuildAPI` build order exists with a penalty term attached (`grep -rn "func Test.*[Ii]ncentivePackage\|func Test.*[Ii]nfrastructureCommitment" internal/engine/fdi/*_test.go`).
- **AC-5 (§46 anchor win — real firm registration, not a scripted bonus).** On a bid win, the anchor is registered as a real firm through `FirmsAPI`'s lifecycle (registered edge) — not a separate "anchor" struct maintained only inside `engine.fdi` — so downstream job counts, wages, and later closure events all flow through `engine.firms`' own machinery. A passing test asserts a win produces a queryable `FirmsAPI` firm record (not merely an internal `engine.fdi` win-flag), and that the firm's employment figure is nonzero and consistent with the archetype's stated job scale (§46 table: e.g. semiconductor fab "highest wages", gigafactory "8k mixed-skill"). Check: `grep -rn "func Test.*[Aa]nchorRegist\|func Test.*[Ww]inCreatesFirm" internal/engine/fdi/*_test.go`. A lazy-but-plausible violation: tracking the anchor's job count as an internal `engine.fdi` field that never actually calls `FirmsAPI` — this check rejects it by requiring the firm to be independently retrievable through `FirmsAPI`, per US-3's "same mechanism, not scripted" requirement.
- **AC-6 (§46 dependency risk — closure reachable through the SAME mechanism, not scripted).** Anchor closure (the "§32-coal-mine-scale shock") is reachable by driving the registered anchor firm to close through `FirmsAPI`'s own closure path (e.g. sustained negative conditions per that module's own criteria) — not a bespoke `engine.fdi`-only "closure event" that bypasses `FirmsAPI`. A passing test drives an anchor firm to closure and asserts (a) `FirmsAPI` reports the firm closed, and (b) the closure is observable from `engine.fdi`'s own prospect-history query as a real historical event, not silently dropped. Check: `grep -rn "func Test.*[Aa]nchorClosure\|func Test.*[Dd]ependencyShock" internal/engine/fdi/*_test.go`. This mirrors `engine.attract`'s AC-4/AC-9 precedent (a defect-catcher requiring the negative branch to run through the same real mechanism as the positive one, not a scripted separate one) applied to firm closure instead of migration.
- **AC-7 (§46/line 680 balance-of-trade contribution — cost-now, benefit-later, both real).** A passing scenario test demonstrates the temporal asymmetry the exit gate's "flip" depends on: immediately after a bid win, the incentive package's `BuildAPI`-posted costs are measurably nonzero and posted before the anchor firm has generated any revenue/tax (cost precedes benefit), and over a longer simulated run, the anchor firm's own revenue/wage-tax flow (via `FirmsAPI`→`FinanceAPI`, existing registered chain) eventually produces a measurable net-positive contribution — the test asserts both the early net-negative state and the later net-positive state are real, distinguishable ledger states, not a single lump-sum "FDI is good" assertion. Check: `grep -rn "func Test.*[Cc]ostBeforeBenefit\|func Test.*[Nn]etFlipOverTime" internal/engine/fdi/*_test.go`. A lazy-but-plausible violation: crediting the anchor's full projected lifetime value to the ledger at win-time (a model where FDI is always immediately net-positive) — this check rejects it because it demands an early state where cost has posted and benefit has not, which such a model cannot produce.

### Error handling

- **AC-8 (GR#7).** Submitting a bid whose infrastructure commitment cannot be issued as a valid `BuildAPI` order (e.g. the target site fails `BuildAPI`'s own validation) returns a registry-sourced error before any incentive cost is posted — never a partially-committed bid that charges the land discount but silently drops the infrastructure order. Check: `grep -n "MET-" internal/engine/fdi/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalidCommitment\|func Test.*[Pp]artialBid" internal/engine/fdi/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no incentive cost was posted to the ledger as a side effect, not merely that a matching-named test function exists.
- **AC-9 (GR#7).** Losing a bid never posts any incentive cost (land/infrastructure) — a passing test asserts the ledger shows zero new trade-related transactions after a bid loss, distinct from a win's nonzero postings (AC-7). Check: `grep -rn "func Test.*[Ll]oseNoCoast\|func Test.*[Ll]osingBidZeroCost" internal/engine/fdi/*_test.go` (naming aside — the check is: a losing bid's cost delta is exactly zero).

## Escalations

- **For Ben — the balance-of-trade flip, this item's contribution.** AC-7 is the load-bearing check: it requires a real early state where incentive cost has posted and anchor benefit has not (cost-before-benefit), paired with a real later state where net benefit turns positive — rejecting a model that credits the anchor's full lifetime value at win-time (which would make FDI trivially always-positive and defeat the exit gate's "flip" language). AC-3's win/lose bidirectionality is the second half: a bid that always wins removes the loss case entirely, which is the other way a "flip" demo gets faked.
- **For Bill/Ben — BUG-058, two instances specific to this file.** `engine.fdi → engine.tax` (tax-holiday incentive) and `engine.fdi → engine.education` (training-partnership incentive, already flagged by BA-Registry as candidate #8) are both named explicitly in §46's incentive-package list but have no registered edge. Scoped out of AC-4 rather than assumed; filed against BUG-058 (comment posted 2026-08-11 alongside the other three modules' findings).
- **For Aaron (ASM-310).** Prospect arrival cadence and the bid-quality-to-win-probability curve are placeholder, data-driven figures used to make AC-3's win/lose scenarios constructible. Real pacing and odds are a design call, not a BA judgment.
