## Why this is a dedicated data-authoring file, not an addition to `engine.policies.md` or `engine.tax.md`

FEAT-056 is tagged `code.json:engine.policies` in the BOW, but its actual deliverable — per its own description ("Code: data/", "PROCESS: ... all values land in data files") — is content for `data/tax_instruments.json` (and, on the policy side, `data/policies.json`, out of this file's scope, see below). Both `engine.tax.md` and `engine.policies.md` are already-committed, actively-gated acceptance files with their own ACs governing the **engine behaviour** that consumes these data files (loading, mechanism-vs-mutation, preview, incidence computation, determinism). Appending to either would mean editing a file this BA does not own (both are explicitly off-limits per the brief) and would conflate "what the engine must do with the data" (settled) with "what the data must contain" (this item's actual gap). `data.modes-naming.md` (FEAT-047) is the established precedent for exactly this shape: a dedicated data-authoring acceptance file, sitting alongside the engine-behaviour files it feeds, scoped to schema + content + provenance rather than engine mechanics. This file follows that precedent.

**A genuine scope split found while reading, logged as ASM-417 (see Escalations):** FEAT-056's direction covers *both* taxes and policies, and its own worked examples span both — the HGV-weekend-ban example is a **policy** (§52's movement-lever library; `engine.policies` consumes `data/policies.json`), while the industrial-EV-van-discount example reads as either a tax relief or a policy discount depending on implementation. This file is scoped to `data/tax_instruments.json` only, per its filename and per the file-ownership rule (only `data.taxinstruments.md` is claimed here). The policy-side half of FEAT-056's direction — zone-scoped policy application in `data/policies.json`, and whether `engine.policies.md`'s `ResolveScope` needs a fourth scope kind — is **not** decided by this file and is flagged to Bill as its own open question, potentially warranting a sibling `data.policyinstruments.md` file mirroring this one.

## Acceptance criteria

### Schema — instrument set completeness

- **AC-1 (FEAT-056; the six-instrument UK-today set, ASM-415).** `data/tax_instruments.json` carries exactly the six instruments FEAT-056 names — `vat`, `importDuties`, `corporationTax`, `paye`, `councilTax`, `businessRates` — each conforming to `engine.tax.md` AC-2's schema (name, category, valid rate range, elasticity coefficient(s), bearer-split weights). The six IDs are the canonical as-authored set and become `engine.tax` lookup keys. **Casing ruling (SEC-090, ASM-652, resolved 2026-08-20):** the IDs are accepted exactly as authored — four are camelCase (`importDuties`, `corporationTax`, `councilTax`, `businessRates`), two lowercase (`vat`, `paye`). The `engine.roads` `buildingIDPattern` lowercase-slug convention is NOT applied to these instrument IDs; an earlier "stable lowercase-slug IDs" clause in this AC was drift, now removed. The loader (`internal/foundation/data/tax_instruments.go`) deliberately accepts the as-authored set and must not be retrofitted to enforce `buildingIDPattern` against it. Note that `councilTax` and `businessRates` may already exist as stub entries from `engine.tax.md`'s own dispatch; this AC's job is to confirm both are present and to add the four instruments §39's own panel never named. Check: a passing loader test asserts the loaded instrument-ID set is a **superset** containing all six IDs (not merely `len() >= 6`, which would pass six wrong instruments) (`grep -rn "func Test.*[Ii]nstrumentSet\|func Test.*[Ss]ixInstruments" internal/foundation/data/tax_instruments_test.go`). **What a lazy implementation looks like:** shipping only `councilTax`/`businessRates` (the two §39 already named) and treating VAT/import-duties/corporation-tax/PAYE as future work — this satisfies "the file loads" but not FEAT-056's actual direction. **False-pass warning:** a count-only check (`len(instruments) == 6`) passes six arbitrary instruments (e.g. six behavioural levies with none of the four UK-today additions); the check must assert the specific ID set, not its cardinality.
- **AC-2 (§39/§54; PAYE's two-component shape, not a single flat rate).** `paye`'s entry declares **two** sub-components — an income-tax band structure and an employee/employer National Insurance rate — as distinct, independently-settable rate fields (never a single blended "PAYE rate" that hides which of the two moved), since §54 names "income tax (per wage band)" as banded and NI is legally a separate deduction with its own employer-side leg (feeding AC-6's PAYE bearer split). Check: `go doc` (or the file's own schema doc, AC-10) shows `paye` carrying both an `incomeTaxBands` structure and a `niRate`/`employerNiRate` pair, not a single scalar; a passing loader test asserts both sub-fields are independently present and independently settable (`grep -rn "func Test.*[Pp]ayeComponents\|func Test.*[Nn]iSplit" internal/foundation/data/tax_instruments_test.go`). **What a lazy implementation looks like:** one `paye.rate` field standing in for both income tax and NI — technically "PAYE exists" but structurally incapable of ever showing the employer-NI half of the incidence split AC-6 requires.
- **AC-3 (§39/§54; VAT and import-duties are consumption/border levies, not income levies — distinct valid-rate domains).** `vat`'s valid rate range and elasticity model apply to local consumption transactions (per §54's "sales tax/VAT share... on local consumption"); `importDuties`'s valid rate range and elasticity model apply to imported-goods transactions specifically (distinct from `engine.market`'s commodity import prices — `importDuties` is a tax *on* those transactions, not a second price figure competing with `data/market.json`'s `importPriceMicropounds`). Check: a passing loader test asserts `vat` and `importDuties` each declare a `category` field distinguishing them (`"consumption"` vs `"import"` or equivalent) and that neither entry duplicates a `data/market.json` commodity price field name (`grep -rn "func Test.*[Vv]atCategory\|func Test.*[Ii]mportDutyCategory" internal/foundation/data/tax_instruments_test.go`; `grep -n "importPriceMicropounds" data/tax_instruments.json` finds no match — GR#3, not a second source of truth for the same figure).

### Schema — zone-scoped application (ASM-416)

- **AC-4 (§39 AC-7 precedent generalised; the zone-override block).** Every one of the six instruments carries an optional `zoneOverrides` field: a map keyed by one of §34's 8-way zone classes (`dwelling`, `shop`, `office`, `entertainment`, `farming`, `manufacturing`, `heavyIndustry`, `mining`) to a per-zone rate multiplier or categorical relief (e.g. a `{"rateMultiplier": 0.7}` discount, or a `{"reliefPercent": 100}` full exemption), each override entry carrying its own `provenance`/placeholder-disclosure per AC-9. At least the instrument FEAT-056's own worked example targets — a business/vehicle-adjacent instrument — carries a populated `zoneOverrides.heavyIndustry` (or `manufacturing`) entry giving a discount, demonstrating the shape end-to-end rather than leaving `zoneOverrides` schema-only-and-empty everywhere. Check: `go doc` (or schema doc, AC-10) documents `zoneOverrides`'s shape and the closed 8-class enum; a passing loader test asserts at least one instrument has a non-empty `zoneOverrides` map and that a zone-scoped query for that instrument in that zone class differs from the citywide default (`grep -rn "func Test.*[Zz]oneOverride\|func Test.*[Zz]oneScoped" internal/foundation/data/tax_instruments_test.go`). **What a lazy implementation looks like:** a `zoneOverrides` field present in the schema (satisfying "the field exists") on every instrument but populated on none — technically schema-complete, but FEAT-056's own worked example ("an industrial area giving a discount on EV vans") never becomes checkable data. **False-pass warning:** a check that only asserts the field's *type* is correct (a map of the right shape) would pass an all-empty implementation; the check must assert at least one populated, queryable-different entry exists.
- **AC-5 (zone-class enum closed and shared, not re-invented per instrument).** The 8-way zone-class key set used in every `zoneOverrides` map is identical across all six instruments (no instrument uses a different spelling, casing, or subset of zone-class keys than another) and matches §34's 8 classes exactly. Check: a passing loader test asserts the observed zone-class key set across every instrument's `zoneOverrides` is a subset of one shared, documented 8-value enum, never an instrument-local ad hoc string (`grep -rn "func Test.*[Zz]oneClassEnum\|func Test.*[Ss]haredZoneKeys" internal/foundation/data/tax_instruments_test.go`).

### Schema — bearer categories for the four new instruments (ASM-418, extending ASM-287)

- **AC-6 (§39/§54 incidence; VAT/import-duties/corporation-tax/PAYE each get a bearer set, per ASM-287's per-instrument pattern).** Following the already-lead-ruled ASM-287 shape (per-instrument bearer sets, not a universal taxonomy), each of the four new instruments declares its own bearer-category weights: `vat` — consumer vs firm (pass-through-dependent); `importDuties` — importer firm vs downstream consumer (pass-through-dependent); `corporationTax` — shareholders/owners vs employees (via wage suppression) vs consumers (via price pass-through); `paye` — employee (income tax + employee NI) vs employer (employer NI, AC-2's second leg). Every bearer weight is a *rate-dependent* field (a function of the current rate, or at minimum two documented example points at different rates), never a fixed split — matching `engine.tax.md` AC-5's requirement that incidence *proportions* move with rate, not just totals. Check: a passing loader test asserts each of the four instruments' bearer-weight data includes at least two distinct rate points with differing bearer-split proportions (`grep -rn "func Test.*[Bb]earerRateDependent\|func Test.*[Ii]ncidenceShiftData" internal/foundation/data/tax_instruments_test.go`). **What a lazy implementation looks like:** a single fixed bearer-split percentage per instrument (e.g. "VAT is always 60% consumer / 40% firm") — this is exactly the fixed-lookup-table shape `engine.tax.md` AC-5 already names as the trap its own check exists to reject; supplying only one rate point's data here would make AC-5's downstream check impossible to satisfy no matter how the engine code is written, because the data itself carries no shift to detect.

### Balance-number placeholder discipline (ASM-284, confirmed regime)

- **AC-9 (every numeric value is a disclosed placeholder, not an invented final figure).** Every rate, threshold, elasticity coefficient, zone-override multiplier/relief, and bearer-weight figure in every one of the six instruments' entries carries a `provenance`/`comment` field stating (a) whether it is transcribed verbatim from the spec (rare — §39/§54 give almost no literal UK-today figures beyond category names), sourced from real UK-today rates as a directional literature reference (VAT 20%, current income-tax bands, etc.), or a derived placeholder with no external anchor, and (b) explicitly disclosing pending-Aaron's-balance-pass status — matching `data/market.json`'s "Plausible v1 static price, pending M2 Batch tuning" convention and `data.modes-naming.md` AC-16's placeholder-disclosure bar (not AC-6's stronger literature-citation bar, since these are player-felt balance numbers, not physics/behavioural-model coefficients). A bare number with no disclosure is a schema violation. Check: a passing loader test asserts every numeric field across all six instruments (rates, thresholds, elasticity coefficients, zone-override multipliers, bearer weights) has a non-empty sibling disclosure field naming pending-tuning status (`grep -rn "func Test.*[Pp]laceholderDisclosure\|func Test.*[Pp]rovenance" internal/foundation/data/tax_instruments_test.go`). **What a lazy implementation looks like:** proposing real-looking UK figures (VAT at 20%, corporation tax at 25%) with no disclosure, which — precisely because they resemble real published rates — would read as "researched and final" to Aaron's balance pass instead of "here's a literature-grounded starting point for you to approve or reject row-by-row," collapsing the delegated-tuning process FEAT-056 explicitly requires into an accidental fait accompli. **False-pass risk:** a disclosure field that says only `"pending tuning"` with no indication of *where the number came from* (spec/literature/pure-placeholder) technically satisfies non-empty-string but fails the row-by-row-approval process's actual need — Aaron needs to know which numbers are "real UK rate, sanity-check the mapping" versus "guessed, sanity-check the number itself." The check must confirm the disclosure names a source category, not merely that it is non-empty.
- **AC-10 (money type consistency with `engine.tax.md` AC-10).** All monetary values (thresholds, absolute-amount instruments if any) are expressed as int64 micro-pounds, never float, matching `engine.tax.md` AC-10's money-type requirement — this file supplies the data, not the Go type, but a float literal in the JSON (e.g. `"threshold": 12570.50`) would force a lossy or ambiguous conversion at load. Check: `grep -nE ":\s*[0-9]+\.[0-9]+" data/tax_instruments.json` on any field documented as a monetary amount finds no decimal-point monetary literal (percentage-rate fields, which are legitimately fractional, are excluded — same carve-out as `engine.tax.md` AC-10).

### ASM-652 — AC-1 casing contradiction resolved as-accepted (amends AC-1; SEC-090)


AC-1 names the six IDs `vat, importDuties, corporationTax, paye, councilTax, businessRates` and, in the same sentence, demands they match `engine.roads`' lowercase-slug `buildingIDPattern` — an internal contradiction (four IDs are camelCase). Resolution: the loader accepts the six exact IDs as-authored and does not reject the file over the casing conflict; the six IDs are the canonical authoring, and the "lowercase-slug" wording in AC-1 is the drift (SEC-090). If lowercase-slug IDs were intended, the data file and any future `engine.tax` lookup keys would need renaming.
