# Acceptance criteria — engine.attract (MOD-029)

**BOW code:** MOD-029
**Spec refs:** §11 Attractiveness & Migration — the master dial (`docs/METROPOLIS-MASTER-v2.1.md` lines 232-236: the seven-term weighted formula `A = w₁·jobAvailability + w₂·housingAffordability + w₃·serviceCoverage + w₄·environment + w₅·leisureFit + w₆·safety + w₇·reputation(momentum)`; `Monthly net migration = g(A − A_world) × capacity constraints`; "Emigration uses the same function per resident (personality-weighted: ambitious citizens leave sooner when opportunity dries up)"; "**Reputation** is a slow-moving momentum term — cities rising attract beyond fundamentals; cities falling repel beyond fundamentals. That asymmetric momentum is the Detroit trap."); §4 Population Scale (line 139: "Growth is migration-dominated... the engine of growth is Attractiveness (§11), pulling migrants from an abstract world pool (v1: infinite pool, static world... both share the 'living outside world' future hook)"); §12 Failure — the Detroit Spiral (lines 238-240: the shock→emigration→tax-base-↓→service-cuts→attractiveness-↓→more-emigration loop this item's negative branch must genuinely support, since `engine.spiral`/MOD-030 is the registered downstream consumer that depends on decline being reachable); code.json `engine.attract` entry (inbound `AttractAPI`, "term-decomposed A score, every term drill-through"; consumed by the 2 registered consumers `engine.spiral`, `engine.tourism`; outbound calls to `engine.citizens`, `engine.finance`, `engine.households` **only** — see ASM-243/BUG-058 below for the five §11 terms this does not cover); `engine.households.md` AC-9 (the `HousingAffordability` accessor this item consumes).
**Date:** 2026-08-11
**Status:** ready
**Package under test:** `internal/engine/attract/` (path from `node claude-bow.js show MOD-029`); the S6 exit-gate scenario test additionally spans `internal/engine/world/`, `internal/engine/build/`, `internal/engine/citizens/`, `internal/engine/households/`, `internal/engine/logistics/` and `internal/engine/core/`'s headless run surface — see AC-9 and ASM-246.
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/attract/...`. **This is the sprint's exit-gate item — the Tester's suite MUST include AC-9 (the end-to-end scenario) run to completion, not skipped as "integration, not unit."**

## User stories

- **US-1.** As `engine.spiral` (MOD-030, the Detroit spiral), I need `AttractAPI`'s migration function to be **genuinely bidirectional** — capable of driving population *down*, not just up — because the spiral's entire failure-state model depends on decline being reachable through this same mechanism, not a scripted separate one (§12: "the same attractiveness engine that drives growth, run in reverse").
- **US-2.** As the reputation term, I need momentum that is **asymmetric** — rising cities attract beyond fundamentals, falling cities repel beyond fundamentals — because a symmetric momentum term would make the Detroit trap a marketing description rather than a mechanic (§11's explicit "that asymmetric momentum is the Detroit trap").
- **US-3.** As an individual resident with personality traits, I need my own emigration probability to depend on my ambition (and the same for every other resident, in principle, per personality axis where the spec is explicit about ambition), so emigration is a real per-person decision, not a city-wide dice roll that happens to remove N citizens.
- **US-4.** As the housing/junction capacity system, I need migration inflow to be genuinely bounded by housing vacancy and junction arrival throughput, so "you can literally bottleneck your own growth" (§11) is a real possible outcome, not flavour text.
- **US-5.** As the S6 sprint exit gate, I need one continuous headless scenario that proves zone→build→migrate→work→deliver end to end, with JIT shortfalls propagating to satisfaction/production and the junction queue's state genuinely populated — because writing this scenario four times (once per S6 file) would violate GR#3, and writing it zero times leaves the sprint's own exit criterion untested.
- **US-6.** As `code.json`'s current registered edges, I need this item to be honest about which of the seven §11 terms it can actually compute by calling a sibling module today (`housingAffordability` via `engine.households`/`engine.finance`) versus which five it cannot (`jobAvailability`, `serviceCoverage`, `environment`, `leisureFit`, `safety` — no registered outbound edge exists to `engine.firms`/`market`, `engine.services`, `engine.world`, `engine.leisure`, `engine.crime`), so the Tester never has to guess whether a call that "shouldn't exist yet" secretly does (GR#20; ASM-243, filed against BUG-058).

## Scope

The `AttractAPI` term-decomposed `A` score (all seven §11 terms independently queryable), the bidirectional monthly-net-migration function `g(A − A_world) × capacity constraints`, per-resident personality-weighted emigration, the asymmetric reputation-momentum term, the v1 static/infinite world pool behind its future hook, and the S6 exit-gate end-to-end scenario (this file's single-owner AC — see US-5).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** An `AttractAPI` exists matching code.json's registered inbound contract: each of the seven §11 terms (`JobAvailability`, `HousingAffordability`, `ServiceCoverage`, `Environment`, `LeisureFit`, `Safety`, `Reputation`) is independently queryable (drill-through, per code.json's own `"pattern"` field), plus the composite `A()` score and a command-based migration-mutation path, consumed by `engine.spiral` and `engine.tourism` through this interface alone. Check: `go doc ./internal/engine/attract AttractAPI` lists all seven term accessors plus `A()`; a passing test asserts changing one term's input changes only that term's accessor output and the composite, never the other six accessors (`grep -rn "func Test.*[Tt]ermDrillThrough\|func Test.*[Tt]ermIsolation" internal/engine/attract/*_test.go`). A lazy-but-plausible violation: computing a single opaque `A` float with no per-term breakdown — this check rejects it because it demands seven independently-inspectable accessors that respond only to their own term's input.
- **AC-2 (§11 formula; GR#15 data-driven weights).** `A`'s seven weights (`w₁`...`w₇`) are loaded from data (not hardcoded Go literals), so rebalancing is a data edit. Check: `grep -n "w1 *=\|0\.[0-9]\+ \*\s*jobAvail\|hardcoded" internal/engine/attract/*.go` (excluding `_test.go`) finds no literal weight constants; a passing test loads two different weight-config fixtures and asserts `A()` differs for identical term inputs (`grep -rn "func Test.*[Ww]eightFromData" internal/engine/attract/*_test.go`). A lazy-but-plausible violation: `w1 := 0.2` etc. baked into source — this check rejects it by swapping the data fixture and demanding the computed score actually change.
- **AC-3 (registered-edge terms vs. pushed-input terms — ASM-243/BUG-058).** `HousingAffordability` is computed by calling `engine.households`' `HousingAffordability` accessor (per `engine.households.md` AC-9) combined with `engine.finance` wage/income context — both registered outbound edges. The remaining five terms (`JobAvailability`, `ServiceCoverage`, `Environment`, `LeisureFit`, `Safety`) are accepted via a documented `TermInputs` struct/command (values pushed in by a caller), because code.json registers no outbound edge from `engine.attract` to `engine.firms`/`market`, `engine.services`, `engine.world`, `engine.leisure`, `engine.crime`. Check: `go doc ./internal/engine/attract` shows `HousingAffordability`'s implementation calling `households.` and `finance.` accessors (`grep -n "households\.\|finance\." internal/engine/attract/*.go`, excluding `_test.go`); `grep -rln "\"Metropolis/internal/engine/\(firms\|market\|services\|world\|leisure\|crime\)\"" internal/engine/attract/*.go` (excluding `_test.go`) finds **no** import of those five packages — proving `engine.attract` does not silently reach into unregistered modules to fake the missing edges, which would be a GR#20 violation disguised as a working feature.
- **AC-4 (§11 bidirectional migration — the central defect-catcher).** Monthly net migration `g(A − A_world)` is signed and unbounded in sign: it can be negative (net emigration) as well as positive (net immigration), and a negative result is actually applied — citizens are removed via `CitizensAPI`'s departure command, not merely reported as a negative number a caller could clamp. Check: a passing test constructs two scenarios differing only in the sign of `(A − A_world)` (equal magnitude, opposite sign) and asserts (a) `g()`'s output has opposite sign in each case, and (b) in the negative case, a scenario-level run over several simulated months shows `CitizensAPI`'s reported population **count actually decreases** (`grep -rn "func Test.*[Bb]idirectionalMigration\|func Test.*[Pp]opulationDecline" internal/engine/attract/*_test.go`). A lazy-but-plausible violation: `g := math.Max(0, k*(A-Aworld))`, or a "departure" path that only decrements a bookkeeping counter without ever calling `CitizensAPI`'s removal command — this check rejects both, because it demands an actual population-count decrease read back from `CitizensAPI`, not just a negative intermediate value that never propagates.
- **AC-5 (§11 reputation-momentum asymmetry — the Detroit-trap mechanic; ASM-244).** Reputation's contribution to `A` is **asymmetric** in magnitude between a rising and an equally-sized falling stimulus: applying equal-magnitude, equal-duration positive and negative shocks to the six non-reputation terms from an identical steady-state baseline produces `|reputation contribution after the negative shock| > |reputation contribution after the positive shock|` over a matched observation window. Check: `grep -rn "func Test.*[Rr]eputationAsymmetr" internal/engine/attract/*_test.go` exists and asserts a strict inequality (not just "reputation changed") between the two shock directions. A lazy-but-plausible violation: reputation implemented as a single symmetric exponential moving average of the six-term sum — real momentum, real lag, but perfectly symmetric — which would pass AC-4's "migration can go negative" check while failing this one, because a symmetric EMA produces equal-magnitude departures for equal-magnitude equal-duration stimuli in each direction. **This is the specific check that would catch a one-way dial disguised as a working migration model** — a build that merely satisfies AC-4 without also satisfying AC-5 is a city that can shrink but never gets the "beyond fundamentals" reputation kick that makes decline self-reinforcing, which is what `engine.spiral`'s Detroit-spiral criteria actually depend on (US-1).
- **AC-6 (§11 per-resident personality-weighted emigration).** Individual emigration probability/hazard is a function of that resident's personality (ambition specifically, per §11's explicit example: "ambitious citizens leave sooner when opportunity dries up"), not one population-wide rate applied uniformly. Check: a passing test constructs two citizens identical in every field except the ambition personality axis, runs both through an identical declining-`A` scenario, and asserts the higher-ambition citizen's per-person emigration probability is strictly greater (`grep -rn "func Test.*[Pp]ersonalityWeightedEmigration" internal/engine/attract/*_test.go`). A lazy-but-plausible violation: computing a single city-wide emigration rate and selecting which N citizens leave uniformly at random — this check rejects it by inspecting the per-citizen probability function directly (not aggregate counts) and demanding it take personality as an input whose value changes the output.
- **AC-7 (§11 capacity constraints on immigration).** Net immigration is bounded by housing vacancy (via `engine.households`) and junction arrival throughput (via `engine.logistics`'s queue-capacity state, consumed at the composition/scenario level per ASM-246 since no direct call edge is registered for it either) even when `A − A_world` is large and positive. Check: a passing test holds `(A − A_world)` at a large positive constant while forcing housing vacancy to zero, and asserts realised net immigration is zero (or capped at the vacancy figure) rather than scaling with `g()` alone (`grep -rn "func Test.*[Cc]apacityConstrain" internal/engine/attract/*_test.go`). A lazy-but-plausible violation: applying `g(A-Aworld)` directly as the admitted-migrant count with no vacancy/throughput check — this check rejects it by forcing vacancy to zero and demanding zero (or capped) admission despite a large attractiveness gap.
- **AC-8 (§4 v1 static/infinite world pool; future hook).** `A_world` (the comparison baseline) is a static, data-loaded value in v1 (GR#15), with the API shaped so a future finite/dynamic world pool (§4's explicit "future hook") is an interface/data change, not a rewrite — e.g. `A_world` is read through an accessor rather than passed as a bare float literal at every call site. Check: `go doc ./internal/engine/attract WorldPool` (or equivalent) documents the v1-static / future-dynamic seam in prose; `grep -n "AWorld.*:=\s*[0-9]" internal/engine/attract/*.go` (excluding `_test.go`) finds no hardcoded numeric literal for `A_world` outside the data-loading path.
- **AC-9 (the S6 exit gate — single-owner, end-to-end scenario; ASM-245/ASM-246).** A headless scenario test, composing only registered public `WorldAPI`/`BuildAPI`/`CitizensAPI`/`HouseholdsAPI`/`AttractAPI`/`engine.logistics`'s API (never reaching into another package's internals — GR#20), run through `engine.core`'s headless command loop, proves the full chain from 0 citizens in one continuous run:
  1. **Zone → build:** land is zoned and at least 2 distinct HS typologies are constructed via `BuildAPI`/`WorldAPI`.
  2. **Migrate (positive branch):** enough simulated months run for `AttractAPI`'s positive migration branch to admit migrants — `CitizensAPI`'s reported population count leaves 0, and each new citizen is attached to a household via `HouseholdsAPI` (not floating unassigned).
  3. **Work (documented interim rule — ASM-245):** migrants transition `CitizensAPI`'s `employmentState` via a documented placeholder rule, since `engine.firms`/`engine.market` (MOD-058, milestone M4) are not built by S6. This step is explicitly a stand-in, not real skill-matched job assignment, and is labelled as such in the test.
  4. **Deliver — JIT shortfall propagation:** a commodity import cut (or equivalent forced shortfall) is deliberately injected into `engine.logistics`, and the test asserts a measurable satisfaction and/or production delta on affected citizens/households afterward — a logged shortfall event alone does not satisfy this step; the delta must be read back from `CitizensAPI`/`HouseholdsAPI` state.
  5. **Junction queue renders:** the junction arrival queue's exported/queryable state (per `engine.logistics`' own ASM-235: rendering is UI's job, this item only requires queryable state) shows nonzero entries during the peak-arrival month following step 2.
  6. **Migrate (negative branch — the direction most likely to be faked):** a second shock (service collapse or an employer-closure-equivalent placeholder, consistent with step 3's interim-employment scope) drives `A` below `A_world`, and the test asserts `CitizensAPI`'s population count **decreases** afterward, before the run ends — proving both directions inside one continuous run, reusing AC-4/AC-5's mechanism rather than a separate disconnected scenario.

  Check: `go test ./internal/engine/attract/... -run S6EndToEnd` (path per ASM-246) passes; its assertions explicitly include a population-count increase assertion after step 2 **and** a population-count decrease assertion after step 6 in the same test run — not two independent tests that could each pass with a one-way model. A run whose only migration assertion is "population increased," or that substitutes mocks for any of the six composed APIs, fails this AC regardless of whether it's green.

### Error handling

- **AC-10 (GR#7).** An invalid weight config (a weight outside its documented valid range, or a config that fails to load) returns a registry-sourced error (new `MET-E`-range code) rather than silently defaulting to an unweighted or zero-weighted term. Check: `grep -n "MET-" internal/engine/attract/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalidWeight" internal/engine/attract/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no unweighted/zero-weighted term was silently substituted into the live config, not merely that a matching-named test function exists.
- **AC-11.** Missing/unloadable `A_world` data degrades to a documented fallback (last-known-good value, or the engine refuses to start with a named error) rather than silently defaulting to `A_world = 0` — which would make any positive `A` register as attractive regardless of actual world conditions, silently breaking the entire migration model without a visible failure. Check: passing test coverage asserts the fallback path is distinguishable from a genuine zero (`grep -rn "func Test.*[Mm]issingWorldPool" internal/engine/attract/*_test.go`).

### Determinism & safety

- **AC-12 (GR#21).** Every stochastic draw (which specific citizens emigrate, net of the personality-weighted probability computed in AC-6; any tie-breaking in migrant-to-household assignment) uses the counter-based hash stream `hash(worldSeed, id, month, purposeTag)` — no shared/global RNG anywhere in the package. Check: `grep -n "rand.New\|math/rand\"" internal/engine/attract/*.go` (excluding `_test.go`) finds no shared/global RNG source.
- **AC-13 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/attract/*.go` (excluding `_test.go`) returns no matches.
- **AC-14.** `go test ./internal/engine/attract/... -race -count=1` passes with no data race.

### Documentation

- **AC-15.** `internal/engine/attract/doc.go` states the module key `engine.attract`, cites §11 and §4, documents the seven-term formula in prose, states in prose which terms are computed via registered calls today vs. accepted as pushed input pending BUG-058 (ASM-243), and states the reputation-momentum asymmetry rule (§11's "cities rising attract beyond fundamentals; cities falling repel beyond fundamentals") explicitly — not merely implied by the code. Check: `grep -n "engine.attract" internal/engine/attract/doc.go` and `grep -n "§11\|section 11" internal/engine/attract/doc.go` and `grep -n "BUG-058\|TermInputs" internal/engine/attract/doc.go` and `grep -n "asymmetr" internal/engine/attract/doc.go` all match.

## Out of scope

- Real computation of `jobAvailability`, `serviceCoverage`, `environment`, `leisureFit`, `safety` from their true source modules (`engine.firms`/`market`, `engine.services`, `engine.world`, `engine.leisure`, `engine.crime`) — no registered call edge exists for any of them (ASM-243/BUG-058); this item accepts them as pushed input and drill-throughs them correctly once supplied.
- Real skill-matched job assignment for arriving migrants — `engine.firms`/`engine.market` territory (MOD-058, milestone M4, not built by S6); AC-9 step 3 uses a documented interim placeholder only.
- The Detroit-spiral failure-state mechanics themselves (abandoned buildings, blight spread, ghost-city ending) — `engine.spiral`'s (MOD-030) job; this item only guarantees the bidirectional/asymmetric migration mechanism MOD-030 depends on being genuinely reachable.
- Coastal/irregular migration (§30) and holiday tourism's visitor economy (§44) — separate later items (`engine.coastal`, `engine.tourism`) that consume `AttractAPI` but aren't built here.
- Rendering the junction queue for the player — UI's job (per `engine.logistics`' own ASM-235); this item's AC-9 step 5 only requires the underlying state to be queryable.

## Escalations

- **For Ben — the headline deliverable.** Bidirectional migration is made checkable by AC-4 (signed `g()`, applied not just reported, population count actually decreases) plus, separately, AC-5 (a strict magnitude inequality between an equal up-shock and an equal down-shock's reputation contribution). AC-4 alone is not enough — a symmetric momentum model passes AC-4 but fails AC-5, and AC-5 is the one that actually protects MOD-030 (Detroit spiral) from becoming vacuously unfailable, since MOD-030's criteria need decline to be *reinforcing*, not merely *possible*.
- **For Ben/Bill — BUG-058 (ASM-243).** Five of the seven §11 terms have no registered outbound call edge from `engine.attract` in code.json. I did not silently assume the calls exist (that would be a GR#20 violation) or invent a fake dependency edge; AC-3 requires the five terms to arrive via a documented input surface instead, and explicitly checks that the five unregistered packages are never imported. If BUG-058 wires the real edges, AC-3 and AC-9 (which currently only exercises `housingAffordability` for real, and stubs/pushes the rest) both need a revision pass.
- **For Bill — placement of the exit-gate scenario test (ASM-246).** No existing BOW item explicitly owns "the S6 cross-module scenario harness"; `engine.headless` (MOD-015) owns `engine.core`'s no-UI run surface, not scenario composition. I placed AC-9's test in `internal/engine/attract`'s own black-box test package, run via the headless command loop. If the dev-team process prefers this under `internal/harness/headless` instead, that's a placement change only — the AC's content (the six-step chain, the two-direction population assertion in one run) doesn't move.
- **For Aaron — the interim employment rule (ASM-245).** AC-9 step 3 needs *some* rule to move a migrant from unemployed to employed since `engine.firms`/`engine.market` don't exist yet at S6. I've scoped it as a documented placeholder, explicitly labelled as such in the test, but the actual rule (instant employment? probability by wealth band? always-employed?) is a real design choice with no spec answer at this milestone — flagging rather than quietly picking one that later looks like it was meant to be permanent.
