# Acceptance criteria — foundation.buildinfo gets a code.json module key (BUG-013)

**BOW code:** BUG-013 (P3, open)
**Spec refs:** GR#6 (GUID documentation / code.json currency); GR#3 (single source of truth) — the rule this bug wants stated and enforced: "every Go package under `internal/` or `cmd/` maps to exactly one code.json key."
**Date:** 2026-08-10
**Status:** active
**Package under test:** `internal/foundation/buildinfo/` plus the master-plan/code.json generation pipeline (`tools/plan/generate.js` and its source master-plan JSON).
**Standard gates:** see `README.md`; SG-4/SG-7 scoped to `./internal/foundation/buildinfo/...` (trivial, link-time-only string vars per the finding's own read); the generation pipeline has its own check, see AC-3.

## Acceptance criteria

### Functional

- **AC-1 (the BOW item's own either/or, resolved).** `foundation.buildinfo` gains a proper module entry in the master plan (regenerating `code.json` to include a `foundation.buildinfo` key), **or** it is deliberately folded under `foundation.repo`'s existing key with that decision documented in `buildinfo`'s package doc — the BOW description offers both as acceptable; this criteria file does not pick for the junior (that would be a BA overriding a legitimate implementation choice with no spec basis either way) — whichever is chosen, AC-2/AC-3 apply. Check: `grep -n "buildinfo" code.json` finds either a `foundation.buildinfo` entry or a documented reference under `foundation.repo`'s entry.
- **AC-2.** `internal/foundation/buildinfo/doc.go`'s package comment states whichever key applies (its own, or the folded-under key with a one-line "why"), so a reader does not have to check `code.json` to find out.
- **AC-3 (Pattern #1 — the invariant is "every package has a key," enforced not asserted).** The BOW item explicitly asks for more than fixing this one package: "the rule should be that every Go package under `internal/` or `cmd/` maps to exactly one code.json key, and something should check it." This is the criterion that makes that a control rather than a wish: a script or test (e.g. `tools/plan/check-package-coverage.js`, or a Go test in a suitable location) walks every directory under `internal/` and `cmd/` containing a `.go` file and asserts each maps to a `code.json` key (via its `doc.go`'s stated key, or a lookup table), failing loudly and naming the orphaned package(s) if any exist. Check: the checker exists, running it today (post-fix) reports zero orphans, and a passing test proves the checker **can** fail — temporarily rename/hide one package's key mapping in a test fixture (not the real `code.json`) and assert the checker reports it, per the drift-test discipline in `dev-team-process.md`'s Weakness pattern #2 ("verify the drift test can actually fail" — a checker that cannot fail is decoration).

### Documentation

- **AC-4.** The new coverage checker's own doc/README explains what "orphaned" means and how to fix a reported orphan (add a master-plan entry, or document a fold-under), so the next package added without a key gets a clear, actionable failure rather than a cryptic one.

## Out of scope

- Auditing every *existing* package for coverage beyond `buildinfo` itself — AC-3's checker does that mechanically going forward; this item does not require a human to hand-verify all current packages are covered (the checker's own first clean run is that proof).

## Escalations

- None — the item's own text already resolves the either/or (AC-1) as a legitimate implementation choice, and the "something should check it" ask maps directly to AC-3.
