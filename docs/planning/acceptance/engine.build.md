## Scope note (S6 exit gate)

S6's exit gate — "headless city grows from 0: zone→build→migrate→work→deliver; JIT shortfalls propagate to satisfaction/production; junction queue renders; attractiveness moves migration both directions" — is owned end-to-end by `docs/planning/acceptance/engine.attract.md` (BA-S6b). This file owns the **zone→build** half; it does not restate the scenario. The **deliver** half and the shortfall-propagation hook contract are `engine.logistics.md`'s (this same BA's sibling file) — `engine.build`'s materials draw consumes that hook (AC-6 below), it does not define it.

## User stories

- **US-1.** As the player, I need to zone a cell into one of eight land types (Dwelling, Shop, Office, Entertainment, Farming, Manufacturing, Heavy Industry, Mining), so §34's full catalogue is real from Sprint 6, not a placeholder subset (§34).
- **US-2.** As a zone's demand bar, I need to expose *why* demand is unfilled (no labour / no power / no freight capacity) rather than a mute number, so the player can act on a real diagnosis (§34's explicit contrast with 'Blue's mute bars).
- **US-3.** As the player, I need land purchase to be a real prerequisite gated on ownership — a cell cannot be zoned or built on before it is owned — so "player buys before building" (§7) is an enforced rule, not documentation (§7; §13-F3).
- **US-4.** As a build order, I need to consume materials (via `engine.logistics`), labour, and finite junction capacity, with a lead time before completion, so construction is a real claim on city resources rather than an instant toggle (§13-F3).
- **US-5.** As a build order in a winter month, I need construction to genuinely take longer than the same order in summer, so §9's "winter slowdown" is a real curve applied to the build queue, not cosmetic flavour text (§9; see Escalations, BUG-058).
- **US-6.** As the player, I need to demolish an owned building, receive documented compensation, and see the cell return to an unowned-or-empty state, so failure recovery (§12's Detroit-spiral remedy: "demolition, targeted investment") is a real, reachable state transition (§13-F3; §12).
- **US-7.** As `engine.households`/`engine.firms`/`engine.cafe`/`engine.mining`/`engine.defence`/`engine.fdi`/`engine.tunnels`/`ui.screen.build` (registered consumers), I need a stable `BuildAPI` where build orders are commands and the queue is visible, so every consumer sees the same build state through one contract (GR#20).
- **US-8.** As `foundation.data` (MOD-006, done), I need the zone/building catalogue (types, materials bill, labour requirement, base lead time) to load from `buildings.json`, so rebalancing construction costs is a data edit (GR#15).

## Scope

Zoning a cell into one of the 8 §34 land types; the land-purchase ownership gate; the build queue (materials + labour + junction capacity + lead time, seasonally modulated); demolition with compensation; zone demand-bar diagnostics — all behind a single `BuildAPI`. No labour-market modelling itself (`engine.households`/`engine.firms`, later), no power/utility network modelling (later modules), no the land-price formula itself (`engine.finance`, a dependency).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `BuildAPI` (or equivalent) exists matching code.json's registered inbound contract — "build orders are commands; queue visible; catalogue-driven from buildings.json" — consumed by `engine.households` and the other registered consumers through this interface alone, never a concrete internal zone/queue struct reached directly. Check: `go doc ./internal/engine/build BuildAPI` shows a command-based order surface (e.g. `SubmitZoneCommand`, `SubmitDemolishCommand`) and a read-only queue query; `grep -rln "build\.\(zoneState\|queue\)\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/build` itself and `_test.go`) finds no direct exported-field writes bypassing the interface. False-pass risk: a grep that only checks `BuildAPI` exists as a name would pass even if a consumer reaches into build internals directly — the check targets writes bypassing the interface.
- **AC-2 (§34; 8-way zone catalogue).** The zone-type catalogue contains exactly the eight types named in §34 (Dwelling, Shop, Office, Entertainment, Farming, Manufacturing, Heavy Industry, Mining), each loaded from `buildings.json` (US-8), not a subset shipped as an "extensible example" set. Check: `go doc ./internal/engine/build ZoneType` (or equivalent enum) lists exactly these eight cases; a passing test asserts the catalogue's zone-type count equals 8 and each is resolvable by name (`grep -rn "func Test.*[Zz]oneType\|func Test.*[Ee]ightZone" internal/engine/build/*_test.go`). False-pass risk: a grep for individual zone-name strings would match doc-comment prose citing the spec without a single type actually registered — the check requires a count assertion plus a named-lookup test.
- **AC-3 (§7; ownership gate — ASM-236, the misuse trap).** A `SubmitZoneCommand`/`SubmitBuildCommand`/`SubmitDemolishCommand` against a cell whose `engine.world` ownership state is not the issuing player's is rejected with a typed error and produces **no** state change to the cell (no zone assignment, no queue entry, no demolition) — checked at the point of command acceptance, not merely documented as a precondition callers must uphold themselves. `engine.build` enforces the gate; the purchase transaction itself is `engine.finance`'s job (ASM-236). Check: `go doc ./internal/engine/build` shows the ownership check on the command-acceptance path, not left to callers; a passing test submits a Zone command against a deliberately-unowned cell fixture and asserts (a) the command is rejected with a typed error and (b) the cell's zone/queue state is byte-identical before and after the attempt (`grep -rn "func Test.*[Uu]nowned\|func Test.*[Oo]wnershipGate" internal/engine/build/*_test.go`). False-pass risk, stated explicitly per the brief's misuse trap: an implementation that rejects the command with an error but **still writes the zone/queue state as a side effect before returning the error** would pass a naive "returns an error for unowned land" grep while leaving unowned land buildable in practice — the check requires the negative-state-change assertion, not just the error return.
- **AC-4 (§13-F3; build queue — materials + labour + junction capacity + lead time).** A submitted build order enters a visible queue and does not complete until (a) its materials bill has been fully drawn from `engine.logistics` via the shared `Stock`/`Draw` mechanism (`engine.logistics.md`'s AC-2/AC-8 — no bespoke materials-only draw path), (b) a labour requirement is satisfied (a documented placeholder gate is acceptable pre-`engine.households`/`engine.firms`, per Out of scope, but the gate must exist and be checkable), and (c) its lead time (buildings.json-defined, per zone/tier) has elapsed. Check: `go doc ./internal/engine/build BuildOrder` shows materials/labour/lead-time fields on the queue entry; a passing test asserts an order whose materials draw is starved (via a stubbed `LogisticsAPI` returning a shortfall) does not advance past the materials-pending state even after its lead time elapses (`grep -rn "func Test.*[Bb]uildQueue\|func Test.*[Mm]aterialsPending" internal/engine/build/*_test.go`). False-pass risk: a queue that tracks a materials-drawn boolean but advances the order to completion regardless of that boolean's value would pass a "materials field exists" grep while a starved order still completes on schedule — the check requires the starved-materials scenario to actually block completion.
- **AC-5 (§34; self-explaining demand bars).** A zone's unfilled-demand figure carries a documented reason code (at minimum: no-labour, no-power, no-freight-capacity — extensible, not a closed enum if future modules add causes) rather than a bare number, consumed by `ui.screen.build`. Check: `go doc ./internal/engine/build DemandReason` (or equivalent) exists; a passing test constructs a zone with an artificially starved input (e.g. a stubbed materials/labour signal) and asserts the returned demand-bar value carries the matching reason code, not just a magnitude (`grep -rn "func Test.*[Dd]emandReason\|func Test.*[Uu]nfilledDemand" internal/engine/build/*_test.go`). False-pass risk: a `DemandReason` type that exists but is never populated (always "unknown") would pass a doc-existence grep while §34's actual promise — "unfillable demand tells you *why*" — remains unmet; the check requires a real reason code from a constructed starvation scenario.
- **AC-6 (§9; winter construction slowdown — RE-ARMED 2026-08-11, BUG-100: the `engine.build`→`engine.season` edge ASM-233 asked for landed in c36778b).** Construction speed at winter months is measurably slower than at non-winter months, sourced from `engine.season`'s `ConstructionSpeedMultiplier` via a live `SeasonAPI` call — the edge is confirmed registered: `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.build'); process.exit(m.outbound.calls.some(c=>c.key==='engine.season')?0:1)"` exits 0. This AC is no longer contingent; it is a normal, immediately-buildable check. Check: `go doc ./internal/engine/build` shows a call into `SeasonAPI.ConstructionSpeedMultiplier`, not a locally-duplicated seasonal curve; `grep -n "season\.\|SeasonAPI" internal/engine/build/*.go` finds the live call; a passing test asserts a winter-month build order's effective lead time is longer than an otherwise-identical summer-month order's, using `engine.season`'s real multiplier (via its registered API, not a build-local mock of the number) (`grep -rn "func Test.*[Ww]interSlowdown\|func Test.*[Ss]eason.*[Cc]onstruction" internal/engine/build/*_test.go`). False-pass risk: a build-local seasonal table that happens to agree with `engine.season`'s numbers today would pass this test right up until the two drift — which is exactly why the AC requires a live call, not merely "produces a slower winter result": a check asserting only the behavioural outcome (winter slower than summer) would pass a duplicated-and-drifted implementation just as easily as a correctly-wired one, so the `grep` for the live `SeasonAPI` call is load-bearing, not decorative.
- **AC-7 (§13-F3, §12; demolition + compensation).** Demolishing an owned building is a distinct command from zoning/building, transitions the cell to an unowned-or-empty state (documented which), and computes a compensation figure via `engine.finance` (never a bare deletion with no financial consequence) — consistent with §12's "demolition, targeted investment" as a costed recovery action, not a free undo. Check: `go doc ./internal/engine/build SubmitDemolishCommand` exists and its result carries a compensation figure; a passing test asserts demolishing a fixture building changes the cell's state (zone cleared, structure ref cleared) and produces a nonzero-or-documented-zero compensation value distinct from "no financial event occurred" (`grep -rn "func Test.*[Dd]emolish" internal/engine/build/*_test.go`). False-pass risk: a `Demolish` that clears the cell but never calls into `engine.finance` at all would pass a bare "demolition works" grep while leaving §12's costed-recovery claim untested — the check requires an assertion on the financial side effect, not just the cell-state side effect.
- **AC-8 (§34; catalogue-driven from buildings.json — US-8).** Zone types, per-tier construction materials bills, labour requirements, and base lead times all load from `buildings.json` via `foundation.data` (MOD-006, done) at package init/load time — no per-zone materials/labour/lead-time literal is hardcoded in Go source (GR#15). Check: a passing test changes a value in the loaded `buildings.json` fixture and asserts the corresponding queue behaviour (materials required, lead time) reflects the change (`grep -rn "func Test.*[Dd]ataDriven\|func Test.*[Rr]eload" internal/engine/build/*_test.go`); `grep -nE "[0-9]+" internal/engine/build/*.go` (excluding `_test.go`) finds no bare materials-quantity/lead-time-shaped numeric literals outside doc-comment prose transcribing the spec.
- **AC-9 (§7; continuous land-price consumption — not re-implementation).** `engine.build` consumes `engine.finance`'s `LandPrice` (that module's registered AC-4) to display/validate a purchase, and never computes its own parallel land-price formula. Check: `grep -n "finance\.\|FinanceAPI" internal/engine/build/*.go` finds calls into the registered `engine.finance` outbound edge for pricing; `grep -nE "base\(|access\(|amenity\(|scarcity\(" internal/engine/build/*.go` (excluding `_test.go` and comments) finds no local re-implementation of §7's pricing formula components.

### Error handling

- **AC-10 (GR#7).** Submitting a command against an unregistered zone-type ID, an out-of-bounds cell reference, or a demolish command against a cell with no structure returns a registry-sourced error (new `MET-E`-range code claimed at build time), never a panic or a silently-accepted no-op that a caller could mistake for success. Check: `grep -n "MET-" internal/engine/build/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownZone\|func Test.*[Ii]nvalidDemolish" internal/engine/build/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zone/demolish command was silently applied as a no-op, not merely that a matching-named test function exists.
- **AC-11 (GR#7).** A malformed or schema-invalid `buildings.json` (a zone type missing its materials bill, a negative lead time, an unrecognised zone-type string) produces a registry-sourced error at load time, never a silent default substitution that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/build/*.go` finds a load-time registry code reference distinct from AC-10's; passing test coverage (`grep -rn "func Test.*[Mm]alformed\|func Test.*[Ii]nvalidBuildings" internal/engine/build/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no default-substituted buildings entry was loaded in place of the malformed one, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-12 (GR#21).** The build-queue tick resolution (materials/labour/lead-time advancement) is a deterministic function of prior tick state, loaded data, and command inputs — repeated runs from an identical starting snapshot over an identical command sequence produce byte-identical queue state, across worker counts. Check: a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/build/*_test.go`). Never assert a wall-clock upper bound on how long a build takes to run in CI; assert tick-count/state equality only.
- **AC-13 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/build/*.go` (excluding `_test.go`) returns no matches — lead-time and seasonal-slowdown resolution are functions of simulation tick/month index only, never wall clock.
- **AC-14.** `go test ./internal/engine/build/... -race -count=1` passes with no data race when `BuildAPI` is queried (queue state) concurrently with a tick advancing the same queue. Check: `grep -n "go func()" internal/engine/build/*_test.go` finds at least one concurrency test.

## Out of scope

- The land-price formula itself (`base × access × amenity × scarcity`) and the money-ledger side of a purchase — `engine.finance` (MOD-022, a dependency); this item only enforces the ownership gate and consumes `LandPrice` (AC-3/AC-9, ASM-236).
- Labour-market modelling (who's available, skill matching) — `engine.households`/`engine.firms` (later, registered consumers); AC-4's labour gate is a documented placeholder check pending those modules, not a full labour market.
- Power/utility network coverage as a build precondition — later utility modules; AC-5's "no-power" reason code is a placeholder reason category this item exposes but does not itself compute until the power network exists.
- The materials-supply mechanism itself (stock, shelf life, shortfall propagation) — `engine.logistics` (MOD-025, a dependency, this same BA's sibling file); this item only consumes it via the shared `Stock`/`Draw` mechanism (AC-4/US-4).
- The seasonal curve's own implementation and exact multiplier value — `engine.season` (MOD-027, already built); this item only consumes `ConstructionSpeedMultiplier` live (AC-6).
- Mining-specific build rules gated on revealed geology (§32) — `engine.mining` (a later, registered consumer); this item's Mining zone type exists in the catalogue (AC-2) but geology-gating is that module's job.
