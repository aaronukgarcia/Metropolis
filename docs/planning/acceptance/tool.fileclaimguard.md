## Why this file reads the way it does

FEAT-136's BOW text names **three** deliverables, and they did not all land. (1) A dispatch-time **hard block** on declared-ownership overlap, plus **auto-claim** the brief scope on dispatch and **auto-release** on completion. (2) A PreToolUse **edit-time guard** that checks `sync_file_claims` before every Edit/Write. (3) **Vestige** as the durable, transcript-surviving record of the claim protocol and near-miss incidents.

The working tree contains **(1) in part** — the hard block *and* the auto-claim are in `claude-dispatch-guard.js`, but **auto-release on completion is not wired** — and **(2) in full** — `claude-file-claim-guard.js` exists, is hooked in `.claude/settings.json` (`matcher: "Edit|Write"`, 10s timeout), and is test-covered. **(3) Vestige does not exist at all** — neither guard reads or writes it; `claude-memory-prefetch.js` (GR#14) recalls *to* the agent but records nothing *about* the claim protocol.

So this file documents the contract of what **exists** — the two guards and the shared claim-TTL notion — and escalates what does **not** (auto-release, the Vestige record, and two smaller parity gaps) rather than writing ACs that pretend the missing halves are done. A Tester verifying this file will PASS it against the committed code and FAIL nothing, because the missing pieces are written as **escalations**, not as ACs the code cannot meet.

## Scope

Two fail-open PreToolUse hooks that make "two agents editing the same file" mechanically impossible *while a claim is live*: the dispatch guard hard-blocks an Agent brief that declares ownership of a path another live session already holds and, on a clean dispatch, claims the brief's owned paths; the edit-time guard hard-blocks any Edit/Write whose target overlaps a foreign live claim, naming the owner and the release command. "Live" is a shared 5-minute TTL notion (GR#3) held in the metro `sync_file_claims` table, keyed by **session id** (per-terminal, sidestepping BUG-238's name churn), not by name.

## Acceptance criteria

### Dispatch-time (Guard 1 — `claude-dispatch-guard.js`)

- **AC-1 (dispatch-time ownership-overlap is a HARD BLOCK, naming the owner).** When an Agent dispatch brief declares ownership of a path — only paths under a `FILES YOU OWN:` / `you own exactly` / `YOU OWN` paragraph, per `extractOwnedPaths()`, not every path the brief merely cites for grounding — and that path **overlaps** a live claim in `sync_file_claims` held by a **different session** (`held.session_id !== sessionId`), the dispatch guard DENIES with `permissionDecision: "deny"`, and the deny reason names the **owner** (`held.name`) and the overlapping path. "Overlap" is the shared `overlaps()` semantics: case-folded path equality, or either path an ancestor/descendant of the other (BUG-135 Windows case-insensitivity). A same-session claim does **not** deny; a disjoint path does **not** deny. Check: `claude-dispatch-guard.fileclaims.test.js` — "an overlapping-ownership brief is DENIED" asserts `permissionDecision === 'deny'` and `permissionDecisionReason` matches `overlaps "internal/ui/dash", claimed by bob`; "a disjoint brief is ALLOWED" and "a brief owning a path claimed by its OWN session is ALLOWED" both assert empty stdout. **As-built note (see Escalation E):** the dispatch-time deny names owner + path but **not** the release command — the release command is only surfaced in the edit-time deny (AC-2).
- **AC-6 (the "live claim" TTL is one shared constant, GR#3).** The notion of "is this claim live?" is a **single** constant — `CLAIM_TTL_MS` (5 × 60 × 1000) is **defined once** in `claude-dispatch-guard.js`, **exported**, and **imported** (destructured) by `claude-file-claim-guard.js`, so the two guards can never disagree on when a claim is dead. Check: `grep -n "CLAIM_TTL_MS" claude-dispatch-guard.js claude-file-claim-guard.js` shows exactly one `const CLAIM_TTL_MS = ...` definition plus one `CLAIM_TTL_MS,` in the module.exports and one in the destructuring require; there is no second `5 * 60 * 1000` literal in `claude-file-claim-guard.js`. **As-built note (Escalation A):** the constant is shared, but `claimed_ms` itself is only *written* at dispatch and never refreshed mid-task — see below.

### Edit-time (Guard 2 — `claude-file-claim-guard.js`)

- **AC-2 (edit-time guard: foreign-owned → DENY naming owner + release command; own-or-unowned → allow silently).** On every `Edit`/`Write`, the guard converts `file_path` to the repo-relative forward-slash form `sync_file_claims` stores (`toRepoRelative`), queries live claims (`claimed_ms > now − CLAIM_TTL_MS`), and: if an overlapping claim is held by a **different** session, DENIES, with a reason naming the **owner** (`hit.owner`) **and the release command** — `node claude-sync.js release "<heldPath>"` (with the owner's awareness) — plus the deliberate-bypass hint; if the path is unowned or owned by the **current** session, allows **silently** (empty stdout, exit 0). The own/foreign decision is the pure `foreignOwner(targetRelPath, claims, sessionId)` function. Check: `claude-file-claim-guard.test.js` — "a foreign-owned edit is DENIED" asserts deny + `/claimed by bob/i` + `/claude-sync\.js release/`; "an own-session edit is ALLOWED" and "an unowned edit is ALLOWED" assert empty stdout. A non-`Edit`/`Write` tool is ignored *before* any DB attempt ("a non-Edit/Write tool is ignored" asserts empty stdout **and** empty stderr with a dead DB, proving the DB was never touched).
- **AC-3 (fail-open on any DB error — stderr warn, exit 0, never a deny).** A DB outage, query failure, or unparsable stdin must never crash an Edit and never produce a deny. Every error path writes a one-line stderr warning naming the guard and `allowing edit (fail-open)` (or the equivalent for the unparsable-input early return) and exits 0. This is load-bearing: this hook runs on *every* edit in *every* session, so a dead database must not freeze the team's editing. Check: `claude-file-claim-guard.test.js` — "a DB failure fails OPEN — exit 0 with a stderr warning" spawns with `METRO_DB_PORT=1` and asserts `status === 0`, stderr matches `/fail-open|allowing edit/i`, and stdout is empty (no deny emitted). The `main().catch()` and the inner query `try/catch` both route to exit 0.
- **AC-4 (kill switch `CLAUDE_DISABLE_FILE_CLAIM_GUARD=1`).** Setting that env var makes the guard allow **immediately** — before parsing stdin and before connecting — with no DB touch and no output. Check: `claude-file-claim-guard.test.js` — "the deliberate-disable kill switch allows the edit" spawns with the env var set *and* a dead DB and asserts `status === 0`, empty stdout, **and empty stderr** (proving the DB was never attempted). This is a distinct switch from the dispatch guard's `CLAUDE_DISABLE_DISPATCH_GUARD=1`, which must remain independently controllable.
- **AC-5 (own-vs-foreign is keyed on session id, not name — sidesteps BUG-238).** The own/foreign decision compares `session_id` only, never the human-readable `name`. BUG-238's root cause is that `checkin` can silently reassign a window's *name* (Bill→Bob); the per-terminal `CLAUDE_SESSION_ID` is stable across that churn, so a claim keyed on name would turn a reassigned agent's own claim into a "foreign" claim and false-DENY it. Both guards implement the session key: the dispatch guard skips `held.session_id === sessionId` (own-claim skip), and the edit guard's `foreignOwner` skips same-session claims and only returns `{ owner, heldPath }` for a different session. The `name` field is **display-only** in the deny message, never the identity key. Check: `claude-file-claim-guard.test.js` — "foreignOwner returns null when the only overlapping claim is the current session's own" (same `session_id`) vs "foreignOwner returns the owner when a different session claims" (different `session_id`, owner name `bob` — the name is carried for display, not compared).
- **AC-7 (tests are red-then-green — the assertions must be able to fail).** The two subprocess suites prove the deny/allow/fail-open/kill-switch behaviour end-to-end by spawning the real script against a **scratch** DB (`metro_test_fileclaim_<pid>` / `metro_test_dispatchclaims_<pid>`, created and dropped by the suite — the real `metro` DB is never written), asserting on observable stdout JSON, stderr, and exit codes — never by grepping source text for a string that could be commented out. The red phase is documented rather than lost: `claude-file-claim-guard.test.js`'s header records that loading the suite *before* the guard exists is a red-phase "Cannot find module", and each deny test asserts the load-bearing tokens (owner name, release command) rather than merely "some deny JSON appeared"; each allow test asserts **empty stdout**, not just exit 0. Check: `node --test claude-dispatch-guard.fileclaims.test.js claude-file-claim-guard.test.js claude-dispatch-guard.test.js` passes; and deleting the guard's `deny()` body (or the `foreignOwner` same-session skip) must turn a green test red — the Tester's own mutation check, per the verification-standards rule that a gate that cannot evaluate must not report success.

## Out of scope

- **The Vestige coordination record (FEAT-136 deliverable #3).** No guard writes or reads Vestige; the claim protocol and near-miss incidents are not durably recorded anywhere transcript-surviving. This is escalated (Escalation D), not AC'd — writing an AC for it now would commission code that is not in the working tree.
- **Auto-release on completion (FEAT-136 deliverable #1, second half).** The dispatch guard auto-*claims*; nothing auto-*releases* on `SubagentStop`. Escalation B, not an AC.
- **The `claim`/`release`/`gc` command contracts themselves.** Their full contract is documented in `tool.sync.md` (AC-9/AC-10); this file only depends on `release <path>` existing and the `sync_file_claims` schema, which it verifies indirectly via the scratch-DB tests.
- **Anything the guards don't need to adjudicate.** Unparsable stdin, non-`Agent`/non-`Edit`/non-`Write` tools, and paths outside the repo root are early-allowed — these are not this guard's problem to judge, and treating them as errors would make a noisy guard that gets switched off (SEC-026's pattern).

## Escalations

- **A. For Bill/Aaron — claim liveness is TTL-only; `claimed_ms` is never refreshed mid-task (ASM-903, P1).** The protection window is **5 minutes from the last dispatch that declared ownership**, not the task's duration. `claimed_ms` is written once at dispatch (`INSERT ... ON DUPLICATE KEY UPDATE`) and is **not** refreshed by the PostToolUse permit ping — `claude-ping-check.js` calls `claude-sync.js renew --auto`, which updates only `sync_permits` (`expires_ms`/`heartbeat_ms`), never `sync_file_claims`. The dispatch guard's own header comment ("the PostToolUse ping refreshes it") is therefore **aspirational, not true**. Consequence: a subagent spawned once and working longer than 5 minutes silently loses its claim — both guards stop seeing it as live — which re-opens exactly the concurrent-edit window FEAT-136 exists to close. Recommend (pick one): refresh `claimed_ms` in the ping/`SubagentStop`/PostToolUse-Edit path; make a successful own-session edit self-renew the lease (touch `claimed_ms`); or lengthen the TTL past the longest expected task. This is the load-bearing cross-check finding.
- **B. For Bill — auto-release on completion is not wired (ASM-902, P2).** FEAT-136's spec says "auto-claim … on dispatch and auto-release on completion"; the code delivers only the claim half. `claude-agent-stop.js` does **not** delete `sync_file_claims` rows (confirmed by grep). A claim ends today only by (a) 5-minute TTL expiry, (b) `node claude-sync.js release <path>`, (c) `checkout` (deletes that name's claims), or (d) `gc` (orphan reap). Decide whether a `SubagentStop` release hook is wanted, or whether TTL + manual release is the accepted release mechanism and the BOW text should be amended to say so.
- **C. For Bill — MultiEdit and any multi-target mutator bypasses the edit-time guard (ASM-904, P2).** The guard's own gate is `if (toolName !== 'Edit' && toolName !== 'Write') allow()`. A `MultiEdit` tool call — whose `.claude/settings.json` matcher `Edit|Write` *would* fire on a substring match — is then allowed **by the guard itself** because its exact name is neither `Edit` nor `Write`, so a single `MultiEdit` spanning a foreign-owned path would sail through with no claim check. Any future file-mutating tool name has the same hole. Recommend: replace the exact-name gate with an explicit known-mutator allow-list (Edit/Write/MultiEdit) — or an explicit non-mutator block-list — and add a MultiEdit subprocess test.
- **D. For Bill — the Vestige coordination record is entirely absent.** FEAT-136 deliverable #3 (Vestige as the durable, transcript-surviving record of the claim protocol + near-miss incidents, recalled via GR#14 memory-prefetch) is not implemented in either guard. If it is still wanted, it is a **separate follow-up item** (a PostToolUse/SubagentStop hook writing claim/near-miss events to Vestige), not an extension of this file's two guards.
- **E. For Bill — two minor parity nits.** (1) The **dispatch-time** deny (AC-1) names owner + path but not the release command, while the **edit-time** deny (AC-2) names both — if the lead wants the release command surfaced at dispatch too, it is a one-line addition to the deny string in `claude-dispatch-guard.js`. (2) The two guards' `session_id` fallbacks are asymmetric — dispatch falls back to `'unknown'`, edit falls back to `null` — so a claim written under the `'unknown'` fallback would read as foreign to its own editor. Harmless in practice (`CLAUDE_SESSION_ID` is always set under `metro`), but the two fallbacks should match for exactness.

## Assumptions logged (see report to Bill)

- **ASM-902** — auto-release on completion is deferred; claims end by TTL expiry, manual `release`, `checkout`, or `gc`, with no `SubagentStop` release hook (Escalation B).
- **ASM-903** — claim liveness is TTL-only; `claimed_ms` is written at dispatch and never refreshed by the permit ping, so a >5-minute in-flight agent loses its claim (Escalation A).
- **ASM-904** — the edit-time guard covers `Edit`/`Write` only; `MultiEdit` and other multi-target mutators are out of scope for the claim check (Escalation C).
- **ASM-960 (confirm-and-close).** Only the four real mutator tool names (Edit/Write/MultiEdit/NotebookEdit) are treated as mutators; unknown names fail-open.
- **ASM-944 (confirm-and-close).** session_id in PreToolUse payload is harness-set, not model-forgeable, so the session-keying attack surface is not exploitable.
- **ASM-898 (confirm-and-close).** FEAT-136 live claim = 5-min `claimed_ms` TTL (`CLAIM_TTL_MS` imported from `claude-dispatch-guard.js`); an older claim is dead and a foreign edit is allowed until the auto-refresh/auto-release follow-up lands.
- **ASM-899 (confirm-and-close).** FEAT-136 own-vs-foreign keyed on `session_id` (hook payload vs stored claim, falling back to `CLAUDE_SESSION_ID`), sidestepping BUG-238 identity reassignment — the same assumption `claude-dispatch-log.js` already relies on.
- **ASM-900 (confirm-and-close).** FEAT-136 dispatch-time overlap already blocks (deny since 6f37bd8); the guard needed no functional change — only the DB-backed regression test and the `CLAIM_TTL_MS` export for the edit guard.
- **ASM-962 (confirm-and-close).** FEAT-136 r2 anchors relative `file_path` to the repo root via `path.resolve(ROOT, file_path)` where `ROOT = __dirname` on BOTH guard sides, so the claim-store and edit-time sides stay mutually consistent even if a session cwd diverged.
- **ASM-963 (confirm-and-close).** FEAT-136 r2 leaves the bare `**` whole-repo over-block unchanged (classified over-block/DoS, not a bypass) — it can only fail-open over-block, never allow a foreign edit of the claimed bytes.
- **ASM-988 (confirm-and-close).** The trailing-dot/space spelling gap (Win32 strips to the same on-disk path) is out-of-contract: reaching it needs a deliberately malformed path — an active attack, not the accidental collision FEAT-136 guards.
