## Acceptance criteria

**AC-1 — Every file parses as valid JSON.**
`node -e "require('./data/traffic/<file>.json')"` succeeds for all 11 data files. Verified: all
11 files parsed clean, sizes 4.6KB–33.4KB (see AC-9, all well under the 200KB cap).

**AC-2 — The scale ladder carries exactly the 18 specified rungs, strictly ascending by
population.**
`scale_ladder.json` `rungs[]` has length 18, `population` values exactly
`[100, 1000, 5000, 10000, 50000, 100000, 250000, 600000, 1000000, 1200000, 2000000, 5000000,
10000000, 20000000, 40000000, 60000000, 80000000, 98000000]` in that order. **Now mechanically
verified (r2 rework, BUG-820):** `validate-traffic-tables.mjs` checks `rungs.length` and every
`rungs[i].population` against `meta.rungPopulations` (the expected sequence is DERIVED from that
field, per GR#15, never a hardcoded `18` literal in the validator) in addition to the
strict-ascending check — previously this AC was true only "by construction" with no mechanical
gate, so a mutant deleting/adding a rung or emptying `rungs[]` entirely survived (round
opus-round-feat792-inc0 finding (a)). 0 failures on the current tables.

**AC-3 — Mode shares sum to 1.0 ± 1e-6 everywhere a mode-share vector appears.**
Checked for every `scale_ladder.json` rung's `modeShare` object and every
`mode_share_by_density.json` band's `shares` object. Verified by
`validate-traffic-tables.mjs` (`Math.abs(sum-1) > 1e-6` fails the run) — **0 failures on the
current tables** (run output: `OK: data/traffic/*.json pass all structural checks.`).

**AC-4 — Monotone totals where physics demands it.**
`dailyPersonTrips` strictly increases rung-to-rung (more people ⇒ more trips, given the trip rate
never collapses to near-zero — see traffic-assumptions.md A-8). Verified by
`validate-traffic-tables.mjs`. **r2 rework (BUG-820) closes the previously-disclosed gap:**
`networkVehicleKmPerDay`, `parkingSpacesDemanded`, `evChargePointsNeeded`,
`emergencyIncidentsPerDay` and `roadWearESALPerDay` are now ALL mechanically checked
non-decreasing rung-to-rung by `validate-traffic-tables.mjs` (previously true only by construction
with no gate — round opus-round-feat792-inc0 finding (e)). The validator also now enforces the four
sum identities that were previously true in today's data but ungated: `tripsByMode` sums to
`dailyPersonTrips` within ±(mode count), `busSubtypeTrips` sums to `tripsByMode.bus` within ±4,
`freightTonnesBySector` and `freightTonnesByVehicleClass` each sum to `freightTonnesPerDay` within
±(entry count), and `workersInCity == round(population × workersInCityShare)` within ±1 (the
`workersInCityShare` values were re-derived to full round-trip precision so this now holds exactly
on all 18 rungs — previously up to 13/18 rungs disagreed by as much as 2,613 due to a 4dp-rounded
share, BUG-823 finding (4)). `peakHourFactor` is now range-gated to `[0.08, 0.15]`. 0 failures on
the current tables.

**AC-5 — Car mode share monotonically falls and rail-family share monotonically rises across the
18 rungs** (the Tokyo/Singapore-shape claim, traffic-assumptions.md A-5/A-14). Spot-check: car
share 0.604 (pop 100) → 0.090 (pop 98,000,000); rail-family (`metro+heavy_rail+hs_rail+tram`)
share 0.034 → 0.575 over the same range. **Mechanically verified** by
`validate-traffic-tables.mjs` (0 failures) across all 18 rungs.

**AC-6 — No duplication of `data/modes.json` / `data/roads.json` / `data/traffic.json` /

**AC-7 — Every numeric row or block carries provenance (`source`, `year`, `confidence`).**
