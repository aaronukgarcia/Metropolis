## Why this file reads the way it does

FEAT-093's BOW text is one sentence with two different jobs in it: "records all 'change' actions in a central history" (an **append-only event log**, per-action, with old→new) and "nice graphs: population growth/decline, money, maintenance spend, death/birth… the full graph suite the reference city-builder ships" (a **monthly aggregate time series** suite). Those are two different data shapes, and conflating them is the single easiest way to build the wrong thing: a per-action log has *events* (policy X enacted, building Y demolished, citizen Z died) while a graph has *sampled series* (population at month 1, month 2, month 3…). The reference city-builder ships both — a city-stats graphs panel and a per-event log/feed — and this file keeps them as two explicitly-separate AC groups so a junior can't quietly fold one into the other.

The load-bearing cross-check finding (Escalation A) is that **almost none of the producer surfaces this log must consume exist yet.** FEAT-091's "change history" exists only in FEAT-091's own BOW description (there is no `feat.policy.md` acceptance file, and `engine.policies.md` specifies no change-history query/event surface); build/demolish (`engine.build`), staffing (`engine.services`), and death (`engine.citizens`) register no change-event outbound edge to feed a central history; and FEAT-089's maintenance spend has no `engine.maintenance` module at all. This is the BUG-058 shape (a spec-mandated capability with no registered edge to carry it), written here as explicit dependencies rather than silently assumed to exist.

## User stories

- **US-1.** As **the player**, I need every change the city makes — a policy enacted, a building raised, a building demolished, a service staffed up or down, a death — recorded in one place with *when* it happened and *what changed from → to*, so I can answer "why did that happen and when" without reconstructing it from memory or from forty-four screens.
- **US-2.** As **the player**, I need to filter that central history by *domain* (policies vs buildings vs staffing vs deaths) and by *time range*, so a long city's full history doesn't bury the one policy change I'm looking for.
- **US-3.** As **the player**, I need the city's headline numbers as graphs over time — population, money, maintenance spend, deaths/births, employment — so I can see a trend (a slow population decline, a maintenance bill creeping up) that a single current number hides.
- **US-4.** As **the player at win or death** (the epilogue, §434), I need the book's history to be the raw material the "whole history" is built from, so the epilogue and the mid-game book tell the same story rather than two different ones.
- **US-5.** As **the Destructive agent auditing this feature**, I need "the log is append-only" and "the log is reproducible" to be *structural* properties (no mutator exists; replay is byte-identical), not qualities a lazy build can claim while storing history in a mutable slice.

## Scope

An engine-side append-only central history: change records across five domains (policy, build, demolish, staffing, death) each carrying a domain tag, a simulation timestamp, a subject/entity reference, and an old→new value pair — plus a deterministic monthly aggregate sampler producing the time series the graph suite plots. A UI "book" surface that renders the filterable history and the five-series graph suite, composed from `ui.widgets`' shared sparkline/Braille primitives, drill-through to the underlying source per UI-SPEC §4. This item does not produce the changes themselves — it consumes the change events/commands of the producing modules (FEAT-091/`engine.policies`, `engine.build`, `engine.services`, `engine.citizens`, and FEAT-089's maintenance spend via `engine.finance`).

## Acceptance criteria

### Functional — the central history (append-only event log)

- **LOG-1 (the central history is one append-only store; the five change domains).** A single central history store records change actions across the five named domains — `policy`, `build`, `demolish`, `staffing`, `death` — each entry carrying a domain tag, a simulation timestamp (sim year + month, never wall clock — see LOG-15), a subject/entity reference (policy ID, cell/building ref, service ref, citizen ID), and an old→new value pair. The store is **append-only by construction**: the exported API exposes an `Append(ChangeRecord)` (or equivalent) and read/query paths, and **no** `Update`, `Delete`, `Mutate`, or by-reference write path on a stored record. Check: `go doc ./internal/engine/history` shows an append + query surface with no mutator method; a passing test appends a record, retrieves it, mutates the *retrieved copy*, and asserts the stored record is unchanged (`grep -rn "func Test.*[Aa]ppendOnly\|func Test.*[Ii]mmutable" internal/engine/history/*_test.go`). **What a lazy implementation looks like:** a history implemented as a mutable slice returned by reference — "records exist" checks pass it, but a caller (or a buggy producer) can rewrite history after the fact, which is exactly what US-5's append-only guarantee exists to rule out.
- **LOG-2 (old→new is recorded, not "something changed").** A change entry carries both the prior and the new value, retrievable independently. For a first-state event (a birth, a build on a vacant cell) the old value is an explicit documented empty/zero state, not an omitted field. Check: a passing test records a policy-change entry and asserts both `old` and `new` are retrievable and equal the recorded values (`grep -rn "func Test.*[Oo]ldNew\|func Test.*[Bb]eforeAfter" internal/engine/history/*_test.go`). **What a lazy implementation looks like:** an entry that stores "policy `rent-control` changed" with no from/to — it satisfies "a change is recorded" superficially but leaves the player unable to answer US-1's "what changed from → to".
- **LOG-3 (GR#3 — consume the producer's change surface, never re-derive it).** Each recorded change entry names its producing module and traces to that module's own command/change surface — policy enactment/repeal from FEAT-091's change history (the `engine.policies` enactment surface), build/demolish from `engine.build`'s build/demolish commands, staffing from `engine.services`' funding/staffing commands, death from `engine.citizens`' per-person mortality events. The history store does **not** independently re-detect changes by diffing engine state between ticks (that would be a second source of truth for "what changed" — GR#3). Check: the `Append` call sites for each domain live on/behind the producer's own command path, not in a history-local diffing loop (`grep -rn "history\.Append\|AppendChange" internal/engine/policies/ internal/engine/build/ internal/engine/services/ internal/engine/citizens/ internal/engine/history/` shows the producers feeding the store). **This is a dispatch-time dependency, not a buildable check today** — see Escalation A: none of these producer surfaces is built/registered yet, so LOG-3 is the AC a junior cannot fully wire until the producers emit change events; until then each unregistered producer is a named open edge, not a silent omission.
- **LOG-4 (death events at a documented granularity; aggregate for the graph).** The `death` domain records death events at a documented granularity (per-event where `engine.citizens` produces individual mortality events; the monthly death *count* is a sampled aggregate series consumed by the graph suite, LOG-10). `doc.go` states the granularity explicitly. **Escalation B flags the volume decision** — at 100M citizens, a per-individual death record per event is a storage question Aaron/Bill should rule on (per-event always vs per-event only for HOT/tracked citizens with cold deaths rolled into the monthly aggregate), and this AC is written to hold under either ruling by requiring the chosen granularity to be *stated*, not guessed.
- **LOG-5 (the store is serialisable; the history survives a save/reload).** The central history is part of the saved game state — a save → reload → query round-trip returns the same history (the same entries, same order, same old/new). Check: a passing test appends entries, serialises, reloads into a fresh store, and asserts deep-equality (`grep -rn "func Test.*[Rr]oundTrip\|func Test.*[Rr]eload" internal/engine/history/*_test.go`). This is what makes "append-only + reproducible" meaningful across sessions rather than a per-run in-memory property.

### Functional — the query surface

- **LOG-6 (filter by domain).** `Query` filters by domain; a passing test appends entries across at least two domains and asserts filtering by one returns only that domain's entries, and an unmatched domain returns an empty set (not all entries) (`grep -rn "func Test.*[Ff]ilterDomain" internal/engine/history/*_test.go`).
- **LOG-7 (filter by time range).** `Query` filters by a simulation-time range `[from, to]` with stated inclusive bounds; a passing test appends entries at months 1, 5, 10 and asserts the range `[2, 8]` returns only the month-5 entry (`grep -rn "func Test.*[Tt]imeRange\|func Test.*[Rr]angeFilter" internal/engine/history/*_test.go`).
- **LOG-8 (deterministic ordering; GR#21).** Entries return in chronological append order; entries sharing the same tick are broken by a documented stable key (e.g. a monotonic sequence number assigned at append, then domain/subject). Check: `grep -n "for .* := range" internal/engine/history/*.go` shows any map feeding ordered output is sorted first (`grep -n "sort\." internal/engine/history/*.go` corroborates); a passing determinism test appends same-tick entries and asserts a stable, repeatable order across runs (`grep -rn "func Test.*[Oo]rder" internal/engine/history/*_test.go`).
- **LOG-9 (the book's search carries F9's "full searchable history log" promise).** The UI book supports text search/filter over the history (by subject name / entity reference), carrying forward §13 F9's "full searchable history log" wording for the *structured* change history — distinct from `engine.news`' salience-scored prose archive (see Out of scope). Check: a passing test seeds entries with distinguishable subjects and asserts a subject query returns the matching entry/entries (`grep -rn "func Test.*[Ss]earch\|func Test.*[Mm]atch" internal/ui/screens/history/*_test.go`).

### Functional — the graph suite

- **LOG-10 (five time series, sourced, directional-only — the meta-AC).** The book plots exactly the five graph series FEAT-093 names, each as a real time series over simulation time: **population** (from `engine.citizens`' population aggregate), **money** (from `engine.finance`'s treasury/cash — int64 micro-pounds, drillable to ledger lines per `engine.finance` AC-11), **maintenance spend** (FEAT-089's maintenance opex line as posted through `engine.finance`), **death/birth** (from `engine.citizens`' monthly births and deaths), and **employment** (from `engine.citizens`' `employmentState`/sector aggregates). **No AC below pins a y-axis scale, tick interval, or value — directional only.** Every series' values come from the registered engine view's data (GR#15), never a hardcoded illustrative shape; the "reference city-builder ships" full suite is honoured as a *shape* requirement (a real plotted series per metric), not as permission to invent numbers the engine doesn't produce. Check: the sampler/query for each series traces to the named source's registered view (`grep -rn "engine.citizens\|engine.finance\|maintenance" internal/engine/history/*.go` for the sampler path, `grep -rn "int.protocol\|protocol\." internal/ui/screens/history/*.go` for the UI path).
- **LOG-11 (each series is a differential read of real data, not a static illustration).** For each of the five series, a passing test feeds two fixture series that differ in a known way (population rising vs declining; a surplus month vs a deficit month; a mortality-spike month vs a flat month) and asserts the plotted points trace to the fixture — changing the fixture changes the plot, and the direction of change follows the data. This is the SF-3-shaped "reads the real source, not a hardcoded picture" check, applied once per series (`grep -rn "func Test.*[Pp]opulation\|func Test.*[Mm]oney\|func Test.*[Mm]aintenance\|func Test.*[Dd]eathBirth\|func Test.*[Ee]mployment" internal/engine/history/*_test.go` and/or `internal/ui/screens/history/*_test.go`). **What a lazy implementation looks like:** a graph panel that renders a plausible-looking curve drawn by hand once, which passes any "a chart appears" smoke test but shows nothing true once wired to real engine state.
- **LOG-12 (graphs compose from `ui.widgets`, not bespoke drawing).** The graph suite renders via `ui.widgets`' shared sparkline (12-cell / 24-month idiom) and Braille high-res chart primitives (MOD-010), not a screen-local reimplementation of line/dot drawing — mirroring `ui.screen.demo.md` DEMO-1's "a rendering requirement, not a named symbol" precedent. Check: `grep -n "widgets\.\(Sparkline\|Braille\)" internal/ui/screens/history/*.go` shows the composition.
- **LOG-13 (drill-through; UI-SPEC §4 — the absolute rule).** Every number the book displays — a series' current value, a graph point, a history entry's old/new value — is selectable and `Enter` navigates to its source (the underlying ledger line, the aggregate's source view, the subject entity). The graph/history tiles register `DrillTarget`s per `ui.dash` (MOD-038). Directional-series points drill to the underlying aggregate source (that month's ledger line / the entity), consistent with `ui.dash.md`'s AC-4/AC-5; if per-row drill-through inside a history entry is needed, the `int.protocol` sub-entity addressing gap (`ui.dash.md`'s `FEAT-042`) binds here too — see Escalation A. Check: a passing test selects a known series point and asserts the resolved `DrillTarget` names its source (`grep -rn "func Test.*[Dd]rill" internal/ui/screens/history/*_test.go`).

### Error handling

- **LOG-14 (GR#7).** Appending a malformed change record (unknown domain tag, a required old/new missing where a prior value must exist, a missing subject/entity reference) is rejected with a registry-sourced error (new `MET-E`-range code) — never silently stored or defaulted. Querying with an invalid filter (unknown domain, an inverted `[to < from]` range) returns a registry-sourced error, not a silent empty result. Check: `grep -n "MET-" internal/engine/history/*.go` finds registry code references on both paths; passing tests for the malformed-append and invalid-filter cases — **GR#7 assertion, stated explicitly (BUG-100 convention):** each test asserts the returned error's registry code matches AND that no partial/incorrect record was stored or no misleading empty result was returned, not merely that a matching-named test function exists.

### Determinism & safety

- **LOG-15 (append-only and reproducible; GR#21).** Replaying the same `(worldSeed, command log)` produces a byte-identical central history — both the change-event log and the sampled aggregate series — across repeated runs and across process restarts. The history is derived from the deterministic simulation (fixed-order tick phases, stable append order per LOG-8), never from wall clock or unordered map iteration. Check: a passing determinism test runs the same command log twice and asserts byte-identical history (`grep -rn "func Test.*[Dd]eterminis\|func Test.*[Rr]eproduc" internal/engine/history/*_test.go`); this rides the existing replay machinery (§14 headless / `harness.replay`) rather than inventing a second replay path.
- **LOG-16 (no wall clock; SG-7 scoped).** `grep -rn "time.Now\|time.Since" internal/engine/history/*.go internal/ui/screens/history/*.go` (excluding `_test.go`) returns no matches — timestamps are simulation month/year; series are tick/month-driven.
- **LOG-17 (GR#20).** `go list -deps ./internal/ui/screens/history/...` shows no import of `internal/engine/...` — the book consumes via `int.protocol`/`ui.core`, never engine internals directly (the same seam every F-screen crosses).
- **LOG-18 (race safety).** `go test ./internal/engine/history/... -race -count=1` passes with no data race when producers append concurrently with a UI query of the history (the append-only store must be safe under concurrent append + read). Check: `grep -n "go func()" internal/engine/history/*_test.go` finds a concurrency test.

### Documentation

- **LOG-19.** The package doc states the module key(s) (proposed `engine.history` + `ui.screen.history`, pending Escalation A), cites §13 F9, UI-SPEC §2/§4, §5, §7, §434, documents (a) the five change domains and their producing modules, (b) the append-only contract and the old→new field requirement, (c) the monthly aggregate sampling frequency, (d) the death-event granularity decision (LOG-4/Escalation B), and (e) that the book is the raw material for the §434 epilogue rather than a second, divergent account. Check: `grep -n "engine.history\|ui.screen.history" internal/engine/history/doc.go` and `grep -n "§13\|§434\|append-only" internal/engine/history/doc.go` match.

## Out of scope

- **Producing the changes themselves** — policy mechanics (`engine.policies`/FEAT-091), build/demolish (`engine.build`), staffing (`engine.services`), mortality (`engine.citizens`), maintenance (`FEAT-089`). This item records and graphs what those modules change; it does not model any of them.
- **The news ticker / bulletin / epilogue prose** (`engine.news`/MOD-064-adjacent `ui.screen.ticker`) — §13 F9's ticker is *generated prose with salience scoring*; the book is *structured change history + graphs*. The two must not be merged or duplicated (GR#3): the book does not re-implement `engine.news`' searchable archive, and `engine.news`' prose generation is out of scope here.
- **The F2/F6 dashboard content itself** — population, money, and employment figures already appear on F2 Finance / F6 Demographics / the F1 Overview; the book's graphs are a *history* view of those series, not a re-ownership of the current-value dashboards.
- **The graph *suite beyond the five named series*** — "the full graph suite the reference city-builder ships" is honoured as the five named series plus the rendering idiom (sparkline/Braille), not as an open-ended mandate to add every city-builder stat. Additional series (e.g. happiness, traffic, education) are follow-up work, flagged not built.
- **Tuned graph scales / axis ranges** — per the balance-number regime and LOG-10, no y-axis scale or tick interval is invented by this item; any aesthetic scale is a rendering default, documented not hardcoded.

## Escalations

- **A. For Bill — the load-bearing cross-check finding (BUG-058 class): almost every producer surface this log consumes is unbuilt or unregistered.** `code.json` has **no `feat.activitylog`, `engine.history`, or `ui.screen.history` entry**, and — worse — the *sources* are missing: (1) FEAT-091's "change history" exists only in FEAT-091's own BOW description; there is **no `feat.policy.md` acceptance file**, and `engine.policies.md` (MOD-064) specifies no change-history query/event surface for the log to consume; (2) `engine.build` (BuildAPI), `engine.services` (ServicesAPI), and `engine.citizens` (CitizensAPI) register **no change-event outbound edge** to feed a central history — build/demolish/staffing/death are command/aggregate surfaces, not an event stream; (3) **FEAT-089 has no module at all** — no `engine.maintenance`, so "maintenance spend" has no registered source beyond `engine.finance`'s generic opex ledger (which FEAT-089 would populate). This is the same shape `ui.dash.md`/`ui.screen.demo.md` already flagged (a spec-mandated capability with no registered edge to carry it). **Recommendation:** before dispatching a junior on FEAT-093, Bill rules on (i) the module split (this file's `engine.history` + `ui.screen.history` proposal vs. folding the store into an existing module), (ii) whether the producer change-event surfaces are a prerequisite item each (folded into FEAT-091/engine.build/engine.services/engine.citizens/FEAT-089 or a new shared event bus), and (iii) registering the resulting keys via `master-plan-v2.1.json` → `tools/plan/generate.js` (never a hand-edit of `code.json`). LOG-3 is written to hold under any of these outcomes by stating the *requirement* (consume the producer's change surface, name the producer) rather than prescribing which module emits.
- **B. For Aaron/Bill — death-event granularity and volume (ASM, to be logged).** "Every death event is recorded" at 100M citizens means potentially enormous per-event history volume. The reference city-builder graphs deaths in aggregate and logs individuals selectively. This file records deaths at the granularity `engine.citizens` produces individual events, with cold deaths rollable into the monthly aggregate (LOG-4), but the *storage/rollup decision* is Aaron's, not this BA's — too consequential to guess (it's the difference between a bounded log and an unbounded one at scale).
- **C. For Bill — is the "book" a new surface, or the "History" half of F9?** §13 F9 already names "full searchable history log" as the ticker's archive, and `ui.screen.ticker` exists (consuming `engine.news`). The book (structured change history + graphs) is materially different from the ticker (generated prose), but where it *lives* — a new screen, a pane inside F9, or an extension of F9's History — is a product decision this BA cannot make from the BOW text. This file assumes a distinct `ui.screen.history` surface; if it should instead extend F9, the UI-level ACs (LOG-9/LOG-12/LOG-13) re-home to that package.
- **D. For Bill — `int.protocol` sub-entity drill-through (inherits `ui.dash.md`'s `FEAT-042`).** LOG-13's "a history entry's value opens its source" wants entity/row-level drill targets; `int.protocol`'s view-name grammar today addresses views, not entities-within-views (the same gap `ui.dash.md` escalated). If history entries need per-entry drill-through, this binds the same cross-module contract gap — recommend resolving once, not per-screen.
- **Assumptions to log as ASM items (see report to Bill):** the module split (Escalation A), the death-event granularity (Escalation B), the book's placement vs F9 (Escalation C), the five-series list being closed (a sixth series is follow-up, not "the full suite"), and the monthly sampling frequency for the aggregate series (BA-chosen default — the graph series are sampled once per simulated month, matching the sparkline's 24-month idiom, not spec-mandated).
