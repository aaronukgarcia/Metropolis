## User stories

- **US-1.** As the player watching a district decline, I need crime generated per-district, per-type, per-month from independently isolable drivers (unemployment, deprivation, inter-district inequality, blight, youth leisure deserts, low policing presence), so a crime wave traces to a cause, not a single opaque dial.
- **US-2.** As the policing budget slider, I need deterrence (concave in patrol coverage), clearance (detectives, suppresses persistence of existing offenders), and prevention (youth/job/lighting/community, cuts new generation) to be three distinct, independently-moving mechanisms, so "more police = less crime" is mechanically true for the right reason rather than one blended multiplier.
- **US-3.** As `engine.spiral` (a registered outbound dependency, MOD-030, the Detroit spiral), I need gangs to be genuinely removable AND genuinely capable of respawning under an incomplete removal — a stateful entity lifecycle with a real negative direction, not a one-way "gangs appear" flag — because a gang system that can only grow, or that any single lever trivially clears, makes the safety term in Attractiveness (§11) and the spiral's own severity curve unfalsifiable.
- **US-4.** As `engine.prison` (MOD-056, the registered consumer of `CrimeAPI`), I need every sentenced offender to arrive at prison's intake as a citizen this module can independently account for through the justice chain (arrest → charge → conviction → sentence), not a bare headcount handed over with no upstream trail — Option B (persistent individuals, no culls ever) makes this a pipeline of identifiable people, and a conservation identity applies at every stage.
- **US-5.** As the Security Service liaison (MI5-analogue), I need the terror-threat dial to be preceded by a genuine, queryable rising indicator — "never random-spam, always preceded by visible threat-level intel" — so a rare, severe event is never an unconditioned per-tick coin flip wearing a cosmetic readout.
- **US-6.** As `code.json`'s current registered edges, I need this item to be honest about which effects it can reach through a registered call today (citizens, services, wellbeing, spiral) versus which two named spec effects it cannot (insurance costs on firms — no `engine.market`/`engine.firms` edge; conservation registration with `engine.invariant` — no edge, contract entirely unpopulated), so the Tester never has to guess whether an unregistered call secretly exists (GR#20; see BUG-058 findings in Escalations).

## Scope

Per-district, per-type crime generation from independently isolable drivers; the deterrence/clearance/prevention triad; the gang lifecycle (formation persistence rule, four distinct territorial/tax/recruitment/violence effects, full-stack removal, decapitation-without-regeneration respawn); the command ladder (posts→stations→Divisional HQ→Constabulary HQ) gating strategy sliders; the MI5-analogue threat dial with its precursor requirement; the justice chain's conservation identity (arrest→charge→conviction→sentence, cross-checked against `engine.prison`'s independent intake ledger) and courthouse-backlog release mechanism; a queryable safety-term output for `engine.attract`'s pushed-input surface.

## Acceptance criteria

### Functional — generation, drivers, and the policing triad

- **AC-1 (GR#20; code.json inbound contract).** A `CrimeAPI` exists matching code.json's registered pattern "generation/deterrence/clearance decomposed and drill-through": per-district, per-type generation is independently queryable, and each of deterrence/clearance/prevention is drill-through inspectable as its own contribution. Check: `go doc ./internal/engine/crime CrimeAPI` lists per-type generation accessors plus separate deterrence/clearance/prevention accessors; a passing test asserts changing one driver's input changes only the terms the spec ties it to, not every crime type uniformly (`grep -rn "func Test.*[Dd]rillThrough\|func Test.*[Tt]ermIsolation" internal/engine/crime/*_test.go`). A lazy-but-plausible violation: one opaque per-district "crime level" float — this check rejects it by demanding independently-inspectable type and mechanism accessors.
- **AC-2 (§28 nine crime types, decomposed).** Petty theft, burglary, vehicle crime, criminal damage, violent crime, drugs supply, organised crime, fraud/cyber, and smuggling are tracked as nine distinct sub-figures per district, not one blended crime index split for display. Check: `go doc ./internal/engine/crime` shows nine named type accessors; a passing test raises port/harbour throughput alone and asserts only the smuggling figure measurably moves while the other eight remain materially unchanged (`grep -rn "func Test.*[Cc]rimeType\|func Test.*[Ss]muggling" internal/engine/crime/*_test.go`). **Lazy implementation this rejects:** a single weighted score with nine display labels computed by proportional split — the same shape `engine.wellbeing.md` AC-3 and `engine.social.md` AC-2 both reject — would satisfy "nine types exist" while making them move together on any driver change.
- **AC-3 (§28 inequality between ADJACENT districts — the driver most likely to be faked as plain deprivation).** The inter-district-inequality driver is computed from a genuine neighbour comparison (this district's wealth/deprivation figure vs. its geographically adjacent districts', via `engine.world`'s cell/district adjacency), not merely correlated with this district's own deprivation level. Check: a passing test constructs two districts with identical own-deprivation figures but different neighbouring-district wealth, and asserts their crime-generation outputs differ (`grep -rn "func Test.*[Ii]nequalityDriver\|func Test.*[Aa]djacentDistrict" internal/engine/crime/*_test.go`). **False-pass risk:** an implementation that reads "inequality" as a synonym for "this district's own poverty level" (the cheapest thing to compute, since it needs no adjacency lookup) would pass any test that varies deprivation and inequality together — the check requires a fixture holding own-deprivation constant while varying only the neighbour's wealth.
- **AC-4 (§28 concave deterrence).** Deterrence's marginal crime-reduction-per-patrol-unit strictly decreases as patrol coverage rises (first cars per 10k cut most; diminishing returns thereafter). Check: a passing test samples deterrence at three increasing coverage levels and asserts the second difference (the marginal-return delta) is negative (`grep -rn "func Test.*[Cc]oncaveDeterrence\|func Test.*[Mm]arginalReturn" internal/engine/crime/*_test.go`). **False-pass risk:** a linear deterrence function checked only at two points ("more patrols, less crime") looks identical to a concave one on a two-point test — the check requires a three-point comparison to expose the diminishing-returns shape specifically.
- **AC-5 (§28 clearance vs. prevention — two mechanisms, independently movable).** Clearance (detectives) suppresses the *persistence* of already-generated/active crime; prevention (youth centres, job centres, lit streets, community centres) cuts *generation* of new crime; these are two distinct terms, and moving one via its own funding lever must not move the other's attributed contribution. Check: two single-variable tests — raise detective capacity holding prevention infrastructure fixed and assert a persistence/recurrence metric drops while the driver-attributable generation term is unchanged; raise prevention infrastructure holding detective capacity fixed and assert the reverse (`grep -rn "func Test.*[Cc]learanceIsolat\|func Test.*[Pp]reventionIsolat" internal/engine/crime/*_test.go`). **Lazy implementation this rejects:** a single "policing effectiveness" scalar fed by total police funding would pass a shallow "more funding, less crime" check while making it impossible to tell which mechanism did the work — exactly the debugging/tuning failure GR#3 exists to prevent.

### Functional — gangs (the central defect-catcher: formation/removal in both directions)

- **AC-6 (§28 gang FORMATION — the persistence requirement, not a peak-detection shortcut).** A gang entity (named, tracked, with a stable identity) forms in a district only after high youth unemployment + blight + low clearance hold *simultaneously* for more than 24 **consecutive** simulated months — not "has exceeded the threshold at any point in the trailing 24 months." Check: a passing test sustains all three conditions above threshold for 23 months, relaxes exactly one condition in month 24, and asserts **no gang forms**; a second scenario sustains all three for the full 24+ months and asserts a gang entity is created with a queryable, stable ID (`grep -rn "func Test.*[Gg]angFormation.*23\|func Test.*[Gg]angFormationSustained" internal/engine/crime/*_test.go`). **False-pass risk:** treating ">24 months" as "ever peaked above threshold within the last 24" rather than an unbroken run would pass a naive "gang eventually forms" test while failing the 23-then-relax negative case this AC specifically demands.
- **AC-7 (§28 gang effects — four distinct, independently isolable).** A formed gang measurably (a) claims a queryable territory (a cell-set attribution), (b) raises **every** local crime type in its territory, not only organised crime, (c) taxes local businesses via a queryable levy that raises closures, and (d) recruits from the matching demographic, reducing the eligible-pool figure AC-3's/AC-2's drivers read from. Check: four independent test scenarios, each constructed to isolate one effect from the other three (`grep -rn "func Test.*[Gg]angTerritory\|func Test.*[Gg]angTax\|func Test.*[Gg]angRecruit\|func Test.*[Gg]angCrimeUplift" internal/engine/crime/*_test.go`). **Lazy implementation this rejects:** implementing only the crime-uplift effect (the cheapest, most player-visible one) while leaving territory/tax/recruitment as flavour text would satisfy "gangs exist and are bad" while three of the four named spec effects remain inert.
- **AC-8 (§28 gang REMOVAL — the full-stack requirement; the sharpest check in this file, the direct answer to "removal trivially easy fails this too").** Gang strength/presence trends toward the removed state **only** when clearance pressure, prison absorption of members, regeneration investment, and youth provision are **all** concurrently above their documented thresholds — applying clearance pressure alone, at any magnitude, does not remove the gang. Check: a passing test applies maximum clearance-pressure-only pressure (the other three stack components held at pre-gang baseline) for an extended run and asserts the gang entity **survives** (does not cross the removed threshold); a second test applies all four components together and asserts the gang crosses the removed threshold within a bounded number of simulated months (`grep -rn "func Test.*[Gg]angRemoval.*[Cc]learanceOnly\|func Test.*[Gg]angFullStack" internal/engine/crime/*_test.go`). **This is the check that catches "trivially easy removal":** a build where clearance pressure alone suffices (a one-lever kill switch) passes any test that only exercises the full-stack-succeeds case while failing this AC's clearance-only negative case.
- **AC-9 (§28 decapitation-without-regeneration respawns — the asymmetry check, the direct `engine.attract` AC-5 analogue for a stateful entity).** A decapitation event (removing a gang's leadership/territorial presence) issued **without** concurrent regeneration investment in that district causes a **new** gang entity (a fresh ID, per AC-6's formation mechanism — not the same entity silently un-deleted) to re-form in that district within a bounded observation window, because the underlying generative conditions are unchanged; the identical decapitation event issued **with** concurrent regeneration investment does not respawn within the same window. Check: two scenarios differing only in whether regeneration investment accompanies decapitation; the decapitation-only scenario must show a new gang forming within the window, the decapitation+regeneration scenario must not (`grep -rn "func Test.*[Dd]ecapitationRespawn\|func Test.*[Rr]egenerationPreventsRespawn" internal/engine/crime/*_test.go`). **A lazy-but-plausible violation this rejects:** a "removal" implementation that is actually just decapitation (delete the gang, leave conditions untouched) could still pass AC-8 if AC-8's own "full stack" fixture happened to include a decapitation step mistaken for sufficient — this AC forces the decapitation-only scenario specifically and demands the respawn actually happen, catching a removal model that looks complete but isn't.
- **Together, AC-8 and AC-9 are this file's answer to the brief's central instruction, mirroring `engine.attract.md`'s AC-4/AC-5 pair:** AC-8 fails a model where any single lever removes a gang (too-easy removal, the risk of a check that only asserts gangs appear); AC-9 fails a model where "removal" is really just decapitation with the underlying drivers left standing (removal that looks complete but regrows). A build satisfying only one of the two is a one-way cycle disguised as bidirectional.

### Functional — command structure, MI5 liaison, justice chain

- **AC-10 (§28 command ladder gates strategy sliders).** The citywide strategy-mix sliders (patrol/detective/community weighting) are settable only once a Constabulary Headquarters is built — a station or Divisional HQ alone does not unlock the citywide mix. Check: a passing test attempts to set the citywide mix with no Constabulary HQ built and asserts rejection; a second test with HQ built asserts the mix is settable and that shifting each of the three weightings independently moves AC-4's deterrence, AC-5's clearance, and AC-5's prevention terms respectively (`grep -rn "func Test.*[Cc]onstabularyGate\|func Test.*[Ss]trategyMix" internal/engine/crime/*_test.go`).
- **AC-11 (§28 MI5-analogue threat dial — never random-spam).** A terror-threat event fires only after a documented, queryable threat-level indicator has been nonzero and rising for at least a minimum lead window, and the event's trigger probability is a function of (major-event/stadium/airport exposure, Security Service funding, liaison level) — not an unconditioned draw each tick. Check: a passing test asserts no test-triggered event fires from a sustained "quiet" threat-level baseline regardless of elapsed ticks, and that a threat-level rise precedes any fired event by at least the documented lead window within the same run; a second test holds exposure fixed while raising Security Service funding and asserts trigger probability strictly decreases (`grep -rn "func Test.*[Tt]hreatPrecursor\|func Test.*[Nn]oRandomSpam" internal/engine/crime/*_test.go`). **False-pass risk:** a cosmetic "threat level" readout uncoupled from the actual trigger roll (decorative UI number, independent RNG underneath) would pass a bare "threat level exists" check while remaining random-spam under the hood — the check requires the precursor window to be observed in the same run that produces the event, and requires funding to move the probability.
- **AC-12 (§28 justice-chain conservation identity — the strongest available check, a pipeline of identifiable people per Option B; mirrors `engine.refuse.md` AC-11/`engine.social.md` AC-11's independently-sourced-terms pattern).** For every accounting month and district/city aggregate, both identities hold exactly: `OffendersArrested == OffendersCharged + OffendersReleasedNoCharge` and `OffendersCharged == OffendersConvicted + OffendersAcquitted + OffendersAwaitingTrial(the courthouse backlog stock carried to next month)`, and `OffendersConvicted == OffendersSentencedToPrison + OffendersSentencedNonCustodial`. Every term is independently sourced — arrested from the clearance mechanism's own apprehension log (AC-5), charged/released-no-charge from the courthouse's charging-decision log, convicted/acquitted/awaiting-trial from the courthouse's trial-outcome log and its own backlog stock — and, critically, `OffendersSentencedToPrison` is cross-checked against `engine.prison`'s **independently-tracked intake ledger** (per `engine.prison.md` AC-2), not trusted as this module's own say-so of having sent it. No term is computed as a remainder. Check: a passing test runs a synthetic multi-district city over several months with a mix of clearance outcomes, charging decisions, trial outcomes, and a deliberately induced backlog (AC-13), independently sums every right-hand term from its own source accessor — crossing into `engine.prison`'s package specifically for the sentenced-to-prison cross-check — and asserts both identities hold exactly per month (`grep -rn "func Test.*[Jj]usticeChainConserv\|func Test.*[Oo]ffenderPipeline" internal/engine/crime/*_test.go`). **Lazy implementation this rejects, the exact warning repeated this wave:** computing `OffendersAwaitingTrial` (or any term) as whatever remainder makes the identity balance, rather than reading it from the courthouse's actual backlog stock, would make the identity tautologically true regardless of a bug that silently loses or double-counts an offender mid-chain — indistinguishable from correct until `engine.prison`'s own intake figure disagrees with what crime believes it sent. Because this chain spans two modules, a same-module remainder trick here would hide a genuine cross-module accounting bug that a single-module identity (like `engine.refuse`'s) structurally cannot — this is the sharpest instance of the anti-pattern in this wave for exactly that reason.
- **AC-13 (§28 courthouse backlog releases offenders — the causal claim, not just a rising number).** A courthouse operating below its throughput capacity accumulates the `OffendersAwaitingTrial` backlog (AC-12); once backlog exceeds a documented threshold, a release-on-bail-or-lapsed-charge mechanism returns offenders to the general population as a distinct, queryable outcome (`OffendersReleasedOnBacklog`, separate from `OffendersAcquitted`), and this release measurably softens AC-3's/AC-5's "low clearance" driver used by AC-6's gang-formation condition — closing the loop the spec names. Check: a passing test saturates courthouse throughput below arrival rate for several months and asserts (a) the backlog stock grows, (b) a nonzero, distinctly-typed `OffendersReleasedOnBacklog` figure appears once past threshold, and (c) the effective clearance driver measurably softens afterward (`grep -rn "func Test.*[Bb]acklogRelease" internal/engine/crime/*_test.go`). **False-pass risk:** a backlog number that rises forever with no release mechanism would satisfy "backlog exists" while missing the spec's explicit causal claim — the check requires the release event and its downstream feedback into clearance/gang conditions, not just the accumulating stock.

### Error handling

- **AC-14 (GR#7).** Querying an unregistered district's crime figures, or issuing a strategy-slider command against an un-built Constabulary HQ, returns a registry-sourced error (new `MET-E`-range code) rather than a silently-created zero-value district entry or a silently-dropped command. Check: `grep -n "MET-" internal/engine/crime/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredDistrict\|func Test.*[Nn]oHQ" internal/engine/crime/*_test.go`).
- **AC-15.** A decapitation command targeting a gang ID that doesn't exist, or a strategy-mix command whose three weights don't sum to a documented total, is rejected with a typed error, never silently ignored or silently renormalised. Check: passing test coverage (`grep -rn "func Test.*[Ii]nvalidDecap\|func Test.*[Ii]nvalidMix" internal/engine/crime/*_test.go`).

### Determinism, safety & scale

- **AC-16 (GR#21).** Crime-event generation, gang-formation/respawn timing, threat-dial draws, and any tie-breaking in courthouse case ordering use the counter-based hash stream `hash(worldSeed, id, month, purposeTag)` — no shared/global RNG anywhere in the package. Check: `grep -n "rand.New\|math/rand\"" internal/engine/crime/*.go` (excluding `_test.go`) finds no shared/global RNG source.
- **AC-17 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/crime/*.go` (excluding `_test.go`) returns no matches.
- **AC-18.** `go test ./internal/engine/crime/... -race -count=1` passes; `grep -n "go func()" internal/engine/crime/*_test.go` finds at least one concurrency test (concurrent per-district generation within a tick).

- `engine.attract`'s consumption of the safety term — this item exposes a queryable safety-shaped output; `engine.attract`'s push-model (per `engine.attract.md` AC-3) is that module's job, and no direct call edge is required for it under GR#20 since attract accepts pushed input.
- `engine.spiral`'s own Detroit-spiral severity curve — this item's registered outbound edge lets `engine.spiral` read decay-adjacent state; the severity math is MOD-030's job.
- The literal ticker/bulletin text naming gang/crime events — `engine.news`'s job; no `engine.crime`↔`engine.news` edge is registered (consistent with BA-S8a's broader `engine.news` edge-coverage finding), so this item emits documented event *values* a future consumer can subscribe to, not a direct call outward.
- Smuggling's port-throughput/customs mechanics in depth — §33's freight-harbour system; this item only consumes port throughput as a generation driver input (AC-2).
- Specific gang-removal thresholds, reoffending-adjacent figures, and threat-dial lead-window length — balance data pending M2 tuning (see Escalations, ASM-327).
