**Spec refs:** §15 (Architecture, `docs/METROPOLIS-MASTER-v2.1.md` lines 261-267); UI-SPEC §1 (rendering architecture, lines 722-729) and §6 (view subscriptions, lines 779-781); M0-ENG §1.1 (process/thread topology, lines 792-817); code.json `int.protocol` entry; code.json `conventions.errorHandling.correlation`.

**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/protocol/...`.

## Scope

The versioned engine<->UI command/event/delta protocol: envelope types, view-subscription contract, and the v1 in-process transport (gRPC dormant behind a flag, not built in this item).

## Acceptance criteria

### Functional

- **AC-1.** A `Command` carries a mandatory, non-empty `CorrelationID`. Check: `go doc ./internal/protocol Command` shows a `CorrelationID` field, and `go doc ./internal/protocol Command.Validate` (or equivalent) rejects an empty one — `grep -n "CorrelationID" internal/protocol/envelope.go` shows both the field and a `Validate` method returning an error (e.g. `ErrMissingCorrelationID`) when it is empty; a passing test exercises this (`grep -rn "ErrMissingCorrelationID" internal/protocol/*_test.go` finds coverage).
- **AC-2.** `Delta` carries a `Seq` field that is monotonically increasing **per subscription**, starting at 1 for the first delta after `Subscribe` is accepted. Check: `grep -n "Seq " internal/protocol/deltas.go` shows the field with a doc comment stating per-subscription monotonicity, and a `SeqTracker`-style gap detector exists (`grep -n "type SeqTracker" internal/protocol/subscription.go`) with a passing test asserting sequential Observe calls report `gap==0` and a skipped Seq reports `gap>0` (`grep -rn "func TestSeqTracker" internal/protocol/*_test.go` finds a test, and `go test ./internal/protocol/... -run TestSeqTracker -race -count=1 -v` passes).
- **AC-3.** Deltas are only produced for **live** subscriptions — a subscription that has been unsubscribed must not still receive deltas. Check: this is documented as a sending-side invariant (`grep -n "must stop pushing the instant Unsubscribe" internal/protocol/deltas.go` or equivalent wording matches), and `SeqTracker.Reset` (or equivalent) exists to forget a subscription's sequence state on unsubscribe (`grep -n "func.*Reset" internal/protocol/subscription.go` matches) with a passing test.
- **AC-4 (GR#20).** The v1 in-process transport (`InProcTransport` or equivalent) implements a `Transport` interface with `SendCommand`, `Results()`, `Events()`, `Deltas()`, `Close()`. Check: `go doc ./internal/protocol Transport` lists exactly these methods (names may differ slightly but must cover send-command, receive-results, receive-events, receive-deltas, close). This interface IS the GR#20 (Contract-First, Stub-Forever) seam every engine/UI module must consume through — `InProcTransport` and any future gRPC implementation both satisfying `Transport` unchanged is the whole point.
- **AC-5.** The in-process transport's full-buffer policy is explicit and documented in the package (not left implicit). Check: `grep -n "full-buffer\|evict\|drop policy" internal/protocol/transport.go` finds a doc comment naming the policy (e.g. evict-oldest), and a passing test exercises a full buffer and asserts the documented behaviour (`grep -rn "func Test.*[Bb]uffer\|func Test.*[Ee]vict\|func Test.*[Dd]rop" internal/protocol/*_test.go` finds at least one such test, and it passes).
- **AC-6.** `SendCommand` never blocks the caller: check the doc comment states this explicitly (`grep -n "never blocks\|non-blocking\|does not block" internal/protocol/transport.go` matches) and it returns an error (not silently swallowed) when the command cannot be accepted (invalid, buffer exhausted per AC-5's policy, or transport closed).
- **AC-7.** `Command.Validate()` (or equivalent) rejects a `ProtocolVersion` other than the package's current constant. Check: `grep -n "ProtocolVersion" internal/protocol/envelope.go` shows the constant, and a passing test asserts `Validate()` errors on a mismatched version (`grep -rn "ProtocolVersion" internal/protocol/*_test.go` finds a version-mismatch test case).
- **AC-8.** A `NewCorrelationID()`-style helper exists and produces a non-empty, valid identifier using a non-wall-clock, non-map-iteration source (crypto-random or equivalent). Check: `grep -n "func NewCorrelationID" internal/protocol/envelope.go` matches and its body does not call `time.Now()` (`grep -n "time.Now" internal/protocol/envelope.go` returns nothing).

### Error handling

- **AC-9.** Sending on a closed transport returns a distinct, checkable error (e.g. `ErrTransportClosed`) rather than panicking or blocking forever. Check: `grep -n "ErrTransportClosed" internal/protocol/transport.go` matches, and a passing test asserts `SendCommand` after `Close()` returns this error (`go test ./internal/protocol/... -run TestClose -race -count=1 -v` or equivalent passes).
- **AC-10.** `Close()` is idempotent — calling it twice does not panic. Check: `grep -rn "func Test.*Close" internal/protocol/*_test.go` finds a test calling `Close()` more than once, and it passes.
- **AC-11.** No exported constructor or method in this package can return a bare `error` from the standard library without going through the package's own typed errors/sentinel errors where the item's own docs promise a specific error (correlation-ID / version / view-name validation) — spot check: `grep -n "ErrMissingCorrelationID\|ErrInvalidViewName\|ErrTransportClosed" internal/protocol/*.go` shows these sentinels are actually returned from their respective `Validate`/`Send*` functions, not just declared.

### Determinism & safety

- **AC-12 (SG-7 scoped; GR#21).** `grep -rn "time.Now" internal/protocol/*.go` (excluding `_test.go`) returns **no matches at all** — this package must never call the wall clock anywhere (stricter than foundation.errors: the protocol package has no injectable-clock carve-out). A regression here is GR#21 (Red Determinism Gate Stops the Line) territory once this package sits on the tick path.
- **AC-13 (GR#21).** `Tick` is an explicit simulation-time type (not wall-clock-derived) used for staleness detection. Check: `grep -n "type Tick" internal/protocol/envelope.go` matches, and its doc comment states it is never derived from wall time.
- **AC-14 (GR#20).** This package imports nothing from `internal/engine` or `internal/ui`. Check: `go list -deps ./internal/protocol/... | grep -E "internal/engine|internal/ui"` outputs nothing. This is GR#20's "internal/ui → internal/engine imports lint-banned" rule applied to the seam package itself: `int.protocol` must stay import-neutral so both sides consume it only via the interface, never each other directly.
- **AC-15 (GR#21).** No `range` over a Go map is used to produce ordering-sensitive output on the send/receive hot path (A8 lint discipline). Check: manual scan of `transport.go`, `subscription.go`, `deltas.go`, `events.go`, `commands.go` for `for _, v := range someMap` where the loop's output order affects wire bytes or channel send order — none found (Tester records any instance found as a FAIL with file:line).
- **AC-16 (GR#21).** `SeqTracker` and `SubscriptionAllocator` (or equivalents) are safe for concurrent use, matching their doc comments. Check: `go test ./internal/protocol/... -race -count=1` reports no data race, and at least one test drives them from multiple goroutines (`grep -n "go func()" internal/protocol/*_test.go` finds one). A data race is a determinism hazard under GR#21, not a routine bug.

### Documentation

- **AC-17.** `internal/protocol/doc.go` states the module key `int.protocol` and cites §15 / UI-SPEC §6 in its package comment. Check: `grep -n "int.protocol" internal/protocol/doc.go` and `grep -n "§15\|UI-SPEC" internal/protocol/doc.go` both match.
- **AC-18.** The view-name grammar (UI-SPEC §6 "named projections") is documented in the package with at least one worked example. Check: `grep -n "ViewName\|view name" internal/protocol/subscription.go` shows a doc comment with a naming grammar and example strings.

## Out of scope

- Engine-side (`T-ENGINE`, `T-SUBSCR`) and UI-side (`T-VIEWS`, `T-RENDER`) consumers of this protocol — those are `MOD-008`/`MOD-009`/`MOD-012`/`MOD-013`, separate items that depend on this one.

- Remote/cloud transport security (auth, TLS) — out of v1 scope per §15's cloud path being "designed, unbuilt v1".

## Why this section is unlike a normal amendment

`int.protocol` was frozen v1 at Sprint 0 under Aaron's own review (AC-1–AC-18 above). This item is not new work on a green field — it is surgery on a contract eight other modules (`ui.core`, `ui.widgets`, `ui.screen.map`, `ui.screen.debug`, `harness.stub`, `harness.headless`, `harness.replay`, `engine.core`) already depend on and compile against, none of which get a rebuild budget in this item. Every AC below that touches the wire format is written to answer one question first: **does this stay additive, and how would we know if it silently didn't?** Compatibility is not a closing checklist item here — it is graded with the same weight as the two new capabilities themselves, in its own section (Compatibility & Amendment Safety), because "an additive field is far safer than a changed one" is a claim that needs a test, not an assertion.

**A narrower amendment than the BOW item's framing implies.** Re-reading `subscription.go`'s own `ViewName` grammar comment during the original drafting pass found that whole-entity drill targets — UI-SPEC §4's "opens that junction", "opens that school" — are *already* addressable under the existing, frozen grammar (`junction.14.approaches`, `citizen.482913.detail` are both real, already-passing cases in `TestValidateViewName`, confirmed by inspection before writing this section). That part of the gap `ui.dash.md`'s escalation raised is a **documentation gap** (AC-19), not a wire-format gap. The genuine new wire capability this item must add is narrower: **addressing a specific element *inside* an already-open view's patch** — a ledger line, a diagram arrow — which the existing grammar cannot reach because those elements are not separate subscriptions. AC-20/AC-21 below are scoped to that real gap. See ASM-305.

## User stories

- **US-1.** As `ui.dash`'s `DrillTarget` (MOD-038, blocked on this item per its Escalations), I need a protocol-side type I can bind a tile's or table row's source identity to, so `AuditDrillCoverage` has something concrete to resolve rather than a documentation promise.
- **US-2.** As `ui.alerts`'s crisis auto-pause (FEAT-013 AC-6, blocked on this item per its Escalations), I need a signal on incoming protocol data that is explicitly crisis-or-not, independent of priority tier, so a P0 "loan payment due" alert cannot accidentally trip auto-pause.
- **US-3.** As every module already built against `int.protocol` v1, I need this amendment to change nothing about my existing compile or runtime behaviour, so I keep working without a rebuild dispensation.
- **US-4.** As `harness.replay`, I need a v1-recorded fixture to still load and mean the same thing under v2 code, so the permanent-fixture estate (M0-ENG §2.1) does not silently invalidate itself the day this amendment merges.

## Scope

Two additive extensions to `internal/protocol/`: (1) a sub-entity/element addressing type for elements inside an already-subscribed view's patch, and a package-level documentation fix confirming the existing `ViewName` grammar already covers whole-entity addressing; (2) an explicit, tier-independent crisis field on `Event`. Both land as new, optional, `omitempty` surface — no existing exported type's field (AC-1–AC-18 above) is renamed, retyped, or removed.

## Acceptance criteria

### Functional — entity addressing

- **AC-19 (documentation fix, not a wire change).** `int.protocol`'s package documentation gives at least one worked example, quoting UI-SPEC §4's own wording, showing that a whole-entity drill target ("opens that junction", "opens that school") is satisfied today by `ViewName`'s existing entity-scoped grammar (`subscription.go`) with zero code change. Check: `grep -n "junction\|citizen" internal/protocol/subscription.go` shows an example tied explicitly to a UI-SPEC §4 phrase (not just the pre-existing generic grammar comment), and `go test ./internal/protocol/... -run TestValidateViewName -v` continues to pass with `junction.14.approaches`/`citizen.482913.detail`-shaped names in its accepted set (already true — this AC is about the example being drawn from the spec's own words, not about new validation behaviour). A false pass looks like: citing the grammar in the abstract without connecting it to a specific UI-SPEC drill-through example, leaving the next reader to re-derive US-1's "which cases are already solved" question from scratch.
- **AC-20 (the wire amendment — addressing an element inside an open view).** A new, additive, exported type names one element inside an already-subscribed view's patch (illustrative name: `EntityID`, a string-based type reusing the "typed:id" convention `subscription.go` and `InspectEntityPayload.EntityRef` already document informally — **BINDING:** it must be an exported, package-level, string-representable type distinct from any existing field; **ILLUSTRATIVE:** the exact name `EntityID`). It ships with a `Validate`-style function mirroring `ValidateViewName`'s shape (non-empty, disallowed characters rejected, not merely documented). Check: `go doc ./internal/protocol` lists the new type; `grep -n "func Validate" internal/protocol/*.go` shows a new validator alongside `ValidateViewName`; a passing test covers at least one valid and one invalid case.
- **AC-21 (the addressable pair — what a DrillTarget binds to).** A new, additive, exported struct combines a `ViewName` and AC-20's element identifier (illustrative name: `TargetRef{ViewName string; EntityID EntityID}` — **BINDING:** exactly two fields, one naming the view, one naming the element within it, both JSON-tagged and exported; **ILLUSTRATIVE:** the struct/field names). This is the type `ui.dash`'s `DrillTarget` and `ui.alerts`' alert-jump-target are expected to embed or losslessly convert to/from (per `ui.dash.md`'s Escalation and `ui.alerts.md`'s AC-3 "same call shape `ui.dash` uses"). Check: `go doc ./internal/protocol TargetRef` (or equivalent) shows the two-field shape; a passing test round-trips one through JSON marshal/unmarshal and asserts field-for-field equality.
- **AC-22 (no duplication of the pair type across consumers — the drift-prevention check).** If `ui.dash`'s `DrillTarget` or `ui.alerts`' alert-target type is implemented as its own independent struct rather than embedding/wrapping AC-21's `TargetRef` directly, a reflection-based field-parity test — modeled directly on `TestHeaderWireFieldsMatchHeader` (`internal/foundation/serialize/serialize_test.go`) — is required in that consumer's own test suite, proving the two types stay in lockstep field-for-field. This AC belongs to this section (not `ui.dash.md`/`ui.alerts.md`) because it is the protocol amendment's job to state the rule those consumers must follow, the same way `int.serializer`'s `Header`/`headerWire` pairing set the precedent this generalises. Check: `grep -rn "TargetRef" internal/ui/dash/*.go internal/ui/screens/chrome/*.go` — if either package defines a parallel struct rather than reusing `protocol.TargetRef` by value/embedding, a matching `func Test.*FieldsMatch` (or equivalent) must exist in that package. **This is the check that rejects the lazy-but-plausible build**: two independently-hand-written structs that happen to agree today and silently drift the next time either side adds a field, with nothing to catch it — exactly the shape `int.serializer`'s own drift test (ASM-096) was written to prevent, reused here rather than re-derived.
- **AC-23 (a worked, spec-matched example, not a placeholder).** `doc.go` (or the type's own doc comment) documents, with a concrete example using UI-SPEC §4's actual wording (a ledger-line or diagram-arrow case, not `"foo.bar"`), how a view's patch schema is expected to embed `EntityID`/`TargetRef` values for the elements it wants drillable. Check: `grep -n "ledger\|diagram" internal/protocol/*.go` (doc comments) shows the worked example tied to AC-20/AC-21's types.

### Functional — crisis signal

- **AC-24 (the field, and the rule it must not silently violate).** `Event` gains one new, additive, `omitempty`-tagged field (illustrative name: `Crisis bool`) that is independently settable from `Severity` — no code path in this package derives one from the other. **BINDING:** the field must be settable to `true` on an `Event` whose `Severity` is `SeverityInfo` or `SeverityWarning`, and settable to `false` on an `Event` whose `Severity` is `SeverityCritical`, without either assignment being rejected or silently overridden; **ILLUSTRATIVE:** the field name `Crisis` and its exact placement in the struct. Check: `grep -n "Crisis" internal/protocol/events.go` shows the field with a doc comment stating explicitly it is not derived from `Severity`; a passing test constructs an `Event{Severity: SeverityInfo, Crisis: true}` and a separate `Event{Severity: SeverityCritical, Crisis: false}` and asserts both fields read back exactly as set. **This is the check that rejects the lazy-but-plausible build**: an implementation that adds a `Crisis()` *method* computed as `Severity == SeverityCritical` would satisfy "a crisis concept exists" while reintroducing exactly the tier-derivation `ui.alerts.md` AC-6 forbids (a P0 "loan payment due" auto-pausing because P0 happens to map to a high severity) — this AC's two-sided test (non-critical-but-crisis, critical-but-not-crisis) is what a tier-derived shortcut cannot pass.
- **AC-25 (absence means false, explicitly, not accidentally).** `Crisis` defaults to `false` when the JSON key is absent entirely (pre-amendment-shaped data), and this is documented as the correct reading for both "genuinely not a crisis" and "recorded before this field existed" (see AC-29 for why those two cases are allowed to be indistinguishable). Check: a passing test decodes a hand-written JSON `Event` object with no `crisis` key at all and asserts `Crisis == false` with no decode error.
- **AC-25b (stable per-instance crisis identity — the dedupe precondition).** Per Aaron's direction on ASM-276 (crisis-taxonomy-proposal.md §6): whatever field or value the engine side uses to identify *which* underlying crisis instance an `Event`/`Delta` belongs to (e.g. `EntityRefs` or a dedicated identifier) is documented as required to be **stable across that crisis instance's lifetime**, never regenerated per delta/event — a repeatable crisis type needs one ID per instance, not one per condition-type or one freshly minted per tick. This is a documentation/contract requirement on this package (what the engine side must guarantee), not new wire surface, since `ui.alerts` AC-8's edge-triggered dedupe (the consumer of this guarantee) cannot function without it regardless of UI-side quality. Check: `grep -n "stable.*lifetime\|stable.*crisis\|per-instance" internal/protocol/events.go` shows this requirement stated in `Event`'s or `Crisis`'s doc comment, tied explicitly to the dedupe precondition it exists to satisfy.

### Compatibility & Amendment Safety

- **AC-26 (byte-determinism for the unchanged case — additive proven, not asserted).** Marshalling a `Command`, `Delta`, or `Event` whose new fields (AC-20/AC-21/AC-24) are all at their zero value produces byte-identical JSON to the pre-amendment schema. Check: a small set of golden JSON fixtures for `Command`, `Delta`, and `Event` is captured from the pre-amendment code as part of this same commit (before the struct changes) and checked in; a passing test re-marshals equivalent values under the post-amendment code and diffs against the golden bytes, failing on any difference. **This is the concrete, mechanical form of "additive needs proving"** — the protocol-package sibling of `int.serializer`'s `TestHeaderWireFieldsMatchHeader`, adapted to prove byte-output stability rather than field-count parity. A false pass looks like: a test that only asserts the *new* field round-trips correctly and never diffs against a fixture that predates the amendment — that shape would pass even if a new field were accidentally added without `omitempty`, silently changing every existing record's bytes.
- **AC-27 (no hidden wire-mirror, or the same drift test if one exists anyway).** This amendment's design (AC-20/AC-21/AC-24) does not require a hand-maintained JSON mirror struct (the `Header`/`headerWire` unexported-field shape) — all new fields are exported and JSON-tagged directly on their owning type. If an implementer nonetheless introduces such a mirror for any reason, the same commit must add a reflection-based parity test modeled on `TestHeaderWireFieldsMatchHeader`. If no mirror is introduced (the expected case), `doc.go` states this explicitly, mirroring `harness.replay.md`'s AC-13b "if not applicable, say so" pattern, so a future Destructive sweep does not have to re-derive the answer.
- **AC-28 (ProtocolVersion does not move — the compatibility contract made explicit).** `ProtocolVersion` (`envelope.go`) remains the literal string `"1.0"` after this amendment lands. Check: `grep -n 'const ProtocolVersion' internal/protocol/envelope.go` still shows `"1.0"`; a passing test builds a `Command{ProtocolVersion: "1.0", ...}` and asserts `Validate()` succeeds against the current running constant, unchanged from before this amendment. **This is the check that rejects the lazy-but-plausible build**: bumping the constant to signal "something changed" looks responsible but is actively wrong here — `Command.Validate` does an **exact string-equality** check (`cmd.ProtocolVersion != ProtocolVersion`), not a major-version-compatible check like `int.serializer`'s `CheckFormatVersion` — so a bump would reject every already-recorded fixture's `Command`s on the very next regression replay, the opposite of what "keeps working" requires. See ASM-301.
- **AC-29 (a v1 replay recording under v2 — explicit, not silent).** A fixture recorded by a pre-amendment build — `Event`/`Delta` JSON with no `crisis`/`entityId`/`targetRef`-shaped keys at all — loads and replays successfully under the post-amendment code, with the new fields deserializing to their documented zero values (AC-25), not an error and not a silently-wrong non-zero value. Check: `harness.replay`'s fixture-loading path (or a new test in this package if `harness.replay` isn't dispatched yet) is run against a fixture predating this amendment — the checked-in sample under `fixtures/` (`harness.replay.md` AC-6) if it already exists, or a hand-constructed pre-amendment-shaped JSON blob otherwise — and asserts a clean load with the documented defaults. **"Version negotiation, or explicit rejection — either is defensible, silently misreading it is not" is answered here as: no per-record version tag is needed, because the schema is deliberately designed so a new field's *absence* is always a valid, self-consistent state (AC-25), never distinguishable-but-untested from "explicitly false".** A false pass looks like: a test that only replays a fixture recorded *after* this amendment landed, which proves nothing about the pre-amendment case — the one this AC exists to cover.
- **AC-30 (GR#20 — the seam stays import-neutral).** `go list -deps ./internal/protocol/...` still shows no `internal/engine` or `internal/ui` import — identical check to AC-14 above, re-run post-amendment; the amendment adds types and fields, not new dependencies.
- **AC-31 (every existing consumer keeps compiling and passing — GR#20's stub-for-life, made mechanical).** `go build ./...` and `go vet ./...` succeed for the whole repository after this amendment, and `go test ./... -count=1` passes for `internal/ui/core`, `internal/ui/widgets`, `internal/ui/screens/map`, `internal/ui/screens/debug`, `internal/engine/stub`, `internal/harness/headless`, `internal/harness/replay`, and `internal/engine/core` (paths per `node claude-bow.js show` for `ui.core`/`ui.widgets`/`ui.screen.map`/`ui.screen.debug`/`harness.stub`/`harness.headless`/`harness.replay`/`engine.core`) with **no source change to any of those packages** beyond a mechanical positional-literal-to-keyed-literal conversion, which must be called out explicitly if it happens. Check: the Tester runs all of the above and records pass/fail per package. **This is the check that rejects the lazy-but-plausible build**: a change that "only" adds fields but happens to break an existing unkeyed (positional) `protocol.Event{...}`/`protocol.Delta{...}` struct literal somewhere in the eight consumer packages would fail to compile here even though a narrower per-file diff review might miss it — Go's positional-literal rule turns a silent field addition into a loud compile error at every affected call site, which is the desired failure mode (see "Why a build failure here is good news" in Escalations), not a bug to route around quietly.

### Error handling

- **AC-32 (GR#7).** Any new sentinel/validation error introduced by AC-20's `Validate`-style function (an invalid `EntityID`, following `ErrInvalidViewName`'s existing shape) is a distinct, named error claimed from this package's own reserved `MET-P0xx` sub-range (`codes.go`), double-checked against both `data/errors.json`'s `ranges.reserved` table and a live source scan (`grep -rn "MET-P[0-9]" internal/ cmd/`) per `harness.replay.md` AC-8b's BUG-008-derived precedent, not just the table alone.
