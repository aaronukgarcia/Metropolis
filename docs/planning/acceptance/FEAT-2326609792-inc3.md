## 1. Why this item exists

`FEAT-2326609772` inc1-3 (network capacity overlay) apportions a line class's `lineUsageOf` usage across its segments by CAPACITY SHARE; inc2 (`FEAT-2326609795`) replaced that with NEAREST-tile demand attribution (`forecastSegmentUsage`, AC-5/AC-6) — a real improvement, but it is still a LOCAL split: a segment's demand is "how much of the city-wide class total is generated near here," never "how much traffic actually PASSES THROUGH here on its way somewhere else." A cul-de-sac segment with dense housing next to it and a through-route segment on the only path to the city's job centre can carry the same forecast demand under nearest-attribution even though the through-route legitimately sees more FLOW. Routing fixes that: this item takes inc2's per-tile person/freight demand and ASSIGNS it over the real line graph by shortest free-flow path to the nearest job-bearing destination, loads every traversed segment, and applies the standard BPR volume-delay curve to turn that load into a travel-time penalty, a v/c ratio, and — sustained past a threshold — a gridlock flag. Gridlock and long commutes are Aaron's stated route to unhappiness (`FEAT-2326609792` epic brief); this increment builds the SUBSTRATE those effects will read from inc5, without coupling to wellbeing itself yet (out of scope, §6).

## 2. The design in one paragraph

**Segment graph (AC-1).** `lineSegmentIndexOf(s)` (`data.ts:3352`) already gives contiguous same-spec tile runs and a `tileToSegment` map, but never says which segments TOUCH each other — a route needs that. A new memoised `segmentAdjacencyOf(s): Map<segmentId, Set<segmentId>>` walks every segment's tiles' 4-neighbours once (reusing `tileToSegment`, no second flood) and records an edge whenever a neighbour tile resolves to a DIFFERENT segmentId of the SAME `kind` (`'road'`↔`'road'`, `'rail'`↔`'rail'` — road and rail never merge, mirroring the existing flood's own per-kind silo, `data.ts:3357`'s header comment). **Capacity basis (Decision D1 below).** `ROAD_TIER_CAPACITY`/`LINE_CAPACITY` (`data.ts:436`, `3072`) are explicitly `⚠ PLACEHOLDER-balance` game-economy figures that already drive `lineUsageOf`'s income-facing saturation and must not be touched (GR#3 — the A-10 "two figures, two purposes" precedent applies again here); this item's v/c/BPR maths uses a SEPARATE, real-world-sourced capacity: `link_capacity.json roadClasses[].capacityPcuPerLanePerHour × roads.json classes[].lanes` for road segments (via a new `ROAD_CLASS_ID_OF_TIER` lookup mapping the 5 `ROAD_TIER_SPECS` to the matching 5 of `link_capacity.json`'s 11 `roadClassId`s — `residential_street`→tier 1 `road`, `avenue_2_plus_2`→tier 2 `rd_avenue`, ..., `motorway`→tier 5 `m20`), and `link_capacity.json railClasses[].trainsPerHourMax × passengersPerTrainRef` for rail/hs1. **Assignment (AC-2/AC-3).** Every `demandForecastOf(s)` tile (inc2) attaches to its nearest ROAD segment (reusing the nearest-segment BFS primitive `forecastSegmentUsage` already builds, `trafficDemand.ts:387-440`, exported for reuse rather than re-derived — GR#3). Person-trips in `ROAD_PERSON_MODE_IDS` (`trafficDemand.ts:320`) convert to VEHICLE-trips via `vehicle_classes.json`'s `avgOccupancyPersons` (A-10 — never seat capacity); freight vehicle-trips (inc2) are already vehicle-shaped. Each origin's vehicle-trips route via one-shot Dijkstra over `segmentAdjacencyOf`, edge weight = the destination segment's FREE-FLOW time (AC-2's `t0`), to the NEAREST tile carrying `sp.jobs != null && isOnline` (the sole destination class — A-7's purpose split stays deferred, so commute and non-commute trips are not distinguished this increment either, an explicit simplification, §5). **BPR delay (AC-4).** Each loaded segment's `v = assigned vehicle-trips ÷ operating hours` (`data/traffic.json`-sourced, not a literal) `/ lanes`, `c = capacityPcuPerLanePerHour` (per-class override from `link_capacity.json bprCurve.perClassOverrides` where present, else `data/traffic.json`'s network default), `t = t0 × (1 + α(v/c)^β)` — ONE pass, no equilibrium loop (assignment already ran once against free-flow times; re-running assignment against loaded times to convergence is out of scope, §6, flagged as a known simplification whose effect is that a genuinely gridlocked alternate route is never discovered mid-tick). **Commute time (AC-5)** sums `baseAccessMinutes` + Σ loaded-segment `t` along the assigned path + `baseCommuteMinutes`'s wait/transfer component (`data/traffic.json`), aggregated to a city-wide median/p90 export. **Gridlock (AC-6)** reuses `CONGESTION_CONSTANTS`'s threshold/sustained-ticks (`data.ts:3604`) BY IMPORT, applied per-segment to the NEW v/c instead of `lineUsageOf`'s class-level saturation (Decision D3) — a parallel, segment-granularity signal that does not touch `congestionLinesOf` or its income coupling (AC-8, money untouched this increment, mirrors inc2 AC-7).

## 3. Acceptance Criteria

### Segment graph

**AC-1 — `segmentAdjacencyOf(s)`: deterministic segment-to-segment adjacency graph.**
New memoised export in `trafficAssignment.ts`: `Map<segmentId, Set<segmentId>>`, built from ONE pass over `lineSegmentIndexOf(s).tileToSegment`'s entries in sorted `"x,y"` key order (GR#21 — no map-range-with-break), adding a same-`kind` edge for every cross-segment tile adjacency (kind read from `lineSegmentByIdOf(s)`, never re-derived). Symmetric by construction (an edge added from A→B is also added B→A in the same pass).
**Check:** a fixture with three collinear same-class road runs interrupted by two 1-tile gaps of a DIFFERENT spec (so `lineSegmentIndexOf` reports 3 segments, not 1) asserts the adjacency graph has exactly the 2 expected edges (1↔2, 2↔3), none between 1 and 3.
**False-pass note:** a fixture using only ONE contiguous run (1 segment) cannot distinguish "adjacency works" from "adjacency trivially empty" — the Tester must use the 3-segment fixture above.
**Mutant:** widen the adjacency check to 8-neighbour (diagonal) instead of 4-neighbour — reds the 3-segment fixture by adding a spurious 1↔3 edge once the gap tiles are diagonally adjacent in the fixture's layout.

**AC-2 — free-flow time per segment (`t0`), road-class-derived, not literal.**
New `segmentFreeFlowMinutesOf(s): Map<segmentId, number>` = `segment.tiles × metresPerTile ÷ (speedLimitMph × 1609.34 / 60)` in minutes, where `speedLimitMph` comes from `data/roads.json classes[].speedLimit` via the new `ROAD_CLASS_ID_OF_TIER` mapping (§2) and `metresPerTile` is a NEW data-sourced field added to `data/traffic.json` this increment (GR#15 — never hand-typed in TS): derive it from `docs/METROPOLIS-MASTER-v2.1.md`'s own geography (`docs/METROPOLIS-MASTER-v2.1.md:110`, "2 × 2 km purchasable tiles... ~900 tiles, ~36 M cells" ⇒ 36,000,000 ÷ 900 = 40,000 cells/tile ⇒ √40,000 = 200 cells/side ⇒ 2,000 m ÷ 200 = **10 metres/cell**), cited in the field's own `source` note rather than asserted bare. Rail/hs1 segments use `railClasses[].trainsPerHourMax`'s implied headway, not a road speed (documented separately, not blocking this AC).
**Check:** a single-tile `two_lane` segment (speedLimit 40 mph, `roads.json:8`) asserts `t0 ≈ 10m ÷ (40×1609.34/60) m/min ≈ 0.0093 min` (fixture compares against the same formula computed independently in the test, not a hand-copied constant).
**False-pass note:** a test that hand-types the expected minutes value with the SAME rounding the implementation uses will pass even if `metresPerTile` silently reverts to a bare literal in the source — the Check must import `metresPerTile` from the loaded `data/traffic.json` fixture, not restate it.
**Mutant:** hand-type `metresPerTile = 10` directly in `trafficAssignment.ts` instead of reading `data/traffic.json` — a grep-based structural check (`grep -n "metresPerTile" trafficAssignment.ts` must show only a destructure/read, never a numeric literal `10` beside the identifier) reds.

### Assignment

**AC-3 — coarse shortest-path assignment: one destination class (nearest job-bearing tile), one rule (GR#3).**
Every `demandForecastOf(s)` tile's road-mode vehicle-trips (`ROAD_PERSON_MODE_IDS` trips ÷ `vehicle_classes.json avgOccupancyPersons`, A-10, plus `freightVehicleTrips` unchanged) attach to their nearest road segment (reused primitive, §2) as the ORIGIN, then route via Dijkstra over `segmentAdjacencyOf` (AC-1) weighted by `segmentFreeFlowMinutesOf` (AC-2) to the nearest segment adjacent to any tile with `sp.jobs != null && isOnline(s,b)` as the DESTINATION — a single rule for every trip this increment (no commute-vs-other purpose split, per A-7's still-deferred purpose dimension). Every segment on the winning path accumulates the origin's vehicle-trips into a new `assignedFlowOf(s): Map<segmentId, number>`.
**Check:** a fixture with one origin tile, two possible road paths to the single job tile (a short 2-segment path and a long 4-segment detour of the same class), asserts `assignedFlowOf` loads ONLY the 2 segments on the short path, never the detour's 4.
**False-pass note:** a fixture with only ONE possible path cannot distinguish "shortest-path routing" from "load every reachable segment" — the Tester must use the two-path fixture above.
**Mutant:** replace Dijkstra-by-free-flow-time with "load every segment within the bounding-box radius" (today's inc2 nearest-attribution shape) — reds the two-path fixture by also loading the 4-segment detour.

**AC-4 — BPR delay and v/c per segment.**
New `segmentDelayOf(s): Map<segmentId, {t0: number; t: number; v: number; c: number; vOverC: number}>` computes, per segment carrying `assignedFlowOf` flow > 0, `c = capacityPcuPerLanePerHour (link_capacity.json, per-class override else data/traffic.json default) × lanes (roads.json)`, `v = assignedFlow ÷ data/traffic.json's peak-hour-equivalent operating window` (sourced, not a literal 24 or 1), `t = t0 × (1 + α(v/c)^β)` using `link_capacity.json bprCurve.perClassOverrides` when present for the segment's road class, else `data/traffic.json`'s `bprAlpha`/`bprBeta`. A segment carrying zero assigned flow is OMITTED (honest absence — never a fabricated `vOverC: 0` indistinguishable from "no data").
**Check:** a single segment with a known capacity and a known assigned flow above capacity (`v > c`) asserts `t > t0` by the exact BPR formula computed independently in the test; a second segment at `v = 0` asserts it is ABSENT from the map (not present with `vOverC: 0`).
**False-pass note:** a test using only `v < c` fixtures cannot distinguish "BPR applied" from "BPR always returns `t0`" (since `(v/c)^β` is small but non-zero either way at low v/c) — the Tester must include a `v > c` (overloaded) fixture where the delay multiplier is visually large.
**Mutant:** apply the road-class override alpha/beta but the DEFAULT capacity (or vice versa — apply default alpha/beta but the per-class capacity) — reds against a fixture on the `motorway` class, whose alpha (0.12, `link_capacity.json`) diverges from the network default (0.15, `data/traffic.json`) enough to produce a numerically distinct `t`.

### Commute time and gridlock

**AC-5 — door-to-door commute time distribution (median, p90), exported for later wellbeing coupling (not consumed this increment).**
New `commuteTimeDistributionOf(s): {medianMinutes: number; p90Minutes: number}` — per demand tile with an assigned path (AC-3), door-to-door minutes = `baseAccessMinutes` (`data/traffic.json`) + Σ `segmentDelayOf(s).get(segId).t` for every segment on that tile's assigned path + `baseCommuteMinutes`'s wait/transfer placeholder component (`data/traffic.json`, read not restated) — aggregated across every ROUTED tile (weighted by that tile's `personTrips`, not by tile count, so a dense tile's commute counts more than a sparse one) into the city's median and 90th-percentile minutes. `data/wellbeing.json`'s `commuteWeight`/`commuteThresholdMinutes`/`commuteStressAtThreshold` (cited, not read) remain untouched and unconsumed — inc5's job.
**Check:** a fixture with 9 tiles at known, hand-computed door-to-door minutes (1 through 9) and equal `personTrips` weight asserts `medianMinutes = 5` and `p90Minutes` matches the nearest-rank p90 definition used (cited in the test, not assumed).
**False-pass note:** a fixture where every tile has the SAME commute time cannot distinguish "median/p90 computed correctly" from "any single value returned by accident" — the Tester must use a spread fixture.
**Mutant:** compute `p90Minutes` as the MEAN instead of the 90th percentile — reds the 9-tile fixture (mean of 1..9 = 5 = median, so a mean-substitution mutant produces `p90Minutes === medianMinutes`, distinguishably wrong against the expected ~8.2).

**AC-6 — gridlock detection reuses `CONGESTION_CONSTANTS` by import; segment-granularity, not class-granularity (Decision D3).**
New `gridlockedSegmentsOf(s, prevGridlockTicks): {ticks: Record<segmentId, number>; gridlocked: string[]}` mirrors `advanceCongestionTicks`'s shape (`data.ts:3646`) at SEGMENT scope: a segment's `vOverC` (AC-4) ≥ `CONGESTION_CONSTANTS.CONGESTION_PENALTY_THRESHOLD` (imported, never restated) accrues a tick, hard-resets to 0 the instant it drops below (same reset rule); `gridlocked` lists every segmentId whose ticks reach `CONGESTION_CONSTANTS.CONGESTION_SUSTAINED_TICKS`. This does NOT write to `s.congestionTicksBySpec` (that field stays `congestionLinesOf`'s, class-level, income-coupled, `data.ts:3604`'s existing consumer) — a new, separate state field (e.g. `s.gridlockTicksBySegment`) is this increment's own, read by nothing outside this module and the future overlay/inc4.
**Check:** a segment held at `vOverC = 0.9` (above the imported threshold) for exactly `CONGESTION_SUSTAINED_TICKS` ticks (looked up from the constant, never hand-typed `60`) appears in `gridlocked`; the same segment one tick short does not.
**False-pass note:** a test that hand-types `60` as the sustained-ticks threshold will still pass today but silently stops tracking `CONGESTION_CONSTANTS` if Aaron's balance pass retunes it — the Check must import the constant, not restate its current value.
**Mutant:** omit the reset-to-zero-on-drop rule (let ticks merely stop incrementing instead of resetting) — reds a fixture where `vOverC` dips below threshold for one tick then returns above it before reaching sustained (a compliant implementation never reaches `gridlocked`; the no-reset mutant reaches it one tick early).

### Determinism and scale

**AC-9 — determinism (GR#21) and structural scale bound (BUG-602 class).**
`segmentAdjacencyOf`/`segmentFreeFlowMinutesOf`/`assignedFlowOf`/`segmentDelayOf`/`commuteTimeDistributionOf`/`gridlockedSegmentsOf` are all `memoOnState`, pure functions of `(s, ...)` — no `Date.now`, no `Math.random`, no `localStorage`; byte-identical across repeated calls and a StrictMode double-mount. Dijkstra (AC-3) runs from each ORIGIN tile's nearest segment over a graph with one node per segment (bounded by segment count, not tile count) — a structural pin asserts total Dijkstra relaxations across one tick stay ≤ `originTileCount × segmentCount` (a loose but real, non-wall-clock bound), never re-run to convergence (ONE BPR pass, no equilibrium loop — §2, out-of-scope §6 names the simplification).
**Check:** `grep -n "Date.now\|Math.random\|localStorage" <new module>` (excluding tests) returns no matches; a structural pin fixture counts Dijkstra relaxations via an instrumented test-only wrapper and asserts the bound above; a 10-rerun determinism test (JSON-identical) passes.
**Mutant:** re-run assignment (AC-3) a second time against AC-4's LOADED times (a naive equilibrium step) without a data-sourced, capped iteration count — reds the "ONE pass" structural pin (relaxation count roughly doubles) and is exactly the un-bounded-loop shape GR#21's determinism gate exists to catch if the iteration count were ever allowed to depend on convergence rather than a fixed cap.

## 4. Decisions for Aaron (recommendation given, not blocking)

**D1 — two capacity bases: `ROAD_TIER_CAPACITY`/`LINE_CAPACITY` (game-balance, income-coupled) vs `link_capacity.json` (real-world, BPR/v-c-coupled). Which becomes the eventual SSOT?**
**Recommend: keep both, permanently split by PURPOSE, not by increment** — mirrors A-10's already-accepted "two figures answer two different questions" precedent (`vehicle_classes.json avgOccupancyPersons` vs `modes.json capacityPerUnit`). `ROAD_TIER_CAPACITY` stays the game-economy number `lineUsageOf`/`congestionLinesOf`/commuter-revenue already depend on (retuning it is a balance-pass action with income consequences); `link_capacity.json` stays the real-world number this item's v/c/BPR/gridlock read. Unlike D1 in the inc2 doc (a genuine "will these converge" question with an observation window), this is not expected to converge — a game-balance capacity number is allowed to diverge from a real-world HCM figure permanently, the way seat capacity and realised occupancy do.

**D2 — single destination class (nearest job tile) for ALL trips, no commute/other purpose split.**
**Recommend: accept for inc3, revisit only if A-7's purpose split ever lands.** Routing every person-trip (not just commute legs) to the nearest job tile over-weights work-destined flow on segments serving retail/civic trips in the opposite direction; A-7 already documents the purpose dimension as deferred pending a real consumer, and inc3's assignment is the first plausible consumer — same call inc2's own D1/D2 made (build the simple version now, name the gap, let a real observed divergence justify the complexity later).

**D3 — gridlock threshold reuses `CONGESTION_CONSTANTS` (game-balance 0.75/60 ticks) rather than a new real-world-sourced segment threshhold.**
**Recommend: reuse for inc3, flag for inc4/inc5.** HCM level-of-service breakdown typically sits nearer v/c ≈ 0.85-0.90, not 0.75 — reusing the existing game-balance constant risks a segment-level gridlock flag that fires MORE readily than real-world congestion research would suggest. Reusing it avoids introducing a second, disagreeing threshold concept for "sustained saturation" on day one (GR#3); the cost is a placeholder threshold inherited from an income-tuning decision, not a congestion-research one. Revisit once inc4 (emergency response) or inc5 (unhappiness) needs to calibrate against a real target.

## 5. Assumptions

- **ASM-1501** — `metresPerTile = 10` (AC-2) is derived from the master-plan's stated tile/cell geography (`docs/METROPOLIS-MASTER-v2.1.md:110`), not independently surveyed. **What breaks if wrong:** every free-flow time, BPR delay minute figure, and commute-time minute figure scales linearly with this constant; if the true simulated cell size differs, only the ABSOLUTE minutes are off — the RELATIVE ordering (which path is shorter, which segment is more saturated) is unaffected, since the constant is a uniform multiplier.
- **ASM-1502** — all person-trips (not just commute legs) route to the nearest job-bearing tile as the sole destination class (D2); no shopping/leisure/civic destination modelling. **What breaks if wrong:** non-commute-purpose segments (pure retail/leisure corridors with no adjacent jobs) may show artificially LOW assigned flow relative to a true multi-purpose model, understating their real-world congestion.
- **ASM-1503** — BPR runs ONE pass against free-flow assignment, never re-assigned against loaded times (no equilibrium/iterative loop). **What breaks if wrong:** a route that becomes genuinely worse than an alternate once loaded is never rediscovered — the assignment can under-spread flow onto a real alternate path a driver would actually take once the primary route visibly gridlocks; acceptable for a first increment per the brief's own "single iteration... unless the doc argues for iteration" allowance.
- **ASM-1504** — gridlock reuses the existing game-balance `CONGESTION_CONSTANTS` threshold/sustained-ticks (D3) rather than a real-world-sourced figure. **What breaks if wrong:** the SHAPE of gridlock detection (sustained-ticks-above-threshold) is sound; the specific 0.75/60 numbers may fire earlier or later than real-world HCM breakdown data would justify — a balance-pass concern, not a structural one.

**Assumption codes filed on `FEAT-2326609796`:** ASM-1501, ASM-1502, ASM-1503, ASM-1504 (`node claude-bow.js add assumption`, `webconsole/src/sim/trafficAssignment.ts`, `ui.webconsole`, per the mandate).
