**Status:** draft-ahead — `feat.farmtypes` is now registered (feature, path `internal/engine/farming/`, outbound `engine.world` only, no inbound contract). Host-module `FarmingAPI` calls stay injected seams (ASM-907).
**Package under test:** `internal/engine/farming/` (shared with `engine.farming`/MOD-045; the farm-type catalogue is a file/type set inside the same package, not a fork — ASM-678).

**Balance-number regime (standing rule, same convention as `engine.farming.md` AC-8, `feat.minetypes.md` AC-4):** every per-type figure — footprint (cells), soil-quality band, BDI term, stocking density, and yield/chain-output coefficients — is a **placeholder** in a data file (`data/farmtypes.json`, ASM-676), each carrying a disclosure comment naming it pending Aaron's balance pass. No AC may be satisfied by a junior inventing a final number; every AC touching a per-type figure requires the value to live in the data file and requires tests to check **shape/direction/distinctness** (two types differ; a field is present and typed; data actually loaded), never a specific magnitude. §31's two literal numeric anchors (conventional +30-40% yield, organic 24-month certification lag) belong to `engine.farming.md` AC-8's regime bundle, not to this catalogue's per-type figures.

## The load-bearing rule (this file exists to enforce it)

Each farm **type is a distinct modelled facility** — its own footprint, soil-quality requirement, BDI term, stocking density (where applicable), and chain output — **never one shared row keyed by a type string**. A single `FarmType` struct carrying a `Type string` discriminator with every other field defaulted (or a `map[string]FarmType` where all values share one footprint/soil/BDI/chain and only the key differs) is the anti-pattern this file's AC-2/AC-4 are written to fail. Two same-category types (e.g. arable and orchard) must resolve to **two different parameter sets from data**. Regime (conventional vs organic) is deliberately *orthogonal* to type — it is `engine.farming.md` AC-8's bundle applied to a type, not a separate facility type (ASM-679).

## User stories

- **US-1.** As a farm type (arable, livestock, orchard, market garden, vineyard/winery), I need my own footprint, soil-quality band, BDI term, stocking density, and chain output — not a generic "farm" row with my name stamped on it — so siting me has type-specific ecological and economic consequences (load-bearing rule).
- **US-2.** As `engine.farming`'s regime/BDI surface (MOD-045), I need the farm types resolved from a typed catalogue so a regime command (conventional/organic) and a BDI term attach to a *resolved type*, not a string the BDI engine has to re-interpret.
- **US-3.** As a livestock type, I need my stocking density carried as my own parameter, so dairy vs beef vs pigs vs poultry are mechanically different stocking realities, not one livestock row with a label (the §31 "with stocking density" clause made structural).
- **US-4.** As a chalk-slope crop (vines, orchard), I need a soil-quality/terrain requirement distinct from arable's, so "vines on chalk slopes — real Kent wine" is a placement consequence, not flavour text.
- **US-5.** As the downstream chain (mill/dairy/abattoir/packhouse/winery), I need each farm type to declare its typed chain output, so `engine.farming.md` AC-11's five named chain-output accessors read real per-type handoffs, not a single undifferentiated "farm output".
- **US-6.** As a balance designer (Aaron, GR#15), I need every per-type figure to live in `data/farmtypes.json`, editable without a rebuild.

## Scope

The farm-type catalogue itself: five typed facility entries (arable, livestock, orchard, market garden, vineyard/winery), each resolving to a distinct parameter set — footprint, soil-quality band, BDI term, stocking density (livestock only), and typed chain output. Data file `data/farmtypes.json`; typed resolver in `internal/engine/farming/`. Does **not** include: `engine.farming.md`'s own BDI engine (the five-factor driver decomposition), regime/certification mechanics, `SeasonAPI` harvest-calendar consumption, pollinator/watercourse feedback, or the compost-input consumption (MOD-045); `engine.world`'s soil/geology computation (consumed, not authored); the build-catalogue entries for these structures (`data.catalogue`/`data/buildings.json` — ASM-693).

## Acceptance criteria

### Functional — the typed catalogue surface

- **AC-1 (GR#20; typed resolve surface, no shared row).** A farm-type catalogue exists on `internal/engine/farming` exposing a typed resolve surface (e.g. `FarmTypeResolve(typeKey) (FarmTypeParams, error)` or equivalent) returning a **distinct parameter struct** per type — footprint, soil-quality band, BDI term, stocking density, and chain output are all named, typed fields, not a `Type string` field whose presence substitutes for the parameters. Check: `go doc ./internal/engine/farming` shows a `FarmType`/`FarmTypeParams` type with named footprint/soil/BDI/stocking/chain fields; `grep -rn "Type string" internal/engine/farming/farmtype*.go` (excluding `_test.go`) finds no bare type-string discriminator on the parameter struct.

- **AC-2 (load-bearing — two types resolve to two different parameter sets from data).** Two same-category types — arable and orchard — resolve to **two different parameter sets**, and the distinguishing fields are each actually populated AND differ: footprint, soil-quality band, BDI term, and chain output are pairwise non-equal. A companion isolation assertion proves the difference is data-sourced: mutating one type's soil-quality band in the loaded `data/farmtypes.json` fixture changes only that type's resolved band (the other type byte-identical before and after). Check: `grep -rn "func Test.*[Dd]istinct.*[Pp]aram\|func Test.*[Tt]woTypesDiffer\|func Test.*[Aa]rableVsOrchard" internal/engine/farming/farmtype*_test.go`; `grep -rn "func Test.*[Ii]solat.*[Ff]armtype\|func Test.*[Ss]ingleTypePerturb" internal/engine/farming/farmtype*_test.go`. **False-pass risk:** a `map[string]FarmTypeParams` where every entry shares one default footprint/soil/BDI/chain and only the map key differs would pass a naive "the catalogue has N farm-type entries" grep while violating the distinct-facility premise — the check requires the resolved *parameters* to differ between two named types.

- **AC-3 (§31 taxonomy completeness; GR#15 data-derived count).** All five §31 facility categories (arable, livestock, orchard, market garden, vineyard/winery) are present as distinct entries, and the named §31 crops/livestock resolve as variants within a category (wheat/barley/rapeseed/potatoes → arable; dairy/beef/sheep/pigs/poultry → livestock; apples/cherries/soft fruit → orchard; field veg/poly-tunnel salads/hops → market garden; vines → vineyard/winery) — per ASM-677, a named crop is a variant *within* a category, not its own top-level type. The expected type set is derived from a data/manifest source, never a hardcoded five-element literal in the test (GR#15). Check: `grep -rn "func Test.*[Tt]axonomy\|func Test.*[Ff]iveTypes" internal/engine/farming/farmtype*_test.go`; `grep -n "arable\|livestock\|orchard\|market\|vineyard" data/farmtypes.json` matches all five.

### Functional — per-type parameters

- **AC-4 (GR#15; every figure data-driven, no hardcoded literals).** Every per-type figure (footprint, soil-quality band, BDI term, stocking density, yield/chain coefficient) loads from `data/farmtypes.json`, none hardcoded as a Go numeric literal, and the data is *actually read* — a test mutates a value in the data file between two runs and asserts the resolved parameter reflects the change. Check: `grep -rn "0\.[0-9]\+\|[0-9]\{2,\}" internal/engine/farming/farmtype*.go` (excluding `_test.go`, array indices, enum ordinals) shows no bare balance-shaped numeric literals; `grep -rn "func Test.*[Dd]ataDriven.*[Ff]armtype\|func Test.*[Rr]eload.*[Ff]armtype" internal/engine/farming/farmtype*_test.go`. **Balance-regime note:** the magnitudes are placeholders with disclosure comments (AC-12); this AC checks *data-sourced and consumed*, not magnitude.

- **AC-5 (per-type soil-quality band + BDI term — the ecological consequence per type).** Each farm type declares (a) a soil-quality requirement band (and, where §31 names it, a terrain/slope preference — vines/orchard on chalk slopes) and (b) a BDI contribution term (the per-type input into `engine.farming.md` AC-2's five-factor regional BDI, not a re-derivation of that engine). The arable type resolves to a chalk-compatible soil band and a low/negative BDI term under conventional intensity; orchard/vineyard resolve to a chalk-slope preference and a higher BDI term (the §31 "chalk grassland is a BDI treasure" direction). Check: `go doc ./internal/engine/farming` shows a soil-band and BDI-term accessor on the resolved params; a passing test asserts arable and vineyard resolve to different soil bands and different BDI terms, with vineyard's BDI term directionally higher (`grep -rn "func Test.*[Ss]oilBand\|func Test.*[Bb]DITerm\|func Test.*[Cc]halkSlope" internal/engine/farming/farmtype*_test.go`). **False-pass risk:** a single "environmental score" field that folds soil and BDI together would let a chalk-loving vine sit on heavy clay unnoticed — the check requires the soil band and BDI term to be distinct fields, because `engine.farming.md` AC-2/AC-3 attribute BDI to five *independent* factors and this catalogue is one source, not the sum.

- **AC-6 (§31 "with stocking density" — livestock's own parameter, distinct per variant).** The livestock type carries a stocking-density parameter (head per cell, or equivalent), and the per-variant values (dairy, beef, sheep, pigs, poultry) are distinct — not one livestock row with a density that never varies by animal. Check: `go doc ./internal/engine/farming` shows a stocking-density accessor on the livestock params; a passing test asserts the dairy and pigs variants resolve to different stocking densities from data, and that the arable/orchard types do *not* carry a stocking-density field at all (the field is livestock-typed, not a shared zero on every type) (`grep -rn "func Test.*[Ss]tockingDensity\|func Test.*[Ll]ivestockVariants" internal/engine/farming/farmtype*_test.go`). **False-pass risk:** a single stocking density on a generic "livestock" entry would satisfy "stocking density exists" while §31's "dairy, beef, sheep, pigs, poultry, with stocking density" (per-animal reality) is unmet — the check requires the variants to differ.

- **AC-7 (§31 chains — typed chain output per type, matching `engine.farming.md` AC-11).** Each farm type declares its downstream chain output as a typed handoff (commodity + destination chain), not a single undifferentiated "farm output": arable → grain→mill, livestock → livestock→abattoir, dairy → milk→dairy plant, orchard/soft fruit → fruit→packhouse, vines → grapes→winery. Check: `go doc ./internal/engine/farming` shows a chain-output accessor on the resolved params; a passing test asserts arable and livestock resolve to different chain-output commodities/destinations, and that at least five distinct chain destinations (mill, dairy, abattoir, packhouse, winery) are reachable across the five types (`grep -rn "func Test.*[Cc]hainOutput\|func Test.*[Ff]iveChains" internal/engine/farming/farmtype*_test.go`). **False-pass risk:** a single "output tonnes" field with no chain destination would pass a "farms produce output" read while `engine.farming.md` AC-11's "five named chain-output accessors" has nothing real to read — the check requires the destination chain to be part of the type's parameter set.

### Error handling

- **AC-8 (GR#7; unknown type / malformed data — no silent default).** Resolving an unknown farm-type key, or loading a `data/farmtypes.json` that fails schema validation (a type missing its footprint or chain output, a negative stocking density, an unknown chain-destination enum value, a field of the wrong JSON type — GR#16), produces a registry-sourced error (a new `MET-`-range code claimed at build time) — never a panic, never a silent default-substituted parameter set. Check: `grep -n "MET-" internal/engine/farming/farmtype*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownFarmType\|func Test.*[Mm]alformedFarmtypes\|func Test.*[Ww]rongTypeFarmtypes" internal/engine/farming/farmtype*_test.go`) — **GR#7 assertion, stated explicitly:** the test asserts the returned error's registry code matches the claimed `MET-` code AND that no partially-loaded or default-substituted catalogue was produced, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-9 (GR#21).** Loading and resolving the farm-type catalogue is a deterministic function of `(data file, type key)` — loading the same `data/farmtypes.json` twice produces byte-identical resolved parameter sets, and resolution never depends on map-iteration order. Check: `grep -rn "func Test.*[Dd]eterminis.*[Ff]armtype" internal/engine/farming/farmtype*_test.go`; `grep -rn "time.Now\|time.Since" internal/engine/farming/farmtype*.go` (excluding `_test.go`) returns no matches.

- **AC-10 (SG-7 scoped; GR#21).** `go test ./internal/engine/farming/... -race -count=1 -run FarmType` passes with no data race (scoped via `-run`, since the shared package also carries `engine.farming.md` AC-16's race suite); `grep -n "go func()" internal/engine/farming/farmtype*_test.go` finds at least one concurrency test.

## Out of scope

No BDI/regime/certification AC belongs in this file.
- `engine.world.md`'s soil/geology/slope computation — consumed via AC-5's soil-band requirement, not reimplemented.
- The downstream chains' own business logic (mill/dairy/abattoir/packhouse/winery mechanics) — this item only declares the typed handoff (AC-7); the chains' throughput/pricing is `engine.freight`/`engine.market`'s.
- `data.catalogue`/`data/buildings.json` build-catalogue entries (unlock/cost/capacity) for the same structures — FEAT-010's; this file's types are the simulation parameters, and the build entry must reference a type key, never duplicate the numbers (ASM-693).
- Exact per-type footprint/soil-band/BDI-term/stocking-density/yield figures — balance data pending Aaron's balance pass.
