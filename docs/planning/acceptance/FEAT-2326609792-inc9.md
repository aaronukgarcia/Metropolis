## 1. Why this item exists

Aaron's epic brief (verbatim): "reward SAFE roads, reward INTEGRATED transport." `rewards.json` (inc0) already defines both scoring formulas as data; nothing consumes them yet. This increment wires two read-out scores (`safeRoadScoreOf` per segment / city-wide, `integratedTransportScoreOf` city-wide) and couples them to wellbeing (new parts, same idiom as inc5) and, where the attract model structurally permits it, to attractiveness — never inventing a mechanism the model doesn't have (GR#25).

## 2. The design in one paragraph

**Safe-road score (AC-1..3).** Per road segment carrying flow (`segmentDelayOf(s)`'s own domain — a zero-flow segment has no vehicles to be safe or unsafe FOR, honest absence mirrored from inc3 AC-4): `roadClassBaseSafety` (by `roadClassIdOfSegment`), `designSpeedPenalty` (`speedKmh = roads.json speedLimit(mph) * traffic.json metresPerMile / 1000` — no hand-typed mph→km/h constant), and `congestionSafetyInteraction` (piecewise-linear off `segmentDelayOf(seg).vOverC`, the **instantaneous** v/c — inc5's sustained-tick tracking is uncommitted at this HEAD and this item does not create a cross-increment dependency on unlanded state, ASM-1526) are always available. `junctionTypeSafety` is available ONLY for a segment that contains a junction tile: reverse-walk `lineSegmentIndexOf(s).tileToSegment` for every online `rd_junction`/`rd_roundabout`/`rd_mwyjunction` building's tile key, map spec id → `rewards.json` junction key (`rd_junction→simple_priority`, `rd_roundabout→roundabout`, `rd_mwyjunction→grade_separated`; **no `signalised` spec exists in this game today — that key is never assigned, ASM-1527, honest scope-down not an invented default**). A segment WITHOUT a junction tile drops the `junctionTypeSafety` term and **renormalizes** the remaining three weights proportionally (`0.35+0.20+0.20=0.75`, each divided by `0.75`) — a mechanical rescale of `rewards.json`'s own weights, never a hand-invented substitute value. City-wide `safeRoadScoreOf` is the **flow-weighted mean** (weight = `assignedFlowOf`) over every scored segment, mirroring the flow-weighted idiom `commuteTimeDistributionOf` already uses (GR#3 shape, not the same function).

**Integrated-transport score (AC-4).** `stationLinks(s).connectedIds` gives binary station↔road adjacency only — no per-station mode count and no 400 m population-catchment exist anywhere in the webconsole today (grep-verified). Rather than invent a radius-based population catchment (GR#25), `interchangeAdjacency` is honestly scoped down to: **share of ONLINE, road-connected stations that are ALSO adjacent to a `bus_lane_variant`/`tram_track_variant`-class road segment** (a second, distinct mode alongside the station's own rail/hs1 mode) — reusing `stationLinks`'s existing adjacency walk plus one `tileToSegment`/`roadClassIdOfSegment` lookup per connected station (GR#3, no second building-array walk). `modeShareBalance` follows `rewards.json`'s OWN formula exactly (Shannon-entropy evenness over the realised city-wide mode-share vector, normalised by `ln(11)`) — sourced from inc2's `demandForecastOf` aggregate `tripsByMode` totals (the REALISED split, which can diverge from the raw ladder `modeShare` table when demand goes unattributed/unrouted, per `traffic.json`'s own `maxAttributionRadiusTiles` mechanism) — **not** the "closeness to the ladder's target split" framing sometimes used informally for this feature; `rewards.json` is the registered SSOT and this doc follows it (D1 flags the discrepancy for Aaron).

**Coupling.** Two new `{label, value}` wellbeing parts, same `part()`/`blend()` idiom as every existing row: `'Safe roads'` = `part(safeRoadScoreOf(s))`, `'Integrated transport'` = `part(integratedTransportScoreOf(s))` — both already `[0,1]`, `1` = best, positive-signed by construction (no inversion, unlike coverage-derived parts elsewhere). Attract: `attractivenessOf` gains one new bounded multiplicative factor, `integrationMultiplier = 0.9 + 0.2 * integratedTransportScoreOf(s)` (range `[0.9, 1.1]`, the SAME small-span-bounded shape `jobsMultiplier` already uses, `engine.ts:626`) — deliberately NOT wired from `safeRoadScoreOf` (D2: safety feeds wellbeing only, avoiding double-counting one signal into two different downstream systems the way inc5's D1 explicitly reasoned about `congestionFactorOf` vs commute-time).

## 3. Acceptance Criteria

**AC-1 — `safeRoadScoreOf(s): Map<segmentId, number>` — per-segment safety score, junction-aware, weight-renormalized when no junction tile.**
New export. For each segment in `segmentDelayOf(s)`'s domain: `roadClassBaseSafety`/`designSpeedPenalty`/`congestionSafetyInteraction` always computed (§2); `junctionTypeSafety` computed only when the segment owns a junction tile (§2's reverse-walk). Formula per `rewards.json`'s own weights, renormalized to the present component set.
**Check:** a fixture with a segment carrying a `rd_roundabout` tile vs an identical segment (same class, same speed, same v/c) with NO junction tile asserts DIFFERENT scores, and the no-junction segment's score equals the SAME formula computed by hand with the three-weight renormalization (to 1e-6) — not the four-weight formula missing a term (which would silently under-weight, not renormalize).
**False-pass note:** a fixture that only checks "junction segments score higher than non-junction" cannot distinguish "renormalized" from "junction term silently zeroed with the ORIGINAL 0.25 weight still in the denominator" (both directions agree, magnitudes differ) — the Tester must assert the exact renormalized value.
**Mutant:** drop the `junctionTypeSafety` term for a no-junction segment WITHOUT renormalizing (denominator stays 1.0, weights stay 0.35/0.25/0.20/0.20 minus the missing term) — reds the exact-value check.

**AC-2 — junction classification is spec-id-driven; `signalised` is never assigned.**
Junction spec→`rewards.json` key mapping reads `SPECS[...].id`, never a hand-typed coordinate list; `signalised` never appears in any test's expected output (no such spec exists — ASM-1527).
**Check:** a fixture with one `rd_junction`, one `rd_roundabout`, one `rd_mwyjunction`, each on a distinct segment, asserts each segment's `junctionTypeSafety` matches `rewards.json`'s `simple_priority`/`roundabout`/`grade_separated` values respectively (not `signalised`, which must never appear).
**Mutant:** hard-code `rd_junction→signalised` (a plausible-looking but wrong mapping, since a plain crossroads is priority-controlled, not light-controlled) — reds the exact-value check.

**AC-3 — `safeRoadScoreOf` city-wide roll-up is flow-weighted, not a plain segment average.**
New `citySafeRoadScoreOf(s): number` = Σ(`safeRoadScoreOf` × `assignedFlowOf`) ÷ Σ`assignedFlowOf` over scored segments; `0` scored segments (no flow anywhere) ⇒ neutral `1.0` (nothing unsafe exists yet), never `NaN`.
**Check:** two segments, scores `0.9` and `0.3`, flows `100` and `900` — asserts the roll-up equals the exact weighted value (`0.36`), not the plain average (`0.6`).
**False-pass note:** an equal-flow fixture cannot distinguish weighted from plain averaging — the Tester must use unequal flows, per the exact-value check above.
**Mutant:** unweighted `reduce`/`length` average — reds the unequal-flow check.

**AC-4 — `integratedTransportScoreOf(s): number` — honestly-scoped interchange share + Shannon-entropy mode balance.**
`interchangeAdjacency` = (online, road-connected stations also adjacent to a `bus_lane_variant`/`tram_track_variant` segment) ÷ (online, road-connected stations); `0` connected stations ⇒ `0` (no interchange possible), never `NaN`. `modeShareBalance` = `-Σ(share_i·ln(share_i))/ln(11)` over the REALISED city-wide `tripsByMode` vector from `demandForecastOf` (a mode with `share_i=0` contributes `0`, not `NaN`/`-Infinity`, per the standard entropy convention). Final score = `0.5*interchangeAdjacency + 0.5*modeShareBalance`, bounded `[0,1]`.
**Check:** a fixture with 2 connected stations, one adjacent to a `bus_lane_variant` segment and one not, asserts `interchangeAdjacency = 0.5` exactly; a fixture with a perfectly even 11-mode split asserts `modeShareBalance = 1.0` (to 1e-6); a single-mode-monoculture fixture asserts `modeShareBalance = 0.0`.
**False-pass note:** a fixture using only the monoculture case cannot prove the entropy NORMALISATION (`/ln(11)`) is present — a mutant that omits the `/ln(11)` divisor still reads `0` at monoculture (entropy is `0` either way) but disagrees at the even-split case (raw entropy `ln(11)` vs normalised `1.0`) — the Tester must run BOTH fixtures.
**Mutant:** omit the `/ln(11)` normalisation — reds the even-split fixture (`modeShareBalance = ln(11) ≈ 2.4`, not `1.0`, breaking the `[0,1]` bound AC-8 also pins).

**AC-5 — two new wellbeing parts, positive-signed, same idiom as every existing row.**
`buildServiceWellbeingParts` gains `{label:'Safe roads', value: part(citySafeRoadScoreOf(s))}` and `{label:'Integrated transport', value: part(integratedTransportScoreOf(s))}`.
**Check:** a monotonicity fixture at `citySafeRoadScoreOf ∈ {0, 0.5, 1}` (forced via a stub score map) asserts STRICTLY ascending `'Safe roads'` part values; the same shape for `'Integrated transport'`. A neutral-point fixture (no change to either score) diffs the FULL parts array before/after and asserts every pre-existing label's value is byte-identical (mirrors inc5 AC-6's neutral-point diff).
**False-pass note:** a non-strict (`>=`) monotonicity assertion would pass on a mutant that flattens the curve to a constant — must be strict across 3 distinct points, per the verification standard.
**Mutant:** invert either part (`part(1 - score)`) — reds its own monotonicity fixture (descending instead of ascending) and would make "0 safety" wellbeing-neutral instead of worst, contradicting Aaron's "reward safe roads" framing.

**AC-6 — attract: one small, bounded `integrationMultiplier`; safety is NOT double-wired into attract.**
`attractivenessOf` gains `integrationMultiplier = clampN(0.9 + 0.2*integratedTransportScoreOf(s), 0.9, 1.1)`, multiplied into the existing return expression alongside `jobsMultiplier`. `safeRoadScoreOf`/`citySafeRoadScoreOf` are NEVER referenced inside `engine.ts`'s `attractivenessOf` (D2 — safety feeds wellbeing only, avoiding the same double-count risk inc5's D1 flagged for congestion).
**Check:** a fixture at `integratedTransportScoreOf = 0` vs `=1` (all other attract inputs held fixed) asserts the ratio between the two `attractivenessOf` outputs equals exactly `0.9/1.1` (the multiplier's own bound ratio), not merely "different"; `grep -n "safeRoadScoreOf\|citySafeRoadScoreOf" webconsole/src/sim/engine.ts` matching lines are confined to the wellbeing-parts block, never inside `attractivenessOf`'s body.
**False-pass note:** a "some difference exists" assertion cannot prove the bound is exactly `[0.9,1.1]` (a mutant with a wider, unbounded span would still pass) — the Tester must assert the exact ratio.
**Mutant:** widen the multiplier span to `[0.5, 1.5]` — reds the exact-ratio check.

**AC-7 — determinism, data-sourced, registry errors, structural bound (mirrors inc3 AC-8 / inc4 AC-8 shape).**
No hand-typed safety weight, junction-key mapping value, entropy divisor, or multiplier bound anywhere but `rewards.json` and the one `ln(11)`/`clampN` shape stated above (the mode count `11` itself is `rewards.json`'s own documented cardinality, cited not restated — a data file listing fewer/more modes is a registry error, `MET-Vxxx`, claimed via `add-error.js claim-range` at build time). All exports `memoOnState`; no `Date.now`/`Math.random`/`localStorage`; byte-identical across repeated calls and a StrictMode double-mount. Cost bound: one O(segments) pass for `safeRoadScoreOf`, one O(connected stations) pass for `interchangeAdjacency`, one O(1) pass over the 11-entry mode vector for `modeShareBalance` — never O(citizens).
**Check:** `grep -n "Date.now\|Math.random\|localStorage" webconsole/src/sim/trafficRewards.ts` returns no matches; a 10-rerun determinism test (JSON-identical); a malformed `rewards.json` (missing `safeRoadScore.components`) fixture asserts the registry error throws fail-closed, not a silent default.
**Mutant:** hand-type `11` instead of reading the mode vector's own length — reds the malformed-fixture check when a future `rewards.json` mode-count change silently diverges from the hard-coded literal.

**AC-8 — no money; no wear/turnout coupling this increment.**
No file this increment touches writes to `s.budget`/`s.treasury`/any `*Pounds`/`*Revenue`/`*Cost` field. `road_wear.json`/`FEAT-2326609800` (inc7, open, not landed) is NOT read — the `congestionSafetyInteraction` term uses ONLY `segmentDelayOf(seg).vOverC`, never a wear/condition field that does not exist in `SimState` yet.
**Check:** `grep -n "budget\|treasury\|Pounds\|Revenue\|Cost\|roadWear\|condition" webconsole/src/sim/trafficRewards.ts` returns no matches.
**Mutant:** read a speculative `seg.condition` field — caught the moment such a read appears (no such field exists on `LineSegment`, would be a type error / a silently-`undefined`-tolerant read).

## 4. Decisions for Aaron (recommendation given, not blocking)

**D1 — `modeShareBalance` follows `rewards.json`'s Shannon-entropy-evenness formula, not a "closeness to the ladder's target split" measure.** Both readings of "reward integrated transport" are plausible; `rewards.json` (the registered SSOT, inc0) already commits to entropy-evenness with a stated rationale (a one-mode-monoculture city should score low even at high aggregate transit share). **Recommend: keep entropy as written**; if Aaron wants a distance-to-target measure instead, that is a `rewards.json` data change, not a code change here (GR#15).

**D2 — safety feeds wellbeing only; integration feeds BOTH wellbeing and attract.** **Recommend: accept as designed.** Wiring `safeRoadScoreOf` into attract too would double-count one signal into two systems the same way inc5's D1 explicitly avoided for congestion; integration genuinely IS an attract-relevant, distinct signal (a well-connected city is more attractive to move into) with no existing attract term already covering it.

**D3 — `integrationMultiplier` lands in `attractivenessOf` THIS increment, not deferred to inc10.** `attractivenessOf` has had two rounds of volatility this epoch (F2/F4, `engine.ts:294-348,552-580`) from OTHER terms; this is a small, independently bounded `[0.9,1.1]` multiplicative factor with no cross-term interaction, the same shape `jobsMultiplier` already proved safe to add. **Recommend: land now** — deferring a self-contained, bounded factor to inc10 (a UI increment) gains nothing and stretches the epic's own "reward integrated transport" line item across two increments for no reason.
