## 1. Why this item exists

Aaron's epic brief (verbatim): "reward SAFE roads, reward INTEGRATED transport." `rewards.json` (inc0) already defines both scoring formulas as data; nothing consumes them yet. This increment wires two read-out scores (`safeRoadScoreOf` per segment / city-wide, `integratedTransportScoreOf` city-wide) and couples them to wellbeing (new parts, same idiom as inc5) and, where the attract model structurally permits it, to attractiveness — never inventing a mechanism the model doesn't have (GR#25).

## 2. The design in one paragraph

**Safe-road score (AC-1..3).** Per road segment carrying flow (`segmentDelayOf(s)`'s own domain — a zero-flow segment has no vehicles to be safe or unsafe FOR, honest absence mirrored from inc3 AC-4): `roadClassBaseSafety` (by `roadClassIdOfSegment`), `designSpeedPenalty` (`speedKmh = roads.json speedLimit(mph) * traffic.json metresPerMile / 1000` — no hand-typed mph→km/h constant), and `congestionSafetyInteraction` (piecewise-linear off `segmentDelayOf(seg).vOverC`, the **instantaneous** v/c — inc5's sustained-tick tracking is uncommitted at this HEAD and this item does not create a cross-increment dependency on unlanded state, ASM-1526) are always available. `junctionTypeSafety` is available ONLY for a segment that contains a junction tile: reverse-walk `lineSegmentIndexOf(s).tileToSegment` for every online `rd_junction`/`rd_roundabout`/`rd_mwyjunction` building's tile key, map spec id → `rewards.json` junction key (`rd_junction→simple_priority`, `rd_roundabout→roundabout`, `rd_mwyjunction→grade_separated`; **no `signalised` spec exists in this game today — that key is never assigned, ASM-1527, honest scope-down not an invented default**). A segment WITHOUT a junction tile drops the `junctionTypeSafety` term and **renormalizes** the remaining three weights proportionally (`0.35+0.20+0.20=0.75`, each divided by `0.75`) — a mechanical rescale of `rewards.json`'s own weights, never a hand-invented substitute value. City-wide `safeRoadScoreOf` is the **flow-weighted mean** (weight = `assignedFlowOf`) over every scored segment, mirroring the flow-weighted idiom `commuteTimeDistributionOf` already uses (GR#3 shape, not the same function).

**Integrated-transport score (AC-4).** `stationLinks(s).connectedIds` gives binary station↔road adjacency only — no per-station mode count and no 400 m population-catchment exist anywhere in the webconsole today (grep-verified). Rather than invent a radius-based population catchment (GR#25), `interchangeAdjacency` is honestly scoped down to: **share of ONLINE, road-connected stations that are ALSO adjacent to a `bus_lane_variant`/`tram_track_variant`-class road segment** (a second, distinct mode alongside the station's own rail/hs1 mode) — reusing `stationLinks`'s existing adjacency walk plus one `tileToSegment`/`roadClassIdOfSegment` lookup per connected station (GR#3, no second building-array walk). **HONEST GAP, permanently inert today (BUG-927, confirmed at round 1):** `bus_lane_variant`/`tram_track_variant` are real `roads.json` classes but are reachable ONLY via `roadClassIdOfSegment`'s fixed 5-entry `ROAD_CLASS_ID_OF_TIER` table (tiers 1..5 → `residential_street`/`avenue_2_plus_2`/`two_lane`/`dual_carriageway`/`motorway`), which never produces either id — no spec anywhere in `data.ts` references them. `interchangeAdjacency` therefore returns `0` for every real, buildable city today; the classifier and the ratio arithmetic are proven correct in isolation, but the true-positive numerator path cannot be exercised end-to-end until such a spec exists. Do not invent a catchment or a substitute classifier to make this half "look" live — the gap stays documented, not papered over.
`modeShareBalance` follows `rewards.json`'s OWN formula (Shannon-entropy evenness over the mode-share vector, normalised by `ln(N)` where `N` is the vector's own length, currently 11). **BUG-938 lead ruling (r3, supersedes BUG-927's r2 "realised, trip-weighted per-tile" correction below, kept here for history):** r2 (BUG-927's fix) replaced the population-keyed `modeShareOf(ladderPointOf(s))` row with a per-tile mechanism — for every tile in `demandForecastOf(s)`, that tile's OWN local ladder point (selected by `ladderAt(scaleLadder, clamp(residentsActual+workersActual, floorRungPopulation, ceilingRungPopulation))`) gave that tile's own `modeShareOf` split, `personTrips`-weighted and summed to 1. Round 2 MEASURED the consequence (BUG-938): real per-tile occupancy tops out around 76,000 (the largest spec) against a scale ladder running to 98,000,000, so only the BOTTOM ~5 of 18 rungs are ever reachable per-tile — every built city, at every population, collapsed onto the same narrow car-heavy band (0.52–0.62), while a genuinely BARE city (which fell back to the population row) scored HIGHER (0.70–0.84) at every population tested. That is a hidden **population bonus for not building**, the exact inversion of "reward integrated transport" — not merely direction/magnitude bugs in the per-tile mechanism (BUG-937 found those too), but a structurally wrong basis. **The r3 ruling reverts to the honest, POPULATION-KEYED city row: `modeShareBalance = shannonModeBalanceOf(modeShareOf(ladderPointOf(s)))`, unconditionally** — the webconsole has no per-tile (land-use/access-keyed) mode-split model, so this is disclosed as population-keyed TODAY, not build-sensitive, rather than dressed up in a per-tile computation that only LOOKED build-sensitive. `FEAT-2326609804` tracks the real prerequisite (a per-tile mode-split model in inc2's own demand code); inc9's integration coupling (below) returns once that lands.

**Coupling (amended, BUG-938 r3 ruling).** ONE new `{label, value}` wellbeing part, same `part()`/`blend()` idiom as every existing row: `'Safe roads'` = `part(safeRoadScoreOf(s))` — `[0,1]`, `1` = best, positive-signed by construction (no inversion, unlike coverage-derived parts elsewhere). **`'Integrated transport'` is NOT a wellbeing part this increment**, and `attractivenessOf` gains **no new multiplicative factor**: `integratedTransportScoreOf` stays an EXPORTED DIAGNOSTIC (still computed each cadence tick, still carried on `s.trafficSnapshot.integratedTransportScore` for the read-out) but nothing in `engine.ts` consumes it — wiring a population-keyed score into either wellbeing or attract would reward city size, not integrated transport, exactly the hidden-bonus risk the ruling rejects. `attractivenessOf` is therefore byte-identical to its pre-inc9 form. `safeRoadScoreOf` stays NOT wired into `attractivenessOf` either (D2, unchanged from the original design: safety feeds wellbeing only, avoiding double-counting one signal into two different downstream systems the way inc5's D1 explicitly reasoned about `congestionFactorOf` vs commute-time).

## 3. Acceptance Criteria

**AC-1 — `safeRoadScoreOf(s): Map<segmentId, number>` — per-segment safety score, junction-aware, weight-renormalized when no junction tile.**
New export. For each segment in `segmentDelayOf(s)`'s domain: `roadClassBaseSafety`/`designSpeedPenalty`/`congestionSafetyInteraction` always computed (§2); `junctionTypeSafety` computed only when the segment owns a junction tile (§2's reverse-walk). Formula per `rewards.json`'s own weights, renormalized to the present component set.
**Check:** a fixture with a segment carrying a `rd_roundabout` tile vs an identical segment (same class, same speed, same v/c) with NO junction tile asserts DIFFERENT scores, and the no-junction segment's score equals the SAME formula computed by hand with the three-weight renormalization (to 1e-6) — not the four-weight formula missing a term (which would silently under-weight, not renormalize).
**False-pass note:** a fixture that only checks "junction segments score higher than non-junction" cannot distinguish "renormalized" from "junction term silently zeroed with the ORIGINAL 0.25 weight still in the denominator" (both directions agree, magnitudes differ) — the Tester must assert the exact renormalized value.
**Mutant:** drop the `junctionTypeSafety` term for a no-junction segment WITHOUT renormalizing (denominator stays 1.0, weights stay 0.35/0.25/0.20/0.20 minus the missing term) — reds the exact-value check.

**AC-2 — junction classification is spec-id-driven; `signalised` is never assigned.**
Junction spec→`rewards.json` key mapping reads `SPECS[...].id`, never a hand-typed coordinate list; `signalised` never appears in any test's expected output (no such spec exists — ASM-1527).
**Check:** a fixture with one `rd_junction`, one `rd_roundabout`, one `rd_mwyjunction`, each on a distinct segment, asserts each segment's `junctionTypeSafety` matches `rewards.json`'s `simple_priority`/`roundabout`/`grade_separated` values respectively (not `signalised`, which must never appear).
**Mutant:** hard-code `rd_junction→signalised` (a plausible-looking but wrong mapping, since a plain crossroads is priority-controlled, not light-controlled) — reds the exact-value check.

**AC-3 — `safeRoadScoreOf` city-wide roll-up is flow-weighted, not a plain segment average.**
New `citySafeRoadScoreOf(s): number` = Σ(`safeRoadScoreOf` × `assignedFlowOf`) ÷ Σ`assignedFlowOf` over scored segments; `0` scored segments (no flow anywhere) ⇒ neutral `1.0` (nothing unsafe exists yet), never `NaN`.
**Check:** two segments, scores `0.9` and `0.3`, flows `100` and `900` — asserts the roll-up equals the exact weighted value (`0.36`), not the plain average (`0.6`).
**False-pass note:** an equal-flow fixture cannot distinguish weighted from plain averaging — the Tester must use unequal flows, per the exact-value check above.
**Mutant:** unweighted `reduce`/`length` average — reds the unequal-flow check.

**AC-4 (amended, BUG-938 r3 ruling) — `integratedTransportScoreOf(s): number` — honestly-scoped interchange share (permanently inert today, BUG-927) + Shannon-entropy mode balance over the CITY-WIDE, POPULATION-KEYED vector. EXPORTED DIAGNOSTIC ONLY — not wired to wellbeing or attract (see AC-5/AC-6).**
`interchangeAdjacency` = (online, road-connected stations also adjacent to a `bus_lane_variant`/`tram_track_variant` segment) ÷ (online, road-connected stations); `0` connected stations ⇒ `0` (no interchange possible), never `NaN`; **always `0` today regardless of city shape — see the honest-gap paragraph above, do not treat a `0` result as a bug.** `modeShareBalance` = `-Σ(share_i·ln(share_i))/ln(N)` (the exported `shannonModeBalanceOf` kernel, `N` = the real vector's own length, currently 11) applied to `modeShareOf(ladderPointOf(s))`, the city-wide, population-keyed row — **unconditionally, per the r3 ruling reverting BUG-927's r2 per-tile mechanism** (BUG-938: real per-tile occupancy scale made every built city score LOWER than a bare map, 13/18 ladder rungs unreachable — a hidden population bonus, not a build reward). Final score = `0.5*interchangeAdjacency + 0.5*modeShareBalance`, bounded `[0,1]`.
**Check:** a fixture with 2 connected stations, one adjacent to a `bus_lane_variant` segment and one not, asserts `interchangeAdjacency = 0.5` exactly (classifier-only proof, since no real spec resolves to that class); `shannonModeBalanceOf` asserted directly against HAND-COMPUTED Shannon values for a synthetic 2-mode vector and an 11-mode even vector (kills the Simpson-kernel mutant, BUG-925); `modeShareBalanceOf` is asserted (BUG-937) against an INDEPENDENT recomputation of the city-level basis to `1e-12`; two same-population fixtures with different land-use mix (all `res_hut` vs mixed `res_tower_nyc`+offices), and a bare city vs the same-population city with roads+road-connected stations, all assert the SAME `modeShareBalanceOf`/`integratedTransportScoreOf` value (BUG-938 — the r1 "inertness" finding is now the documented, intended behaviour); two DIFFERENT populations assert DIFFERENT values (the population dependency itself must remain real).
**False-pass note:** a fixture using only the monoculture case cannot prove the entropy NORMALISATION (`/ln(11)`) is present — a mutant that omits the `/ln(11)` divisor still reads `0` at monoculture (entropy is `0` either way) but disagrees at the even-split case (raw entropy `ln(11)` vs normalised `1.0`) — the Tester must run BOTH fixtures.
**Mutant:** omit the `/ln(11)` normalisation — reds the even-split fixture (`modeShareBalance = ln(11) ≈ 2.4`, not `1.0`, breaking the `[0,1]` bound AC-8 also pins). A re-introduced per-tile mechanism of any shape reds the BUG-938 equal-population/equal-value pins the moment it depends on WHAT is built.

**AC-5 (amended, BUG-938 r3 ruling) — ONE new wellbeing part, positive-signed, same idiom as every existing row.**
`buildServiceWellbeingParts` gains `{label:'Safe roads', value: part(citySafeRoadScoreOf(s))}` only. **`'Integrated transport'` is NOT added** — the score has no build-sensitive input today (AC-4), so a wellbeing row built from it would reward population, not anything the player does.
**Check:** a monotonicity fixture at `citySafeRoadScoreOf ∈ {0, 0.5, 1}` (forced via a stub score map) asserts STRICTLY ascending `'Safe roads'` part values. A neutral-point fixture (no change to the score) diffs the FULL parts array before/after and asserts every pre-existing label's value is byte-identical (mirrors inc5 AC-6's neutral-point diff). A structural check asserts `wellbeingOf(s).parts` has NO `'Integrated transport'` label.
**False-pass note:** a non-strict (`>=`) monotonicity assertion would pass on a mutant that flattens the curve to a constant — must be strict across 3 distinct points, per the verification standard.
**Mutant:** invert the part (`part(1 - score)`) — reds its own monotonicity fixture (descending instead of ascending) and would make "0 safety" wellbeing-neutral instead of worst, contradicting Aaron's "reward safe roads" framing. Re-adding the `'Integrated transport'` part reds the structural absence check.

**AC-6 (amended, BUG-938 r3 ruling) — NO attract coupling this increment; `attractivenessOf` is byte-identical to its pre-inc9 form.**
The original `integrationMultiplier = clampN(0.9 + 0.2*integratedTransportScoreOf(s), 0.9, 1.1)` is **REMOVED** — `integratedTransportScoreOf` has no build-sensitive input today (AC-4), so multiplying it into attract would be a hidden population bonus dressed up as an integration reward. `safeRoadScoreOf`/`citySafeRoadScoreOf`/`integratedTransportScoreOf` (and their `*FromSnapshotOf` cadence readers) are NEVER referenced inside `engine.ts`'s `attractivenessOf` — safety still feeds wellbeing only (D2, unchanged), and integration feeds nothing downstream this increment.
**Check:** `attractivenessOf`'s output is INVARIANT to `trafficSnapshot.integratedTransportScore` across `{0, 0.5, 1, 1e9, -5, NaN}` (proves no coupling of any shape, not merely "no crash"); `grep -n "safeRoadScoreOf\|citySafeRoadScoreOf\|integratedTransportScoreOf\|integrationMultiplier" webconsole/src/sim/engine.ts` has zero matches inside `attractivenessOf`'s body.
**False-pass note:** a "some difference exists" assertion proves nothing about ABSENCE — the Tester must assert full invariance across every tested value, including the corrupt/NaN ones (BUG-939), not just 0 vs 1.

**AC-9 (new, BUG-939/GR#16) — a non-finite `trafficSnapshot` score can never poison `attractivenessOf` or `wellbeingOf` to `NaN`.**
`safeRoadScoreFromSnapshotOf`/`integratedTransportScoreFromSnapshotOf` (`trafficWellbeing.ts`) guard with `Number.isFinite` (not a plain `typeof === 'number'`, which passes for `NaN`), defaulting to the documented neutral (`1.0`/`0`) on `NaN`/`±Infinity`/non-number.
**Check:** for `safeRoadScore`/`integratedTransportScore` ∈ `{NaN, +Infinity, -Infinity, 'x', null, undefined}`, both `attractivenessOf(s, wbOverall)` and every `wellbeingOf(s).parts[].value` stay finite.

**AC-7 — determinism, data-sourced, registry errors, structural bound (mirrors inc3 AC-8 / inc4 AC-8 shape).**
No hand-typed safety weight, junction-key mapping value, entropy divisor, or multiplier bound anywhere but `rewards.json` and the one `ln(11)`/`clampN` shape stated above (the mode count `11` itself is `rewards.json`'s own documented cardinality, cited not restated — a data file listing fewer/more modes is a registry error, `MET-Vxxx`, claimed via `add-error.js claim-range` at build time). ## 4. Decisions for Aaron (recommendation given, not blocking)

**D1 — `modeShareBalance` follows `rewards.json`'s Shannon-entropy-evenness formula, not a "closeness to the ladder's target split" measure.** Both readings of "reward integrated transport" are plausible; `rewards.json` (the registered SSOT, inc0) already commits to entropy-evenness with a stated rationale (a one-mode-monoculture city should score low even at high aggregate transit share). **Recommend: keep entropy as written**; if Aaron wants a distance-to-target measure instead, that is a `rewards.json` data change, not a code change here (GR#15).

**D2 (SUPERSEDED, BUG-938 r3 ruling) — safety feeds wellbeing only; integration was to feed BOTH wellbeing and attract.** ~~Recommend: accept as designed.~~ **Overtaken by BUG-938's measurement**: `integratedTransportScoreOf` has no build-sensitive input today (the webconsole's only mode-split model is population-keyed), so it is not the "genuinely distinct, attract-relevant signal" this decision assumed — wiring it anywhere downstream would reward population, not integration. Safety-feeds-wellbeing-only stands unchanged; integration-feeds-attract is withdrawn.

**D3 (SUPERSEDED, BUG-938 r3 ruling) — `integrationMultiplier` landed in `attractivenessOf`, then was REMOVED same increment.** ~~Recommend: land now.~~ It landed at r1/r2, but round 2's own measurement (BUG-938) showed the multiplier tracked population, not connectivity — every built city scored lower than a bare map regardless of transit provision. The lead ruled it out entirely rather than retune the span (retuning a population-keyed input's bound does not make it build-sensitive). `FEAT-2326609804` (a per-tile mode-split model in inc2's demand code) is the real prerequisite before any attract/wellbeing coupling off this score can be honest; re-litigate D2/D3 once that lands.
