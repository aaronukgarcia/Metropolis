# Acceptance criteria — ui.dash (MOD-038)

**BOW code:** MOD-038
**Spec refs:** UI-SPEC §4 (`docs/METROPOLIS-MASTER-v2.1.md` lines 760-765: composable dashboards, the drill-through rule — "*every number on every screen is selectable and `Enter` goes to its source* — a cash figure opens its ledger lines; a congestion percentage opens that junction; a school-roll number opens that school. No dead ends, the whole UI is one navigable graph." — plus tables (sort/filter/export) and the projections-pane idiom); UI-SPEC §6 (line 782: view-subscription + layout/profile JSON schema); `int.protocol` (INT-001, the seam any source identity must cross); `ui.core` (MOD-009, the view-model layer this package's tiles must bind against); `ui.widgets` (MOD-010, the tile substrate).
**Date:** 2026-08-11
**Status:** in_progress (Sprint 8)
**Package under test:** `internal/ui/dash/` (path from `node claude-bow.js show MOD-038`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/ui/dash/...`.

## Why this file reads differently from the rest of the Sprint-8 estate

UI-SPEC §4 states the drill-through rule as a universal claim ("**every** number... no dead ends"), and a universal claim cannot be honestly checked by sampling. Every AC below that touches drill-through is written to be **exhaustive by construction** — it enumerates the full, closed set of ways a number can enter a shipped dashboard (AC-2/AC-3/AC-4/AC-5 cover: scalar tiles, table cells, embedded diagram elements, and the layout editor's save path) and either (a) makes it structurally impossible to add a number outside that enumeration without also carrying a source, or (b) provides an audit function proven (by a test using a synthetic layout, not a sample of real ones) to walk every element of *any* `Layout` value, so every future screen inherits exhaustive coverage for free rather than needing its own hand-written check. Where I could not make a clause exhaustive rather than structural, I say so rather than writing a check that passes because it only looked at three tiles (see AC-9's honesty note).

## User stories

- **US-1.** As **the player**, I need every dashboard tile (bignum, gauge, sparkline, table, mini-map, alert list) arranged in a shipped default layout per screen, so each F-screen has a sensible overview the moment it lands, without me building one first (UI-SPEC §4).
- **US-2.** As **the player**, I need a layout editor (`F10 → layouts`) that lets me rearrange tiles and saves my arrangement to my profile JSON, so the dashboard I actually use survives a restart.
- **US-3.** As **the player**, I need `Enter` on *any* number — a cash figure, a congestion percentage, a school-roll count, a Sankey band, a chain-diagram arrow — to open that number's source, with no exceptions, so the UI is one navigable graph rather than forty-four screens that each dead-end somewhere (UI-SPEC §4, the absolute rule).
- **US-4.** As **`ui.diagrams`' caller** (`MOD-037`, this item consumes it for embedded diagram tiles), I need this package to carry forward `ui.diagrams`' AC-5 hit-test source mapping into the same drill-target mechanism scalar tiles use, so a number inside a diagram is exactly as drillable as a number in a bignum tile — the drill-through rule does not get an exception for "the number happened to be inside an arrow."
- **US-5.** As **the sprint-9+ juniors building F2/F4/F8** (`FEAT-014`/`FEAT-016`/`FEAT-022`, all depend on `MOD-038`), I need an exported, reusable coverage-audit function rather than a bespoke check per screen, so "does my screen's dashboard honour the drill-through rule" has one answer, checked the same way everywhere.

## Scope

Widget-grid dashboard composition (tile types: bignum, gauge, sparkline chart, table, mini-map, alert list, plus embedded `ui.diagrams` output), shipped default layouts per screen, the user layout editor with profile-JSON persistence, and the drill-through mechanism: binding a tile's displayed value to a view-model path and registering the drill target that `Enter` navigates to. This package does not implement navigation itself (that is `ui.core`'s pane/screen-focus machinery, per `ui.core`'s existing API) — it registers *what* `Enter` should navigate to for a given tile, and calls through to `ui.core` to perform the jump.

## Acceptance criteria

### Functional

- **AC-1.** A widget grid composes tiles of each named type (bignum, gauge, sparkline chart, table, mini-map, alert list) using `ui.widgets`' shared widget set (not bespoke per-tile drawing) — a passing test asserts each tile type renders via its corresponding `ui.widgets` function, not a duplicated implementation (`grep -n "widgets\." internal/ui/dash/*.go` shows calls into the `ui.widgets` package for each tile type).
- **AC-2.** A shipped default layout exists per screen this item is responsible for at dispatch (at minimum, F1's right-rail Overview dashboard instance per UI-SPEC §4's "the Overview (F1's right rail) is just a dashboard instance") — a passing test loads the shipped default and asserts it parses into a valid `Layout` with the expected tile set.
- **AC-3.** A user layout editor lets the player add/remove/rearrange tiles and persists the result to the profile JSON (`F10 → layouts`); reloading the profile reproduces the saved arrangement exactly — a passing test builds a layout via the editor's API, saves, reloads from the saved JSON, and asserts the reloaded `Layout` is deep-equal to the one saved.
- **AC-4 (the drill-through rule, made structural).** A `Tile` cannot be constructed, bound to a value, or added to a `Layout` without a non-nil `DrillTarget`. This is enforced at the type/constructor level, not by a separately-run validator that a caller could skip: the `Layout`-mutating API (`AddTile`, or equivalent) takes `DrillTarget` as a required constructor argument with no zero-value/optional path, and any lower-level path that could bypass it (e.g. direct struct literal construction across package boundaries) is prevented by keeping the `Tile` struct's drill-target field unexported with only the validating constructor exported. Check: `go doc ./internal/ui/dash Tile` and `go doc ./internal/ui/dash AddTile` (or equivalent) show `DrillTarget` (or equivalent) as a required, non-optional parameter, not a settable-later field with a usable zero value; a passing test attempts to construct/add a tile with a nil/zero `DrillTarget` and asserts the call is rejected at construction time, not merely flagged later by a separate lint pass (`grep -rn "func Test.*[Nn]ilDrillTarget\|func Test.*[Rr]equireDrillTarget" internal/ui/dash/*_test.go`). **This is the check that rejects the lazy-but-plausible build**: an implementation that renders correctly and lets `DrillTarget` default to a zero value (silently "no drill target registered") passes every rendering-shape AC but fails AC-4, because AC-4 tests the *construction path itself*, not a rendered tile's appearance.
- **AC-5 (exhaustive coverage, not a sample).** An exported audit function, e.g. `AuditDrillCoverage(l Layout) []Gap`, walks **every** element of a `Layout` that carries a displayed value — including every row of every table tile (not just the table tile as one unit) and every hit-test entry `ui.diagrams` returns for an embedded diagram tile (per `ui.diagrams`' AC-5) — and returns one `Gap` per element with no resolvable `DrillTarget`. Because AC-4 already makes a nil `DrillTarget` unconstructible for scalar/table-row tiles, a `Gap` from `AuditDrillCoverage` on those is expected to be structurally impossible; **this AC's job is to prove the audit function itself is exhaustive**, i.e. that it does not silently skip a tile type. Check: a passing test builds a synthetic `Layout` covering every known tile type including a table with ≥10 rows and an embedded diagram tile with ≥5 hit-test elements (a deliberately large, enumerable fixture, not "a couple of tiles"), removes the `DrillTarget` from one specific element buried inside the table (row 7 of 10) and one specific diagram hit-test element, and asserts `AuditDrillCoverage` reports **exactly those two** gaps — proving the walk reaches inside aggregate tiles rather than only checking top-level tile identity (`grep -rn "func Test.*[Aa]uditDrillCoverage\|func Test.*[Cc]overageGap" internal/ui/dash/*_test.go`). A false pass here looks like: a test that only exercises 2-3 top-level tiles (all bignum/gauge) and never buries a missing target inside a table row or a diagram element — it would pass an audit function that silently returns `nil` for any tile type it doesn't recognise.
- **AC-6.** `Enter` on a selected tile resolves its `DrillTarget` and invokes `ui.core`'s pane/screen-navigation API to jump there (this package does not reimplement navigation) — a passing test asserts selecting a known tile and firing the drill action results in exactly the `ui.core` navigation call its `DrillTarget` specifies (`grep -n "core\.\(Focus\|Navigate\|SwitchScreen\)" internal/ui/dash/*.go` or equivalent shows the call-through).
- **AC-7.** Tables support sort (`s` cycles columns), inline filter (`f`), and CSV export (`x`, to the save folder) — carrying forward `ui.widgets`' AC-8 table contract at the dashboard-composition level: a passing test asserts sorting/filtering/export behave correctly on a dashboard table tile specifically (not re-testing `ui.widgets`' own table, but confirming this package wires the table tile's data through those operations correctly), and — since AC-4/AC-5 apply to *every* table row — that a sorted or filtered table's visible rows retain their original `DrillTarget`s (a lazy sort/filter implementation that rebuilds row structs without carrying the drill target forward would pass AC-7's sort-order check while silently reintroducing exactly the dead-end AC-5 exists to catch; a passing test sorts a table and asserts each visible row's `DrillTarget` still resolves to its original source, not a renumbered/lost one).
- **AC-8.** The projections-pane idiom (history solid, projection dim, threshold lines, decision markers from the queued build order) renders when a dashboard tile is bound to a projection series — a passing test asserts a known projection series with a queued decision marker renders all four visual elements distinctly.

### Error handling

- **AC-9 (honesty note — not claimed exhaustive).** A `DrillTarget` whose resolved subscription/entity no longer exists at drill time (per `int.protocol`'s stale-subscription/vanished-entity case, mirroring `ui.screen.map`'s AC-9) shows a clear "no longer available" state rather than a crash or silent no-op. This is checked per-tile-type (bignum, table-row, diagram-element) with one representative test each — **this is a spot check, stated as one**, because "every possible vanished-entity timing race" is not enumerable the way AC-5's static layout walk is; the exhaustiveness this file claims is over *the set of drillable element kinds*, not over every runtime timing interleaving of engine state disappearing mid-drill.
- **AC-10 (GR#7).** A malformed/corrupt saved layout profile JSON produces a registry-sourced error and falls back to the shipped default layout for that screen, rather than leaving the dashboard unrenderable — a passing test covers malformed-JSON load with fallback. — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that the fallback applies the shipped default layout rather than a corrupted/partial one, not merely that a passing test exists.

### Determinism & safety

- **AC-11 (GR#20).** `go list -deps ./internal/ui/dash/...` shows no import of `internal/engine/...` — this package resolves `DrillTarget`s to view-subscription names/entity identifiers (see Escalations — this is the protocol-carry requirement) and calls through `int.protocol`/`ui.core`, never into engine internals directly.
- **AC-12 (GR#21).** `AuditDrillCoverage`'s walk order (and any tile-grid layout order feeding rendering) does not depend on Go map iteration — `grep -rn "for .* := range" internal/ui/dash/*.go` shows any map range feeding ordered output is sorted first (`grep -n "sort\." internal/ui/dash/*.go` corroborates).
- **AC-13.** `go test ./internal/ui/dash/... -race -count=1` passes with no data race, including the layout editor's save path running concurrently with a live-updating dashboard render (`grep -n "go func()" internal/ui/dash/*_test.go` finds a concurrency test).

### Documentation

- **AC-14.** The package doc states module key `ui.dash`, cites UI-SPEC §4, and documents (a) the `DrillTarget`-required constructor contract from AC-4, (b) that `AuditDrillCoverage` is the canonical, shared way for any future screen to prove its own shipped layout is drill-through-complete (US-5) — future BAs/juniors should call this function in their own screen's tests rather than writing a new one, and (c) what a `DrillTarget` must actually be able to name (see Escalations) so a future screen's BA knows what granularity is available before promising "opens its ledger lines" in their own criteria.

## Out of scope

- Rendering individual widget types — `ui.widgets` (`MOD-010`).
- Computing diagram layouts — `ui.diagrams` (`MOD-037`); this item consumes its AC-5 hit-test output.
- Any specific F-screen's own dashboard content beyond the shipped default this item ships (F1 Overview) — F2/F4/F8's own dashboards are `FEAT-014`/`FEAT-016`/`FEAT-022`, separate items that depend on this one and must run `AuditDrillCoverage` (AC-5, US-5) over their own shipped layouts in their own test suites.
- Implementing the navigation/focus jump itself — `ui.core` (`MOD-009`); this item only resolves and calls it.

## Escalations

- **For Bill — the load-bearing finding (protocol provenance).** The drill-through rule cannot be built to its absolute wording without `int.protocol` carrying a `DrillTarget`-resolvable source identity across the UI/engine seam, and today it does not, cleanly. `int.protocol`'s own acceptance file (`int.protocol.md`, AC-18) only documents a *view-name* grammar ("named projections", e.g. `f1.viewport`, `f2.ledger`) — it does not document any mechanism for addressing a specific *row or entity within* a view (e.g. "ledger line 42 of the F2 ledger", "arrow E7 of a chain diagram", "the junction-14 north approach specifically, not the whole junction pane"). UI-SPEC §4's own worked examples are entity-level, not view-level ("a cash figure opens its ledger lines" — plural, implying the specific figure's contributing lines, not the whole ledger view; "a congestion percentage opens that junction" — a specific junction, not a junction list). Without a documented sub-entity addressing scheme in the protocol's view-name grammar or `Delta` schema, `ui.dash`'s `DrillTarget` type has two honest options, both of which were put to Bill — ruled below rather than picked silently: **(a)** `DrillTarget` names only a view/screen (coarse — `Enter` on a specific ledger line opens "the ledger" generically, not that line), which satisfies UI-SPEC §4's letter weakly and its examples not at all; or **(b)** `int.protocol` gains an addressable entity-ID component to its view-name grammar (e.g. `f2.ledger#line-42`, or a structured `(ViewName, EntityID)` pair threaded through `Delta`) before this item can honestly claim row-level drill-through. I have written AC-4/AC-5/AC-7 assuming **(b)** — a `DrillTarget` carries both a view name and an entity/row identifier — because that is what UI-SPEC §4's own examples require, but this is a cross-module contract gap in the same family as `BUG-058` (a spec-mandated capability with no registered/documented edge to carry it), not something this BA can resolve by writing the UI-side criteria more carefully. Logged and resolved as **FEAT-042** (P0, AARON APPROVED — the `int.protocol` extension for entity-level drill addressing). The canonical `ui.dash` type is **`dash.DrillTarget{ViewName, EntityID}`** (ASM-538/ASM-630): a self-contained struct, `ViewName` validated by `protocol.ValidateViewName`, defined now rather than awaiting `FEAT-042`'s code (which is still open), to be reconciled with `TargetRef` when it lands.
- **For Bill.** UI-SPEC §4 doesn't specify what a projection-pane "decision marker" looks like precisely beyond "a planned school appears as a capacity step... before it's built" — AC-8 is written to accept any reasonable rendering of a step change at the marker's projected date; flag if a specific visual spec exists elsewhere.
- **Assumptions logged separately (ASM-xxx, see report to Ben).** Default-layout tile selection per screen (AC-2), the `DrillTarget` type's exact shape (`dash.DrillTarget{ViewName, EntityID}` — ASM-538/ASM-630 above), and the audit function's fixture size in AC-5 ("≥10 rows, ≥5 diagram elements" — chosen to be large enough that a hand-wavy implementation can't special-case it, not spec-mandated) are all implementer/BA defaults, not spec-mandated numbers.
