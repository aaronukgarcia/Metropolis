## 1. Why this item exists

Aaron's brief: "vehicles pay tax on fuel and pay road tax; just like Blue the more a road is used the more repairs it needs." inc3 gave every road segment a real, routed vehicle flow (`assignedFlowOf`) instead of a population proxy; this increment is the first to spend that flow on MONEY — fuel duty and VED become new inflows sized by what the city's actual traffic does, and segment wear becomes a new outflow that rises with sustained heavy use and resets on repair. This is the "reward/penalise usage" half of the epic that inc9 (rewards) will later extend the OTHER direction (safe roads). GR#3 is the load-bearing constraint throughout: every new figure extends an EXISTING money surface (`computeFlows`, the 'Roads' upkeep bucket) rather than opening a parallel ledger, and every new physical quantity (vehicle-km, wear) traces to a table row, never a hand-typed TS literal.

## 2. The design in one paragraph

**Per-class flow (prerequisite for everything below).** `assignedFlowOf`/`freightVehicleTrips` today are BLENDED scalars — one number per segment or tile, car and articulated truck summed together — because fuel duty and ESAL wear both need vehicle-CLASS-specific rates (litres/km, ESAL factor) applied to CLASS-specific flow, this increment must first un-blend them, reusing the exact computations already made rather than re-deriving a second model (GR#3). `trafficDemand.ts`'s `blendedFreightVehicleCapacity`/`freightVehicleTrips` (~L253-366) already reads `freightTonnesByVehicleClass` per-class shares to build ONE blended figure; this item adds a sibling `freightVehicleTripsByClassOf` that keeps those same per-class shares SEPARATE instead of blending them. `trafficAssignment.ts`'s `assignmentOf` loop (~L640-676) already computes each road person-mode's (`car`/`motorbike`/`taxi`/`bus`) vehicle-trips individually before summing into `roadVehicleTrips`; this item tags each mode's/class's contribution before the `accumulate()` call instead of after, producing `assignedFlowByClassOf(s): Map<segmentId, Record<VehicleClassId, number>>` ALONGSIDE (never replacing) the existing scalar `assignedFlowOf` — the two must sum to the same total by construction (AC-1). From there, `cityVehicleKmByClassOf(s)` sums `assignedFlowByClassOf[seg][class] × segment length in km` (segment length reuses `segmentFreeFlowMinutesOf`'s own tile-count × `webconsoleMetresPerTile` basis, inc3 AC-2, not re-derived) over every segment, giving the real per-class vehicle-km this city's actual road network carries today. **Tax (AC-2/AC-3).** Fuel Duty = Σ classes `vehicleKm[class] × vehicle_classes.json fuelLitresPerKm[class] × data/fuel.json duty.ratePencePerLitre ÷ 100`, booked as one new `computeFlows` inflow line (the `{label,value}` idiom, `engine.ts` inflows array ~L892-929). Road Tax (VED) = Σ classes `vehiclesOwnedByClass[class] × taxation.json fleetAverageByVehicleClass[class].gbpPerYear ÷ TICKS_PER_YEAR`, a second new inflow line; `vehiclesOwnedByClass` is Decision D1 below. **Wear and repair (AC-4/AC-5).** A new persisted `s.roadWearBySegment: Record<segmentId, number>` (mirroring `s.congestionTicksBySpec`'s exact shape: `types.ts` field, `data.ts` sanitizer beside `sanitizeCongestionTicksBySpec`, `debugjson.ts` export, old saves default to `{}`/zero wear) accrues ESAL per tick from `assignedFlowByClassOf × segment-km × road_wear.json esalFactors[class].esalFactorPer100VehicleKm ÷ 100`. `conditionIndexOf` applies `wearToRepairCost.conditionDecayPerESAL` to cumulative wear (additive to, never replacing, `roads.json maintenance.conditionDecayPerMonth`'s own unconsumed age-based decay — confirmed by inspection that no `conditionIndex` state exists anywhere in the TS engine today, so this is the FIRST consumer of both fields); `repairCostCurve`'s piecewise-linear interpolation turns `conditionIndex` into a cost multiplier on the segment's road-class `baseCostPounds` (`roads.json`, via inc3's `ROAD_CLASS_ID_OF_TIER` mapping). The repair cost is folded into the EXISTING `'Roads'` `UPKEEP_BUCKET` outflow total (`engine.ts` ~L1030-1046) — never a second 'Road Repair' line — and, once a segment crosses below `repairTriggerConditionIndex` (60) and that tick's inflated cost is actually paid, `roadWearBySegment[seg]` resets to 0 (a resurfacing event, Decision D2).

## 3. Acceptance Criteria

### Per-class flow (prerequisite)

**AC-1 — `assignedFlowByClassOf(s)` sums exactly to `assignedFlowOf(s)`; data mirror extended.**
`sync-traffic-data.mjs`'s `mirrorPairs()` extras list gains `data/fuel.json` (webconsole reads `duty.ratePencePerLitre` client-side); `data/trip_generation.json` gains a NEW `tripsPerVehiclePerDay` block, one entry per road/freight vehicle class, sourced UK NTS/DfT order-of-magnitude (GR#15, D1). `assignedFlowByClassOf` tags each mode's/class's vehicle-trips before path accumulation in the existing `assignmentOf` loop.
**Check:** on the inc3 two-path fixture, `Σ_class assignedFlowByClassOf(s).get(seg)[class] === assignedFlowOf(s).get(seg)` for every segment carrying flow; `traffic-data-mirror.test.mjs`-style byte parity holds for `fuel.json`.
**False-pass note:** a fixture with only ONE vehicle class active cannot prove the split tags correctly (a bug that dumps everything into one bucket still sums right) — use a mixed car+articulated_truck fixture and assert BOTH classes appear distinctly.
**Mutant:** bucket all freight vehicle-trips under `'car'` instead of their real class — reds the mixed-class fixture (car total inflated, freight classes absent) but not a car-only fixture.

### Tax

**AC-2 — Fuel Duty inflow, real vehicle-km basis (not the population-only ladder figure).**
New `fuelLitresDemandedOf(s)` and one new `computeFlows` inflow `{ label: 'Fuel Duty', value }` = `Math.round(Σ_class cityVehicleKmByClassOf(s)[class] × vehicle_classes.json fuelLitresPerKm[class] × fuel.json duty.ratePencePerLitre / 100)`. EV share is NOT netted out this increment (ASM-1531).
**Check:** a fixture with one segment of known length carrying a known single-class flow asserts the inflow equals the hand-computed litres × 52.95p ÷ 100, rounded, matching the existing rounding convention used by every other `computeFlows` line (e.g. Office Tax).
**False-pass note:** a fixture built only from the ladder's `fuelLitresDemandedPerDay` cannot distinguish "real vehicle-km used" from "population proxy used" when the two happen to agree — build the fixture's road network so the two diverge (a long circuitous route vs. a short one for the same population).
**Mutant:** substitute the ladder's `fuelLitresDemandedPerDay` for the real `cityVehicleKmByClassOf`-derived figure — reds the diverging fixture.

**AC-3 — Road Tax (VED) inflow, vehicle-ownership basis (Decision D1).**
New `vehiclesOwnedByClassOf(s): Record<VehicleClassId, number>` = each class's daily vehicle-trips (AC-1) ÷ that class's `tripsPerVehiclePerDay` (AC-1's new field). One new inflow `{ label: 'Road Tax (VED)', value }` = `Math.round(Σ_class vehiclesOwnedByClassOf(s)[class] × taxation.json fleetAverageByVehicleClass[class].gbpPerYear / TICKS_PER_YEAR)`.
**Check:** a fixture with 2+ classes' known trip counts and known `tripsPerVehiclePerDay` asserts `vehiclesOwned = trips/tripsPerVehicle` exactly per class, and the inflow equals `Σ(vehiclesOwned × gbpPerYear)/360` to the penny.
**False-pass note:** a car-only fixture cannot prove the Σ-over-classes shape actually sums (a bug that silently drops non-car classes still passes) — the fixture must carry at least a car and a freight class.
**Mutant:** divide by `TICKS_PER_MONTH` (30) instead of `TICKS_PER_YEAR` (360) — reds by exactly 12x.

### Wear and repair

**AC-4 — per-segment ESAL wear accrual, persisted (mirrors `congestionTicksBySpec`).**
New `s.roadWearBySegment?: Record<string, number>` (`types.ts`), `sanitizeRoadWearBySegment` (`data.ts`, same shape as `sanitizeCongestionTicksBySpec` at `data.ts:3615`), `advanceRoadWear(prev, assignedFlowByClassOf, segmentKm)` accrues `Δwear[seg] = Σ_class flow[class] × km[seg] × road_wear.json esalFactors[class].esalFactorPer100VehicleKm ÷ 100` per tick. Old saves (field absent) sanitize to `{}` — zero wear, mirroring `data.ts:3686`'s existing backward-compat rule.
**Check:** two otherwise-identical segments, one carrying ONLY `car` flow and one carrying ONLY `articulated_truck` flow at the SAME vehicle count, assert the wear ratio between them equals `road_wear.json`'s `ratioToCarPerPass` (10000) exactly, never a hand-typed constant (ASM-1534).
**False-pass note:** comparing absolute wear values (not the ratio, with base flow held constant) cannot prove the ESAL law is applied per-class correctly.
**Mutant:** apply `ratioToCarPerPass` (a per-PASS figure) where `esalFactorPer100VehicleKm` (a per-100-km rate) belongs — `road_wear.json` documents these as different fields for different purposes — reds the fixed-flow ratio Check.

**AC-5 — condition index + repair cost extends the EXISTING 'Roads' upkeep bucket (GR#3 — never a second ledger).**
`conditionIndexOf(wear)` applies `wearToRepairCost.conditionDecayPerESAL` to cumulative wear, additive to (never replacing) `roads.json maintenance.conditionDecayPerMonth`'s unconsumed age decay. `repairCostMultiplierOf(conditionIndex)` piecewise-linear-interpolates `repairCostCurve`. Per-segment repair cost = multiplier × the segment's road-class `baseCostPounds` × a NEW data-sourced per-tick amortisation fraction (flagged ASM if no suitable field exists in `roads.json`/`road_wear.json` — a Jnr-dev-discovered gap is acceptable, a hand-typed fraction is not). This amount is ADDED into the SAME `'Roads'` bucket total the `UPKEEP_BUCKET` loop (`engine.ts` ~L1030-1046) already produces, never a new outflow label.
**Check:** enabling wear on a fixture city changes the `'Roads'` outflow's VALUE by exactly the expected repair contribution, with the outflow LABEL SET unchanged (still exactly `{Roads, Transport, ...}` per `UPKEEP_BUCKET`'s values) — asserted by diffing `computeFlows(s).outflows` before/after.
**Mutant:** book the repair cost under a new `'Road Repair'` label instead of folding into `'Roads'` — reds the label-set-unchanged assertion (GR#3's extend-don't-duplicate discipline, even though total money moved is identical).

**AC-6 — resurfacing resets wear; automatic-with-notice (Decision D2).**
Once a segment's `conditionIndex` drops below `repairTriggerConditionIndex` (60) AND that tick's inflated cost is actually paid (folded into the AC-5 outflow), `roadWearBySegment[seg]` resets to 0 that same tick. A read-out exports per-segment condition via `debugjson.ts` (mirroring `congestionTicksBySpec`'s own export idiom, `debugjson.ts:331/670/1083`) for a future overlay (inc10, not this increment's UI).
**Check:** a segment driven past the trigger over N ticks shows `roadWearBySegment[seg] === 0` the tick immediately after the paid repair, with that segment's outflow contribution now at the FRESH (`conditionIndex: 100` → multiplier `0.0`) rate, not the pre-repair rate.
**False-pass note:** a fixture that never crosses the trigger cannot prove the reset fires — must drive wear past 60 first.
**Mutant:** reset wear on every READ of an over-threshold segment (not only when the cost is actually paid) — reds a fixture that inspects but does not yet pay for an over-threshold segment and expects its wear to persist.

### Conservation and scale

**AC-7 — conservation absolute: every new line lives in `computeFlows`, exactly once, for 120 ticks.**
`consistency.ts`'s `conservation.funds-vs-flows` (`consistency.ts:849`) and `flows.inflow-labels-unique`/`flows.outflow-labels-unique` checks hold bit-for-bit with wear/tax active, across a scripted 120-tick run (the attack-inc3-round6 R6-3 idiom) over a fixture city with mixed car+freight traffic and at least one resurfacing event mid-run.
**Check:** `runConsistencyChecks(...)` returns `ok: true` on `conservation.funds-vs-flows` and both label-uniqueness checks EVERY tick of the 120, never sampled.
**Mutant:** book the AC-5 repair cost directly against `s.funds` inside `advanceRoadWear`, bypassing `computeFlows`'s outflows array (the exact BUG-400 side-channel class the Regional Grant fix eliminated) — reds `conservation.funds-vs-flows` on tick 1 by exactly the un-booked amount.

**AC-8 — determinism (GR#21), old-save compatibility, and the heavy-truck ratio (ASM-1534).**
`assignedFlowByClassOf`/`cityVehicleKmByClassOf`/`advanceRoadWear`/`conditionIndexOf` are pure, `memoOnState` where read-only, no `Date.now`/`Math.random`/`localStorage`. A save fixture predating this increment (no `roadWearBySegment` field) loads via the sanitizer to `{}` and produces IDENTICAL `computeFlows` outflows to a fresh city with the same buildings — old saves are not retroactively penalised.
**Check:** 10-rerun byte-identical determinism test; the old-save fixture round-trips with zero repair contribution and no throw.
**Mutant:** re-derive the heavy-truck wear ratio via an independent `Math.pow(loadRatio, 4)` in TS instead of reading `road_wear.json`'s `ratioToCarPerPass` — reds AC-4's fixed-flow ratio Check (the schema documents the specific ratios as its own calibrated figures, not independently re-derivable, ASM-1534).

## 4. Decisions for Aaron (recommendation given, not blocking)

**D1 — vehicle-ownership basis for VED: trips-per-day ÷ a new `tripsPerVehiclePerDay` field, vs. a vehicle-km ÷ average-annual-km basis, vs. deferring until a real per-citizen vehicle-ownership state exists.**
**Recommend: trips-based (AC-3).** No per-citizen vehicle-ownership state exists anywhere in the engine today; deriving "vehicles owned" from the SAME per-class trip counts inc2/inc3 already compute (rather than inventing a second demand model, GR#3) keeps VED consistent with everything else this epic has built, at the cost of VED tracking traffic ACTIVITY rather than a true registered-fleet count (ASM-1532 — a city with short average trips could show inflated implied ownership). Revisit once/if a real vehicle-ownership state is ever modelled.

**D2 — resurfacing: automatic-and-charged vs. a player-initiated build action.**
**Recommend: automatic-with-notice for baseline one (AC-6), matching FEAT-1972079919's bi-monthly catch-up precedent.** Consistent with the game not yet exposing per-segment player micromanagement anywhere else in the road system; a player-triggered resurfacing action would be a real rework (a new build-menu action with its own placement/affordability gate), not a tweak, and should wait until Aaron wants that level of manual control (ASM-1533).

**D3 — should a heavily-worn segment's repair cost be capped, or allowed to spike the 'Roads' bucket arbitrarily under sustained overload?**
**Recommend: no special-case cap.** The `repairCostCurve`'s own top multiplier (6.0× at `conditionIndex: 0`) is already the data's stated ceiling; letting a genuinely neglected road cost real money (up to that ceiling) is the point of the mechanic, and the existing insolvency/bailout machinery (`fiscal.ts`) already handles a city that cannot afford its outflows — no new special-case is needed (GR#3, don't build a second safety net for one line).

## 5. Assumptions

- **ASM-1531** — fuel litres taxed at 100% fossil rate; EV share not netted out this increment. What breaks if wrong: Fuel Duty revenue is overstated once EV adoption is material; inc6 must subtract EV vehicle-km before this line is balance-correct.
- **ASM-1532** — VED's vehicle-ownership basis is trips-per-day ÷ a new `tripsPerVehiclePerDay` data field, not a registered-vehicle count. What breaks if wrong: VED scales with trip activity, not true fleet size — see D1.
- **ASM-1533** — resurfacing is automatic-with-notice, not player-initiated. What breaks if wrong: if Aaron wants a player action instead, AC-6 becomes a gated build action, a real rework — see D2.
- **ASM-1534** — the heavy-truck wear ratio is `road_wear.json`'s own `ratioToCarPerPass`, never independently re-derived via a 4th-power formula in code. What breaks if wrong: a code-side re-derivation could silently drift from the data file if either is edited alone (GR#3).
