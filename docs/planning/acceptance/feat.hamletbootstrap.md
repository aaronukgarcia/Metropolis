## User stories

- **US-1.** As a new player, I need the UI to show only what I can meaningfully use at my current scale — starting with roads/zoning/power/water and progressively revealing more as my population grows — so the first hours are a guided bootstrap, not a wall of choices ("North Africa Campaign" syndrome prevention).
- **US-2.** As the game, I need a single source of truth for what "stage" my city is at, derived from the existing milestone ladder and actual population — so every feature that gates on scale (UI panels, tutorial nudges, helper toggles) reads the same number, never a parallel tier enum (GR#3).
- **US-3.** As a player whose city has died, I need a chronological "Why Did My City Die?" timeline tracing the cascade back from the death state — so failure is a learning moment, not a dead end.
- **US-4.** As the game, I need growth to follow a sigmoid curve — fast while the city is empty and cheap, slowing as density/congestion/pollution rise, halting as capacity is reached — so player archetypes (expander vs saver vs specialist) face real, distinct failure modes.
- **US-5.** As a tester/QA, I need the five-player-archetype scenarios vs the optimal path to be runnable as automated scenario tests — so balancing growth is evidence-driven, not anecdotal.

## Scope

Three coordinated changes: (1) a population-tier gate driving progressive UI un-hiding and tutorial/helper nudges — **reading `engine.unlocks`' existing ladder, not a new enum**; (2) an autopsy events ledger + timeline UI tracing the death cascade — **integrating `engine.spiral`'s death verdict and `engine.projections`' WarningLedger, not a parallel failure log**; (3) sigmoid growth replacing `engine.attract`'s current linear migration — touching `engine.spiral` only via the registered A-score consumer edge. Save-metadata extension for the ledger lives in `feat.saveux`. It does **not** re-implement the ladder, the death path, the warning ledger, or save serialization.

## Acceptance criteria

### Design 1 — Progressive UI un-hiding (tier-gated)

- **AC-1 (US-1/US-2; the tier gate IS the existing ladder, never a new enum).** The population stage a screen/panel is filtered by is `engine.unlocks`' milestone ladder tier, derived from live population — NOT a parallel PlayerTier enum with its own thresholds. Check: the build imports/reads the ladder (`internal/engine/unlocks/ladder.go`), and the concept doc's 500/2000/10000 split appears NOWHERE in Go source; `grep -rn "PlayerTier\|2000\|10000" internal/ui internal/engine --include=*.go` (excluding `_test.go`) finds no parallel thresholds. **False-pass risk:** a UI filter built on hardcoded thresholds that only *looks* like the ladder — the check must assert the gate resolves through the ladder's `Tier`/`Population` fields.
- **AC-2 (US-1; the cold-start panel set is exactly the bootstrap set).** At ladder Tier 2 (Hamlet, pop < 100–500 boundary per the real ladder) the visible build panels are exactly: Roads, Zoning (Low-Density Residential, Basic Shops, Light Industry), Power (Wind/Diesel), Water (Pump/Tower) — nothing else. Higher-tier panels are hidden, not disabled-greyed (a hidden panel is invisible; a disabled one implies existence). Check: a passing UI test at Tier 2 asserts the hidden panels' absence from the map/finance screen state (not a zero-value that renders), and at Tier 3+ asserts their presence; `grep -rn "func Test.*[Tt]ier.*[Pp]anel\|func Test.*[Hh]amlet.*[Ss]creen" internal/ui/screens/map/*_test.go internal/ui/screens/finance/*_test.go`. **False-pass risk:** a filter that hides panels in the UI layer but never tests the actual panel-registration table — assert on rendered screen state.
- **AC-3 (US-2; the gate responds to population, not month, and fires a promotion event).** Crossing a ladder tier fires a single promotion signal (event/notification) that consumers (UI panels, tutorial nudges, helper toggles) observe — no polling, no per-consumer threshold math. Check: a passing test advances population across a tier boundary and asserts exactly one promotion event, consumed by at least the map screen and finance screen; the event carries the new tier and the threshold crossed (`grep -rn "func Test.*[Pp]romotion\|func Test.*[Tt]ierCross" internal/engine/unlocks/*_test.go`). The 500/2000/10000 milestones in the concept doc are reconciled to the ladder's real thresholds (Escalation 2) BEFORE this test is written.

### Design 2 — "Why Did My City Die?" autopsy

- **AC-4 (US-3; the ledger is append-only and threshold-gated, integrated not parallel).** An events ledger records `{Month, Type, Description, DeltaValue}` for exactly the four cascade-significant crossings from the guidance — CAPEX placement > 1M credits, service budget cut > 25%, refuse/blight +30% in one month, insolvency / rating-C — by observing `engine.spiral`'s death path and `engine.projections`' WarningLedger signals, NOT a new parallel failure log. Check: `grep -rn "func Test.*[Aa]utopsy\|func Test.*[Ee]ventLedger\|func Test.*[Cc]ascade" internal/engine/spiral/*_test.go internal/engine/projections/*_test.go`; a passing test drives each of the four crossings and asserts exactly one ledger entry per crossing, and that a non-crossing month appends nothing. **False-pass risk:** a ledger that records every event (volume) or re-derives signals the existing modules already emit — assert it observes the registered signals, count-exactly.
- **AC-5 (US-3; the ledger persists in save metadata via feat.saveux/int.serializer).** The events ledger round-trips through save metadata (extend the save `Meta`/state with the ledger slice via `int.serializer`, the `feat.saveux` outbound) — a city that dies, saves, reloads, and hits the autopsy screen shows the full timeline. Check: a passing save/load round-trip preserves the ledger verbatim (`grep -rn "func Test.*[Aa]utopsy.*[Ss]ave\|func Test.*[Ll]edger.*[Rr]ound" internal/engine/save/*_test.go`); a save written by a build without the ledger field loads cleanly (backward-compatible, missing slice = empty, NOT an error — unlike the FEAT-143 GameMode lock, the ledger is diagnostic data, not a fail-closed invariant; see Escalation 4).
- **AC-6 (US-3; the timeline traces backward from the death verdict, using the real death state).** The autopsy timeline is anchored on `engine.spiral`'s actual `DeathVerdict` (insolvency / ghost-city via `EvaluateDeath`), walks the ledger backward month-by-month, and renders the cascade with the guidance's shape (death → preceding cause → catalyst). Check: a passing end-to-end test produces a DeathVerdict from a scripted cascade, opens the autopsy screen, and asserts the timeline renders the recorded entries in reverse-month order with the death state at the top (`grep -rn "func Test.*[Aa]utopsy.*[Tt]imeline\|func Test.*[Dd]eath.*[Tt]race" internal/ui/screens/map/*_test.go`). **False-pass risk:** a timeline built from a fictional death state instead of `EvaluateDeath`'s verdict — assert the anchor is the real verdict, not a re-derivation.

### Design 3 — Sigmoid growth (engine.attract migration)

- **AC-7 (US-4; migration is sigmoid-shaped, replacing the linear path, preserving conservation).** `engine.attract`'s migration applies the sigmoid `M = Mmax · 1/(1+e^(−k(A−θ))) · (1 − P/C)` with `C = min(water, power, housing capacity)`; the existing conservation invariants (applyImmigration netting, the A-score decomposition) hold unchanged. Check: `grep -rn "func Test.*[Ss]igmoid\|func Test.*[Gg]rowth.*[Cc]urve\|func Test.*[Mm]igration.*[Cc]onverve" internal/engine/attract/*_test.go`; a passing test drives A-score and capacity sweeps and asserts (a) the migration rate is monotone in A, (b) it decays to ~0 as P→C, (c) the conservation invariant from the existing migration tests still holds byte-for-byte. **False-pass risk:** a sigmoid that runs *alongside* the linear path (dead code) or a rate that can exceed the old path's conservation bounds — assert the linear path is gone, not layered.
- **AC-8 (US-4; P→C halts growth and feeds the existing spiral, no new spiral math).** When population reaches capacity C, net growth stops and the S-score/drift inputs `engine.spiral` reads from `engine.attract` move toward the death-spiral region — WITHOUT `engine.attract` reimplementing S. Check: a passing test pins P at C across months and asserts migration ≈ 0 and that the attract→spiral consumer edge delivers the shaped A/drift values (spiral's existing S-path reacts); `grep -rn "func Test.*[Ss]piral.*[Aa]ttract\|func Test.*[Cc]apacity.*[Hh]alt" internal/engine/spiral/*_test.go`. **False-pass risk:** a hard cap that silently zeroes migration instead of the smooth `(1 − P/C)` decay — assert continuity near P=C, not a cliff.
- **AC-9 (US-5; the five archetypes are runnable scenario tests vs the optimal path).** The five player-archetype scenarios from the concept doc (Aggressive Expander, Cautious Saver, Specialist, Diversity Planner, Random/Cold) plus the Optimal baseline are automated scenario tests that drive scripted build orders through the same engine and report each archetype's terminal outcome (survive / stagnate / spiral / insolvent). Check: `grep -rn "func Test.*[Aa]rchetype\|func Test.*[Oo]ptimal" internal/engine/attract/*_test.go internal/engine/spiral/*_test.go`; a passing test runs all six and asserts each archetype lands in the concept doc's predicted failure/success class (these are directional expectations, not pass/fail tuning — see Escalation 2).
