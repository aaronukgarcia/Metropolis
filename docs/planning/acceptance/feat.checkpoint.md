## User stories

- **US-1.** As the player, I need to take a whole-state checkpoint at any point I choose, so that I have a named place to come back to that is guaranteed to be everything, not a partial snapshot I discover is missing something after I need it.
- **US-2.** As the player, I need reverting to an earlier checkpoint to not destroy the timeline I'm leaving, so that "maybe this was a mistake" is reversible in both directions — I can go back to my checkpoint, and I can still get back to what I abandoned, at least for a while.
- **US-3.** As the player, I need old abandoned branches to eventually disappear rather than accumulate forever, so that a save directory from a long campaign doesn't grow without bound just because I like reverting.
- **US-4.** As the player, I need a small lineage tree in the save UI, so that when I have several forks I can see which checkpoint spawned which branch, not just a flat list of dates and hope I remember the story.
- **US-5.** As a Tester/Destructive agent (GR#21), I need fork integrity to be independently verifiable — that reloading a checkpoint and replaying a branch's subsequent commands reproduces exactly what that branch's live state was — so that "the fork works" is a proven property, not a claim resting on the save/load code being trusted to have gotten it right.
- **US-6.** As FEAT-065's dev-mode debug console (not this item's scope to build), I need a stable way to reference "the checkpoint/branch active when this feedback was captured", so that a captured bug report can point back at exact reproducible state without FEAT-065 having to invent its own state-identification scheme.

## Scope

A checkpoint/fork layer sitting above `feat.saveux`'s save orchestration and `int.serializer`'s bundle format: manual whole-state checkpoint creation, revert-as-branch semantics (a bounded, prunable fork tree keyed by checkpoint lineage), the lineage data this item's own `List`-equivalent exposes for a future save-UI screen to render as a tree, and the replay-based fork-integrity verification harness described in Aaron's ruling. This item does not build the save-UI screen itself (same split `feat.saveux` draws for its own `List`/`Load`), does not build FEAT-065's debug console, and does not decode or interpret any domain record — it reuses `feat.saveux`'s `Participant` registry and `int.serializer`'s bundle machinery rather than re-specifying them.

## Acceptance criteria

### Functional

- **AC-1 (whole-state checkpoint = a complete bundle, not a delta).** A checkpoint is a complete, independently-loadable state bundle in exactly the sense `feat.saveux`'s `SaveManual` produces one (same `Participant` registry, same `int.serializer` bundle shape — header + shards) — never a diff against a parent checkpoint or a partial subset of registered participants. Check: `go doc ./internal/engine/checkpoint CreateCheckpoint` (or equivalent) shows it delegating to (not reimplementing) `feat.saveux`'s save path — `grep -n "save\.\(SaveManual\|Participant\)" internal/engine/checkpoint/*.go` matches; a passing test creates a checkpoint against a fixture world with non-trivial state in at least two registered participants and asserts `serialize.ValidateBundle` passes on the result with **zero** dependency on any other bundle being present on disk (delete every other file under the checkpoint root first, then assert `Load` still fully reconstructs state) — this is the check that rejects a lazy delta-against-parent implementation, which would fail exactly this deletion test.
- **AC-2 (reload reproduces exact state, GR#12).** Loading a checkpoint reconstructs participant state field-by-field identical to what was live at creation — not "load returned no error." Check: mirrors `feat.saveux` AC-3(c) exactly: a passing test creates a checkpoint, mutates the live fixture world further, then loads the checkpoint back and asserts the reconstructed state equals the pre-mutation snapshot, never the current live state.
- **AC-3 (revert creates a fork, never overwrites the abandoned branch).** Reverting to checkpoint X makes X the head of a **new** active branch and leaves whatever branch was active immediately before the revert fully intact and independently loadable — nothing is deleted, truncated, or silently rebased onto X by the act of reverting itself (pruning is AC-6/AC-7's separate, bounded concern). Check: a passing test creates checkpoint A, advances play to produce further checkpoints B and C off A, reverts to A (creating branch D), and asserts (a) B and C are both still present and independently loadable via this package's own `Load`, each reconstructing the exact state they held before the revert, and (b) D is a new, distinct branch identity, not a rename/mutation of B or C's branch identity.
- **AC-4 (lineage is a tree with recorded parentage, not inferred from timestamps).** Every checkpoint records its immediate parent checkpoint (the one it was created from, or the one that was active when a revert produced it) as an explicit, typed field — never inferred after the fact from creation-time ordering. Check: `go doc ./internal/engine/checkpoint` shows a `ParentID` (or equivalent) field on the checkpoint/branch metadata type; a passing test builds the A→{B,C}, revert-to-A→D shape from AC-3 and asserts a lineage-query function returns D's parent as A and B/C's parent as A, not derivable only by comparing `CreatedAtTick` values (a test that shuffles creation order among sibling branches and still gets correct parentage back is the check that rejects a timestamp-inference implementation).
- **AC-5 (lineage query surface for a future save-UI tree, US-4, US-6).** A `Lineage(root string) (Tree, error)` (or equivalent) function returns, for every discoverable checkpoint/branch under a checkpoint root, at minimum: an identifier, its `ParentID` (AC-4), `CreatedAtTick`/`GameMonth`, and whether it is the currently-active head of a branch — sourced from metadata only, mirroring `feat.saveux` AC-8's "never opens a shard file to answer this" discipline. Check: `go doc ./internal/engine/checkpoint Lineage` (or equivalent) documents the returned shape; a passing test deletes every shard file from a checkpoint bundle after writing it (leaving only its metadata) and asserts `Lineage` still succeeds and reports correct parentage and identifiers — same proof pattern `feat.saveux` AC-8 already established, applied here.

### Bounded fork tree (Aaron's ruling — N is a placeholder, see Escalations/Assumptions)

- **AC-6 (N most recent abandoned branches remain loadable — N is a named, overridable constant, never a bare literal).** The count of abandoned (non-head, non-ancestor-of-a-retained-head) branches retained as independently loadable is governed by a single named constant/config value (e.g. `MaxRetainedForks`), not a number written inline at each call site, and its current placeholder value is documented as **pending Aaron's balance-regime approval** (per the standing rule — placeholder + directional tests + delegated proposal + Aaron's row-by-row approval + balance pass), not asserted as final. Check: `grep -rn "MaxRetainedForks\|maxRetainedForks" internal/engine/checkpoint/*.go` shows exactly one definition site (constant or config-loaded value, per GR#15 — "validators derive from data" applies here too if it ends up data-file-sourced rather than a Go const) and every enforcement site referencing that name, never a re-typed literal; `internal/engine/checkpoint/doc.go` states in prose that the value is a balance placeholder pending Aaron's approval. **What this rejects:** an implementation that hardcodes `if len(abandoned) > 10` at the prune call site passes a naive "keeps roughly 10" functional test while failing this check and while making Aaron's eventual approval a multi-site find-and-replace instead of a one-line change.
- **AC-7 (retention is by branch count, not calendar time, and is exhaustively testable at any N).** The pruning rule — "the N most recent abandoned branches remain loadable, older ones auto-prune" — is verified with a test parameterised over at least two different values of the `MaxRetainedForks` constant (e.g. run the same test body with N=2 and N=5, per this file's balance-placeholder framing: the *shape* of the rule must hold at any N, not just whatever number is currently checked in), asserting after each of several sequential reverts that exactly the N most-recently-abandoned branches remain loadable and any older ones no longer do. Check: `grep -rn "func Test.*[Pp]rune\|func Test.*[Rr]etention" internal/engine/checkpoint/*_test.go` shows a table-driven or parameterised test varying N, not a single test hardcoded against whatever N happens to be set to today — a test that only passes at the current placeholder value and would silently need rewriting the day Aaron approves a different N has failed this AC.
- **AC-8 (pruning never deletes a checkpoint that is still an ancestor of a retained branch — structural sharing).** Because the lineage is a tree, an old checkpoint can be the shared ancestor of both a still-retained branch and a branch old enough to prune; pruning removes only branch heads (and any checkpoints exclusively on a pruned branch's own path with no other retained descendant) and never removes a checkpoint that any retained branch's lineage chain (AC-4) still passes through. Check: a passing test builds a tree where an old checkpoint A has two children — B (later pruned past retention) and C (kept, e.g. still the active head or within the retained N) — prunes until B falls outside retention, and asserts A is still loadable (it is C's ancestor) while B's own exclusive branch content is gone. **False-pass this guards against:** a prune implementation that walks "delete anything older than the Nth-most-recent branch" by raw checkpoint age rather than by branch-exclusivity would delete A and silently break C's lineage chain and (per AC-2) C's own ability to reconstruct its full history — the test must assert on C's continued loadability and correct lineage, not merely on B's absence.
- **AC-9 (pruning is atomic against a failed or interrupted prune — mirrors `feat.saveux` AC-13's error-path pattern).** If pruning the oldest-beyond-retention branch fails partway (I/O error, process interruption), the retained set is left exactly as it was before the prune attempt — no branch is left half-deleted, and no branch that should have survived retention is missing because a prune that never completed was assumed to have. Check: a passing test forces a mid-prune failure and asserts, via `Lineage`, that every branch present before the failed prune attempt is still present and still independently loadable afterward.

### Lineage tree UI surface (structural existence, not full UI polish)

- **AC-10 (US-4 — the tree shape a save-UI screen needs exists and is directly renderable, not reconstructed by the UI from a flat list).** `Lineage`'s (AC-5) returned type is a **tree structure** (parent→children navigable, or an edge list a caller can build one from in O(n) without re-deriving relationships) — not merely a flat, unordered slice of checkpoint records that leaves "which branched from which" for a future UI screen to re-infer. Check: `go doc ./internal/engine/checkpoint Tree` (or equivalent) shows either an explicit `Children []*Node`-shaped structure or a documented edge-list contract; a passing test builds the A→{B,C}, revert-to-A→D shape from AC-3 and asserts the returned structure's root-to-leaf paths correctly reflect that lineage, checked by walking the structure itself (not by re-deriving it from `ParentID` fields a second time in the test, since that would only prove AC-4's data is right, not that this AC's *structure* is navigable). This item does not render the tree — a future `internal/ui/screens/...` item consumes this structure, same split as `feat.saveux`'s `List`/UI boundary.

### Determinism & replay integration (grounded in what `harness.replay` actually does today)

`harness.replay` (MOD-013, as built to `docs/planning/acceptance/harness.replay.md`) provides: a `Recorder` that taps a live `protocol.Transport` and records every `Command`/`Event`/`Delta` into an `int.serializer`-backed fixture (its AC-1/AC-2); a `Player` with a regression mode (`EnginePlayer`, AC-3(b)) that replays a recorded command sequence into a live engine; and a `CompareResult`-producing diff (AC-5) between the replayed run's re-emitted stream/state and the original recording — proven non-trivial by a test asserting a deliberately mismatched fixture produces a non-empty diff. It does **not** today have any notion of a checkpoint, a fork, or a branch — those are this item's vocabulary, not `harness.replay`'s. The ACs below are written to use `harness.replay`'s existing Recorder/Player/CompareResult surface exactly as built, not a fork-aware capability that does not exist.

- **AC-11 (per-branch command log, reusing `harness.replay.Recorder` rather than reimplementing capture).** From the moment a branch becomes the active head (checkpoint creation or revert), every `Command` driving that branch is captured via `harness.replay`'s own `Recorder` type tapping the live engine's `protocol.Transport` (`grep -n "replay\.Recorder\|replay\.NewRecorder" internal/engine/checkpoint/*.go` shows this package constructing/using the existing type, not a second command-log encoder) — the branch's checkpoint bundle plus its recorded command log together are what AC-12 verifies. Check: a passing test creates a checkpoint, drives several commands through the live engine, and asserts a `harness.replay`-shaped fixture exists correlated to that branch (by branch identifier, not by guessing a filename).
- **AC-12 (fork integrity verification — Aaron's "replay harness verifies fork integrity", made concrete).** For a given branch, fork integrity means: (a) reloading the branch's originating checkpoint bundle reproduces the exact state present at the fork point (this is AC-2, restated as the base case), and (b) replaying that branch's recorded command log (AC-11) via `harness.replay`'s `EnginePlayer` regression mode against a freshly-loaded copy of the originating checkpoint produces a `CompareResult` diff that is empty against the branch's live state at the moment of verification (`harness.replay` AC-5's existing comparison, invoked here rather than reinvented). Check: `go doc ./internal/engine/checkpoint VerifyForkIntegrity` (or equivalent) documents both halves; a passing test builds a branch with several post-checkpoint commands, calls the verification function, and asserts a clean result — then deliberately corrupts one command in the recorded log (mirroring `harness.replay`'s own mismatch test, AC-5) and asserts verification reports the resulting non-empty diff rather than false-passing.
- **AC-13 (byte-determinism of the checkpoint bundle itself, GR#21 — mirrors `feat.saveux` AC-14).** Two checkpoints taken from the same deterministic state produce byte-identical bundles across every file (header, every shard, this item's own lineage/parentage metadata) — same proof shape as `feat.saveux` AC-14, applied to checkpoint bundles specifically since they carry an extra `ParentID`/branch-identity field `feat.saveux`'s own bundles do not. Check: a passing test drives the same fixture through checkpoint creation twice into two directories and walks both trees comparing every file's bytes.
- **AC-14 (SG-7 scoped, GR#21).** `grep -rn "time.Now\|time.Since\|time.Ticker\|time.Sleep" internal/engine/checkpoint/*.go` (excluding `_test.go`) returns no matches, except any field explicitly documented as display-only UI metadata never read by any determinism-sensitive path (same exception shape as `feat.saveux` AC-15).

## Spec-fold amendments (FEAT-084 SF wave, 2026-08-19)

> Substantive AC amendments folded from the FEAT-084 ASM disposition (class SF). All six fold from the FEAT-084 re-baseline roster (classified there under feat.saveux/feat.checkpoint; re-read attributes all six to feat.checkpoint — `internal/engine/checkpoint/`, `code.json: feat.checkpoint`).

### ASM-1334 — on-disk lineage layout: manual saves + sidecar + root head pointer (amends AC-1/AC-3)
Checkpoints are stored as `feat.saveux` manual saves under `manual/<id>/` plus a `checkpoint-meta.json` sidecar and a **single root-level `checkpoint-head.json`** active-head pointer. A revert updates exactly one file (the head pointer) and never mutates an abandoned branch (AC-3). A fourth `SaveKind` inside `feat.saveux` was deliberately **not** added (per prior BA assumption 3). Check: the layout reuses `SaveManual` (AC-1); if Bill later prefers checkpoints as a `SaveKind`, the layout and the `manualSubdir` drift test change.

### ASM-1335 — revert = load-then-fork, never a bare re-point (amends AC-3/AC-4)
`Revert(target)` restores target state via `feat.saveux` Load and then creates a **NEW** fork checkpoint with `ParentID=target` capturing that state, so the revert-produced branch D is a real whole-state bundle with a distinct branch identity (AC-3(b)/AC-4) — not a re-point that would leave D unloadable and force AC-3(b)/AC-4 rewording.

### ASM-1388 — maxSaveNameLen duplicated across the module boundary (amends AC-1/AC-13)
`feat.saveux` does not export `maxSaveNameLen` and GR#20 forbids the import surface, so this package duplicates the 255 constant (sanctioned weakness-pattern-#2) as `maxSaveNameLen`, derives `maxCheckpointNameLen` from it, and extends `TestMaxCheckpointNameLenTracksSaveManualLimit` to probe save's real limit. Check: if save's limit ever changes, that drift test fails rather than silently producing over-length fork names (AC-13).

### ASM-1339 — dangling-parent rejection (amends AC-4)
`CreateCheckpoint` rejects a non-empty `ParentID` that does not name an existing checkpoint with `ErrParentNotFound` — boundary validation for AC-4's explicit parentage (the ACs do not literally require it; the Destructive input-validation mandate and recurring checklist 3 do), preventing a dangling parent from silently corrupting the lineage tree.

### ASM-1340 — deterministic fork naming (amends AC-13)
Revert auto-names its new checkpoint `<target>.fork<N>` with a monotonic `forkSeq` persisted in `checkpoint-head.json`, incremented with saturating arithmetic (`foundation/num`, GR#16). This keeps the name deterministic (AC-13) and unique across repeated reverts to the same target — a fixed suffix would save-over the first fork.

### ASM-1373 — bundleExists occupant semantics (amends AC-1/AC-3)
`bundleExists` treats **any** filesystem entry at `manual/<id>` (file or dir) as an occupant (mirroring `isCheckpoint`'s strict `err == nil` style) — judged stricter than needed, so a stray non-directory file blocks a checkpoint create and no overwrite is ever risked. The drift test probes save's unexported `maxSaveNameLen` by binary-searching `SaveManual` behaviour (GR#20 forbids importing the constant).

- **ASM-1336 (confirm-and-close).** Most-recently-abandoned retention uses `CreatedAtTick` as the deterministic recency proxy (no abandonment-time field exists) and leaf nodes as non-active branches; if recency should mean most-recently-ABANDONED a long-active-then-abandoned branch orders differently, but the retention shape holds either way — only membership changes.
