# Acceptance criteria — mechanical AST-derived copy-guard gate replaces the hand sweep (BUG-024)

**BOW code:** BUG-024 (P1, open) — "Convert the copyable-struct sweep into a mechanical check and STOP hand-auditing package by package."
**Spec refs:** GR#15 (validators derive from data/runtime scans, never hardcoded constants); GR#20/#21 posture (mechanical, CI-enforced gates over remembered procedure); `dev-team-process.md` Weakness pattern #3 ("fix the class, not the demonstrated instance") — this item is that rule applied to the audit technique itself; BUG-008's `internal/foundation/errs/source_scan_test.go` (the existing AST-based gate this item is asked to mirror in approach, including its practice of declaring its own blind spots in doc comments); SEC-031/BUG-024's own comment (`errs.SetSink(l *Logger)` — the package-level-function blind spot that escaped nine manual enumerations by four agents); SEC-030/SEC-031(b) (a guard's rejection path flooding a shared bounded ring); SEC-033 (the "9 vs 14" hardcoded-count drift this item exists to make structurally impossible).
**Date:** 2026-08-10
**Status:** active
**Package under test:** new package, proposed `internal/foundation/astgate/` (module key `tool.astgate`, mirroring `tool.planguard`/`tool.secretguard`/`tool.ready`'s existing `tool.*` naming for source-scanning/CI-gate tooling — **ASM-112**, logged below), driven by a `_test.go` gate analogous in shape to `TestSourceCodesAreRegisteredAndInRange`, plus a wire-up in `.github/workflows/ci.yml`.

## User stories

- As the **project's security posture**, I need every struct that mixes a `sync.Mutex`/`sync.RWMutex` value with an aliasable reference field, and every function that can receive such a struct — by receiver **or by parameter** — enumerated mechanically from source, so that a SEC-020-class copy hazard can never again depend on a human correctly remembering to grep for it.
- As **Bill (lead) and the Testers**, I need this gate to run in CI on every push/PR, so that the retired hand-sweep is replaced by a standing control rather than a one-time cleanup that silently rots the next time a guarded type or a package-level constructor is added.
- As a **future developer adding a new guarded type**, I need a gate failure to tell me exactly which type, which file/line, and which unguarded function is the problem, so I can fix it without first having to reverse-engineer what the gate checks.

## Acceptance criteria

### Functional — candidate enumeration (scope item 1)

- **AC-1.** The gate walks the AST of `cmd/` and `internal/` (excluding `_test.go`, mirroring `scanSourceCodes`'s existing precedent and rationale — fixture/test types are not production copy hazards) and identifies every **candidate type**: a `struct` type declaration with (a) at least one field of type `sync.Mutex` or `sync.RWMutex` **by value** (not `*sync.Mutex`/`*sync.RWMutex` — a pointer field aliases the same mutex across copies and is a different, non-SEC-020-shaped hazard out of this item's scope, per BUG-024's own definition of done), AND (b) at least one field whose type is a slice, map, channel, or pointer (the "aliasable reference field" set BUG-024's own description names). Check: a fixture package under a test-only temp tree (mirroring `TestScanSourceCodes_LiteralsOnlyNotComments`'s pattern) containing one struct matching both conditions and one struct matching only one condition; the gate's candidate list includes the first and excludes the second.
- **AC-2.** Candidate identification does not depend on any hardcoded type name, package path, or count — it is derived purely from the AST shape described in AC-1 (GR#15; see AC-11).

### Functional — reachable-function enumeration, the documented blind spot (scope item 2)

- **AC-3 (the core of this item — must be explicit and independently testable).** For each candidate type `T`, the gate enumerates **every function in scanned source that can receive a `T` or `*T`**, split into two distinct sets it must both populate:
  - (a) **receiver methods** — `func (x T) M(...)` and `func (x *T) M(...)`;
  - (b) **package-level functions taking `T`/`*T` as a parameter** — e.g. `func SetSink(l *Logger)` — regardless of parameter position or name.
  Check: a fixture package containing a candidate type `Guarded`, one receiver method on it, and one package-level function `func Consume(g *Guarded)` that is **not** a method. A unit test on the enumeration function alone (not the full gate) asserts `Consume` appears in the reachable-function list. This is the direct regression test for the blind spot named in BUG-024's dispatch comment (`errs.SetSink` escaped nine manual passes because every pass only grepped `func (x *T)`).
- **AC-4.** For each function found in AC-3, the gate determines whether it "guards" — i.e., its body contains a call recognisable as an identity/copy check on the receiver or the relevant parameter (the concrete pattern already in the codebase: a call to a method named `checkNotCopied` — or equivalent — reached on that value, per `checkNotCopied`'s doc comments in `internal/foundation/errs/log.go` and `internal/protocol/transport.go`). A function with no such call, for a candidate type, is **unguarded** and is a violation. Check: in the same fixture package, `Consume` (no guard call) is reported unguarded; a second fixture function that does call a `checkNotCopied`-shaped method first is reported guarded.
- **AC-5.** The gate's own doc comment states, in the same style as `scanSourceCodes`'s "Known blind spots" comment, what detection heuristic AC-4 uses to recognize a "guard call" and what it will miss (e.g. a guard reached indirectly through a helper function one level removed, a guard implemented via a naming convention other than `checkNotCopied`, or a guard on an interface-typed parameter whose concrete type is only known at runtime). Declaring the heuristic's limits is a pass/fail requirement of this criterion, not optional documentation — this is the same discipline BUG-024's own description asks for ("declare its blind spots honestly the way BUG-008 source-scan gate does").

### Functional — flooding-risk flag on rejection paths (scope item 3)

- **AC-6.** For each function found unguarded in AC-4, that is a hard violation (fails the gate). Separately, for functions the gate confirms **are** guarded, the gate additionally inspects each guard's rejection path (the code reached when the identity check fails) and flags — as a named, distinct category of output, not merged into the pass/fail violation list — any rejection path whose reachable statements include a call that writes into a **bounded shared package-level resource**: concretely, a call reachable from the rejection branch that targets a package-level variable of a fixed-capacity type (the existing `ringBuffer`/`copyRejectRing` shape in `internal/foundation/errs/log.go` is the positive fixture; `SEC-030`/`SEC-031(b)`'s pre-fix shape — a rejection path pushing into the same unbounded-relative-to-call-rate `ring` genuine entries are read from — is the fixture this must flag). Check: a fixture guarded function whose rejection path calls `push` on a package-level ring-shaped variable used elsewhere by a non-rejection code path is flagged; a fixture guarded function whose rejection path writes to its own dedicated, unshared buffer (the post-SEC-031(b) `copyRejectRing` shape) is not flagged.
- **AC-7.** AC-6's flag is advisory (does not fail the gate on its own) unless Bill's final review elects otherwise per-instance — this is a heuristic pattern-matcher for a resource-exhaustion shape, not a proof of exploitability, and false positives are expected and acceptable; the gate's output/failure message (see AC-13) must label AC-6 findings distinctly from AC-4's hard violations so a developer cannot mistake an advisory flag for a build-breaking failure or vice versa. **ASM-113**, logged below, records this scoping choice.

### Functional — proof the gate can fail (scope item 4)

- **AC-8 (mandatory, non-negotiable per BUG-024 and process v1.7's "fast path" guidance on regression tests that cannot fail).** The gate's test suite includes at least one **fixture-driven negative control**, analogous to `TestVerifySourceCodes_CatchesUnregisteredCode`/`CatchesRangeOwnershipViolation`/`CatchesUndeclaredRange`: a fixture package defining a struct matching AC-1's candidate shape with **zero** guarded reachable functions, run through the real gate logic (not an assertion of intent), asserting the gate reports at least one violation naming that type. This is evidence the gate detects a deliberately-unguarded type, not a claim that it does.
- **AC-9.** A second fixture proves the AC-3 blind spot specifically does not recur: a candidate type with a fully-guarded receiver-method surface but one **unguarded package-level function** taking it by parameter (mirroring `SetSink`'s exact shape) must be reported as a violation. A gate that only checks methods and passes this fixture is itself a FAIL of this criterion — this is the regression test for the actual incident BUG-024 was filed over, not a generic robustness check.
- **AC-10.** A third fixture proves the clean case: a candidate type where every reachable function (both receiver methods and package-level functions) guards correctly produces **zero** violations — this is what proves AC-8/AC-9's fixtures are exercising real detection logic and not e.g. an off-by-default gate that always reports violations, or a gate that only ever passes.

### GR#15 — no hardcoded counts (scope item 5)

- **AC-11.** No literal count of guarded types, candidate types, or reachable functions appears anywhere in the gate's source or its tests as an expected-value assertion (e.g. no `if len(candidates) != 14`). Any assertion about "how many" must be derived either (a) from the AST scan performed live within the same test run, or (b) by counting entries the test itself constructs as fixture input — never a hardcoded literal standing in for a live count of production code. Check: `grep`-style review of the gate's test file(s) for any bare integer literal compared against a scan result over the real `cmd/`/`internal/` tree; the only permitted integer literals are fixture-construction counts and the AC-8/AC-9/AC-10 "at least one violation" / "zero violations" assertions, which are structural, not population counts. This is the direct, mechanical prevention of the SEC-033 "9 vs 14" drift — a stale comment asserting the count silently diverged from reality until a Tester counted by hand; this gate itself must never repeat that shape.
- **AC-12.** If the gate's own source or doc comments state, in prose, how many candidate types currently exist in the live tree (for narrative/context purposes only, as `coalesceScanBack`'s doc comment now does correctly for `ringCapacity`-adjacent reasoning), that prose must not be used as an input to any pass/fail check — Tester and Destructive-agent review confirms no code path reads that comment-stated number.

### CI wiring and failure messaging (scope item 6)

- **AC-13.** The gate runs as part of the standard `go test ./...` surface in the existing `build-test-vet` CI job in `.github/workflows/ci.yml` (the same job `TestSourceCodesAreRegisteredAndInRange` runs under, per that job's existing `go test ./... -race -count=1` step) — **not** a new bespoke job, unless Bill's review determines during commit that the astgate package needs isolation (e.g. because AST-walking the whole repo is slow enough to want its own job with a longer timeout); if a separate job is added instead, it must be named descriptively (e.g. `copy-guard-gate`) and documented in the same file-header comment block `ci.yml` already uses for `determinism-gate` and `golangci-lint`. **ASM-111**, logged below, records this default-to-existing-job choice and what would change it.
- **AC-14.** A gate failure's message, for each hard violation (AC-4/AC-8/AC-9), names: the candidate type and its file:line; the specific unguarded function's name, file:line, and whether it was found via the receiver-method path or the package-level-function path (so a developer immediately knows which enumeration caught it — directly answering "how would I have found this myself"); and a one-line remedy pointing at the existing pattern (`checkNotCopied`, `atomic.Pointer[T]` `self` field, pre-lock check) with a reference to one real guarded type in the codebase as a worked example (e.g. `internal/foundation/errs/log.go`'s `Logger`). This mirrors `verifySourceCodes`'s existing violation-message discipline (code, location, exact remedy) rather than a bare `got X, want Y`.
- **AC-15.** AC-6's advisory flags, when any exist, are included in the gate's test output (e.g. via `t.Logf`, matching how `TestSEC034_PreFixLoopStillReportsFalseAlarms` logs its false-alarm count for visibility without failing the build on that line alone) but do not by themselves cause a non-zero exit from the CI step — consistent with AC-7.

## Out of scope

- Fixing any violation the gate finds in the live tree on first run — this item is the gate itself; any live finding it produces is filed as its own SEC-/BUG- item per the existing process, not resolved inside this criteria set.
- Detecting mutex-hazard shapes other than the one named in AC-1 (e.g. a `*sync.Mutex` pointer field, `sync.RWMutex` embedded via an embedded struct one level removed, or non-Go-native synchronization primitives) — these are named as explicit blind spots per AC-5's disclosure requirement, not silently handled.
- Replacing `golangci-lint`'s `depguard` (GR#20) or `TestSourceCodesAreRegisteredAndInRange` (BUG-008) — this is a new, additional gate alongside them, not a consolidation of the existing ones.
- Any change to the nine-now-fourteen already-fixed SEC-020 guarded types beyond what the gate needs to use as positive fixtures/worked examples.

## Escalations

- Whether AC-6's flag should eventually be promoted to a hard failure once the pattern is well understood (per AC-7) is a call for Bill, not resolved here — flagged so it isn't silently forgotten as a "someday" item.
- Whether `internal/foundation/astgate` is the right final package location and `tool.astgate` the right final module key (ASM-112) is subject to Bill's architectural review at build dispatch time.

## Assumptions logged (process v1.7)

- **ASM-112** — package location `internal/foundation/astgate/` and module key `tool.astgate`, following the existing `tool.planguard`/`tool.secretguard`/`tool.ready` naming convention for source-scanning CI-gate tooling, since BUG-024's own BOW item is filed under `foundation.errors` (co-located with the BUG-008 gate it was asked to mirror) but the dispatch prompt for these criteria explicitly names the target file `tool.astgate.md`. What breaks if wrong: the junior developer builds in a location or under a module key the lead didn't intend, requiring a mechanical rename rather than a design change — low cost, but logged because a reasonable person could have placed this inside `internal/foundation/errs/` instead (matching BUG-024's own filed code-path), and the acceptance file's own filename is the only signal pointing the other way.
- **ASM-113** — the flooding-risk check (AC-6/AC-7, scope item 3) is scoped as advisory-only, not gate-failing, because the concrete instances of this shape (SEC-030, SEC-031(b)) are already fixed in the live tree, and a heuristic "does this rejection path touch a bounded shared resource" check is expected to have false positives (e.g. a rejection path that logs via `errs.New`, which itself falls back to a ring buffer only on sink failure — indirect, not the direct shape SEC-030 was). What breaks if wrong: if Bill intends this to be a hard gate-failing check from day one, the junior builds the wrong severity and it needs a small follow-up change to promote it; if a real new SEC-030-shaped instance ships in the interim because the check was advisory rather than blocking, that is the concrete cost of getting this wrong.
- **ASM-111** — CI wiring defaults to reusing the existing `build-test-vet` job's `go test ./... -race -count=1` step rather than adding a new job, on the reasoning that BUG-008's own AST-based gate (`TestSourceCodesAreRegisteredAndInRange`) already runs there successfully and this gate is the same shape (an AST walk over `cmd/`+`internal/` as an ordinary Go test). What breaks if wrong: if walking the AST for reachable-function enumeration (AC-3) across the whole tree turns out to be slow enough to meaningfully lengthen `build-test-vet`'s critical path, the junior/lead will need to split it into its own job at build time rather than at criteria time — a config change, not a design change, so the cost of this assumption being wrong is low but non-zero CI minutes.

## SEC-048 — `gate.go`'s bare `fmt.Errorf` (GR#7 exemption, P3)

**Finding:** `node claude-bow.js show SEC-048`. `internal/foundation/astgate/gate.go` uses bare `fmt.Errorf` at three sites with no documented GR#7 exemption anywhere in the file, confirmed on read:
- **line 619** (`loadPackages`, inside the `filepath.WalkDir` callback): `parser.ParseFile` failed on a source file the gate is scanning — `fmt.Errorf("parsing %s: %w", path, perr)`. Wraps a real `go/parser` syntax error.
- **line 631** (`loadPackages`, after the `WalkDir` call): the directory walk itself failed — `fmt.Errorf("scanning %s: %w", root, err)`. Wraps a real `filepath.WalkDir`/filesystem error.
- **line 737** (`resolveRepoRoot`): walked up from `os.Getwd()` to filesystem root without finding a `go.mod` — `fmt.Errorf("astgate: no go.mod found walking up from %s", dir)`. A self-contained astgate error, no wrapped cause.

All three are genuine internal scan-failure conditions (malformed/unreadable source, a broken walk, a missing `go.mod`), not user input rejections and not GR#1 display-path errors — `Run`/`loadPackages`/`resolveRepoRoot` are plain `(T, error)`-returning internal functions today; none of them accept, thread, or mint a `correlationID`, and nothing in `astgate` calls `errs.New`/`errs.Wrap` anywhere else in the file. This is the same bare-`fmt.Errorf` shape SEC-040 found in `internal/harness/replay/gen/main.go`, which resolved to either the `legacy.versionguard`-precedent exemption comment or full `errs.New` conversion (`docs/planning/acceptance/harness.replay.md` AC-18/AC-19). SEC-048's own filing flags the distinguishing fact that matters here: unlike `gen/main.go` (`//go:build ignore`'d out of the shipped binary, run only by hand), `astgate` **is** compiled and exercised by `go test ./...` inside the `build-test-vet` CI job (BUG-024 AC-13) — it is a live, standing CI gate, not a dev-only fixture tool.

That distinction is why this item's AC states a preference rather than SEC-040's neutral either/or, and the preference is grounded in what actually differs about astgate's own code, not asserted on the P3/"real gate" framing alone:

- Unlike `gen/main.go` (which sits outside every registry layer — the `T` "tooling" layer is explicitly documented in `data/errors.json`'s `ranges.layers` as JS build/plan scripts, "currently JS, outside the Go registry"), `astgate` physically lives at `internal/foundation/astgate/`, squarely inside the **`F` — foundation** layer's own path scope (`ranges.layers.F`: "internal/foundation/* (registry, correlation IDs, logging, determinism, serialization, solver, build info)"). A same-layer precedent for claiming a fresh sub-range already exists: `foundation.data` claimed `F600-F699` as "the next free F-sub-range" when `F400-F499` was already taken. As of this read, `F700-F799` is free in both `data/errors.json`'s `ranges.reserved` table and a live `grep -rn "MET-F7" internal/ cmd/` (zero matches) — so a registry claim for astgate's three errors has an unclaimed range ready and a direct sibling precedent to follow, unlike SEC-040's tool which had no natural layer at all.
- The real cost of conversion is not the registry claim — it's that `errs.New`/`errs.Wrap` require a non-empty `correlationID`, and `Run`, `loadPackages`, and `resolveRepoRoot` have no such parameter today. Converting for real (not cosmetically) means either threading a `correlationID` through `Run`'s exported signature, or minting one inline at the site with no caller-supplied ID — `internal/engine/invariant/registry.go:96`'s `errs.New(ErrNilInvariant, errs.NewCorrelationID(), nil)` is the exact precedent for that second option, already established elsewhere in this codebase, so this is not a novel pattern to invent.

- **AC-16 (preferred: registry conversion).** All three cited bare `fmt.Errorf` error-construction sites (lines 619, 631, 737, or wherever they've moved to if the file changed further) convert to `errs.New`/`errs.Wrap`, with three new `MET-F7NN` codes registered in `data/errors.json` under the next free F-layer sub-range (`F700-F799` as of this writing — reverify against both the `ranges.reserved` table AND a live `grep -rn "MET-F7" internal/ cmd/` before claiming, per BUG-008's standing lesson that the table alone is not always current) and a module entry for `tool.astgate` (or whichever module key Bill's review ultimately settles per BUG-024's own ASM-112 escalation — this AC does not re-litigate that choice). Because no astgate function currently accepts or mints a `correlationID`, satisfying `errs.New`'s required parameter means either (a) adding a `correlationID` parameter to `Run`'s exported signature and threading it down through `loadPackages`, or (b) minting one inline at each site with `errs.NewCorrelationID()`, mirroring `internal/engine/invariant/registry.go:96`'s precedent for a call site with no caller-supplied ID — Bill's review picks which, but a hardcoded empty-string literal satisfies neither.
  **Check:** `grep -n "fmt.Errorf" internal/foundation/astgate/gate.go` returns no matches for error-construction call sites (the `violationMessage`/`floodMessage` `fmt.Sprintf` calls at lines ~696/715 are message formatting for the gate's own output, not error construction, and are unaffected either way); `grep -n "errs.New\|errs.Wrap" internal/foundation/astgate/gate.go` matches at all three former sites; the three new codes appear in `data/errors.json` with a claimed sub-range and module entry.
  **What a lazy implementation looks like:** calling `errs.New(code, "", ctx)` with a bare empty-string correlation-ID literal at each site — this compiles, satisfies the grep, and technically "converts" the call sites, but fires the `MET-F004` missing-correlation warning on every single astgate error, which is strictly worse observability than the bare `fmt.Errorf` it replaced. It is not a passing implementation of this AC.
  **False-pass warning:** converting only one or two of the three sites (e.g. the two `loadPackages` sites but not `resolveRepoRoot`'s self-contained error) and leaving the rest bare would pass a shallow "some `errs.New` calls exist now" check while leaving GR#7's actual complaint — an undocumented bare `fmt.Errorf` — still true at the untouched site(s); AC-16's check requires zero remaining bare `fmt.Errorf` construction sites, not "at least one converted."
- **AC-17 (fallback: documented exemption, only if AC-16 is explicitly rejected).** If Bill's review determines during build that threading or minting a `correlationID` into these three internal-scan-failure sites is disproportionate for a P3 finding whose only real consumer today is `go test`'s own failure output (astgate has no GR#1 user-facing display path at all currently), the fallback is a documented exemption matching the `legacy.versionguard` precedent's own convention (per SEC-040 AC-18(a)): a comment added to `gate.go`'s top-of-file doc comment (or, if none exists yet, a new one immediately above the package clause) stating explicitly that the file is exempt from GR#7's registry-error requirement, why (naming the specific reason rejected in this AC — not a generic "it's just tooling," since SEC-048's own filing already flagged that reasoning as weaker here than it was for SEC-040), and citing both the Golden Rule and the BOW code (`GR#7`, `SEC-048`) so a future reader or a strict-mode GR#7 scanner can trace it back to this record.
  **Check:** `grep -n "GR#7\|SEC-048" internal/foundation/astgate/gate.go` matches within the top doc-comment block; the comment's stated reason is not merely "dev tool" or "internal only" (astgate is neither — it runs inside the compiled, CI-gated `build-test-vet` job) but explicitly addresses the correlation-ID threading cost named above.
  **What a lazy implementation looks like:** copying SEC-040's `gen/main.go` exemption wording verbatim (substituting the BOW code) — that comment's own rationale leans on "dev-only, `//go:build ignore`'d, errors only ever reach a developer's terminal," none of which is true of `astgate`; reusing it would state a false justification for the exemption rather than the one this AC actually requires.
- **AC-18.** Whichever of AC-16/AC-17 is chosen, it is a complete pass — not both partially done, not some call sites converted with a dangling exemption comment left in for the others. **Check:** `internal/foundation/astgate/gate.go` contains either three converted `errs.New`/`errs.Wrap` sites with zero remaining bare `fmt.Errorf` error-construction calls and zero exemption comment, or a complete `GR#7`/`SEC-048` exemption comment with all three sites still bare `fmt.Errorf` — not a mix. If AC-17's fallback is used, the exemption comment additionally states in one sentence why AC-16 (the preferred path) was rejected, so the choice is traceable rather than a silent default to the easier option.

This is a P3/minor finding — three ACs, proportionate to "not blocking," matching SEC-040's proportionate scope while reflecting the one real difference SEC-048's filing asked to be weighed: astgate compiles and runs inside a live CI gate, `gen/main.go` does not.
