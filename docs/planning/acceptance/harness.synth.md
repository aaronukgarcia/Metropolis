## What changed since the 2026-08-08 draft

- **Weakness pattern #4 applies almost exactly to this module's stated purpose, and the old draft missed it entirely.** SEC-009 — one of the sweep's nine `input-validation` findings — was `Extent.Width/Height off the wire` used as an **allocation size**, causing OOM from a single crafted message. This package's whole job is "given at minimum: target citizen count, a seed, and sprawl/network-shape parameters" (old AC-1) — `citizenCount` and the sprawl/network parameters size real memory allocation and real work (a synthetic 10M-citizen city is not a small structure). AC-1b/AC-7b below name the privileged position explicitly (allocation size / generation work), state the allowed domain positively, and require rejection rather than silent clamping — even though this tool's callers are CI/developers, not an external attacker, the *shape* of the risk (an unbounded size parameter driving unbounded allocation) is identical, and CI itself is worth protecting from an accidental fat-fingered `citizenCount` bringing down a runner.
- **The old draft's AC-7 (invalid-parameter rejection) already existed but didn't name the privileged position or state the domain positively** — "negative population, sprawl parameter outside its documented domain" is closer to the banned "handles malformed input gracefully" phrasing than the new house standard requires. Rewritten as AC-7b below.

## User stories

- **US-1.** As the development team, I need to know the 10M-citizen monthly-tick cost in month 3 of development (Sprint 2), not month 30 (M0-ENG §2.4), so that a scale problem is discovered while there is still runway to pull the GPU sidecar forward per the sprint plan's guard-rail.
- **US-2.** As CI, I need parametric synthetic cities (population, sprawl, network shape) generated deterministically from a seed and a size parameter, so that every commit can be perf-tested against the same reproducible scale points without needing a hand-built save.
- **US-3.** As the perf CI job, I need tick-time-vs-scale graphed per commit and a hard fail when monthly-tick time regresses >10% at the 1M-citizen synthetic, so that performance is a test, not a hope (M0-ENG §6 point 5).
- **US-4.** As `balance.harness` (a later, Sprint 8 consumer per code.json), I need H-SYNTH's generated worlds to be usable as its own parameter-sweep inputs, so that balance tuning and perf testing share one synthetic-city generator rather than two.

## Scope

Parametric synthetic-city generation (population, sprawl, network shape, seeded/deterministic) and the perf CI job that graphs tick-time vs. scale per commit and fails on >10% regression at the 1M-citizen synthetic.

## Acceptance criteria

### Functional

- **AC-1.** A `Generator` (or equivalent) exists that produces a synthetic world/save given at minimum: target citizen count, a seed, and sprawl/network-shape parameters. Check: `go doc ./internal/harness/synth Generator` (or top-level `Generate` function) shows these parameters.
- **AC-1b (weakness pattern #4 — citizenCount/sprawl parameters size real allocation, name it and bound it).** **(a) The privileged position:** `citizenCount` and every sprawl/network-shape numeric parameter directly determine the size of memory allocated and the amount of generation work performed (a synthetic city's cell grid, road graph, and per-citizen records scale with these inputs) — this is `Extent.Width/Height`'s SEC-009 shape, not a cosmetic parameter. **(b) The allowed domain, stated positively:** a documented hard ceiling (e.g. `MaxSyntheticCitizens`, a named constant — the largest legitimate preset per AC-3 plus headroom, not "whatever fits in RAM") and a documented minimum (`>= 1`), both enforced before any allocation begins, not discovered via an `OutOfMemory` crash partway through generation. **(c) Reject, don't clamp:** a request exceeding the ceiling or below the minimum is rejected with a registry-sourced error naming the requested value and the ceiling/floor — never silently clamped to the nearest legal value (a clamp would let a CI job asking for 500M citizens "succeed" while silently testing 10M, hiding exactly the kind of scale mistake this module exists to catch). Check: `grep -n "MaxSyntheticCitizens\|maxCitizenCount" internal/harness/synth/*.go` shows a named ceiling constant; a passing test asserts a request exceeding the ceiling is rejected before any generation work starts, not clamped (`grep -rn "func Test.*[Cc]eiling\|func Test.*[Tt]ooLarge" internal/harness/synth/*_test.go`).
- **AC-2.** Generated worlds are consumable by `harness.headless` (`H-HEADLESS`, `metropolis -headless -seed N -months M -out snap.json` per M0-ENG §2.3) without a translation step — i.e. `Generate` produces the same save/bundle shape `int.serializer`/`engine.core` already expect. Check: a passing integration test feeds a generated world into the headless harness's run entry point (`grep -rn "headless\." internal/harness/synth/*_test.go` finds it).
- **AC-3.** At least these named scale presets exist and are individually addressable: 1M-citizen and 10M-citizen synthetics (the two figures the spec names explicitly). Check: `grep -n "1_000_000\|1000000\|10_000_000\|10000000" internal/harness/synth/*.go` finds both, ideally as named constants (`grep -n "OneMillion\|TenMillion\|Preset1M\|Preset10M"`).
- **AC-4.** A perf-measurement entry point exists that runs a synthetic city for a fixed number of simulated months under `harness.headless` and records per-phase and total monthly-tick timing. Check: `go doc ./internal/harness/synth RunPerf` (or equivalent) exists; output includes per-phase timing (matches M0-ENG §2.3's "per-phase timing + invariant reports every tick").
- **AC-5.** Timing results are persisted per-commit in a form a CI graphing step can consume (e.g. JSON/CSV keyed by commit hash and scale preset), not only printed to stdout. Check: `grep -n "json.Marshal\|csv.Writer" internal/harness/synth/perf.go` (or equivalent) matches, and a passing test asserts the output file's schema (`grep -rn "func Test.*[Pp]erf.*[Oo]utput\|func Test.*[Rr]esult" internal/harness/synth/*_test.go`).
- **AC-6.** A CI-runnable command/script (e.g. `go run ./internal/harness/synth/cmd/perfci` or documented `go test` target) exists that: generates the 1M-citizen synthetic, runs N months headless, compares monthly-tick time against a stored baseline for the current branch's parent commit, and exits non-zero on a >10% regression. Check: the command/script exists and its `--help`/doc-comment states the 10% threshold explicitly (`grep -n "10%\|0.10\|1.10" internal/harness/synth/*.go`).

### Error handling

- **AC-7 (GR#7).** Requesting an out-of-range or nonsensical parameter combination (e.g. negative population, sprawl parameter outside its documented domain) returns a registry-sourced error rather than generating a corrupt or silently-clamped world. Check: `grep -n "MET-" internal/harness/synth/*.go` finds a registry code reference; a passing test covers invalid input (`grep -rn "func Test.*[Ii]nvalid\|func Test.*[Oo]utOfRange" internal/harness/synth/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no corrupt or silently-clamped world was generated as a side effect, not merely that a matching-named test function exists.
- **AC-7b (weakness pattern #4 — supersedes AC-7's "handles ... gracefully" phrasing with a named domain).** Every parameter `Generate` accepts has its allowed domain documented positively and exhaustively in `doc.go` (not "valid population" but e.g. `citizenCount: 1..MaxSyntheticCitizens`, `sprawl: 0.0..1.0`, `networkShape: one of {grid, radial, organic}` — an explicit enum, not a free string) — every documented boundary has a corresponding rejection test (a value one below the minimum, one above the maximum, and one outside an enum's legal set), not just a generic "invalid input" test asserting the mechanism exists. Check: `doc.go` states every parameter's positive domain; `grep -rn "func Test.*[Bb]oundary\|func Test.*[Dd]omain" internal/harness/synth/*_test.go` shows per-parameter boundary coverage, not one generic invalid-input test standing in for all of them.
- **AC-8.** A missing perf baseline (first run on a new scale preset, or a fresh CI cache) does not fail the build — it records a new baseline and reports "no prior baseline to compare" rather than treating "no baseline" as a 10% regression. Check: passing test coverage (`grep -rn "func Test.*[Bb]aseline" internal/harness/synth/*_test.go`).

### Determinism & safety

- **AC-9 (GR#21).** The same `(seed, citizenCount, sprawl params)` tuple always generates a byte-identical world across repeated runs and across worker-pool sizes (consistent with §5's counter-based hash-stream determinism rule and the shard-count invariance property the sprint plan's S3 exit gate later depends on). Check: a passing test generates the same synthetic twice (and, if feasible at this stage, at two different `GOMAXPROCS`/worker settings) and asserts identical output bytes or hash (`grep -rn "func Test.*[Dd]eterminis" internal/harness/synth/*_test.go`).
- **AC-10 (M0-ENG §6 point 5; GR#21 "perf is a test, not a hope").** The perf CI command from AC-6 is wired to actually fail the build (non-zero exit) on regression — not merely log a warning. Check: `grep -n "os.Exit(1)\|log.Fatal" internal/harness/synth/cmd/perfci/*.go` (or equivalent) matches on the regression path.
- **AC-11.** `go test ./internal/harness/synth/... -race -count=1` passes with no data race in generation or perf-measurement code that uses the shard worker pool. Check: `grep -n "go func()" internal/harness/synth/*_test.go` finds at least one concurrency test, if the generator itself is parallelised; if generation is single-threaded by design, `doc.go` states that explicitly and this AC is satisfied by SG-4 passing with `-race` and no goroutine use.

### Documentation

- **AC-12.** `internal/harness/synth/doc.go` states the module key `harness.synth`, cites M0-ENG §2.4 and §5, and documents the 1M/10M scale presets and the 10% regression threshold in prose (not only as bare constants). Check: `grep -n "harness.synth" internal/harness/synth/doc.go` and `grep -n "10%" internal/harness/synth/doc.go` both match.
- **AC-13.** A short doc explains how the perf CI job's baseline is stored/updated across commits (so a future BA/Tester/QA can audit whether the gate is actually wired into CI, per the sprint plan's S2 exit gate "perf CI graphs tick-time vs 1M/10M synthetic"). ## Acceptance criteria

### BUG-101 — reachability scan: GenDecl alias edges for func-typed vars

- **AC-A1 (the core fix, must be independently testable).** `buildReachabilityGraph` (or its replacement) additionally walks each parsed file's package-level `*ast.GenDecl` (`token.VAR`) declarations and, for each `*ast.ValueSpec` whose initializer is a function-valued expression — an `*ast.Ident` naming an existing package-level function (`var DefaultWire = wireDefaultHook`) or an `*ast.FuncLit` assigned directly (`var DefaultWire = func(e *engine) { ... }`) — records an alias edge from the var's name to the aliased function (or, for a `FuncLit`, treats the literal's body as if it were the aliased function's own body for `hasIdent`/`calls` purposes). A call through the var's name (`DefaultWire(e)`) then resolves via `reachableFromEntry`'s existing `byName` lookup exactly as an ordinary function call does today. Check: a fixture-driven negative-control-turned-positive-control mirroring astgate's AC-8/9/10 pattern — the existing `TestReachability_PackageLevelFuncVarEvades` fixture (`var DefaultWire = wireDefaultHook` in an already-"whitelisted" file, called elsewhere as `DefaultWire(e)`) is run through the fixed graph builder and now returns a non-nil hit naming `wireDefaultHook` (or the alias, per AC-A2's naming choice) — proving the fix actually catches the wire-table idiom, not merely that the scan runs without crashing on a `GenDecl` it previously ignored.
- **AC-A2.** `TestReachability_PackageLevelFuncVarEvades` itself is updated in the same change to assert the NEW (catching) behaviour — its polarity flips from `hit != nil` (evades) to `hit == nil` triggering failure / a real hit expected — and its doc comment and the doc-list entry in `reachability_test.go`'s file-level comment (the numbered list under "What this resolves, and what it does not") both move the wire-table-var bullet from the "NOT resolved" list to the "YES" list, with the fix's actual mechanism (GenDecl alias edges) stated in place of the current "NOT resolved... BUG-101's scope, not a comment's" text. A stale doc comment claiming a gap that the code no longer has is exactly the "declared-gap list narrower than reality" failure mode BUG-101's own dispatch comment named — this criterion requires the fix not to reintroduce the mirror-image version of that mistake (a doc claiming a gap survives after the code no longer has it).
- **AC-A3 (negative control retained — the fix must not over-catch).** A second fixture proves the fix does not regress `TestReachability_FunctionValuePassedAsParameterEvades` (the OTHER declared gap — a function value threaded through an ordinary parameter and invoked under a different local name) — that test's existing "evades" assertion must still pass unchanged after AC-A1 lands, because a parameter-passed function value is a dataflow problem GenDecl alias-edge walking does not, and should not attempt to, solve. Check: the existing test, re-run against the fixed graph builder, keeps its current `hit != nil` (evades) polarity — if this flips too, the fix over-reached its scope and the doc comment's own "materially worse... in KIND, not just instance" distinction between the two gaps has collapsed.
- **AC-A4 (GR#15).** The GenDecl/ValueSpec walk added by AC-A1 identifies a func-typed var purely from AST shape (the initializer expression's kind — `*ast.Ident` resolving to a known function name, or `*ast.FuncLit` directly) — never from a hardcoded variable-name list (e.g. never `if name == "DefaultWire"`). Check: `grep`-style review of the added code and its tests for any bare string literal compared against a variable's own name as a detection condition (fixture variable names used only to construct test input are fine, per astgate's AC-11 precedent).
- **AC-A5 (declared residual limitations, astgate-style).** `reachability_test.go`'s file-level doc comment states, for the fix landed under AC-A1, what it still does not resolve — at minimum: (a) a func-typed var initialized from an expression more complex than a bare identifier or literal (e.g. a conditional `var Wire = cond(); Wire = ...` reassignment, or a var populated inside an `init()` function rather than its own initializer) is not required to be resolved by this fix and, if left unresolved, must be named explicitly rather than silently absent from the doc list; (b) a map/slice of func-typed values (`var handlers = map[string]func(){...}`, the idiom named explicitly in this BOW item's own title) is in scope for AC-A1's fixture per the dispatch brief, but if the junior's implementation resolves the bare-var case (`var DefaultWire = wireDefaultHook`) without also resolving a map-literal entry's function values, that narrower scope must be stated plainly in the doc comment, not left implied by an example that happens to cover only the simpler shape. **Escalation for Bill, logged as ASM-419 below**: whether AC-A1's fixture must include BOTH the bare-var and the map-literal shapes, or whether the bare-var shape alone satisfies "BUG-101's scope" and the map-literal shape is filed as a follow-up, is a real scoping choice this BA is not positioned to make unilaterally — the BOW item's own title privileges the map idiom ("a common Go idiom: `var handlers = map[string]func(){...}`") while its narrative body's concrete reproduction uses only the bare-var shape (`var DefaultWire = wireDefaultHook`).
