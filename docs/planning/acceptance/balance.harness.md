# Acceptance criteria — balance.harness (MOD-036)

**BOW code:** MOD-036
**Spec refs:** §16-M2 (`docs/METROPOLIS-MASTER-v2.1.md` line 272: "M2 — Balance harness: Batch parameter sweeps; tune pacing knob & growth curves until 0→100 M is achievable-but-hard."); §15 Architecture (line 265: "Azure Batch headless balance-tuning during development (thousands of parameter runs, centuries per run)"; line 263 protocol/service boundary); §3 Time (lines 119-133: `secondsPerMonthAt1x` default 480, "the master pacing knob, tuned by headless Batch runs (§15)"; the sanity-check line "1 game year = 24 min at 4×; 250 game years ≈ 100 real hours" — the only spec-stated pacing magnitude); §4 Population Scale & the Milestone Ladder (line 139: migration-dominated growth via Attractiveness); code.json `balance.harness` entry (inbound `SweepRunner`, "CLI + JSON scenario defs", pattern "H-HEADLESS fan-out; results comparable across seeds", zero registered consumers — this is a leaf development tool, not a module other engine code calls into; outbound calls to `harness.headless` (MOD-015) and `harness.synth` (MOD-016)). ## User stories

- **US-1.** As the dev team tuning `secondsPerMonthAt1x`, growth curves, and milestone spacing, I need a sweep runner that fans out thousands of `harness.headless` runs over `data/*.json`'s balance surface, so pacing tuning is a batch job over real simulated centuries, not a human running the game by hand (§15, §16-M2).
- **US-2.** As whoever reviews a sweep's output, I need every configuration the sweep attempted — not just the ones that finished cleanly — accounted for in the result set, so a sweep cannot quietly present a clean frontier built by dropping the runs that crashed (GR#17, the risk this file exists to guard against).
- **US-3.** As GR#21's determinism gate, I need the sweep harness's own determinism claims scoped honestly: reproducible at a fixed worker count, and explicitly NOT claiming cross-worker-count bit-identical numeric output, because that property is unresolved project-wide (`ASM-216`, deferred to `FEAT-041`, blocking `MOD-023`) — a sweep that assumed it settled would measure noise and call it signal.
- **US-4.** As `MOD-069` (Azure tiers, a later consumer of this module's Batch path per §15), I need sweep results in a form that scales from a local run to Azure Batch without a schema change, so the local sweep runner and the eventual cloud path are the same tool at two scales.
- **US-5.** As GR#15 ("validators derive from data"), I need the swept parameter ranges themselves loaded from a scenario definition file, not hardcoded in Go, so widening or narrowing the sweep is a data edit during M2 tuning, never a code change.
- **US-6.** As whoever eventually reads a throughput/perf claim about this harness, I need that claim expressed relative to `harness.synth`'s own baseline/regression machinery (`PerfResult`, `CompareToBaseline`), never as an absolute wall-clock number in CI, because this project has already lost a gate (BUG-031) to exactly that mistake, and `harness.synth`'s own 1M real-scale CI baseline does not exist yet (BUG-034, open P0) — a claim of "no regression" today would be citing a baseline that isn't there.

## Scope

A local sweep runner (`SweepRunner`, CLI + JSON scenario defs) that fans out parameter configurations × seeds to `harness.headless` runs (via `harness.synth`'s synthetic-city generator for scale/shape), collects and persists a result for every attempted (configuration, seed) cell — success, failure, and reason — and reports the pacing/growth-curve frontier this data supports. No Azure Batch implementation itself (§15's cloud path is designed-not-built v1, `MOD-069`'s job later); no UI presentation of sweep results (that belongs to whichever `ui.dash`/`ui.screen.*` item visualises it, out of this BA's ownership).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `SweepRunner` (or equivalent) exists matching code.json's registered inbound contract — CLI entry point accepting a JSON scenario-definition file describing the swept parameter grid (at minimum: `secondsPerMonthAt1x` values, growth-curve coefficient sets, milestone-spacing variants, per MOD-036's own description) and a seed set, fanning results out through `harness.headless` (MOD-015) for the actual runs and `harness.synth` (MOD-016) for the synthetic world each run starts from — the two registered outbound edges, not a private reimplementation of either. Check: `go doc ./tools/balance` (or CLI `--help`) shows a scenario-file flag and a seed-set flag; `grep -rn "harness/headless\|harness/synth" tools/balance/*.go` shows real imports of both packages. False-pass risk: a CLI that merely accepts flags shaped like a scenario file but generates its own ad hoc synthetic cities and drives `engine.core` directly (bypassing `harness.headless`) would satisfy a flag-shape check while violating the registered outbound edge — the check requires the actual import, not merely CLI surface resembling one.
- **AC-2 (GR#17; every configuration accounted for — the central risk this file exists for).** For every (configuration, seed) cell in the swept grid, the persisted sweep-result set contains exactly one terminal record classified as one of: `completed`, `timed-out`, `crashed` (with a machine-readable cause, AC-3), or `rejected` (invalid parameter combination, AC-8). The count of terminal records always equals the count of attempted cells — a sweep cannot finish with fewer result records than configurations attempted. Check: a passing test runs a scenario with N cells where at least one cell is engineered to crash (e.g. a headless run given a parameter that trips a fatal error), and asserts the output record count still equals N, with the crashed cell present and classified `crashed`, not absent (`grep -rn "func Test.*[Aa]ccountedFor\|func Test.*[Cc]ellCount" tools/balance/*_test.go`). **False-pass risk stated explicitly:** a report that prints "N of M cells succeeded" as a single summary line, with M silently including the dropped failures only in the denominator, would look like accounting but isn't — the check requires each cell's *identity* (its parameter values + seed) to appear in a result record, not just a count that could be fabricated from the wrong M.
- **AC-3 (attributable failure, GR#17 continued).** Every non-`completed` terminal record names: the specific (configuration, seed) it belongs to, a cause category drawn from a closed, documented set (e.g. `headless-exit-nonzero`, `registry-error:<MET code>`, `timeout`, `oom`, `invalid-parameter`), and, where available, a pointer to the underlying `harness.headless` run's own output/log artifact for that cell. Check: a passing test injects two *different* failure modes (e.g. a timeout and a nonzero headless exit) in the same sweep and asserts their `cause` fields differ (`grep -rn "func Test.*[Cc]auseDistinct\|func Test.*[Ff]ailureAttribution" tools/balance/*_test.go`). **False-pass risk stated explicitly:** a generic `catch (err) { record("failed") }` pattern would make every failure's cause the identical string `"failed"` — a test that only checks "a failure was recorded" cannot catch that; the check must assert two distinct injected failure modes produce two distinct cause values.
- **AC-4 (retries are additive, never substitutive).** If the sweep runner retries a failed cell, the original failure's record is retained in the output alongside the retry's outcome — a cell that failed once and then succeeded on retry shows both attempts, not just the final one. Check: a passing test forces one failure then a success for the same cell on retry and asserts both attempt records are present and ordered (`grep -rn "func Test.*[Rr]etry" tools/balance/*_test.go`). **False-pass risk:** an implementation that retries in-place and overwrites the prior record would satisfy "the cell eventually has a completed record" while destroying the fact that it failed once — the check requires both records to be independently visible, not just a final "completed" state.
- **AC-5 (§3, §4; the frontier the sweep exists to find).** For each completed cell, the sweep computes and records a real-hours-to-100M figure derived from the simulated result (simulated months elapsed to cross the 100M milestone × the cell's `secondsPerMonthAt1x` ÷ 3600), so the sweep's output directly answers "which configurations land in the 80-150 real-hour band" without a human re-deriving it by hand. Check: a passing test asserts the computed real-hours figure for a cell with known simulated-months-to-100M and known `secondsPerMonthAt1x` matches the arithmetic exactly (`grep -rn "func Test.*[Rr]ealHours\|func Test.*[Ff]rontier" tools/balance/*_test.go`). **False-pass risk:** a report that only shows raw simulated-months-to-milestone without the real-hours conversion would require a human to re-derive the number every time — the check requires the conversion to be present and tested, not merely derivable by a reader.
- **AC-6 (GR#15; sweep grid is data-driven).** The swept parameter ranges (which `secondsPerMonthAt1x` values, which growth-curve coefficient sets, which milestone-spacing variants) are read entirely from the JSON scenario-definition file at AC-1, never hardcoded as Go literals defining the sweep's own search space. Check: `grep -nE "480\b" tools/balance/*.go` (excluding `_test.go` and doc-comment prose transcribing the spec's default) finds no bare hardcoded default value driving the sweep grid itself; a passing test changes the scenario file's parameter list and asserts the sweep actually runs the new list, not a compiled-in one (`grep -rn "func Test.*[Ss]cenario.*[Dd]riven\|func Test.*[Dd]ataGrid" tools/balance/*_test.go`).

### Error handling

- **AC-7 (GR#7).** A malformed scenario-definition JSON (missing required parameter dimension, a growth-curve coefficient set with the wrong shape) is rejected at load time with a registry-sourced error, never silently defaulted to an empty or partial grid that runs anyway. Check: `grep -n "MET-" tools/balance/*.go` finds a registry code reference (new sub-range, claimed at build time — no `B`-layer range exists yet in `data/errors.json`, same situation `engine.season`/`engine.market` were in before their build); passing test coverage (`grep -rn "func Test.*[Mm]alformedScenario" tools/balance/*_test.go`).
- **AC-8 (GR#7; out-of-domain parameter, named domain not "handles gracefully").** A requested parameter value outside its documented domain (e.g. a negative `secondsPerMonthAt1x`, a milestone-spacing value that would place two milestones at the same population tier) is rejected per-cell with a registry-sourced error at that cell's classification (`rejected`, AC-2/AC-3) — never silently clamped into range and run as if the requester had asked for the clamped value. Check: `doc.go` states each swept parameter's positive domain; a passing test asserts an out-of-domain cell is classified `rejected` with the requested (out-of-domain) value preserved in the record, not replaced by a clamped one (`grep -rn "func Test.*[Oo]utOfDomain\|func Test.*[Rr]ejectedCell" tools/balance/*_test.go`).
- **AC-9 (interrupted sweep — GR#17 applied to partial runs, §15's Azure Batch-preemption reality).** If the sweep process is interrupted mid-run (killed, or — per §15's designed Batch path — a compute node preempted), resuming or re-reporting the sweep's state distinguishes "not yet attempted" from "attempted and failed" from "completed" for every cell — an interrupted sweep's partial output never silently reports an unattempted cell as passed, and never silently reports it as absent from the frontier without marking it unattempted. Check: a passing test truncates a partial result file mid-write (simulating a kill) and asserts the remaining ungenerated cells are reported as `not-yet-run`, distinct from both `completed` and `crashed` (`grep -rn "func Test.*[Ii]nterrupted\|func Test.*[Pp]artialResume" tools/balance/*_test.go`).

### Determinism & safety

- **AC-10 (GR#21; fixed worker count).** For a fixed (configuration, seed, worker count) tuple, repeated sweep-cell runs produce byte-identical or hash-identical simulation output, reusing `harness.synth`/`harness.headless`'s existing determinism guarantees rather than a second implementation of them. Check: a passing test runs the same cell twice at the same worker count and asserts identical output hashes (`grep -rn "func Test.*[Dd]eterminis" tools/balance/*_test.go`).
- **AC-11 (GR#21; the ASM-216/FEAT-041 boundary — do not assume it is settled).** This module's determinism checks and its result schema explicitly scope worker-count as a first-class, recorded field on every result — and no check, test, or doc claim in this package asserts bit-identical numeric output *across different worker counts* for any value derived from cross-shard summation (traffic/flow-style accounting). That property is an open P0 (`ASM-216`), deliberately deferred to a dedicated deep dive (`FEAT-041`, which blocks `MOD-023`) rather than decided ad hoc here. If a future cross-worker-count comparison is added to this package for informational purposes, it must be documented as tolerance-based/informational only, never a pass/fail gate, until `FEAT-041` resolves. Check: `grep -rn "WorkerCount\|workerCount" tools/balance/*.go` shows the field present on the result-record schema; `grep -rln "byte-identical\|bit-identical" tools/balance/*.go` — any match must appear only in a fixed-worker-count context (verified by reading the surrounding test, not by the grep alone, since a grep cannot itself distinguish "same worker count" from "across worker counts" — **this is the check's own false-pass risk, named explicitly**: the grep only proves the phrase exists, not which claim it attaches to, so a reviewer must confirm the referenced test holds worker count constant).
- **AC-12 (provenance, mirroring `harness.synth`'s `Measured` flag pattern from BUG-055).** Every persisted sweep result carries: the scenario-file content hash or version, the code commit/version the run executed under, the seed, and the worker count — so a result can never be silently reused or misattributed to a different code version during iterative tuning. Check: `grep -n "CommitHash\|ScenarioHash\|commitSHA" tools/balance/*.go` shows the field; a passing test asserts two runs under different (mocked) commit identifiers produce distinguishable provenance in their records (`grep -rn "func Test.*[Pp]rovenance" tools/balance/*_test.go`).
- **AC-13 (never a CI wall-clock ceiling).** No test, doc comment, or CI configuration in this package asserts an absolute wall-clock upper bound on sweep duration (a single sweep cell simulates centuries and a full sweep is thousands of runs — exactly the shape of number that produced BUG-031 the last time this project hardcoded one). Any perf/throughput claim this package makes is expressed relative to `harness.synth`'s own `PerfResult`/`CompareToBaseline` baseline machinery, reusing its types rather than inventing a parallel one. Check: `grep -rn "time.Sleep\|Duration.*<\|elapsed.*>\|wallClockBudget" tools/balance/*.go tools/balance/**/*.go` (excluding `_test.go`) finds no absolute-seconds comparison gating success/failure; `grep -rn "synth\.PerfResult\|synth\.CompareToBaseline\|synth\.BaselineComparison" tools/balance/*.go` shows reuse of the existing type, if this package makes any such claim at all.
- **AC-14 (BUG-034 honesty — no claim against a baseline that doesn't exist).** Because `harness.synth`'s real-1M-scale CI baseline has not yet been recorded on a CI runner (BUG-034, open P0), nothing in this package's tests, docs, or CLI output states or implies "no regression against the CI baseline" as an achieved, verified condition. Where this package surfaces a `harness.synth`-derived comparison, a missing-baseline state is reported explicitly (mirroring `harness.synth` AC-8's "no prior baseline to compare" behaviour) rather than silently treated as a pass. Check: a passing test exercises the no-baseline-yet condition and asserts the reported status names the missing baseline rather than reporting success (`grep -rn "func Test.*[Nn]oBaseline" tools/balance/*_test.go`); `grep -rn "no regression\|regression-free" tools/balance/*.go docs/planning/acceptance/balance.harness.md` — any such phrase found in shipped doc/CLI text (not this AC file itself) must be conditioned on an actual recorded baseline, not asserted unconditionally.
- **AC-15.** `go test ./tools/balance/... -race -count=1` passes with no data race across concurrently fan-out headless runs. Check: `grep -n "go func()" tools/balance/*_test.go` finds at least one concurrency test.

## Out of scope

- Azure Batch itself — the cloud fan-out target for thousands of parameter runs (§15) is `MOD-069`'s job; this item's `SweepRunner` must be shaped so scaling to Batch is a backend swap, not a rewrite, but does not implement the Batch backend.
- `data/*.json`'s actual tuned values (the balance surface itself) — this item is the mechanism that finds a good frontier; picking and committing the final `secondsPerMonthAt1x`/growth-curve/milestone-spacing values is a later, Aaron-reviewed tuning pass this harness enables but does not itself conclude.
- Any UI presentation of sweep results (frontier charts, dashboard tiles) — owned by the UI-track BAs' files.
- Resolving `ASM-216`/`FEAT-041` (cross-worker-count determinism for float-summed values) — this item must not assume that question settled (AC-11) but does not settle it either; that is `engine.traffic`'s deep dive.
- Recording `harness.synth`'s real-1M CI baseline — that is BUG-034's own remaining work; this item only must not claim it exists before it does (AC-14).

## Escalations

- **For Aaron (via Bill) — what "hard" means, numerically, beyond the 80-150 hour band.** The spec and MOD-036's own description give a real-hours *pacing* target (80-150 hours, consistent with §3's ~100-hour sanity check) but nowhere quantify "hard" as distinct from merely "slow." A sweep configuration that takes 120 real hours because the player has nothing meaningfully difficult to do (no risk of the Detroit spiral, no resource-margin tension, no failure mode a mediocre player hits) satisfies the pacing band while missing the design intent entirely. This is a thing a player feels — squarely Aaron's call per the BA brief's own instruction — so it is not decided here. Logged as `ASM-below` (P1, since it is load-bearing for what "achievable-but-hard" even means as a sweep objective function) rather than invented; AC-5/AC-6 are written to compute and expose whatever difficulty signal a scenario file defines, not to hardcode one.
- **Assumption logged.** `node claude-bow.js add assumption` calls below cover: (1) sample-count-per-configuration (how many seeds constitute a statistically meaningful cell, since neither spec nor BOW states one), (2) the closed failure-cause taxonomy named in AC-3 (my invention, not spec text), (3) the retry-is-additive policy in AC-4 (spec is silent on whether the harness retries at all), and (4) the "hard" numeric-definition gap above.
