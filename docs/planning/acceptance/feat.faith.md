# Acceptance criteria — feat.faith (FEAT-138)

**BOW code:** FEAT-138 (P2, open) — "Faith & places of worship — a light background dimension of the people"
**Module key:** `feat.faith` (proposed — see Escalation ES-1; not yet registered in code.json)
**GUID:** `5ac12af7-0e67-4f7f-b800-5afa47435141`
**Spec refs:** FEAT-138 BOW desc (the authoritative design — this is an Aaron-directed feature with no master-plan section of its own); §LM Landmarks & Uniques (`docs/METROPOLIS-MASTER-v2.1.md` line 1255: `| Cathedral | M8 + community high | reputation + |` — the player-built landmark this feature must NOT collide with, flagged in ES-4); §40 Social Services (line 569: homelessness services = prevention + hostels + housing-first — the outreach destination); §CM/WF (line 1273: `| Housing office | M6+DP | homelessness prevention |`); cross-refs `engine.citizens.md` (MOD-018, AC-1/AC-1b — the citizen record that has no affiliation field today), `engine.wellbeing.md` (MOD-034, AC-1/AC-7 — 15 named drivers, no "cohesion" driver; isolation = sociability × community access), `engine.social.md` (MOD-053, AC-7 — the homelessness pipeline donations feed into); GR#20 (Contract-First, Stub-Forever), GR#7 (registry-sourced errors), GR#15 (validators derive from data), GR#16 (type-safe storage boundaries), GR#21 (Red Determinism Gate).
**Design (Aaron, 2026-08-16, BOW FEAT-138):** A LIGHT background dimension, auto-managed, no player interaction. Every citizen is agnostic or holds one of the mainstream UK faiths (Christian, Muslim, Jewish, Hindu, Sikh, Buddhist, plus the non-religious); each faith community auto-builds its place of worship (church/mosque/synagogue/temple/gurdwara) as it grows — the player never places or manages them. Denominational preference shapes the building (some traditions want grand cathedrals, others small local churches). A place of worship adds to wellbeing and community cohesion (harmony within the neighbourhood); the faithful donate, and community outreach (helping the homeless) flows from those donations.
**This file's role:** this feature is cross-cutting and **auto-managed**. It does not own the citizen record, the wellbeing score, or the social-services caseload — it *surfaces through* them: affiliation through `engine.citizens`, cohesion through `engine.wellbeing`, outreach through `engine.social`. This file owns the faith dimension itself: the deterministic affiliation assignment, the auto-build of places of worship, the denominational building shaping, and the donation→outreach flow — and, as its defining constraint, the **absence of any player build/manage path into it**. The one thing this feature must never do is become a build mechanic.
**Date:** 2026-08-16
**Status:** draft-ahead — the feature is **not registered** in code.json (no `feat.faith`/`engine.faith` key, no inbound contract, no outbound edges to citizens/wellbeing/social — see ES-1); the affiliation/cohesion placement and the §LM Cathedral tension are open Aaron rulings (ES-2/ES-3/ES-4). Directional numbers only, per the balance-number regime below.
**Balance-number regime (standing rule, same convention as `engine.finance.md` AC-21 / `feat.deathwarnings.md` AC-3 / `engine.maintenance.md` AC-2):** congregation-size build thresholds, per-faith population shares, the denominational building map, the cohesion/harmony contribution magnitude, the wellbeing delta magnitude, and donation rates/amounts are all **placeholders** in a data file (`data/faith.json`), each carrying a disclosure comment naming it pending Aaron's balance pass. **No AC may be satisfied by a junior inventing a "church adds X wellbeing" figure or a "a place of worship raises cohesion by N" figure.** Every AC touching a magnitude requires the value to live in the data file and requires tests to check **direction/structure** (with-place-of-worship > without; cohesion rises; donations flow to outreach), never a specific figure.

## User stories

- **US-1.** As the engine, I need every citizen assigned a deterministic affiliation (agnostic, or one of the closed set of mainstream UK faiths) that is stable for that citizen across ticks and runs, so affiliation is a real per-citizen attribute, not a value re-rolled every tick (GR#21).
- **US-2.** As a faith community, I need my place of worship to appear automatically as my congregation grows past a data-driven threshold, so worship places exist without any player action ever triggering them.
- **US-3.** As the player, I need **no** build/manage path into places of worship — they never appear in the build queue, the build catalogue, or the demolish surface — so the "auto-managed, no player interaction" property is a structural guarantee, not a convention a later coder can quietly violate.
- **US-4.** As denominational preference, I need the place-of-worship building shape to resolve from (faith, denomination) via data — cathedral vs small parish church within Christianity; mosque/gurdwara/synagogue/temple for the other faiths — so the closed faith set maps to a closed, deterministic building-type set.
- **US-5.** As `engine.wellbeing`/neighbourhood cohesion, I need a place of worship to add a data-placeholder harmony/wellbeing contribution whose direction is with-place-of-worship > without, so the effect is real and tuneable, not a hardcoded constant a junior invented to make a test pass.
- **US-6.** As the faithful, I need donations to flow into community outreach (helping the homeless) through `engine.social`'s homelessness provision, so charity is a real conserved money flow, not a narrative description with no ledger.
- **US-7.** As `engine.invariant`, I need the donation flow conserved — donated == routed + retained — so money neither appears from nowhere nor vanishes inside the faith dimension.

## Scope

A deterministic per-citizen affiliation over the closed mainstream-UK-faith set, data-driven population shares and congregation thresholds from `data/faith.json`; the automatic (background-tick) construction of a place of worship per faith community, resolved through a data-driven denominational building map; a data-placeholder cohesion/harmony and wellbeing contribution (direction-only); a conserved donation flow into `engine.social`'s outreach provision; and the structural guarantee that no build/manage command path reaches any place of worship. No citizen-record edit (MOD-018 is done — ASM-998), no new wellbeing driver (ASM-999), no build mechanic, and no final balance numbers (Aaron's pass).

## Acceptance criteria

### Functional — affiliation (the per-citizen attribute)

- **AC-1 (closed set, deterministic per-citizen — GR#21).** Every citizen resolves to exactly one affiliation from the closed set {agnostic/non-religious, christian, muslim, jewish, hindu, sikh, buddhist} (with an optional denomination sub-field inside christian, per AC-5), assigned **deterministically** from the counter-based hash stream `hash(worldSeed, id, "affiliation")` (or equivalent purpose tag) — the same citizen id resolves to the same affiliation across ticks, repeated runs, and worker counts, and is never re-rolled. Check: `go doc ./internal/engine/faith` shows the affiliation enum and the derivation function; a passing determinism test assigns affiliations to the same population twice (and, if cheap, at two `WithPoolSize` values) and asserts byte-identical results (`grep -rn "func Test.*[Aa]ffiliation.*[Dd]eterminis\|func Test.*[Ss]table" internal/engine/faith/*_test.go`); `grep -n "rand.New\|math/rand" internal/engine/faith/*.go` (excluding `_test.go`) finds no shared/global RNG on the affiliation path. **False-pass risk:** an implementation that assigns affiliation lazily and caches it but re-derives (with a different result) after a deserialise would pass a single-run determinism test while breaking run-over-run stability — the test must exercise assignment twice from a cold store, not just read a cache back.

- **AC-2 (GR#15 — population shares from data, not hardcoded counts).** The distribution of affiliations over a population is derived from `data/faith.json`'s per-faith population-share table, never a hardcoded per-faith count or ratio in Go. Check: a passing test mutates one faith's share in the loaded fixture and asserts the derived count for that faith (and only that faith) moves accordingly (`grep -rn "func Test.*[Dd]ataDriven\|func Test.*[Ss]hare.*[Rr]eload" internal/engine/faith/*_test.go`); `grep -nE "[0-9]+\.?[0-9]*" internal/engine/faith/*.go` (excluding `_test.go`) finds no bare population-share/threshold-shaped numeric literals outside doc-comment prose. **Balance-regime note:** the shares themselves are placeholders (disclosure comments, AC-14); this AC checks *shares are data-driven*, not any specific percentage.

### Functional — the auto-build (the defining constraint: no player interaction)

- **AC-3 (congregation growth triggers the build, data-driven threshold).** Each faith community auto-builds its place of worship when its congregation size crosses a threshold loaded from `data/faith.json`, and the construction is a **background-tick action** (a phase hook or tick-side effect), not a command the player (or any UI) invokes. Check: `go doc ./internal/engine/faith` shows an auto-build resolution path; a passing test seeds a congregation below threshold, advances ticks until it crosses, and asserts the place-of-worship record appears with no command injected (`grep -rn "func Test.*[Aa]utoBuild\|func Test.*[Cc]ongregation.*[Tt]hreshold" internal/engine/faith/*_test.go`). **False-pass risk:** a build that only happens when some external caller invokes an exported "BuildWorshipPlace" function would pass a "a place of worship eventually exists" reading while failing the auto-managed premise — the check requires the build to occur with zero external trigger. **Balance-regime note:** the threshold value is a placeholder; this AC checks the *auto* trigger, not the specific congregation count.

- **AC-4 (no player path — structural, provable — the load-bearing AC).** Places of worship are **not reachable** through `engine.build`'s command surface, by construction: (a) the faith package carries no outbound edge to `engine.build` — it never calls `BuildAPI` to place or remove anything; (b) no place-of-worship building type exists in the player build catalogue (`data/buildings.json` — the catalogue `engine.build` is driven from); (c) a test proves the build command surface rejects/never enumerates a place of worship and that the faith auto-build path does not route through `BuildAPI`. Check: `grep -rn "build\.\|BuildAPI\|buildings\.json" internal/engine/faith/*.go` (excluding `_test.go`) returns no matches (the auto-build writes a faith-owned structure record, never a build order); `node -e "const b=require('./data/buildings.json'); const ids=JSON.stringify((b.entries||[]).map(x=>x.id)); process.exit(/church|mosque|synagogue|temple|gurdwara/i.test(ids)?1:0)"` exits 0 (the five auto-build worship types are absent from the player catalogue — the sole existing `cathedral` entry is the §LM player landmark, the ES-4-flagged collision, deliberately excluded from this tripwire); a passing test asserts the auto-build path produces a faith-owned place-of-worship record with no `BuildAPI`/build-order side effect (`grep -rn "func Test.*[Nn]oBuildPath\|func Test.*[Nn]ot.*[Bb]uild" internal/engine/faith/*_test.go`). **This is the item's defining constraint — the "never a build/manage mechanic" clause of the spec is a structural guarantee here, not a prose aspiration.** A lazy implementation that quietly adds a "church" entry to the player catalogue "so the map can render it" FAILS both (b) and (c) and defeats the entire feature.

- **AC-5 (denominational building shaping, data-driven, deterministic).** The place-of-worship building type resolves from `(faith, denomination)` via a mapping in `data/faith.json` — e.g. christian/catholic → a cathedral-shaped record, christian/anglican → a small parish-church-shaped record, muslim → mosque, jewish → synagogue, hindu → temple, sikh → gurdwara, buddhist → temple (exact keys the developer's call, all data-driven) — so "some traditions want grand cathedrals, others small local churches" is a real, tuneable resolution, not a single shared "worship" sprite. Check: `go doc ./internal/engine/faith` shows the resolution function; a passing test resolves two distinct faiths (or two denominations within christian) and asserts they map to two distinct documented building-type records, deterministically (`grep -rn "func Test.*[Dd]enominat\|func Test.*[Bb]uilding.*[Rr]esolve" internal/engine/faith/*_test.go`). **False-pass risk:** a `map[faith]buildingType` with every faith mapped to one shared type would pass a "a building type exists" grep while the spec's "denominational preference shapes the building" promise fails — the check requires at least two faiths/denominations to resolve to two different types.

### Functional — cohesion / wellbeing / outreach (all data placeholders, direction only)

- **AC-6 (place of worship adds wellbeing — direction only, GR#15).** The presence of a place of worship raises the local faithful's wellbeing contribution relative to its absence, with the **magnitude loaded from `data/faith.json`** (a placeholder with a disclosure comment), never a hardcoded "church adds X wellbeing" constant in Go. Check: a passing directional test computes the contribution with and without a place of worship present for the same otherwise-identical neighbourhood and asserts `with > without` (`grep -rn "func Test.*[Ww]ith.*[Ww]ithout\|func Test.*[Hh]armony.*[Dd]irection" internal/engine/faith/*_test.go`); the contribution value traces to the data file, not a Go literal. **Balance-regime note (explicit):** the exact wellbeing/harmony delta is Aaron's balance pass; no AC may pin a figure, and a test that pins one is a FAIL — this AC asserts direction and data-sourcing only.

- **AC-7 (cohesion/harmony rises — neighbourhood-level, direction only).** A neighbourhood containing a place of worship reports a cohesion/harmony term strictly higher than the same neighbourhood without one, magnitude data-placeholder. Check: a passing directional test holds all other neighbourhood inputs fixed and asserts the harmony term is higher with the place of worship than without (`grep -rn "func Test.*[Cc]ohesion\|func Test.*[Hh]armony" internal/engine/faith/*_test.go`); the term is neighbourhood-scoped (queryable per neighbourhood/district), not a single city-wide constant. **False-pass risk:** a constant "+harmony bonus" applied to the whole city the moment any one place of worship exists would pass a "harmony exists" grep while the spec's "harmony within the neighbourhood" locality fails — the check requires the term to be localised (a neighbourhood with the building scores differently from one without).

- **AC-8 (donations flow to outreach — a real, conserved money flow into `engine.social`).** Donations from the faithful are routed into `engine.social`'s outreach/homelessness provision (its homelessness pipeline, per `engine.social.md` AC-7) through `SocialAPI`, as a real money flow — not accumulated in a faith-local shadow ledger that `engine.social` (and the rest of the city's books) cannot see. Check: `grep -n "social\.\|SocialAPI" internal/engine/faith/*.go` (excluding `_test.go`) finds the call into the registered social edge; `grep -nE "[Pp]ounds|micro|Money" internal/engine/faith/*.go` (excluding `_test.go`) finds no faith-local currency ledger type; a passing test raises the donation input and asserts `engine.social`'s outreach-provision input rises correspondingly (`grep -rn "func Test.*[Dd]onation.*[Oo]utreach\|func Test.*[Cc]harity" internal/engine/faith/*_test.go`). **Boundary note:** how `engine.social` spends that donation (prevention vs hostel vs housing-first) is `engine.social`'s own mechanics (MOD-053); this AC only requires the donation to cross into `SocialAPI` and be conserved (AC-12).

### Functional — cross-module contract (GR#20)

- **AC-9 (consume citizens/wellbeing/social via their interfaces only).** The faith package sources its per-citizen inputs (population, the `community-mindedness`/`sociability` personality axes that weight religiosity/attendance) through `CitizensAPI`, its wellbeing/harmony contribution through `WellbeingAPI`'s inbound surface, and its donation routing through `SocialAPI` — never a direct import of another engine package's concrete struct, and never a direct reach into `engine.citizens.Citizen`/`engine.wellbeing`/`engine.social` internals. Check: the import block of every non-test file in `internal/engine/faith/` (`grep -n "^import" -A20 internal/engine/faith/*.go`) references only the three registered engine packages plus foundation/protocol/stdlib — and specifically NOT `engine.build`; `grep -rln "citizens\.\(Citizen\|ColdShard\)\.\w\+" internal/engine/faith/*.go` (excluding `_test.go`) returns no matches. **False-pass risk:** a package that imports `CitizensAPI` but also reaches into `engine.citizens`' exported structs directly would pass a shallow import-block check while violating GR#20's "consume only via registered interfaces" — the struct-reach grep is the load-bearing half.

### Error handling

- **AC-10 (GR#7).** Operating on an unknown faith/denomination key, an unknown citizen id, or a negative donation amount returns a registry-sourced error (a new `MET-`-range code claimed at build time against `data/errors.json`), never a panic or a silently-clamped value folded into the affiliation/cohesion/donation state. Check: `grep -n "MET-" internal/engine/faith/*.go` finds a registry-code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownFaith\|func Test.*[Nn]egative.*[Dd]onation" internal/engine/faith/*_test.go`) asserts the returned error's registry code matches **and** that no faith state (affiliation, congregation, donation ledger) was mutated on failure — not merely that a matching-named test function exists (GR#7 assertion, stated explicitly).

### Determinism & safety

- **AC-11 (GR#21).** Affiliation assignment, auto-build resolution, and donation routing are deterministic functions of `(worldSeed, tick, prior state, data)` via the counter-based hash stream, byte-identical across repeated runs and worker counts; no `range` over a Go map on the tick path can affect committed state (where a shortage forces a priority order — e.g. which congregation's build resolves first — the order is a documented, deterministic rule, never map-iteration order). Check: `grep -rn "time.Now\|time.Since" internal/engine/faith/*.go` (excluding `_test.go`) returns no matches — the congregation/build/affiliation state advances by simulation tick only, never wall clock (SG-7); a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/faith/*_test.go`); `grep -n "sort\." internal/engine/faith/*.go` (or a documented stable ordering) appears wherever a map feeds an allocation order.

- **AC-12 (GR#16 — saturating arithmetic + donation conservation).** Donation arithmetic routes through the project's saturating helpers (`foundation/num`), and the donation flow conserves exactly: for every tick, `Donations == RoutedToOutreach + Retained`, with no term the remainder of the others and no budget driven negative. Check: a passing conservation test drives a synthetic faithful population through several ticks, independently sums each term from its own source, and asserts the identity reconciles exactly (`grep -rn "func Test.*[Cc]onserv\|func Test.*[Dd]onation.*[Ii]dentity" internal/engine/faith/*_test.go`); `grep -n "foundation/num\|num\." internal/engine/faith/*.go` (excluding `_test.go`) shows the saturating helpers in use on the money path. **False-pass risk:** a float-based donation ledger that over-routes to clear a slightly larger outreach demand (rounding in the charity's favour) would pass a loose "donations decrease" check while leaking money from nowhere — the check requires the ledger to balance exactly.
