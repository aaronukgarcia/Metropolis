## 1. Why this item exists

Aaron's words: *"we need to know how much a station or bus or bus stop or road is being used, just like how much a water pipe or power line or waste water line is being used. Railway lines can host only so many trains and same goes for motorways."*

**Important finding, stated up front: most of this already exists.** FEAT-1972079902 (rail network inc1) and the 2026-09-02 congestion-teeth work already built:
- **Per-tier road capacity** — `ROAD_TIER_CAPACITY` (`data.ts:317-323`, vehicles/tile/tick by tier 1..5) and `LINE_CAPACITY` for rail classes (`data.ts:2260-2263`, people/tile/tick for `rail`/`hs1`).
- **A unified per-line-class usage/capacity/saturation read-out** — `lineUsageOf()` (`data.ts:2342-2424`), returning `{spec, kind, tiles, capacity, usage, saturation, headroom, overCapacity}` per road-tier class and per rail class, derived deterministically from the SAME demand flows that drive the economy (`trafficActivity`/`feederTrafficWeight` for roads; the exact `Commuter Revenue` formula for rail, `data.ts:2364-2377` — the code comment is explicit that this is done so "the rail-usage read-out and the commuter income can never tell different stories").
- **Consequences when over capacity, already wired into wellbeing/income** — `congestionLinesOf()` (`data.ts:2524-2541`), `congestionFactorOf()` (`data.ts:2554-2559`), and `CONGESTION_CONSTANTS` (`data.ts:2443-2450`): a linear penalty ramp above a 0.75 saturation threshold, sustained for 60 ticks, dragging income by up to 10% (AC-9 of that feature) — this already IS "congestion slows commutes, fed into the existing machinery," per Aaron's own GR#3 instinct, not a new parallel system.
- **Station connectivity** — `stationLinks()` (`data.ts:2208-2238`), which of every station building is road-connected, already weighted by class (Ashford International ×3 into `hs1`, every other connected station ×1 into `rail`, `data.ts:2358-2363`).
- **The water/power overlay idiom to mirror** — `overlaySubsetsOf` building-subset cache (`MapView.tsx:86,490`), the power-infrastructure overlay (`MapView.tsx:519`), and `PIPE_TIERS`/`waterPipeInfo()` (`data.ts:180-184,926-962`) as the "which pipes are near capacity" precedent this item's UI should copy the shape of.

**What is genuinely missing** and is this item's real scope:
1. A **per-segment** (not just per-line-class) breakdown — today `lineUsageOf` answers "how saturated is the whole city's A-road network," not "which specific stretch of A-road is the bottleneck."
2. A **map overlay** surfacing that per-segment saturation visually (today this data exists only in whatever panel already reads `lineUsageOf`/`congestionLinesOf` — no overlay exists).
3. **Bus stops** — do not exist as a feature yet; this item defines the honest-absence contract for when they do (GR#25 forbids building the mechanic now).
4. A **forward-compatible contract** with the underground metro (FEAT-2326609765, unlocked at 7M population, not yet built) so a road segment's utilisation history survives being moved underground.

## 2. The design in one paragraph

Keep the existing citywide-per-class model (`lineUsageOf`/`congestionLinesOf`) **exactly as the SSOT for congestion consequences** — this item does not touch how the wellbeing/income penalty is computed, per GR#3 (one model, not two). It adds a **read-only, finer-grained decomposition**: within each line class (e.g. `rd_aroad`), group the class's tiles into **contiguous connected runs** (a "segment" — one physically continuous stretch of same-tier road, or one rail line's connected tile-run) and apportion that class's ALREADY-COMPUTED total usage across its segments **in proportion to each segment's own capacity share** — the identical apportionment idiom `lineUsageOf` already uses to split the combined rail commuter figure between `hs1` and `rail` (`data.ts:2364-2377`), just one level finer. No new demand model, no new flow simulation — this is arithmetic decomposition of a number that already exists, which is why it is safe to add without risking a second congestion mechanic (GR#3) or a new agent simulation (out of scope, this is Baseline One-adjacent as Aaron's brief states).

## 3. Per-segment aggregation — the ask, part **a**

### AC-1 — the aggregation unit is a contiguous connected run of same-class tiles, not a single tile and not the whole city

**Recommendation: per contiguous run**, not per tile. Rationale:
- Per-tile is too fine to be useful UI (a 500-tile motorway showing 500 identical numbers, since flow is apportioned by capacity and a run's tiles all share the same per-tile capacity within a class) and is pure noise over `lineUsageOf`'s existing citywide-per-class number.
- Per-city-class (today's `lineUsageOf` granularity) is too coarse to answer Aaron's literal question ("which motorway" not "how congested is the motorway network in aggregate").
- **Per contiguous run** is the natural unit a player actually points at — "this stretch, from the docks to the interchange, is the bottleneck" — and is computed with a standard flood-fill/union-find over same-spec-id tiles that are 4-adjacent, an O(tiles-of-that-class) pass, no different in shape from `stationLinks`' own adjacency walk (`data.ts:2208-2238`) or `computeRoadConnectivity`'s existing connected-component logic (cited by FEAT-2326609764 §1.3 as an existing `WeakMap`-on-`s.buildings` cache, `data.ts:610-617`) — this item reuses that SAME connected-component machinery rather than writing a second one (GR#3).

### AC-2 — segment capacity and usage are derived arithmetic, not new numbers

```ts
export interface LineSegment {
  /** Line spec id this segment belongs to. */
  spec: string;
  kind: 'rail' | 'road';
  /** Stable segment key — see AC-6 (must survive re-derivation and, later, undergrounding). */
  segmentId: string;
  /** Tiles making up this contiguous run. */
  tiles: number;
  /** Per-tile capacity (from ROAD_TIER_CAPACITY / LINE_CAPACITY, unchanged) × tiles. */
  capacity: number;
  /** This run's share of its class's total usage, apportioned by capacity share. */
  usage: number;
  saturation: number;   // usage / capacity, same shape as LineUsage
  headroom: number;
  overCapacity: boolean;
}
```

`capacity` per segment reuses `lineCapacityOf(sp)` (`data.ts:2281-2286`) unchanged — no new capacity constant. `usage` for a segment = `classUsage × (segmentCapacity / classTotalCapacity)`, the exact proportional-split idiom `lineUsageOf` already applies for the hs1/rail commuter split (`data.ts:2373-2377`) and for `overlaySubsetsOf`-style class-to-tile expansion. This is **read-only decomposition**: `Σ segment.usage` over one class's segments **must exactly equal** that class's `LineUsage.usage` (an integer-exact invariant test, same discipline as the existing `hs1 + rail === combined` proof at `data.ts:2371`).

### AC-3 — stations get a per-station attribution, reusing the SAME weight the class-level split already computes

`lineUsageOf`'s rail path already assigns each connected station a per-class weight (`hsWeight`/`railWeight`, `data.ts:2358-2363`). A station's own "utilisation" (Aaron's literal "how much is a station being used") = its weight ÷ the total weight of its class × that class's usage — again pure decomposition of an existing number, not a new demand signal. `stationLinks()`'s existing `connectedIds` set (`data.ts:2214-2237`) already tells us which stations count at all; a disconnected station reports null utilisation (honest-absence, mirrors `utilisationOf`'s null-basis convention at `data.ts:1083-1097`), never a fabricated zero-that-looks-like-a-real-measurement.

### AC-4 — buses and bus stops: honest absence, not a placeholder mechanic

No bus feature exists in `data.ts` today (no `SPECS` entry, no bus-specific capacity constant). Per GR#25, this item does **not** invent one. The contract for when a bus feature lands: **it should be able to plug into `LineUsage`/`LineSegment` as a THIRD `kind` value** (`'bus'` alongside `'rail'`/`'road'`) with its own `LINE_CAPACITY`-style table (buses-per-stop-per-tick), reusing this item's segment/overlay/congestion-consequence machinery unchanged — that is the interface commitment this item makes, not a built feature. **No code ships for buses in this item.**

## 5. Behaviour above 100% — AC-6

Unchanged mechanically: `congestionLinesOf`/`congestionFactorOf`/`CONGESTION_CONSTANTS` remain the SOLE source of consequence (income drag, wellbeing) and this item does not touch them (GR#3 — one congestion mechanic). What this item adds is **visibility**: a segment's `overCapacity`/`saturation` (AC-2) feeds the SAME per-line-class `sustainedTicks`/`isSustained` bookkeeping already keyed by `spec` in `s.congestionTicksBySpec` (`data.ts:2464-2501`) — **no change to that keying** (it stays per-class, not per-segment, because the congestion-teeth feature already shipped and re-keying it to segments would be a breaking change to a landed mechanic outside this item's scope). The per-segment view is presented as "here is WHERE the class-level congestion is concentrated," an honest decomposition, while the actual penalty stays exactly what it is today.

**Segment-level penalty is explicitly declined** by this item (kept as an open question, §8/Q100160) — introducing a genuinely NEW per-segment sustained-ticks structure would duplicate `sanitizeCongestionTicksBySpec`'s whole save-boundary/sanitisation apparatus (`data.ts:2454-2473`) for a second time, and Aaron's stated ask ("congestion slows commutes → feeds the existing… machinery, not a new parallel one") reads as an instruction against exactly that duplication unless he says otherwise.

## 6. The overlay — AC-7

Mirrors the water/power overlay idiom directly:
- **Building-subset cache pattern** — `overlaySubsetsOf(state.buildings)` (`MapView.tsx:86,490`) already partitions buildings into overlay-relevant subsets once per state; this item adds a `lines`/`network` subset the same way, not a fresh per-frame `s.buildings` walk.
- **Colour-by-saturation**, same ramp convention the water/power overlays already use (BUG-425's surplus/shortfall pos/neg colour split, cited at `data.ts:2298-2301` as the convention `LineUsage.overCapacity` already follows) — a segment at `overCapacity` renders in the danger colour, headroom renders in the surplus colour, matching what a player already reads on the water panel.
- **BUG-659 viewport-culling constraint, explicit and non-negotiable**: the overlay draws only the CURRENTLY VISIBLE, already-culled tile/building subset (the exact fix BUG-659 landed for the base render path, 9.10ms→0.41ms typical view via viewport culling, `MapView.tsx`) — this item's overlay must hook into that SAME culled draw pass, never add a second full-map per-frame walk. This is stated as a hard constraint because it is exactly the regression class (`O(buildings)` per frame) two P0s were just closed for.

## 7. Underground metro interaction — AC-8 (forward-compatible contract, not an implementation)

FEAT-2326609765 (Underground metro, unlocked at 7M population, **not yet built**) proposes moving major roads below ground into a tube network. This item does not build against that feature — GR#25 forbids speculative prose against an unregistered/unbuilt dependency — but it DOES make one structural commitment now, because retrofitting it later would be expensive: **a segment's identity (`segmentId`, AC-2) must be derived from the road/rail network GRAPH position (which physical stretch this is), not from "currently has a surface building here."** Concretely, `segmentId` should be a stable hash/key of the segment's tile-adjacency chain (or its endpoints, if the chain itself is treated as immutable once formed) rather than, say, an array index recomputed fresh each derivation pass. This means: **when FEAT-2326609765 eventually moves a road segment underground, that feature's own work is to re-flag the SAME segment's medium (surface→underground) — not to delete one `LineSegment` and mint a new one that loses its saturation/congestion history.** This item states the requirement; FEAT-2326609765's own BA pass implements it, once that item is actually scoped and any new `code.json`-relevant edge (if the underground mechanic ever crosses into Go) is registered first.

- **ASM-1517** — segment aggregation unit is a contiguous connected run of same-spec tiles (AC-1), computed via the SAME connected-component approach as `stationLinks`/`computeRoadConnectivity`, not a new algorithm. **RECOMMEND ACCEPT** — reuses existing machinery per GR#3, no new O(n²) risk.
