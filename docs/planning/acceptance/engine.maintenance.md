# Acceptance criteria — engine.maintenance (MOD-072)

**BOW code:** MOD-072 (P1, open) — "Maintenance system: per-instance aging, efficiency decline, lifetime, multi-fix crews."
**Spec refs:** §20 Roads & Auto-Naming (`docs/METROPOLIS-MASTER-v2.1.md` line 364: "maintenance state (potholes raise costs & lower speeds — maintenance budget is real)" — the per-object maintenance-state precedent this module generalises from roads to *every* placed object); §10 Service & Feature Inventory (line 232: "roads & road maintenance" named as a first-class service surface); §12 Failure — the Detroit Spiral (line 242: abandoned buildings carry a "decay state" that drags value and costs money to demolish — the end-of-life/decay precedent a past-lifetime object feeds); §54 The Fiscal Circuit (line 684: the Public Service Pie per-1k-population staffing targets — the staffing tie-in MOD-073 (engine.staffing) owns); §26 Emergency & Care Dispatch (line 412: "a nurse shortage is one shortage everywhere" — the shared-staffing-pool precedent MOD-073 (engine.staffing) generalises to repair staff); §5.2 determinism rule (line 181); code.json `engine.build` entry (the per-instance structure state this sits on).
**Design (Aaron, 2026-08-15, BOW MOD-072):** EVERY placed object carries a MaintenanceView — engineer-days/year scaled by size/class (50m single road vs motorway; wind turbine vs hospital). New objects need less repair; efficiency declines with age; each has a lifetime. A maintenance crew sets off for a DAY and fixes MULTIPLE jobs (10 potholes, or 2 schools, or a job list) — NOT one-trip-one-fix.
**This file's role:** this module is cross-cutting. It sits on `engine.build` (MOD-026, **done**, committed d7f2e72) whose per-instance state (`structures map[cellKey]BuildOrderID`, `zoneState map[cellKey]ZoneType`) is what a MaintenanceView attaches to; it feeds `engine.staffing` (MOD-073, open — the crew supply) and `engine.finance` (MOD-022, **done**, committed ecbb8bb — the OPEX drain; `SettleOpex`/`CatOpex` already exist in `internal/engine/finance`). This file owns the maintenance mechanic itself: the per-instance MaintenanceView, aging, lifetime, the multi-fix crew, and the conservation/backlog invariant. The crew-**supply** side (citizens-as-repair-staff, off-map contractors, training) is MOD-073's, and the OPEX-**ledger** placement of the drain is FEAT-094's. See "Cross-check" and "Escalations" for the remaining code.json seams.
**Date:** 2026-08-15
**Status:** draft-ahead — the module **is registered** in code.json (`engine.maintenance`, inbound `MaintenanceAPI`), but the class ladder its scaling refers to is **not yet authored** (see Escalations). Directional numbers only, per the balance-number regime below.
**Balance-number regime (standing rule, same convention as `engine.finance.md` AC-21 / `feat.deathwarnings.md` AC-3):** per-class engineer-day rates and per-class lifetimes are **placeholders** in a data file (`data/maintenance.json`), each carrying a disclosure comment naming it pending Aaron's balance pass. No AC may be satisfied by a junior inventing a final rate or lifetime; every AC touching a rate/lifetime requires the value to live in the data file and requires tests to check **direction/structure** (new < old; two classes differ; a past-lifetime object is flagged) rather than pinning a specific figure.

## User stories

- **US-1.** As a placed object, I need a **per-instance** MaintenanceView (engineer-days/year, age, efficiency, lifetime) so each object ages and degrades independently of every other object of the same type — a 50-year-old hospital and a 2-year-old hospital are two different maintenance realities, not one shared row (§20 generalised; design).
- **US-2.** As the player, I need a placed object's efficiency to decline monotonically with age, with new objects needing less repair than old, so aging is a real, felt curve that makes the age of my stock matter (design: "new objects need less repair; efficiency declines with age").
- **US-3.** As the player, I need an object whose age has passed its lifetime to be flagged for refit/rebuild (a distinct, queryable state), not to silently keep working, so end-of-life is a real decision point rather than an invisible number (§12's decay-state precedent).
- **US-4.** As a maintenance crew, I need my daily work capacity to be a **job list** — N potholes or M schools or a mixed list — not one-trip-one-fix, so one crew-day resolves multiple jobs rather than a single repair per outing (design).
- **US-5.** As the city's books, I need a crew's daily capacity to be a **bounded budget** and un-fixed demand to **accumulate as a visible backlog**, so under-funding maintenance produces a growing, inspectable deficit rather than silently vanishing work (design: conservation).
- **US-6.** As `engine.staffing` (MOD-073), I need city-wide repair demand (the aggregate of every placed object's engineer-days/year plus the accumulated backlog) surfaced through one stable contract, so crew supply can be matched against real demand instead of an invented figure.
- **US-7.** As `engine.finance`, I need maintenance spend (crew cost when met locally, off-map contractor cost for the un-met remainder) reported as OPEX through finance's existing settlement surface, so the drain is visible and real rather than a maintenance-local shadow ledger (FEAT-094's concern, fed by this item).

## Scope

A per-instance MaintenanceView on every placed structure (engineer-days/year scaled by class, age, efficiency, lifetime), data-driven class scaling and lifetimes from `data/maintenance.json`; monotonic aging and a past-lifetime refit/rebuild flag; a multi-fix crew whose daily capacity is a bounded engineer-day budget applied against a job-list backlog with a conservation invariant; and the two feed edges — city-wide demand to `engine.staffing`, maintenance spend to `engine.finance` OPEX. No crew-supply modelling (MOD-073), no OPEX-ledger placement (FEAT-094/`engine.finance`), no class-ladder authoring (MOD-024/`engine.roads` + the future building catalogue), and no final rate/lifetime values (Aaron's balance pass).

## Acceptance criteria

### Functional — the MaintenanceView and its scaling

- **AC-1 (GR#20; per-instance — one view per placed object, not per zone type).** Every placed structure carries its **own** MaintenanceView, keyed to the structure's identity (engine.build's per-cell `Structure`/`BuildOrderID`), not a single view shared per `ZoneType`. Two otherwise-identical objects of the same class placed at different times hold distinct records with distinct ages, and aging one does not move the other. Check: `go doc ./internal/engine/maintenance MaintenanceAPI` (or wherever the view lands — see Escalation ES-1) shows a per-structure view surface; a passing test places two same-class structures at different months, ages the world, and asserts their two MaintenanceView ages differ and that mutating/aging one leaves the other byte-identical (`grep -rn "func Test.*[Pp]erInstance\|func Test.*[Ss]ameClass.*[Dd]istinct" internal/engine/maintenance/*_test.go`). **False-pass risk:** a `map[ZoneType]MaintenanceView` keyed by type (one view shared by every dwelling) would pass a naive "a MaintenanceView exists" grep while violating the item's own "per-instance" premise — the check requires two same-class instances to hold independent ages.

- **AC-2 (GR#15; engineer-days/year scaled by class, data-driven).** Each instance's engineer-days/year figure is a function of its **class**, loaded from `data/maintenance.json` (per-class rate × a size/scale factor), with the class→rate mapping in data, never a hardcoded per-class Go literal. The data file must define **at least two classes with distinct rates** so "scaled by size/class (single road vs motorway; wind turbine vs hospital)" is a real ordering, not a single constant wearing a class field. Check: a passing test mutates one class's rate in the loaded `data/maintenance.json` fixture and asserts the computed engineer-days/year for that class (and only that class) reflects the change (`grep -rn "func Test.*[Dd]ataDriven\|func Test.*[Rr]eload.*[Mm]aintenance" internal/engine/maintenance/*_test.go`); `grep -nE "[0-9]+" internal/engine/maintenance/*.go` (excluding `_test.go`) finds no bare engineer-day-rate/lifetime-shaped numeric literals outside doc-comment prose. **False-pass risk:** a single shared rate for all classes with the "class" field merely recorded (but not scaling the number) would pass a "per-class field exists" grep while the design's "scaled by size/class" promise is unmet — the check requires two classes to resolve to two different rates from data. **Balance-regime note:** the specific rates are placeholders with disclosure comments (see AC-16); this AC checks *scaling-by-class is real and data-driven*, not any specific magnitude.

### Functional — aging and lifetime

- **AC-3 (aging — efficiency declines monotonically with age; new needs less repair than old).** An instance's efficiency is a non-increasing function of its age: for two otherwise-identical instances with ages `a < b`, `efficiency(a) >= efficiency(b)` holds for every pair the test exercises, and the per-instance repair demand of the newer instance is `<=` that of the older. New objects needing less repair is the load-bearing direction. Check: a passing directional test ages a fixture through several ages and asserts the efficiency sequence is monotonically non-increasing and the repair-demand sequence monotonically non-decreasing, never a reversal (`grep -rn "func Test.*[Mm]onotonic.*[Ee]fficiency\|func Test.*[Nn]ewLessThanOld" internal/engine/maintenance/*_test.go`). **False-pass risk:** a test that pins one specific efficiency number would pass an implementation whose curve happens to agree with that number today but is not actually monotonic elsewhere — this AC asserts the *ordering*, not a value. **Balance-regime note:** the shape/steepness of the curve is a placeholder; the monotonicity is the invariant, not the slope.

- **AC-4 (lifetime — a past-lifetime object is flagged for refit/rebuild, not silently kept).** Each class carries a lifetime (simulation-years, data-driven placeholder). An instance whose age has reached/passed its lifetime transitions to a distinct, queryable end-of-life state (`NeedsRefit`/`EndOfLife` — documented which), and that flag is exposed through the maintenance query surface — the object does not silently continue at full efficiency. Check: `go doc ./internal/engine/maintenance` shows the flag state and its transition; a passing test ages an instance to exactly its lifetime and asserts the flag flips and remains set beyond it, while an otherwise-identical instance just under the lifetime stays unflagged (`grep -rn "func Test.*[Ll]ifetime\|func Test.*[Rr]efit.*[Ff]lag" internal/engine/maintenance/*_test.go`). **False-pass risk:** an "efficiency asymptotically approaches zero" implementation with no explicit lifetime flag would pass a "old objects are worse" reading of AC-3 while the design's "each has a lifetime … flagged for refit/rebuild" decision point never materialises — the check requires the *distinct flag*, not just worsening numbers. **Balance-regime note:** the lifetime value per class is a placeholder (disclosure comment, AC-16); this AC checks the flag exists and flips, not the number of years.

### Functional — the multi-fix crew and conservation

- **AC-5 (multi-fix — a crew's day is a job list, not one-trip-one-fix).** A crew's daily capacity is expressed as a bounded engineer-day budget applied against a **list** of jobs (each job a class-scaled repair unit — a pothole costs a fraction of a school's repair). In one crew-day (one maintenance tick), the crew resolves **multiple** jobs when its budget suffices, up to the budget — a budget worth 10 potholes against a 10-pothole backlog resolves all 10 in a single day, not one pothole per day over ten days. Check: a passing test builds a crew with a budget equal to 10 × the pothole-class job cost and a 10-job backlog of that class, runs one day, and asserts all 10 jobs resolved in that single tick (`grep -rn "func Test.*[Mm]ultiFix\|func Test.*[Jj]obList\|func Test.*[Tt]enJobs.*[Oo]neDay" internal/engine/maintenance/*_test.go`). **False-pass risk:** an implementation that caps each crew-day at exactly one job (resolving one pothole and "banking" the rest of the budget) would pass a conservation-of-budget reading of AC-6 while the design's central "NOT one-trip-one-fix" requirement fails — the check requires *>1 job resolved in one day*, which is the whole point of the feature.

- **AC-6 (bounded daily budget + conservation — GR#16).** A crew's daily capacity is a **bounded** budget: the total engineer-days applied across all jobs in one day never exceeds the day's budget, the budget is never driven negative, and un-applied budget does not invent or destroy work. All budget arithmetic routes through the project's saturating helpers (`foundation/num`), matching `engine.build`'s and `engine.finance`'s numeric-safety standard (FEAT-086). Check: a passing conservation test applies a crew against a backlog larger than its budget and asserts (a) applied engineer-days `<=` budget, (b) budget never negative, (c) the unresolved remainder is exactly the difference and is still present as backlog (`grep -rn "func Test.*[Cc]onserv\|func Test.*[Bb]udget" internal/engine/maintenance/*_test.go`). **False-pass risk:** a float-based budget that over-applies to clear a backlog slightly bigger than the budget (rounding in the crew's favour) would pass a loose "backlog eventually empties" check while leaking engineer-days from nowhere — the check requires the ledger to balance exactly, in integer engineer-day units.

- **AC-7 (backlog accumulates, is visible, and decreases only by applied work).** Un-fixed demand accumulates as a **visible** backlog (queryable per-class and city-wide): under sustained under-funding the backlog grows monotonically; it decreases only by exactly the engineer-days a crew actually applies; and it never goes negative. Check: a passing test under-funds a growing city for N days and asserts the backlog strictly grows day-over-day, then applies a known budget and asserts the backlog decreases by exactly the applied engineer-days (`grep -rn "func Test.*[Bb]acklog" internal/engine/maintenance/*_test.go`). **False-pass risk:** a "backlog" that is recomputed fresh each tick as `demand − applied` (with no persistent accumulation) would read zero under steady under-funding and pass a "backlog is queryable" grep while the design's "un-fixed demand accumulates" promise fails — the check requires the backlog to *grow* under under-funding, proving accumulation is stateful.

### Functional — the two feed edges (engine.staffing, engine.finance)

- **AC-8 (city-wide repair demand surfaced for MOD-073).** The maintenance query surface exposes city-wide repair demand — the sum of every placed object's engineer-days/year plus the accumulated backlog — computed by aggregation, not a separately-maintained counter. Check: a passing test places several objects across classes and asserts the reported city-wide demand equals the sum of the per-instance demands the same surface reports (conservation of aggregation) (`grep -rn "func Test.*[Cc]ityWide.*[Dd]emand\|func Test.*[Aa]ggregate.*[Dd]emand" internal/engine/maintenance/*_test.go`). **False-pass risk:** a hand-incremented `cityDemand += x` counter that can drift out of step with the actual per-instance sum would pass a "demand is queryable" grep while MOD-073 reads a wrong number — the check requires the aggregate to be derived from (and equal to) the sum of its parts.

- **AC-9 (crew supply is injected, not maintenance-local — GR#20 boundary to MOD-073).** The crew capacity (how many crews / how many engineer-days are available today) is an **injected input** (an interface or setter MOD-073 wires), never computed by the maintenance module itself from citizen/population state — maintenance owns the *demand* and the *application* of work; MOD-073 owns the *supply*. Check: `go doc ./internal/engine/maintenance` shows a supply-injection surface (e.g. `SetCrewCapacity`/`SetDailyBudget`) with no citizen/education/employment import in the maintenance package; `grep -rn "households\|citizens\|education" internal/engine/maintenance/*.go` (excluding `_test.go`) returns no matches. **False-pass risk:** a maintenance module that computes crew availability from population itself would pass a "crews exist" functional test while pre-empting MOD-073's entire mandate and coupling maintenance to a not-yet-built module — the check requires the supply boundary to be explicit and external.

- **AC-10 (maintenance spend flows to engine.finance as OPEX, not a maintenance-local ledger).** Maintenance spend — crew cost when the daily budget meets demand locally, off-map contractor cost for the un-met remainder — is reported to `engine.finance`'s existing OPEX surface (`SettleOpex`/`CatOpex`, already built in MOD-022), never accumulated in a maintenance-local money ledger that finance cannot see. Check: `grep -n "finance\.\|FinanceAPI\|SettleOpex" internal/engine/maintenance/*.go` finds the call into the registered finance edge; `grep -nE "[Pp]ounds|micro|Money" internal/engine/maintenance/*.go` (excluding `_test.go`) finds no maintenance-local currency ledger type. **False-pass risk:** a maintenance module that computes a "cost" figure for display but never settles it through finance would pass a "spend is computed" grep while FEAT-094's "maintenance is a MAJOR drain" OPEX promise is silently un-met — the check requires the finance settlement call. **Boundary note:** the *engineering* of the contractor rate and the OPEX categorisation is FEAT-094's; this AC only requires the spend to cross into finance's surface, not the full P&L placement.

### Error handling

- **AC-11 (GR#7).** Operating on an unknown structure reference, an unknown class key, a negative age, or assigning a negative crew budget returns a registry-sourced error (a new `MET-`-range code claimed at build time), never a panic or a silently-accepted no-op a caller could mistake for success. Check: `grep -n "MET-" internal/engine/maintenance/*.go` finds a registry-code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownClass\|func Test.*[Nn]egative.*[Bb]udget" internal/engine/maintenance/*_test.go`) asserts the returned error's registry code matches **and** that no maintenance state (age, backlog, spend) was mutated on failure — not merely that a matching-named test function exists (GR#7 assertion, stated explicitly).

- **AC-12 (GR#7).** A malformed or schema-invalid `data/maintenance.json` (a class missing its rate, a negative lifetime, an unrecognised class string, a class rate defined but absent from the resolvable class vocabulary) produces a registry-sourced error at load time, never a silent default substitution that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/maintenance/*.go` finds a load-time registry code distinct from AC-11's; passing test coverage (`grep -rn "func Test.*[Mm]alformed\|func Test.*[Ii]nvalidMaintenance" internal/engine/maintenance/*_test.go`) asserts the error's registry code matches **and** that no default-substituted rate/lifetime was loaded in place of the malformed one.

### Determinism & safety

- **AC-13 (GR#21).** The maintenance tick resolution (aging, efficiency derivation, backlog growth, crew application) is a deterministic function of prior tick state, loaded data, and injected inputs — repeated runs from an identical snapshot over an identical command/injection sequence produce byte-identical MaintenanceView/backlog state, across worker counts. Check: a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/maintenance/*_test.go`); and `grep -rn "time.Now\|time.Since" internal/engine/maintenance/*.go` (excluding `_test.go`) returns no matches — age advances by simulation tick/month index only, never wall clock (the same SG-7 gate `engine.build` AC-13 and `engine.roads` AC-17 enforce). Never assert a wall-clock upper bound on how long a tick takes in CI; assert tick-count/state equality only.

- **AC-14 (GR#21).** `go test ./internal/engine/maintenance/... -race -count=1` passes with no data race when the maintenance query surface (per-instance view, backlog) is read concurrently with a tick aging objects and applying a crew. Check: `grep -n "go func()" internal/engine/maintenance/*_test.go` finds at least one concurrency test.

## Spec-fold amendments (FEAT-084 SF wave, 2026-08-18)

> Substantive AC amendments folded from the FEAT-084 ASM disposition (class SF).

### ASM-1225 — crews resolve whole jobs only (amends AC-6)
Job-list semantics (a pothole is fixed or not) and integer engineer-day conservation require indivisibility: a crew resolves **whole jobs only** — a job whose cost exceeds the remaining daily budget is skipped (not partially resolved), and the crew stops at the first unaffordable job in FIFO order. Partial resolution would force fractional engineer-days into the ledger and lose AC-6's exact-integer balance. Check: a test gives a crew a budget smaller than one job's cost and asserts that job is skipped whole (zero partial spend) and the budget is conserved to the integer.

### ASM-1300 — SetFinance is dependency injection, not config (amends AC-10)
`SetFinance` stores a raw `*finance.FinanceAPI` pointer that is **not** cloned: it wires a live shared collaborator whose whole purpose is to post `SettleOpex` into the same treasury the composition root holds, and cloning it would break the AC-10 settle-to-finance edge. It is classified as dependency injection, not the SEC-167 config-aliasing class (a config struct stored by value with a reference-typed field). Check: the doc comment on `SetFinance` states the DI rationale so a future SEC-167 sweep does not re-flag it as config aliasing.

### ASM-1227 — nil-finance skips spend settlement (amends AC-10)


When finance is not wired (nil), `RunCrewDay` still applies the crew day but skips the spend settlement entirely — there is no maintenance-local shadow ledger.
