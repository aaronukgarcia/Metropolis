# Acceptance criteria — BOW prose-reference drift lint (FEAT-060)

**BOW code:** FEAT-060 (P2, open) — "BOW hygiene lint: flag prose-named codes not wired as dependencies, and depend/ref drift."
**Spec refs:** GR#15 (validators/derived constants come from data, never a hardcoded stale list — governs the code-prefix set, AC-1); GR#12 (`done` refuses while dependencies are open — this item is the prose-level mirror of that mechanical check, since GR#12 only sees `bow_dependencies` rows, not description text); `dev-team-process.md`'s "an AC's check must be able to fail" standard (v1.9, BUG-033) and the astgate lesson cited in FEAT-060's own description ("report-only first... land green, then ratchet," `tool.astgate.md` AC-13/AC-15); BUG-012 (the Class-1 motivating example — its own description names MOD-068/MOD-069/INT-004 as a gating condition with zero corresponding `bow_dependencies` rows); BUG-075 (the Class-2 motivating example — fabricated ASM codes relayed as fact, none resolving to a real `bow_items` row).
**Date:** 2026-08-11
**Status:** active
**Package under test:** a new subcommand on the existing `claude-bow.js` CLI (not a new file, not a `/codejson-audit` extension — see the standalone-vs-extension decision below and ASM logged against it), plus supporting test coverage against a scratch database, not `metro`.

## Standalone-vs-extension decision (binding on the build)

FEAT-060's own description offers a choice: "a `claude-bow.js` lint (or `/codejson-audit` extension)." This file requires the **standalone `claude-bow.js` subcommand** shape, for reasons a developer must not silently override:

- `/codejson-audit` (`.claude/commands/codejson-audit.md`) audits consistency **between three stores that are supposed to agree** — `master-plan-v2.1.json`, generated `code.json`, and the BOW's mirrored planning fields (guid/seq/sprint). Its checks are diff-and-regenerate operations against files, run by an agent following prose instructions, not a program.
- FEAT-060 audits something structurally different: **free-text prose inside `bow_items.description` and `bow_comments.body` against the `bow_dependencies` graph and `bow_items.code`/`status` columns** — a pure database query, with no code.json or master-plan involvement at all. It has more in common with `cmdWeakness` (`claude-bow.js weakness`, a report over `bow_items`/`finding_class` with no file-diffing) than with anything `/codejson-audit` does.
- A `/codejson-audit` extension would mean teaching a markdown-instructions skill to run SQL-shaped prose reasoning over free text, which is exactly the kind of check that should be mechanical and repeatable rather than agent-interpreted — the same reasoning FEAT-060's own description gives for wanting this "cheap, mechanical" in the first place.

Binding shape: `node claude-bow.js lint` — one new subcommand, implemented in `claude-bow.js` alongside `cmdWeakness`/`cmdReady`, added to the `switch` in the entry block and to the usage string. `/codejson-audit`'s instructions **may** grow a one-line pointer to `node claude-bow.js lint` as a related-but-separate check in a later pass — that is out of scope for this item's initial build (see Out of scope).

## User stories

- As **Bill (lead)**, I need a mechanical report of BOW items whose prose claims a gating relationship the dependency graph does not actually encode, so that `node claude-bow.js ready`'s output can be trusted as what is *actually* blocking, not what a description merely says is blocking (the BUG-012 class).
- As a **Tester or the lead relaying a cited code into a downstream brief**, I need a one-command way to see which cited codes in the BOW's own text do not resolve to a real item, so that the BUG-075 class (a fabricated citation propagating as fact) is caught by a tool instead of by a Tester noticing it by hand.
- As the **project's process discipline**, I need this lint to be safe to run and safe to ignore on day one — report-only, exit 0 always — so that landing it does not risk becoming a second, uncoordinated blocking gate alongside `tool.astgate`'s and requires no CI change to ship.

## Acceptance criteria

### Detection mechanism — token extraction (scope item 1)

- **AC-1 (GR#15 — prefix set derived, not duplicated).** The set of BOW-code prefixes the lint recognises (`MOD`, `FEAT`, `BUG`, `INT`, `ASM`, `SEC`) is read from the **existing `TYPE_PREFIX` constant already defined in `claude-bow.js`** (`{ module: 'MOD', feature: 'FEAT', bug: 'BUG', interface: 'INT', assumption: 'ASM', finding: 'SEC' }`) — never a second, independently-typed list of prefix strings. Because the lint lives in the same file as `TYPE_PREFIX`, this is satisfiable by direct reference (`Object.values(TYPE_PREFIX)`), not merely by a documentation pointer; there is no cross-file duplication to drift, so weakness pattern #2's "duplicated value needs a drift test" does not even apply here — the correct fix is simpler than a mirror-plus-test, and a developer reaching for the mirror-plus-test pattern out of habit has overbuilt it. Check: `grep -n "TYPE_PREFIX" claude-bow.js` shows exactly one object literal definition; the lint's token regex is built from that object's values at runtime (e.g. via `Object.values(TYPE_PREFIX).join('|')`), confirmed by a test that temporarily can't literally mutate the constant (it's a `const`) but can assert, via a unit test on the extraction function alone, that it returns the same prefix set `Object.values(TYPE_PREFIX)` yields — i.e. the test derives its expectation from the constant, not from a hardcoded `['MOD','FEAT','BUG','INT','ASM','SEC']` array (GR#15 applies to the test too, not just the implementation). **What a lazy implementation looks like:** a regex literal `/\b(MOD|FEAT|BUG|INT|ASM|SEC)-\d+\b/` typed directly into the lint function — it happens to agree with `TYPE_PREFIX` today, and will silently stop covering a 7th type the day one is added, exactly the stale-list failure GR#15 exists to prevent.
- **AC-2 (extraction scope — which columns).** The lint scans `bow_items.description` and `bow_comments.body` for every item in the database (open and closed both — Class 3 specifically needs closed items). It does **not** scan `bow_comments.example_code`: that column already exists as a structurally separate field precisely so that a code appearing inside an illustrative code sample (e.g. a comment showing a worked `node claude-bow.js depend` invocation that happens to name a BOW code as its example argument) is not conflated with a code appearing in the comment's prose. Check: a fixture comment with a real, non-existent-code-shaped token (e.g. `FEAT-999`) placed only in `example_code` (with `body` containing unrelated text) produces **zero** findings from the lint; the same token placed in `body` instead produces a Class-2 finding (assuming `FEAT-999` is not a real item — construct the fixture so it isn't). **What a lazy implementation looks like:** concatenating `body` and `example_code` before scanning "to be thorough" — this reintroduces exactly the conflation the schema's column split was already designed to prevent, and the check above catches it directly.
- **AC-3 (extraction scope — backtick-quoted literals inside prose).** Within `description`/`body` text (not `example_code`, per AC-2), a code-shaped token that appears inside a single backtick span (`` `LIKE-THIS` ``) is extracted as a **candidate** but is never, on its own, sufficient to produce a Class-1 finding — backtick-wrapping in this project's own written BOW comments is the established convention for "naming a code as an illustrative example" (e.g. this very file's AC-1 uses `` `MOD-068` ``-shaped literals no differently), not for "asserting a real gating relationship." It remains eligible for Class-2 (does-it-resolve) and Class-3 (done-but-cites-open-gate) checks, since those two classes are mechanical regardless of quoting style — only Class-1's phrase-trigger check (AC-5/AC-6) treats backtick-quoting as a signal that lowers confidence. Check: a fixture description containing a gating-trigger phrase (per AC-5) immediately followed by a backtick-quoted code that is not wired as a dependency does **not** produce a Class-1 finding, while the same phrase with a bare (non-backtick-quoted) code **does**. **False-pass warning:** this AC is deliberately narrow — it only suppresses Class-1 on backtick-quoted tokens, not Class-2/Class-3; an implementation that skips backtick-quoted tokens entirely would silently under-report Class 2 (a fabricated code cited as `` `ASM-347` `` in a report, mirroring exactly how BUG-075's fabricated codes could plausibly have been written) and must be rejected.

### Class 1 — prose-named, not wired as a dependency (scope item 2, the hardest of the three)

**Detection-rule decision, stated and defended up front, per this brief's explicit instruction to be honest about how hard this is:** distinguishing a genuine gating claim ("gate it against MOD-068") from an incidental mention ("similar to the pattern in MOD-068", "see also SEC-030") cannot be done reliably by proximity to a keyword — `tool.astgate.md`'s own acceptance file mentions `SEC-030`/`SEC-031(b)` more than a dozen times as historical worked examples, and a "code near the word gate/block" heuristic run over that file's eventual BOW description text would manufacture Class-1 findings against every one of those incidental citations. The chosen rule is **precision over recall**: a small, closed, in-source list of literal gating **phrase templates**, matched against the same sentence (bounded by `.`/`;`/newline) that contains the code token, not the whole field. A code token is a Class-1 candidate only if one of these phrases appears in the same sentence:
  - `gate (it )?against`, `gated against`, `gating against`
  - `gate (it )?on`, `gated on`
  - `blocked by`, `blocks on`
  - `must land before`, `whichever lands first`

This list is intentionally short and will **under-match** novel phrasings a future item might use (e.g. "waits on X" or "can't ship until X" would not trigger it as written). That is the accepted tradeoff, not an oversight: a report-only tool that is noisy on day one trains its own readers to ignore it, which is the exact failure `tool.astgate.md`'s "land green, then ratchet" lesson (cited in FEAT-060's own description) exists to avoid. The phrase list is a single named constant in the lint's source (GR#15 — visibly the one place it lives), and growing it in response to a real missed instance is expected future work, not a defect in this initial version.

- **AC-4.** For each sentence containing both a code-shaped token (per AC-1/AC-2, from `description` or `body`, per AC-3's confidence adjustment) and one of the gating-phrase templates above, the lint checks whether a `bow_dependencies` row exists with `item_guid` = the owning BOW item and `depends_on_guid` = the referenced code's item (resolved via the same `code`-lookup `findItem` already uses). If no such row exists, it is a **Class-1 finding**: `<owning item code> — prose says "<matched phrase>" about <referenced code>, but no bow_dependencies row links them`. Check: a fixture item whose description reads `"...gate it against FIX-100..."` where `FIX-100` is a real item and no `bow_dependencies` row links the two produces exactly one Class-1 finding naming both codes and the matched phrase.
- **AC-5.** The BUG-012 shape — multiple codes joined by `/` or `or` inside one gating phrase's sentence ("gate it against MOD-068/MOD-069 or INT-004") — produces **one Class-1 finding per referenced code that lacks a dependency row**, not one finding for the sentence as a whole; if some of the joined codes are wired and others are not, only the unwired ones are reported. Check: a fixture sentence naming three codes after one gating phrase, where exactly one of the three has a real `bow_dependencies` row to the owning item, produces exactly two Class-1 findings (the other two codes), not one and not three.
- **AC-6.** A code-shaped token appearing in a sentence with **no** gating-phrase match is never a Class-1 finding, regardless of how close it sits to unrelated gate/block vocabulary elsewhere in the field. Check: a fixture description containing the sentence "MOD-068 blocks other work in general, but not this item specifically" in one sentence and, in a separate sentence, "see MOD-068 for background" — construct so neither sentence contains one of the AC-4 literal phrase templates — produces zero Class-1 findings for MOD-068 from that item. **False-pass warning:** an implementation using a wide window (e.g. "code within 40 characters of the word gate") rather than a sentence-bounded, exact-phrase match would flag this fixture; the check specifically exists to catch that broader, noisier implementation.

### Class 2 — codes that do not resolve at all (scope item 3, mechanical)

- **AC-7.** Every code-shaped token extracted per AC-1/AC-2/AC-3 (regardless of Class-1 phrase-matching — Class 2 applies to *every* extracted token, not just gating-phrase ones) is checked against `bow_items.code` (case-insensitive, matching `findItem`'s existing `UPPER(code) = UPPER(?)` behaviour — no second, differently-cased comparison invented for this command). A token with no matching row is a **Class-2 finding**: `<owning item code> — cites "<token>" which does not exist in bow_items`. Check: a fixture item whose description contains a token matching the recognised-prefix shape (e.g. `ASM-999`) that is not a real row in a scratch `bow_items` table produces exactly one Class-2 finding; the same fixture with `ASM-999` replaced by a real, existing code produces none. This is the direct mechanical reproduction of the BUG-075 shape (fabricated ASM codes cited as fact) — the check is not "does this look like a plausible code," it is "does this row actually exist," which is exactly what a `claude-bow.js show` on BUG-075's fabricated codes would have failed to find had anyone run it at the time.

### Class 3 — done items whose text cites a gate that is still open (scope item 4)

- **AC-8.** For every `bow_items` row with `status = 'done'`, the lint re-runs the AC-4/AC-5 sentence-level gating-phrase match against that item's `description` and its comments' `body` text, and for each resulting referenced code, checks that code's **current `status`**. If the referenced item's status is in `OPEN_STATUSES` (`open`, `in_progress`, `blocked` — the same constant `cmdReady`/`cmdList` already use, not a redefined list), it is a **Class-3 finding**: `<done item code> — done, but its own text says "<matched phrase>" against <referenced code>, which is still <status>`. Check: a fixture item marked `done` whose description contains `"...gated against FIX-200..."` where `FIX-200` is a real, currently-`open` item produces exactly one Class-3 finding; the same fixture with `FIX-200` set to `done` (or `cancelled`) produces none.
- **AC-9.** Class 3 reuses the exact same phrase-template constant and sentence-bounding logic as Class 1 (AC-4's list) — not a second, independently-maintained phrase list — since the underlying detection question ("does this text assert a genuine gating relationship") is identical; only the downstream check differs (dependency-row-exists vs. referenced-item-status). Check: `grep`-style review of the lint's source confirms the gating-phrase array is defined once and referenced by both the Class-1 and Class-3 code paths.

### Report-only posture (scope item 5)

- **AC-10 (explicit, matching `tool.astgate.md` AC-13/AC-15's discipline of stating the CI-wiring choice as plainly as the detection logic).** `node claude-bow.js lint` **always exits 0**, regardless of how many findings of any class it reports — there is no `--strict`/exit-nonzero mode in this initial version, and no code path in this command calls `process.exit` with a nonzero code for a finding (as distinct from a genuine usage/connection error, which every other `claude-bow.js` command already exits nonzero for and this one may too). Check: a fixture database seeded with at least one instance of each of the three finding classes still produces exit code 0 when `node claude-bow.js lint` is run against it (`$?`/`$LASTEXITCODE` after the call, in the same style the Tester baseline already checks exit codes for other commands).
- **AC-11.** The lint is **not** wired into any hook, CI job, or pre-commit path in this version — `.github/workflows/ci.yml`, `.claude/settings.json`'s hooks array, and `claude-pre-commit-check.js`/`claude-plan-guard.js` are all untouched by this item's build. It is invoked on demand (`node claude-bow.js lint`) or, at the lead's future discretion, folded into `startup-summary`'s printed output as an additional informational line — that wiring, if wanted, is a separate follow-up decision, not part of this item's initial scope (see Out of scope). Check: `git status` / `git diff --stat` for the commit delivering this item shows no changes to `.github/workflows/ci.yml`, `.claude/settings.json`, or any `claude-*-check.js`/`claude-*-guard.js` file. **What a lazy implementation looks like:** adding a quiet one-line call into `claude-pre-commit-check.js` "since it's cheap to run" — this is exactly the shortcut FEAT-060's own description explicitly rules out by citing the astgate lesson, and it would make this item silently blocking on day one with no BA sign-off on that step.

### Fixture-driven negative controls (scope item 6, mirrors `tool.astgate.md` AC-8/9/10)

- **AC-12.** The lint's test suite runs against a **scratch/test database**, never the project's real `metro` database — using the same `METRO_DB_*` environment-variable override mechanism `claude-bow.js`'s `connect()` already supports (e.g. `METRO_DB_NAME=metro_test_bowlint`), so fixture rows never appear in `node claude-bow.js list`/`ready`/`show` against the real BOW. Check: the test setup/teardown creates and drops (or fully clears) a distinctly-named test database, and a passing test asserts the real `metro` database's `bow_items` row count is unchanged before/after the full lint test suite runs.
- **AC-13.** A **Class-1 fixture**, run through the real lint logic (not an assertion of intent): an item whose description contains a gating-phrase-matched reference to a second, real item with no corresponding `bow_dependencies` row — mirroring BUG-012's exact shape (one item, three referenced codes joined by `/`/`or`, zero of them wired). Asserts the lint reports at least the expected Class-1 finding(s) naming the correct codes.
- **AC-14.** A **Class-2 fixture**: an item whose description or a comment's body cites a code-shaped token that resolves to no real `bow_items` row — mirroring BUG-075's exact shape (multiple fabricated codes cited as if real). Asserts the lint reports a Class-2 finding for each fabricated token and **not** for any real code also present in the same fixture text.
- **AC-15.** A **Class-3 fixture**: a `done` item whose description/comment text gating-phrase-references a second item that is still `open`. Asserts the lint reports the Class-3 finding, and that setting the referenced item to `done` (same fixture, mutated) makes the finding disappear on a re-run — proving the check reads live status, not a cached snapshot (the same "mutate the data, don't grep for it" standard this project already holds itself to elsewhere).
- **AC-16 (the clean case — proves AC-13/14/15 exercise real detection, not an always-on or always-off gate).** A fourth fixture with zero drift of any class — every prose-cited code either has no gating-phrase match, or does and is properly wired as a dependency; every cited code resolves; no `done` item's text cites an open gate — produces **zero** findings across all three classes when run through the same lint logic. Check: a passing test asserts the lint's finding count is exactly 0 against this fixture, run in the same test process as AC-13/14/15 so a gate that always reports (or never reports) findings cannot pass all four.

## Out of scope

- Wiring `node claude-bow.js lint` into `startup-summary`, any CI job, or any hook — deliberately deferred per AC-11; a future item may propose "ratcheting" it once its false-positive rate is observed against the real BOW, per the astgate-lesson framing FEAT-060's own description invokes.
- Adding a pointer to this lint from `/codejson-audit`'s instructions (`.claude/commands/codejson-audit.md`) — plausible future polish, not required for this item, and that file is not owned by this acceptance file's scope regardless.
- Expanding the Class-1 gating-phrase list beyond the six templates in AC-4 — logged as a known, accepted under-match (see the Class-1 preamble), not silently handled.
- Auto-fixing anything the lint finds (auto-adding a missing `bow_dependencies` row, auto-reopening a wrongly-`done` item) — this item reports only; any remediation is a separate, human-reviewed action.

## Escalations

- Whether the Class-1 gating-phrase list should eventually grow, and by what process (a BA amendment vs. an ad-hoc developer addition when a bounce reveals a missed phrasing), is a call for Bill once real usage produces evidence either way — not resolved here.
- Whether `lint` is the right final subcommand name (vs. e.g. `bow-lint`, `drift`, `audit`) is subject to Bill's review at build dispatch; no existing `claude-bow.js` subcommand uses a hyphen, which is the reasoning behind choosing the single word `lint` here, but it is a naming call, not a structural one.

## Assumptions logged (process v1.7)

- **ASM-401** — the standalone-`claude-bow.js`-subcommand vs. `/codejson-audit`-extension choice is decided in this file as standalone (see the dedicated section above), because the two audits check structurally different things (file-vs-file/plan drift vs. database-prose-vs-database-graph drift) and `/codejson-audit`'s existing shape (agent-followed markdown instructions calling `node tools/plan/generate.js --check`) has no natural home for a SQL-shaped prose scan.
