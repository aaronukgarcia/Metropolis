# Acceptance criteria — engine.dispatch (MOD-040)

**BOW code:** MOD-040
**Spec refs:** §26 Emergency & Care Dispatch Model (unified) (`docs/METROPOLIS-MASTER-v2.1.md` lines 408-410: fire/ambulance/air-ambulance/police share one dispatch engine — incident spawns at a cell → nearest available unit assigned → travels the real road network at blue-light speed (congestion still bites, ~×1.6 free-flow, not teleport) → outcome quality = f(response time); fire spread is per-cell (material, density, wind, hydrant pressure), slow response = block loss; medical outcome curves make response minutes literally lethal or not; air ambulance ignores roads (weather-limited, 1 unit ≈ 10 ground units of marginal coverage in congested eras); hospitals queue non-urgent care as waiting lists (months, visible, funded down); elder care and home-care draw from the same staffing pool as hospitals — "a nurse shortage is one shortage everywhere"; "all response-time distributions appear in F4 and Projections"); code.json `engine.dispatch` entry (inbound `DispatchAPI`, "incident queue + unit assignment; outcome curves from data", consumers `engine.chemicals`/`ui.screen.services`; outbound calls `engine.traffic`, `engine.services`, `engine.world`).
**Date:** 2026-08-11 (BA-S9a, first pass)
**Status:** draft-ahead — `MOD-023` (engine.traffic) and `MOD-033` (engine.services) are both `open`; this item is not in the ready queue until its dependencies land. Content written now, ahead of both.
**Package under test:** `internal/engine/dispatch/` (path from `node claude-bow.js show MOD-040`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/dispatch/...`.

## User stories

- **US-1.** As fire, ambulance, air-ambulance, and police services, I need one shared dispatch engine (per code.json's "incident queue + unit assignment" pattern) rather than four independently-built assignment models, so nearest-unit logic, blue-light routing, and outcome curves are written once and trusted everywhere.
- **US-2.** As `engine.traffic` (a registered outbound dependency, MOD-023), I need blue-light units to actually route through the real congested road network at a documented multiplier over free-flow — not a privileged teleport — so gridlock is a genuine emergency-response risk the player must manage, not a cosmetic-only problem.
- **US-3.** As `engine.services` (a registered outbound dependency, MOD-033), I need elder care and home-care to draw from the exact same staffing pool as hospital care (§26's explicit example of the shared-pool mechanism `engine.services.md` AC-4 builds), so a nurse shortage is mechanically one shortage everywhere, never per-service-siloed.
- **US-4.** As the player reading F4 or a projection pane, I need response-time distributions per incident type queryable in a form those panes can render directly, so "response minutes are literally lethal or not" is a number I can see coming, not a surprise post-mortem.
- **US-5.** As `engine.chemicals` and `ui.screen.services` (the two registered inbound consumers), I need to submit an incident and receive a queryable outcome/status through `DispatchAPI` alone, never a direct reach into unit-assignment internals.
- **US-6.** As `engine.world`, I need fire spread to consume per-cell material/density data through the registered outbound edge, so fire behaviour reflects real built environment, not an abstracted city-wide constant.
- **US-7.** As `engine.invariant`, I need every dispatch unit (fire appliance, ambulance, air-ambulance, police car) accounted for as a conserved stock the moment this module exists, so no unit can be assigned to an incident and never returned to the pool by a silent bug.

## Scope

The unified incident-queue and nearest-available-unit-assignment engine for fire/ambulance/air-ambulance/police; blue-light routing through `engine.traffic` at the documented ~×1.6 congestion-sensitive multiplier; response-time→outcome-quality curves per incident class; per-cell fire spread; air-ambulance's road-independent, weather-limited routing; hospital non-urgent waiting lists; the shared staffing pool linking hospital/elder-care/home-care; unit-fleet conservation accounting as a new invariant-checker stock.

## Acceptance criteria

### Functional — incident queue and unit assignment

- **AC-1 (GR#20; code.json inbound contract).** A `DispatchAPI` exists exposing an incident-submission command and unit-assignment/status queries, matching code.json's documented pattern "incident queue + unit assignment; outcome curves from data". Check: `go doc ./internal/engine/dispatch DispatchAPI` shows an incident-submission command and a status-query surface; `grep -n "func.*SubmitIncident\|func.*ReportIncident" internal/engine/dispatch/*.go` confirms incidents enter via a command, not a direct queue-slice append from another package.
- **AC-2 (§26 unified across four services; US-1).** Fire, ambulance, air-ambulance, and police incidents are all resolved by the same assignment algorithm/entry point (one nearest-available-unit resolver parameterised by unit-type constraints), not four independently-coded per-service dispatch functions duplicating the same logic. Check: `grep -n "func.*[Aa]ssign" internal/engine/dispatch/*.go` shows a single assignment function (or a thin per-type wrapper calling one shared core) rather than four structurally-independent implementations; a passing test submits one incident of each of the four types and asserts each resolves through the same traced call path (`grep -rn "func Test.*[Uu]nifiedDispatch\|func Test.*[Ss]haredAssign" internal/engine/dispatch/*_test.go`). **Lazy implementation this rejects:** four separately-written `assignFireUnit`/`assignAmbulance`/etc. functions that happen to look similar would satisfy "all four services dispatch" on inspection while violating the "one dispatch engine" contract §26 states explicitly and risking exactly the kind of drift GR#3 exists to prevent — the check requires a traceable shared core, not merely superficially-parallel code.
- **AC-3 (§26 nearest-available-unit).** Unit assignment selects the nearest **available** unit by real road-network travel time (not straight-line/Euclidean distance) among units not already committed to another incident, and an incident with no available unit of the required type queues rather than silently failing. Check: `go doc ./internal/engine/dispatch` shows the assignment considers travel time via `engine.traffic`, not raw distance; a passing test places two units of differing road-distance-vs-straight-line-distance from an incident and asserts the road-nearer one is selected even when straight-line-nearer would differ (`grep -rn "func Test.*[Nn]earestUnit\|func Test.*[Rr]oadDistance" internal/engine/dispatch/*_test.go`); a second test exhausts available units and asserts the incident enters a documented queue state rather than an error/drop (`grep -rn "func Test.*[Nn]oUnitAvailable\|func Test.*[Qq]ueueIncident" internal/engine/dispatch/*_test.go`).

### Functional — blue-light routing and response-time→outcome

- **AC-4 (§26 blue-light multiplier, not teleport; GR#20 outbound contract).** A dispatched unit's travel time is computed by calling `engine.traffic`'s registered routing/congestion query and applying a documented blue-light speed multiplier (spec-stated ~×1.6 over free-flow, transcribed not invented) to the *free-flow* baseline — congestion still increases the actual travel time above the blue-light-adjusted free-flow figure, it is never zeroed out. Check: `grep -rn "traffic\.(Route|Congestion|FreeFlow)" internal/engine/dispatch/*.go` (excluding `_test.go`) shows a live call into `engine.traffic`'s registered query, not a locally-duplicated road-graph/travel-time table; a passing test asserts (a) a blue-light unit's travel time on a congestion-free route is materially less than a civilian vehicle's but not zero, and (b) the same unit's travel time on a congested route is measurably longer than on the same route congestion-free — congestion is never fully bypassed (`grep -rn "func Test.*[Bb]lueLight\|func Test.*[Cc]ongestionBites" internal/engine/dispatch/*_test.go`). **Lazy implementation this rejects — the exact failure mode the spec's parenthetical "(congestion still bites... not teleport)" calls out:** a build that computes blue-light travel time from static road length ÷ a flat blue-light speed, ignoring `engine.traffic`'s live congestion state entirely, would satisfy "units travel roads, not instantly" on a shallow read while making gridlock cost-free for emergency response — the second half of the check (congested-route travel time increases) specifically catches this.
- **AC-5 (§26 response-time→outcome quality).** Outcome quality for a resolved incident is a documented, monotonic function of response time (worse outcome as response time increases), sourced from data (GR#15, not a hardcoded curve literal) and distinct per incident class (a fire's block-loss curve is not the same function as a cardiac-arrest survival curve). Check: `go doc ./internal/engine/dispatch OutcomeQuality` (or equivalent) exists; a passing test asserts outcome quality strictly worsens as response time increases for a fixed incident, for at least two distinct incident classes with independently-verified different curve shapes (`grep -rn "func Test.*[Oo]utcome.*[Rr]esponseTime" internal/engine/dispatch/*_test.go`); `grep -nE "[0-9]+\.[0-9]+" internal/engine/dispatch/*.go` (excluding `_test.go`) finds no bare outcome-curve literal — values load from `data/dispatch.json` (or equivalent).
- **AC-6 (§26 fire spread, per-cell).** Fire spread is computed per-cell from that cell's material, density, and the world's wind/weather state (via `engine.world`, a registered outbound dependency), and hydrant pressure at/near the cell modifies containment — a slower response measurably increases the number of cells lost to spread by the time containment is achieved, closing the loop §26 states ("slow response = block loss"). Check: `go doc ./internal/engine/dispatch FireSpread` (or equivalent) shows material/density/wind/hydrant-pressure inputs sourced from `engine.world`; a passing test holds material/density/wind fixed and varies only response delay, asserting cells-lost increases with delay (`grep -rn "func Test.*[Ff]ireSpread\|func Test.*[Bb]lockLoss" internal/engine/dispatch/*_test.go`).
- **AC-7 (§26 air ambulance).** Air-ambulance routing ignores road-network travel time entirely (a distinct code path from AC-4's ground routing, not the same function with a multiplier override), is limited by a weather state (a documented weather condition disables/degrades air dispatch), and its marginal coverage value is queryable as a documented multiple (spec: "≈10 ground units") of a single ground unit's marginal coverage in a congested area specifically — the spec's comparison is congestion-conditional, not a flat constant. Check: `go doc ./internal/engine/dispatch AirAmbulance` (or equivalent) shows a road-independent travel-time computation and a weather-gate check; a passing test asserts (a) air-ambulance travel time is unaffected by a congestion state that measurably slows a ground unit on the same route, and (b) a documented adverse-weather state disables/degrades air dispatch (`grep -rn "func Test.*[Aa]irAmbulance" internal/engine/dispatch/*_test.go`). **Lazy implementation this rejects:** a "ground unit with a speed multiplier" implementation of air-ambulance would satisfy "it's faster" on a shallow read while still being blocked by road-network congestion under the hood (since it reuses the ground pathfinder) — the check requires demonstrating congestion-immunity specifically, which a multiplier-only implementation cannot pass.
- **AC-8 (§26 hospital waiting lists).** Non-urgent hospital care is modelled as a waiting-list queue (months-scale, per §26's "JIT-for-people" framing), queryable and visibly lengthening as hospital funding/capacity (via `engine.services`) drops, distinct from the urgent-incident dispatch path AC-2/AC-3 cover. Check: `go doc ./internal/engine/dispatch WaitingList` (or equivalent) exists distinct from the incident-queue type; a passing test asserts reducing hospital funding (via `engine.services`) lengthens the non-urgent waiting list's queryable wait-time figure (`grep -rn "func Test.*[Ww]aitingList" internal/engine/dispatch/*_test.go`).
- **AC-9 (§26 shared staffing pool; US-3; GR#20 outbound contract).** Elder care and home-care draw from the identical staffing-pool instance (`engine.services`' `StaffingPool`, per `engine.services.md` AC-4) hospital care draws from — not a same-named-but-separate pool per service. Check: `grep -rn "services\.StaffingPool" internal/engine/dispatch/*.go` (excluding `_test.go`) shows dispatch-owned care services referencing the same pool identifier `engine.services` exposes for hospitals, never a dispatch-local staffing count; a passing test reduces the shared nursing pool and asserts both hospital response outcome quality and elder/home-care service quality degrade together, in the same tick (`grep -rn "func Test.*[Ss]haredNursing\|func Test.*[Nn]urseShortage" internal/engine/dispatch/*_test.go`). This mirrors `engine.services.md` AC-4's own isolation-style check; the failure mode this rejects is a dispatch module that reads a *value* from the shared pool once at startup and then tracks its own independent counter, silently drifting from the real shared state.

### Functional — response-time distributions surfaced to F4/Projections

- **AC-10 (§26 "all response-time distributions appear in F4 and Projections" — RE-ARMED 2026-08-11, BUG-100: the `engine.dispatch`→`engine.projections` edge landed in c36778b).** Per-incident-class response-time distributions (not just point averages) are exposed on `DispatchAPI` in a form suitable for registration as an `engine.projections` curve provider, per that module's documented registration pattern (`engine.projections.md` AC-1), AND that registration is actually made — the edge blocking this is now registered (`node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.dispatch'); process.exit(m.outbound.calls.some(c=>c.key==='engine.projections')?0:1)"` exits 0), so the deferred half of this AC is no longer legally deferrable. Check: `go doc ./internal/engine/dispatch` shows a distribution-query accessor (e.g. histogram or percentile set) per incident class; a passing test asserts the distribution updates as incidents resolve across a run (`grep -rn "func Test.*[Dd]istribution" internal/engine/dispatch/*_test.go`); `grep -n "projections\.Register\|projections\.RegisterCurveProvider" internal/engine/dispatch/*.go` (excluding `_test.go`) shows the real registration call at boot — a build with the distribution accessor but no registration call FAILS this AC, it does not pass as "interim"; `internal/engine/dispatch/doc.go` no longer cites BUG-058 as a live block for this AC (a stale citation is itself a defect once the edge is wired).

### Functional — conservation identity (the appliance/crew fleet stock)

- **AC-11 (fleet conservation — the strongest available check).** For every unit type (fire appliance, ambulance, air-ambulance, police car), the following identity holds exactly at every tick: `TotalUnits == UnitsAvailable + UnitsEnRoute + UnitsOnScene + UnitsOutOfService(maintenance/refuelling)`. Each right-hand term is independently sourced (available from the unit pool's free-list, en-route/on-scene from active incident assignments, out-of-service from a documented maintenance scheduler) — no term is computed as the identity's remainder. An assignment moves a unit between exactly two of these buckets in one atomic transition; nothing else changes `TotalUnits`. Check: a passing test constructs a fleet, drives it through a mix of assignments, completions, and maintenance cycles across several ticks, independently sums all four terms from their own sources each tick, and asserts the sum equals the fleet's fixed `TotalUnits` at every tick (`grep -rn "func Test.*[Ff]leetConserv\|func Test.*[Uu]nitConservation" internal/engine/dispatch/*_test.go`). **Lazy implementation this rejects:** deriving `UnitsAvailable` as `TotalUnits − (en-route + on-scene + out-of-service)` rather than from the pool's own free-list would make the identity tautologically true and hide a bug where a unit is assigned twice (double-booked) or never returned to the pool after an incident resolves — exactly the "a unit vanishes into an incident and never reappears" bug class this AC exists to catch. A second, explicit assertion is required: a test that resolves an incident and asserts the assigned unit's ID reappears in `UnitsAvailable`'s own free-list, not merely that the aggregate count is right (an aggregate-only check could pass even if the *wrong* unit ID reappeared).
- **AC-12 (US-7; registration with `engine.invariant` — STILL BLOCKED after c36778b; BUG-100 tripwire applied).** The fleet-conservation identity (AC-11) is registered as a conserved stock with `engine.invariant`'s registration seam. **Blocked pending BUG-058:** code.json still shows no `engine.dispatch`→`engine.invariant` outbound edge as of c36778b (that commit registered `engine.dispatch`→`engine.projections`, not this edge), and `engine.invariant`'s inbound contract remains entirely unpopulated. AC-11's local test suite is the interim proof of correctness. **Tripwire (mechanical, not a prose label — BUG-100):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.dispatch'); process.exit(m.outbound.calls.some(c=>c.key==='engine.invariant')?1:0)"` must exit **0** (edge still absent). A nonzero exit means the edge has been registered and this AC is stale, unarmed prose that MUST be rewritten to the real check (mirroring AC-10's re-arm above) before the next commit touching `internal/engine/dispatch/`; Tester/CI treat a nonzero exit here as a hard FAIL of this AC, not a silent pass. Until the tripwire fires: once unblocked, `grep -n "invariant\.Register" internal/engine/dispatch/*.go` shows registration at boot; until then, `doc.go` states the block, citing BUG-058.

### Error handling

- **AC-13 (GR#7).** Submitting an incident at an unregistered/off-map cell, or querying assignment status for an unregistered incident ID, returns a registry-sourced error (new `MET-E`-range code, claimed at build time — no `engine.dispatch` sub-range exists yet), never a silently-created zero-value incident. Check: `grep -n "MET-" internal/engine/dispatch/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownCell\|func Test.*[Uu]nknownIncident" internal/engine/dispatch/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches the claimed `MET-E` code AND that no incident/assignment record was created as a side effect, not merely that a matching-named test function exists and returns without panicking.
- **AC-14.** An incident submitted requesting an unrecognised unit type, or a maintenance command targeting a unit already assigned to an active incident, is rejected with a typed error, never silently reassigned or silently dropped. Check: passing test coverage (`grep -rn "func Test.*[Ii]nvalidUnitType\|func Test.*[Dd]oubleAssign" internal/engine/dispatch/*_test.go`).

### Determinism, safety & scale

- **AC-15 (GR#21).** Assignment, routing-time computation, and outcome resolution are deterministic functions of `(worldSeed, tick, prior state, commands)` — byte-identical assignment decisions and outcome results across repeated runs and worker counts, including tie-breaking when two units are equidistant (a documented, deterministic tie-break rule, never map-iteration order). Check: `grep -n "for .* := range" internal/engine/dispatch/*.go` on any map feeding assignment order is sorted/deterministic (`grep -n "sort\." internal/engine/dispatch/*.go`); a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/dispatch/*_test.go`).
- **AC-16 (SG-7; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/dispatch/*.go` (excluding `_test.go`) returns no matches.
- **AC-17.** `go test ./internal/engine/dispatch/... -race -count=1` passes; `grep -n "go func()" internal/engine/dispatch/*_test.go` finds at least one concurrency test (concurrent incident submission across multiple sources within a tick).

## Out of scope

- `engine.traffic`'s own routing/congestion computation — this item only *consumes* it for blue-light travel-time (AC-4); it does not build a second road graph.
- `engine.services`' own staffing-pool/funding→quality mechanics — this item only draws from the registered shared pool (AC-9); the pool's allocation-under-shortage rules belong to `engine.services`.
- `engine.world`'s own per-cell material/density/wind data — this item only consumes it for fire spread (AC-6).
- `engine.chemicals`'s own hazmat-incident generation logic — that module is a registered *consumer* of `DispatchAPI`, not built here.
- The real wiring of response-time distributions into `engine.projections` and `ui.screen.services`'s rendering of them — deferred until BUG-058's edge lands (AC-10) and until `ui.screen.services`'s own item builds the render.
- Specific outcome-curve shapes, the exact ×1.6 blue-light figure's per-road-class variation, and hydrant-pressure/wind coefficients — balance data pending M2 tuning (see Escalations); the ×1.6 baseline itself is spec-transcribed (§26), not invented.
