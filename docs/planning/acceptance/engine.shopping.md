# Acceptance criteria — engine.shopping (MOD-050)

**BOW code:** MOD-050
**Spec refs:** §37 Shopping & Grocery Access (`docs/METROPOLIS-MASTER-v2.1.md` lines 548-550, in full: households generate shopping trips — real travel demand, cars/walks/bus — with frequency and destination by format access: corner shop (walkable, dear, thin range) · market hall (fresh++, §31 local link) · supermarket (car-borne, cheap, freight anchor) · retail park (car-only) · online delivery (§35 share: no trip, van instead); each home cell gets a grocery access score (time × price × freshness); poor scores = food deserts → diet quality ↓ → physical health (§18), a poverty-geography mechanic emerging naturally in blighted districts when the last supermarket leaves; shopping trips load the network — Saturday peak differs from commute peak — and grocery price level feeds cost-of-living → real wages → attractiveness); §48 Destination Leisure & Retail (line 648, the Bluewater mega-mall's "colossal parking §38... hoovers regional retail spend in... pressuring your own high streets §35/§41 tension at maximum scale" — the town-centre-vs-mall dynamic this module's format-access model must remain consistent with); code.json `engine.shopping` entry (inbound `ShoppingAPI`, pattern "trip generation into TrafficAPI; access scores as overlay", consumers: none registered; outbound calls: `engine.traffic`, `engine.market`, `engine.wellbeing`).
**Date:** 2026-08-11 (BA-S10a, first pass)
**Status:** draft-ahead — `MOD-020` (engine.market) and `MOD-023` (engine.traffic) are both `open`; this item is not in the ready queue until both land. Content written now, ahead of both.
**Package under test:** `internal/engine/shopping/` (path from `node claude-bow.js show MOD-050`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/shopping/...`.

## User stories

- **US-1.** As a household, I need my shopping-trip frequency and destination format to be determined by which formats are actually accessible to me (walk-time to corner shop, drive-time to retail park, whether online delivery is available per §35), so trip generation reflects real access geography, not a city-wide average.
- **US-2.** As `engine.traffic` (the registered outbound edge, code.json's own "trip generation into TrafficAPI" pattern), I need shopping trips to load the network as real trips with a Saturday-peak profile distinct from the commute peak, so retail traffic is a genuine, separately-timed load on the road graph.
- **US-3.** As a home cell in a district where the last supermarket has closed, I need my grocery access score to fall as a direct, computed consequence (not a scripted "blight event"), so food deserts emerge from the same access-score mechanic that produces a good score anywhere else — an emergent consequence, not a special case.
- **US-4.** As `engine.wellbeing` (the registered outbound edge), I need a diet-quality signal derived from the grocery access score to reach the physical-health driver through the registered `WellbeingAPI`, so a food desert's health consequence is a live query, not a duplicated health number (per `engine.wellbeing.md`'s own AC-12 escalation, which names this exact edge as needed from wellbeing's side).
- **US-5.** As `engine.market` (the registered outbound edge, MOD-020), I need grocery price level sourced through `MarketAPI`'s commodity prices (food-staples/food-fresh), so cost-of-living pressure traces back to the same prices every other consumer sees, not a shopping-owned duplicate price table.
- **US-6.** As the player reading the cost-of-living → real wages → attractiveness chain, I need grocery price level to be a queryable output a downstream attractiveness consumer can subscribe to, so that chain is a real code path once the edge exists.

## Scope

Household shopping-trip generation (frequency + destination format, Saturday-vs-commute peak profile) into `TrafficAPI`; the five documented format-access channels (corner shop, market hall, supermarket, retail park, online delivery); the per-home-cell grocery access score (time × price × freshness); the food-desert consequence chain into `WellbeingAPI`; the grocery price level output feeding cost-of-living. No trip assignment/routing itself (`engine.traffic`'s job, only consumed here), no commodity pricing (`engine.market`'s job, only consumed here), no physical-health driver decomposition (`engine.wellbeing`'s job, only fed here), no household typology/demand-generation mechanics beyond consuming a household's location and format-access inputs (blocked pending BUG-058, see Escalations).

## Acceptance criteria

### Functional — trip generation by format access

- **AC-1 (GR#20; code.json inbound contract).** A `ShoppingAPI` exists exposing per-home-cell access-score queries and trip-generation triggers, matching code.json's documented pattern "trip generation into TrafficAPI; access scores as overlay". Check: `go doc ./internal/engine/shopping ShoppingAPI` shows an access-score query surface and a trip-generation surface feeding `engine.traffic`.
- **AC-2 (§37 five format channels).** Every home cell's shopping demand is split across the five documented formats — corner shop, market hall, supermarket, retail park, online delivery — each with a distinct, documented access characteristic (walkability, price tier, range/freshness, car-dependency), not one undifferentiated "grocery trip" split by a fixed ratio. Check: `go doc ./internal/engine/shopping FormatChannel` (or equivalent enum) lists all five; a passing test asserts a home cell with a nearby corner shop but no retail park access generates trips weighted toward corner-shop format, while an otherwise-identical cell with retail-park access but no corner shop weights the other way (`grep -rn "func Test.*[Ff]ormatAccess\|func Test.*[Cc]hannelSplit" internal/engine/shopping/*_test.go`). **Lazy implementation this rejects:** a single "grocery trips" number allocated to formats by a city-wide fixed percentage (e.g. "40% supermarket, 20% corner shop, always") would satisfy "five formats exist" on a shallow read but produce IDENTICAL format splits regardless of which formats are actually near a given home cell — the check requires the split to respond to per-cell access, not a global constant.
- **AC-3 (§37 online delivery — no trip, van instead).** The online-delivery format generates ZERO trips into `TrafficAPI` from the household side (per §35's "no trip, van instead" framing) — its demand instead reduces the OTHER four formats' trip counts proportionally to the e-commerce share it displaces, with the delivery van traffic itself being a DIFFERENT module's logistics movement (out of scope here, per Escalations), not a shopping-generated trip. Check: a passing test raises online-delivery's share and asserts total household-generated shopping trips into `TrafficAPI` fall (not rise, and not stay flat with a phantom "delivery trip" added) (`grep -rn "func Test.*[Oo]nlineDelivery.*[Nn]oTrip\|func Test.*[Dd]eliveryDisplace" internal/engine/shopping/*_test.go`). **Blocked pending BUG-058 (see Escalations):** the online-delivery share input itself is meant to come from `engine.comms`'s e-commerce-share coefficient (`engine.comms.md` AC-6), but no `engine.shopping`↔`engine.comms` edge is registered — this AC requires only that the trip-displacement MECHANISM be correct given a share value; the share's real source is blocked until the edge lands, and the interim source must be an explicitly marked placeholder (`grep -n "TODO\|STUB\|PLACEHOLDER" internal/engine/shopping/*.go` referencing online-delivery share).
- **AC-4 (§37 Saturday peak distinct from commute peak).** Shopping-trip generation carries its own weekly time-of-day/day-of-week profile, with a Saturday peak that is measurably distinct from (not a scaled copy of) the commute peak's Monday-Friday morning/evening profile. Check: `go doc ./internal/engine/shopping` shows a documented weekly trip-profile accessor; a passing test asserts the Saturday trip-volume-by-hour curve's peak hour differs from the commute peak's morning-rush hour, and that scaling the commute profile by a constant does NOT reproduce the Saturday shopping profile (`grep -rn "func Test.*[Ss]aturdayPeak\|func Test.*[Ww]eeklyProfile" internal/engine/shopping/*_test.go`).

### Functional — grocery access score and food deserts

- **AC-5 (§37 access score is a genuine product of three independent factors).** The per-home-cell grocery access score is computed as time × price × freshness, and each factor is independently movable: holding price and freshness fixed while varying only travel time changes the score, holding time and freshness fixed while varying only price changes the score, and holding time and price fixed while varying only freshness changes the score — proving all three are load-bearing, not one dominant term with the other two as decoration. Check: `go doc ./internal/engine/shopping GroceryAccessScore` (or equivalent) documents the three-factor formula; a passing test perturbs each factor independently (three separate sub-tests) and asserts the score moves in each case (`grep -rn "func Test.*[Aa]ccessScore.*[Ii]solat\|func Test.*[Tt]hreeFactor" internal/engine/shopping/*_test.go`). This mirrors `engine.wellbeing.md` AC-3's isolation pattern applied to a three-factor product instead of an additive attribution — the same defence against a build that computes one blended "access" number and dresses it up as three named factors that don't actually move independently.
- **AC-6 (§37 food deserts emerge, not scripted).** A home cell's access score falls, through the SAME AC-5 formula, when its nearest supermarket/retail-park option closes (travel time to the nearest remaining option rises) — there is no separate "food desert" flag/event type computed by different code; the food-desert state is simply a documented low-access-score threshold read off the ordinary access-score accessor. Check: `grep -n "FoodDesert" internal/engine/shopping/*.go` (excluding `_test.go`), if present, resolves to a threshold READ on `GroceryAccessScore`'s own output, not an independently-computed boolean; a passing test closes a cell's nearest supermarket, recomputes access score through AC-5's ordinary path, and asserts the score falls below the documented food-desert threshold with no separate "trigger blight" code path involved (`grep -rn "func Test.*[Ff]oodDesert" internal/engine/shopping/*_test.go`). **Lazy implementation this rejects:** a hardcoded "if district.Blighted { access = FoodDesertConstant }" branch would satisfy "food deserts exist and are low-access" on a shallow read while being a scripted special case rather than an emergent consequence of the real access formula — the check requires the low score to be REACHED via AC-5's factors (specifically travel time rising), not assigned by a blight-status lookup.
- **AC-7 (§18/§37 diet-quality → physical health via `WellbeingAPI` — US-4).** The grocery access score's freshness/price-derived diet-quality signal is routed to `engine.wellbeing`'s physical-health driver through the registered outbound `WellbeingAPI` call, never a shopping-owned duplicate health number. Check: `grep -rn "wellbeing\.\(Diet\|PhysicalDriver\)" internal/engine/shopping/*.go` (excluding `_test.go`) shows a real call into `engine.wellbeing`'s package; a passing test drives a cell's access score into food-desert range and asserts the call into `WellbeingAPI` carries a correspondingly-lowered diet-quality value (`grep -rn "func Test.*[Dd]ietSignal\|func Test.*[Ww]ellbeingCall" internal/engine/shopping/*_test.go`). **Lazy implementation this rejects:** computing an internal "health penalty" number and never actually calling into `WellbeingAPI` would satisfy "food deserts affect health" on a design-doc read while duplicating a system `engine.wellbeing` already owns (GR#3) — the check requires the call to cross the registered interface, exactly as `engine.refuse.md` AC-7 requires for its own overflow-health chain.
- **AC-8 (§37 grocery price level via `MarketAPI` — US-5).** Grocery price level (feeding cost-of-living) is sourced from `MarketAPI.Price` for food-staples and food-fresh commodities (the registered outbound edge), weighted by which formats a district actually has access to (a corner-shop-only district's effective price level is higher than a supermarket-served district's, per §37's "corner shop... dear" framing), never a shopping-owned hardcoded price. Check: `grep -rn "market\.Price" internal/engine/shopping/*.go` (excluding `_test.go`) shows a real call; a passing test asserts a corner-shop-only district's effective grocery price level exceeds a supermarket-served district's for the same underlying `MarketAPI` commodity price (`grep -rn "func Test.*[Pp]riceLevel\|func Test.*[Ff]ormatPriceWeight" internal/engine/shopping/*_test.go`).

### Error handling

- **AC-9 (GR#7).** Querying access score for a home cell with no registered format-access data, or a negative/out-of-domain travel-time or price input, returns a registry-sourced error (new `MET-E`-range code, claimed against `data/errors.json`'s reserved table at build time — no `engine.shopping` sub-range exists yet) rather than a silently-computed zero-value score. Check: `grep -n "MET-" internal/engine/shopping/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredCell\|func Test.*[Ii]nvalidAccessInput" internal/engine/shopping/*_test.go`).
- **AC-10.** An online-delivery share input above 100% or below 0% is rejected with a typed error, never silently clamped. Check: passing test coverage (`grep -rn "func Test.*[Oo]utOfRangeShare" internal/engine/shopping/*_test.go`).

### Determinism, safety & scale

- **AC-11 (GR#21).** Trip generation, access-score computation, and the diet-quality signal are deterministic functions of `(worldSeed, tick, prior state, commands)` — repeated runs from identical starting state and command sequence produce byte-identical access scores and trip counts, across worker counts. Check: `grep -rn "func Test.*[Dd]etermnis\|func Test.*[Dd]eterminis" internal/engine/shopping/*_test.go`.
- **AC-12 (SG-7; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/shopping/*.go` (excluding `_test.go`) returns no matches.
- **AC-13.** `go test ./internal/engine/shopping/... -race -count=1` passes; `grep -n "go func()" internal/engine/shopping/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-14.** `internal/engine/shopping/doc.go` states the module key `engine.shopping`, cites §37 and §48, states the three-independent-factor access-score contract (AC-5) in prose, states the food-desert-is-emergent-not-scripted contract (AC-6), and states the two outstanding BUG-058 gaps (household/citizen demand-source edge and the `engine.comms` online-delivery-share edge) explicitly so a future reader does not assume either wiring already happened. Check: `grep -n "engine.shopping" internal/engine/shopping/doc.go` and `grep -n "§37\|section 37" internal/engine/shopping/doc.go` both match; `grep -n "BUG-058" internal/engine/shopping/doc.go` matches.

## Out of scope

- `engine.traffic`'s own trip-assignment/routing mechanics — this item only generates trips into it (AC-1/AC-4).
- `engine.market`'s own commodity pricing — this item only queries it (AC-8).
- `engine.wellbeing`'s own physical-health driver decomposition — this item only supplies the diet-quality input via the registered interface (AC-7).
- `engine.comms`'s own e-commerce-share computation — this item only consumes a share value (AC-3), currently as a marked placeholder pending BUG-058.
- The delivery van traffic itself (a logistics movement belonging to whichever module owns last-mile delivery — `engine.comms`/`engine.logistics`, per `engine.comms.md` AC-8) — this item's AC-3 only requires that the household side generates zero trips for delivery-served demand.
- The specific format-access weightings, the access-score's exact time/price/freshness functional form, and the food-desert threshold value — balance data pending M2 tuning (see Escalations).

## Escalations

- **For Ben — BUG-058 addendum (new findings, this wave).** Reading §37 against code.json's registered edges for `engine.shopping` surfaced a significant gap: `engine.shopping`'s outbound calls are `engine.traffic`, `engine.market`, `engine.wellbeing` ONLY — there is no registered edge to any household/citizen/consumption-source module (`engine.households`, `engine.citizens`, or `engine.consumption`) at all. §37's own opening sentence is "Households generate shopping trips" — the demand-generating actor (a household, located at a home cell, with income/composition affecting format choice) is not reachable from this module's registered outbound list under GR#20. This is a more foundational gap than the two-way edges other modules in this wave are missing: without SOME registered path to household/citizen location and income data, `engine.shopping` cannot legally source "whose trip is this" at all, only aggregate trip counts — which would itself replicate the aggregate-vs-individual concern the brief raises for `engine.firms`, applied here to shopping demand. Recommend `engine.shopping`↔`engine.households` as the most likely intended edge (households own home-cell location and typology/income per §21), with `engine.consumption` (MOD-021, needs & commodities coefficients) as the secondary candidate for the raw demand-quantity input. Also confirming, from this module's own side, the `engine.shopping`↔`engine.comms` gap `engine.comms.md` (this same BA wave) already flags from its side — needed for AC-3's online-delivery-share input. Both written into AC-3's blocked-pending-fix language rather than assumed. Adding to the existing BUG-058 comment thread; not editing code.json or master-plan-v2.1.json myself.
- **For Aaron (balance numbers).** The exact time/price/freshness weighting in the access-score formula, the per-format base-price multipliers (corner shop "dear" vs supermarket "cheap", exact ratio unstated), and the food-desert threshold are none of them spec-given numbers — §37 describes the mechanism and direction but no figures. ACs above check shape/independence/direction only (per GR#15); the actual figures are `data/shopping.json` (or equivalent) balance data pending M2 tuning.
- **For Ben (dependency risk, and the foundational gap above).** This item depends on `MOD-020` (market) and `MOD-023` (traffic), both open, and — per the escalation above — has NO currently-registered path to household/citizen demand data at all. Recommend this be resolved (which module supplies the demand-source edge) before dispatch, since AC-2/AC-5/AC-6's entire "per-home-cell" framing assumes SOME real per-cell household reference exists to key off of; building against an interface stub is not enough here because the stub itself doesn't exist yet in the registry.
