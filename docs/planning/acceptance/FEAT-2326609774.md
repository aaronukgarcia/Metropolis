## 1. Why this item exists

Aaron's words: *"we need per building utilisation for everything, not just city wide — we need to know which building is being used to 100 percent and which is not."*

`utilisationOf()` (`data.ts:990-1098`) is the only per-building utilisation signal the game has, and its own doc comment (`data.ts:969-976`) admits the defect: every building of a kind is stamped with the SAME citywide ratio — every residential block shows the same `"citywide occupancy"`, every power plant the same `"citywide MW draw"`, every commercial/office/industrial/mine building the same `"citywide workers vs jobs"`. There is no such thing today as "this specific block is full while that one is empty." The basis string says so on purpose (`"citywide occupancy"`, not `"occupancy vs capacity"`) — this is GR#15 honesty about a placeholder, not a bug in the arithmetic.

This is also load-bearing for two things already shipped or in flight:
- **The consolidator** (FEAT-2326609761) needs to find *which specific buildings* are underused to justify demolish/rebuild, and Aaron's own live-city ruling on that item ("stranded capacity… 20,000 not on road network") is a per-building fact that `utilisationOf()` cannot currently answer.
- **BUG-606/641/649** (all closed 2026-09-02/03) fixed the SAME class of dishonesty one level up — sized demand messages that must never claim a number the data doesn't support, and must name their unit. The same discipline binds here: a per-building number must never be fabricated when no per-building signal exists.

## 2. The design in one paragraph

Replace citywide-ratio-stamped-on-every-building with a **deterministic assignment ledger**: every resident is assigned to exactly one dwelling, every filled job to exactly one job-building, every served citizen (school/health/police/fire/water) to exactly one service building, up to that building's own `capacityAtTier`. The ledger is an **incremental, event-driven** structure — assignment changes only for the citizens/jobs that actually moved this tick (a birth, a death, a move-in, a move-out, an `isOnline` flip, a tier-up) — never a full recompute, because a full recompute is exactly the O(buildings) walk BUG-642/643 just killed. `utilisationOf()` gains one new basis per migrated kind (`"true occupancy"`, `"true jobs filled"`, `"true students enrolled"`, …) that reads the ledger instead of the citywide ratio; kinds not yet migrated keep their honest `"citywide *"` basis unchanged (GR#15 — no regression to a worse lie while a kind is mid-migration).

## 3. The assignment rule (the ask, part **a**)

### AC-1 — the rule is FILL-ORDER, not proximity

**Recommendation: deterministic placement-order fill**, not proximity-weighted matching. Rationale:

- Proximity-weighted assignment (nearest dwelling to nearest job, say) requires a distance computation between every unassigned citizen and every candidate building — an O(citizens × buildings) matching problem, or at best an O(n log n) spatial join per tick. At 49k buildings / ~3.2M population (BUG-659's cited scale) that is not a tick-budget-compatible operation, and Aaron's stated direction is a 100M-population city (FEAT-2326609764 §1) where the citizen count dwarfs the building count by ~60×.
- Fill-order needs no spatial computation at all: each building-kind pool (dwellings, job-slots-by-sector, school places, …) is walked in one fixed, stable order — **building id ascending** (ids are assigned once at placement and never reused, so this order is stable for the life of the city and requires no re-sort) — and citizens/slots are handed out first-building-with-a-free-slot-first.
- It is **order-independent by construction** (GR#21): "first building with a free slot, walked in id order" is a pure function of (building set, capacities, occupant count) — it does not depend on iteration order of any *other* collection (citizens, ticks), only on the one canonical id-sorted walk over buildings, which is itself deterministic.
- It is honest about what it models: Metropolis does not simulate commute choice or housing preference (that is out of scope — GR#25 declines to invent a preference model this item does not need). Fill-order is the correct level of fidelity: it answers "which specific building is full" without pretending to answer "why did this citizen pick this building."

A test asserts: given a fixed building set and a fixed target occupant count, two runs of the assignment function (built with `s.buildings` shuffled into a different `Array` order beforehand) produce byte-identical per-building occupancy — proving the id-sort, not incoming array order, governs the result.

### AC-2 — one ledger per assignable kind, keyed on building id

```ts
export interface OccupancyLedger {
  /** buildingId -> occupants currently assigned to it (residents / filled jobs / served pop). */
  byBuilding: Record<number, number>;
  /** Citizens/slots waiting for a building with spare capacity (never negative). */
  unassigned: number;
}
```

One ledger per assignable family: `residentialOccupancy`, `jobOccupancyBySector` (commercial/office/industrial/mine each independent, matching `totalJobsBySector`/`filledJobsBySector`'s existing sector split — `data.ts` per FEAT-1972079902-era sector work), `schoolOccupancy`, `healthOccupancy`, `policeOccupancy`, `fireOccupancy`, `waterOccupancy`. Power is **excluded from assignment** (AC-9) — see the honesty note there.

### AC-3 — capacity per building comes from the EXISTING per-building capacity model, never a new one

`capacityAtTier(sp, b.capacityTier ?? 0)` already exists per building (`data.ts:2062`'s doc comment, backing `residentialConstructionSummary`/`residentsCapacity`) for residential; the equivalent per-building capacity fields already exist on `Spec` for jobs (`sp.jobs`), school (`sp.children`), and served-population service kinds (`sp.served`, adjusted for water by `plantEffServed`'s pipe-tier multiplier, `data.ts:817-819`). This item does **not** invent a new capacity number for any building — it only decides, for city-wide-aggregate-sized occupant pools that already sum these same per-building capacities, WHICH building each occupant lands in.

### AC-4 — an offline building is excluded from the pool entirely, not just from the sum

Mirrors `isOnline(s, b)`'s existing gate (`data.ts:518-521`, used identically by `waterCaps`, `serviceCapacityAggregates`, `powerStats`): a building under construction, road-disconnected, or otherwise offline contributes **zero** slots to its kind's fill-order walk. Its existing occupants (if it just went offline — see AC-7) are evicted into `unassigned`, not left "occupying a building with 0 capacity."

## 4. Interaction with the auto-scale ladder — AC-5

When a building tiers up (`capacityAtTier` increases), its ledger entry's capacity increases but its **current occupant count is untouched** — existing occupants keep their assignment (nobody is displaced by their own building growing). The newly opened slots are simply available capacity the NEXT fill-order pass will consume from `unassigned` first, because id-order fill always prefers the lowest-id building with spare room — a building that just tiered up becomes, from that tick, one of the first candidates any pending `unassigned` citizen fills into. **No rebalancing pass is needed or run**: existing occupants never move buildings once assigned (GR#21 stability — a citizen's assigned building does not change on a tick where they, personally, did nothing).

## 5. Interaction with per-tick population/employment churn — AC-6

Each tick, the reducer already knows the **net delta** of citizens needing a dwelling (births, deaths, migration in/out) and workers needing a job slot (hires, layoffs) — these are the same deltas `residentsCapacity`/`totalJobs` consume today to produce the citywide ratio. This item processes exactly those deltas against the ledger:
- A **gain** (birth, move-in, hire) attempts one fill-order lookup starting from the lowest id with known spare capacity; on success, increments that building's `byBuilding` entry and decrements available capacity; on failure (no building anywhere has room — a real citywide shortfall), the citizen/job-fill goes to `unassigned`, which is exactly what a shortfall already means in `serviceCoverageOf`/`totalJobs` today (GR#3 — no new shortfall concept).
- A **loss** (death, move-out, layoff) decrements the specific building the citizen/job was assigned to (looked up by citizen id → building id, a field added to the citizen record or a reverse index — see AC-8) and frees one slot.

**Cost budget at 49,174 buildings (BUG-659's cited live scale):** this is **O(events this tick)**, not O(buildings) — a tick with 40 net population change costs 40 lookups, regardless of whether the city has 30k or 1.5M buildings, matching the O(changed) discipline FEAT-2326609764 establishes for every other per-tick derivation. The one O(buildings) cost this item pays is a **one-time cold build** of the initial ledger from a loaded/legacy save (walk all buildings once, in id order, greedily filling from the existing city-wide occupant count) — identical in shape to `sectorIndexOf`'s "one memoOnState walk, occupied sectors only" cold-build (FEAT-2326609764 inc1) and to `onlineByBuilding`'s existing per-state walk (`data.ts:512-516`). This item explicitly rides on FEAT-2326609764's dirty-tracking side-band once that lands (§8) rather than re-deriving its own O(changed) plumbing — but does **not block** on it: inc1 (§7) ships with its own minimal per-tick delta processing, independent of the sector work.

**"Where does a fill-order lookup find the lowest-id building with room in O(1)-ish time, not O(buildings)?"** — recommend a small per-kind **min-heap (or sorted free-list) of `{buildingId, spareCapacity}`**, maintained incrementally: a building enters the free-list when it gains spare capacity (placed, tiered-up, occupant left) and leaves when it fills. This is the standard "first-fit with a free list" structure and keeps every operation (fill, free, tier-up) at O(log occupied-sectors-with-room) rather than O(buildings). This structure is itself the concrete implementation of AC-1's "walked in a fixed order" requirement — the heap enforces lowest-id-first without a fresh sort per event.

## 6. Interaction with `isOnline` flips — AC-7

When a building's `isOnline` flips **false** (construction interrupted — cannot happen post-completion; road disconnected; mid-tier demolition), every occupant currently in its `byBuilding` entry moves to `unassigned` in the SAME tick the flip is detected (the reducer already recomputes `isOnline` every tick via `onlineByBuilding`, `data.ts:512-521` — this item hooks the same recompute, does not add a second one). Those citizens are **not silently deleted and not silently kept "housed" in a building the game says is offline** — this is the honesty rule BUG-606/641/649 established for demand messaging, applied here to occupancy: a citizen in an offline dwelling would be exactly the kind of fabricated-looking number Aaron flagged those bugs over. When the building comes back online (road reconnected), its freed slots re-enter the free-list and the next fill-order pass (driven by the SAME per-tick unassigned-processing loop as AC-6, no special-cased "reconnection sweep") re-houses from `unassigned` — first-come-first-served, oldest `unassigned` entries first (FIFO), matching the existing `DeathQueue`/handoff FIFO idiom already in the Go engine (FEAT-087, cited for pattern precedent only — no cross-language dependency is created, GR#25).

## 7. Save/replay byte-identity — AC-8

The ledger (`byBuilding` maps + `unassigned` counts, one set per assignable kind) is **journalled `SimState`**, not a derived/memoised value (contrast with `waterCaps`/`stationLinks`, which ARE pure re-derivable memoisations) — because assignment carries information (WHICH building a specific occupant landed in) that is not recoverable by re-running a pure function of the current building set; it depends on **history** (the order events happened in). This mirrors FEAT-2326609761's ASM-1504 ruling that consolidator settings are journalled sim state, never localStorage, "because they change the simulation and replay determinism depends on it" — the same reasoning applies here a fortiori, since the ledger literally IS simulation state, not a setting.

- **Old-save default:** a save with no ledger field cold-builds one on load (§5's one-time walk), deterministically, from the save's own building set and city-wide occupant totals — so loading an old save never fabricates a "wrong" assignment, it derives the SAME assignment a fresh cold-build always would from that exact building set (GR#16 type-safe storage boundary: sanitise a corrupted/partial ledger back to a cold rebuild, never trust stored counts blindly — mirrors `sanitizeCongestionTicksBySpec`'s pattern, `data.ts:2464-2473`).
- **Reverse index** (citizen/job → assigned building id) needed for AC-6's loss path is likewise journalled state, sized O(population) — this is new memory the game does not currently spend, and is the item's one real cost line (see §9 open question on memory budget, which must be read against FEAT-2326609764's own memory ceiling analysis for 100M citizens).
- A genesis-replay determinism test (the standing house pattern) proves: replaying the same event stream from genesis produces a byte-identical ledger to a freshly-built one — this is the item's primary Destructive-round target, because a ledger that drifts from a straight recompute is a worse defect than the citywide-ratio placeholder it replaces.

## 8. Perf constraint restated (CRITICAL) — AC-9

**This item must not recreate the per-building O(n) walk BUG-642/643 just killed.** Concretely:
- `utilisationOf(s, b)` stays an **O(1) ledger lookup** per call (`ledger.byBuilding[b.id] / capacityAtTier(...)`), never a scan — the SAME shape improvement BUG-630 already made for the `school` case (reusing `serviceCapacityAggregates` instead of re-deriving per call, `data.ts:1014-1021`) applies here: read a pre-computed structure, never re-walk.
- Assignment maintenance is **event-driven** (§5), not a per-tick full recompute — the periodic self-audit pattern FEAT-2326609764 specifies (full recompute every ~300 ticks, mismatch ⇒ registry error + fall back) is the recommended safety net here too, so a ledger that silently drifts from the truth is caught mechanically rather than discovered by Aaron mid-game.
- **Power is explicitly OUT of scope for true assignment** (not "citywide MW draw vs true draw") — a power plant does not serve a fixed set of buildings, it feeds a shared grid; inventing a "which plant powers which building" assignment would be exactly the kind of speculative model GR#25 forbids when the domain (grid physics) doesn't actually have that structure. `utilisationOf`'s `'power'` case keeps its honest `"citywide MW draw"` basis, unchanged, forever (or until a real grid-topology feature — FEAT-2326609741/2326609753 — gives power a segment structure worth assigning against, which is a separate BA pass).
- **Budget at 49k buildings:** cold-build ≤ the existing `onlineByBuilding` cold-build cost (one walk, memoised) measured against BUG-659's 147.8ms headless-tick baseline; per-tick incremental cost bounded by event count, target **≤1ms** added at Aaron's live scale (to be measured in inc1's Destructive round, not asserted here as a promise).

## 9. UI — AC-10 through AC-13

### AC-10 — where the true number shows
The building **inspector** (the existing per-building detail panel) gains a "Utilisation" row reading `utilisationOf(s, b)` exactly as today, but for a migrated kind the `.basis` string changes from `"citywide occupancy"` to `"true occupancy"` (etc. per kind) and the `.ratio` is the ledger-derived number. Hover tooltips on the map (wherever they currently surface citywide ratios) inherit the same change automatically since they read the same function.

### AC-11 — a heat overlay, reusing the water/power overlay idiom
A new "Utilisation" map overlay toggle mirrors the existing power-infrastructure-overlay idiom (`MapView.tsx:519`, `overlaySubsetsOf` building-subset cache, `MapView.tsx:86,490`) — colour each assignable building by its true ratio (a green→amber→red ramp, reusing whatever palette convention the water/power overlays already use). **Respects the BUG-659 viewport-culling fix**: the overlay draws only the currently-culled/visible building subset, never a fresh full-map pass (the exact regression class BUG-659 closed for the base render path).

### AC-12 — honesty rules (the BUG-606/641/649 lineage, applied to occupancy)
- **Never show a migrated-kind number that isn't ledger-backed.** A kind stays on `"citywide *"` until its ledger actually exists and is wired — no interim "true-ish" approximation.
- **Never claim a unit the number doesn't have.** BUG-649's lesson (a shortfall number rendered without saying jobs-vs-residents) applies directly: a building inspector row must say what's full — "18 of 20 dwellings occupied", "340 of 400 job slots filled" — not a bare percentage with an ambiguous basis.
- **A building at 0% because it just went offline is NOT the same story as a building at 0% because nobody wants to live/work there** — the inspector row for an offline building shows the SAME `computeFailedGates()` (`data.ts:796-815`) reason it already shows for offline status, not a bare "0% utilised" that reads as a demand problem.

### AC-13 — the consolidator seam
The consolidator's objective function (FEAT-2326609761, currently ranking stranded-capacity reconnection above density consolidation per Aaron's live-city ruling) consumes this ledger directly for its "which specific building is underused" question — a new read-only helper, e.g. `underutilisedBuildings(s, kind, thresholdRatio)` returning building ids below a ratio, backed by one pass over the relevant ledger's `byBuilding` map (already O(occupied buildings of that kind), not O(all buildings)). This item does not implement the consolidator's consumption of that helper (that is FEAT-2326609761's scope) — it only guarantees the helper exists and is truthful, which is the seam the consolidator BA needs registered before writing consolidator prose that references per-building occupancy (GR#25).

## 11. ASM candidates (numbered from ASM-1513)

- **ASM-1513** — fill-order is id-ascending, not placement-tick-ascending or (x,y)-ascending. Building id is already the stable, never-reused, assignment-order-independent key the codebase uses elsewhere (`onlineByBuilding` keys on the building object itself, but every serialisable index in this codebase that needs a stable citizen-independent order uses id). **RECOMMEND ACCEPT** — matches existing convention, needs no new sort key.
- **ASM-1514** — the reverse index (citizen/job → assigned building id) is sized O(population), which at Aaron's stated 100M-citizen goal is a real, non-trivial memory line that must be read against FEAT-2326609764 §1.3's own memory ceiling analysis (which already puts 1.5M buildings at 300MB+ of plain objects before this). **MEASURE before inc2** — inc1 (residential only) is the right increment to measure the true per-citizen overhead on Aaron's live save before committing to all seven ledgers.
- **ASM-1515** — power is permanently excluded from per-building assignment (§8) because the grid has no fixed serving relationship to assign against, unlike a dwelling/job/school seat. **ACCEPT AS VERIFIED** (grid topology feature FEAT-2326609741/2326609753 would need to land first to change this — separate BA pass).
- **ASM-1516** — FIFO re-housing order for `unassigned` citizens after a reconnection event (§6) is fair-but-arbitrary — it is NOT the same as "nearest first" or "highest-need first". **RECOMMEND ACCEPT for inc1** (matches the DeathQueue FIFO precedent and needs no new sort), revisit only if Aaron finds the visible re-housing order feels wrong in play.
