# Acceptance criteria — split the conflated MET-E002 default-deny code (BUG-011)

**BOW code:** BUG-011 (P3, open, depends on BUG-009 done)
**Spec refs:** GR#7 (registry-sourced errors — one code, one meaning); the item's own root cause in `internal/engine/core/errors.go` / `checkSpeed8xAllowed`; closes ASM-012.
**Date:** 2026-08-10
**Status:** active
**Package under test:** `internal/engine/core/` (specifically `errors.go` and the `checkSpeed8xAllowed` call site).
**Standard gates:** see `README.md`, package `./internal/engine/core/...`.

## Scope

A new, distinct registry error code for "8x would be valid if debug were wired, but no `Speed8xGate` is configured," replacing the current stopgap reuse of `MET-E002` (`ErrInvalidSpeed`) with a `reason:no_gate_configured` context field.

## Acceptance criteria

### Functional

- **AC-1.** A new constant (e.g. `ErrSpeed8xGateNotConfigured`) is added in `internal/engine/core/errors.go`, mapped to a **new** `data/errors.json` code claimed from `engine.core`'s already-owned range (per `README.md`'s Sprint-1-ratified convention: the owning module claims the next free subrange and records the claim in `data/errors.json`'s range table) — not a reused code. Check: `grep -n "ErrSpeed8xGateNotConfigured" internal/engine/core/errors.go` matches, and the paired `data/errors.json` entry has a distinct code from `MET-E002`, with real `severity`/`module`/`message`/`remedy` fields (not placeholders).
- **AC-2.** `checkSpeed8xAllowed` (or wherever the default-deny path lives) is updated to raise the new code instead of `ErrInvalidSpeed` when the gate is unconfigured, while still raising `ErrInvalidSpeed`/`MET-E002` for an actually-invalid speed value. Check: `grep -n "MET-E002\|ErrInvalidSpeed" internal/engine/core/*.go` (excluding `_test.go`) shows `ErrInvalidSpeed` used only for the genuinely-invalid-value path, and the new constant used only for the gate-unconfigured path.
- **AC-3 (Pattern #1 — the invariant this bug is about).** The two failure classes are **distinguishable by code alone**, without reading the `reason` context field — that was the whole complaint ("anyone triaging by error code alone cannot tell them apart"). A passing test asserts `SetSpeed(Speed8xDebug)` with no gate configured returns an `*errs.E` whose `.Code` differs from the code returned by `SetSpeed(<some invalid value>)`.

### Error handling

- **AC-4.** Neither path panics and both remain registry-sourced (`errs.New`/`errs.Wrap`, never a bare `fmt.Errorf`) — check via `go test ./internal/engine/core/... -race -count=1`.

### Documentation

- **AC-5.** `data/errors.json`'s new entry documents, in its `remedy` field, that this code means "wire a `Speed8xGate`," distinct from `MET-E002`'s "supply a valid speed value" remedy — so the two codes are also distinguishable by a human reading the registry, not only by a machine comparing strings.

## Out of scope

- Any change to what gates 8x behind debug (`feat.debugmode`'s own contract) — this item only fixes the error-code conflation, not the gating logic itself.

## Escalations

- None — the BOW item's own "Definition of done" is precise and maps directly onto AC-1/AC-2/AC-3 with no ambiguity requiring an assumption.
