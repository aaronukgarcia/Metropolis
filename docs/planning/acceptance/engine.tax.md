# Acceptance criteria — engine.tax (MOD-052)

**BOW code:** MOD-052
**Spec refs:** §39 Taxation — fine-grain controls (`docs/METROPOLIS-MASTER-v2.1.md` lines 558-565: the full instrument panel — council-tax bands by typology, per-district multipliers, empty-homes premium, holiday-let surcharge; business rates by zone×land-value with small-business relief and enterprise-zone discounts; a dozen behavioural levies; "every instrument has a shown elasticity response curve, a revenue line, an incidence display and a projected behavioural response... Laffer-honest"); §49 fuel-duty erosion (line 656: "fuel duty erodes as EVs grow — the tax base drives away, and the player must replace it... a genuinely modern fiscal problem, on rails, in the projections"); code.json `engine.tax` entry (inbound `TaxAPI`, "instruments as data-defined curves; incidence computed, not asserted"; consumers `engine.fiscal`, `engine.fuel`, `engine.policies`, `ui.screen.districts`, `ui.screen.finance`; outbound calls `engine.finance`, `foundation.data`).

**Package under test:** `internal/engine/tax/` (path from `node claude-bow.js show MOD-052`)

## User stories

- **US-1.** As the player, I need every tax/levy instrument's headline rate to be independently settable, so §39's "full instrument panel" is a real set of controls, not three sliders wearing extra labels.
- **US-2.** As the player, I need each instrument's elasticity to be a genuine behavioural response — raise the rate too far and the taxed base actually shrinks (evasion/departure/substitution) — so the "Laffer-honest" claim is a property of the model, not a decorative curve drawn once and never touched again.
- **US-3.** As the player, I need each instrument's incidence display to say who actually bears the cost *at the current rate*, and to visibly move when I change that rate, so §39's "incidence display (who actually pays)" is informative rather than a fixed label.
- **US-4.** As `engine.fiscal` (this BA's sibling file, this sprint), I need `TaxAPI` to post every collected instrument's revenue through `engine.finance`'s ledger, so the whole-economy Sankey view and the money-conservation invariant see real transactions, not a second tax total `engine.tax` keeps for itself.
- **US-5.** As `engine.policies` (this BA's sibling file, this sprint, a later-seq dependent), I need council-tax bands, business rates and levies to support a per-district multiplier, so named districts (Tax-Free Harbour, enterprise zones) are a real fiscal identity, not cosmetic.
- **US-6.** As `ui.screen.districts` and `ui.screen.finance`, I need every instrument's revenue, elasticity curve and incidence display to be queryable data, not rendered text baked into a UI package, so both screens can show the same numbers without duplicating the model.

## Scope

The tax instrument panel: residential (council-tax bands by typology, per-district multipliers, empty-homes premium, holiday-let surcharge), business (rates by zone×land-value, small-business relief, enterprise-zone discounts), and behavioural/levy instruments (parking, congestion cordon, tolls, landfill tax, nightlife levy, workplace parking levy, fuel duty share, tourist bed tax, planning fees, user charges) — each data-defined, each with a real elasticity response, a real incidence split, and revenue posted through `engine.finance`. Fuel-duty erosion's EV-share coupling is data-shaped here but the EV mechanics that drive it are out of scope (later sprint).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `TaxAPI` exists exposing: a query surface listing all registered instruments with current rate/revenue/elasticity-curve/incidence, and a mutation surface to set an instrument's rate — matching code.json's "instruments as data-defined curves; incidence computed, not asserted" pattern. Check: `go doc ./internal/engine/tax TaxAPI` shows both a listing/query method and a rate-setting command; `grep -rn "func Test.*[Ll]istInstrument\|func Test.*[Ss]etRate" internal/engine/tax/*_test.go` finds coverage.
- **AC-2 (§39; GR#15 data-driven, ASM-283).** All instrument definitions (name, category, valid rate range, elasticity coefficient(s), bearer-split weights per ASM-287) are loaded from `data/tax_instruments.json`, not a hardcoded Go switch/struct literal per instrument. Check: `grep -n "\"instruments\"\|\\$comment" data/tax_instruments.json` matches; `grep -rn "func Test.*[Ll]oadInstrument" internal/engine/tax/*_test.go` finds a passing load test; `grep -nE "council.?tax|business.?rate|congestion" internal/engine/tax/*.go` (excluding `_test.go`) finds no instrument-name string literal driving branching logic (names come from the loaded data, not `if key == "councilTax"` chains).
- **AC-3 (§39 elasticity — the behavioural-response trap).** Raising an instrument's rate produces a measurably smaller taxed base at the higher rate than at the lower rate, for the same starting population/firm state — elasticity is a real input-to-output relationship, not a number shown next to a rate that doesn't otherwise affect anything. Check: a passing test sets an instrument to a low rate, records the resulting taxed base (e.g. number of liable households/firms, or taxed transaction volume), resets to identical starting state, sets a high rate, and asserts the high-rate base is strictly smaller (`grep -rn "func Test.*[Ee]lastic.*[Bb]ase\|func Test.*[Rr]ateResponse" internal/engine/tax/*_test.go`). **Lazy implementation this rejects:** an instrument whose "elasticity response curve" is rendered in the UI from a static coefficient but whose actual tax-collection code always taxes the full, unchanged base regardless of rate (elasticity as decoration) would pass any check that only inspects the shown curve's shape — this check instead re-derives the base from the collection code path itself, before and after a rate change, so a base that never moves fails it outright.
- **AC-4 (§39 revenue = rate × responsive base, Laffer-honest).** `Revenue(instrument)` is computed from the current rate multiplied by the *current, rate-responsive* base (AC-3's base, not a cached pre-change value), so revenue growth decelerates as rate rises past the point where base shrinkage outpaces the rate increase. Check: a passing test sweeps an instrument's rate across at least three points (low/mid/high) and asserts marginal revenue (Δrevenue/Δrate) is smaller between mid→high than between low→mid — i.e. revenue is provably non-linear/concave in rate, not a straight `rate × fixedBase` line (`grep -rn "func Test.*[Ll]affer\|func Test.*[Mm]arginalRevenue" internal/engine/tax/*_test.go`). **False-pass risk:** a test that only checks "revenue increases with rate" would pass a purely linear (non-Laffer) model — the check requires the concavity/deceleration comparison, not just monotonic direction.
- **AC-5 (§39 incidence — the display-vs-response trap, this item's hardest AC).** `IncidenceDisplay(instrument)` returns a per-bearer-category breakdown (ASM-287; e.g. council tax: owner-occupier vs landlord vs tenant; business rates: firm vs pass-through consumer) whose *proportions*, not just totals, are recomputed from the current rate and base state — changing the rate changes who bears how much of the burden, not merely how much total revenue there is. Check: a passing test sets an instrument to two different rates, queries `IncidenceDisplay` at each, and asserts the bearer-category *percentage split* differs between the two calls for at least one instrument where the spec/data implies pass-through varies with rate (e.g. a landlord absorbing more of a low council-tax rate but passing more through to rent at a high rate) (`grep -rn "func Test.*[Ii]ncidence.*[Ss]hift\|func Test.*[Bb]earer" internal/engine/tax/*_test.go`). **Lazy implementation this rejects, and why it's the load-bearing check:** a tax panel that shows an incidence breakdown computed once from a fixed lookup table (e.g. "council tax is always 70% owner/30% landlord") would satisfy any check that only asserts the panel *displays* a breakdown — this check instead requires the split itself to move when the rate moves, which a constant-table implementation cannot pass no matter how the display looks.
- **AC-6 (§39 per-district multipliers).** Every instrument supports an optional per-`DistrictID` rate multiplier (ASM-285's cell-tagged district model), stacking with the instrument's citywide base rate; querying revenue/incidence for a district-scoped instrument reflects the multiplier. `TaxAPI` stores and resolves district multipliers itself (keyed by `DistrictID`, a plain identifier) — it does **not** call `engine.policies` to do so (`engine.policies` depends on `engine.tax`, not the reverse; a call the other way would be a dependency cycle). Check: `go doc ./internal/engine/tax SetDistrictMultiplier` (or equivalent) exists; a passing test sets a district multiplier and asserts the district-scoped revenue/incidence differ from the citywide default (`grep -rn "func Test.*[Dd]istrictMultiplier" internal/engine/tax/*_test.go`).
- **AC-7 (§39 business rates; land-value input).** Business-rate calculation multiplies a zone-class coefficient by the cell's land value, sourced from `engine.finance`'s `LandPrice` query (the registered `engine.tax`→`engine.finance` edge) — not a second, independently-maintained land-value figure inside `engine.tax`. Check: `grep -n "LandPrice\|engine/finance" internal/engine/tax/*.go` shows the call; a passing test asserts business-rate revenue for two cells with different `LandPrice` results differs accordingly (`grep -rn "func Test.*[Bb]usinessRate" internal/engine/tax/*_test.go`).
- **AC-8 (GR#3; money reuse, not a second total).** `engine.tax` posts every collected instrument's revenue as a transaction through `engine.finance`'s `FinanceAPI` (the registered `engine.tax`→`engine.finance` edge) and does not maintain its own independent running "total tax collected" figure that isn't derived by querying finance's ledger. Check: `grep -rn "PostTransaction\|FinanceAPI" internal/engine/tax/*.go` shows revenue posting through finance; `grep -n "totalRevenue\s*+=\|totalCollected\s*+=" internal/engine/tax/*.go` (excluding `_test.go`) finds no independently-accumulated running total field — any "total revenue" query derives from a `FinanceAPI` query at call time.
- **AC-9 (§39/§49 fuel-duty erosion — data shape only, EV mechanics out of scope).** The fuel-duty instrument's elasticity/base declares an explicit EV-share input parameter (a documented field on the instrument's query/response, not a hidden constant), so `engine.fuel`/vehicle mechanics (later sprint) can push a growing EV share in and observe duty revenue erode, without this item needing to model EV adoption itself. Check: `go doc ./internal/engine/tax` shows the fuel-duty instrument's response type carrying an EV-share (or equivalent taxed-base-erosion) field; a passing test pushes two different EV-share inputs and asserts fuel-duty revenue differs (`grep -rn "func Test.*[Ff]uelDuty" internal/engine/tax/*_test.go`).
- **AC-10 (money type — GR#3/M0-ENG §1.2 consistency with engine.finance).** All monetary values `engine.tax` produces or accepts (rates expressed as absolute amounts, revenue, thresholds) use `engine.finance`'s `Money` (int64 micro-pounds) type, never a locally-declared money type or a `float32`/`float64` monetary field. Check: `grep -n "float32\|float64" internal/engine/tax/*.go` (excluding `_test.go` and rate-*percentage* fields, which are legitimately fractional) finds no monetary-field matches; `go doc ./internal/engine/tax` shows monetary fields typed as `finance.Money` (or the package's aliased equivalent).

### Error handling

- **AC-11 (GR#7).** Setting a rate outside an instrument's declared valid range (from `data/tax_instruments.json`) is rejected with a registry-sourced error (new `MET-E`-range code) naming the instrument and the attempted value, never silently clamped or accepted. Check: `grep -n "MET-" internal/engine/tax/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalidRate\|func Test.*[Oo]utOfRange" internal/engine/tax/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no clamped or silently-accepted rate was written to the instrument, not merely that a matching-named test function exists.
- **AC-12 (GR#7).** Querying/setting an unregistered instrument key returns a registry-sourced error, never a zero-value instrument silently treated as valid. Check: `grep -n "MET-" internal/engine/tax/*.go`; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredInstrument" internal/engine/tax/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value instrument was silently treated as valid, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-13 (GR#21).** Any cross-district or cross-instrument summation (e.g. citywide revenue aggregated across all districts) iterates in a fixed, sorted order — never unordered Go map iteration. Check: `grep -n "for .* := range" internal/engine/tax/*.go` on any map feeding a monetary sum is either absent or followed by sorted-key iteration (`grep -n "sort\." internal/engine/tax/*.go`); a passing determinism test asserts identical totals across repeated runs (`grep -rn "func Test.*[Dd]eterminis" internal/engine/tax/*_test.go`).
- **AC-14 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/tax/*.go` (excluding `_test.go`) returns no matches — instrument evaluation is a function of simulation state/tick, never wall clock.
- **AC-15.** `go test ./internal/engine/tax/... -race -count=1` passes with no data race when instruments are queried/set concurrently across shards within a single monthly tax phase. Check: `grep -n "go func()" internal/engine/tax/*_test.go` finds at least one concurrency test.

## Out of scope

- EV adoption modelling and the vehicle fleet itself (`engine.vehicles`/`engine.fuel`, later sprint) — AC-9 only requires the fuel-duty instrument to accept an EV-share input, not to compute one.
- Named-district drawing/naming UX (`ui.screen.districts`, this BA's sibling file) — `engine.tax` only needs a `DistrictID` key to scope multipliers against.
- Policy-driven coefficient moves onto tax instruments (`engine.policies`, this BA's sibling file, e.g. a freeport policy suppressing business rates) — `engine.policies` calls into `TaxAPI` (the registered edge); this item only needs to expose settable rates for that caller, not model the policy layer itself.
- The full whole-economy Fiscal Circuit view and civil-service net-cost accounting (§54, `engine.fiscal`, this BA's sibling file) — this item posts underlying ledger entries; the whole-economy visualisation is that module's job.
