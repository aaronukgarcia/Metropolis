## User stories

- **US-1.** As every later service-specific module (`engine.education`, `engine.crime`, `engine.dispatch`, `engine.refuse`, `engine.social`, `engine.coastal`, `engine.prison`, `engine.comms`), I need one generic service model (capacity, coverage radius, funding level → quality) so each specific service is a thin registration against a shared framework, not N independent reimplementations of the same capacity/coverage/quality arithmetic.
- **US-2.** As the player adjusting a funding slider, I need funding level to drive quality through a real, queryable function, so a funding cut is felt as a documented quality degradation, not a hidden number that only surfaces in flavour text.
- **US-3.** As §26's unified dispatch model, I need elder care and home-care staffing to draw from the same pool as hospital staffing — a nurse shortage is genuinely one shortage everywhere, not per-service-siloed staffing pools that happen to share a name.
- **US-4.** As §54's Public Service Pie, I need the default per-1,000-population benchmark staffing ratios (police ~2.4, teachers per pupil, nurses & GPs, dentists & opticians, firefighters, social workers, refuse crews, council officers) loaded as data, with consequences that scale from village-mild to city-systemic as population grows, so a 10% police cut is mechanically a quiet month at 2k population and §28-arithmetic-serious at 2M.
- **US-5.** As `engine.finance` (MOD-022, this BA's own file above), I need every service's funding level to be a real budget line the ledger tracks, and every service's opex to post through `FinanceAPI`, so services are a genuine drain on the city budget, not narratively-described but financially inert.
- **US-6.** As `ui.screen.services`, I need funding sliders exposed as commands (per code.json's documented pattern), so the UI never mutates service state directly, only issues funding-level change commands through the protocol.
- **US-7.** As `data.catalogue`'s service-building entries (FEAT-010, this BA's Sprint 2 file), I need each service building's declared capacity/coverage figures to feed this module's per-service capacity accounting directly, so a built clinic's capacity is the number this module actually uses, not a duplicate.

## Scope

The generic service model (capacity, coverage radius, funding-level→quality function) for every §10-listed service; shared staffing pools across related services (§26); the Public Service Pie's default per-1k benchmark ratios and their scale-dependent consequence curve (§54); funding-level commands. Individual service-specific mechanics (education stage transitions, crime/gang dynamics, dispatch routing, refuse rounds) belong to their own later modules, which register against this framework.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `ServicesAPI` exists exposing per-service capacity/demand/coverage queries and funding-level mutation commands, matching code.json's documented pattern exactly ("per-service capacity/demand/coverage; funding sliders are commands"). Check: `go doc ./internal/engine/services ServicesAPI` shows both query and command shapes; `grep -n "func.*SetFunding" internal/engine/services/*.go` confirms funding is mutated via a command handler, not a public field setter.
- **AC-2 (§10 generic model).** A `Service` (or equivalent) type/interface is generic enough to represent every §10-listed service (roads-maintenance, electricity, water-sewage, healthcare, deathcare, garbage, education, fire, police & jail, elder care, child benefit, public transport, parks & leisure, communications, districts & policies administration, disasters-lite response) via registration, not a hardcoded enum requiring a code change per new service. Check: `go doc ./internal/engine/services Service` (or `ServiceKind`/registration function) shows an extensible registration mechanism; a passing test registers a synthetic new service kind and asserts it's queryable through the same `ServicesAPI` methods as a built-in one (`grep -rn "func Test.*[Rr]egisterService\|func Test.*[Ee]xtensib" internal/engine/services/*_test.go`).
- **AC-3 (§10 capacity/coverage/funding→quality).** Every registered service instance carries: a capacity figure (consumed from `data.catalogue`'s building capacity fields per US-7), a coverage radius (spatial reach from the service building's cell, consumed against `engine.world`), and a funding level (0-100% or equivalent), with quality computed as a documented function of all three (funding alone doesn't determine quality if capacity/coverage are also short). Check: `go doc ./internal/engine/services Quality` (or equivalent) exists; a passing test asserts quality degrades when funding drops, independently asserts quality degrades when demand exceeds capacity at full funding, and independently asserts quality degrades for out-of-coverage-radius demand (`grep -rn "func Test.*[Qq]uality" internal/engine/services/*_test.go`).
- **AC-4 (§26 shared staffing pools).** A staffing-pool abstraction exists where multiple services can be configured (via data, not hardcoded) to draw from the same named pool — at minimum, hospital + elder-care + home-care sharing a "nursing" pool per §26's explicit example — such that a shortage in the shared pool degrades quality/capacity for every service drawing from it simultaneously. Check: `go doc ./internal/engine/services StaffingPool` (or equivalent) exists; a passing test asserts reducing a shared pool's available staff degrades quality for two distinct services drawing from it, in the same tick (`grep -rn "func Test.*[Ss]taffingPool\|func Test.*[Ss]haredStaff" internal/engine/services/*_test.go`).
- **AC-5 (§54 Public Service Pie).** Default per-1,000-population benchmark staffing ratios are loaded from data (not hardcoded), including at minimum: police officers ~2.4/1k, refuse crews, firefighters, teachers-per-pupil, nurses & GPs, dentists & opticians, social workers, and council officers, each with a documented source citation to §54. Check: a passing test asserts the loaded police ratio is 2.4 per 1,000 (GR#15: transcribed from §54) and that all eight named categories are present (`grep -rn "func Test.*[Pp]ublicServicePie\|func Test.*[Bb]enchmarkRatio" internal/engine/services/*_test.go`).
- **AC-6 (§54 scale-dependent consequences).** The consequence of a given percentage staffing shortfall relative to the benchmark ratio scales with population — a passing test demonstrates that an identical relative shortfall (e.g. 10% below benchmark) produces a materially smaller quality/service-metric impact at a small population (2,000) than at a large population (2,000,000), matching §54's explicit "mild at village scale, systemic at city scale" framing. Check: `grep -rn "func Test.*[Ss]cale.*[Cc]onsequence\|func Test.*[Vv]illageVsCity" internal/engine/services/*_test.go` finds this comparison and it passes.
- **AC-7 (§10 tier-gating; sprint-plan S4 exit gate — "milestone tiers 1–4 gate correctly").** Service availability respects the §4 milestone ladder — a service whose enabling building isn't yet unlocked (via `engine.unlocks`, MOD-032, this sprint) cannot be registered/funded. Since the S4 exit gate names tiers 1–4 specifically, this AC's check is anchored to §4's own early-tier table rather than a generic synthetic gate: at tier-1 (Wilderness) population, attempting to fund the basic clinic (a tier-2/Hamlet unlock) is rejected; after crossing tier-2's threshold it succeeds; attempting to fund fire & police posts (a tier-4/Small Town unlock) is rejected below tier-4's 5,000 threshold and succeeds at/above it. Check: `go doc ./internal/engine/services` shows the tier-gate check calling `engine.unlocks`'s `IsUnlocked` (not a locally-duplicated milestone check); a passing test exercises the clinic-at-tier-2 and fire/police-at-tier-4 cases above, both the rejected-below and accepted-at-or-above sides (`grep -rn "func Test.*[Tt]ierGate\|func Test.*[Nn]otUnlocked\|func Test.*[Ee]arlyTierGate" internal/engine/services/*_test.go`). False-pass risk: a test with one un-unlocked service and one unlocked service, both arbitrarily chosen, would pass a build whose gate check is wired to the wrong tier boundary (off-by-one against §4's actual thresholds) as long as the two fixture services happen to straddle *some* boundary — anchoring the check to §4's literal tier-2/tier-4 examples closes that gap.
- **AC-8 (§54 civil-service net-cost framing).** Every service's opex includes wage costs for its staffing pool, and the module exposes both gross wage cost and net fiscal cost (gross wage − income-tax clawback, consuming `engine.finance`'s tax-collection figures) as distinct queryable values, so "the game's books show gross vs net" (§54) is a real, not narrative, distinction. Check: `go doc ./internal/engine/services` shows both `GrossWageCost` and `NetFiscalCost` (or equivalent); a passing test asserts `NetFiscalCost < GrossWageCost` for a positive tax rate (`grep -rn "func Test.*[Nn]etFiscal\|func Test.*[Gg]rossNet" internal/engine/services/*_test.go`). False-pass risk: `NetFiscalCost < GrossWageCost` alone would pass a build that subtracts a hardcoded constant or a made-up flat percentage instead of actually querying `engine.finance`'s live income-tax rate (violating GR#15 for the tax-rate input specifically, even though the ratios elsewhere in this file are correctly left untuned) — the check requires a second assertion that changing `engine.finance`'s tax rate (holding gross wage fixed) changes `NetFiscalCost` by the corresponding amount, proving the clawback is a live query, not a baked-in guess.
- **AC-9 (§10 upgrade paths).** Services expose an upgrade-path query (per catalogue tiers, e.g. clinic→hospital) reflecting `data.catalogue`'s building-tier progression, distinct from the funding-level slider — upgrading changes capacity/coverage ceilings, funding only affects realised quality within the current ceiling. Check: `go doc ./internal/engine/services UpgradePath` (or equivalent) exists; a passing test asserts an upgraded service instance has a higher capacity ceiling than its pre-upgrade state at identical funding (`grep -rn "func Test.*[Uu]pgrade" internal/engine/services/*_test.go`).
- **AC-10 (US-7; data.catalogue seam).** A service's capacity is sourced directly from its underlying `data/buildings.json` entry's declared capacity field (this BA's `data.catalogue.md` AC-5), not a duplicate hand-authored value. Check: a passing integration test loads a `buildings.json` fixture entry and asserts the registered service's capacity equals the catalogue entry's capacity field (`grep -rn "func Test.*[Cc]atalogueCapacity" internal/engine/services/*_test.go`).

### Error handling

- **AC-11 (GR#7).** Registering a service against an unregistered `ServiceKind`, or querying a service that was never registered, returns a registry-sourced error (new `MET-E`-range code) rather than a zero-value quality/capacity silently treated as "service exists but is empty". Check: `grep -n "MET-" internal/engine/services/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredService" internal/engine/services/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value quality/capacity record was silently created, not merely that a matching-named test function exists.
- **AC-12.** A funding-level command outside its valid range (negative, or above 100% where the data schema caps it) is rejected with a typed error, never silently clamped without the caller knowing clamping occurred. Check: passing test coverage (`grep -rn "func Test.*[Ii]nvalidFunding" internal/engine/services/*_test.go`).

### Determinism & safety

- **AC-13 (GR#21).** Quality computation and staffing-pool allocation across competing services are deterministic — when a shared pool is short and must allocate staff across multiple services, the allocation order is a documented, deterministic priority rule (e.g. sorted by service ID or a data-declared priority weight), never map-iteration order. Check: `grep -n "for .* := range" internal/engine/services/*.go` on any map feeding allocation order is sorted (`grep -n "sort\." internal/engine/services/*.go`); a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/services/*_test.go`).
- **AC-14 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/services/*.go` (excluding `_test.go`) returns no matches — quality, staffing allocation, and funding effects are computed purely from simulation tick/state inputs, never wall clock.
- **AC-15.** `go test ./internal/engine/services/... -race -count=1` passes with no data race when multiple services concurrently query/draw from shared staffing pools within a tick. Check: `grep -n "go func()" internal/engine/services/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-16.** `internal/engine/services/doc.go` states the module key `engine.services`, cites §10, §54, and §26, and documents the extensibility contract for registering a new service kind (US-1), so later-sprint modules (`engine.education`, `engine.crime`, etc.) have a template. Check: `grep -n "engine.services" internal/engine/services/doc.go` and `grep -n "§10\|section 10" internal/engine/services/doc.go` and `grep -n "§54\|Public Service Pie" internal/engine/services/doc.go` all match.
- **AC-17.** The Public Service Pie's default ratios are documented in a comment citing §54 next to their declaration/loaded location, distinguishing "default benchmark" (data, tunable in M2 Batch) from "hard requirement" (there is no hard requirement — the whole point is the player can deviate and feel the consequence). Check: `grep -n "§54\|benchmark" internal/engine/services/pie.go` (or equivalent) finds this framing.

## Out of scope

- Every individual service's specific mechanics (education stage transitions §27, crime/gang dynamics §28, unified dispatch routing §26's response-time model, refuse rounds §25, coastal arrivals §30, prison/rehabilitation §43, social services floor §53, comms/e-commerce §35) — those are their own later-sprint modules (`engine.education`, `engine.crime`, `engine.dispatch`, `engine.refuse`, `engine.coastal`, `engine.prison`, `engine.social`, `engine.comms`), which register against this framework rather than this item implementing them.
- Districts & policies' actual per-district tax/ordinance mechanics (§52, tier 7+) — this item only needs districts/policies present as one of §10's service categories at the generic-model level.
- Disasters-lite's actual event generation (road closure, storm surge, aquifer drought) — `feat.disasters` (a later item) generates the events; this item's job is that "disasters-lite" is a registrable service-adjacent category the event pressure can act on.
- Municipality/planning-quality's permit-speed and build-cost-error mechanics (§54's "municipality quality" paragraph) — that is `engine.fiscal`'s (Sprint 9) job; this item only needs council-officer staffing as one Pie category.
