# Acceptance criteria — cloud.gpu (MOD-068)

**BOW code:** MOD-068 (P3, open, `milestone: future`) — "GPU solver sidecar (C++/CUDA)".
**Spec refs:** M0-ENG §1 (`docs/METROPOLIS-MASTER-v2.1.md` line 788 "Target hardware & the resource doctrine"; line 790 reference machine "RTX 3050-class GPU (~2,560 CUDA cores, 4 GB VRAM)"; line 792 "CPU (v1, always works) → GPU sidecar (local acceleration) → cloud (Azure). One seam, three muscles. Do not entangle CUDA with the engine."; process topology line 810 `solver-gpu.exe C++/CUDA sidecar (traffic assignment, cold-pass batch) — LATER`; GPU paragraph line 842 "road graph + OD matrices + flow vectors ≪ 4 GB VRAM… the engine cannot tell CPU from GPU from cloud except by latency… v1 ships CPU-only"); A4 (line 1348 / constitution line 1366: "identical contract CPU/GPU/cloud"); A9 (line 1371: "GPU sidecar is the intermediate tier"); `docs/design/solver-contract.md` (INT-003, the frozen seam — its "gRPC mapping sketch (prose only)" and Open Question #4 name this module as the trigger for named priority constants); code.json `cloud.gpu` entry (inbound `SolverGPU` gRPC, outbound `int.solver`).
**Date:** 2026-08-16
**Status:** draft-ahead — the module is **unbuilt and deferred** (v1 ships CPU-only, M0-ENG §1). No code.json registration beyond the module/interface skeleton exists; the package path is written by assumption (see ASM-797 / ES-1).
**This file's role:** this is the *local* acceleration tier of the solver-offload seam. It does **not** add any new engine capability — it implements the already-frozen `int.solver` `Solver` contract behind a separate `solver-gpu.exe` process so heavy solves (traffic assignment, cold-pass batches) can run on the RTX-class GPU without the engine ever knowing or caring. The single load-bearing contract, inherited from `int.solver` and `solver-contract.md`, is **bit-identical determinism**: for a `Deterministic=true` request the GPU's `Response.Payload` MUST be byte-identical to the CPU's, or the fallback chain (and the CI determinism gate) breaks. Everything else is plumbing around that invariant.
**Operational-number regime (same convention as `engine.finance.md` AC-21 / `feat.maintenance.md` AC-2/AC-16):** this module has **no player-felt balance numbers** to invent. The hardware thresholds it touches — the 4 GB VRAM envelope and the 20–30 M local-CPU ceiling — are **spec constants single-sourced in `int.solver`'s `sizing.go`** (`FitsGPUEnvelope`, `GPUVRAMEnvelopeBytes`, `ExceedsLocalCPUCeiling*`). The sidecar **consumes those helpers rather than re-hardcoding them** (GR#3). No AC may be satisfied by a junior inventing a threshold; the one place a number *could* be hand-rolled is the installed-card VRAM, which is **queried at runtime** (`cudaMemGetInfo`), never a literal (ASM-805).

## User stories

- **US-1.** As the engine's solver registry, I need a GPU backend that implements the frozen `int.solver.Solver` wire contract — the same `Solve(Request) (Response, error)` / `Supports(ProblemKind) bool` shape the CPU answers — so the one existing `solver.Get(problem)` → `.Solve(req)` call path can be answered by GPU with **zero engine-side change** ("a gRPC-backed `Solver` implementation is just another `registry.Register` call", `solver-contract.md`).
- **US-2.** As the player, I need a GPU-accelerated solve to be **bit-identical** to the CPU solve, so moving between tiers never changes my city — the fallback chain can swap CPU↔GPU mid-request and the world stays byte-identical (GR#21; M0-ENG §1.2 determinism gate).
- **US-3.** As the engine, I need the GPU sidecar to be **optional and fail-closed to CPU** — if it is missing, crashed, unreachable, or the job exceeds the card's VRAM, the CPU answers (slower, never wrong), because local fallback is mandatory (§15; `solver-contract.md` Fallback semantics).
- **US-4.** As a maintainer, I need **CUDA confined to the sidecar** — no engine package imports CUDA, gRPC stubs, or the sidecar client ("Do not entangle CUDA with the engine", M0-ENG §1; "Nothing else in the codebase is allowed to import CUDA…", `solver-contract.md`).
- **US-5.** As a debugging operator, I need the sidecar to report its **schema version** and its **actual available VRAM**, so a schema mismatch or an over-envelope job is a typed error I can see, never a silent wrong answer or a hung process.

## Scope

The `solver-gpu.exe` C++/CUDA sidecar plus the Go-side gRPC-backed `Solver` implementation that registers it into `int.solver`'s registry: wire-contract conformance (the unary `SolverService.Solve` RPC), the v1 `ProblemKind` subset it accelerates (`TrafficAssignment`, `ColdPassBatch`), bit-identical-to-CPU determinism, the VRAM-envelope refusal, schema-version negotiation, and typed registry-sourced errors. No CUDA in the engine; no Azure/cloud backend (that is `MOD-069`); no re-implementation of the registry/fallback chain (that is `int.solver`).

## Acceptance criteria

### Functional — the seam and the stub

- **AC-1 (GR#20; backend plugs the `int.solver` seam, never the engine).** A Go-side backend type (e.g. `GPUBackend` / `SidecarBackend`) implements `int.solver.Solver` — both `Solve(Request) (Response, error)` and `Supports(ProblemKind) bool` — and is registered into `int.solver`'s registry from a package **outside the engine**, at a priority between CPU (0) and cloud (100) per the documented convention (≈50). The engine never imports the sidecar or its client. Check: `grep -rn "Register" sidecar/solver-gpu/*.go` shows the registration call into `internal/foundation/solver`; `grep -rn "sidecar/solver-gpu\|GPUBackend\|SidecarBackend" internal/engine/` returns **no** matches (engine never imports the sidecar). **False-pass risk:** a backend type that satisfies the interface but is only wired in a test would pass a "the interface is implemented" grep while no production binary ever registers it — the check requires the registration to exist in a real init path, not only `_test.go`.

- **AC-2 (GR#20; stub forever).** A stub `Solver` for the GPU tier exists (e.g. `GPUStub` / `SidecarStub`) that returns a typed "sidecar unavailable" error from `Solve` and reports `Supports` honestly, so the registry/fallback/determinism logic is exercisable **headlessly, with no CUDA driver or GPU present**. Check: `grep -rn "type.*Stub\|SidecarStub\|GPUStub" sidecar/solver-gpu/*.go` finds the stub, and a passing test registers the stub and asserts the registry falls through to CPU (mirrors `int.solver`'s own `EchoProblem`/fallback tests). GR#20's "every module keeps a passing stub for life" is embodied here as the always-available stub — the sidecar's permanent headless stand-in, exactly as `CPUBackend` is the solver seam's own minimum implementation.

### Functional — the wire contract and the Supported kinds

- **AC-3 (GR#20; wire-contract conformance — field-for-field).** The sidecar's gRPC service is the single unary RPC `SolverService.Solve(SolveRequest) returns (SolveResponse)`, mapping field-for-field onto `int.solver`'s `Request`/`Response` (`Problem`, `SchemaVersion`, `Seed`, `Deterministic`, `Payload` in; `Payload`, `Backend`, `Stats`, `Warnings` out) — matching `solver-contract.md`'s "gRPC mapping sketch" exactly, no extra fields, no dropped fields. Check: the `.proto` (or generated stubs) under `sidecar/solver-gpu/` declare precisely those fields; a passing test round-trips a `Request` through the Go client → transport → a fake/mock `SolverService` and asserts `Response.Payload` is preserved byte-for-byte and `Seed`/`Deterministic`/`SchemaVersion` arrive unmutated.

- **AC-4 (Supports — the sidecar declares exactly what it can accelerate).** `Supports` returns true for the v1 subset the BOW item names — `TrafficAssignment` and `ColdPassBatch` — and false for every other kind (`DeepProjection`, `LifeWriting`, `EchoProblem`) until their schemas firm up. Check: `grep -rn "Supports\|TrafficAssignment\|ColdPassBatch" sidecar/solver-gpu/*.go` shows the declared set; a passing test asserts `solver.Get` for an out-of-subset kind never selects the GPU backend. **Rationale:** the two in-scope kinds are the only ones whose payload schemas exist (see ASM-795 / ES-2); the sidecar must not claim a kind it cannot honour, or the registry would route a malformed request to it.

### Functional — mandatory local fallback

- **AC-5 (local fallback mandatory; fail closed to CPU, never wrong).** When the sidecar process is absent, crashed, or unreachable, the Go client returns a typed error and the `int.solver` chain **falls through to `CPUBackend`** — the caller still receives a correct answer, distinguishable only by `Response.Backend` (e.g. `"cpu.v1"` vs `"gpu.sidecar"`). Check: a passing test with no live binary (or a mock transport returning `Unavailable`) asserts `Solve` still succeeds, the returned `Payload` equals the CPU result, and `Response.Backend` reflects the failover — never a nil `Response`, a panic, or a hung call. **False-pass risk:** a client that swallows the connection error and returns an empty `Response` (or `(nil, nil)`) would pass a "no panic" grep while silently returning wrong/empty state to the engine — the check requires the CPU result, not merely "didn't crash".

### Determinism & safety — the load-bearing group

- **AC-6 (GR#21; bit-identical to CPU — the crown invariant).** For the same `(Problem, Seed, Payload)` with `Deterministic=true`, the GPU backend's `Response.Payload` is **byte-identical** to `CPUBackend`'s, for every `ProblemKind` the sidecar `Supports`. Check: a golden cross-backend test runs a tiny deterministic `TrafficAssignment` fixture (and a `ColdPassBatch` fixture once its schema lands) through **both** CPU and GPU and asserts `bytes.Equal(cpuPayload, gpuPayload)`. The test is structured to **skip with a loud, named reason when no GPU is present** (never silently pass on a no-hardware CI), and the fixture is small enough to fit any VRAM. A mismatch is **auto-P0 under GR#21**. **False-pass risk:** a test that only asserts "GPU returns *some* non-empty payload" would pass a backend that is fast-but-wrong; the check requires `bytes.Equal` against the CPU result — that equality is the entire point of the seam.

- **AC-7 (GR#21; no nondeterministic float reduction inside the sidecar).** The sidecar's floating-point reductions (OD-matrix flow sums, VDF iterations) use **fixed-order / tree reductions matching the CPU backend's fixed-order summation** — no GPU float atomics, no unordered accumulation, no run-to-run variance. Check: the invariant is documented in the sidecar's headers/README (`grep -rn "fixed-order\|tree reduction\|deterministic" sidecar/solver-gpu/` matches), and the golden test (AC-6) is re-run N times asserting the GPU result is **stable across N runs** as well as equal to CPU. **Rationale (ASM-796):** CUDA's default float reduction order is not guaranteed to match Go's, and GR#21 makes any divergence a line-stopping P0 — the sidecar must engineer determinism in, not assume the hardware gives it.

- **AC-8 (GR#21; diagnostics never leak into state).** The Go client returns `Response.Payload` to the caller and sets `Backend`/`Stats`/`Warnings` as diagnostics only — it never reads `Backend`/`Stats` back into a `Request`, never hashes them into a snapshot, and never feeds them into another `Solve`'s `Seed`/`Payload`. Check: source review of the client for any such feedback loop; none exists (the same loop-closing ban `int.solver` AC-15 enforces on the contract package).

- **AC-9 (VRAM envelope refusal — over-envelope job fails loud, falls through to CPU).** Before solving, the sidecar estimates the job's referenced-data size (road graph + OD matrix + flow vectors, per A4) and, if it exceeds the **actually available VRAM — queried at runtime via `cudaMemGetInfo`, not a hardcoded 4 GB** — returns a typed error that the chain treats as "this backend failed, fall through to CPU". Check: a passing test (a mocked size estimate against a mocked small VRAM budget) asserts a typed error and registry fall-through to CPU; the 4 GB *reference* figure is **consumed from `int.solver`'s `FitsGPUEnvelope`/`GPUVRAMEnvelopeBytes`**, never re-declared (`grep -rn "4_000_000_000\|4 \* 1024\|4GB" sidecar/solver-gpu/` finds no literal). **Rationale (ASM-805):** the envelope is the card's real capability, not a spec guess; a job over it must degrade, not silently overflow or OOM the process.

### Version & schema

- **AC-10 (GR#2; schema negotiation — never silently mis-decode).** The sidecar reports the `SchemaVersion`(s) it can honour and **refuses** a `Request` whose `SchemaVersion` it does not support with a typed error — it never silently decodes a newer/older payload it does not understand. Check: a passing test sends an unknown `SchemaVersion` and asserts a typed error; the version the sidecar serves is derived from `git describe` via the same ldflags pattern as the rest of the project (GR#2) or, at minimum, is not a hand-maintained version file (version-guard doctrine).

### Error handling

- **AC-11 (GR#7; every failure mode is registry-sourced).** All sidecar failure modes — unavailable, schema mismatch, over-envelope, CUDA init failure, kernel/launch error — surface as **registry-sourced `MET-`-range errors** in the Go client: the gRPC status/error code is **mapped to a specific `MET-` code**, never a panic, never a bare gRPC/SDK error leaking to the caller, never a zero-value `Response`. Check: `grep -n "MET-" sidecar/solver-gpu/*.go` finds the mapping; passing tests assert the returned error's registry code matches for at least the unavailable and schema-mismatch cases (GR#7 assertion — the code, not merely a matching test name).

- **AC-12 (GR#7; malformed payload is an error, not a process death).** A garbage/malformed `Payload` for a declared `ProblemKind` returns a typed registry-sourced error and **leaves the sidecar process alive** to answer the next request — no crash, no undefined-behaviour result, no partial write into shared state. Check: a passing test feeds invalid bytes, asserts a typed error, then sends a second valid request and asserts the sidecar still answers it correctly.

### Documentation

- **AC-13.** `sidecar/solver-gpu/` carries a `doc.go` (or README) stating the module key `cloud.gpu`, citing M0-ENG §1 / A4 / A9 / `docs/design/solver-contract.md`, and stating explicitly (a) **bit-identical-to-CPU is the load-bearing contract** (GR#21), (b) **CUDA is confined to this package** — never the engine (GR#20), and (c) **local fallback is mandatory** — the sidecar is strictly an accelerant, never a dependency. Check: `grep -n "cloud.gpu" sidecar/solver-gpu/doc.go` (or README) and `grep -n "A4\|A9\|M0-ENG\|solver-contract" sidecar/solver-gpu/doc.go` both match.

## Out of scope

- The **CPU backend, the registry, and the fallback chain** — owned by `int.solver` (INT-003, done). This module only *registers into* them.
- The **Azure cloud backend and cloud-GPU instances** — `MOD-069` / `cloud.azure`; the far-future cloud-GPU tier is gated behind a measured perf-CI breach (`docs/cloud.md` §1, §4), not scheduled.
- **Real problem-kind payload schemas** for `TrafficAssignment`/`ColdPassBatch` beyond the frozen V1 shapes, and anything for `DeepProjection`/`LifeWriting` (TODO-SPEC with `engine.traffic`/`engine.citizens`, `solver-contract.md` Open Question #5).
- **Streaming/partial results and progress reporting** — the contract is one request/one response (`solver-contract.md`); a long-solve progress mechanism is a future `Response` field addition, not a shape change.
- **CUDA inside the engine** — forbidden by M0-ENG §1; this file's AC-1/AC-13 enforce the ban rather than open the door.

## Cross-check (edges this module sits on / feeds)

- **Sits on `int.solver` (INT-003, done).** The frozen `Solver` interface + priority/fallback registry is the whole seam this module plugs. The gRPC mapping it implements is documented prose in `docs/design/solver-contract.md` (no code, no deps added) — AC-3 is that prose made concrete. `int.solver`'s `chainSolver` already performs transparent failover, which is what makes AC-5's "fall through to CPU" free for this module to rely on.
- **Sits on the A4/A9 sizing tables** in `int.solver`'s `sizing.go` (`FitsGPUEnvelope`, `ExceedsLocalCPUCeiling*`). This module consumes them (AC-9), never re-declares them (GR#3 single source).
- **Feeds nothing directly.** `cloud.gpu`'s code.json `inbound.consumers` is empty — correct, because it is a *backend*, not a producer: engine modules consume `int.solver`, and `int.solver` routes to whichever backend is registered. The engine never sees the sidecar's GUID.
- **Sibling `cloud.azure` (MOD-069) and `cloud.netpolicy` (INT-004).** Both also register against `int.solver`. The priority convention (CPU 0 < GPU ≈50 < cloud ≈100) must not collide across the three backends — this is exactly `solver-contract.md` Open Question #4 (see ES-1).

- **For Bill — ES-1: named priority constants (solver-contract OQ #4) resolve before dispatch.** `solver-contract.md` explicitly names this module as the trigger: "Worth revisiting once the GPU sidecar module (`cloud.gpu`, MOD-068) actually registers a backend — do we want named priority constants (`PriorityCPU`, `PriorityGPU`, `PriorityCloud`) exported… instead of bare integers at each call site?" Recommend ruling yes and exporting them from `internal/foundation/solver` so AC-1's "≈50" is a named constant, not a magic integer that can collide with `cloud.azure`'s "≈100".
- **For Bill — ES-2: the sidecar can only accelerate kinds whose schemas exist (ASM-795).** `TrafficAssignment`'s V1 fields are "fixed" but `ColdPassBatch`/`DeepProjection`/`LifeWriting` are "minimal stub, TODO-SPEC with `engine.citizens`/projection module" (`solver-contract.md` Open Question #5). This does **not** block the sidecar skeleton (wire contract, stub, fallback, `EchoProblem`-adjacent plumbing, and one real kind are all buildable now), but the BOW item's "cold-pass batches on the GPU" promise needs `engine.citizens`' `ColdPassBatchRequestV1` schema to land first. Flag before a junior is dispatched on the cold-pass path specifically.
- **For Bill — ES-3: bit-identical GPU float determinism is the real engineering risk, not a given.** AC-6/AC-7 encode the invariant, but CUDA does not guarantee reduction-order parity with Go by default; this is a de-risk-to-verify item. Given the module is P3/future and the proportionality ruling ("we are not building NASA code"), recommend: keep the AC as written (it is the load-bearing contract and must hold), but expect the golden cross-backend test (AC-6) to be the *first* thing a junior proves on real hardware before any broader sidecar work — if fixed-order float parity cannot be made to hold cheaply, that is a stop-and-escalate, not a "ship the fast-but-2-ulp-off GPU path anyway".
