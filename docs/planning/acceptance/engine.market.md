# Acceptance criteria — engine.market (MOD-020)

**BOW code:** MOD-020
**Spec refs:** §6 Needs & Commodities (`docs/METROPOLIS-MASTER-v2.1.md` lines 189-204: every need imported/produced-locally/hybrid; the commodity table — water, power, food staple/fresh, fuel, construction materials, consumer goods, waste; services declared non-tradable separately); I.3 Fixed decisions (line 28: "static import prices v1 behind a market interface so dynamic pricing is a config flip later"); §2.2 (off-map connections: grid/gas/water/rail/port tranche purchase, consumed alongside this item's import channel); code.json `engine.market` entry (inbound `MarketAPI`, Go interface, "price/availability queries; dynamic-world future hook"; consumed by `engine.consumption`, `engine.farming`, `engine.finance`, `engine.firms`, `engine.freight`, `engine.logistics`, `engine.shopping`).
**Date:** 2026-08-09
**Status:** draft-ahead
**Package under test:** `internal/engine/market/` (path from `node claude-bow.js show MOD-020`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/market/...`.

## User stories

- **US-1.** As `engine.logistics`/`engine.consumption`/`engine.firms` and every other tradable-commodity consumer, I need a single `Market` interface exposing price and availability queries per commodity, so every module reads prices the same way regardless of whether pricing is static (v1) or dynamic (future) — I.3's "static import prices v1 behind a market interface so dynamic pricing is a config flip".
- **US-2.** As the player, I need every commodity in §6's table (water, power, food staples, food fresh, fuel, construction materials, consumer goods, waste) classified as importable, locally producible, or hybrid, with import consuming logistics capacity (opex, tonnes/slots) and local production consuming capex + land + jobs + input commodities, so the JIT/logistics system (§8) has real supply-side numbers to draw stock from.
- **US-3.** As `engine.finance`, I need every import transaction to produce a money-flow entry (opex against the city budget) through a documented seam, so §7's "import contracts" budget line is populated from real market activity, not invented separately.
- **US-4.** As the future dynamic-pricing feature (explicitly out of v1 scope but seam-guaranteed), I need the `Market` interface's static-price v1 implementation to be swappable for a dynamic-price implementation via configuration alone — no consumer-side code change — so I.3's "config flip" promise is a structural property, not aspirational.
- **US-5.** As `engine.services` (a §6 consumer via the non-tradable-services declaration), I need waste to be modelled as a genuine negative commodity — dear to export, accumulating if unhandled with health/land-value consequences — distinct from every positively-priced commodity's demand/supply shape.

## Scope

The `Market` interface: per-commodity static v1 import prices, local-production cost/input declarations, the import-vs-local-vs-hybrid classification for every §6 commodity, and the services-are-non-tradable boundary. Does not include the logistics stock/replenishment/truck mechanics themselves (§8, a later module) — this item is the price/availability oracle those mechanics query.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `Market` (or `MarketAPI`) Go interface exists with at minimum a price query (`Price(commodity CommodityKind) Money`) and an availability query (`Available(commodity CommodityKind, quantity int64) bool` or equivalent), consumed only through the interface by other modules (never a concrete `StaticMarket` type imported directly). Check: `go doc ./internal/engine/market Market` shows both query shapes; `grep -rn "market\.StaticMarket\b" internal/engine/*/` (excluding the `market` package itself) finds no direct concrete-type imports from other engine packages.
- **AC-2 (§6).** Every commodity in §6's table is represented: water, power, food-staples, food-fresh, fuel, construction-materials, consumer-goods, and waste (as a negative-priced/export-cost commodity), each carrying a `CommodityKind` value and a classification field (`import`/`local`/`hybrid`) matching §6's own table column. Check: `go doc ./internal/engine/market CommodityKind` lists all eight; a passing test asserts each has a non-empty classification (`grep -rn "func Test.*[Cc]ommodit" internal/engine/market/*_test.go`).
- **AC-3 (I.3; static v1).** `StaticMarket` (or equivalent), the mandatory v1 implementation of `Market`, returns a fixed price per commodity loaded from `data/consumption.json` or a dedicated `data/market.json` (documented which — GR#15 requires the number come from data, not a Go literal), never varying with quantity purchased, city size, or simulated demand/supply pressure. Check: `grep -n "type StaticMarket" internal/engine/market/*.go` matches; a passing test asserts `Price` returns the same value for two different `Available` quantities requested in the same tick (`grep -rn "func Test.*[Ss]tatic" internal/engine/market/*_test.go`).
- **AC-4 (I.3; the config-flip seam).** The engine's market backend selection is a configuration value (not a compile-time constant), and the interface has at least a documented extension point (a registry/factory analogous to `foundation.solver`'s backend selection) proving a second, dynamic-pricing implementation could be registered without changing `Market`'s method signatures. Check: `grep -n "NewMarket\|MarketBackend\|RegisterMarket" internal/engine/market/*.go` shows a selection/registration mechanism, not a single hardcoded constructor call site.
- **AC-5 (§6 import channel).** Each commodity's import path carries a documented opex cost and a logistics-capacity cost (tonnes/day or slot count, consumed by `engine.logistics` later) distinct from its price — e.g. importing water via bowser (small, road) vs. off-map pipe (per §2.2) have different capacity footprints even at the same £/unit. Check: `go doc ./internal/engine/market ImportChannel` (or equivalent) shows both a price and a capacity-cost field; a passing test asserts at least two different import channels for one commodity (e.g. water: bowser vs. pipe) carry different capacity costs (`grep -rn "func Test.*[Ii]mportChannel" internal/engine/market/*_test.go`).
- **AC-6 (§6 local production).** Each locally-producible commodity declares its production cost structure (capex, land requirement, jobs, input-commodity dependencies) as data consumed later by `engine.firms`/`engine.build`, not simulated by this package itself (this package declares the *shape* of local production options, e.g. "Boreholes: capex X, no input commodities" vs. "Light industry: capex Y, needs consumer-goods inputs"). Check: `go doc ./internal/engine/market LocalProductionOption` (or equivalent) exists; a passing test asserts at least one commodity (water) has more than one local production option (boreholes, reservoir, desalination per §6) each with distinct capex (`grep -rn "func Test.*[Ll]ocalProduction" internal/engine/market/*_test.go`).
- **AC-7 (§6 hybrid).** At least one commodity is modelled as `hybrid` (importable AND locally producible simultaneously, e.g. food-fresh: road/port import + market gardens/fishing), and `Market`'s availability query correctly reflects combined supply when both channels are active. Check: a passing test asserts a hybrid commodity's `Available` reflects the sum of import capacity and local production capacity (`grep -rn "func Test.*[Hh]ybrid" internal/engine/market/*_test.go`).
- **AC-8 (§6 waste).** Waste is modelled with an export cost (paying to remove it is dearer than importing an equivalent-value positive commodity is cheap) rather than a symmetric price, and `Market`'s price query for waste returns a cost-to-dispose value, not a price-to-acquire value — the sign/semantics are documented explicitly so consumers don't misread it as a purchase price. Check: `go doc ./internal/engine/market` documents waste's cost semantics; a passing test asserts querying waste's "price" returns a value tagged/typed distinctly from a normal commodity purchase price (`grep -rn "func Test.*[Ww]aste" internal/engine/market/*_test.go`).
- **AC-9 (§6 services boundary).** Non-tradable services (education, healthcare, elder care, fire, police, deathcare, leisure, transport) are explicitly NOT `CommodityKind` values and are not queryable through `Market` — `engine.services` owns them entirely, per §6's "services (non-tradable, §10) declared separately". Check: `grep -n "education\|healthcare\|police" internal/engine/market/commodities.go` (or wherever `CommodityKind` is enumerated) finds none of these as commodities.

### Error handling

- **AC-10 (GR#7).** Querying `Price`/`Available` for an unregistered `CommodityKind` returns a registry-sourced error (new `MET-E`-range code) rather than a zero-value price that could be silently spent as if real. Check: `grep -n "MET-" internal/engine/market/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregistered" internal/engine/market/*_test.go`).
- **AC-11.** A malformed/missing price entry in `data/consumption.json`/`data/market.json` (per AC-3) fails loudly at load time via `foundation.data`'s validated-load path, never silently defaulting a commodity's price to zero. Check: passing test coverage (`grep -rn "func Test.*[Mm]issingPrice\|func Test.*[Ll]oadFail" internal/engine/market/*_test.go`).

### Determinism & safety

- **AC-12 (GR#21).** `StaticMarket`'s prices are pure data lookups — querying the same commodity twice in the same tick (or across ticks, since v1 prices are static) returns byte-identical results, with zero dependence on call order or map iteration. Check: `grep -rn "for .* := range" internal/engine/market/*.go` — any range over commodity maps feeding an ordered output is sorted (`grep -n "sort\." internal/engine/market/*.go`); a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/market/*_test.go`).
- **AC-13 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/market/*.go` (excluding `_test.go`) returns no matches — v1 static prices have no time dimension at all; even a future dynamic-pricing implementation (out of this item's scope) would key off simulation tick, never wall clock.
- **AC-14.** `go test ./internal/engine/market/... -race -count=1` passes with no data race when queried concurrently by multiple consumer modules under the shard worker pool. Check: `grep -n "go func()" internal/engine/market/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-15.** `internal/engine/market/doc.go` states the module key `engine.market`, cites §6 and I.3, and documents the dynamic-pricing config-flip seam explicitly (what a future implementer needs to do to add a second backend). Check: `grep -n "engine.market" internal/engine/market/doc.go` and `grep -n "config.flip\|dynamic pricing" internal/engine/market/doc.go` both match.
- **AC-16.** Each commodity's classification (import/local/hybrid) and its §6 table source row are documented in a comment next to its declaration, so a later balance pass (M2 Batch) can trace every price back to its spec origin. Check: `grep -n "§6\|section 6" internal/engine/market/commodities.go` finds citations.

## Out of scope

- The logistics/JIT stock, replenishment, and truck-movement mechanics (§8, a later Sprint 6 module, `engine.logistics`) — this item is queried by that module, it does not implement stock drawdown itself.
- Dynamic pricing itself — only the seam (AC-4) is required; the actual dynamic-pricing algorithm is unscheduled future work per the sprint plan.
- Firm-level P&L and production chains (§33, `engine.firms`/`engine.freight`) — this item declares local-production *options* as data; it does not simulate firms opening/closing.
- Off-map tranche purchase mechanics (grid/gas/rail/port capacity bought in discrete tranches, §2.2/§22) — that is `engine.unlocks`'s "Buy" currency; this item's import channel is the ongoing per-unit opex flow, not the one-off capacity purchase.
- Aquifer sustainable-yield degradation modelling (§6's water note) — that is `engine.consumption`'s utility-network concern; this item only prices/classifies water as a commodity.
