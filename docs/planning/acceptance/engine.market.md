# Acceptance criteria — engine.market (MOD-020)

**BOW code:** MOD-020
**Spec refs:** §6 Needs & Commodities, in full (`docs/METROPOLIS-MASTER-v2.1.md` lines 189-204: the import/local-production/hybrid taxonomy, the eight-row commodity table — water, power, food-staples, food-fresh, fuel, construction materials, consumer goods, waste — and the "services (non-tradable, §10) declared separately" line); I.3 Fixed decisions (line 28: "static import prices v1 behind a market interface"); §17.1/§17.2 and §2.2 (lines 292, 105: gas as a fourth, separately-networked utility — "Gas network is optional strategy... gas arrives by off-map pipeline tranche... or LNG via port" — the source for MOD-020's own description naming **gas** as a ninth commodity beyond §6 table's eight rows, see ASM below); M0-ENG §1.2 (line 825: money is int64 micro-pounds, referenced here because `engine.finance` — a registered consumer — carries this representation and Market's prices must feed it without a lossy conversion); code.json `engine.market` entry (inbound `MarketAPI`, "price/availability queries; dynamic-world future hook"; consumed by all 7 registered consumers, verified against the registry rather than paraphrased: `engine.consumption`, `engine.farming`, `engine.finance`, `engine.firms`, `engine.freight`, `engine.logistics`, `engine.shopping`; outbound calls to `engine.core`, `foundation.data`).
**Date:** 2026-08-10
**Status:** ready
**Package under test:** `internal/engine/market/` (path from `node claude-bow.js show MOD-020`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/market/...`.

## User stories

- **US-1.** As `engine.consumption`/`engine.farming`/`engine.firms`/`engine.freight`/`engine.logistics`/`engine.shopping` (registered consumers), I need a single `MarketAPI` for price/availability queries, so every module that needs "what does this commodity cost / can I get it" goes through one contract instead of duplicating pricing logic (GR#20).
- **US-2.** As the v1 game, I need import prices to be static data-driven values now, with the interface shaped so dynamic pricing can be switched on later purely by a config flip (I.3), so the pricing model can evolve without every consumer's call site changing.
- **US-3.** As `engine.logistics` (MOD-025, a later-sprint consumer, currently open), I need Market's availability answer bounded by a modelled logistics-capacity concept (tonnes/slots, per §8's junction/port/rail throughput), so "how much of this commodity can I actually get" is never an unconditional yes even before the JIT queue mechanics themselves exist.
- **US-4.** As the player reading the make-vs-buy trade-off, I need each commodity tagged with whether it's import-only, locally-producible, or hybrid (matching §6's per-row local-production notes), so later modules (`engine.farming`, `engine.firms`, future mining/power modules) know which commodities they're allowed to compete against imports for.
- **US-5.** As `engine.finance` (a registered consumer carrying money as int64 micro-pounds per M0-ENG §1.2), I need Market's prices expressed in that same fixed-point representation, so a price never silently loses precision crossing the module boundary.
- **US-6.** As the waste-disposal accounting path (§6's "Waste (negative commodity)" row), I need waste priced as an export cost, not folded into the same "pay to receive" semantics as the other eight commodities, so the negative-commodity distinction is a real code path, not a sign-convention footnote.
- **US-7.** As §10's non-tradable services (education, healthcare, elder care, fire, police, deathcare, leisure, transport), I need to never appear in Market's commodity registry, so "declared separately" is a structural guarantee, not a comment.

## Scope

The commodity registry (the nine tradable commodities per §6's table plus gas, see ASM-below), the import/local-producible/hybrid supply-mode tag per commodity, the static v1 import-price lookup loaded from data, a logistics-capacity-bounded availability query, and the waste negative-commodity export-price path — all behind a single `MarketAPI`. No dynamic pricing implementation, no local-production capex/build mechanics, no JIT queue/day-tick resolution.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `MarketAPI` (or equivalent) exists matching code.json's registered inbound contract — pattern "price/availability queries; dynamic-world future hook" — consumed by all 7 registered consumers (`engine.consumption`, `engine.farming`, `engine.finance`, `engine.firms`, `engine.freight`, `engine.logistics`, `engine.shopping`) through this interface alone, never a concrete internal market/commodity state struct reached directly from another package's non-test code. Check: `go doc ./internal/engine/market MarketAPI` shows query methods (e.g. `Price`, `Availability`); `grep -rln "market\.\(commodityState\|Registry\)\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/market` itself and `_test.go` files, the sanctioned H-STUB fixture exception) finds no direct exported-field writes from another package. State the false-pass risk explicitly: a grep that only checks `MarketAPI` exists as a name would pass even if every consumer actually reaches into market internals directly — the check must target writes bypassing the interface, not the interface's mere presence.
- **AC-2 (§6 commodity coverage).** The commodity registry contains exactly the nine commodities named in MOD-020's own BOW description and traced to §6/§17/§2.2 (water, power, gas, food-staples, food-fresh, fuel, construction materials, consumer goods, waste) — not a subset shipped as an "extensible example" set. Check: `go doc ./internal/engine/market CommodityType` (or equivalent enum) lists exactly these nine cases; a passing test asserts the registry's commodity count equals 9 and each is resolvable by name (`grep -rn "func Test.*[Cc]ommodit.*[Cc]ount\|func Test.*[Nn]ineCommodit" internal/engine/market/*_test.go`). False-pass risk: a grep for individual commodity-name strings (e.g. `grep -n "water\|power\|gas"`) would match doc-comment prose citing the spec without a single commodity actually being registered — the check requires a count assertion plus a named-lookup test, not string presence.
- **AC-3 (§6 supply-mode taxonomy).** Every commodity carries an explicit supply-mode classification — import-only, locally-producible, or hybrid — matching §6's table per-row (e.g. Fuel = import-only v1, "None early; synthetic late"; Water/Power/Food-staples/Food-fresh/Materials/Goods = hybrid, each having a local-production option named in §6; Gas = hybrid per §17's "all-electric city possible... or gas arrives by off-map pipeline"). Check: `go doc ./internal/engine/market SupplyMode` (or equivalent) exists as an enum with these cases; a passing test asserts Fuel's `SupplyMode()` returns import-only while Water's returns hybrid — i.e., at least two commodities differ — so a build that marks every commodity "hybrid" as a single fallback default fails this test (`grep -rn "func Test.*[Ss]upplyMode" internal/engine/market/*_test.go`).
- **AC-4 (I.3; static v1 price behind a config-flip seam).** Each importable commodity (all except Waste — AC-9) exposes a per-unit import price via a single `Price(commodity)` method on `MarketAPI`, backed at v1 by a static data-driven value (not computed from supply/demand), with the static-vs-dynamic pricing mode selected by a config flag so a future flip does not change `MarketAPI`'s method signature or add a second parallel pricing method. Check: `go doc ./internal/engine/market MarketAPI` shows exactly one exported price-query method for commodities (not a `StaticPrice`/`DynamicPrice` pair); `grep -n "pricingMode" data/market.json` (or equivalent) finds the config seam; a passing test calls `Price()` twice for the same commodity with no intervening command and asserts identical results, proving v1's static behaviour through the real interface rather than by inspection (`grep -rn "func Test.*[Ss]taticPrice\|func Test.*[Pp]riceStable" internal/engine/market/*_test.go`). State the false-pass risk: a grep merely finding the word "static" or "dynamic" in a doc comment proves nothing about whether the interface shape would survive a real pricing-mode swap — a second parallel method (e.g. an additional `DynamicPrice`) is exactly what would break the "config flip" promise while still making that grep pass, so the check targets method count, not vocabulary.
- **AC-5 (§6/§8; logistics-capacity-bounded availability).** `Availability(commodity, quantity)` (or equivalent) returns a value bounded by a modelled logistics-capacity concept (tonnes/slots, per MOD-020's own description and §8's junction/port/rail throughput) — Market's job is to expose this bound as data, even though the JIT queue mechanics themselves are `engine.logistics`'s (MOD-025, out of scope, still open). Check: the return type carries a capacity/quantity field, not a bare boolean; a passing test asserts lowering a commodity's configured import-capacity ceiling below a requested quantity changes the returned availability figure (`grep -rn "func Test.*[Cc]apacityBound\|func Test.*[Aa]vailabilityLimit" internal/engine/market/*_test.go`). False-pass risk: a method literally named `Availability` that always reports "yes"/unlimited satisfies a grep for the method's existence — the check requires a test proving the returned figure actually varies with a capacity input, not merely that the method compiles.
- **AC-6 (§6 waste — negative commodity).** Waste is priced through a distinct export-cost path (e.g. `ExportPrice(waste)`), not the same "pay a supplier to receive it" semantics `Price()` gives the other eight commodities. Check: `go doc ./internal/engine/market` shows a distinct waste-export accessor, or `Price(Waste)` is documented and tested to return a typed rejection directing callers to the export path; a passing test asserts calling the import-price path for Waste does not silently return a positive per-unit-received price (`grep -rn "func Test.*[Ww]aste.*[Ee]xport\|func Test.*[Nn]egativeCommodity" internal/engine/market/*_test.go`).
- **AC-7 (§6/§10; services excluded).** The commodity registry contains no services (education, healthcare, elder care, fire, police, deathcare, leisure, transport per §6's "declared separately" line and §10). Check: a passing test looks up each of the eight service names against the commodity registry and asserts every lookup returns not-found/zero-value, never a valid `CommodityType` (`grep -rn "func Test.*[Nn]oServic" internal/engine/market/*_test.go`). False-pass risk noted: a bare text grep for service names would match legitimate spec-citation prose in `doc.go` — the check must exercise the actual registry lookup, not search source text.
- **AC-8 (GR#15; no hardcoded prices).** Static v1 import prices, capacity ceilings, and supply-mode tags load from `data/market.json` (or equivalent) at package init/load time — no per-commodity price, capacity, or mode literal is hardcoded in Go source. Check: a passing test changes a value in the loaded data fixture and asserts `Price()`/`Availability()`/`SupplyMode()` reflect the change (mirrors `engine.season`'s AC-10 pattern exactly) (`grep -rn "func Test.*[Dd]ataDriven\|func Test.*[Rr]eload" internal/engine/market/*_test.go`); `grep -nE "[0-9]+\.[0-9]+" internal/engine/market/*.go` (excluding `_test.go`) finds no bare price-shaped numeric literals outside doc-comment prose transcribing the spec.
- **AC-9 (code.json outbound calls; int64 micro-pounds).** `Price()` and `ExportPrice()` return the same fixed-point money representation `engine.finance` uses (int64 micro-pounds, M0-ENG §1.2) — not a `float64` — so a registered consumer never loses precision converting a Market price into a ledger entry. Check: `go doc ./internal/engine/market` shows the price return type is an integer/fixed-point type, not `float64` or `float32`; `grep -n "float32\|float64" internal/engine/market/*.go` (excluding `_test.go`) finds no match on the price-computation path.

### Error handling

- **AC-10 (GR#7).** Querying `Price`/`Availability`/`SupplyMode` for an unregistered commodity ID returns a registry-sourced error (new `MET-E`-range code claimed at build time per the README's Sprint-1 convention), never a panic or a silently-returned zero value that a caller could mistake for a real price of zero. Check: `grep -n "MET-" internal/engine/market/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownCommodity\|func Test.*[Ii]nvalidCommodity" internal/engine/market/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value price/availability was returned as if it were real, not merely that a matching-named test function exists.
- **AC-11 (GR#7).** A malformed or schema-invalid `data/market.json` (a commodity missing its price field, a negative price or capacity, an unrecognised supply-mode string) produces a registry-sourced error at load time, never a silent default-to-zero or default-to-"hybrid" substitution that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/market/*.go` finds a load-time registry code reference distinct from AC-10's query-time code; passing test coverage (`grep -rn "func Test.*[Mm]alformed\|func Test.*[Ii]nvalidMarketData" internal/engine/market/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no default-to-zero or default-to-"hybrid" substitution was silently loaded, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-12 (GR#21).** `Price`, `Availability`, and `SupplyMode` are pure/deterministic functions of loaded data plus current tick/command state — repeated calls with no intervening command return byte-identical results, and results are identical across worker counts. Check: a passing determinism test exists and asserts identical output across repeated calls and (if feasible) across worker counts (`grep -rn "func Test.*[Dd]eterminis" internal/engine/market/*_test.go`).
- **AC-13 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/market/*.go` (excluding `_test.go`) returns no matches — pricing and availability are functions of loaded data and simulation tick/command inputs only, never wall clock.
- **AC-14.** `go test ./internal/engine/market/... -race -count=1` passes with no data race when `MarketAPI` is queried concurrently from multiple consumer shards (the package's read-only, load-once commodity/price data must be safe for concurrent reads without a lock on the hot query path). Check: `grep -n "go func()" internal/engine/market/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-15.** `internal/engine/market/doc.go` states the module key `engine.market`, cites §6 and I.3, lists all nine commodities each with its supply-mode tag, and states explicitly (a) the waste negative-commodity export-price treatment and (b) the static-v1/dynamic-later config-flip seam this item establishes but does not implement. Check: `grep -n "engine.market" internal/engine/market/doc.go` and `grep -n "§6\|section 6" internal/engine/market/doc.go` and `grep -n "I\.3\|static import price" internal/engine/market/doc.go` all match, and all nine commodity names appear.
- **AC-16.** `data/market.json` carries a `$comment`/`meta` block citing §6/I.3 and documenting, for every commodity, its unit of measure (kg/L/kWh/tonne, matching §17's units where the commodity overlaps a utility) and confirms the price is expressed in int64 micro-pounds per that unit — so a downstream consumer never has to guess whether a figure is £/kg, £/L, or £/tonne. Check: `grep -n "\$comment\|\"meta\"" data/market.json` matches and the per-commodity unit-of-measure is stated explicitly for all nine commodities, mirroring `engine.season`'s AC-18 fence-post-error caution applied to unit ambiguity instead of month-indexing.

## Out of scope

- Dynamic/supply-demand-driven pricing itself — this item only establishes the static v1 value and the config-flip seam (AC-4); implementing the second pricing mode is future work per I.3.
- Local production mechanics (capex, land, jobs, input-commodity chains) for any hybrid/locally-producible commodity — that belongs to the modules that will actually build things (`engine.build`, `engine.firms`, and future farming/mining/power modules); this item only tags a commodity's supply mode (AC-3), it does not implement production.
- The JIT queue/day-tick resolution (stock draws, replenishment orders, safety buffers, junction/port/rail slot allocation itself per §8) — that is `engine.logistics` (MOD-025, open, blocked on nothing but not yet built); this item only exposes a capacity-bounded availability figure for logistics to consume (AC-5).
- Non-tradable services (§10) — explicitly excluded from the commodity registry (AC-7); services capacity/coverage/funding is a separate later system.
- The Service Capacity Export "surplus book" mechanic (§36 — selling spare service capacity off-map) — that is a different, service-side export mechanism, not this item's commodity-import Market.
- Freight/tonnage production-chain mechanics (raw→intermediate→commodity, §33/§45) — `engine.freight` (MOD-047, a registered consumer) builds on Market's commodity prices but this item does not model production chains itself.

## Escalations

- **Assumption flagged (per BA instructions §3) — ASM-189 (gas as a ninth commodity).** §6's commodity table (lines 193-202) lists eight rows and does not give Gas its own row (Power's row folds in "gas CCGT" only as a local-production option for Power). MOD-020's own BOW description, however, explicitly names "water, power, **gas**, food staple/fresh, fuel, materials, goods, waste" as nine items, and §17/§2.2 independently describe gas as a fourth, separately-networked utility with its own off-map pipeline/LNG import channel — structurally identical to how Power has its own off-map Sellindge connection. I have resolved this in favour of treating Gas as the ninth, distinct commodity (AC-2/AC-3), since that is what the BOW item itself asks for and §17/§2.2 give it a real, separate import channel. If Bill intended §6's literal eight-row table to be authoritative instead (Gas folded under Power), AC-2/AC-3/AC-15/AC-16 all need a one-commodity trim. Logged as ASM below.
- **Assumption flagged — ASM-190 (waste export-price interface shape).** §6 states Waste is a "negative commodity" but does not specify the exact interface shape for how its cost is queried (a distinct method vs. a documented sign/semantics on the same `Price` method). AC-6 requires the distinction be a real, testable code path but leaves the exact shape (`ExportPrice` vs. a documented negative-price convention on `Price`) to the developer, consistent with "e.g." being illustrative there. Logged as ASM below since the requirement that a *distinct, checkable path* exist at all is my addition, not spec text.
- **Assumption flagged — ASM-191 (Market/logistics scope boundary).** MOD-020's description says imports consume "logistics capacity in tonnes/slots" but MOD-025 (`engine.logistics`, the module that would own the live capacity ledger and JIT queue) is a separate, currently-open, later item. I have drawn the boundary at: Market exposes a capacity-bounded *query* (AC-5) sourced from configured ceilings in its own data, while the live consumption/queueing of that capacity across a running simulation is `engine.logistics`'s job. This is a scope-drawing assumption, not a spec-stated boundary — if Bill wants Market to own the live capacity ledger itself (with `engine.logistics` only queuing against it), AC-5 and this item's Scope section need revision.
- **For Bill.** This item is P0, dependency-free (`MOD-006`/`MOD-012` both `done`), and next in the S3 queue per its own BOW record — no blocking escalation to raise beyond the three assumptions above.

## Spec-fold amendments (FEAT-084 SF wave, 2026-08-27)

### ASM-486 — nine-commodity registry is domestic-only (new AC-17)

- **AC-17 (international board is not an extension of this registry).** This module's commodity registry remains exactly the nine domestic needs-commodities AC-2 names (water, power, gas, food-staples, food-fresh, fuel, construction materials, consumer goods, waste). Ores, metals, chemicals, and pharma products are **not** added here. The international/world-price board is `feat.commoditymarket`'s own surface; that feature already has a registered outbound edge to `MarketAPI` and consumes it for money representation and domestic input prices only. Check: AC-2's count-and-named-lookup test still asserts exactly nine; `grep -nE "copper|uranium|pharma|plastic" internal/engine/market/*.go` (excluding `_test.go` and spec-citing comments) finds no new commodity cases (`grep -rn "func Test.*[Nn]ineCommodit" internal/engine/market/*_test.go`). **False-pass:** appending ores to `CommodityType` and still grepping for "MarketAPI exists".

### ASM-489 — static v1 price; no dynamic world market on MarketAPI (new AC-18)

- **AC-18 (always-on floor/ceiling is not this module's dynamic market).** `Price` remains the static v1 data-driven value AC-4 already requires. A dynamic supply/demand world price is out of scope for `engine.market` (I.3; §16 shelved). This AC does not specify `feat.commoditymarket`'s `WorldPrice` implementation. Check: AC-4's identical-repeat `Price()` test still holds; `go doc ./internal/engine/market MarketAPI` shows no `DynamicPrice`/`WorldPrice` method on this interface. **False-pass:** a config flag named "dynamic" that does not change behaviour, or a world-price method added onto `MarketAPI` that would collapse the two surfaces AC-17 keeps apart.
