## North-star vetting (dev-team-process.md v1.12 BA mandate)

This item answers **question 5 (long bet)** primarily, and **question 1 (conflicting demand)** as a direct consequence of the design decision below:

- **Q5, directly — this is the item the design brief names for it.** §10's own north-star check calls out "survey speculation, tile purchase on unproven ground" as a worked Q5 example, and `feat.resourcedeposits.md`'s North-star section already frames the fixed, never-reshuffled deposit map as existing precisely so a player can bet on it before it is fully known. A free-full-knowledge overlay would delete that bet entirely — there would be nothing to stretch for, only a fact to read. The progression model (Design decision, below) is what makes Q5 real for this system rather than aspirational.
- **Q1, as a consequence.** Once surveying costs money (Design decision), the overlay creates a genuine new claim on the pie: capital spent proving ground you might not develop for years competes directly with capital spent on the extraction, refinement, or unrelated civic spend the same turn could fund. A free overlay sharpens no demand — it's a UI toggle. A paid, tiered overlay sharpens the same capex-hungry-extraction-vs-everything-else demand §10 Q1 already names for the parent system, at the specific moment of "do I even find out what's here."
- **Q3, inherited, not sharpened here.** A bad survey call (spending on a tile that turns out barren, or skipping a survey and buying blind) is a consequence that sticks per the parent system's Q3 answer — this item's contribution is only that the *information itself* is priced and tiered, so the consequence has something to attach to.

## Design decision — survey is a progression, not free knowledge

**The brief explicitly defers this to the BA** ("Design question for the BA: whether full deposit knowledge is free or surveying is itself a progression"). Resolved: **surveying is a progression — prospect → survey → proven reserves — not free full knowledge.** Three knowledge tiers, cumulative, per cell:

1. **Unsurveyed (default).** No resource-overlay content rendered for the cell, even though a deposit record may already exist underneath it (per `feat.resourcedeposits.md` AC-9, deposits are placed at world-gen across the full owned-and-unowned extent, before any purchase or survey). This is the state every cell starts in.
2. **Prospected.** Reuses `engine.world`'s existing `Prospect`/`IsProspected` geology-reveal gate (`engine.world.md`) — **this file does not invent a second, resource-specific prospecting mechanic.** Prospecting reveals only the underlying geology classification (chalk/clay/sand-gravel/deep-coal-eastern), which lets a player reason informally about likely co-located resources (per `feat.resourcedeposits.md` AC-5's "uranium doesn't sit in the chalk") without the overlay stating a deposit type or size directly.
3. **Surveyed.** A new, paid, player-triggered action this feature owns: reveals the deposit's type exactly, but its size/depth as a **bounded estimate range** around the true value, not the exact scalar — modelling "yield variance against survey estimates" (§5) as a real, checkable feature of the overlay rather than a narrative line. Costs money (GR#15 data-sourced, balance-pending — see Escalations), so choosing to survey a tile is itself a Q1 spend decision.
4. **Proven reserves.** Reached only once an extraction structure is actually sited on the cell (`feat.extraction`/FEAT-051's scope, not built yet) — at that point the exact deposit record (`feat.resourcedeposits.md` AC-1's `DepositAt` values) is known with full confidence, matching the real-world sense in which "proven reserves" means confirmed by drilling/production, not estimated from a survey.

**Why this call, not free knowledge:** (a) the brief's own wording — "squeezed, never ambushed, but you *pay* to see underground" — is a direct instruction, not a hint; a free overlay contradicts "pay" outright. (b) It is the only reading consistent with §5's risk ladder, which names "yield variance against survey estimates" as a real industrial-tier risk — that sentence presupposes surveys are estimates, distinct from ground truth, which requires a tiered model to be true at all. (c) It is the only reading consistent with the sibling `feat.resourcedeposits.md`'s own North-star section, already written this session, which frames FEAT-050 as "survey progression" and treats pre-proven-reserve purchase as the Q5 stretch bet — free knowledge would falsify a claim the sibling document already treats as settled. (d) Free knowledge would make this item answer none of the five questions (per §10's own worked classification of "necessary infrastructure" items), which the brief's author explicitly did not intend by naming a design *question* rather than stating "the overlay just shows everything."

## Scope

The resource overlay's rendering in the F1 overlay cycle, its three-tier (prospected/surveyed/proven) knowledge model as consumed and displayed, and the surveyed-tier's bounded-estimate rendering. Does **not** include: the deposit model or seeded shuffle itself (FEAT-049 — this item only renders what that item produces, gated by tier); `engine.world`'s `Prospect`/`IsProspected` mechanic (already exists — this item only consumes it for Tier 2 gating); F1's general overlay-cycle machinery, minimap, pan, inspect, or follow (`ui.screen.map.md`/FEAT-005 — this item adds one overlay to an existing cycle, it does not rebuild the cycle); the extraction structure siting that unlocks Tier 4 proven reserves (`feat.extraction`/FEAT-051 — out of scope, this file only defines the tier's rendering contract so FEAT-051 has something to trigger into); survey cost balance numbers (Escalations); the finance-ledger debit mechanics for the survey action's cost (existing `engine.finance` surface, consumed not built here).

## Acceptance criteria

### Functional — overlay-cycle integration

- **AC-1 (extends `ui.screen.map.md` AC-3's overlay list; does not restate its cycle mechanics).** The resource overlay is added to F1's existing `o`/`O` overlay cycle as one additional entry, alongside ownership/land value/zoning/utilities/traffic/pollution/decay/coverage/parking/vitality. Check: `go doc ./internal/ui/screens/map` shows the overlay enum with one more entry than `ui.screen.map.md` AC-3's baseline list; the existing full-cycle test (`ui.screen.map.md` AC-3's "N steps returns to start" check) still passes with `N` incremented by exactly one — a passing test specific to this file asserts the resource overlay is reachable by cycling and that cycling past it returns to ownership (`grep -rn "func Test.*[Rr]esourceOverlay.*[Cc]ycle" internal/ui/screens/map/*_test.go`).
- **AC-2 (carries forward `ui.screen.map.md` AC-4's two-layer rule; does not restate it).** The resource overlay renders as a background-colour heatmap layer keyed to deposit type/tier while the foreground glyph continues to show structure/terrain unchanged — a passing test asserts switching to/from the resource overlay changes only background colour data for cells whose terrain/structure state is unchanged (`grep -rn "func Test.*[Rr]esourceOverlay.*[Ff]oreground" internal/ui/screens/map/*_test.go`).

### Functional — the three-tier knowledge model (Design decision, above)

- **AC-3 (Tier 1, default state).** A cell with a real, non-nil deposit record (per `feat.resourcedeposits.md` AC-9, deposits exist under unowned/unsurveyed tiles from world-gen) renders with NO resource-overlay content — neutral background — while its tier is "unsurveyed". Check: a passing test seeds a fixture cell with a known non-nil deposit record, sets tier explicitly to unsurveyed, and asserts the overlay's rendered background colour/glyph for that cell is indistinguishable from a genuinely barren cell at the same tier (`grep -rn "func Test.*[Uu]nsurveyed.*[Nn]oReveal" internal/ui/screens/map/*_test.go`) — this is the assertion a "the overlay just shows the deposit model" implementation would fail, which is exactly the free-knowledge reading this file rejects.
- **AC-4 (Tier 2, prospected — reuses `engine.world`, does not duplicate it).** The overlay's "prospected" gate reads `engine.world`'s real `IsProspected` query directly; a prospected-but-not-surveyed cell renders geology-derived colour/texture only (no deposit type, size, or depth) — the same content `engine.world.md`'s own geology layer already exposes, not a second copy. Check: `grep -rn "world\.(Prospect|IsProspected)" internal/ui/screens/map/*.go` (excluding `_test.go`) shows a call into the real `engine.world` surface; `grep -rn "func.*[Pp]rospect" internal/ui/screens/map/*.go` (excluding `_test.go` and the above call) finds no locally-reimplemented prospect/reveal function.
- **AC-5 (Tier 3, surveyed — exact type, estimated size/depth).** A cell at "surveyed" tier renders its deposit's TYPE exactly (matching `feat.resourcedeposits.md` AC-1's `DepositAt` type field) but its SIZE and DEPTH as a bounded estimate range (min/max), not the exact scalar. Check: a passing test seeds a representative sample of deposit records, transitions each to "surveyed" tier, and asserts (a) the rendered type always equals the true `DepositAt` type, (b) the rendered size/depth range always CONTAINS the true `DepositAt` value, and (c) the rendered range is never a zero-width range equal to the true value (proving it is a genuine estimate, not ground truth relabelled) (`grep -rn "func Test.*[Ss]urveyEstimate.*[Bb]ounded" internal/ui/screens/map/*_test.go`).
- **AC-6 (Tier 3 entry — a paid, player-triggered command, not automatic or free).** Transitioning a cell from "prospected" to "surveyed" requires an explicit player command (a new F1 key binding or menu action) that debits a cost from the existing finance surface before the tier changes; the tier never advances to "surveyed" as a side effect of prospecting, panning, or inspecting. Check: a passing test asserts issuing the survey command against a sufficiently-funded fixture both changes the tier AND records a matching finance debit in the same transaction (`grep -rn "func Test.*[Ss]urveyCommand.*[Dd]ebit" internal/ui/screens/map/*_test.go`); a companion test asserts merely panning/inspecting/prospecting the same cell does NOT change its tier.
- **AC-7 (Tier 4, proven reserves — forward contract for `feat.extraction`/FEAT-051, not built here).** The overlay's tier enum includes a fourth "proven" value whose rendering shows the deposit's EXACT type/size/depth (matching `feat.resourcedeposits.md` AC-1's `DepositAt` values with no estimate band), even though nothing in this feature's own scope can currently drive a cell into that tier (FEAT-051's extraction-siting scope). Check: `go doc ./internal/ui/screens/map` shows a 4-value tier enum (unsurveyed/prospected/surveyed/proven); a passing test forces a fixture cell directly to "proven" tier and asserts the rendered values equal the true `DepositAt` values exactly, with no estimate-range rendering path taken (`grep -rn "func Test.*[Pp]rovenReserve" internal/ui/screens/map/*_test.go`).

### Error handling

- **AC-8 (GR#7 — insufficient funds for the survey command).** Issuing the survey command (AC-6) against a cell when the player's finance balance is insufficient for the data-sourced survey cost produces a registry-sourced error (new `MET-E`-range code) and the tier does NOT advance and no funds are debited. Check: `grep -n "MET-" internal/ui/screens/map/*.go` finds a registry code reference in the survey-command path; a passing test asserts the returned error's registry code matches the claimed `MET-E` code AND that the cell's tier is unchanged AND the finance balance is unchanged after the rejected attempt (`grep -rn "func Test.*[Ii]nsufficientFunds.*[Ss]urvey" internal/ui/screens/map/*_test.go`).
- **AC-9 (GR#7 — re-surveying an already-proven cell).** Issuing the survey command against a cell already at "proven" tier (AC-7 — already fully known with no estimate band to improve on) is rejected with a registry-sourced error (a second, distinct `MET-E`-range code from AC-8) rather than silently charging the player again for information the overlay already renders exactly. Check: `grep -n "MET-" internal/ui/screens/map/*.go` finds a second, distinct registry code for this path; a passing test asserts the specific code returned and that no funds are debited for the rejected re-survey (`grep -rn "func Test.*[Rr]edundantSurvey\|func Test.*[Aa]lreadyProven" internal/ui/screens/map/*_test.go`).

- **AC-10 (carries forward `ui.screen.map.md` AC-10's purity rule).** The resource overlay's rendering is a pure function of (deposit record, per-cell tier state, viewport position) — no `time.Now()`-driven content. `grep -rn "time.Now" internal/ui/screens/map/*.go` (excluding `_test.go` and the shared 300ms threshold-pulse primitive already exempted by `ui.screen.map.md` AC-10) returns no additional matches attributable to this feature's own files.

## Escalations

- **For Bill (dependency/ownership gap).** This file's Tier 2/3/4 model requires a mutable per-cell "knowledge tier" field and a survey command with a write path into engine state — but code.json's registered `deps`/`calls` for `feat.resourcesurvey` list only `ui.screen.map` and `feat.resourcedeposits` (both read-side: screen framework and deposit data). Neither is a natural owner for mutable survey-progression state or the finance-debiting command. The natural home is `engine.mining` (MOD-046, already shares `feat.resourcedeposits.md`'s package and already owns the geology-gated reveal mechanism per that file's US-5), but it is not currently a registered dependency of this item. Recommend registering `engine.mining` as an explicit dependency (and, if the survey command needs a new `int.protocol` command surface distinct from the existing view-subscription pattern, a small `INT-0xx` addition) before a developer is dispatched — mirrors `feat.resourcedeposits.md`'s own Ben escalation about `MOD-046`'s gating.
- **For Aaron (balance number, per the Balance number regime — do not re-interview, cite this note).** The survey command's cost, the surveyed-tier estimate band's width (how imprecise a "survey estimate" is relative to the true value), and any per-tier-transition costs are spec-qualitative ("pay to see underground") not spec-numeric. Per the established Balance number regime (placeholder + directional tests + delegated proposal + row-by-row approval + balance pass), this file's ACs check presence/direction/boundedness only (AC-5's "contains but never equals" shape, AC-6's "some cost, whatever it is, is actually debited"), never a specific numeric target. A developer building to this file should propose placeholder values and file the balance pass separately.
- **For the QA/independent audit pass.** AC-5's bounded-estimate check is a statistical assertion over a seed sample (not a single-seed exact-equality check) — worth an independent sanity check on sample size and estimate-band-width choice once implemented, mirroring `feat.resourcedeposits.md`'s own escalation about its AC-5/AC-7 statistical checks' flake risk.
