# Acceptance criteria — secure-by-default Go helper primitives (FEAT-135)

**BOW code:** FEAT-135 (P2, open) — "Standardize Secure-by-Default Go Helper Libraries for Input Validation and Encapsulation"
**Provenance:** `docs/planning/proposals/meta-tooling-reform.md` §A1 ("secure-by-default Go helpers — additive, no reversal"), fed by Ben's independent audit (FEAT-135 filed alongside BUG-243…247).
**Spec refs / evidence anchors:** SEC-093 (NaN funding accepted silently, `engine.services`), SEC-080 (int64 XP overflow to negative, `engine.unlocks`), SEC-066 (live keymap/layout-profile pointers returned with no defensive copy, `ui.screen.menu`), SEC-062 (nested slices returned that alias internal screen state, `ui.screen.proj`), SEC-020 (copyable mutex-bearing structs with aliased reference fields — nine types, one class; astgate is the standing mechanical control, BUG-024).
**Date:** 2026-08-16
**Status:** draft-ahead — no code dispatch until Bill final-review freezes scope (see Escalations: module registration and wrapper-home are unresolved).
**Packages under test:** `internal/foundation/num/` (scope item 1) and `internal/foundation/registry/` (scope item 2), plus `.claude/commands/brief.md` + `.claude/commands/safe-module.md` (scope item 3). Confirm exact paths via `node claude-bow.js show FEAT-135` at dispatch.
**Standard gates:** see `README.md` — package(s) for SG-4/SG-7 are `./internal/foundation/num/...` and `./internal/foundation/registry/...`.

## Design-north-star framing (applied, not decorative)

FEAT-135 is pure infrastructure: a shared library plus a brief-template mandate. It answers **none** of `design-north-star.md`'s five questions (it sharpens no player-facing demand, the player gives up nothing, nothing sticks or snowballs, and no long bet can be made on it). That is an honest classification, not a failure to qualify — same footing as `feat.helper.md`'s framing. The ACs below exist to stop the library from *doing its job badly*, not to score the feature. Because it is infrastructure, it must not crowd out game code (v1.11 game-first priority): it is deliberately scoped to "add a library + a mandate", not "migrate every existing module".

## User stories

- **US-1.** As an incoming **junior developer** opening a new `internal/` package, I need one sanctioned set of helpers for numeric coercion, copy-guarding, and defensive copies, so I stop writing the insecure patterns (`int64(float64(...))`, hand-rolled `checkNotCopied`, live-pointer accessors) that the Destructive agent keeps rejecting as SEC-020/062/066/080/093.
- **US-2.** As the **lead (Bill)** and the **Testers**, I need the `/brief` mandatory block to name *real, shipped* helpers — not phantom names a junior then can't import — so the mandate is executable, not aspirational (the BUG-075 phantom-citation class applied to our own template).
- **US-3.** As a **Destructive agent**, I need the shared copy-guard and defensive-copy wrappers to be shaped so the standing astgate gate (SEC-020 class) still sees the guard, so "centralize the boilerplate" does not silently reopen the class it exists to close.
- **US-4 (GR#3 / GR#20).** As **QA**, I need `foundation/num` and `foundation/registry` to be genuinely registered modules with GUIDs in `code.json`, not informally-agreed Go packages that a future developer forks a parallel copy of.

## Scope

**In scope (per proposal A1):**
1. **Type-safe coercion in `foundation/num`:** the sanctioned `safeInt64` float→int64 coercion and a bounded + NaN-checked float helper, made the *only* sanctioned path (the existing `SatAdd`/`SatSub`/`SafeMul`/`ClampInt64FromFloat`/`IsFinite`/`GuardFinite` already cover most of this — this item canonicalizes the names the skills will cite and closes the two genuinely-missing helpers).
2. **Copy-guard + defensive-copy wrappers in `foundation/registry`:** centralize the `checkNotCopied` + `atomic.Pointer` identity-check boilerplate (SEC-020 family) and a deep-copy primitive for nested-slice/map accessors (SEC-062/SEC-066 family).
3. **Mandate use in junior briefs:** the `/brief` mandatory block and the `/safe-module` template reference the *shipped* helpers by their real names.

**Out of scope (see AC-7 and Escalations):**
- Migrating any *existing* hand-rolled `checkNotCopied` site (attract/build/citizens/finance/world/errs/transport) or fixing the 42 open findings — this item "adds a library, removes nothing" (proposal A1); real migration is per-module follow-up with a BUG-032-shaped blast radius.
- Extending `tool.astgate` to recognize a new guard-call shape — the wrapper must fit the *existing* gate, not grow it.
- Any mechanical (lint/depguard/astgate-rule) enforcement of "no hand-rolled numeric helpers" beyond what the brief mandate and this item's own diff-scope check provide — a standing anti-duplication gate is a separate, larger ask.

## Acceptance criteria

### Functional — scope item 1: type-safe coercion in `foundation/num`

- **AC-1 (the sanctioned int64 coercion saturates, never wraps).** There is exactly one sanctioned `float64→int64` coercion entry point in `foundation/num` — either the existing `ClampInt64FromFloat` or a thin `SafeInt64` alias over it — and it saturates: `NaN → 0`, `+Inf` and anything at/past `float64(math.MaxInt64)` (`== 2^63`) → `math.MaxInt64`, `-Inf` and anything at/past `float64(math.MinInt64)` → `math.MinInt64`, in-range → truncation toward zero. **Check:** `go doc ./internal/foundation/num` lists the function by the exact name the skills cite (AC-8); a test drives the boundary cross-product `{float64(math.MaxInt64), float64(math.MaxInt64)+1, math.Inf(1), math.NaN(), float64(math.MinInt64), math.Inf(-1), 0, 123.9, -123.9}` through it and asserts the saturated result against a `math/big`-clamp reference (mirroring the existing `TestClampInt64FromFloatNeverWraps`). **What a lazy implementation looks like:** the sanctioned path is `int64(f)` — which wraps `2^63` into a negative value on amd64 (the exact SEC-080 shape) and passes any test that only feeds in-range inputs. **False-pass warning:** a test asserting only "returns an `int64`" or "no panic" passes a wrapping implementation; the check must assert the *saturated value* for each boundary input, not merely the absence of a crash.

- **AC-2 (bounded + NaN-checked float helper).** A bounded-float helper exists in `foundation/num` that, given `(value, lo, hi)`, returns a value guaranteed finite and inside `[lo, hi]`, with a documented NaN/±Inf policy (either reject-with-`ok=false`, or clamp to the nearer bound). This is the genuinely *new* helper — the existing `GuardFinite`/`IsFinite` check finiteness but do not bound. **Check:** `go doc ./internal/foundation/num` shows the helper; a test drives `{NaN, +Inf, -Inf, below-lo, above-hi, in-range}` and asserts the result is in `[lo, hi]` and finite, or `ok=false` for the non-finite inputs, whichever policy the doc commits to. **What a lazy implementation looks like:** a helper that returns `lo` for `value < lo` and `hi` for `value > hi` but lets `NaN`/`±Inf` through untouched (`NaN` compares false to every bound and falls straight through) — the SEC-093 "NaN funding accepted silently" shape, one helper later. **False-pass warning:** a test over only finite in-range/out-of-range values passes an implementation that is NaN-broken; the check must exercise the non-finite inputs explicitly.

- **AC-3 (no second sanctioned path is shipped — GR#3).** The deliverable introduces **zero** new saturating-arithmetic, coercion, or NaN/finiteness helper *definitions* outside `internal/foundation/num/`. "Make it the only sanctioned path" is enforced here by *not shipping a duplicate*, not by prose. **Check:** `git diff` for this item's delivery shows numeric-helper additions only under `internal/foundation/num/`; `grep -rnE "func (Sat|Safe|Clamp|Guard|IsFinite|Bounded|Bound)[A-Z]"` over the item's new non-test code outside `foundation/num` returns no new matches. **What a lazy implementation looks like:** a junior, reasoning "this module only needs one saturating add," adds a local `satAdd`/`safeAdd` — which is precisely how `foundation/num`'s own doc comment says the ad-hoc duplication (`satAddMoney`, `safeMul`, `mulDiv`) originated.

### Functional — scope item 2: copy-guard + defensive-copy wrappers in `foundation/registry`

- **AC-4 (shared copy-guard wrapper centralizes the SEC-020 machinery).** A shared copy-guard type in `foundation/registry` (e.g. `registry.CopyGuard[T]`) provides the three pieces every hand-rolled `checkNotCopied` today re-implements: (a) the `atomic.Pointer[T]` self field, (b) an arm step that stores the identity exactly once at construction (the `self.Store(this)` call), and (c) a check that returns a registry-sourced error when the passed pointer does not equal the armed identity — including the unarmed case (a bare `T{}`/`new(T)` whose arm step never ran). **Check:** `go doc ./internal/foundation/registry` shows the type and its arm/check methods; a fixture type embeds it and is armed; a test-only byte-copy (the sanctioned `unsafe.Pointer` memcpy, mirroring `sec020_test.go`'s `registryByteCopy`) is taken, and the copy's guard rejects while the original's passes — and a never-armed zero value also rejects (mirroring `TestSEC020_ZeroValue_FailsClosed_NoMuTouch`). **What a lazy implementation looks like:** a doc comment saying "callers must not copy this struct" with no runtime check — weakness pattern #1 ("an invariant stated in prose is not enforced"), the exact SEC-005 shape.

- **AC-5 (astgate compatibility — a migrated module has zero SEC-020-class findings).** The wrapper is shaped so the standing astgate gate continues to recognize guarded functions. Concretely, a module adopting the wrapper keeps a thin `func (x *T) checkNotCopied(method string) error` method that delegates to the wrapper's check, preserving astgate's literal `<value>.checkNotCopied(...)` recognition (`guardMethodName = "checkNotCopied"`, `internal/foundation/astgate/gate.go`). **Check:** `go test ./internal/foundation/astgate/... -count=1` passes; a fixture package containing a candidate type (mutex-by-value + aliasable reference field, per BUG-024 AC-1) migrated to the wrapper produces **zero** astgate violations; and a second fixture with a fully-guarded method surface but one *unguarded package-level function taking the type by parameter* is still reported (the BUG-024 AC-3/AC-9 `SetSink` blind-spot regression stays live). **What a lazy implementation looks like:** the wrapper replaces `checkNotCopied` with a `guard.Check(a, method)` call that astgate does not recognize — every migrated module then flags unguarded, and "centralize the boilerplate" has silently reopened the SEC-020 class it exists to close. **Escalation:** extending `tool.astgate`'s recognized guard shapes to cover the wrapper is out of scope (see Out of scope); the wrapper must fit the gate, not the other way round.

- **AC-6 (defensive-copy wrapper blocks nested-slice aliasing — the SEC-062/SEC-066 class).** The shared defensive-copy primitive produces a copy whose mutation does not touch internal state, *including nested elements*. **Check:** a test stores a nested slice (e.g. `[][]int` with at least one non-empty inner slice) in a guarded/owned type, returns it through the wrapper, mutates an **inner** element of the returned value, and asserts the internal state is unchanged (and vice-versa: mutating the internal state does not change the already-returned copy). **What a lazy implementation looks like:** `append([]T(nil), src...)` where `T` is itself a slice or map — a shallow copy whose top-level array is fresh but whose elements still alias the internal backing arrays, which is exactly the SEC-062 "nested slices that alias internal screen state" shape. **False-pass warning:** a test that mutates only the *outer* slice (or only a scalar element) passes a shallow copy — a shallow copy already isolates those; the check must mutate a *nested* element, which is the only thing that distinguishes a real deep copy from `append`.

- **AC-7 (the wrapper is proven against the cited findings' shapes, via fixture).** The defensive-copy wrapper is exercised against fixtures that reproduce the two findings the item cites — SEC-066's shape (a struct holding and returning a map/slice of *pointers*) and SEC-062's shape (an accessor returning nested slices) — and each is verified mutation-isolated after routing through the wrapper. **Check:** a fixture test named for each shape (`SEC-066`-shaped pointer-map and `SEC-062`-shaped nested-slice) exists and asserts the caller-mutation isolation; a BOW comment on the item records which of the *live* SEC-066/SEC-062 sites were left to a follow-up (weakness pattern #3 — "log what you left"). **What a lazy implementation looks like:** proving the wrapper only on a toy `[]int` and declaring SEC-066/SEC-062 "covered" — the pointer-map and nested-slice shapes are precisely the two the item is about, and a `[]int` proof proves neither.

### Functional — scope item 3: mandate use in junior briefs

- **AC-8 (the skills reference only shipped names — no phantom citations).** Every helper name referenced in `.claude/commands/brief.md` (mandatory block 6) and `.claude/commands/safe-module.md` resolves to an exported symbol of the *delivered* packages. Specifically, today's `num.SafeInt64()`, `num.SafeFloat64()`, and `foundation/registry`'s `noCopy` are **phantom** — none exists in the shipped packages — and must either be added under those exact names or (preferred) the skills updated to cite the shipped names (`ClampInt64FromFloat`, `GuardFinite`/`IsFinite`, the actual copy-guard type). **Check:** extract every `num.<Name>` / `registry.<Name>` / `foundation.<X>.<Name>` reference from both files and verify each resolves via `go doc ./internal/foundation/num` / `./internal/foundation/registry`; any name present in the skills but absent from `go doc` is a FAIL. **What a lazy implementation looks like:** leaving the existing phantom references in place — a junior dispatched against the mandate reads "use `num.SafeInt64()`", the import does not compile, and the mandate is silently ignored (the BUG-075 phantom-citation class, in our own template). **False-pass warning:** checking only that "block 6 exists" or that "the words safe/copy-guard appear" passes a template whose helper names are all wrong; the check must *resolve* the names.

- **AC-9 (the mandate names the three classes with their helpers — actionable, not aspirational).** The mandatory block names, minimum: (a) numeric coercion → the sanctioned `num` int64/float helper(s) (AC-1/AC-2); (b) mutex-bearing or aliasable-reference-field structs → the `registry` copy-guard wrapper (AC-4); (c) slice/map/nested-slice-returning accessors → the defensive-copy wrapper (AC-6). **Check:** the block text contains all three class→helper pairings by name. **What a lazy implementation looks like:** "use the safe helpers, don't hand-roll validation or locks" — which is the current block's tail, names nothing importable, and gives a junior nothing to grep for.

- **AC-10 (the mandate is in the compose path, and `/safe-module` agrees with it).** The FEAT-135 block remains a numbered item in `/brief`'s GATE 2 mandatory-block list (currently item 6 — not a skippable appendix), and `.claude/commands/safe-module.md` teaches the *same* shipped helpers and the *same* copy-guard pattern (the `atomic.Pointer` + `checkNotCopied` SEC-020 pattern), not a divergent `noCopy`+`Lock/Unlock` vet-marker variant that the codebase does not actually use for this class. **Check:** `brief.md` GATE 2 still lists the block in its numbered sequence; `safe-module.md`'s example imports and helper names match AC-8/AC-9's shipped set. **What a lazy implementation looks like:** fixing `brief.md` but leaving `safe-module.md`'s `num.SafeInt64()`/`noCopy` example intact — the new-module template a junior copies on day one teaches the phantom names the mandate just corrected.

### Error handling (GR#7)

- **AC-11 (one shared registry error code, not a per-module copy).** The copy-guard wrapper's rejection error is registry-sourced via a **single shared** code — reusing the existing `MET-F106`/`codeRegistryCopied` family (or one new shared code in the F-layer range) — never a fresh `ErrCopiedValue` per adopting module. **Check:** the wrapper's error construction uses `errs.New` with a `data/errors.json`-registered code; `grep` shows the item adds no new per-module copy-error code and no bare `fmt.Errorf` at a construction site (the `tool.astgate.md` AC-16 model). **What a lazy implementation looks like:** `fmt.Errorf("copied %s", method)` — no code, no correlation ID, GR#7 violated; or a wrapper that still requires each module to mint its own `ErrCopiedValue`, which is the "nine guards each solving their own flooding" shape (weakness pattern #5) applied to error codes.

### Determinism & safety (GR#21)

- **AC-12 (no race, no wall clock).** `go test ./internal/foundation/num/... ./internal/foundation/registry/... -race -count=1` passes, and the new wrapper code introduces no `time.Now()`/unseeded-RNG read on any guarded or copy path. **Check:** `grep -rn "time.Now\|rand\.\(Int\|Float\)" internal/foundation/num internal/foundation/registry` (excluding `_test.go`) finds no match on the new code (SG-7). **What a lazy implementation looks like:** a defensive-copy helper that timestamps copies, or a guard that reads a clock — a determinism leak smuggled into a "safe primitives" package that every engine module is about to be told to import.

### Documentation

- **AC-13 (the packages state the mandate, and their registration is real — GR#6/GR#20).** `foundation/num` and `foundation/registry` package doc comments state that these helpers are the **sanctioned** path (not optional alternatives), and `foundation/num` carries a module key + GUID in `code.json` — it currently has **none** (verified: no `foundation.num` key, no GUID header in `num.go`), which is a GR#6 gap that must close before the item can be the "only sanctioned path" it claims. **Check:** `go doc` package comment on each package states the mandate; `code.json` contains a registered `foundation.num` module (GUID resolvable), or the item's Escalations carry the `/register-guid` handoff for Bill with the gap not silently shipped. **What a lazy implementation looks like:** leaving `foundation.num` unregistered while telling every junior it is the mandatory import — a mandated dependency that QA's registry-consistency audit cannot trace, and a future developer's licence to fork "their own" copy because there is no single source of truth on record.

## Out of scope

- Migrating existing hand-rolled `checkNotCopied` sites or fixing any of the 42 open SEC- findings (proposal A1: "adds a library, removes nothing").
- Extending `tool.astgate` to recognize a new guard-call shape (AC-5 mandates the wrapper fit the existing gate instead).
- A standing lint/depguard/astgate rule that mechanically forbids hand-rolled numeric helpers or live-pointer accessors — a separate, larger tooling ask beyond "add a library + a mandate".
- `/ci-green`'s, `/astgate-accept`'s, or `/new-error`'s ergonomics — those are separate `tool.*` lane items in the proposal's implementation plan, not FEAT-135.

## Escalations

1. **`foundation.num` is unregistered (GR#6) — needs `/register-guid`.** The item's own centerpiece ("make `foundation/num` the only sanctioned path") has no `code.json` module key and no GUID. The brief/safe-module skills and the proposal all point juniors at it. This must be registered (or the gap formally handed to Bill) before FEAT-135 can claim to be the sanctioned path. This is also why the assumption references below use `foundation.num` as a *proposed* key.
2. **Wrapper home is a mis-fit and should be Bill's call.** Proposal A1 puts the copy-guard + defensive-copy wrappers "in `foundation/registry`" — but `foundation/registry` is the *module* registry (boot/status/health/toggle), and a generic copy-guard/defensive-copy primitive is a cross-cutting utility. A dedicated `foundation/copyguard` (or similar) package is arguably cleaner, and it would also keep the "safe primitives" surface from straddling two packages that serve unrelated consumers. The ACs above default to `foundation/registry` per the proposal but do not require it; Bill decides at `/register-guid` time.
3. **The mandate already exists and is already half-wrong.** `/brief` block 6 and `/safe-module` were written against helpers that were never shipped (`num.SafeInt64()`, `num.SafeFloat64()`, `registry.noCopy`). FEAT-135 is therefore partly a *repair* of our own template (the BUG-075 phantom-citation class), not a green-field add. AC-8/AC-10 are the direct controls; flagging so the "mandate" scope item is understood as "make the mandate true", not "write a new block".
4. **"Mandate" has no mechanical teeth in this item.** A brief-template block is a human-habit control — the exact thing the SEC-020/astgate work replaced with a gate. The proposal scopes FEAT-135 to "library + mandate" and explicitly does not ask for a standing anti-duplication lint. That is a legitimate proportionality call (v1.11), but the honest statement is: FEAT-135 does not *prevent* the next junior from hand-rolling; it makes the secure path the default and the loud one. If mechanical enforcement is wanted, that is a follow-up tooling item, not this one.

## Assumptions logged (process v1.7)

- **ASM-881 (registration identity gap)** — FEAT-135 has a NULL mkey and `foundation.num` is unregistered in `code.json`; this file is named `feat.secureprimitives.md` following the `feat.*` convention, and both the mkey and the `foundation.num` registration are escalated to Bill's `/register-guid` rather than decided here. What breaks if wrong: the dispatch guard / `/brief` resolves the item by a different mkey and the criteria file is not found, or the mandated import stays untraceable.
- **ASM-882 (wrapper home + no-migration)** — the copy-guard/defensive-copy wrappers default to `foundation/registry` per proposal A1 (a dedicated package is escalated, not decided), and no existing hand-rolled `checkNotCopied` site is migrated in this item (library + mandate only, fixture-proven). What breaks if wrong: Bill intended a real migration or a different package, costing a mechanical rename or an under-delivery.
- **ASM-883 (astgate compatibility via thin delegate)** — the wrapper preserves astgate's literal `<value>.checkNotCopied(...)` recognition by requiring a thin per-module delegate method rather than extending `tool.astgate`'s recognized guard shapes (out of scope). What breaks if wrong: if Bill prefers extending astgate instead, migrated modules otherwise flag unguarded and the SEC-020 class reopens.
- **ASM-884 (naming canonicalization)** — the skills' phantom `num.SafeInt64()`/`num.SafeFloat64()`/`registry.noCopy` are reconciled by updating the skills to cite the shipped `ClampInt64FromFloat`/`GuardFinite`/copy-guard type, not by adding aliases under the phantom names (either direction is acceptable; the skills and the package must agree, and the ACs default to updating the skills). What breaks if wrong: if a junior instead adds `SafeInt64`/`SafeFloat64` aliases, the end state is still consistent — the risk is only the phantom references persisting.
