# Acceptance criteria — BOW description repair path + corruption guard (BUG-017)

**BOW code:** BUG-017 (P2, open)
**Spec refs:** `docs/planning/dev-team-process.md` v1.7 ("Assumptions are logged or the work is rejected" — the description field this bug is about **is** the audit record that rule depends on); Weakness pattern #1 (an unguarded repair path is exactly "a comment saying never X" — here there wasn't even a comment); the finding's own linkage to SEC-002/SEC-004 (same unescaped-interpolation root cause, third context).
**Date:** 2026-08-10
**Status:** active
**Package under test:** `claude-bow.js` (root-level tooling script; no `internal/` package — Standard Gates SG-1/SG-2/SG-3/SG-6 do not apply to this file the way they do to Go packages, see Standard gates note below).
**Standard gates:** SG-4-equivalent: `node claude-bow.js` has no existing automated test harness — the Tester's baseline for this item is the scripted CLI-invocation checks each AC specifies directly, run against a scratch/test database or a dry-run mode (Tester confirms which the junior used and that it did not corrupt the live `metro` database). SG-5 (forbidden-touch) applies as usual: only `claude-bow.js` and, for the ASM-032 repair specifically, the live database row it targets.

## User stories

- As **any agent bound by the v1.7 assumption rule**, I need a corrupted description to be repairable through the tool I'm required to use, so a shell-expansion accident doesn't leave a permanently wrong audit record with no sanctioned fix.
- As **Bill**, I need `add`/`comment`/`set` to warn when a text field looks like it swallowed command output, so the next ASM-032 is caught at write time instead of discovered later by a Tester reading the corrupted record.
- As **the record ASM-032 itself**, I need to be repaired through the tool once it exists, so the fix is dogfooded on the exact incident that motivated it, not left as a permanent scar proving the gap existed.

## Scope

`claude-bow.js set` gains `--desc` and `--title`; `add`/`comment`/`set` gain a loud (non-blocking) warning when a text field's content looks like expanded shell/command output; ASM-032's description is repaired through the new `set --desc` path as the first real use and proof the fix works.

## Acceptance criteria

### Functional

- **AC-1.** `node claude-bow.js set <CODE> --desc "<text>"` updates the item's description field and no other field. Check: run against a scratch item, `node claude-bow.js show <CODE>` before/after shows only `Desc:` changed — every other field (`priority`, `status`, `mkey`, `code-path`, `codejson`, comments, git refs) is byte-identical.
- **AC-2.** `node claude-bow.js set <CODE> --title "<text>"` updates the item's title and no other field, verified the same way as AC-1.
- **AC-3 (Pattern #4 — the trust boundary this bug is actually about).** `--desc`/`--title`/`add`'s description argument/`comment`'s text argument are **input crossing a trust boundary** the moment they are interpolated into a SQL statement or, per this bug's own root cause, arrive already-corrupted by shell expansion before Node ever sees them. Per Weakness pattern #4:
  - **(a) Privileged position it reaches:** a stored database row read back verbatim by every future `show`/`list`/`comment` call and, critically, treated as ground truth by the v1.7 audit-trail rule — i.e. it becomes *record*, not just *display text*.
  - **(b) Allowed domain, stated positively:** any UTF-8 text the tool receives as a single shell argument is accepted verbatim and stored byte-for-byte via a parameterised query (never string-concatenated SQL) — this AC does **not** ask the tool to guess whether text "looks like" a command substitution result and reject it (that would be pattern-matching prose content, which is unreliable and not this bug's fix); it asks that whatever text arrives is stored exactly, with SQL injection structurally impossible. Check: `grep -n "\\?\\|prepare\\|execute" claude-bow.js` shows `set`/`add`/`comment`'s SQL uses parameterised placeholders for every text field, never template-string interpolation of user-supplied text into the query itself (`grep -n "\`.*\\${.*desc\|\\${.*title\|\\${.*text" claude-bow.js` finds no such interpolation).
  - **(c) Rejected, not repaired, for the injection vector; but NOT for the shell-expansion content itself** — see AC-4's warning, which is deliberately advisory, not a rejection, because the tool cannot know whether "text containing a diff hunk marker" is corruption or a legitimate description of a diff. This is a documented, deliberate departure from pattern #4's default "reject" stance — logged as an assumption (see Escalations) because the alternative (rejecting anything that pattern-matches command output) would make the tool unusable for its own legitimate purpose of describing code changes.
- **AC-4 (the warning, not a guard).** `add`/`comment`/`set --desc`/`set --title` inspect the supplied text for at least these expanded-output shapes and print a loud, non-blocking warning (to stderr, so it doesn't corrupt piped stdout) when found, but still complete the write: a line matching `^Author: `, a line matching `^commit [0-9a-f]{7,40}`, a line beginning with `diff --git `, a line beginning with `+++` or `---` followed by a path, or a line matching `^@@ .* @@` (a diff hunk marker). Check: a passing test feeds each shape as `--desc` text and asserts (1) the warning is printed, (2) the item is still created/updated with that exact text (this is advisory, per AC-3(c)'s note, not a rejection).
- **AC-5 (dogfooding the fix).** ASM-032's description is repaired via `node claude-bow.js set ASM-032 --desc "<the corrected, non-corrupted text — Bill/the operator supplies the correct content, not the junior>"`. Check: `node claude-bow.js show ASM-032` shows a description with no `Author:`/`commit`/`diff --git` content in it, and a BOW comment on ASM-032 records that the repair was performed via the new `set --desc` path (not raw SQL), closing the loop the finding names as GR-discouraged today.

### Error handling

- **AC-6.** `set --desc`/`set --title` with an empty string is rejected with a clear error (`node claude-bow.js set <CODE> --desc ""` fails loudly) — an empty description is never a silent, ambiguous way to "clear" a field, since that would itself corrupt the audit record this bug exists to protect. Check: a passing test asserts a non-zero exit / thrown error and that the item's description is unchanged after the attempt.
- **AC-7.** `set --desc`/`set --title` on a non-existent `<CODE>` fails with a clear "item not found" error, consistent with every other `set` sub-flag's existing behaviour (`grep -n "not found\|Unknown code" claude-bow.js` shows the existing pattern `set` already follows for other flags; the new flags reuse it, not invent a second error shape).

### Documentation

- **AC-8.** `claude-bow.js`'s header-comment command reference (the block `README.md`/CLAUDE.md's `/bow` skill and this file both point readers to) is updated to list `set --desc`/`set --title` alongside the existing settable fields, and states the warning behaviour from AC-4, so a future agent discovers the repair path without reading the source.

## Out of scope

- A fully reliable, false-positive-free detector for "this text is corrupted" — AC-4's warning is a heuristic on known incident shapes (diff/commit-header patterns), not a guarantee; see Escalations.
- Preventing the *shell* from expanding command substitution before Node ever sees the argument — that is a caller-discipline problem (quote your arguments), and this bug's own text explicitly rules out "telling agents to quote better" as the fix, which is why the fix is a repair path plus a warning, not an input-validation reject.
- Widening this pattern to every other BOW text field beyond `desc`/`title` (e.g. comment text already has no `set` equivalent, since comments are meant to be append-only/immutable) — comments are out of scope by design, not by oversight: repairing history would itself corrupt the audit trail.

## Escalations

- **Logged as an assumption, not a spec decision:** AC-3(c)/AC-4's choice to warn-and-proceed rather than reject-on-pattern-match for shell-expansion-shaped text is a judgement call — the bug's own description says "do not solve this by telling agents to quote better," which rules out silent rejection too (a described diff genuinely might contain a `diff --git` line as legitimate content, e.g. describing this very bug). `ASM-` to be logged against `claude-bow.js` / `code.json:tool.bow` per v1.7, citing this reasoning.
- No escalation to Bill needed on the criteria themselves — the BOW description's own "Definition of done" maps directly onto AC-1/AC-4/AC-5 with no gap found.
