## User stories

- **US-1.** As the engine, I need a build-time heightmap import from OS Terrain 50, downsampled to the 200×200 10m-cell start tile per `data/georef.json`'s frozen anchor coordinates, so that Folkestone-64's real successor tile has real Kent elevation data, not a hand-drawn placeholder (§2.1).
- **US-2.** As the terrain importer, I need to implement Aaron's Option (a) artistic-compression mapping (real elevations/features preserved, true north-south distance foreshortened) exactly as `data/georef.json`'s `designDecision` specifies, so the escarpment/M20/shelf/shore layout described in §2.1 is genuinely present in-tile despite the real-world span exceeding 2km (georef-notes.md §2).
- **US-3.** As every consumer module listed in code.json (`engine.airunits`, `engine.build`, `engine.consumption`, `engine.dispatch`, `engine.farming`, `engine.finance`, `engine.logistics`, `engine.mining`, `engine.parking`, `engine.roads`, `engine.spiral`, `engine.traffic`, `engine.wellbeing`, `feat.disasters`, `feat.resourcedeposits`, `ui.screen.map`), I need a stable `WorldAPI` — cell/tile queries plus ownership mutations via commands only — so my module never reaches into world internals directly (GR#20).
- **US-4.** As `engine.mining` (a later sprint consumer), I need a geology layer (chalk everywhere; clay pockets; sand/gravel in valleys; deep coal seams in the eastern tiles) gating what can be prospected/mined where, derived from real Kent geology per §32, so mining siting is geography-driven, not arbitrary.
- **US-5.** As the hydrology system, I need real Pent/Seabrook stream lines derived from a terrain flow model over the imported heightmap, so water features are physically grounded rather than hand-placed (§2.1: "Real hydrology... derived from the terrain flow model").
- **US-6.** As the tile-expansion economy (§2.3), I need 2×2km purchasable tiles across the ~60×60km Kent extent, each carrying real terrain + a price before purchase, with only owned tiles fully simulated, so the 100M-citizen late-game arithmetic has real ground to build on.
- **US-7.** As the route-cache/memory-budget doctrine (M0-ENG §1.3), I need the world/cells/network memory region to respect its 4GB budget and be provably contents-independent for cache correctness (a cache miss changes speed, never simulation results), so world state never becomes the thing that blows the 20GB envelope.

## Scope

Build-time OS Terrain 50 import and downsample to the 10m/cell start-tile grid (per `data/georef.json`'s anchors and compression mapping), per-cell state (§2.4: elevation, slope class, surface, ownership, zoning, structure ref, land value, overlay scratch), the geology layer (§32), hydrology derivation, and 2×2km tile purchase/expansion mechanics across the ~60×60km extent (only owned tiles fully simulated).

## Acceptance criteria

### BUG-062 — re-import must be a partial (terrain-only) reset

- **AC-23 (GR#1).** Re-running `ImportAndPlaceStartTile` against an already-generated start tile preserves every non-terrain field on the existing `*tile` — ownership (`owned`, `ownerID`), zoning/owner per cell (`tl.sim.owner`/`tl.sim.zoning`), and prospected status (`prospected`) — while replacing only the terrain SoA (elevation/slope/surface). Check: a passing test constructs a `WorldAPI`, calls `ImportAndPlaceStartTile` once, `PurchaseTile`s the start tile, `Prospect`s it, and issues an `ApplyOwnershipCommand` setting a real cell's owner/zoning to non-zero/non-default values (e.g. `Owner:42, Zoning:ZoningResidential`, mirroring BUG-062's own repro), confirms `TileAt.Owned`, `IsProspected`, and the cell's `Owner`/`Zoning` all read back correctly-set, THEN calls `ImportAndPlaceStartTile` a second time (with either the same or a different fixture heightmap) and asserts **all four values are byte-identical to their pre-reimport values**, and the second call returns a **nil error** (a rejection here would itself be wrong — re-import is a legitimate, expected operation per the BOW item's own chosen contract, not an error condition).
  **What a lazy implementation looks like:** a fix that makes re-import refuse to run at all once a tile is owned (avoids the data loss by making re-import fail instead) — this passes a test that only checks "ownership survives" but fails BUG-062's own stated contract ("re-import always succeeds... refusing it outright would make a normal operation fail") and would itself need a NEW bug filed. AC-23's "second call returns nil error" clause is what catches this.
  **False-pass warning:** a test that re-imports over an UNPURCHASED, UNPROSPECTED, never-mutated tile only proves the reset path doesn't crash — it can't distinguish "ownership is correctly preserved" from "ownership was never at risk because it was already zero." The fixture must set real, distinguishable non-zero-default state on all three axes (owned/prospected/cell-owner+zoning) before re-importing, exactly as BUG-062's own repro did.
- **AC-24 (companion — the reset must still be real, GR#1).** The terrain fields themselves (elevation/slope/surface) DO change on re-import when the source heightmap differs — re-import is not a no-op disguised as a fix. Check: a passing test imports once with fixture heightmap A, records a cell's `Elevation`/`Slope`/`Surface` via `CellAt`, re-imports with a fixture heightmap B whose values differ at that cell's position, and asserts the terrain fields now reflect B, not A, while (per AC-23, checked in the same test or a shared setup) ownership/prospected/cell-owner-zoning remain A's values throughout. **What a lazy implementation looks like:** "fixing" BUG-062 by making `ImportAndPlaceStartTile`'s second call a full no-op (skip regeneration entirely once a tile exists) — this trivially passes AC-23 (nothing to preserve was ever touched) but silently breaks the importer's actual purpose (a legitimate retry/second-importer-run per the BOW item's own framing never picks up corrected/updated terrain data) and would fail AC-24's "terrain now reflects B" assertion. AC-23 and AC-24 must both pass from the SAME fixture pair to prove the fix is a partial reset, not "preserve everything" or "reset everything" — either extreme is its own bug.

### BUG-063 — bounds checking must reject Col/Row individually, before composite-index conversion
