## User stories

- **US-1.** As the engine, I need a build-time heightmap import from OS Terrain 50, downsampled to the 200×200 10m-cell start tile per `data/georef.json`'s frozen anchor coordinates, so that Folkestone-64's real successor tile has real Kent elevation data, not a hand-drawn placeholder (§2.1).
- **US-2.** As the terrain importer, I need to implement Aaron's Option (a) artistic-compression mapping (real elevations/features preserved, true north-south distance foreshortened) exactly as `data/georef.json`'s `designDecision` specifies, so the escarpment/M20/shelf/shore layout described in §2.1 is genuinely present in-tile despite the real-world span exceeding 2km (georef-notes.md §2).
- **US-3.** As every consumer module listed in code.json (`engine.build`, `engine.roads`, `engine.traffic`, `engine.mining`, `engine.farming`, `engine.finance`, `engine.logistics`, `engine.parking`, `engine.dispatch`, `engine.spiral`, `feat.disasters`, `ui.screen.map`), I need a stable `WorldAPI` — cell/tile queries plus ownership mutations via commands only — so my module never reaches into world internals directly (GR#20).
- **US-4.** As `engine.mining` (a later sprint consumer), I need a geology layer (chalk everywhere; clay pockets; sand/gravel in valleys; deep coal seams in the eastern tiles) gating what can be prospected/mined where, derived from real Kent geology per §32, so mining siting is geography-driven, not arbitrary.
- **US-5.** As the hydrology system, I need real Pent/Seabrook stream lines derived from a terrain flow model over the imported heightmap, so water features are physically grounded rather than hand-placed (§2.1: "Real hydrology... derived from the terrain flow model").
- **US-6.** As the tile-expansion economy (§2.3), I need 2×2km purchasable tiles across the ~60×60km Kent extent, each carrying real terrain + a price before purchase, with only owned tiles fully simulated, so the 100M-citizen late-game arithmetic has real ground to build on.
- **US-7.** As the route-cache/memory-budget doctrine (M0-ENG §1.3), I need the world/cells/network memory region to respect its 4GB budget and be provably contents-independent for cache correctness (a cache miss changes speed, never simulation results), so world state never becomes the thing that blows the 20GB envelope.

## Scope

Build-time OS Terrain 50 import and downsample to the 10m/cell start-tile grid (per `data/georef.json`'s anchors and compression mapping), per-cell state (§2.4: elevation, slope class, surface, ownership, zoning, structure ref, land value, overlay scratch), the geology layer (§32), hydrology derivation, and 2×2km tile purchase/expansion mechanics across the ~60×60km extent (only owned tiles fully simulated).

## Acceptance criteria

### Functional

- **AC-1 (GR#20).** A `WorldAPI` (or equivalent) exists matching code.json's inbound contract: cell/tile read queries plus ownership mutations expressed only as commands (never a direct field-set), consumed by `engine.build` and the other listed modules. Check: `go doc ./internal/engine/world WorldAPI` shows query methods (e.g. `CellAt`, `TileAt`) and a command-based mutation path (e.g. `ApplyOwnershipCommand`), not exported setters on cell/tile structs.
- **AC-2 (§2.1; georef.json).** A build-time importer reads OS Terrain 50 ASCII-grid/GML tiles (`data/georef.json`'s `source` block: 50m native post spacing, tile TR23 for the start square) and downsamples to the 200×200, 10m-cell start tile using `data/georef.json`'s `startTile` bounds (`swEasting: 620000, swNorthing: 135000, sizeM: 2000`). Check: `go doc ./internal/engine/world ImportTerrain` (or equivalent) exists; a passing test runs the importer against a fixture Terrain-50-shaped input and asserts the output grid is exactly 200×200 cells.
- **AC-3 (georef.json designDecision).** The importer applies the Option (a) artistic-compression mapping — real elevations and named features (escarpment start, M20 corridor + one grade-separated junction, buildable shelf, shoreline) are all present in-tile; true real-world north-south distances (shore-to-crest ~4.4km per georef-notes.md §2) are non-linearly compressed onto the 2km span, not simply cropped/truncated. Check: `internal/engine/world/doc.go` or `compression.go` documents the mapping function; a passing test asserts all four §2.1 features (rising ground near the north edge, a road-graph junction north of centre, a low-slope shelf band, a shoreline/sea band at the south edge) are present in the imported+compressed grid (`grep -rn "func Test.*[Cc]ompress" internal/engine/world/*_test.go`).
- **AC-4 (§2.4).** Per-cell state is exactly the documented ~30-byte-core set: elevation, slope class (flat/gentle/steep/unbuildable), surface (grass/woodland/water/shingle/rock), ownership, zoning, structure ref, land value, and per-overlay flow scratch (traffic, utility coverage, pollution, decay). Check: `go doc ./internal/engine/world Cell` lists all these fields; `grep -n "unsafe.Sizeof" internal/engine/world/*_test.go` (or a documented size comment) shows the core struct is in the ~30-byte range, excluding the variable-size overlay scratch.
- **AC-5.** Slope class is derived from the imported heightmap's local gradient and multiplies construction cost / gates building types (consumed later by `engine.build`), with the four documented classes (flat/gentle/steep/unbuildable) each having a distinct cost multiplier exposed via the API. Check: `go doc ./internal/engine/world SlopeClass` and a cost-multiplier accessor both exist; a passing test asserts a steep-slope cell returns a higher multiplier than flat (`grep -rn "func Test.*[Ss]lope" internal/engine/world/*_test.go`).
- **AC-6 (§32).** A geology layer exists per-cell (or per-region, if geology is coarser-grained than the 10m cell — documented either way) encoding at least: chalk (everywhere baseline), clay pockets, sand/gravel valleys, and deep coal seams restricted to the eastern tiles (real Betteshanger/Snowdown coalfield location, per §32). Check: `go doc ./internal/engine/world Geology` (or equivalent) exists; a passing test asserts deep coal is present in at least one eastern-tile fixture and absent from a western-tile fixture (`grep -rn "func Test.*[Gg]eology" internal/engine/world/*_test.go`).
- **AC-7 (§32).** A "revealed by prospecting" gate exists on the geology layer — mining-relevant geology is not queryable/visible through `WorldAPI` for an unprospected tile, only its presence-or-absence becomes queryable after a prospecting action runs (consumed later by `engine.mining`). Check: `go doc ./internal/engine/world` shows a `Prospect`/`IsProspected` pair; a passing test asserts geology queries return "unknown" pre-prospect and a real value post-prospect (`grep -rn "func Test.*[Pp]rospect" internal/engine/world/*_test.go`).
- **AC-8 (§2.1).** Real hydrology (Pent/Seabrook stream lines) is derived from a terrain flow model run over the imported heightmap (flow accumulation / drainage direction from elevation), not hand-authored coordinates. Check: `go doc ./internal/engine/world DeriveHydrology` (or equivalent) exists and takes the heightmap as its only input; a passing test asserts changing the input heightmap changes the derived stream path deterministically (`grep -rn "func Test.*[Hh]ydrology" internal/engine/world/*_test.go`).
- **AC-9 (§2.2).** Off-map connection anchors exist: the motorway's edge turnaround loops (traffic to/from "the world"), a purchasable grid-power connection referencing the Sellindge converter station (tranche-based capacity + standing charge + import price, consumed later by the power network), and a dormant sea/port connection. Check: `grep -n "Sellindge\|offMapConnection\|OffMap" internal/engine/world/*.go` finds these anchors modelled as world/network entry points.
- **AC-10 (§2.3).** 2×2km purchasable tiles are modelled across the ~60×60km expansion extent per `data/georef.json`'s `expansion` block (`swEasting: 590000, swNorthing: 110000` to `neEasting: 650000, neNorthing: 170000`, 36 constituent 10km OS tiles); an unowned tile exposes terrain + a price via `WorldAPI` but is not fully simulated (no per-cell overlay scratch updates) until purchased. Check: `go doc ./internal/engine/world PurchaseTile` (or equivalent) exists; a passing test asserts an unowned tile's cells are queryable (terrain, price) but a mutation command against an unowned tile is rejected (`grep -rn "func Test.*[Uu]nowned\|func Test.*[Pp]urchase" internal/engine/world/*_test.go`).
- **AC-11 (§2.3).** Tile price is a function of terrain quality, adjacency to the currently-owned city, and milestone tier — not a flat per-tile constant. Check: a passing test asserts two tiles differing only in adjacency (one bordering owned land, one not) return different prices (`grep -rn "func Test.*[Pp]rice" internal/engine/world/*_test.go`).
- **AC-12 (BOW comment obligation 3).** The real land/sea split of the 36 expansion tiles is computed programmatically against a coastline dataset/polygon at import time — not carried forward as `georef.json`'s "approximately 24-28 of 36" placeholder estimate. Check: `grep -n "coastline\|landSeaSplit" internal/engine/world/*.go` finds a real computation; a passing test asserts the computed on-land tile count for the fixture/real dataset is a concrete number, not the placeholder string.
- **AC-13 (BOW comment obligation 2).** `data/georef.json`'s anchor coordinates (start tile corners, expansion box corners, landmark grid references) are re-verified against actual downloaded OS Terrain 50 / OSTN15-transformed data rather than the ad-hoc linear interpolation the FEAT-009 research pass used (georef.json `openQuestions` item 1: J13's position was estimated ±200m). Check: `internal/engine/world/doc.go` or a `tools/terrain/verify_georef.go` records the verification result and either confirms or corrects `data/georef.json`'s `confidence` fields; if a correction is made, `data/georef.json` is updated in the same commit (SG-5 permits this path).

### Error handling

- **AC-14 (GR#7).** Importing a Terrain 50 tile that fails checksum/format validation, or a `data/georef.json` anchor that resolves outside the actual downloaded tile's extent, produces a registry-sourced error (new `MET-E`-range code) naming the tile and the discrepancy, never a silent best-effort import. Check: `grep -n "MET-" internal/engine/world/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalid.*[Tt]errain\|func Test.*[Oo]utOfExtent" internal/engine/world/*_test.go`).
- **AC-15.** A mutation command against a cell/tile the caller doesn't own (or that doesn't exist, e.g. off-extent) returns a typed rejection via `CommandResult`/`ErrorRef` (per `docs/design/protocol.md`), never a panic or silent no-op. Check: passing test coverage (`grep -rn "func Test.*[Uu]nowned.*[Rr]eject\|func Test.*[Oo]utOfBounds" internal/engine/world/*_test.go`).

### Determinism & safety

- **AC-16 (GR#21).** Importing the same OS Terrain 50 source data with the same compression mapping produces a byte-identical/hash-identical cell grid every time, and identically across worker counts (256-shard partitioning per M0-ENG §1.2, spatial for world cells). Check: a passing test imports twice (and if feasible, at two worker counts) and asserts identical output hash (`grep -rn "func Test.*[Dd]eterminis" internal/engine/world/*_test.go`).
- **AC-17 (M0-ENG §1.3).** The route cache (if implemented in this package rather than `engine.roads`/`engine.traffic`) is contents-independent for determinism — asserted by a CI test that a cache-cold run and a cache-warm run of the same query produce identical results, only differing in latency. Check: `grep -rn "func Test.*[Cc]ache.*[Dd]eterminis\|func Test.*[Cc]acheInvariant" internal/engine/world/*_test.go` finds coverage, or `doc.go` states the route cache lives entirely in `engine.roads`/`engine.traffic` and this AC is N/A for this package (state which, explicitly).
- **AC-18 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/world/*.go` (excluding `_test.go`) returns no matches — world state and its derivations (slope, geology, hydrology, tile price) are pure functions of imported terrain data and simulation tick/command inputs, never wall clock.
- **AC-19 (M0-ENG §1.2/§1.3 memory budget).** World cells + networks + route cache stay within the 4GB budget at the full 60×60km/~900-tile/~36M-cell extent, verified by a memory-accounting test/benchmark (per-cell byte size × cell count, plus network/cache estimate) rather than asserted by inspection alone. Check: `go test ./internal/engine/world/... -race -count=1 -v -run Memory` (or equivalent named test) passes and prints/asserts a total under 4GB (`grep -rn "func Test.*[Mm]emory\|func Benchmark.*Memory" internal/engine/world/*_test.go`).
- **AC-20.** `go test ./internal/engine/world/... -race -count=1` passes with no data race under the 256-fixed-shard worker pool pattern (spatial shards for cells/network per M0-ENG §1.2). Check: `grep -n "go func()" internal/engine/world/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-21.** `internal/engine/world/doc.go` states the module key `engine.world`, cites §2 (all subsections), §32, and `data/georef.json`'s designDecision, and states explicitly which BOW-comment obligations (compression mapping, OSTN15 verification, land/sea split, OGL attribution) this item closes out. Check: `grep -n "engine.world" internal/engine/world/doc.go` and `grep -n "georef" internal/engine/world/doc.go` and `grep -n "§32\|section 32" internal/engine/world/doc.go` all match.
- **AC-22 (BOW comment obligation 4).** OGL attribution wording is confirmed against the actual downloaded OS Terrain 50 licence file (not the generic web-sourced placeholder in `georef-notes.md`) and recorded in `data/georef.json`'s `source.attribution` field with the correct `[YEAR]`. Check: `grep -n "Crown copyright" data/georef.json` shows a concrete year, not `[YEAR]`, and a comment/commit note states the licence file it was verified against.

## Out of scope

- Any engine module that *consumes* `WorldAPI` (`engine.build`, `engine.roads`, `engine.traffic`, `engine.mining`, `engine.farming`, `engine.finance`, `engine.logistics`, `engine.parking`, `engine.dispatch`, `engine.spiral`, `feat.disasters`, `ui.screen.map`) — this item only provides the query/mutation surface those modules build against, per GR#20.
- Actual mining mechanics (extraction rates, subsidence, blight radius computation from the geology this item exposes) — that's `engine.mining` (Sprint 11 per the sprint plan).
- The route-cache implementation itself if it turns out to live in `engine.roads`/`engine.traffic` rather than here (AC-17 allows either placement, documented).
- Real-time terrain rendering/heatmap overlays — that is `ui.screen.map`'s job, consuming this package's data.
- GPU-accelerated terrain import — build-time import is a one-off, offline, CPU-only step; no solver-seam involvement.
