# Acceptance criteria — engine.chemicals (MOD-063)

**BOW code:** MOD-063
**Spec refs:** §50 Oils, Rubber, Plastics & the Chemical Network (`docs/METROPOLIS-MASTER-v2.1.md` lines 656-658: crude oil lands by tanker at the port (t/day, tank farm) → refinery (major build: fuel + feedstock outputs, top blight class + §26 hazmat fire category) → petrochemical works (feedstock → plastics, solvents) → plastics converters (→ consumer goods chain) and rubber (imported natural + synthetic from feedstock) → tyre plant (→ vehicle chain); distribution is a fourth pipe network — the chemical/fuel pipeline grid, port↔refinery↔works↔industrial estates, expensive per km, small inspectable leak-event risk, removes hundreds of hazardous truck movements/day (safety-vs-capex trade in F5); no refinery? import refined product at margin, the make-vs-buy doctrine [§6] at its largest scale); §26 Emergency & Care Dispatch Model (lines 408-410: unified dispatch engine — incident spawns at a cell, nearest unit assigned, travels real roads, outcome quality = f(response time); this is the hazmat-fire-category consumer the refinery cites); §32 (line 460: the blight model this module's refinery/petrochemical works register against as "heavy industry", currently unregistered — see Escalations); §33 (the freight-harbour tonnes/chain-family pattern this module's own chain-stages-as-firms structure follows); code.json `engine.chemicals` entry (inbound `ChemAPI`, pattern **"chain stages as firms; pipeline as UtilityAPI-style network"**; consumers: none registered; outbound calls `engine.freight`, `engine.consumption`, `engine.dispatch` — all three verified bidirectionally correct: `UtilityAPI`'s and `DispatchAPI`'s own inbound `consumers` lists already name `engine.chemicals`).

## User stories

- **US-1.** As the player, I need the full crude→refinery→petrochemical→plastics/rubber→tyre chain modelled as five distinct firm stages, each with its own input t/day → output t/day, jobs, and blight class, so the chain is a real production graph (matching §33's chain-family pattern), not a single "chemicals" black box.
- **US-2.** As `engine.freight` (a registered outbound dependency, MOD-047), I need crude-oil tanker landings and refined-product import/export to be ordinary freight tonnage moving through the port, so the chemical chain does not reimplement port/berth/tank-farm accounting `engine.freight` already owns.
- **US-3.** As `engine.consumption` (a registered outbound dependency via `UtilityAPI`), I need the chemical/fuel pipeline grid to reuse `UtilityAPI`'s "network solve per daily tick; coefficients from Store" pattern as its fourth network, so pipeline load/loss/capacity accounting is one shared network-solver discipline, not a bespoke one.
- **US-4.** As `engine.dispatch` (a registered outbound dependency via `DispatchAPI`), I need the refinery's top-blight-class, hazmat-fire-category status to be a real, queryable incident-risk input to the unified dispatch engine, so a refinery fire is dispatched exactly like any other fire incident (§26), not narrated separately.
- **US-5.** As the player deciding make-vs-buy, I need importing refined product at margin to be a real, always-available alternative to building the refinery chain, with a documented cost delta so the trade-off (§6's doctrine "at its largest scale") is a genuine decision, not a strictly-dominant option in either direction.
- **US-6.** As the player watching F5, I need the pipeline-vs-truck safety/capex trade to be visible: building the pipeline network measurably reduces hazardous truck movements on the road network relative to the no-pipeline case, at a documented capex/per-km cost.

## Scope

The five-stage production chain (refinery, petrochemical works, plastics converters, rubber, tyre plant) as firms with tonnage input/output, jobs, and blight class; the chemical/fuel pipeline grid as a fourth utility-style network reusing `UtilityAPI`'s solve pattern; leak-event risk (small, inspectable, maintenance-funded); the make-vs-buy import-at-margin alternative; the hazmat-fire-category input to `DispatchAPI`. Does not include `engine.freight`'s own tanker/port/tank-farm mechanics, `engine.consumption`'s network-solver internals, or `engine.dispatch`'s incident-outcome curves.

## Acceptance criteria

### Functional — the production chain

- **AC-1 (GR#20; code.json inbound contract).** A `ChemAPI` exists exposing per-stage-firm queries (input/output tonnage, jobs, blight class) and construction/routing commands, matching code.json's pattern "chain stages as firms; pipeline as UtilityAPI-style network". Check: `go doc ./internal/engine/chemicals ChemAPI` shows both a per-stage query surface and a command surface; `grep -n "func.*Build\|func.*Route" internal/engine/chemicals/*.go` confirms construction/routing are commands.
- **AC-2 (§50 five distinct stages).** Refinery, petrochemical works, plastics converters, rubber, and tyre plant are each a distinct firm type with its own documented input t/day → output t/day conversion, jobs figure, and blight class — not one blended "chemicals output" number split only at the point of consumption. Check: `go doc ./internal/engine/chemicals` shows five named stage-firm types each with input/output/jobs/blightClass fields; a passing test asserts the refinery's blight class is strictly higher than the tyre plant's (per "top blight class" applying specifically to the refinery, §50) (`grep -rn "func Test.*[Ss]tage\|func Test.*[Bb]lightClass" internal/engine/chemicals/*_test.go`). **Lazy implementation this rejects:** a single "chemical industry output" scalar with a flavour-text stage list would satisfy "the chain exists" on a shallow read while making it impossible to isolate which stage is bottlenecked or which stage is the hazmat risk — the check requires per-stage blight-class differentiation specifically because the refinery's top-blight-class/hazmat status (AC-6) is a distinct, checkable claim from the other four stages'.
- **AC-3 (§50 chain conservation — tonnage identity, mirrors `engine.refuse.md` AC-11 pattern).** For each accounting period, each stage's own tonnage identity holds independently: `StageInputConsumed == Σ(upstream stage's OutputRouted to this stage) + ImportedInput`, and `StageOutputProduced` feeds the next stage's input via the SAME independently-tracked routing figure — no stage's input is inferred as "whatever the previous stage happened to produce" without an explicit routed-tonnage figure that could, in principle, diverge (e.g. spoilage, routing loss, stockpiling). Check: a passing test runs a five-stage chain for several ticks with a documented routing-loss factor and asserts each stage's independently-tracked consumed/produced/routed tonnage is internally consistent to a documented epsilon (`grep -rn "func Test.*[Cc]hainTonnage\|func Test.*[Ss]tageConserv" internal/engine/chemicals/*_test.go`). **Lazy implementation this rejects:** computing a downstream stage's input as a bare pass-through equal to the upstream stage's output (implicit 100% routing, zero loss, no independent tracking) would pass a shallow "output feeds input" check while being unable to represent routing loss, stockpiling, or a broken pipeline segment — the check requires the routed figure to be its own tracked quantity, not a derived alias.
- **AC-4 (§50 make-vs-buy — US-5).** Importing refined product at a documented per-unit margin (ASM-321, data-sourced) is available at all times as an alternative to any/all of the five domestic chain stages, and the resulting per-unit cost to the city is queryable and comparable against the domestic chain's own per-unit cost at the current utilisation/efficiency level — neither option is hardcoded to always win. Check: `go doc ./internal/engine/chemicals ImportRefinedProduct` (or equivalent) exists; a passing test asserts a city with no refinery built can still satisfy plastics/rubber/tyre-chain demand via import, at a documented cost premium over an efficient domestic chain (`grep -rn "func Test.*[Mm]akeVsBuy\|func Test.*[Ii]mport" internal/engine/chemicals/*_test.go`).

### Functional — the pipeline network

- **AC-5 (§50 pipeline as UtilityAPI-style network, GR#3 reuse — US-3).** The chemical/fuel pipeline grid reuses `engine.consumption`'s `UtilityAPI` network-solve pattern structurally — a per-daily-tick network solve with coefficients sourced from `foundation.data`'s `Store`, per code.json's own pattern string — rather than a bespoke chemicals-only network solver with independent scheduling/loss logic. Check: `grep -rn "consumption\.(Network|Solve|Utility)" internal/engine/chemicals/*.go` (excluding `_test.go`) shows the pipeline constructed through `engine.consumption`'s exported network-solve type/function, not a parallel `PipelineNetwork` type with an independently-written solve loop; a passing test asserts pipeline capacity/loss behaviour under load reproduces `engine.consumption`'s own network-solve semantics (`grep -rn "func Test.*[Pp]ipeline.*[Nn]etwork" internal/engine/chemicals/*_test.go`). **False-pass risk:** a `PipelineNetwork` type that merely LOOKS similar (same field names, "coefficients from data") but runs its own independent daily-tick solve would pass a naming grep while never actually sharing `engine.consumption`'s solver code — the check requires the reused-behaviour assertion, not just the presence of similarly-named types, exactly the same trap `engine.refuse.md` AC-4 documents for its own logistics-reuse requirement.
- **AC-6 (§50 leak-event risk, inspectable and maintenance-funded).** The pipeline carries a small, non-zero, maintenance-funding-sensitive leak-event risk (probability rises as maintenance funding falls below a documented threshold, per ASM-321) that is independently inspectable per pipeline segment (a player/ticker can query WHICH segment is at elevated risk before an event fires), distinct from a hazmat FIRE risk at the refinery stage specifically (§50's "top blight class + §26 hazmat fire category" is a refinery-stage attribute, not a pipeline-wide one). Check: `go doc ./internal/engine/chemicals` shows a per-segment leak-risk accessor separate from the refinery's hazmat-fire accessor; a passing test asserts leak-event probability rises as segment maintenance funding falls (`grep -rn "func Test.*[Ll]eak" internal/engine/chemicals/*_test.go`).
- **AC-7 (§50 pipeline-vs-truck safety/capex trade — US-6).** Building the pipeline network between the port/refinery/works/industrial estates measurably reduces hazardous freight-truck movements on the road network relative to the no-pipeline case, at a documented per-km capex cost distinct from the leak-risk/maintenance-cost of AC-6, so the F5 safety-vs-capex screen has two independently-moving numbers (fewer trucks, higher capex) rather than one flavour label. Check: a passing test compares hazardous-goods truck-movement counts (via `engine.freight`'s own movement accounting) with and without the pipeline built between the same two points, asserting the pipeline case is materially lower (`grep -rn "func Test.*[Tt]ruckReduction\|func Test.*[Pp]ipelineVsTruck" internal/engine/chemicals/*_test.go`).

### Error handling

- **AC-8 (GR#7).** Routing tonnage to a stage that doesn't exist yet (e.g. plastics converters before petrochemical works is built), or constructing a pipeline segment between two points with no valid industrial/port anchor, produces a registry-sourced error (new `MET-E`-range code) rather than a silently-created phantom stage/segment. Check: `grep -n "MET-" internal/engine/chemicals/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Mm]issingStage\|func Test.*[Ii]nvalidSegment" internal/engine/chemicals/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no phantom stage/segment was created, not merely that a matching-named test function exists.

### Determinism, safety & scale

- **AC-9 (GR#21).** Chain-stage tonnage flow, pipeline network solving, and leak-event determination are deterministic functions of `(worldSeed, tick, prior state, commands)`, byte-identical across repeated runs and worker counts. Check: `grep -rn "func Test.*[Dd]etermnis\|func Test.*[Dd]eterminis" internal/engine/chemicals/*_test.go`.
- **AC-10 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/chemicals/*.go` (excluding `_test.go`) returns no matches.
- **AC-11.** `go test ./internal/engine/chemicals/... -race -count=1` passes; `grep -n "go func()" internal/engine/chemicals/*_test.go` finds at least one concurrency test.

## Out of scope

- `engine.freight`'s own port/berth/tank-farm/crane-rate accounting — this item only *uses* freight tonnage movements for crude landings and refined-product import/export (AC-4), it does not reimplement port capacity.
- `engine.consumption`'s own network-solver implementation — this item only reuses it for the pipeline (AC-5).
- `engine.dispatch`'s own incident-outcome curves — this item only supplies the hazmat-fire-category input (AC-6) via the registered edge.
- The specific leak-event probability curve, per-unit import margin, and per-stage tonnage-conversion ratios — balance data pending M2 tuning (ASM-321).
- Registering the refinery/petrochemical-works stages themselves as `engine.mining`'s `BlightAPI`-tracked "heavy industry" blighting objects — blocked pending BUG-058 (see AC-13/Escalations); this item can compute its own internal blight-class figure (AC-2) without that registration, but cannot yet participate in the cross-module noise/viewshed model `engine.mining.md` describes.
