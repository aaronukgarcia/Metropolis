## Purpose

Turn "run this city on the cheapest sensible host" into one routine, safe, auditable command. The engine already runs anywhere a Linux amd64 container runs (a3.md). What is provider-specific is starting and stopping a city on a host. The launcher owns that, plus three things that must never be left to chance: **no paid start without Aaron's Authorise, never two writers for one city, and nothing is left billing after a stop or a failure.**

## Definitions

- **Launcher:** a command-line tool Aaron (or a session on his behalf) runs on the laptop. It starts, does its work, and exits. It is not a daemon, a service, a scheduler or a listener (GGR94: nothing long-running on the laptop).
- **Backend:** one provider adapter implementing the interface in section B. Initial set: `pix`, `aws-spot`, `gcp-spot`, `azure-aca`, and `fake` (tests only).
- **Cost class:** `free` (pix, dev) or `paid` (aws-spot, gcp-spot, azure-aca). A paid start is any call that can create or resume a billable resource. Meter host classes (feat-9995385596) map one to one: `pix`, `spot-aws`, `spot-gcp`, `azure`.
- **Size label:** A (2 vCPU / 4 GB, a 10M city), B (4 vCPU / 8 GB or 16 GiB class, up to 30M with paging), C (64 GiB class, the 100M proving run), as in a4.md.
- **Placement:** the launcher's record of which backend holds which city (section E). It is a hint; the cloud resources' own tags and the store's epoch are the truth.
- **Gate token:** the cost-gate token minted only by Aaron's explicit Authorise through `/cost-gate`, bound to one action pattern, valid 30 minutes. The launcher only ever checks one. It never mints, copies, extends or fabricates one.
- **Reclaim:** the provider's notice that a Spot instance will be taken (AWS about 2 minutes, GCP about 30 seconds).

## A. Scope and command surface

- **AC-1** The command surface is `launcher start <city>`, `stop <city>`, `status [<city>|--all]`, `move <city> --to <backend>`, and `plan <city>` (the dry-run view, AC-69). Flags: `--backend`, `--size A|B|C`, `--max-hours N`, `--dry-run`, `--region`, `--config`. Unknown commands or flags exit non-zero with usage and perform no provider call.
- **AC-2** The launcher is a short-lived process: no listener, no background goroutine that outlives a command, no scheduler, no tray or service registration. A test asserts the package opens no listening socket and starts no goroutine after `Run` returns (goleak-style check).
- **AC-3** Every command exits with a documented code: 0 success or no-op, 2 usage, 3 refused by policy or gate, 4 refused by safety (second writer risk), 5 backend failure after cleanup, 6 backend failure with cleanup NOT confirmed (resource may still bill). Exit 6 prints the resource ids prominently on stderr. Table-tested.
- **AC-4** A city key is `<tenant>/<city>` (the existing `CityKey`). The launcher validates it with the same traversal-proof rules as the store (no `..`, no separators, bounded length); an invalid key is refused before any call.
- **AC-5** The launcher never modifies engine behaviour: it only chooses a host and passes flags and environment to the same image. It imports no engine, composition or citizens package; a test asserts that no package under `internal/engine` is imported (GR#21, determinism is unaffected by where a city runs).
- **AC-6** Out of scope (stated so the review does not hunt for it): the Cloudflare Tunnel and Access set-up (FEAT-9995385599), the store (FEAT-9995385594), hibernation and drain behaviour inside the engine, any automatic or scheduled wake, arm64 hosts (FEAT-9995385602), and Alibaba (Q100165).

## B. Backend interface (GR#20: contract first)

- **AC-7** The Go interface `Backend` has exactly these methods, with the contract documented in doc comments and in `code.json` before any adapter is written: `Start(ctx, StartSpec) (Instance, error)`, `Stop(ctx, InstanceRef, StopMode) error`, `Status(ctx, CityKey) ([]Instance, error)`, `Endpoint(ctx, Instance) (URL, error)`, `CostClass() CostClass`, plus `Name() string` and `Forecast(StartSpec) (Forecast, error)` (pure, no network spend). Extra methods need an AC amendment.
- **AC-8** `Status` returns every instance this backend can see that is tagged for the city, running or not (including `stopping` and `unknown`). It is read-only and free on every backend. A backend that cannot answer returns `StatusUnknown`, never an empty list (empty must mean "checked and none").
- **AC-9** `Start` is idempotent on `StartSpec.RunID` (AC-67): a second call with the same RunID returns the existing instance. `Stop` of a non-existent instance returns success. Both are asserted against the fake and against each adapter's request-builder with recorded fixtures.
- **AC-10** `StartSpec` carries: city key, size label, image reference pinned by digest (AC-64), host class, active-hours budget, `max-hours` TTL, environment (secret values by reference only, AC-62), region, and the RunID. It carries no gate token; the gate is checked by the caller before `Start` (AC-22), and a backend refuses to run if `StartSpec.Authorised` is not set by the gate package (AC-24).
- **AC-11** `StopMode` is `graceful` (SIGTERM, wait for the final snapshot, then release the resource) or `force` (release now). `graceful` waits up to a configured deadline (default the engine's `--shutdown-snapshot-deadline` plus 15 s margin) and then falls through to `force`, logging that the snapshot outcome is unconfirmed (AC-30 for the consequence).
- **AC-12** A `fake` backend implements the interface in memory with controllable behaviour (start latency, failures at each step, a stuck stop, a pre-existing running instance, a Spot reclaim injected at a given moment) and records every call. All launcher logic is tested through it. The fake is the only backend compiled into test binaries; no unit test needs a network, a cloud credential or a laptop listener.

## C. Host selection policy

Selection is a pure function: `Select(inputs) -> ordered candidates, each with a reason`. It makes no calls itself; inputs are gathered first (AC-18).

- **AC-13** Inputs: city size (citizen count from the latest manifest, falling back to an explicit `--size`), pix reachability, pix capacity figure, run kind (`play` or `proving`), per-backend availability and live Spot price, gate status per backend, and any `--backend` override. A table test covers every row of AC-14 to AC-17.
- **AC-14** Rule 1, **pix first**: choose `pix` when the run kind is `play`, pix answers its health probe, and the city fits pix (`citizens <= PixMaxCitizens`, configuration, default 10,000,000, and the memory headroom check AC-15). pix is `free` so no gate is involved.
- **AC-15** Fits means both the citizen figure and a live headroom check: pix `/health` must report free capacity for the new city's estimated resident bytes (using the engine's own sizing figure, not a launcher constant: OQ-3). When /health cannot report it, the launcher falls back to the citizen cap alone and says so in the plan. pix hosts other tenants (TeslaMate, sign), so a refusal here is an expected outcome, not an error.
- **AC-16** Rule 2, **cheapest Spot**: when pix is down, full, or the city exceeds the cap, or the run is `proving` (100M never goes to pix), choose the cheaper of `aws-spot` and `gcp-spot` for the size label, by live Spot price at start time (AC-17) times the estimated hours. A price tie within 5 percent breaks to the region with the lower measured latency for `play`, to the lower price for `proving`. A backend with no usable capacity or no credentials is skipped with a reason.
- **AC-17** Live price comes from the provider's read-only pricing or Spot-history call (free, no gate), cached for the run only. If neither provider's price can be read, Spot is skipped for that provider; the launcher never guesses a price from a stale table. a4.md figures are test fixtures, not production inputs.
- **AC-18** Rule 3, **Azure last**: choose `azure-aca` only when no Spot candidate is available or both Spot providers are refused (capacity, credentials), and only for sizes it can host (A and B; size C is refused on Azure with `E-LAUNCH-SIZE`, since a4.md and README record no 64 GiB ACA fit). Azure is the held fallback (inc1-cost-forecast.md).
- **AC-19** Size C (the 100M proving run) is headless: it chooses by price only, in any region, and always requires the `--max-hours` TTL (AC-35). Size A and B `play` runs are restricted to regions within the latency budget (default: UK/EU for London-based play; the allowed list is configuration, OQ-6) because the 160 ms turbo budget applies.
- **AC-20** Amd64 only (Q100162): every candidate instance type and every image must be amd64. The selector refuses any arm64 type, and a test feeds it a Graviton type and an arm64 image and expects `E-LAUNCH-ARCH`.
- **AC-21** `--backend X` overrides the choice but not the safety or gate checks: a forced paid backend still needs a live token, and a forced backend that the policy would refuse for size (C on Azure, 100M on pix) is refused with the reason. The plan output always shows what the policy would have chosen.

## D. The cost gate (fail closed)

- **AC-22** Every start of a paid backend, including a restart after a reclaim, a `move` into a paid backend, a resume of a stopped instance, and the creation of any provider resource that can bill (instance, disk, IP, container app, revision), is preceded by a gate check for that exact backend pattern and size. No check, or any doubt, means refuse with exit 3 and `E-LAUNCH-GATE`. `Stop` and `Status` never need a token (stopping reduces cost).
- **AC-23** The launcher **never mints, writes, edits, extends or bypasses** a token. Its only gate operation is a read-only check (OQ-2: how). The package has no code path that writes the gate's token store; a test greps the built package's call graph for the token-writing function and asserts none is reachable. There is no `--yes`, `--force`, `--skip-gate` or environment variable that skips the check, and a test asserts the flag set contains none.
- **AC-24** The gate check returns a typed `Authorised` value only from the gate package; `Backend.Start` rejects a spec without it (AC-10). A test calls a paid backend's `Start` directly with a hand-built spec and asserts a refusal, so a future caller cannot forget the check.
- **AC-25** The check is fail-closed on every ambiguity: gate tool missing, unreadable, timed out, output unparsable, token expired, token bound to a different pattern or backend, token past its 30 minutes at the moment of the provider call (not only at command start). Each case has its own test with the fake gate and ends with **zero** provider mutations recorded on the fake backend.
- **AC-26** The token is re-checked immediately before each mutating provider call, not once per command. A command that begins inside the 30-minute window but whose first paid call lands after expiry refuses at that call, having created nothing.
- **AC-27** Forecast before Authorise: `plan` and a `start` that finds no live token print the forecast the `/cost-gate` skill needs (backend, region, instance type, price seen, hours, worst-case at the `--max-hours` TTL, payment instrument, the pattern string) and exit 3. They do not call the skill, prompt, or wait; Aaron runs `/cost-gate` himself and re-runs `start`. The forecast text is deterministic for the same inputs.
- **AC-28** A token authorises one action pattern. A single `start` may create several billable resources only if they all fall inside the pattern named in the forecast; the launcher lists them in the plan, and a resource outside the pattern refuses the whole start before any creation (all-or-nothing preflight, not a mid-way refusal).
- **AC-29** Money spent while no token is live is impossible by construction, not by hope: the **dead-man TTL** (AC-35) applies to every paid resource so a launcher crash after creation cannot bill past the TTL even if no further launcher command ever runs.
- **AC-30** Reclaim and restart: when a Spot city is reclaimed, the city is safe in the store (or, if the 20 s budget was missed, at the previous snapshot plus journal). The launcher does **not** restart it on a paid backend without a live token. With no token the city simply stays down, `status` shows `reclaimed, awaiting authorise`, and the forecast for the next paid start is printed. If pix is up and the city fits, `start` can place it there at no cost.
- **AC-31** The launcher's own enforcement is independent of the Claude-session cost-gate hook. The hook only guards shell calls made by Claude sessions; Aaron may run the launcher by hand, from a script, or via another tool, and the check in AC-22 holds in all of those. A test runs the launcher with the hook environment absent.
- **AC-32** Each paid start logs the gate token's identifier (never its secret), the pattern, the forecast and the actual resources created, so spend can be reconciled against Authorise (AC-53).
- **AC-33** A paid start whose readiness check fails (AC-50) stops and releases what it created before exiting, and that cleanup does not need a token. If cleanup cannot be confirmed the exit is 6 with the ids.

## E. Single-writer safety across hosts

The store's writer epoch with conditional writes is the real fence (Q100159, inc2). The launcher is a second line, never a replacement.

- **AC-34** Before any `Start`, for the target backend and for every other backend, the launcher calls `Status(city)`. If **any** instance is running, starting, stopping or `StatusUnknown` for the city anywhere, a new start is refused with exit 4 and `E-LAUNCH-WRITER-EXISTS`, naming the instance. `StatusUnknown` is treated as "possibly running" (fail closed).
- **AC-35** Every paid instance is created with a dead-man TTL (the `--max-hours` value, default from config, never unlimited): the VM or app terminates itself at that time regardless of the launcher (instance-initiated terminate on shutdown, a `shutdown -h +N` in the startup script, or the provider's max-run feature). A paid start with no TTL, or a TTL above the configured ceiling, is refused. A test asserts every `StartSpec` produced for every paid backend carries one.
- **AC-36** The launcher never kills a running writer on its own initiative. If it finds one (AC-34), it reports where it is and its age, and suggests `launcher stop` or `launcher move`. It exits without changing anything.
- **AC-37** `move <city> --to B` is the only multi-step operation and runs strictly in this order: (1) gate check for B (if paid) with nothing created; (2) `graceful` Stop on the current backend; (3) wait until the current instance is confirmed gone **and** the store shows a clean final snapshot (manifest newer than the last journal position or the engine's own clean-shutdown marker); (4) only then Start on B. If step 3 cannot be confirmed within the deadline the move aborts with exit 4 and does not start B (the city stays down, safe in the store). A test with the fake injects each failure in each step and asserts B is never started while the old instance is alive or unconfirmed.
- **AC-38** Zombie writer: given a writer that survives the stop (a hung process, a partitioned VM), When the new instance starts and takes the next writer epoch, Then the zombie's next conditional write fails with `E-WRITER-FENCED` and it stops. The launcher does not rely on this: it treats a still-answering old instance as a refusal at AC-34. A test with a two-writer fake store (FEAT-9995385594's conformance fake) asserts the old writer is fenced and no committed record is lost.
- **AC-39** The launcher reads the store read-only to learn the city's size, latest snapshot and epoch (AC-13, AC-37). It never writes city data, snapshots, manifests or journal objects. The only thing it may write to the store is its placement hint (AC-40).
- **AC-40** Placement hint: after a successful start the launcher writes `{city, backend, instance id, host class, region, started at, runId, tokenId}` as a host-scoped record (the same store mechanism the meter uses, feat-9995385596 AC-11) with a compare-and-swap. Before trusting it, `status` cross-checks the hint against live `Status` results; on disagreement the live result wins and a `placement-drift` warning is printed. A lost CAS is an error, never an overwrite.
- **AC-41** Two launcher invocations racing for one city (two terminals, a retry plus a manual start): exactly one proceeds; the other exits 4. Mutual exclusion is the CAS on the placement record plus the AC-34 sweep; a race test runs 16 concurrent starts against the fake and asserts exactly one instance exists afterwards. (No local lock file is relied on, because the launcher can run on a different machine.)
- **AC-42** The launcher cannot know whether a process on pix started outside it (the SAFE route `docker --context pix compose ...`, a manual `docker run`). The pix adapter's `Status` therefore asks the container runtime and the engine's `/health` for loaded cities, not only its own records, so a city already served by pix is found by AC-34.

## F. Wake, drain and the active-hours meter

- **AC-43** The launcher sets the meter's flags on every start from its own per-class configuration and from nothing else: `-host-class` (`pix`, `azure`, `spot-aws`, `spot-gcp`) and `-active-hours-budget` for the metered classes (feat-9995385596 AC-22, AC-27). A paid start with no configured budget is refused with `E-LAUNCH-CONFIG`, mirroring the engine's refusal (AC-23 of the meter) so the failure shows before anything is created.
- **AC-44** The launcher passes the hibernation and drain flags the engine defines (`--scale-to-zero-after` on paid classes, disabled on `pix`; `--shutdown-snapshot-deadline` 20 s; idle threshold) from configuration, not literals (feat-9995385595 AC-8, AC-25, feat-9995385597 AC-D7). Defaults live in the launcher's example config and are asserted by a golden test so a drift is visible in review.
- **AC-45** Scale-to-zero by self-exit (feat-9995385595 OQ-5) means a paid VM that has no loaded city exits the process. The launcher's VM bootstrap treats that exit as the signal to release the instance (terminate on process exit), so an idle Spot VM or ACA replica stops billing without any laptop involvement. A test of the bootstrap script (a pure generator, golden-file tested) asserts the terminate-on-exit wiring. On pix the process stays up and the launcher does nothing.
- **AC-46** `stop` and `reclaim` use the engine's SIGTERM path (drain, final snapshot, release) with the reasons `host-drain` (feat-9995385595 AC-28, feat-9995385597 AC-D1). The launcher never kills the process before the graceful deadline unless `StopMode` is `force`.
- **AC-47** The launcher has no automatic wake. A city that hibernated and whose host exited stays down until someone runs `launcher start` (OQ-4). `start` is always the human act that also supplies the gate token. On pix a hibernated city wakes on connect with no launcher (the process is up). The launcher documents this in its `--help` and in `status` output (`asleep: run launcher start`).
- **AC-48** `start` for a city that is already loaded (instance present and healthy) is a no-op that prints the endpoint. It does not re-wake, restart or re-gate.
- **AC-49** The meter's `exhausted` state is the engine's, not the launcher's: when the engine has stopped every city for budget (feat-9995385596 AC-30), `status` surfaces `/health`'s `activeHours.state` and the launcher does not start the city again on the same class in the same month. A start on a class whose bucket is `exhausted` is refused before creation by reading `/health` of a running host, or the host-scoped meter record when none is running (OQ-7). Moving to a class with remaining budget (pix, or another Spot class) stays allowed, matching the meter's per-class buckets (AC-12 there).
- **AC-50** Readiness: after `Start`, the launcher polls the endpoint's `/health` (through the tunnel, AC-59) until it reports the expected host class, the pinned build, `status: ok` and the meter state not `unknown`, or the readiness timeout (default the Q100153 wake figure plus provisioning margin, configuration) elapses. Poll uses injected clock and backoff with jitter. Timeout triggers AC-33. A wrong host class or a build mismatch is a refusal, not a warning.

## G. Spot interruption

- **AC-51** The reclaim watcher runs **on the instance**, shipped in the bootstrap the launcher generates, not on the laptop (AC-2, GGR94). It polls the provider's metadata endpoint (AWS instance metadata interruption notice, GCP preemption/`ACPI G2` signal) and on a notice sends `SIGTERM` to metroserve, the same path as `stop` (AC-46).
- **AC-52** Budget: the watcher sends SIGTERM immediately on the notice; the engine owns the 20 s snapshot-plus-upload budget (Q100163). On GCP the notice leaves about 30 s, so a margin of about 10 s remains; AWS leaves about 2 minutes. The meter's flush counts inside the 20 s (feat-9995385596 AC-14). A test of the generated watcher script (a fake metadata server) asserts SIGTERM is sent within one poll interval of a notice and that the poll interval is at most 2 s on GCP and 5 s on AWS.
- **AC-53** If the reclaim lands before the snapshot finishes, nothing is lost: the city resumes from the previous snapshot plus the journal, only the replay is longer (README trap 2; A2Bev001 v23 note on BUG-1197). The launcher's `status` after a reclaim prints which: `final snapshot confirmed` or `resuming from previous snapshot, replay about N ticks`, computed from the store, never assumed.
- **AC-54** After a reclaim the launcher takes no action (it is not running, AC-2). The watcher writes a `reclaimed` marker (reason, time, snapshot outcome) into the placement record (CAS, best effort, within the 20 s budget but after the snapshot, so it can never delay it). The next `launcher status` or `start` reads it. Whether a restart elsewhere should ever be automatic is OQ-5.
- **AC-55** Spot capacity failure at start (no capacity in region, price above `--max-price`): the launcher tries the next candidate from AC-16 only if a token for that candidate is also live; otherwise it stops and prints what token is needed. It never retries the same provider in a tight loop (bounded retries with backoff, configuration, default 3).

## H. Observability

- **AC-56** Every command writes structured JSON log lines (one per step) to stderr and to a run log under the project's git-ignored temp folder (`temp/launcher/<runId>.jsonl`, with a retention cap, GGR66 rule 4). Fields: time, runId, city, command, backend, step, outcome, durations, instance id, region, tokenId (identifier only), exit code. No log line contains a secret value (AC-62, AC-63).
- **AC-57** `status <city>` prints, per backend, the instance state, the host class, the endpoint, uptime, the estimated spend so far (price seen at start times elapsed hours, labelled an estimate), the TTL remaining, the placement hint with any drift warning, and the engine's `/health` meter fields when reachable. `status --all` lists every launcher-tagged resource across all backends, including ones the placement record does not know (AC-66 orphans). Machine output with `--json`.
- **AC-58** Every paid start writes a spend record the next monthly review can reconcile: the forecast, tokenId, the resource ids and the actual stop time. Estimated versus actual (from provider billing where reachable) is a manual step and is not automated here.
- **AC-59** `Endpoint` returns the player-facing URL, which is the stable Cloudflare Tunnel hostname for the city (a4.md, Q100160), not the host's own address. The launcher verifies `/health` **through that hostname** and rejects a mismatch of instance or host class (this catches a stale tunnel connector from the old host). Tunnel and Access are set up by FEAT-9995385599; this item only starts the connector with the token it is given and checks the result.
- **AC-60** The launcher emits a one-line summary on success: city, backend, host class, endpoint, TTL, and "estimated cost to TTL: £x". On a refusal it names the AC-coded reason and the next action Aaron can take.

## I. Configuration and secrets

- **AC-61** Configuration is one file (`launcher.yml`) with an example committed (`launcher.example.yml`, all values placeholders) and the real file git-ignored under the project root, selected with `--config` or `LAUNCHER_CONFIG`. It holds non-secret values only: regions, size-to-instance-type map per provider, pix address and cap, price margins, TTL ceiling, readiness timeouts, budgets per host class. An unknown key is an error (typo-safe). A test loads the example and asserts it validates.
- **AC-62** Secrets (R2 access keys, the Cloudflare tunnel token, cloud credentials, registry pull credentials) are **never** in git, in the config file, in the example, in a log, in `status`, in `plan`, or on the command line. They come from the environment or the provider's own credential chain (AWS and GCP credential files, `az` login) and are passed to instances by the provider's secret or instance-profile mechanism, with a bucket-scoped R2 token, never the account key (OQ-8). `plan` and `--dry-run` print secret **names** and where each would come from, never values.
- **AC-63** A redaction test builds a launcher run with sentinel secret values in the environment and asserts none appears in stdout, stderr, the run log, the plan, the generated bootstrap's logged output, or the error text of any simulated failure. The repo's gitleaks pre-push and the canonical low-entropy fixture rule apply to the tests' fixtures (see memory: hook gotchas).
- **AC-64** Images are referenced by immutable digest. A `latest` or tag-only reference is refused. The image the launcher starts must be amd64 (AC-20) and have the build version the player's client expects (no BUG-1097 handshake surprise); the launcher reads the digest from configuration or from the CI build output, and the plan prints it. Where the image is pulled from is OQ-9.
- **AC-65** The launcher needs the least privilege that works: a dedicated provider identity per cloud limited to its own tag scope (create and terminate instances tagged `metropolis-launcher`, read pricing, read status). A test of the policy documents the exact permissions (a checked-in JSON policy per provider, a golden file); applying the policy is Aaron's act and is itself out of scope.

## J. Idempotency, retries, dry-run (GGR62)

- **AC-66** Every resource the launcher creates carries tags/labels `metropolis-launcher=1`, `city=<key>`, `runId=<id>`, `ttl=<ts>`, `class=<host class>`. This is how `status` finds resources the launcher created but failed to record (a crash between create and CAS).
- **AC-67** RunID is a deterministic function of city, backend and a caller-supplied or generated nonce that is persisted in the run log; the provider's own idempotency token is set from it (AWS `ClientToken`, GCP request id, ACA resource name derived from it), so a retried create after a lost response returns the existing resource rather than a second one. A fake that applies a create and drops the response is retried and the instance count after is one.
- **AC-68** A crash (kill -9) at each step boundary of `start` and `move` leaves a state `status` can name and `stop` can clean up: no untagged resources, no resource without a TTL. A test kills the fake run at every step and asserts both. This is the launcher's equivalent of BUG-1197's per-step crash tests.
- **AC-69** `--dry-run` (and the `plan` command) makes **zero** mutating provider calls, **zero** store writes and **zero** gate-token reads that could consume anything; it makes only read-only calls (status, pricing, health). It prints: the selection with the reason for each rejected candidate, the exact resources and tags, the generated bootstrap with secrets redacted, the flags passed to the engine, the forecast, and the gate state. A test wraps the fake backend so any mutating call fails the test, runs `start --dry-run`, and asserts exit 0.
- **AC-70** There is no dry-run **default** for paid backends that quietly becomes a real run: the dry-run flag is explicit, and a run without it behaves as normal. Aaron's expected habit is `plan` first (AC-27). OQ-10 asks whether paid backends should instead require `--confirm`.
- **AC-71** Generated bootstrap scripts (VM user-data, the ACA revision template, the pix compose arguments) are produced by pure functions and tested by golden file, then **executed once with the launch line swapped for echo** as part of the item's verification (GGR62: a launcher is ready only after it has been run). Known faults to test for: brackets in REM-like comments, quoted variable expansion, control characters, and the variadic-argument trap.
- **AC-72** A transient provider error (throttle, 5xx, timeout) retries with bounded exponential backoff and jitter on the injected clock; a non-transient error (permission denied, quota, invalid type) fails immediately with the provider's code preserved in the registry error. Retrying never bypasses the gate (AC-26) or the TTL (AC-35).

## K. Adapter specifics

- **AC-73** `pix`: `Start` ensures the container is up through the SAFE route (`docker --context pix compose -p metropolis -f deploy/compose.yml up -d`, never `--build` for an unchanged digest; OQ-11 says whether the launcher may run this or only verify it) and returns the existing endpoint. `Stop` does **not** stop the container (pix runs 24/7 and other tenants share it); it asks the engine to hibernate the city if the engine exposes that, otherwise it is a no-op reported as such. `CostClass` is `free`. pix never needs a gate token.
- **AC-74** `pix` capacity is the compose limit (5 GiB, GOMEMLIMIT 4500 MiB, 4 CPUs as deployed on 2026-11-17) and nothing the launcher invents; it reads limits from `/health` or the compose file, not a literal. x1 only (the firewall admits one client); the launcher does not widen it.
- **AC-75** `aws-spot` and `gcp-spot`: `Start` creates one tagged Spot instance of the size's mapped type, amd64, with `instance-initiated-shutdown-behavior=terminate` (AWS) or `instanceTerminationAction=DELETE` (GCP), the TTL (AC-35), the generated bootstrap (docker or a plain systemd unit that pulls the digest image, runs cloudflared with the tunnel token, runs metroserve with the engine flags, runs the reclaim watcher), and a local ephemeral disk for citizen paging and nothing durable. All durable state is the store. Burstable types (t3a and the like) are refused for the engine (a4.md: CPU credit exhaustion), enforced by a deny-list test.
- **AC-76** `azure-aca`: `Start` creates or updates one Container App revision with `min-replicas 0`, `max-replicas 1`, the digest image, the TTL expressed as a scheduled scale-down or a budget kill (not just a hope), and the meter flags. It reuses the existing environment and registry named in configuration (inc1-cost-forecast.md R1 to R7 are Aaron's one-off provisioning, not the launcher's). The launcher refuses to run if the Azure Budget and kill-switch runbook named in configuration cannot be confirmed to exist (read-only check), since that is the Azure fallback's required guard.
- **AC-77** A backend's `Forecast` uses the provider price read (AC-17) times the size's hours at the TTL, labelled with the date and source; Azure uses the unverified paid rate from inc1-cost-forecast.md and says "UNVERIFIED" in the forecast until Aaron's calculator check is recorded in configuration.
- **AC-78** Adding a backend (for example `hetzner`) needs only a new adapter plus a config block and its entry in the cost-class table; no change to the selector, the gate or the safety logic. A test registers a second fake backend with a different cost class and runs the same suite against it.

## Unstated assumptions (proposals; nothing registered)

- **ASM-L1** The launcher is Go, built from the same module, run as a one-shot command (no daemon).
- **ASM-L2** The gate exposes a read-only check the launcher can call (a command or a state file) that answers for one action pattern; today only the hook and the `/cost-gate` skill touch the gate (OQ-2).
- **ASM-L3** The store (FEAT-9995385594) exposes host-scoped records with compare-and-swap (the meter's ASM-1618) and a read of the manifest (size, epoch, snapshot position); the launcher uses exactly that and nothing more.
- **ASM-L4** `/health` through the tunnel reports host class, build version and meter state (feat-9995385596 AC-44); the readiness check relies on it.
- **ASM-L5** A player is a human (Aaron) who can run a command to wake a paid city. Nothing requires automatic wake for a single player.
- **ASM-L6** Cloud Spot price reads and instance status calls are free; only creation of resources bills.
- **ASM-L7** Terminating a launcher-tagged cloud instance is a cost-reducing stop and not a "deletion outside the project" under the deletion gate (OQ-12).
- **ASM-L8** pix compose stays the SAFE-registered route; the launcher does not add a second deployment path on pix.
- **ASM-L9** One city occupies at most one instance (no splitting a city across servers, README section 2).
- **ASM-L10** The a4.md price figures are indicative and used only as test fixtures; production forecasts use live reads.

## Open questions for Aaron (each with a recommended answer)

- **OQ-1 Language and home.** Go in `tools/launcher/` (shares the store client and error registry) or Node alongside `harness/`. **Recommend Go**: it shares the persist read side and the registry, produces one static binary, and fits GR#20.
- **OQ-2 How does the launcher check a token?** Today only the Claude hook and `/cost-gate` touch it. **Recommend** a read-only `gate.py cost check <pattern>` subcommand (exit 0 only on a live, matching token) that the launcher shells out to, fail closed if absent; the launcher never reads the token store directly. If SAFE will not add it, the fallback is a prompt-free "refuse unless `--token-id` matches a live token file", which is weaker. Needs a SAFE BOW item either way.
- **OQ-3 pix's real capacity.** a4.md says "about 10M"; the compose caps 5 GiB shared with TeslaMate and sign. **Recommend** the cap is a measured figure from inc1 (FEAT-9995385600), the launcher uses the engine's own sizing and `/health` headroom, and `PixMaxCitizens` ships at 10,000,000 only as a placeholder until inc1 measures.
- **OQ-4 Automatic wake of a paid city.** An always-on trigger would need a service (Cloudflare Worker or similar) holding cloud credentials, against GGR94 and the cost gate. **Recommend none**: `launcher start` is the wake, and the web console shows "host is asleep, ask Aaron" until then. Revisit only if a second player appears.
- **OQ-5 Restart after a Spot reclaim.** BOW and a4.md say "restart elsewhere". A restart is a paid start and needs a live token, so it cannot be unattended without bypassing the gate. **Recommend no automatic restart** (AC-30, AC-54): the city is safe in R2, `status` says so, Aaron runs `start`. This is a deliberate narrowing of the BOW wording; confirm.
- **OQ-6 Regions.** Which regions may play use? **Recommend** London for AWS, a London or nearby EU region for GCP (not the Iowa prices in a4.md, which are a default-region artefact), Ohio allowed only for `proving` runs; the allowed list in config.
- **OQ-7 Meter state when nothing is running.** To refuse a start on an exhausted bucket the launcher must read the host-scoped meter record from the store. **Recommend** it reads it (read-only) and refuses; if the record is `unknown` it refuses and says why, matching the meter's fail-closed rule.
- **OQ-8 Secret delivery to a Spot VM.** User-data is readable on the instance. **Recommend** a bucket-scoped R2 token and a single-purpose tunnel token, each rotated by Aaron on a schedule; no account-level keys on any VM; instance profile (AWS) or service account (GCP) for the cloud APIs. Secrets Manager or Secret Manager only if Aaron wants the small cost.
- **OQ-9 Where does the Spot image come from?** pix builds from the laptop's context over the docker context; a Spot VM needs a registry. **Recommend** a public GHCR image built by CI and pinned by digest (the repo is public, AGPL; no registry cost). The existing `prixsixacr` stays Azure's. If a private image is wanted, an ECR or Artifact Registry fee applies and needs its own forecast.
- **OQ-10 Dry-run default.** **Recommend** explicit `plan` and `--dry-run` (AC-70), plus the unavoidable fact that a paid start with no token refuses anyway. A mandatory `--confirm` on paid starts is an alternative; it adds little over the token.
- **OQ-11 pix start under SAFE.** SAFE deploys and registers metropolis on pix (compose header). **Recommend** the launcher only verifies pix (health, status) and never runs compose itself; `launcher start` on pix means "check it is up and tell me", and a down pix is SAFE's to bring back. This keeps one deployment path (ASM-L8).
- **OQ-12 Terminating cloud resources and the deletion gate.** Terminating the launcher's own tagged instance stops billing but is a deletion. **Recommend** treating `stop` of a launcher-tagged resource as allowed without a token (the dead-man TTL does it anyway), and asking SAFE to confirm the deletion gate does not trip on `aws ec2 terminate-instances` for tagged launcher resources.
- **OQ-13 Latency probe for ties.** AC-16 breaks ties by latency for play. **Recommend** a static region-to-latency table in config (measured once by Aaron) rather than a live probe; the launcher should not add a network dependency to selection.
- **OQ-14 Dead-man TTL values.** **Recommend** defaults of 8 hours for `play` (one session plus margin) and the proving run's declared duration plus 25 percent, ceiling 24 hours in config; the meter budget is the in-process guard, the TTL is the cloud-side one.

## Conflicts and gaps noticed in the sibling documents (for the lead)

1. **BOW and a4.md say the launcher restarts the city elsewhere after a reclaim.** That is a paid start and cannot run unattended under Q100164's "cost gate on every paid start", and the launcher is not a service (GGR94). The ACs narrow this to manual restart (OQ-5).
2. **a4.md says the AWS 2-minute warning is turned into SIGTERM by "the adapter".** The adapter runs on the laptop, which is not up during play. The ACs put the watcher on the instance (AC-51).
3. **a4.md section 5 lists adapters `aws-ondemand`, `gcp-run`, `hetzner`.** The BOW item names pix, aws-spot, gcp-spot, azure-aca. The ACs follow the BOW item and make other adapters additive (AC-78).
4. **The meter (feat-9995385596 AC-27) says the launcher holds per-class budgets.** Accepted (AC-43); the launcher therefore needs the budget values before it can start any paid class, which is a new Aaron decision per class.
5. **feat-9995385595 AC-25 and OQ-5 recommend self-exit for scale-to-zero.** That leaves a Spot VM running with no process unless the bootstrap terminates on exit; AC-45 adds that, and it is the launcher's, not the engine's, to deliver.
6. **a4.md prices London for AWS but Iowa for GCP (the page default).** The selector must not compare them as like for like; AC-17 requires live prices for the actual region.
7. **The compose file runs `-city dogfood`, one default city.** The launcher addresses cities by key; whether pix serves more than the default depends on `CityHost` creation on connect, not on the launcher. No change asked, but pix `Status` (AC-42) must not assume the default city is the only one.
8. **inc2's epoch fence is the real guard and does not exist yet.** The launcher's own safety (AC-34 to AC-41) is shippable before inc2 only in a degraded form (no placement CAS, no store read). The BOW dependency on FEAT-9995385594 stands; do not start launcher code before it.
