## North-star vetting (dev-team-process.md v1.12 BA mandate)

This item answers **question 5 (long bet)** and, downstream through the items it blocks, questions **1 and 3**:

- **Q5, directly.** The deposit map is fixed at world-gen and never regenerates — the player who prospects and buys ground *before* proven-reserve confirmation (FEAT-050's survey progression) is making a stretch bet on unproven geology exactly as §5 of the north-star describes: "planting a crop... before you can comfortably afford it." A deterministic, seeded, never-reshuffled map is what makes that bet real rather than a slot-machine pull — the ground you bought stays what it was, good or bad, forever (Q3, consequence sticks, inherited from the fixed-map property).
- **Q1 (conflicting demand), inherited by FEAT-051/FEAT-053's extraction and permit items, not sharpened by this item alone.** This item itself creates no spendable choice — it only lays out what exists in the ground. It is, in Aaron's own §10 framing, **necessary infrastructure that answers none of the five questions on its own** (no capex is spent, no consequence is felt, nothing snowballs) but must not crowd out the entertainment items it enables. Its acceptance criteria are therefore scoped to correctness/determinism/data-hygiene, not to balance or fun — those questions belong to FEAT-050 (survey progression, Q5's "pay to see underground") and FEAT-051 (extraction ladder, Q1/Q2/Q4).
- **Framing carried into the ACs below:** every AC here proves the shuffle is honest (deterministic, geology-aware, data-driven, unowned-tile-inclusive) so that the entertainment built on top of it (survey, extraction, decommissioning) is a bet against real, fixed ground truth rather than a moving target.

## User stories

- **US-1.** As the deterministic seeded RNG (GR#21), I need the deposit shuffle to draw exclusively from `engine.world`'s counter-based hash stream — never a shared/global `math/rand` source — so that re-running world-gen with the same seed produces a bit-identical deposit map, and so that a shard/worker-count change (SG-7) cannot silently reorder or reassign deposits.
- **US-2.** As `engine.world`'s geology layer (`engine.world.md` AC-6/AC-7 — chalk/clay/sand-gravel/deep-coal-eastern, revealed by prospecting), I need the deposit shuffle to read my real per-cell/per-region geology classification and bias deposit type/co-location against it, so "uranium doesn't sit in the chalk" and "coal measures imply gas" are mechanical consequences of a shared geology model, not a disaster-style parallel classification invented inside the mining package.
- **US-3.** As a balance designer (Aaron, GR#15), I need every tunable number this shuffle uses — deposit counts per type, size-curve shape, depth-band ranges, co-location weightings, and the "don't be stingy" coalfield generosity multiplier — to live in a data file I can edit without a rebuild, never as a Go constant, so a future balance pass on Kent's coalfield generosity does not require touching shuffle code.
- **US-4.** As a player deciding whether to buy an unproven, unowned tile (the §3 "a reason to buy them" framing, and the north-star Q5 long bet this item exists to enable), I need deposits to be laid out across the FULL tile extent — owned and unowned alike — at world-gen, before any purchase decision is made, so tile value is a real pre-existing fact the player is betting on, not something conjured at purchase time.
- **US-5.** As `engine.mining`'s own siting/prospecting surface (MOD-046 AC-1/AC-2), I need this feature's deposit records to be queryable through the SAME package's geology-gated reveal mechanism `engine.mining.md` already specifies — not a second, deposit-model-owned visibility gate — so a future prospecting/survey action (FEAT-050) has exactly one place to ask "what's under this cell."

## Scope

The subsurface deposit model and its deterministic seeded world-gen shuffle: per-deposit type (metallic ore / hydrocarbon-coal / offshore field / sanctioned fictional resource), size, density, and depth band; geology-aware co-location bias consuming `engine.world`'s real geology layer; the GR#15 data file carrying every distribution parameter; deposit placement across the full owned-and-unowned tile extent, including offshore cells. Does **not** include: prospecting/survey/reveal mechanics or the map overlay (FEAT-050 — this item only produces the underlying map FEAT-050 will expose); extraction, depletion, or yield (FEAT-051); the extraction-scale ladder or facility permits (FEAT-051/facilitypermits); `engine.mining`'s own siting/`BlightAPI` machinery (MOD-046 — this item's deposits are inert data until a sited extraction structure consumes them).

## Acceptance criteria

### Functional — the deposit model & taxonomy

- **AC-1 (GR#20; code.json inbound contract — currently unpopulated, mirrors `feat.disasters.md` AC-1's pattern).** A queryable deposit-record surface exists on the shared `internal/engine/mining` package (e.g. `DepositAt(TileCoord, CellLocal) (Deposit, bool, error)` or equivalent) returning, at minimum, resource type, size, density, and depth band for a given cell — even though code.json's `feat.resourcedeposits` entry currently has no registered inbound contract (`name`/`format`/`pattern`) of its own, since it shares `engine.mining`'s package and is expected to surface through that module's eventual `MiningAPI`. Check: `go doc ./internal/engine/mining` shows a deposit-query function distinct from `engine.mining.md` AC-1's `BlightAPI`/siting surface; `internal/engine/mining/doc.go` notes the shared-package, no-separate-inbound-contract arrangement explicitly (`grep -n "feat.resourcedeposits" internal/engine/mining/doc.go`).
- **AC-2 (§2 resource-type taxonomy).** The deposit type enum covers, at minimum: metallic ores (copper, tin, iron, uranium, rare-earth metals), hydrocarbons/coal (gas, oil, coal), offshore fields (gas/oil sited on sea cells), and at least one sanctioned fictional resource slot — each with a distinct, documented, data-sourced (GR#15) realistic depth-band range so fictional resources sit believably alongside the real ones rather than at an arbitrary fixed depth. Check: `go doc ./internal/engine/mining` shows a `DepositType` (or equivalent) enum listing all named real resources plus at least one fictional slot; `grep -rn "func Test.*[Tt]axonomy\|func Test.*[Dd]epositType" internal/engine/mining/*_test.go` finds a passing test asserting every enum value resolves to a depth-band range sourced from the GR#15 data file (AC-6), not a hardcoded literal in the enum's own definition file.
- **AC-3 (§2 offshore fields — the sea-cell case).** At least one deposit type (gas/oil) can be placed on sea cells (`engine.world`'s cell-surface classification, per `engine.world.md`'s cell-state fields), giving the sea a deposit role distinct from the port/fishing/reclamation set §9 already assigns it. Check: a passing test seeds a fixture containing sea cells and asserts at least one offshore deposit is placed on a sea cell across a representative sample of seeds, while asserting metallic-ore types are NEVER placed on sea cells (`grep -rn "func Test.*[Oo]ffshore" internal/engine/mining/*_test.go`) — the second half of this assertion is what a shuffle that ignores cell-surface entirely would fail, since an unconstrained placement would eventually put ore offshore too.
- **AC-4 (§2/§3 deposit attributes — size, density, depth as first-class, independently varying fields).** Every placed deposit record carries independently-varying size, density, and depth values (not a single combined "richness" scalar that conflates them) — size and density both drawn from data-sourced curves (AC-6), depth constrained to the type's realistic band (AC-2). Check: `go doc ./internal/engine/mining Deposit` (or equivalent) shows three distinct numeric fields for size/density/depth; a passing test seeds a large sample and asserts size and density are NOT perfectly correlated (i.e., the two curves are independently sampled, not derived from one another) (`grep -rn "func Test.*[Ss]izeDensityIndependent" internal/engine/mining/*_test.go`).

### Functional — geology-aware co-location (the "not random" core of §2/§3)

- **AC-5 (§2/§3 geology-aware co-location — the fixture-based check, mirrors `engine.mining.md` AC-4's ridge-fixture rigor for the equivalent "computed from real X, not distance/chance alone" claim).** The shuffle reads `engine.world`'s real geology classification (`engine.world.md` AC-6/AC-7 — chalk/clay/sand-gravel/deep-coal-eastern) for each candidate cell and biases deposit placement against it such that: (a) uranium deposit density in a chalk-classified region is statistically far lower than in a non-chalk region across a representative sample of seeds; (b) a cell placed within a coal-measures region shows elevated co-located-gas probability compared to an identical-shaped non-coal region, holding all other placement parameters constant. Check: a passing test constructs two geology fixtures differing ONLY in their `engine.world` geology classification (one chalk, one not; one coal-measures, one not) and runs the SAME seed range against both, asserting the uranium-in-chalk and gas-with-coal correlations hold in aggregate over the sample (`grep -rn "func Test.*[Gg]eologyCoLocation\|func Test.*[Nn]oUraniumInChalk" internal/engine/mining/*_test.go`). **False-pass risk (mirrors `engine.mining.md` AC-4's stated risk for viewshed-vs-radius):** a shuffle that reads geology only to gate deposit *presence* (e.g. "no ore at all under chalk") but otherwise places every resource type with flat, geology-blind probability would satisfy a shallow "geology is consulted somewhere" check while failing the actual co-location claim — this AC requires the CORRELATION (uranium-vs-chalk, gas-vs-coal) to be measured directly, not merely that the geology query was called.
- **AC-6 (§3 GR#15 — distribution parameters live in a data file, not code constants).** Deposit counts per type, size-curve shape parameters, depth-band ranges, co-location weighting factors (including the chalk/uranium exclusion and coal/gas correlation strengths from AC-5), and the East Kent coalfield "don't be stingy" generosity multiplier are ALL sourced from a data file (e.g. `data/deposits.json`, following the `data/*.json` convention already used by `errors.json`/`modes.json`/`naming_corpus.json`) — none hardcoded as Go numeric literals in the shuffle implementation. Check: `grep -rn "0\.[0-9]\+\|[0-9]\{2,\}" internal/engine/mining/deposit*.go` (excluding `_test.go` and excluding array indices/enum ordinals) shows no bare balance-shaped numeric literals — every such value traces to a load from the data file; `go doc ./internal/engine/mining` or `internal/engine/mining/doc.go` names the data file path explicitly; a passing test asserts the shuffle's output changes when the data file's coalfield-generosity multiplier is edited between two test runs with the SAME seed (proving the parameter is actually read, not merely present in a file nobody loads) (`grep -rn "func Test.*[Dd]ataDriven\|func Test.*[Gg]enerosity" internal/engine/mining/*_test.go`).
- **AC-7 (§2 Kent coalfield calibration — "don't be stingy", a concrete generosity check).** Within the eastern coal-measures region (`engine.world.md` AC-6's real Betteshanger/Snowdown-country fixture), coal deposit density/coverage is measured against a documented minimum coverage floor sourced from the AC-6 data file — the test proves generosity is a real, checkable floor, not just a qualitative aspiration in a comment. Check: a passing test seeds the real (or fixture-equivalent) eastern coal-measures extent across a representative seed sample and asserts coal-deposit tile coverage meets or exceeds the data file's documented floor value in every sampled seed (`grep -rn "func Test.*[Cc]oalfieldGenerosity\|func Test.*[Nn]otStingy" internal/engine/mining/*_test.go`).

### Functional — determinism & unowned-tile placement

- **AC-8 (GR#21 — the headline determinism claim, "same seed => bit-identical deposit map").** Running the full world-gen deposit shuffle twice with the SAME `worldSeed` produces byte-identical deposit records (type, size, density, depth, cell location) for every placed deposit, across repeated runs and across different worker/shard counts (SG-7). Check: a passing test runs the shuffle twice with an identical seed (once single-threaded, once with the package's configured worker count if parallelised) and asserts the two resulting deposit sets are deep-equal, including field order/count, not merely equal in aggregate statistics (`grep -rn "func Test.*[Dd]eterministic.*[Dd]eposit\|func Test.*[Ss]hardInvarian.*[Dd]eposit" internal/engine/mining/*_test.go`). A companion test asserts a DIFFERENT seed produces a measurably different deposit set (proving the seed is actually consumed, not silently ignored — the can-never-fail trap `engine.mining.md` AC-12's own escalation notes as a real prior instance in this codebase).
- **AC-9 (§3 unowned-tile placement — "deposits exist in unowned tiles too").** The shuffle runs across the full world-gen tile extent (owned and unowned alike, per §3's "owned-and-unowned tile extent") at world-gen time, BEFORE any tile purchase — a deposit record's existence and content is never contingent on `TileAt.Owned` being true. Check: a passing test constructs a world with at least one never-purchased tile, runs the shuffle, and asserts deposit records exist under that unpurchased tile identical in kind/shape to those under a purchased tile from the same seed (`grep -rn "func Test.*[Uu]nownedTile.*[Dd]eposit\|func Test.*[Dd]epositBeforePurchase" internal/engine/mining/*_test.go`); a second assertion in the same test confirms purchasing the tile afterward does NOT alter the already-placed deposit record (purchase reveals, it does not create).
- **AC-10 (§3 "runs alongside the Terrain 50 heightmap pipeline" — ordering/dependency check).** The deposit shuffle executes only after `engine.world`'s terrain import/geology derivation has completed for the tile in question (consuming `engine.world.md` AC-6's geology layer as an input), never before or independently of it — since AC-5's co-location bias is meaningless against an unpopulated geology layer. Check: `grep -rn "world\.(Geology|PocketGeology|GeologyBaseline)" internal/engine/mining/*.go` (excluding `_test.go`) shows the shuffle calling `engine.world`'s real geology query, not a mining-local terrain/geology copy; a passing test asserts calling the shuffle against a tile whose geology has not yet been derived returns the AC-13 error rather than placing deposits against zero-value/default geology.

### Error handling

- **AC-11 (GR#7 — malformed/missing GR#15 data file).** Loading the deposit-parameters data file (AC-6) at world-gen start, when the file is missing, malformed (invalid JSON), or fails schema validation (e.g. a negative count, an inverted depth-band range, an out-of-taxonomy resource type key), produces a registry-sourced error (new `MET-E`-range code) and the shuffle does NOT proceed with silent defaults or a partially-populated deposit map. Check: `grep -n "MET-" internal/engine/mining/*.go` finds a registry code reference in the data-loading path specifically; passing test coverage (`grep -rn "func Test.*[Mm]issingDepositData\|func Test.*[Mm]alformedDepositData" internal/engine/mining/*_test.go`) — **GR#7 assertion, stated explicitly:** the test asserts the returned error's registry code matches the claimed `MET-E` code AND that no deposit records were placed as a side effect of the failed load (an all-or-nothing load, not a partial one silently continuing).
- **AC-12 (GR#7 — geology-not-yet-derived case, companion to AC-10).** Invoking the deposit shuffle against a tile whose `engine.world` geology has not been derived yet (AC-10's ordering dependency) produces a registry-sourced error (new `MET-E`-range code) distinct from AC-11's data-file error, rather than proceeding against zero-value geology and silently producing a geology-blind (effectively random) deposit map that would look superficially valid. Check: `grep -n "MET-" internal/engine/mining/*.go` finds a second, distinct registry code for this path; passing test coverage asserts the specific code returned and that zero deposits were placed for the affected tile (`grep -rn "func Test.*[Gg]eologyNotDerived" internal/engine/mining/*_test.go`).

### Determinism, safety & scale

- **AC-13 (GR#21, restated for this feature's own file per house convention — see AC-8 for the headline claim this formalises).** Deposit shuffle draws use `engine.world`'s counter-based hash stream (`hash(worldSeed, tileID, cellID, purposeTag)` or equivalent) exclusively — no shared/global `math/rand`. Check: `grep -n "rand.New\|math/rand\"" internal/engine/mining/deposit*.go` (excluding `_test.go`) finds no shared/global RNG source.
- **AC-14 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/mining/deposit*.go` (excluding `_test.go`) returns no matches — the deposit map is a pure function of `(worldSeed, geology, distribution-data-file)`, never wall clock.
- **AC-15.** `go test ./internal/engine/mining/... -race -count=1 -run Deposit` passes with no data race (scoped to the deposit-shuffle test subset via `-run`, since the full package also carries `engine.mining.md`'s own AC-14 race suite).

## Out of scope

- `engine.world`'s own terrain import, geology derivation, and `CellAt`/geology-query implementation — this item only calls it (AC-5/AC-9/AC-10); see `engine.world.md`.
- `engine.mining`'s own `BlightAPI`, geology-gated siting, blight/noise/viewshed model, reclamation, and closure mechanics — this item's deposits are inert data those mechanics will eventually consume; see `engine.mining.md`. No siting, extraction, or blight AC belongs in this file.
- Prospecting, survey progression, proven-reserve confirmation, and the F1 map overlay — FEAT-050's scope entirely; this item only produces the ground-truth map FEAT-050 will reveal incrementally.
- Extraction rates, yield, depletion, the artisanal-to-Parker scale ladder, and price exposure — FEAT-051's scope.
- Facility permits, decommissioning liability — the separate facilitypermits/decommission feature items per §7-8 of the design brief.
- Exact deposit counts, size-curve shape, depth-band numeric ranges, co-location weighting strengths, and the coalfield generosity floor's precise value — balance data pending M2 tuning (see Escalations, new ASM item); this file's ACs check that these live in a data file and are consumed correctly (AC-6, AC-7's floor mechanism), not what the values should be.
