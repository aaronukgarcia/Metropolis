# Acceptance criteria — feat.factorytypes (FEAT-105)

**BOW code:** FEAT-105 (P2, open) — "Factory unit types — manufacturing facility catalogue."
**Spec refs:** §33 The Freight Harbour — Tonnes & Chains (`docs/METROPOLIS-MASTER-v2.1.md` lines 464-478: five production-chain families, "each stage a firm with input t/day → output t/day, jobs, power/water draw, blight class"); §46 Multinational Attraction (FDI) & Anchor Employers (lines 627-640: the archetype table — semiconductor fab "the utility boss-fight", chemicals complex "blight class high; feeds plastics chain", steel process plant "§33 chain anchor", EV gigafactory "60+ ha, 100 MW"); §34 Zoning (line 480-482: **Manufacturing** light-industrial vs **Heavy Industry** blight-class buffer rules); §17 Resource Consumption Model (line 324: "Farms, quarries, plants: producer coefficients in catalogue"); §45 Firms (the "stages register as firms" pattern); code.json `engine.freight` entry (inbound `FreightAPI`, pattern "chains from data; stages register as firms; tonnes conserved (invariant)"); the parent acceptance files `engine.freight.md` (MOD-047 — AC-4's "stages register as firms", AC-5's per-stage input/output/jobs/power-water/blight) and `engine.firms.md` (MOD-058) and `engine.fdi.md` (MOD-059) — this file cross-references, it does not restate.
**Date:** 2026-08-16 (BA, first pass; pipelined ahead per dev-team-process.md)
**Status:** draft-ahead — `MOD-047` (`engine.freight`) is BOW-status `done` (code exists, `data/freight.json` carries the chain-stage input/output/jobs/power-water/blight data — see Cross-check), `MOD-058` (`engine.firms`) is `open`. This item is not in the ready queue until the single-source-of-truth boundary against `data/freight.json` is ruled (Escalations ES-2). The feature has **no code.json registration** (`feat.factorytypes` is absent from code.json — see Escalations ES-1).
**Package under test:** `internal/engine/freight/` (shared with `engine.freight`/MOD-047; the factory-type catalogue is a file/type set inside the same package, not a fork — ASM-682).
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/freight/...`.
**Balance-number regime (standing rule, same convention as `engine.freight.md` AC-5, `feat.minetypes.md` AC-4):** every per-type figure — footprint (cells), input/output t/day, jobs, utility draw (power/water), and blight class — is a **placeholder** in a data file (`data/factorytypes.json`, ASM-680), each carrying a disclosure comment naming it pending Aaron's balance pass. No AC may be satisfied by a junior inventing a final number; every AC touching a per-type figure requires the value to live in the data file and requires tests to check **shape/direction/distinctness** (two types differ; a field is present and typed; data actually loaded), never a specific magnitude. The §33 modal caps (road 25t, rail 1000t, sea 3-40kt) are `engine.freight.md`'s, not this catalogue's.

## The load-bearing rule (this file exists to enforce it)

Each factory **type is a distinct modelled facility** — its own footprint, input-output pair, jobs, utility draw, and blight class — **never a generic factory** with a `Type string` discriminator and defaulted fields. A single `FactoryType` struct carrying a `Type string` field with every other field defaulted (or a `map[string]FactoryType` where all values share one footprint/input-output/jobs/utility/blight and only the key differs) is the anti-pattern this file's AC-2/AC-4 are written to fail. Two same-category types (e.g. steel mill and electronics) must resolve to **two different parameter sets from data**.

## User stories

- **US-1.** As a factory type (assembler, steel mill, electronics, chemicals converter, food processing, textiles, cement, glass), I need my own footprint, input-output pair, jobs, utility draw, and blight class — not a generic "factory" row with my name stamped on it — so siting me has type-specific consequences, not one shared consequence with a cosmetic label (load-bearing rule).
- **US-2.** As `engine.freight`'s chain-stage surface (MOD-047 AC-4/AC-5), I need the factory types resolved from a typed catalogue whose input-output/jobs/utility/blight are the **same** values the chain stages carry — never a second, driftable copy — so "each stage a firm with input t/day → output t/day, jobs, power/water draw, blight class" has one source of truth (GR#3).
- **US-3.** As `engine.fdi`'s prospect archetypes (MOD-059, §46), I need a semiconductor fab / chemicals complex / steel process plant / EV gigafactory to map onto a factory type whose utility draw and blight class make the archetype's "utility boss-fight" / "blight class high" character mechanically real, not a prose aside.
- **US-4.** As `engine.firms` (MOD-058), I need a factory type's jobs figure to be the headcount a chain-stage firm hires against, so "stages register as firms" hires from a real per-type jobs number, not a generic factory headcount.
- **US-5.** As the blight/zoning systems (§32/§34), I need heavy-industry types (steel, chemicals) to carry a higher blight class than light-manufacturing types (electronics, textiles, assembler), so Manufacturing vs Heavy Industry zoning is a real placement distinction, not a cosmetic label.
- **US-6.** As a balance designer (Aaron, GR#15), I need every per-type figure to live in `data/factorytypes.json`, editable without a rebuild.

## Scope

The factory-type catalogue itself: eight typed facility entries (assembler, steel mill, electronics, chemicals converter, food processing, textiles, cement, glass), each resolving to a distinct parameter set — footprint, input-output t/day pair, jobs, utility draw (power/water), and blight class — with a single-source-of-truth link to `engine.freight`'s chain-stage data (AC-5). Data file `data/factorytypes.json`; typed resolver in `internal/engine/freight/`. Does **not** include: `engine.freight.md`'s own port-capacity, customs, modal-reach, storage-site, balance-of-trade and mass-conservation machinery (MOD-047); `engine.firms.md`'s firm lifecycle (the *stages-register-as-firms* call is `engine.freight.md` AC-4's, not this catalogue's); `engine.fdi.md`'s prospect/bid/commitment mechanics (MOD-059 — this catalogue only supplies the per-type params an archetype maps to); the build-catalogue entries for these structures (`data.catalogue`/`data/buildings.json` — ASM-694).

## Acceptance criteria

### Functional — the typed catalogue surface

- **AC-1 (GR#20; typed resolve surface, no shared row).** A factory-type catalogue exists on `internal/engine/freight` exposing a typed resolve surface (e.g. `FactoryTypeResolve(typeKey) (FactoryTypeParams, error)` or equivalent) returning a **distinct parameter struct** per type — footprint, input-output, jobs, utility draw, and blight class are all named, typed fields, not a `Type string` field whose presence substitutes for the parameters. Check: `go doc ./internal/engine/freight` shows a `FactoryType`/`FactoryTypeParams` type with named footprint/input-output/jobs/utility/blight fields; `grep -rn "Type string" internal/engine/freight/factorytype*.go` (excluding `_test.go`) finds no bare type-string discriminator on the parameter struct.

- **AC-2 (load-bearing — two types resolve to two different parameter sets from data).** Two same-category types — steel mill and electronics — resolve to **two different parameter sets**, and the distinguishing fields are each actually populated AND differ: footprint, input-output pair, jobs, utility draw, and blight class are pairwise non-equal. A companion isolation assertion proves the difference is data-sourced: mutating one type's utility draw in the loaded `data/factorytypes.json` fixture changes only that type's resolved utility draw (the other type byte-identical before and after). Check: `grep -rn "func Test.*[Dd]istinct.*[Pp]aram\|func Test.*[Tt]woTypesDiffer\|func Test.*[Ss]teelVsElectronics" internal/engine/freight/factorytype*_test.go`; `grep -rn "func Test.*[Ii]solat.*[Ff]actorytype\|func Test.*[Ss]ingleTypePerturb" internal/engine/freight/factorytype*_test.go`. **False-pass risk:** a `map[string]FactoryTypeParams` where every entry shares one default footprint/input-output/jobs/utility/blight and only the map key differs would pass a naive "the catalogue has N factory-type entries" grep while violating the "not a generic factory" premise — the check requires the resolved *parameters* to differ between two named types.

- **AC-3 (§33/§46 taxonomy completeness; GR#15 data-derived count).** All eight named factory types (assembler, steel mill, electronics, chemicals converter, food processing, textiles, cement, glass) are present as distinct entries, each resolving to a non-zero input-output pair and jobs figure. The expected type set is derived from a data/manifest source, never a hardcoded eight-element literal in the test (GR#15). Check: `grep -rn "func Test.*[Tt]axonomy\|func Test.*[Ee]ightTypes" internal/engine/freight/factorytype*_test.go`; `grep -n "assembler\|steel\|electronics\|chemicals\|food\|textiles\|cement\|glass" data/factorytypes.json` matches all eight.

### Functional — per-type parameters

- **AC-4 (GR#15; every figure data-driven, no hardcoded literals).** Every per-type figure (footprint, input/output t/day, jobs, utility draw, blight class ordinal) loads from `data/factorytypes.json`, none hardcoded as a Go numeric literal, and the data is *actually read* — a test mutates a value in the data file between two runs and asserts the resolved parameter reflects the change. Check: `grep -rn "0\.[0-9]\+\|[0-9]\{2,\}" internal/engine/freight/factorytype*.go` (excluding `_test.go`, array indices, enum ordinals) shows no bare balance-shaped numeric literals; `grep -rn "func Test.*[Dd]ataDriven.*[Ff]actorytype\|func Test.*[Rr]eload.*[Ff]actorytype" internal/engine/freight/factorytype*_test.go`. **Balance-regime note:** the magnitudes are placeholders with disclosure comments (AC-12); this AC checks *data-sourced and consumed*, not magnitude.

- **AC-5 (GR#3 single source of truth — the sharpest AC; no duplication of `data/freight.json`).** The factory type's input-output/jobs/utility/blight values resolve to the **same source** `engine.freight`'s chain stages carry in `data/freight.json` — never a second, independently-edited copy. Concretely, either (a) a factory type carries only a `stageRef`/`stagesRef` into `data/freight.json`'s chain stages and re-exports those stages' input-output/jobs/utility/blight by reference, or (b) the per-stage numbers are consolidated into `data/factorytypes.json` as the single source and `data/freight.json` becomes the chain-structure view that reads them — documented which. In either case, for every factory type that corresponds to a §33 chain stage (cement ↔ cementPlant, steel mill ↔ steel stage, food processing ↔ food-chain stages), the resolved input-output/jobs/utility/blight are byte-equal to the chain stage's values, resolved through **one** code path. Check: a passing test loads both files and, for the overlapping facilities, asserts the factory-type resolution and the chain-stage data agree exactly, and that mutating one source changes both surfaces together (proving a reference, not a copy) (`grep -rn "func Test.*[Ss]ingleSource\|func Test.*[Nn]oDuplicate.*[Ss]tage\|func Test.*[Cc]ementStageAgree" internal/engine/freight/factorytype*_test.go`); `grep -rn "jobs\|blight\|power" internal/engine/freight/factorytype*.go` (excluding `_test.go`) shows no factorytype-local re-declaration of a jobs/power/water/blight literal that `data/freight.json` already holds. **False-pass risk (logged as ASM-680, P1):** two files each holding their own copy of "cement jobs = 30" would pass any "jobs exists and is queryable" read today while silently drifting the moment either is rebalanced — the check requires the resolved values to *agree through one path*, which a duplicated copy cannot survive under mutation.

- **AC-6 (footprint + blight class as facility-level parameters — the Manufacturing/Heavy-Industry distinction).** Each factory type carries a footprint (cells) and a blight class (a documented enum, matching `data.catalogue.md` AC-7's convention), and the two are *distinct per type*: heavy-industry types (steel mill, chemicals converter, cement) resolve to a materially larger footprint and a higher blight class than light-manufacturing types (electronics, textiles, assembler). Check: `go doc ./internal/engine/freight` shows a footprint and blight-class accessor; a passing test asserts steel-mill's footprint and blight class are greater than electronics', and that the blight class maps to a value from the documented enum, not a free-form string (`grep -rn "func Test.*[Ff]ootprint\|func Test.*[Bb]lightClass\|func Test.*[Hh]eavyVsLight" internal/engine/freight/factorytype*_test.go`). **False-pass risk:** a single "blight class = medium" on every factory would pass "factories have a blight class" while §34's Manufacturing-vs-Heavy-Industry buffer rules have no mechanical teeth — the check requires the heavy/light distinction to resolve to different footprint and blight values.

- **AC-7 (§46 FDI archetype mapping + §17 utility draw).** The §46 FDI archetypes map onto factory types with the archetype's named character preserved as a per-type parameter: semiconductor fab → electronics (the "colossal 40 MW / utility boss-fight" utility draw), chemicals complex → chemicals converter (the "blight class high; feeds plastics chain"), steel process plant → steel mill (the "§33 chain anchor"). The utility draw is a per-type power/water coefficient (matching §17's producer-coefficient discipline), and the electronics type's utility draw is materially higher than textiles' or assembler's. Check: `go doc ./internal/engine/freight` shows a utility-draw accessor (power and water); a passing test asserts electronics' utility draw exceeds textiles', and that the chemicals-converter type's blight class exceeds the assembler's (`grep -rn "func Test.*[Ff]diArchetype\|func Test.*[Uu]tilityDraw\|func Test.*[Ss]emiconductorVsTextiles" internal/engine/freight/factorytype*_test.go`). **False-pass risk:** an archetype mapping that is prose-only (a comment "semiconductor fab = electronics") with no per-type utility/blight consequence would satisfy "the archetype is named somewhere" while the §46 "utility boss-fight" / "blight class high" character is unreadable in state — the check requires the per-type parameters to carry the character.

### Error handling

- **AC-8 (GR#7; unknown type / malformed data — no silent default).** Resolving an unknown factory-type key, or loading a `data/factorytypes.json` that fails schema validation (a type missing its footprint or input-output pair, a negative jobs count, an unknown blight-class enum value, a dangling stage reference, a field of the wrong JSON type — GR#16), produces a registry-sourced error (a new `MET-`-range code claimed at build time) — never a panic, never a silent default-substituted parameter set. Check: `grep -n "MET-" internal/engine/freight/factorytype*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownFactoryType\|func Test.*[Mm]alformedFactorytypes\|func Test.*[Ww]rongTypeFactorytypes" internal/engine/freight/factorytype*_test.go`) — **GR#7 assertion, stated explicitly:** the test asserts the returned error's registry code matches the claimed `MET-` code AND that no partially-loaded or default-substituted catalogue was produced, not merely that a matching-named test function exists.

### Determinism & safety

- **AC-9 (GR#21).** Loading and resolving the factory-type catalogue is a deterministic function of `(data file, type key)` — loading the same `data/factorytypes.json` twice produces byte-identical resolved parameter sets, and resolution never depends on map-iteration order. Check: `grep -rn "func Test.*[Dd]eterminis.*[Ff]actorytype" internal/engine/freight/factorytype*_test.go`; `grep -rn "time.Now\|time.Since" internal/engine/freight/factorytype*.go` (excluding `_test.go`) returns no matches.

- **AC-10 (SG-7 scoped; GR#21).** `go test ./internal/engine/freight/... -race -count=1 -run FactoryType` passes with no data race (scoped via `-run`, since the shared package also carries `engine.freight.md` AC-16's race suite); `grep -n "go func()" internal/engine/freight/factorytype*_test.go` finds at least one concurrency test.

- `engine.firms.md`'s firm lifecycle (founding, growth, credit, failure) — the *stages-register-as-firms* call is `engine.freight.md` AC-4's obligation; this catalogue supplies the per-type jobs/input-output a firm registers with, it does not create or manage firms.

- `engine.consumption`/utility-network mechanics — the utility draw is a per-type coefficient reference, not the network solve itself (§17/`engine.consumption`).
- `data.catalogue`/`data/buildings.json` build-catalogue entries (unlock/cost/capacity) for the same structures — FEAT-010's; this file's types are the simulation parameters, and the build entry must reference a type key, never duplicate the numbers (ASM-694).
