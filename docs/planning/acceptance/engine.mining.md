## User stories

- **US-1.** As a prospected tile, I need a geology-gated extraction type (chalk quarry, sand/gravel pit, clay pit+brickworks, ragstone quarry, deep coal mine, offshore dredger) each with distinct outputs and site character, consuming `engine.world`'s already-revealed geology layer (`WorldAPI.IsProspected`/geology query, `engine.world.md` AC-7), so mining siting is geography-driven per §32, not arbitrary.
- **US-2.** As ANY module that owns a blighting object — mines (self), heavy industry, abattoir, incinerator, landfill, airport, motorway — I need to register that object with `BlightAPI` and get back a noise/viewshed effect computed from real terrain, so the blight model is genuinely general (per its own code.json pattern text and its own module title), not mining-specific machinery other modules merely cite in prose.
- **US-3.** As a home cell that sits behind the escarpment from a registered blighting object, I need my viewshed exposure to be computed from actual intervening elevation — not a flat radius — so that siting behind high ground is a real, mechanically-earned mitigation exactly as §32 describes ("the escarpment hides or exposes things honestly"), and two home cells at identical straight-line distance from the same source can receive genuinely different "seen" outcomes.
- **US-4.** As a player who builds a screening bund or tree belt, I need that earthwork to change the SAME viewshed computation any other terrain change would (not a flat percentage discount applied after the fact), so mitigation is mechanically identical to natural topography, per §32's "siting behind the escarpment is free mitigation — topography as gameplay."
- **US-5.** As an exhausted extraction site, I need a reclamation command (lake/park/landfill-void) that, when the void option is chosen, hands off to the SAME mechanic `engine.refuse` uses for landfill lifecycle (§32's own cross-reference: "then §25 rules") — **the `engine.refuse`↔`engine.mining` edge is still absent (see Escalations)** — rather than a mining-local reimplementation.
- **US-6.** As a deep coal mine approaching exhaustion, I need a subsidence-risk radius and a documented, queryable "workforce at risk" figure at closure, so the deliberate "scripted-by-you Detroit test" §32 names is a real, checkable consequence a player can see coming, not a narrative aside with no state behind it.

## Scope

Geology-gated extraction (six site types, prospecting-revealed via `engine.world`); the GENERAL blight model — `BlightAPI` registration surface, noise-radius (dBA falloff) and elevation-based viewshed computation, mental-health/land-value effect stacking; real-earthwork mitigations (bunds, tree belts with grow-in delay, enclosures, night bans as a policy lever); reclamation on exhaustion (lake/park/landfill-void); deep-mine subsidence and closure consequences. Does not include the six blighting-object-source modules' own siting decisions (heavy industry, abattoir, incinerator, landfill, airport, motorway each own when/where they build) — only the shared effect computation those objects register against.

## Acceptance criteria

### Functional — geology-gated extraction

- **AC-1 (GR#20; code.json inbound contract).** A `BlightAPI` (or a `MiningAPI` exposing extraction plus a shared `BlightAPI` surface — documented which) exists matching code.json's pattern "any module registers blighting objects; viewshed computed from WorldAPI elevation": a registration command taking a blighting object's location + noise/visual profile, and a query returning the effect at any home cell. Check: `go doc ./internal/engine/mining` shows a `RegisterBlightingObject` (or equivalent) command and an `EffectAt` (or equivalent) query; `grep -n "world\.WorldAPI\|world\.CellAt" internal/engine/mining/*.go` confirms the viewshed path genuinely calls into `engine.world`'s `CellAt`, not a mining-local terrain copy.
- **AC-2 (§32 six extraction types, geology-gated).** Each of the six named extraction types (chalk quarry, sand/gravel pit, clay pit+brickworks, ragstone quarry, deep coal mine, offshore dredger) is a distinct, siteable structure whose availability is gated by `engine.world`'s prospected geology query (chalk everywhere, clay/sand-gravel/coal region-restricted per `engine.world.md` AC-6), with a distinct documented output and a per-type extraction rate (ASM-317, data-sourced). Check: `go doc ./internal/engine/mining` shows all six named site types with distinct output accessors; a passing test asserts attempting to site a deep-coal-mine on a western (non-coal) prospected tile is rejected while an eastern-tile attempt succeeds (`grep -rn "func Test.*[Ss]ite.*[Gg]eology\|func Test.*[Cc]oalGate" internal/engine/mining/*_test.go`).
- **AC-3 (§32 deep coal — headgear/spoil tip/subsidence).** A deep coal mine carries a documented spoil-tip footprint (itself a minor blighting object, registered against `BlightAPI` like any other) and a subsidence-risk radius within which nearby structures/land carry a documented risk flag (ASM-316, data-sourced magnitude) distinct from the noise/viewshed blight effect. Check: `go doc ./internal/engine/mining` shows a subsidence-radius accessor separate from the noise/viewshed accessors; a passing test asserts a cell within the radius carries the risk flag and a cell just outside does not (`grep -rn "func Test.*[Ss]ubsidence" internal/engine/mining/*_test.go`).

### Functional — the GENERAL blight model (the core of this module)

- **AC-4 (§32; "computed from real elevation" — the check the brief specifically demands, US-3).** `EffectAt` (or equivalent)'s "seen" (viewshed) component is computed via a genuine line-of-sight test against `WorldAPI.CellAt(...).Elevation` along the path between the blighting object and the queried home cell — NOT solely a function of planar distance. **The test fixture is constructed so elevation and distance disagree, per the brief:** a synthetic ridge is placed between a blighting-object cell and TWO home cells, both at IDENTICAL straight-line distance from the object — home cell A sits directly behind the ridge (a higher-elevation cell lies on the straight path between object and A), home cell B sits on flat, unobstructed ground at the same distance. Check: a passing test asserts A's "seen" land-value/satisfaction hit is materially SMALLER than B's (down to zero, if the implementation's line-of-sight is fully blocking) despite A and B being equidistant from the source (`grep -rn "func Test.*[Vv]iewshed.*[Rr]idge\|func Test.*[Ee]levation.*[Bb]lock" internal/engine/mining/*_test.go`). **This is precisely the check a radius-based blight model fails and the brief is written against:** a radius model treats A and B identically because it only ever reads distance — it cannot fail an assertion that only checks "blight decays with distance" (both A and B are at the same distance, so a radius model gives them the same, non-zero answer), which is exactly why that weaker assertion is insufficient and is NOT what this AC checks. A second, complementary assertion in the same test: raising the ridge's elevation (making it MORE occluding, distance unchanged) must strictly reduce A's seen-effect further, and lowering it must strictly increase A's seen-effect — proving the result tracks elevation continuously, not merely a binary "is there a ridge" flag that could itself be gamed by a radius model with a hand-authored exception list.
- **AC-5 (§32 noise radius, correctly distance-based — the companion, non-viewshed half).** The "heard" (noise) component is a genuine dBA-falloff function of distance (ASM-316, data-sourced curve shape) — unlike the "seen" component, this one IS legitimately radius/distance-driven per spec, and this AC exists specifically to confirm the two components are NOT accidentally merged or NOT accidentally both replaced by the same elevation-only or distance-only function. Check: a passing test asserts the noise component is monotonically non-increasing with distance regardless of elevation (using the same ridge fixture as AC-4 — A and B's HEARD component should be equal or near-equal since noise doesn't care about line-of-sight the way sight does, only distance and terrain-conducted attenuation if modelled) while the SEEN component differs sharply between A and B at that same distance (`grep -rn "func Test.*[Nn]oise.*[Dd]istance" internal/engine/mining/*_test.go`). **What this rejects:** an implementation that computes ONE combined "blight" number purely from distance for both heard and seen would pass AC-4's weaker sibling checks if AC-4 only asserted "seen differs somewhere" — pairing AC-4 and AC-5 in the same fixture is what proves the two are mechanically distinct, not just differently named.
- **AC-6 (§32 stacking).** A home cell that both hears AND sees the same blighting object receives BOTH the mental-health/satisfaction hit and the land-value/satisfaction hit, and the combined satisfaction effect is not simply the larger of the two (both stack, per spec's explicit "both stack"). Check: a passing test constructs a cell within both the noise radius and the (unobstructed) viewshed, and asserts the combined satisfaction penalty exceeds either individual component's penalty alone (`grep -rn "func Test.*[Ss]tack" internal/engine/mining/*_test.go`).
- **AC-7 (§32 real-earthwork mitigation — same viewshed computation, US-4).** A screening bund or tree belt is modelled as a real terrain/occlusion object that participates in the SAME line-of-sight computation AC-4 exercises (e.g. as an elevation delta or an explicit occluder inserted into the path check), not a flat percentage reduction applied to the final blight number; tree belts additionally carry a documented 5-year grow-in delay before reaching full occlusion effect. Check: a passing test inserts a bund/tree-belt occluder into the AC-4 fixture's line of sight for a previously-unobstructed cell and asserts its seen-effect drops using the SAME code path AC-4's ridge case exercises (`grep -rn "func Test.*[Bb]und\|func Test.*[Tt]reeBelt" internal/engine/mining/*_test.go` — the test must call the identical viewshed function AC-4's test calls, not a separate "apply mitigation percentage" helper); a second test asserts a freshly-placed tree belt's occlusion is materially weaker than the same belt 5 simulated years later. **False-pass risk:** a mitigation system implemented as `finalBlight *= (1 - mitigationPercent)` would satisfy "mitigation exists and reduces blight" on a shallow read while being mechanically unrelated to the viewshed the escarpment itself uses — the check requires the SAME function, which a percentage-multiplier bypass cannot share.
- **AC-8 (§32 mitigations, non-viewshed).** Enclosure buildings and night-working-ban policy each independently reduce the noise (AC-5) component specifically, documented and tested separately from the viewshed mitigations of AC-7. Check: `go doc ./internal/engine/mining` shows enclosure/night-ban accessors distinct from the bund/tree-belt ones; a passing test asserts each reduces the noise component without affecting the viewshed component (`grep -rn "func Test.*[Ee]nclosure\|func Test.*[Nn]ightBan" internal/engine/mining/*_test.go`).

### Functional — reclamation and closure

- **AC-9 (§32 exhaustion and reclamation).** An exhausted site (extraction reaches its data-defined capacity) can no longer produce further output and exposes a reclamation command with (at minimum) lake and country-park options fully implemented in this package; the landfill-void option is **still blocked after BUG-058 closed (c36778b)** — no `engine.refuse`↔`engine.mining` edge exists to hand off to §25's rules (c36778b registered `engine.refuse`↔`engine.farming` instead, a different pair); the edge is now governed by the collaborations gate rather than "pending BUG-058" (see Escalations). **Tripwire (mechanical, BUG-100):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.mining'); process.exit(m.outbound.calls.some(c=>c.key==='engine.refuse')?1:0)"` must exit 0 (edge still absent); a nonzero exit means the edge landed and the landfill-void reclamation option must be re-armed into AC-9's scope with a real check. Check: `go doc ./internal/engine/mining` shows a `Reclaim` command with at least `Lake`/`Park` options; a passing test exhausts a site and asserts further extraction is rejected while `Reclaim(Lake)`/`Reclaim(Park)` succeed and change the site's registered blight status (a reclaimed lake/park is no longer a registered blighting object) (`grep -rn "func Test.*[Rr]eclaim" internal/engine/mining/*_test.go`); `internal/engine/mining/doc.go` states the landfill-void path is blocked (edge absent), noting BUG-058 is closed and the edge is governed by the collaborations gate.
- **AC-10 (§32 closure consequence).** Deep-mine closure exposes a queryable "workforce at risk" figure (the mining-jobs-culture headcount tied to that site) at the moment closure is triggered, distinct from a generic layoff event — the "scripted-by-you Detroit test" requires the player to be able to see the number coming, per US-6. Check: `go doc ./internal/engine/mining` shows a workforce/closure-impact accessor; a passing test asserts querying it before triggering closure returns a nonzero figure tied to the specific mine (`grep -rn "func Test.*[Cc]losure.*[Ww]orkforce" internal/engine/mining/*_test.go`).

### Error handling

- **AC-11 (GR#7).** Attempting to site an extraction on ungeologically-gated or unprospected land, registering a blighting object with an out-of-extent or negative noise/visual profile, or reclaiming an already-reclaimed site, produces a registry-sourced error (new `MET-E`-range code) rather than a silent no-op. Check: `grep -n "MET-" internal/engine/mining/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]ngeologyGated\|func Test.*[Dd]oubleReclaim" internal/engine/mining/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches the claimed `MET-E` code AND that no site/blighting-object record was created or mutated as a side effect, not merely that a matching-named test function exists.

### Determinism, safety & scale

- **AC-12 (GR#21).** Viewshed/noise computation, extraction accumulation, and reclamation state transitions are deterministic functions of `(worldSeed, tick, prior state, commands)`, byte-identical across repeated runs and worker counts — this matters specifically for the viewshed line-of-sight algorithm (AC-4), since a floating-point elevation comparison near a threshold is exactly the kind of computation that can silently diverge across shard/worker boundaries if not carefully pinned. **Typo fix (BUG-100, 2026-08-11):** the prior grep pattern's first alternative, `[Dd]etermnis`, was a misspelling of "determinis[tic]" (missing the "i" after "m") — and the pattern's second alternative, plain `[Dd]eterminis`, matched ANY test with "deterministic" anywhere in its name across the whole package, not specifically the viewshed/float-divergence case this AC's prose is about, making the check pass on an unrelated determinism test with the misspelling doing no work either way — the purest can-never-fail-for-the-stated-reason instance in this file. Corrected to require the test name to name the viewshed case specifically. Check: `grep -rn "func Test.*[Vv]iewshed.*[Dd]eterminis\|func Test.*[Ss]hardInvarian.*[Vv]iewshed" internal/engine/mining/*_test.go`.
- **AC-13 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/mining/*.go` (excluding `_test.go`) returns no matches.
- **AC-14.** `go test ./internal/engine/mining/... -race -count=1` passes; `grep -n "go func()" internal/engine/mining/*_test.go` finds at least one concurrency test.

## Out of scope

- `engine.world`'s terrain/elevation storage and `CellAt` implementation — this item only calls it (AC-1/AC-4).
- Any individual blighting-object-source module's own siting logic (`engine.build`'s heavy-industry placement, `engine.farming`'s abattoir, `engine.refuse`'s landfill/incinerator, roads/traffic's motorway, and any future airport module) — this item only provides the shared registration+effect surface those modules would call, per GR#20; those four registration edges are currently unregistered (see Escalations) and this item cannot force their creation.
- `engine.wellbeing`'s and land-value's own formula for converting a "heard"/"seen" input into a citizen-level mental-health/land-value delta — this item supplies the input via the already-registered `engine.mining`→`engine.wellbeing` outbound edge; the driver math itself belongs to `engine.wellbeing`.
- `engine.refuse`'s own landfill lifecycle mechanics — this item only hands off to them once the reclamation-to-landfill-void edge exists (AC-9).
- Exact extraction rates, dBA-falloff curve shape, and subsidence-radius magnitude — balance data pending M2 tuning (ASM-316, ASM-317).
