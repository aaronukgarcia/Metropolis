## This file's role (and the ownership split vs FEAT-099)

FEAT-099 (`feat.containerport`) owns the **cargo** half of the port: the deep-sea container terminal's berths × crane rate × hours, intermodal rail, customs/smuggling, and the importer→exporter flip — the `resources-design-brief.md` §8 "Felixstowe-scale container port" tier. **This feature does not re-specify any of that** (GR#3). FEAT-139 owns the **non-cargo** harbour: the fishing fleet (fresh-food landings that draw the shared fishing stock and feed `engine.freight`'s `fish→processing` chain) and the RoRo passenger/car ferry (a sea transport link that complements the Chunnel as a second crossing). The two files' boundary is the same "different facility class, same shared `engine.freight` machinery" split `feat.containerport.md` already draws against `engine.freight.md` — see ES-1/ASM-1011.

## User stories

- **US-1.** As the player, I need the harbour to **start tiny and expand** — a single fishing boat and a single RoRo ferry, each growing through distinct tiers to fleet-scale and Dover-scale — so the harbour is a real ladder of modelled stages, not one flat "harbour exists" constant (ASM-1010).
- **US-2.** As `engine.farming` (MOD-045, the registered owner of the fishing stock), I need the fleet's landings to **draw down my fishing-stock figure**, so fishing is a shared resource with real depletion, not a harbour-local fish counter that can never run out (ASM-1008).
- **US-3.** As `engine.freight` (MOD-047), I need fishing landings to enter the **`fish→processing` food-chain stage** as conserved tonnes, so the food chain accounts the fish, not a second harbour-local food ledger (ASM-1008).
- **US-4.** As the player watching a ferry queue, I need the ferry's throughput to be a **real function of RoRo capacity, crossing time, and weather** — more cars+passengers and calmer seas move more; demand exceeding capacity queues visibly — so the ferry is a transport link, not a passenger number on a sign.
- **US-5.** As the Chunnel (FEAT-100), I need the ferry to be a **distinct second crossing** with its own sea-crossing trade — weather-vulnerable, cheaper, car-carrying — that does **not** re-use my TBM/bundling/interconnection machinery, so the two crossings genuinely differ rather than duplicate (§53/§PT).
- **US-6.** As `engine.season` (MOD-027), I need the ferry's weather-cancel to read a **seasonal/weather signal** (month index, storm season), so the cancel rate is a directional input the player can watch, not a hardcoded "sometimes cancelled" constant (ASM-1009).

## Scope

The harbour as a growing facility: the fishing scale ladder (single boat → fleet → optional Dover fish dock) with data-driven boat counts and landings throughput; the ferry scale ladder (ferry pier → RoRo external terminal → Dover-scale special facility) with data-driven RoRo car+passenger capacity, crossing time, and crossings/day; the fishing-stock draw through `engine.farming`'s `FarmingAPI` (no separate fish ledger); landings handed into `engine.freight`'s `fish→processing` chain stage; the ferry's throughput/queue/weather trade; the catalogue reconciliation against the existing `fishing_quay`/`fishing_harbour`/`ferry_pier_terminal`/`ferry_terminal_external` entries. No `engine.farming` fishing-stock/BDI mechanics (consumed), no `engine.freight` berth/crane/customs/chain machinery (extended, not reimplemented), no Chunnel TBM/bundling/interconnection machinery (`feat.channeltunnel`/`engine.tunnels` — explicitly not reused, AC-9), no `engine.coastal` arrival/rescue machinery (see ES-5), no `engine.season` curve computation (consumed), and no final figure magnitudes (Aaron's balance pass).

## Acceptance criteria

### Functional — the fishing scale ladder

- **AC-1 (GR#20; shared-package surface, feature-shape per ASM-1007).** A harbour surface exists on the shared `internal/engine/freight` package (a fishing-fleet + ferry type set, not a fork), distinct from `engine.freight.md` AC-1's `FreightAPI` port/chain/customs surface and from `feat.containerport.md`'s deep-sea-tier surface, and consuming `FreightAPI`, `FarmingAPI`, and `SeasonAPI` via direct calls rather than reimplementing any of them. Check: `go doc ./internal/engine/freight` shows harbour accessors (fishing tier, ferry tier) distinct from `FreightAPI`'s; `internal/engine/freight/doc.go` (or the harbour file's package doc) notes the shared-package, no-separate-inbound-contract arrangement (`grep -n "feat.harbour" internal/engine/freight/doc.go`), mirroring `feat.containerport.md` AC-1's convention.

- **AC-2 (GR#15; fishing scale ladder — single boat → fleet, every stage a distinct modelled tier, never one constant).** The fishing capacity is a **ladder of distinct tiers** loaded from `data/harbour.json`: `fishing_quay` (single boat) → `fishing_harbour` (fleet) → optionally a Dover fish-dock tier, each carrying its own data-driven boat count and landings t/day figure, so adding/upgrading a tier changes landings. It is **not** a single `landingsPerDay` constant wearing a tier label. Check: a passing test mutates one tier's boat count in the loaded fixture and asserts the computed landings for that tier (and only that tier) reflect the change; a second asserts the tiers sort strictly upward in milestone/cost and that the fleet tier out-lands the single-boat tier (`grep -rn "func Test.*[Ff]ishing.*[Ll]adder\|func Test.*[Ss]ingleBoat.*[Ff]leet\|func Test.*[Dd]ataDriven.*[Hh]arbour" internal/engine/freight/*_test.go`); `grep -nE "[0-9]+" internal/engine/freight/harbour*.go` (excluding `_test.go`) finds no bare boat-count/landings-shaped numeric literals outside doc-comment prose. **False-pass risk:** a single `landingsPerDay` constant that a UI reads as "fishing exists" would pass a shallow grep while the core "single boat → fleet" ladder is unmet — the check requires at least two tiers resolving to two different landings figures from data, and the upgrade path to move between them. **Balance-regime note:** magnitudes are placeholders (AC-16); this AC checks *tiered and data-driven*, not any magnitude.

### Functional — fishing ties into engine.farming's stock and the food chain

- **AC-3 (GR#20; fishing draws engine.farming's stock — no separate fish ledger, ASM-1008).** The fleet's landings draw down `engine.farming`'s fishing-stock figure through `FarmingAPI` (the registered surface `engine.farming.md` AC-6 names — watercourse-quality-gated), and there is **no harbour-local fish-stock ledger** of its own. Overfishing — fleet draw exceeding the stock's regeneration — depletes the shared stock and, directionally, reduces subsequent landings; the stock is never a harbour-owned number that a junior could silently fork. Check: `grep -rn "farming\.\|FarmingAPI" internal/engine/freight/harbour*.go` (excluding `_test.go`) shows a real call into `engine.farming`'s stock surface; `grep -nE "[Ff]ishStock|[Ss]tock.*[Ff]ish" internal/engine/freight/harbour*.go` (excluding `_test.go`) finds no harbour-local fish-stock store type; a passing test reduces the farming stock (via a fake satisfying `FarmingAPI`) and asserts landings fall, and a second drives fleet draw above the stock and asserts the stock is depleted rather than the harbour inventing fish (`grep -rn "func Test.*[Ff]ishStock.*[Dd]raw\|func Test.*[Oo]verfish" internal/engine/freight/*_test.go`). **False-pass risk:** a harbour-local `fishStock` field that is displayed and only *cosmetically* referenced to farming would pass a "fishing exists" read while the shared-resource depletion (the load-bearing requirement) never happens — the check requires the draw to resolve through `FarmingAPI` and the overfishing depletion to be observable on the *farming* side. **Dependency note:** `engine.farming` is `open` with no code; its fishing-stock method name is owned by `engine.farming.md`, not pinned here (ASM-1008).

- **AC-4 (GR#20; landings feed the food chain via engine.freight's fish→processing stage, ASM-1008).** Fishing landings enter `engine.freight`'s food chain as the **`fish→processing`** stage's input (§33's chain table, "Food … fish→processing"), accounted as conserved tonnes through `FreightAPI` — there is no harbour-local food/fish tonnage ledger that bypasses the chain. Check: `grep -rn "freight\.\|FreightAPI" internal/engine/freight/harbour*.go` (excluding `_test.go`) shows the landings handed into `engine.freight`'s chain-stage surface; a passing test lands N tonnes of fish and asserts the `fish→processing` stage's input rises by N via `FreightAPI`'s own accessor (not a harbour mirror) (`grep -rn "func Test.*[Ff]ish.*[Pp]rocessing\|func Test.*[Ll]andings.*[Cc]hain" internal/engine/freight/*_test.go`). **False-pass risk:** a harbour-local `landingsTonnes` field that never reaches the chain would pass a "landings exist" grep while the food chain (and its mass-conservation identity) never sees the fish — the check requires the `FreightAPI` handoff.

### Functional — the ferry scale ladder and the transport link

- **AC-5 (GR#15; ferry scale ladder — single RoRo → Dover-scale special facility, distinct modelled tiers, ASM-1010).** The ferry capacity is a **ladder of distinct tiers** loaded from `data/harbour.json`: `ferry_pier_terminal` (coastal hop) → `ferry_terminal_external` (single RoRo) → a Dover-scale special-facility tier, each with its own data-driven RoRo car + passenger capacity and crossings/day figure. It is **not** a single `paxPerDay` constant. Check: a passing test mutates one tier's RoRo capacity in the loaded fixture and asserts that tier's throughput reflects the change; a second asserts the tiers sort strictly upward in milestone/cost and the Dover-scale tier out-carries the single RoRo (`grep -rn "func Test.*[Ff]erry.*[Ll]adder\|func Test.*[Rr]oRo.*[Dd]over\|func Test.*[Ff]erryTier" internal/engine/freight/*_test.go`). **False-pass risk:** a renamed `ferry_terminal_external` entry with the same capacity function would pass a "ferry exists" grep while "Dover-scale special facility" is unmet — the check requires the Dover-scale tier to sort above and to change the capacity model's scale, not just its label (the same discipline `feat.containerport.md` AC-2 states for the deep-sea tier). **Balance-regime note:** magnitudes are placeholders (AC-16).

- **AC-6 (GR#3; catalogue reconciliation — extend or add-above, no silent third entry).** The harbour is reconciled against the existing `fishing_quay`, `fishing_harbour`, `ferry_pier_terminal`, and `ferry_terminal_external` entries in `data/buildings.json`: exactly **one** of two shapes, chosen and documented — (a) the Dover-scale ferry *is* `ferry_terminal_external` and this feature enriches it in place (adds RoRo/weather/queue fields without renaming), or (b) it is a **distinct, fuller** Dover-scale entry that sits beside `ferry_terminal_external` and whose unlock/cost sorts strictly above it, with the relationship documented. There is **no** third shape: a silent second ferry entry with no stated relationship is a GR#3 violation. Check: `grep -n "ferry_terminal_external\|fishing_harbour\|fishing_quay" data/buildings.json` still resolves; a passing test loads the catalogue and asserts there is exactly one entry the Dover-scale tier resolves to as its anchor, and that any second entry (shape b) sorts above `ferry_terminal_external` in milestone/cost (`grep -rn "func Test.*[Cc]atalogue.*[Rr]econcil.*[Hh]arbour\|func Test.*[Dd]over.*[Ee]ntry" internal/engine/freight/*_test.go`). **False-pass risk:** adding `dover_ferry` alongside `ferry_terminal_external` with divergent unlock/cost and no documented relationship would pass a "a Dover ferry exists" grep while leaving the supplement with two conflicting ferry entries — the check requires the relationship to be explicit and the ordering (if two entries) asserted. (ASM-1010 — this reconciliation is Aaron/Bill's call.)

- **AC-7 (ferry transport link — RoRo capacity + crossing time + queue, directionally).** The ferry's throughput is a documented function of its **RoRo capacity** (cars + passengers) and its **crossing time** (crossings/day = capacity ÷ a data-driven crossing-duration term): more capacity or a shorter crossing yields more throughput, and demand exceeding capacity forms a **queryable queue** (vehicles/passengers waiting) that grows under sustained over-demand and drains when capacity is added — not silently dropped. Check: a passing test builds a small RoRo ferry, floods demand above capacity, asserts a queue forms and grows day-over-day, then enlarges the ferry (higher tier) and asserts the queue drains (`grep -rn "func Test.*[Ff]erry.*[Qq]ueue\|func Test.*[Cc]rossing.*[Tt]ime\|func Test.*[Rr]oRo.*[Cc]apacity" internal/engine/freight/*_test.go`). **False-pass risk:** a flat `paxPerDay` with demand clamped to it (no queue state) would pass a "throughput is queryable" read while the "queue trade" is cosmetic — the check requires the queue to be stateful and responsive to capacity changes. **Balance-regime note:** crossing time and capacity are placeholders (AC-16); the queueing *behaviour* is the invariant.

- **AC-8 (ferry weather cancel — directional, consumes engine.season, ASM-1009).** Crossings are subject to a **data-driven weather/season cancel rate**: a storm-season / bad-weather month index produces fewer effective crossings than a calm-season index, reducing throughput directionally. The cancel input is read from `engine.season`'s `SeasonAPI` (month-index curves), never a hardcoded "sometimes cancelled" constant and never wall-clock weather. Check: a passing test holds the ferry fixed and varies the month-index (storm vs calm) and asserts effective crossings fall in the storm month, with the cancel rate read from `data/harbour.json` (`grep -rn "func Test.*[Ww]eather.*[Cc]ancel\|func Test.*[Ss]tormSeason.*[Ff]erry" internal/engine/freight/*_test.go`); `grep -rn "season\.\|SeasonAPI" internal/engine/freight/harbour*.go` (excluding `_test.go`) shows the call into `engine.season`. **False-pass risk:** a constant `cancelRate` unaffected by season would pass a "weather exists" read while the directional storm-season trade is unmet — the check requires the cancel rate to respond to the month index. **Dependency note:** the `feat.harbour → engine.season` edge is unregistered (ES-4); `engine.season`'s month-index method name is owned by `engine.season.md`, not pinned here.

- **AC-9 (GR#20/GR#3; complements, does not duplicate, the Chunnel — a distinct second crossing, ASM-1011).** The ferry is a **sea transport link distinct from the Chunnel**: it is **not** expressed through `engine.tunnels`/`engine.rail` (the Chunnel's TBM/bundling/interconnection machinery, `feat.channeltunnel.md` AC-2/AC-5), and it carries its own RoRo + weather + queue model. The two crossings' throughput figures are independently queryable — the ferry's weather-cancel trade is what the Chunnel (weather-immune) lacks, and the Chunnel's TBM-capex/prestige character is not restated here. Check: `grep -rn "tunnels\.\|rail\.\|TunnelsAPI\|RailAPI" internal/engine/freight/harbour*.go` (excluding `_test.go`) finds **no** ferry-crossing call into the Chunnel's machinery; a passing test builds both a ferry and a (stubbed) Chunnel and asserts each crossing's throughput figure moves independently of the other's (`grep -rn "func Test.*[Ss]econdCrossing\|func Test.*[Ff]erry.*[Cc]hunnel.*[Ii]ndep" internal/engine/freight/*_test.go`). **False-pass risk:** reusing the Chunnel's rail-interconnection path for the ferry (or a ferry that reads `feat.channeltunnel`'s cost model) would pass a "second crossing exists" grep while the "complements not duplicates" requirement fails — the check requires the ferry's model to be harbour-local and independent of the tunnel/rail surfaces. **Dependency note:** `engine.rail`/`engine.tunnels` are `open`; this AC is a *negative* constraint (do not call them), so it needs no registered edge.
