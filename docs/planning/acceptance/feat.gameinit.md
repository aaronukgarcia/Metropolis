## User stories

- **US-1.** As the player, I need a choice of two initialization modes at new-game start — Unlimited Money (sandbox: financial checks bypassed, un-depletable reserve) or Real (finite starting capital, full financial-failure loop active) — so I can choose between experimentation and the survival game.
- **US-2.** As the game session, I need the chosen mode to be locked at initialization and immutable for the whole session — no in-game settings toggle, no dev-console flip, no mid-save re-serialization changing it — so the mode is a property of the game, not a state that can drift (GR#12: config lock is the invariant).
- **US-3.** As the save system (`feat.saveux`), I need the mode declared in the save metadata on the initial save and enforced on every load — a load whose metadata carries a different mode than the one the session started with must fail closed, never silently re-mode the game.
- **US-4.** As `engine.finance`, I need the mode to gate the failure loop: in Unlimited mode, placement/OPEX/payroll financial checks are bypassed and insolvency/debt-rating triggers are disabled; in Real mode they are fully active — so the same finance code serves both, with the mode as a gate, never two divergent implementations.
- **US-5.** As `ui.screen.finance`, I need the mode visible (infinite indicator in Unlimited; P&L/balance/budget in Real) — so the UI never lies about whether money is a constraint.

## Scope

The initialization-mode config (two modes), the lock-at-startup + immutable-for-session invariant, the save-metadata declaration + fail-closed load enforcement, and the `engine.finance` gate that bypasses the failure loop in Unlimited mode. It does **not** re-implement finance bookkeeping, save serialization, or the finance UI — it consumes them. The starting-capital value is a data-file-sourced placeholder pending Aaron's balance pass (balance regime; see AC-6).

## Acceptance criteria

### Functional — the mode gate

- **AC-1 (US-1; both modes exist and are mutually exclusive).** A new game is initialized in exactly one of two modes: `unlimited` or `real`. The mode is captured at initialization and is the single source of truth for the finance bypass. Check: `go doc ./internal/engine/core GameMode` (or the dispatch-resolved config surface) documents the two-mode enum; a passing test initializes in each mode and asserts the mode is set to exactly that value and never both/neither (`grep -rn "func Test.*[Gg]ameMode" internal/engine/core/*_test.go`). **False-pass risk:** a mode that only lives in the UI or only in the save file, with the engine reading a zero-value default — the engine's own mode must be a real enum value read back from the init call.
- **AC-2 (US-4; Unlimited bypasses the finance failure loop; Real does not).** With `unlimited`, `FinanceAPI` placement/OPEX/payroll financial checks pass regardless of balance, and the insolvency/debt-rating triggers are inert (`InsolvencyMonths` never advances, `CreditRatingNow` never downgrades to failure on its own). With `real`, the existing finance failure loop runs unchanged. Check: passing tests drive the same under-funded scenario in both modes and assert (a) `unlimited` — placement succeeds with zero balance and `InsolvencyMonths()` stays at its non-failing value across months; (b) `real` — the same scenario produces the existing insolvency path (`grep -rn "func Test.*[Mm]ode.*[Bb]ypass\|func Test.*[Uu]nlimited.*[Ii]nsolven" internal/engine/finance/*_test.go`). **False-pass risk:** a bypass implemented as "unlimited mode has a huge balance" instead of a gate — the check must assert the mode is the *cause* (toggle mode, same state, different outcome), not just that a rich city doesn't fail.
- **AC-3 (US-2; locked at startup, immutable for the session).** Once initialized, the mode cannot be changed by any in-game path: settings, dev console, command, or re-serialization. Check: `grep -rn "func Test.*[Mm]ode.*[Ii]mmutab\|func Test.*[Ll]ockedMode" internal/engine/core/*_test.go`; a passing test attempts every mode-changing surface (a `SetGameMode`-style command, a settings write) and asserts each is rejected with a registry-sourced typed error, and the mode read-back is unchanged (GR#12).

### The save-metadata lock (feat.saveux)

- **AC-4 (US-3; mode declared in save metadata, initial save carries it).** The `GameMode` field is written into the save `Meta` (extend `internal/engine/save/kind.go`'s `Meta` struct) on the initial save and every subsequent save, so a session's mode is recoverable from any bundle. Check: `go doc ./internal/engine/save Meta` shows the `GameMode` field; a passing save/load round-trip preserves the mode verbatim (`grep -rn "func Test.*[Gg]ameMode.*[Ss]ave\|func Test.*[Mm]eta.*[Mm]ode" internal/engine/save/*_test.go`).
- **AC-5 (US-3; load enforces the locked mode — fail closed).** Loading a save whose `Meta.GameMode` differs from the current session's mode FAILS with a registry-sourced typed error (`save.ErrGameModeMismatch`, MET-E820); it never silently adopts the file's mode and never re-modes the session. Check: a passing test writes a `real`-mode save, loads it into an `unlimited` session (and vice-versa) and asserts the typed error + no state mutation.
  > **LEAD RULING (Aaron/Bev, 2026-09-05, BUG-737 round-2 — REPLACES this AC's original "a save with an absent/unknown mode value is likewise rejected" sentence and its false-pass-risk note below).** This AC was written before any real save bundle existed under it, and the original blanket-rejection text broke on contact with a real save estate: **every save bundle written before FEAT-143 shipped has no `GameMode` field at all**, and refusing all of them outright left no migration path. The corrected rule is a genuine three-way split, never a blanket rejection:
  >  - `Meta.GameMode` matches the loading session's mode: proceed (unchanged).
  >  - `Meta.GameMode` is **present but differs**: refuse (`save.ErrGameModeMismatch`, unchanged — this is the mismatch case AC-5's own header describes).
  >  - `Meta.GameMode` is **absent** (a genuine pre-FEAT-143 bundle): loads **only** into a **real**-mode session (the conservative default) — raising `save.ErrLegacyGameModeAssumedReal` (MET-E1000), a non-fatal, WARN-severity registry event that is *constructed* (so `errs.New`'s own auto-log makes it visible — never silent) but *not returned as an error*. The **same absent-mode bundle loaded into an unlimited session still refuses** — an absent mode is never treated as "matches unlimited" (the original false-pass-risk note survives intact for this one direction: a load that treated "no mode" as `unlimited` would let an old save silently unlock money). A bundle accepted under this legacy path is re-stamped with the session's real `GameMode` on its very next save — `Composition.Save` always writes the current session's own locked mode, never what was loaded, so no special re-stamp logic is needed; the gap closes automatically one save later.
  >
  > Check (updated): `internal/engine/save/feat143_gamemode_test.go`'s `TestGameMode_AbsentModeAssumedRealNeverUnlimited` (absent-mode bundle accepted into `real`, refused into `unlimited`) and `internal/engine/compose/compose_gameinit_test.go`'s `TestComposeGameInit_LegacySaveBundleLoadsRealWarnsNeverUnlimited` / `TestComposeGameInit_LegacySaveBundleRestampedOnNextSave` (the same rule proven through the real `Composition.Save`/`Load` surface, plus the automatic re-stamp). The identical migration problem exists one layer down, at the persist-dir level (a live Azure dogfood city with a recorded world seed and real journal history but no `gamemode.json`, because the concept did not exist yet) — see `internal/persist/store.go`'s `Store.HasGameModeEpoch` doc comment and `internal/engine/compose/snapshot.go`'s `checkGameMode` for that fix (a durable "mode epoch" marker, stored independently of `gamemode.json`, distinguishes a genuinely legacy city — stamp once with a WARN, `gameinit.ErrLegacyGameModeStamped` MET-G5420 — from one whose sidecar has gone missing between boots on an already-migrated city, which still refuses).

### The finance UI and the balance regime

- **AC-6 (US-4/US-5; starting capital is data-sourced placeholder, directional-only).** In `real` mode the starting treasury balance is loaded from a data file (e.g. `data/finance.json` or the dispatch-resolved config), NOT a hardcoded Go literal, and the file carries a `$comment`/`meta` block marking the value a placeholder pending Aaron's balance pass. Check: `grep -n "\$comment\|\"meta\"" data/*.json` matches and states "placeholder pending balance pass"; `grep -nE "[0-9]{3,}" internal/engine/core/*.go internal/engine/finance/*.go` (excluding `_test.go`) finds no bare starting-capital literal outside doc prose. No numeric value is pinned by this file — the only spec'd properties are directional (real mode starts with a *finite* positive capital; unlimited is un-depletable). **Balance regime:** per Aaron's standing rule, player-felt numbers = placeholder + directional tests + delegated proposal (see Escalations — the 5,000,000 figure is a proposal, not a spec).
- **AC-7 (US-5; finance UI reflects the mode honestly).** `ui.screen.finance` renders an explicit infinite/unlimited indicator in `unlimited` mode (money is not a constraint) and the full P&L/balance/budget surfaces in `real` mode. Check: the screen's patch/state carries the mode or its derived "unlimited" flag; a passing e2e test renders each mode and asserts the correct indicator/absence of a budget constraint (`grep -rn "func Test.*[Ff]inance.*[Uu]nlimited\|func Test.*[Ff]inance.*[Mm]ode" internal/ui/screens/finance/*_test.go`).

- **For Bev — mkey + edges registration (blocks dispatch, GR#25).** `feat.gameinit` is NOT registered in code.json (confirmed 2026-08-21: no `feat.gameinit`/`game-init`/`money`/`sandbox` key; FEAT-143 has no mkey/sprint/seq/master-plan entry). Recommend: register `feat.gameinit` with outbound edges to `engine.finance`, `feat.saveux`, `ui.screen.finance` (or the reverse consumer edges) in master-plan → regenerate.
- **For Aaron — starting-capital figure (balance regime).** The 5,000,000 micropounds figure in the feature spec is a player-felt number. Per the standing balance-number regime, AC-6 pins no value; the data file ships a placeholder and a delegated proposal lands for Aaron's row-by-row approval before any real-balance tuning. Also confirm the £-realism of "infinite reserve represented as un-depletable" vs "large finite number" for Unlimited mode (the spec says un-depletable reserve — AC-2 treats it as a genuine bypass, not a huge balance; flag if Aaron prefers the latter).
- **For Bill/Bev — module split.** Whether the mode config lives in `engine.core`, a new small config surface, or `engine.finance` itself is a composition decision; the finance bypass gate must not fork the finance implementation (US-4: one finance code, mode as a gate). Route to the lead before dispatch.
- **Dependency risk.** `engine.finance` (MOD-020), `feat.saveux` (MOD-058/MOD-051) are the two hard consumers. Both are registered and built on origin/main. The composition-root wiring (how init mode reaches finance at boot) is the FEAT-082 concern — this item must specify against the real wiring, not a stub.
