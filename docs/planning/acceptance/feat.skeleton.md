## User stories

- As **the Sprint 1 exit gate**, I need "protocol + registry + stub-everything engine + H-STUB + determinism gate + F1 map on fixture" running end-to-end, so Sprint 2 can start on a proven vertical slice instead of untested independently-built pieces.
- As **Bill**, I need one command that launches a playable-looking-but-computes-nothing city on Folkestone-64, so I can visually confirm the whole stack (protocol → stub engine → UI) before any real model work begins.
- As **every later engine module**, I need the module registry booted and visible in F12 with every module correctly reporting `stub` status, so "one module real at a time" (M0-ENG §2's stubbing discipline) has a proven starting state to flip from.

## Scope

The integration of `int.protocol`, `foundation.errors`, `harness.stub`, `engine.core`, `feat.detgate`, `ui.core`, `ui.widgets`, `ui.screen.map`, and the module registry into one runnable binary (`cmd/metropolis`) that boots, runs Folkestone-64 end-to-end, and passes the determinism gate.

## Acceptance criteria

### Functional (integration)

- **AC-1a (Sprint-1 verifiable NOW — wiring & render correctness).** `go run ./cmd/metropolis` (default, non-headless) boots `harness.stub`'s `StubEngine` over `int.protocol`'s `Transport` and renders F1 (`ui.screen.map`) showing the Folkestone-64 fixture — verified by an integration test that constructs Commands **directly via `int.protocol`'s own public API** (e.g. `Subscribe`, then consuming the resulting `Delta`s), not simulated keystrokes, drives them through the wired stack, and asserts the resulting `ui.core` cell-buffer contents match an expected snapshot of Folkestone-64's initial view. This drives the real, already-accepted `harness.stub`/`int.protocol`/`ui.core`/`ui.screen.map` implementations end-to-end — nothing mocked, nothing standing in for a real dependency — so it proves genuine protocol→engine→UI-render wiring, not a mock talking to a mock. It does **not** prove a human's keystrokes reach those same Commands through a real terminal; that leg is AC-1b/AC-5b, deferred below because its owning module doesn't exist yet.
- **AC-1b (DEFERRED — genuinely blocked, not this item's or this Sprint's to build).** The keystroke-level half of the original criterion — that literal scripted terminal key sequences, translated by `ui.keys`' key grammar and replayed against a recorded delta-stream fixture, reproduce the same result — requires `ui.harness` (`MOD-014`) and, transitively, `harness.replay` (`MOD-013`); both are Sprint-2 items, `open`, owned outside this BA's remit. `feat.skeleton` must not be held open waiting on them. **Follow-up for Bill to raise:** file against `ui.harness` (`MOD-014`), same pattern as `FEAT-031` for the deferred map-overlays work — "feat.skeleton keystroke-driven regression: replay Folkestone-64's boot key sequence through `ui.harness` once `MOD-013`/`MOD-014` land." AC-1a is the full extent of what `feat.skeleton` itself is held to at Sprint-1 close.
- **AC-2.** The module registry (`MOD-005`, a Sprint-0/1 dependency of `engine.core`) boots with **every** registered module reporting status `stub` and health `ok` — a passing integration test queries the registry after boot and asserts zero modules report `real`, `off`, or a non-`ok` health.
- **AC-3.** F12 (`ui.screen.debug`) surfaces this stub-everything state. `ui.screen.debug` (`FEAT-007`) has not landed as of this refresh (concurrently dispatched, per Bill) but `feat.skeleton` is deliberately the last Sprint-1 item built regardless (its BOW `depends on` list already enforces the ordering). **The Tester re-checks `FEAT-007`'s status at `feat.skeleton`'s own Tester-pass time (not dispatch time)**: if `ui.screen.debug` has closed by then, verify via its actual rendered output; if it is still open/in the Tester loop, verify via the registry's own API directly (the lower-level check `ui.screen.debug` will later just render). Both branches check the **same property** (every module `stub`/`ok`) at different layers, so this is equal-rigour either way — not a moving target. Tester records explicitly which path was exercised.
- **AC-4.** The determinism gate (`feat.detgate`) is green when run against this fully-wired binary/orchestrator at both `POOL-SIM=1` and `POOL-SIM=14` — `go test ./internal/engine/detgate/... -run TestDeterminismGate -race -count=1` passes using the real wired-up `cmd/metropolis` boot path, not a synthetic harness bypassing the actual wiring. (Corrected: the gate test lives in package `detgate` at `internal/engine/detgate/gate_test.go`, not `internal/engine/core` — `internal/engine/core`'s own `determinism_test.go` covers related but different smoke tests, `TestDeterminism_SameSeedSameCommands_IdenticalSnapshot` / `TestDeterminism_PoolSizeInvariance`, not the named gate test. - **AC-5a (Sprint-1 verifiable NOW — Command→Delta→render half).** `AdvanceTicks`, `SetSpeed`, `Pause`, `Resume`, `Subscribe`, `Unsubscribe` are exercised end-to-end from the protocol layer down: a passing test constructs each Command **directly via `int.protocol`'s own API** (not simulated key input) and asserts the correct visible effect through the full stack this item can reach today — `harness.stub` → `Delta` → `ui.core` render (e.g. pause stops tick advancement visible in a directly-queried `Clock`/timing value; subscribe causes F1's rendered buffer to start reflecting fixture updates).
- **AC-5b (DEFERRED — genuinely blocked, same category as AC-1b, not a same-sprint sequencing dependency).** The "UI key input →" half requires `ui.keys` (`MOD-011`) to translate a captured key event into a Command. ### Error handling

- **AC-7.** A boot-time failure in any wired component (e.g. `harness.stub` fixture fails to load) produces a clear, registry-sourced startup error and a non-zero exit — not a partial boot that silently renders a broken/blank screen.

### Determinism & safety

- **AC-8 (GR#21).** AC-4's determinism-gate pass is the authoritative determinism check for this item — no additional ad-hoc determinism assertions are needed here beyond confirming the gate runs against the *actual* wired binary, not a stand-in.
- **AC-9.** `go vet ./...` and `gofmt -l .` are clean across the **entire repo**, not just this item's own new files — since this item's job is proving everything fits together, a lint/format regression anywhere in the stack it wires is this item's problem to catch (the Tester runs the full-repo SG-1/SG-2/SG-3 gates, not scoped to `cmd/metropolis/` alone, for this one item). **The authoritative check is a green CI run, not a local run.** Context: `BUG-004` (P1) found `gofmt -l .` passed locally on every prior run while failing on GitHub's Windows runners — root cause was `core.autocrlf=true` with no `.gitattributes`, so the runner checkout was CRLF while local blobs were LF, and local evidence could not detect it. The fix (`.gitattributes` pinning `text=auto eol=lf`) is pushed (`d5c9c19`) and the lint job is green for the first time in the project's history; one unrelated test flake still keeps the overall build red. A local `gofmt -l .`/`go vet ./...` pass is a useful pre-check but is **not sufficient evidence** for AC-9 — the Tester must cite an actual green CI run (`gh run list`/`gh run view`) for the commit under test, not just local output, precisely because local-vs-CI divergence is how BUG-004 happened.

### Documentation

- **AC-10.** `cmd/metropolis/`'s package doc (or a `docs/design/` walking-skeleton page) states module key `feat.skeleton`, cites M0-ENG §6.4, and lists exactly which Sprint 0/1 items it wires together, so a reader can trace "why does this file import X" back to the BOW.

## Out of scope

- Any new simulation/UI behaviour beyond wiring already-built (and already independently-accepted) items together — if an integration test reveals a bug in a dependency item (e.g. `harness.stub` mishandles a command), the fix belongs to that item's own junior/Tester loop, not to `feat.skeleton`, per the BA's standing rule (criteria are the contract each item is independently held to).
- Any ad hoc key-input handling inside `cmd/metropolis` or elsewhere that bypasses `ui.keys` (`MOD-011`) to make AC-5b pass early — see AC-5b: that translation belongs to `ui.keys` alone (GR#20/GR#3).
- Real simulation models, real terrain, real citizens — Sprint 1's skeleton is deliberately "a playable-looking nothing" (M0-ENG §6.4's own phrase).
- Sprint 2+ harnesses (`harness.replay`, `harness.synth`) — this item only needs `harness.stub` and `harness.headless`'s seam.
