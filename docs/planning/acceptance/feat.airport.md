# Acceptance criteria — feat.airport (FEAT-096)

**BOW code:** FEAT-096 (P2, open) — "Heathrow-scale international airport: runways, terminals, freight apron, air-cargo and passenger connectivity feeding tourism (MOD-057), FDI (MOD-059) and freight (MOD-047); thousands of jobs, huge traffic generation, noise blight via the MOD-046 blight model. Requires permit (FEAT-053), enormous land, and road/rail links (MOD-024/MOD-060). Long-horizon bet: colossal capex, compounding connectivity payoff."
**Spec refs:** `docs/METROPOLIS-MASTER-v2.1.md` §MP (line 499: "Heathrow-class International Airport — M11 + regional airport ach, 5B, 4 runways, ~200k pax/day, migration & tourism ××, huge noise contour + surface-access burden (its own motorway/rail spurs required)"); §44 Holiday Tourism (line 585: "access (external rail, coach, ferry terminal, **airport tiers step-change reach: domestic → continental → global**)"); §46 FDI (line 640: "Aerospace campus ('Airbus Toulouse') — **airport adjacency, runway access**, supply park, engineers"); §33 The Freight Harbour (line 466: the tonnes-conservation identity and modal reach the air-cargo arm must join); §32 The Blight Model (line 462: the blight model "applies to mines, heavy industry, abattoir, incinerator, landfill, **airport**, motorway" — the airport is a named blighting-object class); §18 Wellbeing (line 332: "noise (proximity to motorway/industry/**airport**)" as a mental-health driver); §17.2 (line 319: the "Airport (passenger)" per-passenger consumption coefficients — 15 L water, 6 kWh elec, 2 kWh gas, 0.7 kg waste); §4 milestone ladder (line 153: tier 9 Metropolis = "Airport"); `data/buildings.json` (line 5574: the existing `heathrow_class_international_airport` entry in the `mega-projects` supplement — this feature **extends** that entry, per ASM-668 — and line 3583: `regional_airport`); `docs/planning/acceptance/feat.megafacilities.md` (FEAT-055 — the sibling that extends the same `mega-projects` supplement; its AC-1/AC-2 "extend, don't fork" and AC-8/AC-9 permit/decommission inheritance are the precedents this file mirrors).
**Date:** 2026-08-16 (BA, first pass)
**Status:** draft-ahead — the feature has **no code.json registration yet** (verified: no `feat.airport`/`engine.airport` key exists), its three consumer edges (`engine.tourism`/`engine.fdi`/`engine.freight`) are unregistered, and two of its dependencies (`FEAT-053` permit, `MOD-060` rail) are BOW-`open` with no code. See "Cross-check" and "Escalations".
**Package under test:** `internal/engine/airport/` (path from the ASM-666 module-shape assumption — the registration shape is an open Bill decision, see ES-1).

**Balance-number regime (standing rule, same convention as `feat.maintenance.md` AC-16 / `engine.freight.md` AC-2 / `feat.megafacilities.md` AC-3):** every runway count, terminal capacity, pax/day figure, air-cargo t/day figure, jobs figure, noise-contour radius, land footprint, and surface-access threshold is a **placeholder** in a data file (`data/airport.json`), each carrying a disclosure comment naming it pending Aaron's balance pass. No AC may be satisfied by a junior inventing a final figure; every AC touching a figure requires the value to live in the data file and requires tests to check **direction/structure** (more runways → more pax; a tiered airport out-reaches a regional airport; without surface access throughput degrades) rather than pinning a specific magnitude.

## User stories

- **US-1.** As the player, I need the airport to be a **multi-component node** — runways, terminals, and a freight apron as distinct components with distinct capacities — so a Heathrow-class airport is a real facility whose throughput is a function of its parts (§MP "4 runways"), not a single flat capacity constant wearing an airport label.
- **US-2.** As `engine.tourism` (MOD-057, §44), I need the airport's tier to **step-change access reach** (domestic → continental → global), so an airport is a real tourism-draw multiplier — a bigger, tiered airport opens a bigger visitor pool — rather than a flat "+tourists" bonus.
- **US-3.** As `engine.fdi` (MOD-059, §46), I need the airport's **runway-access/adjacency** to be queryable, so the aerospace-campus prospect's requirement sheet ("airport adjacency, runway access") is satisfiable by a real airport, not by narration.
- **US-4.** As `engine.freight` (MOD-047, §33), I need **air-cargo tonnage** to flow through the freight mass-conservation identity as one more modal arm, so air freight is conserved alongside road/rail/sea, not a parallel tonnage ledger that can silently leak.
- **US-5.** As `engine.mining`'s shared blight model (§32), I need the airport's **noise contour** registered as a blighting object, so the "huge noise contour" is real, elevation-aware blight — the same viewshed/noise machinery the escarpment already hides or exposes — not a cosmetic label.
- **US-6.** As the player, I need the **surface-access burden** (the motorway/rail spurs §MP names) to be a real, testable prerequisite, so an airport without its road/rail links cannot run at full throughput.
- **US-7.** As the player, I need the airport to be **permit-gated** and land-hungry (§7/§MP "enormous land"), so it is the colossal-capex long bet the spec says it is, not a free placement.

## Scope

The airport as a mega-node: the runway/terminal/freight-apron component decomposition; passenger throughput (pax/day) as a real, data-driven function of those components; air-cargo tonnage as a conserved modal arm of `engine.freight`; the access-tier step-change fed to `engine.tourism`; the runway-access/adjacency query fed to `engine.fdi`; the noise-contour blight registration through `engine.mining`'s `BlightAPI`; the surface-access (road/rail spur) requirement; the permit + land gate via `feat.facilitypermits`. No tourism draw/spend machinery (`engine.tourism`), no FDI bidding/prospect machinery (`engine.fdi`), no freight port/chain/customs machinery (`engine.freight`), no blight viewshed/noise computation (`engine.mining`), no permit routing (`feat.facilitypermits`), no road/rail construction mechanics (`engine.roads`/`engine.rail`), and no final figure magnitudes (Aaron's balance pass).

## Acceptance criteria

### Functional — the node and its component decomposition

- **AC-1 (GR#20; inbound contract — `AirportAPI`, module-shape per ASM-666).** An `AirportAPI` exists exposing at minimum: component queries (runway count, terminal capacity, freight-apron capacity), passenger-throughput, air-cargo-tonnage, access-tier, runway-access/adjacency, and the surface-access status — consumed by `engine.tourism`/`engine.fdi`/`engine.freight` through registered interfaces only (ASM-667). Check: `go doc ./internal/engine/airport AirportAPI` shows a query surface with the component accessors; `grep -rln "airport\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/airport` and `_test.go`) finds no direct exported-field writes bypassing the interface.
- **AC-2 (§MP "4 runways" — the node decomposes; no single capacity constant).** The airport's passenger throughput is a documented **function of its components** (runway count × a per-runway slot rate × terminal gate capacity, or equivalent documented model), so adding a runway or a terminal moves throughput — it is not a single `paxPerDay` constant. Check: a passing test constructs two airports differing only in runway count and asserts the throughput differs; a second asserts terminal capacity independently moves throughput (`grep -rn "func Test.*[Rr]unway.*[Tt]hroughput\|func Test.*[Tt]erminal.*[Cc]apacity" internal/engine/airport/*_test.go`). **False-pass risk:** a `capacityRaw`-style single number copied out of the catalogue would pass a "throughput is queryable" grep while the §MP "4 runways" component decomposition is unmet — the check requires the throughput to respond to each named component independently.
- **AC-3 (GR#15; pax/day and component capacities are data-driven).** The passenger-throughput and per-component capacity figures are loaded from `data/airport.json` (per-component rate × size, class→rate mapping in data), never hardcoded Go literals, and the data file defines **at least two tiers with distinct reach/capacity** (regional vs international) so the tier ladder is a real ordering. Check: a passing test mutates one tier's per-runway rate in the loaded fixture and asserts the computed throughput for that tier (and only that tier) reflects the change; `grep -nE "[0-9]+" internal/engine/airport/*.go` (excluding `_test.go`) finds no bare throughput/capacity-shaped numeric literals outside doc-comment prose. **Balance-regime note:** the specific magnitudes are placeholders (AC-14); this AC checks *data-driven and tier-ordered*, not any magnitude.

### Functional — the three feed edges (tourism, FDI, freight)

- **AC-4 (§44/§33 air-cargo — GR#20 outbound contract, conserved via `engine.freight`).** Air-cargo tonnage is accounted through `engine.freight`'s `FreightAPI` (the registered mass-conservation surface `engine.freight.md` AC-10 owns), so a tonne flown into or out of the airport enters the same conserved-tonnes identity as road/rail/sea — there is **no airport-local air-cargo tonnage ledger**. Check: `grep -rn "freight\.\|FreightAPI" internal/engine/airport/*.go` (excluding `_test.go`) shows a real call into `engine.freight`'s movement/tonnage surface; `grep -nE "[Tt]onnes" internal/engine/airport/*.go` (excluding `_test.go`) shows no airport-local tonnage store. **False-pass risk:** an `airCargoTonnes` field that is displayed but never handed to `engine.freight` would pass a "cargo exists" grep while the freight invariant never sees the tonnage — the check requires the freight call. **Dependency note:** `engine.freight` is `done` (MOD-047); its `FreightAPI` method names are owned by `engine.freight.md`, not pinned here.
- **AC-5 (§44 access-tier step-change — a real reach ladder, not a flat bonus).** The airport exposes an access tier (domestic/continental/global, or equivalent documented ladder) that is a **step function** of the airport's tier/scale, and the tourism-facing effect is expressed as a reach multiplier that increases materially as the tier rises — a global-tier airport opens a materially larger visitor pool than a domestic-tier one, and a domestic-tier airport opens more than no airport. Check: a passing test asserts the reach/tier figure is monotonic non-decreasing across the tier ladder with a strict increase between at least two adjacent tiers, and that the no-airport case yields the lowest reach (`grep -rn "func Test.*[Aa]ccessTier\|func Test.*[Rr]eachLadder" internal/engine/airport/*_test.go`). **False-pass risk:** a flat "+N tourism" constant that ignores tiers would pass a "airport helps tourism" read while §44's explicit "step-change reach" is unmet — the check requires the ladder to be ordered and the no-airport floor to be lowest. **Dependency note:** the `engine.airport → engine.tourism` edge is unregistered (ASM-667/ES-2); until it lands, the reach figure is queryable from `AirportAPI` and the cross-module injection is a stub.
- **AC-6 (§46 runway-access/adjacency — queryable for the aerospace prospect).** The airport exposes a runway-access/adjacency status (queryable from `AirportAPI`) that `engine.fdi`'s aerospace-campus requirement sheet can test against — a built, operating airport reports runway access available; no airport (or a regional-only airport with no international runway) does not. Check: a passing test builds an airport and asserts the adjacency/access query returns available, then removes/demotes it and asserts the query flips (`grep -rn "func Test.*[Rr]unwayAccess\|func Test.*[Aa]erospace.*[Aa]djacency" internal/engine/airport/*_test.go`). **Dependency note:** the `engine.airport → engine.fdi` edge is unregistered (ASM-667); the adjacency is queryable locally until that edge lands.

### Functional — blight, surface access, and the permit gate

- **AC-7 (§32 blight — registered via `engine.mining`'s `BlightAPI`, GR#3 reuse).** The airport's noise contour is registered with `engine.mining`'s `BlightAPI` (the general "any module registers blighting objects" surface `engine.mining.md` AC-1 owns) — the airport is one of §32's seven named blight classes, and it must not compute its own noise/viewshed effect. Check: `grep -rn "mining\.\|BlightAPI\|RegisterBlightingObject" internal/engine/airport/*.go` (excluding `_test.go`) shows a real call into `engine.mining`'s registration surface; `grep -rn "func.*[Nn]oise\|func.*[Vv]iewshed" internal/engine/airport/*.go` shows no airport-local blight-effect computation. **False-pass risk:** a local noise-radius field that never reaches `BlightAPI` would pass a "noise exists" grep while §32's elevation-aware viewshed is silently bypassed — the check requires the `BlightAPI` registration call (ASM-674). **Dependency note:** the `engine.airport → engine.mining` edge is unregistered (ES-2); `engine.mining.md`'s own escalation already lists "airport" as one of the four-of-seven blight classes with no registered consumer edge.
- **AC-8 (§MP "its own motorway/rail spurs required" — surface access is a real prerequisite).** An airport's full throughput is gated on its surface-access links: without the required road and/or rail spur, the airport operates at a materially reduced (data-driven) throughput — the surface-access burden is a computed dependency, not a notes-field remark. Check: a passing test builds an airport with no surface link and asserts reduced throughput, then adds the road/rail link and asserts throughput rises to the full figure (`grep -rn "func Test.*[Ss]urfaceAccess\|func Test.*[Ss]pur" internal/engine/airport/*_test.go`). **False-pass risk:** a "surface access required" note with no throughput consequence would pass a grep for the phrase while §MP's burden is cosmetic — the check requires the throughput delta. **Boundary note:** the road/rail spur *construction* is `engine.roads`/`engine.rail`'s; this AC only reads whether the links exist.
- **AC-9 (§7/§MP permit + enormous land — via `feat.facilitypermits`, inherited not reimplemented).** Building the airport is permit-gated through `feat.facilitypermits` (FEAT-053, the §7 permit "for ANY large facility") and requires an enormous, data-sourced land footprint — the airport neither reimplements the three-route permit gate nor silently omits it, and a build without the required permit/land is rejected. Check: `grep -n "facilitypermits\|permit" internal/engine/airport/*.go` (excluding `_test.go`) shows the build path delegating to the permit feature's surface (or the doc.go stating the inheritance), and no airport-local permit-state field is declared. **Dependency note:** the `feat.airport → feat.facilitypermits` edge is unregistered (ES-2).

### Error handling

- **AC-10 (GR#7).** Building the airport without a valid permit (AC-9), without the required land footprint, with an unregisterable noise profile, or querying a component of an airport that does not exist, produces a registry-sourced error (new `MET-`-range code claimed at build time), never a panic, a silent no-op, or a partially-created airport. Check: `grep -n "MET-" internal/engine/airport/*.go` finds a registry-code reference; passing test coverage asserts the returned error's registry code matches AND that no airport state (component, permit, blight registration) was mutated on failure (`grep -rn "func Test.*[Nn]oPermit\|func Test.*[Uu]nknownAirport" internal/engine/airport/*_test.go`).
- **AC-11 (GR#7).** A malformed or schema-invalid `data/airport.json` (a tier missing its per-runway rate, a negative capacity, an unrecognised tier key) produces a registry-sourced load-time error distinct from AC-10's, never a silent default substitution that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/airport/*.go` finds a second distinct code; passing test coverage (`grep -rn "func Test.*[Mm]alformed.*[Aa]irport\|func Test.*[Ii]nvalidAirportData" internal/engine/airport/*_test.go`) asserts the error's registry code matches AND that no default-substituted capacity was loaded.

### Determinism, safety & scale

- **AC-12 (GR#21).** Throughput computation, air-cargo handoff, access-tier derivation, and surface-access gating are deterministic functions of `(worldSeed, tick, prior state, loaded data, commands)` — repeated runs from an identical snapshot produce byte-identical airport state, across worker counts. Check: a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/airport/*_test.go`); `grep -rn "time.Now\|time.Since" internal/engine/airport/*.go` (excluding `_test.go`) returns no matches — age/throughput advance by simulation tick only, never wall clock. Never assert a wall-clock upper bound in CI.
- **AC-13.** `go test ./internal/engine/airport/... -race -count=1` passes; `grep -n "go func()" internal/engine/airport/*_test.go` finds at least one concurrency test (concurrent component queries against a tick advancing throughput).
