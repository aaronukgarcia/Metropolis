## User stories

- **US-1.** As the player, I need F6 to show the city's age/sex/education-tier population makeup as three independent splines (per §13-F6's "ASCII population pyramid… education pipeline"), so I can see the shape of my citizenry at a glance, not infer it from a single blended number.
- **US-2.** As the player, I need F6 to show the blue/white-collar workforce split against supply (§45's explicit "F6 workforce view"), so a labour mismatch is visible before it forces an adult-ed or migration-profile decision.
- **US-3.** As the player, I need F6's eight city KPIs (GDP, happiness, land value, homeless, in-hospital, out-of-work, unfilled jobs, job→skill demand) each `Enter`-selectable to their source, per UI-SPEC §4's absolute drill-through rule, so a KPI is never a dead end.
- **US-4.** As the player drilling into a citizen bio from a KPI's source list, I need to see that citizen's cradle-to-grave facets (education stage trajectory + industry tie, employment, family/home, retirement month, income), so a KPI's underlying entity is a real, inspectable citizen record, not an opaque count.
- **US-5.** As **GR#20**, I need every number F6 renders to reach the screen exclusively through `int.protocol` view subscriptions, never through a direct `internal/engine` import, so the UI/engine boundary already enforced on every other screen holds here too.

## Scope

The F6 Demographics/Census screen: the three population splines (age band, sex, highest education tier), the blue/white-collar workforce graph, the eight city-KPI tile row with `Enter`-to-source drill-in, citizen-bio drill-in rendering (education/employment/family/retirement/income facets), and the education→crime linkage report (mean attainment vs crime rate, with the observed policy coefficient). All state crosses the boundary via `int.protocol` view subscriptions against `harness.stub` (pre-`FEAT-208`) and, unchanged, a real engine later. Personality/leisure-taste distribution and a full 4-way sector/skill breakdown are **not** in scope — see Escalations/Blocked ACs, `engine.census` does not expose that data today.

## Dependencies

`FEAT-208` (SubscriptionServer real-engine wiring) is open — `internal/protocol`'s `SubscriptionServer` hardcodes `engine.status` and publishes no live `engine.census` view today. Every subscription-fed AC below (AC-1 through AC-8, AC-11) is written to be testable now against a synthetic/fixture patch stream driven through `harness.stub` (the same pattern `ui.screen.ticker`'s F8/F5 tests already use, and the pattern `ui.screen.finance.md`'s SF-4 "transport-swap transparency" formalises: the same test suite runs unchanged against a real engine once one exists behind the same `Transport`). Live end-to-end (F6 rendering an actually-simulated city) is explicitly deferred to `FEAT-208`'s rollout and is not a gate for this file's ACs.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json outbound contract).** F6 reaches `engine.census` (code.json's registered `ui.screen.census` outbound edge) exclusively through an `int.protocol` view subscription — no direct import of `internal/engine/census` types. Check: `go list -deps ./internal/ui/screens/census/...` shows no import of `internal/engine/...` (test files exempt per README.md's `_test.go` depguard carve-out, fixtures only). This alone is necessary but not sufficient — see AC-2.
- **AC-2 (field traceability; the "stub cannot fake" check, mirroring `ui.screen.finance.md` SF-2/SF-3).** `doc.go` states, per displayed figure/widget, the exact view-subscription field it is sourced from (a table: e.g. "age-band spline ← `census.demographics.ageBands`"). For each such figure, a passing test drives `harness.stub` through two distinct scripted delta sequences that differ in exactly that field's value and asserts (a) the bound widget's rendered output differs correspondingly, and (b) every other widget's rendered output is byte-identical between the two runs. Check: `grep -rn "func Test.*[Dd]ifferential\|func Test.*[Ss]tubCannotFake" internal/ui/screens/census/*_test.go`. **False-pass risk this rejects:** a screen wired to a stub that always emits the same canned splines would pass a superficial "renders three splines" check while never actually being wired to anything — SF-3's differential single-field mutation is the only check that catches it.
- **AC-3 (§13-F6 demographic splines — sourced live, three independently-perturbable series, mirrors `engine.census.md` AC-18).** F6 renders three population series — age band, sex (M/F), highest education tier — from `CensusAPI.AgeBandSeries`/`SexSeries`/`EducationTierSeries`'s subscribed view fields, not a UI-side recomputation from raw citizen records. Check: a passing test feeds a fixture delta stream with a known age/sex/education-tier distribution and asserts the three rendered series match that fixture exactly (`grep -rn "func Test.*[Aa]geBandSpline\|func Test.*[Ss]exSpline\|func Test.*[Ee]ducationTierSpline" internal/ui/screens/census/*_test.go`); a second test perturbs only the education-tier fixture field and asserts the age-band and sex series render byte-identically (independence, matching the engine-side AC-18 guarantee this screen must not flatten away).
- **AC-4 (§45 blue/white-collar workforce graph — emergent, not hardcoded).** F6 renders the blue/white-collar split from `CensusAPI.BlueWhiteCollar`'s subscribed view field — a passing test feeds two fixture deltas differing only in the blue/white split and asserts the rendered graph's two bars move accordingly (`grep -rn "func Test.*[Bb]lueWhiteCollar" internal/ui/screens/census/*_test.go`). **Lazy implementation this rejects:** a bar pair whose proportions are computed from a screen-local constant rather than the subscribed field would satisfy "a graph renders two bars" while failing the differential check.
- **AC-5 (city KPI tile row — eight named KPIs, all sourced live).** F6 renders a tile per KPI (`gdp`, `happiness`, `land-value`, `homeless`, `in-hospital`, `out-of-work`, `unfilled-jobs`, `job-skill-demand` — `CensusAPI`'s `KPIKey*` constants), each showing the value from its own subscribed view field. Check: `go doc ./internal/ui/screens/census` (or `doc.go`) names all eight tiles against their `KPIKey*` source; a passing test feeds a fixture delta with known values for all eight and asserts all eight tiles render the fixture's values, and that changing one KPI's fixture field changes only that tile (`grep -rn "func Test.*[Kk][Pp][Ii]Tile" internal/ui/screens/census/*_test.go`).
- **AC-6 (KPI drill-in — every tile `Enter`-selectable to its source, per UI-SPEC §4 and `engine.census.md` AC-20).** `Enter` on a KPI tile resolves to `CensusAPI.Source(aggregateID)`'s `SourceResolution` (entity IDs for a population-derived KPI — `homeless`/`out-of-work` — or the ledger `LineValue` for an aggregate KPI — `gdp`/`land-value`/`in-hospital`/`unfilled-jobs`/`job-skill-demand`/`happiness`) and opens the resolved source view. Check: a passing test resolves `homeless`'s source against a fixture and asserts the drilled view shows exactly the fixture's entity-ID set (`grep -rn "func Test.*[Dd]rillSource\|func Test.*[Kk][Pp][Ii]Drill" internal/ui/screens/census/*_test.go`); a second test resolves `gdp`'s source and asserts the drilled view shows the fixture's `LineValue`, not a recomputed figure. **False-pass risk:** a drill target that always opens the same static "details" pane regardless of which KPI was selected would pass a "Enter does something" smoke test while failing UI-SPEC §4's "goes to its source" requirement — the check requires the resolved content to trace to the specific KPI's fixture data.
- **AC-7 (citizen bio drill-in — cradle-to-grave facets rendered from `CensusAPI.CitizenBio`, mirrors `engine.census.md` AC-9/AC-10).** Drilling from a KPI's entity list (AC-6) into one citizen opens a bio pane rendering: education (stage trajectory + attainment + industry tie, per `engine.census.md` AC-10), employment (state, sector, workplace), family (household, partner, home), retirement month, and income — all from the subscribed `CensusAPI.CitizenBio` view, never a screen-local recomputation. Check: a passing test feeds a fixture bio (including a specialist-university industry tie) and asserts all five facets render the fixture's values verbatim (`grep -rn "func Test.*[Cc]itizenBio.*[Rr]ender" internal/ui/screens/census/*_test.go`).
- **AC-8 (education→crime linkage report, mirrors `engine.census.md` AC-14).** F6 renders `CensusAPI.EducationCrimeLinkage`'s report (population, mean attainment, crime rate, uneducated fraction, the observed policy coefficient) as a direction-and-structure display — the render shows which of two compared scopes has the lower attainment and higher crime rate, never a hardcoded slope. Check: a passing test feeds two fixture linkage snapshots differing only in mean attainment (one lower) and asserts the render distinguishes them (e.g. the lower-attainment fixture's crime figure renders as the higher one) without the screen computing its own elasticity (`grep -rn "func Test.*[Ee]ducationCrimeLink" internal/ui/screens/census/*_test.go`). **Balance-number regime note (per `feat.citycensus.md`'s standing rule):** this is a player-felt correlation whose steepness is a `data/census.json` placeholder pending Aaron's balance pass — the check asserts direction/structure only, never a pinned magnitude.
- **AC-9 (KPI tiles registered into `ui.dash`'s drill graph — `ui.dash` BOW dependency, tile substrate reuse).** Each of the eight KPI tiles (AC-5) and each citizen-bio facet figure (AC-7) is a `dash.Tile`/registered `dash.DrillTarget{ViewName, EntityID}` (the canonical shape — ASM-538/ASM-630, not a bespoke per-screen seam, matching `ui.screen.build`/`ui.screen.services`' existing consumption of `ui.dash`) — this screen supplies the registration, it does not reimplement `ui.dash`'s navigation/dead-end-detection graph. Check: `grep -n "dash\.\(Tile\|DrillTarget\)" internal/ui/screens/census/*.go` (excluding `_test.go`) shows the registration calls; a passing test asserts every AC-5/AC-7 figure has a corresponding `dash.DrillTarget` registration (`grep -rn "func Test.*[Dd]ashRegist" internal/ui/screens/census/*_test.go`).
- **AC-10 (ASCII population pyramid — composed from existing `ui.widgets` primitives, no new widget invented).** The age-band spline (AC-3) renders as a two-sided (male/female) horizontal-bar pyramid using `ui.widgets`' existing `braille.go`/`heatmap.go`/`sparkline.go` primitives (reused, per the same "reuse `ui.widgets.Sparkline`, not a bespoke reimplementation" convention `ui.screen.debug.md` AC-8 established) — no new widget type is required for §13-F6's "ASCII population pyramid" phrase. Check: `grep -n "widgets\." internal/ui/screens/census/*.go` (excluding `_test.go`) shows calls into an existing `ui.widgets` primitive for the pyramid render, not a bespoke from-scratch cell-buffer routine.

### Blocked ACs (engine gap — `ASM-1161`'s no-live-source class)

- **BLOCKED-1 (§13-F6 "personality & leisure-taste distribution of the city" — no source in `engine.census` today).** `CensusAPI`'s `CitizenView` (`internal/engine/census/sources.go`) carries `ID, BirthMonth, Sex, Household, Partner, Home, Workplace, School, Employment, Sector, HealthBand, Wealth` — **no personality or leisure-taste field exists anywhere in the package** (verified: `grep -n "Personality\|LeisureTaste\|Sociability" internal/engine/census/*.go` returns no matches). This half of §13-F6's demographics view cannot be built against the registered `engine.census` edge as it stands. **Tripwire (mechanical):** `grep -c "Personality\|LeisureTaste" internal/engine/census/*.go` must return `0`; a nonzero count means the field has landed and this AC should be re-armed as a live AC citing the new accessor. Until then: no personality/leisure-taste pane exists in this package (`grep -rn "[Pp]ersonality\|[Ll]eisureTaste" internal/ui/screens/census/*.go` excluding `_test.go` finds no matches — this screen invents no census-local personality model to fill the gap, per GR#3).
- **BLOCKED-2 (§13-F6 "workforce by sector/skill" — only a 2-way blue/white split is exposed, not the underlying 4-way sector or any skill dimension).** `CensusAPI.BlueWhiteCollar` (AC-4) aggregates `CitizenView.Sector`'s four values (`SectorPrimary/Secondary/Tertiary/Public`) down to a blue/white binary; no `CensusAPI` accessor exposes the four sectors independently, and no "skill" dimension exists anywhere in the package (`JobSkillDemand`, AC-5, is a single citywide demand figure, not a per-citizen skill distribution). §45's own line 625 text this file's Spec refs cite is explicit that only the blue/white split is the F6 workforce view's documented contract — this AC is descoped to that binary (AC-4), and the finer sector/skill breakdown is logged here rather than silently omitted. **Tripwire (mechanical):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.census'); process.exit(0)"` combined with `grep -c "func (c \*CensusAPI) SectorSeries\|func (c \*CensusAPI) SkillSeries" internal/engine/census/*.go` must return `0`; a nonzero count means a finer accessor has landed and this AC should be re-armed.
- **BLOCKED-3 (car/house/chopper bios in F6 — `engine.census.md` ES-3's own open escalation, not new here).** `CensusAPI.ObjectBio` (AC-7's sibling for non-citizen objects) is a generic, kind-agnostic surface, but the owning modules that would populate car/house/chopper GUIDs into the census's tracked set (`engine.traffic`, `engine.build`, `engine.airunits`) are outside the seven consumed sources `feat.citycensus.md`'s ES-3 already flags as an open gap. F6 renders whatever bios exist in the tracked set (AC-7 covers the citizen case fully); this file does not claim non-citizen bio rendering is complete, since it depends on an escalation this file does not own resolving first.

### Error handling

- **AC-11.** A delta for an unknown/stale subscription (matching `ui.screen.map`'s AC-8 / `ui.screen.finance.md` SF-7 precedent) is dropped and logged (registry-sourced, via `foundation.errors`) rather than applied or causing a panic.
- **AC-12.** A KPI or bio query the engine rejects with a registry-sourced error (`engine.census`'s `MET-G2701`/`MET-G2702` — unknown object/unknown key, per `internal/engine/census/errors.go`) surfaces that rejection to the player as a clear "unavailable" state on the affected tile/pane, never a silently-rendered zero the player could mistake for a real empty figure (mirrors `engine.census.md` AC-21's "no zero-value bio/KPI" guarantee, carried through to the render layer).

### Determinism & safety

- **AC-13 (copy-guard, SEC-020 family — mirrors `ui.screen.debug`'s ASM-093 / `SubscriptionServer`'s SEC-019 precedent).** Every exported method on this screen's struct that reads or writes a receiver field is `checkNotCopied`-guarded (the same mechanism `internal/ui/core/copyguard.go`, `internal/protocol/subscription.go`, and `internal/ui/screens/demo/copyguard.go` already establish) — a method called on a struct-copied value returns a registry-sourced error rather than operating on an independently-zeroed, aliasing copy. Check: `grep -n "func (s \*Screen)" internal/ui/screens/census/*.go` (excluding `_test.go`) cross-referenced against `grep -n "checkNotCopied" internal/ui/screens/census/*.go` — every receiver-field-touching method has a guard call, or is documented as a deliberate exception (mirroring `ui.screen.debug`'s `TailEntry` precedent) naming why it touches zero receiver fields.
- **AC-14.** F6's rendering is a pure function of (subscribed view-model state, selected KPI, selected citizen/bio, selected linkage scope) — the same inputs render identically across repeated calls; no `time.Now()`-driven content beyond the shared 300ms threshold-pulse primitive from `ui.widgets` (reused, not reimplemented). `grep -rn "time.Now" internal/ui/screens/census/*.go` (excluding `_test.go`) returns no matches.
- **AC-15.** `go test ./internal/ui/screens/census/... -race -count=1` passes with no data race between the delta-applying goroutine and the render path.
