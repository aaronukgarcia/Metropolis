## User stories

- **US-1.** As the player, I need XP earned continuously (construction, population, service performance, milestone progress) to accumulate toward the next milestone, so §22's "XP — earned continuously" is a live counter the player watches climb, not a hidden or batch-computed value.
- **US-2.** As the milestone ladder (§4), I need each of the 13 tiers (Wilderness through Centopolis) to grant its documented population-threshold unlocks, expansion-permit allowance, cash award, and loan-facility uplift automatically the instant the population threshold is crossed, so crossing 100,000 citizens genuinely unlocks the port and district/policy systems the same tick, not on a delayed check.
- **US-3.** As the player choosing a specialisation, I need Development Points spent in 12 per-category progression trees (Roads, Electricity, Water & Gas, Health & Deathcare, Education, Fire, Police, Garbage, Parks & Rec, Transport, Communications, Welfare) loaded from `unlock_trees.json`, so two players at the same milestone tier genuinely own different toolkits (§22).
- **US-4.** As `data.catalogue`'s `unlock` field (FEAT-010, this BA's Sprint 2 file), I need every catalogue entry's milestone/DP/achievement gate to be checkable through this module's gate-check function, so the catalogue's declared unlock requirements are enforced somewhere real, not just recorded as inert data.
- **US-5.** As the player, I need off-map capacity (grid/gas/rail/port/water tranches) to always be directly purchasable with money regardless of accumulated Development Points, so §22's "Buy — off-map capacity is purchased directly with money regardless of points" path is genuinely independent of the DP-tree gate, never accidentally coupled to it.
- **US-6.** As a developer/tester in debug mode, I need a cheat/debug force-unlock path that can unlock any milestone tier or tree node for testing (e.g. port-testing pre-100k, per §4's own example), consistent with M0-ENG §3's debug-mode doctrine (runtime feature switch, save-header-flagged).
- **US-7.** As `engine.finance` (MOD-022, this BA's own file above), I need milestone-granted cash awards and loan-facility uplifts to post as real ledger transactions/state changes through `FinanceAPI`, not a parallel unlocks-only currency untracked by the books.

## Scope

XP accrual, the 13-tier milestone ladder (thresholds, grants: unlocks/expansion permits/cash/loan uplift), the 12 category Development Point trees loaded from `unlock_trees.json`, the always-available money-only "Buy" path for off-map capacity, gate-check queries consumed by other modules (notably `data.catalogue`'s `unlock` field), and the debug force-unlock override.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `UnlocksAPI` exists with, at minimum, a gate-check query (`IsUnlocked(gate Gate) bool` or equivalent) and mutation commands for spending Development Points / crossing milestones, matching code.json's "gate checks data-driven from unlock_trees.json" pattern. Check: `go doc ./internal/engine/unlocks UnlocksAPI` shows both.
- **AC-2 (§22 XP).** XP accrues continuously from at least the four named sources (construction, population, service performance, milestone progress), each contributing via a documented, per-source formula/rate (not a single opaque "gainXP(amount)" called ad hoc from unrelated code with invented numbers). Check: `go doc ./internal/engine/unlocks` shows per-source XP-award functions (`AwardConstructionXP`, `AwardPopulationXP`, etc., or equivalent); a passing test asserts XP increases when each source event fires (`grep -rn "func Test.*XP" internal/engine/unlocks/*_test.go`).
- **AC-3 (§4 the 13-tier ladder).** All 13 milestone tiers are loaded from data (not hardcoded), each carrying its population threshold (0, 100, 500, 5,000, 20,000, 50,000, 100,000, 250,000, 1,000,000, 5,000,000, 10,000,000, 50,000,000, 100,000,000) and tier name (Wilderness…Centopolis), matching §4's table exactly. Check: a passing test asserts all 13 thresholds and names match the spec table verbatim (GR#15: transcribed from §4, not invented) (`grep -rn "func Test.*[Mm]ilestone.*[Tt]ier\|func Test.*[Ll]adder" internal/engine/unlocks/*_test.go`).
- **AC-4 (§4 milestone grants).** Crossing a milestone's population threshold triggers, in the same tick: the tier's signature unlocks becoming gate-passable, an expansion-permit allowance increase, a cash award (posted through `FinanceAPI`, US-7), and a loan-facility uplift (consumed by `engine.finance`'s credit/loan logic). Check: `go doc ./internal/engine/unlocks` shows a milestone-crossing event/command producing all four effects; a passing test crosses a threshold and asserts all four (`grep -rn "func Test.*[Cc]rossMilestone\|func Test.*[Mm]ilestoneGrant" internal/engine/unlocks/*_test.go`).
- **AC-5 (§4/§22; monotonic, no regression).** Milestone tiers only ever advance forward — a population dip below a previously-crossed threshold (e.g. during a Detroit-spiral emigration event, §12) does NOT revoke previously-granted unlocks or downgrade the tier. Check: a passing test crosses a threshold, then reduces population below it, and asserts the tier/unlocks remain at the higher-water-mark level (`grep -rn "func Test.*[Nn]oRegress\|func Test.*[Hh]igherWaterMark" internal/engine/unlocks/*_test.go`).
- **AC-6 (§22 Development Points; 12 trees).** Exactly the 12 named categories (Roads, Electricity, Water & Gas, Health & Deathcare, Education, Fire, Police, Garbage, Parks & Rec, Transport, Communications, Welfare) exist as distinct progression trees, each loaded from `data/unlock_trees.json`, each tree a directed graph of nodes with DP costs and (optionally) milestone-tier prerequisites. Check: a passing test asserts exactly these 12 category names are loaded (`grep -rn "func Test.*[Cc]ategor\|func Test.*[Tt]welve" internal/engine/unlocks/*_test.go`). False-pass risk: a test asserting "at least 12" or "12 or more" category names are present would pass a build that also loads a 13th, unspecified category by accident (e.g. a copy-paste duplicate under a different key) — the check requires an exact-count assertion, not a lower bound.
- **AC-7 (§22 spend-to-unlock).** Spending Development Points on a tree node requires: sufficient accumulated (unspent) DP balance, and (where the node declares one) the prerequisite milestone tier already reached; spending debits the DP balance and marks the node unlocked, callable only via a command (never a direct field mutation). Check: `go doc ./internal/engine/unlocks SpendDevelopmentPoints` (or equivalent command) exists; passing tests cover successful spend, insufficient-DP rejection, and missing-tier-prerequisite rejection (`grep -rn "func Test.*[Ss]pendDP\|func Test.*[Ii]nsufficientDP" internal/engine/unlocks/*_test.go`).
- **AC-8 (§22 divergent toolkits).** Two independently-simulated worlds at the same milestone tier but with different DP spend histories report different sets of unlocked tree nodes via `IsUnlocked` — proving "two players at tier 6 own different toolkits" is a real, queryable property, not just a narrative claim. Check: a passing test constructs two DP-spend histories at the same tier and asserts differing `IsUnlocked` results for at least one node (`grep -rn "func Test.*[Dd]ivergent\|func Test.*[Dd]ifferentToolkit" internal/engine/unlocks/*_test.go`).
- **AC-9 (§22 Buy path; US-5).** Off-map capacity (grid/gas/rail/port/water tranches) is purchasable via a money-only command that does NOT check or consume Development Points and does NOT check the DP-tree gate for the equivalent infrastructure — it debits money through `FinanceAPI` and grants capacity directly, independent of §22's points economy. Check: `go doc ./internal/engine/unlocks BuyOffMapCapacity` (or equivalent) exists; a passing test asserts a zero-DP-balance world can still successfully purchase a tranche given sufficient money (`grep -rn "func Test.*[Bb]uy.*[Cc]apacity\|func Test.*[Oo]ffMap" internal/engine/unlocks/*_test.go`). False-pass risk: a test that only exercises the zero-DP-balance success path would pass a build that *also* silently deducts DP when available (coupling Buy to the points economy in the background, contrary to US-5's "genuinely independent" requirement) — a second assertion is required that a world with a positive DP balance has that balance unchanged after a Buy purchase.
- **AC-10 (§4/data.catalogue seam).** `data/buildings.json`'s `unlock` field (this BA's `data.catalogue.md` AC-4) is checkable through `IsUnlocked` — given a catalogue entry's `unlock.milestone`/`unlock.dp`/`unlock.achievement` structured flags, `UnlocksAPI` resolves whether that specific building is currently buildable. Check: a passing integration test loads a `buildings.json` fixture entry and asserts `IsUnlocked` correctly reflects the current milestone/DP/achievement state (`grep -rn "func Test.*[Cc]atalogueGate\|func Test.*[Bb]uildingUnlock" internal/engine/unlocks/*_test.go`).
- **AC-11 (§4/M0-ENG §3 debug force-unlock).** A debug-mode-only command force-unlocks any milestone tier or tree node for testing (e.g. §4's own "port testing pre-100k" example), and using it flags the save/session as debug-touched (via `int.serializer`'s `Header.DebugTouched`, sticky-forever per M0-ENG §3/§14) — never usable silently in a non-debug build. Check: `go doc ./internal/engine/unlocks ForceUnlock` (or equivalent, debug-gated) exists; a passing test asserts calling it in non-debug mode is rejected, and in debug mode it succeeds and triggers `DebugTouched` (`grep -rn "func Test.*[Ff]orceUnlock" internal/engine/unlocks/*_test.go`).

- **AC-19 (sprint-plan S4 exit gate — "milestone tiers 1–4 gate correctly", the composite proof).** A single passing test crosses the population thresholds for §4's tiers 1–4 (Wilderness→0, Hamlet→100, Village→500, Small Town→5,000) in sequence within one synthetic run and asserts, at each crossing: (a) the tier's named signature unlocks from §4's table become gate-passable via `IsUnlocked` (e.g. tier 2's farm plots/general store/basic clinic; tier 4's Sellindge grid connection/secondary school/bus routes/fire & police posts), (b) a cash award posts through `FinanceAPI` (AC-4), and (c) content still gated behind a tier not yet reached (e.g. tier 5's expansion tiles, checked at tier-4 population) remains locked. This is the item's own composite evidence for the exit gate's literal wording, distinct from AC-3/AC-4's generic per-tier mechanism tests. Check: `grep -rn "func Test.*[Tt]ier1.*4\|func Test.*[Ee]xitGate\|func Test.*[Ee]arlyTiers" internal/engine/unlocks/*_test.go` finds this sequential test and it passes. False-pass risk: AC-3's existing "13 thresholds match the table" test and AC-4's existing "crossing a threshold produces all four grants" test could both pass without ever running tiers 1 through 4 *in sequence within one run* (e.g. both could test a single isolated threshold in isolation, or test only a late tier like tier 9) — the exit gate specifically needs tiers 1–4 exercised together as the early-game on-ramp, since that is what an S4-era headless run will actually reach, and no existing AC pins that composite scenario.

### Error handling

- **AC-12 (GR#7).** A gate check or spend command referencing an unregistered tree/node/tier (a typo'd category name, an out-of-range tier index) returns a registry-sourced error (new `MET-E`-range code), never a silent "not unlocked" false negative indistinguishable from a genuine gate failure. Check: `grep -n "MET-" internal/engine/unlocks/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredGate" internal/engine/unlocks/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no silent "not unlocked" false negative was returned in place of the typed error, not merely that a matching-named test function exists.
- **AC-13.** A malformed `data/unlock_trees.json` (missing category, node referencing a nonexistent DP cost, a cyclic tree dependency) fails loudly at load time via `foundation.data`'s validated-load path. Check: passing test coverage (`grep -rn "func Test.*[Mm]alformedTree\|func Test.*[Cc]ycle" internal/engine/unlocks/*_test.go`).

### Determinism & safety

- **AC-14 (GR#21).** Milestone-crossing and DP-spend evaluation order is deterministic — no map-iteration dependence in which unlocks are granted first within a tick when multiple thresholds/nodes resolve simultaneously (sorted by a documented stable key, e.g. tier index then node ID). Check: `grep -n "for .* := range" internal/engine/unlocks/*.go` on any map feeding grant order is sorted (`grep -n "sort\." internal/engine/unlocks/*.go`); a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/unlocks/*_test.go`).
- **AC-15 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/unlocks/*.go` (excluding `_test.go`) returns no matches — XP accrual and milestone evaluation are driven by simulation events/tick, never wall clock.
- **AC-16.** `go test ./internal/engine/unlocks/... -race -count=1` passes with no data race when XP/milestone/DP state is read and mutated concurrently across shards. Check: `grep -n "go func()" internal/engine/unlocks/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-17.** `internal/engine/unlocks/doc.go` states the module key `engine.unlocks`, cites §4/§22/§23, and documents the four-currency model (XP/Milestones/Development Points/Buy) with which is data-driven (all of it, per GR#15) explicitly noted. Check: `grep -n "engine.unlocks" internal/engine/unlocks/doc.go` and `grep -n "§22\|section 22" internal/engine/unlocks/doc.go` both match.
- **AC-18.** `data/unlock_trees.json` carries a `$comment`/`meta` block citing §22 and listing the 12 category names, consistent with the convention established in this BA's earlier data-file ACs. Check: `grep -n "\$comment\|\"meta\"" data/unlock_trees.json` matches.

## Out of scope

- The 12 progression trees' actual node content (which specific buildings/abilities each node unlocks beyond what `data.catalogue`'s `unlock` field already declares) — this item's job is the gate-check mechanism and DP economy; populating every tree's exact node graph in full detail may be split into a follow-up data-population BOW item if `unlock_trees.json`'s scope proves too large for one item (flagged in Escalations).
- `ui.screen.build`'s rendering of unlock state, progression trees, or the palette's `:` unlock-browsing UI — this item only exposes the queryable API that screen consumes.
- Achievement-gated content's achievement-tracking logic itself (`+ach` flags in the catalogue) — this item's gate-check consumes an `IsAchieved` boolean per achievement; achievement *detection* (e.g. "first 100 deaths" triggering the War Memorial landmark) belongs to whichever module owns that event.
- Research points (§27, university output) as a separate currency — §22 names exactly XP/Milestones/DP/Buy; research points are a different, later-sprint mechanic (`engine.education`) that happens to also gate mega-projects.
