## User stories

- **US-1.** As the player, I need to draw and name a district on the map, so §52's "named districts are the scope system" is something I actually do, not read about.
- **US-2.** As the player, I need to browse the policy library by category with each entry's mechanism, cost, and scope shown, so choosing a policy is an informed decision, not a guess at a toggle's label.
- **US-3.** As the player about to enact a policy, I need to see its previewed impact — with the same computed-vs-extrapolated honesty `engine.projections` already promises everywhere else — before I confirm, so I decide with real information, per §52's "F7 preview *before* enactment".
- **US-4.** As the player, I need to see a conflict warning inline when a policy I'm about to enact conflicts with one already active in scope, before I confirm, not only discover it afterward.
- **US-5.** As the player, I need per-district tax settings (§39's per-district multipliers) editable from the same screen a district's identity lives on, so fiscal identity and district identity are one coherent place, not two.
- **US-6.** As **GR#20**, I need every number and every engine fact on F8 to reach the screen exclusively through `int.protocol`, never through a direct `internal/engine` import, so the UI/engine boundary this project has enforced on every other screen holds here too.

## Scope

The F8 Districts & Policies screen: district drawing/naming (cell-paint against `engine.world` cells via `engine.policies`' `CreateDistrict`), a policy library browser (categorised, mechanism/cost/scope shown, sourced live from `PoliciesAPI`), impact-preview rendering (confidence-tagged, per `engine.policies.md` AC-4/AC-5), inline conflict warnings (per `engine.policies.md` AC-11), and a per-district tax-settings panel (per `engine.tax.md` AC-6). All state crosses the boundary via `int.protocol`.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json outbound contract).** F8 reaches `engine.policies` and `engine.tax` (code.json's registered `ui.screen.districts` outbound edges) exclusively through `int.protocol` view subscriptions and commands — no direct import of `internal/engine/policies` or `internal/engine/tax` types. Check: `go list -deps ./internal/ui/screens/districts/...` shows no import of `internal/engine/...`.
- **AC-2 (§52 district drawing/naming).** The player paints a set of cells (cell-tagged, per `engine.policies.md`'s ASM-285 model) and assigns a name, issuing a `CreateDistrict` command through `int.protocol`; a passing test paints a fixture cell set, submits the command, and asserts the resulting delta stream reflects the new district's cells and name — the screen does not locally compute or cache a "district exists" state ahead of the engine's own delta confirming it (avoiding an optimistic-UI desync with the authoritative engine state). Check: `grep -rn "func Test.*[Cc]reateDistrict\|func Test.*[Dd]rawDistrict" internal/ui/screens/districts/*_test.go`.
- **AC-3 (§52 policy library browser — sourced live, not duplicated).** The browser lists every policy from `PoliciesAPI`'s registered library query, grouped by the four categories (movement, layout & wellbeing, economy, social), showing name/mechanism/cost/scope per entry — these fields are rendered from the subscribed view's data, never a UI-side hardcoded copy of `policies.json`. Check: a passing test feeds a fixture `PoliciesAPI` dataset (via the stub transport) containing a known set of policies and asserts the browser's rendered rows match that fixture's fields exactly, and that changing the fixture (adding/removing a policy) changes the rendered rows without a code change (`grep -rn "func Test.*[Pp]olicyLibrary\|func Test.*[Bb]rowser" internal/ui/screens/districts/*_test.go`). **False-pass risk:** a test that only checks "N rows render" would pass a build that hardcodes N plausible-looking rows independent of the fixture — the check requires asserting the rendered *content* traces to the fixture data, and that changing the fixture changes the render.
- **AC-4 (§52 impact preview — confidence-honest rendering; consistency with `engine.policies.md`/`engine.projections.md`).** Selecting a policy renders its `PreviewImpact` result (per `engine.policies.md` AC-4/AC-5) with `Computed`-tagged points rendered solid and `Extrapolated`/`Unavailable` points rendered dim/distinct (per UI-SPEC §4's history-vs-projection idiom, reused rather than a screen-local re-invention of that distinction) — and viewing the preview alone never triggers enactment; enactment requires a separate, explicit confirm step. Check: a passing test feeds a preview payload with a mix of `Computed` and `Extrapolated` points and asserts the two render with visibly distinct styles (not merged into one undifferentiated series), and a second test asserts selecting/viewing a policy's preview does not, by itself, change the policy's active/enacted state (`grep -rn "func Test.*[Pp]review.*[Rr]ender\|func Test.*[Cc]onfidenceStyle" internal/ui/screens/districts/*_test.go`). **Lazy implementation this rejects:** a preview pane that renders every point identically (no solid/dim distinction) would satisfy "a preview chart shows" but fails the specific confidence-honesty check this AC requires, matching the same anti-ambush failure mode `engine.projections.md` AC-6 already guards against at the engine layer — this AC guards it again at the render layer, since a correct engine payload can still be flattened into a dishonest display.
- **AC-5 (§52 conflict warnings surfaced pre-confirm).** When the selected policy conflicts (per `engine.policies.md` AC-11's `conflictsWith` data) with an already-active policy in an overlapping scope, the browser/confirm flow shows the warning inline before the confirm step — sourced from `PoliciesAPI`'s query, not a screen-local re-derivation of conflict pairs. Check: a passing test selects a policy known (via fixture data) to conflict with an active one and asserts the warning renders before any confirm interaction is available/completed (`grep -rn "func Test.*[Cc]onflictWarn" internal/ui/screens/districts/*_test.go`).
- **AC-6 (§39 per-district tax settings).** A tax-settings panel, scoped to the currently-selected district, shows and edits `TaxAPI`'s per-district multipliers (per `engine.tax.md` AC-6); changing a value issues a command through `int.protocol` and the displayed value updates from the resulting delta, not from a locally-mutated value held before the engine confirms it. Check: a passing test changes a multiplier control, asserts the command payload matches the intended new value, and asserts the rendered value only updates once a corresponding delta arrives (`grep -rn "func Test.*[Tt]axSetting\|func Test.*[Dd]istrictMultiplier" internal/ui/screens/districts/*_test.go`).
- **AC-7 (UI-SPEC §4 drill-through — partially buildable, partially blocked; see Escalations/ASM-275).** Every whole-view aggregate figure on F8 (e.g. "this district's total policy cost", "this district's tax revenue") is selectable and `Enter` opens the relevant whole source view (e.g. F2 Finance filtered to the district, per the existing cross-screen navigation pattern) — this half is buildable now. **Not buildable yet:** drilling from a specific number down to the exact underlying ledger line or specific incidence entry (e.g. "this £X of business-rate revenue, from this cell") requires `int.protocol` to carry a structured sub-entity/row-level `DrillTarget` addressing scheme, which `ASM-275` (already open, filed by another BA) states does not exist yet. Check: a passing test asserts whole-view drill-through (`Enter` on a district revenue figure opens F2 scoped to that district) works (`grep -rn "func Test.*[Dd]rillThrough.*[Ww]hole" internal/ui/screens/districts/*_test.go`); row-level drill-through has **no** check in this file and must not be claimed done until `ASM-275` resolves — `doc.go` states this explicitly (AC-11).
- **AC-8 (F8's own scope-resolution consumption).** F8's district cell-highlight rendering (showing which cells belong to the selected district) is sourced from `engine.policies`' `ResolveScope` query (the registered `ui.screen.districts`→`engine.policies` edge, `engine.policies.md` AC-9) — not a screen-local recomputation of which cells have which `DistrictID`. Check: `grep -n "ResolveScope" internal/ui/screens/districts/*.go` shows the call; a passing test asserts the highlighted cell set matches a fixture `ResolveScope` response exactly (`grep -rn "func Test.*[Hh]ighlight.*[Dd]istrict\|func Test.*[Ss]copeRender" internal/ui/screens/districts/*_test.go`).

### Error handling

- **AC-9.** A command the engine rejects (invalid cell selection for district creation, insufficient funds for enactment once `engine.policies`' AC-19 cost-debit lands, an unknown scope target) surfaces the rejection reason to the player — via the returned error/event — rather than silently no-op'ing or leaving the UI in an ambiguous pending state. Check: a passing test submits a command the stub transport is configured to reject and asserts the rejection reason renders (`grep -rn "func Test.*[Cc]ommandReject" internal/ui/screens/districts/*_test.go`).
- **AC-10.** A delta for an unknown/stale subscription (matching `ui.screen.map`'s AC-8 precedent) is dropped and logged (registry-sourced, via `foundation.errors`) rather than applied or causing a panic.

### Determinism & safety

- **AC-11.** F8's rendering is a pure function of (subscribed view-model state, selected district, selected policy, active preview payload) — the same inputs render identically across repeated calls; no `time.Now()`-driven content beyond the shared 300ms threshold-pulse primitive from `ui.widgets` (reused, not reimplemented). `grep -rn "time.Now" internal/ui/screens/districts/*.go` (excluding `_test.go`) returns no matches.
- **AC-12.** `go test ./internal/ui/screens/districts/... -race -count=1` passes with no data race between the delta-applying goroutine and the render path.

### Documentation

- **AC-13.** The package doc states module key `ui.screen.districts`, cites §13-F8 and §52, documents the view-subscription/command name(s) F8 depends on, states explicitly that row-level drill-through is blocked pending `ASM-275` (AC-7), and cross-references `engine.policies.md`'s `PreviewDrift`/confidence-tag conventions this screen renders rather than reinvents.

## Out of scope

- The policy/tax/district engine mechanics themselves (`engine.policies`, `engine.tax`, this BA's sibling files) — this screen is a view and command surface over their registered `PoliciesAPI`/`TaxAPI`.
- Row-level drill-through (see AC-7) — blocked on `ASM-275`'s `int.protocol` addressing-scheme gap, not this item's to solve.
- The Sankey/text-diagram rendering of the Fiscal Circuit (`engine.fiscal`, `ui.diagrams`) — F8 is Districts & Policies, not F2 Finance; this screen links to F2 for whole-view fiscal drill-through (AC-7) rather than rendering the Sankey itself.
- The general dashboards/layout-editor/drill-through framework (`MOD-038`) — F8 only needs to demonstrate the pattern for its own entities, per the same convention `ui.screen.map.md`'s AC-5/AC-6 established for F1.
- Enactment-cost debiting UX (waits on `engine.policies` AC-19, itself blocked on BUG-058) — F8's confirm flow is built to accommodate a cost figure once that edge lands; AC-9's rejection-surfacing path is written generically enough to cover it without rework.

## Escalations

- **For Ben (ASM-275, already open — not a new finding, but directly blocking this item's AC-7).** `int.protocol` has no documented sub-entity/row-level `DrillTarget` addressing scheme, so F8 cannot promise the absolute drill-through rule's full depth (a specific ledger line, a specific incidence entry) — only whole-view drill-through is buildable today. AC-7 is written to reflect exactly that split rather than assuming the finer addressing exists.
- **For Ben (BUG-058, cross-reference — logged against `engine.policies.md`, not a new instance here).** F8's confirm-and-cost flow (AC-9) is written to be forward-compatible with `engine.policies`' currently-blocked AC-19 (enactment cost debit), but cannot fully exercise a cost-rejection path until that edge is registered and built.
- **Assumption logged: ASM-285 (P1, cross-referenced from `engine.policies.md`).** District drawing is cell-paint against a cell-tagged model, not freeform vector geometry — this screen's AC-2 inherits that assumption directly; a vector-polygon design would change this screen's input handling substantially.
- **No independent BUG-058 instance found in `ui.screen.districts`'s own registered edges.** Checked specifically for the "every UI screen needs `ui.core`/`ui.widgets`" pattern seen on the two already-built screens (`ui.screen.map`, `ui.screen.debug`) — but every other not-yet-built F-screen in code.json (`ui.screen.finance`, `ui.screen.build`, `ui.screen.proj`, `ui.screen.services`, `ui.screen.trade`) shows the same omission (engine edges only, no `ui.core`/`ui.widgets`), so this is the established registration convention for undispatched screens, not a drift specific to F8 — not filed as a new BUG-058 instance.
