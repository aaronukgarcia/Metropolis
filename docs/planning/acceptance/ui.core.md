# Acceptance criteria — ui.core (MOD-009)

**BOW code:** MOD-009
**Spec refs:** UI-SPEC §1 (Rendering architecture, `docs/METROPOLIS-MASTER-v2.1.md` lines 722-729); UI-SPEC §5 (Performance budget, lines 765-777); M0-ENG §1.1 (process/thread topology, lines 792-817); `int.protocol` (INT-001, the seam this consumes).
**Date:** 2026-08-08
**Status:** draft-ahead (Sprint 1); **Escalation flagged below — tcell dependency**
**Package under test:** `internal/ui/core/` (confirm via `node claude-bow.js show MOD-009` at dispatch)
**Standard gates:** see `README.md` — package for SG-4/SG-7 is `./internal/ui/core/...`.

## User stories

- As **the player**, I need keystrokes to echo in under 10ms regardless of what the engine is doing, so the game feels instrument-panel-fast, not laggy (UI-SPEC §1/§5).
- As **any F-screen** (`ui.screen.map`, `ui.screen.debug`, …), I need a retained cell-buffer renderer with diff flushing, so screen updates never flicker and only changed cells cost render time.
- As **`T-VIEWS`**, I need a decoupled delta-subscription client applying `int.protocol` deltas to double-buffered view models, so the render loop never blocks on or races with incoming engine state.
- As **any terminal environment** (Windows Terminal or conhost), I need a capability probe selecting the right colour/mouse profile automatically, so the game degrades gracefully instead of rendering garbage on a less-capable terminal.

## Scope

`tcell`-backed TUI core: front/back styled cell buffers with diff flushing, `T-INPUT`/`T-RENDER`/`T-VIEWS` loop topology, capability probe (Windows Terminal vs conhost), minimum-size layout/reflow, zero-allocation hot draw paths.

## Acceptance criteria

### Functional

- **AC-1.** Front/back cell buffers exist covering the full terminal size; a flush diffs back against front and emits only changed cell runs as ANSI — a passing test renders two frames differing in a handful of cells and asserts the flush call count/byte output is proportional to the changed region, not the whole screen.
- **AC-2.** `T-INPUT` translates `tcell` events to internal input messages and **never blocks** — a passing test/benchmark demonstrates the input-handling function returns without waiting on any render or engine operation (e.g. it enqueues to a channel and returns immediately).
- **AC-3.** `T-RENDER` runs on a 10Hz UI tick plus immediate-on-input, and is the **sole** goroutine touching the `tcell` screen (UI-SPEC §1: "tcell screen access is single-goroutine"). Check: `grep -rn "screen\." internal/ui/core/*.go` (the `tcell.Screen` calls) shows they are confined to the file(s)/goroutine implementing `T-RENDER`, and a doc comment states this constraint explicitly.
- **AC-4.** `T-VIEWS` applies `int.protocol` `Delta`s to double-buffered view models: `T-RENDER` reads the front view-model buffer while `T-VIEWS` writes the back one, swapping between ticks — a passing concurrency test drives both loops simultaneously (`-race`) and asserts no torn reads.
- **AC-5.** A capability probe selects Windows Terminal (truecolor, mouse, full Unicode) vs conhost (16-colour palette map, no mouse) automatically at startup — a passing test with a mocked/injected terminal-capability source asserts the correct profile is selected for each case.
- **AC-6.** Minimum terminal size is enforced at 120×30; layout reflows on resize; a pane below its minimum size collapses to a tab stub rather than rendering corrupted/overlapping content — a passing test resizes below a pane's minimum and asserts the collapsed-stub state, not a crash or garbled buffer.
- **AC-7.** Hot draw paths (the cell-buffer diff/flush loop) are zero-allocation in steady state — a `go test -bench . -benchmem` run reports `0 allocs/op` for the flush benchmark after warm-up (matching `engine.core`'s AC-9 pattern; if not yet achievable, the escape-analysis-gate fallback applies identically).

### Error handling

- **AC-8.** A `tcell` initialization failure (e.g. no compatible terminal) produces a registry-sourced error (new `MET-U`-range code, per the per-module subrange-claiming convention) identifying the underlying `tcell` failure, and the process exits with that message printed to the user rather than panicking with a raw Go stack trace or leaving a silent blank screen. Check: a passing test injects a failing `tcell.Screen` initialiser (mocked/stubbed) and asserts the returned/logged error's registry code matches the claimed code AND that no `tcell` panic reaches the caller — not merely that a function named `TestInit*` exists and passes.
- **AC-9.** A malformed/unexpected `Delta` (fails to apply to any known view model) produces a registry-sourced error (new `MET-U`-range code, distinct from AC-8's) naming the `Delta`'s view name and the reason it failed to apply, and the `Delta` is dropped without mutating any view model. Check: a passing test feeds a `Delta` targeting an unknown view (or one with a shape that fails to apply to its known view model) and asserts (a) the returned/logged error's registry code matches the claimed code, and (b) every existing view model's state is byte-identical before and after the dropped `Delta`, and the render loop continues processing subsequent valid `Delta`s afterwards — not merely that a `TestMalformedDelta`-named test exists and passes.

### Determinism & safety

- **AC-10.** No shared memory between the UI process-domain and engine domain — the UI holds *view models built from deltas only*, never a direct reference into engine-owned state. Check: `go list -deps ./internal/ui/core/...` shows no import of `internal/engine/...`, only `internal/protocol` (mirrors `int.protocol`'s AC-14, applied from the consumer side — GR#20).
- **AC-11.** `go test ./internal/ui/core/... -race -count=1` passes with no data race across `T-INPUT`/`T-RENDER`/`T-VIEWS` running concurrently.

### Documentation

- **AC-12.** The package doc states module key `ui.core`, cites UI-SPEC §1/§5 and M0-ENG §1.1, and documents the single-goroutine `tcell` access rule (AC-3) prominently, since violating it is a correctness bug that won't show up until real terminal races occur.

### Security — terminal-escape sanitisation (SEC-011, P1 finding)

**Context (do not re-litigate in review — this is the finding's own text, restated so the criteria below are self-contained):** no render path in `ui.core`/`ui.widgets`/`ui.screen.debug` filters control/escape characters out of drawn text before it reaches `tcell.Screen.SetContent`. Six call sites are cited: `internal/ui/core/buffer.go:56-60` (`Buffer.Set` itself — the funnel every other site already writes through), `internal/ui/widgets/border.go:137` (`drawTitle`), `internal/ui/widgets/table.go:184` (`drawRow`), `internal/ui/widgets/queuelane.go:74` (`QueueLane`), `internal/ui/widgets/bignum.go:103-113` (`drawText`), and `internal/ui/screens/debug/render.go:76-85` (`drawText`/`cursor.line`, which renders the F12 error tail's `errs.Entry.Msg`). Reading all six confirms they already share one thing: every one of them ends in a `buf.Set(x, y, r, style)` call inside a `for _, r := range s` loop over caller-supplied text — none does its own cell writing. That makes `core.Buffer.Set` the true single choke point, not merely the recommended one; see ASM below for why criteria route enforcement there rather than at a new widgets-layer helper.

- **AC-13 (the shared sanitiser).** Before any rune reaches a `Cell` (i.e. inside `core.Buffer.Set`, or a function `Set` unconditionally calls before storing), a rune `r` for which `unicode.IsPrint(r) == false` is never stored verbatim — it is replaced with `�` (Unicode REPLACEMENT CHARACTER), not silently dropped. **Design decision, stated so a reviewer can disagree with it explicitly rather than discover it implicitly:** replace, don't strip. Every one of the six call sites computes cell positions assuming one input rune consumes exactly one output cell (`cx++` / `x++` per rune, clipped against `maxW`/`colLimit`/`limit`); silently dropping a rune shifts every subsequent rune one cell left of where the caller's own width/clipping math expects it, which is a second, quieter bug on top of the one being fixed (and could itself be used to make injected control bytes land somewhere less obviously wrong, if a future draw path ever branched on cell position). A visible placeholder preserves the 1-rune-in/1-cell-out invariant every call site already relies on, and gives a developer glancing at a pane a visible tell that something was filtered, rather than text quietly getting shorter.
  - **No explicit box-drawing/Braille allowlist is required, and the AC below is written to prove that rather than assume it.** `unicode.IsPrint()` classifies Unicode category **So** (Symbol, other) — which covers the box-drawing block (U+2500-257F), block elements (U+2580-259F, the `▁▂▃▄▅▆▇█`/`█▓▒░` glyphs `ui.widgets` already emits), and the Braille pattern block (U+2800-28FF) — as printable already. An implementation that adds a separate, hand-maintained allowlist of "the glyphs we currently emit" is doing unnecessary, drift-prone extra work (GR#3 — a second copy of "what's legitimate" that a future widget author must remember to extend, exactly the class of gap this finding exists to close) and is not what this AC asks for.
  - **Check — negative control:** a fixture string containing a raw ESC byte (`"\x1b[2Jtest"`, chosen because it is the finding's own named example — a screen-clear OSC-adjacent sequence) drawn through the real `core.Buffer.Set` path (calling `Set` directly, or through any one real call site) results in a `Cell.Rune` of `'�'` at that position, never `0x1B` — read back via `Buffer.Get`, not by inspecting an intermediate string.
  - **Check — a second, differently-shaped control byte, not just ESC:** a second fixture using BEL (`0x07`) or a C1 control byte (e.g. `0x9B`, the 8-bit CSI introducer) is filtered the same way. **This second fixture is mandatory, not optional padding** — see the false-pass warning below.
  - **Check — positive control:** a fixture string containing `─│┌┐└┘├┤` (box-drawing), one Braille pattern rune (e.g. `'⠿'`, U+28FF), and the sparkline/gauge block glyphs (`▁▂▃▄▅▆▇█`, `░▒▓█`) drawn through the same real path renders every one of those runes **unchanged** — `Buffer.Get` at each position returns the exact input rune, not `�` and not a blank.
  - **What a lazy implementation looks like:** a switch/blocklist naming specific bytes — `case 0x1B, 0x0D, 0x0A:` — rather than `unicode.IsPrint(r) == false`. It passes an ESC-only test suite and lets BEL, C1 controls, or any Unicode `Cc`/`Cf`/`Cs`/`Co`/`Cn` rune outside the named set straight through, which is a real hole: OSC sequences that terminal emulators respond to don't all start with the same lead byte, and `Cf` (format) runes include bidi-override control characters (e.g. RIGHT-TO-LEFT OVERRIDE) that can visually reorder rendered text without ever being a C0 control byte at all.
  - **False-pass warning:** a check asserting only "the ESC fixture is filtered" cannot distinguish `unicode.IsPrint()`-based filtering from a one-byte-specific blocklist — both pass that single fixture. The second fixture (a control byte with no plausible shared `case` label with ESC) is what actually discriminates a real printability check from a demonstrated-instance patch, per `dev-team-process.md`'s Weakness pattern #3 ("fix the class, not the demonstrated instance") — this is exactly that pattern applied to this AC's own check.

- **AC-14 (enforced once, centrally — not five patched sites and one missed).** All six cited locations produce sanitised output, and they do so **because they all end in the same `Buffer.Set` call**, not because each was independently patched to filter before calling it.
  - **Check — static:** `grep -rn "unicode.IsPrint\|IsPrint(" internal/ui/widgets/*.go internal/ui/screens/debug/*.go` (excluding `_test.go`) returns **no matches** outside `internal/ui/core/`. A match in a widget or screen file is itself a finding under this AC — it means a call site grew its own copy of the filter instead of relying on the shared one, which is the "five independent copies of similar-but-drifted logic" failure mode this AC exists to catch (GR#3), even if that copy happens to be correct today.
  - **Check — live, one sub-test per call site (six sub-tests, not one shared string reused loosely):** a control-byte-carrying string (reuse the AC-13 ESC fixture) is drawn through each of `drawTitle` (border.go), `drawRow` (table.go), `QueueLane` (queuelane.go), `drawText` (bignum.go), and `drawText`/`cursor.line` (debug/render.go) — calling the real exported/package function with a real `*core.Buffer`, not a mock — and in every one of the six, `Buffer.Get` at the written position(s) returns `�`, never the raw control rune. Six assertions, six named sub-tests (`t.Run("border.drawTitle", ...)` etc.) so a future regression names exactly which call site stopped routing through `Buffer.Set` rather than reporting one opaque failure.
  - **False-pass warning:** a single end-to-end test that only exercises `debug/render.go` (the F12 case AC-15 already covers) and infers "the other five must be fine because they call the same `buf.Set`" is not this AC — the whole point of Weakness pattern #3 is that a plausible-sounding inference is exactly what leaves siblings standing. Each of the six needs its own passing assertion.

- **AC-15 (the named real-world case — F12's error tail).** A fixture constructs an `errs.Entry` (`internal/foundation/errs/log.go`) with `Msg` set to a string carrying a raw ESC-led sequence (e.g. `"connection reset\x1b]0;pwned\x07"`, an OSC title-bar-spoofing shape — the concrete attack class named in the finding's own text), routes it through the real debug-screen error-tail render path (`renderErrorTail`/equivalent → `cursor.line` → `drawText` → `Buffer.Set`, not a hand-rolled stand-in), into a real `*core.Buffer`, and then scans **every** `Cell` the render touched (not just the position a human would eyeball) asserting no `Cell.Rune` fails `unicode.IsPrint()`. This is the end-to-end proof that the specific path named in SEC-011's opening sentence is closed, not merely that the underlying primitive (AC-13) works in isolation.
  - **False-pass warning:** asserting only that the rendered *string representation* (if the render path is ever refactored to build a string before drawing) contains no ESC byte is not equivalent to this check — the finding is specifically that bytes reach a `Cell` via `SetContent`, so the assertion must read back `Cell` values from the `Buffer`, the same object `Flush` reads from to call `tcell.Screen.SetContent`.

## Out of scope

- Individual widgets (sparklines, Braille charts, etc.) — `ui.widgets` (`MOD-010`), a separate item built on top of this core.
- The key-grammar/leader-sequence input language — `MOD-011`, separate item; `ui.core` only needs to deliver translated input events, not interpret the grammar.
- Any specific F-screen's content — `ui.screen.map`, `ui.screen.debug`, etc., separate items.

- **SEC-011 is one instance of a class, per its own linked BOW comment — flagged, not decided, here.** Bill's 2026-08-09 comment on SEC-011 links it to SEC-022 (an untrusted `ShardMeta.SHA256` reaching stderr via `%s` instead of `%q` in `int.serializer`) and ASM-060 (Destructive-1's own note that a scoped grep sweep — there, `int.serializer` + `cmd/metctl` — does not prove completeness elsewhere). Recommending, not deciding: given this is now the *second* independently-discovered instance of the same class (UI cell-rendering here, error-formatting in SEC-022), a repo-wide mechanical check — astgate-style (`internal/foundation/astgate/`, `tool.astgate`, BUG-024's approach: AST-derived enumeration rather than a hand grep) walking for raw `%s`/string-interpolation of a value traceable to an untrusted source, and/or any rune-writing path that bypasses `core.Buffer.Set` — may be warranted as a follow-up BOW item separate from this fix, exactly per ASM-060's own point that a scoped sweep doesn't prove completeness.
