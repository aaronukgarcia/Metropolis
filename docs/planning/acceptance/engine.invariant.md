## What changed since the 2026-08-08 draft

- **`engine.core`'s real phase-hook API replaces AC-7's placeholder.** The draft hedged AC-7 with "if `engine.core` doesn't exist yet... satisfied by a `RunEveryTick(pipeline PhaseRegistrar)` registration function". It exists now: `Engine.RegisterPhaseHook(kind PhaseKind, hook PhaseHook) error` (`internal/engine/core/phase.go`/`engine.go`), where `PhaseHook` has `RunShard(shard int) ([]Effect, error)` and `ApplyEffect(Effect)`. AC-7 is rewritten below against the real signature, and picks up the real constraint that comes with it: **registration must happen before the engine seals** (`ErrEngineSealed`, `MET-E011`, ffirst on `AdvanceTicks`) — an invariant checker that tries to register itself lazily, on first use, is now a defined failure mode, not a hypothetical one.
- **Weakness pattern #1 applies directly to this module's entire premise.** "Conservation... hard assert in dev" (§14) and "nothing ever despawns... an invariant-checker assert" (§19.3) are exactly the shape of prose invariant the sweep's first three findings were about (an exported mutable slice claiming "never reordered", hooks claiming "boot only" with nothing enforcing it). This item's whole job is to be the *code* that makes an invariant "impossible or loud" instead of prose — so its own criteria must hold itself to that standard doubly hard: AC-1b below requires the `Invariant` registry itself (not just the stocks it checks) to resist being silently bypassed or partially skipped through its own public API.
- **Weakness pattern #4 — a `Violation`'s entity IDs are a privileged position too.** AC-11 (old draft) already required a `Violation` to carry "affected entity IDs where applicable" for `errs.New` construction. Those IDs, once this checker's output reaches F12's error-tail rendering (a later UI consumer) or a log line, become the kind of value SEC-011 found dangerous elsewhere (a rendered string carrying terminal control bytes). AC-11b below closes that before a consumer ever exists to be attacked.

## Standing: an AC's check must be able to fail (liftable BA-template text, from dev-team-process.md v1.9 / BUG-033)

Every acceptance criterion in this file is a pair: a **rule** (what must be true) and a **check** (how a verifier proves it). The two can drift — a check written as a grep, a type sketch, or an example artifact name can be satisfiable by an implementation that reads the rule's prose and still violates its intent. This file's AC-1 (Check sketch vs. AC-1b's ran/skipped requirement) is a worked example of exactly that drift, caught only when a developer tried to build both halves at once.

**The standard, binding on this BA and every BA:**

- **A check must be capable of FAILING an implementation that satisfies the AC's prose but violates its rule.** Before writing a check, describe the laziest plausible implementation that technically reads as compliant, and confirm the check rejects it. If it wouldn't, the check is documentation, not verification.
- **Where a check is a grep**, state what a false pass looks like — a string existing is not the same as the string meaning what the rule needs (e.g. a `grep -n "MET-"` finding the code inside an unrelated comment, or a `grep -rn "func Test.*Foo"` finding a test that runs and asserts nothing).
- **Where a check is a type/signature sketch**, say explicitly which part is binding (the information the type must be able to carry) and which is illustrative (field names, exact method signature, "e.g." on the shape itself). "e.g." on a signature is fine; "e.g." on the information the signature must carry is not — that is the exact mistake AC-1 made before this correction.
- **Where a check names an artifact**, name its shape (file vs. directory, format, what makes it valid), not an example filename — an example implies a shape by accident, and a reader builds to the accident.

This section may be lifted verbatim (with the worked-example paragraph above trimmed or swapped for a new file's own instance) into the BA acceptance-criteria template once one exists.

## User stories

- **US-1.** As the engine, I need a hard assert every tick (in dev builds) that people, money, goods, and vehicles conserve, so that a bug that silently creates or destroys state is caught at the moment it happens, not months of game-time later when the discrepancy has compounded (§14).
- **US-2.** As a release build, I need the same conservation checks to run but produce a registry-sourced logged error instead of a hard crash, so that a live game can surface a real bug to the player/F12 panel without terminating the process (§14; GR#1/#7).
- **US-3.** As the transport system's design (§19), I need vehicle-conservation enforced structurally, so that despawn-masking gridlock — a known failure mode of 'Blue' — is impossible even before `engine.traffic` exists to generate vehicles (§19.3).
- **US-4.** As `harness.headless` and CI, I need the invariant suite runnable standalone against a scenario/save, so that H-HEADLESS's "per-phase timing + invariant reports every tick" (M0-ENG §2.3) has real checks to report, and so H-SYNTH's perf runs are validated as not just fast but correct.
- **US-5.** As a future engine module (`engine.market`, `engine.finance`, `engine.traffic`, etc., landing Sprint 4+ per the sprint plan), I need a registration seam for adding new conserved stocks, so that "conservation invariants extended to each new stock" (sprint plan S9 exit gate) is a config/registration change, not a rewrite of this package.

## Scope

The invariant-checker framework (hard assert in dev / registry-logged error in release), the four v1 conserved stocks (people, money, goods, vehicles), its wiring into `engine.core`'s tick pipeline, and its standalone-runnable form for H-HEADLESS/CI.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; amended per ASM-157 — see "Corrections" below).** An `Invariant` interface exists with a method that computes/verifies a conservation check against the current world state (or a state snapshot/delta), and returns a value that structurally distinguishes three outcomes, never conflating any two of them: "this invariant ran and found no violation", "this invariant did not run" (AC-1b/AC-12's unregistered-stock case), and "this invariant ran and found a violation". **Binding:** the return type must carry a ran/skipped signal that is separate from the violation payload itself — a bare violation type cannot do this, because its own zero value is the only candidate for "no violation", and that same zero value cannot simultaneously mean "skipped, never checked". **Illustrative, not binding:** the exact method name, field names, and type layout — e.g. `Check(state Snapshot) Result`, where `Result` carries `Ran bool` alongside a `Violation`, is one satisfying shape; a differently-named tri-state or a `(ran bool, v Violation)` two-return-value form would satisfy the same binding requirement. Check: `go doc ./internal/engine/invariant Invariant` shows the method; `go doc ./internal/engine/invariant Result` (or whatever the return type is named) shows a field distinguishable from the violation payload that can carry "did this run" independently of "what did it find" — a check that only confirms a `Check`-shaped method exists, without inspecting whether its return type can represent that distinction, would pass a bare-`Violation` implementation that satisfies this AC's prose while making AC-1b structurally unenforceable, which is exactly the contradiction this amendment closes.
- **AC-1b (weakness pattern #1 — the registry cannot be silently starved).** The set of registered invariants actually run each tick cannot be reduced through the public API without it being loud: there is no exported way to unregister a previously-registered invariant, and a partial-registration state (some stocks registered, some not — the legitimate AC-12 case) is always distinguishable in the suite's output from "all stocks conserved" — a consumer reading `RunSuite`'s result can never mistake "3 of 4 invariants ran clean" for "4 of 4 invariants ran clean". Check: `grep -n "Unregister" internal/engine/invariant/*.go` finds no exported unregister method (or, if one exists for a legitimate hot-reload/debug reason, it is logged/loud per this AC's spirit and a passing test proves it); a passing test asserts `RunSuite`'s result structurally reports which invariants ran vs. which were skipped, not just an aggregate pass/fail (`grep -rn "func Test.*[Pp]artial\|func Test.*[Ss]kipped" internal/engine/invariant/*_test.go`).
- **AC-2.** A registry of `Invariant` implementations exists, seeded with at least four: people conservation, money conservation, goods conservation, vehicle conservation. Check: `grep -n "type PeopleInvariant\|type MoneyInvariant\|type GoodsInvariant\|type VehicleInvariant" internal/engine/invariant/*.go` (or equivalently named types) all match.
- **AC-3.** People conservation: total citizen count across all fidelity tiers (HOT/WARM/COLD, §5.2) plus tracked emigration/immigration/birth/death deltas for the tick balances to zero unexplained change — a citizen must be traceable to birth, death, or migration, never simply vanish or appear. Check: a passing test constructs a state with an untracked citizen disappearance and asserts a `Violation` is reported (`grep -rn "func Test.*[Pp]eople" internal/engine/invariant/*_test.go`).
- **AC-4.** Money conservation: total money in circulation (citizen wealth + firm/institution balances + city treasury + in-flight transactions) balances against tracked income/expenditure for the tick — this is the invariant the sprint plan's S4 exit gate later relies on running "green over 120 headless months", so it must be extensible to the finance module's ledger without a rewrite. Check: a passing test asserts an untracked money creation/destruction is caught (`grep -rn "func Test.*[Mm]oney" internal/engine/invariant/*_test.go`).
- **AC-5.** Goods conservation: tracked commodity/stock quantities (per §6/§8 JIT logistics, once those modules register their stocks) balance against production, consumption, and in-transit flows for the tick. Check: `grep -n "GoodsInvariant" internal/engine/invariant/*.go` and a passing test covering a synthetic goods-stock scenario (`grep -rn "func Test.*[Gg]oods" internal/engine/invariant/*_test.go`).
- **AC-6 (§19.3).** Vehicle conservation: every vehicle instance is traceable to spawn (trip origin) and despawn (trip completion/parking), and the invariant fails loudly if a vehicle's count changes without a matching spawn/despawn event — making despawn-masking structurally impossible per §19.3, even before `engine.traffic` (Sprint 5) exists to generate real vehicles. Check: a passing test constructs a synthetic vehicle-count mismatch and asserts a `Violation` (`grep -rn "func Test.*[Vv]ehicle" internal/engine/invariant/*_test.go`).
- **AC-7 (rewritten against the real, landed `engine.core` API).** The invariant checker registers itself as one or more `core.PhaseHook` implementations via `(*core.Engine).RegisterPhaseHook(kind core.PhaseKind, hook core.PhaseHook)` — real signature, `internal/engine/core/phase.go` — against whichever phase(s) conservation checking belongs to (the daily tick and/or the monthly `finance`/`consumption-shortfall` phases, documented explicitly since §14 doesn't mandate a specific phase). Registration happens at boot time, **before** the caller's first `AdvanceTicks` call — a registration attempted after sealing must handle `ErrEngineSealed` (`MET-E011`) as a defined, documented failure the wiring code surfaces loudly (AC-7b), never swallowed. Check: `go doc ./internal/engine/invariant` shows a constructor/wiring function accepting `*core.Engine` (or an interface narrow enough to satisfy it) and calling `RegisterPhaseHook`; a passing test registers against a real (or minimally-faked) `core.Engine` and asserts the hook fires once per the documented phase per tick (`grep -rn "func Test.*[Ww]iring\|func Test.*[Pp]haseHook" internal/engine/invariant/*_test.go`).
- **AC-7b (new — sealing interaction).** If this package's own wiring helper is called after the target engine has already sealed (a caller-ordering mistake, not this package's own bug), it surfaces `ErrEngineSealed` verbatim (wrapped with this package's own correlation ID, not swallowed into a generic "registration failed") rather than silently no-op'ing and leaving the invariant suite quietly never running. Check: a passing test seals a fake/real engine first, then attempts wiring, and asserts the caller receives an error identifying `ErrEngineSealed` as the cause (`grep -rn "func Test.*[Ss]ealed" internal/engine/invariant/*_test.go`).
- **AC-8.** In dev builds (a build tag or debug-mode runtime flag, consistent with M0-ENG §3's "debug is a runtime feature switch, not a build flavour"), a `Violation` triggers a hard assert (panic or `os.Exit` with diagnostic output naming the invariant, the tick, and the imbalance amount). Check: `go doc ./internal/engine/invariant` documents the dev-mode hard-fail behaviour; a passing test (using a test-only override, not an actual process-killing panic in the test binary) asserts the hard-fail path is selected when debug mode is on (`grep -rn "func Test.*[Hh]ardFail\|func Test.*[Dd]evMode" internal/engine/invariant/*_test.go`).
- **AC-9.** In release builds/non-debug mode, a `Violation` instead produces a registry-sourced logged error (GR#1/#7: new `MET-E`-range code(s) added to `data/errors.json`) surfaced to the F12 error log tail's underlying store (`foundation.errors`), never a silent drop. Check: `grep -n "MET-" internal/engine/invariant/*.go` finds registry code references; a passing test asserts the release-mode path logs rather than panics (`grep -rn "func Test.*[Rr]elease" internal/engine/invariant/*_test.go`).
- **AC-10.** A standalone entry point (function or small `cmd/`) runs the full invariant suite against a save/scenario outside the live tick loop, for `harness.headless`'s "invariant reports every tick" output and CI's invariant suite (sprint plan S2 exit gate: "stub-vs-real conformance suite runs" alongside this). Check: `go doc ./internal/engine/invariant RunSuite` (or equivalent) exists and is exercised by a passing test loading a fixture/synthetic save.

### Error handling

- **AC-11 (GR#7).** Every `Violation` carries enough context (invariant name, tick, expected vs. actual value, affected entity IDs where applicable) to construct a registry error via `errs.New` without a second data-gathering pass. Check: `go doc ./internal/engine/invariant Violation` lists these fields.
- **AC-11b (weakness pattern #4 — a rendered ID is terminal input, however inert it looks).** `Violation`'s free-text/ID fields (entity IDs, invariant names, any diagnostic string) are documented as **display data that must be sanitised or escaped by whatever renders them** (F12's error-tail, a future log formatter) before reaching a terminal or log sink verbatim — mirroring SEC-011's finding that "any rendered string, e.g. an error message" is a path to terminal-control-byte injection. This package does not itself render to a terminal, so its obligation is narrower and cheaper: it must **never construct an entity-ID-derived string that gets interpreted as anything other than opaque display text downstream** (no format-string assembly of an ID into a second string that a consumer might `Printf`-interpret) and its doc comment states the sanitisation obligation explicitly for the next package in the chain. Check: `grep -n "fmt.Sprintf.*%s.*ID\|fmt.Sprintf.*ID.*%s" internal/engine/invariant/*.go` (excluding `_test.go`) finds no ID interpolation into a further format string; `go doc ./internal/engine/invariant Violation` states the downstream-sanitisation obligation.
- **AC-12.** A missing/unregistered stock referenced by a module that hasn't registered its invariant yet (e.g. `engine.market` not yet real) does not crash the suite — the checker skips unregistered stocks and reports which are unchecked, rather than assuming zero and false-flagging. Check: passing test coverage (`grep -rn "func Test.*[Uu]nregistered" internal/engine/invariant/*_test.go`).

### Determinism & safety

- **AC-13 (GR#21).** Running the invariant suite twice against the same tick's state produces identical `Violation` results (no nondeterministic floating-point accumulation order causing a flaky false-positive). Check: a passing test asserts determinism (`grep -rn "func Test.*[Dd]eterminis" internal/engine/invariant/*_test.go`).
- **AC-14 (M0-ENG §6 point 3 DoD; shard-count invariance).** The invariant suite produces identical results run against the same world computed under different shard/worker counts (1 vs. N workers) — this is the specific DoD requirement for determinism-relevant modules. Check: `grep -rn "func Test.*[Ss]hard.*[Ii]nvarian\|func Test.*[Ww]orkerCount" internal/engine/invariant/*_test.go` finds coverage, and it passes.
- **AC-15 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/invariant/*.go` (excluding `_test.go`) returns no matches — invariant checks run against simulation tick/state data only, never wall clock.
- **AC-16.** `go test ./internal/engine/invariant/... -race -count=1` passes with no data race when invariants are checked concurrently across the 256-shard worker pool (§1.2/M0-ENG §1) that `engine.core` will eventually drive this from. Check: `grep -n "go func()" internal/engine/invariant/*_test.go` finds at least one concurrency test.
- **AC-16b (new — copy-safety, following SEC-014/SEC-016/SEC-019/SEC-020's precedent).** If this package's invariant registry type holds a mutex alongside a reference-type field (a map of registered invariants, most likely), it follows the same copy-safety guard `engine.core`'s `Engine` and `internal/protocol`'s `SubscriptionServer`/`InProcTransport` now carry: an identity (`self`) check before any lock is taken, rejecting a struct-copied receiver with a registry-sourced error rather than risking a permanent silent deadlock (SEC-016's shape) or a torn-map crash (SEC-003/SEC-019's shape). Check: if the registry type combines `sync.Mutex`/`sync.RWMutex` with a reference-type field, `grep -n "self\s" internal/engine/invariant/*.go` shows the identity guard and a passing test constructs a struct copy and asserts rejection, not a hang (`grep -rn "func Test.*[Cc]opy" internal/engine/invariant/*_test.go`); if no such combination exists in this package, `doc.go` states that explicitly.

## Out of scope

- The actual production/consumption/transaction logic of any stock (finance ledger, JIT logistics, traffic vehicle spawning) — those are their owning modules' (Sprint 4/5+) jobs; this item only checks conservation of whatever numbers those modules report.
- F12 Info Panel rendering of invariant status — that is a UI-layer concern consuming `foundation.errors`'/this package's output.
- Historical/trend analysis of invariant violations over a play session — this item reports per-tick violations, not a dashboard.
- Auto-repair or self-healing of a detected imbalance — a violation is reported/asserted, never silently corrected (that would itself violate GR#1's "never silently drift").
