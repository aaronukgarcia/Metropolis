## Design-north-star framing (applied, not decorative)

`docs/planning/design-north-star.md`'s five-question test, applied to this item, because an "advisor" is exactly the shape of feature the north star warns about — something that can relieve pressure without creating a new claim on the pie:

1. **Which conflicting demand does this sharpen?** None, directly — Helper is infrastructure/UX, not a lever on money, land, or throughput. It answers the north star's own closing line: "a feature that answers none of these may still be necessary infrastructure — but it isn't *entertainment*." That is an honest classification, not a failure to qualify.
2. **What does the player give up?** As specified, nothing tangible — querying the Helper has no in-game cost (no time tick, no fee) named anywhere in FEAT-063's description or Aaron's ruling. This is a real gap against north-star idea #1 ("the pie is only so big") and is escalated below (not decided here — a query-cost mechanic is balance-number-regime territory, Aaron's alone to set).
3. **Does the consequence stick?** Not applicable to Helper's own action — but it is applicable to what Helper *tells the player*, transitively: if a "what if I do X" projection is wrong, the player's real, sticking decision was made on bad information. AC-5 below is the direct control for this: a projection must be sourced from the same pricing data path the real action uses, not a hand-authored duplicate that can drift out of truth.
4. **Does it snowball?** Not applicable.
5. **Can a long bet be made on it?** Not applicable.

**Conclusion, binding on the ACs below:** Helper is necessary infrastructure, not itself a north-star-scoring feature, and the ACs below exist to stop it from *accidentally* violating the north star while it does its infrastructure job — specifically: (a) it must not become a "best move" oracle that plays the juggle for the player (AC-7), and (b) its answers must not be allowed to silently drift from the real consequence the player will actually face (AC-5). It must not crowd out entertainment-bearing work — this is why v1 is deliberately narrow (ask-driven panel only, registration-metadata cost only) rather than a fuller advisor.

## User stories

- **US-1.** As every future player-action feature module, I need a single, stable contract (action taxonomy id, preconditions, a consequence-pricing projection query) to implement and register with, so that adding a new player action never requires bespoke advisor plumbing — the cost is metadata, paid once, at the point the action is built.
- **US-2.** As the player, I need to open a panel and ask "what should I do?" and get back the set of currently-available registered actions with their preconditions and headline consequences, so I can make an informed choice without the game either hiding the option space or making the choice for me.
- **US-3.** As the player, I need to ask "what if I do X?" for a specific action and get back its registered consequence-pricing projection, so I can judge a stretch (north-star idea #5) before committing real money to it.
- **US-4.** As a future BA/developer building the contextual-preview layer later, I need this item's registration data model to already carry everything a hover/selection-triggered preview would need, so that layer is a new UI surface over existing data, not a rework of the registration contract itself.
- **URS-5 (GR#20).** As the lead and QA, I need the registration contract to be a real registered `code.json` interface with named consumers, not an informally-agreed Go type that every future feature module happens to import, so contract drift is caught the same way `engine.market`'s `MarketAPI` consumers are tracked today.

## Scope

**In scope (v1):**
1. The advisor-metadata registration contract: a `Registrant`-shaped Go interface (action taxonomy id, preconditions, a consequence-pricing projection query) and a `Registry` type every player-action feature module registers against at boot.
2. The ask-driven panel query surface: `Recommend(state)` ("what should I do?") and `Preview(state, actionID, params)` ("what if I do X?"), both pull-only, both read-only.
3. Fixture-driven proof of both, since no real player-action feature exists yet to register (mirrors `tool.astgate.md`'s fixture-only proof pattern for BUG-024).

**Out of scope (v1) — see the dedicated scope-boundary ACs below:**
- Contextual on-selection previews (hover/select-triggered inline Helper suggestions) — a later layer, not built now.
- Any actual UI rendering/widget work for the panel beyond what proves the query surface is consumable (Documentation/QA cross-check this at build time; this file does not specify pixel layout).
- A query-cost/consultant-fee mechanic (escalated, not decided).
- Any real player-action feature registering for real — none exist in the tree yet; that happens feature-by-feature as each is built, per US-1.

## Acceptance criteria

### Functional — the registration contract (structural; this is the load-bearing part, GR#20)

- **AC-1 (the `Registrant` contract shape).** A `Registrant` interface exists with exactly three members, each independently testable: (a) an **action taxonomy id** accessor returning a stable, non-empty, registry-unique identifier type (e.g. `ActionTaxonomyID string`, mirroring `engine.market`'s `CommodityType string` pattern — the JSON/Go identity is the same value, no separate name-mapping table); (b) a **preconditions** accessor returning a slice of independently-evaluable precondition objects, not a single opaque boolean; (c) a **consequence-pricing projection query** method taking the action's parameters and a read-only game-state view, returning a structured projection or a registry-sourced error — never a bare string or an `interface{}`. Check: `go doc ./internal/engine/helper Registrant` shows exactly these three members with the named shapes; a fixture package (mirroring `tool.astgate.md`'s fixture convention) defines a minimal `Registrant` implementation and a test asserts it satisfies the interface at compile time (`var _ helper.Registrant = (*fixtureAction)(nil)`). **What a lazy implementation looks like:** a `Registrant` interface with a single `Describe() string` method that a feature satisfies by writing prose — this "registers" in the sense of compiling, but carries none of the three named obligations and cannot be queried structurally by `Recommend`/`Preview`. **False-pass warning:** a test that only asserts "a type can implement `Registrant`" without asserting the three members' *return shapes* would pass a `Registrant` whose precondition accessor returns `[]string` (unevaluatable prose) instead of evaluable precondition objects — the check must inspect the shape, not just presence.
- **AC-2 (preconditions are independently evaluable, never a panic).** Each precondition returned by AC-1(b) carries a stable id, a human-readable description function, and an `Evaluate(state) (bool, error)` function that never panics on a well-formed `GameStateView` and returns a registry-sourced error (GR#7) — never a silent `false` — when it genuinely cannot evaluate (e.g. a required field is absent from the state view). Check: a fixture precondition whose `Evaluate` is given a state missing a field it needs returns a non-nil registry error, not `(false, nil)`; a Destructive-agent pass specifically tries feeding a zero-value `GameStateView` to every fixture precondition and confirms no panic (`go test -race` over the fixture package with a fuzzed/zero-value input). **What a lazy implementation looks like:** `Evaluate` returning `false` whenever it hits an unexpected state shape, which reads to a caller as "precondition genuinely not met" rather than "evaluation was impossible" — indistinguishable failure modes that silently misinform the panel's `Recommend` output (AC-7).
- **AC-3 (registration is sealed after boot — the invariant-in-prose trap, weakness pattern #1).** `Registry.Register` is only callable during boot wiring; once the registry has been read from (by `Recommend`/`Preview`, or an explicit `Seal()`/equivalent call), a further `Register` call returns a registry-sourced error rather than either panicking or silently succeeding into a registry a live query has already read a stale view of. This must be enforced by the type, not stated only in a doc comment — mirrors `dev-team-process.md`'s standing rule ("a comment saying 'never X at runtime' is a code smell, not a control") and `MarketAPI`'s "populated once at construction, never mutated afterward" precedent. Check: a test registers a fixture, calls `Recommend` once (or an explicit seal), then calls `Register` again with a second fixture and asserts a non-nil registry-sourced error is returned, `Register`'s target set is unchanged, and no panic occurs (`grep -rn "func Test.*[Ss]eal\|func Test.*[Ll]ateRegist" internal/engine/helper/*_test.go`). **What a lazy implementation looks like:** an exported mutable slice/map that any package can append to at any time (the exact `SEC-005` shape from weakness pattern #1) — compiles, "registers" fine, and is late-registrable from anywhere with no error, no lock, no seal.
- **AC-4 (registering costs ONLY metadata — the standing constraint, and the AC that must catch both failure directions).** A `Registrant` that implements AC-1's three members and does nothing else compiles, registers successfully, and appears correctly in `Recommend`'s candidate set (AC-7) and `Preview`'s query results (AC-8) with **no** additional obligation: no UI rendering hook, no widget registration, no reference to any presentation/screen package. This is checked from **both directions**, per the dispatch brief's explicit concern: (a) a fixture `Registrant` with zero UI-facing code anywhere in its package registers and queries successfully — proving nothing was silently skipped because "nothing calls it yet"; (b) `internal/engine/helper`'s own package has **zero** imports of any `internal/ui/...` package and **zero** code path that fires on a selection/hover/cursor event — proving the contextual-preview layer (out of scope, see AC-10) was not accidentally built in reaching for "complete". Check: `grep -rn "internal/ui" internal/engine/helper/*.go` (excluding `_test.go`) returns no matches; the AC-1 fixture package (a) above has no import of anything UI-shaped and its registration/query test passes standalone. **What a lazy implementation looks like:** a developer who, reasoning "the panel needs *something* to show," adds a `RenderHint`/`IconID`/`OnHover` field to `Registrant` "since it's convenient" — this technically still "just metadata" by a loose reading but is the first thread of the later contextual-preview layer being pulled forward uninvited; the check is that no such field exists on `Registrant` at all in v1, not that it's merely unused.
- **AC-5 (consequence projections are sourced from the real pricing path — no hand-authored duplicate, weakness pattern #2).** `ProjectConsequence`'s implementation, for any real feature that later registers, is required (by this contract's documented obligation, verified against the AC-1 fixture in the interim) to read from the same pricing/data source its actual execution path would use — never a second, hand-maintained estimate that can silently drift from the real cost (the exact shape weakness pattern #2 names: "a value duplicated across a module boundary needs a drift test"). Since no real feature exists yet to prove this against, this AC is satisfied at contract level by (a) `ProjectConsequence`'s doc comment stating the obligation explicitly, in the imperative, with a worked example of the failure mode it prevents (a projection promising a rate the real transaction never honours), and (b) the fixture `Registrant`'s `ProjectConsequence` reading its numbers from a fixture data source shared with a fixture "execute" stub, with a drift test (per weakness pattern #2's four-step remedy) asserting the two agree. Check: `internal/engine/helper/doc.go` (or the interface's own doc comment) states this obligation in prose citing weakness pattern #2 by name; the fixture package's drift test exists and is proven able to fail (weakness pattern #2 step 4 — mutate the fixture's duplicated constant and confirm the test catches it, don't just add the test). **What a lazy implementation looks like:** documenting the obligation in prose only ("registrants should avoid drift") with no fixture demonstrating the drift-test pattern — this is exactly `dev-team-process.md`'s "an invariant stated in prose is not enforced" trap, one layer up, applied to a *future* feature's obligation rather than this package's own state.
- **AC-6 (GR#21 determinism; no wall clock, no hidden RNG).** `Preview`/`ProjectConsequence`, given the same `GameStateView` and the same action parameters, returns byte-identical results on repeated calls within the same process and across a fresh process given a serialised-identical state (mirrors `MarketAPI.Price`'s AC-12 precedent: "two calls with the same commodity... return the identical value"). No implementation may read `time.Now()`, an unseeded RNG, or any other non-deterministic source on this path. Check: a fixture test calls `Preview` twice with an identical constructed state and asserts equal results; `grep -rn "time.Now()\|rand\.\(Int\|Float\)" internal/engine/helper/*.go` (excluding `_test.go`) finds no unguarded non-deterministic calls on the query path.

### Functional — the ask-driven panel (v1 scope)

- **AC-7 ("what should I do?" — `Recommend`, and the north-star-preserving shape).** `Recommend(state)` returns the set of currently-registered actions whose preconditions currently evaluate true against `state`, each carrying its taxonomy id, a human-readable description, and (where cheap to compute — see Out of scope) a headline consequence summary — presented as a **candidate set the player chooses among**, never collapsed into a single ranked "do this" imperative with hidden tie-breaking logic. This is the direct functional expression of the north-star framing above: the sim presents the competing demands, the player remains the optimiser. Check: `Recommend`'s return type is a slice/set (`[]Recommendation` or equivalent), not a single value; a fixture test registers three actions with different, non-dominated trade-offs and asserts all three appear in `Recommend`'s output with no field expressing a total order/rank between them (`grep -rn "func Test.*[Rr]ecommend" internal/engine/helper/*_test.go` and a manual read confirming no `Rank`/`Score`/`Best` field on the returned type). **What a lazy implementation looks like:** a `Recommend` that internally scores every candidate and returns only the top-N (or the single top) result — cheap to build, reads as "helpful," and is exactly the oracle the north-star framing above rules out; a `Score float64` field on the return type, even if unused by the panel today, is the same defect one refactor away from being read by a UI that renders it as a verdict. **False-pass warning:** a test asserting only "the correct actions are present" would pass a version that also silently sorts them best-to-worst with no explicit rank field — the check must confirm no ordering-implies-verdict signal exists, not just that membership is correct.
- **AC-8 ("what if I do X?" — `Preview`).** `Preview(state, actionID, params)` resolves `actionID` against the registry (returning a registry-sourced `ErrUnknownAction`-shaped error for an unregistered id — never a silent zero-value projection, mirroring `MarketAPI.lookup`'s `ErrUnknownCommodity` precedent), evaluates that action's preconditions against `state` and surfaces their pass/fail state alongside the projection (so a preview can honestly say "here's what would happen, but you don't currently qualify" rather than presenting an unreachable fantasy as available), and calls the registrant's `ProjectConsequence` with `state`/`params`, returning its result unmodified. `Preview` never mutates `state` and never calls any action-execution path — it is read-only by construction (v1's pull-only, no-side-effects requirement). Check: a fixture test calls `Preview` for an unregistered id and asserts the specific unknown-action error; a second test calls `Preview` for a registered but currently-precondition-failing action and asserts the response carries both the projection and the failing-precondition information (not one or the other); a state-equality assertion before/after `Preview` confirms no field of the passed `GameStateView` changed (only meaningful if `GameStateView` is a concrete comparable fixture type in the test — assert via `reflect.DeepEqual` or equivalent on the fixture). **What a lazy implementation looks like:** `Preview` silently calling the registrant's real execution/apply path "to compute the real numbers" instead of a separate projection path — the single most direct violation of "pull-only" possible, since it would make *asking* the Helper a way to accidentally take the action.
- **AC-9 (presentation ships once).** The panel's rendering of `Recommend`/`Preview` output exists in exactly one UI surface (the panel) for v1 — no second, duplicate rendering of the same registered data on any other screen. Check: `grep -rln "helper\.\(Recommend\|Preview\)" internal/ui/` (or wherever the panel's package lands) returns matches from exactly one screen package. This is the direct converse check to AC-10 below.

### Scope boundary — contextual on-selection previews are OUT of v1

- **AC-10 (the boundary check, must catch both failure directions).** No code path in the delivered tree triggers a Helper query (`Recommend` or `Preview`) from a hover, selection, or cursor-focus UI event — the only trigger for a Helper query in v1 is an explicit player action opening the panel and submitting an ask. Check: `grep -rn "Recommend(\|Preview(" internal/ui/` (excluding the panel's own screen package) returns no matches; a manual read of every UI event handler registered against selection/hover events (`grep -rn "OnHover\|OnSelect\|OnFocus" internal/ui/` — whatever the actual event-handler naming convention turns out to be at build time) confirms none call into `internal/engine/helper`. **What a lazy implementation looks like, direction (a) — skipping the contract:** a junior reasons "the panel is all that's asked for, I'll just hardcode the panel's three example questions and skip building `Registrant`/`Registry` entirely" — this passes a shallow "the panel shows recommendations" smoke test while delivering none of AC-1 through AC-6's actual infrastructure, and every future feature is left with nothing to register against (US-1 silently fails). **What a lazy implementation looks like, direction (b) — building the later layer uninvited:** a junior, having built the registration contract, reasons "it would be trivial to also wire a hover tooltip, and it's basically free now" and adds it — this is explicitly against Aaron's 2026-08-12 ruling ("not a v1 requirement on every UI surface") regardless of how cheap it is to add, and AC-4(b)/AC-10 together are the mechanical catch for it. **False-pass warning:** a Tester who only checks "does the panel answer both questions correctly" would pass either failure direction; this AC must be checked explicitly and separately, exactly as v1.9's "an AC's check must be able to fail" rule requires — a check that only verifies the panel's happy path cannot distinguish "correctly scoped v1" from either lazy direction.
- **AC-11 (fixture-only proof, since no real registrant exists yet).** Every AC above that references "a real feature registering" is proven exclusively through a fixture package (mirroring `tool.astgate.md`'s and BUG-024's fixture-driven proof pattern) — this file does not require, and this item does not deliver, any change to an existing engine feature module to make it register with Helper. That wiring happens feature-by-feature, going forward, each future feature's own acceptance criteria carrying its own "register with Helper" AC from this point on (US-1). Check: `git status`/diff for this item's delivery touches only `internal/engine/helper/` (+ its fixtures/tests), the panel's screen package, and `internal/protocol` wiring if needed — no existing `internal/engine/<other>/` package is modified to add a registration.

### Error handling

- **AC-12 (GR#7).** Every error this package constructs — unknown action id, late registration, precondition-evaluation failure, malformed `GameStateView` — is created from the error registry (`data/errors.json`), carrying a correlation ID, following `MarketAPI`'s established `errs.New`/`errs.Wrap` pattern. No bare `fmt.Errorf` at a construction site without a documented exemption (`SEC-048`'s astgate precedent is the model for either path: convert, or document why not).

### Determinism & safety (GR#21)

- **AC-13.** `Registry` is safe for concurrent read access once sealed (AC-3) — multiple goroutines calling `Recommend`/`Preview` concurrently never race (verified with `go test -race`), mirroring `MarketAPI`'s "populated once at construction... safe for concurrent use" precedent.
- **AC-14.** No panic is reachable from any exported `Registry`/`Registrant`-adjacent function given any input reachable through the exported API surface, including a zero-value `GameStateView`, an empty `params`, or a `Registrant` returning a nil precondition slice — every such case returns a registry-sourced error or a defined empty result, never a crash (Destructive-agent pass required per GR#23 before this item can be committed).

### Documentation

- **AC-15.** `internal/engine/helper/doc.go` states: the contract's purpose and its three-member shape (AC-1); the boot-time-only registration invariant and how it's enforced (AC-3, not merely asserted); the "metadata-only cost" standing constraint verbatim, citing Aaron's 2026-08-12 ruling; and the explicit v1/later-layer scope boundary (AC-10), so a future developer reading only this file's doc comment understands why there is no `OnHover` field before they go looking for one.

## Escalations

- **Module key split (GR#20, for Bill/`/register-guid`, not decided here).** This file proposes **two** module keys rather than one: `engine.helper` for the registration contract + registry (the load-bearing, engine-layer piece every future feature module implements/registers with, analogous to `engine.market`'s registry role for its own consumers) and `feat.helper` for the ask-driven panel UI surface (matching this session's `feat.*` naming convention for player-facing UI features — `feat.saveux`, `feat.debugmode`, `feat.disasters`), with the panel consuming the registry through `internal/protocol` rather than importing `internal/engine/helper` directly if that import would otherwise cross the `internal/ui → internal/engine` ban (mirrors `int.protocol`'s existing role as the UI-reachable boundary for engine.core). Whether this needs to be genuinely two registered modules, or one module with two named interfaces (inbound "Registrant contract" + inbound "panel query API", both under a single `feat.helper` or `engine.helper` key), is an architectural call for Bill, not this BA — logged as **ASM (see below)**.
- **Query-cost mechanic (north-star gap #2, Aaron's call).** As specified, asking the Helper anything costs the player nothing — no in-game time, no fee. This sits uneasily against north-star idea #1/#2 ("every yes must have a felt no") for a feature that gives free, perfect information. Whether v1 needs a cost mechanic, or whether "the player still has to hold the trade-off in their own head even with perfect information" is judged sufficient friction on its own, is a design call outside this BA's authority (balance-number regime: player-felt numbers are Aaron's alone). Flagged so it is a decision, not a silent default to "free."
- **`GameStateView`'s concrete field set.** This file deliberately does not enumerate what fields `GameStateView` must expose (treasury balance, current tick, unlocked facilities, etc.) — that depends on which engine modules exist to query at build time, and pinning it now risks the same kind of premature narrowing `data.modes-naming.md`'s AC-3 nested-logit escalation flagged for a structurally analogous reason. Left to the dispatched junior/Bill's review to shape minimally and extend per-feature as real registrants land (US-4 requires it not need rework, not that it be complete on day one).
