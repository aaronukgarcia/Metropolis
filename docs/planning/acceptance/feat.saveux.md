# Acceptance criteria — feat.saveux (FEAT-011)

**BOW code:** FEAT-011
**Spec refs:** §3 Time (`docs/METROPOLIS-MASTER-v2.1.md` lines 115-133, esp. line 131: "Save points: manual anytime + autosave every game year (rolling 10) + milestone saves"; the fixed monthly-tick phase list, lines 127-129: `production → logistics settlement → consumption & shortfall → population → land value & decay → finance`); §14 Debug Mode (lines 257-259: "Fixed RNG seed per save"; debug-touched save-header flagging, M0-ENG §3); §4 Population Scale & the Milestone Ladder (lines 137-157: the 13-tier Wilderness→Centopolis table, population thresholds); A3 Serialization (lines 1342-1344, 1361-1369: `StateSerializer` interface, NDJSON canonical + binary at scale, lossless `metctl export`); `int.serializer`'s own acceptance file (`docs/planning/acceptance/int.serializer.md`) and freeze page (`docs/design/save-format.md`), which this item builds on rather than reimplements; code.json `feat.saveux` entry (outbound calls: `int.serializer` only — see Escalations).
**Date:** 2026-08-11
**Status:** active
**Package under test:** `internal/engine/save/` (path from `node claude-bow.js show FEAT-011`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/save/...`.

## User stories

- **US-1.** As the player, I need to save my city at any moment, so that I never lose more than the choice not to save.
- **US-2.** As the player, I need the game to autosave once per game year without my intervention, keeping the last 10, so that a crash or a bad decision I want to undo costs me at most one game year of progress and my disk doesn't fill with autosaves (§3 line 131).
- **US-3.** As the player, I need a save taken automatically at every milestone I reach, so that "before I unlocked the port" is always a place I can go back to, distinct from whatever the yearly rotation happens to still hold.
- **US-4.** As the player, I need every save — manual, autosave, or milestone — to load back exactly what was there, not a plausible-looking but incomplete copy of my city, so that "I saved" and "I can get it back" are the same guarantee.
- **US-5.** As the player, I need a save that was interrupted (crash, power loss, disk full) to never quietly become "the save I load next time" as a half-written city, so that a failure during save is a failure I'm told about, not one I discover three loads later.
- **US-6.** As a future F10 save/load menu (out of scope for this item's own UI, in scope for the data it needs), I need to list every discoverable save with its kind, in-game time, and debug-touched status without opening a single shard file, so that the picker is fast even with a 10-slot rolling history plus every milestone plus every manual save.
- **US-7.** As GR#12 ("never a backup without a restore test"), I need each of the three save points — manual, autosave, milestone — proven to load back, not merely proven to write valid bytes, so that a save nobody has ever restored is treated as what it is: an unverified file, not a backup.

## Scope

The save/load orchestration layer that sits above `int.serializer`'s `StateSerializer`/bundle contract: the participant registry each domain module registers its saved state through, the three save-trigger paths (manual, rolling yearly autosave with 10-deep retention, milestone), atomic/interrupted-write safety, corrupted/older-save handling on load, and the save-completeness obligation `int.serializer` explicitly deferred to its consumers (`int.serializer.md`'s Out-of-scope: "Engine-side record-kind decoders... belong to the engine modules that own each record kind; this package only moves opaque bytes + a `Kind` label"). This item does not decode or interpret any citizen/building/market record itself and does not build the F10 UI screen — it provides the API surface that screen will call.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; contract-first participant registry).** `internal/engine/save` defines a `Participant` (or equivalent) contract — `Kind() string` plus a method producing a `serialize.RecordSource` for writing and one consuming a `serialize.RecordHandler` for reading — and a static, explicitly-coded registration list (a package-level slice/map literal naming each participant), not a reflection-driven auto-discovery over other engine packages. Check: `go doc ./internal/engine/save Participant` (or equivalent) shows both directions; `grep -n "var.*[Pp]articipants\s*=\|registry\s*=" internal/engine/save/*.go` shows a literal, enumerable list, and `go build ./...` compiles it — reject any implementation that walks `reflect` over arbitrary package exports to "discover" what to save, since that defeats AC-2's ability to name an exhaustive registry.
- **AC-2 (completeness — the core obligation this item inherits from `int.serializer`'s scope note; weakness pattern #2).** For every domain struct type actually written by a registered `Participant` (AC-1), a reflection-based field-parity drift test exists in the owning package, modelled directly on `serialize.TestHeaderWireFieldsMatchHeader` (`internal/foundation/serialize/serialize_test.go`): it enumerates the domain struct's exported fields and asserts each has a named counterpart in its save/wire record projection, OR the field appears on an explicit, commented exclusion allowlist stating why it is not persisted (e.g. a derived/cached value recomputed on load). Check: the number of registered `Participant` entries from AC-1 equals the number of matching field-parity tests found by `grep -rln "FieldsMatch\|FieldParity" internal/engine/**/*_test.go` (naming convention: `Test<Struct>WireFieldsMatch<Struct>`) — every participant without a matching test is a FAIL, named explicitly in the Tester's report. **What this rejects that equality alone would not:** a developer registers `Kind() string { return "citizen" }`, hand-writes a `citizenWire` struct that compiles, and a normal `TestCitizenRoundTrip` (write bytes, read bytes, assert equal) passes cleanly even if `citizenWire` silently omits a field `Citizen` gained later (e.g. a new health-state field) — the equality test only proves what got written comes back unchanged, exactly the trap this file's brief names. The field-parity test is the only one of the two that can fail against that build, because it inspects `Citizen`'s field set directly rather than trusting the wire struct's author to have kept up.
- **AC-3 (Manual save + restore, §3 line 131, GR#12).** A `SaveManual(name string) error` (or equivalent) entry point produces a complete bundle from the current live state, callable at any tick-phase boundary (see AC-11 for the mid-phase restriction) regardless of game speed. Check: `go doc ./internal/engine/save SaveManual` (or equivalent) exists; a passing test (a) calls it against a fixture world with non-trivial state in at least two different registered participants, (b) confirms `serialize.ValidateBundle` passes on the result, and (c) **loads it back** via this package's own `Load` function and asserts the reconstructed participant state equals the pre-save state field-by-field (not just "load returned no error") — satisfying GR#12's restore-test requirement for the manual path specifically, distinct from `int.serializer`'s own generic bundle round-trip test.
- **AC-4 (Rolling yearly autosave + retention + restore, §3 line 131, GR#12).** An autosave component fires exactly once per completed game year — triggered off the simulation's own year-boundary event/tick count, never a real-world timer (`time.Ticker`, `time.Sleep`, or wall-clock polling) — and retains at most 10 autosave bundles, pruning the oldest **only after** the new autosave has been written and confirmed `ValidateBundle`-clean (see AC-13 for the failure-path half of this). Check: `go doc ./internal/engine/save` shows the autosave trigger is parameterised on/driven by a game-year counter, not a `time` package call (cross-checked by AC-15); a passing test drives ≥11 simulated year-boundaries through it with a fixture world and asserts (a) exactly 10 autosave bundles remain and they are the 10 most recent, and (b) **at least one of the retained autosaves loads back** via `Load` with reconstructed state matching what was live at that year (GR#12 restore-test for the autosave path). False-pass this guards against: a test that only counts directory entries without ever loading one back would pass a build that writes ten empty-but-technically-`ValidateBundle`-clean bundles.
- **AC-5 (Milestone saves + restore, §3 line 131 / §4 lines 137-157, GR#12; ASM — see Escalations).** A milestone-save component fires when the simulated population crosses one of §4's 13 tier thresholds (Wilderness through Centopolis), producing a bundle distinct from the yearly-autosave rotation (it is never pruned by AC-4's 10-deep retention) and tagged with which tier was crossed. Check: `go doc ./internal/engine/save` shows a milestone-triggered save path taking or deriving a tier identifier; a passing test crosses at least two thresholds (e.g. Hamlet at 100 and Small Town at 5,000) against a fixture world, asserts a distinct bundle exists per crossing (not overwritten by the next), and **loads at least one back** via `Load`, asserting reconstructed state matches what was live at that crossing (GR#12 restore-test for the milestone path) and that the loaded bundle's recorded tier matches the crossing that produced it.
- **AC-6 (Save-kind and provenance metadata).** Every bundle produced by AC-3/4/5 carries, in addition to `int.serializer`'s own `Header`, a project-defined `SaveKind` (at minimum `Manual`, `Autosave`, `Milestone`, and — if AC-5 assigns one — the tier identifier) stored as feat.saveux's own metadata rather than by widening `int.serializer.Header`'s wire shape (that package's contract is fixed at `int.serializer`'s module boundary, GR#20 — feat.saveux is a consumer, not a co-owner). Check: `go doc ./internal/engine/save SaveKind` (or equivalent) exists with at least those three named values; a passing test produces one save via each of AC-3/4/5 and asserts the kind read back after `List` (AC-8) or `Load` matches the path that produced it — reject an implementation that infers kind from directory-name string-matching alone with no typed field, since a future rename would silently misclassify every existing save.
- **AC-7 (Streams through `int.serializer`, §5.3; builds on, does not reimplement, `int.serializer`'s AC-3).** Every `Participant`'s records are passed to `serialize.WriteShard`/`ReadShard` via the `RecordSource`/`RecordHandler` pull/push contract without this package ever materialising a full `[]serialize.Record` slice for a `Kind` before the first `WriteShard` call. Check: `grep -n "func.*[Ww]riteAllShards\|func.*[Ss]ave" internal/engine/save/*.go` shows the per-participant record production wired as a closure/iterator passed directly to `WriteShard`, not built into a slice first — same "no accumulation" check `int.serializer`'s own AC-3 runs on `ndjson.go`, applied here at the call site.
- **AC-8 (List surface for a future F10 menu, US-6).** A `List(root string) ([]SaveSummary, error)` (or equivalent) function returns, for every discoverable bundle under a save root, at minimum: display name, `SaveKind` (AC-6), `CreatedAtTick`, `GameMonth`, `AppVersion`, `DebugTouched` — all sourced from `header.json`/feat.saveux's own metadata file, never by opening a shard file. Check: `go doc ./internal/engine/save List` (or equivalent) exists and documents the returned fields; a passing test deletes every shard file from a bundle after writing it (leaving `header.json` and feat.saveux's metadata intact) and asserts `List` still succeeds and reports the same summary — proving it never touches shard data.

### Error handling

- **AC-9 (Atomic promotion — no half-written save is ever selectable; GR#17, this file's central completeness clause).** A save is written to a location invisible to `List`/`Load` (a staging path outside the discoverable save root, or a name excluded from `List`'s enumeration) and is moved/renamed into a discoverable name **only after** a full `serialize.ValidateBundle` pass succeeds on the staged bundle. Check: a passing test forces a failure partway through a save (the `RecordSource` for one participant returns an error after N records, or the staged shard directory is truncated before promotion would occur) and then asserts, against the save root as a whole: (a) `List` returns exactly the same result as before the attempt (the failed attempt is invisible), and (b) no directory reachable by `Load`/`List` carries the failed save's intended name. **What this rejects that a bare "returns non-nil error" check would not:** an implementation that writes directly into the final named directory and simply propagates the shard-write error passes a naive "the call returned an error" assertion while leaving the half-written directory sitting exactly where the next `List`/`Load` will find it — this is the "the game silently loads a half-written city" failure named in this file's brief, and the check must inspect post-failure `List`/`Load` state, not just the failing call's own return value, to catch it.
- **AC-10 (Corrupt/truncated newest save does not lose older history — BUG-054's pattern, applied to feat.saveux's own load-latest path, GR#17).** A "load most recent" entry point (`LoadLatest` or equivalent), given a save history containing one corrupted/truncated bundle at the newest position and N valid older ones, skips the corrupted entry — returning both the next valid bundle's loaded state **and** a non-nil accompanying record of what was skipped and why — rather than aborting the entire load or crashing on the one bad entry. Check: a passing test builds a save root with 3 valid autosaves plus a hand-corrupted 4th (newest, byte-flipped per `int.serializer`'s own corruption test pattern), calls `LoadLatest`, and asserts it returns the 3rd (newest-still-valid) bundle's state with a non-nil warning identifying the skipped one. False-pass this guards against: an implementation that calls `ValidateBundle` on the newest only and, on failure, propagates the raw error upward without trying the next-older entry — that passes "returns an error on a corrupt save" but fails this AC's "and then still gets me back into my city" half, reproducing BUG-054's exact shape (one torn record aborting an entire history) one layer up.
- **AC-11 (Save timing safety — tick-phase boundary only; single-save-in-flight guard; ASM — see Escalations).** A save (any of AC-3/4/5) may only begin at a boundary between §3's fixed monthly-tick phases (lines 127-129), never mid-phase, and at most one save is ever in flight at a time — a second trigger arriving while one is running is either queued to run immediately after, or rejected with a typed, loggable outcome; it is never silently dropped and never allowed to interleave shard writes with the in-flight save. Check: a passing `-race` concurrency test fires a manual-save trigger and an autosave trigger against the same fixture engine/registry at effectively the same time and asserts (a) no data race, (b) the two saves' shard writes are never interleaved (each produced bundle is internally `ValidateBundle`-clean, not a mix of two states), and (c) the second trigger's outcome (queued-then-ran, or rejected-with-reason) is itself observable in the test, not silently absorbed.
- **AC-12 (Older-format-version load surfaces a registry-sourced error, GR#7; builds on `int.serializer`'s `CheckFormatVersion`).** Loading a bundle whose `Header.FormatVersion` has a different MAJOR than the running build's produces a registry-sourced `MET-` error (this package's own claimed sub-range, per the README's Sprint-1 convention) that wraps/names `int.serializer`'s `CheckFormatVersion` error rather than a generic or swallowed failure. Check: a passing test constructs a bundle with a bumped-major `FormatVersion` and asserts `Load` returns a `MET-`-coded error whose message includes both the saved and current format versions (not a bare `"load failed"`).
- **AC-13 (Autosave retention survives a failed write — the error-path half of AC-4).** If writing a new rolling autosave fails at any point (a participant's `RecordSource` errors, a shard write I/O-fails, or the post-write `ValidateBundle` fails), the existing retained autosave set is left completely unchanged — no old autosave is pruned on the strength of a write that never completed. Check: a passing test forces the write of an 11th autosave to fail after its first shard, then asserts all 10 previously-retained autosaves are still present, unmodified, and still individually `ValidateBundle`-clean.

### Determinism & safety

- **AC-14 (GR#21; end-to-end byte-determinism, builds on `int.serializer`'s per-shard determinism).** Two saves taken from the same deterministic state (same `worldSeed`, same `CreatedAtTick`, same command log driving the fixture world to that state) produce byte-identical bundles across **every** file in the bundle directory — header, every shard, and feat.saveux's own metadata file (AC-6) — not just a per-shard check. Check: a passing test drives the same fixture through the full `SaveManual` path twice into two directories and walks both trees comparing every file's bytes (`grep -rn "func Test.*[Bb]yte[Dd]etermin\|func Test.*[Ee]ndToEnd.*[Dd]etermin" internal/engine/save/*_test.go`), not merely comparing one shard or the header alone.
- **AC-15 (SG-7 scoped, GR#21).** `grep -rn "time.Now\|time.Since\|time.Ticker\|time.Sleep" internal/engine/save/*.go` (excluding `_test.go`) returns no matches, **except** any field/parameter explicitly documented as display-only UI metadata (e.g. a human-readable "saved at" wall-clock string shown in a save-list picker) that is never read by any determinism-sensitive path (AC-14, AC-4's year-boundary trigger, `CheckFormatVersion`). Any such exception must be named in a doc comment; an unexplained match is a FAIL, consistent with `Header`'s own "no wall-clock" invariant this package must not reintroduce one layer up.
- **AC-16 (Readers never observe a torn bundle during a concurrent write).** While an autosave or milestone save is in flight in the background, concurrent `List`/`Load` calls from other goroutines only ever observe either the pre-promotion (old) state or the fully-promoted (new) state — never a partially-written bundle — consistent with AC-9's atomic-promotion design. Check: a passing `-race` test runs a background save concurrently with repeated `List`/`Load` calls and asserts every bundle any `List`/`Load` call returns is independently `ValidateBundle`-clean at the moment it is read.

### Documentation

- **AC-17.** `internal/engine/save/doc.go` states the module key `feat.saveux`, cites §3/§14/A3/§4, and documents: the three save-kinds and their triggers, the 10-slot rolling-autosave retention rule, the atomic-promotion/staging design (AC-9), and the milestone-trigger source this file adopted (AC-5's ASM, see Escalations). Check: `grep -n "feat.saveux" internal/engine/save/doc.go` and `grep -n "§3\|§14\|§4\|A3" internal/engine/save/doc.go` both match, and all of {manual, autosave, milestone} appear.
- **AC-18 (the exclusion-allowlist convention is documented, not just implemented, AC-2).** A doc comment on the `Participant` registry (or `doc.go`) states the completeness policy in prose: every exported field of a saved domain struct must have a wire counterpart or an explicit, reasoned exclusion, and every registered `Participant` must carry the field-parity drift test AC-2 requires. Check: `grep -n "exclusion\|allowlist" internal/engine/save/*.go` matches a comment stating this policy, not only the code implementing it.

## Out of scope

- Any citizen/building/market/finance record's actual field layout or wire projection — those belong to the owning engine module (`engine.citizens`, `engine.world`, `engine.market`, `engine.finance`, etc.); this item only requires that whichever such module registers a `Participant` also carries AC-2's field-parity test, and provides the registry + orchestration those participants plug into.
- The F10 save/load UI screen itself (list rendering, keybinding, confirmation dialogs) — `internal/engine/save`'s `List`/`Load`/`SaveManual` are the API surface a future `internal/ui/screens/...` item consumes; this item's `path:` (`internal/engine/save/`) is engine-layer only.
- The versioned binary shard format above `int.serializer`'s size threshold — out of scope there (`int.serializer.md`'s Out-of-scope) and therefore out of scope here; this item's saves are NDJSON+gzip bundles like every other consumer until that threshold is chosen and built.
- Cloud save sync (`cloud.azure`) — separate module (`MOD-069`), per `int.serializer.md`'s own Out-of-scope entry.
- Older-major `FormatVersion` migration (`MigrateV1toV2`-shaped work) — `int.serializer` itself defers this until a migrator is actually needed; feat.saveux only needs to surface the refusal cleanly (AC-12), not build the migrator.
- MOD-011's key-grammar/F10 binding mechanics themselves — feat.saveux depends on MOD-011 existing (per `node claude-bow.js show FEAT-011`'s dependency list) but does not re-specify keymap behaviour, which is that module's own acceptance file.

## Escalations

- **For Bill — ASM required before dispatch, milestone-trigger linkage (AC-5).** §3 (line 131) names "milestone saves" as a save point but does not itself state what triggers one; §4's 13-tier population ladder is the only spec-defined notion of "milestone" in the document, and `engine.unlocks.md` (a sibling BA's file, already written) independently arrives at the same reading — its AC-4 has milestone-crossing already firing grants "in the same tick" a population threshold is crossed. This file adopts that linkage (milestone save ⇒ §4 tier crossing) as the acceptance criterion in AC-5, but it is this BA's inference, not literal spec text, and cadence/trigger points are exactly the kind of thing the brief says is usually Aaron's call. Logged as an assumption below (`ASM` — priority P1, since AC-5 is unbuildable as written if the linkage is wrong).
- **For Bill — code.json call-edge gap (BUG-058), affects AC-5 and AC-11.** `node -e "require('./code.json').modules.find(m=>m.key==='feat.saveux')"` shows `outbound.calls` containing only `int.serializer` — no registered edge to `engine.unlocks` (which AC-5 needs, to learn a milestone tier was crossed) or to `engine.core` (which AC-11 needs, to learn the engine is at a tick-phase boundary and not mid-phase). This file writes AC-5/AC-11 against the *behaviour* the spec requires rather than inventing a call path that isn't registered; the actual wiring (event subscription vs. direct call, and which package emits vs. consumes) is left for the dispatched developer to resolve against whatever `engine.unlocks`/`engine.core` actually expose by Sprint 7, and reported here per this file's brief ("if you need a call path with no registered edge, report it against BUG-058 rather than assuming it exists") rather than assumed silently.
- **Resolved, matching `int.serializer.md`'s own escalations.** GR#20/GR#21 exist (`CLAUDE.md` lines 51-52); cited above as AC-1/AC-6 (GR#20) and AC-14/AC-15/AC-16 (GR#21). No new escalation needed for those.

## Assumptions logged

The following are logged via `node claude-bow.js add assumption ...` (see command output referenced by BOW code below); summarised here per this file's own Escalations section for a reader who does not have BOW access open:

1. **Milestone-save trigger = §4 population-tier crossing** (AC-5). See Escalations above. `code-path: internal/engine/save/`, `codejson: feat.saveux`, priority P1.
2. **Exclusion-allowlist policy is opt-out, not opt-in** (AC-2/AC-18): every exported field of a registered domain struct is assumed persisted unless explicitly excluded with a reason, rather than requiring an explicit opt-in list of what to save. Chosen because opt-out fails loud (a new field with no wire counterpart trips AC-2 the moment it's added) while opt-in fails silent (a new field simply isn't saved until someone remembers to add it) — the opposite of what this file's brief asks for. `code-path: internal/engine/save/`, `codejson: feat.saveux`, priority P2.
3. **Atomic-promotion mechanism is a staging-then-rename design**, not specified by the spec at this level of detail (staging directory naming, whether promotion is an OS rename or a copy-then-delete-old). AC-9 is written against the observable property (no half-written save is ever selectable), not the mechanism, so a developer choosing a different mechanism that satisfies AC-9 is not in conflict with this file — but the *fact* that some staging design is required, rather than writing directly into the final name, is this BA's architectural call. `code-path: internal/engine/save/`, `codejson: feat.saveux`, priority P2.
4. **`SaveKind`/provenance metadata lives in feat.saveux's own sidecar file, not in `int.serializer.Header`** (AC-6): `int.serializer`'s `Header` shape is treated as a fixed contract this item consumes rather than extends, per GR#20's module-boundary discipline — a plausible alternative (widen `Header` itself) was considered and rejected because it would make `int.serializer` depend on feat.saveux's vocabulary (Manual/Autosave/Milestone) for a concept it doesn't otherwise need. `code-path: internal/engine/save/`, `codejson: feat.saveux`, priority P2.
5. **Single-save-in-flight guard's response to a second trigger (queue vs. reject) is left open in AC-11**, deliberately: both are acceptable provided the outcome is observable and no interleaving occurs. This is itself a choice (permissiveness rather than picking one), made because the spec is silent and either answer is defensible; if Bill wants one mandated, AC-11 should be tightened before dispatch rather than left to the junior's judgement, since it changes what the concurrency test must assert. `code-path: internal/engine/save/`, `codejson: feat.saveux`, priority P2.
