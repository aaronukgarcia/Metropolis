# Acceptance criteria — engine.logistics (MOD-025)

## Scope note (S6 exit gate)

S6's exit gate — "headless city grows from 0: zone→build→migrate→work→deliver; JIT shortfalls propagate to satisfaction/production; junction queue renders; attractiveness moves migration both directions" — is owned end-to-end by `docs/planning/acceptance/engine.attract.md` (BA-S6b). This file owns the **deliver** half and the **shortfall-propagation contract** the exit gate depends on (AC-9/AC-10 below); it does not restate the scenario. Zone→build is `engine.build.md`'s half of this file's sibling deliverable.

## User stories

- **US-1.** As a household/firm/service/construction site (a stock consumer), I need to draw from a local stock with capacity, holding cost, and per-commodity shelf life, so consumption is bounded by what's actually on the shelf, not an unconditional market pull (§8 step 1).
- **US-2.** As a stock manager, I need to issue replenishment orders against forecast demand plus a player-tunable lean/fat safety buffer per commodity, so the player has a real risk/cost lever (§8 step 2).
- **US-3.** As the road graph, I need orders to become truck movements consuming finite per-junction daily slots, with excess queuing rather than teleporting through, so junction saturation is a real, visible bottleneck (§8 step 3; §II.5).
- **US-4.** As `ui.screen.trade` (F5, a registered consumer), I need per-junction queue state — depth, cargo composition, wait times — queryable through `LogisticsAPI`, so the live queue view is a read of real engine state, not a UI-side simulation (§13-F5).
- **US-5.** As an import order, I need a lead time that's a genuine function of mode (road: days; sea: longer, but 10× the bulk per shipment), so the make-vs-buy and buffer-sizing decisions the player faces are real trade-offs (§8 step 4).
- **US-6.** As a perishable commodity, I need to expire while queued (in the junction backlog, not just on the shelf), so an oversized safety buffer or a saturated junction has a real spoilage cost (§8 step 4).
- **US-7.** As `engine.consumption`/health/`engine.build`/`engine.firms` (downstream shortfall consumers, later sprints), I need a shortfall to be a nonzero, typed quantity reaching a documented hook — not merely a number logged for the player to read — so "JIT shortfalls propagate to satisfaction/production" (the S6 exit gate) is a real code path from day one, not a fact that becomes true only once every downstream module happens to poll the right field (§8 step 4).
- **US-8.** As `engine.build` (MOD-026, a registered consumer, this sprint), I need the materials draw for an active construction site to be a first-class stock consumer exactly like a household's shop draw, so a materials shortfall stalls the build queue through the same mechanism a food shortfall hits satisfaction, not a bespoke parallel path (§8 step 4; code.json edge to `engine.build`).
- **US-9.** As `engine.market` (MOD-020, already built/ready), I need `engine.logistics` to query my `Availability`/`Price` for import ceiling and cost data as an input to ordering decisions, while I never see or mutate `engine.logistics`'s live per-junction slot ledger — the two capacity concepts are related but distinct (ASM-191/ASM-232; code.json outbound edge).
- **US-10.** As the player reading F5, I need warehouse stock/buffer policy set per commodity (lean vs fat), so the buffer is a first-class configurable, not an internal constant only a developer can change.

## Scope

The daily-tick JIT resolution loop (stock draw → replenishment order → truck movement → junction queue → delivery/expiry → shortfall propagation) behind a single `LogisticsAPI`; the live per-junction slot ledger and per-commodity order book; lead-time and shelf-life modelling; the shortfall hook contract downstream modules attach to. No traffic assignment itself (`engine.traffic`, a dependency), no commodity pricing (`engine.market`, a dependency), no UI rendering of the queue (`ui.screen.trade`).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `LogisticsAPI` (or equivalent) exists matching code.json's registered inbound contract — "order book + movement scheduler; queue states subscribable per junction" — consumed by `engine.build` and the other registered consumers through this interface alone, never a concrete internal stock/order-book/ledger struct reached directly from another package's non-test code. Check: `go doc ./internal/engine/logistics LogisticsAPI` shows order/query methods; `grep -rln "logistics\.\(stockState\|orderBook\|junctionLedger\)\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/logistics` itself and `_test.go` files) finds no direct exported-field writes bypassing the interface. False-pass risk stated: a grep that only checks `LogisticsAPI` exists as a name would pass even if `engine.build` reaches into logistics internals directly for materials — the check must target writes bypassing the interface, not the interface's mere presence.
- **AC-2 (§8 step 1; local stock draw).** Every registered consumer draws from a local stock record carrying capacity, a per-unit holding cost, and a per-commodity shelf life (0/undefined shelf life is a legal "non-perishable" value, not an error). Check: `go doc ./internal/engine/logistics Stock` (or equivalent) shows `Capacity`, `HoldingCost`, `ShelfLife` fields; a passing test asserts a draw exceeding current stock returns a partial fill plus a nonzero shortfall, not a full fill (`grep -rn "func Test.*[Ss]tockDraw\|func Test.*[Pp]artialFill" internal/engine/logistics/*_test.go`). False-pass risk: a `Draw` that always returns "requested amount granted" regardless of stock level would satisfy a grep for the method's existence — the check requires the returned quantity to actually be capped by available stock in a constructed low-stock scenario.
- **AC-3 (§8 step 2; forecast + safety buffer).** Replenishment orders are sized from forecast demand plus a per-commodity, player-tunable safety-buffer setting with at least two distinct tiers ("lean": smaller buffer, lower holding cost, higher stockout risk; "fat": larger buffer, higher holding cost, lower stockout risk — exact multipliers are balance data, ASM-234). Check: `go doc ./internal/engine/logistics SetBufferPolicy` (or equivalent command) exists; a passing test asserts a "fat" policy produces a larger order quantity than "lean" for identical forecast demand, and that the resulting stock's realised stockout rate under a fixed synthetic demand trace is lower for "fat" than "lean" (`grep -rn "func Test.*[Bb]uffer[Pp]olicy\|func Test.*[Ll]eanFat" internal/engine/logistics/*_test.go`). False-pass risk: an implementation with one buffer constant applied uniformly regardless of the policy argument would pass a grep for "lean"/"fat" string presence in doc comments — the check requires order-quantity divergence between the two tiers on identical input.
- **AC-4 (§8 step 3; §II.5 junction slots).** Orders become truck movements consuming a finite, per-junction, per-day slot count; a movement that cannot be assigned a slot on its scheduled day enters a queue rather than completing that day. Check: `go doc ./internal/engine/logistics` shows a per-junction slot ledger accessor (e.g. `JunctionSlotsUsed`, `JunctionSlotsAvailable`); a passing test drives movement demand above a fixed junction's daily slot count and asserts (a) exactly the slot count's worth of movements complete that day and (b) the remainder appear in the next day's queue rather than silently disappearing or all completing anyway (`grep -rn "func Test.*[Jj]unction[Ss]lot\|func Test.*[Ss]lotSaturat" internal/engine/logistics/*_test.go`). False-pass risk: a slot ledger field that exists but is never read by the movement-scheduling path (an unenforced cap) would satisfy a doc-existence grep while every movement still completes same-day — the check requires the saturation scenario to actually produce a next-day queue.
- **AC-5 (§13-F5, US-4; queue state query, not render — ASM-235).** Per-junction queue state (queue depth, cargo composition by commodity, and each queued movement's accrued wait time) is queryable through `LogisticsAPI` without mutating it, and updates as movements enter/leave the queue across ticks. `engine.logistics` does not itself format or draw the queue — that is `ui.screen.trade`'s job (ASM-235). Check: `go doc ./internal/engine/logistics JunctionQueue` (or equivalent) exists and returns a read-only view; a passing test asserts calling it twice with no intervening tick returns identical results, and that after a tick advances a queued movement's wait time, the returned wait time increases (`grep -rn "func Test.*[Qq]ueueState\|func Test.*[Ww]aitTime" internal/engine/logistics/*_test.go`).
- **AC-6 (§8 step 4; lead time by mode).** Import lead time is a genuine function of transport mode: sea-mode lead time is strictly greater than road-mode lead time for the same origin-class import, and sea-mode shipment size (bulk per movement) is a fixed, documented multiple of road-mode shipment size (the "10× bulk" ratio, transcribed from spec, not a different invented ratio). Exact day counts are balance data (ASM-234). Check: `go doc ./internal/engine/logistics` shows a mode-parameterised lead-time/bulk accessor; a passing test asserts `LeadTime(Sea) > LeadTime(Road)` and `Bulk(Sea) == 10 * Bulk(Road)` for the same commodity class (`grep -rn "func Test.*[Ll]eadTime\|func Test.*[Ss]eaBulk" internal/engine/logistics/*_test.go`). False-pass risk: hardcoding `Bulk(Sea) = 10 * Bulk(Road)` as a Go literal would pass this test while violating AC-11's data-driven requirement — the two checks are deliberately separate so a build can fail one without the other masking it.
- **AC-7 (§8 step 4; perishable expiry in queue).** A perishable commodity's shelf-life clock advances while queued at a junction (not only while sitting on a warehouse shelf), and a movement whose cargo's shelf life expires before delivery is removed from the queue as spoiled stock, distinct from a completed delivery. A non-perishable (undefined/zero shelf life) commodity never expires regardless of queue time. Check: `go doc ./internal/engine/logistics` shows a spoilage/expiry accessor or event; a passing test constructs a perishable movement with a shelf life shorter than a saturated junction's queue wait, advances ticks, and asserts the movement is marked spoiled rather than eventually delivered; a second test asserts an otherwise-identical non-perishable movement under the same queue delay is still delivered (`grep -rn "func Test.*[Ss]poil\|func Test.*[Pp]erishable[Qq]ueue" internal/engine/logistics/*_test.go`). False-pass risk: an expiry check that only fires on warehouse-shelf stock (never on queued movements) would pass a bare "spoilage exists" grep while the queue-specific case the spec calls out (`§8`: "perishables expire in queue") remains unreachable — the test must specifically construct a queue-bound expiry, not a shelf-bound one.
- **AC-8 (§8 step 4; construction as a stock consumer — US-8).** A construction site's materials draw uses the exact same `Stock`/`Draw` mechanism AC-2 defines for any other consumer (no bespoke materials-only code path), so `engine.build`'s materials shortfall is reachable through the identical stockout mechanism §8 describes for food/water. Check: `grep -rn "func Test.*[Mm]aterial" internal/engine/logistics/*_test.go` shows a materials-commodity test reusing the same `Draw`/`Stock` API surface AC-2's test exercises, not a separate `MaterialsDraw` type with independent logic. False-pass risk: a parallel `ConstructionStock` type that happens to expose a similar-looking API but is implemented independently would pass a naming grep while silently diverging in behaviour from the general stock mechanism (e.g. no shelf life, no buffer policy) — the check requires the same underlying type/method set, not merely a similarly-named one.
- **AC-9 (§8 step 4; shortfall is a nonzero, typed, reachable value — US-7, the exit-gate load-bearing AC).** When a draw's requested quantity exceeds available stock, the returned/reported shortfall is a nonzero quantity of the correct commodity and magnitude (`requested − fulfilled`, never a rounded-to-zero or capped-at-a-flag boolean), and a scenario that never actually runs short (adequate stock throughout) produces zero shortfall events over the same tick range. Check: `go doc ./internal/engine/logistics` shows the draw result carries a shortfall quantity, not a single boolean; a passing test (a) engineers a stockout (demand fixture exceeding stock+incoming replenishment) and asserts a nonzero shortfall with the correct magnitude is returned, and (b) runs an adequate-stock fixture over the same tick range and asserts zero shortfall events occur (`grep -rn "func Test.*[Ss]hortfall" internal/engine/logistics/*_test.go`). False-pass risk, stated per the v1.9 rule: an implementation where the shortfall path is structurally unreachable (e.g. `Draw` silently clamps the request to available stock and reports success) would pass a naive "shortfall field exists" check while never actually producing one — this AC requires BOTH the positive case (a constructed stockout produces a nonzero shortfall) and the negative case (adequate stock produces none), so a build that can never reach the shortfall path fails the positive half.
- **AC-10 (§8 step 4; shortfall reaches a documented downstream hook — the propagation half of the exit gate).** A nonzero shortfall from AC-9 is delivered to a documented, subscribable hook (e.g. an event/callback carrying commodity, magnitude, and consumer-class) that a downstream module (satisfaction/health for households, production-stoppage for firms, construction-stall for `engine.build`) can attach to — not merely recorded in an internal counter or log line a downstream module would have to poll. Check: `go doc ./internal/engine/logistics` documents a shortfall event/hook type; a passing test registers a hook, engineers a stockout per AC-9, and asserts the hook fires exactly once with the correct commodity/magnitude/consumer-class (`grep -rn "func Test.*[Ss]hortfall[Hh]ook\|func Test.*[Ss]hortfallEvent" internal/engine/logistics/*_test.go`). False-pass risk: a shortfall that only updates an unexported struct field a downstream module would need direct access to read would pass a "shortfall is recorded somewhere" check while leaving the S6 exit gate's "propagates to satisfaction/production" claim untestable by any consumer through the documented API — the check requires an active hook/event a subscriber receives, not a passive field a subscriber must poll.
- **AC-11 (GR#15; no hardcoded balance constants).** Safety-buffer multipliers, junction slot counts, lead-time day values, and shelf-life defaults load from `data/logistics.json` (or equivalent) at package init/load time — no per-commodity or per-mode literal of this kind is hardcoded in Go source (ASM-234 records that the exact values are unpinned balance data, not that the loading mechanism is optional). Check: a passing test changes a value in the loaded data fixture and asserts the corresponding behaviour (order size, slot cap, lead time) reflects the change, mirroring `engine.season`'s AC-10/`engine.market`'s AC-8 pattern (`grep -rn "func Test.*[Dd]ataDriven\|func Test.*[Rr]eload" internal/engine/logistics/*_test.go`); `grep -nE "[0-9]+" internal/engine/logistics/*.go` (excluding `_test.go`) finds no bare balance-shaped numeric literals outside doc-comment prose transcribing the spec (the AC-6 "10×" ratio literal is the one sanctioned exception, since that figure is spec-stated, not balance data — AC-6's own test isolates it).
- **AC-12 (US-9; Market boundary — ASM-191/ASM-232).** `engine.logistics` calls `MarketAPI.Availability`/`Price` (the registered code.json outbound edge) when sizing an import order, but never writes to any `engine.market`-owned state, and its own per-junction slot ledger / per-commodity order book is never read or mutated by `engine.market`. Check: `grep -rln "market\.\w\+ = " internal/engine/logistics/*.go` (excluding `_test.go`) finds no direct writes into market-owned state; `go doc ./internal/engine/market` shows no method reading `engine.logistics`-owned types. False-pass risk: a grep that only confirms `MarketAPI` is called somewhere would pass even if logistics also reached past the interface into market's internal ceiling data structures directly — the check targets the absence of that reach, not the presence of a legitimate call.

### Error handling

- **AC-13 (GR#7).** Ordering, drawing, or querying queue state for an unregistered commodity ID, or issuing a movement against an unregistered junction ID, returns a registry-sourced error (new `MET-E`-range code claimed at build time per the README's convention), never a panic or a silently-created zero-value stock/queue entry. Check: `grep -n "MET-" internal/engine/logistics/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nknownCommodity\|func Test.*[Uu]nknownJunction" internal/engine/logistics/*_test.go`).
- **AC-14 (GR#7).** A malformed or schema-invalid `data/logistics.json` (a commodity missing its shelf-life/buffer fields, a negative slot count, a sea lead time not exceeding the road lead time) produces a registry-sourced error at load time, never a silent default substitution. Check: `grep -n "MET-" internal/engine/logistics/*.go` finds a load-time registry code reference distinct from AC-13's query-time code; passing test coverage (`grep -rn "func Test.*[Mm]alformed\|func Test.*[Ii]nvalidLogistics" internal/engine/logistics/*_test.go`).

### Determinism & safety

- **AC-15 (GR#21).** The daily-tick resolution (stock draw → order → movement → queue → delivery/expiry → shortfall) is a deterministic function of prior tick state, loaded data, and command inputs — repeated runs from an identical starting snapshot over an identical command sequence produce byte-identical stock levels, queue contents, and shortfall events, across worker counts. Check: a passing determinism test exists and asserts identical output across repeated runs and (if feasible) across worker counts (`grep -rn "func Test.*[Dd]eterminis" internal/engine/logistics/*_test.go`). Never assert a wall-clock upper bound (e.g. "resolves within N milliseconds") — assert tick-count/state equality only, per dev-team-process's CI-jitter caution.
- **AC-16 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/logistics/*.go` (excluding `_test.go`) returns no matches — ordering, lead times, and expiry are functions of simulation tick/day-count only, never wall clock.
- **AC-17.** `go test ./internal/engine/logistics/... -race -count=1` passes with no data race when `LogisticsAPI` is queried (AC-5's queue state) concurrently with a tick advancing the same junction's ledger. Check: `grep -n "go func()" internal/engine/logistics/*_test.go` finds at least one concurrency test.

### Documentation

- **AC-18.** `internal/engine/logistics/doc.go` states the module key `engine.logistics`, cites §8 and §II.5, states the Market/logistics capacity-ledger boundary (ASM-191/ASM-232) explicitly, and states that queue rendering is `ui.screen.trade`'s responsibility, not this package's (ASM-235). Check: `grep -n "engine.logistics" internal/engine/logistics/doc.go` and `grep -n "§8\|section 8" internal/engine/logistics/doc.go` and `grep -n "engine.market\|ASM-191\|capacity ledger" internal/engine/logistics/doc.go` all match.
- **AC-19.** `data/logistics.json` carries a `$comment`/`meta` block citing §8 and stating, per commodity, its unit of measure and confirming it is consistent with `engine.market`'s unit-of-measure convention (`engine.market`'s AC-16) so a tonnes-vs-slots figure is never ambiguous across the boundary. Check: `grep -n "\$comment\|\"meta\"" data/logistics.json` matches and states units explicitly per commodity.

## Out of scope

- Traffic assignment itself (SUE, congestion, route caching) — `engine.traffic` (a dependency, MOD-023, open); this item only consumes junction slot capacity as an input, per the outbound code.json edge.
- Commodity pricing and the static-v1 import price — `engine.market` (a dependency, MOD-020, ready); this item only queries `Price`/`Availability` as ordering inputs (AC-12).
- Cell/tile/geology state — `engine.world` (a dependency, MOD-017, open); the outbound edge exists for junction/road-graph geometry lookups only.
- The literal queue text-render (colour-coded trucks, F5's live view) — `ui.screen.trade`, per ASM-235.
- Consuming modules' actual use of the shortfall hook (what satisfaction/production/construction-stall does with a shortfall event) — that is each consumer's own item (`engine.consumption`, `engine.build`, `engine.firms`); this item only guarantees the hook fires with correct data (AC-10).
- Port/rail modal capacity (tier-7+) — §8 names road/sea; rail freight is §33's freight-harbour system (`engine.freight`, a later registered consumer), not this item.
