## 1. Why this item exists, and its place on the critical path

FEAT-2326609764 (the spatial-partition tick spec, §11) proved that the ×50 map is where 100M's sector/fold arithmetic lands, and that the map is "solved on paper" — **land is not the constraint, the O(buildings) tick is.** But FEAT-2326609764 assumed the ×50 map *exists*; it never specified how a city gets from today's 440×260 tiles to it. That is this item's job, and it is also a **gameplay mechanic**, not a one-time migration. **Aaron's ruling (2026-09-04) confirms the mechanism: map growth is tree-ring based**, with one-tile-thick rings expanding the map perimeter at each level 19-25 milestone. Each ring grows all four edges simultaneously (north, south, east, west) and is silent — no fanfare, imperceptible per event but compounds across levels. This makes land a progression reward, avoids a 5.7m-tile allocation on day one, and lets us ship expansion incrementally instead of one big-bang map.

### 1.1 The scale this has to reach, and the scale it does not have to reach here

From FEAT-2326609764 §1.2: today's map is 440×260 = 114,400 tiles; the ×50 map is ~3,111×1,838 ≈ 5.7M tiles. That whole journey does not have to happen inside seven levels. This item's honest scope is:

- **Levels 19-25 are seven ring-annexation events.** Each is a discrete, bounded, testable unit of the same mechanism. Getting the *mechanism* right — one ring, journalled, every downstream consumer proven — is what inc1 buys; the *curve* (how thick each ring is) is retunable forever without touching the mechanism (GR#3: one derivation, not seven copy-pasted ones).
- **§3 below proposes a curve that reaches roughly 2.7% of the ×50 target by level 25** (see the table) and explicitly does **not** try to land exactly on ×50 inside these seven levels. What happens past level 25 (a continuation of the same curve, a discontinuity where the last few levels jump to close the gap, or a shift to a different unlock currency entirely — Aaron's `/10m playable first` recommendation at Q100137 suggests the honest next milestone is 10M, not 100M, and 10M's land needs are far short of ×50 too) is **out of this item's scope** and flagged as **ASM-1520**.

## 2. What "annexation" (ring growth) means mechanically

**AC-1 — annexation is a reducer action, journalled like any other state mutation.**

A new action, e.g. `ANNEX_RING`, fires when `levelOf(s.xp)` crosses one of 19..25 (the same "crossed a threshold since last time" idiom `applyLevelRewards` (`engine.ts:757-769`) already uses for the cash-injection reward — **this item is a sibling of that function, not a replacement**: XP crossing a level boundary triggers *both* the existing cash reward *and*, for levels 19-25 specifically, a ring annexation). It is emitted by the tick loop the moment the crossing is detected, exactly once per level, idempotently (mirrors `lastRewardedLevel`, AC-4 below adds `lastAnnexedLevel`).

Being a reducer action means:
- It is **appended to the journal** like a placement or a bulldoze (GR#2 replay contract).
- **Replaying the journal reproduces the exact same map growth at the exact same tick**, because the trigger (`xp` crossing a threshold) is itself fully determined by the replayed history — no wall-clock, no randomness (GR#21).
- A **savepoint** taken after annexation N has occurred captures the grown dimensions as *data* (AC-3), not as a re-derivation from `xp` at load time — loading must never require "replay enough to re-earn the land", it must simply be *told* the land is there.

**AC-2 — a ring is a one-or-more-tile-thick band added simultaneously to all four map edges.**

Each annexation adds a ring of new buildable terrain around the entire current map perimeter. The ring expands the map's width and height symmetrically (north and south edges expand height; east and west edges expand width, all at once). No L-shapes, no islands, no non-contiguous chunks. This keeps `sectionOriginOf`'s existing clip-to-edge logic (`consolidator.ts:168-169`, already proven to handle a non-exact map/section division — today's 440/16 and 260/16 are both already fractional, §5) as the **only** geometry-handling code path annexation needs; nothing new has to reason about corners or holes. The whole-perimeter growth is simpler to reason about than parcel-based partial annexation: `mapW += 2 * ringThickness`, `mapH += 2 * ringThickness`.

**AC-3 — map dimensions become per-city DATA, not module constants.**

This is the load-bearing structural change and it is worth stating baldly: **`MAP_W`/`MAP_H` (`data.ts:43-44`) cannot remain hardcoded module-level constants once annexation exists**, because two different cities (or the same city before/after level 19) legitimately have different map sizes. They move into `SimState` as e.g. `mapW`/`mapH` fields, with `data.ts`'s `MAP_W`/`MAP_H` demoted to **the genesis default** (`GENESIS_MAP_W = 440`, `GENESIS_MAP_H = 260`) used only to seed a new game and to backfill old saves (AC-11).

Every current consumer of the bare exported constants (enumerated exhaustively in §4) must be re-pointed at `s.mapW`/`s.mapH` (or the per-module local mirrors, e.g. `consolidator.ts:142-143`'s "local mirror... safe to duplicate the VALUE" comment, which stops being true the moment the value is no longer a compile-time constant — that mirror must become a function of `s`, or be deleted in favour of importing the real field).

**AC-4 — a fresh reward-tracking field, parallel to `lastRewardedLevel`.**

`s.lastAnnexedLevel` (seeded to 18 on a new/backfilled game, AC-11) tracks the highest level whose ring has been annexed, exactly mirroring `lastRewardedLevel`'s idempotency contract (`engine.ts:759-760`): safe to re-check after any `xp` change, never double-annexes, never skips a level even if two level-ups land in the same tick (loop `while (lastAnnexedLevel < min(levelOf(xp), 25))`, same shape as the existing cash-reward loop must already have to handle multi-level jumps — verify and mirror it, do not diverge).

## 3. The growth curve and ring-thickness scaling (the ask, part **a**)

### AC-5 — ring thickness scales with level to compound growth toward the ×50 target

Each level from 19-25 adds a ring of tiles around the entire map perimeter. **Ring thickness = level - 18**, so:
- Level 19 adds a **1-tile-thick ring** around the 440×260 genesis map → map becomes 442×262
- Level 20 adds a **2-tile-thick ring** around the current map → map becomes 446×266
- Level 21 adds a **3-tile-thick ring** → map becomes 452×272
- ... and so on through level 25 (7-tile-thick ring)

**The arithmetic:** A k-tile-thick ring added to a map of dimensions W×H grows both width and height by 2k tiles (k on each side), adding tiles equal to approximately 2k(W+H) + 4k². For the genesis 440×260 map, one 1-tile-thick ring adds ~2(440+260) + 4 = 1,404 tiles. As the map grows and ring thickness increases, each successive level's ring adds exponentially more area.

**Rationale for scaling thickness:** A constant 1-tile-thick ring per level would add only ~1,404 tiles/level × 7 levels ≈ 9,828 tiles total by level 25, reaching only 1.09× the genesis map — nowhere close to the ×50 target needed for 100M. By scaling ring thickness with level, growth compounds: later rings are added to larger maps (so their absolute tile count is higher) and are themselves thicker, creating a compounding effect. **This is a PLACEHOLDER curve flagged for Aaron's balance pass** (ASM-1521) — the mechanism (thickness scales per level) is the AC, not the exact exponent. After playing the game and measuring level-progression pacing, Aaron may tune the scaling formula (e.g. `thickness = level - 18` vs. some other function).

**Table (PLACEHOLDER-balance — mechanism is the AC, not these exact figures; ASM-1521):**

| Level | Ring thickness | `mapW × mapH` at end of level | Tiles added this level | Cumulative tiles | % of ×50 target (5.72M) |
|---|---|---|---|---|---|
| 18 (genesis) | — | 440 × 260 | — | 114,400 | 2.0% |
| **19** | 1 | 442 × 262 | ~1,404 | 115,804 | 2.0% |
| 20 | 2 | 446 × 266 | ~2,832 | 118,636 | 2.1% |
| 21 | 3 | 452 × 272 | ~4,308 | 122,944 | 2.1% |
| 22 | 4 | 460 × 280 | ~5,856 | 128,800 | 2.3% |
| 23 | 5 | 470 × 290 | ~7,500 | 136,300 | 2.4% |
| 24 | 6 | 482 × 302 | ~9,264 | 145,564 | 2.5% |
| 25 | 7 | 496 × 316 | ~11,172 | 156,736 | 2.7% |

By level 25 the map is ~496×316, ~1.37× the genesis linear extent, ~2.7% of the ×50 area target — **deliberately incomplete** (§1.1), and **rings alone do not reach ×50 within these seven levels.** Closing the gap to ×50 or any intermediate target (10M's land needs, per Q100137) is a follow-up item (ASM-1520) that may extend the ladder past level 25, increase ring thickness scaling beyond linear, add annexation at other progression milestones (not just levels), or some combination thereof.

### AC-6 — every ring dimension is validated against a hard cap before it is applied

`RAIL_BRANCH_BUDGET = 200,000` (`railConnect.ts:59`) is today a **hardcoded literal** justified by a comment claiming it sits "ABOVE the whole board's cell count (MAP_W·MAP_H = 440·260 = 114,400)". That comment's premise breaks well within the level 19-25 ladder — by level 25, cumulative 156,736 tiles, the budget would be depleted — **this is a real latent defect this feature activates, not a hypothetical one.** AC-6 requires `RAIL_BRANCH_BUDGET` to be re-derived as a function of `s.mapW * s.mapH` (e.g. `mapW * mapH * 2`, preserving the "genuinely walled off, never merely distant" property at any map size) rather than a compile-time constant, **landed as part of inc1** regardless of which level's ring is being tested, because inc1's differential harness (AC-19) will otherwise silently pass on a map too small to trigger the bug and ship it live for level 22+.

## 4. What a ring contains on arrival (the ask, part **b**)

### AC-7 — a freshly annexed ring is empty buildable terrain, road-disconnected, at the current construction-cost/tag defaults

No pre-placed buildings, no pre-existing roads, no special terrain features. This is the **only** option that requires no new terrain-generation system, no new data (real-Kent geometry, coastline, elevation) and no new rendering — the ring's new tiles are exactly the same "flat 50m tile, buildable, part of no zone" that every tile on today's map already is outside a placed building's footprint. `isPlaceable`'s existing defer to `specUnlocked` (`data.ts:3` comment) needs no change; the new tiles simply exist and are placeable like any other.

### ASM-1522 — real-Kent geography for annexed rings is explicitly deferred

Metropolis's premise (CLAUDE.md: "real OS Terrain 50 Kent geography, Folkestone start tile") implies annexed land should *eventually* be real terrain, not a featureless rectangle — but sourcing OS Terrain 50 data for the expanding perimeter and rendering it are their own feature-sized pieces of work with no code today (`MapView.tsx` renders zone colours, not terrain). **Recommendation: ship AC-7 (empty terrain) for the full 19-25 ladder**, and treat "give annexed rings real Kent geography" as a separate, later, explicitly-scoped item — not a silent scope-creep inside this one. **Aaron to confirm** (Q100172).

### AC-8 — base-26 multi-letter row labels, landed BEFORE any level crosses the 26-band threshold

`ROW_BAND = 10` (`data.ts:46`), so band count is `ceil(mapH / 10)`. Genesis: `ceil(260/10) = 26` bands — **already exactly at the ceiling**, which is why BUG-657's fix clamped to 25 (0-indexed) and why its own closing comment flagged this: *"base-26 labels needed before map growth."* The level-20 target (`mapH = 390`) is `ceil(390/10) = 39` bands — **the very first annexation in the ladder (level 19, `mapH` unchanged at 319... wait, recompute: level 19 grows width only, `mapH` stays 260 per the table — level 20 is the first `mapH` growth, taking it to 390 = 39 bands.**

`yLabel` must become the standard base-26 bijective-numeration scheme (A..Z, AA..AZ, BA..., matching spreadsheet column naming): band `n` (0-indexed) renders as the base-26 representation using digits 1-26 mapped to A-Z (bijective base-26, **not** ordinary base-26, because ordinary base-26 has no representation for the "0" digit in a non-leading position the way A-Z does — this is the same trap spreadsheet-column-letter code always has to get right, and a test enumerating bands 0..999 and asserting round-trip uniqueness is mandatory, not optional, given BUG-657's history of exactly this function being wrong in production undetected). Landed as part of **inc1** even though inc1's own parcel (level 19) does not cross the threshold — because inc1 is also where AC-7's "gutter loop iterates the real band count" (row 3 of the table) lands, and a hardcoded-26 loop calling a base-26 `yLabel` on band 26+ would silently truncate rather than crash, exactly the shape of failure BUG-657 was.

### AC-9 — road-edge reseeding is the determinism-critical wrinkle, spec'd explicitly, and fires on EVERY ring

**The problem, stated precisely:** `computeRoadConnectivity` (`data.ts:677-723`) seeds its connectivity BFS from any road tile where `x === 0 || y === 0 || x === MAP_W - 1 || y === MAP_H - 1` — i.e., "a road that touches the edge of the known world is assumed to connect onward to the region beyond." **Ring annexation moves the edge.** A road tile at `x = 439` (the old east edge after genesis + level-19 ring to `mapW = 442`) was a connectivity seed before level 20; after the level-20 ring-2 growth to `mapW = 446`, that same tile is now an **interior** tile (`x = 439 ≠ 445`) and is **no longer a seed** — its connectivity now depends on genuinely reaching a road network, not on merely touching the old boundary. **This wrinkle occurs on EVERY ring annexation (levels 19-25), not just the first one** — making the determinism contract stricter: the edge-seeding rule must be re-evaluated and the connectivity cache must be invalidated after every ring, not as a one-time anomaly at level 19.

This means **the connectivity graph changes as a direct, deterministic side effect of each ring annexation**, even though not a single building or road tile moved. A city with a road stub built out to the old map edge specifically to "reach the edge of the map" (a legitimate, previously-correct strategy under today's seeding rule) could have that stub's buildings **silently lose road connectivity, and therefore drop out of Layer G / the online set**, the instant a level lands and a ring is annexed — a real, felt, "why did my buildings just go offline" bug if it is not handled.

**Required behaviour (not optional, not a "nice to have"):**

1. Annexation is **itself** one of the triggers in FEAT-2326609764 AC-8's "what marks a sector dirty" table, if/when that spec lands first — but even independently of the partition work, this item on its own requires: annexation **bumps `GlobalInputVersions.roadConnectivityVersion`** (FEAT-2326609764 AC-11's precedent, or — if that spec has not landed — **forces a full `computeRoadConnectivity` recompute** the same way any other roadConnectivityCache-invalidating event does today, since `roadConnectivityCache` (`data.ts:676`) is keyed on `s.buildings` object identity and a `mapW`/`mapH` change with the *same* `buildings` array would otherwise return the **stale cached result computed under the old edge rule** — this is a second, independent staleness hazard on top of the felt-gameplay one above, and it is a plain cache-correctness bug: **the cache key must include map dimensions, or the cache must be explicitly busted on annexation.**
2. A test builds a city with a road stub at the old `MAP_W - 1` edge (connected, feeding online buildings), annexes a parcel, and asserts: (a) connectivity is recomputed (not served stale), (b) the old-edge tiles that are no longer geometrically at the edge and have no other path to a trunk/edge seed **correctly lose seed status and, if genuinely unreached, lose connectivity** — this is the CORRECT and intended behaviour, not a bug, and (c) a road stub built at the **old** edge that also happens to reach the **new** edge (i.e., extends across the annexed parcel) is seeded via the new edge, so the player's existing infrastructure is not automatically stranded if it was already the sort of trunk-reaching road that would stay connected under normal play.
3. This is exactly the class of thing GR#21 (determinism) and the project's replay-byte-identity discipline (FEAT-2326609764 AC-22) care about: **an annexation replayed twice from the same journal must produce byte-identical connectivity before and after**, and the test in AC-16 below proves it.

**ASM-1524:** the "edge = off-map connection to the world" convention was presumably chosen because the genesis map's edges (mostly sea/county-boundary in the real Kent geometry framing) plausibly represent real infrastructure leaving the modelled area. Annexation **inherits this same convention at the new edge** — the newly annexed parcel's own outer boundary becomes the new "edge of the world" seed line, and the boundary between old and new land is just ordinary interior tiles. **Recommend accepting this** as the simplest self-consistent rule (no new concept needed — "the edge of the map" already means "the edge of the world" and a bigger map just has a bigger world), but it is Aaron's call whether some annexed edges should NOT auto-seed (e.g. a natural inland boundary that should require the player to actually build a connecting road) — folded into Q100170.

### AC-10 — every derived-from-dims cache in the exhaustive list above is proven correct across an annexation boundary by ONE shared test fixture

A single `test/annex-derived-consumers.mjs` fixture builds a city, annexes a parcel, and re-runs the full assertion set from rows 1-17 of the §5 table in one pass — not seventeen separate ad hoc tests scattered across files, so that a future eighteenth consumer (the next thing anyone adds that reads `MAP_W`) has one obvious place to add its assertion, and so that a regression in the *interaction* between two consumers (e.g. the twelfths cache AND the road-connectivity cache both needing invalidation on the same event) is caught by one test running both, not by two tests that each pass in isolation.

## 6. Savepoint and journal compatibility (the ask, part **c**)

### AC-11 — an old savepoint with no `mapW`/`mapH` field defaults to the genesis dimensions

`SimState`'s decode path (`saveCodec.ts`, per FEAT-2326609764 AC-18's citation) must treat a missing `mapW`/`mapH` as `GENESIS_MAP_W`/`GENESIS_MAP_H` (440/260) and `lastAnnexedLevel` as `18` — i.e. **an old save loads as if it had never annexed anything**, which is correct: it genuinely never has, because the feature did not exist when it was saved. This is the same "old-savepoint defaults explicit so no silent economy change on load" contract FEAT-2326609711's inc1/inc2 ACs already established for `externalCover` toggles — this item follows the identical pattern, not a new one.

**A subtlety worth stating:** if that old save's `xp` already corresponds to level 21 (the player was already past level 18 when this feature shipped), the very first tick after load must **immediately** run the annexation catch-up loop (AC-4's `while (lastAnnexedLevel < min(levelOf(xp), 25))`) — annexing levels 19, 20, 21 in sequence, in the same journalled-action shape as if they were happening live, **on the load tick**, not deferred and not skipped. A test loads a pre-feature save at level 21's XP and asserts the city gains exactly three parcels (19, 20, 21) on the first tick after load, each independently journalled, each producing the byte-identical dimensions the table in §3 specifies for a city that had actually played through those levels live.

### AC-12 — replay across an annexation boundary is byte-identical

## 7. XP thresholds for levels 19-25 (the ask, part **d**)

### AC-14 — `XP_LEVELS` must be extended past its current ceiling of level 20

`XP_LEVELS` (`engine.ts:267-275`) is built by a loop `for (let l = 2; l <= 20; l++)`, producing an array of length 20 (index 0 = level 1's threshold `0`, ..., index 19 = level 20's threshold). **Level 20 is the highest level the game can currently reach at all** — `levelOf` (`engine.ts:277-281`) can never return more than 20 today, and `xpForLevel` (`engine.ts:283-284`) clamps any higher `level` argument down to index 19 (level 20's threshold), silently. **This item's very first requirement, before any parcel logic, is extending the loop bound from `l <= 20` to `l <= 25`**, continuing the existing `step = Math.round(step * 1.5)` progression with no change to its shape — levels 1-20's thresholds are **unchanged** (GR#3: do not silently retune an existing, presumably-already-balanced curve as a side effect of extending it), levels 21-25 are new entries continuing the same geometric step.

**PLACEHOLDER-balance, flagged (ASM-1525):** the resulting level-25 threshold is whatever the `×1.5` step arithmetic produces after 7 more iterations from wherever level 20 left off — a large number, appropriate for a late-game milestone, but not derived from any playtesting data (none exists yet for a game that cannot currently reach level 20 in normal play, per `BASELINE_XP: 30` genesis seed at `engine.ts:383` and the general early-stage balance regime). **Aaron to retune after playing against it**, per the project's standing "player-felt numbers = placeholder + directional tests + Aaron row-by-row + balance pass" regime.

### AC-15 — `unlockedAtLevel`'s existing per-level-notice mechanism needs no change, and is the natural home for the ring announcement

`unlockedAtLevel(level)` (`data.ts:500-512`) already exists to tell the player what became available "EXACTLY at `level`" — used today for real specs (with a `unlock !== 99` filter excluding auto-placed network scaffolding). The level-up notice for 19-25 should surface the ring arrival through the **same notice mechanism** the cash-reward and spec-unlock notices already use (`applyLevelRewards`'s notice-building, `engine.ts:757` onward), not a bespoke new UI path. The notice text should be silent/minimal (e.g. "New land available.") matching Aaron's "no fanfare" rule — this is a docs/UX-adjacent AC, not a data-shape one, and is flagged for the jnr developer to confirm the existing notice queue can carry a "land" notice type alongside its existing "cash" and "spec" ones.
