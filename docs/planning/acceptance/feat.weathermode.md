## Why this file is scoped the way it is

FEAT-067 is a **mode switch**, not a new simulation system. Hard mode's "random weather damage" must be built entirely out of `engine.season`'s existing seasonal curves plus `feat.disasters`'s existing event-pressure/precursor/no-bespoke-resolution machinery (mirroring exactly how `feat.disasters.md` itself was scoped against `engine.logistics`/`engine.world`) — this file does not invent a third, parallel damage system. Easy mode's "extra-money/high-tax economy" must be built entirely out of `engine.finance`'s ledger and `engine.tax`'s instrument panel — a mode-scoped starting grant/subsidy posted as real transactions and a mode-scoped baseline tax-rate uplift applied through real instruments, never a hidden multiplier bypassing either module's machinery.

The design-north-star test is applied explicitly to both modes (AC-1 covers hard, AC-9 covers easy, AC-15 covers the switch as a whole), because this item is the north star's own textbook case: a naive reading would make hard mode "worse" and easy mode "better", which the north star's thesis says is a failure mode, not a feature.

## User stories

- **US-1.** As the player choosing a save's difficulty at game seed, I need that choice to be a real, immutable-for-the-save decision with two genuinely different economic/risk shapes — not a cosmetic label — so the choice matters for the life of the city.
- **US-2.** As `engine.season` (already built, pure month-index curves), I need hard mode's weather-damage frequency/severity to be *weighted by* my existing seasonal curves (e.g. storm season more likely in the months my curves already mark as high-risk) rather than a mode-owned calendar that ignores me, so seasonality stays the single source of truth for "when" (GR#3).
- **US-3.** As `feat.disasters` (draft-ahead, event-pressure machinery already specified against `engine.logistics`/`engine.world`), I need hard mode's weather damage to be an amplification of my existing event categories (frequency/severity multiplier, precursor lead-window unchanged in kind) — never a second event-injection path that bypasses my precursor/no-bespoke-resolution rules — so hard mode is "more of the same real pressure", not a different kind of pressure with different rules.
- **US-4.** As `engine.finance`, I need easy mode's "extra money" to be a real, ledger-posted transaction (a seed-time grant and/or a recurring subsidy line) — queryable, drill-through-able, subject to the same insolvency/conservation invariants as every other transaction — never a hidden balance adjustment outside the ledger.
- **US-5.** As `engine.tax`, I need easy mode's "high tax" to be a real baseline uplift on real instrument rates — subject to my own elasticity/incidence/Laffer machinery (`engine.tax.md` AC-3/AC-4/AC-5) — so a high tax rate in easy mode still shrinks its own base and still shows a real, moving incidence split, not a rate number that renders but does nothing.
- **US-6.** As the player who chose easy mode, I need the extra money to come with a felt, structural cost (not merely "the same city but richer") — a genuine trade-off per the design north star's thesis (US-2 of that document: "every yes must have a felt no") — so easy mode is a different *kind* of city to run, not hard mode with the difficulty knob turned down.
- **US-7.** As the player who chose hard mode, I need the weather-damage pressure to be foreshadowed exactly the way every other disaster category is (§10's "never random-spam, projected where possible"), consistent with Pillar 3's "squeezed, never ambushed" — so hard mode is *harder*, not *unfair*.

## Scope

A seed-time, immutable, two-valued mode switch (hard/easy). Hard mode: a frequency/severity multiplier applied to `feat.disasters`'s existing weather-adjacent event categories (storm surge at minimum; other categories at BA/Aaron's discretion — see Escalations), itself weighted by `engine.season`'s existing seasonal curves, with `feat.disasters`'s precursor and no-bespoke-resolution rules unchanged. Easy mode: a seed-time treasury grant and/or recurring subsidy posted through `engine.finance`'s ledger, plus a baseline uplift on `engine.tax`'s instrument rates applied through real instruments (subject to real elasticity/incidence). All numeric values (multipliers, grant amount, subsidy rate, tax uplift) are placeholders pending Aaron's balance pass.

## Acceptance criteria

### Functional — the mode switch itself

- **AC-1 (US-1; design-north-star five-question test, applied to the switch as a mechanic).** A `WeatherMode` (or equivalent) is chosen at world-seed time, persisted in the save/world state, and immutable thereafter — no in-game command, cheat, or debug-mode unlock (per `feat.debugmode.md`) may change it mid-save. Check: `go doc ./internal/engine/weathermode` (or the package hosting the mode field, confirmed at dispatch) shows the mode set only via a seed/new-game construction path; a passing test constructs a world with a chosen mode, attempts a post-seed mutation call, and asserts it is rejected (`grep -rn "func Test.*[Ii]mmutable.*[Mm]ode\|func Test.*[Mm]odeLocked" internal/engine/weathermode/*_test.go`). **What a lazy implementation looks like:** a plain mutable struct field with no guard, technically "set at seed" because nothing else happens to call the setter yet — this passes a shallow "mode exists" reading while leaving the immutability invariant unenforced through the public API (the exact GR#23/dev-team-process "weakness pattern #1" shape: an invariant stated in prose, not enforced in code). The check above requires the mutation attempt to be structurally rejected, not merely untested.
- **AC-2 (GR#15; data-driven, no invented constants).** Both modes' numeric parameters (hard mode's event frequency/severity multiplier; easy mode's grant amount, subsidy rate, and tax-rate uplift) are loaded from a data file (e.g. `data/weathermode.json`), not hardcoded Go literals, and each carries a `$comment`/`meta` block marking it a placeholder pending Aaron's balance pass (per the standing balance-number regime — Vestige `metropolis-balance-number-regime`). Check: `grep -n "\$comment\|\"meta\"" data/weathermode.json` (or wherever the values land — confirm at dispatch) matches and states "placeholder pending balance pass"; `grep -nE "[0-9]\.[0-9]|[0-9]{2,}" internal/engine/weathermode/*.go` (excluding `_test.go`) finds no bare numeric literal for a mode parameter outside doc-comment prose.

### Functional — hard mode, grounded in engine.season + feat.disasters

- **AC-3 (US-2/US-3; hard mode amplifies feat.disasters, does not replace it).** Hard mode's weather damage is implemented exclusively as a frequency/severity multiplier applied to `feat.disasters`'s existing event-injection surface (`EventsAPI`/`DisasterAPI` per `feat.disasters.md` AC-1) — this package contains no independent event-trigger, damage-calculation, or resolution logic of its own. Check: `grep -rn "events\.\(InjectEvent\|EventsAPI\)\|disasters\." internal/engine/weathermode/*.go` (excluding `_test.go`) shows the hard-mode path calling into `feat.disasters`'s real surface with a multiplier parameter, not a locally-computed damage value; `grep -rln "type.*Damage\|type.*Resolution" internal/engine/weathermode/*.go` finds no mode-owned damage/resolution type. **What a lazy implementation looks like:** a "weather damage" system that reads engine state and applies its own reduction to a building/stock value directly, only consulting `feat.disasters` for flavour text — this would satisfy "hard mode does more damage" while being exactly the parallel-system anti-pattern `feat.disasters.md` itself was scoped to prevent (see that file's AC-2/AC-3/AC-4 false-pass warnings); the check requires the real call-through, not merely a plausible-looking damage number.
- **AC-4 (US-2; seasonally weighted, not a flat mode-owned calendar).** The hard-mode frequency/severity multiplier is itself weighted by `engine.season`'s existing curve(s) for the relevant month (e.g. storm-surge pressure higher in months `engine.season`'s data already marks as high-risk, if such a curve exists; if no directly-applicable curve exists yet, this AC requires the multiplier to at minimum accept a month-index input and vary by it, sourced from `SeasonAPI`, not a mode-local 12-entry table duplicating that concern). Check: `grep -rn "season\.\(SeasonAPI\|.*Multiplier\)" internal/engine/weathermode/*.go` (excluding `_test.go`) shows a real call into `engine.season`'s package; a passing test asserts the hard-mode-adjusted event probability/severity differs between at least two months in the documented direction (`grep -rn "func Test.*[Ss]easonalWeight" internal/engine/weathermode/*_test.go`).
- **AC-5 (US-7; §10/Pillar-3 "never random-spam, squeezed never ambushed" — reuses feat.disasters's precursor rule verbatim, does not weaken it).** Turning hard mode on changes the *frequency and severity* of weather events, never the *precursor lead-window rule* itself — `feat.disasters.md` AC-5's rising, queryable precursor before every event still applies unmodified under hard mode. Check: a passing test runs the same precursor-observability assertion `feat.disasters.md` AC-5 requires (nonzero, rising precursor for at least the documented lead window before any hard-mode-amplified event fires) and asserts it holds identically under hard mode (`grep -rn "func Test.*[Hh]ardMode.*[Pp]recursor" internal/engine/weathermode/*_test.go`). **False-pass risk, stated explicitly because this is the item's central tension with Pillar 3:** an implementation that raises event *frequency* by shortening or skipping the precursor window (more events by making them less foreshadowed, rather than by making them more frequent within the same foreshadowing rule) would satisfy a shallow "hard mode has more weather damage" reading while directly violating "squeezed, never ambushed" — the check requires the same lead-window assertion `feat.disasters.md` uses, run specifically under hard mode, to catch exactly this shortcut.
- **AC-6 (US-3; no bespoke resolution, hard mode included).** Hard-mode-amplified events resolve exactly as `feat.disasters.md` AC-6 requires — through the affected module's (`engine.logistics`/`engine.world`) own normal state recovery, never a mode-owned countdown or "hard mode heals faster/slower" side timer. Check: `grep -rln "type.*Recovery\|type.*Resolution" internal/engine/weathermode/*.go` finds no mode-owned recovery-state type (identical check to `feat.disasters.md` AC-6, re-run against this package).

### Functional — easy mode, grounded in engine.finance + engine.tax

- **AC-7 (US-4; real ledger transaction, not a hidden balance bump).** Easy mode's starting grant and/or recurring subsidy is posted through `engine.finance`'s `FinanceAPI` as a real, categorised transaction (a distinct account/category, e.g. `EasyModeSubsidy`, not folded into an existing category where it can't be drilled through per `engine.finance.md` AC-11) — never a direct mutation of a balance field bypassing the ledger. Check: `grep -rn "finance\.\(PostTransaction\|FinanceAPI\)" internal/engine/weathermode/*.go` (excluding `_test.go`) shows the grant/subsidy posted through finance's real surface; a passing test seeds an easy-mode world and asserts the grant/subsidy appears as a drill-through-able ledger line via `Lines(aggregateID)` (`grep -rn "func Test.*[Ee]asyModeSubsidy\|func Test.*[Ss]eedGrant" internal/engine/weathermode/*_test.go`).
- **AC-8 (US-5; real tax-instrument uplift, subject to real elasticity/incidence — the load-bearing check for "not simply free money").** Easy mode's tax uplift is applied as a baseline rate increase on one or more real `engine.tax` instruments (via `TaxAPI`'s rate-setting surface, per `engine.tax.md` AC-1), not a separate flat "easy mode tax" side-channel outside the instrument panel — and the uplifted rate is proven to still exercise `engine.tax`'s real elasticity/base-shrinkage and incidence-shift machinery (`engine.tax.md` AC-3/AC-4/AC-5), not a rate that is cosmetically higher but functionally inert. Check: `grep -rn "tax\.\(SetRate\|TaxAPI\)" internal/engine/weathermode/*.go` (excluding `_test.go`) shows the uplift applied through the real rate-setting surface; a passing test compares an easy-mode-uplifted instrument's taxed base and incidence split against the same instrument at hard mode's baseline rate and asserts the base is measurably smaller and the incidence split differs (reusing `engine.tax.md` AC-3/AC-5's own comparison shape) (`grep -rn "func Test.*[Ee]asyMode.*[Tt]axUplift" internal/engine/weathermode/*_test.go`). **What a lazy implementation looks like:** an "easy mode" that simply adds a flat percentage to every finance query's displayed revenue figure, with `engine.tax`'s actual instrument rates left untouched — this would satisfy "easy mode collects more tax" in a UI screenshot while never touching a real instrument, meaning AC-3/AC-4/AC-5's Laffer/incidence machinery (the whole reason "high-tax" is interesting rather than decorative) never engages. The comparison check above specifically requires the real base-shrinkage/incidence-shift to reproduce under the uplifted rate.
- **AC-9 (US-6; design-north-star five-question test, applied to easy mode explicitly — the AC that proves easy mode is a different city, not a richer hard-mode city).** Easy mode's tax uplift measurably suppresses at least one real growth/attractiveness metric that a lower, hard-mode-baseline rate would not (reusing whatever directional mechanism `engine.tax`'s elasticity produces — e.g. business formation, migration attractiveness, or an equivalent metric already exposed by a module this package legitimately calls) — proving the "felt no" the north star's second question demands, so easy mode is not simply hard mode with money added. Check: a passing test runs an identical scripted scenario at hard-mode baseline rates and at easy-mode uplifted rates and asserts the chosen growth/attractiveness metric is measurably lower under easy mode, in addition to AC-8's base-shrinkage assertion (`grep -rn "func Test.*[Ee]asyMode.*[Tt]radeOff\|func Test.*[Nn]otSimplyRicher" internal/engine/weathermode/*_test.go`), mirroring `engine.coastal.md` AC-11's "real trade-offs" pattern (opposite-direction pairing as a structural property, not documentation).
