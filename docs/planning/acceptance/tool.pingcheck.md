## Why this file exists, and why it is documented after the fact

The session permit has a 5-minute TTL and is renewed by this PostToolUse hook, not by hand. The hook implements the DHCP "renewal at T/2" pattern: the hook checks at most every 2 minutes, `claude-sync.js renew --auto` only actually renews when under 3.5 minutes remain, so the net effect is a renewal at the first check after ~1.5 minutes have elapsed. v2.2 made every part of it per-window (`session_id` from the hook payload, a per-window throttle file) because two Claude Code windows sharing a throttle file is exactly how Bill's permit silently expired on 2026-07-13 — one window's ping suppressed the other's renewal.

Like the other `tool.*` hook files, this shipped without a criteria file; the contract below is stated after the fact so the next round of work (a future test file, or a Destructive round) has something to build or attack against instead of starting from the code again.

## A. Behaviour

- **AC-1 (engagement — hook type).** The hook runs as a **PostToolUse** hook with **no `matcher`** (the first entry in `.claude/settings.json`'s `PostToolUse` array), so it runs after *every* tool use across all tool types — unlike the `matcher: "Bash"` / `matcher: "PowerShell"` PostToolUse siblings (`claude-bow-autoref.js`, `claude-reflection.js`). Check: `grep -n "claude-ping-check.js" .claude/settings.json` shows it inside the matcher-less PostToolUse entry (the `Agent` PostToolUse entry is `claude-agent-stop.js`, a different file). **What a false pass looks like:** a reader who assumes this hook is Bash-only would describe the wrong engagement surface — the check is "which entry is it in," not "what does it do."
- **AC-2 (window identity source).** The window id is taken from the hook stdin payload's `session_id` field, falling back to `process.env.CLAUDE_CODE_SESSION_ID` when the payload is missing, unparseable, or lacks `session_id` (source: `claude-ping-check.js:59-63`). Check: a test feeding `{"session_id":"W-A"}` asserts the renewal is keyed to `W-A`; a test feeding invalid JSON with the env var set to `W-B` asserts the fallback `W-B` is used. Both halves are required — a check that only tests the payload case would also pass a build that ignored the env fallback entirely.
- **AC-3 (per-window throttle file).** The throttle file is `.claude/.last-ping-${windowId}`, falling back to the shared `.claude/.last-ping` only when no window id is known (source: `claude-ping-check.js:67`). Two windows must never share a throttle file, so window A's ping cannot suppress window B's renewal. Check: a test asserts the filename for window `W-A` differs from the filename for `W-B`, and both differ from the no-id fallback `.last-ping`.
- **AC-4 (fast path — the whole point of the throttle).** If `Date.now() - lastPingMs < CHECK_INTERVAL_MS` (2 minutes, source: `claude-ping-check.js:33`), the process exits 0 immediately after a single local file read — no subprocess is spawned, no database is touched (source: `claude-ping-check.js:74-77`). Check: a test with a fresh throttle file asserts exit 0 **and** asserts `claude-sync.js` was never invoked (intercept `child_process.execSync`; the binding part is the negative — "no spawn happened", not merely "exited 0", which a slow-path implementation that still runs `renew --auto` would also produce).
- **AC-5 (slow path — write timestamp first).** When the interval has elapsed, the new timestamp is written to the throttle file **before** `claude-sync.js renew --auto` is invoked, so a renewal that fails (network/db) still throttles — no retry spam (source: `claude-ping-check.js:79-80`). Check: a test forces the subprocess to fail, then asserts the throttle file now holds `~now`; a follow-up immediate invocation must take the fast path (AC-4) rather than re-attempting the renewal. **What a lazy implementation looks like:** writing the timestamp *after* a successful renewal would re-attempt on every tool use while the DB is down — the check's second half (a second call is throttled) is what distinguishes the two orderings.
- **AC-6 (renewal invocation).** The slow path runs `node claude-sync.js renew --auto` with `timeout: 15000`, `cwd: __dirname`, and `env` = `{...process.env, CLAUDE_CODE_SESSION_ID: windowId}` (source: `claude-ping-check.js:83-88`). The env override is what lets `claude-sync.js` resolve *this* window's permit from the session map rather than cross-renewing via a shared key. Note (ASM-947): the invocation is `execSync` with a **single interpolated template string** (`node "${SYNC_SCRIPT}" renew --auto`), not `spawnSync` with an argv array — so a test intercepts the command string (or stubs `child_process.execSync`), not a spawn argv. Check: a test intercepts the invocation and asserts the command string contains `renew --auto` and that `env.CLAUDE_CODE_SESSION_ID` equals the window id derived in AC-2.
- **AC-7 (output passthrough).** Any non-empty stdout from `renew --auto` is forwarded to the hook's own stdout (source: `claude-ping-check.js:89-92`). This is the only way wake-recovery and `IDENTITY CHANGED` notices reach the user. Check: a test stubs the subprocess to return a known string and asserts that string appears on stdout; a second test with empty stdout output asserts nothing extra is emitted.
- **AC-8 (error swallow).** A non-zero exit or timeout from the subprocess is swallowed and the process still exits 0 (source: `claude-ping-check.js:93-96`). The throttle write in AC-5 already guarantees no retry storm. Check: a test forces the subprocess to throw and asserts exit 0 with no unhandled rejection/crash.
- **AC-9 (DHCP T/2 contract).** The header's stated arithmetic must hold as a designed behaviour: TTL 5 min, hook interval 2 min, `renew --auto` threshold 3.5 min remaining → the permit renews at the first check after ~1.5 min have elapsed. Check: this is verified by reading `RENEW_THRESHOLD_MS` in `claude-sync.js` against `CHECK_INTERVAL_MS` in this file — a `grep`-and-eyeball check, not a runtime test, because the arithmetic spans two processes.
- **AC-10 (stdin safety net).** `readStdin` never hangs the agent: if stdin is a TTY (manual run) it returns immediately with `''`; otherwise a 2000 ms `.unref()` timeout forces completion even if stdin misbehaves (source: `claude-ping-check.js:43-51`). Check: a test asserting the unref'd timeout exists (or, more cheaply, that the `isTTY` branch returns without reading), with the header comment "never hang the agent" reviewed by eye.
- **AC-11 (always exit 0).** Every path terminates in `process.exit(0)` (source: `claude-ping-check.js:76, 96`). Check: `grep -n "process.exit" claude-ping-check.js` shows no non-zero exit code.

## B. Fail-open posture

- **AC-12 (never blocks, always fails open).** This hook never denies, blocks, or delays a tool; on every error path — subprocess failure, timeout, unreadable or first-run throttle file, invalid stdin — it exits 0, silently. It is a **freshness/availability mechanism, not a security gate**, and it must not be mistaken for one (contrast: `claude-destructive-guard.js` and `claude-author-guard.js` are fail-**closed** PreToolUse gates; this is a fail-**open** PostToolUse one). ASM-723 records this posture as deliberate. Check: the header's "Fast path … no Firestore hit" plus the catch-with-no-output block are read together; a test asserting "a failed renewal yields exit 0 and empty stderr" is the runnable form.
- **AC-13 (failure mode is recovery, not loss).** The cost of a silent renewal failure is a permit that eventually expires — recoverable by the next `checkin` or by `renew --auto`'s wake-recovery path (re-acquire the window's previous name, or a new slot with an `IDENTITY CHANGED` notice) — not a security breach or a stuck session. The fail-open posture is justified by that asymmetry, the same shape `tool.authorguard.md` and `tool.destructiveguard.md` spell out for their own (opposite) postures. Check: reviewed by eye — prose, not grep-checkable.

## C. Tests

- **AC-14 (the gap — written RED today).** **No test file exists** for this hook (`claude-ping-check.test.js` is absent from the repo root, alongside every other `claude-*.test.js`). ASM-724 records this. Every AC below is a test *that a future test file must contain* and is therefore **RED by absence** today — not "not yet written", but "no check currently proves any of the contract above, so a regression would land silently." Do not mark this file's ACs as passing without a `claude-ping-check.test.js` landing that covers AC-15–AC-20.
- **AC-15.** A passing test asserts the fast path: fresh throttle file → exit 0 **and** no subprocess spawn (the binding half of AC-4).
- **AC-16.** A passing test asserts the slow path: stale throttle → timestamp written **and** `renew --auto` spawned with the correct argv and `env.CLAUDE_CODE_SESSION_ID` (AC-5/AC-6).
- **AC-17.** A passing test asserts window-id precedence: payload `session_id` beats the env fallback, and the env fallback is used when the payload is invalid (AC-2).
- **AC-18.** A passing test asserts per-window throttle isolation: two distinct window ids produce two distinct throttle files (AC-3).
- **AC-19.** A passing test asserts write-before-renew: a failing subprocess still throttles, so a second immediate call takes the fast path (AC-5's second half).
- **AC-20.** A passing test asserts output passthrough and error swallow: known stdout is forwarded; a throwing subprocess still exits 0 with no crash (AC-7/AC-8).

## Out of scope (stated, not silently absent)

- The actual permit acquisition/renewal/wake-recovery logic — that lives in `claude-sync.js` (`cmdRenew`, `findMine`, `acquire`), which is a separate module. This hook is only the *throttle + scheduler* that decides when to call it.
- Retrying a failed renewal, or any backoff beyond "the throttle timestamp was already written" (AC-5) — there is no retry; the next renewal is simply the next tool use after the next 2-minute window.
