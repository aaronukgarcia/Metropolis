## 1. Problem + goal

At ~68,000 simulated citizens, placing a zone in the dogfood webconsole lags roughly **5 seconds** behind the mouse. Root cause: the entire simulation — reducer, tick loop, and every derived-data selector — runs on the **same thread that also has to paint the cursor, the map canvas, and every dock panel**. JavaScript is single-threaded per realm, so any synchronous computation triggered by a user action blocks the event loop until it finishes; nothing else (including drawing the placement preview under the mouse) can run until it returns.

Concretely, the placement path already recomputes the whole city on every click:

- `place` (`webconsole/src/sim/engine.ts:2744-2793`) calls `occupiedSet(state)` (`webconsole/src/sim/data.ts:2538`) — an O(buildings × footprint) rebuild of the occupied-tile set — just to fit-check the **one** new building being placed.
- The top-level `reducer` (`engine.ts:3657`) then unconditionally recomputes `computeRoadConnectivity` (`engine.ts:3660-3664`, calling `data.ts:539-598`) whenever `buildings` changed, not only on the tick boundary.
- Every subsequent render of `RightDock` and `DemandDock` (which subscribe to the **whole** `SimState` via `useSim()`, not a slice) re-evaluates `serviceCoverageOf` (`data.ts:2143-2189`, ~10 full building-list passes via 8 calls to `sumBy` at `data.ts:1929` plus a manual water loop plus `powerStats`) and `wellbeingOf` (`engine.ts:3696`), which itself calls `serviceCoverageOf` again. None of this is memoized (`data.ts` has no `useMemo`/cache anywhere).
- The ambient tick (`advance()`, `engine.ts:1010`) does the same `computeRoadConnectivity` recompute again unconditionally at `engine.ts:1079`, plus `computeFlows()` (`engine.ts:480`) calling `countByKindOnline` twice (`engine.ts:486,512`), `stationLinks` (`engine.ts:499`), and `powerStats` (`engine.ts:535`) — every tick, at whatever speed the player has selected (`store.tsx:479-485`).

At small city sizes this is invisible. At 68K it is O(buildings) times a double-digit multiplier of redundant full-city passes, run synchronously inside the same event-loop turn that has to acknowledge the mouse. The genesis-replay path already worked around a version of this cost — `genesisReplay.ts:44` sets `setReplayMode(true)` specifically to **skip** the per-action connectivity recompute during headless replay, with a comment calling the recompute "pure allocation churn" in a loop. That workaround exists only for the replay path; the interactive path pays the full cost on every click.

**Goal:** pointer interaction (drag, hover-preview, click-to-place) stays responsive regardless of city population, by moving the simulation's expensive work off the thread that owns rendering and input.

## 2. Architecture options

### Option A — Full sim in the worker
The reducer, the tick/`advance()` loop, and all derived selectors run inside a dedicated Web Worker. The worker owns the authoritative `SimState`. The main thread holds a **read-only mirror** for rendering (`MapView.tsx`, `RightDock.tsx`, `DemandDock.tsx`) and posts `Action`s to the worker instead of calling `dispatch` synchronously. The worker posts state updates (patches, see §3) back.

- **Responsiveness:** best possible — the main thread never runs `occupiedSet`, `computeRoadConnectivity`, `serviceCoverageOf`, or `advance()`. Pointer events are free to paint every frame.
- **Determinism safety:** high, *if* done correctly. The reducer is already a **pure function with no RNG** (grep across `engine.ts`/`genesisReplay.ts` finds `Math.random`/`seedrandom` only in GR#21 comments *forbidding* their use — e.g. `engine.ts:170,470,2183,2305,2373,2537,2854,3581`; `genesisReplay.ts:12,78,105,128`). A pure fold over a recorded `Action` log produces the same output regardless of which thread runs it, so worker-vs-main is not itself a determinism risk — unlike a design that had to smuggle a shared RNG cursor across the postMessage boundary.
- **Serialization cost:** the real risk. `SimState` (`webconsole/src/sim/types.ts:163-578`, ~108 top-level fields including the full `buildings[]` array) is large — a saved game is 1.77 MB raw before compression (`saveCodec.ts` comment, cites `lz-string` compressing to ~300 KB). `postMessage` performs a structured-clone **deep copy** of whatever is sent; sending the *whole* state every tick would trade one bottleneck for another. This must be solved with a patch protocol (§3), not a full-snapshot-per-tick protocol.
- **Replay/journal compatibility:** the journal already records the exact `Action` sequence consumed by the pure reducer (`journal.ts`; `genesisReplay.ts:40-54` replays `initialState()` + every journaled action through the same reducer). Moving the reducer into a worker doesn't change what gets journaled, only where it runs.
- **Implementation risk:** highest of the three — every call site that currently reads `state` synchronously off `useSim()` (MapView's placement-preview logic, both docks, any inline `wellbeingOf`/`powerStats` call in a component) has to be re-derived from the async mirror, and the previously-synchronous "does this tile fit" check for the placement cursor becomes either (a) predicted optimistically on the main thread from a cached slice, or (b) genuinely async. Also: **Workers do not have `localStorage`** (only `Window` exposes it) — the autosave interval (`store.tsx:399-420`) and `saveCodec.ts` currently write straight to `localStorage`, so a worker-resident state either round-trips a snapshot to main for persistence or the save path moves to `IndexedDB` (which workers can access). This is a real, non-cosmetic wrinkle, not an implementation detail — see §4.

### Option B — Offload only the heavy pure selectors
Keep the reducer and tick on the main thread; move `computeRoadConnectivity`, `serviceCoverageOf`, `occupiedSet`, `powerStats` to worker-executed pure functions, called asynchronously, with results cached and applied back to state.

- **Responsiveness:** does **not** fix the placement lag as reported. The `place` action handler (`engine.ts:2744-2793`) calls `occupiedSet` **synchronously as part of the fit-check**, on the main thread, before the placement can even be accepted or rejected — that's what blocks the cursor. Making `occupiedSet` itself run in a worker either makes placement asynchronous (a UX change bigger than it looks: "can I place here" no longer answers in the same tick) or requires keeping a second, cheap, main-thread-resident occupancy structure anyway, which duplicates state and reintroduces the determinism-hazard-by-duplication class of bug this project has been bitten by before (BUG-357's `{token}` class, BUG-356's structurally-deaf loops).
- **Determinism safety:** fine in isolation (these are pure functions), but splitting "authoritative state" across two owners (reducer on main, selector outputs computed elsewhere and merged back) creates a synchronization-order hazard that doesn't exist in Option A, where there's exactly one writer.
- **Serialization cost:** lower per message (a computed `Set`/coverage record instead of the whole state), but paid on **every** call site, and several selectors are called from multiple places per render (e.g. `powerStats` from `computeFlows`, `serviceCoverageOf`, and `RightDock.tsx:319` independently) — so message-passing overhead could exceed the savings unless call-sites are deduplicated first anyway.
- **Verdict:** worth doing as a *first, worker-free step* (dedupe + memoize the redundant selector calls — this alone removes several of the 10+ full-building-list passes per action) but it does not, on its own, solve the reported bug. Treated as a staging step under the recommendation below, not a standalone destination.

### Option C — Move only the tick/`advance()` loop to the worker
Keep the reducer (including `place`) on main; move the periodic `advance()` call (currently `setInterval`-driven, `store.tsx:479-485`) into the worker, with the worker producing a state delta on each tick that main applies.

- **Responsiveness:** partial. It removes `computeFlows()`'s three-plus full-city passes (`engine.ts:480-535`) and the monthly `evaluateRoadMonitors`/`evaluateBuildingMonitors` full scans from the main thread's background load, which reduces overall main-thread contention and should shrink the *baseline* frame-time jitter as population grows. But the specific defect Aaron reported — a **placement** click lagging 5s — is triggered by the `place` action's own synchronous `occupiedSet`/`computeRoadConnectivity` work, which stays on main thread under this option and is untouched.
- **Determinism safety:** same pure-reducer argument as A, but now the reducer itself has two invocation sites (main for user actions, worker for tick) that must interleave in the journal in the exact order they actually happened — an ordering hazard A doesn't have, since A has a single owner processing one queue.
- **Verdict:** a genuine partial win, useful as an intermediate landing, but insufficient as the destination architecture.

### Recommendation: **Option A, staged in incrementally starting from a de-duplication pass and Option C**

Go to full Option A as the destination, because it is the only option that removes the specific synchronous call (`occupiedSet` inside `place`) that produces the reported symptom, and because the reducer's existing purity/no-RNG design (already proven out for genesis replay) makes the determinism risk of "which thread" close to zero — the actual risk is entirely in the **message protocol** (§3) and the **save-path's `localStorage` worker restriction** (§4), both solvable with contained, reviewable changes. Land it in three stages so each is independently shippable and attackable (§6):

1. **Stage 0 (no worker, ships first, de-risks everything after it):** dedupe/memoize the redundant selector calls found in this audit — `powerStats` called 3×, `serviceCoverageOf`'s internal 8×`sumBy`, `computeFlows`'s double `countByKindOnline` — and stop the reducer from recomputing `computeRoadConnectivity` on every action when the changed buildings didn't affect connectivity. This is Option B's insight applied without a worker, purely as a same-thread cleanup, and should measurably reduce the lag on its own while adding zero serialization/architecture risk.
2. **Stage 1 (Option C):** move `advance()`/tick to the worker; main thread keeps the reducer for user-triggered actions (`place`, `bulldoze`, etc.) and applies worker-produced tick deltas. Proves the message protocol and worker lifecycle under real load without touching the placement path at all.
3. **Stage 2 (full Option A):** move the full reducer (including `place`) into the worker; main thread becomes a thin action-dispatcher + render-from-mirror. This is the stage that actually fixes the reported bug.

## 3. Message protocol

**Main → worker:**
- `{type: 'action', action: Action, clientSeq: number}` — every dispatched action (place, bulldoze, tick-speed-change, etc.), tagged with a monotonically increasing sequence number so main can correlate the worker's eventual ack/patch with the optimistic UI it already rendered.
- `{type: 'init', savepoint: Savepoint, journalTail: Action[]}` — sent once on worker startup (or on load-game) to seed worker-resident state without re-running the whole `replayFromGenesis` if a savepoint is available (mirrors today's `wireAndRehydrate`-style snapshot-first restore pattern used engine-side).

**Worker → main:**
- `{type: 'patch', appliedSeq: number, patch: StatePatch}` — **not** a full `SimState` clone. `StatePatch` is a small, explicit diff object: `{buildingsUpserted: Building[], buildingsRemoved: string[], flowsDelta?: FlowsSnapshot, roadConnectivityDelta?: ..., ledgerDelta?: ..., tick: number}`. Only fields that changed since the last patch are populated. This is the direct fix for the "sending 1.77MB every tick" risk identified in §2 — the worker already knows exactly what the reducer touched (it just ran it), so it can emit a targeted patch instead of forcing main to structured-clone the whole state to find out.
- `{type: 'queueDepth', pending: number, oldestPendingAgeMs: number}` — sent whenever the worker's action queue backlog changes. This directly surfaces the busy/lag indicator Aaron has asked for (an engine-lag readout): if `pending` grows or `oldestPendingAgeMs` climbs, the UI can show a "simulation is catching up" affordance instead of silently feeling laggy the way it does today.

**Optimistic UI reconciliation:** the placement cursor/preview is rendered from a **client-side prediction**, not from the worker's authoritative reply. Main thread keeps a cheap, approximate mirror of `occupiedSet` (rebuilt incrementally as `buildingsUpserted`/`buildingsRemoved` patches arrive, never recomputed from scratch) purely to answer "does the hovered tile look free" for the *preview*. The actual placement is optimistic: on click, main immediately renders the new building (assume success) and dispatches the action to the worker; if the worker's patch later reports the placement was rejected (e.g. a race where two rapid clicks target overlapping footprints), main reconciles by removing the optimistic building and showing a toast — the same "action failed after the fact" pattern already implicit in any client-predicted system, applied here for the first time in this codebase. This must be called out explicitly to Aaron (§7) since it is a genuine UX-visible behavior change (a placement can now flicker-and-revert under contention, which cannot happen in today's fully-synchronous model).

## 4. Determinism & save/replay

- **RNG:** none exists in the TS sim (§1) — nothing to synchronize across the thread boundary. This removes the single hardest problem this kind of migration usually has.
- **Tick/action order:** the worker must process `action` messages strictly in the order main sent them (JS `MessagePort` preserves message order for a single channel, so this holds automatically as long as there is exactly one channel/worker — do not shard across multiple workers without re-deriving an explicit ordering guarantee). The journal continues to record the same `Action` sequence it does today; **where** it's recorded is the one thing that changes; see next point.
- **Journal recording moves with the reducer.** Today `wrappedDispatch` (`store.tsx:339-399`) records the action to the journal as part of the same synchronous call that invokes `dispatch`. Once the reducer moves to the worker (Stage 2), the journal write must happen either (a) in the worker, with the worker periodically flushing the journal back to main for persistence, or (b) on main, recording the action optimistically **before** worker confirmation — option (b) is simpler and already matches the optimistic-UI model in §3, but means a worker-side action rejection must also retract the journal entry, which is new machinery. Recommend (a): the worker is the single source of truth for "what actually happened," so it should own the journal write; main's job is purely to relay the write to persistent storage.
- **`localStorage` is not available inside a Worker.** The autosave interval (`store.tsx:399-420`) and `saveCodec.ts`'s compress-and-write path currently assume main-thread `localStorage`. Once the worker owns state and journal, either (a) the worker posts periodic `{type: 'saveSnapshot', savepoint, journal}` messages back to main, which does the existing `saveCodec`/`localStorage` write unchanged, or (b) the save path migrates to `IndexedDB` (available from within a worker) and drops `localStorage` entirely. Recommend (a) for Stage 2 — it's the smaller diff and keeps GR#27's capture-before-wipe hook (which lives in the main-thread store reset path) working unchanged, since it never has to reach into the worker.
- **Byte-identical replay is verified the same way it is today:** `replayFromGenesis` (`genesisReplay.ts:40-54`) folds the recorded journal through the reducer and compares via `stableStringify` (`genesisReplay.ts:~80`). This continues to work unchanged whether the reducer's *live* execution happened on main or in a worker — replay itself can stay a main-thread (or worker) invocation of the same pure function against the same recorded actions. The acceptance test for this feature is precisely: **run the same journal once through the pre-migration main-thread reducer and once through the post-migration worker reducer; `stableStringify` output must be byte-identical.**

## 5. Acceptance criteria

Each is written to be able to FAIL — a criterion that cannot fail is not a criterion.

1. **AC-1 (responsiveness bar).** At a city with ≥68,000 population (or the largest available fixture/save), dragging the placement cursor across the map produces a visible preview update within **one animation frame under normal load, and never more than 100ms**, measured via `requestAnimationFrame` timestamp deltas from pointermove to the next paint, for 95% of samples over a 10-second drag. FAILS if p95 latency exceeds 100ms or any single sample exceeds 500ms.
2. **AC-2 (placement doesn't block input).** Clicking to place a building does not block subsequent `pointermove`/`mousemove` event handling — verified by dispatching a placement action and asserting that a synthetic pointermove event queued immediately after is handled within one frame, not after the placement's full reducer pass completes. FAILS if the pointermove handler is measurably delayed by the place action's processing time (today it is, by construction, since both run synchronously on one thread).
3. **AC-3 (determinism, worker vs main).** For a fixed journal (genesis + N actions, N ≥ 500, covering place/bulldoze/tick/save/load), replaying it through the pre-migration main-thread reducer and the post-migration worker-hosted reducer produces byte-identical `stableStringify` output. FAILS on any diff.
4. **AC-4 (save/load round-trip).** A game saved under the worker architecture loads correctly (state matches pre-save state after `replayFromGenesis`-equivalent verification) and a game saved under the **pre-migration** build still loads correctly post-migration (backward compatibility, matching the existing magic-prefix scheme in `saveCodec.ts`). FAILS if either direction fails to load or produces divergent state.
5. **AC-5 (genesis replay compatibility).** `replayFromGenesis` continues to produce a result matching the live-played state for the same journal, run through whichever thread now hosts the reducer. FAILS if replay diverges from live play.
6. **AC-6 (no visual regression).** All existing MapView/RightDock/DemandDock rendering (building sprites, coverage overlays, wellbeing readouts, flow figures) matches pre-migration output pixel-for-pixel (or value-for-value for numeric readouts) on a fixed test city, aside from any explicitly-approved optimistic-placement flicker (§3). FAILS on any unapproved visual diff.
7. **AC-7 (queue-depth / lag surfacing).** When the worker's action queue backlog exceeds a threshold (tunable, default suggestion: 3 pending ticks or 250ms oldest-pending age), the UI surfaces a visible "simulation catching up" indicator within one render cycle of the `queueDepth` message. FAILS if the indicator never appears under an artificially throttled worker (test harness can inject an artificial delay).
8. **AC-8 (Worker-unavailable fallback).** In an environment where `typeof Worker === 'undefined'` (or worker construction throws), the app falls back to running the reducer/tick synchronously on the main thread using the **same reducer module**, with no user-visible error and no loss of save/load/journal functionality — only the responsiveness improvement is absent. FAILS if the app fails to boot, or if the fallback path uses a forked/divergent copy of the reducer rather than the same module.
9. **AC-9 (optimistic-placement reconciliation).** When a worker rejects an optimistically-rendered placement (simulated via a forced-conflict test case — two placements targeting overlapping footprints in rapid succession), the UI retracts the optimistic building and surfaces a rejection notice within one patch cycle. FAILS if the optimistic building is left rendered permanently (a silent visual lie about state) or if the retraction corrupts the client-side occupancy mirror used for subsequent placement previews.
10. **AC-10 (GR#27 capture-before-wipe still fires).** A wipe/reset action still triggers the existing fail-closed debug capture (the hook currently lives in the main-thread store reset path) before any worker-resident state is discarded. FAILS if a reset can occur (e.g. via a race between a wipe action and an in-flight worker patch) without the capture having completed first.

## 6. Staging (incremental, independently shippable/attackable landings)

1. **Landing 1 — Stage 0, selector de-duplication (no worker).** Memoize/dedupe `powerStats`, `serviceCoverageOf`'s internal `sumBy` calls, `computeFlows`'s double `countByKindOnline`, and make the reducer's `computeRoadConnectivity` recompute conditional on whether the changed buildings actually affect connectivity (footprint/road-adjacency changed) rather than unconditional on any `buildings` mutation. Independently measurable (before/after frame-time at a fixed population), independently attackable (pure refactor, no behavior change — a destructive round can diff outputs against the un-memoized version).
2. **Landing 2 — worker scaffold + Stage 1 (tick-only offload).** Introduce the Worker, the message protocol (§3, tick-relevant subset only), move `advance()` there; main thread still owns `place`/`bulldoze`/user actions directly. Ships the queue-depth indicator (AC-7) here since it's needed regardless of which actions eventually move. Attackable in isolation: a destructive round can hammer tick-speed changes, save-during-tick races, and worker-crash/restart behavior without touching the placement path at all.
3. **Landing 3 — Stage 2, move the full reducer + journal ownership.** Move `place`/`bulldoze`/every remaining action into the worker; main becomes dispatch-and-render-from-mirror; journal recording moves to the worker per §4. This is the landing that closes AC-1/AC-2 (the actual reported bug) and AC-9 (optimistic reconciliation). Highest-risk landing — gets its own full GR#23 destructive round focused specifically on race conditions (rapid clicks, save-mid-action, wipe-mid-action per AC-10).
4. **Landing 4 — save-path migration.** Wire the worker→main `saveSnapshot` relay (§4) so autosave and manual save continue to work with the worker as state owner; verify AC-4/AC-5 exhaustively (old saves, new saves, cross-version loads). Kept separate from Landing 3 so a save-path regression doesn't block or get conflated with the reducer-migration regression surface.
5. **Landing 5 — fallback path + polish.** Implement and test AC-8 (no-Worker fallback), tune the AC-7 queue-depth thresholds against real dogfood telemetry, remove the now-redundant Stage-0 workarounds if Stage 2 has made them moot (e.g. confirm `genesisReplay.ts:44`'s `setReplayMode` skip-hack is still needed or can be simplified now that the live path also avoids the naive recompute).

Each landing should independently pass its own subset of the AC list above and get its own GR#23 destructive round — do not bundle Landings 2 and 3 into one PR; the tick-only and full-reducer moves have materially different risk profiles (Landing 2 cannot corrupt a user-initiated action since it doesn't touch that path; Landing 3 can).

## 7. Open questions for Aaron

1. **Is the AC-1 responsiveness bar (p95 ≤ 100ms, 95th-percentile over a 10s drag) the right number, or does he want something tighter/looser?** *Recommendation: accept 100ms as a first target — it's below the ~16ms-per-frame threshold most users perceive as "instant" only when hit consistently, so 100ms is already a generous but clearly-fixing-the-5s-bug bar; tighten later once telemetry from real dogfood sessions exists.*
2. **Is optimistic placement (AC-9's flicker-and-revert-on-conflict behavior) acceptable, or does he want placement to stay fully synchronous/blocking (i.e., wait for worker confirmation before rendering)?** *Recommendation: accept optimistic placement. A synchronous-wait model reintroduces exactly the perceived lag this feature exists to remove — the worker round-trip, even fast, is nonzero, and a "wait for the worker" placement model would just move the 5-second bug from "reducer computation" to "message round-trip + queue depth," not eliminate it. Conflicts (two placements racing on the same tile) should be rare enough in normal single-player use that the revert case is a corner case, not a common experience.*
3. **Does he want Landing 3 (full reducer in worker) built at all in the near term, or should the team stop at Landing 2 (tick-only offload) and re-evaluate whether that alone is "good enough"?** *Recommendation: Landing 2 alone will NOT fix the reported bug (§2, Option C verdict) — the `place` action's synchronous `occupiedSet` call is what blocks the cursor, and that call stays on main thread under Landing 2. If schedule pressure forces a stopping point, stopping at Landing 2 should be presented to Aaron explicitly as "the background tick lag is fixed, the placement-click lag is not," not silently declared done.*
4. **Journal-ownership model (§4): worker-owns-and-flushes vs. main-owns-optimistically-then-retracts-on-rejection.** *Recommendation: worker-owns (option (a) in §4) — simpler mental model (single source of truth for "what happened"), and avoids inventing a journal-retraction mechanism that doesn't exist anywhere else in the codebase today.*
5. **Save-path target: relay-to-main-`localStorage` (§4 option (a)) vs. migrate to `IndexedDB` accessed directly from the worker (§4 option (b))?** *Recommendation: relay-to-main for this feature's scope — it's a strictly smaller diff, and an IndexedDB migration is a separable concern (arguably its own FEAT) that shouldn't be coupled to unblocking the placement-lag bug.*
