## User stories

- **US-1.** As a transit line (bus or train), I need a unique route id and named, ordered stops — not an anonymous list — so the player (and the UI's live vehicle count) can address "the XZY2309 High Street → Train Station line" the way 'Blue' does.
- **US-2.** As the vehicle-allocation engine, I need a line to start with 1 vehicle and auto-allocate more per line from vehicles-available × line-length × waiting-demand, up to saturation — the point where more vehicles stop helping because the underlying road/rail capacity cannot carry more — so service scales to demand within real infrastructure limits instead of a fixed schedule.
- **US-3.** As the player watching the UI, I need the live vehicle count per line to be the honest output of that allocation (the saturation result), never a cosmetic number uncoupled from the allocation math.
- **US-4.** As code.json, I need the allocation's three inputs — waiting demand per stop (from `engine.traffic`), line capacity (from `engine.roads`/`engine.rail`), and available depot units (from `engine.rail`/a bus depot source) — to arrive through registered edges, and none of those edges exist yet for this feature's owning module.

## Scope

Line/stop identity (unique route id, named ordered stops); the deterministic vehicle auto-allocation model (start-at-1, scale by vehicles-available × line-length × waiting-demand, capped at infrastructure saturation); the saturation definition as the point where additional vehicles no longer raise effective service (bounded by line capacity and depot units). The three demand/capacity/fleet inputs are injected seams (AC-6) pending registered edges (AC-7, Escalations). User-agreed infrastructure expansion on saturation is `FEAT-162.md`'s scope, not this file's.

## Acceptance criteria

### Functional — line & stop identity

- **AC-1 (line identity — unique route id, Blue-style).** Every transit line carries a unique route id generated deterministically and non-colliding (e.g. the `XZY2309` form), distinct from any other line's id, with the id generation using `foundation.det` (no shared RNG, no map-iteration order). Check: `go doc ./internal/engine/transit` shows a `Line` type/accessor exposing `RouteID`; a passing test creates many lines and asserts every `RouteID` is unique within the run and deterministic across two runs with the same seed (`grep -rn "func Test.*[Rr]outeID\\|func Test.*[Ll]ineIdentity" internal/engine/transit/*_test.go`). **Lazy violation this rejects:** a build that assigns ids by a global incrementing counter would be unique-but-nondeterministic across runs; the cross-run determinism assertion rules it out.

- **AC-2 (named, ordered stops — the line is addressable, not anonymous).** Each line's stops are named and ordered (e.g. "001 High Street" → "200 Train Station"), so a line is a sequence of identifiable stops, not a bare geometry list. Check: `go doc ./internal/engine/transit` shows a stop type with both a name and a sequence index; a passing test asserts the stop order is preserved and each stop's name/index is queryable (`grep -rn "func Test.*[Nn]amedStops\\|func Test.*[Ss]topOrder" internal/engine/transit/*_test.go`).

### Functional — vehicle auto-allocation to saturation

- **AC-3 (start-at-1, scale to saturation — the core allocation rule).** A line starts with exactly 1 vehicle at creation; the allocation then scales vehicles from the three bound inputs (vehicles available × line length × waiting demand) and is CAPPED at saturation — adding a vehicle beyond saturation does not raise effective service because infrastructure capacity cannot carry it. Check: a passing test drives waiting-demand upward and asserts the allocated vehicle count rises from 1 toward the cap, then asserts that once the line-capacity or depot-units bound binds, further demand increase does NOT raise the allocated count (the saturation plateau) (`grep -rn "func Test.*[Aa]utoAllocat\\|func Test.*[Ss]aturationPlateau" internal/engine/transit/*_test.go`). **Lazy violation this rejects:** a build that always allocates `k × demand` with no capacity cap would satisfy "scales to demand" while missing the saturation definition the feature exists to encode — the plateau assertion is what catches it.

- **AC-4 (saturation is a function of the three documented bounds — integrated-transport §2's formula).** Effective service is `min(demand_target, line_capacity_paths_per_hour, depot_available_units / round_trip_cycle_hours)`, and saturation is the state where one of the three binds; the allocation exposes WHICH bound is binding (demand / line-capacity / depot), so the UI and FEAT-162's expansion proposal know what to propose. Check: `go doc ./internal/engine/transit` shows the three-input formula and a binding-cause query; a passing test constructs three fixtures each pinning a different bound and asserts the allocation reports the correct binding cause in each (`grep -rn "func Test.*[Bb]indingCause\\|func Test.*[Tt]hreeBounds" internal/engine/transit/*_test.go`). **Lazy violation this rejects:** a single blended "capacity" scalar would let all three collapse into one, so the check requires the three inputs to move independently and each to be reportable as the binding one.

- **AC-5 (GR#15; allocation parameters from data, not Go literals).** The start-vehicle count, the allocation coefficients (vehicles-available × line-length × demand weights), the round-trip-cycle denominator, and the saturation thresholds are loaded from `data/transit.json` — no player-felt balance number as a Go literal. Check: `grep -n "transit.json\\|TransitData" internal/engine/transit/*.go` shows the data-load path; `grep -rn "= [0-9]\\+ \\* .*demand\\|= [0-9]\\+ \\* .*length" internal/engine/transit/*.go` (a heuristic scan for an inline literal multiplying a demand/length term) finds no matches; a passing test asserts the start-vehicle count read from the data file is what a new line actually receives (`grep -rn "func Test.*[Ss]tartVehicle\\|func Test.*[Aa]llocParams" internal/engine/transit/*_test.go`).

- **AC-6 (GR#25 — demand/capacity/fleet inputs are injected seams pending registered edges; the algorithmic work is NOT blocked).** The three allocation inputs (waiting demand per stop, line capacity per hour, depot available units) arrive through Go interfaces (`DemandSource`, `LineCapacitySource`, `FleetSource` — or equivalent), not through direct imports of `engine.traffic`/`engine.roads`/`engine.rail`. This keeps the allocation algorithm testable in isolation today and re-wirable to the real edges when AC-7 lands. Check: `go doc ./internal/engine/transit` shows the three seam interfaces; `grep -rn "traffic\\.\\|roads\\.\\|rail\\.\\|engine/traffic\\|engine/roads\\|engine/rail" internal/engine/transit/*.go` (excluding `_test.go`) finds NO direct cross-package import — every input crosses a seam.

- **AC-7 (GR#25 — real cross-module edges, BLOCKED; edge-needed list).** The real wiring for AC-6's seams requires registered edges that DO NOT exist in code.json: (a) `engine.transit`→`engine.traffic` for waiting counts/demand per stop (traffic's outbound is world/solver/citizens/roads/invariant — no transit; and no consumer of traffic is `engine.transit`); (b) `engine.transit`→`engine.rail` for train depot units (rail's outbound is traffic/freight; rail has no transit consumer); (c) `engine.transit`→`engine.roads` for line geometry/road capacity (roads' outbound is world/foundation). This AC records the three module pairs + the call needed; it does NOT author prose describing a call this package makes today. **Tripwire (mechanical):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.transit'); process.exit(m?1:0)"` must exit **0** (module still unregistered) AND `node -e "const t=require('./code.json').modules.find(x=>x.key==='engine.traffic'); process.exit(t.inbound.consumers.some(c=>c.key==='engine.transit')?1:0)"` must exit **0** (no reverse edge). A nonzero exit means the module/edge has landed and AC-6's seams must be replaced with real calls before the next commit touching the package.

### Error handling

- **AC-8 (GR#7).** Allocating against an unregistered line, a negative waiting-demand input, or a zero/negative line-capacity input returns a registry-sourced error (new `MET-E`-range code) rather than silently clamping to zero vehicles or panicking. Check: `grep -n "MET-" internal/engine/transit/*.go` finds a registry code reference; passing test coverage asserts the error code matches AND no silent clamp occurred (`grep -rn "func Test.*[U]nregisteredLine\\|func Test.*[Ii]nvalidAllocInput" internal/engine/transit/*_test.go`).

- **AC-9 (GR#7).** A duplicate route id (a forced collision against an existing line) is rejected with a typed error, never silently re-keyed. Check: `grep -rn "func Test.*[Dd]uplicateRouteID" internal/engine/transit/*_test.go`.

### Determinism & safety

- **AC-10 (GR#21; allocation and id generation use `det.NewStream`).** Vehicle-allocation draws, route-id generation, and any tie-breaking use `det.NewStream(worldSeed, lineID, tick, purposeTag)` — no shared/global RNG, no `math/rand`, no map-iteration order feeding a result. Check: `grep -n "rand.New\\|math/rand\\"" internal/engine/transit/*.go` (excluding `_test.go`) finds no shared/global RNG source; `grep -rn "for .* := range" internal/engine/transit/*.go` shows no map-range feeding an allocation result without a prior `sort.`.

- **AC-11 (SG-7; GR#21).** `grep -rn "time.Now\\|time.Since" internal/engine/transit/*.go` (excluding `_test.go`) returns no matches — "hour"/"day" are simulation-tick concepts, never wall clock.

- **AC-12 (GR#21; determinism across worker counts).** Repeated runs from identical `(worldSeed, command log)` produce byte-identical allocations, route ids, and binding-cause reports across worker counts. Check: `grep -rn "func Test.*[Dd]eterminis" internal/engine/transit/*_test.go` finds the test asserting identical output across at least two worker counts.

- **AC-13.** `go test ./internal/engine/transit/... -race -count=1` passes; `grep -n "go func()" internal/engine/transit/*_test.go` finds at least one concurrency test (concurrent allocation across many lines).

### Documentation

- **AC-14.** `internal/engine/transit/doc.go` states the module key `engine.transit`, the start-at-1 scale-to-saturation rule (AC-3), the three-bound saturation formula and binding-cause query (AC-4), the injected-seam boundary (AC-6), and the AC-7 edge-needed list explicitly. Check: `grep -n "engine.transit" internal/engine/transit/doc.go` and `grep -n "saturation\\|allocat" internal/engine/transit/doc.go` and `grep -n "BUG-058\\|blocked\\|edge" internal/engine/transit/doc.go` all match.

## Out of scope

- `engine.traffic`'s own SUE assignment / mode-logit / commute-accounting machinery — this feature only consumes waiting-demand inputs through a seam (AC-6/AC-7).
- `engine.rail`'s own fleet/works accounting — this feature only consumes depot-unit inputs through a seam.
- `engine.roads`' own road identity/class/upgrade mechanics — this feature only consumes line geometry/capacity through a seam.
- User-agreed infrastructure expansion on saturation — `FEAT-162.md`'s scope; this feature only reports the saturation binding cause (AC-4) that FEAT-162's proposal reads.
- The exact allocation coefficients, start-vehicle count, round-trip-cycle denominator, and saturation thresholds — balance data in `data/transit.json`, pending M2 tuning (GR#15; balance-number regime).
