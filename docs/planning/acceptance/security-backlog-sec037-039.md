## Evidence standard binding on all three findings (non-negotiable, per the dispatch brief)

- **EV-1 (regression tests must be proven able to fail).** For every regression test claimed against these three findings, the Tester's evidence must include a run of that exact test **against the unfixed code** (the working tree with only this fix's diff hunk removed — the v1.5.1 "correct baseline" rule, not `HEAD`, since other uncommitted work may sit under this fix) showing it **fails**, plus a run against the fixed code showing it **passes**. A test with no demonstrated red run is a FAIL on that AC, full stop — this is the standing rule from "three drafts of one test measured 0/500 against known-buggy code before one bit," restated as a gate rather than a story.
- **EV-2 (the PoC is the floor, not the whole test).** Each finding already has a Destructive-agent PoC at `internal/harness/replay/destructive_poc_test.go` (SEC-037/038) or `internal/ui/screens/map/destructive_poc_test.go` (SEC-039). The regression test for that finding must supersede or absorb the PoC (same repro shape, now asserting the fixed behaviour) — a fix is not "done" while the PoC file still demonstrates the bug and a separately-named test demonstrates the fix side by side; that is two tests disagreeing about the current state of the code, which is a FAIL by itself (Tester must actively check for this, not just run both green).
- **EV-3 (negative-result regressions are equally mandatory, not optional extras).** Weakness pattern #6 was explicit that what resisted attack must be recorded so a later fix cannot quietly remove it. The three controls below are each already confirmed correct by the Destructive agent; every one gets its own passing regression test in this same wave, run **before and after** the fix diff to prove the fix did not touch them:
  1. `serialize`'s `ReadShard`/`Load` SHA256 + `ByteSize` digest check (fixture.go:206-218) — must still reject a tampered or truncated shard exactly as today.
  2. `serialize.ValidateShardName`'s traversal/absolute-path/UNC/drive-marker/trailing-dot-or-space/Windows-device-name defences — must still reject every one of those forms.
  3. `limits.go`'s `maxGridSide`/`maxGridCells` derivation and the per-dimension-before-product overflow guard in `applyFullLocked` (screen.go:196-212) — must still reject an oversized `Extent` and must still be provably overflow-free at the boundary (`maxGridSide*maxGridSide <= maxGridCells` for `int`).
  A PASS that is silent about these three is incomplete, per EV-3 — cite the passing test names for each in the Tester's report, not just "no regressions observed."
- **EV-4 (GR#15 — limit derivation, not a chosen number).** Anywhere this wave introduces a numeric bound (SEC-038's decompression cap, SEC-039's wire-size/cell-count cap), the acceptance criteria below require the derivation to be **written down in the same place `limits.go`'s `maxGridBudgetBytes` derivation is written** (a comment naming the spec source or measured population, the arithmetic, and — this is the SEC-033 lesson the dispatch brief named explicitly — **which population the number was measured against and why that population is still the right one today**). A bound with no cited population, or one whose population is going stale (e.g. hardcoded against today's Folkestone-64 fixture size with no note that a later, bigger tile will need it re-derived), is an incomplete AC, not a style nit.

## SEC-037 — `replay.Save` silently drops all records for a struct-copied `*Recorder`

### What a correct fix looks like vs. what merely silences the symptom

A fix that adds `if len(rec.Records()) == 0 { return err }` (or equivalent) inside `Save` is a **FAIL**, even though it stops the exact PoC. It cannot distinguish "the Recorder was rejected as a copy" from "the Recorder legitimately captured zero records" (an empty session is a real, valid case per this package's own doc comments — nothing says a Recorder must have observed at least one record). A fix collapsing both into "Save now errors on zero records" trades silent data loss for a **false rejection of a legitimate empty capture**, which is a new, different defect, not a fix. Correctness requires the *source* of the ambiguity — `Recorder.Records()` (record.go:138-150) returning a bare `nil` for both "copy" and "empty" — to stop being ambiguous.

- **AC-1 (the ambiguity is resolved at source, not shadowed at the call site).** `Recorder`'s copy-rejection and its "legitimately empty" case are observable as two distinct outcomes through its public API — e.g. `Records()` gains an `error` return (breaking-but-honest), or a new exported predicate (`r.Rejected(correlationID) error` / equivalent) that `Save` and every other caller can check before trusting a `nil`/empty result. Whichever shape is chosen, it must be impossible for a caller who calls the guarded accessor and checks its full return set to still receive an ambiguous "empty" for both cases — mirrors Weakness pattern #6's rule ("make the rejection impossible to confuse with a normal result; an error return is usually the honest shape") and pattern #1 ("an invariant matters only if the API makes violating it impossible or loud"). Check: `go doc` on the changed signature states both cases explicitly; a unit test calls the accessor on (a) a copied Recorder and (b) a genuinely empty, never-copied Recorder and asserts the two are **distinguishable by return value alone**, no reliance on any side channel (log line, `errs` ring) to tell them apart.
- **AC-2 (`Save` uses the resolved signal and fails loudly on rejection).** `Save` calls the AC-1 accessor, and when it reports "rejected copy," `Save` returns a **non-nil, registry-sourced error** (new code in the `H000-H099` range this package already owns — see `internal/harness/replay/errors.go`) and writes **no file at all** (neither the `.ndjson.gz` shard nor the `.header.json` sidecar) — a partially-written fixture is a worse failure mode than today's fully-written-but-empty one, so this is not merely "add a check," it is "add a check that also does not leave a half-valid artifact on disk." Check: `TestSave_RejectsCopiedRecorder` (superseding the current PoC per EV-2) asserts `Save` returns a non-nil error whose registry code is the new one, and that `os.Stat` on both the would-be shard and header paths returns `os.ErrNotExist` afterward.
- **AC-3 (a genuinely empty, uncopied Recorder still saves successfully).** `Save(dir, name, rec, meta)` on a `Recorder` obtained fresh from `NewRecorder()` with zero `Observe*` calls still succeeds today's way: valid gzip+SHA256+header fixture, `nil` error, `Load()` round-trips it with `len(Records) == 0`. This is the criterion that catches the "reject on zero records" false-fix described above. Check: `TestSave_GenuinelyEmptyRecorderStillSucceeds` (new, not previously covered — the existing suite apparently never exercised the zero-record-but-valid case explicitly, which is itself part of why SEC-037 went unnoticed) passes both before and after this fix (it is not a regression test for the bug, it is a guard against the wrong fix, so its "before" run should already be green — if it is not, that is a separate, existing gap the Tester must report, not silently fix).
- **AC-4 (GR#18 sibling audit, done as source and reported as a check, not a promise).** Every package-level function or exported method anywhere in the repo that receives a value of one of the copy-guarded types (`*Recorder`, `*EnginePlayer` in this package; the full SEC-020 type list elsewhere) **as a parameter rather than as its own receiver** is enumerated and checked for the same "guard exists upstream but the caller doesn't use its full signal" shape. Weakness pattern #6's own §"argument position is the blind spot" is explicit that this class of bug hides from method-shaped sweeps — `Save(dir, name, rec *Recorder, meta)` was found *because* an agent was told to look for exactly this shape, not by the nine prior manual passes. Check: the enumeration method is stated in the commit (e.g. `grep -rn "\*Recorder\b" internal/ --include=*.go | grep -v _test.go | grep -v "func (r \*Recorder)"`, or better, an AST-based pass reusing `tool.astgate`'s machinery if it already does something structurally similar) and its output, with a disposition (fixed / already-safe / N/A) for each hit, is either in the commit message or a `docs/design/` note — "we grepped and found nothing else" is an acceptable outcome **only if the grep/AST command used is stated**, so a reviewer can judge its recall, not just trust the conclusion.
- **AC-5 (`Recorder.Len()` is a declared sibling, not an oversight).** `Len()` (record.go:152-164) has the **identical** nil/copy-vs-empty collapse as `Records()` — both are guarded accessors returning a bare zero-value on rejection today, `Len()` just returns `0` instead of `nil`. The dispatch brief's wording ("audit all sibling *callers*") could be read narrowly as "other call sites of `Save`" — this criterion states explicitly that "sibling" must be read at the **method** level too: `Len()` is fixed by the same AC-1 mechanism (or explicitly documented as an accepted, logged exception if the team decides `Len()`'s zero-vs-zero ambiguity is lower-stakes — see Escalations, this is exactly the kind of call that must be an `ASM-`, not a silent choice). Check: `Len()`'s new behaviour is exercised by an AC-1-shaped test analogous to `Records()`'s.

### Where this disagrees with the brief

Bill's brief already gets the core call right (fix `Records()`'s ambiguity, not `Save`'s check) — no disagreement there. Two gaps: (1) "audit all sibling callers" reads as callers of `Save`/`Records()`, and the actual sibling that needed naming is `Len()`, a second accessor with the identical collapse that has zero current callers in production code but is exported and will accumulate them (AC-5) — the brief should have named it directly rather than leaving it to be found by "sibling" being read broadly. (2) The brief does not say what `Save` must do to the filesystem on rejection — AC-2's "no partially-written fixture" requirement is new; a fix that returns an error but still leaves an empty `.ndjson.gz`+`.header.json` pair on disk (because it wrote the shard before checking) would technically satisfy "Save returns an error" while still leaving exactly the kind of "looks valid, isn't" artifact SEC-037 is about — this needed to be explicit, not implied.

## SEC-038 — `harness.replay` `Load()` / `serialize.ReadShard` unbounded gzip decompression

### What a correct fix looks like vs. what merely silences the symptom

A fix that decompresses fully, counts the resulting bytes, and rejects **after** decompression completes stops nothing — it still pays the full memory/CPU cost the attack exploits, then reports an error. That is symptom-silencing dressed as a fix: the repro's own numbers (65KB on disk forcing 67MB resident) show the cost is paid at decompression time, so the bound must act **during** decompression, not on its output.

- **AC-6 (the bound is enforced during decompression, not after).** The read path (`serialize.NDJSONSerializer.ReadShard`, or a wrapper it or `fixture.Load` installs around the `gzip.Reader`) is bounded by an `io.LimitReader` (or equivalent incremental byte-counting that aborts the read loop) applied to the **decompressed** stream, so that a shard whose decompressed size would exceed the bound is rejected **before** the last of it is read into memory — not merely before `Load` returns. Check: a regression test forges a fixture whose decompressed size is, say, 4x the configured bound using a small on-disk shard (mirroring the PoC's ~1028x ratio, so the disk file stays trivially small), and asserts both that `Load`/`ReadShard` returns a non-nil, registry-sourced error, AND (EV-4-style, quantified, not just "it returned an error") that peak process memory or total bytes read from the reader across the call is bounded near the configured limit — e.g. via a counting wrapper the test itself installs beneath the `LimitReader`, asserting the wrapper's cumulative `Read` byte count never exceeds `limit + one buffer's worth of overrun`, not "close to 67MB" per the unfixed repro.
- **AC-7 (the bound value is derived and its population is named — EV-4).** The limit constant lives beside a derivation comment in the same style as `limits.go`'s `maxGridBudgetBytes` (spec source or measured population, arithmetic, units) — not a bare `const maxDecompressedBytes = 64 << 20` with no comment. **This is the criterion carrying the SEC-033 lesson named in the dispatch brief**: SEC-033 shipped a bound derived from the wrong population and went stale. This package has (at least) two legitimately different populations reading through `serialize.ReadShard` today or foreseeably: `harness.replay` fixtures (small, bounded by test/CI needs) and — reading `data/errors.json`'s `F300-F399` range comment ("save/fixture format") and `foundation.serialize`'s own doc comment — **saves**, which this codebase's own architecture expects to be much larger (world state, not a short command/event/delta capture). A single hardcoded ceiling picked to comfortably fit a fixture and silently applied to a save load (or vice versa) is exactly SEC-033's shape one level up. Check (this is the substantive AC, not paperwork): the limit is either (a) a parameter the caller supplies per its own population (`fixture.Load` passing a fixture-sized bound, any future save-loader passing a save-sized bound) rather than a single package-level constant in `foundation.serialize`, or (b) if a single shared constant is kept, the commit states explicitly which population it was derived from, why that population currently bounds every current caller (a check of every current call site of `ReadShard`/`Load`, similar in spirit to AC-4's sibling sweep), and what breaks and how it will be caught (not just "we hope someone remembers") the day a caller with a legitimately bigger payload is added. A comment merely asserting a number with no population or re-derivation trigger is an incomplete AC.
- **AC-8 (rejection is loud and registry-sourced, never a silent truncation).** Exceeding the bound produces a **new** registry error code (claimed in this package's already-owned `H000-H099` range, or `foundation.serialize`'s `F300-F399` range if the check lands there instead — whichever module AC-7 puts the check in owns the code) naming the fixture/shard and the limit that was exceeded — never a truncated-but-silently-accepted partial read (that would produce a `Fixture`/decoded result that looks valid but is missing data, which is SEC-037's exact failure shape recurring one layer down). Check: the forged-oversized-fixture test from AC-6 asserts the specific new error code, not just `err != nil`.
- **AC-9 (must-not-regress — restated from EV-3 for this finding specifically).** The existing SHA256/`ByteSize` digest check (fixture.go:206-218) still runs and still catches tampering/truncation on any shard that passes the new size bound — i.e. the new limit is an **additional** gate ahead of the existing one, not a replacement for it, and a shard that is undersized-but-corrupted must still be caught by the digest check exactly as today. Check: the existing tamper/truncation tests (wherever they live today) are re-run post-fix and still pass, cited by name in the Tester's report per EV-3.

### Where this disagrees with the brief

The brief says "bound it, limit derived not magic (GR#15), registry-sourced error on exceed" — correct as far as it goes, but it does not raise the population question at all, and population is the entire content of the SEC-033 lesson it cites by name. "Derived, not magic" is necessary but not sufficient — a number can be derived (arithmetic shown, cited source) and *still* be derived from the wrong population, which is precisely what happened to SEC-033. AC-7 is where I depart from a literal reading of the brief: I require the fix to either scope the bound per-caller or explicitly justify a single shared bound against every current caller's population, not just show its arithmetic. I'd flag this to Bill directly if I could: this is the one place across all three findings where "follow the brief" and "follow the process rule the brief itself cites" are not obviously the same thing, and it's worth the junior/Tester explicitly confirming which reading was built before this lands.

## SEC-039 — `map.ApplyPatch` / `decodeWirePatch`: the SEC-009 clamp bounds the derived grid, not the incoming wire payload

### What a correct fix looks like vs. what merely silences the symptom

A fix that adds `if len(p.Cells) > maxGridCells { reject }` **after** `decodeWirePatch` returns, inside `applyFullLocked`, stops the PoC's 300,000-cell iteration — but the PoC's own measured cost (1.43s, 198MB of wire JSON) is dominated by `json.Unmarshal` inside `decodeWirePatch` fully decoding every one of those 300,000 `wireCell` entries (each with three string fields) into Go structs **before** `ApplyPatch` or `applyFullLocked` ever sees a `Cells` length to check. A check placed after decode is the same mistake SEC-039 itself is a report of, one call frame further in: it bounds a value derived from the expensive step, not the expensive step's input. This must be flagged clearly because the brief's own wording ("reject a patch whose `len(p.Cells)` exceeds... before the per-cell loop runs") describes exactly this insufficient fix.

- **AC-10 (the wire payload's byte size is bounded before `json.Unmarshal` ever runs).** `ApplyPatch(raw json.RawMessage)` checks `len(raw)` against a derived byte budget **before** calling `decodeWirePatch` — the cheapest possible check, on data already fully in memory as `raw` by the time `ApplyPatch` receives it (so this AC does not claim to protect against the transport/protocol layer handing the screen an oversized buffer in the first place — see Out of scope), but it stops this package's own most expensive step, the full JSON unmarshal, from ever running on a payload past the budget. Check: a regression test constructs a `raw json.RawMessage` whose byte length exceeds the configured budget (reusing the PoC's ~198MB shape, or a smaller multiple of the real budget so the test itself stays fast) and asserts `ApplyPatch` returns/logs the malformed-patch path **without** `decodeWirePatch`'s `json.Unmarshal` having run — provable via a wrapper/instrumentation point (e.g. a package-level counter incremented inside `decodeWirePatch`, gated behind a test build tag or exported only to `_test.go` files) or, at minimum, a benchmark-style timing assertion showing the rejection path's cost does not scale with the oversized payload's size the way the PoC's 1.43s did.
- **AC-11 (the decoded `Cells` length is also bounded, as defense in depth — the brief's fix, kept as a second layer, not the only layer).** After AC-10's byte-size gate, `applyFullLocked` (or `decodeWirePatch` itself) still rejects a patch whose `len(p.Cells)` exceeds `maxGridCells` (or the patch's own declared `w*h`, whichever this AC's implementer justifies as tighter and still correct for legitimate sparse-inside-full patches) **before** the `for _, c := range p.Cells` loop runs — this is the check the brief specified, and it is still required, just not sufficient on its own. Check: a variant of the PoC where `len(raw)` is kept just under AC-10's byte budget (so it passes AC-10) but `p.Cells` is still padded past `maxGridCells` with minimal-size entries — asserts rejection here too, and that the existing `errExtentTooLarge`-style malformed-patch logging path is reused rather than a parallel, differently-shaped error being invented (consistency with `screen.go`'s existing malformed-patch posture, per Weakness pattern #3's "fix the class" framing applied to error-shape consistency, not just the vulnerability class).
- **AC-12 (the byte budget is derived and its population named — EV-4/GR#15, mirroring `limits.go`'s own existing pattern).** `maxGridBudgetBytes`/`maxGridSide`/`maxGridCells` already model the derivation style expected here (spec citation, arithmetic, explicit "headroom vs. today's real fixture" comparison) — the new wire-byte budget for `ApplyPatch`'s raw payload must be derived the same way, in `limits.go`, sitting alongside the existing constants rather than as a bare literal in `screen.go`. Its derivation is necessarily a **different** population than `maxGridBudgetBytes` (that one bounds the *decoded, deduplicated* grid slab; this one bounds the *wire, redundant, string-heavy* JSON payload, which for the same logical grid can be far larger per cell than `cellData`'s packed struct size) — the commit must show the arithmetic connecting the two (e.g. worst-case bytes-per-`wireCell`-entry on the wire × a cell-count ceiling, with the string-field sizes either bounded separately or assumed-worst-case and cited) rather than reusing `maxGridBudgetBytes`'s number under a new name. Check: `limits.go`'s new constant has a derivation comment in the same shape as the existing ones; a reviewer can recompute the number from the comment's own inputs.
- **AC-13 (must-not-regress — SEC-009's existing clamp, restated from EV-3 for this finding specifically).** `applyFullLocked`'s existing per-dimension-then-product `Extent` clamp (screen.go:196-212) and `limits.go`'s `maxGridSide = floor(sqrt(maxGridCells))` overflow-safety property are unchanged in behaviour and still pass their existing tests after this fix lands — this fix adds a gate **before** SEC-009's, it does not touch or replace SEC-009's own logic. Check: existing SEC-009 tests re-run post-fix, cited by name per EV-3.

### Where this disagrees with the brief

This is the strongest disagreement of the three. The brief's stated fix — "reject a patch whose `len(p.Cells)` exceeds `maxGridCells`... BEFORE the per-cell loop runs" — is Weakness pattern #6 applied incompletely: it bounds the *output of decode* (the `Cells` slice length) rather than the *input to decode* (the raw wire bytes `json.Unmarshal` is about to walk). The PoC's own reported cost (1.43s, 198MB) is spent inside `json.Unmarshal`, which finishes and returns a fully-populated `wirePatch` *before* `len(p.Cells)` is ever available to check against anything — so a literal build of the brief stops the render-loop iteration cost the finding's "impact" paragraph worries about (CPU exhaustion via repeated floods) but does not stop the allocation/parse cost of a single oversized patch, which is itself a resource-exhaustion vector (a handful of 200MB patches, not a flood, would still force full unmarshal each time). AC-10 is the fix I believe is actually required to close the finding as described; AC-11 keeps the brief's check as a real, useful second layer rather than discarding it. I'd want Bill to confirm explicitly whether Junior-6 was told about the byte-level gate or only the `Cells`-length one before this is called done — if only the latter, the finding is not closed, it is narrowed.

## Out of scope (all three findings)

- Any change to `internal/protocol`'s transport/message-framing layer, even though a hostile 198MB single message is also, at a different layer, a transport-level concern — these three findings and this file are scoped to the receiving package's own defences (`harness.replay`, `foundation.serialize`, `ui.screens.map`), not to adding an upstream frame-size cap in `internal/protocol`. If Bill wants that too, it needs its own BOW item and its own criteria — noting it here so it is a decision, not a gap nobody named (Weakness pattern #3's "log it as an assumption naming what you left" applied to a BA-level scoping choice).
- Redesigning `Recorder`'s or `EnginePlayer`'s public API beyond what AC-1 requires (e.g. this file does not mandate a particular Go idiom — `(T, error)`, a second predicate method, a sum-type-style result — only that the two cases become distinguishable through the API).
- Any new decompression/parsing library swap (e.g. a streaming JSON decoder to replace `json.Unmarshal` for SEC-039) — AC-10's byte-size gate ahead of `Unmarshal` is the required minimum; a streaming rewrite is a legitimate future improvement but not required to satisfy these criteria.
