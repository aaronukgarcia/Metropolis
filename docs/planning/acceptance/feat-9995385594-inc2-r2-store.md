## Scope

A second `persist.Store` implementation speaking the S3 API (Cloudflare R2 primary), and the three format changes it needs on every Store: multi-part snapshots, journal record v2 with group commit and segments, and writer-epoch fencing. Out of scope: the SIGTERM/hibernate trigger itself (D2, BUG-1197), the snapshot cadence policy (inc3), the launcher (Q100164), the browser reconnect and `server.waking` protocol (a2 s2.1), the Cloudflare Tunnel set-up (Q100160), and zstd (Q100156, only if the wake measurement misses). The Store does not learn what a citizen is: part bodies are opaque to it, and the SoA codec (AC-S section) lives on the citizens side, not in persist (ASM-1613, review 2026-11-17).

**North-star vetting:** not player-facing; it is infrastructure that makes the wake budget (Q100153) and Spot reclaim (Q100163) possible. Stated explicitly per the process.

**Naming.** Errors below are written `E-<NAME>`: each is a registry code claimed through `tools/plan/add-error.js` (claim-range, add, check) with the number pre-assigned by the lead in the dev brief (parallel lanes collide otherwise). The reservation owner is the module key (`int.persist`, or `engine.citizens` for codec codes), never `FEAT-9995385594`: a FEAT-/BUG- owner passes the Node check but reddens the Go scanner. **Timing in tests (review 2026-11-17).** Every duration in sections A to F (`P-batch-ms`, `P-orphan-age`, `P-retain-days`, retry backoff) is driven by an injected clock or fake timer in tests. ## Object layout (the contract the ACs refer to; a2 s1.3/1.4, design s4.4)

```
<tenant>/<city>/manifest.json                 city manifest: epoch, latestSnapshot, commitSeq   (CAS, If-Match)
<tenant>/<city>/journal/head.json             {epoch, seq}                                       (CAS, If-Match)
<tenant>/<city>/journal/<epoch>-<firstSeq>/<seq>.blk   immutable batch objects; <seq> = first seq in the batch   (If-None-Match:*)
<tenant>/<city>/snapshot/<id>/manifest.json   SnapshotManifest, immutable                        (If-None-Match:*)
<tenant>/<city>/snapshot/<id>/<part>          immutable parts
```
Tenant and city path segments are `encodeSegment`-style hashes or an equivalently traversal-proof encoding (see AC-X3). Sidecars (world seed, game mode, mode epoch) keep their existing semantics under `<tenant>/<city>/`. Every numeric key segment (`<epoch>`, `<firstSeq>`, `<seq>`) is zero-padded to 20 decimal digits so a LIST's lexical order equals numeric order (ASM-1612); a test lists epochs 9 and 10 and seqs 9 and 10 and asserts numeric order.

## A. Store contract and the S3 implementation (AC-A)

- **AC-A1.** Given `internal/persist`, when the package builds, then a new `S3Store` (name is the builder's) satisfies the `Store` interface, and `store_conformance_test.go`'s `runStoreConformance` is run against it by a third test (`TestS3StoreConformance`) with no case skipped or special-cased for it. (a2 s1.3; Q100159)
- **AC-A2.** Given the conformance suite, when it runs against `S3Store`, then the backend is an in-process fake S3 server (httptest) that enforces If-Match and If-None-Match with real ETag semantics, so the suite needs no network and no credentials. A second, build-tagged live suite (`-tags r2live`) runs the same suite against a real bucket only when the endpoint env vars are set, and is never part of CI. (ASM-1553)
- **AC-A3.** Given the fake S3 server, when its conditional-write enforcement is switched off, then the fencing tests of section F fail (proof the tests can fail; per verification standards).
- **AC-A4.** Given config (endpoint URL, bucket, region, access key id, secret, path-style flag, optional key prefix), when `S3Store` opens, then it reads them only from a typed config struct populated from environment or `*_FILE` secret paths; no provider-specific constant (no `r2.cloudflarestorage.com` literal) appears in non-test code. A test points it at a non-R2 endpoint and passes. (Q100159 "stays S3-portable"; ASM-1575)
- **AC-A5.** *[Amended 2026-11-17, Q-3 RULED]* Given `go.mod`, when the change lands, then the only new direct dependency is `github.com/minio/minio-go/v7` (or `aws-sdk-go-v2`'s S3 module if ASM-1611's conditional-header check fails), pinned to an exact version, approved by Aaron under GR#10 in A2Bev001 v23.3; its transitive additions are listed in the commit body. The library is imported in exactly one file (or one persist-owned sub-package) that implements a narrow internal interface (get, head, conditional put with If-Match / If-None-Match, list with start-after, delete); every other persist file uses only that interface, and a compile-time assertion plus a second, in-memory implementation of the interface prove the swap point. There is no hand-rolled request signing anywhere in the repo. No Azure module is imported anywhere, and `go list -deps ./internal/persist/` contains no `azure` path. (a2 s1.3; ASM-1611)
- **AC-A6.** Given the first open of a city for writing, when the capability probe runs (two create-only PUTs to a probe key unique to this probe, for example `<tenant>/<city>/probe/<random 128-bit hex>`, then one If-Match with a wrong ETag, then a best-effort delete of the probe key; *[amended 2026-11-17: a fixed probe key would make every reopen fail its first create-only PUT]*), then a backend that accepts the second create-only PUT or the wrong-ETag PUT makes `Open` fail closed with `E-COND-WRITE-UNSUPPORTED`, naming the endpoint host (never the credentials), and writes nothing else. A read-only open (restore for inspection) skips the probe. (a3 s2 "to verify per provider"; ASM-1553)
- **AC-A7.** Given a transient 5xx, 429 or network error on any request, when the call is idempotent (GET, HEAD, create-only PUT with the same body, DELETE), then it retries with bounded exponential backoff and jitter up to `P-retries` (default 5) and respects `ctx` cancellation; a non-idempotent step (the head CAS) is retried only after re-reading the ETag, never blindly. On exhaustion it returns a registry error carrying the HTTP status class. *[Amended 2026-11-17, ASM-1617]* Lost-response cases are defined and tested with a fake that applies a write and then drops the response: (a) a retried create-only PUT that gets 412 is success if and only if the stored object's checksum equals the body sent, otherwise `E-JOURNAL-CORRUPT` (batch) or a part error; (b) a head CAS whose response was lost is resolved by re-reading `head.json`: a value equal to the one written (same epoch and seq) is success, a higher epoch is `E-WRITER-FENCED`, anything else is retried from the fresh ETag. Backoff uses the injected clock and every retry stops at `ctx` deadline.
- **AC-A8.** Given `ctx` cancelled mid-request, when any Store method is running, then it returns once `ctx` is done without waiting for the blocked request (tested with a fake that never answers; the test's own timeout is a hang guard, not a timing assertion) with the ctx error wrapped in a registry error, and leaves no partially visible state (orphans only, per AC-B6).
- **AC-A9.** *[Amended 2026-11-17: the original was not testable; it asked for a stale-listing fake and then a strongly consistent one.]* Given the restore path, when it lists journal objects, then the list is bounded to segments at or after the snapshot's `JournalSegment` (start-after, ASM-1612), and the seqs found must be dense from `JournalSeq + 1` up to `head.seq`. Given a fake whose LIST omits a batch object that `head.seq` says exists (stale listing), when restore runs, then it fails closed with `E-JOURNAL-CORRUPT` naming the missing seq range and replays nothing past the gap; it never silently restores a prefix. Eventually-consistent backends stay unsupported (ASM-1554) and the runbook says so. (ASM-1554)
- **AC-A10.** Given `Exists`, `ListCities`, seed/game-mode/epoch sidecars, when run on `S3Store`, then they pass the existing conformance cases, including "stamping a seed alone does not make a city exist" and `SetWorldSeedIfAbsent` first-writer-wins via If-None-Match:* under 16 concurrent callers.

## B. Multi-part snapshots (AC-B)

- **AC-B1.** Given the Store interface, when this item lands, then every implementation (DiskStore, MemStore, S3Store) provides `BeginSnapshot(ctx, city, tick) (SnapshotWriter, error)` with `PutPart(ctx, name, io.Reader)`, `Commit(ctx, SnapshotManifest) (SnapshotID, error)`, `Abort(ctx)`, and `OpenSnapshot(ctx, city, id) (SnapshotReader, error)` with `Manifest()` and `OpenPart(ctx, name) (io.ReadCloser, error)`, and all three pass the same new conformance cases below. `PutSnapshot`/`GetSnapshot` stay and keep their current tests unchanged. Every other in-repo `Store` implementation or wrapper keeps compiling and behaving: the test doubles in `compose/snapshot_test.go`, `compose/attack_bug480_restart_test.go`, `cmd/metroserve/attack_inc3b_test.go`, and the production wrapper `rehydrateGuardStore` (AC-W2). (a2 s1.3; ASM-1567)
- **AC-B2.** Given a committed snapshot, when `Manifest()` is read, then it carries `Tick`, `JournalSegment`, `JournalSeq` (the exact position covered), `Epoch`, `Format` (`"soa-v1+gzip"`, `"ndjson+gzip"` or `"zip"`), `CreatedAtUnix` (ASM-1557) and `Parts` as an ordered list of `{name, size, sha256, rawSha256}`; JSON field names are fixed by a golden test, and unknown future fields are ignored on read. (a2 s1.3; ASM-1559)
- **AC-B3.** Given 256 parts of random bytes written concurrently with `P-upload-concurrency` (default 8, ASM-1562), when `Commit` is called, then `OpenPart` for each name returns exactly the bytes written, `Manifest().Parts[i].sha256` equals the SHA-256 of what was stored, and a reader opening any part checks size and sha256 while streaming and returns `E-PART-CORRUPT` on mismatch at EOF (never a silent short read).
- **AC-B4.** Given `PutPart` called with the same part name twice in one writer, when the second call starts, then it fails with a registry error (parts are immutable within a snapshot) and the first stays intact.
- **AC-B5.** Given a `Commit` whose manifest lists a part that was never put, or a put part not listed, when committed, then it fails with `E-MANIFEST-PARTS-MISMATCH` and nothing becomes visible.
- **AC-B6.** Given a crash (writer abandoned, process killed in a test by dropping the writer) after N of 256 parts and before `Commit`, when `ListSnapshots`, `OpenSnapshot` and restore run, then the orphan parts are invisible: `ListSnapshots` does not list the id, `OpenSnapshot` returns not-found, and restore selects the previous snapshot. (a2 s1.3 "orphan parts invisible")
- **AC-B7.** Given orphan parts older than `P-orphan-age` (default 24 h, judged by the backend's object last-modified time against an injected clock; never `time.Now()` inside the logic) with no committed manifest, when `SweepOrphans(ctx, city)` runs (also called once at writer acquire), then they are deleted; parts of an in-progress writer younger than the age, and any committed snapshot, are never deleted. A sweep never deletes under a prefix belonging to another city. (a2 s1.3 "a sweeper deletes"; nothing outside project temp is deleted without a gate: this is runtime deletion of the store's own data, not a tool action)
- **AC-B8.** Given `Abort`, when called, then uploaded parts are removed best-effort, `Abort` after `Commit` is a no-op returning nil, and `Abort` twice is nil.
- **AC-B9.** Given a snapshot under 10 MB compressed (design s4.4 rule 2), when the compose layer writes it, then `PutSnapshot` (single blob) may still be used and `GetSnapshot`/`ListSnapshots` list it alongside multi-part snapshots in one ascending, deterministic order; `DeleteSnapshot` removes either kind and stays idempotent. (a2 "PutSnapshot kept for small payloads")
- **AC-B10.** Given `OpenSnapshot` of 256 parts, when 16 goroutines call `OpenPart` concurrently, then it is race-clean (`-race`) and each reader is independent (parallel-safe, a2 s1.3).
- **AC-B11.** Given a snapshot commit on `S3Store`, when it runs, then the order is: parts, then CAS of city `manifest.json` (If-Match, proves ownership, increments `commitSeq`), then create-only PUT of `snapshot/<id>/manifest.json`. A crash between the last two leaves no listed snapshot. (ASM-1571; section F for the 412 case)
- **AC-B12.** Given a deadline on `ctx` passed to `Commit` (the SIGTERM path), when the deadline expires before the manifest is committed, then `Commit` returns a deadline error, calls Abort semantics, and the previous snapshot, journal head and city manifest are unchanged and still restorable. (Q100163; ASM-1569)

## C. Packed binary SoA citizen snapshot format (AC-S)

*[Review 2026-11-17]* The codec lives in `internal/engine/citizens` beside `participant.go`'s `coldStream` (ASM-1613): it writes a shard to an `io.Writer` and reads one from an `io.Reader`; compose passes those streams to `SnapshotWriter.PutPart` / `SnapshotReader.OpenPart`. persist never sees a column. Hot-set citizens and households are not in the shard parts; they ride in the core part (AC-S11, ASM-1614).

- **AC-S1.** Given a shard, when encoded with format `soa-v1`, then the part is: a versioned header (magic, format version, shard index, world seed, epoch month, row count, column count, per-column id, width and byte length), followed by little-endian column buffers in a fixed, documented column order, then gzip (stdlib `compress/gzip`) at a fast level (`gzip.BestSpeed` unless the brief sets another; Q100156). No zstd and no new dependency. (a2 s1.3; Q100156)
- **AC-S2.** Given identical citizen state encoded twice (and encoded under different `GOMAXPROCS`, and with the shards encoded in any worker order), when the parts are compared, then each part's bytes are identical and the manifest part list is identical; gzip header fields are pinned as in `internal/foundation/serialize/ndjson.go` (ModTime zero, OS 255, no Name/Comment). Within one Go toolchain version and amd64. (GR#21; ASM-1559)
- **AC-S3.** Given the manifest, when a part's `rawSha256` is read, then it equals the SHA-256 of the uncompressed bytes, so a Go-version bump that changes flate output does not change `rawSha256`; a test asserts `rawSha256` equality against a committed golden for a seeded fixture. (ASM-1559)
- **AC-S4.** Given a populated cold store (paging off and paging on), when saved as `soa-v1` and loaded into a fresh `CitizensAPI`, then the post-load `PopulationHash` equals the pre-save hash AND every ColdShard column of every one of the 256 shards is compared element by element at full width (plus `epochMonth`). *[Amended 2026-11-17: `PopulationHash` hashes only `byte(monthlyUpdates[i])` (registry.go), so a codec that truncated that uint32 column to 8 bits would pass a hash-only check.]* Edge rows cover every column's type extremes as the column is declared in `coldshard.go` (for example zero workplace/school, maximum uint64 household/partner, int64 wealth min/max, int8 satisfaction -128/127, `monthlyUpdates` above 255); an edge the declared type cannot hold is not tested. The default fixture is about 65,536 rows touching all 256 shards; the full-size runs belong to the perf tags. (a2 s1.3; ASM-1560)
- **AC-S5.** Given the BUG-666 `rowOf` index, when a snapshot is saved, then no index bytes are written (assert part size equals header plus columns), and when loaded the index is rebuilt per shard in parallel and a lookup of every id returns its row. The rebuild is asserted correct, not timed, on the default fixture in the scoped `-race` run, and on 1M rows under the `perf10m` tag (a 1M-row fixture under `-race` risks the 30-minute watchdog). (a2 s1.3 "rebuilt on load, not stored")
- **AC-S6.** Given a part with a bad magic, an unknown format version, a column length not a multiple of its width, a row count that disagrees with a column length, or a shard index or world seed that disagrees with the manifest and the destination, when loaded, then it fails closed with a registry code naming the field, and the engine does not adopt any rows from it (cf. the BUG-713 stamp lessons in `paging.go`).
- **AC-S7.** Given a legacy value outside a narrower SoA column width (for example a wire `satHousing` outside int8), when converting an old save, then conversion fails with a registry error naming the citizen id and field; it never clamps. (ASM-1560)
- **AC-S8.** Given a save written in the current format (`ndjson+gzip` inside a zip bundle, no manifest part list), when loaded after this change, then it loads byte-for-byte as today (existing tests unchanged and green), and a committed fixture save from before this change is part of the test data. Format is chosen from `Manifest().Format` or, for legacy blobs, from content sniffing, never from a flag. (a2 s1.3 "old saves still load"; Q100156)
- **AC-S9.** Given the NDJSON path, when an export is requested (`save export --format ndjson` seam or the existing function), then the portable human-readable export still works and round-trips; NDJSON is also the fallback read path when `soa-v1` support is absent for a given part format string. (a2 "NDJSON kept as export/fallback")
- **AC-S10.** Given the encoder, when saving 256 shards, then it streams shard by shard through the existing `coldStream`-style single-shard snapshot (never building the whole population or the whole snapshot in one `[]byte`), peak extra heap during save is bounded by `P-upload-concurrency x max part size` plus one shard buffer. *[Amended 2026-11-17: sampled `runtime.MemStats` peaks depend on GC timing and are not a stable CI assertion.]* CI asserts the bound structurally: the pipeline keeps an in-flight buffered-bytes counter (high-water mark exposed in `SnapshotStats`), and a test with a counting fake asserts the high-water mark is at most `P-upload-concurrency x largest part + one shard buffer`, and that no code path materialises the whole population (no call into a whole-population gather; BUG-1198's streaming walk is reused). Peak `HeapInuse` at 1M and 10M is reported as a measurement under the perf tags, not asserted. (a2 s1.1; memory contract)
- **AC-S11.** Given the non-citizen compose bundle, when saved, then it is written as a separate `core` part (format `zip` or the existing bundle bytes) so its encoding is untouched and old and new bundles differ only in how cold-shard citizens are carried; the hot set and households stay in the core part in their existing encoding (ASM-1614), and AC-S4's `PopulationHash` equality is the proof they survive. (ASM-1561)

## D. Journal record v2, group commit, dedup, segments (AC-J)

- **AC-J1.** Given a command appended, when read back, then the record is `{v:2, seq, epoch, kind:"cmd"|"ext", session, body}` where `seq` is dense (no gaps, no repeats) starting at 1 per city, assigned only by the single writer, and `epoch` is the writer's epoch; a golden file pins the JSON field names and order. (a2 s1.4; ASM-1566)
- **AC-J2.** Given an old city with v1 journal records (bare Command JSON, no `v`), when restored, then they replay exactly as today, and a mixed journal (v1 then v2 after upgrade) restores; the first v2 record's `seq` continues from the count of v1 records so seq stays dense. (ASM-1566)
- **AC-J3.** Given `kind:"ext"`, when appended and read, then `body` is returned verbatim without interpretation. (ASM-1565)
- **AC-J4. REJECTED (review 2026-11-17).** It assumes a `session` identity that does not exist: `protocol.Command` (internal/protocol/envelope.go) carries `correlationId` but no session, and nothing says where a session comes from or whether it survives a reconnect (a retry from a new WebSocket is exactly the case dedup exists for). It also assumes the engine can return "the original `CommandResult` unchanged", but results are not stored anywhere today. BA must supply: the session source (field on `Command`, or a transport-level id threaded through `ObserveCommand`) and its lifetime across reconnects; where the cached results live and their bound; and whether this is a protocol change (GR#20, wire version). Original text kept for the BA: Given two commands with the same `(session, correlationId)` within the dedup window (`P-dedup-window` default 4096 keys per session, ASM-1564), when the second is submitted, then it is not appended, the original `CommandResult` is returned unchanged, and `seq` does not advance; a key outside the window is treated as new; two sessions with the same correlationId do not collide.
- **AC-J5. REJECTED (review 2026-11-17).** Depends on AC-J4. After a restart the tail holds commands, not results, so "still deduped" can only mean "not re-applied"; the original `CommandResult` cannot be returned unless results are journaled. BA must say which is promised. Original text: Given a restart, when the journal tail is replayed, then the dedup window is rebuilt from the tail records, so a retry of a command whose record is in the tail is still deduped after restart. (ASM-1564)
- **AC-J6. REJECTED pending the seam (review 2026-11-17).** The behaviour is testable, but the doc places it nowhere. Today `persistCommandJournaler.ObserveCommand` (compose/persistjournal.go) calls `store.AppendJournal` synchronously per command inside the engine's command path. A flush "on the tick boundary" cannot be awaited from inside that call without stalling or deadlocking the tick that must end first, and `P-batch-ms` = 200 ms is longer than the 160 ms turbo tick (Q100147). Lead/BA must supply the contract change first (GR#20): which interface gains batch/async semantics (`core.CommandJournaler` or a new one), who owns the flush timer, and how `CommandResult` emission is deferred until the flush. The timer must be an injected clock in tests. Original text: Given group commit with `P-batch-records` (64), `P-batch-ms` (200), or a tick boundary (ASM-1563), when commands arrive, then the batch flushes on whichever comes first, one durable write per flush (one `fsync` on disk; one batch object plus one head CAS on S3), and an empty batch never writes anything.
- **AC-J7. REJECTED pending the seam (review 2026-11-17).** Same gap as AC-J6: "no `CommandResult` has been sent" needs the result-emission path named (engine core or wsserver), which is outside the stated package scope. Keep the mutation requirement once the seam is named. Original text: Given a command awaiting durability, when its batch has not yet flushed (fake store blocks the write), then no `CommandResult` for it has been sent; when the flush succeeds, the result is sent; when the flush fails, the result is an error and the engine halts per BUG-472 policy, and no later command is acknowledged. A test with a blocking fake proves ack never precedes durability and a mutation (ack before flush) turns the test red. (a2 s1.4 "ack means durable"; BUG-472)
- **AC-J8.** Given the S3 journal, when a batch is flushed, then it is written as one immutable object `journal/<epoch>-<firstSeq>/<seq>.blk` (create-only) containing CRC-framed v2 records (existing `journal.go` framing), followed by the head CAS of AC-F4; there is no append-in-place and no AppendBlock call. ## F. Writer epoch fencing (AC-F)
