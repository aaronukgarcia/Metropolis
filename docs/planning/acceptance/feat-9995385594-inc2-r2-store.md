## Scope

A second `persist.Store` implementation speaking the S3 API (Cloudflare R2 primary), and the three format changes it needs on every Store: multi-part snapshots, journal record v2 with group commit and segments, and writer-epoch fencing. Out of scope: the SIGTERM/hibernate trigger itself (D2, BUG-1197), the snapshot cadence policy (inc3), the launcher (Q100164), the browser reconnect and `server.waking` protocol (a2 s2.1), the Cloudflare Tunnel set-up (Q100160), and zstd (Q100156, only if the wake measurement misses). The Store does not learn what a citizen is: part bodies are opaque to it except in the SoA codec file (AC-S section).

**North-star vetting:** not player-facing; it is infrastructure that makes the wake budget (Q100153) and Spot reclaim (Q100163) possible. Stated explicitly per the process.

**Naming.** Errors below are written `E-<NAME>`: each is a registry code claimed through `tools/plan/add-error.js` (claim-range, add, check) with the number pre-assigned by the lead in the dev brief (parallel lanes collide otherwise). The builder runs the Go scanner as well as the Node check. Parameters are written `P-<name>` with the proposed default and its ASM; none is a ruling.

## Object layout (the contract the ACs refer to; a2 s1.3/1.4, design s4.4)

```
<tenant>/<city>/manifest.json                 city manifest: epoch, latestSnapshot, commitSeq   (CAS, If-Match)
<tenant>/<city>/journal/head.json             {epoch, seq}                                       (CAS, If-Match)
<tenant>/<city>/journal/<epoch>-<firstSeq>/<seq>.blk   immutable batch objects                   (If-None-Match:*)
<tenant>/<city>/snapshot/<id>/manifest.json   SnapshotManifest, immutable                        (If-None-Match:*)
<tenant>/<city>/snapshot/<id>/<part>          immutable parts
```
Tenant and city path segments are `encodeSegment`-style hashes or an equivalently traversal-proof encoding (see AC-X3). Sidecars (world seed, game mode, mode epoch) keep their existing semantics under `<tenant>/<city>/`.

## A. Store contract and the S3 implementation (AC-A)

- **AC-A1.** Given `internal/persist`, when the package builds, then a new `S3Store` (name is the builder's) satisfies the `Store` interface, and `store_conformance_test.go`'s `runStoreConformance` is run against it by a third test (`TestS3StoreConformance`) with no case skipped or special-cased for it. (a2 s1.3; Q100159)
- **AC-A2.** Given the conformance suite, when it runs against `S3Store`, then the backend is an in-process fake S3 server (httptest) that enforces If-Match and If-None-Match with real ETag semantics, so the suite needs no network and no credentials. A second, build-tagged live suite (`-tags r2live`) runs the same suite against a real bucket only when the endpoint env vars are set, and is never part of CI. (ASM-1553)
- **AC-A3.** Given the fake S3 server, when its conditional-write enforcement is switched off, then the fencing tests of section F fail (proof the tests can fail; per verification standards).
- **AC-A4.** Given config (endpoint URL, bucket, region, access key id, secret, path-style flag, optional key prefix), when `S3Store` opens, then it reads them only from a typed config struct populated from environment or `*_FILE` secret paths; no provider-specific constant (no `r2.cloudflarestorage.com` literal) appears in non-test code. A test points it at a non-R2 endpoint and passes. (Q100159 "stays S3-portable"; ASM-1575)
- **AC-A5.** Given `go.mod`, when the change lands, then the only new dependency is either none (default: in-repo SigV4 client, ASM-1550) or one S3 client library that Aaron approved in the brief (GR#10); no Azure module is imported anywhere in the repo, and `go list -deps ./internal/persist/` contains no `azure` path. (a2 s1.3)
- **AC-A6.** Given the first open of a city for writing, when the capability probe runs (two create-only PUTs to a probe key, one If-Match with a wrong ETag), then a backend that accepts the second create-only PUT or the wrong-ETag PUT makes `Open` fail closed with `E-COND-WRITE-UNSUPPORTED`, naming the endpoint host (never the credentials), and writes nothing else. A read-only open (restore for inspection) skips the probe. (a3 s2 "to verify per provider"; ASM-1553)
- **AC-A7.** Given a transient 5xx, 429 or network error on any request, when the call is idempotent (GET, HEAD, create-only PUT with the same body, DELETE), then it retries with bounded exponential backoff and jitter up to `P-retries` (default 5) and respects `ctx` cancellation; a non-idempotent step (the head CAS) is retried only after re-reading the ETag, never blindly. On exhaustion it returns a registry error carrying the HTTP status class.
- **AC-A8.** Given `ctx` cancelled mid-request, when any Store method is running, then it returns within one HTTP round trip with the ctx error wrapped in a registry error, and leaves no partially visible state (orphans only, per AC-B6).
- **AC-A9.** Given a part GET or list on a fake that returns a stale listing, when the store lists after its own PUT, then behaviour is defined by ASM-1554: the test uses a strongly consistent fake and documents that an eventually-consistent backend is unsupported. (ASM-1554)
- **AC-A10.** Given `Exists`, `ListCities`, seed/game-mode/epoch sidecars, when run on `S3Store`, then they pass the existing conformance cases, including "stamping a seed alone does not make a city exist" and `SetWorldSeedIfAbsent` first-writer-wins via If-None-Match:* under 16 concurrent callers.

## B. Multi-part snapshots (AC-B)

- **AC-B1.** Given the Store interface, when this item lands, then every implementation (DiskStore, MemStore, S3Store) provides `BeginSnapshot(ctx, city, tick) (SnapshotWriter, error)` with `PutPart(ctx, name, io.Reader)`, `Commit(ctx, SnapshotManifest) (SnapshotID, error)`, `Abort(ctx)`, and `OpenSnapshot(ctx, city, id) (SnapshotReader, error)` with `Manifest()` and `OpenPart(ctx, name) (io.ReadCloser, error)`, and all three pass the same new conformance cases below. `PutSnapshot`/`GetSnapshot` stay and keep their current tests unchanged. (a2 s1.3; ASM-1567)
- **AC-B2.** Given a committed snapshot, when `Manifest()` is read, then it carries `Tick`, `JournalSegment`, `JournalSeq` (the exact position covered), `Epoch`, `Format` (`"soa-v1+gzip"`, `"ndjson+gzip"` or `"zip"`), `CreatedAtUnix` (ASM-1557) and `Parts` as an ordered list of `{name, size, sha256, rawSha256}`; JSON field names are fixed by a golden test, and unknown future fields are ignored on read. (a2 s1.3; ASM-1559)
- **AC-B3.** Given 256 parts of random bytes written concurrently with `P-upload-concurrency` (default 8, ASM-1562), when `Commit` is called, then `OpenPart` for each name returns exactly the bytes written, `Manifest().Parts[i].sha256` equals the SHA-256 of what was stored, and a reader opening any part checks size and sha256 while streaming and returns `E-PART-CORRUPT` on mismatch at EOF (never a silent short read).
- **AC-B4.** Given `PutPart` called with the same part name twice in one writer, when the second call starts, then it fails with a registry error (parts are immutable within a snapshot) and the first stays intact.
- **AC-B5.** Given a `Commit` whose manifest lists a part that was never put, or a put part not listed, when committed, then it fails with `E-MANIFEST-PARTS-MISMATCH` and nothing becomes visible.
- **AC-B6.** Given a crash (writer abandoned, process killed in a test by dropping the writer) after N of 256 parts and before `Commit`, when `ListSnapshots`, `OpenSnapshot` and restore run, then the orphan parts are invisible: `ListSnapshots` does not list the id, `OpenSnapshot` returns not-found, and restore selects the previous snapshot. (a2 s1.3 "orphan parts invisible")
- **AC-B7.** Given orphan parts older than `P-orphan-age` (default 24 h, wall clock) with no committed manifest, when `SweepOrphans(ctx, city)` runs (also called once at writer acquire), then they are deleted; parts of an in-progress writer younger than the age, and any committed snapshot, are never deleted. A sweep never deletes under a prefix belonging to another city. (a2 s1.3 "a sweeper deletes"; nothing outside project temp is deleted without a gate: this is runtime deletion of the store's own data, not a tool action)
- **AC-B8.** Given `Abort`, when called, then uploaded parts are removed best-effort, `Abort` after `Commit` is a no-op returning nil, and `Abort` twice is nil.
- **AC-B9.** Given a snapshot under 10 MB compressed (design s4.4 rule 2), when the compose layer writes it, then `PutSnapshot` (single blob) may still be used and `GetSnapshot`/`ListSnapshots` list it alongside multi-part snapshots in one ascending, deterministic order; `DeleteSnapshot` removes either kind and stays idempotent. (a2 "PutSnapshot kept for small payloads")
- **AC-B10.** Given `OpenSnapshot` of 256 parts, when 16 goroutines call `OpenPart` concurrently, then it is race-clean (`-race`) and each reader is independent (parallel-safe, a2 s1.3).
- **AC-B11.** Given a snapshot commit on `S3Store`, when it runs, then the order is: parts, then CAS of city `manifest.json` (If-Match, proves ownership, increments `commitSeq`), then create-only PUT of `snapshot/<id>/manifest.json`. A crash between the last two leaves no listed snapshot. (ASM-1571; section F for the 412 case)
- **AC-B12.** Given a deadline on `ctx` passed to `Commit` (the SIGTERM path), when the deadline expires before the manifest is committed, then `Commit` returns a deadline error, calls Abort semantics, and the previous snapshot, journal head and city manifest are unchanged and still restorable. (Q100163; ASM-1569)

## C. Packed binary SoA citizen snapshot format (AC-S)

- **AC-S1.** Given a shard, when encoded with format `soa-v1`, then the part is: a versioned header (magic, format version, shard index, world seed, epoch month, row count, column count, per-column id, width and byte length), followed by little-endian column buffers in a fixed, documented column order, then gzip (stdlib `compress/gzip`) at a fast level (`gzip.BestSpeed` unless the brief sets another; Q100156). No zstd and no new dependency. (a2 s1.3; Q100156)
- **AC-S2.** Given identical citizen state encoded twice (and encoded under different `GOMAXPROCS`, and with the shards encoded in any worker order), when the parts are compared, then each part's bytes are identical and the manifest part list is identical; gzip header fields are pinned as in `serialize/ndjson.go` (ModTime zero, OS 255, no Name/Comment). Within one Go toolchain version and amd64. (GR#21; ASM-1559)
- **AC-S3.** Given the manifest, when a part's `rawSha256` is read, then it equals the SHA-256 of the uncompressed bytes, so a Go-version bump that changes flate output does not change `rawSha256`; a test asserts `rawSha256` equality against a committed golden for a seeded fixture. (ASM-1559)
- **AC-S4.** Given a populated cold store (paging off and paging on), when saved as `soa-v1` and loaded into a fresh `CitizensAPI`, then the post-load population hash (`PopulationHash` inputs, including `monthlyUpdates`) equals the pre-save hash and a per-shard digest comparison passes for all 256 shards, including edge rows: zero workplace/school, maximum uint64 household/partner, negative attainment, int64 wealth min/max. (a2 s1.3; ASM-1560)
- **AC-S5.** Given the BUG-666 `rowOf` index, when a snapshot is saved, then no index bytes are written (assert part size equals header plus columns), and when loaded the index is rebuilt per shard in parallel and a lookup of every id returns its row. The rebuild is exercised with 1M rows and asserted correct, not timed. (a2 s1.3 "rebuilt on load, not stored")
- **AC-S6.** Given a part with a bad magic, an unknown format version, a column length not a multiple of its width, a row count that disagrees with a column length, or a shard index or world seed that disagrees with the manifest and the destination, when loaded, then it fails closed with a registry code naming the field, and the engine does not adopt any rows from it (cf. the BUG-713 stamp lessons in `paging.go`).
- **AC-S7.** Given a legacy value outside a narrower SoA column width (for example a wire `satHousing` outside int8), when converting an old save, then conversion fails with a registry error naming the citizen id and field; it never clamps. (ASM-1560)
- **AC-S8.** Given a save written in the current format (`ndjson+gzip` inside a zip bundle, no manifest part list), when loaded after this change, then it loads byte-for-byte as today (existing tests unchanged and green), and a committed fixture save from before this change is part of the test data. Format is chosen from `Manifest().Format` or, for legacy blobs, from content sniffing, never from a flag. (a2 s1.3 "old saves still load"; Q100156)
- **AC-S9.** Given the NDJSON path, when an export is requested (`save export --format ndjson` seam or the existing function), then the portable human-readable export still works and round-trips; NDJSON is also the fallback read path when `soa-v1` support is absent for a given part format string. (a2 "NDJSON kept as export/fallback")
- **AC-S10.** Given the encoder, when saving 256 shards, then it streams shard by shard through the existing `coldStream`-style single-shard snapshot (never building the whole population or the whole snapshot in one `[]byte`), peak extra heap during save is bounded by `P-upload-concurrency x max part size` plus one shard buffer, and a test with `runtime.MemStats` at a scaled-down 1M-citizen fixture asserts peak heap growth stays under a fixed multiple of one shard, measured as allocated-bytes not time. (a2 s1.1; memory contract)
- **AC-S11.** Given the non-citizen compose bundle, when saved, then it is written as a separate `core` part (format `zip` or the existing bundle bytes) so its encoding is untouched and old and new bundles differ only in how citizens are carried. (ASM-1561)

## D. Journal record v2, group commit, dedup, segments (AC-J)

- **AC-J1.** Given a command appended, when read back, then the record is `{v:2, seq, epoch, kind:"cmd"|"ext", session, body}` where `seq` is dense (no gaps, no repeats) starting at 1 per city, assigned only by the single writer, and `epoch` is the writer's epoch; a golden file pins the JSON field names and order. (a2 s1.4; ASM-1566)
- **AC-J2.** Given an old city with v1 journal records (bare Command JSON, no `v`), when restored, then they replay exactly as today, and a mixed journal (v1 then v2 after upgrade) restores; the first v2 record's `seq` continues from the count of v1 records so seq stays dense. (ASM-1566)
- **AC-J3.** Given `kind:"ext"`, when appended and read, then `body` is returned verbatim without interpretation. (ASM-1565)
- **AC-J4.** Given two commands with the same `(session, correlationId)` within the dedup window (`P-dedup-window` default 4096 keys per session, ASM-1564), when the second is submitted, then it is not appended, the original `CommandResult` is returned unchanged, and `seq` does not advance; a key outside the window is treated as new; two sessions with the same correlationId do not collide.
- **AC-J5.** Given a restart, when the journal tail is replayed, then the dedup window is rebuilt from the tail records, so a retry of a command whose record is in the tail is still deduped after restart. (ASM-1564)
- **AC-J6.** Given group commit with `P-batch-records` (64), `P-batch-ms` (200), or a tick boundary (ASM-1563), when commands arrive, then the batch flushes on whichever comes first, one durable write per flush (one `fsync` on disk; one batch object plus one head CAS on S3), and an empty batch never writes anything.
- **AC-J7.** Given a command awaiting durability, when its batch has not yet flushed (fake store blocks the write), then no `CommandResult` for it has been sent; when the flush succeeds, the result is sent; when the flush fails, the result is an error and the engine halts per BUG-472 policy, and no later command is acknowledged. A test with a blocking fake proves ack never precedes durability and a mutation (ack before flush) turns the test red. (a2 s1.4 "ack means durable"; BUG-472)
- **AC-J8.** Given the S3 journal, when a batch is flushed, then it is written as one immutable object `journal/<epoch>-<firstSeq>/<seq>.blk` (create-only) containing CRC-framed v2 records (existing `journal.go` framing), followed by the head CAS of AC-F4; there is no append-in-place and no AppendBlock call. (ASM-1551)
- **AC-J9.** Given a snapshot commit, when it succeeds, then the active segment is sealed: the manifest records `JournalSegment` and `JournalSeq`, and the next append starts a new segment named `<epoch>-<firstSeq>` with `firstSeq = JournalSeq + 1`. A segment is never modified after sealing. (a2 s1.4)
- **AC-J10.** Given a restore, when it runs, then it reads `head.json`, loads the newest valid snapshot, and reads only journal objects with `seq > manifest.JournalSeq` and `seq <= head.seq` (O(tail)); a test with a fake counting GETs shows that with a 100,000-record history and a 100-record tail the number of journal object GETs equals the tail's batch count, not the history's. (a2 s1.4 "O(tail)")
- **AC-J11.** Given batch objects with `seq > head.seq` (written but never acknowledged because the head CAS did not happen), when restoring, then they are ignored and never replayed; given a CRC-bad frame inside `seq <= head.seq`, then restore fails closed with `E-JOURNAL-CORRUPT` naming object and offset (no silent truncation of acknowledged data). (ASM-1552)
- **AC-J12.** Given the local DiskStore, when restart finds a torn final frame in the live segment (a2 s1.4), then the file is truncated to the last good frame, a registry warning code is logged once with byte counts, and a later append lands directly after the last good frame; the existing "torn tail excluded" conformance behaviour is preserved. A mid-file bad frame is not truncated: it fails closed as in AC-J11.
- **AC-J13.** Given the Store journal read API, when asked for records after a position (segment, seq), then it streams (iterator or reader) and the restore path in `compose/snapshot.go` no longer calls `io.ReadAll`/`ReadJournal` for the whole history on a store that supports the new API; `ReadJournal` stays for compatibility. (a2 s1.4 "restore reads the entire journal into memory")
- **AC-J14.** Given existing BUG-480 behaviour, when run after this change, then restore still walks back to an older snapshot when the newest is ahead of the journal (MET-G810 path) and the journal-dirty latch (MET-G813) still refuses a snapshot after a swallowed append; the existing tests for both stay green.

## E. Retention (AC-R)

- **AC-R1.** Given `S3Store` retention config `P-retain-days` (default 30) and `P-thin-ticks` (default 360, ASM-1556), when `ApplyRetention(ctx, city, now)` runs (called after each successful snapshot commit and once at writer acquire), then every snapshot younger than 30 days (by `CreatedAtUnix`) is kept, and among snapshots older than 30 days exactly the newest of each `tick / 360` bucket is kept and the rest are deleted. The clock is injected, never `time.Now()` inside the logic. (Q100149)
- **AC-R2.** Given retention, when it deletes a snapshot, then it never deletes the newest snapshot of the city, never a snapshot while a restore against it is open in the same process, and never any journal segment or head object, at any age. A test with a 5-year journal and thinned snapshots asserts all segments still exist. (Q100149 "never delete journal segments")
- **AC-R3.** Given thinned snapshots, when the restore needs to walk back past the newest (MET-G810), then every retained older snapshot has all journal segments from its position onward present, so restore from any retained snapshot is possible. (a2 s1.4)
- **AC-R4.** Given the store capability `ArchiveTier` (bool, ASM-1555), when the provider supports a cool/archive transition and it is configured (`P-archive-after-days`, no default), then sealed segments older than that are transitioned by lifecycle rule configuration or a store call, with objects never deleted; on R2, `ArchiveTier` is false, no transition is attempted, no error is raised, and sealed segments stay in standard storage. A test asserts the false path is a silent no-op that logs one info line at open.
- **AC-R5.** Given the existing `MaxRetainedSnapshots = 5` pruning in the compose layer, when the store is `S3Store`, then that call defers to the store's retention policy and does not delete snapshots inside 30 days; DiskStore and MemStore keep the 5-cap unchanged. (ASM-1558)
- **AC-R6.** Given retention is idempotent, when run twice, then the second run deletes nothing and returns nil; a deletion failure leaves the snapshot listed (retry later), never half-listed.

## F. Writer epoch fencing (AC-F)

- **AC-F1.** Given a city with no manifest, when a writer acquires, then it creates `manifest.json` with `epoch: 1` and `head.json {epoch:1, seq:0}` using If-None-Match:*; two concurrent first acquirers result in exactly one winner (the other gets 412, re-reads, and acquires epoch 2 or fails per AC-F3). (Q100159)
- **AC-F2.** Given an existing manifest at epoch N, when a writer acquires, then it PUTs `epoch N+1` with `If-Match: <etag read>` and then CASes `head.json` to `{epoch:N+1, seq:<last seq>}` with its ETag; the epoch is held in memory and stamped on every record and segment name. (a2 s1.4(3); a3 s2)
- **AC-F3.** Given two writers racing to acquire the same city, when both read epoch N, then exactly one If-Match succeeds; the loser re-reads once and, if it still wants ownership, it acquires N+2 and thereby fences the winner (last acquirer wins, as a restarted Spot replacement must). The loser's behaviour is a parameter `P-acquire-mode` (`takeover` default, `fail`) and both modes are tested.
- **AC-F4.** Given a flush, when the writer persists a batch, then after the create-only batch PUT it CASes `head.json` with `If-Match` its last known ETag (strict mode, ASM-1552) and only then acknowledges; a 412 on the head CAS means the writer is fenced.
- **AC-F5.** Given a fenced writer (stale epoch), when any journal head CAS, snapshot-commit CAS or manifest PUT returns 412, then the engine halts the city (same policy as BUG-472), raises `E-WRITER-FENCED` (registry code) with the stale epoch and the observed epoch, sends no further `CommandResult`, writes no further object, and the process does not retry the write. Test: acquire as A, acquire as B, then A flushes: A halts, B continues, B's journal has none of A's post-fence batches as acknowledged.
- **AC-F6.** Given a zombie that wrote a batch object (create-only succeeded) but whose head CAS failed, when the new writer restores, then that object is beyond `head.seq` and is ignored (AC-J11), and the zombie never acknowledged the command to its client.
- **AC-F7.** Given a restore reading segment names, when it finds an epoch-lower segment whose seq range extends beyond the first seq of a higher-epoch segment, then records at seq >= that first seq from the lower epoch are rejected with `E-EPOCH-OUT-OF-ORDER`, and restore proceeds with the legitimate prefix; segments and records with epochs not strictly non-decreasing along seq order are rejected, never replayed. (a2 s1.4 "rejects out-of-order epochs")
- **AC-F8.** Given a snapshot manifest whose `(Epoch, JournalSeq)` lies beyond the next-higher epoch's first seq, when restore selects a snapshot, then that snapshot is skipped with `E-EPOCH-OUT-OF-ORDER` and the previous valid one is used. (ASM-1571)
- **AC-F9.** Given the local DiskStore, when a second process opens the same city directory, then the BUG-799 OS file lock (the `tryLockFile` primitive in `compose/citizen_paging_lock_*.go`, reused or moved to a shared internal package without changing its behaviour) makes the second refuse with a registry error, and the kernel releases the lock on process death (reuse of the existing death test pattern); the epoch is kept in `meta.json` and incremented on acquire. (Q100159; a2 s1.4 local disk)
- **AC-F10.** Given MemStore, when two writers acquire the same city, then epoch semantics match DiskStore's in-process behaviour, and the shared conformance cases for epoch (acquire increments, stale writer rejected) run against all three stores.
- **AC-F11.** Given an acquire, when it succeeds, then the epoch is logged at info with city key, never any credential, and a halted/fenced city is visible in `/health` or the existing city status as fenced (field name is the builder's).

## G. Wake and Spot-reclaim performance (AC-P)

Wall-clock budgets are verified by a recorded measurement (ASM-1570), not as a CI timing assertion. CI-asserted: structural bounds (request counts, in-flight concurrency, bytes, allocation). The measurement is a build-tagged test (`-tags perf10m`, `-tags perf30m`) plus a runbook entry; its output (host class, Go version, region pair, uplink, p50/p95 over at least 20 runs) is posted as a comment on this BOW item and is the Tester's evidence.

- **AC-P1.** Given a restore of a 256-part snapshot, when parts are fetched, then at most `P-download-concurrency` (default 16, configurable 16 to 32; ASM-1562) part GETs are in flight at any instant (asserted with a counting fake), all 256 parts are fetched, and decode/decompress runs on a worker pool bounded by `GOMAXPROCS`. ## L. Open questions for Aaron

- **Q-1 (cadence vs cost vs crash wake).** a2 s2.1 sizes periodic snapshots so a crash tail replays in about 5 s, which at 10M is a snapshot every about 8 game-days, roughly every 5 s of wall time at turbo; each is about 260 Class A operations and 150 to 250 MB. That is incompatible with the R2 free tier and the storage line. Which do you want: cheap and slow crash wake (p95 15 s only for clean hibernate/SIGTERM), or frequent snapshots? Default in these ACs: cadence is inc3's and this item only exposes the cost (AC-C2, AC-P8).
- **Q-2 (strict fencing).** If-None-Match on a journal object cannot be fenced by the manifest epoch, so full fencing needs a head-object CAS per flush (2 PUTs per flush instead of 1). Strict is the default (ASM-1552). Say if you prefer relaxed (periodic recheck, a bounded window in which a zombie can acknowledge a command that is later lost).
- **Q-3 (S3 client).** Hand-rolled SigV4 client (default, no dependency) or a library (aws-sdk-go-v2 or minio-go, GR#10 dependency decision)? (ASM-1550)
- **Q-4 (30M in 20 s).** 30M compressed is an extrapolated 450 to 750 MB, so about 25 to 40 MB/s sustained to R2. If measurement says no, is partial-snapshot reuse (unchanged parts by hash) in scope? (AC-P5)
- **Q-5 (R2 archive).** R2 has no archive tier as written in the brief; accept "segments stay in standard storage forever" on R2, or add a second cold store later? (ASM-1555; storage cost grows without bound.)
