## User stories

- **US-1.** As the player, I need every policy to state which coefficients it moves, so §52's "modelled instruments" claim is checkable against real code, not narrative flavour dressed as a mechanic.
- **US-2.** As the player about to enact a policy, I need to see its projected impact *before* I commit, computed through the same machinery that will actually apply the policy's effect, so the preview is a real forecast and not a guess wearing the F7 UI's clothing.
- **US-3.** As the player, when a preview turns out to have been wrong, I need the game to tell me so and say by how much, so a bad preview costs the game's credibility rather than silently costing me a decision I made on false information.
- **US-4.** As the player drawing districts, I need a district's name and boundary to be real, queryable state that other modules can resolve scope against, so "Tax-Free Harbour" is a mechanic, not a label on the map.
- **US-5.** As `ui.screen.districts` (this BA's sibling file), I need a scope-resolution service that maps a policy's declared scope (citywide/district/road) to the actual affected entities, so the UI (and every future consumer) doesn't reimplement that resolution itself.
- **US-6.** As the player enacting overlapping policies, I need their combined effect to be visibly different from either policy alone (compounding, shown) and a warning when two active policies conflict, so §52's interaction claims are real, queryable properties.

## Scope

A policy library (loaded from `policies.json`, categories: movement, layout & wellbeing, economy, social) where every policy declares its coefficient-mutation mechanism, cost/enforcement needs, and scope; an enactment-preview mechanism built on `engine.projections`' registered curve-provider/confidence machinery (never a parallel estimate formula); a preview-vs-outcome tracking mechanism that surfaces disagreement rather than absorbing it silently; named-district creation/naming (cell-tagged, per ASM-285) as the scope system; a scope-resolution query other modules consume; and policy interaction (compounding) and conflict-warning mechanics.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `PoliciesAPI` exists exposing: a policy-library query (name, category, mechanism, cost, scope, per code.json's "instruments = data-defined coefficient moves"), an enact/repeal command surface, and a scope-resolution query ("scope resolution service for all modules"). Check: `go doc ./internal/engine/policies PoliciesAPI` shows all three surfaces; `grep -rn "func Test.*[Ll]ibrary\|func Test.*[Ee]nact\|func Test.*[Ss]copeResolve" internal/engine/policies/*_test.go` finds coverage.
- **AC-2 (§52 mechanism = data-defined coefficient deltas; GR#15).** Every policy's mechanism is declared in `policies.json` as an explicit list of `(coefficientKey, delta)` pairs, loaded generically (no `switch policy.Name` branching to decide what a policy does). Check: `grep -n "\"mechanism\"\|\"coefficients\"" data/policies.json` matches; `grep -nE "case \"|switch .*[Pp]olicy" internal/engine/policies/*.go` (excluding `_test.go`) finds no name-branching mechanism dispatch.
- **AC-3 (§52 mechanism-vs-mutation consistency — a differential single-field mutation test, per the ASM-257 precedent this BA is following).** Enacting a policy mutates **exactly** the coefficient(s) its `policies.json` entry declares, and nothing else — a passing test enacts a fake policy declaring a single coefficient delta against a snapshot of full engine state, and asserts a field-by-field diff shows only the declared coefficient(s) changed. Check: `grep -rn "func Test.*[Ss]ingleField\|func Test.*[Mm]echanismDiff" internal/engine/policies/*_test.go`. **Lazy implementation this rejects:** a policy that is actually implemented as a hand-written function with side effects beyond its declared mechanism (e.g. a "cycle-priority network" policy that also silently nudges an unrelated pollution coefficient) would pass any check that only asserts "the declared coefficient changed" — the full-state diff catches the undeclared extra mutation the declaration doesn't disclose.
- **AC-4 (§52 preview — same-model, not a second formula; the sprint's hardest AC).** `PreviewImpact(policyID, scope)` computes its projected curve by feeding the **identical** coefficient-delta payload AC-3 proves the real enactment applies into `engine.projections`' registered curve providers (the registered `engine.policies`→`engine.projections` edge) — it is a same-model conditional/what-if query, never an independently-coded estimate formula that merely resembles the real mechanism. Check: a passing test captures the coefficient-delta payload `PreviewImpact` sends to `ProjectionsAPI` and separately captures the payload the real `Enact` path applies for the same policy, and asserts the two payloads are identical (`grep -rn "func Test.*[Pp]reviewMatchesEnact\|func Test.*[Ss]ameModel" internal/engine/policies/*_test.go`). **This is the load-bearing check named in the brief:** a preview built as a plausible-looking but separately-authored quick-estimate (a lookup table, a hand-tuned formula) would satisfy any check that merely asks "does a preview number render" — this check specifically diffs the two code paths' actual inputs to the shared curve machinery, so a parallel-formula implementation fails it even if its output numbers happen to look reasonable.
- **AC-5 (§52 preview confidence/provenance — consistency with `engine.projections.md` AC-6).** `PreviewImpact`'s returned curve carries `engine.projections`' `Computed`/`Extrapolated`/`Unavailable` confidence tag per point (not a policies-local re-invention of that distinction), and no point beyond `ProjectionsAPI`'s current horizon N is ever presented to the caller tagged `Computed`. Check: `grep -n "projections\.Computed\|projections\.Confidence" internal/engine/policies/*.go` shows reuse of the shared type (not a locally-redeclared enum); a passing test queries a preview whose requested range exceeds horizon N and asserts the beyond-horizon portion is not `Computed` (`grep -rn "func Test.*[Bb]eyondHorizonPreview" internal/engine/policies/*_test.go`).
- **AC-6 (§52 preview promise, part 1 — what it promises).** A preview is documented and behaviourally proven to be exactly one thing: a same-model conditional projection of the declared coefficient deltas, carrying `engine.projections`' confidence semantics — **not** a guarantee, not a point estimate with an implied error bar the game never states, and not independent of other decisions the player or the simulation makes between preview and enactment. `doc.go` states this explicitly (AC-15). Check: `internal/engine/policies/doc.go` contains a stated definition of what `PreviewImpact` promises, matching this AC's wording, cross-referenced in AC-15.
- **AC-7 (§52 preview promise, part 2 — what happens when it's wrong; ASM-286).** Every enacted policy's preview snapshot (the coefficient-delta payload and the `Computed`-tagged portion of its curve, per AC-4/AC-5) is persisted at enactment time keyed by a policy-enactment ID. At documented checkpoints after enactment, the actual observed curve values for the same coefficients are compared against the stored preview's `Computed` points; a divergence beyond a documented tolerance (ASM-286 — tolerance/cadence are BA-chosen pending Aaron) raises a registry-sourced `PreviewDrift` event naming the policy, the coefficient, the checkpoint, and the magnitude of the divergence — this is never silently discarded or left for the player to notice on their own. Check: a passing test enacts a fake policy with a synthetic stored preview, advances to a checkpoint with actual state diverging beyond tolerance, and asserts a `PreviewDrift` event fires with the policy/coefficient/checkpoint/magnitude fields populated; a second test feeds actual state within tolerance and asserts no event fires (`grep -rn "func Test.*[Pp]reviewDrift" internal/engine/policies/*_test.go`). **False-pass risk:** a test that only unit-tests the comparator function in isolation (never invoked from the tick pipeline) would pass a build where `PreviewDrift` is correct code that nothing ever calls — the check requires the tick-driven checkpoint evaluation to actually fire the event, not just the comparator's arithmetic to be right.
- **AC-8 (§52 named districts — cell-tagged, ASM-285).** A district is created with a name and a set of cell references (`DistrictID` tagged onto `engine.world` cells, per ASM-285), queryable by name and by ID; renaming preserves the same `DistrictID` and its existing policy/tax scoping. Check: `go doc ./internal/engine/policies CreateDistrict` (or equivalent) exists; a passing test creates a district, renames it, and asserts the `DistrictID`'s scoped policies/cells are unchanged by the rename (`grep -rn "func Test.*[Dd]istrict.*[Nn]ame\|func Test.*[Cc]reateDistrict" internal/engine/policies/*_test.go`).
- **AC-9 (§52 scope resolution service).** `ResolveScope(policyID)` returns the concrete set of affected entities for a policy's declared scope: all cells/roads for `citywide`, a district's cell set for `district`, a named road's edge set for `road` — exposed as a shared query other modules call rather than each reimplementing scope logic locally. Check: `go doc ./internal/engine/policies ResolveScope` exists; a passing test asserts each of the three scope kinds resolves to the expected entity set for a fixture district/road (`grep -rn "func Test.*[Rr]esolveScope" internal/engine/policies/*_test.go`).
- **AC-10 (§52 interaction/compounding — shown, not silently summed).** Two enacted policies with overlapping coefficient targets in the same scope produce a combined effect that is (a) different from either policy's individual declared magnitude in a documented way (e.g. diminishing-returns or multiplicative combination — the specific rule is data-declared, not this AC's to pin) and (b) itself queryable as a distinct value, not only visible by the player doing arithmetic on two separate numbers. Check: `go doc ./internal/engine/policies` shows a combined-effect query distinct from per-policy queries; a passing test enacts two overlapping fake policies and asserts the combined-effect query differs from the naive sum of the two individual declared deltas (`grep -rn "func Test.*[Cc]ompound" internal/engine/policies/*_test.go`).
- **AC-11 (§52 conflict warnings; ASM-288).** `policies.json` declares `conflictsWith` pairs per policy (GR#15 — not hardcoded pairs in Go); enacting a policy that conflicts with an already-active policy **in an overlapping scope** raises a queryable, non-blocking warning (§52 says bundles "warn", not "are prevented") — the second policy still enacts. Check: `grep -n "conflictsWith" data/policies.json` matches; a passing test enacts a conflicting pair in overlapping scope and asserts both a warning is queryable **and** the second policy's status is active, not rejected (`grep -rn "func Test.*[Cc]onflictWarn" internal/engine/policies/*_test.go`).
- **AC-12 (§52 named districts as identity — Name exposed, firm-location logic out of scope).** A district's `Name` is exposed as queryable metadata other modules can read (feeding firm location/reputation per §52's "the name is a mechanic" — the actual consumption by `engine.firms` is a Sprint-10, out-of-scope concern). Check: `go doc ./internal/engine/policies` shows `Name` on the district query result; a passing test asserts a renamed district's `Name` is immediately visible via query (`grep -rn "func Test.*[Dd]istrictName" internal/engine/policies/*_test.go`).

### Error handling

- **AC-13 (GR#7).** Enacting an already-active policy in an identical scope, or resolving scope for an unknown `DistrictID`/road, returns a registry-sourced error (new `MET-E`-range code) naming the policy/scope, never a silent no-op or a resolved-to-empty-set false success. Check: `grep -n "MET-" internal/engine/policies/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Aa]lreadyActive\|func Test.*[Uu]nknownScope" internal/engine/policies/*_test.go`).

### Determinism & safety

- **AC-14 (GR#21).** Policy evaluation order (compounding resolution, `PreviewDrift` checkpoint evaluation across multiple active policies) is deterministic — sorted by a documented stable key (e.g. `PolicyID` then `DistrictID`), never dependent on unordered map iteration. Check: `grep -n "for .* := range" internal/engine/policies/*.go` on any map feeding evaluation order is sorted (`grep -n "sort\." internal/engine/policies/*.go`); a passing determinism test exists (`grep -rn "func Test.*[Dd]eterminis" internal/engine/policies/*_test.go`).
- **AC-15 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/policies/*.go` (excluding `_test.go`) returns no matches — checkpoint evaluation and preview generation are driven by simulation month, never wall clock.
- **AC-16.** `go test ./internal/engine/policies/... -race -count=1` passes with no data race when policies are enacted/queried concurrently across shards. Check: `grep -n "go func()" internal/engine/policies/*_test.go` finds at least one concurrency test.

## Blocked (pending BUG-058 fix)

- **AC-19 (§52 cost/enforcement needs — BLOCKED, no legal call path today).** Every policy's declared cost debits through `engine.finance`'s `FinanceAPI` at enactment, and ongoing enforcement needs debit as a recurring opex line — **this AC cannot be built under GR#20 as code.json is currently registered**: `engine.policies`' outbound calls are `engine.projections`, `engine.tax`, `foundation.data` only; there is no `engine.policies`→`engine.finance` edge. §52 explicitly names "cost/enforcement needs" as part of every policy's stated contract, and per the brief's GR#3 instruction ("consume [finance's] machinery, do not build a second one"), a workaround that posts cost through `engine.tax` instead (the one money-touching edge that *is* registered) would misrepresent an enactment cost as a tax transaction — the wrong category, not a legal substitute. Do not implement this AC until the edge is registered; do not route the cost through `engine.tax` as a workaround. See Escalations — logged against BUG-058, 2026-08-11.

## Out of scope

- The full tax instrument panel (`engine.tax`, this BA's sibling file) — `engine.policies` calls into `TaxAPI` to move tax coefficients (e.g. a freeport policy suppressing business rates); it does not implement tax mechanics itself.
- The whole-economy Fiscal Circuit view (`engine.fiscal`, this BA's sibling file) — that module reads tax/finance data; it does not consume `engine.policies` directly per code.json's current registration.
- `ui.screen.districts`' rendering of the policy library, preview, conflict warnings, or district drawing (this BA's sibling file) — this item exposes the queryable API; the screen consumes it via `int.protocol`.
- `engine.firms`' actual consumption of district `Name`/identity for firm-location decisions (Sprint 10) — AC-12 only exposes the queryable metadata.
- Tuned cost/effect/conflict-pair values in `policies.json` (ASM-284/ASM-288) — M2 Balance harness content, not this BA's to invent.

- **What a policy preview promises, and what happens when it's wrong (summary for Ben, per brief instruction to read this first).** The preview promises exactly one thing: a same-model conditional projection, run through the identical coefficient-mutation payload the real enactment applies (AC-4), carrying `engine.projections`' own `Computed`/`Extrapolated` confidence tags rather than a policies-local invention of confidence (AC-5) — never a guarantee, never an independent estimate. When the eventual outcome disagrees with what was previewed beyond a stated tolerance, that disagreement is not absorbed silently: it is persisted, checked at defined checkpoints, and raised as a named, queryable `PreviewDrift` event carrying which policy, which coefficient, and by how much (AC-7). This mirrors `engine.projections.md`'s own anti-ambush stance (a guess must never wear a computed value's confidence) and extends it with the one thing `engine.projections` itself doesn't need, because it never claims a single decision's future is settled: an explicit reckoning when the promise and the result don't match.
- **How incidence-shift was made checkable rather than displayable (cross-reference for Ben, since it's this BA's `engine.tax.md` sibling file, not this one).** See `engine.tax.md` AC-5 — incidence proportions, not just totals, are asserted to move across two different rate settings for the same instrument; a fixed-lookup-table incidence display cannot pass that check regardless of how the display renders.
