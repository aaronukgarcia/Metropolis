## User stories

- **US-1.** As the player, I need every policy to state which coefficients it moves, so §52's "modelled instruments" claim is checkable against real code, not narrative flavour dressed as a mechanic.
- **US-2.** As the player about to enact a policy, I need to see its projected impact *before* I commit, computed through the same machinery that will actually apply the policy's effect, so the preview is a real forecast and not a guess wearing the F7 UI's clothing.
- **US-3.** As the player, when a preview turns out to have been wrong, I need the game to tell me so and say by how much, so a bad preview costs the game's credibility rather than silently costing me a decision I made on false information.
- **US-4.** As the player drawing districts, I need a district's name and boundary to be real, queryable state that other modules can resolve scope against, so "Tax-Free Harbour" is a mechanic, not a label on the map.
- **US-5.** As `ui.screen.districts` (this BA's sibling file), I need a scope-resolution service that maps a policy's declared scope (citywide/district/road) to the actual affected entities, so the UI (and every future consumer) doesn't reimplement that resolution itself.
- **US-6.** As the player enacting overlapping policies, I need their combined effect to be visibly different from either policy alone (compounding, shown) and a warning when two active policies conflict, so §52's interaction claims are real, queryable properties.
- **US-7 (folded from feat.policy/FEAT-091 US-1, ASM-942).** As the player, I need a policy to have one GLOBAL setting that applies everywhere by default, so a single decision governs the whole city rather than forcing me to re-set it per area (design: "policies are GLOBAL").
- **US-8 (folded from feat.policy US-2).** As the player, I need any zone class to override a policy with a different value — the dwelling 'no trucks at weekends' example — so one policy can mean one thing city-wide and something else inside a specific zone class, and the override never leaks into the global value or another zone (design: "zones can override").
- **US-9 (folded from feat.policy US-3).** As the player, I need every policy value to be either [auto] — the game computes it from a documented, deterministic source — or [manual] — I set it and it stays where I left it — so I can either delegate a lever to the engine or pin it by hand (design: "[auto]/[manual] values"; §19.2 signals and §17 waste-routes "auto-optimised or hand-set" precedent).
- **US-10 (folded from feat.policy US-4).** As the player, I need a change history that records every change to every policy — global or zone, auto or manual — with the old value, the new value, and when it happened, so I can see exactly how a policy arrived at its current state (design: "change history so the player sees every change").
- **US-11 (folded from feat.policy US-5).** As the player browsing a policy, I need its detailed explanation (what it does, what it costs, its consequences) and its reader notes (context, caveats, design intent) surfaced from data, so a policy is explained rather than a bare toggle label (design: "detailed explanation + reader notes").
- **US-12 (folded from feat.policy US-6).** As `ui.screen.districts` (FEAT-022), I need the global/zone setting, the auto/manual mode, the history, and the explanation content reachable through one registered engine contract, so the F8 screen renders configuration state without re-deriving it (GR#20).

## Scope

A policy library (loaded from `policies.json`, categories: movement, layout & wellbeing, economy, social) where every policy declares its coefficient-mutation mechanism, cost/enforcement needs, and scope; an enactment-preview mechanism built on `engine.projections`' registered curve-provider/confidence machinery (never a parallel estimate formula); a preview-vs-outcome tracking mechanism that surfaces disagreement rather than absorbing it silently; named-district creation/naming (cell-tagged, per ASM-285) as the scope system; a scope-resolution query other modules consume; and policy interaction (compounding) and conflict-warning mechanics.

**Policy configuration-state layer (folded from feat.policy/FEAT-091, ASM-942):** a global setting per policy with optional per-`ZoneType` overrides; effective-value resolution (override else global); a per-setting [auto]/[manual] mode where auto is a deterministic, data-declared engine computation and manual is a persisted player value; an append-only, ordered change-history ledger; and explanation + reader-notes content loaded from data. This layer records *what a policy is set to*; the mechanism ACs above record *what a policy does* — the two are one module, sharing `internal/engine/policies/` and `data/policies.json`. Does **not** include the F8 screen that renders this state (`ui.screen.districts`/FEAT-022), the central activity-log "book" (FEAT-093), or any final rate/value figure (Aaron's balance pass).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `PoliciesAPI` exists exposing: a policy-library query (name, category, mechanism, cost, scope, per code.json's "instruments = data-defined coefficient moves"), an enact/repeal command surface, and a scope-resolution query ("scope resolution service for all modules"). Check: `go doc ./internal/engine/policies PoliciesAPI` shows all three surfaces; `grep -rn "func Test.*[Ll]ibrary\|func Test.*[Ee]nact\|func Test.*[Ss]copeResolve" internal/engine/policies/*_test.go` finds coverage.
- **AC-2 (§52 mechanism = data-defined coefficient deltas; GR#15).** Every policy's mechanism is declared in `policies.json` as an explicit list of `(coefficientKey, delta)` pairs, loaded generically (no `switch policy.Name` branching to decide what a policy does). Check: `grep -n "\"mechanism\"\|\"coefficients\"" data/policies.json` matches; `grep -nE "case \"|switch .*[Pp]olicy" internal/engine/policies/*.go` (excluding `_test.go`) finds no name-branching mechanism dispatch.
- **AC-3 (§52 mechanism-vs-mutation consistency — a differential single-field mutation test, per the ASM-257 precedent this BA is following).** Enacting a policy mutates **exactly** the coefficient(s) its `policies.json` entry declares, and nothing else — a passing test enacts a fake policy declaring a single coefficient delta against a snapshot of full engine state, and asserts a field-by-field diff shows only the declared coefficient(s) changed. Check: `grep -rn "func Test.*[Ss]ingleField\|func Test.*[Mm]echanismDiff" internal/engine/policies/*_test.go`. **Lazy implementation this rejects:** a policy that is actually implemented as a hand-written function with side effects beyond its declared mechanism (e.g. a "cycle-priority network" policy that also silently nudges an unrelated pollution coefficient) would pass any check that only asserts "the declared coefficient changed" — the full-state diff catches the undeclared extra mutation the declaration doesn't disclose.
- **AC-4 (§52 preview — same-model, not a second formula; the sprint's hardest AC).** `PreviewImpact(policyID, scope)` computes its projected curve by feeding the **identical** coefficient-delta payload AC-3 proves the real enactment applies into `engine.projections`' registered curve providers (the registered `engine.policies`→`engine.projections` edge) — it is a same-model conditional/what-if query, never an independently-coded estimate formula that merely resembles the real mechanism. Check: a passing test captures the coefficient-delta payload `PreviewImpact` sends to `ProjectionsAPI` and separately captures the payload the real `Enact` path applies for the same policy, and asserts the two payloads are identical (`grep -rn "func Test.*[Pp]reviewMatchesEnact\|func Test.*[Ss]ameModel" internal/engine/policies/*_test.go`). **This is the load-bearing check named in the brief:** a preview built as a plausible-looking but separately-authored quick-estimate (a lookup table, a hand-tuned formula) would satisfy any check that merely asks "does a preview number render" — this check specifically diffs the two code paths' actual inputs to the shared curve machinery, so a parallel-formula implementation fails it even if its output numbers happen to look reasonable.
- **AC-5 (§52 preview confidence/provenance — consistency with `engine.projections.md` AC-6).** `PreviewImpact`'s returned curve carries `engine.projections`' `Computed`/`Extrapolated`/`Unavailable` confidence tag per point (not a policies-local re-invention of that distinction), and no point beyond `ProjectionsAPI`'s current horizon N is ever presented to the caller tagged `Computed`. Check: `grep -n "projections\.Computed\|projections\.Confidence" internal/engine/policies/*.go` shows reuse of the shared type (not a locally-redeclared enum); a passing test queries a preview whose requested range exceeds horizon N and asserts the beyond-horizon portion is not `Computed` (`grep -rn "func Test.*[Bb]eyondHorizonPreview" internal/engine/policies/*_test.go`).
- **AC-6 (§52 preview promise, part 1 — what it promises).** A preview is documented and behaviourally proven to be exactly one thing: a same-model conditional projection of the declared coefficient deltas, carrying `engine.projections`' confidence semantics — **not** a guarantee, not a point estimate with an implied error bar the game never states, and not independent of other decisions the player or the simulation makes between preview and enactment. `doc.go` states this explicitly (AC-15). Check: `internal/engine/policies/doc.go` contains a stated definition of what `PreviewImpact` promises, matching this AC's wording, cross-referenced in AC-15.
- **AC-7 (§52 preview promise, part 2 — what happens when it's wrong; ASM-286).** Every enacted policy's preview snapshot (the coefficient-delta payload and the `Computed`-tagged portion of its curve, per AC-4/AC-5) is persisted at enactment time keyed by a policy-enactment ID. At documented checkpoints after enactment, the actual observed curve values for the same coefficients are compared against the stored preview's `Computed` points; a divergence beyond a documented tolerance (ASM-286 — tolerance/cadence are BA-chosen pending Aaron) raises a registry-sourced `PreviewDrift` event naming the policy, the coefficient, the checkpoint, and the magnitude of the divergence — this is never silently discarded or left for the player to notice on their own. Check: a passing test enacts a fake policy with a synthetic stored preview, advances to a checkpoint with actual state diverging beyond tolerance, and asserts a `PreviewDrift` event fires with the policy/coefficient/checkpoint/magnitude fields populated; a second test feeds actual state within tolerance and asserts no event fires (`grep -rn "func Test.*[Pp]reviewDrift" internal/engine/policies/*_test.go`). **False-pass risk:** a test that only unit-tests the comparator function in isolation (never invoked from the tick pipeline) would pass a build where `PreviewDrift` is correct code that nothing ever calls — the check requires the tick-driven checkpoint evaluation to actually fire the event, not just the comparator's arithmetic to be right.
- **AC-8 (§52 named districts — cell-tagged, ASM-285).** A district is created with a name and a set of cell references (`DistrictID` tagged onto `engine.world` cells, per ASM-285), queryable by name and by ID; renaming preserves the same `DistrictID` and its existing policy/tax scoping. Check: `go doc ./internal/engine/policies CreateDistrict` (or equivalent) exists; a passing test creates a district, renames it, and asserts the `DistrictID`'s scoped policies/cells are unchanged by the rename (`grep -rn "func Test.*[Dd]istrict.*[Nn]ame\|func Test.*[Cc]reateDistrict" internal/engine/policies/*_test.go`).
- **AC-9 (§52 scope resolution service).** `ResolveScope(policyID)` returns the concrete set of affected entities for a policy's declared scope: all cells/roads for `citywide`, a district's cell set for `district`, a named road's edge set for `road` — exposed as a shared query other modules call rather than each reimplementing scope logic locally. Check: `go doc ./internal/engine/policies ResolveScope` exists; a passing test asserts each of the three scope kinds resolves to the expected entity set for a fixture district/road (`grep -rn "func Test.*[Rr]esolveScope" internal/engine/policies/*_test.go`).
- **AC-10 (§52 interaction/compounding — shown, not silently summed).** Two enacted policies with overlapping coefficient targets in the same scope produce a combined effect that is (a) different from either policy's individual declared magnitude in a documented way (e.g. diminishing-returns or multiplicative combination — the specific rule is data-declared, not this AC's to pin) and (b) itself queryable as a distinct value, not only visible by the player doing arithmetic on two separate numbers. Check: `go doc ./internal/engine/policies` shows a combined-effect query distinct from per-policy queries; a passing test enacts two overlapping fake policies and asserts the combined-effect query differs from the naive sum of the two individual declared deltas (`grep -rn "func Test.*[Cc]ompound" internal/engine/policies/*_test.go`).
- **AC-11 (§52 conflict warnings; ASM-288).** `policies.json` declares `conflictsWith` pairs per policy (GR#15 — not hardcoded pairs in Go); enacting a policy that conflicts with an already-active policy **in an overlapping scope** raises a queryable, non-blocking warning (§52 says bundles "warn", not "are prevented") — the second policy still enacts. Check: `grep -n "conflictsWith" data/policies.json` matches; a passing test enacts a conflicting pair in overlapping scope and asserts both a warning is queryable **and** the second policy's status is active, not rejected (`grep -rn "func Test.*[Cc]onflictWarn" internal/engine/policies/*_test.go`).
- **AC-12 (§52 named districts as identity — Name exposed, firm-location logic out of scope).** A district's `Name` is exposed as queryable metadata other modules can read (feeding firm location/reputation per §52's "the name is a mechanic" — the actual consumption by `engine.firms` is a Sprint-10, out-of-scope concern). ## Policy configuration-state layer (folded from feat.policy/FEAT-091, ASM-942)

The ACs below are the configuration-state half of MOD-064, folded from the superseded `feat.policy` (FEAT-091). They share the same `internal/engine/policies/` package and the same `data/policies.json` as the mechanism ACs above. **Design (Aaron, 2026-08-15, BOW FEAT-091):** player-set policies are GLOBAL, but zones (business district, industrial, recreational) can override with different policies (e.g. dwelling 'no trucks at weekends'); every policy has a detailed explanation + reader notes + [auto]/[manual] values, with a change history so the player sees every change. **Role split:** this layer records *what a policy is set to* (the global value, per-zone override, auto/manual mode, append-only change history, explanation/reader-notes content); the mechanism ACs above record *what a policy does* (coefficient-mutation, preview, scope resolution, compounding/conflict). This layer does **not** re-implement the mechanism. **Balance-number regime (standing, same convention as `engine.finance.md` AC-21 / `feat.maintenance.md` / `data.taxinstruments.md` AC-9):** every numeric policy figure — valid value ranges, auto-value defaults, any per-zone multiplier — is a **placeholder** in `data/policies.json` (extended per ASM-784), each carrying a disclosure comment naming it pending Aaron's balance pass. No AC may be satisfied by a junior inventing a final value; every AC touching a value requires it to live in data and requires tests to check **direction/structure** (override differs from global; auto value tracks its documented input; a mode switch is recorded), never a specific figure. **Status note:** the feat.policy draft-ahead caveats (no `feat.policy` code.json entry, `internal/engine/policies/` not on disk, `data/policies.json` a 36-byte stub) are resolved by this supersession — there is one registered `engine.policies` entry and one shared package.

### Functional — global + zone override

- **AC-20 (GR#20; code.json inbound contract — the surface exists, registered, and is not reachable by direct UI import; folded from feat.policy AC-1).** A `PolicySettingsAPI` (or equivalent, name per ASM-783) exists exposing at minimum: set/clear a global setting, set/clear a zone override, resolve the effective setting for a zone, set the auto/manual mode, query the change history, and query explanation/reader-notes. The surface lives on the shared `internal/engine/policies/` package and imports **no** `internal/ui/...` package — the F8 screen consumes it through `int.protocol`, never by direct import. Check: `go doc ./internal/engine/policies PolicySettingsAPI` (or the named surface) shows the setting/override/resolve/mode/history/content surfaces; `go list -deps ./internal/engine/policies/...` shows no `internal/ui/...` import; `grep -rn "func Test.*[Ss]ettings\|func Test.*[Oo]verride\|func Test.*[Hh]istory\|func Test.*[Ee]xplanation" internal/engine/policies/*_test.go` finds coverage. **False-pass risk:** a surface that exists but is only reachable by `ui.screen.districts` importing the package directly (rather than via `int.protocol`) would pass a "the functions exist" read while breaking the GR#20 UI/engine split every other module enforces — the check requires the no-UI-import property explicitly.

- **AC-21 (global + zone override — the headline property; a differential single-field test; folded from feat.policy AC-2).** Each policy carries exactly one global setting; any of the eight §34 zone classes may additionally carry an override. The effective setting for a zone is the override when one exists, else the global — and setting a zone override mutates **exactly** that (policy, zone) cell, leaving the global value and every other zone's override byte-identical. Check: a passing test sets a global value, then a `dwelling` override, and asserts (a) resolving `dwelling` returns the override while resolving `shop` returns the global, and (b) a field-by-field diff of full settings state before/after the override shows only the `dwelling` cell changed (`grep -rn "func Test.*[Ss]ingleField\|func Test.*[Oo]verride.*[Ii]ndependent\|func Test.*[Gg]lobalVsZone" internal/engine/policies/*_test.go`). **Lazy implementation this rejects:** an override that is implemented as a global rewrite (setting `dwelling` also flips the global) would pass a "dwelling now returns the override" check while silently breaking every other zone — the full-state diff catches the undeclared mutation, exactly the ASM-257 single-field precedent AC-3 above already established.

- **AC-22 (zone override key = the §34 `ZoneType` enum, closed and data-derived; ASM-780; folded from feat.policy AC-3).** The override key is `engine.build`'s §34 eight-way `ZoneType` (`dwelling`, `shop`, `office`, `entertainment`, `farming`, `manufacturing`, `heavy_industry`, `mining`), sourced from `engine.build`'s own catalogue — **not** a free string, and **not** the BOW description's illustrative naming ("business district / industrial / recreational"). An override for anything outside that closed enum is rejected. Check: `grep -n "ZoneType\|ZoneTypes\|ZoneTypeByID" internal/engine/policies/*.go` shows reuse of `engine.build`'s type (not a locally-redeclared string enum); a passing test sets an override keyed `dwelling` and asserts resolving `dwelling` differs from resolving `shop`, and a second test asserts an override keyed to a non-§34 string is rejected (`grep -rn "func Test.*[Zz]oneKey\|func Test.*[Zz]oneOverride.*[Ee]num" internal/engine/policies/*_test.go`). **Cross-note (folded from feat.policy cross-check, ASM-416/ASM-595):** `data/tax_instruments.json` already keys zone overrides by the §34 eight-way class set, but with a known casing defect (`heavyIndustry` vs the authoritative `heavy_industry`, ASM-595). This AC keys the same closed enum but mandates the authoritative `engine.build` casing, so "zone" means one thing across tax and policy and the tax-side casing bug is not silently inherited here. **False-pass risk:** a `map[string]T` keyed by free string would accept "dwelling" and "dwelling " as two different zones, or accept a typo silently — the closed-enum check is what makes "the dwelling override" a well-defined, single concept rather than a string-matching accident.

### Functional — [auto]/[manual] values

- **AC-23 ([auto]/[manual] per-setting; auto is deterministic engine-derived, manual is persisted; ASM-781; folded from feat.policy AC-4).** Each setting (each global value and each zone override) carries a mode: **manual** = the value is exactly what the player set, persisted and stable across ticks until changed; **auto** = the value is computed by a documented, deterministic, per-policy engine function whose source is data-declared. Switching a setting to auto immediately reflects the computed value, and re-running the auto computation on identical engine state is byte-identical (GR#21). (This reads "values" as *per-setting* mode — each global value and each override carries its own; if a single per-policy mode was intended, this collapses trivially.) Check: a passing test (a) sets a manual value and asserts the resolved value equals it exactly across two ticks, (b) switches the same setting to auto and asserts the resolved value equals the engine's computed value, and (c) mutates the input the auto source reads and asserts the auto value changes directionally (never a pinned figure) and deterministically (`grep -rn "func Test.*[Mm]ode\|func Test.*[Aa]utoVsManual\|func Test.*[Aa]uto.*[Dd]eterministic" internal/engine/policies/*_test.go`). **False-pass risk:** an "auto" mode that is really a fixed default constant baked in code (never re-derived from current engine state) would pass a "the mode field flips" grep while the design's delegation promise — the game manages the lever as conditions change — is unmet; the check requires the auto value to track its documented input, not merely to exist.

### Functional — change history

- **AC-24 (change history — append-only, ordered, every change recorded; "the player sees every change"; ASM-785; folded from feat.policy AC-5).** Every mutation — setting/clearing a global value, setting/clearing a zone override, switching auto/manual mode, repealing a policy — appends one entry to a queryable, append-only history ledger keyed by policy (and scoped where relevant), recording the old value, the new value, the mode, the source (manual/auto), and the simulation month. The ledger is ordered; a later entry never rewrites an earlier one. Check: a passing test performs three mutations on one policy, then queries the history and asserts exactly three entries in mutation order with correct old→new transitions; a second test asserts the history surface exposes no mutation/rewrite of an existing entry (append-only) (`grep -rn "func Test.*[Hh]istory.*[Oo]rder\|func Test.*[Aa]ppendOnly\|func Test.*[Cc]hangeHistory" internal/engine/policies/*_test.go`). **False-pass risk:** a history that recomputes "current value only" (no per-change record) would pass a "history is queryable" grep while the player can never see the *sequence* of changes the design promises — the check requires the ordered list of transitions, not just a present-state read.

- **AC-25 (explanation + reader notes — content from data, never hardcoded prose; ASM-784; folded from feat.policy AC-6).** Every policy's detailed explanation and reader notes are loaded from `data/policies.json` (extended per-policy), keyed by policy, and surfaced through the query API. Check: a passing test queries a fixture policy's explanation/reader-notes and asserts the returned text matches the data-file entry; a second test edits the explanation text in the data fixture between two loads and asserts the queried text changes without a code change (`grep -rn "func Test.*[Ee]xplanation.*[Pp]rovenance\|func Test.*[Rr]eaderNotes\|func Test.*[Cc]ontent.*[Dd]ataDriven" internal/engine/policies/*_test.go`). **False-pass risk:** prose baked into `internal/engine/policies/*.go` as string literals would pass a "the field renders" grep while the design's "every policy has detailed explanation + reader notes" becomes code-shipped content that a balance/edit pass can't touch without a rebuild — the check requires the content to trace to data.

### Functional — single source of truth and the boundary to the mechanism

- **AC-26 (effective-value resolution is the single source of truth — GR#3; folded from feat.policy AC-7).** The effective setting for a (policy, zone) pair is resolved by one pure function on the settings surface; consumers query it rather than re-deriving override-else-global themselves. The resolution is a pure function of (settings state, policy, zone) — same inputs, same output, no hidden state. Check: a passing test queries the same (policy, zone) twice with identical state and asserts byte-identical results, and asserts a fixture consumer that reads the resolved value (not raw global + raw override + its own `if override != nil` logic) gets the same answer (`grep -rn "func Test.*[Rr]esolve.*[Pp]ure\|func Test.*[Ee]ffective.*[Dd]eterministic" internal/engine/policies/*_test.go`). **Lazy implementation this rejects:** two modules each reimplementing "override if present else global" would drift the moment a third scope kind is added — the single resolution function is what keeps "what is this policy set to here" a one-word answer.

- **AC-27 (boundary — the settings surface records configuration, it does not mutate coefficients; that is the mechanism AC-2/AC-3 above; folded from feat.policy AC-8).** Setting a policy value (global or override) records the configuration and its history and resolves the effective value; it does **not** itself mutate the coefficient(s) the policy targets. The coefficient effect of the resolved value is the mechanism (AC-2/AC-3), applied by the engine, not a configuration-local mutation. Check: `grep -nE "coefficient|Coefficient" internal/engine/policies/*.go` on the settings surface finds **no** coefficient-mutation code (references to the concept are fine; a mutation is not); a passing test sets a value and asserts the settings/history state changed while no coefficient delta was applied by the settings surface itself (`grep -rn "func Test.*[Bb]oundary\|func Test.*[Nn]oMechanism" internal/engine/policies/*_test.go`). **False-pass risk:** a settings surface that also reaches into the mechanism and applies the coefficient delta would pass every configuration AC while silently duplicating the mechanism's job (a second source of truth for "what this policy does"), the exact GR#3 violation this AC exists to catch.

### Error handling (configuration)

- **AC-28 (GR#7 — invalid operations; folded from feat.policy AC-9).** Setting/clearing a global or override value for an unknown `PolicyID`, an override for a non-§34 zone key (AC-22), a manual value outside the policy's data-declared valid range, or an unknown mode, each returns a registry-sourced error (a new `MET-`-range code claimed at build time) naming the policy/scope/value — never a silent no-op, never a coerced-to-nearest-valid-value false success. - **AC-29 (GR#7 — malformed configuration data; folded from feat.policy AC-10).** A malformed or schema-invalid policy data file (a missing explanation or reader-notes field, an auto-source referencing an unknown input, a valid-range whose lower bound exceeds its upper bound, an explanation/reader-notes field that is not a string) produces a registry-sourced error at load time identifying the offending policy/field — never a silent empty-string default that would mask a data-authoring bug. Check: `grep -n "MET-" internal/engine/policies/*.go` finds a load-time registry code distinct from AC-28's; passing test coverage (`grep -rn "func Test.*[Mm]alformed.*[Pp]olicy\|func Test.*[Ii]nvalid.*[Pp]olicyContent" internal/engine/policies/*_test.go`) asserts the error's registry code matches **and** that no default-substituted explanation/reader-notes/range was loaded in place of the malformed one.

### Determinism, safety & type-safety (configuration)

- **AC-30 (GR#21 — deterministic auto computation and deterministic history ordering; extends AC-14 to the settings/history surfaces; folded from feat.policy AC-11).** Auto-value computation and history enumeration are deterministic: any iteration over settings/history that feeds output is sorted by a documented stable key (e.g. `PolicyID` then zone, and for history the append sequence — simulation month + sequence number), never dependent on unordered map iteration.
