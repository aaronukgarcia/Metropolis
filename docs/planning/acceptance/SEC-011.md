# Acceptance criteria — terminal-escape injection at the render boundary (SEC-011)

**BOW code:** SEC-011 (P1, open) — linked to SEC-022 (done) and ASM-060 per Bill's 2026-08-09 comment on the finding.
**Spec refs:** `docs/planning/dev-team-process.md` v1.8, Weakness pattern #4 ("a value in a privileged position is input, however inert it looks" — SEC-011's own row: "any rendered string... terminal control bytes"); Weakness pattern #3 ("fix the class, not the demonstrated instance" — this file's whole reason for existing per Bill's reframing); GR#1 (aggressive error trapping does not license unfiltered display of arbitrary bytes).
**Date:** 2026-08-10
**Status:** active
**Package under test:** `internal/ui/core/` (primary — see AC-1's centralisation rationale), with regression coverage over the finding's cited call sites in `internal/ui/widgets/` and `internal/ui/screens/debug/`.
**Standard gates:** see `README.md` — SG-1/SG-2/SG-3/SG-6 apply repo-wide as usual; SG-4/SG-7 scoped to `./internal/ui/core/...` plus a full run of `./internal/ui/widgets/...` and `./internal/ui/screens/debug/...` since this fix must not regress any existing widget snapshot test.

## User stories

- As **the terminal the player is sitting at**, I need every byte Metropolis ever writes to me to be either a glyph the UI intended to draw or nothing at all, so a hostile string (a malformed error message, a future save-imported name, a multiplayer peer's text) can never reposition my cursor, clear my scrollback, or spoof my window title.
- As **a future widget author**, I need the protection to live at the one place every widget already funnels through, so I cannot forget to apply it — this is Weakness pattern #1's rule ("if an invariant matters, the API must make violating it impossible or loud") applied to a rendering boundary instead of a data boundary.
- As **Bill**, I need this written as a rule with a mechanical check, not a list of patched call sites, per the reframing on the finding: SEC-011 (UI cell buffer) and SEC-022 (an `%s`-formatted hostile hash reaching stderr, already fixed) are the same root cause in two different surfaces, and a third surface nobody has looked at yet is exactly what Weakness pattern #3 predicts exists.

## Scope

A single, unbypassable filtering choke point for every rune that reaches a terminal cell via `internal/ui/core.Buffer`, plus a structural check that no code path can reach the real screen without passing through it. Regression coverage over the finding's five cited call sites. Does **not** re-open SEC-022 (already fixed, `serialize`/`metctl`) — it is cited here only as the sibling proving the root cause is repo-wide, per Bill's framing.

## Acceptance criteria

### Functional

- **AC-1 (the centralised choke point).** `core.Buffer.Set(x, y int, r rune, style tcell.Style)` (`internal/ui/core/buffer.go`) is the single point every draw path in `ui.core`/`ui.widgets`/`ui.screen.debug` already funnels through to place a rune in a cell (confirmed by the finding's own reading of every call site in scope: `border.go`'s `drawTitle`, `table.go`'s `drawRow`, `queuelane.go`, `bignum.go`'s `drawText`, `screens/debug/render.go`'s `drawText`/`cursor.line`). Rather than patching each of those five call sites individually (Weakness pattern #3's exact anti-pattern), `Buffer.Set` itself gains the filter: any rune for which `unicode.IsPrint(r) == false`, **except** the runes this package's own widgets deliberately emit outside the "printable" definition (box-drawing `─│┌┐└┘├┤`, Braille U+2800–U+28FF, block-fill `▁▂▃▄▅▆▇█▓▒░`), is replaced with a single documented placeholder rune (e.g. `·` or `□` — Tester confirms whichever the implementation picks is applied consistently and documented) before the cell is written. Check: `go doc ./internal/ui/core Buffer.Set` states the filtering behaviour in its doc comment; a passing test calls `Buffer.Set` directly with `'\x1b'` (ESC), `'\a'` (BEL), and `'\r'` and asserts the stored cell content is the placeholder, never the control rune.
- **AC-2 (regression, not re-derivation).** Each of the finding's five cited call sites is exercised end-to-end (not just at the `Buffer.Set` unit level) with a string containing an embedded ESC byte, and the test asserts the flushed buffer contains no raw control rune anywhere in that widget's drawn region. Check: `go test ./internal/ui/widgets/... ./internal/ui/screens/debug/... -run TestSEC011 -race -count=1 -v` passes, with one subtest per cited call site (`border.go` title, `table.go` cell, `queuelane.go` label, `bignum.go` label/value, `screens/debug/render.go` error-tail message — the exact `errs.Entry.Msg` path the finding names).
- **AC-3 (the whitelist is exhaustive and closed).** The set of "printable per this package" runes is a single named list/function (not scattered `unicode.IsPrint(r) || r == '─' || r == '│' || ...` repeated at each call site) that every widget's own glyph tables (`sparkGlyphs`, box-drawing set, Braille set, gauge fill set) are checked against in a test, so a future widget adding a new glyph rune has one place to register it and a test that would fail if it forgot. Check: `grep -n "func.*[Pp]rintable\|isDrawable" internal/ui/core/*.go` finds the single function, and a passing test asserts every rune in each existing widget's glyph table passes it.

### Determinism & safety

- **AC-4 (GR#21, Pattern #1 — cannot be broken through the public API).** `Buffer.Set` is the **only** call in the `ui.core`/`ui.widgets`/`ui.screen.debug` packages that invokes `tcell.Screen.SetContent` (directly or transitively) — i.e. there is no second, unfiltered path to the real screen a future widget could reach for. Check: `grep -rn "SetContent(" internal/ui/core/*.go internal/ui/widgets/*.go internal/ui/screens/debug/*.go` (excluding `_test.go`) shows exactly one production call site, inside `core.Buffer`'s own flush path, and it is downstream of the AC-1 filter (i.e. `Buffer.Set` populates the cell that flush later reads — there is no route that writes a cell and skips `Set`). This is the criterion that makes the invariant "every rune is filtered" true by construction rather than by convention, per Weakness pattern #1's own wording: a comment saying "always call Set" is not a control, this AC is.
- **AC-5.** The filter adds no allocation on `Buffer.Set`'s hot path — a `-benchmem` benchmark on `Buffer.Set` reports the same `0 allocs/op` figure it reported before this fix (or the Tester records the delta and escalates if it regressed, per `ui.widgets`' own AC-13 zero-allocation contract that this package shares).

### Error handling

- **AC-6.** A string containing control bytes reaching a draw path is **not** an error condition (rendering a filtered/degraded glyph is the correct, silent-to-the-player behaviour for display text — this is the one place in the security sweep where "sanitise, don't reject" is the right call, not pattern #4's usual "reject, never repair," because the alternative to filtering here is refusing to render the F12 error tail at all, which is worse for GR#1's "aggressive error trapping... selectable display" than a filtered display) — but the **fact** that a filtered rune was encountered is observable for diagnosis: check that `Buffer.Set`'s doc comment or a companion counter/log records at least a total-filtered-count (not necessarily per-occurrence, to avoid the filter itself becoming a new logging-volume DoS vector) so a operator/tester can tell the filter fired versus never being exercised.

### Documentation

- **AC-7.** `internal/ui/core/doc.go` (or `buffer.go`'s own doc comment) states the rule this fix establishes — "every rune written to a Cell is filtered for printability at `Buffer.Set`; there is no second path to the screen" — and cites SEC-011, so a future reader understands this is a security boundary, not an incidental implementation detail.
- **AC-8.** A note is added (package doc or `docs/design/`) cross-referencing SEC-022 as the same root cause in `serialize`, and stating the general rule for the rest of the codebase: **any field a package's own doc comment identifies as untrusted/attacker-controlled/hostile must never be formatted with a bare `%s` (or written raw to a `Buffer`/terminal/log) without passing through a boundary filter (`%q` for error/log text, `Buffer.Set`'s printability filter for rendered text)** — this is the "rule and a way to check it" Bill asked for in place of patching sites one at a time. The "way to check it": a repo-wide grep-based spot-check, `grep -rn "untrusted\|attacker-controlled\|hostile" --include=*.go -l internal/ | xargs grep -n '%s'`, is documented as a manual QA/Destructive-agent check (not fully automatable without a stricter tagging convention — see Escalations) run at least once per security sweep, so the next surface (Weakness pattern #3's prediction) is looked for on a cadence rather than only when someone happens to notice.

## Out of scope

- Re-verifying SEC-022's fix (`serialize`/`metctl`, already `done`) — cited here only as the sibling establishing the root cause is repo-wide.
- A fully automated, zero-false-negative static check for "every untrusted field is safely formatted everywhere in the repo" — see Escalations; today's tooling (grep on doc-comment keywords) is a spot-check, not a proof.
- Any change to what counts as "printable" for player-facing *content* glyphs the game legitimately wants to draw (e.g. a future emoji/CJK citizen-name feature) — that is a fidelity/i18n decision for whoever builds that feature, not this fix's call to make.

## Escalations

- **Open judgement call, logged as an assumption (see report):** Weakness pattern #4 says "reject, never sanitise" for hostile values in a privileged position. This item's fix is a sanitiser (replace, don't reject) by design — rejecting would mean refusing to render the F12 error tail (or any widget) whenever an upstream string contains one bad byte, which trades a display glitch for an outage of the exact diagnostic surface GR#1 requires. I am treating "reject, never sanitise" as scoped to *structural/identity* data (path names, commands — where sanitising creates aliasing/ambiguity, per `ValidateShardName`'s own reasoning) and *not* to display text, where a bounded, documented, allocation-free replacement is the correct boundary control. This is a reading of an ambiguous rule application, not a spec decision — logging it as `ASM-` per v1.7, `--code-path internal/ui/core/buffer.go --codejson ui.core`.
- **No further escalation needed on the fix shape itself** — AC-1/AC-4 together satisfy Pattern #1 (invariant unbreakable through the public API) without weakening anything.
- **ASM-077 (policy-scope fold, SEC-011):** this item's sanitiser-vs-reject choice is the recorded answer to ASM-077 — Weakness pattern #4's "reject, never repair" is scoped to *identity/path data* (where sanitising creates aliasing/ambiguity) and does **not** apply to *display text*, where a bounded, documented, allocation-free replacement is the correct boundary control. Display text stays sanitise-don't-reject by design (AC-1/AC-6).
