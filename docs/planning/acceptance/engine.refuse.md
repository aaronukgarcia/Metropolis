# Acceptance criteria — engine.refuse (MOD-039)

**BOW code:** MOD-039
**Spec refs:** §25 Refuse Collection & the Waste–Health Loop (`docs/METROPOLIS-MASTER-v2.1.md` lines 406-409: per-cell waste generation into bin stock — residential wheelie/commercial trade/industrial skip, differing capacities; scheduled rounds run by real trucks on real roads from depots/transfer stations, auto-optimised, player-overridable, consuming road space and fuel like any freight; missed collections — truck shortage, gridlock, strike event, depot underfunding — leave bin overflow → vermin index up → local physical health down, land value down, fire risk up, ticker names the street; streams: general→landfill/incinerator, recycling with player-set service level and contamination reducing resale, food waste→composting→farm input §31; landfills fill *permanently* and blight; incineration trades airshed pollution for energy; exhausted sites can be capped and reclaimed as parkland §32; "the loop: waste budget cuts are invisible for months, then vermin, then illness, then emigration — a classic Detroit on-ramp"); §31 Farming & the Biodiversity Engine (lines 441-448, the compost→farm-input consumer of the food-waste stream); code.json `engine.refuse` entry (inbound `RefuseAPI`, "rounds are logistics movements; overflow states per cell", consumers: `engine.farming`; outbound calls `engine.logistics`, `engine.services`, `engine.wellbeing`, `engine.farming`).

## User stories

- **US-1.** As every occupied cell, I need waste generated each tick into a typed bin stock (wheelie/trade/skip) with a documented capacity, so overflow is a real state transition, not a flavour description.
- **US-2.** As `engine.logistics` (MOD-025, a registered outbound dependency), I need refuse rounds expressed as ordinary logistics movements (per code.json's "rounds are logistics movements" pattern) — trucks from depots on real roads, consuming junction slots and fuel like any freight — so refuse does not reimplement a second truck-routing model.
- **US-3.** As `engine.wellbeing` (a registered outbound dependency), I need overflow to feed the physical-health driver's pollution/vermin term through the registered `WellbeingAPI`, so the health consequence of a missed round is a live query, not a duplicated health table.
- **US-4.** As `engine.services` (a registered outbound dependency, MOD-033), I need refuse crews staffed from the Public Service Pie's refuse-crew benchmark ratio and refuse funding to gate round frequency/reliability through the generic service-funding→quality function, so a refuse budget cut is felt exactly like any other service cut.
- **US-5.** As the player watching the ticker, I need a missed collection to name the affected street, so the consequence is legible and locatable, not an aggregate city-wide number.
- **US-6.** As `engine.invariant` (MOD-019), I need refuse tonnage registered as a conserved stock the moment this module exists, so "conservation invariants extended to each new stock" (the S9 exit gate) is true of refuse specifically, not merely asserted.
- **US-7.** As `engine.farming` (§31, now a registered consumer — the `engine.refuse`↔`engine.farming` edge landed in c36778b), I need the food-waste→compost→farm-input chain to be a real, queryable output, not a described-but-inert flavour loop.

## Scope

Per-cell waste generation into typed bin stock; scheduled, auto-optimised, player-overridable collection rounds expressed as `engine.logistics` movements; missed-collection overflow states with the documented downstream chain (vermin → physical health → land value → fire risk, ticker-named); the three waste streams (general→disposal, recycling with contamination, food→compost); landfill/incineration disposal-site lifecycle (fill, blight, cap-and-reclaim per §32); mass-conservation accounting for refuse tonnage as a new invariant-checker stock.

## Acceptance criteria

### Functional — waste generation and bin stock

- **AC-1 (GR#20; code.json inbound contract).** A `RefuseAPI` exists exposing per-cell bin-stock queries (level, capacity, type) and round-scheduling/override commands, matching code.json's documented pattern "rounds are logistics movements; overflow states per cell". Check: `go doc ./internal/engine/refuse RefuseAPI` shows both a bin-stock query surface and a command surface for round overrides; `grep -n "func.*Override" internal/engine/refuse/*.go` confirms player overrides are commands, not direct field writes.
- **AC-2 (§25 typed bin stock).** Every occupied cell carries a bin stock typed by land use — residential wheelie, commercial trade bin, industrial skip — each with a distinct, documented capacity, and waste is generated into it each tick from the cell's §17-consumption-coefficient-derived waste rate. Check: `go doc ./internal/engine/refuse BinStock` (or equivalent) shows the three types with distinct capacity fields; a passing test asserts a residential and an industrial cell of identical population/output generate into stocks with different capacities (`grep -rn "func Test.*[Bb]inType\|func Test.*[Cc]apacity" internal/engine/refuse/*_test.go`).
- **AC-3 (§25 three streams).** General waste, recycling (with a player-set service level and a contamination factor that reduces recycling resale value), and food waste (routed to composting) are tracked as three distinct sub-stocks per cell, not one undifferentiated waste number split only at disposal time. Check: `go doc ./internal/engine/refuse` shows three named stream accessors; a passing test asserts raising the contamination input lowers the recycling stream's resale-value output while leaving the general and food streams unaffected (`grep -rn "func Test.*[Ss]tream\|func Test.*[Cc]ontamination" internal/engine/refuse/*_test.go`). **Lazy implementation this rejects:** a single blended "waste" number with a recycling percentage applied only at the point of disposal would satisfy "recycling exists" on a shallow read but couldn't isolate a contamination effect from a collection-rate effect — the check requires contamination to move only the recycling stream's own output.

### Functional — collection as logistics movements

- **AC-4 (§25; US-2; GR#20 outbound contract).** Scheduled collection rounds are literally `engine.logistics` movements — trucks depart depots/transfer stations, consume junction slots and fuel, and travel real roads — reusing `LogisticsAPI`'s existing stock-draw/movement machinery (per `engine.logistics.md` AC-8's "same underlying type/method set, not merely a similarly-named one" precedent) rather than a bespoke refuse-only truck model. Check: `grep -rn "logistics\.(Movement|Draw|Stock)" internal/engine/refuse/*.go` (excluding `_test.go`) shows refuse rounds constructed through `engine.logistics`'s exported movement type, not a parallel `RefuseTruck` type with independent scheduling logic; a passing test asserts a saturated junction on a refuse truck's route produces the same next-day-queue behaviour `engine.logistics.md` AC-4 defines for any other movement (`grep -rn "func Test.*[Rr]ound.*[Mm]ovement\|func Test.*[Tt]ruckQueue" internal/engine/refuse/*_test.go`). **False-pass risk:** a `RefuseTruck` type that merely looks similar (same field names) but is scheduled by independent code would pass a naming grep while never actually contending for the junction slots `engine.logistics` tracks — the check requires the saturation scenario to reproduce `engine.logistics`'s own queueing behaviour, proving genuine reuse.
- **AC-5 (§25 auto-optimisation, player-overridable).** Round routing/scheduling is auto-optimised by default (a documented objective, e.g. minimising total truck-distance or maximising on-time collection coverage) and the player can override a specific round's route/schedule via a command that takes precedence over the auto-optimiser for that round until cleared. Check: `go doc ./internal/engine/refuse` shows an auto-optimise entry point and an `OverrideRound` command; a passing test asserts an overridden round's actual route differs from the auto-optimiser's output and persists across the next optimisation pass until explicitly cleared (`grep -rn "func Test.*[Oo]verride" internal/engine/refuse/*_test.go`).
- **AC-6 (§25 missed collection causes).** A round can fail to complete (truck shortage from the refuse-crew staffing pool, gridlock delay exceeding the round's time window, a strike event, or depot underfunding), and each cause is independently constructible in a test — a single generic "collection failed" boolean is insufficient because the spec names four distinct causes with (implicitly) distinct downstream framing in the ticker. Check: `go doc ./internal/engine/refuse` shows a typed miss-cause field/enum with at least the four named values; a passing test constructs each cause independently and asserts the resulting bin-stock overflow state records which cause applied (`grep -rn "func Test.*[Mm]issedCollection" internal/engine/refuse/*_test.go`).

### Functional — overflow chain and disposal lifecycle

- **AC-7 (§25 overflow chain, the causal spine of this module).** A cell whose bin stock exceeds capacity (missed collection with continued generation) enters a documented overflow state that drives, in order: a vermin index (rising with overflow duration/magnitude), then a physical-health penalty routed through `WellbeingAPI`'s registered `PollutionExposure`-or-equivalent driver (not a refuse-owned duplicate health number), a land-value penalty, and a fire-risk increase — and the ticker names the affected street. Check: `go doc ./internal/engine/refuse` shows the vermin-index/land-value/fire-risk accessors and a street-naming ticker-event type; a passing test drives one cell into sustained overflow and asserts all four consequences move in the documented direction, with the wellbeing consequence specifically asserted via a call into the registered `WellbeingAPI` (not a locally reimplemented health formula) (`grep -rn "func Test.*[Oo]verflow.*[Cc]hain\|func Test.*[Vv]erminIndex" internal/engine/refuse/*_test.go`). **Lazy implementation this rejects:** a build that computes its own "overflow health penalty" number independent of `WellbeingAPI` would satisfy "health goes down" on a shallow read while duplicating a system `engine.wellbeing` already owns (GR#3 single-source-of-truth) — the check requires the call to cross the registered interface.
- **AC-8 (§25 landfill permanence and blight; §32 reclamation).** A landfill site's remaining capacity only ever decreases (general waste routed there is permanently consumed capacity, never reclaimed by simply stopping input), a full landfill triggers a documented blight effect on its surrounding cells (reusing §32's reclamation/blight mechanic per the spec's explicit "§32 reclamation shares the mechanic" cross-reference, not a refuse-local reimplementation), and a capped, exhausted site can transition to reclaimed parkland via a command, after which it is no longer a valid disposal target. Check: `go doc ./internal/engine/refuse` shows a landfill-capacity accessor that only decreases under load and a `CapAndReclaim` (or equivalent) command; a passing test fills a landfill to capacity, asserts blight applies to a neighbouring cell, then reclaims it and asserts routing further general waste there is rejected (`grep -rn "func Test.*[Ll]andfill.*[Bb]light\|func Test.*[Rr]eclaim" internal/engine/refuse/*_test.go`).
- **AC-9 (§25 incineration trade-off).** Routing general waste to incineration instead of landfill produces energy output (queryable, feeding whatever energy-accounting module later consumes it) at the documented cost of an airshed-pollution term, distinct from and in addition to the overflow-driven `PollutionExposure` term of AC-7 — so a player choosing incineration over landfill faces a real trade-off, not a strictly-dominant option. Check: `go doc ./internal/engine/refuse` shows both an energy-output accessor and an airshed-pollution accessor on the incineration path, with no equivalent airshed term on the landfill path; a passing test asserts routing identical waste volume to incineration vs. landfill produces different pollution profiles (`grep -rn "func Test.*[Ii]ncinerat" internal/engine/refuse/*_test.go`).
- **AC-10 (§31 food-waste→compost→farm-input chain — RE-ARMED 2026-08-11, BUG-100: the `engine.refuse`↔`engine.farming` edge landed in c36778b, both directions).** The food-waste stream's collected tonnage becomes a queryable compost output that is a genuine input value AND is now legally consumable by `engine.farming` — `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.farming'); process.exit(m.outbound.calls.some(c=>c.key==='engine.refuse')?0:1)"` exits 0, confirming the edge (see `engine.farming.md` AC-10, the mirror of this check). This AC requires the compost output to be a real, independently queryable, exported value on `RefuseAPI` — a build that tracks compost tonnage as an internal-only, unexported number satisfies neither GR#3 nor this AC's intent — and, now the edge exists, `engine.refuse`'s own side of the doc.go/Escalations block citation must be removed (it is `engine.farming`'s consumption call that completes the wiring, per that file's AC-10; this file's obligation is only to expose the accessor, which no longer carries a "blocked" caveat). Check: `go doc ./internal/engine/refuse` shows an exported compost-output accessor; a passing test asserts food-waste tonnage collected converts to compost output at a documented (data-sourced, GR#15) ratio (`grep -rn "func Test.*[Cc]ompost" internal/engine/refuse/*_test.go`); `internal/engine/refuse/doc.go` no longer cites BUG-058 as a live block for AC-10.

### Functional — conservation identity (the mass-conservation stock)

- **AC-11 (mass conservation — the strongest available check, per the brief).** For every accounting period (tick or month, documented which), the following identity holds exactly for every waste stream and every cell/city-wide aggregate the module tracks: `TonnesGenerated == TonnesCollected + TonnesUncollected(overflow) + TonnesInTransit(en-route in a logistics movement, per AC-4) + TonnesDisposalBacklog(queued at a landfill/incinerator/compost facility awaiting processing)`. No term may be inferred as a remainder — each is independently computed from its own source (generation from §17 coefficients, collected from completed round deliveries, uncollected from bin-stock overflow state, in-transit from `engine.logistics`'s own movement ledger per AC-4, backlog from the disposal site's own queue) and then the identity is *checked*, not constructed to balance by definition. Check: a passing test runs a synthetic city for several ticks with a mix of successful and missed rounds, independently sums each of the four right-hand terms from its own source accessor, and asserts the sum equals the independently-tracked `TonnesGenerated` figure to an exact (integer-tonnage) or documented epsilon (`grep -rn "func Test.*[Mm]assConserv\|func Test.*[Tt]onnage.*[Ii]dentity" internal/engine/refuse/*_test.go`). **Lazy implementation this rejects:** computing `TonnesUncollected` (or any term) as `TonnesGenerated − (the other three)` rather than from its own independent source would make the identity trivially, tautologically true regardless of a bug in any individual term's real accounting — indistinguishable from correct until a downstream consumer (health, land value) reads a wrong number. The check requires all four terms sourced independently before summing, exactly analogous to `engine.wellbeing.md`'s AC-2/AC-3 pairing (additive identity alone is insufficient; independence of the terms is what makes the identity able to fail).
- **AC-12 (US-6; registration with `engine.invariant` — STILL BLOCKED after c36778b; BUG-100 tripwire applied).** Refuse tonnage (per AC-11's identity) is registered as a conserved stock with `engine.invariant`'s (MOD-019) registry, per that module's documented "registration seam for adding new conserved stocks" (`engine.invariant.md` US-5), so a bug that silently creates/destroys tonnage is caught by the standing invariant-checker infrastructure every tick, not only by this package's own test suite. **Blocked — edge still absent (BUG-058 closed, c36778b):** code.json still shows (a) no `engine.refuse`→`engine.invariant` outbound call edge — c36778b registered `engine.refuse`↔`engine.farming`, not this edge — and (b) `engine.invariant`'s own inbound contract is populated only by `engine.citizens`/`engine.finance`/`engine.traffic`, `engine.refuse` still absent. The edge is now governed by the collaborations gate (declare `engine.invariant` in this module's `collaborations.consumesFrom` in `master-plan-v2.1.json` to have `generate.js` enforce it), rather than "pending BUG-058". The package must still pass AC-11's local identity test (which needs no cross-module edge) as the interim proof of correctness. **Tripwire (mechanical, not a prose label — BUG-100):** `node -e "const m=require('./code.json').modules.find(x=>x.key==='engine.refuse'); process.exit(m.outbound.calls.some(c=>c.key==='engine.invariant')?1:0)"` must exit **0** (edge still absent). A nonzero exit means the edge has landed and this AC is stale, unarmed prose that MUST be rewritten to the real check before the next commit touching `internal/engine/refuse/`; Tester/CI treat a nonzero exit here as a hard FAIL, not a silent pass. Until the tripwire fires: once unblocked, `grep -n "invariant\.Register" internal/engine/refuse/*.go` shows a registration call at package init/boot; until then, `internal/engine/refuse/doc.go` states the block (edge absent) explicitly, noting BUG-058 is closed and the edge is governed by the collaborations gate.

### Error handling

- **AC-13 (GR#7).** Scheduling a round against an unregistered depot ID, or querying bin stock for a cell with no registered land-use type, returns a registry-sourced error (new `MET-E`-range code, claimed against `data/errors.json`'s reserved table at build time — no `engine.refuse` sub-range exists yet) rather than a silently-created zero-value stock entry. Check: `grep -n "MET-" internal/engine/refuse/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Uu]nregisteredDepot\|func Test.*[Uu]nknownCell" internal/engine/refuse/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no zero-value stock entry was created, not merely that a matching-named test function exists.
- **AC-14.** A round-override command targeting a round that has already completed, or a negative/over-100% contamination or funding input, is rejected with a typed error, never silently clamped or silently ignored. Check: passing test coverage (`grep -rn "func Test.*[Ii]nvalidOverride\|func Test.*[Oo]utOfRange" internal/engine/refuse/*_test.go`).

### Determinism, safety & scale

- **AC-15 (GR#21).** Round auto-optimisation, overflow accumulation, and disposal-site allocation are deterministic functions of `(worldSeed, tick, prior state, commands)` — repeated runs from identical starting state and command sequence produce byte-identical bin-stock levels, overflow states, and landfill capacities, across worker counts. Check: `grep -rn "func Test.*[Dd]etermnis\|func Test.*[Dd]eterminis" internal/engine/refuse/*_test.go`.
- **AC-16 (SG-7; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/refuse/*.go` (excluding `_test.go`) returns no matches.
- **AC-17.** `go test ./internal/engine/refuse/... -race -count=1` passes; `grep -n "go func()" internal/engine/refuse/*_test.go` finds at least one concurrency test (concurrent round processing across depots within a tick).
