## User stories

- **US-1.** As `engine.attract` (the S6 exit-gate consumer), I need `HouseholdsAPI` to expose overcrowding, rent-burden, and an "unhoused-by-preference" signal per household/district, so the master dial's `housingAffordability` term reflects real mismatch, not just a vacancy count.
- **US-2.** As `engine.citizens`, whose own `Household` entity and partnering event already exist (citizens.md AC-12), I need `engine.households` to consume that entity via `CitizensAPI` rather than re-implement formation, so household membership has exactly one source of truth (GR#3) — see ASM-247's boundary ruling.
- **US-3.** As the housing-demand model, I need citywide demand expressed as a *distribution* over the 17 documented typologies (weighted by household stage × wealth × personality), so "a city of identical blocks leaves whole personality segments unhoused-by-preference" (§21) is a real, testable outcome, not a single aggregate number that vacancy alone could satisfy.
- **US-4.** As a player reading F6, I need demand-vs-stock mismatch by type to be a queryable, per-typology figure, so under-provision of a segment (e.g. no retiree housing while retirees keep arriving) is visible before it silently suppresses attractiveness.
- **US-5.** As GR#15, I need the 17 typologies, their density/unlock data, and their appeal tags loaded from `data/buildings.json`'s `HS` section — never hardcoded — so Batch tuning changes a data file, not Go source.

## Scope

Housing-demand modelling for the 17 `HS`-catalogue typologies: dwelling-size preference (personality/wealth-driven), per-typology appeal profiles (interpreting `buildings.json`'s tag-based `appealProfile` arrays against household stage × wealth × personality — the translation layer per ASM-248), citywide demand as a distribution over types, the unhoused-by-preference signal, and overcrowding/rent-burden derivation from household composition and dwelling capacity. Household *formation itself* (partnering events, `householdId` assignment) is `engine.citizens`' entity per its own AC-12 and is consumed here via `CitizensAPI`, not re-implemented (ASM-247).

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `HouseholdsAPI` exists matching code.json's registered inbound contract — query methods (per-household composition, per-typology appeal/demand, per-district overcrowding/rent-burden/unhoused-by-preference) plus mutation paths expressed only as commands — consumed by `engine.attract` and `ui.screen.demo` through this interface alone. Check: `go doc ./internal/engine/households HouseholdsAPI` shows query methods (e.g. `DemandByType`, `OvercrowdingOf`, `RentBurdenOf`, `UnhousedByPreference`) and a command-based mutation path; `grep -rln "households\.\w\+\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/households` and `_test.go`) finds no direct exported-field writes from another package.
- **AC-2 (§5.4; boundary per ASM-247).** `engine.households` obtains household membership and composition (which citizens belong to which household) by calling `CitizensAPI`'s `Household`/membership queries, never by running its own partnering RNG or independently assigning `householdId`. Check: `go doc ./internal/engine/households` shows no `Partner`/`FormHousehold`-shaped exported function that mints new `householdId`s; a passing test asserts a household's member list returned by `HouseholdsAPI` matches the member list `CitizensAPI` reports for the same `householdId` (`grep -rn "func Test.*[Mm]embership[Cc]onsist" internal/engine/households/*_test.go`). A lazy-but-plausible violation: reimplementing a second, independent partnering pass that can silently diverge from citizens' own `householdId` assignment — this check catches that by asserting cross-API agreement, not merely that some membership data exists.
- **AC-3 (Part IV HS; data-driven count — GR#15).** Exactly 17 housing typologies are modelled, and the count is *derived from* `data/buildings.json`'s `HS`-section entries at load time, not a hardcoded Go literal `17`. Check: `go doc ./internal/engine/households Typology` (or equivalent) exists; a passing test loads a fixture `buildings.json` with a different `HS` entry count (e.g. 18) and asserts the package's reported typology count changes to match (`grep -rn "func Test.*[Tt]ypologyCount" internal/engine/households/*_test.go`) — a naive `if len(typologies) != 17 { panic }` guard would fail this fixture-swap test, proving the count is genuinely data-derived rather than validated against a hardcoded expectation.
- **AC-4 (§21 appeal profile).** Each typology's appeal is a function over household stage × wealth × personality (not a single scalar per typology), derived from `buildings.json`'s tag array via the documented tag→weight translation (ASM-248) — e.g. a `novelty` tag weights the personality axis `noveltySeeking` positively, a `retirees` tag weights the `stage=retired` axis positively. Check: `go doc ./internal/engine/households AppealOf` (or equivalent) takes a household-stage/wealth/personality input and a typology, returning a differentiated score; a passing test asserts `AppealOf(penthouseTower, noveltySeekingHousehold) > AppealOf(penthouseTower, communityMindedHousehold)` and `AppealOf(bungalow, retireeCoastalHousehold) > AppealOf(bungalow, youngSingleHousehold)` (`grep -rn "func Test.*[Aa]ppeal" internal/engine/households/*_test.go`). A lazy-but-plausible violation: one fixed appeal scalar per typology applied to every household regardless of stage/wealth/personality — this check rejects it because it demands the score actually differ across household segments for the same typology.
- **AC-5 (§21 demand as distribution).** Citywide housing demand is exposed as a distribution over the 17 typologies (a vector, not a single total), computed from the population's stage/wealth/personality composition — independent of the *current stock mix* (demand is what households would prefer, not what happens to be built). Check: `go doc ./internal/engine/households DemandByType` returns a per-typology figure summing to the household count; a passing test holds population composition fixed while varying the built-stock mix and asserts the demand distribution is unchanged (`grep -rn "func Test.*[Dd]emandIndependentOfStock" internal/engine/households/*_test.go`). A lazy-but-plausible violation: distributing demand proportionally to whatever stock currently exists (demand "follows" supply) — this check rejects that directly by holding stock variable and population fixed.
- **AC-6 (§21 unhoused-by-preference — the AC-5 companion, per ASM-249).** A distinct `UnhousedByPreference` signal exists, separate from raw vacancy, quantifying households whose preferred-typology demand exceeds available stock of that typology even when citywide vacancy (summed across all types) is positive. Check: a passing test constructs a scenario with 100% single-typology stock (e.g. all terraces) at citywide vacancy > 0, and a population containing a significant retiree/novelty-seeking segment whose top-preference typologies (bungalow, tower) are entirely absent from stock; asserts `UnhousedByPreference() > 0` in that scenario (`grep -rn "func Test.*[Uu]nhousedByPreference" internal/engine/households/*_test.go`). A lazy-but-plausible violation: computing housing satisfaction from vacancy alone (`satisfaction = f(vacancy)`) — this check rejects that because it demands a nonzero unhoused-by-preference reading in a scenario where raw vacancy is deliberately positive.
- **AC-7 (§5.4 overcrowding & rent burden).** Overcrowding is derived from household size vs. dwelling capacity (occupants exceeding the typology's per-unit capacity threshold); rent burden is derived from rent vs. household income, using the §18 35%-of-income threshold (ASM-249's sibling reuse, logged separately as this file's own judgment call — see Escalations) to flag burden. Check: `go doc ./internal/engine/households OvercrowdingOf` and `RentBurdenOf` both exist; a passing test asserts a household with occupants > capacity returns `Overcrowded() == true` and one with rent/income > 0.35 returns `RentBurdened() == true`, while a comparable household under both thresholds returns `false` for each (`grep -rn "func Test.*[Oo]vercrowd\|func Test.*[Rr]entBurden" internal/engine/households/*_test.go`).
- **AC-8 (§5.4 dwelling-size preference).** Dwelling-size preference (bedroom/floor-area class sought) is a function of household size, wealth, and personality (per ASM's sibling in `households`), not a fixed constant applied to every household regardless of composition. Check: a passing test asserts two households differing only in wealth band return different preferred dwelling-size classes (`grep -rn "func Test.*[Dd]wellingSizePref" internal/engine/households/*_test.go`). A lazy-but-plausible violation: one preference constant for all households — this check rejects it by varying only wealth and demanding the output differ.
- **AC-9 (feeds `engine.attract`'s `housingAffordability` term).** `HouseholdsAPI` exposes a per-district (or citywide, if district granularity isn't yet modelled — document which) affordability figure combining overcrowding + rent burden + unhoused-by-preference into the single input `engine.attract`'s registered outbound call (`engine.households` → consumed by `engine.attract`, per code.json) needs, so the master dial's housing term is one queried value, not `engine.attract` reimplementing this file's math. Check: `go doc ./internal/engine/households HousingAffordability` (or equivalent single accessor) exists; `engine.attract`'s own package (per `engine.attract.md` AC-3) calls this accessor rather than computing overcrowding/rent-burden itself (cross-file check, verified at Tester time by grepping `internal/engine/attract/*.go` for a `households\.` call site).

### Error handling

- **AC-10 (GR#7).** Constructing/updating a household record referencing a nonexistent `householdId` (not present via `CitizensAPI`), or an appeal-profile lookup for an unrecognised typology id, returns a registry-sourced error (new `MET-E`-range code) rather than a nil-panic or silently-zeroed appeal. Check: `grep -n "MET-" internal/engine/households/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Ii]nvalid.*[Hh]ousehold\|func Test.*[Uu]nknownTypology" internal/engine/households/*_test.go`).
- **AC-11.** A typology whose `buildings.json` entry has an empty/unrecognised `appealProfile` tag array degrades to a documented neutral-appeal fallback (rather than a divide-by-zero or an untyped-nil appeal function), and the degradation is visible (not silently indistinguishable from a genuinely computed low appeal). Check: passing test coverage asserts the fallback path is distinguishable from a real zero score, e.g. via a `Fallback bool` field or logged low-confidence marker (`grep -rn "func Test.*[Ee]mptyAppealProfile\|func Test.*[Ff]allback" internal/engine/households/*_test.go`).

### Determinism & safety

- **AC-12 (GR#21).** Any stochastic element in dwelling-size-preference noise or appeal-tie-breaking uses the counter-based hash stream `hash(worldSeed, householdId, month, purposeTag)` — no shared/global RNG. Check: `grep -n "rand.New\|math/rand\"" internal/engine/households/*.go` (excluding `_test.go`) finds no shared RNG source.
- **AC-13 (SG-7 scoped; GR#21).** `grep -rn "time.Now\|time.Since" internal/engine/households/*.go` (excluding `_test.go`) returns no matches.
- **AC-14.** `go test ./internal/engine/households/... -race -count=1` passes with no data race.

### Documentation

- **AC-15.** `internal/engine/households/doc.go` states the module key `engine.households`, cites §5.4 and §21, names the 17 typologies as sourced from `data/buildings.json`'s `HS` section, and states explicitly (per ASM-247) that household formation/partnering is `engine.citizens`' entity, consumed here rather than re-implemented. Check: `grep -n "engine.households" internal/engine/households/doc.go` and `grep -n "§5.4\|section 5.4" internal/engine/households/doc.go` and `grep -n "buildings.json" internal/engine/households/doc.go` and `grep -n "engine.citizens\|CitizensAPI" internal/engine/households/doc.go` all match.

## Out of scope

- Household formation/partnering itself (the event that mints a `householdId` and its membership) — `engine.citizens`' entity per its own AC-12; this item consumes it (ASM-247).
- Migration decisions (who arrives/leaves) and the weighted `A` score itself — `engine.attract`'s job; this item only supplies the `housingAffordability` input.
- Zoning/construction of the typologies themselves (which typologies exist to build, lead times, materials) — `engine.build`'s job; this item consumes `BuildAPI`'s built-stock counts by typology, doesn't create them.
- The end-to-end zone→build→migrate→work→deliver scenario AC — owned entirely by `engine.attract.md` per the sprint's single-source-of-truth rule; this file's ACs are exercised as part of that scenario but do not restate it.

## Escalations

- **For Ben (ASM-247).** Cross-module scope boundary between `engine.citizens`' already-written AC-12 (household formation/partnering) and this item's BOW title ("Households & housing typologies: **formation**..."). I resolved it as citizens-owns-the-entity, households-owns-the-typology-layer, and did not edit `engine.citizens.md`. Recommend confirming this reading with whoever builds/reviews `engine.citizens` before dispatch, since the BOW title's own wording could mislead a junior into re-implementing formation here.
- **For Aaron (ASM-248).** `data/buildings.json`'s 17 `HS` entries carry `appealProfile` as free-text tags (`"retirees"`, `"coastal"`, `"novelty"`, `"wealth"`, etc.), not the numeric stage × wealth × personality weight vectors §21 implies. I've scoped a tag→weight translation layer as this module's job (AC-4), but if the tag vocabulary turns out too coarse to produce meaningfully differentiated appeal scores, that's a data-schema question for `foundation.data`/Aaron, not something this BA or the junior should silently patch by inventing numeric weights inside `buildings.json` unreviewed.
- **Assumption flagged (ASM-249).** "Unhoused-by-preference" has no spec-given name, field, or formula — I introduced it as the distinct-from-vacancy signal AC-6 needs to make §21's claim checkable. Exact scoring formula is left open for the junior/Batch tuning; only its existence and independence from vacancy are asserted.
