# Acceptance criteria — feat.debugmode (FEAT-008)

**BOW code:** FEAT-008
**Spec refs:** §14 (Debug Mode, `docs/METROPOLIS-MASTER-v2.1.md` lines 257-260); M0-ENG §3 (Debug mode & the Info Panel, lines 853-865, esp. "debug-touched saves are flagged forever"); `int.serializer`'s `Header.DebugTouched`/`TouchDebug`/`MergeDebugTouched` (INT-002, already frozen Sprint 0).
**Date:** 2026-08-08
**Status:** active (Sprint 1) — refreshed against landed APIs 2026-08-09 by BA-1, see Escalations
**Package under test:** `internal/engine/debug/` (confirm via `node claude-bow.js show FEAT-008` at dispatch)
**Standard gates:** see `README.md` — package for SG-4/SG-7 is `./internal/engine/debug/...`.

## User stories

- As **a developer**, I need debug to be a runtime feature switch (`--debug`, config, or `:debug on`) rather than a build flavour, so release builds always carry it (default off) and I never need a separate debug binary.
- As **the save-data hygiene contract** (M0-ENG §3), I need switching debug ON to sticky-flag the save header forever via `int.serializer`'s `Header.DebugTouched`, so debug-touched saves can never silently re-enter clean balance data.
- As **a developer with debug on**, I need 8× speed, cheats (free money, instant build, force milestone), an entity JSON inspector, fidelity-dial exposure, the console, and fixture record/replay controls unlocked, so I can test and demo without waiting on real economy pacing.
- As **`ui.screen.debug`** (F12), I need a single source of truth for "is debug on right now", so the panel's visibility and this module's unlocks never disagree.

## Scope

The runtime debug-mode switch: enable paths (`--debug` flag, config, `:debug on` palette command), the sticky `DebugTouched` save-header write, and the unlock set (8× speed, cheats, entity inspector, fidelity-dial exposure, console, fixture record/replay).

## Acceptance criteria

### Functional

- **AC-1.** A debug-state type/singleton exists exposing `IsOn() bool` (or equivalent) as the single source of truth every other module (`ui.screen.debug`, speed control, cheat commands) reads — a passing test asserts all three enable paths (flag, config, palette command) converge on the same state read by `IsOn()`.
- **AC-2.** Release builds carry debug support and default to **off** — a passing test asserts a freshly constructed debug-state (no flag, no config, no palette command issued) reports `IsOn() == false`.
- **AC-3.** Enabling debug at any point in a session calls `int.serializer`'s `Header.TouchDebug()` (or `MergeDebugTouched(true)`) on the active save header — a passing test enables debug mid-session and asserts the header's `DebugTouched` field is `true` immediately after, and remains `true` across a subsequent disable-then-save (the sticky invariant, carrying forward `int.serializer`'s own AC-8).
- **AC-4.** Disabling debug (`:debug off`, if supported) does **not** clear `DebugTouched` on the header — a passing test toggles debug on then off and asserts the header's flag is still `true`.
- **AC-5.** With debug on, speed control accepts 8× (in addition to the pause/1x/2x/4x `engine.core` already supports) — a passing test asserts `SetSpeed(8x)` is accepted when `IsOn()==true` and rejected (or clamped with a clear error) when `IsOn()==false`.
- **AC-6.** With debug on, cheat commands (free money, instant build, force milestone unlock) are available and, when invoked, apply their effect and emit a world-event/log entry documenting the cheat was used (balance-data hygiene: cheats must be visible in the record, not silent) — a passing test invokes each cheat and asserts both the state change and the logged event.
- **AC-7.** With debug on, an entity JSON inspector is available: given an entity reference (cell/citizen/firm/market), it dumps the entity as JSON — a passing test inspects a known fixture entity and asserts the JSON output round-trips the entity's known fields.
- **AC-8.** With debug on, the fidelity-dial (HOT radius, §5.2) becomes adjustable and its current cost is observable — a passing test asserts the dial's exposed range/current-value API is only reachable when `IsOn()==true`.
- **AC-9.** With debug off, none of AC-5 through AC-8's unlocks are reachable — a passing test asserts each attempted unlock action is rejected with a clear "debug mode required" error when `IsOn()==false`.
- **AC-10.** The console (`` ` ``) and fixture record/replay controls are gated behind debug the same way — a passing test asserts both are unreachable with debug off and reachable with it on.

### Error handling

- **AC-11.** Every action gated behind debug (AC-5 through AC-8, AC-10) returns a registry-sourced `errs.E` (via `foundation.errors`) when attempted with debug off — never a silent no-op and never a panic.
- **AC-12.** `Header.TouchDebug()` failing to persist (e.g. header write fails) is surfaced as a registry-sourced error to the caller that requested debug ON — the enable path must not report success if the sticky flag failed to record, since that would silently violate the hygiene contract.

### Determinism & safety

- **AC-13 (GR#21).** Enabling/disabling debug and invoking cheats does not retroactively change already-committed simulation history — a passing test asserts pre-existing world state (tick count, prior deltas) is unaffected by the act of toggling debug on/off itself (as opposed to a cheat's own intended effect, which legitimately changes state and is logged per AC-6).
- **AC-14.** `grep -rn "time.Now" internal/engine/debug/*.go` (excluding `_test.go`) returns no matches on the tick-affecting paths — any wall-clock use (e.g. timestamping the "cheat used" log entry) must route through `foundation.errors`' injectable clock, consistent with the rest of the engine domain's determinism discipline.

### Documentation

- **AC-15.** The package doc states module key `feat.debugmode`, cites §14 and M0-ENG §3, and explicitly documents the sticky `DebugTouched` contract (once true, forever true) so a future contributor doesn't "fix" it into a togglable flag.

## Out of scope

- F12's rendering of debug-mode state — `ui.screen.debug` (`FEAT-007`) reads `IsOn()` and the registry; this item only provides the switch and unlocks, not the panel.
- `int.serializer`'s `Header`/`DebugTouched` implementation itself — already frozen in Sprint 0 (`INT-002`); this item only calls it.
- The actual fixture record/replay file format — `harness.replay` (`MOD-013`, Sprint 2); this item only gates access to whatever controls that module exposes.

# Acceptance criteria — FEAT-035 wiring (`feat.debugmode` actually operating in `cmd/metropolis`)

**BOW code:** FEAT-035 (P1)
**Filed under:** `docs/planning/acceptance/feat.debugmode.md` per `code.json:feat.debugmode`, appended after the FEAT-008 section above rather than replacing it — mirroring how BUG-088's criteria were appended to `tool.secretguard.md` after its FEAT-028 content. **Date:** 2026-08-11
**Status:** active
**Package under test:** `cmd/metropolis/` (the enable-path wiring, DoD #1) + `internal/engine/core/` (the `Snapshot`/`MergeDebugTouched` carry-forward, DoD #2) + a new integration-test surface spanning both plus `internal/harness/headless/` and `internal/foundation/serialize/` (the mandatory end-to-end test, DoD #3). No existing package is fully "under test" here in the FEAT-008 sense — this item's own tests must live where they can exercise the real construction/wiring path, which for #1 and #3 means a test in (or driving) `cmd/metropolis` itself, not a unit test inside `internal/engine/debug`.
**Standard gates:** see `README.md` — SG-1 through SG-4 apply; package scope for SG-4/SG-7 is `./cmd/metropolis/... ./internal/engine/core/... ./internal/engine/debug/... ./internal/harness/headless/...`. SG-7's determinism smoke additionally applies to this section's own AC-D1/AC-D2 below.

## Why this file exists, and how it differs from its siblings (read first)

FEAT-008's criteria above are **unit-level** criteria against `internal/engine/debug` in isolation, and every one of them passed while `debug.NewState`/`WithHeader` had zero production callers and `Engine.Snapshot` never called `MergeDebugTouched` — confirmed by dispatch: `grep -rn "debug.NewState\|debug.WithHeader" --include=*.go cmd/ internal/ | grep -v _test.go` returns **no matches**, and `grep -n "MergeDebugTouched" internal/engine/core/*.go` also returns **no matches**. The hygiene guarantee this package exists to provide — "a debug-touched save can never masquerade as a clean one" — has never actually been exercised by the running binary. Every criterion below is written so that a check passing requires the real wiring to exist; a criterion satisfiable by a unit test alone is treated as a defect in this file, not a shortcut.

**A second, load-bearing finding from dispatch reading, stated up front because it changes what "the real binary" means here:** `cmd/metropolis`'s own `main.go` package doc comment (current, as of this dispatch) states explicitly that the **interactive** binary does not construct a `core.Engine` at all — it drives `harness.stub.StubEngine` only, tracked as `ASM-001` ("resolve when engine.core actually drives this binary"), and `boot.go`'s `bootCore` confirms this: no `core.NewEngine` call anywhere in that file. The **only** production code path that builds a real `*core.Engine` and calls `Engine.Snapshot` today is `metropolis -headless` (`internal/harness/headless/run.go`'s `Run`/`writeBundle`). Consequently:

- DoD #1's "`--debug` flag ... `Speed8xGate` injection into `engine.core`" must be wired on **both** paths where they are reachable at all: the `-headless` path (which has a real `Engine` to inject a gate into and a real `Header` `WithHeader` can be given) is where AC-E3/AC-E4/AC-D1 below require the wiring to be provably real; the interactive path's `:debug on` palette command and the `--debug`/config flags on the interactive binary are still required by DoD #1's own text (AC-E1/AC-E2), but since no `core.Engine` exists on that path yet, the criteria for it are scoped to what DoD #1 actually asks for there — the enable path converging on one `debug.State.IsOn()` and (once `engine.core` is reachable via `RunCommandLoop`, which `boot.go` currently does not use either) `Speed8xGate` reaching `commands.go`'s `checkSpeed8xAllowed`. **AC-E5 below flags this scoping split explicitly** rather than silently narrowing DoD #1 to only the headless path.
- DoD #3's mandatory end-to-end test ("enable debug → snapshot → reload → snapshot → assert survived both hops") is therefore written against `metropolis -headless`, because that is the only existing entry point with a real `Engine`/`Snapshot`/`Header` to enable debug against, take a snapshot from, and reload. It is **not** written against the interactive TUI path. See AC-E5's assumption for the CLI-flag-name consequence of this.

## User stories

- As **the save-data hygiene contract** (M0-ENG §3), I need `DebugTouched` to actually reach a real save header written by the real binary, not just a header hand-built inside a package test, so the guarantee this whole feature exists for is true of the shipped game rather than only of `internal/engine/debug`'s own test suite.
- As **Bill, reviewing SEC-027's finding**, I need this item's own acceptance criteria to be structurally incapable of the exact failure mode FEAT-008's criteria had (unit-level assertions that pass on an unwired module), so closing this item is real evidence the gap is closed, not a repeat of the same process mistake with a new BOW number.
- As **a developer debugging a corrupted-balance-data report**, I need `metropolis -headless -debug` (or equivalent) to be the thing that actually flips `DebugTouched` in a bundle `metctl verify` can read, so "was this save ever debug-touched" is answerable from the artifact itself, not from trusting that the feature was wired in at the time.

## Scope

Wiring `internal/engine/debug`'s `State` into `cmd/metropolis`'s real construction/dispatch paths (DoD #1); making `Engine.Snapshot` carry a prior save's `DebugTouched` forward via `Header.MergeDebugTouched` instead of always starting from a fresh `serialize.NewHeader` (DoD #2); and the mandatory end-to-end reload test proving both halves operate together through the real binary/engine path, not through a hand-constructed `debug.State` (DoD #3).

## Acceptance criteria

### DoD #1 — enable-path wiring (`cmd/metropolis` constructs and wires a real `debug.State`)

- **AC-E1.** All three of `debug.EnableSource`'s documented sources are reachable from `cmd/metropolis`'s real flag/command surface and converge on one shared `*debug.State`: a `--debug` flag on `run()`'s `flag.FlagSet` (mirroring the existing `-headless`/`-version` flags in `run.go`) calls `Enable(debug.SourceFlag, ...)` at boot; a config-file path (if a config loader does not yet exist elsewhere in the tree, a minimal one scoped to this flag is in scope here — confirm at dispatch via `grep -rn "package config" internal/` before building a second one) calls `Enable(debug.SourceConfig, ...)`; and the `:debug on` in-game command — routed through `protocol.KindDebug`'s currently-stub `handleDebug` in `internal/engine/core/commands.go` — calls `Enable(debug.SourcePalette, ...)` on the same `*debug.State` instance the flag/config path constructed. **Check:** a test that boots `cmd/metropolis` via each of the three paths independently (flag set, config file present, `:debug on` command sent) and asserts `IsOn()` on the **one shared State instance** the binary constructed reads `true` after each — not three independently-constructed `debug.State` values that each individually report `true`, which would satisfy a naive reading of "three paths work" while failing AC-1's own "single source of truth" requirement (carried forward from FEAT-008). **What a lazy implementation looks like:** three separate `debug.NewState()` calls, one per enable path, each correctly flipping `IsOn()==true` on its own instance, with no shared instance any of `ui.screen.debug`/`engine.core`/the cheat call sites actually read — this passes a shallow "does calling Enable work" check while leaving the "single source of truth" guarantee AC-1 exists for completely unmet in the running binary. The check above rejects this by asserting identity (same `*State` pointer, or an equivalent single-construction-site proof), not just three independent `true` reads.
- **AC-E2.** With none of the three enable paths exercised, the constructed `*debug.State`'s `IsOn()` is `false` at boot (release-default-off, carrying FEAT-008's AC-2 forward into the wired binary) — **Check:** boot `cmd/metropolis` (or `metropolis -headless`) with no `--debug` flag, no debug config key, and no `:debug on` command sent; assert `IsOn()` is `false` on the constructed State before any command is processed.
- **AC-E3 (Speed8xGate injection).** `metropolis -headless`'s `core.NewEngine` construction (`internal/harness/headless/run.go`'s `Run`) passes `core.WithSpeed8xGate(state.AllowSpeed8x)` (the exact method value named in `debug/gates.go`'s own doc comment as the concrete `Speed8xGate` implementation) so that `Engine.checkSpeed8xAllowed` — currently unconditionally denied on every path in the running binary, since `e.speed8xGate` is `nil` on every existing `core.NewEngine` call site — is real. **Check:** an integration test drives `metropolis -headless` (or an equivalent call into `headless.Run` with the real `Config` plumbing this AC adds) with debug disabled and asserts a `SetSpeed(Speed8xDebug)` command is rejected with `ErrInvalidSpeed`/`reason: "no_gate_configured"` is **not** the reason given (i.e. a real gate is configured and it is the gate, not the absence of one, doing the rejecting) — then repeats with debug enabled first and asserts the same command is accepted. **False-pass warning:** a test that only asserts "Speed8xDebug is accepted when debug is on" without also asserting the *rejection* path's `reason` field is not `"no_gate_configured"` would still pass if the implementer wired `WithSpeed8xGate` to a gate that always allows (a function literal that ignores `state.IsOn()` entirely) — the two-sided check (denied-because-off distinct from denied-because-unconfigured, accepted-because-on) is required precisely to catch that shape, which is the direct `AllowSpeed8x`-analogue of FEAT-008's own AC-9.
- **AC-E4 (`WithHeader` against the real header).** The `*debug.State` `-headless` constructs is built with `debug.WithHeader(h)` where `h` is a `*serialize.Header` that is **the same header value `Engine.Snapshot` (via `writeBundle`) goes on to write to `OutDir/header.json`** — not a separately-constructed `serialize.Header` that happens to share field values. **Check:** an integration test enables debug via the real enable path (AC-E1), then reads back `OutDir/header.json` via `serialize.ReadHeader` after the run completes, and asserts `DebugTouched()` is `true` on the **file that was actually written to disk** — not on an in-memory `*debug.State`'s own header field, which is exactly the shape a hand-injected unit test would check instead (see the mandatory end-to-end AC-M1 below, which this AC is a necessary but not sufficient precondition for).
- **AC-E5.** This section's own scoping split (headless path gets the full DoD #1 wiring provably; the interactive TUI path gets only what DoD #1 asks for given `ASM-001`'s pre-existing "no `core.Engine` in the interactive binary" constraint) is stated in this file's own "Why this file exists" section above, not silently narrowed — **Check:** Tester/QA review confirms this file's own prose states the split; no code-level check applies to a documentation requirement.

### DoD #2 — `Engine.Snapshot` carries `DebugTouched` forward

- **AC-S1.** `Engine.Snapshot` (`internal/engine/core/persist.go`) no longer unconditionally starts from a header with `debugTouched` at its zero value on every call — when a prior header for the same running session/save is available (the exact plumbing — an `Engine` field set at construction via a new `core.Option` such as `WithPriorDebugTouched(bool)`, or an explicit parameter added to `Snapshot`'s signature — is an implementation decision for the junior/lead, not fixed by this AC) it is merged in via `Header.MergeDebugTouched`, never assigned directly and never left to `serialize.NewHeader`'s always-`false` default alone. **Check:** a table-driven unit test on `Engine.Snapshot` (or its underlying header-construction helper) with the prior-flag plumbing set to `true` asserts the returned `Header`'s `DebugTouched()` is `true` even though `Enable` was never called in that test process — proving the carry-forward path is `MergeDebugTouched`-shaped (OR-in), not "session state happens to already be on."
- **AC-S2.** With no prior header/flag supplied (a brand-new save, `Engine` constructed with no `WithPriorDebugTouched` or equivalent), `Snapshot`'s returned header's `DebugTouched()` is `false` — **Check:** a unit test asserts this explicitly, so AC-S1's carry-forward wiring cannot be satisfied by a change that makes every snapshot unconditionally `true` regardless of input (the SEC-024 failure-direction bias documented in `header.go` — "lean toward over-flagging" — governs failure paths, not the default no-prior-state case, which must still default to clean).
- **AC-S3.** `AC-S1`'s plumbing is exercised by `internal/harness/headless`'s real `writeBundle`/`Run` path, not only by a direct unit-level call into `Engine.Snapshot` with a hand-set field — **Check:** this is the same requirement AC-M1 below tests end to end; AC-S1/AC-S2's unit tests are necessary (they prove `MergeDebugTouched` is used correctly in isolation) but explicitly insufficient on their own to close DoD #2 — AC-M1 is the criterion that actually closes it, per this file's own governing principle.

### DoD #3 — the mandatory end-to-end test (the single most important AC in this file)

- **AC-M1 (mandatory, non-negotiable — this is DoD #3, named explicitly in FEAT-035's own BOW text).** A test exists that: (1) invokes `metropolis -headless` — the real compiled/testable binary entry point (`cmd/metropolis`'s `run()` function called directly with `-headless` args and real `os.Args`-shaped input, or an `exec.Command` invocation of the built binary — either is acceptable, but it must go through `run()`/`main()`'s actual argument-parsing and construction code, never a hand-assembled `headless.Config{}` struct literal that bypasses flag parsing) with the real `--debug`-equivalent enable path from AC-E1 set, producing a bundle at some `OutDir`; (2) reads that bundle's `header.json` back via `serialize.ReadHeader` and asserts `DebugTouched()` is `true` (first hop); (3) invokes `metropolis -headless` a **second time**, as a genuinely separate process/`run()` call, **without** the debug enable flag set this time, configured to carry forward from the first run's output (the reload mechanism — a `-in`/`-resume` flag reading the prior bundle's header before constructing the second run's `Engine`, since no such flag exists in `internal/harness/headless/run.go`'s `Config` today and this AC's own dispatch must add one, or an equivalent load-and-carry-forward path) producing a second bundle; (4) reads the **second** bundle's `header.json` back via `serialize.ReadHeader` and asserts `DebugTouched()` is still `true`, despite debug never having been enabled in the second `run()` call at all. Both assertions read from files written by the real binary path, never from an in-memory `*debug.State` or a hand-constructed `*serialize.Header`.

  **What a lazy implementation looks like, spelled out exactly (read this before building or testing):** a unit test that does the following instead — `h := &serialize.Header{}`; `state := debug.NewState(debug.WithHeader(h))`; `state.Enable(debug.SourceFlag, "test")`; assert `h.DebugTouched() == true`; construct a **second**, separate `h2 := &serialize.Header{}`; call `h2.MergeDebugTouched(h.DebugTouched())` directly (or equivalently, construct a second `debug.State` and manually feed it `h`'s flag); assert `h2.DebugTouched() == true`. **This is, field for field, what FEAT-008's original criteria already covered (this section's own AC-3/AC-4 above), and it is exactly the process failure SEC-027 found: it proves `MergeDebugTouched`'s own OR-logic is correct in isolation, and it proves `debug.State.Enable` sets a header's flag in isolation, but it never once calls `cmd/metropolis`'s `run()`, never once goes through `-headless`'s real flag parsing or `Engine.Snapshot`, and never once proves the two halves (DoD #1's wiring, DoD #2's carry-forward) are actually connected to each other inside the real binary.** A reviewer (Tester or Bill) presented with a test of this shape as "evidence AC-M1 passes" must reject it explicitly, citing this paragraph, exactly as this section's own governing principle requires — not accept it because its assertions superficially match "flag survived both hops."

  **False-pass warning:** even a test that DOES invoke `run()`/`-headless` for both hops can still quietly degrade into the lazy shape above if the *second* invocation's "reload" step is faked — e.g. if the test manually copies `DebugTouched: true` into the second run's config/header instead of the second `run()` call genuinely reading the first bundle's `header.json` from disk and the carry-forward happening inside `Engine`/`Snapshot` itself (AC-S1's real plumbing). The check must confirm the second `run()` invocation's only source of "this save was debug-touched" is the first bundle's on-disk `header.json`, read through `serialize.ReadHeader` (or equivalent), with debug's enable path genuinely never called in the second process — not a test harness quietly threading the flag through out of band.

- **AC-M2.** AC-M1's test is placed where it can actually invoke `cmd/metropolis`'s `run()` (a `_test.go` file in package `main` under `cmd/metropolis/`, following `run_test.go`'s existing precedent for testing `run()` without a real terminal — see `boot_test.go`/`run_test.go`'s current pattern for headless-mode testing) — **not** inside `internal/engine/debug` or `internal/harness/headless` alone, each of which can only prove its own half. **Check:** `git status`/file-location review at Tester review confirms the test file's package and import graph actually reach `cmd/metropolis.run`, not a re-implementation of `run`'s logic inside a different package that merely resembles it.

### Golden Rules

- **AC-G1 (GR#1, error trapping on construction failure).** If `debug.NewState`'s construction fails to produce a usable State in the wired path (e.g. `WithHeader` given a `nil` header, or the config loader AC-E1 adds fails to parse) `cmd/metropolis`'s boot sequence surfaces a registry-sourced `*errs.E` (the existing `MET-E900`/`codeBootFailure` convention `boot.go` already uses for every other boot-time dependency) and does not silently boot with debug support unavailable while claiming success — **Check:** a test forces the config/header construction to fail and asserts `run()`'s exit code and stderr output follow `printBootError`'s existing convention, exactly as every other `bootCore` dependency failure does today.
- **AC-G2 (determinism interaction, stated explicitly per this file's dispatch instruction).** Enabling debug via any of the three paths, and the act of `Engine.Snapshot` merging `DebugTouched` forward, does not itself perturb the deterministic tick/command stream `feat.detgate`'s gate verifies — carrying FEAT-008's own AC-13/AC-14 forward into the wired path: `grep -rn "time.Now" cmd/metropolis/*.go internal/engine/core/persist.go` (excluding `_test.go`) shows no unguarded wall-clock use introduced by this item's changes, and a `-headless` run with `-debug` produces the identical `TicksAdvanced`/tick-stream shape (modulo the `DebugTouched` header bit itself and whatever AC-E3's `Speed8xDebug` unlock legitimately changes if actually invoked) as the same run without `-debug`, when `Speed8xDebug` is never actually selected during the run. **Check:** a determinism-style test runs the same seed/months/scenario twice, once with debug enabled and the speed left at a non-debug value, once without, and asserts the resulting bundles are byte-identical except for the header's `DebugTouched`/`AppVersion`-adjacent fields already excluded by this project's existing byte-determinism test conventions (see `internal/engine/core/determinism_test.go`'s existing exclusion list for the precedent to extend, not reinvent).
