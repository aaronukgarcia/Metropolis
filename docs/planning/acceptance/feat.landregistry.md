## User stories

- **US-1.** As the player (the Crown), I need to be the ultimate owner of all land, able to exercise compulsory purchase over any tile — so every plot is ultimately mine, private parties only ever hold building interests, and the tenure ledger always bottoms out at the crown.
- **US-2.** As the game, I need a single per-tile ledger (player acquisition cost, current land value, tenure records, building id, maturity level) as the SSOT for who owns what — so no second module keeps its own tenure list that can drift from this one (GR#3).
- **US-3.** As a netizen or netibusiness (including a policy-gated NFP housing association), I need my ownership interest in a building (freehold or leasehold) to be traceable against my own ID — so ownership is literal and auditable, not a city-wide "n% owner-occupied" figure.
- **US-4.** As the game, I need the ledger to be checked for consistency once per game year by a scheduled audit that can actually fail — every property correctly listed ∧ every listing points to the correct property — so a mismatch is a loud registry error surfacing as an HMRC audit finding, never a silent drift (GR#17: an audit that cannot evaluate must not report success).
- **US-5.** As `engine.fiscal`/`engine.tax` (and the HMRC surface FEAT-204 builds), I need the registry audit's mismatches to arrive as a real finding record I can render — so the annual audit is a function I can surface, not a log the registry keeps to itself.

## Scope

The per-tile land-registry ledger + the crown-ownership model + the designed-in once-per-game-year bidirectional consistency audit. Per-tile fields: player acquisition cost, current land value, tenure records (owner type + owner ID + freehold/leasehold interest), building id, maturity level. It does **not** re-implement the tile grid (`engine.world`), the building/structures model (`engine.build`), the money/ledger (`engine.finance`), the moving-home ownership-transfer events (`engine.households` + FEAT-170), the land-VALUE dynamics (FEAT-201, open — the registry STORES the current value, it does not compute its demand curve), the building-maturity LEVEL computation (Escalation 2c — the registry TRACKS the level, the four effects are a separate ruled design), or the HMRC surface (FEAT-204 — the registry surfaces audit findings, HMRC renders them). It consumes all of those through registered edges.

## Acceptance criteria

### Design 1 — The crown-ownership model and the per-tile ledger

- **AC-1 (US-1/US-3; crown model: player is ultimate owner; private interests are building-level, traceable to real IDs).** Every tile in `engine.world` resolves to exactly one ultimate owner — the player (Crown). Any building on the tile is held freehold or leasehold by a `engine.citizens` netizen or a `engine.firms`/netibusiness entity, or by a policy-gated NFP housing association where the housing policy allows (the gate reads `engine.policies` — **built on origin/main, 17 files; verify a housing-association gate surface exists in its API at dispatch, see Escalation 4**). Every ownership record carries the owner's real ID — no aggregate "n% owner-occupied" placeholder. Check: `go doc ./internal/engine/landregistry LandAPI` (or the dispatch-resolved package) shows a per-tile owner query and a per-owner holdings query; a passing test constructs a tile with a citizen-owned building and a business-owned building and asserts (i) both resolve to their owner IDs, (ii) both bottom out to the Crown as ultimate owner, (iii) the holdings query returns exactly the tiles each owner holds (`grep -rn "func Test.*[Cc]rown\|func Test.*[Oo]wnership\|func Test.*[Hh]oldings" internal/engine/landregistry/*_test.go`). **False-pass risk:** an ownership model that is a player-owned blanket over everything with no per-ID private interest — assert the trace, not the aggregate.

### Design 2 — The consistency checker (designed-in, GR#17)

- **AC-2 (US-4; bidirectional referential integrity, scheduled once per game year, loud on mismatch).** The ledger is checked by a consistency audit that runs once per game year (a scheduled event in the existing tick — not ad-hoc) and asserts BOTH directions: every property is listed, and every listing points to the correct property (a listed tile's building id resolves via `engine.build` to the building actually on that tile; a building's ownership record resolves to the tile it occupies). A mismatch produces a registry-sourced error (GR#7 — via `node tools/plan/add-error.js`, never a hand-written string) and surfaces as an HMRC audit finding (US-5/AC-3). **The audit can genuinely fail**: an injected mismatch (flip a building id, swap an owner, point a record at a non-existent tile) must produce the error; and **an audit that cannot evaluate (missing building data, unqueryable tile) must report FAILURE, not success** (GR#17 — the "silent-pass" trap from `docs/planning/verification-standards.md`). Check: `grep -rn "func Test.*[Aa]udit\|func Test.*[Cc]onsisten\|func Test.*[Rr]eferent" internal/engine/landregistry/*_test.go`; a passing test runs the audit over a clean ledger and asserts PASS, then injects each of three mismatch classes (property-listed-twice, listing-points-to-wrong-building, record-points-to-missing-tile) and asserts each produces the typed registry error; a fourth test makes the audit's inputs unqueryable (e.g. a world reference that cannot resolve) and asserts the audit reports a FAILURE — never a false clean bill. **False-pass risk:** an audit that walks its own internal copy of the data (self-consistent by construction — the "cannot evaluate" trap), or one that only logs a warning without a typed error — assert the audit reads the LIVE world/build state and emits the registry error.

### Design 3 — The HMRC audit-findings surface

- **AC-3 (US-5; mismatches surface as HMRC audit findings through the registered fiscal/tax surface, not a parallel log).** A consistency mismatch produces an audit-finding record that the HMRC surface (FEAT-204's collection engine, or `engine.fiscal`/`engine.tax` when they land) can read and render — the registry publishes findings, it does not keep a private "problems" list the rest of the game never sees. Check: `go doc ./internal/engine/landregistry` shows a findings-query surface; a passing test runs the AC-2 mismatches and asserts the finding records appear in the fiscal/tax-facing surface (or the dispatch-resolved sink) with the owning tile/building and the mismatch class (`grep -rn "func Test.*[Ff]inding\|func Test.*[Aa]udit.*[Ss]urface" internal/engine/landregistry/*_test.go internal/engine/fiscal/*_test.go internal/engine/tax/*_test.go`). **False-pass risk:** an audit that records mismatches in its own slice that nothing else reads — the built-but-not-wired family from `docs/METROPOLIS-MASTER-v2.1.md` §(the memory's dominant defect class) — assert the sink reads the findings, not the presence of a log.

### Design 4 — Compulsory purchase and the maturity level

- **AC-4 (US-1; compulsory purchase is a real, consistency-preserving event).** The player can exercise compulsory purchase over any tile: the tenure record flips to Crown, the previous holder's interest is cleared, and the acquisition cost is charged through `engine.finance` at the data-sourced compensation basis (balance regime — placeholder; see Escalation 2a). The audit must still PASS immediately after a compulsory purchase (the CP itself must not corrupt the ledger). Check: `grep -rn "func Test.*[Cc]ompulsory\|func Test.*[Cc]ompensation" internal/engine/landregistry/*_test.go`; a passing test CPs a citizen-held tile and asserts (i) the record flips to Crown, (ii) the acquisition cost posts through finance, (iii) a subsequent audit passes. **False-pass risk:** a CP that mutates the tile without the tenure record (world says Crown, ledger says citizen — exactly the drift the audit exists to catch) — assert the ledger is the first thing that changes.
- **AC-5 (US-2; maturity level is tracked deterministically from the existing inputs, never a parallel counter).** The ledger tracks each building's maturity level (the §5 1–99 scale, milestone every 10) as a **pure monthly function** of the tracked inputs (maintenance funded × occupancy/custom × age — the `engine.maintenance`/`engine.build` inputs) per GR#21 — the registry records the level each month; the level's four ruled effects (§5) are out of scope here (Escalation 2c). Check: `grep -rn "func Test.*[Mm]aturity\|func Test.*[Ll]evel" internal/engine/landregistry/*_test.go`; a passing test advances a maintained+occupied building and an unmaintained one through months and asserts the level is monotone in the maintained case, decays in the neglected case, and is byte-identical across two identical runs (GR#21 determinism). **False-pass risk:** a maturity counter the registry owns that nobody feeds (always zero), or a non-deterministic level (wall-clock/time-based) — assert it consumes the maintenance/build inputs and is reproducible.

### Data and the balance regime

- **AC-6 (US-2; every player-felt magnitude is a data-file placeholder).** The acquisition cost, current land value (the STORED value — its dynamics are FEAT-201), and the compulsory-purchase compensation basis are all loaded from a data file (the registry's own data file or the `data/`-level precedent) with a `disclosure`/`$comment` block marking each a placeholder pending Aaron's balance pass (the `engine.crime` `crime.json` precedent). NO bare literal outside doc prose in Go source. Check: `grep -n "disclosure\|PLACEHOLDER\|\\\\$comment" <registry data file>` matches for each magnitude; `grep -rnE "[0-9]+(\\.[0-9]+)?%|[0-9]+p" internal/engine/landregistry/*.go` (excluding `_test.go`) finds no bare cost/value/compensation literal; a passing test mutates each placeholder in the data file and asserts the engine follows (read-the-file, not shadowed) (`grep -rn "func Test.*[Mm]utate\|func Test.*[Cc]ost.*[Ff]ollows" internal/engine/landregistry/*_test.go`). No numeric value is pinned by this file.

- **For Aaron — balance-regime + design review (the ruling-class hard gate; blocks dispatch).** Four decisions: (a) **compulsory-purchase mechanics** — is the compensation basis current land value × a data-sourced factor, and does CP fire immediately (same-tick tenure flip) or as a scheduled event? The criteria pin the flip + finance posting (AC-4) but defer the magnitude; (b) **ownership-transfer events** — FEAT-170 (moving-home) and FEAT-204 (stamp duty on purchases) both touch tenure; who FIRES the tenure-record change — the registry exposes a transfer command the household/land-economics code calls, or the registry observes their events? Recommend: registry TRACKS + persists the level from the maintenance/build inputs (AC-5 as written); the four effects land in the build/maturity feature; (d) **land value** — FEAT-201 (Land economics) is a separate open item (Tier 2); the registry stores the current value as a data-sourced placeholder until FEAT-201 supplies the demand curve. All magnitudes are balance-regime placeholders per AC-6.
- **For Bill/Bev — module split + sequencing.** Recommend a new `internal/engine/landregistry/` package (distinct from `foundation.registry`, distinct from `engine.build`) owning the ledger + the scheduled audit; findings published to the HMRC/fiscal surface.
