## 1. Why this item exists

`FEAT-2326609772` inc3 (network capacity overlay, landed `376b108`) found that its capacity-share apportionment makes per-segment saturation equal per-class saturation **by construction** — every segment of a class necessarily shows the same saturation because `lineUsageOf`'s usage number has no spatial texture to apportion unevenly (Q100163, filed as a design gap). Two segments of one road class can only legitimately DIFFER in saturation if the demand feeding them differs — which requires knowing WHERE demand is generated (per tile, from the people actually living/working there), not just the city-wide class total. inc2 is the first CONSUMER of inc1's scale ladder: it turns "how many residents and workers are on this tile" into "how many person-trips and freight-tonnes per day that generates," splits those trips by mode using the ladder's own density-adjusted mode share, and re-aggregates by line class and by segment so `lineUsageOf`/`lineSegmentIndexOf` can (eventually) be fed a real spatial flow basis instead of a uniform capacity-share split.

---

## 2. The design in one paragraph

A new memoised export `demandForecastOf(s)` computes, per demand-generating tile (every online building with `residents` or `jobs`), a person-trip count = `(actual residents on this tile) × ladderPoint.tripRatePersonPerDay + (actual workers on this tile) × 2.0 commute legs` — "actual" because `SPECS[...].residents`/`.jobs` are CAPACITY figures (`capacityAtTier`, `data.ts:497`), so each tile's capacity is scaled by the city-wide occupancy fraction (`s.population / onlineResidentsCapacity(s)` for residents, `totalJobs(s) / jobsCapacity` — see AC-1's exact rule and A-2's employment-fill assumption) to get an ACTUAL count, never the raw capacity. `ladderPoint` is `ladderAt(scaleLadder, s.population)` (inc1, one call per tick, not per tile — GR#21/O(rungs) cost, not O(tiles×rungs)). Mode split reads `ladderPoint.fields` for the `modeShare.<modeId>` keys already computed by inc0's rollup (log-linear-in-population, itself density-adjusted per rung per A-4/A-5 of `traffic-assumptions.md`) — **no second mode-choice model, no tile-level density lookup** (GR#3): the CITY's current rung already encodes the density-driven split; re-deriving a per-tile density band would be a second, disagreeing model of the same quantity. Freight tonnes/day is computed per tile from `totalJobsBySector`'s sector split × `trip_generation.json`'s `freightTonnesPerJobPerDay`, converted to vehicle-trips via `vehicle_classes.json`'s `capacityTonnes` per freight class. All four outputs (person-trips, mode-split trips, freight tonnes, freight vehicle-trips) are then aggregated into a NEW `forecastLineUsage(s)`: per line-class demand, computed in PARALLEL to (not replacing) `lineUsageOf`'s existing `usage` field this increment, exposing a `divergence` ratio so the two models' disagreement is visible rather than silently swapped (Decision D1 below — the memory lesson on silent divergence between two models, `metropolis-liveness-needs-both-bounds.md`, applies directly here). Per-segment attribution (`forecastSegmentUsage(s)`) apportions each class's forecast demand across `lineSegmentIndexOf(s)`'s segments by NEAREST-SEGMENT tile-demand sum (AC-5), not by capacity share — this is the actual fix for Q100163.

## 3. Acceptance Criteria

### Person-trip generation

**AC-1 — per-tile actual residents/workers, not capacity, drive demand generation.**
For each online building `b` with `SPECS[b.spec].residents` (a capacity figure, e.g. `res_hut: 8`, `data.ts:1797`) or `.jobs` (e.g. `off_suite: 25`, `data.ts:2050`), the tile's ACTUAL person count is the building's `capacityAtTier(sp, b.capacityTier ?? 0)` (`data.ts:497`) scaled by a city-wide occupancy fraction: `residentsActual = capacityAtTier(sp,tier) × (s.population / onlineResidentsCapacity(s))` for residential specs, `workersActual = capacityAtTier(sp,tier) × (totalJobs(s) / <online jobs capacity>)` for job-bearing specs — never the raw `residents`/`jobs` field used directly as if every building were always at 100% occupancy (which would double-count demand the moment a city has vacancy, contradicting A-1's "demand from PEOPLE, not buildings"). Person-trips per tile = `residentsActual × ladderPoint's tripRatePersonPerDay field` (dotted key `tripRatePersonPerDay`, `LadderField.value`) + `workersActual × 2.0` (`trip_generation.json` `workerTripRate.commuteLegsPerWorkerPerDay`, a literal `2.0` is banned by GR#15 — this value MUST be read from `trip_generation.json` at load time via a small parallel loader mirroring `scaleLadderData.ts`'s static-import shape, not hand-typed into `data.ts`).
**Check:** a golden fixture with 2 buildings (one `res_hut` at tier 0, one `off_suite` at tier 0) and a hand-set `s.population`/`totalJobs` asserts the exact residentsActual/workersActual/trip numbers.
**False-pass note:** a test that uses `SPECS[...].residents` directly (capacity, not actual) will pass at 100% occupancy fixtures and only fail once occupancy < 100% — the Tester must include at least one fixture where `s.population < onlineResidentsCapacity(s)`.
**Mutant:** replace the occupancy-fraction multiply with `× 1` (i.e. always-full occupancy) — reds the sub-100%-occupancy fixture's trip count.

**AC-2 — mode split reads the ladder's OWN `modeShare.<modeId>` fields; no second density model.**
Each tile's person-trips are split by mode using `ladderPoint.fields` entries keyed `modeShare.<modeId>` (11 keys, per inc0's schema) — read via a small typed accessor `modeShareOf(point: LadderPoint): Record<string,number>` that filters `fields` by the `modeShare.` prefix (the typed-accessor work inc1 deferred to inc2, per inc1's own note "the typed accessor lands in inc2 once the field names are known"). This is the SAME rung-level split for every tile in the city in one tick — no per-tile density lookup against `mode_share_by_density.json` directly (that table is inc0's INPUT to the ladder rollup, already baked into `modeShare` at rollup time; reading it again per-tile would be a second, independently-interpolated density model disagreeing with the ladder's own value the moment the two interpolation rules drift, violating GR#3).
**Check:** `grep -n "mode_share_by_density" webconsole/src/sim/*.ts` outside test files returns no import — the only path to a mode share is through `ladderPoint.fields`.
**False-pass note:** a correct-looking mode split that happens to read the RIGHT numbers but via a fresh `mode_share_by_density.json` import (bypassing the ladder) still passes value-comparison tests today (the two tables currently agree by construction) but silently creates the banned second model — the check above, not a value assertion, is what catches it.
**Mutant:** hand-edit a test fixture's `scale_ladder.json`-derived `modeShare.car` to a value that DISAGREES with `mode_share_by_density.json`'s corresponding band — a compliant implementation follows the ladder value; a violating implementation follows the density table and reds against the ladder-only assertion.

### Freight

**AC-3 — freight tonnes/day from jobs by sector, converted to vehicle-trips via vehicle_classes.json.**
Per tile, freight tonnes/day = `workersActual-by-sector (via totalJobsBySector's SectorJobs shape, data.ts:4404) × trip_generation.json's freightTonnesPerJobPerDay[sector]`. Vehicle-trips = tonnes ÷ `vehicle_classes.json roadVehicles[].capacityTonnes` (cargo_van 1.0t / rigid_truck 12.0t / articulated_truck 26.0t) — the CHOICE of which vehicle class carries a given tile's freight is NOT modelled in inc2 (assumed as an even split by `sectorMixByDensityBand`-implied vehicle mix is out of scope, see §5); inc2 reports tonnes/day and a single blended vehicle-trip count using a fixed weighted-average capacity derived from `data/traffic/trip_generation.json`'s sector mix at the city's current rung (no literal weighting in TS — GR#15).
**Check:** a fixture with one `ind_heavy` building (110 jobs) at a known population asserts the exact tonnes/day and vehicle-trip figures traced back to `freightTonnesPerJobPerDay.manufacturing` (or whichever sector `KIND_TO_WAGE_SECTOR` maps `industrial` to — cite the exact mapping at the site it is read).
**Mutant:** swap `capacityTonnes` for `capacityTonnesRange`'s midpoint hand-typed in TS instead of the JSON field — reds the traced-value assertion when `vehicle_classes.json`'s `rigid_truck.capacityTonnes` (12.0, the already-midpointed canonical field) is edited in the fixture copy and the hand-typed value does not follow.

### Aggregation into line-class and per-segment demand

**AC-4 — per-line-class demand aggregation runs IN PARALLEL to `lineUsageOf`'s existing usage this increment, with a visible divergence indicator (Decision D1).**
A new export `forecastLineUsage(s): Map<spec, {demand: number, legacyUsage: number, divergenceRatio: number}>` sums every tile's mode-split trips into line-class demand (road tiers via `ROAD_TIER_CAPACITY`'s tier keys, rail/hs1 via the modeShare's `rail`/`hs_rail` keys) and reports `divergenceRatio = Math.abs(demand - legacyUsage) / Math.max(1, legacyUsage)` alongside the existing `lineUsageOf(s)` value for the SAME spec, computed but not yet consumed by `lineUsageOf`, `congestionLinesOf`, or the commuter-revenue formula (`data.ts:3164-3175` and neighbouring lines) — this increment does NOT replace those call sites' inputs (GR#3 risk: an unaudited swap could silently move the wellbeing/income penalty onto an unvalidated new number). The switch-over is Decision D1, deferred to Aaron.
**Check:** `grep -n "forecastLineUsage" webconsole/src/sim/data.ts` shows the export defined and, outside its own module/tests, ZERO call sites feeding `lineUsageOf`'s return value or `congestionLinesOf`'s input — mirrors inc1's AC-10 "no consumer yet" contract, but here the NEW artefact is exposed for observation (e.g. a future debug panel), not merely built-and-untouched.
**False-pass note:** a `divergenceRatio` of exactly 0 on every fixture is NOT evidence of correctness — it more likely means the forecast model was accidentally derived FROM `lineUsageOf`'s own output rather than independently from tile demand (a circular "prove itself right" bug). The Tester must confirm `forecastLineUsage` never reads `lineUsageOf`'s `usage` field as an input (only as the comparison target).
**Mutant:** feed `lineUsageOf(s).usage` into `forecastLineUsage`'s own computation (aliasing) — a divergence-ratio-always-zero test passes; the "never reads .usage as an input" grep-based structural check catches it.

**AC-5 — per-segment demand: nearest-segment attribution, precisely specified and deterministic.**
Each demand-generating tile's freight+person trips are attributed to the road/rail segment its BUILDING TILE resolves to via `lineSegmentIdByTileOf(s)` (`data.ts:3483-3484`) if the tile itself is a line tile (stations only — most demand tiles are NOT line tiles); for the general case (a residential/office/industrial tile is never itself a line segment), attribution uses the NEAREST in-scope line tile by Manhattan distance, ties broken by sorted `"x,y"` key order (GR#21 — deterministic, no map-range-with-early-break per the documented gotcha), resolved to that tile's segment via the same `lineSegmentIdByTileOf` map. A tile with no reachable line tile within a bounded search radius (derived from the city's current road-tier reach, not a hardcoded constant — GR#15) contributes to NO segment (honest absence, not silently dropped nor silently assigned to segment 0).
**Check:** a fixture with two parallel road segments of the SAME class, one closer to a dense residential cluster and one closer to sparse buildings, asserts the two segments' `forecastSegmentUsage` DIFFER (the actual fix for Q100163 — today's capacity-share split makes them equal by construction; this must not).
**False-pass note:** a test using only ONE segment per class cannot distinguish "attribution works" from "attribution defaulted to capacity-share" — the Tester must use a two-segment-same-class fixture.
**Mutant:** replace nearest-segment attribution with capacity-share attribution (today's `lineSegmentIndexOf` behaviour) — reds the two-segment differentiation assertion.

**AC-6 — conservation: segment demand sums exactly to class demand (floor-with-remainder-on-last).**
`Σ forecastSegmentUsage[spec].get(segmentId).demand` over all segments of one spec equals `forecastLineUsage(s).get(spec).demand` exactly — same floor-per-segment/remainder-on-last-by-sorted-segmentId idiom `stationUtilisationOf` (`data.ts:3521+`) and `lineSegmentIndexOf` already use.
**Check:** an integer-exact sum-equality test across every in-scope class, on a fixture with ≥3 segments in one class (so the remainder-on-last case is actually exercised, not vacuously true for 1 segment).
**Mutant:** drop the remainder correction (plain per-segment floor, no last-segment adjustment) — reds the sum-equality assertion by the total rounding loss (proportional to segment count).

**AC-9 — determinism and scale (GR#21, BUG-602 class).**

**Check:** `grep -n "Date.now\|Math.random\|localStorage" <new module>` (excluding tests) returns no matches; a `testing`-style alloc/structural pin (mirroring inc1's AC-9) asserts the module's exported functions take `(s: SimState)` only — no citizen-shaped parameter, so it cannot scale with citizen count by construction; a large-fixture timing smoke test exists for LOCAL profiling only and asserts nothing in CI (no wall-clock bounds).

## 4. Decisions for Aaron (recommendation given, not blocking)

**D1 — replace `lineUsageOf`'s usage source, or run in parallel with a divergence indicator?**
**Recommend: parallel-with-indicator for this increment** (AC-4), switch to REPLACE in a follow-up increment once `divergenceRatio` has been observed against real dogfood cities for at least one session. Rationale: the memory lesson on silent divergence between two models (`metropolis-liveness-needs-both-bounds.md` — a fixed-freeze regression shipped a 20× clock runaway because a progress floor existed with no rate ceiling and no indicator) applies directly — swapping the SSOT for `lineUsageOf`'s usage (which already feeds the commuter-revenue formula and the congestion income penalty, `FEAT-2326609772.md` §1) on day one, with no observation window, risks a silent balance regression nobody notices until a much later increment. A visible divergence number costs little and de-risks the eventual switch.

**D2 — does "workers" include MOD-035 external commuters?**
**No, not today** — `grep -rn "MOD-035\|externalCommut\|extcommute\|in-commuter"` over `webconsole/src/sim/data.ts` returns zero matches; the webconsole sim has no external-commuter concept wired (the memory index's `metropolis-extcommute-citizens-gap.md` notes the ENGINE side is blocked on a closed `EmploymentState` enum — a Go-side gap, not resolved here). **Recommend:** `workersActual` for inc2 uses `totalJobs(s)` (all filled jobs, city-wide) scaled per-tile by `capacityAtTier`, i.e. assumes every job is filled by SOME resident-equivalent worker without asking whether that worker physically lives inside the city boundary — this is a KNOWN OVERCOUNT relative to a true resident-vs-commuter split, flagged honestly (ASM below) rather than inventing an external-commuter model inc2 has no data to back (`FEAT-2326609792`'s own epic description lists MOD-035 as a "Reuses" target for the whole epic, not an inc2 deliverable).

## 5. Assumptions

- **ASM-1495** — per-tile actual occupancy is a UNIFORM city-wide fraction (`s.population / onlineResidentsCapacity(s)`) applied to every residential building alike, not a per-building or per-district vacancy model. **What breaks if wrong:** if vacancy is spatially concentrated (e.g. new-build blocks under-occupied while old stock is full), this uniform scaling under/over-states demand at specific tiles even though the CITY total is correct — acceptable for a first increment (the city total, which feeds the class-level demand, is exact; only the SPATIAL distribution within a class is approximate) but should be revisited once a per-building occupancy field exists.
- **ASM-1496** — freight vehicle-class mix (cargo_van/rigid/articulated split) is a single blended weighted-average capacity, not a per-tile vehicle-choice model (AC-3). **What breaks if wrong:** segment-level freight vehicle-TRIP counts (as opposed to tonnes, which are exact) carry a modelling approximation; tonnes/day, the input to `road_wear.json`'s ESAL accrual, is unaffected.
- **ASM-1497 (D2 above)** — workers = `totalJobs(s)`, no external-commuter deduction. **What breaks if wrong:** inc2's forecast demand modestly OVER-counts commute trips relative to a true resident-worker model, in the same direction the epic's own MOD-035 dependency note anticipates being closed later.

**Assumption codes filed on `FEAT-2326609795`:** ASM-1495, ASM-1496, ASM-1497 (`node claude-bow.js add assumption`, `webconsole/src/sim/data.ts`, `ui.webconsole`, per the mandate).
