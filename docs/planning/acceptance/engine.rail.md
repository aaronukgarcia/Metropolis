# Acceptance criteria — engine.rail (MOD-060)

**BOW code:** MOD-060
**Spec refs:** §47 Rail Industry & Interconnected Transport, in full (`docs/METROPOLIS-MASTER-v2.1.md` lines 642-644: "stabling sidings → maintenance depot → heavy works (mandatory per fleet size — unserviced fleets fail in traffic)", "freight yards + intermodal terminal (container crane: sea↔rail↔road transfer in tonnes, §33)", "rolling-stock works... build trains/trams/metros locally (capex ↓, jobs, export contracts to off-map regions — §36 in physical form)", the interconnection doctrine (transfer quality: timed connections, single ticketing, walk distance), the shared citizen/player journey planner, and "badly interconnected networks show up as transfer-penalty mode-share loss"); §33 The Freight Harbour (the tonnes-conservation contract this item's freight-yard consumer relationship inherits); `docs/planning/sprint-plan-v1.md` S10 exit gate (line 38 — this file's share of "balance-of-trade flips demo" via its export-contract line, blocked pending BUG-058, see Escalations); code.json `engine.rail` entry (inbound `RailAPI`, "fleet/works accounting; transfer quality feeds mode logit", zero registered consumers today; outbound calls to `engine.traffic`, `engine.freight`); `engine.logistics.md` (the lead-time-by-mode contract this item consumes rather than duplicates — see Scope).

**IMPORTANT — a registered consumer edge does not yet exist for this module.** code.json's `engine.rail` inbound `consumers` list is empty. `engine.freight`'s own registered consumers list, however, includes `engine.rail` (freight → rail is registered) — so freight can legally call into rail, but nothing is registered to call into `RailAPI` itself from outside this package yet (not even `ui.screen.trade`, which currently only consumes `engine.logistics`/`engine.freight` per that file's own Escalations). This item's ACs are written so its API is ready to be consumed the moment a consumer edge is registered, not blocked by the absence.

**Date:** 2026-08-11
**Status:** ready (rolling-stock export-contract revenue is blocked-pending-fix — see Escalations/BUG-058)
**Package under test:** `internal/engine/rail/` (path from `node claude-bow.js show MOD-060`)
**Standard gates:** see `README.md` — all apply, package for SG-4/SG-7 is `./internal/engine/rail/...`.

## User stories

- **US-1.** As the city's traffic model, I need a fleet whose stabling/maintenance/heavy-works infrastructure genuinely scales with fleet size, so an under-built rail operation fails visibly in traffic (§47's explicit "unserviced fleets fail in traffic"), not silently degrading.
- **US-2.** As `engine.freight` (a registered consumer relationship — freight's own consumers list includes `engine.rail`, and this item's outbound calls include `engine.freight`), I need the intermodal container-transfer point to conserve tonnes across the sea↔rail↔road handoff, per §33's invariant.
- **US-3.** As `engine.traffic` (this item's registered outbound edge), I need hub transfer-quality to be a real number that moves the mode logit, so "badly interconnected networks show up as transfer-penalty mode-share loss" is a mechanic, not narration.
- **US-4.** As a rolling-stock works, I need to build fleet locally at a capex discount and, per §47's own text, sell export contracts to off-map regions using "§36 in physical form" — the same mechanic `engine.capexport` implements — so this item doesn't invent a second export-contract model (GR#3).
- **US-5.** As the citizens' journey planner, I need the router the player queries to be the same one citizens actually use for their trips — this item supplies transfer-quality data into `engine.traffic`'s router (the existing registered edge), it does not build a second router.

## Scope

Fleet/works accounting (stabling → depot → heavy works, scaled to fleet size, with a real under-provisioned-fleet failure mode reaching `engine.traffic`), the freight-yard/intermodal container-transfer point consuming and conserving tonnes via `engine.freight`, hub transfer-quality scoring fed into `engine.traffic`'s mode logit, and rolling-stock works build-cost accounting via the discount mechanic. Rolling-stock export-contract revenue ("§36 in physical form") is named by spec but has no registered call edge to `engine.capexport` or `engine.finance` — scoped out, blocked-pending-fix (see Escalations). The journey-planner query surface itself, and lead-time-by-mode logistics accounting, are `engine.traffic`'s and `engine.logistics`' own contracts respectively — this item feeds data into them, it does not rebuild either.

## Acceptance criteria

### Functional

- **AC-1 (GR#20; code.json inbound contract).** A `RailAPI` exists matching code.json's registered pattern — fleet/works accounting; transfer quality feeds mode logit — with fleet-serviceability state consumed by `engine.traffic` and freight tonnage consumed by/through `engine.freight`, exclusively through their registered interfaces. Check: `go doc ./internal/engine/rail RailAPI` shows a fleet-accounting surface and a transfer-quality query; `grep -rln "traffic\.\(modeLogit\|Registry\)\.\w\+ = \|freight\.\(tonnesState\)\.\w\+ = " internal/engine/*/ internal/ui/*/` (excluding `internal/engine/rail`, `internal/engine/traffic`, `internal/engine/freight`, and `_test.go`) finds no direct exported-field write bypassing either interface.
- **AC-2 (§47 fleet-size-scaled works — the failure mode is real, not flavour).** Stabling/maintenance-depot/heavy-works capacity is tracked against fleet size with a documented data-driven ratio (ASM-311), and a passing test constructs two scenarios differing only in whether works capacity meets or falls short of the ratio for an identical fleet size, asserting the under-provisioned scenario produces a measurable degraded-serviceability signal read back through `RailAPI` (not merely logged) that a consuming `engine.traffic` call would receive as reduced availability/reliability. Check: `grep -rn "func Test.*[Uu]nservicedFleet\|func Test.*[Ww]orksCapacity" internal/engine/rail/*_test.go`. A lazy-but-plausible violation: a works-capacity field that is tracked and displayed but never actually gates a serviceability output — this check rejects it by requiring the degraded scenario's serviceability figure to differ measurably from the adequately-serviced scenario's, both read through the same accessor.
- **AC-3 (§33/§47 intermodal tonnes conservation).** The freight-yard/intermodal container-transfer point conserves tonnes across the sea↔rail↔road handoff — a passing test moves a known tonnage through the transfer point and asserts total tonnes in equals total tonnes out (accounting for any documented dwell/buffer state, which must itself be queryable, not lost). Check: `grep -rn "func Test.*[Tt]onnesConserv\|func Test.*[Ii]ntermodalTransfer" internal/engine/rail/*_test.go`. False-pass risk: a test that only asserts the transfer point *reports* a conservation-OK flag would pass a build that never actually sums the physical tonnage — the check requires summing tonnes-in and tonnes-out independently and comparing. **Cross-ref (deliberately not merged):** this same tonnes-conservation invariant is specified three times in this wave — `engine.freight.md` AC-10 (system-wide freight mass conservation) and `engine.chemicals.md` AC-3 (per-stage chain tonnage identity) also carry it; keep all three, each checking its own slice of the same physical tonne.
- **AC-4 (§47 interconnection doctrine — transfer quality is a real, moving number).** Hub transfer-quality (timed-connection tightness, single-ticketing flag, walk distance between modes) is computed per hub and fed into `engine.traffic`'s mode logit through the registered edge, and a passing test asserts changing walk distance (holding timing/ticketing constant) changes the fed transfer-quality figure, and separately that a worse transfer-quality figure produces a measurably lower mode-share for rail in a paired `engine.traffic` scenario (or, if that scenario composition belongs to a later integration test, at minimum that the transfer-quality figure itself responds to each of its three named inputs independently). Check: `grep -rn "func Test.*[Tt]ransferQuality" internal/engine/rail/*_test.go`. A lazy-but-plausible violation: a single flat "hub quality: good/bad" enum with no walk-distance/timing/ticketing decomposition — this check rejects it by requiring each of the three named inputs to move the output independently.
- **AC-5 (§47 badly-interconnected penalty — the negative branch, not just the positive).** Mirroring AC-4 but from the failure side (the spec's own "badly interconnected networks show up as transfer-penalty mode-share loss"): a passing test constructs a deliberately poor-transfer hub (long walk distance, no timed connections, no single ticketing) and asserts the fed transfer-quality figure is measurably worse than a well-connected hub's, in the same test run as the positive case — not a separate test that could each pass with a one-way "quality can only improve" model. Check: `grep -rn "func Test.*[Bb]adInterchange\|func Test.*[Tt]ransferPenalty" internal/engine/rail/*_test.go` asserts both a good-hub and a bad-hub figure in the same run with a strict inequality between them.
- **AC-6 (§47 rolling-stock works — local build discount).** Building rolling stock locally (via the works, once constructed) carries a documented capex discount versus off-map procurement, exposed as a comparable figure through `RailAPI`, and a passing test asserts the local-build cost is strictly less than the equivalent off-map-procurement cost for the same stock spec. Check: `grep -rn "func Test.*[Ll]ocalBuildDiscount\|func Test.*[Rr]ollingStockCost" internal/engine/rail/*_test.go`.

### Error handling

- **AC-7 (GR#7).** Assigning fleet beyond currently-registered works capacity without an explicit acknowledgement of degraded serviceability (AC-2) returns a registry-sourced error/warning event distinct from a silent capacity overrun. Check: `grep -n "MET-" internal/engine/rail/*.go` finds a registry code reference; passing test coverage (`grep -rn "func Test.*[Cc]apacityOverrun\|func Test.*[Ff]leetExceedsWorks" internal/engine/rail/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error/warning's registry code matches AND that no silent capacity overrun was accepted without the required acknowledgement, not merely that a matching-named test function exists.

Check: `grep -n "MET-" internal/engine/rail/*.go` finds a second distinct code; passing test coverage (`grep -rn "func Test.*[Mm]alformedRailData" internal/engine/rail/*_test.go`) — **GR#7 assertion, stated explicitly (BUG-100):** the test asserts the returned error's registry code matches AND that no default-to-zero walk-distance/fleet value was silently loaded, not merely that a matching-named test function exists.

## Escalations

- **For Ben/Bill — BUG-058 (this file's stake, filed as part of the four-instance comment 2026-08-11).** `engine.rail → engine.capexport` (or, failing that, a direct `engine.rail → engine.finance` edge) is missing despite §47's own text framing rolling-stock export contracts as "§36 in physical form" — literally the same mechanic MOD-049 (`engine.capexport`) already implements with a registered `FinanceAPI` edge. Building a second, parallel export-contract/ledger path inside `engine.rail` instead of waiting for the edge would be a GR#3 violation; I've scoped AC-6 to stop at the local-build discount (a real, checkable figure with no cross-module dependency) and left export revenue blocked. Recommend wiring `engine.rail → engine.capexport` specifically (not a bespoke finance edge), since capexport already owns the contract-curve/`ProjectionsAPI` machinery this revenue stream should share.
- **For Ben/Bill — no registered consumer of `RailAPI` exists yet.** Flagged at the top of this file: neither `ui.screen.trade` nor any engine module currently has a registered inbound edge to `engine.rail`. This item's ACs are written to be consumer-agnostic (testable against `RailAPI` directly) so this doesn't block build, but it's worth confirming at S10 dispatch whether `ui.screen.trade` (or a new F5 extension) is meant to pick this up, since the player currently has no named screen path to see rail-industry state.
- **For Aaron (ASM-311).** The fleet-size-to-works-capacity ratio used in AC-2's failure-mode test is a placeholder, data-driven figure — §47 mandates the *rule* ("unserviced fleets fail in traffic") but not the numeric ratio. Real figures (ideally grounded in a reference operator's stabling-diagram ratios, since the spec's own Sandwich/Kent-precedent style favours real-world grounding) are Aaron's call.

## Spec-fold amendments (FEAT-084 SF wave, 2026-08-18)

> Substantive AC amendments folded from the FEAT-084 ASM disposition (class SF).

### ASM-1267 — modal-cap drift test instead of a live freight import (amends AC-3)
The GR#3 drift between `engine.rail`'s modal caps and `engine.freight`'s modal caps is closed with a `_test.go` drift test (`TestModalCapsAgreeWithFreight`) rather than a live import of `freight.ModalCap` — a live import would require constructing a full `*freight.FreightAPI` (`freight.LoadDefault` pulls in `engine.market` + `engine.logistics`), which the stub deliberately avoids via its self-contained `loadModalCaps` reader. The drift test is the tripwire that fails on any silent divergence (verified: it fails rail=0 vs freight=3000 when min parsing is dropped). Check: `grep -rn "TestModalCapsAgreeWithFreight" internal/engine/rail/*_test.go` matches, and the test fails when rail's caps disagree with freight's.

### ASM-1028 — intermodal edge built stub-first (amends AC-3; MOD-060 was open, no package)
When `feat.containerport` needed the intermodal handoff, `engine.rail` (MOD-060) was open with **no package**, so the edge was built stub-first: a minimal stub-for-baseline `internal/engine/rail` `RailAPI` exposing only `IntermodalTransfer` (this AC-3's tonnes conservation), consumed by `feat.containerport` through the `freight.RailIntermodal` dependency-inversion seam — mirroring how `engine.firms` implements `freight.FirmRegistrar`. No import cycle: rail imports freight, freight never imports rail. The full MOD-060 build (this file) replaces or expands that stub; AC-3's tonnes-conservation check runs against whichever implementation is live.

### ASM-1270 — under current data every sea-involving handoff is rejected (documented stub limitation on AC-3)
Under current data — **sea min 3000t, rail max 1000t, road max 25t** — every sea-involving intermodal handoff is rejected, because the stub models one handoff as one movement of each mode (AC-3), so a sea leg needs ≥3000t in a single movement that rail (1000t) or road (25t) cannot carry. This rejection is accepted as a **stub-level limitation**: if the full MOD-060 build allows a sea leg to split across multiple rail movements, the stub-level rejection is too strict — but that is the full build's modelling, out of scope for the stub. A test asserting a sea↔rail handoff *succeeds* at 3000t would fail today and must not be written until the full build lands.

- **ASM-1268 (confirm-and-close).** The intermodal below-min floor is the LARGER of the two modes' per-movement minimums (both legs must meet their mode's floor); with `min >= 0` validated, that is `tonnes < max(minFrom, minTo)`.


### ASM-1073 — intermodal modal cap is min(source,dest) max (amends AC-3/AC-13)


The intermodal transfer point enforces the smaller of the source and destination modes' `maxTonnesPerMovement` from `data/freight.json` (road 25 / rail 1000 / sea 40000). Only MAX caps are enforced at the transfer point; sea's 3kt minimum is **not** enforced because a handoff is a leg, not the whole sea movement. Over-cap is rejected (AC-13 reject-don't-clamp), never clamped.
