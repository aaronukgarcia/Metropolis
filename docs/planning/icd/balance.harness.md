## 2. Purpose

`balance.harness` (MOD-036, M2) is the mechanical home of the balance-number regime: it sweeps player-felt parameters across seeded scenario definitions, fans each point out through `harness.headless` (a full deterministic engine run over a tick window) on worlds generated by `harness.synth`, and compares results across seeds to land pacing at "achievable-but-hard" instead of by hand-guess. Today `tools/balance/` does not exist, so pacing/balance proposals have no reproducible, data-derived sweep to back them. This module provides that harness: a CLI that takes a JSON scenario (parameter ranges + metric targets), runs the sweep, and emits comparable per-seed results a BA/Aaron can approve row-by-row.

## 3. Inputs

| Source module | Shard-state read | Type |
|---|---|---|
| `balance.harness` (CLI) | JSON scenario definition — parameter name/range, sweep points, target metric, seed set | CLI args / `tools/balance/scenarios/*.json` |
| `harness.synth` | A seed-derived synthetic world/citizen fixture for each sweep point | synth fixture (opaque; consumed by `harness.headless`) |
| `harness.headless` | A full deterministic engine run over a fixed tick window (the sweep's measurement) | headless run result (metric deltas, invariants) |

The sweep is command-only from `balance.harness`'s point of view: it never mutates engine state directly, only observes the results `harness.headless` returns. The metric (pacing, population response, money flow) is read out of the headless run's end-state deltas, not computed inside the harness.

## 4. Outputs

| Effect | Target stock/edge | Type |
|---|---|---|
| Per-seed metric-vs-parameter result table | CLI stdout / a results JSON — no engine stock, no conservation accumulator (offline tooling) | JSON (`tools/balance/results/*.json`) |
| Achievable-but-hard pacing proposal | a proposal diff for `data/*_balance.json` parameters — authored as a delegate proposal, not applied directly (balance-number regime: Aaron approves row-by-row) | JSON proposal |
| Sweep determinism proof | two identical sweep runs (same seeds) produce byte-identical result tables — the evidence a tuning change is reproducible | n/a |

No `simState` ledger (`peopleDelta`/`moneyDelta`) or any conservation accumulator is mutated by the harness itself — every engine mutation happens inside the disposable headless runs it spawns, which are discarded after measurement.

## 5. Update Class

**T1** — batchable. A parameter sweep is a heavy, shardable, cloud-offloadable workload (one headless run per sweep point, each independent), but it is explicitly not in the critical every-tick tier (it drives disposable headless engines, never the live sim) and is not coalescible display telemetry (its results are authoritative tuning evidence). The sweep queue absorbs bursts; a one-run skew degrades wall-clock duration only, never a live invariant.

---

## 6. Shard Scope

**Single-shard** in the integration sense: the `SweepRunner` CLI is one process with one entry point; it does not participate in the engine's 256-shard tick. Parallelism lives one level down — the fan-out across sweep points is a plain worker pool over independent `harness.headless` runs, each of which is a complete deterministic engine instance with its own shard/phase machinery. If/when this is later expressed as an `integration.Integration[T,M]`, it is `SingleShard() == true` (one call per sweep, not per shard).

---

## 7. Determinism Guarantee

Every sweep point is keyed by an explicit seed (from the scenario's seed set); `harness.synth` and `harness.headless` both derive their worlds and runs from that seed, so two runs of the same scenario produce byte-identical result tables regardless of worker count or fan-out order — results merge in ascending (sweep-point, seed) order, never in completion order. **No wall-clock time is read anywhere in this integration**: sweep duration is an operational metric only, never a determinism input; "ticks run" is `core.Engine`'s internal logical counter, not `time.Now()`.

---

## 8. Error / Registry Codes

`balance.harness` has **no MET range of its own yet** (it is a `tools/` layer module, not an engine module — GR#7 range claim must happen when it is built). It surfaces registry codes from its two dependencies (`harness.headless` and `harness.synth`, both of which carry foundation error ranges) and wraps its own CLI/scenario validation failures via `foundation.errors` with a `balance.harness` correlation id. Open item (§12 OD-2): claim a tooling error range before the first scenario validator is written, so no ad-hoc string errors exist.

---

## 9. Resilience Behaviour

Offline CLI — the degenerate `integration.LocalReconnectHooks` case (no connection, no queue, no catch-up). The only failure modes are a malformed scenario (fail-fast, registry-wrapped) or a crashed headless run; both are deterministic given the same seed, so the correct "retry" is "fix the scenario/seed and re-run the sweep", never a backoff loop. A crash mid-sweep is recovered by re-running the idempotent sweep — results are pure functions of seed, so partial sweeps are simply discarded and re-derived.

---

## 10. Monitoring Signals

**Status:** sweep running / complete / failed (a single state flag on the CLI). **Throughput:** completed sweep points per second (wall-clock, operational only). **Queue depth:** pending sweep points remaining in the fan-out pool. **Peak load:** max concurrent headless runs (the wall-clock cost of the sweep, watched against machine limits — not a determinism input).

---

## 11. Required Tests

- **Determinism:** two identical `sweep` runs (same scenario, same seeds) produce byte-identical result JSON, regardless of worker-pool size.
- **Sweep reproducibility / regression:** a fixture scenario with a known achievable-but-hard target asserts the harness proposes a parameter within tolerance of that target (the "results comparable across seeds" contract).
- **Contract-conformance:** the scenario JSON schema validator rejects malformed sweeps (missing seed set, empty parameter range) with registry codes — the ICD's §3 Inputs contract, not prose.
- **AC-coverage:** the MOD-036 acceptance criteria must exist and pass `tools/plan/spec-lint.js` clean before the Go/CLI build (GR#25 standing rule).
