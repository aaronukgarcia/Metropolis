## 2. Purpose

`engine.citizens`' `EmploymentState` is a closed 5-value enum (`EmploymentNone/Student/Employed/Unemployed/Retired`) with no way to represent a resident who commutes to an off-map job pool (§21 external commuting — London/Ashford/Dover). `engine.extcommute` (already built, `E:\git\metropolis-bob\internal\engine\extcommute`) tracks its own `assignments map[citizenID]{poolID, sinceMonth}` internally, but never writes that fact back into the citizen's own `Employment.State` — so a citizen assigned off-map still reads as `EmploymentEmployed` or `EmploymentUnemployed` in citizens' own record. This breaks `engine.extcommute.md`'s AC-6 dormitory-arithmetic identity (`TotalWorkingAgeResidents == Σ LocallyEmployed + Σ_pool OffMapEmployed(pool) + Unemployed + NotInLaborForce`, exact, not approximate): the same citizen is currently either double-counted (once in `LocallyEmployed`/`Unemployed` via citizens, once in `OffMapEmployed` via extcommute's own map) or, if never locally employed, silently uncounted. AC-6 and AC-7 (the identity holding across every assign/release transition) are honestly skip-gated in `engine.extcommute.md` today for exactly this reason (see that file's Escalations section, "cross-module obligation on `engine.citizens`"). This extension adds the one enum variant citizens is missing so a citizen's own record can distinguish "has a job, but off-map" from "has a job, locally" — unblocking `engine.extcommute` to flip a citizen's coarse state on `Assign`/`Release` and making the AC-6/AC-7 identity computable and exact.

## 5. Update Class

**T1 (batchable).** `EmploymentState` transitions are not named in the Integration Engine proposal's critical-tier set ("population, money, conservation — small, must run every tick"); an employment-state flip has no conservation-accumulator effect (§4) and is not on the critical-tier population/money path. It is driven by `extcommute.Assign`/`Release`, which are themselves player-command-triggered (not a per-tick unconditional pass like `AdvanceDayTick`), so there is no "must land this exact tick" requirement — a one-tick delay between the `extcommute` command committing and the citizen's own `Employment.State` reflecting it would not corrupt any invariant (extcommute's own `assignments` map is the AC-3/AC-8 capacity-enforcement source of truth regardless of when the citizens-side flag catches up). In practice both mutations happen synchronously in the same call (§4), so this is a batchability classification, not an actual observed lag.

---

## 6. Shard Scope

**Single-citizen, not shard-scoped.** `ApplyLifeEventCommand(LifeEventEmployment)` already operates on exactly one `CitizenID` per call (`registry.go:414-430`) — it looks up the citizen's shard via `mutateColdLocked` internally (citizens' own `det.ShardForEntity` routing, unchanged) and mutates only that one row. `extcommute.Assign`/`Release` are themselves single-citizen commands (`AssignCommand.CitizenID`, `ReleaseCommand.CitizenID`) — there is no batch/all-shards path in this extension. `runShardsParallel`/`ColdPassSchedule` (the cold pass's own shard fan-out) are untouched; this extension does not add a new per-shard pass, only a new value the existing single-citizen command already knows how to write.

---

## 7. Determinism Guarantee

The extension introduces no new stochastic draw. `EmploymentOffMap` is written only via `ApplyLifeEventCommand`, an explicit command from `extcommute.Assign`/`Release` — both of which are themselves deterministic functions of `(worldSeed, tick/month, command log)` per `engine.extcommute.md` AC-16 (unchanged by this ICD). `validateEmploymentState`'s widened range check (§8) is a pure comparison, no randomness. The cold-pass `matchJob` (`coldshard.go:217-233`) statistical job-matching switch is amended (§11) to explicitly SKIP `EmploymentOffMap` citizens (they hold a real job already; the deterministic per-citizen draw `hash(seed, id, month, "employment")`/`hash(seed, id, month, "employment-sector")` must not fire for them) — this is an explicit new `case` added to an existing `switch`, not a new draw. **No wall-clock time is read anywhere in this extension** — every mutation is command-driven (extcommute's own commands, themselves GR#21-compliant) or a pure per-field range/domain check.

## 8. Error / Registry Codes

`engine.citizens` owns range `MOD-018` / `MET-G000`–`MET-G099` (`data/errors.json`'s `G000-G099` block). This extension surfaces **no new error code** — `validateEmploymentState` (`citizen.go:243-245`) already routes an out-of-domain value through the existing generic `fieldOutOfRange` → `MET-G007` (`ErrFieldOutOfRange`, "citizen {id} field {field} value {value} is outside [{min}, {max}]") path; widening the upper bound from `EmploymentRetired` (4) to `EmploymentOffMap` (5) only moves where the boundary sits, it does not change which code fires for a value outside the (now six-value) domain. `LifeEventEmployment`'s existing pre-mutation validation call (`registry.go:419`, `validateEmploymentState(cmd.CitizenID, cmd.Employment, cmd.CorrelationID)`) needs no signature change — it already rejects any value the updated `validateEmploymentState` deems out of range, using the same `MET-G007` code. **No `tools/plan/add-error.js` registration is needed for this extension.**

## 9. Resilience Behaviour

In-process, always-connected — the degenerate case, same as the reference `engine.citizens-coldpass.md` ICD. `ApplyLifeEventCommand(LifeEventEmployment)`'s only failure mode for this extension is the existing `MET-G007` domain-validation rejection (deterministic given the same inputs — a caller passing an already-invalid `EmploymentState` will fail identically on retry; the correct fix is the caller bug, not a backoff loop) or the pre-existing `MET-G004` copied-handle rejection (SEC-020 family, unrelated to this extension). No queue, no catch-up semantics beyond the existing checkpoint/replay path — this extension adds a value to an enum and one new `switch`/`if` arm per consumer (§11), not a new subsystem with its own failure surface.

## 10. Monitoring Signals

No new monitoring surface. The existing `PopulationHash` (§4) already fingerprints the new state value as part of its generic per-citizen `EmploymentState`/`Sector` byte pair — no dashboard change needed to detect a determinism divergence involving off-map citizens. `extcommute`'s own `FilledSlots`/`Assignment` queries remain the authoritative operational signal for pool occupancy (§12 Open Decision 1) — citizens' `Employment.State == EmploymentOffMap` is a coarse cross-check signal only (e.g. a future audit test could assert `count(citizens with EmploymentOffMap) == Σ_pool extcommute.FilledSlots(pool)`, the cross-module consistency check named in §11's required tests), not a replacement for extcommute's own bookkeeping.

## 11. Required Tests

- **Enum domain / round-trip:** a new `citizens` package test asserting `ApplyLifeEventCommand(LifeEventEmployment, Employment: EmploymentOffMap, Sector: SectorNone)` succeeds, that `GetCitizen`/cold `recordAt` round-trips the value losslessly through `packEmployment`/`unpackEmployment` (the 4-bit state nibble has room — current max packed value is 4, `EmploymentOffMap` is 5, well inside the 0-15 nibble range), and that `EmploymentOffMap+1` (6) is still rejected via `MET-G007` (proves the domain widened to exactly one new value, not silently opened further).
- **Exhaustive-switch guard test:** a table-driven test in `internal/engine/citizens` (or a small cross-package audit test, since some switches live outside citizens — see the file:line list below) that iterates every declared `EmploymentState` constant against each switch's known case set and fails if a new constant is ever added without a corresponding `case` — the mechanical guard against "a new enum variant silently falls through any switch" this ICD's own DISCOVER phase was asked to protect. Concretely, this extension must land a `case citizens.EmploymentOffMap:` (or an explicit documented pass-through) at every one of these sites, each independently verified against `engine.extcommute.md`'s ACs:
  - `internal/engine/citizens/coldshard.go:217-233` (`matchJob`) — **must add `case EmploymentOffMap:` that does nothing** (an off-map-employed citizen already has a job; the statistical job-matching draw must not fire for them, mirroring the existing implicit skip for `EmploymentEmployed`'s own sector-drift-only case). Without this, the `switch`'s default (no case matches) already happens to no-op today — but that is accidental (Go's zero-case fallthrough), not documented; making it explicit is required so a future reader cannot mistake it for an oversight. **Not a silent-drop risk today** (falls through to no-op either way) but flagged for explicitness.
  - `internal/engine/wellbeing/drivers.go:114-140` (`jobLevel`) — **REAL SILENT-MISCLASSIFICATION RISK.** This `switch` has a `default: return 0.0` (line 137-138). Without an explicit `case citizens.EmploymentOffMap:`, an off-map-employed citizen (who has a real, often well-paid job) would silently be scored `jobLevel == 0.0` — WORSE than `EmploymentUnemployed`'s `0.1` — corrupting `jobAmbitionMismatchDelta`'s wellbeing driver for every dormitory-town resident. Must add an explicit case (proposed: treat as `EmploymentEmployed` would with an unknown/off-map sector — i.e. return the same `0.5`+ baseline the `SectorPrimary`/default sector case uses, a documented ASM-5-class placeholder like the rest of this function, not a new balance decision this ICD makes unilaterally — flag the exact number for Bill/Aaron same as the rest of `jobLevel`'s placeholder values).
  - `internal/engine/leisure/types.go:101-117` (`lifeStageFor`) — **note only, not this ICD's file to edit** (another agent is building in `internal/engine/leisure` concurrently per this task's own instructions). This `switch` has no `default:` case; an unmatched state falls through to the post-switch age check (`StageChild` if under 18, else `StageUnemployed`). An off-map-employed adult would silently be bucketed as `StageUnemployed` for weekly-budget purposes — wrong (they have full working hours, just off-map) but not a panic. **Flagged for the leisure-module owner to add `case citizens.EmploymentOffMap: return StageEmployed` before merge; out of scope for this ICD's own file writes.**
  - `internal/engine/census/stats.go:144-152` (`switch cv.Employment`) — **not affected.** `engine.census` owns its OWN independent `EmploymentState` type (`census/sources.go:83-91`, a separate 5-value enum, not `citizens.EmploymentState`) fed through a `CitizenView` seam adapter that does not exist in production code yet (only test fakes populate `CitizenView` today — `grep -rn "CitizenView{" internal/ cmd/` finds no non-test construction site). When that adapter is eventually built (composition-root scope), its author must decide how to map `citizens.EmploymentOffMap` into census's own bucket set — flagged as a future obligation, not a live exhaustive-switch gap today.
  - `internal/engine/households/types.go:147-166` (`deriveLifeStage`) — **not a switch, no risk.** Two independent `if m.Employment.State == citizens.EmploymentRetired`/`== citizens.EmploymentStudent` equality checks, not an exhaustive switch; an off-map-employed member simply falls through to the same "other" default an `EmploymentEmployed` member already does. No change required.
- **Conservation-unchanged test:** a `citizens` package test asserting `TotalPopulation()`/`PopulationHash` before and after an `Assign`-equivalent `LifeEventEmployment` → `EmploymentOffMap` transition shows population count exactly unchanged (only the hash differs, proving the state changed but the resident count did not) — the concrete expression of §4's "no conservation-accumulator effect" ruling.

## 12. Change Control

Additive-only: `EmploymentOffMap = 5` is a new enum value, not a change to any existing value's meaning or the `packEmployment`/`unpackEmployment` layout (the 4-bit state nibble already accommodates values 0-15; no persistence-format migration is needed for existing saves, which never contain the value 5 in that column). Any later REMOVAL or renumbering of an existing `EmploymentState` value would require a new ICD version and a fresh Destructive-verdict round (GR#23) on every listed consumer switch, per the template's standing rule.

**Open decisions this ICD rules on (not deferred):**

1. **No pool id / since-month duplication in citizens (ruling, not deferred).** The task brief that produced this ICD proposed "OffMapEmployed with pool id + sinceMonth" as a starting hypothesis. Having read `engine.extcommute`'s actual code (`E:\git\metropolis-bob\internal\engine\extcommute\extcommute.go`/`types.go`), that module ALREADY tracks `{poolID, sinceMonth}` per citizen in its own `assignments` map and exposes it via `Assignment(citizenID)` — its own source comment states this explicitly: *"the 'which pool, since when' the citizens EmploymentState enum does not carry."* Duplicating pool id/since-month inside citizens' own record would create a second, independently-mutable copy of the same fact — a direct GR#3 (Single Source of Truth) violation risk (the two copies could drift on a partial-failure path, e.g. citizens' flip succeeds but extcommute's map write fails, or vice versa) for zero additional capability: no AC in `engine.extcommute.md` reads pool id or since-month FROM citizens — AC-6/AC-9/AC-11's checks all query `extcommute.Assignment`/`FilledSlots` directly. **Ruling: citizens gets ONLY the coarse `EmploymentOffMap` state, no pool/month payload.** `extcommute.Assign`/`Release` remain the sole source of truth for which pool and since when; citizens is the sole source of truth for the coarse resident/employment bucket. This is the minimal extension that unblocks AC-6/AC-7 (§2) without gold-plating.
2. **`NotInLaborForce` — ruled NOT needed as a new stored enum value.** `engine.extcommute.md` AC-6 names four buckets: `LocallyEmployed, OffMapEmployed(pool), Unemployed, NotInLaborForce`. Re-reading AC-6/AC-7's actual check requirements: neither AC requires citizens to STORE a `NotInLaborForce` state — the identity is a SUM check performed by whatever test/consumer computes it, and "not in labor force" is already fully expressible as a computed aggregate over citizens' EXISTING states for working-age residents: `NotInLaborForce := count(EmploymentRetired) + count(EmploymentStudent) + count(EmploymentNone AND age >= 18)` (the last term because `EmploymentNone`'s documented meaning is "child / never worked," `types.go:36`, and `leisure/types.go`'s own `lifeStageFor` already draws exactly this child-vs-adult distinction via `cit.Age() < 18*12`). Adding a redundant stored `NotInLaborForce` value would let an adult's state simultaneously be expressible two ways (`EmploymentNone` OR `EmploymentNotInLaborForce`) with no rule forcing consistency — a genuine gold-plating risk the task brief itself warned against. **Ruling: no new enum value; the AC-6 test (built at the `engine.extcommute` consumer, not here) computes `NotInLaborForce` as the aggregate above.**
3. **GR#25 edge check — confirmed no missing edge.** `code.json`'s `engine.citizens` module (`guid 99e0d1f5-...`) already lists `engine.extcommute` (`outboundGuid d4dbc368-...`) as a registered inbound consumer, and `engine.extcommute`'s own `outbound.calls[]` lists `engine.citizens` (`moduleGuid 99e0d1f5-...`, `inboundGuid 35078084-...`) symmetrically. Verified read-only against the live `code.json` at authoring time (2026-08-18) — **no new edge registration is required before the extcommute-side build proceeds.**
4. **Flagged for Bill/Aaron — `extcommute`'s own build is out of this ICD's scope.** This ICD only specifies the CITIZENS-side extension (new enum value, widened validator, the `matchJob`/`jobLevel` switch amendments). Wiring `extcommute.Assign`/`Release` to actually CALL `ApplyLifeEventCommand` (§4's output row) is a change to `engine.extcommute`'s own code (`E:\git\metropolis-bob`, a different worktree/lane) and must be dispatched as its own follow-up build item against this ICD once it lands here — not bundled into this citizens-side commit.
