### Tier 1 detail

### GGR16v03 — Cost gate — human authorisation before anything that could incur money

**Why:** Written after a real cloud/CDN/registrar setup where cost-bearing actions could otherwise slip through under normal agentic momentum. A hook alone cannot forecast cost, and a skill alone cannot stop a tool call — the hook is the wall, the human's Authorise answer is the only key, and false positives (one extra confirmation round-trip) are strictly preferable to a false negative (unauthorised spend).

**Applies when:** the agent has tool access capable of creating cloud resources, spending money, or navigating to payment flows

**Merged from:** COST_GATE

### GGR38v02 — Secrets and credential lifecycle — never committed, always rotated, always audited

**Why:** Repos get cloned, forked, and made public, and CI logs get shared — a committed key is compromised the moment it lands, and deleting the file does nothing because history retains it. Gitignore failures are asymmetric: they work silently for years, then one renamed key file slips past an exact-name rule and is in history forever. If rotating a key means re-encrypting everything or a big-bang cutover, rotation gets deferred forever — envelope encryption and dual-accept rollover windows are what make rotation boring enough to actually happen, and recovery keys need at least two independent custody locations, one offline/human.

**Merged from:** SEC-01, SEC-07, SEC-08, SEC-14

### GGR66v02 — Nothing outside a project's boundary; every project uses its own temp folder

**Why:** Aaron, 2026-09-24: scratch folders and files were littering every drive. The first tidy run found 57 loose entries at roots, 4 shared temp folders in use, a 10.5 GB SitRep checkpoint folder outside the SitRep repo, and a folder of contact data at C:\temp_pw.

### GGR34v02 — Destructive-operation protocol — query first, confirm twice

**Why:** A bulk operation with a subtly wrong filter deletes the wrong rows at machine speed; the query-first step converts 'I think it affects 4 rows' into 'it affects these 4 specific rows, here they are' before anything irreversible happens. The same discipline also stops a compromised or confused tool/agent from doing catastrophic damage.

**Applies when:** the project has a datastore that supports bulk or irreversible mutation operations

**Merged from:** DATA-07, GGR12v01

### GGR64v02 — No AI attribution in git, ever

**Why:** Aaron's repos are his work under his name; a 2026-09-24 sweep found 1,115 commits across 11 repos carrying Claude co-author trailers that the harness had added by default.

### GGR35v03 — No feature without backup; no backup without a tested restore

**Why:** A new storage area silently missing from backups is invisible until the exact day it is needed — the single worst moment to discover it. Untested backups fail at that same moment for reasons that never show up any earlier: a lost key, a missing collection, a format that no longer parses.

**Applies when:** the project has persistent state worth losing

**Merged from:** DATA-08, GGR36v01

### GGR3v03 — Silent failure detection — every background job proves it is alive

**Why:** A scheduled job silently OOM'd every run for six-plus weeks while appearing ACTIVE in the platform's own listing; the dashboard kept showing the last successful run's timestamp because the crash happened before the status write. Nobody noticed because nobody had a freshness monitor, and the failure only ever touched a status document, never the error log anyone actually looks at.

**Applies when:** the project runs scheduled or background jobs

**Merged from:** GR#17, ERR-04

### GGR68v02 — A hook never blocks a tool call because the hook itself failed, except the money, secret and deletion gates, which fail closed with a named, logged disable variable

**Why:** The v1 text was written after a Ghost Flux hook blocked prompts; its cure (exit 0 on every failure) would also have made the cost gate, the secret scan and the deletion gate fail open, and it ran from a synced folder in breach of GGR63. The spec's fail-mode policy (section 3) keeps the cure for nudges and names the three gates that must not have it.

**Applies when:** any project configures Claude Code hooks in settings.json

### GGR7v02 — Multi-agent identity, leases, and claimed territory

**Why:** Two agents editing the same file produces silently lost work or merge chaos, and unattributed actions make every incident unauditable. Leases must expire on their own because crashed sessions never clean up. An agent once trusted a stale 'you are X' marker after an anomaly and worked under another live session's name — the fix is to always re-derive identity from state, never from memory, and to keep an honest running tally rather than claiming a clean record when a mid-session correction actually happened.

**Applies when:** more than one agent or human session can work the same project concurrently

**Merged from:** GR#4, GR#8, AGENT-01

### GGR70v03 — No project is 'assembled' until forge doctor is green

**Why:** A freshly-assembled project (2026-10-07) was reported 'assembled' with every hook dead: forge wrote the hook scripts to the repo root while settings.json wired them under harness/ and the scripts set projectRoot=__dirname/.., so SessionStart failed MODULE_NOT_FOUND and no guard fired. Nothing caught it because nothing ran the project before it was declared ready. A deterministic post-assembly smoke test is the gate.

**Applies when:** assembling or upgrading a project via forge /new

**Merged from:** GGR47v01

### GGR63v02 — Nothing executes from a cloud-synced folder

**Why:** Executing from E:\GoogleDrive intermittently failed with 'Access is denied' on both new.bat and sunset.bat during the first forge trial on 2026-09-19, and Drive refused to write a dot-file in the same folder. The other launchers never failed because they live in the local WindowsApps folder.

### GGR88v01 — Every change to the kit, the rules or the registry carries its project, session and identity

**Why:** Before Wave 4 forge fell back to the bare codename and wrote events with no project; a registry whose history cannot say who changed what, from where, cannot be trusted as the source of the kit (GGR7's "every action is attributable" and GGR22's "registry in sync in the same commit" are its ancestors).
