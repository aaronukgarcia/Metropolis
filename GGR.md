### GGR1v01 — Aggressive error trapping — four pillars, no exceptions

Every function, API call, database operation, or async action must have comprehensive error handling with all four pillars present on every error: it is logged to a persistent, queryable store; it carries a typed code from a central registry (never a hand-typed string); it carries a unique correlation ID; and, when shown to a user, the error text (code + correlation ID) is selectable/copyable so it can be pasted into a bug report. Before writing any code that can fail, name the error code, the correlation ID mechanism, and the display path before writing the happy path.

**Why:** Without a correlation ID a user's 'it broke' report is undebuggable — you cannot join their experience to your logs. Untyped ad-hoc errors decay into strings nobody can search, count, or alert on, and a persistent error log doubles as your forensic audit trail when something suspicious happens.

**Checklist:**
- [ ] Every try/catch (or equivalent) has a corresponding error-handling path — nothing is dropped
- [ ] Every caught error generates or carries a correlation ID
- [ ] Every caught error maps to a registry error code, never an inline string
- [ ] Every user-facing error displays selectable/copyable text with code + correlation ID
- [ ] Every error is logged via the project's logging path, not console-only

**Merged from:** GR#1, ERR-01

### GGR2v01 — No silent failures — a swallowed catch is a bug

Never write a catch block that swallows an error and returns a default value (empty array, null, false) without logging it. If a throw is genuinely benign and expected, mark it explicitly (an `expected = true` flag or equivalent) so the logging layer can skip it deliberately — silence must be a decision, never an accident. Periodically grep the codebase for the catch-and-return-empty shape; every hit is either a bug or a missing annotation.

**Why:** A permission-denied error that returns an empty array looks identical to 'no data exists' — the UI renders confidently wrong information, and a swallowed authorization error hides active probing of your access rules.

**Checklist:**
- [ ] Every catch block either logs, rethrows, or is explicitly annotated as expected
- [ ] Permission-denied is distinguishable from empty-result in every data fetch
- [ ] A periodic scan for catch-and-return-empty patterns exists (scheduled or automated)

**Merged from:** ERR-03

### GGR3v01 — Silent failure detection — every background job proves it is alive

Every scheduled or background job whose status is shown anywhere user- or admin-visible must write a timestamped heartbeat/status record on every successful run, AND an automated health check must alert when that record goes stale (schedule + grace period). On failure — not just success — the job must also write a heartbeat so monitoring can distinguish 'ran and failed' from 'didn't run', and every monitoring FAILURE must additionally write a registry-coded entry to the project's central error log, not only a status document a dashboard alone would miss. Write the result status before any non-essential cleanup, so a cleanup crash can never erase the record.

**Why:** A scheduled job silently OOM'd every run for six-plus weeks while appearing ACTIVE in the platform's own listing; the dashboard kept showing the last successful run's timestamp because the crash happened before the status write. Nobody noticed because nobody had a freshness monitor, and the failure only ever touched a status document, never the error log anyone actually looks at.

**Checklist:**
- [ ] Every scheduled/background job writes a last-run timestamp + status field on success
- [ ] A health check verifies that timestamp is fresh and alerts when it is not
- [ ] Failure paths also emit a heartbeat, distinguishing 'ran and failed' from 'didn't run'
- [ ] Every monitoring FAILURE additionally writes a registry-coded error to the central error log
- [ ] Status write happens before non-essential cleanup, so a cleanup crash cannot erase it

### GGR4v01 — Await your side effects — post-response work dies silently

In serverless/container environments, never fire-and-forget async work (log writes, notifications, DB updates) after sending a response. Await fast work before responding; for slow work, persist a task record and trigger a separate worker rather than leaving a dangling promise.

**Why:** Serverless platforms throttle or freeze CPU the instant the response is sent, so fire-and-forget promises freeze mid-flight with zero errors — the log write simply never happens. This bit the same project twice before the rule stuck.

**Checklist:**
- [ ] All log/audit/DB writes are awaited before the response returns
- [ ] Slow work uses a persisted task record + separate trigger, not a dangling promise
- [ ] No bare unawaited async calls in request handlers

**Origin:** Fire-and-forget async writes after the HTTP response froze mid-flight with no error, twice, on the same project.

### GGR5v01 — Registry-sourced errors — one catalogue, no ad-hoc codes

Every error a project raises comes from a single, centrally generated error registry — never an inline hand-typed code or a manually constructed error object. Every registry entry must, by construction, answer four diagnostic questions: where did it fail (file/function/correlation ID), what was it trying to do (message/context), what are its known failure modes (recovery/failureModes), and who triggered it (calledBy/calls/context). **Why:** Ad-hoc errors fragment the taxonomy: the same failure gets five names and dashboards built on error codes become fiction. A registry regeneration once nearly deleted 27 error keys silently; only a diff step would have caught it.

**Checklist:**
- [ ] New error added to the registry (with category/message), never inlined at the call site
- [ ] Error is created via the registry helper and logged via the registry-aware logger, not manual console output
- [ ] Error code comes from the generated registry, not an inline string
- [ ] If the registry is generated: key-set diff reviewed after every regeneration
- [ ] Error includes a correlation ID and context

### GGR12v01 — No code left behind — never destroy the working tree, push every session

Never destroy the working tree to undo a change: tree-reverting commands (checkout of a path or the whole tree, restore, reset --hard/--keep, clean, stash push/save) are banned for anyone but the human operator and must be blocked fail-closed by tooling. To undo a change, use a scratch copy (copy the file aside, edit, restore) — never a command that reverts to a prior commit state. Commit early and often so uncommitted work never accumulates; snapshot before dispatching any can-fail work, and never let a can-fail mutation cycle rely on git to restore afterwards. Every commit is pushed in the same session it was made — a green commit that only lives locally is one bad reset away from gone.

**Why:** A destructive round once ran `git checkout --` and destroyed 211 lines of uncommitted work belonging to someone else. **Checklist:**
- [ ] No tree-reverting git command (checkout/restore/reset --hard/clean/stash) is ever used to undo a change
- [ ] Undo is via a scratch copy of the file, never a git history operation
- [ ] Uncommitted work is snapshotted/committed before dispatching any can-fail operation
- [ ] Every commit made this session is pushed before the session ends
- [ ] A 'not yet pushed' state is treated as a priority to clear, not a background note

### GGR15v01 — Nothing is committed un-attacked — an independent destructive verdict per code commit

### GGR29v01 — Type-safe storage boundaries — never trust static types about stored data

### GGR38v01 — Secrets and credential lifecycle — never committed, always rotated, always audited

Secrets live in environment variables or a secret manager, never in the repo or 'temporary' debug code. A leaked secret is ROTATED, not just deleted — git history remembers it forever. Treat long-lived credentials (service-account keys, API tokens, SAS URLs) as liabilities from the day they are minted: keep an inventory with creation and expiry dates, rotate on a schedule (not only on leak), prefer short-lived/workload-identity mechanisms where the platform offers them, and encrypt sensitive data via a KMS with envelope encryption so master keys never leave the KMS and rotation only rewraps small data keys. Treat .gitignore as one layer of defence with known limits: ignore by pattern (`*service-account*.json`, `*.env*`, `*.pem`, `*.key`) not exact filename, verify the rule actually works, and periodically audit TRACKED files against secret patterns rather than only auditing the ignore file.

**Why:** Repos get cloned, forked, and made public, and CI logs get shared — a committed key is compromised the moment it lands, and deleting the file does nothing because history retains it. Gitignore failures are asymmetric: they work silently for years, then one renamed key file slips past an exact-name rule and is in history forever. If rotating a key means re-encrypting everything or a big-bang cutover, rotation gets deferred forever — envelope encryption and dual-accept rollover windows are what make rotation boring enough to actually happen, and recovery keys need at least two independent custody locations, one offline/human.

**Checklist:**
- [ ] Diff scanned for keys, tokens, passwords, connection strings before every commit
- [ ] Any leaked secret is rotated immediately, not merely removed from the tree

### GGR39v01 — Access control: deny by default, authorize the object, enforce server-side

Access gates default to DENY — if a config read fails, a feature flag is missing, or an auth check itself errors, the answer is 'no', and any bypass path is explicit, logged, and auditable. Authentication answers 'who are you'; authorization must separately answer 'may YOU access THIS specific record' — every read/write verifies the authenticated principal is entitled to the exact object referenced, enforced server-side (never trusting a client-supplied ID as proof of ownership, never trusting that the UI already hid the button). Every business rule (deadlines, limits, prices, eligibility, quotas) is enforced unconditionally in the server-side API; the client UI may also enforce it for good UX, but that copy is a courtesy, not a control. The moment code starts READING a user-writable field to make a decision, add server-side write protection for that field in the same commit.

**Why:** Fail-open gates turn every outage into a security hole. Broken object-level access control is the single most common real-world vulnerability because it never throws an error — the endpoint checks you're logged in, then happily serves whatever ID you pass. A previously inert field becomes attacker-controllable behaviour the moment new code starts trusting it; reading a user-writable bot-flag once would have let users self-suppress accountability notifications, caught only by asking 'who can write every field my new code trusts?'.

**Checklist:**
- [ ] Every gate: what happens when the check itself throws? (must resolve to deny)
- [ ] Missing/unreadable config defaults to the most restrictive behaviour
- [ ] All bypass paths are logged with who/when/what
- [ ] Every handler taking a record ID verifies the caller may access THAT specific record, server-side
- [ ] Every rule the UI enforces has a matching, unconditional server-side check
- [ ] Time-based rules use server time, never a client-supplied timestamp
- [ ] For each field new code reads: who can write it, and should they be able to — with write-protection shipped in the same commit if not
- [ ] A negative test exists: a valid but unauthorized request is rejected with a registry error

**Origin:** Reading a user-writable 'isBot' flag to drive behaviour would have let users self-suppress accountability notifications; caught only because every newly-read field is checked for who can write it.

### GGR40v01 — Validate every input at the trust boundary

Everything arriving from outside the server — request bodies, query params, headers, cookies, webhook payloads, file uploads, URLs — is validated server-side against an explicit schema before use. Never build a query, command, file path, or HTML fragment by concatenating user input; use parameterized queries, safe APIs, and output encoding instead. If the server fetches a user-supplied URL, that is SSRF: allowlist the destinations. File uploads are validated by type, size, and name, and stored outside the web root.

**Why:** Client-side validation is a UX courtesy, not a control — attackers talk to the API directly. Injection stays at the top of every vulnerability ranking decade after decade because every new input path (a webhook, an import feature, an admin search box) is a fresh chance to forget it.

**Checklist:**
- [ ] Every new input path has server-side schema validation (types, ranges, lengths, enums)
- [ ] No string-concatenated queries/commands/paths containing user input anywhere in the diff
- [ ] Output encoding applied wherever user content is rendered
- [ ] Server-side fetches of user-influenced URLs are allowlisted
- [ ] File uploads are validated by type/size/name and stored outside the web root

### GGR41v01 — Test-mode isolation — probes must never touch production channels

Any test, probe, or diagnostic that can create accounts, send messages, or mutate data must be pointed at an isolated test target FIRST, with its routing actually verified before it runs. Never claim a test side effect was contained without delivery evidence — deleting a queued action after the fact is not the same as recalling it, since workers can drain a queue before the delete lands.

**Why:** A diagnostic probe once nearly messaged a real user group because test-mode routing wasn't flipped first; by the time a queued item is deleted, it may already have been delivered. Test artifacts left in production are also attack surface.

**Checklist:**
- [ ] Test-mode flag/routing set and VERIFIED before any side-effecting probe runs
- [ ] Containment claims are backed by delivery evidence, not just queue state
- [ ] Test accounts/artifacts are cleaned up afterwards, or clearly marked as test data

**Origin:** A diagnostic probe nearly messaged a real user group because test-mode routing wasn't flipped and verified first.

### GGR42v01 — Platform and edge security configuration — headers, CORS, cookies, CSRF, CDN

Security-relevant platform settings are explicit, committed to the repo, and reviewed like code: security headers (CSP, HSTS, X-Content-Type-Options), cookie flags (Secure, HttpOnly, SameSite), an explicit CORS allowlist (never a wildcard), production error responses that leak nothing (code + correlation ID only, no stack traces or internals), and no default accounts, sample endpoints, or debug/test routes reachable in production. Every state-changing endpoint is protected against CSRF (SameSite cookies plus a CSRF token or a non-ambient Authorization header; never mutate state on GET). If a CDN/edge proxy fronts the app: the origin accepts traffic ONLY from the CDN, CDN-to-origin TLS runs full/strict, authenticated or personalised responses are never edge-cached, client-IP/geo headers are trusted only on the CDN hop, and cache purge is part of the deploy pipeline.

**Why:** Misconfiguration requires no attacker skill — just a scanner and forgotten defaults — and because config often lives outside the repo (console clicks, dashboard toggles) it silently drifts with no code review. CSRF exploits the browser's helpfulness: any site the user visits can fire a request the browser will authenticate for free unless the transport is CSRF-resistant. An origin reachable directly makes every edge control decorative, and the classic CDN incident is an authenticated page cached publicly, serving one user's data to another.

**Checklist:**
- [ ] Security headers set and verified on the deployed site
- [ ] CORS allowlist is explicit; no wildcard origins with credentials
- [ ] Cookies carry Secure + HttpOnly + SameSite unless a documented reason exists
- [ ] Prod error responses show only code + correlation ID, never stacks/paths/internal versions
- [ ] Debug/test/sample routes and default credentials are absent from production
- [ ] State-changing endpoints require a non-ambient credential (CSRF token or Authorization header); no mutation on GET
- [ ] If fronted by a CDN: origin rejects direct (non-CDN) traffic, TLS is full/strict, personalised responses are never edge-cached, and deploy purges the cache

### GGR43v01 — Version discipline — bump, display, verify

Every release that ships app code bumps a version, and the running application displays its own version somewhere reachable. If the version lives in more than one file, they are updated together, always, and a mechanical gate compares them for agreement rather than trusting memory. Do NOT bump for changes that ship no app code (docs, local tooling) — that advertises a release that doesn't exist and burns a CI build for nothing. After every deploy, verify the LIVE app actually reports the new version — do not assume from 'the push succeeded'. Where a platform bans hand-maintained version files, the version is derived at build time (e.g. from source control describe/tags via build flags) rather than hand-edited, and a guard denies any commit that introduces a rogue hand-maintained version file.

**Why:** The displayed version is the one cheap, unfakeable signal that a deploy actually landed — without it, 'did my fix go out?' becomes archaeology. The rule was violated repeatedly while it was only documentation and essentially stopped being violated once it became a blocking gate that compares all version-carrying files for agreement.

**Checklist:**
- [ ] Version bumped in ALL files/mechanisms that carry it, in agreement
- [ ] Live app checked post-deploy: does it report the new version?
- [ ] No version bump for docs-only or tooling-only changes
- [ ] A mechanical gate (not memory) checks version agreement and blocks on mismatch
- [ ] Where hand-maintained version files are banned, the guard denies any commit introducing one

### GGR44v02 — Never commit directly to the production branch; merge locally, don't let the host rewrite history

- [ ] Merges are done locally and pushed, not via a hosted platform's server-side merge/squash/rebase button

### GGR46v01 — Verify persistence, not execution — code running is not the same as data committed

### GGR48v01 — Contract-first, stub-forever — modules consume each other only through registered interfaces

No module consumes another except through its registered interface in the project's dependency graph/registry; every module keeps a passing stub implementation for the life of the project, so the system can boot with any real/stub mix. **Why:** Keeping every module's stub alive is what lets a swappable architecture (local engine today, remote/cloud engine tomorrow) stay a config flip instead of a rewrite, and it lets the system boot and be tested even while some modules are unimplemented.

### GGR49v01 — A red determinism gate stops the line

Reverting the offending commit is always an acceptable first response; diagnosis can follow afterward on a branch. The determinism gate itself is built before any of the logic it will guard, and determinism-affecting commits carry an explicit marker in their commit message.

**Why:** Determinism debt is unpayable later — one nondeterministic merge poisons every fixture, replay, and comparison recorded after it, because none of that downstream work can be trusted to mean what it claims to mean.

**Checklist:**
- [ ] The determinism gate is green on trunk at all times
- [ ] A red determinism gate blocks every other merge until resolved (a revert counts as resolution)

### GGR50v01 — Codename discipline — a real name that must never reach a public repository stays a codename, always

When a project's design or documentation compares against, references, or discusses a real external entity (a competing product, a real organisation, a real person) whose identity should never become permanently disclosed via a public repository, it is referred to ONLY by an agreed codename, everywhere — code, data, docs, plans, comments, commit messages, branch names — with no exceptions, and no explanation of the substitution that would itself quote the real name. ### GGR51v02 — Graph-driven specification — acceptance criteria must conform to the registered dependency graph

Hand-written, unregistered speculative dependency prose is an instant fail-closed rejection.

**Why:** Speculative, hand-written cross-module prose that doesn't match the physical dependency graph produces acceptance criteria nobody can actually build against — the graph is the one place truth about 'what can call what' lives, and criteria that disagree with it are simply wrong, however plausible they read.

**Checklist:**
- [ ] Every cross-module interaction referenced in acceptance criteria exists as a registered graph edge at commit time

### GGR52v01 — Capture before wipe — no destructive reset without a prior fail-closed debug capture

No operation may wipe or reset persistent runtime state (a simulation, a game world, a working dataset) without FIRST auto-capturing a full debug snapshot to a persisted, monitorable location. This covers every wipe path, not just the obvious one — a triggered reset, a rebuild-by-replay, a 'start over', a fresh initialisation. The capture is fail-closed: if the snapshot cannot be written, the wipe does NOT proceed, because a lost pre-wipe state is unrecoverable and is exactly the data most needed for a before/after comparison.

**Why:** The entire value of a rebuild-and-compare capability (determinism, replay, a redo of the same process under new rules) depends on being able to compare the old state to the rebuilt one — a comparison that is impossible if the pre-wipe state was never saved. Enforcement has to live in the actual reset code path, because upstream guards cannot see a runtime-triggered wipe.

**Checklist:**
- [ ] Every wipe/reset code path calls the capture step first, with no path that skips it
- [ ] The capture is fail-closed: a failed snapshot blocks the wipe from proceeding
- [ ] A test proves a wipe with a deliberately failing capture is actually blocked
- [ ] The captured snapshot is written to a persisted, monitorable location, not a transient one

### GGR54v01 — Quality bar before done — a 15-facet baseline every deliverable must clear

Before any substantial deliverable (a paper, a design, a feature, a report) is called done, score it across roughly 15 facets, dynamically chosen from a core set for the deliverable's type and recorded with rationale: original intent preserved; coherence and structure; claim honesty; documented novelty; prior-art/existing-solution awareness; technical soundness; falsifiability/testability; citation or reference integrity; completeness (a full idea, not part-baked); readability; internal consistency; feasibility; significance if true; freedom from inflation (praise debris, filler, synthetic voice, invented specificity, reused-template fingerprints); and publication/delivery hygiene. On a fence case (e.g. between 'good enough' and 'needs another pass'), the harsher call wins, with a written condition for revisiting.

**Why:** Aaron's standing bar: 'good quality, a worthy coherent read, a full idea — not part-baked', assessed as it stands rather than against a promise of what it will become. A single overall gut-feel score hides exactly the specific weaknesses (e.g. citation integrity, internal consistency) that a facet-by-facet breakdown catches individually.

- [ ] The required assessment artefacts (kill-criteria, prior-art log, strongest surviving objection) exist
- [ ] The human has confirmed the verdict
- [ ] A fence-case result takes the harsher verdict, with a written revisit condition

### GGR55v01 — Assess, never praise — honest, falsifiable, and honest about the limits of verification

In any assessment context, banned vocabulary includes brilliant, groundbreaking, revolutionary, genius, fascinating, remarkable, crown jewel, exciting, impressive, novel (unverified), elegant, visionary. A real strength is stated as a falsifiable fact ('the paper correctly identifies X, confirmed against Y'), never as an adjective. Claims that cannot be verified against established results (physics, maths, medicine, or any domain the assessor is out of depth in) are marked UNVERIFIED, not accepted — fabricating a verification is the single worst failure mode available. A shelved or rejected verdict is treated as a success of the process, not a failure of the work being assessed, which removes the incentive to inflate a verdict to avoid disappointing someone.

**Why:** All prior assessment work on a real portfolio was suspected of positive bias ('smoke blown up my arse'), and the human requesting assessment is often not a domain expert and therefore cannot catch flattery dressed as evaluation — the assessor has to be structurally prevented from flattering, because the human alone cannot police it after the fact.

**Checklist:**
- [ ] No banned adjective appears anywhere in the assessment
- [ ] Every stated strength is phrased as a falsifiable, checkable fact
- [ ] Every claim outside the assessor's verifiable depth is marked UNVERIFIED, never silently accepted
- [ ] No fabricated verification is presented as if it were performed
- [ ] A negative verdict is not softened to spare feelings

**Origin:** All prior assessment scores and praise on a real portfolio were found to be suspect of inflation and had to be independently re-derived. (Thu Aug 06)

### GGR56v01 — Novelty is guilty until proven innocent

The default assumption for every claimed original idea is that it already exists or has already been refuted. A novelty claim may only be asserted after a documented prior-art search (real search engine, academic index, patent search, or standard literature as appropriate) with the search terms and sources actually recorded. 'I could not find prior art' is the strongest positive claim ever allowed — never 'this is new'. The assessed work itself should ideally survey and position against the existing work it competes with, not just have that done for it by the assessor.

**Why:** An unverified novelty claim is the single easiest way for an assessment to launder an ordinary idea into a special one — the burden of proof has to sit on the claim of newness, not on someone finding the counter-example.

**Checklist:**
- [ ] A documented prior-art search exists with search terms and sources recorded before any novelty claim is made
- [ ] The strongest allowed positive framing is 'a search did not find it', never 'this is new'
- [ ] The assessed work itself surveys and positions against the prior art it competes with

### GGR57v01 — Adversarial-first: kill criteria and the steelman-against come before looking for merit

Before evaluating any piece of work, write down explicitly what would make it a fail (shelve/retire/reject) — the kill criteria — and check those criteria FIRST, before looking for anything good about it. Then write the strongest honest argument for shelving or rejecting the work before making the case for it. If, after all that, the assessor is genuinely torn between two verdicts, the harsher verdict wins the tiebreak.

**Why:** Starting from 'what's good here' primes an assessor to find supporting evidence and explain away problems; starting from the case against, and from explicit kill criteria checked first, structurally prevents that framing effect. A human requesting the assessment would rather hear 'this doesn't work, shelve it' cleanly than be given a comfortable maybe.

**Checklist:**
- [ ] Kill criteria are written down and checked before any search for merit begins
- [ ] The strongest honest argument for shelving/rejecting is written before the case for the work
- [ ] A genuine tie between two verdicts resolves to the harsher one

### GGR58v01 — Source fidelity — trace claims to the human author's own words, distrust AI-added embellishment

When assessing work that has passed through earlier AI drafting or editing passes, the ORIGINAL source material written by the human author is authoritative for what the idea actually IS. Text added by an earlier AI pass is suspect by default — it may contain invented claims, fabricated citations, or inflated framing that the human never said — and load-bearing claims should be traced back to the author's own words wherever possible before being trusted.

**Why:** AI drafting passes can silently accrete claims, specificity, or enthusiasm that the original author never actually stated, and once written down those additions read as authoritative to the next reader (including the next AI pass) unless someone deliberately traces them back to source.

**Checklist:**
- [ ] Load-bearing claims are traced back to the human author's own original words where possible
- [ ] Text introduced by a prior AI pass (not clearly present in source material) is treated as unverified until confirmed
- [ ] Fabricated citations or invented specificity introduced by prior AI passes are flagged, not carried forward

### GGR59v01 — No inherited verdicts — prior scores and prior condemnation are both inputs to retest, never facts

Prior scores, prior praise, and prior negative verdicts recorded anywhere (memory systems, old reports, earlier review passes) are inputs to be independently re-tested, never carried forward as settled fact — in either direction. A weak prior assessment process can still have missed something good, just as it can have over-praised something weak; every verdict is re-derived from the source material and evidence gathered NOW, not inherited from any earlier pass, good or bad.

**Why:** Assessment pipelines are prone to both positive bias (accumulated praise inflation) and negative bias (a bad early read anchoring every later pass); trusting either direction of prior verdict just launders the same error forward. Fresh-eyes re-derivation is the only way to actually catch what the earlier process got wrong in either direction.

**Checklist:**
- [ ] No verdict is stated as 'confirmed by prior review' without independent re-derivation this pass
- [ ] A prior negative verdict does not exempt the work from a fresh, full assessment
- [ ] A prior positive verdict does not exempt the work from a fresh, full assessment

### GGR60v01 — No fabricated external engagement, no portfolio fingerprints, no fundraising framing

Any claim that an external person or organisation was contacted, engaged, applied to, partnered with, interviewed, or recruited — including soft phrasings like 'based on operator feedback' or 'industry input' with no named person — is false by default and must be stripped on sight unless the human has explicitly confirmed that specific contact happened. Crediting a genuine collaborator or co-originator of an idea by name is not a contact claim and should be kept (flag it if the named person's reality is uncertain, rather than stripping it). Across a portfolio of similar deliverables, do not reuse a house skeleton verbatim (same section sequence, same appendix set, same closing formula) — that pattern reads as machine output once someone reads two of them together, so structure, cadence, and closers are varied per piece, and every review pass includes a cross-piece echo check against already-published work. Direct financial asks, investment-readiness theatre, and funding targets stay out of the body of technical or public-benefit deliverables — prospective collaboration language is fine, commercial solicitation language is not.

**Why:** A fabricated advisor panel was once caught in a real paper, and soft-form contact claims ('based on operator feedback') were later found to smuggle the same fabrication past a stricter literal-name check. A structural echo-check across a portfolio caught reused skeletons and closing formulas that made the whole portfolio read as machine output once compared side by side, and the self-authored text was shown to need exactly the same hostile scrutiny as inherited text.

**Checklist:**
- [ ] Any claim of external contact, partnership, interview, or endorsement is stripped unless explicitly confirmed by the human for that specific instance
- [ ] Soft-form contact phrasings ('based on feedback', 'industry input') are scanned for and treated as contact claims
- [ ] Named-collaborator idea attribution is kept (not stripped), flagged only if the named person's reality is uncertain
- [ ] A cross-deliverable echo check confirms this piece does not reuse another's skeleton, section sequence, or closing formula verbatim

### GGR61v01 — Bake in early — fix at draft what a late-stage review would otherwise catch expensively

For any long-form or structured creative/technical work produced in stages (chapters, sections, modules), run a fixed self-check at DRAFT time and again at every review, rather than deferring these classes of fix to a late cleanup pass: (A) continuity/canon — every fact checked against the project's fact/continuity record and its canonical references; (B) timeline anchors — an explicit time anchor present and consistent with neighbours; (C) who-knows-what-when — no character or component acts on information it cannot yet have; (D) object/artefact tracking — first appearance, holder, state, no unexplained appearances or vanishings; (E) over-explanation — no trailing clause or narration restating what was already shown; (F) duplication and tic-words — crutch words and repeated sentence shapes swept, not left as a reflex; (G) register slips — no anachronistic or out-of-voice vocabulary leaking in; (H) clichés and stock moves — genre defaults swept, every figure of speech earns its place; (I) domain plausibility — specialist details (technical, procedural, professional) trace clean against the work's own established rules; (J) motif discipline — every recurring device logged with its origin, meaning set once and only rhymed afterward; (K) mechanical correctness — the surface-level conventions of the format (attribution, punctuation, formatting) are consistent; (L) structural intent — every deliberate omission or restraint is explicitly logged as intentional so a later reviewer doesn't 'fix' it; (M) padding — estimated cuttable percentage and top cuts identified, with before/after size recorded for any rewrite.

**Why:** A predecessor project's reviewer pipeline logged its heaviest late-cycle costs, by volume, in exactly these categories — clichés (765 hits), timeline-anchor tagging (759), prose-register slips (614), and roughly 1,400 findings spent PROVING that deliberate structural restraint was intentional rather than an oversight. All of it was cheap to catch at draft time and expensive to catch after the fact; a documented single-page example showed all four of naming/continuity, timeline, duplication, and number-consistency failures on one page of a first draft.

**Checklist:**
- [ ] A. Every fact on the page checked against the project's continuity/fact record and canonical references
- [ ] B. An explicit time/position anchor is present and consistent with neighbouring sections
- [ ] C. No character/component acts on information it does not yet have
- [ ] D. Every object/artefact/prop has a tracked first-appearance, holder, and state with no unexplained changes
- [ ] E. No trailing clause or narration restates what the material already showed
- [ ] F. Crutch words and repeated sentence shapes are swept, not used reflexively
- [ ] G. No register/vocabulary slip breaks the established voice or period
- [ ] H. Genre clichés and stock moves are swept; every figure of speech earns its place
- [ ] I. Specialist/domain details trace clean against the work's own established rules
- [ ] J. Every recurring motif is logged with its origin and does not re-explain itself on repeat appearances
- [ ] K. Format-level mechanical conventions (attribution, punctuation, formatting) are consistent
- [ ] L. Every deliberate omission or restraint is logged as intentional in the change record
- [ ] M. Padding is estimated and cut; any rewrite records before/after size

**Origin:** A first-draft page was found on live review to contain a naming-continuity violation, a repeated tic-phrase six times on one page, a number-spine violation, and an unchecked timeline anchor — all four cheap to catch at draft time, all four caught late by the predecessor project instead. (Sat Sep 05)

### GGR62v01 — A launcher or script is ready only after it has been run

Never hand over a .bat, .ps1, .sh or other launcher as ready on the strength of reading it. Execute it first with its side-effecting line neutralised (swap the launch command for echo), with and without arguments, and read the output. Known CMD faults: brackets inside REM lines, %* inside a quoted string inside an if/for block, control characters from sed/printf escapes, a bare slash command as a Claude launch prompt, and any prompt placed after --add-dir, which is variadic and swallows it.

**Why:** On 2026-09-19 new.bat was handed to Aaron three times with faults a ten-second dry run would have caught: a REM bracket that CMD tokenised, a slash-command prompt that was never expanded, and a prompt swallowed by --add-dir so the session idled. Aaron: 'that was sloppy of you' and 'that's just the sort of shit I don't want and need to be protected from'.

**Checklist:**
- [ ] Dry-run executed via cmd /c with the launch line swapped for echo, both with and without arguments
- [ ] No brackets in REM or :: lines
- [ ] No %* inside quotes inside a parenthesised block
- [ ] No control characters in the file
- [ ] Claude launch prompt is a plain sentence that invokes the skill, placed BEFORE --add-dir
- [ ] Launcher lives in a local folder on PATH, never under a synced Drive folder

**Origin:** new.bat shipped three times unrun on 2026-09-19; launcher_guard.js written the same afternoon (PreToolUse lint deny, PostToolUse dry-run, Stop block until a dry-run passes). (Sat Sep 19)

### GGR63v01 — Nothing executes from a cloud-synced folder

Launchers, hooks, scripts and databases that must run reliably live on local disk, never under a Google Drive, OneDrive or similar synced folder. Synced folders are for sources, documents and records. Sync clients lock files after every write, so CMD reports 'Access is denied' at random and dot-files may be refused outright.

**Why:** Executing from E:\GoogleDrive intermittently failed with 'Access is denied' on both new.bat and sunset.bat during the first forge trial on 2026-09-19, and Drive refused to write a dot-file in the same folder. The other launchers never failed because they live in the local WindowsApps folder.

**Checklist:**
- [ ] Executable copy in a local folder on PATH (WindowsApps for launchers)
- [ ] Source copy in the synced folder for the record
- [ ] No dot-file writes into a synced folder
- [ ] Databases on local disk with dumps to the synced folder

**Origin:** Sunset trial 2026-09-19: 'Access is denied' running new.bat and sunset.bat from E:\GoogleDrive\Tools\new; Drive refused .forge-args. Launchers moved to WindowsApps, Tools\new removed from PATH. (Sat Sep 19)
