## v22 — THE CLOUD ENGINE APPROACH (your "engines up" instruction)

**Full design document: `docs/planning/azure-cloud-engine-design.md`** (BOW: FEAT-2326609775). The approach in five lines:

1. **inc1 — "one engine up, one round-trip measured" (~1 day, ~£2/month):** `cmd/metroserve` (the Go durable host that already exists) in a container on **Azure Container Apps**, `uksouth`, reusing your existing ACR + environment; Azure Files mounted for durability with ZERO new Go code; min-replicas 0, max 1. The only code change is a `/health` endpoint (none exists). The webconsole's `protocolClient.ts` already exists flag-gated — client work is near-zero. **The smoke test IS the deliverable:** 1,000 round-trips (p50/95/99), a 360-tick batch, journal-append latency against Azure Files, kill-the-revision recovery. Pass = round-trip p95 <100ms AND append p95 <25ms. Your "minimal small, smoke test, then increment" — literally.
2. **NLB/API gateway: DEFERRED with a written trigger, not vibes** — Container Apps ingress already IS an L7 load balancer with TLS and sticky routing; a gateway earns its place when anyone besides you gets a link (Q100144).
3. **Redis: DEFERRED with a written trigger** — the engine is structurally one-replica-per-city (one live WS per transport, no file lock on the store), so there is nothing to share yet. The trigger is written in the doc.
4. **"Database or tiny files?" — NEITHER, and the honest answer forks on Q100138.** Your webconsole savepoint holds NO individual people (population is one number; the file is buildings, ~302KB compressed at 49k buildings). The GO engine stores real citizens at ~75B each → 100m = 7.5GB. Recommendation: **Blob Storage, chunked at boundaries the engine already has** (cold shards / the spatial-partition sectors), as a second implementation of the already-registered persist Store interface — no new code.json edge needed. Tiny-files would cost ~£4 in PUTs per save at scale; SQL ~£50/mo for query capability the sim never uses.
5. **Background threads offloaded** = the cloud engine runs your city continuously (it already ticks itself and snapshots on cadence); the browser stays the responsive UI. Divergence detection uses the converge harness's 3-tier tolerance contract — byte-identical TS↔Go parity was proven the wrong bar.

**Three warnings the design surfaced, worth your eyes:** the protocol handshake refuses any client whose BUILD STRING differs, so deploy-on-green-main would lock out every open tab several times a day (Q100145 — relax to protocol-semver); turbo ships at 6.25 game-days/sec, not the 3 you ruled (Q100147 — which is right?); the journal fsyncs per record, a real risk on a network filesystem, hence the inc1 latency gate.

## THE HEADLINE — your finish line changed everything

You answered Q100114 with **"finish line is 100m"**. That is not a tweak, it re-scopes the project, so I modelled it properly rather than nodding. Numbers below are measured, not estimated.

**The map is a town, not a metropolis.** 440×260 tiles at 50m = 22km × 13km = **286 km²**, which is 0.18× Greater London. 100m people on it would be 349,650/km² — **7.9× Dhaka**, the densest city that has ever existed. No building design fixes that.

**Space: your ×50 gut was right, to the number.** ×50 = 14,300 km² ≈ Tokyo metro (13,500 km², 37m people). 100m there is ~7,000/km²: denser than London, sparser than Manhattan. Believable. At ×10 you'd need 103% of every tile; at ×50 you need 20.6%.

**But space is not the blocker — buildings are.** Your city is 29,831 buildings for 1.9m people = 15,700 per million. At 100m that's **1.57m buildings**, and at the measured 1.853µs/building/tick that's a **2.9-second tick**. The playable budget (100ms) is ~54,000 buildings.

**And the real wall is memory, not time.** Your 30k city compresses to 550,307 bytes. 1.57m buildings extrapolates to a **~27MB savepoint against a 5MB localStorage quota**. A 1.57m-building city cannot be *saved* at any tick speed.

**So the path to 100m is density, not scale.** At ~10× people-per-building, 100m is **~157,000 buildings**: ~3MB savepoint, ~4ms steady tick, ~25ms build burst. Playable. That makes the consolidator and the ultra-dense towers **critical path, not flavour** — and it's why I did NOT recommend moving the heavy path to Go (it would duplicate 29 derivations across two languages to buy a constant factor that density gives free).

Full spec landed: `docs/planning/acceptance/FEAT-2326609764.md` (spatial-partition tick, 26 ACs).

## QUESTIONS Q100118–Q100137 — 20 new, each with my recommendation

**Q100118 — the ×50 map: one map or a frontier?** ×50 is 5.7m tiles. A: ONE 3,100×1,840 map, generated lazily (empty terrain is derivable, so memory stays sane). B: the current map plus expansion "parcels" you unlock and annex at levels 19-25, each a chunk of terrain. **Rec: B** — it makes land a progression reward (your Q100105 answer), avoids a 5.7m-tile allocation on day one, and lets us ship expansion incrementally instead of one big-bang map.

**Q100119 — what's at the edge?** When the map is 22km wide today, the border is arbitrary. At 190km it needs meaning. A: coastline/sea on one side (Folkestone is coastal — it's the real geography). B: neighbouring regions you later trade with (ties to Q100107). C: mountains/impassable terrain. **Rec: A+C** — real Kent geography where it exists, terrain elsewhere; B arrives with regions.

**Q100120 — density vs sprawl, which does the game REWARD?** Right now sprawl is punished only by land. If 100m needs ~157k buildings not 1.57m, the game should actively push density. A: economic — dense buildings get better cost-per-capita and lower per-building upkeep. B: mechanical — an upkeep penalty per BUILDING regardless of size, so 20 huts cost more to run than one tower. C: both. **Rec: C** — B is the one that actually changes behaviour, and it's honest (more buildings = more roads, more services, more admin).

**Q100121 — the 1.57m-building save problem.** A 3MB savepoint sits at the edge of the 5MB localStorage quota even in the good case. A: move saves to IndexedDB now (no practical quota, async, more moving parts).
